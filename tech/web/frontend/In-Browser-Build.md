# 브라우저 내 빌드 런타임

## 정의

서버 컴파일 없이 브라우저 안에서 TypeScript, JSX 소스를 직접 번들링하고 실행해 결과를 즉시 보여주는 런타임. 라이브 프리뷰, 코드 플레이그라운드, AI가 생성한 코드의 즉시 렌더 같은 곳에 쓴다.

## 구성 요소 (mental model)

1. 브라우저 내 컴파일러: esbuild-wasm처럼 WebAssembly로 포팅한 번들러가 클라이언트에서 TS와 JSX를 트랜스파일하고 번들한다. 무거운 작업이라 Web Worker에서 돌려 메인 스레드를 막지 않는다.
2. 가상 파일 시스템(레이어드 파일 저장소): 파일을 소유 범위와 변경 주기로 계층화한다(사용자 편집이 프로젝트 공유, 템플릿, 런타임 파일보다 우선). 모듈을 해석할 때 사용자 편집을 가장 앞에 둔다.
3. 의존성 해석: 매번 npm에서 내려받지 않고 import map으로 런타임에 모듈 경로를 매핑한다. 의존성 조합을 해시로 식별해 동일 조합은 미리 빌드한 산출물을 재사용한다.
4. 격리: 실행을 iframe 샌드박스로 분리해 한 사용자의 컴파일 오류나 런타임이 다른 사용자에게 영향을 주지 않게 한다. CORS나 사설망 접근 문제는 프록시로 우회한다.

## 핵심 원리: 일을 로드 타임에서 빌드 타임으로

프리뷰를 열 때마다 모든 의존성을 받아오면 느리다. 대신 package.json이 바뀔 때 한 번만 설치해 import map과 번들 모듈을 만들어 저장해 두고, 프리뷰를 렌더할 때는 이미 만든 import map과 패키지 파일을 가져오기만 한다. 해시 기반 식별로 캐시 정합성을 지키고, 같은 의존성 조합을 쓰는 프로젝트끼리 산출물을 공유한다.

## 트레이드오프

- HMR을 포기하고 빌드마다 문서를 전체 교체하는 모델은 구현이 단순하고 프리뷰 용도엔 충분하지만, 편집 반영 지연과 상태 보존이 필요한 실개발 환경에는 맞지 않는다.
- 브라우저 컴파일은 서버 왕복을 없애지만 클라이언트 CPU와 메모리를 쓰고 대형 의존성엔 초기 빌드 비용이 크다. 그래서 빌드 타임 사전 준비가 관건이다.
- 사전 설치는 peerDependencies와 버전 충돌을 패키지 매니저에 맡겨 커스텀 리졸버를 피할 수 있다.

## 사례

토스 TOI(AI 어드민 제작 플랫폼)는 Sandpack이 프리뷰마다 npm 의존성을 전부 받던 구조를 esbuild-wasm 번들과 사전 빌드한 import map으로 바꿔 초기 로딩을 47초에서 1.3초로 줄였다.

## 체크포인트

- CDN 스크립트와 스타일만 로드 가능한 CSP 환경에서는 import map이 가리키는 호스트가 허용 목록에 있어야 한다.
- import map은 브라우저 네이티브 기능이라 별도 로더 없이 모듈 경로를 재매핑한다. 지원 범위는 대상 브라우저에서 확인한다.
- esbuild-wasm 컴파일은 Web Worker로 오프로딩해 메인 스레드 반응성을 지킨다.
