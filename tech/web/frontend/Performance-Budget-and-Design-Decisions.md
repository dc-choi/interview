# 성능 예산과 디자인 결정: 빠른 페이지는 설계에서 정해진다

페이지 속도는 구현 마지막에 덧붙이는 최적화가 아니라 무엇을 어떻게 보여 줄지 정할 때 함께 정해진다. 느린 페이지의 비용은 사라지지 않고 방문자가 기다림과 데이터 요금으로 낸다. 첫 화면 전체를 채우는 자동 재생 영상, 굵기가 여러 개인 커스텀 폰트, 첫 화면의 캐러셀, 스크롤 애니메이션, 동작하는 데 수백 KB의 JavaScript가 필요한 페이지는 모두 방문자의 시간과 데이터를 쓰는 결정이다.

## 속도를 정하는 다섯 층

아래 다섯 층은 사례 글이 속도를 좌우하는 요인으로 든 것을 이 vault의 문서에 대응시킨 것이다.

| 층 | 정하는 것 | 자세한 문서 |
|---|---|---|
| 거리 | 방문자와 응답하는 서버 사이의 왕복, CDN 위치 | [[TTFB-and-Search-Crawling\|TTFB와 검색 크롤링]] |
| HTML 생성 방식 | 미리 만들기, 요청마다 서버에서 만들기, 브라우저에서 조립하기 | [[Frontend-Rendering-Models\|프런트엔드 렌더링 모델]] |
| 캐시 정책 | 내용이 바뀌면 이름도 바뀌는 자산은 길게, HTML은 짧게 | [[HTTP-Caching\|HTTP 캐싱]] |
| 리소스 도착 순서 | 첫 화면의 가장 큰 요소가 언제 요청되고 도착하는가 | 아래 LCP 절 |
| 메인 스레드 작업 | 스크립트, 애니메이션과 입력 응답 | [[Browser-Main-Thread\|브라우저 메인 스레드]] |

## 첫 화면의 가장 큰 요소를 먼저 부른다

web.dev는 LCP를 TTFB, 리소스 로드 지연, 리소스 로드 시간, 요소 렌더 지연의 네 하위 단계로 나누고, TTFB와 로드 시간이 각각 약 40%, 나머지 둘이 각각 10% 미만이 되는 배분을 엄격한 규칙이 아닌 지침으로 제시한다(2026-11-25 확인).

- LCP 리소스는 HTML 원문에서 발견할 수 있어야 리소스 로드 지연이 생기지 않는다.
- LCP 이미지는 지연 로딩하지 않는다. web.dev는 이것이 항상 불필요한 로드 지연을 만든다고 적는다.
- LCP 요소가 될 가능성이 큰 `<img>`에는 `fetchpriority="high"`를 둔다. 높은 우선순위를 한두 개보다 많은 이미지에 주면 LCP를 줄이는 데 도움이 되지 않는다.
- 이미지를 작게 만들어도 줄어든 시간이 요소 렌더 지연으로 옮겨 가면 LCP는 그대로다. web.dev는 대부분의 사이트에서 로드 시간이 큰 병목이 아니라고 본다. 바이트를 줄이는 방법은 [[Image-Delivery-Optimization|이미지 전송 최적화]]에서 다룬다.

```html
<!-- 첫 화면에 보이는 첫 카드: 지연 로딩하지 않고 우선순위를 올린다 -->
<img src="/card-1-small.webp" alt="첫 작품" width="640" height="480" fetchpriority="high">
<!-- 처음에 보이지 않는 다음 카드: 지연 로딩 -->
<img src="/card-2.webp" alt="둘째 작품" width="640" height="480" loading="lazy">
```

캐러셀은 첫 장이 LCP 요소가 되기 쉬운데, 슬라이드 전체에 같은 지연 로딩 설정을 일괄 적용하면 첫 장까지 늦게 요청된다(아래 사례). 자동 재생 캐러셀의 접근성 제어는 [[Swiper-Carousel|Swiper 이미지 슬라이드]]에서 다룬다.

## 성능 예산을 먼저 적는다

성능 예산은 지표마다 넘지 않을 값을 정해 두고 디자인과 구현의 변경을 그 값으로 판정하는 방식이다. web.dev가 제시하는 Core Web Vitals의 좋음 기준은 LCP 2.5초 이내, INP 200ms 이하, CLS 0.1 이하이며, 모바일과 데스크톱을 나눈 페이지 로드의 75번째 백분위수로 평가한다. 예산에는 사용자 지표(표시, 입력 응답, 레이아웃 이동, 서버 응답)와 자원 한도(전송량, JavaScript 크기, 가장 긴 작업)를 함께 넣고 측정 조건을 같이 적는다. 초과 항목을 숨기지 않고 남겨 두는 것이 예산을 판단 도구로 쓰는 방식이다. 예산은 이후의 변경이 참조할 수 있는 곳에 둔다. 코딩 에이전트와 일하면 저장소 지침 파일에 예산과 측정 조건을 함께 두는 방식이 그 예다(기준값은 web.dev, 예산의 구성과 보관 위치는 아래 사례에서 뽑은 이 문서의 정리다).

## 빠른 노트북은 최선의 경우다

- Lighthouse의 모바일 기본값은 측정한 무제한 로드를 바탕으로 느린 조건을 계산하는 시뮬레이션이며, Slow 4G(TCP RTT 150ms, 처리량 1,638.4Kbps)와 CPU 4배 감속을 쓴다. 데스크톱 기본값은 RTT 40ms, 10,240Kbps에 CPU 감속이 없다. DevTools의 요청 단위 제한은 실제 패킷 단위의 지연을 근사할 뿐이고, 패킷 단위 도구가 가장 정확하지만 편차가 크다고 Lighthouse 문서는 설명한다.
- 캐시를 비운 첫 로드를 여러 번 재서 중앙값을 본다. 실험실 수치와 실제 사용자 분포(CrUX의 75번째 백분위수)는 구분한다([[TTFB-and-Search-Crawling#측정과 해석|TTFB 측정과 해석]]).

## 사례: 첫 카드를 지연 로딩하던 홈페이지

2026-10-19 게시된 글 Fast is a design decision의 저자는 Lighthouse 시뮬레이션과 비슷한 조건(약 1.6Mbps, 지연 150ms, 저자 노트북보다 4배 느린 CPU)에서 홈페이지 첫 로드 세 번의 중앙값을 쟀다.

- 휴대전화에서 가장 큰 요소는 지연 로딩으로 낮은 우선순위를 받은 캐러셀 첫 카드였다. 약 1.1초에 요청돼 약 2.5초에 도착했고 LCP는 2,544ms였다.
- 휴대전화에는 미리 만든 작은 카드 이미지를 높은 우선순위로 즉시 불러오게 바꾸자 1,320ms가 됐다.
- 파일을 `max-age=0`으로 내보내 페이지를 볼 때마다 약 40개 파일을 다시 확인하고 있었고, 주소 끝 슬래시 리디렉션은 제한한 휴대전화에서 이동마다 약 800ms를 썼다. 화면 밖으로 나가도 계속 돌던 첫 화면(hero) 애니메이션은 데스크톱에서 5초마다 약 446ms를 썼고(120Hz 화면에서는 약 두 배), 화면 밖에서는 멈추게 바꿨다.

같은 글에 실린 예산과 제한한 휴대전화 조건의 실험실 측정값은 다음과 같다.

| 항목 | 예산 | 측정 |
|---|---|---|
| 가장 큰 콘텐츠 표시 | 2.5초 미만 | 1.32초 |
| 입력 응답 | 200ms 미만 | 48ms |
| 레이아웃 이동 | 0.1 미만 | 0.00 |
| 첫 표시 | 1.8초 미만 | 1.32초 |
| 서버 응답 | 200ms 미만 | 381ms(초과) |
| 전송량 | 1MB 미만 | 488KB |
| JavaScript | 250KB 미만 | 209KB |
| 가장 긴 작업 | 50ms 미만 | 78ms(초과) |

서버 응답 초과는 먼 Cloudflare 데이터 센터로의 라우팅 때문으로, 가장 긴 작업은 느린 프로세서에서만 78ms에 이르는 것으로 글은 설명하고, 예산을 이후의 프롬프트가 볼 수 있는 곳에 적어 두라고 권한다.

모두 저자의 측정이며 직접 재현하지 않았다.

## 디자인 결정 점검표

다음은 사례 글의 점검 목록을 바탕으로 이 문서가 정리한 제안이다.

- 공개 페이지의 HTML이 어디서 만들어지는지 확인한다. 브라우저가 조립한다면 미리 렌더링할 방법을 묻는다.
- 방문자 가까이에 CDN 위치가 있는지, 해시된 자산은 길게 캐시하고 HTML은 짧게 두는지 응답 헤더로 확인한다.
- 첫 화면의 가장 큰 요소를 찾아 지연 로딩이나 스크립트 뒤에 묶여 있지 않은지 본다.
- 자동 재생 영상, 폰트 굵기 수, 첫 화면 캐러셀과 애니메이션마다 방문자가 내는 바이트와 메인 스레드 시간을 적고, 그 값을 예산과 비교해 채택한다. 움직임 감소 설정은 [[Browser-CSS-Animation-and-Compatibility|브라우저 CSS 애니메이션]]을 따른다.
- 페이지가 실어 보내는 JavaScript의 양과 용도를 적는다.
