# 웹 기술의 진화와 퇴장 패턴

웹 기술은 단순히 오래돼서 퇴장하지 않는다. 설치와 업데이트 비용, 특정 브라우저나 운영체제 의존, 보안 경계, 접근성과 모바일 호환성처럼 웹의 개방성에 맞지 않는 비용이 커질 때 주류에서 내려온다. 반대로 어떤 기술은 자신이 해결하던 문제가 표준에 흡수되면서 역할이 줄어든다.

## 대표 사례

| 기술 | 해결하려던 문제 | 주류에서 내려온 이유 | 남긴 교훈 |
|---|---|---|---|
| Frameset | 메뉴, 헤더와 본문 영역을 독립적으로 구성 | 주소가 내부 화면 상태를 제대로 표현하지 못해 링크 공유, 북마크와 검색 색인에 불리 | 화면 상태와 URL을 일치시켜야 한다 |
| Flash | 애니메이션, 게임과 풍부한 상호작용 | 플러그인 설치, 반복된 보안 문제, 모바일과의 부조화 | 브라우저 밖 전용 런타임은 배포와 보안 비용이 크다 |
| Silverlight | 기업용 리치 UI와 미디어 앱 | 특정 공급자 생태계와 플러그인에 의존하고 지원 브라우저가 줄어듦 | 공급자 종속은 클라이언트 도달 범위를 제한한다 |
| ActiveX | 브라우저에서 결제와 보안 모듈 등 네이티브 기능 실행 | Windows와 Internet Explorer 종속, 설치 마찰과 큰 권한으로 인한 보안 위험 | 웹의 설치 없는 접근성과 최소 권한을 깨면 운영 비용이 커진다 |
| Java Applet | 브라우저 안에서 Java 프로그램 실행 | 느린 시작, 보안 경고와 플러그인 의존, 브라우저의 플러그인 인터페이스 제거 | 브라우저 샌드박스와 배포 정책 밖에 있는 실행 모델은 오래 유지하기 어렵다 |
| Classic ASP | 스크립트로 동적 페이지를 빠르게 개발 | 표현과 서버 로직이 섞이기 쉬웠고 후속 런타임과 구조화된 프레임워크가 등장 | 빠른 시작과 장기 유지보수성은 별도 축이다 |
| SOAP | 엄격한 계약, 확장 규격과 기업 간 통합 | 일반 웹과 모바일 API에서는 REST와 JSON의 단순한 도구 체인이 널리 채택됨 | 강한 계약의 가치와 복잡성 비용을 요구에 맞춰 비교해야 한다 |
| jQuery | 브라우저별 DOM과 이벤트 차이를 단일 API로 흡수 | 브라우저 표준 API가 성숙하고 컴포넌트 중심 UI 도구가 보편화 | 해결하던 호환성 문제가 줄면 추상화의 가치도 달라진다 |
| Internet Explorer | Windows 기본 브라우저와 독자 기능 제공 | 표준과의 차이, 보안 및 호환성 비용이 누적되고 경쟁 브라우저가 성장 | 독점적 확장은 단기 편의와 장기 호환성 비용을 맞바꾼다 |

SOAP, jQuery와 Classic ASP는 완전히 사라졌다고 단정할 수 없다. 기존 시스템과 특정 기업 환경에서는 계속 쓰인다. 주류에서 내려왔다는 말은 신규 선택의 기본값과 생태계 투자가 다른 곳으로 이동했다는 뜻이다.

## 반복되는 퇴장 원인

### 외부 런타임과 설치 의존

플러그인과 네이티브 모듈은 브라우저만으로 제공하기 어려운 기능을 빠르게 열어 줬지만, 사용자 설치와 버전 관리, 배포 권한과 패치 책임을 함께 만들었다. 브라우저가 같은 기능을 표준 API와 샌드박스 안에서 제공하기 시작하면 전용 런타임의 이점은 줄어든다.

### 공급자와 플랫폼 종속

특정 운영체제, 브라우저나 회사의 런타임에 묶이면 지원 종료와 정책 변경이 곧 서비스 위험이 된다. 웹에서는 같은 콘텐츠와 기능이 다양한 구현체에서 동작하는 상호운용성이 장기 생존에 중요하다.

### 보안 경계 위반

웹 페이지가 로컬 실행 파일과 비슷한 권한을 얻을수록 공격 표면도 커진다. 브라우저는 플러그인 제거, 샌드박스와 권한 제한을 통해 실행 경계를 좁혀 왔다. 기능이 강하다는 이유만으로 넓은 권한을 허용하면 업데이트와 사고 대응 비용이 따라온다.

### 원래 문제가 표준에 흡수됨

jQuery는 브라우저 호환성 문제를 크게 줄였고 Flash는 초기 멀티미디어 웹을 확장했다. 이후 표준 API와 브라우저 구현이 발전하면서 이 도구들이 담당하던 기능이 플랫폼 자체로 이동했다. 성공한 도구도 문제의 형태가 바뀌면 역할이 축소될 수 있다.

## 기술 선택 체크리스트

1. 여러 브라우저와 운영체제에서 같은 계약으로 동작하는가
2. 별도 설치 없이 접근할 수 있고 접근성 요구를 충족하는가
3. 권한 범위가 작고 보안 업데이트 경로가 명확한가
4. 공급자 지원이 끝나도 데이터와 기능을 옮길 수 있는가
5. 현재 문제를 실제로 해결하며 표준 기능과 중복되지 않는가
6. 도입 속도뿐 아니라 운영, 마이그레이션과 팀 학습 비용을 감당할 수 있는가

오래 살아남는 기술을 정확히 예측할 수는 없다. 따라서 특정 도구를 영구 전제로 삼기보다 표준 경계, 교체 가능한 인터페이스와 이관 경로를 설계하는 것이 현실적인 대응이다.

## 면접 체크포인트

- 플러그인 기반 기술이 보안, 배포와 모바일 환경에서 불리했던 이유
- 표준 API의 성숙이 jQuery 같은 추상화의 역할을 줄인 과정
- SOAP과 REST를 생존과 사망이 아니라 계약 강도와 복잡성의 트레이드오프로 비교하는 방법
- 공급자 종속과 상호운용성이 기술 수명에 미치는 영향
