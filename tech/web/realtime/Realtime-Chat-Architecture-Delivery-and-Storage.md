# 실시간 채팅: 메시지 전달 경로와 이력 저장소

[[Realtime-Chat-Architecture|실시간 채팅 시스템 아키텍처]]의 대표 구성(WebSocket, 내구성 경로, Pub/Sub 팬아웃)을 예로, 메시지를 누구에게 어떤 경로로 보낼지와 지난 메시지를 어떤 키로 쌓을지를 다룬다. 서버가 여러 대이고 클라이언트가 아무 서버에나 붙는 환경에서는 인스턴스 사이의 전달 구조를 함께 설계해야 한다.

## 채팅 워크로드의 특성

- 메시지는 양이 많고 한 건의 가치는 낮으며, 사용자는 대부분 최근 대화를 본다.
- 1:1 대화는 메시지 한 건을 상대 한 명이 받는다. 단체방은 쓰기 한 건이 멤버 수만큼 전달되므로 같은 쓰기량에서도 전달량이 방 크기에 비례한다.
- 대화 하나 안에서는 최근 구간을 읽지만 저장소 전체로 보면 수많은 대화의 최근 구간이 흩어져 읽힌다. 아래 사례에서는 읽기가 매우 무작위였고 읽기와 쓰기 비율이 약 50:50이었으며, 메시지가 드물거나 멤버가 적은 서버의 데이터는 요청 빈도가 낮아 디스크 캐시에 남기 어려웠다. 최신 편향이 곧 캐시 적중을 뜻하지는 않는다.

이 특성이 전달 경로(누가 받는가)와 저장 키(무엇으로 묶어 읽는가)를 정한다.

## 방 채널 브로드캐스트와 수신자 기준 라우팅

| 축 | 방 채널 브로드캐스트 | 수신자 기준 라우팅 |
|---|---|---|
| 흐름 | 메시지를 방 채널에 발행하고, 그 방을 구독한 서버가 자기 연결에 전달 | 수신자 목록을 정한 뒤 수신자마다 접속 서버나 알림 경로로 보냄 |
| 전달 단위 | 방을 구독한 서버 수 | 수신자 수 |
| 미접속 수신자 | 채널은 누가 빠졌는지 모르므로 별도 확인이 필요 | 수신자마다 접속 여부를 판단하므로 자연스럽다 |
| 읽음, 다중 기기 | 사용자별 상태를 따로 관리 | 사용자 단위 처리에 맞다 |
| 큰 방 | 전달 수가 서버 수로 묶여 유리 | 멤버 수만큼 증폭 |

기존 문서의 Redis Pub/Sub 팬아웃이 왼쪽이다. 두 방식은 배타적이지 않아서 작은 방은 수신자 기준으로, 큰 방은 방 채널로 보내는 혼합도 가능하다. 큰 방의 채널 집중은 [[Realtime-Chat-Architecture#스케일링 고려사항|Hot Room]]을 따른다.

### 1:1 흐름

1. 송신 클라이언트가 임의의 채팅 서버에 WebSocket으로 메시지를 보낸다.
2. 서버는 메시지를 내구성 경로에 기록한 뒤 송신자에게 ACK를 보낸다 ([[Realtime-Chat-Architecture#아키텍처 예시|아키텍처 예시]]).
3. 수신자가 접속 중이면 수신자가 연결된 서버로 보내고, 그 서버가 WebSocket으로 전달한다.
4. 접속 중이 아니면 알림 경로로 넘긴다.

### 수신자의 서버를 찾는 방법

수신자 기준 라우팅은 메시지가 수신자의 연결을 가진 서버에 도착해야 성립한다. 사용자별 큐를 구독한 서버가 전달한다고 설계해도 브로커의 소비 배정은 연결 위치를 모르므로 한 단계를 더 정해야 한다.

- Kafka는 구독하는 컨슈머 그룹마다 각 파티션을 그룹 안의 컨슈머 하나만 읽게 한다. 채팅 서버들이 한 그룹으로 공유 토픽을 읽으면 메시지는 그 파티션을 배정받은 서버로 가고, 그 서버에 수신자 연결이 있다는 보장은 없다.
- 서버마다 다른 그룹으로 읽으면 모든 서버가 모든 메시지를 받아 자기 연결만 골라 전달한다. 방 채널 브로드캐스트와 같은 비용 구조다. 그룹 단위 분배는 [[Fan-Out-Architecture|팬아웃 아키텍처]]에서 다룬다.
- 사용자마다 토픽이나 큐를 만들면 사용자 수만큼 토픽이 생겨 브로커 메타데이터와 구독 관리가 사용자 수에 비례해 늘어난다. 측정 없이 이 구조를 택하지 않는다.
- 흔한 구체화는 연결 레지스트리다. 연결할 때 `userId → serverId, connectionId`를 TTL과 함께 기록하고 heartbeat로 갱신하며, 송신 측은 레지스트리를 조회해 수신자 서버 전용 채널(서버별 큐나 Pub/Sub 채널)로 보낸다. 다중 기기면 한 사용자에 연결이 여러 개 등록된다. 갱신 방식은 [[Realtime-Chat-Architecture#스케일링 고려사항|Presence]]의 heartbeat 정리와 같다.

레지스트리와 실제 연결 사이에는 늘 시차가 있다. 죽은 서버의 항목은 TTL이 지우고, 이미 끊긴 연결로 보낸 메시지는 재연결 때 `lastSequence` 이후 재조회로 복구한다. 실시간 경로는 최선 노력이고 정본은 내구성 저장소라는 원칙이 그대로 적용된다.

## 오프라인 수신자 알림

채팅 서버가 실시간 전달과 푸시 발송을 함께 맡지 않고 알림 모듈을 따로 둔다. 푸시 제공자의 지연, 할당량과 재시도가 WebSocket 처리 경로를 막지 않게 격리하려는 것이다.

- 알림 모듈은 내구성 경로의 메시지 이벤트를 별도 컨슈머 그룹으로 구독한다. Kafka에서는 구독하는 그룹마다 모든 파티션을 받으므로 채팅 서버의 소비와 독립적으로 같은 메시지를 받는다.
- 연결 레지스트리로 수신자의 접속 여부를 확인해 미접속 수신자에게만 푸시한다. 판단과 전달 사이의 경합으로 실시간 메시지와 푸시가 함께 갈 수 있으므로 클라이언트는 `messageId`로 중복을 제거한다.
- Kafka의 일반적인 at-least-once 소비에서는 같은 이벤트를 다시 처리할 수 있고, 외부 시스템으로의 exactly-once는 그 시스템의 협력이 필요하다. `(messageId, 수신자)` 발송 기록만으로는 푸시 호출과 기록을 원자적으로 묶을 수 없다. 호출 전에 완료를 기록하면 crash 시 발송이 누락되고, 호출 뒤 기록 전에 죽으면 재시도로 중복 푸시가 생긴다. 제공자가 보장하는 멱등 키나 결과 조회가 있으면 활용하고, 그렇지 않으면 결과 불명 상태와 재시도 정책을 기록하며 앱에서 처리하는 메시지는 `messageId`로 중복을 흡수한다. FCM의 background notification처럼 SDK가 자동 표시하는 알림은 앱의 중복 제거가 표시 전에 실행된다고 보장할 수 없다 ([[Idempotent-Consumer|멱등 컨슈머]]).
- 푸시는 깨우기 신호로 쓰고 메시지의 정본으로 쓰지 않는다. payload에는 방 ID와 `messageId` 정도만 담고, 앱이 열리면 마지막 sequence 이후를 재조회한다. 제공자의 수락이 기기 도착을 뜻하지 않는 점과 collapse의 한계는 [[Notification-Broadcast-System#Provider 수락, 전달, 표시와 등록 정보|대규모 알림 시스템]]을 본다.
- 메시지를 DB에 저장한 뒤 브로커에 따로 발행하면 둘 중 하나만 성공할 수 있다. 저장과 발행을 묶으려면 [[Transactional-Outbox|Transactional Outbox]]나 CDC를 쓴다.

## 단체방 수신자 결정

단체방은 방 멤버 정보를 담는 저장소를 두고, 메시지가 오면 멤버 목록을 조회해 수신자를 정한다. 1:1과 달리 수신자를 특정하는 조회 단계가 하나 더 붙는다.

- 메시지마다 멤버를 DB에서 조회하면 조회 수가 메시지 수에 비례하고 큰 방은 결과도 크다. 방 ID별 멤버 집합을 캐시하고 가입, 탈퇴, 강퇴 이벤트로 무효화한다 ([[Cache-Strategies|Cache 전략]]).
- 캐시가 갱신되기 전 짧은 구간에는 탈퇴한 사용자에게 전달되거나 새 멤버가 빠질 수 있다. 권한이 중요한 방은 전달 시점에 멤버십을 다시 확인하고, 멤버십 변경도 방 sequence에 기록해 어느 메시지부터 볼 수 있는지 기준을 남긴다.
- 수신자 기준 팬아웃은 멤버 수만큼 전달 작업이 늘어난다. 멤버 수가 임계값을 넘는 방은 방 채널 브로드캐스트로 바꾸는 기준을 미리 정한다.

## 메시지 이력 저장소

이력 조회는 조인이 거의 없고 대화 하나의 최근 구간을 시간 순서로 읽는 단순한 접근이 대부분이다. 그래서 대화 키로 분산하기 쉬운 NoSQL(문서형, wide-column 등)이 흔한 후보가 된다. 다만 RDB도 `(room_id, room_sequence)` 복합 인덱스로 같은 접근을 처리하므로, 저장소 종류보다 데이터량과 쓰기 속도, 팀의 운영 역량을 먼저 확인한다 ([[NoSQL-Overview#선택 절차|NoSQL 선택 절차]]).

키 설계의 원칙은 저장소와 무관하다.

- 파티션 키는 방(대화) ID, 정렬 키는 `roomSequence`나 시간 순으로 정렬되는 ID로 두고 최근 순으로 읽는다. 위로 스크롤하는 페이지 조회는 `sequence < 커서`, 재연결 복구는 `sequence > lastSequence`로 같은 키를 앞뒤로 읽는다 ([[Realtime-Chat-Architecture#스케일링 고려사항|영구 메시지와 복구]]).
- 방 ID만으로 묶으면 오래되고 활발한 방의 파티션이 끝없이 커진다. 고정 시간 창을 버킷으로 파티션 키에 넣어 크기를 제한한다 ([[MongoDB-Schema-Design#Bucket Pattern|Bucket Pattern]]). 대가로 메시지가 드문 방은 충분한 메시지를 모으려고 여러 버킷을 차례로 읽어야 하므로 빈 버킷을 기록해 건너뛴다.
- 인기 방은 한 파티션에 동시 읽기가 몰리는 핫 파티션이 된다. 같은 행에 대한 동시 요청을 한 번의 조회로 합치거나 최근 구간을 캐시해 저장소 앞에서 흡수한다.
- 개별 메시지의 가치가 낮다는 특성은 보존 정책으로 이어진다. 오래된 버킷은 저비용 계층으로 옮기거나 보존 기간 뒤 삭제하되, 법적 보존 의무와 사용자의 삭제 요청을 먼저 확인한다.

### 사례: Discord의 메시지 저장소 (공개 글 기준)

- 초기에는 모든 데이터를 MongoDB replica set 하나에 두고 메시지를 `channel_id`, `created_at` 복합 인덱스로 조회했다. 2015년 11월 저장 메시지가 약 1억 건에 이르자 데이터와 인덱스가 RAM에 들어가지 않아 지연이 불안정해졌고, Cassandra로 옮겼다(2017-01 공개 글).
- 기본 키는 `((channel_id, bucket), message_id)`다. 파티션 키는 채널과 고정 시간 창 버킷, 정렬 키는 시간 순으로 정렬되는 Snowflake ID다. 큰 채널 기준 약 10일 치를 한 버킷에 담아 파티션을 100MB 아래로 유지했다.
- 이후 큰 서버의 채널과 버킷 하나에 읽기가 몰리는 핫 파티션이 노드 지연을 키우고, quorum으로 읽고 쓰는 다른 요청까지 느려지게 했다. 채널 ID를 라우팅 키로 한 일관 해시로 같은 채널 요청을 같은 데이터 서비스 인스턴스에 보내고, 동시에 들어온 같은 행 요청은 DB 조회 한 번으로 합쳤다. 메시지 DB는 2022년 5월 ScyllaDB로 옮겼고 채널과 버킷 기준 파티셔닝은 유지했다(2023-03 공개 글).

## 흔한 함정

- **사용자 큐를 구독한 서버가 곧 수신자 연결을 가진 서버라고 가정** — 컨슈머 그룹의 파티션 배정은 연결 위치와 무관하다
- **채팅 서버 안에서 푸시를 동기 호출** — 제공자 지연이 실시간 경로를 막는다
- **발송 기록만으로 외부 호출의 멱등성을 가정** — 호출과 기록 사이의 crash로 누락이나 중복이 생기므로 provider 계약과 결과 불명 처리까지 확인한다
- **단체방 메시지마다 멤버를 DB에서 조회** — 메시지 수와 방 크기의 곱만큼 부하가 늘어난다
- **방 ID만으로 이력 파티션을 잡음** — 오래된 큰 방의 파티션이 한없이 커진다

## 면접 체크포인트

- 채팅 워크로드(양, 낮은 개별 가치, 최신 편향, 1:1과 단체방의 전달 비율)가 전달 경로와 저장 키에 주는 영향
- 방 채널 브로드캐스트와 수신자 기준 라우팅의 비용 차이와 혼합 기준
- 컨슈머 그룹 배정만으로 수신자 서버에 메시지를 보낼 수 없는 이유와 연결 레지스트리
- 오프라인 알림 모듈을 분리하는 이유와 중복 푸시 방지
- 이력 저장소의 키 설계(방 ID, 시간 버킷, 정렬 키)와 RDB도 후보가 되는 조건
