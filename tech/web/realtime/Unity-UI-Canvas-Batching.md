# Unity UI 캔버스 배칭과 분할: 재구성 비용과 드로우콜의 균형

Unity의 uGUI(Unity UI)에서 Canvas는 그 아래 UI 요소를 메시로 만들고, 가능한 한 적은 드로우콜로 그리도록 배치(batch)로 묶는다. 드로우콜은 CPU가 GPU에 보내는 그리기 요청이다. 배치 생성은 비싸므로 요소가 바뀔 때만 다시 만든다. 이 문서는 그 재구성이 어느 범위에 걸리는지, 캔버스를 나눌 때 무엇을 얻고 잃는지를 다룬다. 프레임 하나에 쓸 수 있는 시간 예산은 [[Game-Loop-Frame-Timing|게임 루프의 프레임 시간]]을 따른다.

이 문서는 uGUI(GameObject 기반 UI)에 대한 것이다. 대조한 Unity 자료는 uGUI만 다루므로 UI Toolkit에는 같은 규칙을 그대로 옮기지 않는다.

## 요소 하나가 바뀌면 캔버스 전체를 다시 묶는다

- 캔버스 안의 요소 하나가 위치, 회전, 크기, 텍스트, 스프라이트나 색이 바뀌면 그 캔버스의 배치를 전부 다시 만든다. 비용은 바뀐 요소만이 아니라 캔버스 전체에 든다.
- 그래서 매 프레임 바뀌는 요소(타이머, 체력 게이지, 움직이는 표식)가 정적인 배경과 테두리와 한 캔버스에 있으면, 정적 요소까지 매 프레임 다시 묶인다. Unity의 UI 최적화 안내(대상 버전 미표기)는 게임 전체 UI를 수천 개 요소가 있는 캔버스 하나에 둔 경우 수 밀리초의 CPU 급증이 생길 수 있다고 설명한다. 특정 버전의 측정값은 아니다. 60 FPS의 프레임 예산이 약 16.7ms이므로 작지 않은 몫이다.
- 프로파일러에서 `Canvas.BuildBatch`가 매 프레임 나타나면 그 캔버스의 무언가가 매 프레임 바뀌고 있다는 신호다.

흔히 이 상태를 요소가 dirty로 표시됐다고 말한다. Unity 자료는 레이아웃 쪽에서도 dirty를 쓴다. 레이아웃을 dirty로 표시하는 요소마다 부모에서 레이아웃 그룹을 찾는 `GetComponent` 호출이 최소 한 번 일어나고, 레이아웃 그룹이 더 없을 때까지 계층을 올라간다. 레이아웃 그룹이 중첩되면 그룹 하나마다 각 자식의 dirty 처리에 호출이 하나씩 더해진다.

## 바뀌는 주기로 캔버스를 나눈다

해법은 캔버스를 나누는 것이고, Unity가 제시하는 한 가지 기준은 갱신 빈도다.

1. 바뀌지 않는 요소(배경, 라벨, 프레임)는 한 캔버스에 둔다.
2. 매 프레임이나 자주 바뀌는 요소는 자기 `Canvas` 컴포넌트를 가진 GameObject 아래로 옮긴다. 기존 계층 안의 중첩 캔버스여도 되고 별도 최상위 캔버스여도 된다. 같은 때에 함께 바뀌는 요소끼리 작은 하위 캔버스로 묶는다.
3. 나누기 전후의 `Canvas.BuildBatch`와 프레임 시간을 프로파일러로 비교한다.

중첩 캔버스(자식 GameObject의 Canvas 컴포넌트)는 자기 배치를 따로 가지고 부모, 형제 캔버스와 독립적으로 재구성된다. 그래서 하위 캔버스의 숫자가 바뀌어도 부모의 정적 요소는 다시 묶이지 않는다.

같은 캔버스 안에서 배치가 잘 묶이려면 요소들의 Z 값, 머티리얼과 텍스처가 같아야 한다.

## 많이 나누면 드로우콜이 는다

캔버스는 각자 배치를 만들고, 서로 다른 캔버스의 배치는 합쳐지지 않는다. 원래 한 번에 그릴 수 있던 요소도 캔버스가 다르면 따로 그려지므로, 캔버스를 하나 더할 때마다 드로우콜이 는다. 요소마다 캔버스를 만드는 식의 과도한 분할은 재구성 비용을 줄인 대신 드로우콜 비용을 키운다.

| 선택 | 줄어드는 비용 | 늘어나는 비용 |
|---|---|---|
| 큰 캔버스 하나 | 드로우콜(배치를 최대한 합친다) | 요소 하나만 바뀌어도 전체 재구성 |
| 갱신 주기별 분할 | 정적 요소의 재구성 | 캔버스 수만큼의 추가 배치와 드로우콜 |
| 요소마다 캔버스(이 문서의 해석) | 재구성 범위는 최소 | 배치를 합칠 수 없어 드로우콜 최대 |

Unity의 지원 문서도 재구성 비용과 추가 드로우콜 비용을 저울질하고, 나눠도 프레임 시간이 나아지지 않으면 나누지 말라고 한다. 이 문서의 해석으로는 요소의 종류보다 함께 바뀌는 주기로 묶는 것이 출발점이고, 채택 여부는 측정으로 정한다.

## 함께 보는 uGUI 비용 요인

아래 항목은 Unity의 UI 최적화 안내(대상 버전 미표기, uGUI) 기준이다.

- **입력 판정:** 입력이 필요한 캔버스마다(하위 캔버스 포함) Graphic Raycaster가 필요하다. 입력을 받는 요소를 하위 캔버스로 옮기면 그 캔버스에도 Graphic Raycaster를 붙인다. 상호작용이 없는 캔버스에서는 Graphic Raycaster를 빼고, 정적이거나 상호작용이 없는 요소의 Raycast Target을 끈다. 버튼 안 텍스트의 Raycast Target을 끄면 프레임마다 하는 교차 검사가 준다.
- **숨기기:** 캔버스를 숨길 때 Canvas 컴포넌트를 끄면 GPU에 드로우콜을 보내지 않으면서 메시와 정점은 유지하므로 다시 켤 때 재구성이 일어나지 않고, 계층 전체의 OnDisable/OnEnable 콜백도 부르지 않는다. 다만 매 프레임 비싼 코드를 도는 자식 컴포넌트는 따로 꺼야 한다.
- **레이아웃 그룹:** 가능하면 쓰지 않고 비례 배치는 앵커로 한다. 자주 갱신되고 요소 수가 바뀌는 UI는 변경마다가 아니라 필요할 때만 실행하는 자체 레이아웃 코드를 검토한다.
- **Animator:** 값이 바뀌지 않아도 매 프레임 UI 요소를 dirty로 만든다. 항상 바뀌는 요소에만 쓰고 나머지는 코드나 트윈으로 움직인다.
- **풀링:** 풀로 돌려보낼 때는 먼저 끄고 부모를 바꾸며, 꺼낼 때는 부모를 바꾸고 데이터를 갱신한 뒤 켠다. 돌려보낼 때 먼저 끄면 이전 계층은 한 번만 dirty가 되고 풀 쪽 계층은 dirty가 되지 않는다.

## AI에게 최적화를 맡길 때의 요청 단위

막연한 최적화 요청보다 위 판단 기준을 그대로 조건으로 준다. 갱신 빈도로 나누고 전후 성능을 비교하게 하는 데까지가 계기가 된 영상의 제안이고, 아래 측정 항목과 되돌림 조건은 이 문서가 덧붙인 점검 제안이다. 예를 들어 UI 요소를 갱신 빈도(정적, 이벤트 시, 매 프레임)로 분류해 캔버스를 나누고, 분할 전후 `Canvas.BuildBatch` 시간, 배치 수와 프레임 시간을 같은 장면에서 측정해 보고하게 한다. 개선이 측정되지 않으면 분할을 되돌리는 조건도 함께 준다.

## 면접 체크포인트

- 캔버스 안 텍스트 하나의 변경이 왜 캔버스 전체의 비용이 되는지 설명할 수 있는가.
- 캔버스를 나눌 때 줄어드는 비용과 늘어나는 비용을 구분하고, 분할 기준을 요소 종류가 아닌 갱신 주기로 말할 수 있는가.
- 분할 효과를 어떤 프로파일러 항목과 지표로 확인할지 말할 수 있는가.
