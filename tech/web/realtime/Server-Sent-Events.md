# Server-Sent Events (SSE)

SSE는 서버가 하나의 HTTP 응답에서 UTF-8 텍스트 이벤트를 연속 전송하는 단방향 통신 방식이다. 연결을 계속 유지하는 알림뿐 아니라, 필요한 데이터를 모두 보낸 뒤 종료하는 유한 스트림에도 사용할 수 있다.

핵심은 전체 작업 완료 시간이 아니라 **먼저 준비된 결과를 먼저 보여줄 수 있다는 점**이다. 마지막 데이터가 도착하는 시간은 그대로여도 사용자가 첫 화면을 보는 시간은 앞당길 수 있다.

## 이벤트 형식

서버는 `Content-Type: text/event-stream`으로 응답하고 빈 줄로 이벤트 경계를 구분한다.

```text
event: section
id: home-hero
data: {"slotId":"hero","payload":{"title":"추천 콘텐츠"}}

event: done
data: {}

```

주요 필드는 다음과 같다.

- `event`: 이벤트 종류다. 생략하면 `message`가 된다.
- `data`: 이벤트 데이터다. 여러 줄을 사용할 수 있다.
- `id`: 재연결할 때 서버로 전달할 마지막 이벤트 식별자다.
- `retry`: 브라우저의 재연결 대기 시간을 지정한다.

`done`은 SSE 표준 필드가 아니라 애플리케이션이 정의한 종료 이벤트다. 유한 스트림이라면 완료 이벤트를 보낸 뒤 응답을 닫는 계약을 명확히 둔다. 네이티브 `EventSource`는 정상적인 `200` 응답 스트림이 끝나도 재연결할 수 있으므로 `done`을 받았을 때 `source.close()`를 호출해야 한다. `fetch` 클라이언트는 `done`이나 EOF를 완료로 처리할 수 있다.

SSE는 특정 HTTP 버전에 종속되지 않는다. HTTP/1.1에서는 보통 chunked 전송을 사용하고, HTTP/2와 HTTP/3에서는 각 버전의 프레임으로 응답 본문을 나눠 보낸다.

## BFF에서 페이지를 점진적으로 조립하기

한 화면이 여러 백엔드 응답을 필요로 할 때 단일 JSON 응답은 가장 느린 호출이 끝날 때까지 전체 화면을 기다리게 한다. BFF가 SSE를 사용하면 클라이언트 요청은 하나로 유지하면서 준비된 영역부터 전달할 수 있다.

```text
브라우저 ── GET /page ──> BFF ──> 레이아웃, 영역 A, 영역 B, 영역 C
브라우저 <── layout ───── BFF
브라우저 <── section B ── BFF
브라우저 <── section A ── BFF
브라우저 <── error C ──── BFF
브라우저 <── done ─────── BFF
```

일반적인 흐름은 다음과 같다.

1. BFF가 화면 구성 정보나 스켈레톤 배치를 먼저 보낸다.
2. 여러 백엔드 요청을 병렬 실행한다.
3. 완료된 영역을 슬롯 식별자와 함께 즉시 보낸다.
4. 영역 하나가 실패하면 해당 영역의 오류나 대체 데이터를 보낸다.
5. 모든 영역의 결과가 결정되면 완료 이벤트를 보내고 응답을 닫는다.

이 구조에서 BFF는 **조합 순서, 타임아웃, 실패 격리, 종료 조건**을 소유한다. 각 영역의 도메인 데이터까지 다시 정의할 필요는 없다. 공통 이벤트 봉투만 BFF가 정의하고, 내부 `payload`는 담당 서버의 계약을 유지하면 불필요한 스키마 중복을 줄일 수 있다.

### 얻는 것

- 클라이언트가 페이지 단위 API 하나만 호출한다.
- 빠른 영역을 느린 영역 때문에 늦게 보여주지 않는다.
- 일부 백엔드 실패를 화면 전체 실패와 분리할 수 있다.
- 화면 조합과 대체 정책을 서버에서 일관되게 관리한다.

### 새로 생기는 비용

- 도착 순서가 고정되지 않으므로 슬롯 식별과 중복 처리 규칙이 필요하다.
- 스트림 파싱, 완료, 취소, 재연결 정책을 구현해야 한다.
- BFF와 프록시가 응답이 끝날 때까지 연결과 관련 자원을 유지한다.
- 전체 완료 시간은 가장 느린 백엔드가 정한다. SSE 자체가 백엔드를 빠르게 만들지는 않는다.

## REST, HTTP 스트리밍, WebSocket과 비교

| 방식 | 적합한 상황 | 고려할 점 |
|---|---|---|
| 단일 JSON 응답 | 결과가 작고 한 번에 렌더링해도 됨 | 가장 단순하지만 가장 느린 작업을 기다림 |
| 원시 HTTP 스트림 | 이벤트 규격이 필요 없는 단순 바이트 스트림 | 메시지 경계와 재연결 규칙을 직접 정의 |
| SSE | 서버에서 클라이언트로 텍스트 이벤트를 순차 전달 | 표준 이벤트 형식을 쓰지만 단방향 |
| WebSocket | 양쪽이 자주 메시지를 보내는 지속 연결 | 연결 수명, 인증, 재연결을 별도로 관리 |

유한 응답이라도 이벤트 이름, 식별자, 재연결 같은 SSE 규약이 도움이 된다면 SSE를 선택할 수 있다. 단순한 줄 단위 결과만 필요하면 NDJSON 같은 더 작은 규약도 후보가 된다.

## 브라우저 클라이언트 선택

### EventSource

브라우저의 `EventSource`는 이벤트 파싱, 자동 재연결, `Last-Event-ID` 처리를 제공한다. 표준 생성자 옵션은 URL과 `withCredentials`뿐이므로 임의의 요청 헤더를 직접 지정할 수 없다.

쿠키 기반 인증이 가능하고 기본 재연결 동작이 필요하다면 가장 단순한 선택이다.

### fetch와 ReadableStream

`Authorization` 같은 요청 헤더가 필요하면 `fetch`로 요청하고 `Response.body`의 `ReadableStream`을 읽을 수 있다. 이 경우 다음 기능은 직접 책임져야 한다.

- 교차 출처에서 `Authorization`을 사용하면 CORS preflight와 서버의 헤더 허용 설정이 필요하다.
- 네트워크 청크를 이벤트 경계로 착각하지 않고 불완전한 줄을 버퍼링한다.
- `TextDecoder`의 스트림 모드로 청크 사이에 나뉜 문자를 처리한다.
- 이벤트 이름, 여러 `data` 줄, `id`를 SSE 규칙에 맞게 해석한다.
- 재연결, 마지막 이벤트 식별자, 중복 제거 정책을 구현한다.
- 화면 이탈 시 `AbortSignal`로 요청을 취소한다.

네트워크가 나눈 청크와 SSE 이벤트는 같은 단위가 아니다. 직접 파서를 만들기보다 검증된 SSE 파서를 쓰는 편이 안전하며, 의존성을 추가할 때는 위 규칙이 실제로 필요한지 먼저 확인한다.

## 렌더링과 캐시 분리

스트림 수신 코드가 UI를 직접 갱신하면 연결 수명과 화면 상태가 강하게 결합된다. 대신 이벤트를 클라이언트 캐시에 기록하고 각 컴포넌트는 자신의 캐시 키만 구독할 수 있다.

- 레이아웃 이벤트로 슬롯과 스켈레톤을 먼저 만든다.
- 영역 이벤트를 `page`, `slotId`, 요청 조건이 포함된 키에 기록한다.
- 같은 이벤트가 다시 와도 결과가 달라지지 않도록 멱등성을 확보한다.
- 이미 유효한 캐시가 있다면 새 스트림을 열지 않을지 결정한다.
- 새로고침, 필터 변경, 만료 시점에 어떤 캐시를 폐기할지 명시한다.

캐시는 네트워크 최적화이면서 제품 정책이다. 다시 방문했을 때 최신성을 우선할지 즉시 표시를 우선할지에 따라 무효화 기준이 달라진다.

## 실패와 종료 계약

유한 SSE는 성공 이벤트만큼 실패와 종료 이벤트가 중요하다.

- `requestId`와 `slotId`로 어느 요청의 어느 영역인지 식별한다.
- 영역별 타임아웃을 두고 실패 이벤트나 대체 데이터를 보낸다.
- 필수 영역 실패와 선택 영역 실패를 구분한다.
- 완료 이벤트가 없거나 연결이 먼저 닫혔을 때의 UI 상태를 정한다.
- 클라이언트 연결이 끊기면 불필요한 백엔드 호출을 취소할지 결정한다.
- 동시에 실행할 백엔드 요청 수를 제한해 BFF의 부하 증폭을 막는다.

## 프록시와 운영

Nginx의 `proxy_buffering on`은 응답 전체를 받은 뒤에만 전송한다는 뜻이 아니다. 기본 설정에서는 업스트림 응답을 가능한 한 빨리 버퍼로 읽으면서 클라이언트에 전달한다. `off`로 설정하면 받은 응답을 클라이언트에 동기적으로 전달하고, 전체 응답을 미리 읽지 않는다.

따라서 모든 SSE에 `proxy_buffering off`를 적용하는 규칙은 정확하지 않다. 다음 조건을 실제 경로에서 확인해 선택한다.

- 이벤트가 브라우저에 도착한 시각을 기준으로 점진 전송 여부를 측정한다.
- 압축과 다른 응답 필터를 켠 상태에서도 이벤트가 제때 flush되는지 확인한다.
- 프록시, CDN, 로드밸런서를 모두 거친 운영 경로로 시험한다.
- 장기 스트림에서 느린 클라이언트가 버퍼, 임시 파일, 업스트림 속도에 미치는 영향을 확인한다.
- 유휴 타임아웃, 최대 연결 수, 연결 종료 감지를 점검한다.

필요하면 Nginx 설정이나 업스트림 응답의 `X-Accel-Buffering` 헤더로 버퍼링을 제어할 수 있다. 단, `proxy_ignore_headers`가 이 헤더를 무시하도록 설정되어 있으면 적용되지 않는다. 설정 자체보다 첫 이벤트, 각 영역, 완료 이벤트의 도착 시간을 관측하는 것이 우선이다.

## 선택 체크리스트

다음 조건이 많으면 SSE가 잘 맞는다.

- 데이터 흐름이 서버에서 클라이언트 방향으로 충분하다.
- 전체 완료 전 일부 결과를 보여주는 가치가 있다.
- 데이터가 UTF-8 텍스트로 표현 가능하다.
- 연결을 유지하는 동안의 서버와 프록시 자원을 감당할 수 있다.
- 이벤트별 실패, 중복, 종료 규칙을 정의할 수 있다.

클라이언트도 빈번히 데이터를 보내야 하거나, 바이너리 양방향 저지연 통신이 핵심이면 WebSocket이나 WebTransport를 검토한다. 첫 결과를 앞당길 제품 가치가 없다면 단일 JSON 응답이 더 단순하다.

성능을 비교할 때는 서버 처리 시간 하나만 보지 말고 **첫 바이트, 첫 의미 있는 영역, 전체 완료**를 각각 측정해야 한다.
