# 소프트웨어 모델링과 좋은 모델의 기준

모델링은 해결할 문제를 바라보는 관점을 정하고, 그 관점을 코드로 표현할 수 있는 구조로 정리하는 일이다. 모델은 그 결과물로, 문제를 추상화하고 구조화한 표현이자 설계이며 설명서다. 요구사항을 잘못 해석해 다시 짜는 일, 요구사항 변경 때 기존 코드를 분석하고 다시 짜는 일, 디버깅을 위해 코드를 읽는 일처럼 개발 시간을 크게 잡아먹는 작업의 상당수는 모델이 문제를 잘못 담았을 때 커진다.

## 모델링의 범위

모델링을 UML 다이어그램, 테이블 설계, 거창한 아키텍처 구조도로만 좁혀 보기 쉽지만, 다음도 모두 모델링이다.

- API 응답의 구조를 정하는 것
- 함수 하나가 어떤 책임을 가질지 정하는 것
- 상태를 어떻게 표현하고 그 흐름을 어디서 제어할지 정하는 것
- 복잡한 조건을 명확한 규칙으로 바꾸는 것
- 여러 개념을 어디까지 묶고 어디서 나눌지 판단하는 것

하루에도 여러 번 반복하는 일이며 이름을 붙이지 않았을 뿐이다. 코드 수준의 모델링은 객체지향 프로그래밍과 닮았지만, 객체지향이 코드를 작성하는 방법론이라면 모델링은 문제를 해석하는 사고방식과 그 구현에 가깝다.

## 추상화와 구조화

- **추상화**: 복잡한 대상에서 목적에 필요한 특징만 골라 담고 나머지를 버린다. 무엇을 담을지는 풀려는 문제가 정한다. 같은 사용자라도 어떤 시스템은 이메일만 필요하고, 다른 시스템은 나이, 성별, 구매 이력까지 필요하다. 일반화와의 차이는 [[Generalization-vs-Abstraction]]에 있다.
- **구조화**: 추상화한 개념을 어떻게 구성할지 정한다. 어떤 속성은 별도 객체로 분리하고, 어떤 책임은 메서드로 넣고, 어떤 요소끼리 관계를 맺을지 결정한다. 좋은 구조화는 겹치지 않게 나누고 빈틈없이 연결한다.

같은 피자 주문 시스템도 목적에 따라 모델이 달라진다.

| 시스템 목적 | 모델의 중심 |
|---|---|
| 재고 관리 | 구성 재료, 재료별 수량, 유통기한 |
| 마케팅 | 고객 주문 이력, 선호 토핑, 쿠폰 사용 내역 |
| 배달 최적화 | 주소, 배달 소요 시간, 라이더 위치와 일정 |
| 모두 다뤄야 함 | 관심사별 모델을 나누고 서로 협력하게 구조화 |

모델은 현실을 그대로 흉내 낸 복제가 아니라 관점을 담은 해석이다. 관심사별로 모델을 나누는 경계 설정은 DDD의 bounded context로 이어진다. [[DDD]]

## 좋은 모델의 네 가지 기준

### 1. 문제를 해결한다

모델은 문제를 해결하는 도구이므로 코드의 아름다움, 구조의 정교함보다 실제 문제를 풀고 있는지가 먼저다. 다음 질문에 답할 수 있어야 한다.

- 이 모델은 어떤 문제를 해결하려고 존재하는가
- 그 문제는 이 모델만으로 충분히 해결되는가
- 모델이 해결하는 문제가 명확히 정의되어 있는가

### 2. 내부가 블랙박스여도 쓸 수 있다

메서드 이름, 필드 구성, 인터페이스만 보고 역할과 사용법을 알 수 있어야 한다. 외부 계약이 잘 정의된 모델은 내부 구현을 몰라도 쓸 수 있고, 그만큼 사용자의 인지 부하가 줄고 리팩터링도 쉬워진다.

```ts
const price = Money.won(1_000);
const shipping = Money.won(500);
const total = price.add(shipping);
```

읽는 사람은 두 값이 원화 금액이고 `add`가 금액을 더한다는 것을 바로 안다. 내부가 정수, 십진 소수 타입, 통화 비교 중 무엇을 쓰든 사용자에게는 중요하지 않다. 금액 같은 값 객체의 설계는 [[VO-DTO]]와 [[Commerce-Change-Propagation-and-Money-Invariants]]에서 이어진다.

### 3. 개발자의 인지 범위 안에 있다

사람이 한 번에 붙잡을 수 있는 정보는 적다. 고전적으로는 7±2개로 알려졌고, 이후 연구는 작업 기억이 다루는 청크를 3~4개 정도로 더 작게 본다. 한 모델을 이해하려고 너무 많은 맥락을 요구하면 이미 설계가 실패에 가깝다. [[Readable-Code-Cognition]]

- 모델 하나만 봐도 역할과 책임이 드러난다.
- 모델 전체가 하나의 문제 해결을 위한 구조를 이룬다.
- 협력 객체는 적을수록, 의존성은 단순할수록 좋다.
- 동작 흐름을 예상할 수 있다.

모델의 크기, 깊이, 의존 수는 팀 개발자의 인지 부하를 기준으로 정한다. 아무리 정교한 추상화라도 팀에 부담이 되면 좋은 모델이 아니다.

### 4. 예측할 수 있다

어떻게 동작할지, 어디서 쓰일지, 무엇을 바꾸면 어디에 영향이 갈지 짐작할 수 있어야 한다. 예측할 수 있는 모델은 장애 원인을 좁히기 쉽고 변경도 안전하다. 반대로 예측이 어려우면 실행해 보기 전까지 동작을 알 수 없고, 수정할 때마다 모든 사용처를 추적해야 하며, 변경의 파급을 확신할 수 없다.

블랙박스와 예측 가능성은 충돌하지 않는다. 내부는 감추되 외부 계약은 명확히 드러내야 한다. 무조건 숨기는 것이 캡슐화의 본질이 아니며, 예측 가능성은 숨김이 아니라 명확한 표현에서 나온다.

- 메서드 이름이 의도를 드러낸다.
- 파라미터의 역할이 드러난다.
- 언제 실패하고 어떤 예외가 나는지 코드에서 유추할 수 있다.

```ts
// 나쁜 예: 부호에 숨은 규칙을 알아야 동작을 안다(양수면 차감, 음수면 적립)
class PointManager {
  apply(userId: string, point: number): boolean {
    return point > 0 ? this.deduct(userId, point) : this.earn(userId, -point);
  }
  // ...
}

// 좋은 예: 의도가 이름에 드러나 호출부에서 실수할 여지가 줄어든다
class PointAccount {
  earn(point: number): void { /* ... */ }
  deduct(point: number): void { /* 잔액 부족이면 InsufficientPointError */ }
}
```

값의 부호나 boolean 플래그로 동작을 바꾸는 메서드는 호출부만 봐서는 무엇을 하는지 알 수 없어 주석이 필요해지고 실수와 디버깅 비용이 늘어난다. 의도가 다른 동작은 이름이 다른 메서드로 나눈다.

## AI 시대의 모델링

세부 구현은 AI가 점점 잘 만들어 주지만, 문제를 재정의하고 무엇을 담고 버릴지, 어디서 나눌지를 정하는 일은 여전히 사람의 몫이다. 모델링은 AI에게 일을 정확하게 시키는 핵심이기도 하다. 모델과 계약이 명확할수록 AI가 만든 구현을 검증하기 쉽다. [[Agent-Spec-Writing]], [[Essential-vs-Accidental-Complexity]]

## 체크포인트

- 모델링이 다이어그램이나 테이블 설계보다 넓은 개념인 이유와 일상 코드에서의 예
- 추상화와 구조화의 차이, 같은 도메인도 목적에 따라 모델이 달라지는 예
- 블랙박스로 쓸 수 있는 모델과 예측할 수 있는 모델이 함께 성립하는 이유
- 부호나 플래그로 동작을 바꾸는 API의 문제와 개선 방향
- 모델의 크기와 의존 수를 인지 부하 기준으로 정하는 이유
