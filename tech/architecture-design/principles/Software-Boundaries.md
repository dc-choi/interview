# 소프트웨어의 경계

경계는 서로 다른 관심사, 책임, 맥락이 만나는 지점이다. 함수 호출, 모듈 인터페이스, 클라이언트와 서버 사이의 네트워크, 애플리케이션과 데이터베이스 사이의 쿼리, 팀과 팀 사이가 모두 경계다. 실무에서 개발자를 괴롭히는 문제의 상당수는 코드 내부 로직보다 이런 접점에서 생긴다. 설계 회의의 논쟁도 박스 안이 아니라 박스와 박스 사이에서 벌어진다. 알고리즘 오류나 오타처럼 경계와 무관한 버그도 있지만, 단일 책임 판단, 외부 API 실패 대응, 여러 DB 사이의 일관성, 컴포넌트 분리 기준, 공통 라이브러리 소유 같은 모호한 문제는 대부분 경계 문제다.

## 경계의 역설

함수를 나누고, 클래스를 정의하고, 모듈과 서비스를 쪼개는 일은 모두 관심사를 분리해 복잡성을 다루려는 경계 설정이다. 그런데 경계를 긋는 순간 누가 누구를 부르는지, 무엇을 주고받는지, 실패는 누가 처리하는지라는 새 문제가 함께 생긴다. 경계는 복잡성을 다루려고 만들지만 경계 자체가 새 복잡성의 원천이다. 그래도 경계 없는 소프트웨어는 사람이 다룰 수 없고, 규모와 조직이 커지면 네트워크와 팀 사이의 경계는 피할 수 없다. 긋든 긋지 않든 전체 복잡성은 사라지지 않고 위치만 바뀐다. 분해와 구조화의 원리는 [[Abstraction-and-Structural-Thinking]]에 있다.

## 경계의 종류

| 범주 | 경계 | 생기는 문제 | 이어지는 문서 |
|---|---|---|---|
| 코드 | 호출자와 피호출자 | 없음을 null로 줄지 예외로 줄지 같은 계약이 모호하면 양쪽이 서로 처리할 거라 기대하고 아무도 처리하지 않는다. 방어적 프로그래밍(경계 불신)과 계약에 의한 설계(명시적 계약)는 이 문제에 대한 두 접근이다 | [[Defensive-Copy]], [[Railway-Oriented-Programming]] |
| 코드 | 인터페이스(추상화) | 추상화는 정보를 감추는 대신 알아야 할 것까지 감춘다. 파일 한 줄 읽기가 네트워크 드라이브 지연, 파일 잠금, 거대 파일 메모리 부족을 만나면 감춰진 계층이 새어 나온다(추상화 누수) | [[Abstraction-and-Structural-Thinking#동작 추상화|동작 추상화]] |
| 코드 | 의존성 | 통제하지 못하는 외부 API와 라이브러리는 예고 없이 형식과 동작을 바꾼다. 통합 지점은 장애의 첫 번째 원인으로 꼽힌다 | [[External-Service-Resilience]], [[Backward-Compatibility-Design]] |
| 코드 | 변환 | 객체와 테이블처럼 같은 개념을 다르게 표현하는 시스템 사이에서 의미가 왜곡되거나 손실된다. DTO 같은 경계 전용 객체는 이를 줄이지만 변환 코드를 늘린다 | [[DTO-Layering]], [[View-Model-Design]] |
| 코드 | 신뢰 | 검증된 데이터와 검증되지 않은 데이터가 만나는 곳이다. 외부 웹훅을 서명 검증 없이 믿으면 위조된 결제 완료 요청을 받아들이게 된다 | [[Application-Security]], [[Payment-System-Principles]] |
| 코드 | 설계와 구현 | 요구사항, 설계, 구현, 테스트, 운영을 거칠 때마다 의도가 조금씩 손실된다. 정적인 시안에는 없던 긴 텍스트, 깨진 이미지, 로딩과 오류 상태가 구현에서 태어난다 | [[Software-Modeling]] |
| 물리 | 순서 | 비동기와 분산에서는 순서가 보장되지 않는다. 동기처럼 보이는 await와 suspend 지점 사이에도 상태가 바뀔 수 있고, 서버 시계와 네트워크 지연은 사건 순서를 뒤바꾼다 | [[System-Time-and-Clock-Sync]] |
| 물리 | 규모 | 커넥션 풀 고갈, 데이터 증가로 느려지는 쿼리처럼 임계점을 넘으면 문제가 질적으로 바뀐다. 대부분 사후에 발견된다 | [[Connection-Pool]], [[Monitoring-Graph-Reading]] |
| 물리 | 환경 | 로컬은 한국 시간, 서버는 UTC일 때 오늘의 범위가 9시간 밀리고, 파일 시스템의 대소문자 구분이나 메모리 제한이 다르면 같은 코드가 다르게 동작한다 | [[Temporal-Modeling]], [[Deterministic-Test]] |
| 물리 | 인프라 | 하나의 작업이 여러 서비스와 DB에 걸치면 원자성이 사라진다. 결제는 됐는데 재고 차감이 실패한 상태를 다뤄야 한다 | [[Saga-Pattern]], [[Transactional-Outbox]] |
| 사람 | 조직 | 시스템 구조는 조직의 소통 구조를 닮는다(콘웨이 법칙). 조직을 재편해도 코드는 그대로라 소유가 모호한 코드와 다른 팀 백로그에 묶인 병목이 생긴다 | [[Modular-Monolith#콘웨이 법칙과 함께 설계한다|콘웨이 법칙]] |
| 사람 | 소통 | 같은 단어로 다른 것을 상상하고, 설계 이유 같은 암묵지는 문서에 남지 않는다. 한 사람만 아는 시스템은 그 사람이 떠나면 벽이 된다 | [[Cross-Team-Communication]], [[Beautiful-Code#점검할 때 1: 코드 오너십이 흐려질 때|코드 오너십]] |
| 사람 | 사용자와 개발자 | 개발자에게 안전한 여러 단계의 확인이 사용자에게는 귀찮은 장벽이다. 경계를 줄이면 경험은 좋아지고 시스템은 복잡해진다 | [[View-Model-Design]] |

## 경계를 다스리는 법

### 숨은 경계를 찾는다

함수 시그니처나 API 스키마처럼 보이는 경계만 있는 것이 아니다. 두 서비스가 같은 테이블을 읽으면 코드상 연결은 없어도 강하게 결합되어 있다. 배포 스크립트의 암묵적 순서, 문서화되지 않은 팀 간 합의도 경계다. 데이터가 어디서 어디로 흐르는지, 한쪽의 변화가 어디까지 번지는지를 물으면 숨은 경계가 드러난다.

### 패턴보다 문제 정의가 먼저다

마이크로서비스라서 Saga, 외부 API라서 부패 방지 계층처럼 패턴부터 꺼내면 경계를 인식한 것이 아니라 패턴을 신봉한 것이다. 그 패턴이 푸는 문제가 내 시스템에 있는지, 비용을 감수할 만큼 경계가 불안정한지를 먼저 묻는다. 패턴의 이름을 아는 것과 필요한 상황을 판단하는 것은 다른 능력이다.

### 경계 앞의 세 가지 질문

1. **이 경계를 넘는 것은 무엇인가**: 데이터, 신뢰, 가정, 의도 중 무엇이 넘어가는지에 따라 위험이 다르다. 시간대 문제는 오늘이라는 가정이, 추상화 누수는 아래 계층을 신경 쓰지 않아도 된다는 가정이 경계를 넘은 결과다.
2. **이 경계가 깨지면 무슨 일이 일어나는가**: 결제 불일치와 로그 형식 불일치는 무게가 다르다. 깨졌을 때 컴파일 에러로 잡히는지, 테스트에서 보이는지, 운영 장애가 되는지에 따라 타입, 계약 테스트, 검증 계층 같은 보호 장치에 투자할 수준을 정한다. 대가가 작은 경계에 같은 보호를 거는 것은 과잉 투자다.
3. **이 경계는 누가 관리하는가**: 관리 주체가 없는 경계가 가장 위험하고 시간이 지나면 부패한다. 경계를 그을 때 양쪽 소유자를 함께 정한다.

### 긋지 않는 것도 선택이다

함께 변하는 것을 한곳에 두고, 아직 이해하지 못한 영역을 섣불리 나누지 않고, 관리 비용을 피하려 모놀리스를 유지하는 것도 의식적인 판단이다. 다만 경계를 긋지 않기로 한 판단(이 둘은 항상 함께 변한다)과 경계를 생각하지 않은 것은 다르다. 긋지 않았다면 이유가 있어야 한다. [[Change-Pressure-Proportion]]

### 경계는 진화한다

요구사항을 충분히 이해하기 전에 서비스를 나누면 잘못된 곳에 경계를 긋는다. 초기에는 모놀리스가 맞을 수 있고, 트래픽과 팀이 커져 특정 모듈이 병목이 되면 분리할 이유가 생긴다. 조직이 바뀌면 나눈 서비스를 다시 합치는 편이 나을 수도 있다. 어제의 올바른 경계가 오늘도 올바르다는 보장은 없으므로 정기적으로 검토한다. 이 구조가 정답이라는 확신이 가장 경계할 대상이다. [[Monolith-vs-Microservice]]

## 체크포인트

- 경계를 만들면 복잡성이 사라지지 않고 경계로 옮겨 가는 이유
- 코드, 물리, 사람 범주의 경계 예와 각 경계에서 생기는 전형적인 문제
- 추상화 누수의 의미와 예
- 경계 앞의 세 가지 질문으로 보호 장치의 투자 수준을 정하는 방법
- 경계를 긋지 않는 판단과 경계를 무시하는 것의 차이
