# 블록체인의 복제와 합의 비용

블록체인을 검토할 때는 노드 수보다 무엇을 나누고 무엇을 반복 검증하는지 먼저 본다. 아래의 구체적인 실행, 저장과 확정성 설명은 Ethereum의 공식 문서를 기준으로 한다. 다른 체인의 처리량이나 합의 조건까지 같은 것으로 일반화하지 않는다.

## 노드 추가와 작업 분할은 다르다

샤딩은 데이터를 나눠 담당하게 하는 방식이고, 복제는 같은 데이터나 상태를 여러 곳에 유지하는 방식이다. Ethereum에서는 실행 클라이언트가 트랜잭션을 실행하고, 합의 클라이언트가 검증된 데이터에 대한 체인의 합의를 다룬다. 블록을 받는 검증자는 트랜잭션을 다시 실행해 제안된 상태 변경을 확인한다.

같은 블록을 검증하는 노드가 늘어나는 것을 서로 다른 트랜잭션의 병렬 처리 능력이 늘어나는 것으로 계산하면 안 된다. 다만 노드 증가가 처리량을 전혀 바꾸지 않는다거나 모든 블록체인이 단일 노드의 성능에 묶인다는 주장도 별도 설계 근거 없이 적용하지 않는다.

## 비용과 확인 경계

| 항목 | 발생하는 일 | 설계할 때의 질문 |
|---|---|---|
| 실행과 통신 | 트랜잭션 실행, 검증과 블록 전파가 필요하다 | 노드 수 외에 블록 처리량과 전파 지연을 어떻게 측정하는가? |
| 확정 대기 | 블록 포함과 합의상 확정이 구분된다 | 외부 지급이나 상품 제공은 어떤 상태에서 허용하는가? |
| 저장과 동기화 | 현재 상태와 이력을 보관하고 검증한다 | 운영 목적에 full node와 archive node 중 무엇이 필요한가? |
| 외부 데이터 | 오라클을 통해 체인 밖 정보를 입력한다 | 데이터의 정확성, 최신성과 공급 중단을 누가 책임지는가? |

Ethereum PoS의 확정성은 체크포인트에 대한 **총 스테이크의 3분의 2 이상**을 대표하는 투표와 연결된다. 단순 노드 개수나 모든 체인에 공통인 정직한 참여자 비율로 바꾸어 설명하지 않는다. 블록이 처음 포함됐다는 사실만으로 확정됐다고 판단하지 않는다.

저장 비용도 노드 유형에 따라 다르다. Full node는 과거 상태를 정리할 수 있고 archive node는 역사적 상태 조회를 위해 더 많은 자료를 유지한다. 따라서 모든 노드가 모든 과거 상태를 영구 보관한다는 전제로 디스크 사용량을 계산하지 않는다.

## 결정성과 외부 데이터

Ethereum의 실행은 같은 초기 상태와 입력에서 같은 결과를 내야 한다. 노드마다 외부 환율 API를 직접 조회하면 응답 시점이나 장애에 따라 값이 달라질 수 있다. 오라클은 외부 데이터를 체인에서 사용할 수 있게 전달하지만, 입력의 정확성과 가용성에 관한 신뢰 문제까지 없애지는 않는다.

외부 입력이 틀렸는데 모든 노드가 같은 결과를 계산했다면 실행의 일치만 확인한 것이다. 현실의 사실까지 검증한 것으로 해석하지 않는다. 이는 오라클의 정확성과 결정성을 구분한 설계상의 귀결이다.

## 가스는 실행량의 한도이기도 하다

Gas는 Ethereum 연산에 필요한 계산 작업의 단위다. 트랜잭션별 gas limit은 무한 루프와 과도한 계산이 실행 자원을 끝없이 점유하지 못하도록 제한한다. 실행 도중 가스를 소진하면 해당 실행의 상태 변경은 되돌아가지만 사용한 가스 비용은 남는다. 실행 전 검증에서 거절되는 경우와 구분해야 한다.

## 선택 기준과 이해 확인

### 복제된 기록과 변경 권한은 별개다

Ethereum의 업그레이드 패턴은 배포된 코드를 직접 고치는 대신 프록시가 참조하는 로직 계약 등을 바꾼다. 상태와 사용자 진입 주소를 유지하면서 실행되는 업무 로직을 교체할 수 있으므로, 기록을 여러 노드가 검증한다는 사실만으로 애플리케이션의 규칙 변경 권한까지 분산되지는 않는다.

설계 검토에서는 누가 로직 주소를 바꿀 수 있는지, 승인 권한이 누구에게 모이는지, 변경 전 사용자가 확인할 시간과 이탈 경로가 있는지를 묻는다. 이는 업그레이드 구조에서 도출한 검토 질문이다. 관리자 키 하나가 존재한다는 사실을 체인의 과거 블록을 임의로 다시 쓸 수 있다는 뜻으로 확대하지 않는다.

부분 검증(2026-10-27): Ethereum의 공식 업그레이드 문서로 로직 교체와 상태 보존의 구분을 대조했다. 특정 서비스의 관리자 권한이나 탈중앙화 수준은 확인하지 않았다.

### 도입 판단

다음은 아키텍처 검토 질문이다. 특정 제품의 도입 결정이나 성능 보장은 아니다.

- 여러 주체가 단일 운영자를 신뢰하지 않고도 같은 기록을 검증해야 하는가?
- 운영자 하나가 업무 규칙을 결정하는 문제라면 일반 DB, 복제와 감사 기록으로 충족할 수 있는가?
- 체인의 확정 상태와 외부 시스템의 지급 완료를 어떻게 연결하고 중복 실행을 막을 것인가?
- 노드 수를 두 배로 늘리면 무엇이 두 배가 되는지, 저장과 검증 및 처리량을 나눠 설명할 수 있는가?
