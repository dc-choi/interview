# 일반화와 추상화

일반화와 추상화는 객체지향 설계에서 함께 쓰이지만 같은 작업은 아니다. 일반화는 여러 구체 개념의 공통 의미를 상위 개념으로 묶는 관계이고, 추상화는 특정 사용자가 문제를 다루는 데 필요한 특징만 드러내고 나머지 세부를 감추는 관점이다.

## 차이

| 축 | 일반화(Generalization) | 추상화(Abstraction) |
|----|------------------------|---------------------|
| 핵심 질문 | 이 대상들은 어떤 공통 종류로 묶이는가? | 이 맥락에서 사용자가 알아야 할 것은 무엇인가? |
| 출발점 | 여러 구체 타입이나 사례 | 복잡한 대상과 사용 맥락 |
| 결과 | 상위 타입과 하위 타입의 관계 | 단순하고 안정적인 역할이나 모델 |
| 반대 방향 | 특수화(Specialization) | 구체화(Concretization) |
| 대표 수단 | 상속, interface 구현, 타입 계층 | interface, facade, API, 캡슐화와 모델링 |

일반화도 넓은 의미의 추상화 기법 중 하나가 될 수 있다. 다만 모든 추상화가 타입 계층을 만들지는 않는다. 세부 구현을 함수나 service 뒤에 숨기는 것, 업무에 필요한 속성만 entity에 담는 것도 추상화다.

## 도형 예시

원, 사각형과 삼각형이 모두 넓이와 둘레를 계산할 수 있다면 `Shape`라는 상위 타입으로 일반화할 수 있다. 이때 실제 설계에서는 두 질문을 분리한다.

- 일반화: 세 타입이 같은 계약으로 대체 가능하고 같은 종류로 다뤄져도 되는가?
- 추상화: 호출자에게 넓이와 둘레만 보여 주고 좌표 저장, 계산 cache와 렌더링 세부는 숨겨도 되는가?

단순히 필드 이름이 같다는 이유만으로 일반화하면 우연한 중복을 잘못된 상속 관계로 굳힐 수 있다. 공통 의미와 대체 가능성이 있어야 한다.

## 결제 예시

여러 결제 수단을 `PaymentMethod`로 일반화하고 호출자에게 `pay()`라는 계약만 노출할 수 있다. 카드사 SDK, 인증 단계와 재시도는 구현 내부에 둔다.

- 일반화는 카드, 계좌와 간편결제를 같은 역할의 구현으로 묶는다.
- 추상화는 주문 service가 결제사별 세부 대신 안정적인 결제 계약에 의존하게 한다.

새 결제 수단이 기존 계약을 지키지 못하거나 실패와 취소 의미가 다르면 억지로 같은 타입에 넣지 않는다. 계약을 나누거나 더 적합한 모델을 찾는다.

## 문법과 개념을 구분한다

- `extends`를 썼다고 좋은 일반화가 되는 것은 아니다.
- `interface`나 `abstract class`를 만들었다고 유용한 추상화가 되는 것은 아니다.
- 상속은 코드 재사용보다 의미 있는 is-a 관계와 대체 가능성을 우선한다.
- 추상화는 정보를 없애는 일이 아니라 사용자가 알아야 할 정보와 책임을 선별하는 일이다.

## 설계 순서

1. 구체 사례와 변화하는 요구를 먼저 관찰한다.
2. 공통된 의미와 계약이 반복될 때 상위 개념을 후보로 잡는다.
3. 각 사용자의 필요에 맞춰 노출할 역할과 숨길 세부를 정한다.
4. 하위 구현이 상위 계약을 실제로 대체할 수 있는지 검증한다.
5. 새 요구가 생겼을 때 abstraction을 수정하지 않고 구현을 추가할 수 있는지 확인한다.

성급한 일반화는 잘못된 타입 계층을 만들고, 성급한 추상화는 사용 사례가 다른 코드를 하나의 계약에 가둔다. 반복되는 변화 방향이 보일 때 추상화하는 편이 안전하다.
