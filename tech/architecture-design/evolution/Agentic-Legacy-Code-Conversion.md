# 에이전트 기반 레거시 코드 전환 파이프라인

레거시 코드를 다른 언어나 프레임워크로 옮길 때 에이전트에게 파일을 통째로 번역시키지 않고, 분석으로 만든 지식 그래프에서 함수 단위 작업을 뽑아 변환한 뒤 빌드, 정적 검사, 리팩토링을 각각 검증 루프로 돌리는 방식이다. 빌드 성공은 기존 동작이 보존됐다는 증거가 아니므로, 사람은 변환된 코드의 업무 로직 검증과 테스트에 집중한다.

전환 전략 자체(Strangler Fig, Recode 등)는 [[Legacy-Modernization-Strategies|레거시 현대화 전략]], 낯선 레거시를 이해하고 작게 바꾸는 루프는 [[AI-Assisted-Legacy-Onboarding|AI를 활용한 레거시 온보딩과 변경]], 언어 중립 테스트 스위트가 있는 일괄 이전은 [[Agent-Language-Port|에이전트로 하는 대규모 언어 이전]]에서 다룬다. 이 문서의 단계 구분과 기법은 금융 코드 전환 사례(2026년 9월 공급사 발표)를 일반화한 것이다.

## 레거시 전환이 어려운 이유

- **코드 복잡도:** Pro*C처럼 SQL을 호스트 언어 안에 넣는 임베디드 SQL이 C 로직과 강하게 묶여 있으면, 다른 DB 접근 방식(매퍼나 ORM)으로 옮길 때 SQL과 로직을 함께 분해해야 한다.
- **숨은 규칙과 흩어진 자산:** 업무 규칙이 코드와 SQL 조건 안에 들어 있고, 화면, 배치, 대외 연계, 공통 모듈, 설정 파일, 담당자 경험에 자산이 흩어져 있다. 문서와 실제 구현이 다른 경우가 흔하다.
- **인력:** 레거시 언어를 운영하던 인력은 줄고 새 언어 개발자는 옛 코드를 읽기 어렵다.
- **기간과 병행 운영:** 대형 금융사는 구 시스템과 새 시스템을 오래 함께 돌리며 비용과 운영 복잡도를 진다. IBM 기업가치연구소(IBV)는 2025-09-22 보고서 제목을 The 94% core banking problem으로 붙이고, 소개 문구에서 현대화 프로젝트의 94%가 일정을 넘긴다고 적는다(2026-11-23 IBM 페이지 대조, 조사 표본과 지연의 정의는 보고서 본문을 열람하지 못해 확인하지 못했다).

## 파이프라인 한눈에 보기

| 단계 | 하는 일 | 다음 단계로 넘길 신호 |
|---|---|---|
| 분석(Analyze) | 소스, 헤더, SQL을 파싱해 파일과 함수의 호출, 사용 관계를 뽑고 영향도로 전환 대상을 고른다 | 누락 파일, 해석하지 못한 매크로와 동적 호출의 목록 |
| 문서화(Document) | 파일마다 함수 목록, 매개변수, 설명, 함수 안의 SQL 설명, 호출 순서도를 쓴다 | 업무 담당자의 표본 검토 |
| 분해와 지식 그래프(Decompose) | As-Is 요소와 To-Be 대상(메서드, DAO, DTO, SQL 매핑)을 잇고 전환 규칙을 붙인다 | 대응 대상이 없는 요소의 수 |
| 변환(Translate) | 그래프에서 함수별 변환 프롬프트를 만들어 함수 단위로 바꾼다 | 컴파일 오류 피드백 |
| 빌드(Build) | 병렬 빌드 에이전트가 성공할 때까지 오류를 고친다 | 빌드 성공 |
| 코드 검사(Code Inspection) | 정적 분석 규칙 위반을 찾아 고친다 | 규칙 위반 수 |
| 리팩토링과 최종 검증 | 품질 지표가 좋아지는 방향으로 다듬고 테스트와 품질 지표로 최종 검증한다 | 테스트 결과, 품질 점수 |

분석, 문서화, 분해 단계의 신호는 발표에 없는 설계 판단이다.

정적 분석에는 PMD 같은 규칙 기반 도구를 쓸 수 있다. PMD는 사용하지 않는 변수 같은 흔한 결함을 찾는 다언어 정적 분석기다(2026-11-23 공식 사이트 확인).

## 분석 결과를 지식 그래프로 쌓는다

함수 하나를 바꾸는 데 필요한 것은 전체 코드가 아니라 그 함수의 의존 요소, 대응할 대상과 규칙이다. 그래프는 이 부분 맥락을 결정적으로 뽑는 색인이 된다(해석).

- **노드:** As-Is 쪽은 프로그램, 함수, 헤더, 매크로, 구조체 정의와 필드, 함수 인자, SQL 쿼리, 호스트 변수다. To-Be 쪽은 DAO 파일과 메서드, DB 입출력 정의, 입출력 메시지 필드, Java 변수다. 전환 규칙(공통 함수 전환 규칙, 패턴 전환 규칙)도 노드로 둔다.
- **관계:** 호출(CALLS), 포함(CONTAINS, INCLUDES), 실행(EXECUTES), 정의와 선언(DEFINES, DECLARES), 대응(CORRESPONDS_TO, MAPS_TO, TRANSFORMED_TO), 참조(REFERENCES_DTO, REFERENCES_MACRO) 같은 유형이다.
- **담는 정보:** 각 As-Is 함수와 자료구조의 연관 요소와 호출, 사용 관계, 그것이 To-Be 아키텍처의 어느 메서드나 객체(관련 SQL 매핑, DAO, VO, DTO)에 대응하는지, 그 전환 방식의 지침이다.

구조 추출은 파서로 하고 AI는 설명 작성과 매핑 제안에 쓰는 편이 안전하다(설계 판단, 발표는 분담을 밝히지 않았다). 확인된 연결과 추론한 연결을 나눠 저장하는 원칙은 [[Codebase-Knowledge-Map|대규모 코드베이스 지식 지도]]와 같다.

## 함수 단위 변환 프롬프트에 넣는 것

- **대상 프레임워크 규칙:** 메서드에 붙일 필수 어노테이션과 속성, C 함수 하나를 메서드 하나로 1:1 대응시키고 새 메서드를 만들지 않는다는 규칙, 그 메서드 하나만 출력한다는 형식이다.
- **자료형 제한:** 값을 담는 변수는 정해 둔 타입(String, int, boolean, BigDecimal, Date(발표 화면 표기는 Data), DTO)만 쓰게 하고, 예를 들어 long은 BigDecimal로 옮긴다.
- **전역 상태:** C의 전역 변수 역할을 하는 데이터 클래스(context VO)를 만들어 내부 함수의 입출력으로 넘기고 매개변수 이름을 고정한다.
- **검증 피드백:** 생성 결과의 컴파일 오류(예: String을 int로 바꿀 수 없음)를 다시 넣어 자료형을 보완한 뒤 병합한다.
- **형식:** 지침, 자료형, 메서드 선언 규칙과 예시를 XML 태그로 나눠 넣었다.

이 방식은 원래 구조를 먼저 보존하고 관용적인 코드로의 정리는 뒤로 미루는 충실한 포팅이다(설계 판단). 전역 상태를 명시적인 인자로 바꾸면 숨은 의존이 드러나지만, 결과 코드는 대상 언어의 객체 설계가 아니라 C의 구조를 옮긴 모양이 된다.

자료형 대응은 의미 차이의 원인이 된다(해석). C의 정수 오버플로와 나눗셈 버림, 부동소수점 연산은 BigDecimal의 정밀도와 반올림 규칙과 다르게 동작할 수 있으므로, 금액과 수량 계산은 대표 입력의 기존 결과와 비교한다. 같아 보이는 코드가 다르게 동작해 회귀가 생긴 예는 [[Agent-Language-Port#같아 보이지만 다르게 동작하는 코드가 회귀를 만든다|Bun의 언어 이전]]에 있다.

## 온라인과 배치는 변환 방식을 달리한다

온라인 서비스는 함수 1:1 변환을 쓰고, 대량 데이터를 일괄 처리하는 배치는 대상 프레임워크의 배치 구조(Step)에 맞춰 함수를 다시 설계한다. 함수를 그대로 옮기면 대상 프레임워크의 청크 처리, 재시작과 트랜잭션 경계를 쓰지 못하기 때문이다(해석, [[Spring-Batch-Essentials|Spring Batch 핵심]]).

| 역할 | 하는 일 |
|---|---|
| 큐레이터 | 프레임워크 가이드와 배치 코드 샘플을 읽고 특성을 분류해 규칙을 뽑는다 |
| 코드 분석 | As-Is 코드와 파싱 결과로 에이전트가 쓰기 좋은 전환 패키지를 만든다 |
| 전환 플래너 | Step 분리 전략, 기존 DAO 같은 자산의 재사용 전략, 데이터 전달 바인딩을 정한다 |
| 코드 생성 | 계획대로 코드를 만들고 기존 자산을 쓴다 |
| 코드 리뷰 | 계획 충실도, DAO 바인딩과 매핑 완전성을 검증하고 통과나 실패 보고서를 낸다 |

실패하면 원인이 분석, 계획, 생성 중 어디의 결함인지 분류해 그 단계로만 최소한 되돌아간다. 처음부터 다시 돌리지 않으므로 반복 비용이 줄지만, 분류가 틀리면 엉뚱한 단계를 고치게 되므로 분류 근거를 보고서에 남긴다(해석).

## 빌드는 병렬 에이전트로 돌리고 성공의 뜻을 좁힌다

전환 파일이 늘면 빌드 오류의 맥락도 커진다. 파일 600개를 전환하면 Java 파일이 약 1만 2천 개 생긴다는 예가 발표에 나왔다. 관리 에이전트가 오류 조치 방법을 확인하며 빌드 과정을 지휘하고, 실행 에이전트들은 각자 별도 작업 공간에서 빌드, 오류 수정, 결과 보고를 성공할 때까지 반복한다.

빌드 성공은 컴파일 가능성만 뜻한다. 컴파일을 통과시키려고 함수를 빈 구현으로 바꾸거나 우회를 정당화하는 주석을 다는 행동은 [[Agent-Language-Port#작업 구조: 구현과 리뷰를 다른 에이전트에 둔다|다른 대규모 이전]]에서도 관찰됐으므로, 리뷰 단계에서 이런 통과용 우회를 거부하는 규칙을 둔다(설계 판단).

## 지표 기반 리팩토링 루프

1. 정적 분석 도구로 품질 지표를 잰다.
2. 기준에 못 미치는 항목을 영향도로 정렬한다.
3. 에이전트가 한 라운드에 한 항목만 고친다. 고치기 전과 후에 테스트를 돌린다.
4. 테스트를 수행하고 지표를 다시 잰다. 점수가 오르면 체크포인트 커밋 뒤 진행하고, 오류가 나거나 전체 점수가 떨어지면 최고 점수 체크포인트로 자동 롤백한 뒤 다른 방법으로 다시 시도한다.

다음 대상은 지표 추이로 고르고, 과거에 AI가 리팩토링에 실패한 항목은 우선순위가 높아도 뒤로 미룬다. 지표를 재는 도구는 교체할 수 있게 둬서 다른 지표를 최적화할 때 도구만 바꾼다. 한 라운드에 한 항목만 다루면 실패 원인이 좁혀지고 되돌리기가 싸진다. 반면 점수만 좇으면 지표가 보지 못하는 설계 품질이 나빠질 수 있으므로 테스트 통과를 롤백 조건에 함께 두는 것이 전제다(해석, [[Agent-Loop-Engineering#점수가 오른다고 결과가 좋아지지는 않는다|점수 상승과 결과의 구분]], [[Architecture-Fitness-Functions|아키텍처 fitness function]]).

## 동작 보존은 빌드와 따로 증명한다

변환 결과의 완료는 컴파일 성공, 정적 규칙 통과, 기존 동작 보존(같은 입력에 같은 출력과 DB 상태), 성능, 운영 전환 준비로 나눠 판정한다. 기존 동작 보존의 근거는 다음 셋에서 고른다.

- 변환 전에 고정한 특성화 테스트와 승인 테스트([[Legacy-Code-Testing|레거시 코드의 특성화, 승인과 변이 테스트]])
- 운영 거래 기록을 재현해 결과를 비교하는 회귀 검증([[Regression-Test-Automation#운영 거래 기록을 재현해 회귀 기준을 만든다|운영 거래 재현 회귀]])
- 같은 입력을 구 시스템과 새 시스템에 함께 넣어 출력을 비교하는 병렬 실행([[Legacy-Modernization-Strategies#3. Recode (재작성)|Recode의 병렬 QA]], [[Shadow-Traffic|Shadow Traffic]])

새 고객사에 적용하기 전에는 외부 라이브러리 처리, 테스트 환경과 수행 방안, 전환 중에 들어오는 As-Is 코드 변경 요청의 반영 방안을 먼저 합의한다. 전환 기간에 원본이 계속 바뀌면 변환 결과가 낡으므로 변경 동결 범위나 재변환 절차를 정해 둔다(해석).

## 읽기 전용 분석부터 시작한다

변환보다 먼저 쓸 수 있는 것은 분석이다. 코드, 모듈과 배치, DB와 API(테이블, 뷰, 저장 프로시저), 설계와 운영 문서를 읽기 전용으로 연결해 세 산출물을 만든다.

1. 시스템 구조와 호출 흐름: 화면이나 서비스에서 모듈을 거쳐 DB까지의 경로
2. 업무 규칙과 근거 코드의 연결: 규칙, 그 규칙이 들어 있는 코드, 설명을 한 묶음으로
3. 변경 대상, 영향 범위, 테스트 대상의 연결

코드와 데이터는 조회만 하고 배포와 운영 환경은 바꾸지 않는다. 실행 권한은 읽기 전용 분석, 변경안 제안, 승인 범위 안의 수정, 빌드와 테스트 자동화, 반복 운영 순으로 승인과 검증 근거가 쌓인 범위부터 넓힌다. 통제된 변경 흐름은 [[Enterprise-Code-Agent-Operations#금융 코드 변경은 영향 범위부터 통제한다|기업 코드 에이전트 운영]], 자율권 조정의 일반 원칙은 [[Production-Agent-Architecture-Delegation#자율권은 작업별 증거로 넓히고 다시 줄인다|작업별 증거로 자율권 조정]]을 따른다.

생성된 분석 산출물도 검증 부담을 만든다. 산출물이 수천 건이면 사람이 전수 확인할 수 없으므로 표본 기준, 업무 담당자 확인이 필요한 미결 항목, 확인된 규칙과 추론한 규칙의 구분을 처음부터 정한다(해석).

## 사례 (2026년 9월 발표 기준, 공급사와 고객사 발표)

- **금융사 C to Java 선도 개발:** Pro*C 기반 계정계와 정보계의 주요 온라인, 배치 서비스 199개(파일 3,500개, 종합 잔고 조회, 예수금 조회, 매수 가능 수량 계산 등)를 66시간에 전환해 Java 파일 약 5.6만 개를 만들었고, 출력 파일당 4.24초(H100 GPU 8장)라고 밝혔다. 변환 직후(빌드 에이전트 실행 전) 빌드 성공률 95.5%, 최종 100%다. 목적은 차세대 착수 전에 레거시 C 코드의 사양서, 거래 흐름과 기반 Java 코드를 확보하는 것이며, 6,500개를 더해 1만 개로 넓히는 2차 선도 개발이 진행 중이라고 했다. 빌드 성공은 컴파일 기준이고, 기능 동등성 시험 결과, 사람이 고친 양, 66시간에 포함된 단계는 공개되지 않았다.
- **지식 그래프 규모:** 발표 화면의 전환용 그래프는 노드 902,726개, 관계 2,425,607개였다.
- **리팩토링 추이:** 사내 품질 지표의 종합 점수가 약 190회의 라운드에 걸쳐 약 3.88에서 약 4.0으로 올랐다(발표 그래프 판독). 지표의 정의와 척도는 공개되지 않았다.
- **레거시 분석 적용(2026년 7월, As-Is에서 Spring으로의 전환 프로젝트):** 고객 조회 화면, 보험 해약 접수, 카드 납입과 매입 청구, 프레임워크 모듈 영역(Java, Spring Boot, JPA, Maven)에서 소스 파일 6,294개를 분석해 업무 규칙 1,129개와 SQL 652개를 뽑고, 코드 86,423줄을 전환하고 단위 테스트 1,305개와 문서 6종을 만들었다고 밝혔다. 확인된 사항으로 소스만으로 업무 로직을 문서화할 수 있었다는 점, 표준 규칙 기반의 일관된 전환, 전환 결과 검증 체계의 동작을 들었고, 다음 단계로 미결 항목의 현업 확인, 난이도 상위 화면의 추가 검증, 성능 검증을 남겼다. 업무 규칙의 정확도와 단위 테스트의 기대값을 무엇으로 정했는지는 공개되지 않았다.
- **분석 산출물의 검증 부담:** GS리테일은 레거시 소스코드, DB와 API를 AI로 분석해 문서와 다이어그램을 대량으로 만드는 도구를 포함해 AI 도구들이 산출물을 쏟아내는 상황에서, 한 시스템의 분석 산출물만 16,979건이라 건당 5분씩 사람이 확인하면 약 9MM이 들어 전수 확인이 사실상 불가능하다고 밝혔다.
- **대조하지 못한 인용 통계:** 발표가 인용한 업계 통계 가운데 IBM의 94%만 위에서 대조했다. 금융 IT 예산의 레거시 유지보수 비중 70%(McKinsey 인용)와 레거시 유지보수 가능 인력 2명 이하 77%(Baringa 인용)는 인용된 1차 자료에 접근하지 못해 대조하지 못했다. 발표의 2차 인용으로만 적어 두며 근거로 쓰지 않는다.
