# API 버저닝 설계 (API Versioning Design)

이 문서는 **언제 버전을 만들고 언제 없애는가**를 다룬다. URI, 헤더, 미디어 타입 중 무엇으로 버전을 실어 보낼지의 전달 방식은 [[API-Versioning|API 버저닝 메커니즘]]과 [[API-Conventions-Operations|API 규약 운영]]에 있고, 여기서는 그보다 앞선 판단과 그 뒤의 수명주기를 본다.

짝 문서와의 경계는 이렇다. 어떤 변경이 계약을 깨는지의 기질 중립 판정과 호환 유지 대 새 버전으로 끊기의 비용 비교(분기 폭발)는 [[Backward-Compatibility-Design|하위 호환성 설계]]가 소유한다. 이 문서는 그 판정 뒤에 남는 버저닝 결정, 즉 additive로 흡수할지 버전으로 끊을지의 필터, 버전 스코프, 폐기 수명주기를 맡는다.

핵심 전제는 하나다. 새 버전은 기본값이 아니라 마지막 수단이다. 버전 하나를 만드는 순간 생기는 것은 코드 분기가 아니라 **폐기까지 이어지는 운영 계약**이고, 그 계약에는 유지 비용, 소유자, 종료일이 따라붙는다.

## 버전을 올리기 전에 묻는 것

새 버전 제안이 들어오면 세 질문을 순서대로 통과시킨다. 하나라도 앞에서 걸리면 버전은 만들지 않는다.

1. **additive change로 끝나는가** — 선택 파라미터 추가, 응답 필드 추가, 새 엔드포인트 신설로 목적을 달성할 수 있으면 버전은 불필요하다. Stripe가 backward-compatible로 분류하는 변경도 정확히 이 범주다 (새 리소스 추가, 기존 메서드에 선택 파라미터 추가, 기존 응답에 속성 추가, 응답 속성 순서 변경, 새 이벤트 타입 추가).
2. **계약을 깨는가, 현재 영향은 얼마인가** — 명세와 공개 계약이 breaking 여부를 정의한다. 실제 트래픽과 소비자 계측은 지금 영향받는 호출자가 누구인지, 언제 제거할 수 있는지를 보여 준다. 명세상 안전한 필드 추가도 스키마 비인식 클라이언트에는 파싱 실패가 될 수 있으므로 contract test와 계측을 함께 본다.
3. **깨지는 소비자를 식별할 수 있는가** — 식별할 수 없으면 새 버전을 만들어도 구버전을 영원히 못 없앤다. 이 경우 필요한 것은 버전이 아니라 **계측**이다.

## 스키마에 안 보이는 HTTP 계약

필드 추가와 제거, required 승격, enum 확장, 제약 강화 같은 판정표와 의미만 바뀌는 변경이 가장 위험한 이유는 [[Backward-Compatibility-Design|하위 호환성 설계]]가 소유한다. Google AIP-180과 Stripe의 호환성 규칙이 그 판정의 REST 쪽 구체형이다. 여기서 더할 것은 **응답 스키마에 표현되지 않아 스키마 diff가 통과시키는 HTTP 계약**이다.

| 변경 | 판정 | 버저닝 관점 |
|---|---|---|
| 에러 코드, HTTP 상태 코드 변경 | breaking | 재시도, 서킷브레이커, 알림 규칙이 상태 코드에 붙어 있다. 새 코드는 추가하고 옛 코드는 폐기 경로로 뺀다 |
| 기본 정렬, 기본 페이지 크기 변경 | breaking | 명세에 없어도 소비자가 관측된 동작에 의존하는 암묵 계약이다. 새 기본값은 선택 파라미터로 먼저 노출한다 |
| ID 길이, 형식 변경 | 소비자에 따라 갈림 | Stripe는 object ID 같은 opaque string의 길이와 형식 변경을 backward-compatible로 분류한다 (접두사 추가와 제거 포함, 최대 255자 저장 권고). ID를 opaque로 다루는 계약이라면 호환되지만, 길이 제한 컬럼이나 정규식 제약을 공개 계약으로 둔 경우에는 breaking이다. 트래픽 계측은 영향 소비자를 찾는 증거다 |
| 요구 스코프, 권한 조건 강화 | breaking | 같은 토큰의 호출이 403이 된다. 요청과 응답 스키마는 그대로다 |

버저닝 결정으로 옮기면 질문은 하나로 좁혀진다. **그 변경을 새 필드나 새 코드 추가로 흡수하면 버전은 필요 없고, 옛 표현을 즉시 없애야 하거나 흡수할 자리가 없으면 그때 버전이다.** 의미 변경을 필드 재사용 없이 새 필드로 처리하는 규칙 자체는 위 짝 문서를 따른다.

## 버전 단위를 어디에 둘 것인가

| 전략 | 적합한 상황 | 대가 |
|---|---|---|
| 전역 API 버전 (v1, v2 전체) | 외부 공개 API, 파트너 연동 | 무관한 엔드포인트까지 함께 올라가 소비자 이주 비용이 커진다 |
| 리소스, 엔드포인트 단위 버전 | 변경이 특정 도메인에 몰릴 때 | 소비자가 엔드포인트마다 다른 버전을 조합해 지원 조합이 폭발한다 |
| 무버전 (additive + deprecation) | 사내 단일 소비자, 동시 배포 가능한 조직 | 폐기 규율과 계측이 없으면 필드 묘지가 된다 |

선택 축은 세 가지다.

- **소비자 통제력** — 사내 서비스는 내가 배포 시점을 정할 수 있고, 파트너는 협의가 필요하며, 강제 업데이트가 없는 모바일 앱은 통제력이 사실상 0이다. 통제력이 낮을수록 명시 버전과 긴 공존 기간이 필요하다.
- **배포 결합도** — 서버와 클라이언트를 같은 파이프라인에서 동시에 배포할 수 있으면 버전을 만드는 것보다 동시 배포가 훨씬 싸다. 사내 단일 소비자에게 v2를 만드는 것은 대개 과설계다.
- **동시 유지 비용** — 버전 N개는 테스트 N배, 장애 대응 경로 N배다. 이 비용을 감당할 팀 규모가 아니면 버전 수 자체를 설계 제약으로 둔다.

## 공존 기간 운영

구버전과 신버전이 동시에 사는 동안에도 **도메인 로직과 데이터 모델은 하나**여야 한다.

- **상위 버전을 정본으로 둔다** — 서비스 계층과 도메인 모델은 최신 버전 기준으로만 작성한다.
- **구버전은 경계 계층 어댑터로 변환한다** — 컨트롤러 바로 안쪽에서 신버전 응답을 구버전 형태로 되돌리는 변환기를 둔다. 변환기는 얇고, 삭제 시점에 파일 단위로 지워진다.
- **서비스 계층에 버전 분기를 심지 않는다** — `if (version === 'v1')`이 도메인 로직에 들어가면 폐기가 코드 전역 수색이 된다. 분기가 경계에만 있으면 폐기는 어댑터 삭제로 끝난다.
- **두 버전을 통째로 복제하지 않는다** — 복제는 초기엔 편하지만 버그 수정이 한쪽에만 반영되며 드리프트가 쌓인다. 공존 기간이 길수록 복제 비용은 기하급수적이다.

공존 중 DB 스키마는 구버전과 신버전 코드가 동시에 읽고 쓰므로 전후방 호환이어야 한다. 구체적인 expand-contract 절차는 [[Blue-Green|Blue-Green 배포]], 마이그레이션 히스토리 운영은 [[Schema-Versioning|스키마 버저닝]]에 위임한다.

## 폐기 정책

폐기는 공지 한 번이 아니라 4단계이고, 각 단계는 종료 조건을 만족해야 다음으로 넘어간다.

| 단계 | 하는 일 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| 1. 예고 | 명세에 deprecated 표기, 응답에 `Deprecation`, `Sunset` 헤더, 대체 경로 안내 | 대체 경로가 실제로 동작하고 문서화됨 |
| 2. 계측 | 클라이언트별 호출량, 최종 호출 시각, 버전별 트래픽 비중 수집 | 남은 호출자를 전부 식별하고 연락 경로 확보 |
| 3. 축소 | 신규 사용 차단, 개별 이주 지원, 필요하면 rate limit 하향 | 잔여 트래픽이 합의한 임계 아래이고 남은 호출자가 이주 일정에 동의 |
| 4. 제거 | 라우트와 어댑터 삭제, 계약과 인덱스에서 제거 | 제거 후 관측 기간에 4xx 급증 없음 |

- **증거 기반 제거의 일반 원칙은 짝 문서를 따른다** — 소비자 식별자별 사용량 계측, 소비자 인벤토리, 계절성 때문에 관측 창을 넓게 잡는 규칙, `Deprecation`과 `Sunset` 헤더가 계약이 아니라 힌트라는 점은 [[Backward-Compatibility-Design|하위 호환성 설계]]의 Contract 단계가 소유한다. 아래는 버전 폐기에만 붙는 조건이다.
- **종료 조건은 공지가 아니라 동의다** — Zalando RESTful API Guidelines는 폐기 항목에서 `MUST monitor usage of deprecated API scheduled for sunset`과 `MUST obtain approval of clients before API shut down`을 나란히 둔다. 남은 호출자의 이주 합의를 3단계 종료 조건에 명시하지 않으면 4단계는 일방 삭제가 된다.
- **장수 클라이언트에는 다른 종료 조건을 준다** — 강제 업데이트가 없는 모바일 앱, 분기 단위로만 도는 사내 배치, 파트너 연동은 일반 공존 기간 안에 이주하지 못한다. 최소 지원 앱 버전 정책처럼 그 버전만의 종료 조건을 계약에 적고, 이 소비자가 남아 있는 한 버전 수 상한은 그만큼 잠긴다.

## 버전 수를 늘리지 않는 규율

- **동시 지원 버전 상한을 숫자로 못 박는다** — 예를 들어 2개. 3번째를 만들려면 먼저 가장 오래된 것을 지워야 한다. 상한이 없으면 버전은 단조 증가한다.
- **신설 게이트를 둔다** — 폐기 계획(종료 조건, 예상 일정, 소유자)이 없는 새 버전은 승인하지 않는다. 만드는 비용보다 없애는 비용이 크기 때문이다.
- **버전별 소유자와 EOL 날짜를 계약에 명시한다** — 소유자가 없는 버전은 아무도 지우지 않는다. Stripe가 월간 릴리스는 backward-compatible만, 메이저 릴리스만 breaking을 담는다고 공개 정책으로 고정한 것도 같은 종류의 규율이다 (2026-08-31 문서 기준).
- 이 상한과 게이트를 사람의 기억이 아니라 CI 게이트와 지속 모니터로 옮기는 방법은 [[Architecture-Fitness-Functions|아키텍처 fitness function]]을 따른다.

## 흔한 실패 패턴

- **만들기만 하고 폐기하지 않음** — v1부터 v4까지 영구 병존. 테스트 매트릭스와 장애 대응 경로가 4배가 되고, 신규 기능은 어느 버전까지 지원할지 매번 논쟁거리가 된다.
- **내부 리팩터링마다 버전 상승** — 소비자가 보는 계약이 그대로면 버전은 올라가지 않는다. 버전은 내부 변경량이 아니라 계약 변경 여부를 따른다.
- **버전 번호에 마케팅 의미 부여** — v2를 신제품 이름처럼 쓰면 호환성 신호가 흐려지고, 사업 일정 때문에 breaking이 아닌 변경에도 버전이 붙는다.
- **계측 없는 일방 공지 후 제거** — 공지 메일과 헤더만 붙이고 삭제하면 조용한 소비자가 장애로 드러난다.
- **두 버전 전체 복제** — 한쪽에만 반영된 버그 수정이 드리프트로 쌓인다.
- **버전은 올렸는데 데이터 모델이 같음** — 구버전 응답이 신버전 도메인 로직의 버그를 그대로 받는다. 어댑터 방식의 정상 동작이므로, 이걸 격리하려 했다면 애초에 버전이 아니라 별도 서비스가 필요했던 것이다.

## 면접 체크포인트

- 버전을 올리지 않고 해결하는 경우를 먼저 설명할 수 있는가 (additive change, 신규 필드 추가 후 구필드 폐기)
- 이미 breaking으로 판정된 변경을 additive로 흡수할지 버전으로 끊을지의 기준을 댈 수 있는가
- 소비자 통제력(사내, 파트너, 강제 업데이트 없는 모바일)에 따라 전략이 갈리는 이유
- 폐기가 계측에 의존하는 이유와, 계측 없이 제거했을 때 생기는 일
- 공존 기간에 버전 분기를 경계 계층에 두는 이유 (폐기가 어댑터 삭제로 끝나는가, 코드 전역 수색이 되는가)
- 동시 지원 버전 상한을 숫자로 두는 이유와 신설 게이트의 역할
- 폐기 각 단계의 종료 조건을 경과 시간이 아니라 증거와 잔여 호출자의 동의로 두는 이유
