# 라이브러리 ABI 안정성 설계

API는 소스 코드의 호출 계약이고 ABI는 컴파일된 바이너리가 연결되는 계약이다. 헤더가 같아 보여도 구조체 배치, 열거형 크기, 심볼 이름이나 호출 규약이 바뀌면 다시 빌드하지 않은 바이너리가 깨진다. 배포판이 라이브러리를 따로 패키징하고 애플리케이션이 동적으로 연결하게 하려면 ABI를 판이 바뀌어도 유지해야 한다. 런타임별 사례는 [[Nodejs-Native-Addons|Node.js 네이티브 애드온의 API와 ABI]]에 있다.

## 무엇이 ABI를 깨는가

| 변경 | 다시 빌드하지 않은 호출자에게 생기는 일 |
|---|---|
| 공개 구조체의 필드 추가, 삭제나 순서 변경 | 컴파일 때 정한 크기와 오프셋이 실제와 달라진다 |
| 열거형 기반 타입의 크기 변화 | 인자와 필드의 크기가 달라진다 |
| 함수 시그니처 변경, 심볼 삭제나 개명 | 로드나 연결이 실패하거나 잘못된 인자로 호출된다 |
| 내부 구조에 의존하는 인라인 함수와 매크로 | 옛 바이너리에 옛 구현이 박혀 있어 새 라이브러리와 어긋난다 |

## 진화할 여지를 남기는 기법

- **불투명 핸들:** 공개 헤더에는 포인터 타입만 두고 구조체 정의를 숨긴다. 호출자는 크기와 오프셋을 모르므로 내부 필드를 바꿔도 바이너리가 깨지지 않는다. 대신 생성과 해제를 라이브러리 함수로만 하고 접근마다 함수 호출이 든다.
- **열거형 키로 묻는 getter와 setter:** 값마다 함수를 만들지 않고 핸들과 키를 받아 값을 읽고 쓰게 하면, 새 값을 추가해도 새 심볼이 필요 없다. 대신 컴파일 시 타입 검사가 약해진다.
- **크기 필드와 예약 공간:** 꼭 공개해야 하는 구조체에는 자기 크기를 담는 필드나 예약 패딩을 둬 나중에 필드를 늘린다. 라이브러리는 받은 크기로 호출자가 아는 판을 판단한다.
- **열거형 크기 고정:** 컴파일러와 설정에 따라 열거형 기반 타입이 달라질 수 있으므로 `int`처럼 크기를 정해 둔다.
- **모르는 요청에 오류 돌려주기:** 새 헤더로 빌드한 호출자가 옛 라이브러리에 새 키를 물으면 충돌 대신 지원하지 않는다는 결과를 돌려준다.

## 배포와 검사

- **SONAME:** ELF 공유 라이브러리를 만들 때 DT_SONAME 필드에 넣는 이름이다. 이 필드가 있는 라이브러리와 링크한 실행 파일은 실행할 때 링크 시점의 파일 이름 대신 SONAME으로 라이브러리를 찾는다(2026-11-09 GNU ld 문서 대조). 그래서 같은 SONAME의 새 판은 재빌드 없이 교체돼 적재되므로, 호환을 깨는 판에서만 SONAME을 바꾸는 것이 관례다.
- **ELF 심볼 버전:** GNU ld의 version script는 버전 노드의 트리를 정의한다. 프로그램은 각 라이브러리에서 필요한 버전 노드를 기록하고, 동적 로더는 시작할 때 그 노드가 있는지 확인해 너무 옛 라이브러리를 실행 도중이 아니라 시작 시점에 걸러낸다. 같은 함수의 여러 판을 한 라이브러리에 두고 새 연결의 기본판을 정할 수도 있다(2026-11-09 GNU ld 문서 대조).
- **CI의 ABI 비교:** 직전 릴리스와 ABI 산출물을 비교해 깨짐을 사람이 아니라 CI가 잡게 한다. libabigail은 ABI 관련 산출물을 만들고 비교하는 라이브러리다. 도구가 없는 플랫폼은 공개 타입의 크기와 배치를 적은 기준 목록과 비교한다.
- **패키징:** 공유와 정적 라이브러리, 헤더, pkg-config와 CMake 설정 파일, 오프라인 빌드용 소스와 의존성 묶음을 함께 내면 배포판이 별도 패키지로 만들기 쉽다.

## 내장되는 라이브러리의 자원 계약

다른 프로그램 안에 들어가는 라이브러리는 기능 외에 자원 사용 방식도 계약이다. 스레드를 만들지 않고 메모리를 호출자가 바꿀 수 있는 할당자로만 잡으면 호출자의 이벤트 루프와 메모리 정책 안에 넣기 쉽다. 하위 시스템을 컴파일에서 뺄 수 있는 기능 플래그가 있으면 WebAssembly나 bare metal처럼 작은 대상에도 넣을 수 있다.

## 사례: libghostty-vt 1.0

2026-11-06 발표를 2026-11-09 대조했다. Ghostty 터미널의 에뮬레이션 핵심을 분리한 C 라이브러리이며, 1.0에서 라이브러리와 C ABI를 안정판으로 선언하고 semantic versioning을 따른다.

- **ABI 설계:** 모든 객체는 불투명 핸들이고, 값은 열거형 키 getter와 setter로 다룬다. 공개 구조체는 크기나 예약 패딩을 갖고 열거형은 `int`로 고정한다. 새 헤더를 옛 라이브러리와 쓰면 충돌 대신 `GHOSTTY_UNSUPPORTED`를 받는다.
- **검사:** CI가 Linux에서 libabigail로, macOS와 WebAssembly에서 기준 타입 목록으로 변경을 검사한다. ELF 플랫폼에서는 내보내는 심볼에 버전을 붙여 맞지 않는 라이브러리는 로드되지 않게 한다.
- **배포:** Ghostty 앱과 별도의 릴리스 주기를 갖고, 서명한 소스 tarball과 오프라인 빌드용 의존성 tarball을 낸다. 빌드는 SONAME 있는 공유와 정적 라이브러리, 헤더, pkg-config와 CMake 설정을 설치한다. MIT 라이선스다.
- **자원:** 스레드를 만들지 않고 사용자 지정 할당자로만 할당한다. SIMD를 끄면 libc 없이 빌드할 수 있다. 저자는 4코어, 8GB Linux 서버에서 터미널 10,000개를 셸과 함께 돌린 시험을 소개한다.
- **채택:** JetBrains IDE의 터미널, Turborepo의 작업 출력 렌더링, OrbStack 등이 쓰고, Neovim에서는 libvterm을 바꾸는 PR이 승인돼 태그 릴리스를 기다린다.
- **범위의 한계:** 렌더링과 입력 처리까지 안정성 약속에 들어가는지는 발표에서 분명하지 않다. 일부 플랫폼은 CI에서 빌드만 하고 시험하지 않는다.

## 점검 항목

- 공개 헤더에 크기가 드러난 구조체가 있는가? 있다면 필드를 늘릴 방법이 있는가?
- 열거형 크기가 고정돼 있는가?
- 새 기능이 새 심볼을 요구하는가, 기존 키 조회로 들어갈 수 있는가?
- CI가 직전 릴리스와 ABI를 비교하는가?
- 호환을 깨는 변경이 SONAME 변경과 함께 가는가?
- 옛 라이브러리와 새 헤더 조합에서 충돌 대신 오류를 돌려주는가?
