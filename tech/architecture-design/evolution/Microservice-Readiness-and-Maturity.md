# 마이크로서비스 준비도와 성숙도

마이크로서비스는 서비스 개수가 아니라 **독립적인 변경과 운영 능력**을 얻기 위한 선택이다. 분산 시스템 비용을 감당할 준비 없이 프로세스만 나누면 모놀리스의 결합이 네트워크와 배포 파이프라인으로 이동한다.

따라서 도입 결정은 기술 목록이 아니라 해결할 사업 문제, 조직 경계, 전달 능력과 운영 증거를 함께 봐야 한다.

## 아키텍처는 스펙트럼이다

| 선택 | 배포 단위 | 경계 강제력 | 분산 비용 | 잘 맞는 상황 |
|---|---|---|---|---|
| 모놀리스 | 하나 | 팀 규율과 코드 규칙 | 낮음 | 작은 팀, 불확실한 제품과 도메인 |
| [[Modular-Monolith|모듈러 모놀리스]] | 하나 | 모듈 API와 의존성 검사 | 낮음 | 경계를 학습하면서 빠르게 전달해야 할 때 |
| 거친 서비스 분할 | 소수 | 프로세스와 API | 중간 | 경계가 일부 안정됐고 독립 운영을 연습할 때 |
| 마이크로서비스 | 다수 | API, 데이터 소유권과 팀 책임 | 높음 | 독립 배포와 확장의 가치가 운영 비용을 넘을 때 |

목표는 오른쪽 끝에 도달하는 것이 아니다. 현재 문제를 가장 낮은 복잡도로 해결하는 지점을 고른다.

## 준비도 7축

### 1. 사업 동기

- 팀 간 릴리스 대기, 특정 기능의 부하 편차, 규제 경계처럼 현재의 병목이 관측됐는가
- 분리 후 줄어들 리드 타임이나 장애 영향 범위를 측정할 수 있는가
- 미래에 커질 것이라는 추측만으로 분산 비용을 선결제하고 있지 않은가

### 2. 도메인과 경계

- 팀이 핵심 업무 흐름과 용어를 함께 이해하는가
- 변경이 함께 일어나는 기능과 데이터가 같은 경계에 있는가
- 서비스 간 호출 없이 지켜야 할 비즈니스 불변식을 설명할 수 있는가

초기에는 경계를 틀릴 가능성이 높다. 프로세스 사이 기능 이동은 모듈 사이 이동보다 비싸므로, 모듈러 모놀리스나 거친 서비스로 먼저 학습할 수 있다.

### 3. 팀 소유권

- 서비스의 개발, 배포, 운영과 장애 대응 책임자가 명확한가
- 팀이 UI, 애플리케이션, 데이터와 운영을 가로질러 결과를 낼 수 있는가
- 조직의 의사소통 경계와 서비스 경계가 심하게 충돌하지 않는가

DevOps는 별도 도구팀의 이름이 아니라 개발과 운영이 전달 결과를 함께 책임지는 방식이다.

### 4. 독립 전달

- 한 서비스 변경을 다른 서비스의 동시 배포 없이 출시할 수 있는가
- 자동 테스트, 하위 호환 계약, 점진 배포와 빠른 롤백이 있는가
- 새 실행 환경을 반복 가능하게 프로비저닝할 수 있는가

배포를 항상 조율해야 한다면 프로세스는 나뉘었어도 독립 배포라는 핵심 가치는 얻지 못한 상태다.

### 5. 데이터 소유권과 일관성

- 각 데이터의 쓰기 권한과 기준 시스템이 명확한가
- 다른 서비스가 소유 테이블을 직접 수정하지 않고 계약을 통하는가
- 즉시 일관성이 필요한 불변식과 지연을 허용할 뷰를 구분했는가
- 중복, 순서 역전, 재시도와 보상 실패를 처리할 수 있는가

데이터 소유권은 처음부터 물리 서버를 모두 분리하라는 규칙이 아니다. 같은 DBMS를 쓰더라도 스키마, 계정과 쓰기 경계를 강제하며 점진적으로 분리할 수 있다.

### 6. 운영과 회복성

- 오류율, 지연, 포화도와 사업 지표를 서비스별로 볼 수 있는가
- 요청과 이벤트의 상관관계를 끝까지 추적할 수 있는가
- timeout, 제한된 retry, circuit breaker, bulkhead와 backpressure 정책이 있는가
- 부분 장애와 의존성 장애를 훈련하고 복구 시간을 측정하는가

서비스 분리는 장애 지점을 늘린다. 격리는 경계 자체가 아니라 제한, 실패 처리와 검증된 복구 절차가 만든다.

### 7. 거버넌스와 보안

- 인증, 권한, secret, 감사와 공급망 정책의 최소 기준이 있는가
- 로그, 지표, 배포와 API 계약에 공통 paved road가 있는가
- 기술 자율성이 팀 전체의 운영 부담으로 전가되지 않는가

분산 거버넌스는 모든 팀이 다른 스택을 써야 한다는 뜻이 아니다. 제한된 기본 스택과 예외 절차가 보통 더 지속 가능하다.

## 증거 기반 도입 게이트

다음 질문에 문서나 운영 지표로 답할 수 있을 때 첫 분리를 검토한다.

1. 현재 병목과 성공 지표는 무엇인가
2. 후보 경계의 소유 팀과 데이터는 무엇인가
3. 독립 배포가 실제로 가능한가
4. 네트워크 실패와 일관성 지연을 어떻게 다룰 것인가
5. 관측, 경보, rollback과 incident 대응이 준비됐는가
6. 분리 효과가 없을 때 되돌리거나 다시 합칠 수 있는가

모든 축이 완벽할 필요는 없다. 다만 위험을 아는 것과 누가 언제 보완할지 합의한 것이 체크리스트 통과보다 중요하다.

## 점진적 전환 루프

```text
현재 병목 측정
  -> 모듈 경계 정리
  -> 변화율이 높고 독립 가치가 큰 한 경계 선택
  -> 계약, 데이터 소유권과 실패 정책 정의
  -> 점진적으로 트래픽 이동
  -> 전달 속도와 운영 비용 재측정
  -> 유지, 추가 분리, 재결합 중 선택
```

성숙도는 서비스 수, Kubernetes 사용 여부나 polyglot 개수로 판단하지 않는다. 작은 변경의 lead time, 독립 배포 비율, 복구 시간, 변경 실패율과 서비스 간 조율 횟수처럼 결과로 판단한다.

## 자주 만나는 오해

- **MSA면 확장성이 좋아진다**: 선택 확장이 가능해질 뿐, 상태와 호출 경계가 나쁘면 병목도 분산된다.
- **MSA면 장애가 격리된다**: timeout과 bulkhead가 없으면 연쇄 장애가 더 쉬워진다.
- **서비스마다 DB 제품이 달라야 한다**: 필요한 것은 소유권과 계약이지 기술 다양성 자체가 아니다.
- **공유 DB는 언제나 금지다**: 직접 교차 쓰기는 피해야 하지만 물리 분리는 준비도에 따라 단계적으로 할 수 있다.
- **한 번 나누면 계속 더 작게 나눠야 한다**: 경계가 잘못됐거나 조율 비용이 크면 합치는 것도 진화다.
