# 통합 임베딩 공간과 범용 리트리버

추천 칸(지면 안의 구좌)마다 후보 모델을 따로 두면 칸이 늘수록 학습 파이프라인, 서빙과 모니터링이 함께 늘고, 같은 개선을 모델마다 반복해야 한다. 통합 임베딩은 상품, 브랜드, 카테고리, 사용자를 하나의 벡터 공간에 두고, 각 칸의 요청을 기준 벡터 하나와 조건의 조합으로 바꿔 범용 리트리버 API 하나로 후보를 꺼내는 설계다.

## 요청을 기준과 조건으로 나눈다

추천 칸이 묻는 것은 누구에게 무엇을 어떻게 보여줄지이고, 대부분 사용자에게 상품을 보여주므로 칸마다 다른 것은 어떻게다. 이를 두 부분으로 나눈다.

| 부분 | 뜻 | 예 |
|---|---|---|
| 기준 | 무엇과 비슷한 것을 찾는가 | 사용자 취향, 방금 본 상품, 특정 브랜드 |
| 조건 | 무엇으로 거르는가 | 할인 여부, 성별, 브랜드, 카테고리, 대상 집단 |

요청은 무엇에서(기준 엔티티) 무엇을(대상 엔티티) 어떤 조건으로 몇 개 가져올지로 표현된다. 나에게 맞는 브랜드는 내 벡터와 가까운 브랜드 벡터를 찾는 일이 되고, 할인 중인 내 취향 상품은 내 벡터와 가까운 상품 중 할인 조건을 만족하는 것을 찾는 일이 된다. 기준과 조건의 조합마다 모델을 만드는 대신 조합을 요청 인자로 받는다.

통합 임베딩은 후보 생성, 랭킹 모델의 임베딩 테이블 초기값과 유사도 특징, 밴딧의 컨텍스트, 관심 사용자 집단 선정에 함께 쓰일 수 있다. 후보 생성 단계의 위치와 다른 source와의 관계는 [[Recommendation-System-Candidate-Generation|후보 생성]]을 따른다.

## 공간 만들기: 상품만 학습하고 나머지는 집계한다

- **텍스트 bi-encoder**: 질의와 상품을 같은 인코더 하나로 따로 인코딩한다. 상품은 브랜드, 카테고리, 성별, 상품명 같은 텍스트 속성을 이어 붙인 문자열로 표현하고, 가격과 할인은 텍스트에 넣지 않고 리트리벌 조건으로 건다. 한국어 사전 학습 인코더(예: KLUE RoBERTa base, hidden size 768)를 미세 조정하고 토큰 벡터를 평균 내 문장 벡터를 만든다.
- **같은 인코더를 쓰는 이유**: 검색어가 대개 상품명의 일부인 서비스라면 둘이 같은 어휘를 쓰고, 클릭이 없는 신상품도 텍스트만으로 등록 즉시 벡터를 만들 수 있으며, 검색어까지 같은 좌표계에 들어와 어떤 쌍이든 코사인 하나로 비교된다.
- **파생 엔티티는 상품 벡터의 집계다**: 브랜드와 카테고리 벡터는 거기 속한 판매 중 상품 벡터의 평균이고, 사용자 벡터는 최근 클릭한 상품 벡터의 가중 평균(최근일수록 크게, 같은 브랜드의 반복 클릭은 줄여 한 브랜드가 독차지하지 않게)이다. 연령대와 성별 세그먼트 벡터는 그 세그먼트 사용자 벡터의 평균이며 이력 없는 사용자에게 대신 쓴다. 새 엔티티도 상품 묶음으로 정의할 수 있으면 집계 방식만 더하면 되고 모델을 다시 학습하지 않는다.
- **평균의 한계**: 관심사가 여럿인 사용자를 하나로 평균 내면 관심사 사이의 어중간한 지점에 놓인다. 관심별 벡터를 두는 방식은 [[Recommendation-System-Multi-Interest-Modeling|다중 관심 사용자 표현]]에서 다룬다. 상품 구성만 비슷하고 사용자가 실제로 다르게 보는 브랜드가 가깝게 나오는 문제도 있어, 비슷한 브랜드 추천에서는 브랜드 벡터 유사도에 그 브랜드 클릭이 몰린 카테고리 분포를 두 번째 신호로 섞고 섞는 비율을 브랜드마다 정할 수 있다.

## 학습: 대조 학습과 오답 설계

검색어와 그때 클릭한 상품을 positive 쌍으로 두는 대조 학습이며, 뼈대는 InfoNCE다. InfoNCE는 positive 하나를 여러 negative 사이에서 고르도록 하는 손실로, Contrastive Predictive Coding 논문이 이 이름을 붙였다.

| 장치 | 목적 | 주의 |
|---|---|---|
| In-batch negative(여러 GPU 배치 합산) | 추가 검색 없이 오답 수를 늘린다 | accidental hit 제거는 [[Recommendation-System-Candidate-Generation#Negative Sampling은 학습 목표의 일부다\|negative sampling]] 참고 |
| BM25 hard negative, 최상위 일부는 건너뜀 | 글자가 비슷한 어려운 오답에 집중한다 | 최상위는 같은 모델의 다른 색상처럼 사실상 정답일 수 있다 |
| 사실상 정답인 상품을 오답에서 제외 | false negative를 줄인다 | 제외 범위가 넓으면 아래의 붕괴가 생긴다 |
| logQ 보정 | in-batch 오답의 인기 상품 쏠림을 줄인다 | 식은 [[Recommendation-System-Hubness-Popularity-Debiasing\|허브니스와 사용자 무관 점수 성분]] 참고 |
| 카테고리가 다른 오답의 점수 감점 | 쉽게 구분되는 오답보다 헷갈리는 같은 카테고리 상품 구분에 학습을 집중한다 | |
| 상품명으로 상품 맞추기 자기 지도 데이터 | 클릭 없는 신상품에 신호를 준다 | 클릭 있는 상품까지 강하게 넣으면 엉뚱한 상품이 섞인다 |

- **오답에서 빼면 구분할 이유가 사라진다**: 같은 브랜드나 경쟁 브랜드 상품을 오답에서 아예 빼면, 모델 입장에서는 그 상품들을 한 점에 모아도 손해가 없어 상품을 구분하지 못하는 모델이 나올 수 있다. 오답으로 남겨 두되 일정 margin 안에서만 가깝게 두는 쪽이 가깝되 구분되는 관계를 만든다.
- **배포 전 붕괴 검사**: 검증 지표(예: Recall@1)가 정상 범위보다 크게 낮으면 붕괴로 보고 배포를 멈추는 문턱을 둔다. 마지막 epoch 대신 최고점 근처 epoch 중 카테고리 구분이 선명한 모델을 고르는 방식도 쓸 수 있다.

## 차원과 좌표계

- **Matryoshka Representation Learning(MRL)**: 벡터의 앞 m개 차원(예: 768 중 앞 128) 각각이 독립적으로 쓸 수 있는 표현이 되도록 여러 prefix 길이의 손실을 함께 학습한다. 논문은 각 prefix가 같은 크기로 따로 학습한 표현과 적어도 같은 수준의 정확도를 보인다고 보고하고, 낮은 차원으로 후보를 좁히고 더 많은 차원으로 재정렬하는 adaptive retrieval을 제안한다. 저장은 전체 차원 하나로 두고 소비처가 쓸 차원을 고르면 된다. 정규화된 벡터의 내적으로 코사인을 대신하는 인덱스라면 잘라 낸 벡터를 다시 정규화한다.
- **재학습마다 좌표계가 바뀐다**: 처음부터 다시 학습한 모델은 같은 상품이라도 다른 좌표를 갖는다. 그래서 벡터를 쓰는 곳은 인덱스를 다시 만들거나, 벡터를 특징으로 쓰는 모델을 같은 버전의 임베딩으로 다시 학습해 버전을 맞춘다.
- **회전 정렬로 버전 맞춤을 없애려면 먼저 측정한다**: 직교 Procrustes는 두 행렬 A, B에 대해 `A @ R`과 B의 Frobenius 거리를 최소화하는 직교 행렬 R(회전과 반사만, 크기와 평행 이동 없음)을 찾는다. 두 공간이 회전만 다르다면 정렬 뒤 같은 상품끼리의 코사인이 1에 가까워야 한다. 독립 학습한 두 모델은 이웃 구조 자체가 달라 이 가정이 깨질 수 있으므로, 정렬 뒤 같은 엔티티 코사인과 k-NN 이웃 겹침을 재고 도입 여부를 정한다.

## 조건 리트리벌: 정확도와 지연을 같이 지킨다

- **조합별 목록 대신 조건값별 비트맵**: 조건 조합마다 상품 목록을 미리 만들어 공유 저장소에 두면, 조합 수가 브랜드 수 곱하기 카테고리 수 곱하기 집단과 성별로 폭발하고 요청마다 공유 저장소를 오가며 다른 서비스에도 부하를 준다. 조건값 하나마다 Roaring bitmap 하나를 서버 메모리에 두고 요청 때 필요한 비트맵을 AND로 겹치면 조합이 자유로워지고, 제외 조건은 ANDNOT(차집합) 한 번으로 처리된다. Roaring bitmap은 65,536개 정수 단위 chunk마다 array, bitmap, run 중 맞는 container를 골라 압축하고, 집합 연산을 dense chunk에서 비트 연산으로 수행한다.
- **조건이 있으면 ANN 대신 전수 계산을 고를 수 있다**: 질의 근처에서 이웃을 따라 탐색하는 ANN에 필터 인지 전략이 없으면, 카테고리처럼 조건을 만족하는 상품이 공간의 한구석에 몰려 있고 질의가 그 밖에 있을 때 탐색이 거기 닿기 전에 끝날 수 있다. 할인처럼 조건 상품이 흩어져 있으면 상대적으로 잘 찾는다(아래 사례). 엔진별 필터 인지 전략과 exact fallback은 링크한 문서에 있다. 칸이 보낼 조건 모양을 미리 알 수 없다면 조건부 요청은 비트맵으로 좁힌 후보를 전수 계산해 recall 100%를 지키고, 그 비용을 줄이는 쪽으로 최적화한다. 필터와 ANN 결합 방식의 일반론은 [[Vector-Similarity-Search#메타데이터 필터와 ANN|벡터 유사도 검색]]에 있다.
- **전수 계산은 할당부터 본다**: 요청마다 후보 수 곱하기 차원 크기의 배열을 새로 잡으면 메모리 할당이 점수 계산 시간의 큰 몫(아래 사례에서는 절반가량)을 차지할 수 있다. 작업 스레드마다 고정 크기 버퍼를 두고 후보를 조각으로 나눠 계산하면 할당이 사라지고 버퍼가 캐시에 머문다.
- **조건 API는 실패를 닫힌 쪽으로**: 조건을 단일 칸과 전용 필드 대신 리스트로 받아 모두 AND로 겹치고, 기존 요청 형식은 그대로 동작하게 둔다. 인덱스에 없는 조건값이 오면 조건을 조용히 빼지 않고 빈 결과를 돌려줘야 의도보다 넓은 상품이 노출되지 않는다.
- **안 쓰는 인덱스는 올리지 않는다**: 서비스에서 호출되지 않는 엔티티 인덱스가 서버 메모리 대부분을 차지할 수 있다. 엔티티별 호출 여부를 보고 적재 대상을 정한다.

## 사례: 커머스 통합 임베딩 v1에서 v2로

NAVER Engineering Day 10th에서 발표되고 NAVER D2로 공개된 KREAM의 사례다. 수치는 모두 발표 기준이며 음성 인식으로 확인한 값 중 불명확한 것은 뺐고 외부에서 재현하지 않았다.

- 학습 데이터는 최근 14일 검색 로그의 검색어와 클릭 상품 쌍이고, 검색어마다 배치 상품 256개와 hard negative 3개 사이에서 클릭 상품을 고르게 했다. BM25 hard negative는 최상위 30개를 건너뛰었다.
- v1의 조건 필터는 하루 두 번 배치로 조합별 목록을 Redis에 넣고 요청 때 목록 전체를 점수 계산했다. 할인 조건 칸을 넓은 할인 범위로 열었다가 응답 지연이 평소의 수십 배로 뛰어 롤백했고 범위를 좁혀 다시 출시했다. 조합을 모두 미리 만들려면 브랜드 약 2,000개, 중분류 약 180개에 대상 집단과 성별을 곱해 이론상 수백만 개의 키가 필요했다.
- 같은 공간으로 관심 사용자 집단을 정하자(해당 카테고리 클릭 사용자에 더해 사용자 벡터가 그룹 벡터와 가까운 사용자) 클릭 기준만 쓸 때보다 대상 사용자가 키즈 51%, 뷰티 23% 늘었다.
- v2는 경쟁 브랜드를 margin을 둔 오답으로 되돌린 변경으로 Recall@1을 0.347에서 0.411로, MRR을 0.468에서 0.531로 올렸고, 자기 지도 데이터를 클릭 없는 상품에만 넣는 변경은 신상품 예시의 이웃 유사도로 효과를 보였다. 붕괴 문턱은 학습 중 검증 Recall@1(앞의 오프라인 Recall@1과 다른 측정)이 정상이면 0.7을 넘는데 0.5 미만이면 배포를 멈추는 것이었다.
- MRL 없이 학습한 모델은 128차원으로 자르면 768차원 성능의 93.1%로 떨어졌지만 MRL로 학습한 v2의 128차원은 v1의 768차원보다 recall이 약간 높았다. 전체 카탈로그 인덱스는 2.5GB에서 421MB로 줄었다. 후보 검색과 랭킹 특징은 128차원을 쓰고, 홈 배너와 섹션 개인화는 더 큰 차원을 쓴다(값은 음성이 불명확해 뺐다).
- Procrustes 정렬 뒤 같은 상품끼리의 코사인은 1에 크게 못 미쳤고(음성 인식상 약 0.64), 독립 학습한 두 모델의 같은 상품 이웃 10개 중 약 5개만 겹쳐 정렬을 도입하지 않고 버전 맞춤을 유지했다.
- 지연의 약 1/3은 필터, 2/3는 점수 계산이었다. 카테고리와 럭셔리 같은 몰린 조건에서 ANN recall은 15~56%였고 탐색 폭을 4배로 넓혀도 80%를 넘지 못했으며, 흩어진 할인 조건은 87~99%였다. 비트맵 필터로 가장 큰 조건의 필터 시간은 3.4ms가 됐고, 스레드별 버퍼 재사용으로 요청의 85%가 몰리는 후보 3만~5만 개 구간의 점수 계산 중앙값이 62% 줄었다. 운영 대시보드 기준 중앙 지연은 70ms에서 15.7ms, 느린 1% 요청은 150ms에서 39.4ms가 됐고 서버 메모리는 1.7GiB로 줄었다.
- 다음 과제로 사용자 멀티벡터, 검색과 다른 지면으로의 확장, 브랜드나 카테고리 벡터와 가까운 사용자를 뽑는 마케팅 타겟팅을 꼽았다.

## 적용 점검

1. 칸마다 다른 요구를 기준과 조건으로 분해할 수 있는지 먼저 본다. 기준이 상품 묶음으로 정의되지 않는 엔티티는 집계로 만들 수 없다.
2. 오답에서 빼는 규칙을 더할 때마다 구분이 필요한 상품 쌍의 유사도 분포와 붕괴 문턱을 확인한다.
3. 소비처별로 필요한 차원과 임베딩 버전을 기록하고, 재학습 뒤 인덱스와 하위 모델의 버전 맞춤을 배포 절차에 넣는다.
4. 조건별 선택도와 공간 분포(몰림과 흩어짐)에 따라 같은 조건을 건 exact 결과 대비 ANN recall을 재고 전수 계산 여부를 정한다.
5. 알 수 없는 조건값, 빈 비트맵과 조건 조합의 동작을 계약으로 정하고 시험한다.
