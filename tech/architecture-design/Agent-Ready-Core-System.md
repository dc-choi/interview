# 에이전트가 일하기 좋은 코어 시스템 구조

에이전트 도입의 병목이 모델이 아니라 에이전트가 붙어야 할 시스템 구조인 경우가 많다. 완성된 자율주행차도 표준 규격 없이 좁고 막다른 길이 얽힌 구도심 골목에서는 제 성능을 내지 못하듯, 업무가 한 덩어리로 얽힌 기간계에는 에이전트가 필요한 기능만 골라 부를 연결점이 없다. 에이전트 친화 코어 시스템은 업무 단위 기능을 표준 인터페이스로 노출하고, 한 기능의 변경과 장애가 다른 업무로 번지지 않게 나누며, 에이전트의 모든 호출을 인증, 권한, 추적이 있는 관문으로 지나게 하는 구조다.

이 문서는 보험 코어 시스템 사례(2026년 9월 공급사 발표)를 바탕으로 구조와 트레이드오프를 정리한다. ERP 전환에서 같은 질문을 다룬 문서는 [[AI-Ready-ERP-Transformation|AI 활용 기반으로서의 ERP 전환]], 에이전트가 쓰기 좋은 인터페이스 설계는 [[Agent-Ready-API-Design|에이전트 친화 API 설계]]에 있다.

## 기존 기간계에 에이전트를 붙이기 어려운 이유

1. **얽힌 업무 구조:** 업무가 하나의 덩어리로 묶여 있어 에이전트가 특정 기능만 호출하거나 연계하기 어렵다.
2. **표준 인터페이스 부재:** Open API나 MCP 같은 표준 연결점이 없어 연동할 때마다 개별 개발이 필요하다.
3. **변경의 위험:** 한 곳을 바꾸면 전체에 영향이 가므로 부작용(side effect) 우려로 확장과 개선이 늦어진다.

에이전트는 고정 부품이 아니다. 심사, 신용평가, 상품 설계, 고객 상담 에이전트를 더 나은 것으로 바꾸고 업무 변화에 따라 더할 수 있어야 하므로, 코어는 특정 에이전트가 아니라 교체될 수 있는 여러 호출자를 전제로 설계한다.

## 업무 단위 서비스와 표준 관문

업무 프로세스 단위(청약과 심사, 계약 관리, 지급 등)로 서비스를 나누고 서비스마다 원장(업무 데이터의 정본)을 따로 둔다. 기대 효과는 세 가지다(공급사 주장, 아래 트레이드오프와 함께 읽는다).

- **필요한 기능만 호출:** 서비스마다 표준 인터페이스(Open API, MCP)를 두어 에이전트가 필요한 기능만 골라 부른다.
- **자유로운 조립:** 서비스 단위로 통합, 분리, 선별 적용을 할 수 있어 연계 지점을 유연하게 구성한다.
- **장애 격리:** API 게이트웨이의 서킷 브레이커, 라우팅, 추적으로 한 서비스의 문제가 전체로 번지는 것을 막는다.

호출 경로는 에이전트 요청, 표준 API나 MCP 호출(게이트웨이에서 인증과 권한, 라우팅, 추적), 해당 서비스의 원장 처리, 결과와 근거 반환 순이다. 모든 에이전트 호출이 게이트웨이를 지나므로 권한 통제와 추적이 한곳에 모인다. 개발 위키, 그래프 DB, 벡터 DB 같은 지식과 데이터 원천은 에이전트가 판단 근거를 찾는 곳으로 따로 둔다.

| 업무 에이전트 예 | 하는 일 |
|---|---|
| 언더라이팅 | 계약 심사 자동 판정 |
| 지급 심사 | 청구 서류와 규칙 검토 |
| 상품 | 계산식 초안 생성 |
| 조회 응대 | 계약과 지급 조회 응대 |
| 이상 거래 | 사기와 오류 지급 탐지 |

단위 에이전트(Unit Agent)는 하나의 도구, 데이터베이스, 모델처럼 명확한 하위 기능이나 단일 책임을 맡는 최소 단위 에이전트이고, 다중 에이전트(Multi Agent)는 단위 에이전트를 자율형이나 워크플로 기반으로 조합한 것이다(공급사 정의).

### 트레이드오프 (설계 판단)

- **서비스별 원장의 비용:** 서비스 사이의 일관성을 분산 트랜잭션 대신 사가와 보상, 아웃박스로 맞춰야 하고, 여러 원장에 걸친 조회를 합치는 비용이 생긴다([[Microservice-Data-Ownership-and-Queries|마이크로서비스 데이터 소유권과 조회]], [[Saga-Pattern|사가 패턴]], [[CDC&Outbox|CDC와 아웃박스]]).
- **배포 분리는 목적이 아니다:** 에이전트가 필요한 기능만 부르게 하는 것이 목적이라면 배포를 나누지 않고 모듈 경계와 공개 API를 강제하는 모듈러 모놀리스로도 같은 연결점을 줄 수 있다. 장애 격리와 독립 배포가 실제로 필요한지가 분리 여부를 가른다([[Modular-Monolith|모듈러 모놀리스]], [[Monolith-vs-Microservice|Monolith vs Microservice]]).
- **도구는 업무 동작 단위로:** 내부 API를 그대로 노출하기보다 지급 심사 요청처럼 업무 동작 단위로 묶어 열고, 쓰기 동작에는 승인 모드와 감사 기록을 둔다([[Agent-Governance-Controls|에이전트 거버넌스 통제]], [[MCP-Gateway-Architecture|MCP 게이트웨이]]).
- **결과와 함께 근거를:** 적용한 규칙, 읽은 원장의 버전 같은 근거를 결과와 함께 돌려주면 사람의 검토와 감사가 쉬워진다.

## 표준 프로세스와 확장점

에이전트가 기대어 일하려면 호출 단위와 그 부작용이 예측 가능해야 한다. 업무마다 따로 만든 흐름을 표준 단계로 모으고, 업무별 차이는 정해 둔 확장점에서만 바꾸게 하는 것이 그 방법이다.

- **지급 공통 프로세스:** 업무(일반지급, 사고지급, 보험계약대출)마다 따로 만든 지급 흐름(접수, 계약 반영, 지급 요청, 지급 취소)은 중복 개발과 불일치, 상품과 제도 요건을 반영할 때의 긴 분석과 개발 기간, 테스트 비용 증가를 낳았다. 표준 단계는 접수(계약과 금액 조회, 계약 잠금, 접수 생성), 계약 반영(계약 원장 반영, 약관대출 상계 반영, 잠금 해제), 지급 요청(급부금 배분, 지급 생성, 입출금 전기)으로 묶고 단계마다 표준 구현과 사용자 정의 지점, 설정을 둔다. 지급 취소는 계약 반영 취소, 약관대출 상계 취소, 접수와 지급 취소의 역방향 단계로 둔다. 자동 송금, 단체, 심사, 조사 같은 업무별 기능은 표준 위에 확장한다.
- **전표 기반 입출금:** 업무마다 다르던 입출금을 전표 기반 거래로 통합하면 처리가 납입 방법(실시간 이체, 카드, 가상계좌)에 의존하지 않아 납입 방법을 더할 때 빨리 반영하고, 같은 고객의 업무별 입출금을 합산해 처리하며, 회계 연계의 원천 정보가 하나가 돼 정합성을 지키기 쉽다.
- **계약 원장의 버전:** 업무별 이력을 통합하고 원장에 버전(V1, V2, V3)을 붙여 기준 시점을 조정(되돌리기, 다시 하기, 현재, 시뮬레이션)하고, 보험료 청구나 갱신 같은 업무 이벤트를 일정으로 관리한다. 이력 모델링의 일반형은 [[SCD-Type2|SCD Type 2]]와 [[Event-Sourcing|이벤트 소싱]]을 본다.
- **유연한 상품 모델:** 판매상품, 보험 패키지, 세부보험의 기본 구조에 계약자, 피보험자, 보험료, 가입금액, 할인과 할증, 펀드, 위험률 같은 항목 엔티티를 연결 제약 없이 붙여, 할인이 여럿인 건강보험과 피보험자가 여럿인 가족보험을 같은 모델로 표현한다. 상품 구조를 계약에 그대로 비추는(mirroring) 구조로 계약 정보를 만들어 업무 로직을 단순하게 한다.

확장점이 있으면 새 요건이 그 지점 안에서만 바뀌어 영향 범위가 좁아지고, 에이전트가 부르는 표준 단계의 동작이 안정된다. 반대로 확장점과 설정이 많아질수록 조합이 늘어 시험해야 할 경우가 커지므로, 확장 조합을 회귀 범위에 넣는다(해석).

## 검증 기반: 바꿔도 깨지지 않았다는 증거

에이전트가 코어를 바꾸거나 코어에 쓰기 호출을 늘릴수록 자동 회귀가 변경 승인의 전제가 된다(해석).

- **상품 출시 전 단계별 검증:** 가입 설계를 시나리오로 검증하고, 계산식 결과를 상품 인가용 산출 자료의 참값과 자동 비교하며, 대체 상품 코드로 입금, 지급, 출금 같은 선후행 업무를 함께 시험한다. 출시 뒤에도 계산식이나 상품 정보가 바뀌면 사전 저장한 참값과 비교한다.
- **운영 거래 재현 회귀:** 특정 시점의 원장을 백업하고 그 뒤의 거래 로그를 검증 환경에서 다시 돌려 운영 결과와 비교한다. 절차와 함정은 [[Regression-Test-Automation#운영 거래 기록을 재현해 회귀 기준을 만든다|회귀 테스트 자동화]]에 있다.

## 도입 방식

| 방식 | 내용 | 맞는 경우 |
|---|---|---|
| 참조 모델 기반 | To-Be 요구사항으로 설계하고 개발하되 솔루션의 모델, 코드, 문서를 참고한다 | 고객사 고유 프로세스의 강점을 지키고 싶을 때 |
| 패키지 기반 | Fit & Gap 분석 뒤 커스터마이징해 솔루션을 그대로 쓴다 | 업무 전반을 바꾸며 패키지의 장점을 쓰고 싶을 때 |

두 방식을 섞거나 필요한 모듈만 고를 수도 있다(예: 상품 모듈과 회귀 검증부터). 패키지 커스터마이징이 늘수록 업그레이드 부담이 커지는 문제는 [[AI-Ready-ERP-Transformation#시스템: Clean Core와 핵심 업무 시스템 연계|Clean Core의 표준 우선, 코어 밖 확장, 통제된 예외]]와 같은 원칙으로 다룬다.

## 점검 질문

- 에이전트가 부를 업무 기능이 독립된 인터페이스로 노출돼 있는가, 화면이나 DB를 거쳐야만 하는가
- 모든 에이전트 호출이 인증, 권한, 추적이 있는 관문을 지나고, 관문을 거치지 않는 경로는 막혀 있는가
- 원장을 나눌 때 서비스 사이 일관성(보상, 아웃박스)과 조회 합성 비용을 설계했는가, 배포 분리 없이 모듈 경계만으로 충분한지 따져 봤는가
- 표준 프로세스의 확장점과 설정이 문서화돼 있고 확장 조합이 회귀 범위에 들어 있는가
- 에이전트를 바꾸거나 더해도 코어를 고치지 않고 연결되는가
- 변경 뒤 운영 거래를 재현해 원장과 계산 결과를 비교할 수 있는가

## 사례 (2026년 9월 발표 기준, 공급사 발표)

- **보험 코어 솔루션:** 상품 개발, 마케팅과 판매, 언더라이팅, 계약 관리, 클레임, 고객 서비스로 이어지는 보험사 밸류체인을 소스 코드, 모델, 산출물로 제공하는 솔루션을 구축 기간과 비용, 상품 출시 속도, 에이전트 연계, 안정적 운영의 네 질문에 답하는 구조로 소개했다. 구축 기간은 참조 모델 기반이 2~3개월(약 10%), 패키지 기반이 3~8개월(약 20%) 줄어든다고 밝혔지만 기준이 된 사업 규모와 비교 대상은 공개되지 않았다. 제품 기능 목록은 옮기지 않았다.
- **AI 네이티브 보험 플랫폼 구성도:** 사용자 채널, 에이전틱 서비스, 단위와 다중 에이전트, 에이전트 플랫폼(빌더, 지식과 도구, 마켓플레이스, 에이전트 운영), MSA 코어, AI 활용 데이터(레이크하우스, 시맨틱 계층, 저장소), 거버넌스(데이터, 보안과 컴플라이언스, AI 윤리), 운영(DevOps)의 층으로 나눴다.
