# 제조 AI의 데이터 아키텍처: IT/OT 통합, 엣지 배치와 디지털 트윈

## 정의

제조 AI의 데이터 아키텍처는 공장 설비와 업무 시스템에 흩어진 데이터를 AI가 판단에 쓸 수 있는 맥락으로 바꾸고, 그 판단을 데이터가 생기는 현장 가까이에서 실행하게 하는 구조다. 파일럿에서 성과를 낸 AI가 전사로 퍼지지 못하는 원인을 모델 성능보다 데이터 연결, 작업 방식과 거버넌스에서 찾는 것이 출발점이다(2026년 9월 Dell Technologies 발표의 관점).

## 확산을 막는 다섯 병목

발표 자료가 든 원인이다. 함께 적힌 비율(84%, 82%, 95%)은 그 쪽에 출처 표기가 없어 옮기지 않았다.

1. **데이터 사일로와 IT-OT 단절:** IT(ERP, SCM)와 OT(MES, SCADA, 센서) 데이터가 물리적으로도 의미상으로도 끊겨 AI가 조각난 정보만 본다.
2. **작업을 다시 설계하지 않음:** 기존 업무에 AI 도구만 덧붙이고 의사결정 단계와 사람의 개입 시점을 바꾸지 않는다.
3. **불명확한 ROI와 거버넌스:** 정량 가치를 재는 체계가 없어 파일럿에 머물고, 데이터 접근 권한과 보안 체계가 없어 전사 확산 승인을 받지 못한다.
4. **데이터 준비:** 고유 데이터를 가진 것과 그 데이터를 AI 학습과 검색에 쓸 수 있게 정제한 것 사이의 격차, 특히 비정형 데이터의 정제가 가장 큰 진입장벽이다.
5. **기술 밖의 요인:** 에이전트라는 이름만 붙인 제품(agent washing)에 따른 신뢰 하락, 클라우드와 추론 단계의 예상하지 못한 비용 증가, AI와 도메인을 함께 아는 인력 부족.

ERP 쪽의 같은 문제는 [[AI-Ready-ERP-Transformation#네 병목과 끊기는 단계|ERP 전환의 네 병목]]이 다룬다.

## AI를 데이터 가까이 둔다

제조 데이터는 대부분 현장에서 생기고 현장에서 쓰인다. 지연, 데이터 양과 반출 제약 때문에 실시간 판단은 현장에서 하고, 무거운 학습과 장기 저장은 데이터센터로 올린다.

| 계층 | 맡는 일 |
|---|---|
| 공장 엣지 | 현장 실시간 추론 |
| 공장 운영 플랫폼 | 운영 데이터의 수집과 오케스트레이션 |
| 데이터센터 | 대규모 학습, 저장과 모델 런타임 |
| 클라우드(필요할 때) | 확장, 협업, 일시적 용량 확보(burst) |

데이터는 수집, 오케스트레이션, 저장, 모델 런타임, 자동화 순으로 흐르고 보안과 거버넌스는 모든 계층을 관통한다. 발표 자료는 이 위에서 데이터 통합, 가상 환경의 검증(디지털 트윈), 에이전트의 판단과 실행, 피지컬 AI를 통한 실세계 자동화로 가는 순서를 제시한다. 앞 단계의 데이터가 없으면 뒤 단계가 서지 않는다는 순서다(해석). 설비 데이터 파이프라인에서의 배치는 [[IoT-Edge-Cloud-Pipeline#장비, 게이트웨이와 클라우드에 추론을 나눠 배치한다|장비, 게이트웨이와 클라우드의 추론 배치]]와 [[Outposts-Workload-Boundaries#시스템 전체보다 지연에 민감한 경로를 나눈다|지연 민감 경로의 분리]]를 따른다.

### 엣지 플랫폼에 요구되는 것

발표 자료가 든 여섯 요건이다. 각 요건의 대가는 이 문서의 해석이다.

- **IT/OT 융합:** 기존 OT는 그대로 두고 현장 추론 계층을 더해 데이터 흐름을 다시 설계한다. 대가로 추론 계층이 OT 망에 새 경로를 만든다.
- **단일 아키텍처:** 라인 하나의 PoC에서 여러 공장까지 같은 구조로 늘린다. 대가로 첫 PoC부터 표준화 비용이 든다.
- **산업 연결성:** PLC, 로봇, 카메라와 센서의 여러 OT 프로토콜을 한 통합 지점에서 받는다. 대가로 통합 지점이 단일 장애점이 된다.
- **레거시 현대화:** 기존 애플리케이션과 데이터를 다시 작성하지 않고 재호스팅해 투자를 보존한다. 대가로 구조 개선은 미뤄진다.
- **워크로드 통합:** 공장 PC, CAD, MES, VDI를 하나의 엣지 플랫폼에 모아 운영 부담을 줄인다. 대가로 장애와 침해의 영향 범위가 커진다.
- **산업 사이버보안:** OT 환경에 제로 트러스트를 적용한다. 경계 분리만으로 막지 못하는 범위는 [[Network-Separation#무엇을 막고 무엇을 못 막는가|망분리가 막는 것과 못 막는 것]]을 따른다.

## 디지털 트윈의 데이터 요건은 둘이다

| 접근 | 대상 | 쓰임 | 필요한 데이터 |
|---|---|---|---|
| 하향식(top-down) | 공장, 공급망, 제품 라인 전체를 하나의 거시 모델로 | 공정 시뮬레이션, what-if 시나리오, 공급망과 물류, 전사 최적화 | 넓고 얕게. 여러 시스템의 데이터를 모아 한 그림으로 본다 |
| 상향식(bottom-up) | 펌프, 모터, 로봇, CNC 같은 자산 한 대를 정밀하게 | 실시간 자산 모니터링, 예지 정비, 수율 최적화, 부품 단위 분석 | 좁고 깊게. 자산 한 대의 모든 신호를 끝까지 판다 |

두 접근은 데이터 계약이 다르다. 하향식은 시스템 사이의 식별자 매핑과 시각 정렬이, 상향식은 고빈도 신호와 고장 이력의 연결이 먼저 필요하다(해석). 설비 신호에 의미와 관계를 붙이는 방법은 [[IoT-Edge-Cloud-Pipeline#원시 수집과 설비 맥락 연결을 분리한다|원시 수집과 설비 맥락 연결]]을 따른다.

## 데이터 플랫폼의 요건

발표 자료가 든 여섯 요건이다.

- **엣지-코어-클라우드 연속성:** 데이터 중력, 지연과 주권 요구에 맞춰 위치를 고른다.
- **IT-OT 데이터 통합:** 흩어진 시스템의 데이터에 공통 맥락을 붙인다.
- **스토리지와 컴퓨트 분리:** 워크로드마다 따로 늘리고 비용을 맞춘다.
- **여러 엔진:** 실시간 처리, 검색과 RAG, 분석을 같은 데이터 위에서 돌린다.
- **개방형 표준 포맷:** 벤더 종속을 피하고 데이터를 재사용한다([[Data-Lake-Table-Formats|데이터 레이크 테이블 포맷]]).
- **사이버 복원력과 거버넌스:** 보안을 파이프라인 안에 넣는다.

### 파이프라인에서 맥락까지

발표 자료가 제품 명세가 아닌 예시라고 밝힌 논리 구조를 일반화하면 다음과 같다.

1. **원천:** 실시간 데이터, 이력 데이터, 로그와 텔레메트리, 문서, 이미지와 영상과 음성.
2. **수집과 정규화:** 받아들이고 검증하고 정제하고 중복을 없애고 표준화하고 보강한다.
3. **처리:** 변환, 조인과 집계(데이터 엔지니어링), 품질과 업무 규칙을 적용한 신뢰 데이터 관리(큐레이션), 검색할 수 있는 맥락으로의 구조화(컨텍스트 엔지니어링).
4. **제공:** 큐레이션된 데이터셋과 특징(데이터 제품), 키워드 검색, 벡터 검색, 그래프 검색.
5. **맥락:** 에이전트와 LLM에 넘기는 맥락을 여섯 종류로 나눈다.

| 맥락 | 설비 질문의 예 |
|---|---|
| 사실 | 설비 온도 신호 |
| 키워드 | CNC, 스핀들, 라인, 진동 |
| 의미 | 최근 상태 추세가 감지됨 |
| 관계 | 센서가 어느 설비와 생산 라인에 연결됐는가 |
| 시간 | 정상 운전, 이상, 정지로 이어진 순서 |
| 기억 | 정비 이력과 운전 맥락 |

한 종류의 검색으로 여섯 맥락을 다 얻지 못한다. 키워드와 벡터 검색은 문서와 로그를, 그래프 검색은 설비와 라인의 관계를, 시계열 저장소는 시간 순서를 맡는다(해석). 검색 방식의 조합은 [[RAG-Retrieval-Engineering|RAG 검색 엔지니어링]]과 [[GraphRAG-Retrieval|GraphRAG 검색]], 에이전트가 쓸 데이터의 계약은 [[Agent-Ready-Data|에이전트용 데이터 준비]]를 따른다.

발표 자료는 기업 AI를 데이터 평면(신뢰할 수 있는 맥락을 준비하고 관리)과 실행 평면(검증된 모델을 대규모로 저지연 추론)의 두 축으로 나눈다. 실행 평면의 효율은 [[LLM-Inference-Fleet-Efficiency|LLM 추론 플릿 효율]]이 다룬다.

### 데이터 준비 단계

1. **발견:** 어떤 데이터를 어떤 업무 목적에 쓸지 정한다.
2. **준비:** 정제, 라벨링과 익명화로 AI가 쓸 수 있는 형식을 만든다.
3. **통합:** 흩어진 데이터를 파이프라인으로 묶어 재사용할 수 있는 데이터 제품으로 만든다.
4. **결합:** 정제한 자사 데이터를 LLM과 결합해 차별화된 사용 사례를 만든다.

운영 단계에서는 품질, 성능, 사용과 가치를 감시하고, 거버넌스, 위험과 규정 준수를 관리하며, 방어, 탐지와 복구를 강화한다. 데이터 제품의 계층 구분은 [[AI-Ready-ERP-Transformation#데이터: 기준정보와 Data Product|기준정보와 Data Product]]와 같은 방향이다.

## 희귀 결함은 합성 데이터로 보완한다

품질 검사 AI에는 희귀 결함 이미지가 필요하지만 실제 라인에서 모으려면 오래 걸린다. 정상품 이미지에 결함을 렌더링하고 픽셀 단위 라벨을 자동으로 만들면 결함이 생기기를 기다리지 않고 학습할 수 있다.

- **보고된 사례:** Roboflow와 NVIDIA는 Corning의 광섬유 공정 벤치마크에서 실제 결함 이미지 8장과 합성 이미지로 학습한 모델이 mAP 0.95와 가장 어려운 결함 클래스의 재현율 100%에 이르러 실제 데이터만 쓴 기준선을 넘었다고 발표했다(2026-05-31 Roboflow, 2026-06-30 NVIDIA 블로그). 기준선의 수치와 평가 조건은 공개되지 않았다. NVIDIA는 같은 글에서 DeepHow의 SOP 검증 에이전트가 Foxconn의 GB300 서버 라인에서 초도 수율을 3% 높였다고 적는데, 발표 자료도 지적하듯 SOP 검증 솔루션 전체의 성과라 합성 데이터의 기여는 분리되지 않는다.
- **실데이터를 대체하지 않는다:** Nature에 실린 연구(2024-07-24)는 생성 모델(LLM, VAE, GMM)의 다음 세대를 앞 세대 모델이 만든 데이터로 무분별하게 학습시키면 원래 분포의 꼬리부터 사라지는 모델 붕괴가 일어난다고 보이고, 원본 데이터에 대한 접근을 유지해야 한다고 적는다. 결함 렌더링으로 검출 모델을 학습시키는 일은 세대를 거듭하는 생성 모델의 재귀 학습과 대상도 조건도 다르지만, 희귀 결함이 바로 분포의 꼬리라는 점에서 같은 경고를 참고한다(해석). 발표 자료가 인용한 포토리소그래피 패턴의 SEM 결함 탐지 연구(2025년 5월 표기)는 합성 SEM 데이터로 학습한 YOLOv8이 합성 평가 세트에서 mAP 96%, 실데이터 테스트에서 Bridge 84.6%와 Break 78.3% 검출이었다고 적는다(발표 자료 인용, 원 논문 미대조). 채택 여부는 실제 결함 이미지로 만든 평가 세트에서 정한다([[Synthetic-Vision-Data-Evaluation|합성 비전 데이터와 인식 모델 평가]]).

## 사례: Dell이 발표한 고객 수치

2026년 9월 발표 기준이며 측정 기간, 기준선과 조건은 공개되지 않았다.

- **InstaDeep:** 강화학습 기반 에이전트가 PCB 배치와 배선을 자동화해 설계 시간을 10분의 1로 줄이고, 모델 훈련 속도를 40% 높이고, 인프라 운영 비용을 30% 줄였다고 밝혔다.
- **Sandisk:** 무인(lights-out) 운영 비율이 80%에서 95%로 오르고, 100만 개당 불량 부품이 800개에서 100개로(87.5% 감소) 줄었으며, 에너지 사용량 46%, CO2 배출량 45%, 원자재 폐기 16%, 공장 운영 비용 32%가 줄었다고 밝혔다.
