# AI 구현 위임과 코드 리뷰

## 구현보다 먼저 정할 계약

구현을 위임해도 목표, 보존할 동작, 허용할 절충과 완료 기준은 필요하다. 자연어가 모호하면 인터페이스, 함수 시그니처와 입출력 예시로 의도를 전달한다. 코드는 구현물인 동시에 의사소통 수단이다.

## 리뷰의 목적

- **적합성:** 동작하는 결과와 요구한 결과가 같은지 확인한다.
- **경계:** 모듈 책임, 보안 조건과 성능 예산을 확인한다.
- **이해:** 운영과 후속 변경을 판단할 만큼 시스템을 이해한다.
- **영향:** 인증, 공유 라이브러리처럼 파급 범위가 큰 변경을 집중 검토한다.

리뷰는 결함 탐지와 지식 전달을 함께 수행한다. 에이전트가 작성했다는 사실은 배포 책임을 이전하지 않는다.

## 관례와 피드백

프레임워크의 기존 구조를 재사용하면 생성할 코드와 검토할 범위를 줄일 수 있다. 자연어 관례와 실행 단계의 강제는 다르다. 프레임워크를 쓴다고 업무 요구나 보안이 자동 보장되지는 않는다.

테스트는 반복 수정의 피드백을, 로그와 트레이스는 운영 동작의 근거를 제공한다. 운영 관측도 배포 전 검증을 대신하지 않는다. 도구 추천은 현재 문서와 팀의 제약에 대조하고, 익숙한 라이브러리라는 이유만으로 채택하지 않는다.

## 기본기를 리뷰 질문으로 바꾼다

CS 개념의 이름을 아는 것과 변경의 결과를 설명하는 것은 다르다. AI가 초안을 만들었더라도 다음 질문으로 사람이 확인할 범위를 정한다. 이는 Google의 코드 리뷰 지침을 AI 구현 위임에 적용한 점검 제안이며, 특정 채용의 합격 기준이나 학습 효과를 측정한 결과는 아니다.

- **설계:** 변경이 기존 시스템과 어떻게 연결되며, 책임을 이 모듈에 둔 이유는 무엇인가?
- **동시성:** 두 실행이 겹칠 때 공유 상태가 어떻게 바뀌며, 경쟁 상태나 교착이 생길 순서는 없는가? 실행 한 번의 성공만으로 안전성을 판정하지 않는다.
- **테스트:** 요구한 동작이 깨졌을 때 테스트도 실패하는가? 생성된 테스트의 통과 여부와 별개로 입력, 기대 결과와 assertion을 검토한다.
- **이해와 범위:** 담당한 코드를 설명할 수 있는가? 이해되지 않는 부분은 설명을 요청하고, 보안이나 동시성처럼 전문성이 부족한 부분에는 적합한 검토자를 포함한다. 일부만 검토했다면 그 범위를 남긴다.

학습에 적용할 때는 작은 변경 하나를 골라 동작과 실패 조건을 먼저 설명하고, 테스트나 실행 추적으로 설명을 확인한다. 모르는 부분을 구체적인 질문으로 바꾸는 연습이며, 설명을 잘했다는 사실만으로 운영 안전성을 보장하지 않는다.

2026-10-24 Google의 설계, 동시성, 테스트와 검토 범위 지침을 대조했다. 기존 경험 기반 전망을 재검증한 것은 아니다.

## 도구 사용 표기와 제출 품질은 별도로 확인한다

AI를 썼다는 표시만으로 코드의 정확성이나 작성자의 이해를 확인할 수는 없다. 반대로 도구 사용을 허용한다는 말이 출처 공개, 테스트와 프로젝트의 제출 절차를 생략해도 된다는 뜻은 아니다.

Linux 커널의 도구 생성 콘텐츠 지침은 제출물 전체를 이해하고 리뷰에 답할 준비를 요구한다. 사용한 도구, 영향을 받은 부분과 테스트 방법을 설명하고, 짧은 프롬프트나 긴 세션의 요약도 투명성을 높일 정보로 제시한다. 설명하지 못하는 변경은 제출하지 않으며, 유지관리자는 상세 리뷰 없이 거절할 수 있다. 이는 해당 프로젝트의 제출 기준이지 모든 프로젝트의 동일한 의무는 아니다.

AI 버그 수정 지침은 사소하지 않은 결함의 재현 시도, 수정 후 빌드와 재현 또는 전체 분석을 통한 확인, 수행하지 못한 검사 공개를 요구한다. 이를 일반적인 리뷰 요청에 적용할 때는 다음을 남긴다(운영 제안).

- 조사한 코드의 기준 커밋과 문제가 발생하는 조건
- 수정 전 실패와 수정 후 결과를 비교할 재현 방법
- 실제 수행한 검사, 결과와 수행하지 못한 검사
- 작성자가 설명할 수 있는 수정 이유와 영향 범위

2026-10-24에 확인한 공식 AI 지침에는 `Assisted-by` 절이 남아 있었다. 태그 폐지 제안이나 도구 금지에 대한 발언을 현재 문서의 변경 완료로 해석하지 않는다. 실제 제출 시점에는 대상 트리와 유지관리자의 최신 지침을 다시 확인한다. 이 확인은 관련 패치의 병합 여부나 영상에서 언급한 개별 버그 수를 검증한 기록이 아니다.

## 형식 검증도 명세의 적합성까지 대신하지 않는다

검증기가 구현과 명세의 일치를 확인해도, 그 명세가 사용자의 요구를 충분히 표현했는지는 별도 문제다. AI가 코드와 증명을 함께 만들었다는 설명만으로 검토를 끝내지 않는다.

Dafny 4 튜토리얼의 절댓값 예제에서 후조건이 `0 <= y`뿐이면 어떤 입력에도 `0`을 반환하는 구현이 그 조건을 만족한다. 절댓값을 요구하려면 입력이 음수인지에 따른 결과 관계도 명세에 담아야 한다. 전조건은 호출자가 충족해야 하며, 구현은 그 전제 아래 후조건을 만족해야 한다.

이를 AI 코드 리뷰에 적용하면 다음을 따로 확인한다(점검 제안).

- 요구한 성질이 명세에 빠짐없이 표현됐는가?
- 실제 호출부가 명세의 전조건을 만족하는가?
- 검증에 성공한 범위와 검증하지 않은 외부 연동, 운영 조건이 구분돼 있는가?

2026-10-26 공식 튜토리얼의 명세와 전후조건 설명을 대조했다. 일반 LLM이 임의의 프로그램에 올바른 증명을 자동 생성한다는 성능 주장이나 향후 인증 제도를 확인한 것은 아니다. 예제는 문서로 확인했으며 Dafny를 직접 실행하지 않았다.

## 학습과 전망의 경계

직접 구현하고 실패를 고치는 연습은 판단력을 기르는 수단이다. 문법의 폭뿐 아니라 메모리, 동시성, 네트워크와 트랜잭션의 작동 모델을 익힌다. 멘토링에서는 정답 전달과 사고 과정의 전수를 구분한다.

2026-10-09의 경험 기반 전망에는 수작업 코딩, TDD의 수동 절차와 페어 입력의 축소, DRY와 SOLID의 적용 비중 변화, 랜딩 페이지 제작업의 위축이 포함된다. 이는 검증된 보편 결론이 아니다. 테스트 폐기, 설계 원칙 무용론이나 특정 사업의 종료 결정으로 확대하지 않는다.
