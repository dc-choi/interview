# AI 시민 개발 — 도메인 전문가가 직접 만드는 내부 도구

시민 개발(Citizen Development)은 현업 담당자(비개발자)가 자기 업무의 도구를 직접 만드는 패턴이다. 로우코드 시절에는 플랫폼이 허용하는 범위에 갇혔지만, AI 코딩 에이전트가 구현을 대신하면서 실제 서비스 수준(웹 앱, 외부 API 연동, 인증)까지 범위가 확장됐다. 핵심 명제: **AI가 구현 비용을 무너뜨리면 희소 자원은 코딩이 아니라 도메인 지식이 되고, 문제를 가장 잘 아는 사람이 도구를 쥐는 것이 최적이 된다.**

## 내부 도구의 전통적 딜레마

- 사내 불편(흩어진 시트, 반복 질문, 수동 예약)은 **보이지 않는 소통 비용**으로 쌓이지만, 개별 건의 ROI가 작아 보여 개발팀 백로그에 진입하지 못한다
- 결과적으로 현업 담당자가 게이트키퍼가 된다 — 정보 요청이 모두 한 사람을 거치고, 그 사람의 시간이 반복 응대로 소진된다
- 개발자가 만들자니 도메인 파악 비용이 크고, 현업이 만들자니 구현 능력이 없었다 — AI가 이 두 번째 벽을 제거

## 도메인 전문가의 우위

구현이 싸지면 남는 병목은 문제 정의다. 현업 담당자는 개발자가 갖기 어려운 세 가지를 이미 안다.

| 우위 | 내용 |
|---|---|
| 불편의 우선순위 | 어떤 반복 질문이 가장 잦은지, 무엇부터 풀어야 체감이 큰지 |
| 데이터의 실체 | 어느 시트에 어떤 필드가 있고 무엇이 최신인지 (파편화의 지도) |
| 조직 수용성 | 어느 팀의 협조가 필요하고 누가 이해관계자인지 |

## AI의 역할 — 초안 기계가 아니라 동료

비개발자 주도 구축에서 AI가 실제로 담당하는 것은 코드 생성만이 아니다.

- **기술 초안** — 코드, 문서, 구조 설계
- **판단 근거 제공** — 보안 트레이드오프(아래 사례)처럼 선택지의 위험을 설명해, 비개발자가 보안팀과 같은 언어로 대화할 수 있게 함
- **이해관계자 식별** — 어떤 팀에 무엇을 요청해야 하는지 함께 정리
- **계획 우선 진행** — 구현 전에 Plan Mode로 전략을 합의하고 시작 ([[Claude-Code-Fundamentals|Claude Code 기초]])

## 기술 판단은 생략되지 않는다 — 두 사례

비개발자가 만들어도 아키텍처와 보안 판단은 그대로 등장한다. AI가 근거를 제공하고 사람이 선택한다.

### 사내망 봇의 인바운드 노출 문제

- 문제: 슬랙 슬래시 커맨드는 공개 Request URL을 요구하는데, 시스템은 사내망 전용 — 외부 노출은 보안 범위를 키움
- 해결: **Slack Socket Mode** — 봇이 슬랙으로 아웃바운드 WebSocket을 먼저 열어, 공개 엔드포인트 없이 커맨드를 수신 ([[WebSocket|WebSocket]]의 아웃바운드 연결 패턴)

### 대표 계정 하나로 전 직원 예약 생성 문제

- 문제: 초기 구현이 관리자 계정 하나로 모든 회의실 예약을 생성 → 모든 예약의 주최자가 담당자로 기록, 전사 알림이 한 계정에 집중, 도메인 전체 위임은 키 하나로 전 직원 캘린더에 접근하는 마스터키 리스크
- 해결: **사용자별 OAuth + 최소 스코프**(calendar.events만), 토큰은 세션별 암호화 보관, 퇴사 시 권한 자동 정리 ([[OAuth2|OAuth 2.0]]의 위임 범위 설계)

## 만든 결과를 검토할 수 있는 형태로 받기

비개발자가 결과를 1차로 검토하려면 코드만 받지 않고 검토 경로를 함께 산출물로 요구한다.

- **리뷰 순서와 설명 주석**: 비개발자가 읽을 수 있는 주석과, 제품 범위 문서에서 화면, 데이터, 돈(주문과 결제), 파일, 운영 순으로 내려가는 리뷰 순서 문서를 만들게 한다. 단계마다 열어 볼 파일과 확인 질문을 적게 한다.
- **파일 역할 지도**: 어떤 파일이 화면, 서버 API, 테이블과 업무 규칙을 맡는지 받는다. Next.js App Router라면 `app` 아래 폴더 구조가 URL 경로를 정하고 `page.tsx`는 그 주소의 화면, `route.ts`는 서버 API다([[NextJS-App-Structure|App Router 폴더와 파일]], [[NextJS-App-Route-Handlers|Route Handler]]). 문구 하나를 바꿔 화면이 따라 바뀌는지 보면 대응 관계를 직접 확인할 수 있다.
- **데모와 실제 연동의 구분**: 외부 서비스 키 없이 만든 결과는 상품 목록이 코드에 넣은 임시 데이터이거나 결제와 다운로드가 데모 경로로 흉내만 내는 상태일 수 있다. 화면이 동작한다는 사실을 연동 완료로 읽지 않도록 무엇이 데모인지 리뷰 문서에 표시하게 한다. 주석과 문서는 의도의 설명이지 동작의 증거가 아니므로 결과는 실행으로 확인한다.
- **오류 전달**: 리뷰 몇 단계에서 어떤 버튼을 눌렀는지, 화면의 오류 메시지와 입력 상태(예: 구매 동의 체크 여부)를 함께 넘겨 원인 분석을 맡긴다. 설정값이 비어 있는 경우의 처리를 빠뜨린 것 같은 원인도 이런 재현 조건이 있어야 좁혀진다.

## 조직 수용 전략 — 강제 대신 취지

내부 도구는 채택이 절반이다. 데이터 통일(예: 프로필 사진)이 필요할 때 변경을 강요하면 반발이 생기고, 일관된 정보 제공이라는 취지와 가이드라인(AI 생성 프로필 제안 등)을 전달하면 자발적 참여가 따라온다. 구성원 각자가 참아온 불편을 공동의 문제로 재정의하는 것이 확산의 동력.

## 효과의 구조

- 조회 작업이 담당자 경유에서 **셀프서비스**로 전환 — 게이트키퍼 병목 제거
- 담당자의 반복 응대 시간이 판단이 필요한 업무로 재배치
- 파편화된 데이터(여러 시트)가 단일 진입점으로 통합

## 한계와 전제

- **운영 책임** — 만든 뒤의 유지보수, 장애 대응 주체가 필요하다. 개발자의 코드 리뷰와 피드백을 받는 협업 구조가 안전판
- **보안 거버넌스** — 사내 데이터에 접근하는 도구이므로 보안팀을 초기부터 참여시켜야 한다. 비개발자일수록 최소 권한, 노출 면적 판단을 AI 근거와 함께 검증받을 것
- **노출 범위** — 다룰 난이도는 기능 수보다 누가 쓰는가와 어디서 접속하는가로 커진다. 사용자 범위가 넓어질 때의 사용성, 보안과 규모 문제([[AI-Solo-Software-Business#개인용에서 보편적 소프트웨어로|개인용에서 보편적 소프트웨어로]])와 별개로, 나만 쓰는 도구도 휴대폰 같은 다른 기기에서 쓰려고 인터넷에 배포하면 누구나 닿는 주소와 연동 키가 생겨 인증과 키 관리가 필요해진다. 사내 전용이면 위 Socket Mode 사례처럼 인바운드 노출 자체를 줄이는 선택지를 먼저 본다
- 개발자 대체 서사가 아니라 [[AX-Transformation|AX 조직 전환]]의 산출자에서 판단자로의 역할 이동이 비개발 직군까지 확장된 형태 — 문제 정의자가 주도하고 AI가 산출한다

## 면접 체크포인트

- AI가 구현 비용을 낮추면 병목이 어디로 이동하는가 (문제 정의, 도메인 지식)
- 내부 도구가 개발 백로그에 못 들어가는 구조적 이유와 시민 개발이 그 틈을 메우는 방식
- 비개발자 주도 구축에서도 등장하는 기술 판단 사례 (인바운드 노출 회피, 최소 권한 위임)
- 내부 도구 확산에서 강제와 취지 공유의 차이
- 시민 개발의 운영 책임, 보안 거버넌스 전제
- 비개발자가 AI 결과물을 검토할 수 있게 받을 산출물 (리뷰 순서, 파일 역할 지도, 데모와 실제 연동 구분)

## 사례

아임웹 GA(총무) 담당자가 Claude와 함께 좌석 배치도, 회의실 현황과 예약, 슬랙 커맨드 조회, 인사 데이터 통합 대시보드를 구축. 첫 GitHub PR을 올린 비개발자가 Socket Mode 채택과 개별 OAuth 전환 같은 기술 판단을 AI의 근거 설명과 함께 통과시켰고, 개발자들의 리뷰를 받으며 운영 중.

## 사례: 치과 업무의 로컬 AI 자동화

제공된 2026-10-15 GeekNews 발췌는 생물학 전공 치과 원장이 네트워크 구축에서 시작해 로컬 모델과 코딩 에이전트로 업무를 자동화한 경험을 전한다. UniFi 네트워크, DGX Spark급 장비 12대를 4대씩 묶은 모델 실행, Mac mini의 음성과 검색 및 서류 판독, 통화와 환자 서류의 병원 내부 처리가 제시된다.

이 사례에서 재사용할 질문은 업무 데이터를 어디서 처리하는지, 모델 결과를 누가 검토하는지, 사람이 최종 승인할 변경은 무엇인지다. 로컬 실행은 개인정보 보호를 설계할 선택지지만 그 자체가 유출 방지나 법규 준수의 증거는 아니다. 외부 API 호출, 백업, 원격 접속과 로그까지 대조해야 한다.

사례가 제시하는 통제 구조는 자동 처리와 사람 판단의 경계를 나누는 방식으로 재사용할 수 있다.

- **자동 확정과 검토 대상의 분리**: 보험사 서류 904개, 3,389쪽을 판독해 지급 금액과 거절 사유를 내부 기록과 대사하고, 지급 내역 항목(줄)의 약 77%를 자동 확정했으며 직원은 확인 필요로 분류된 나머지만 검토했다고 한다. 이런 구조에서 볼 지표는 판독 정확도와 함께 줄어든 검토량과 자동 확정분의 오류율이다. 자동 확정 기준이 틀리면 검토 대상에서 빠진 오류가 그대로 확정되므로 자동 확정분은 표본 감사로 확인하고, 판독 신뢰도와 업무상 검토 조건은 따로 설계한다([[LLM-Workflow-Patterns-Data-and-Operations#사람 검토로 넘기는 조건을 분리한다|사람 검토로 넘기는 조건]]).
- **사람 채점 화면**: 통화 요약과 분류(목적, 긴급도, 할 일)를 사람이 채점하는 화면을 따로 만들었다. 영상 해설은 두 모델의 판정이 엇갈린 통화부터 보고, 어느 모델의 답인지 가린 채 비교하는 방식도 소개한다. 불일치를 먼저 보면 한정된 검토 시간을 오류 가능성이 높은 건에 쓰고, 모델을 가리면 특정 모델에 대한 선입견이 채점에 섞이는 것을 줄인다. 다만 두 모델이 같은 오답으로 일치한 경우는 불일치 목록에 나오지 않으므로 일치한 통화도 무작위 표본으로 채점하고, 나란히 비교할 때는 제시 순서도 섞는다([[Eval-LLM-Judge|LLM 판정 평가]]).
- **역할별 에이전트와 직접 승인**: 코딩 에이전트를 포털, 전화 시스템, 음성 서버, 인프라 담당으로 나눠 서로 오류를 확인하게 하고, 운영 설정 변경은 원장이 직접 승인하며 다른 에이전트가 전달한 승인은 인정하지 않는다. 이 규칙을 일반화하면, 승인 근거는 승인권자에게서 왔음을 검증할 수 있고 해당 변경과 시점에 묶여야 한다. 다른 에이전트가 전한 승인 주장(전언)은 실행 주체가 그 출처를 검증할 수 없어 이를 보장하지 못한다. 이 확인은 에이전트의 판단에 맡기지 않고 도구 권한과 실행 경로에서 집행한다([[LLM-Workflow-Patterns-Chain-vs-Agent#콘텐츠 초안과 승인 대기열|승인 대기열]]).
- **사람이 맡는 경계**: 진료 기록 작성은 사람이 하고 운영 설정 변경은 사람이 승인하며, 세금 신고처럼 도장(서명 책임)이 필요한 일은 사람 전문가에게 맡긴다. GeekNews 발췌는 AI가 진료 기록을 읽고 정리하고 제안하는 데까지만 맡고 최종 판단은 사람이 한다고 밝히고 영상 해설도 AI는 읽고 제안까지만 한다고 요약하지만, 위 대사의 자동 확정은 이 경계 밖에서 기계가 내리는 결정이므로 별도 감사 대상이다.

## 사례: 광역 지자체 공무원이 만든 행정 업무 도구

2026-10-27 공공 AI 전환 사례 공유 생방송(제목에 행정안전부와 한국지능정보사회진흥원 병기)에서 광역 지자체 AI 전담 부서 담당자(이하 발표자)가 자신과 부서 직원이 AI로 만든 업무 도구를 소개했다. 발표자는 기존 절차를 그대로 둔 효율화와 일하는 방식 자체를 바꾸는 재설계를 구분해 업무 방식을 먼저 바꾸고 AI를 적용해야 한다고 봤고, 발표 중 질의응답에서는 AI를 잘하는 사람보다 행정 경험이 많은 사람이 AI에 많이 던져 보고 시도할 때 더 좋은 결과물이 나올 수 있다는 의견도 나왔다. 아래 기능, 비용, 운영 상태와 보안 판단은 발표 기준이며 운영 성과나 보안 심사를 검증한 기록이 아니다.

- **기존 시스템에 붙인 보조 도구**: 발표자는 출장 기간, 출장지, 교통비와 숙박비 영수증, 제공받은 식사를 넣으면 여비를 계산해 정산서 PDF를 만드는 도구와, 그 PDF를 읽어 지방재정관리시스템(e호조+, 발표에서는 e호조)의 지출 입력 화면에 제목, 출장 기간과 출장지를 채우는 도우미를 만들었다. 세부사업과 거래처처럼 판단이 필요한 항목, 예산과 계좌 확인, 승인 요청은 지출을 입력하는 직원의 몫으로 남겼다. 형식이 정해진 자체 정산서여야 안정적으로 읽히고, 웹 화면 요소를 찾아 값을 넣는 방식이라 반복 수정을 거쳐야 하는 부분이 있었다고 한다.
- **저장하지 않는 구조**: 여비 도구의 보안 검토 대응을 묻자 발표자는 정보가 저장되지 않고 DB도 없어 다행히 보안 문제에서 조금 자유로웠다고 답하면서도, 체계화되면 더 깊이 검토해야 한다고 했다. 저장하지 않아도 처리 중 데이터의 전송 경로와 업무 시스템에 입력하는 권한은 따로 확인할 대상이다.
- **비개발 직원을 테스트베드로**: 전산직이 대부분이던 부서에서 부서장은 유일한 행정직 직원을 테스트베드라고 불렀다. 부서가 만든 도구를 매뉴얼만 받은 그 직원이 혼자 쓸 수 있으면 조직 누구라도 쓸 수 있다는 뜻이었다. 그 직원도 AI 챔피언 교육을 받은 뒤, e호조에서 내려받은 예산서와 집행 현황 엑셀 세 개를 올리면 사업별 예산, 집행액과 집행률을 보여 주는 HTML 대시보드를 AI로 만들었다.
- **개인정보를 받을 서버가 필요한 지점의 용역**: 발표자가 직접 맡았던 협상에 의한 계약 업무를 바탕으로 만든 업무지원 시스템은 평가위원 신청 PDF를 엑셀 명부로 옮겨 적던 일을 온라인 접수로 바꾸고, 참여 횟수를 넘긴 위원 선별, 위원 추첨, 카카오톡 알림으로 받는 참석 응답, 평가 점수 집계와 수당, 원천징수 계산을 묶었다. 발표자는 아이디어를 Claude에 전달할 뿐 실제 개발은 Claude가 한다고 했다. 전자 접수로 개인정보를 처리하려면 서버가 필요해 용역을 맡겼고, 개인정보와 보안 때문에 AI에만 의존할 수는 없다고 했다. 직접 만든 소스 코드를 넘긴 용역에 약 1천만 원이 들었고 업체는 처음부터 개발하면 약 3,500만 원이 든다고 답한 것으로 기억했으며, 업체에 끌려가지 않고 사업을 주도할 수 있다는 점은 그래도 장점일 수 있다고 봤다. 발표 시점에는 다음 달 부서의 실제 계약에서 처음 운영할 예정이었다.
- **담당자가 바뀌어도 이어지게**: 부서는 개인의 성과에 기대던 단계에서 직무진단(예산, 세무, 법규, 총무, 민원)과 파일명 규칙, 라벨링 같은 데이터 기초 작업으로 조직의 업무 방식을 다루는 단계로 넘어가려 한다고 했다. 발표자는 아직 개인 유료 구독을 쓰고 퇴근 뒤 자기 개발처럼 만든 때가 많았다고 했으며, 진행을 맡은 한국지능정보사회진흥원 측은 올해 블랙 교육생에게 토큰 비용을 지원했고 사용료 지원 등을 준비하고 실행하고 있다고 했다.
- **예산, 인력, 보안의 제약**: 다른 기관 참여자는 범정부 공통기반에서 전 직원에게 제공하는 채팅 기능이 첨부 용량 제한이 작고 맥락을 오래 유지하지 못한다고 평가했고, 보안부서 협의와 내부망 반입 검토를 거치려 하며 기관 계정으로 쓰는 외부 생성형 AI에도 공개 자료만 넣는다고 했다. 다른 대담 참여자는 공통기반의 컨셉과 구성은 잘 되어 있지만 장비와 예산 제약이 많아 상용 서비스에 준하기는 어렵다고 봤다(두 평가 모두 발언 시점 기준). 진행 측은 외부 전문가가 조직 안에서 제 역할을 못 하거나 오래 남지 못하자 행정안전부가 자기 업무를 AI로 푸는 내부 인력을 키우기로 했다고 설명했고, 방송 중 대화에서는 외부 전문가가 업무 절차와 도메인에 익숙하지 않은 점이 이유로 거론됐다.

협상에 의한 계약은 계약 이행에 전문성, 기술성, 창의성 등이 필요한 물품, 용역 계약에서 여러 공급자의 제안서를 평가하고 협상해 해당 지방자치단체에 가장 유리하다고 인정되는 자와 계약하는 방식이며, 제안서 평가는 국가와 다른 지방자치단체 공무원, 계약에 관한 학식과 경험이 풍부한 사람 등으로 구성한 제안서평가위원회의 심의를 거친다(지방계약법 시행령 제43조 제1항, 제9항부터 제11항, 2026-06-03 시행본). AI 챔피언은 행정안전부가 마련한 AI 역량교육 과정을 이수하고 실무 인재 인증을 받은 공무원을 가리킨다. 2026-05-07 행정안전부 보도자료는 블루(중급)와 최고 등급인 블랙(고급)을 언급하고, 같은 방송에서 진행 측은 그린(초급), 블루, 블랙의 3단계 등급이 있다고 설명했다.

이 사례에서 위의 도메인 전문가의 우위는 반복 업무의 선택과 데이터의 실체(어느 시스템에서 어떤 파일을 내려받고 어느 칸에 사람 판단이 남는지)에서 나왔고, 매뉴얼만으로 혼자 쓸 수 있으면 누구나 쓸 수 있다며 비개발 직원을 테스트베드로 부른 발상은 결과를 실행으로 확인하는 원칙을 사용성으로 넓힌 형태다. 기술 판단도 생략되지 않아 전자 접수로 외부 신청자의 개인정보를 받으려면 서버가 필요한지가 직접 만든 도구로 끝낼 범위와 용역으로 넘길 범위를 갈랐고, 화면 구조에 기대는 자동 입력과 개인 구독, 개인 시간에 기댄 제작은 담당자가 바뀌면 유지가 끊길 수 있어 위 한계와 전제의 운영 책임 주체가 필요하다.
