# 코딩 에이전트와 스펙 주도 개발

스펙 주도 개발(SDD)은 무엇을 왜 만들지를 Markdown 스펙으로 먼저 합의하고 구현은 코딩 에이전트에게 맡기는 방식이다. 스펙은 구현 방법(how)과 분리한 무엇과 왜(what, why)의 계약이며, 사람끼리의 합의이자 사람과 에이전트 사이의 합의다. SDD의 일반 정의와 문서 계층은 [[RFC-Writing#Spec-Driven Development (SDD)|RFC / PRD 작성의 SDD 절]], 결정 기록을 남기는 팀 규칙은 [[Spec-Decision-Records|에이전트 작업의 스펙과 결정 기록]]이 정본이다. 이 문서는 에이전트와 프로젝트를 진행하는 반복 구조, 곧 프로젝트 헌법, 기능 루프와 재계획을 다룬다.

구조는 코딩 에이전트용 SDD 단기 강좌의 흐름을 일반화했고, 도구 절은 공식 저장소와 문서로 대조했다. 효과에 관한 설명은 측정값 없이 제시된 주장이다.

## 스펙을 먼저 쓰는 이유

- **증폭:** 스펙의 한 문장(예: 저장소는 SQLite와 특정 ORM)이 수백 줄의 코드를 정한다. 스펙을 고치는 편이 코드를 고치는 것보다 싸고, 반대로 스펙의 작은 오류도 그만큼 커진다.
- **세션을 넘는 맥락:** 세션이 바뀌면 대화 속 결정이 사라지고, 긴 세션은 컨텍스트가 차면서 실수가 는다([[Context-Engineering#Context Rot|Context Rot]]). 저장소에 둔 스펙은 세션과 에이전트가 바뀌어도 시작 시점에 같은 핵심 맥락을 준다.
- **의도 충실도:** 문제, 성공 기준, 제약과 사용자 흐름을 코드 생성 전에 정하게 해 에이전트가 빈칸을 임의로 채우는 범위를 줄인다. 여러 개발자가 각자 에이전트로 빠르게 만들면서 서로 어긋난 방향으로 가는 문제도 공유 스펙이 줄인다.
- **상세도:** 목표, 대상 사용자와 제약은 자세히, 에이전트가 스스로 정할 수 있는 낮은 수준의 결정(변수 이름, CSS 클래스)은 적게 쓴다. 자연어 요구 뒤에 숨은 결정을 꺼내는 질문은 [[Agent-Spec-Writing#숨은 결정 드러내기 — 결정 축 인터뷰|결정 축 인터뷰]]를 본다.

## 프로젝트 헌법

프로젝트 수준의 불변 기준을 세 문서로 둔다. 헌법(constitution)은 이런 프로젝트 수준 결정을 형식화하는 한 방법이다.

| 문서 | 담는 것 |
|---|---|
| 미션 | 왜 만드는가. 비전, 대상 사용자, 범위 |
| 기술 스택 | 개발과 배포 기술, 팀이 쓰는 언어와 프레임워크, 제약 |
| 로드맵 | 작은 단계로 나눈 기능 phase의 순서. 계속 고치는 살아 있는 문서 |

- **지침 파일과의 관계:** 강좌는 헌법을 AGENTS.md보다 구조화된, 특정 에이전트와 무관한 기록으로 구분한다. AGENTS.md도 여러 에이전트가 읽는 공용 형식이므로 차이는 형식보다 역할로 보는 편이 정확하다. 지침 파일은 세션마다 읽는 작업 규칙이고([[Agent-Repository-Instructions|AGENTS.md 작성과 운영]]), 헌법은 이해관계자도 읽는 제품과 기술 결정의 합의다(이 문서의 해석).
- **대화로 쓴다:** 에이전트가 질문하게 하면 고려하지 않은 아키텍처 패턴, 이미 있는 패키지, 속도와 데이터 정확도 같은 트레이드오프가 드러난다. 초안에서 빠진 것(예: 대상 사용자)은 직접 고치기보다 에이전트에게 고치게 해 관련 문서가 함께 맞춰지게 한다. 로드맵은 사람이 검토할 수 있는 작은 단계로 나누라고 지시한다.
- **기존 코드베이스는 역으로 만든다:** 브라운필드에서는 에이전트가 코드, 커밋, README와 할 일 목록이나 이슈 트래커를 읽고 미션, 사용 중인 스택과 버전, 로드맵을 추출하게 한 뒤 사람이 검토하고 커밋한다. 그다음부터는 새 프로젝트와 같은 루프를 돈다.

## 기능 루프: 계획, 구현, 검증

로드맵의 기능 하나를 브랜치 하나에서 끝낸다.

1. **새 컨텍스트와 브랜치에서 시작한다.** 이전 대화의 기억 대신 헌법을 공식 맥락으로 읽게 한다.
2. **스펙을 인터뷰로 만든다.** 에이전트가 범위, 요구사항과 검증 방법을 묻고 사람이 고른다. 결과는 세 파일이다.
   - plan: 접근 방식과 작업 그룹의 순서
   - requirements: 중요한 기술 요구와 제약. 변수 이름 같은 세부는 넣지 않는다
   - validation: 에이전트와 사람이 결과를 확인할 방법
3. **스펙을 검토하고 커밋한 뒤 구현한다.** 고칠 점은 에이전트에게 맡겨 세 파일이 서로 맞게 유지되게 한다. 구현은 컨텍스트를 비우고 시작하며, 작업 그룹을 한 번에 구현하거나 보안과 데이터베이스처럼 작은 실수가 쌓이는 영역은 그룹 하나씩 구현하고 커밋한다.
4. **사람은 높은 수준에서 검증한다.** 기능이 동작하고 스펙을 반영하는지를 보고 변수 이름 같은 세부는 지적하지 않는다. 코드의 잘못이 계획의 잘못에서 왔다면 에이전트에게 스펙과 코드를 함께 고치게 한다. 리뷰에서 스펙에 없던 결정을 발견한 것은 실패가 아니라 스펙을 보강할 정보다.
5. **손으로 고친 뒤에도 스펙을 맞춘다.** IDE에서 파일을 옮기는 것처럼 사람이 직접 고치면 스펙과 README가 코드와 어긋나는 drift가 생긴다. 직접 고친 뒤에는 에이전트에게 관련 언급을 찾아 맞추게 한다.
6. **두 번째 확인을 둔다.** 테스트를 읽고 디버거로 따라가며 변경을 이해하고, 서브에이전트 여럿에게 프로젝트 전체를 다시 검토하게 한다. 서브에이전트는 별도 컨텍스트에서 일하므로 주 에이전트의 컨텍스트를 덜 쓴다. 리뷰를 맡기는 범위와 발견의 검증은 [[Independent-Agent-Code-Review|독립 에이전트 리뷰]]를 본다.
7. 변경 기록을 갱신하고 커밋한 뒤 병합한다.

예시: 첫 기능이 홈 화면 하나인 최소 서버라면 requirements에 프레임워크 버전 고정과 엄격한 타입 검사를, validation에 수동 HTTP 요청으로 응답을 확인하는 절차를 둔다. 리뷰에서 머리글, 본문과 바닥글을 나눈 레이아웃 컴포넌트가 필요하다고 판단하면, 코드만 고치지 않고 plan에 작업 그룹을 더하게 해 스펙과 구현을 함께 바꾼다.

## 재계획: 기능 사이에 멈춘다

기능 하나를 끝낼 때마다 다음 기능으로 바로 가지 않고 헌법, 로드맵과 작업 방식을 다시 본다. 개발자의 일이 구현보다 계획과 검증에 몰리므로 이 시간을 따로 잡는다.

- **헌법 변경은 별도 브랜치에서 한다.** 어느 헌법 버전이 어느 코드를 만들었는지 추적하려는 것이다. 로드맵에 완료 표시만 하는 작은 변경은 기능 브랜치에 함께 둘 수 있다. 스펙과 코드 변경을 어떻게 짝지어 버전 관리할지는 아직 정해진 관례가 없다.
- **헌법을 바꾸면 기존 스펙과 코드도 맞춘다.** 예를 들어 테스트 프레임워크를 기술 스택에 넣으면 기존 기능 스펙과 구현도 갱신하게 한다. 설정만 바뀌고 테스트는 쓰이지 않을 수 있으므로 결과를 확인한다.
- **제품 변경의 크기로 자리를 정한다.** 작은 변경은 재계획 중에 바로 반영하고, 큰 변경은 로드맵의 새 phase로 올린다. 서로 묶이는 로드맵 항목은 합친다.
- **작업 방식도 고친다.** 반복하는 프롬프트와 절차는 skill로 만든다(예: 병합 때 변경 기록 갱신, 검증 단계의 린트, 포맷과 테스트 실행). 그 skill을 이 프로젝트에만 둘지 모든 프로젝트에 둘지도 정한다.
- **도중에 떠오른 조사는 따로 남긴다.** 기능 작업 중 데이터베이스 선택 같은 생각이 들면 브랜치 작업을 멈추지 않고 정해진 위치에 조사 보고서를 쓰게 한다. 나중에 로드맵 항목에서 그 보고서를 링크해 일정으로 올린다.

## 검토 피로를 줄이는 시작 점검

에이전트가 빠르게 많은 변경을 만들면 사람의 검증이 병목이 되고 피로가 쌓인다. 변경을 작게 나누고 자주 커밋하며, 기능을 시작할 때 다음을 확인한다.

- 끝내지 못한 작업이 없고 지난 기능 브랜치를 병합했는가
- 로드맵의 다음 항목이 여전히 맞는가
- 에이전트의 컨텍스트를 비워, 기억이 아니라 스펙이 의도를 전달하게 했는가

코드가 무엇을 하고 어떻게 바뀌어 왔는지 따라가는 부담을 강좌는 cognitive debt라고 부른다. 이 용어의 다른 쓰임과 은유의 한계는 [[Technical-Debt#오용 ② — AI 시대, 모든 게 부채가 됐다|기술 부채]]를 본다.

## 스펙을 시험하는 큰 구현

남은 로드맵 전체를 한 번에 구현하게 하는 것은 헌법과 스펙의 품질을 시험하는 극단적인 실험이다. 스펙을 충분히 믿고 결과를 검토할 여력이 있을 때만 한다. 결과가 의도와 다르면 에이전트를 빗나가게 한 원인을 재계획에서 고친다. 코드를 검증하기 전에 에이전트에게 결과를 스펙과 대조하게 하면 계획의 빈틈이 드러나기도 한다.

## 도구로 구현한 SDD

2026-11-18 공식 저장소와 문서 기준이다. 둘 다 MIT 라이선스이고 명령과 파일 구조가 자주 바뀌므로 도입 전에 다시 확인한다.

| 도구 | 흐름 | 산출물과 특징 |
|---|---|---|
| Spec Kit (GitHub) | 프로젝트마다 한 번 `constitution`, 기능마다 `specify`, `plan`, `tasks`, `implement`, `converge`. `clarify`, `checklist`, `analyze`는 선택 품질 게이트다 | `spec.md`, `plan.md`, `tasks.md`. `converge`는 구현을 산출물과 대조해 남은 일을 `tasks.md`에 덧붙이기만 하고 코드는 고치지 않으며, `Converged`가 나올 때까지 `implement`와 번갈아 돈다. Python 3.11 이상과 uv가 필요하다 |
| OpenSpec (Fission AI) | 필요하면 `explore`로 탐색하고 `propose`, `apply-change`, `archive-change` 순으로 진행한다 | 변경마다 `openspec/changes/<이름>/`에 proposal, 요구사항과 시나리오를 담은 스펙, design, tasks를 만든다. archive는 변경을 보관 폴더로 옮기고 기준 스펙을 갱신한다. 2.0부터 skill로 배포하며 1.x는 `/opsx:*` 명령이었다 |

- **호출 표기:** Spec Kit 문서는 `/speckit.specify` 같은 점 표기를 쓰지만 GitHub Copilot의 기본 skill 모드에서는 `/speckit-specify`, Codex에서는 `$speckit-specify`로 부른다. OpenSpec도 대부분의 도구에서 `/openspec-propose`, Codex에서 `$openspec-propose`다.
- **루프와의 대응:** 강좌는 OpenSpec의 propose와 explore를 계획에, apply를 구현에, archive를 재계획에 대응시킨다. Spec Kit에서는 constitution이 헌법, specify부터 tasks까지가 기능 계획, implement와 converge가 구현과 대조에 해당한다(이 문서의 해석).
- **비교 주장:** OpenSpec README는 Spec Kit을 꼼꼼하지만 무겁다(엄격한 단계 게이트, 많은 Markdown, Python 설치)고 비교한다. 경쟁 도구의 자기 비교이므로 자기 저장소의 같은 기능으로 시험한 뒤 고른다.
- **같은 계열:** 역할별 에이전트를 둔 [[BMad-Method|BMad Method]], 팀 의식과 승인 게이트를 둔 [[AI-DLC|AI-DLC]], 요구사항, 설계와 작업 목록을 나누는 Kiro의 흐름([[Agent-Spec-Writing#스펙 산출물과 승인 지점을 분리한다|스펙 산출물과 승인 지점]])도 같은 문제를 푼다. 기성 도구를 고르더라도 위의 기능 루프와 재계획을 skill로 감싸 팀 방식에 맞출 수 있다.

## 에이전트를 바꿔도 남는 워크플로우

스펙은 Markdown이라 특정 에이전트나 IDE에 묶이지 않는다. 모델과 에이전트의 순위가 빠르게 바뀌므로, 워크플로우는 표준을 따르는 부분에 두면 에이전트를 바꿀 때도 옮길 수 있다.

- **작업 규칙:** AGENTS.md
- **반복 절차:** Agent Skills. 같은 skill을 다른 에이전트의 skill 경로로 복사해 쓸 수 있다. 에이전트는 설명을 보고 skill을 고르는데 컨텍스트가 커질수록 판단이 흔들리므로, 꼭 써야 하면 프롬프트에서 이름을 부른다([[Agent-Skills#동작 — 점진적 공개(Progressive Disclosure)|점진적 공개]]).
- **외부 도구:** MCP, 또는 CLI를 부르는 skill. 두 표면의 컨텍스트 비용 차이는 [[Agent-Email-Interface|이메일 에이전트 인터페이스]]의 비교를 본다.
- **편집기 연결:** ACP([[Agent-Client-Protocol|Agent Client Protocol]], IDE 쪽 registry는 [[JetBrains-IDE-Agent-Integration|JetBrains IDE의 에이전트 통합]])
- **플러그인:** 아직 에이전트 사이의 표준이 아니고 코드를 실행할 수 있으므로 설치와 갱신 때 출처를 확인한다([[Agent-Skills#설치 경로와 신뢰 — 표면마다 따로, 출처는 먼저|설치 경로와 신뢰]]).

## 트레이드오프

- **장점:** 결정이 저장소에 남아 세션, 에이전트와 사람이 바뀌어도 이어진다. 스펙 변경으로 큰 코드 변경을 통제하고, 사람의 리뷰를 작은 단위로 나눈다.
- **비용:** 스펙 작성은 제품, 기능과 아키텍처를 실제로 결정하는 일이라 시간이 든다. 한 프롬프트로 끝나는 작은 일에는 과하다. 스펙과 코드가 어긋나면 낡은 스펙이 다음 작업을 오도하므로 동기화를 계속 유지해야 한다.
- **한계:** 스펙 파일이 생겼다고 사람이 검토한 것은 아니고, 스펙대로 구현했다는 에이전트의 보고가 동작을 증명하지도 않는다. 테스트와 실행 결과는 따로 확인한다. 기성 도구는 메이저 버전마다 명령과 구조가 바뀌었다(OpenSpec 1.x에서 2.0).

## 적용 체크포인트

- 미션, 기술 스택과 로드맵이 저장소에 있고 지침 파일과 역할이 겹치지 않는가
- 기능마다 브랜치와 새 컨텍스트에서 계획, 요구사항과 검증 방법을 먼저 커밋했는가
- 리뷰에서 바꾼 결정이 스펙에도 반영됐고, 손으로 고친 뒤 스펙과 문서를 맞췄는가
- 헌법 변경을 별도 브랜치로 남겨 어느 버전이 어느 코드를 만들었는지 추적할 수 있는가
- 기능 사이에 재계획 시간을 두고, 반복 절차를 skill로 옮기고 있는가
