# 하네스 엔지니어링 (Harness Engineering)

## 정의

OpenAI가 2026년 2월 블로그 Harness engineering: leveraging Codex in an agent-first world에서 제시한 개념(공식 원문 재확인 2026-08-27). **AI 에이전트가 코드를 올바르게 작성할 수 있는 환경을 설계하는 것.**

OpenAI 사례의 핵심은 에이전트 자체보다 에이전트가 읽을 수 있는 환경, 의도, 도구와 피드백 루프를 설계하는 데 있다. 아래 단계와 5대 원칙은 공식 글의 고정 분류가 아니라 이 vault에서 실무 적용을 위해 재구성한 점검 프레임이다.

## AI 활용의 진화: 프롬프트 → 컨텍스트 → 하네스 → 루프

AI 활용 역량은 단계로 깊어진다.

| 단계 | 설계 대상 | 한계 |
|---|---|---|
| 프롬프트 엔지니어링 | 좋은 질문과 지시 | 1회성, 개인 스킬 의존 |
| 컨텍스트 엔지니어링 | AI가 읽을 배경지식과 자료 | 여전히 단일 에이전트의 단일 호흡 |
| 하네스 엔지니어링 | 환경, 도구, 검증과 피드백 루프 | 설계 비용과 운영 복잡도 |
| 루프 엔지니어링 | 정지 조건까지 스스로 도는 실행 루프(관찰→행동→검증→재시도)와 트리거로 일감을 발견하는 바깥 루프 | 루프 종료, 비용, 무한 반복 통제 |

어원(말의 고삐와 마구)대로, 하네스는 강한 모델을 그냥 풀어놓는 게 아니라 목적과 품질 기준 안에서 움직이도록 묶는 설계다. 한 번의 지시만 다듬는 데서 환경, 도구, 검증과 피드백 루프를 설계하는 쪽으로 범위를 넓히며, 핵심은 자동화가 아니라 통제된 자동화다. → [[Context-Engineering]]

[[Agent-Loop-Engineering|루프 엔지니어링]]은 그다음 단계로, 하네스가 짜둔 구조 안에서 에이전트가 한 번에 끝내는 게 아니라 스스로 돌며 회복하게 만들고, 나아가 스케줄과 이벤트로 일감을 스스로 발견하는 바깥 루프까지 하네스를 확장하는 데 초점을 둔다. 한 번에 맞히게 만들기보다 틀려도 루프 안에서 다시 맞히게 설계하며, 이는 [[LLM-Eval-Strategy|Pass@k]] 사고, [[Production-Agent-Architecture|Closure-loop]]와 같은 결이다.

## 이 vault의 5대 점검 축

| 원칙 | 설명 | 핵심 질문 |
|---|---|---|
| **Constrain** | 에이전트 행동을 제한 | 뭘 하면 안 되는가? |
| **Inform** | 무엇을 해야 하는지 알려줌 | 뭘 알아야 하는가? |
| **Verify** | 작업 결과를 검증 | 제대로 했는가? |
| **Correct** | 실수를 교정 | 틀렸으면 어떻게 고치는가? |
| **Human-in-the-loop** | 고위험 결정에 인간 개입 | 사람이 확인해야 하는가? |

## 하네스 인프라 구성 요소

| 요소 | 역할 | 예시 |
|---|---|---|
| **프로젝트 맥락 문서** | 프로젝트 전체 구조, ERD, 명령어, 코딩 스타일 제공 | AGENTS.md, CLAUDE.md |
| **도메인별 규칙** | 영역마다 아키텍처 패턴, 금지 사항, 코딩 규칙 명시 | Rules 파일 (API, Web, DB 등) |
| **워크플로우 자동화** | 반복 작업을 구조화된 단계로 자동화 | Skills (SDD, 테스트, 커밋 등) |
| **전문 에이전트** | 역할 기반 검증 (보안, 디자인, 성능, 비즈니스) | Custom Agents |
| **지속 기억** | 대화 간 피드백, 결정, 맥락 보존 | 승인된 결정 기록과 Memory 메커니즘 |
| **비즈니스 맥락** | "왜 이걸 만드는지"를 에이전트에 전달 | Business docs |
| **개발 프로세스** | 문서→구현→검증의 구조화된 흐름 | SDD 7단계 |

## 5대 점검 축별 실천 방법

### 1. Constrain (제약) — 에이전트가 하면 안 되는 것을 명시

- 도메인별 Rules 파일로 아키텍처 패턴과 금지 사항 분리
- 예: "데이터 접근은 Use Case 경계를 거친다", "민감 정보는 생성물과 로그에 남기지 않는다"
- 200줄 분할 규칙과 약 190줄의 선제 점검으로 문서 비대화 방지
- 커밋 컨벤션, 브랜치 네이밍, 코딩 스타일 규정

### 2. Inform (맥락) — 에이전트가 알아야 할 것을 구조화

- AGENTS.md, CLAUDE.md: 도구별 프로젝트 개요, 명령어와 코딩 스타일
- Rules: 디렉토리 구조, 주요 패턴, 주의사항
- Business docs: 가치 제안, 수익 모델, GTM, 사용자 피드백
- SDD의 PRD/기능 설계: "왜 만드는가", "어떻게 동작하는가"

### 3. Verify (검증) — 에이전트 작업을 자동으로 검증

- SDD 5단계에 테스트 포함 (구현 후 자동 lint/typecheck/build/test)
- 서브에이전트(security-reviewer, design-reviewer, performance-analyzer)가 PR 전 자동 리뷰
- CI/CD 파이프라인으로 PR 시 자동 검증 게이트

### 4. Correct (교정) — 같은 실수를 반복하지 않도록

- Memory 시스템의 feedback 타입으로 사용자 피드백 저장
- 에이전트가 다음 대화에서 이전 피드백을 참조
- 이상적: 자동 롤백, diff 리뷰 메커니즘

### 5. Human-in-the-loop — 고위험 결정에 인간이 개입

- 브레인스토밍 → 사용자 결정 없이 로드맵에 반영하지 않음
- SDD 전환 시 체크리스트로 인간 확인
- PR 리뷰 → 머지 결정은 사용자

## 멀티 에이전트 오케스트레이션

멀티 에이전트는 하네스의 필수 조건이 아니라, 서로 독립적인 하위 작업과 별도 검증 역할이 있을 때 쓸 수 있는 실행 모델이다. 한 에이전트가 끝까지 보는 편이 맥락 전달 비용이 작은 작업도 있다. 역할을 나눌 때는 분업 이득이 조정, 통합과 재검증 비용보다 큰지 먼저 본다.

- **역할 분리**: 조사, 작성, 검증, 편집처럼 작업을 잘게 나눠 각 에이전트에 명확한 책임을 준다
- **병렬 처리**: 독립적인 하위 작업만 동시에 진행한다. 공유 파일과 강한 순서 의존성이 있으면 충돌과 통합 비용이 이득을 넘을 수 있다
- **검증의 우선성**: 가장 위험한 것은 그럴듯하지만 틀린 결과다. QA, 오류 검증, 일관성 점검 에이전트가 생성물을 재확인한다. 정확성이 중요한 작업일수록 생성보다 검증 설계가 더 중요하다. 좋은 하네스는 많이 만드는 시스템이 아니라 틀린 결과를 걸러내는 구조까지 포함한 시스템이다

이는 5대 원칙의 Verify와 Correct를 별도 에이전트로 분리해 구현한 형태다. 한 에이전트가 생성하고 다른 에이전트가 평가하는 LLM-as-a-Judge 패턴이 여기 속한다 → [[Agent-Spec-Writing]].

### 템플릿화 (반복 업무의 하네스)

자주 하는 업무(사업계획서, 콘텐츠 기획, 소프트웨어 개발, 데이터 분석)는 에이전트 역할과 절차를 미리 정의한 템플릿으로 묶는다. 가치는 속도다. 매번 처음부터 오케스트레이션을 설계하지 않고 새 목표만 갈아끼워 실행한다. 작게 시작해도 된다. 한 작업에 작성자 에이전트와 검토자 에이전트 둘만 붙여도 하네스적 사고의 시작이다.

## 적용 점검: 개인 프로젝트

아래 두 항목은 본인이 직접 수행한 경험을 공개 가능한 범위로 일반화한 사례다. 개인 프로젝트에서 하네스를 적용할 때는 구성 요소의 개수나 점수보다 경계와 회복 흐름을 점검했다.

| 원칙 | 점검 질문 |
|---|---|
| Constrain | 도메인별 규칙과 금지 변경이 가까운 경로에 있는가? |
| Inform | 작업자가 목표, 제약, 사용자 가치와 코드 구조를 필요한 시점에 읽는가? |
| Verify | 구현 뒤 자동 검사와 독립 리뷰가 실패를 발견하는가? |
| Correct | 발견한 실패를 규칙, 테스트, 회고로 다시 흡수하는가? |
| Human-in-loop | 제품 방향, 권한, 비용처럼 고위험 결정은 사람이 승인하는가? |

개인 프로젝트에서 도메인 규칙, 역할 기반 검토, 문제의 비즈니스 맥락과 명세 중심 개발을 함께 둬 변경 경계를 명확히 했다. 다음 개선은 자동 검증, 생성물 검토, 작업 관찰과 실패 복구를 실제 작업 흐름에 맞게 하나씩 추가하는 것이다.

## 적용 점검: 팀 AI 협업

AI 코드 생성에만 의존하던 협업 흐름에서 변경 경계 누락, 맥락 과다 로드와 세션 간 품질 편차를 직접 겪었다. 이를 줄이기 위해 다음 원칙을 작업 규칙과 검토 흐름에 적용했다.

- **Constrain** — 변경 위험이 큰 경로와 금지 행위를 규칙으로 명시하고, 규칙을 대상 경로 가까이에 둔다.
- **Inform** — 필요한 도메인 맥락, 실행 방법과 검증 기준만 작업에 맞춰 로드한다.
- **Verify** — diff 확인, 관련 테스트, 정적 검사와 독립 품질 리뷰를 변경 후 게이트로 둔다.
- **워크플로우 자동화** — 조사, 구현, 검토처럼 책임이 다른 반복 작업은 역할과 입력, 종료 조건을 분리한다.

그 결과 개인의 프롬프트 역량에만 의존하던 흐름에서 벗어나, 사람이 설계 판단과 리뷰에 더 시간을 쓸 수 있는 공통 검토 경계를 만들었다. 다만 효과는 결함 재발, 재작업과 배포 안전성 같은 지표로 접근이 통제된 운영 기록에서 검증해야 한다. 개인 적용이 스스로의 실수를 빠르게 발견하는 데 초점을 둔다면, 팀 적용은 다른 사람이 변경해도 같은 경계와 검증이 작동하게 만드는 데 초점을 둔다.

## 면접 포인트

Q. AI 시대에 엔지니어링 생산성을 어떻게 높이는가?
- 하네스 엔지니어링: 에이전트를 감싸는 제약/맥락/검증/교정/인간 개입 인프라 설계
- 도메인별 규칙, 역할 기반 검토와 명세 중심 워크플로우를 조합해 실제 작업 흐름에 맞게 구축
- 강점과 부족한 축은 구성 요소 수가 아니라 제약, 맥락, 검증, 교정과 승인 흐름이 실제로 작동하는지로 점검

Q. 단순히 AI를 사용하는 것과 하네스를 설계하는 것의 차이는?
- AI 사용: 프롬프트를 잘 쓰는 것 (개인 스킬)
- 하네스 설계: 반복 작업의 제약과 검증을 환경에 넣어 결과 편차를 줄이는 것 (조직 역량)
- 생산성 저점을 높이는 것은 가설이며, 결함 재발, 재작업과 lead time으로 실제 효과를 검증한다
- 이 자료의 실무 프레임으로: 프롬프트 → 컨텍스트 → 하네스. 반복 가능한 도구와 피드백을 먼저 만들고, 독립 분업의 이득이 있을 때만 역할을 나눈다

Q. 멀티 에이전트로 나누면 뭐가 좋고, 검증은 왜 별도 에이전트로 두나?
- 독립적인 조사, 작성, 검증을 분리하면 병렬 처리와 독립 검토의 이득을 얻을 수 있지만 조정 비용을 함께 측정
- 가장 위험한 건 그럴듯하게 틀린 결과 → 생성보다 검증 설계가 중요. QA와 일관성 에이전트로 Verify와 Correct를 분리
- 좋은 하네스는 많이 만드는 게 아니라 틀린 결과를 걸러내는 구조까지 포함한 시스템
