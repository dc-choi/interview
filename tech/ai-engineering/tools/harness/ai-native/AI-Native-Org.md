# AI-Native 조직 (AI-Native Org)

[[AI-Native-System|AI Native 레포]]가 개인의 코딩 생산성을 풀었다면, 다음 경계는 조직 전체가 AI를 호출하고 검증하고 기억하는 **공용 실행 계층**이다. 개인 IDE 안의 AI는 세션 내 단발이고 협업 흐름(요구→승인→구현→검증→기억)과 세션 밖 기억을 갖지 못한다. 이를 푸는 것이 팀의 공용 인터페이스 위에 올린 전사 AI 실행 하네스다.

## 왜 조직 단위인가 — 개인 IDE의 한계

- 세션 내 단발이라 협업 맥락(누가, 왜, 어떤 제약으로 요청했는지)이 없다
- 세션이 끝나면 결정과 발견이 사라져 매번 재설명해야 한다
- 비개발자는 IDE 안의 AI에 접근할 수 없다

조직 실행 계층이 주는 것: 요구사항과 승인, 피드백, 결과가 한 스레드에 시간순으로 기록되어 감사 가능성이 자동 확보되고 세션 밖 지식이 누적되며 누구나 같은 인터페이스로 접근한다.

## 설계 원칙 4가지

1. **기존 흐름을 따른다** — 새 UI로 사람을 옮기는 대신, 조직이 이미 일하는 인터페이스(공용 팀챗) 안으로 AI를 넣는다. 채택 비용이 낮고, 협업이 이미 스레드 단위라 맥락이 자연스럽게 쌓인다.
2. **세션 밖 메모리는 필수** — pod 재시작이나 세션 종료로 기억이 날아가면 매번 재설명이 발생하고 조직 학습이 불가능하다. 기억을 세션 바깥 계층에 둔다.
3. **이미 좋은 것은 재구현하지 않는다** — 성숙한 코딩 루프(계획→수정→테스트→Git)는 재활용하고 조직 실행 계층(인터페이스, 상태 관리, 메모리)에만 집중한다. 하네스 위에 하네스를 얹는 전략이다.
4. **복구가 기능만큼 중요하다** — 중복 처리, stale lock 회수, pod 중단 중 상태 복구가 시스템 신뢰도를 결정한다. 신규 기능보다 실패 복구에 더 많은 시간이 든다.

## 아키텍처 — 팀챗 위 멀티 에이전트 플랫폼

실행 흐름은 단방향 파이프라인이다.

팀챗 webhook 수신 → API 서버(stateless: 스레드 문맥 복원, 상태머신 관리, 태스크를 PostgreSQL에 저장) → Orchestrator(DB 스캔, 워커 pod 생성과 회수) → Kubernetes Job 워커 pod(코딩 에이전트 코어 실행: 탐색, 수정, 테스트, PR) → 결과를 팀챗 스레드에 보고.

| 컴포넌트 | 역할 |
|---|---|
| API 서버 (stateless) | 스레드 문맥 복원, 상태머신 관리, 태스크 저장 |
| Orchestrator | DB를 스캔해 워커 pod 생성과 회수 |
| Conversation Agent | 팀챗 메시지 해석, 스레드 root와 reply history로 문맥 회수 |
| Specialized Agent | 도메인 작업 (브라우저 자동화, 로그 분석 등) |
| Worker (K8s Job) | 코딩 에이전트 코어 루프 실행 |

저장소: PostgreSQL(태스크와 상태), Redis(중복 처리와 lock), 벡터 DB(의미 검색), 그래프 DB(심볼 의존성), 지식 베이스(결정과 규칙).

### 상태머신 제어 + Human-in-the-loop

암묵적 협업 규칙을 명시적 상태 전이로 강제한다.

PLAN_REVIEW → (사용자 승인) → IMPLEMENTING → CODE_REVIEW → COMPLETED

각 전이에 사람의 개입점이 고정된다: 계획 승인(구현 전 검증), 코드 리뷰(PR 생성 후 피드백), 머지 판단(최종은 사람). 개입 모드는 유연하다 — 질문만 하고 끝낼 수도, 같은 스레드에서 구현으로 전환할 수도, 진행 중 언제든 제약을 추가할 수도 있다.

하이브리드 결정론으로 **결정론적 상태 전이 + 비결정론적 대화 해석**을 결합한다. 실제 사용자 대화는 비선형(질문→실행→제약 추가→재실행)이라 순수 결정론으로는 담을 수 없다. 결정론을 포기하는 게 아니라 그 경계를 어디에 둘지 찾는 일이다.

### Kubernetes Job 워커 격리

태스크당 일회성(ephemeral) pod로 워커를 실행한다. init container가 대상 레포를 clone하고, main container가 코딩 에이전트를 실행하며, 작업이 끝나면 자동 정리된다. 이점은 실행 환경 격리, 실패 격리, 역할별 이미지 차별화다. 같은 webhook이 여러 pod에 중복 유입되는 것은 Redis 기반 dedup으로 막고, stale lock 회수로 재시도 가능성을 보장한다.

### MCP 프록시 — 자격증명 중앙화

워커 pod에 자격증명을 직접 두지 않는다. pod 안의 MCP 서버가 내부 API를 거치고, 자격증명과 조직별 권한, 설정은 서버에서 중앙 관리한 뒤 외부 API를 호출한다. 권한이 중앙화되어 감사가 쉽고 pod 유출 위험이 줄어든다. → [[MCP]]

## 메모리 계층 — 조직 학습의 누적

세션 밖 기억을 4계층으로 둔다.

| 계층 | 범위 | 저장 내용 |
|---|---|---|
| L1 | 현재 세션 | 진행 중 컨텍스트 |
| L2 | 태스크 | 결정, 발견 |
| L3 | 레포/서비스 | 코드 패턴, 아키텍처 |
| L4 | 조직 | 규칙, 제약, 경험 |

검색은 세 방식을 동시에 운영한다: 벡터 검색(코드와 문서의 의미 기반), 그래프 검색(심볼 의존성 관계 추적), 메모리 검색(축적된 결정과 규칙 조회). 저장 대상은 어떤 태스크에서 어떤 결정이 내려졌는지, 반복되는 레포 구조와 패턴, 조직 차원의 제약과 규칙, 관찰된 실패와 사이드이펙트다.

주의: 잘못된 규칙이 쌓이면 오히려 독이 된다. 메모리 정확성은 명시적 검증과 짝을 이뤄야 한다. 불투명한 자동 메모리를 끄고 검증된 정의만 정책으로 인정하는 [[Production-Agent-Architecture-Knowledge#Auto Memory 비활성화|프로덕션 에이전트 아키텍처]]의 Auto Memory 논의와 같은 긴장이다.

## 활용 양상 — 코딩을 넘어

같은 스레드 인터페이스 위에서 개발 외 작업도 처리된다.

- **보안 전수조사**: 취약점 영향 프로젝트를 자동 트리아주하고 역할별 액션 아이템으로 분배
- **배포 직후 관측**: 관측 도구의 에러율과 latency 이상징후를 자동 확인해 후속 검토 항목만 필터
- **조직 지식 조회**: 스펙 문답을 비개발자도 같은 인터페이스로 질의
- **자기 수정**: 플랫폼이 자기 레포를 한 스레드에서 계획→승인→구현→PR→머지까지 완성

운영 알람 채널의 자동 트리아주가 도입 확산의 주된 동력이 된다.

## 트레이드오프, 한계

- 결정론과 대화형의 균형 — 경계 설정 자체가 설계의 본질
- 복구 로직이 기능 개발보다 시간이 더 든다 (dedup, stale lock, pod crash 복구)
- 확장성 — 수천 태스크 동시 처리 시 DB와 Orchestrator가 병목
- 메모리 정확성 — 잘못된 규칙 누적 위험
- 보안과 권한 — 역할별 접근 제어와 감사 로깅 필요

## AI-Native 조직의 6요소

조직이 AI를 실제로 굴리려면 여섯 가지가 함께 있어야 한다.

1. 좋은 레포 ([[AI-Native-System|AI Native 코드베이스]])
2. 강제되는 규칙 (lint, 테스트, 아키텍처 검증)
3. 조직 지식 (문서, 아키텍처 결정)
4. 세션 밖 메모리 (L2~L4 계층)
5. 공용 인터페이스 (팀챗 스레드)
6. 조직 문화 (AI를 실제로 쓰려는 의지)

## 출시 흐름의 병목은 단계를 따라 옮겨 간다

에이전트가 코드를 쓰고 엔지니어가 방향을 잡게 하는 것만으로는 출시가 그만큼 빨라지지 않을 수 있다. 한 단계를 빠르게 해도 다음 단계의 처리 용량이 그대로면 그곳에 일이 쌓일 수 있으므로, 출시 흐름을 단계별로 나눠 어디가 막혔는지 확인하고 차례로 고친다. 아래는 앞 단계가 빨라질 때마다 다음 단계에 일이 쌓였다고 밝힌 한 조직의 순서와 대응이며(수치는 사례 절), 다른 조직도 같은 순서로 막힌다는 근거는 아니다.

| 막힌 단계 | 대응 |
|---|---|
| 테스트 | 에이전트가 코드와 함께 테스트를 쓴다 |
| 리뷰 | 사람보다 먼저 AI가 리뷰하고 사람은 판단이 필요한 부분에 집중한다 |
| CI | 테스트를 병렬화하고 변경의 영향을 받는 테스트만 돌린다 |
| 버그 접수 | 누구나 팀챗으로 제보하고 에이전트가 중복 확인, 티켓 등록과 담당자 지정을 맡는다 |
| 머지 | 테스트, 자동 검사와 AI 리뷰를 통과한 저위험 변경은 사람 없이 머지한다 |

저위험의 판정 기준은 따로 정해야 한다(아래 사례도 기준을 밝히지 않는다). 이 경로는 위 상태머신처럼 머지를 사람의 최종 판단으로 고정한 설계와 달리, 저위험으로 판정한 변경에서만 그 판단을 테스트, 자동 검사와 AI 리뷰로 바꾼다. 변경 내용으로 위험 등급을 나눠 사람 승인 수를 정한 운영 예는 [[Code-Review-AI-Agent-Operations#위험에 따른 검증|에이전트 시대 코드 리뷰 운영]]에, 작성이 늘 때 어느 단계가 먼저 막혔는지의 다른 사례는 [[AI-Work-Output-and-Employment#산출이 늘면 병목은 다음 단계로 옮겨 간다|산출 증가 뒤의 병목 이동]]에 있다. 흐름을 고치는 동안에는 엔지니어링 시간이 테스트와 도구에 들어가 고객에게 나가는 변경이 바로 늘지 않을 수 있다.

### 엔지니어만 알던 규칙을 자동 검사로 바꾼다

버그나 리뷰 지적으로 엔지니어만 알던 규칙이 드러날 때마다 그 규칙을 작은 검사 코드로 만든다. 검사는 모든 커밋과 PR에서 돌고, 위반하면 빌드를 실패시키면서 고칠 방법을 출력한다. 에이전트가 검사에 걸리면 출력을 보고 스스로 코드를 고친 뒤 작업을 이어 가게 한다. 이렇게 쌓인 검사가 저위험 변경을 사람 없이 머지하는 경로를 받친다. 팀만 아는 규칙에 게이트를 거는 기준은 [[Harness-Gate-Placement#게이트를 걸어야 하는 세 곳|게이트 배치]], 진단 출력이 그대로 수정 입력이 되는 예는 [[Design-System-Lint|디자인 시스템 lint]], 반복 실수를 시스템으로 흡수하는 루프는 [[AI-Native-System#마인드셋 — 실수를 시스템으로 흡수하는 루프|AI 네이티브 시스템]]이 다룬다.

### 구현이 빨라지면 무엇을 만들지 정하는 일이 병목이 된다

계획 3일, 구현 6일, 리뷰 1일인 10일짜리 기능에서 구현만 3.5배 빨라지면 전체 기간은 약 5.7일로 1.75배 빨라지는 데 그치고, 계획과 리뷰의 비중은 40%에서 70%로 커진다. 측정값이 아니라 단순화한 예시 계산이다. 빨라지지 않은 구간이 전체 속도를 묶는 원리는 [[AI-Leverage-Small-Teams#How가 빨라지면 What이 병목이 된다|How가 빨라지면 What이 병목이 된다]]와 [[Developer-Role-AI-Era#구현이 싸질 때 옮겨 가는 병목 — 결정과 승인 대역폭|결정과 승인 대역폭]]으로 이어진다.

이 병목에 관리 계층을 더하는 대신 엔지니어가 고객 문제를 이해하는 일부터 계획, 출시, 성공 확인과 운영 회귀 대응까지 더 많이 맡게 하는 설계가 제안된다. 사례 조직이 직급과 관리자 역할까지 포함해 내놓은 구체안은 사례 절에 두며, 그 조직이 아직 초기라고 밝힌 가설이지 효과를 검증한 조직 모델이 아니다. 책임 범위가 넓어질 때의 번아웃과 단일 담당자 위험은 [[AI-Leverage-Small-Teams#작은 팀 전략의 한계|작은 팀 전략의 한계]], 주니어가 에이전트의 오류를 알아볼 판단력을 기르는 경로는 [[Developer-Role-AI-Era#견습 사다리에 생기는 압박|견습 사다리]]를 본다.

### 결정 병목을 기록된 판단 원칙으로 줄이는 시도

PR과 사람 승인까지 걷어 내면 남는 병목은 사람에게 쌓이는 판단 요청이다. 한 게임 스타트업(Spawn)의 창업자는 2년 동안 기록한 대화와 결정에서 사람별 판단 원칙을 뽑아, AI 판정자(judge)가 기존 결정으로 답할 수 있는 요청을 처리하고 새로운 판단만 사람에게 넘기게 했다. 첫 판정 뒤 8일 동안 11,000건 넘게 판정해 7,296건을 결정하고 2,213건을 돌려보내며 1,863건을 사람에게 넘겼고, 하루에 반영한 변경이 판정자 도입 전 약 1,000건에서 10월 10일 7,250건이 됐다고 밝혔다(모두 자기 보고, 나머지 수치는 사례 절). 사람은 제품을 직접 써 보며 무엇을 만들고 거절하고 지울지 정하고, 작은 개선을 반복하는 에이전트가 떠올리지 못하는 큰 목표를 준다.

이 방식은 아래 사다리의 멈춤 신호와 함께 읽는다(추론). 판정 원칙은 과거 결정을 압축한 것이라 새 유형의 판단을 사람에게 넘기는 출구가 필수이고, 판정자의 오판과 되돌림을 따로 세지 않으면 결정량 증가를 품질 개선으로 볼 수 없다. 같은 회사는 이 수준의 자율이 특정 모델 하나로만 가능했고 그 모델의 접근이 수출 통제 명령으로 6월 12일부터 7월 1일까지 끊긴 기간도 있었다고 적어, 한 모델의 장애가 곧 사업 중단으로 이어지는 의존 구조도 보여 준다.

## 업무별 전환 단계는 증거로 올린다

AI 네이티브 여부를 회사 전체의 등급으로 붙이기보다 업무마다 지금 어느 단계에 있는지 정하고, 다음 단계로 갈 증거와 멈출 신호로 판단할 수 있다. 아래 사다리와 사고실험은 2026-10-22까지의 사실로 쓴 AI 네이티브 핸드북(ETRI 연구자 저술, 407쪽, CC BY-NC-ND 4.0)의 틀을 이 문서의 말로 요약한 것이다. 이 틀과 부록 점검표는 검증된 성숙도 진단 도구가 아니므로(책의 부록 설명), 아래 기준은 실증 결과가 아니라 설계 제안으로 쓴다.

- **네 단계:** Ready는 데이터, 권한, 책임과 기준선을 준비하고, Enabled는 기존 업무 일부를 AI로 보조하며, First는 AI를 전제로 업무 흐름과 역할을 다시 짜고, Native는 AI가 핵심 가치와 학습 구조에 결합된 상태다. 같은 회사에서도 업무마다 단계가 다르고, 규제가 강한 업무가 위험과 효용을 따져 Enabled에 머무는 것은 실패가 아니다.
- **오를 근거:** Ready에서 Enabled로는 소유자와 성공 기준을 정한 통제된 실제 사용이 필요하다. Enabled에서 First로는 기능 하나의 정확도가 아니라 처리 시간, 재작업, 고객 결과와 사고 비용을 한 흐름에서 잰 결과를 본다. First에서 Native로는 대체 모델, 기능을 줄인 제한 모드, 사람의 개입과 복구 목표까지 제품 설계에 넣어야 한다.
- **멈춤 신호:** 데이터 출처를 설명할 수 없거나 사고 책임자가 없을 때, 검토 부담과 오류 비용이 편익을 넘을 때, 일부 단계만 빨라져 병목이 옮겨 가거나 책임이 흐려질 때, 한 모델의 장애가 곧 사업 중단으로 이어질 때다.

### AI를 빼 보는 사고실험

제품이나 서비스에서 AI를 뺐을 때 무엇이 남는지를 네 축으로 본다. 고객 가치는 전에 불가능했던 결과가 사라지는지, 시간과 비용만 나빠지는지, 고객이 차이를 알아차리지 못하는지로 나눈다. 운영 부담은 같은 품질을 사람이 만들 때의 시간, 비용, 오류와 검토 부담이다. 복원력은 모델 API 중단이나 품질 저하 때 축소 운영, 사람이 맡을 최소 기능, 모델 교체와 복구 책임자가 있는지다. 차별화와 학습은 경쟁사가 같은 모델을 연결해도 같은 결과가 나오는지다. 고객이 계속 선택할 이유와 복제하기 어려운 가치는 [[AI-Commoditization-Differentiation|AI 범용화와 사업 차별화]]의 질문으로 이어진다. 네 축을 한 점수로 합치지 않는다. 가치는 큰데 복원력이 약하면 대체 경로를, 복원력은 충분한데 고객이 차이를 못 느끼면 문제 정의를 먼저 고친다.

같은 책의 증거 점검표는 등급을 매기는 도구가 아니라 주장과 실제 운영 사이에서 증거가 비어 있는 곳을 찾는 용도이며, 있다고 답할 때는 승인 문서, 운영 로그나 계약처럼 다른 사람이 확인할 수 있는 자료를 적게 한다. 팀 점검에서는 평균보다 답이 갈린 문항을, 조직 점검에서는 부서별 비율보다 고위험 업무의 공백을 먼저 본다. 이 방식은 [[Production-Agent-Architecture-Delegation#자율권은 작업별 증거로 넓히고 다시 줄인다|작업별 증거로 자율권을 조정하는 원칙]]과 같은 방향이다.

## 면접 체크포인트

- 개인 IDE의 AI와 조직 AI 플랫폼의 차이 (협업 맥락 + 세션 밖 메모리 + 접근성)
- 왜 새 UI 대신 기존 팀챗 위에 올리나 (채택 비용, 감사 가능성, 맥락 누적)
- 상태머신과 대화 해석을 결합하는 이유 (비선형 대화에서 결정론의 경계 찾기)
- K8s Job ephemeral 워커 격리의 이점 (실행, 실패 격리 + 역할별 이미지)
- 복구가 기능만큼 중요한 이유 (dedup, stale lock, crash 복구가 신뢰도 결정)
- AI를 전사 워크플로우로 쓰는 조직에서 백엔드가 만드는 것 = 이 실행 인프라(상태 관리, 워커 격리, 메모리 계층)
- 업무별 전환 단계를 올릴 증거와 멈출 신호, AI를 빼 보는 사고실험의 네 축(고객 가치, 운영 부담, 복원력, 차별화와 학습)
- 코드 작성이 빨라진 뒤 병목이 테스트, 리뷰, CI, 머지를 거쳐 무엇을 만들지 정하는 결정으로 옮겨 간 한 사례와 단계별 대응 (엔지니어만 알던 규칙의 자동 검사화와 저위험 자동 머지, 관리 계층 대신 넓히는 엔지니어의 책임 범위)

## 사례

- 도입 후 3개월 내 사용량 3배 이상 성장, 운영 알람 자동 트리아주가 변곡점
- 자기 수정 사례 — 플랫폼이 자기 레포의 코드를 한 스레드에서 계획부터 머지까지 완성
- FurtherAI(공동창업자 겸 CTO의 2026-10-29 공개 글)는 2026년 3월부터 9월까지 코드 작성, 테스트, 리뷰, CI, 버그 접수, 규칙, 머지, 팀챗 코드 채널 순으로 출시 흐름을 고쳤다. 1월 이후 엔지니어 1인당 근무일 병합 변경 약 5배와 되돌림 비율 0.5% 미만, 테스트를 포함한 변경 15%에서 91%, 사람보다 먼저 AI가 리뷰한 변경 60%에서 99%, 같은 17분 CI에서 도는 테스트 20배, 에이전트가 등록한 버그 티켓 60%, 규칙 검사 0개에서 21개, 사람 없이 머지된 변경 최대 3분의 1을 보고했다. 그래프 주석은 병합 수를 백엔드와 웹 앱의 주간 병합 PR(1월 5일~10월 11일)로 세고 그사이 활성 엔지니어가 8명에서 18명으로 늘어 1인당 값으로 보정했다고 밝히며, 같은 그래프의 병합 막대에는 에이전트 자체 계정, 봇과 엔지니어링 밖 사람의 병합도 함께 쌓여 있다. 1인당 선의 값은 이 막대 전체를 활성 엔지니어 수와 근무일로 나눈 값과 맞아 보이며(눈금 대조 추정), 글은 5배에 엔지니어가 아닌 계정의 병합이 들어가는지 밝히지 않는다. 다른 지표는 변경 전과 10월의 비교만 있고 분모와 판정 기준, 원자료를 밝히지 않은 자기 보고다.
- 같은 조직의 CTO는 직급을 한 사람이 처음부터 끝까지 맡을 수 있는 문제의 범위로 보기 시작했다며, 주니어는 에이전트와 함께 구현하고 에이전트가 틀렸을 때 알아보고, 시니어는 자기 작업을 직접 계획하고 리뷰하며, 스태프는 모호한 문제의 트레이드오프를 정하고 효과를 판정할 지표를 책임지는 틀을 들었다. 관리자에게는 무엇을 왜 만드는지 이해하고, 코드가 리뷰됐는지만 확인하지 않고 스테이징에서 최종 사용자처럼 기능을 써 보며, 기술뿐 아니라 제품 결정도 내리고 엔지니어가 그 판단력을 기르도록 돕기를 바란다고 썼다. 모든 작은 제품 결정에 PM이나 디자이너를 거치지 않아도 되게 하자는 취지다.
- 같은 조직은 여름 동안 엔지니어링 노력의 상당 부분을 테스트와 도구에 써 엔지니어 1인당 고객 대상 변경이 월 17~30건에 머물렀고 9월에 45건이 됐다고 밝혔다(10월은 48건 추세). 누구나 팀챗 채널에서 에이전트에게 변경을 설명해 PR을 열고 여러 사람이 같은 에이전트를 함께 조정하는 코드 채널도 두었으며, 디자이너가 8월 이후 디자인 시스템 작업을 포함해 약 50건을 머지하는 등 비엔지니어도 코드를 출시했다.
- Spawn(창업자 Jacob Sansbury의 2026-10-29 X 장문 글)은 직원이 10명이라고 밝힌 게임 회사다. 인건비의 30배를 토큰에 쓰며 지난달 토큰 비용이 310만 달러였다고 적었다. 이름, 기억, 실제 시스템 권한과 담당 영역(재무, 배포 등)을 가진 상시 에이전트들이 날마다 보조 에이전트 수천 개를 만든다. 올해 초 PR을 없앴고, 최신 코드에 전체 테스트를 15분마다 약 5,000 vCPU와 GPU 150개로 돌리며 매시간 배포한다(한 시간 동안 배포가 없으면 장애로 취급). 무엇이 깨지면 그 자리에서 에이전트를 만들어 고치게 하고 롤백은 30초다. 최근 30일 실질 변경 77,000건, 지난 1년 123,548건 중 1,055건(약 0.9%) 되돌림을 보고했다. 실질 변경은 엔진 코드나 게임 로직을 복잡하게 건드리는 변경이라는 정성적 설명과 예시만 있고, 집계 기준, 되돌림의 정의와 원자료는 공개하지 않았다. 본문에 다섯 명이라는 표현도 있어 인원 구성은 불명확하다. 이 글을 소개한 Simon Willison은 게임이어서 통하는 방식일 수 있고 실패의 대가가 큰 소프트웨어에서는 상상하기 어렵다고 평했다.
