# 에이전트 작업의 스펙과 결정 기록

코딩 에이전트가 실행을 빠르게 대신하면 병목은 구현에서 검토와 자산화로 옮겨 간다. 작업 의도, 선택 근거와 시행착오가 세션 안에만 있다가 사라지면 사람의 이해(멘탈 모델)가 자라지 않고, 에이전트가 낸 많은 산출물에서 무엇이 빠졌고 왜 바뀌었는지 놓치기 쉽다. 스펙 주도 개발(SDD)을 팀 정책으로 둘 때는 이 손실을 막는 최소 기록을 고정하고 만드는 방법은 열어 두는 구성이 쓰인다.

아래 구성은 분석, 실험과 파이프라인 운영이 섞인 한 팀의 정책을 발표 기준으로 정리한 것이다. 그 팀은 Spec Kit 같은 공개 SDD 도구가 소프트웨어 개발 흐름에 맞춰져 있고 산출물이 많아 도입 부담이 크다고 보고 필요한 개념과 산출물만 골라 직접 만들었다. 각 규칙의 효과는 측정값 없이 발표된 경험이다.

SDD 자체의 정의와 문서 계층은 [[RFC-Writing#Spec-Driven Development (SDD)|RFC / PRD 작성의 SDD 절]]에 있다. 이 문서는 에이전트와 함께 일하는 팀이 그 기록을 어떻게 남기고 운영하는지를 다룬다.

## 기록이 막는 세 가지 손실

| 손실 | 증상 | 막는 기록 |
|---|---|---|
| 의도 소실 | 컨텍스트가 길어지면 첫 요청과 제약이 묻히고 작업 방향이 모델의 주목을 따라 흘러간다 | 작업 전에 범위, 의도, 주의사항을 적은 계획 |
| 산출물 맥락 소실 | 결과물은 빨리 쌓이지만 왜 그렇게 나왔는지 찾을 수 없다 | 검토한 선택지와 근거를 결과물과 함께 남긴 결정 기록 |
| 시행착오 반복 | 막힌 지점을 에이전트가 풀고 사람은 승인만 해 해법이 팀에 남지 않는다. 사람이나 세션이 바뀌면 같은 문제를 다시 푼다 | 시행착오와 해결 방법을 다음 작업의 지침으로 정리 |

## 두 필수 문서

작업 단위 하나마다 저장소의 스펙 폴더 아래에 날짜와 작업명으로 폴더를 만들고 두 문서를 둔다. 코드와 같은 저장소에 두면 PR에서 코드 변경과 스펙 변경을 함께 검토한다.

- **plan.md (무엇을 하는가)**: 배경과 외부 제약, 이번 범위에서 할 것과 하지 않을 것, 단계별 목표와 진행 상황, 완료 기준과 검증 방법, 실행 전제, 용어, 나중에 할 일. 데이터 형태와 사용할 자원 같은 외부 제약을 처음에 적어야 그에 맞는 산출물이 나온다. 하지 않을 것과 후속으로 미룬 것을 명시하면 에이전트가 범위를 임의로 넓혀 시간과 토큰을 쓰는 일을 줄인다.
- **decisions.md (왜 그렇게 했는가)**: 결정 하나를 문제, 검토한 옵션, 선택, 근거로 나눈다. 예를 들어 새 분류 기준을 키워드 규칙으로 판별할지 LLM 추론으로 판별할지 두 옵션을 놓고, 표현 변형이 많다는 근거로 LLM 추론을 고른 기록이다.

두 문서는 사람이 처음부터 쓰기보다 요구사항을 에이전트에게 넘기고, 모호하거나 설계가 갈리는 지점을 질문받아 하나씩 고르는 대화로 구체화한다. 그 대화의 결과가 두 문서로 나온다. 계획이나 설계를 설계 트리(design tree)의 모든 분기가 풀릴 때까지 질문하게 하는 `grill-me` 같은 공개 스킬을 감싸 쓰는 방식이 한 예다(저장소 README 2026-11-17 확인).

## 결정 기록의 규칙

- **출처 태그**: 결정마다 제안자(사람 또는 AI)와 반영을 결정한 주체를 남긴다. 작업자가 의도해 고른 부분과 에이전트가 작업 중 스스로 정한 부분을 리뷰에서 구별할 수 있다.
- **영향도 태그**: 그 결정이 변경에 얼마나 영향을 주었는지 표시해 리뷰와 설계 변경의 우선순위로 쓴다.
- **누적과 고유 번호**: 한 번 적은 결정은 지우지 않고 쌓는다. 번호는 결정이 뒤집혀도 다시 매기지 않아 다른 문서에서 안정적으로 참조할 수 있다.
- **뒤집기의 흔적**: 기존 결정을 뒤집으면 옛 결정에 대체한 결정 번호를 표시하고, 새 결정에 관련 설계와 변경 이력을 적는다. 다시 논의할 결정에는 재논의 표시를 붙인다. 에이전트가 기존 결정을 뒤집을 때는 작업자에게 보고하게 해 스펙을 마음대로 고치지 못하게 한다.

이 방식은 ADR의 superseded 관행과 같은 방향으로 읽을 수 있다(이 문서의 해석). 차이는 사람과 AI 중 누가 제안하고 정했는지를 결정 단위로 남긴다는 점이다.

## 규칙과 스킬의 배치

팀 스킬이 여러 개로 늘고 고쳐지면서 같은 절차가 여러 스킬에 흩어지면 두 문제가 생긴다. 결정 번호 매기기 같은 기본 규칙이 스킬을 부르지 않은 작업에서 빠지고, 스킬을 고칠 때 중복된 곳 일부만 바뀌어 모델이 어느 쪽을 따를지 헷갈린다.

- **항상 적용할 핵심 규칙은 rule로 둔다.** Claude Code 공식 문서 기준(2026-11-17 확인) `paths` frontmatter가 없는 `.claude/rules/` 파일은 세션 시작 때 `.claude/CLAUDE.md`와 같은 우선순위로 로드되고, `paths`가 있으면 일치하는 파일을 읽거나 쓸 때 로드된다. 일반 세션에서 스킬은 설명만 상시 로드되고 본문은 호출되거나 관련 있다고 판단될 때 로드된다. 스킬을 미리 붙인 서브에이전트는 예외로 시작 때 본문이 들어간다.
- **여러 스킬이 공유하는 절차와 템플릿은 단일 원천 문서로 빼고** 스킬은 그 문서를 참조만 한다.
- **스킬과 규칙만 별도 저장소와 플러그인으로 분리하고 날짜 태그로 릴리스한다.** 각자 받은 시점이 달라 미묘하게 다른 규칙으로 일하는 문제를 겨냥하고, 누가 어느 버전을 쓰는지 말할 수 있다. 발표한 팀은 세션 시작 때 규칙을 자동 주입했다. 공식 플러그인 레퍼런스 기준(2026-11-17 확인) 플러그인에는 rule 구성요소가 없고 플러그인 루트의 `CLAUDE.md`도 컨텍스트로 로드되지 않으며, 컨텍스트에 넣을 지시는 skill에 두라고 안내한다. 플러그인으로 상시 규칙을 배포하려면 이 차이를 확인하고 경로를 고른다. 위의 로드 우선순위는 실제 `.claude/rules/` 파일에만 해당한다. 플러그인 자동 업데이트는 검토한 파일이 나중에 바뀔 수 있다는 보안 경계도 함께 본다([[Claude-Code-Customization]]).
- **산출물 계약만 고정하고 만드는 방법은 고르게 한다.** 두 문서와 핵심 규칙만 팀 공통으로 두면, 팀 스킬을 그대로 쓰든 공개 스킬 묶음을 감싸 쓰든 결과 형식은 같다. 핵심 규칙이 rule에 있어야 가능한 구조다.

## 스펙이 쌓일 때의 현황 문서

작업 단위마다 스펙과 부가 문서가 쌓이면 관련 이력이 흩어지고, 뒤의 결정이 앞 스펙을 뒤집어 최신 상태를 파악하기 어려워진다. 에이전트가 그때그때 grep으로 찾게 두는 방식은 문서가 늘수록 비용이 커진다.

원장 스펙은 계속 쌓고, 프로젝트 전체 현황은 자동 생성 문서로 따로 유지하는 방법이 있다. LangChain의 OpenWiki는 코드베이스의 Markdown wiki를 쓰고 유지하는 오픈소스 CLI(저장소 기준 MIT 라이선스)이며, 공식 문서와 저장소 기준(2026-11-17 확인) 일정에 따라 문서를 갱신하고 wiki가 바뀌었을 때만 PR이나 MR을 여는 CI 예제(GitHub Actions, GitLab CI, Bitbucket)를 제공한다. quickstart 페이지는 자신이 안내할 다른 페이지에 링크할 수 있도록 마지막에 쓰인다. 발표한 팀은 이를 처음 보는 사람의 입구로 썼다. PR마다 실행하도록 바꾸는 것은 팀의 구성이며 공식 예제의 기본 동작이 아니다. 자동 현황 문서는 원장 결정 기록을 대체하지 않고 읽는 입구 역할을 한다.

## 모델이 좋아지면 규칙을 덜고 실험으로 확인한다

이전 모델의 한계를 메우려고 넣은 세부 순서와 금지 규칙이, 판단력이 좋아진 모델에서는 과잉 준수로 오히려 결과를 비트는 함정이 될 수 있다. 목표, 맥락, 제약과 완료 기준을 주고 방법과 순서는 모델이 고르게 하는 방향으로 지침을 줄인다. 발표 사례(2026-11 공개)에서는 새 스펙 폴더를 만드는 절차 문서가 1239줄에서 738줄로, 그 안의 금지 표현이 39건에서 23건으로 줄어드는 중이었다(음성 전사 기준).

규칙도 이전 시행착오의 결과이므로 검증 없이 지우지 않는다. 규칙과 스킬이 얽히면 한 곳을 고친 영향이 어디까지 번지는지 읽어서는 판단할 수 없다. 같은 프롬프트를 변경 전과 후의 규칙으로 별도 세션에서 실행하고, 파일이 실제로 생겼는지, 도구 호출 순서, 요청 사항을 다 지켰는지를 비교하는 A/B 평가로 확인한다. Claude Code의 `claude plugin eval`은 도구 사용, 도구 호출 순서와 파일 생성을 채점하는 grader를 제공하지만 보통 플러그인 유무 두 갈래로 실행하고(`--ablation`으로 조정), 실행은 플러그인만 올린 격리 설정에서 돈다(공식 문서 2026-11-17 확인). 규칙 변경 전후 비교는 두 버전을 따로 실행하거나 이전 실행 기록과 비교하는 grader를 쓰는 식으로 설계한다. 평가 설계는 [[Harness-Component-Evaluation|하네스 구성요소 평가]]를 따른다.

사람이 계속 기록해야 남는 것도 있다. 이번 범위에서 꼭 확인할 테스트 목록, 자주 틀리는 부분을 모은 오답 노트, 에이전트가 놓치는 범위가 그렇다.

## 적용 점검

- 두 문서가 작업 전에 범위와 하지 않을 것을 고정하고, 결정마다 출처와 영향도가 남는가
- 결정을 지우거나 번호를 다시 매기지 않고, 뒤집힌 결정이 대체 결정을 가리키는가
- 항상 지켜야 할 규칙이 스킬 호출 여부와 관계없이 로드되는 자리에 있는가
- 팀원이 쓰는 규칙과 스킬의 버전을 확인할 수 있는가
- 규칙을 더하거나 뺄 때 변경 전후를 같은 과제로 비교했는가
