# 하네스 도입 계단 (Harness Adoption Ladder)

하네스는 한 번에 완성하는 것이 아니라 계단으로 올린다. 이 문서는 무엇을 어느 순서로 얹을지, 각 단계가 어떤 실패를 없애는지를 다룬다. 블록 구조는 [[Harness-Anatomy]], 어디에 게이트를 걸지는 [[Harness-Gate-Placement]], 점검 프레임은 [[Harness-Engineering]]이 맡는다.

## 도입 범위는 실제 실패로 정한다

컨텍스트, 하네스와 루프 기법을 모두 설치하는 것을 시작 조건으로 두지 않는다. 먼저 현재 도구로 대표 작업을 수행하고, 필요한 정보 누락, 검증 누락과 반복 실행의 실패를 구분한다. 복잡한 구성이 필요하다는 판단은 용어의 유행보다 결과 개선과 비용의 근거로 내린다.

아래는 Anthropic의 단순한 구성부터 평가하며 확장하는 원칙과 컨텍스트 관리 지침을 조합한 실무 판단 예시다. 정해진 학습 순서나 제품이 보장하는 성숙도 기준은 아니다. 해당 원칙과 Hooks의 실행 경계는 2026-10-18 공식 문서로 대조했다.

| 관측한 문제 | 먼저 확인할 범위 | 확인할 결과 |
|---|---|---|
| 필요한 코드나 요구사항을 찾지 못한다 | 관련 파일 경로, 검색 도구와 필요한 시점의 자료 로딩 | 같은 작업에서 근거 누락이 줄었는가 |
| 결과는 나오지만 완료 여부를 판단할 수 없다 | 성공 기준, 테스트와 검토 근거 | 재현 가능한 기준으로 통과와 실패를 나눌 수 있는가 |
| 생성과 피드백을 반복해도 좋아지지 않는다 | 평가 기준의 명확성, 피드백의 유효성과 종료 조건 | 반복 전후 품질 차이를 확인할 수 있는가 |
| 긴 작업 중 결정과 미완료 항목을 잃는다 | 상태 기록과 압축 시 보존할 정보 | 새 컨텍스트에서도 다음 작업을 이어갈 수 있는가 |

구성을 바꾼 뒤에는 대표 작업의 정확성뿐 아니라 재작업, 실행 시간과 호출 비용도 비교한다. 이득이 확인되지 않으면 추가 분업이나 반복 호출을 도입할 근거가 부족하다. 개인 사용자의 만족 비율은 과제, 표본과 채점 기준이 없으면 일반적인 성공률로 사용하지 않는다.

도구에 정보를 주는 규칙과 실행을 차단하는 통제도 구분한다. Claude Code의 `PreToolUse`는 도구 실행 전에 차단할 수 있지만 `PostToolUse`는 이미 실행된 작업을 취소하지 못한다. 훅은 이벤트, 적용 범위와 실패 처리 설정까지 확인해야 하며, 훅 파일이 있다는 사실만으로 모든 경로가 보호된다고 판단하지 않는다.

### 원격으로 피드백할 때도 검토 대상은 실제 산출물이다

휴대폰이나 메신저로 작업을 요청하는 인터페이스와 작업을 검증하는 하네스는 별개다. 보고서의 가독성이나 첫 요청의 짧은 길이는 결과의 정확성을 입증하지 않는다. Anthropic의 에이전트 패턴은 실행 중 도구 결과로 진행을 확인하고, 검토 지점이나 막힌 상황에서 사람에게 돌아오며, 반복 횟수 같은 종료 조건을 두도록 설명한다(2026-11-04 해당 절 대조).

이를 원격 운영에 적용한 점검 예시는 다음과 같다. 특정 장비나 메신저가 제공하는 기능 보장이 아니다.

- 결과 보고에는 확인할 파일이나 미리보기, 수행한 검사와 미완료 항목을 함께 둔다. 영상의 첫 구간만 검수했다면 전체 영상 검수가 끝났다고 기록하지 않는다.
- 피드백을 반영한 뒤에는 같은 평가 기준으로 다시 확인한다. 피드백 루프는 평가 기준이 명확하고 반복 수정의 개선을 확인할 수 있을 때 쓴다.
- 결과물 수정과 공통 규칙 변경을 나눈다. 한 결과에 대한 선호를 모든 작업의 규칙이나 권한 확대에 자동 적용하지 않고, 재사용할 조건을 별도로 검토한다.

마지막 두 항목의 구체적인 운영 방식은 이 문서의 적용 제안이다. 원격 접속과 재부팅 뒤 세션 유지의 기술 조건은 [[Agent-Always-On-Mac-Host|상시 실행 Mac 에이전트 호스트]]에서 확인한다.

## 성숙도 계단

오른쪽으로 갈수록 시간 투자와 통제력이 함께 오른다. 시간은 발표가 제시한 최초 셋업 기준의 눈대중이다.

| 단계 | 얹는 것 | 최초 투자 | 줄이려는 실패 |
|---|---|---|---|
| Lv.0 | 프롬프트만 | 0분 | 없음 |
| Lv.1 | CLAUDE.md | 5분 | 매번 다시 설명하던 반복 실수 |
| Lv.2 | 검증자 분리 | 30분 | 만든 쪽이 스스로 채점하는 편향 |
| Lv.3 | 훅 검증 | 1시간 | 규칙 망각 |
| Lv.4 | 핸드오프 | 2시간 | 세션이 끊기면 맥락이 사라지는 문제 |
| Lv.5 | 실패 축적 | 지속 | 같은 실패의 재발 |

발표는 Lv.1만으로 반복 실수의 약 30%가 사라진다고 제시하지만 측정 방법이 공개되지 않았으므로, 자기 저장소에서 결함 재발 건수로 다시 확인할 수치로 둔다.

레벨 번호보다 반복 실패를 줄이는 습관이 중요하다. 실패마다 규칙을 누적하기보다 기존 규칙의 충돌, 누락된 근거와 검증 도구 중 무엇을 바꿔야 하는지 판단한다.

## 실무 프로젝트에 얹는 순서

| 순서 | 무엇을 | 왜 |
|---|---|---|
| 1 | 규칙 문서 | 해당 도구가 읽는 위치와 범위에 팀 규칙을 둔다 |
| 2 | 훅 | 지원하는 이벤트에서 검사와 차단을 자동화한다 |
| 3 | 스킬 | 세션 인계와 결정 기록 같은 반복 절차를 한마디로 줄인다 |
| 4 | 검증 에이전트 | 만든 쪽과 검사하는 쪽을 분리한다 |
| 5 | 작업 범위 분리 | 허용 경로와 권한 경계를 정하고 실제 차단 여부를 확인한다 |
| 6 | 그 다음 | 컨텍스트 절약과 명세 도구 같은 고급 부품 |

앞의 성숙도 계단과 이 표의 순서는 어긋난다. 훅은 계단에서 검증자 분리보다 위인데 구축 순서에서는 규칙 문서 바로 다음이다. 발표는 두 목록을 나란히 제시할 뿐 이 차이를 설명하지 않는다. 이 vault의 읽기는 축이 다르다는 것이다. 계단은 시간 투자와 통제력이 얼마나 오르는지를 재고, 이 표는 무엇부터 만들어야 다음 것이 쉬워지는지를 본다.

한 번에 다 하지 않는 게 중요하다. 기본기가 자리 잡기 전에 6번부터 손대면 무엇이 효과를 냈는지 분리되지 않는다. 각 부품의 문법과 예산은 [[Claude-Code-Extension-Reference]], 팀에서 조직으로 확장하는 축은 [[Claude-Code-Workflows]]를 따른다.

참조 구현을 저장소에 얹으면 배치는 대략 이런 모양이 된다.

| 계층 | 위치 | 하는 일 |
|---|---|---|
| 검사 훅 | `.claude/hooks/` | 설정에서 연결한 이벤트의 위험 명령과 파일 접근을 검사한다. 차단 여부는 이벤트와 구현에 달려 있다 |
| 전문 에이전트 | `.claude/agents/` | 리뷰, QA, 보안처럼 역할별로 분리해 위임한다. 커맨드 하나로 한 번에 부를 수 있다 |
| 워크플로 스킬 | `.claude/skills/` | 커밋과 핸드오프 같은 반복 절차를 한마디로 줄인다 |
| 규칙 문서 | 저장소 루트의 지침 파일 | 훅과 에이전트가 참조하는 기준을 둔다 |

발표 시점의 참조 구현 기준으로 강제 훅은 8개, 전문 에이전트는 9종이고, 에이전트는 `/squad` 같은 커맨드로 역할별로 한 번에 호출한다. 훅의 예는 파괴 명령 차단, 비밀 파일 보호, 테스트 실패 시 push 차단이다. 개수는 그 시점의 규모일 뿐이므로 목표치로 삼지 않는다.

## 다섯 단계 파이프라인과 네 게이트

구분선은 도구도 모델도 아니라 중간에 멈춰 확인하는 지점의 개수다. 게이트가 0개면 프롬프트에서 코드로, 코드에서 배포로 곧장 간다. 흔히 바이브 코딩이라 부르는 흐름이고, 작은 실습과 프로토타입까지는 이걸로도 통한다. 문제는 서비스 코드다. 확인 지점이 없으면 실수가 그대로 배포된다. 게이트를 둘 이상 넣어 계획과 검증 뒤에 각각 멈추게 하면 품질이 운에서 예측 가능한 쪽으로 옮겨간다.

완성형 하네스는 단계마다 게이트를 둬서 통과하지 못하면 다음으로 못 가게 한다. 게이트 0개 구조와 정반대다.

| 단계 | 이 단계가 요구하는 것 |
|---|---|
| 조사 | 원자료는 밖에 두고 요약만 가져온다 |
| 계획 | 검증 가능한 문장으로 쓰고 사람이 승인한다 |
| 실행 | 훅 검사가 전부 통과해야 한다 |
| 리뷰 | 정확성과 요구사항 위반이 0건이어야 한다 |
| 배포 | 사람이 증거를 확인한다. 단언만으로는 통과하지 못한다 |

게이트는 단계 사이의 네 전이점이다. 조사에서 계획으로, 계획에서 실행으로, 실행에서 리뷰로, 리뷰에서 배포로 넘어갈 때 각각 걸린다. 다섯 단계에 네 게이트라는 개수는 여기서 나온다. 사람이 승인하는 첫 게이트는 계획을 넘길 때다.

리뷰 게이트에서 취향 문제는 게이트가 아니다. 리뷰어에게 문제를 찾으라고만 시키면 없는 문제도 만들어 오므로, 게이트로 삼는 항목은 정확성과 요구사항 위반으로 좁힌다. 배포 게이트에서 통과 근거는 단언이 아니라 증거다. 테스트 출력, 명령 반환값, 스크린샷이 말하게 한다.

이 구조는 한 사람의 발명이 아니다. 여러 워크플로우 도구가 독립적으로 비슷한 답에 수렴했으므로, 직접 짜기 전에 이미 만들어진 것을 먼저 본다. 발표가 수렴 사례로 든 것은 Superpowers, BMAD, Spec Kit이다. 이 vault에서 각각을 검증한 기록은 아직 없으므로 채택 전에 직접 확인한다.

## 계획을 파일로 남길 때

계획 단계의 산출물을 파일로 두면 리뷰 단계가 그 문장을 그대로 결과와 대조할 수 있다. 쓸모를 만드는 규칙은 다음과 같다.

- 체크박스 한 줄이 검증 한 항목이 되게 쓴다. 잘 되게 해달라 같은 문장은 대조할 수 없다.
- 범위 밖을 미리 적는다. 시키지 않은 수정을 잡아내는 근거가 된다.
- 엣지 케이스는 요구사항과 별도 절로 떼고 각 항목에 테스트를 붙인다. 경계값이나 윈도우 경계처럼 요구사항 문장만으로는 대조되지 않는 것들이 여기 모인다.
- 막막하면 방향을 뒤집어, 나를 인터뷰해서 계획을 완성해 달라고 시킨다.

이때 계획 파일은 산문형 설계 문서가 아니라 대조 가능한 체크리스트여야 한다. [[Context-Engineering]]이 근거 자료로 마크다운 계획서보다 스펙과 테스트 스위트와 루브릭을 권하는 것과 충돌하지 않는 이유가 여기 있다. 대조 가능한 체크박스 목록은 산문형 계획서가 아니라 루브릭 쪽에 가깝다. 실제로 이 파일은 작업이 끝나면 버려지는 채점표이고, 그것을 버리지 않고 쌓으면 골든셋이 된다 → [[Eval-Golden-Set-and-Deploy-Gates]]. 스펙 자체의 작성법은 [[Agent-Spec-Writing]], 계획 승인을 상태 전이로 고정한 조직 사례는 [[AI-Native-Org]]를 본다.

### 장기 작업은 계획의 의존성과 완료 상태를 드러낸다

여러 세션에 걸친 작업에서는 체크리스트에 단계 간 의존성과 완료 근거를 더한다. 다음은 선언형 계획과 실행 피드백을 결합한 설계 제안이다.

- **목표와 제약:** 최종 결과, 공통 계약과 허용 범위를 먼저 적는다.
- **의존성:** API 계약 확정 뒤 화면을 구현하는 것처럼 선행 조건을 표시한다. 독립된 작업만 병렬 실행 후보로 둔다.
- **완료와 승인:** 단계마다 검사 결과와 필요한 사람 승인을 연결한다. 에이전트의 완료 선언만으로 다음 단계로 넘기지 않는다.
- **재개와 중단:** 완료한 단계, 남은 단계와 실패 근거를 보존하고 반복 횟수나 비용 한도에서 멈춘다.

소프트웨어 공장이라는 표현은 이런 목표, 작업과 피드백의 반복을 설명하는 비유로 쓸 수 있다. 표준화된 성숙도 등급이나 많은 에이전트를 동시에 실행한다는 뜻으로 쓰지 않는다. 구조화한 계획이 있어도 실행기에서 의존성, 승인과 한도를 실제로 검사하는지는 별도 확인해야 한다. 실행 그래프의 세부 계약은 [[Agent-Graph-Engineering|그래프 엔지니어링]]에서 다룬다.

### 규칙 준수와 설계 가정의 검증을 나눈다

의존성 검사와 테스트가 통과해도 추상화가 다른 사용 조건에 맞는다는 결론은 나오지 않는다. 특정 데이터베이스를 직접 import하지 않는 공통 계층에도 그 데이터베이스의 동작 가정이 남을 수 있다.

적용 제안: 공통 계층을 확정하기 전에 차이가 있는 실제 사용 사례 두세 개로 작은 구현을 시험한다. 기존 검사에서 통과한 규칙과 새 사례에서 깨진 가정을 따로 기록하고, 가정을 수정한 뒤 회귀 검사에 반영한다. 사례 수는 충분성을 보장하는 통계 기준이 아니라 성급한 일반화를 줄이기 위한 출발점이다.

### 배포 뒤 관측 결과도 다음 작업의 입력으로 삼는다

데모 완성과 운영 중 문제 해결은 다른 검증 범위다. 배포 뒤 오류 로그와 느린 쿼리 같은 관측을 다음 수정 작업의 입력으로 연결한다. 적용 제안: 관측한 증상, 재현 조건, 수정 결과와 배포 뒤 재확인 결과를 이어서 남긴다. 로그를 읽을 수 있다는 사실이 운영 데이터 수정이나 자동 배포 권한까지 부여하지는 않는다.

위 세 절은 2026-10-26 공개 발표의 계획 구조, ORM 설계 경험과 운영 피드백 관점을 바탕으로 정리하고, 2026-11-04 행사 페이지와 로컬 음성 전사문을 대조했다. 실행 피드백과 중단 조건은 Anthropic의 공식 설명도 확인했다. Fractal의 런타임 기능, Prisma의 버전별 지원 범위와 생산성 배수는 검증하지 않았으며 이 제안의 보장으로 사용하지 않는다.

## 그다음 부품 - 코드 지도

기본기가 자리 잡은 뒤 효과가 큰 항목으로 프로젝트 구조 문서가 있다. 진짜 병목은 코드를 짜는 능력보다 어디를 고칠지 찾는 능력이고, 전체를 훑는 대신 개요에서 관련 영역으로, 다시 정확한 파일과 줄로 좁혀 들어가게 만드는 것이 목적이다. 발표는 구조 문서를 하네스에 넣었을 때 계획 품질이 10에서 19%포인트 오르고 토큰이 9에서 13% 줄었다는 2026년 실험(Harness Handbook)을 인용한다. 원 실험의 대상과 측정 방법이 발표 자료에 명시되지 않았으므로 방향만 참고하고 수치는 자기 저장소에서 다시 재는 편이 낫다. 문서를 만드는 대신 도구로 탐색하는 선택지와 그 트레이드오프는 [[Agent-Code-Search]]가 정본이다. 발표는 LSP 계열 심볼 도구 외에 Graft, Headroom, RTK를 예로 드는데, 이 vault에서 검증한 기록이 없으므로 도입 전에 직접 확인할 후보로만 둔다.

## 사례 - 한 사람의 도입 6단계

HashiCorp 공동창업자 Mitchell Hashimoto가 2026년 2월에 공개한 자신의 AI 도입 여정이다.

| 단계 | 내용 |
|---|---|
| 1 | 챗봇 버리기. 파일을 읽고 명령을 실행하는 에이전트로 옮긴다 |
| 2 | 자기 작업 재현. 수동으로 커밋한 것을 에이전트로 다시 만들어 본다 |
| 3 | 퇴근 전 에이전트. 하루의 마지막 30분을 착수 시간으로 블록한다 |
| 4 | 확실한 작업 위임. 확실히 잘할 작업만 넘긴다 |
| 5 | 하네스 엔지니어링. 실수를 발견할 때마다 그 실수가 재발하지 않을 구조를 만든다 |
| 6 | 항상 에이전트 실행 |

읽을 점이 셋이다. 첫째, 2단계 끝까지도 대부분 에이전트를 지켜보는 시간이라 자기가 하는 것보다 느리지는 않지만 빨라진 느낌도 없었다고 본인이 밝힌다. 순 효율 이득을 느끼기 시작한 것은 3단계 끝이고 그것도 아주 조금이라고 적는다. 도입 초반에 효율이 안 나는 것은 정상이며, 그 구간은 어디에 에이전트를 쓰지 말아야 하는지를 배우는 기간이다. 둘째, 6단계는 5단계 다음이 아니라 5단계와 동시에 진행하는 목표다. 셋째, 6단계는 도달점이 아니라 지향이다. 본인도 하루의 10에서 20% 정도라고 적는다.

덧붙이면 하네스 엔지니어링이라는 말 자체를 이 글이 널리 합의된 용어인지 모르겠다면서 자기가 그렇게 부르게 됐다고 소개한다. 같은 시기 OpenAI 쪽에서 제시한 개념 정의와는 별개 경로로 같은 이름에 도달한 셈이다 → [[Harness-Engineering]].

5단계는 반복 실수를 줄이는 규칙이나 검증 도구를 만드는 접근이다. 이를 적용할 때는 규칙 수를 늘리는 것보다 같은 실패의 재발 여부를 확인한다.

## 면접 체크포인트

- 하네스를 계단으로 올리는 이유와, 각 단계가 없애는 실패를 짝지을 수 있는가
- 얹는 순서에서 규칙 문서와 훅이 먼저이고 컨텍스트 최적화가 나중인 이유
- 게이트 개수로 바이브 코딩과 검증된 흐름을 가르는 기준
- 다섯 단계 파이프라인의 네 게이트와, 리뷰 게이트에서 취향을 제외하는 이유
- 계획 파일이 산문이 아니라 대조 가능한 체크리스트여야 하는 이유
- 도입 초반에 생산성 이득이 없는 구간을 어떻게 설명하고 버틸 것인가
