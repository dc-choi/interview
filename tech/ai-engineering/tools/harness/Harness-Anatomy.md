# 하네스 구성도 (Harness Anatomy)

코딩 에이전트는 모델 하나가 아니라 모델과 그것을 감싸는 코드의 합이다. 이 문서는 그 감싸는 코드가 어떤 블록으로 이뤄지고 각 블록이 런타임의 어디에 앉는지를 지도로 둔다. 무엇을 점검할지의 프레임은 [[Harness-Engineering]]의 5축, 어디에 게이트를 걸지는 [[Harness-Gate-Placement]], 얼마나 쌓을지는 [[Harness-Adoption-Ladder]]가 맡는다.

## 모델은 엔진, 하네스는 나머지 차량 전부

| 자동차 부품 | 대응하는 하네스 요소 |
|---|---|
| 엔진 | 모델 - 지능과 동력 |
| 핸들 | 방향 - 프롬프트, 계획, 제약 |
| 브레이크 | 안전 - 권한, 차단 훅, 가드레일 |
| 변속기 | 실행 - 도구 호출과 오케스트레이션 |
| 계기판 | 관찰 - 로그, 상태, 피드백 |

엔진이 좋아도 핸들과 브레이크와 바퀴가 없으면 도로에 나갈 수 없다. 하네스 엔지니어링은 엔진을 개조하는 일이 아니라 차량을 설계하는 일이다.

## 다섯 개의 손잡이

에이전트를 쓸 때 이미 매번 만나는 다섯 가지가 곧 하네스다. 새로 만드는 게 아니라 의도적으로 조정하는 대상이다.

| 요소 | 의미 | Claude Code에서의 접점 |
|---|---|---|
| Tools | 파일 읽기와 명령 실행 | Read, Bash 같은 도구 집합 |
| Knowledge | 규칙과 도메인 지식 | CLAUDE.md, 스킬 |
| Observation | 결과 관찰 | 테스트 출력, 로그 |
| Action | 코드 변경 | Edit, 커밋 |
| Permissions | 안전 경계 | 권한 설정, 훅 |

## 런타임 블록 지도

아래는 발표에서 제시한 구성도를 정리한 것이다. 블록 이름은 이 지도의 표기이고, 기계적 근거가 있는 것은 각 행의 접점 열에 적었다.

| 블록 | 하는 일 | 접점 |
|---|---|---|
| 인터페이스 계층 | 사용자와 CI가 하네스와 만나는 면 | 대화형과 헤드리스가 같은 코어를 쓴다 |
| 컨텍스트 조립 | 이번 턴에 모델이 볼 것을 고른다 | 시스템 프롬프트, CLAUDE.md, 스킬 로딩 |
| 제너레이터 | 모델을 호출해 다음 행동을 만든다 | 하네스에서 유일하게 모델을 부르는 지점 |
| 사전 훅 | 실행 전 검사, 위반이면 차단 | `PreToolUse` |
| 권한 게이트 | 허용, 확인, 금지 판정 | `permissions`와 권한 모드 |
| 도구 실행 | 의도를 실제 행동으로 바꾼다 | 파일시스템, 셸, Git |
| 사후 훅 | 실행 후 포맷과 린트 검사 | `PostToolUse` |
| 이밸류에이터 | 결과가 맞는지 판정하고 실패를 피드백 | 테스트, 채점 스크립트, 검증 서브에이전트 |
| 관찰 기록 | 결과를 다음 턴의 입력으로 되돌린다 | 도구 결과가 대화에 붙는 지점 |

루프 전체를 가로지르는 층이 셋 더 있다.

- **루프 가드**: 최대 턴, 토큰 예산, 같은 도구 호출의 반복 감지, 컴팩션 트리거. 모델의 판단과 별개로 종료를 강제한다. Claude Code의 `--max-turns`는 에이전트 턴 수를 제한하고 한도에 닿으면 오류로 종료하며, 공식 문서 기준 print 모드에서만 적용된다. 루프 설계 자체는 [[Agent-Loop-Engineering]].
- **확장 계층**: MCP 서버, 스킬과 커맨드, 서브에이전트, 플러그인을 꽂는 자리. 문법과 예산은 [[Claude-Code-Extension-Reference]].
- **세션, 상태, 관측성**: resume, 체크포인트와 롤백, 도구 호출 트레이스, 토큰 회계, 감사 로그. 모든 턴을 기록하고 되돌리는 지점.

## 하네스 경계 밖에 있는 것

구성도에서 점선으로 그려지는 세 상자는 하네스가 빌려 쓰거나 하네스를 바깥에서 검증하는 대상이다.

| 바깥 상자 | 관계 |
|---|---|
| 모델 | 제너레이터가 호출하는 대상. Claude API, 다른 벤더 API, 로컬 추론 서버 |
| 실행 환경 | 도구 실행이 닿는 대상. 파일시스템, 셸, Git, 샌드박스 안의 네트워크 |
| 평가 하네스 | 런타임 밖에서 하네스 자체를 회귀 검증. 골든셋과 채점 스크립트 |

여기서 하네스가 팀의 자산이 되는 이유가 나온다. 모델을 갈아 끼우는 일은 제너레이터 한 곳을 바꾸는 일이고, 안쪽 블록은 그대로 남는다. 그 교체가 품질을 떨어뜨렸는지는 평가 하네스가 런타임 밖에서 판정한다 → [[Evaluation-Driven-Development]].

## 겉모습은 넷, 코어는 하나

터미널 TUI, IDE 확장, 헤드리스 실행, SDK와 앱서버는 입구가 다를 뿐 같은 코어로 수렴한다. 코어는 컨텍스트 조립, 에이전트 루프, 평가와 제어 셋이다. 입구와 바깥(모델 API, 샌드박스와 셸, MCP 서버)은 갈아 끼우는 부분이고, 가운데가 팀이 만드는 부분이다. 그래서 한 도구에서 익힌 구조는 도구를 바꿔도 대부분 옮겨간다.

## 제약과 검증이 끼어드는 지점

에이전트 루프 한 바퀴는 다음과 같이 돈다.

1. 모델이 다음 행동을 결정한다.
2. 도구가 필요 없으면 응답하고 루프를 끝낸다.
3. 도구가 필요하면 하네스가 사전 훅, 권한 판정, 실행, 사후 훅 순으로 도구를 실행한다. 순서가 이렇게 되는 이유는 `PreToolUse` 훅이 권한 결정 자체를 돌려줄 수 있기 때문이다.
4. 결과를 모델에 전달하고 1로 돌아간다.

도구를 쓰는 턴에서 제약과 검증이 끼어드는 주된 자리는 3번이다. 다만 3번 하나만 있는 것은 아니다. 도구 호출 없이 끝나는 2번에는 `Stop` 훅이 붙어 완료 선언 자체를 막을 수 있고(→ [[Eval-Rubric-and-Score-Gate]]), 턴 경계에는 위의 루프 가드가 따로 걸린다. 같은 규칙이라도 CLAUDE.md에 문장으로 두면 모델이 기억해야 하는 대상이지만, 3번의 훅에 두면 루프가 돌 때마다 코드가 검사한다. 이 차이가 요청과 강제를 가른다. 어느 규칙을 어느 층에 둘지의 판별 기준은 [[Harness-Gate-Placement]]가 정본이고, 배경 논의는 [[AI-Native-System]]의 부탁 대 강제와 [[Context-Engineering]]의 Advisory와 강제 검증에 있다.

## 세 기둥

| 기둥 | 묻는 질문 | 수단 |
|---|---|---|
| 제약(Constraints) | 무엇을 못 하게 할까 | CLAUDE.md 규칙, 도구 권한 제한, 린터와 구조 테스트 |
| 피드백 루프(Feedback) | 실수를 어떻게 잡을까 | 자기 리뷰(약), 독립 리뷰어(중), 자동 검증(강) |
| 상태 관리(State) | 맥락을 어떻게 유지할까 | 파일 핸드오프, 컨텍스트 리셋, 서브에이전트 격리 |

제약은 사고를 일어나기 전에 막고, 피드백 루프는 이미 저지른 실수를 배포 전에 잡고, 상태 관리는 세션이 끊겨도 맥락이 이어지게 한다. 피드백은 약에서 강으로 갈수록 믿을 수 있는데, 자기가 만든 코드의 빈틈은 만든 쪽 눈에 잘 안 보이기 때문이다.

여기서 분리의 축은 모델이 아니라 컨텍스트라는 점이 중요하다. 같은 모델이라도 컨텍스트가 다르면 서로의 버그를 찾아낸다. 그래서 검사하는 쪽은 별도 컨텍스트에서 돌리고 수정 권한을 주지 않는다. 이 분리의 근거와 역효과 사례는 [[Agent-Test-Verification-Behavior]].

## 면접 체크포인트

- 에이전트를 모델과 하네스의 합으로 분해하고, 하네스 안쪽 블록과 바깥 상자를 구분할 수 있는가
- 모델 교체가 왜 제너레이터 한 곳의 변경인지, 그 교체를 무엇이 검증하는지
- 제약과 검증이 루프의 어느 단계에 끼어드는지, 그래서 왜 문장보다 훅이 센지
- 루프 가드가 모델 판단과 별개로 존재해야 하는 이유
- 세 기둥 중 자기 팀에 비어 있는 기둥을 지목할 수 있는가
