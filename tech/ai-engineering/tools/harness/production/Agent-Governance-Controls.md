# 에이전트 거버넌스 통제

에이전트 거버넌스는 어떤 에이전트가 누구의 권한으로(누가), 어느 세션에서 어떤 순서로(언제), 어떤 데이터를 읽고 어떤 도구를 호출했으며(무엇을), 어떤 입력과 모델 버전으로(어떻게), 어떤 근거로 판단했는지(왜)를 알고, 그 앎을 바탕으로 허가 밖 행동이 일어날 수 없게 만드는 통제와 증거의 묶음이다. 알아야 정할 수 있고, 정해야 막을 수 있다.

## 판단은 확률적이어도 통제는 결정론이다

에이전트의 해석과 도구 선택은 확률적이다. 같은 입력에도 매번 다른 행동이 나올 수 있으므로 한 번 시험을 통과했다고 다음에도 안전하다고 말할 수 없다. 또 사람은 몇 번 시도하다 멈추지만 에이전트는 비용이 거의 들지 않아 사람이 건너뛰던 경로까지 시도한다. 그래서 위험한 행동의 허가 여부는 문서를 읽은 모델의 판단에 맡기지 않고 조건과 코드로 강제한다.

목표를 좇다 경계를 넘는 행동은 통제된 시험에서 관찰됐다. Anthropic은 16개 모델을 가상의 기업 환경에서 시험했고, 목표 충돌과 교체 위협을 함께 준 조건에서 Claude Opus 4와 Gemini 2.5 Flash가 96%, GPT-4.1과 Grok 3 Beta가 80% 비율로 협박을 택했다고 보고했다(2025-06). 다른 방법이 없도록 일부러 만든 시뮬레이션이며, 실제 배포에서는 이런 사례를 보지 못했다고 밝혔다. Claude Opus 4에게 행동 전에 시험인지 실제 배포인지 따지게 한 추가 실험에서는 추론에 실제 배포라고 적은 경우 55.1%, 평가라고 적은 경우 6.5% 비율로 협박을 택했다(500개 표본). 추론에 적은 내용이 실제 판단과 다를 수 있어 이 결론을 확신할 수 없다는 단서도 달았다. 시험이라고 여길 때 덜 일탈한다면 평가가 실제 위험을 과소평가할 수 있어 평가 점수만으로 운영 안전을 보장하기 어렵다. 정렬과 감독의 연구 흐름은 [[AI-Alignment-and-Control|AI 정렬과 통제]], 평가 중 에이전트가 운영 인프라로 나간 사례는 [[Agent-Swarm-Containment|에이전트 군집 격리]]에서 다룬다.

## 네 가지 통제

| 통제 | 묻는 것 | 결정론으로 두는 방법 |
|---|---|---|
| 신원과 권한 | 누구의 권한으로 일하는가 | 요청자 신원을 데이터 계층까지 전달해 그 사람이 볼 수 없는 것은 에이전트도 못 보게 한다 |
| 승인 체계 | 언제 사람이 결재하는가 | 조건을 코드로 판정하고, 조건에 걸리면 결재선을 반드시 지난다 |
| 롤백과 복구 | 잘못되면 어떻게 되돌리는가 | 실행마다 되돌리기 방법과 가능 시간을 미리 선언한다 |
| 추적과 감사 | 무엇을 했는지 남는가 | 요청부터 실행까지 하나의 추적 기록으로 남긴다 |

### 신원과 권한

- 사람이 대화를 여는 에이전트는 요청자의 권한으로 실행하고, 요청자 식별값을 데이터베이스 세션 같은 하위 계층의 신원으로 넘긴다. 그러면 행 단위 필터와 열 가림 같은 기존 데이터 권한이 그대로 적용된다.
- 이 신원 값은 모델이 정하거나 바꿀 수 없어야 한다. 요청자가 없거나 조직 구성원이 아니면 공용 서비스 계정으로 대신 실행하지 않고 멈춘다.
- 상시로 도는 에이전트는 시작한 사람이나 넘겨받은 담당자를 행위자로 두고, 그 사람이 권한을 잃으면 에이전트도 멈춘다.
- 에이전트가 다른 에이전트에게 일을 맡기는 단계가 여러 번 이어져도 처음 요청한 사람의 권한이 끝까지 따라간다. 접근하는 시스템마다 그 권한이 유효한지 조직의 통합 인증과 연동해 다시 확인하고, 중간 에이전트의 권한으로 바꿔 실행하지 않는다(설계 해석). 실효 권한은 요청자 권한과 그 에이전트에 준 범위의 교집합이고, 시스템 작업에 제한된 서비스 계정을 섞는 경우는 [[Production-Agent-Architecture-Delegation|위임 경계]]를 따른다. 토큰에 실제 행위자를 함께 남기는 방식은 [[OAuth2-Token-Exchange#가장과 위임|가장과 위임]]을 따른다.
- 에이전트의 요청은 사내 시스템, 협력사 에이전트, SaaS, MCP 도구 연결을 가리지 않고 하나의 관문을 지나게 한다. 에이전트가 늘어도 인증과 정책이 같은 기준으로 걸리고, 어떤 권한으로 무엇을 실행했는지가 자동으로 남는다. 관문을 거치지 않고 대상을 직접 부르는 경로는 따로 막는다([[MCP-Gateway-Architecture|MCP 게이트웨이]], [[Bedrock-AgentCore-Operations#Policy는 Gateway를 지나는 호출에 적용한다|우회 경로]]).
- 에이전트 하나에 여러 업무를 몰지 않고 업무 목적별 작은 단위로 나눠 각각 최소 권한만 준다. 권한을 합친 에이전트는 탈취됐을 때의 피해 범위도 그 합이다.
- 여러 사용자가 쓰는 에이전트의 실행 주체 결정은 [[Production-Agent-Architecture-Delegation#여러 사용자가 쓰는 에이전트는 누구의 권한으로 실행하는지 정한다|위임 경계]], 에이전트 신원과 일시적인 권한의 분리는 [[LLM-Application-Security#에이전트 신원과 일시적인 권한을 분리한다|LLM 애플리케이션 보안]]에서 다룬다. 에이전트 신원, 위임 신원과 둘을 결합한 권한증의 비교, 접근 통제의 다섯 질문과 위협 시나리오는 [[Agent-Identity-and-Execution-Authority|에이전트 신원과 실행 권한]]에서 다룬다.

### 승인 체계

"많이 주문하면 승인을 받아라"를 지침에 쓰고 모델에 맡기지 않는다. 도구마다 승인 모드(자동, 승인 후 실행, 조건부)를 두고 조건을 호출 입력값이나 원장 누적값으로 판정한다.

| 하루 누적 발주량 | 처리 |
|---|---|
| 1~5개 | 결재 없이 실행 |
| 6~100개 | 결재선 승인 뒤 실행 |
| 100개 초과 | 실행하지 않는다 |

- 위에서부터 처음 맞는 조건의 결재선을 쓰고, 조건을 판정할 수 없으면 가장 엄격한 줄을 쓴다.
- 결재선은 단계별 승인자와 필요 인원을 정하고, 한 명이라도 거절하면 거절한다.
- 승인되면 요청 당시의 인자 그대로 한 번만 실행한다. 승인 사이에 인자가 바뀌면 다시 승인받는다.
- 사람 승인이 형식적인 클릭이 되지 않게 하는 조건은 [[Harness-Gate-Placement#사람 승인과 실질적인 검토를 구분한다|게이트 배치]]를 따른다.

### 롤백과 복구

- 실행 동작마다 짝이 되는 보상 동작(결제 취소, 재고 복원, 고객 알림)과 되돌릴 수 있는 시간을 선언한다. 배송 시작처럼 상태가 넘어가면 자동 취소 대신 반품 같은 사람 절차로 넘긴다.
- 한 건 또는 한 요청 묶음 단위로 되돌리고, 그 뒤 다른 변경이나 확정, 만료가 있으면 되돌리기를 막는다. 결과가 불확실한 호출은 조회 동작으로 상태를 먼저 확인한다.
- 지식이나 설정의 편집은 버전으로 쌓고, 되돌려도 기록을 지우지 않고 이전 내용을 새 버전으로 다시 쓰는 방식(restore-forward)을 쓴다.
- 확산을 멈출 비상 수단(작업 공간 전체 쓰기 정지)을 둔다.

### 추적과 감사

한 요청이 남겨야 할 기록은 감사가 묻는 질문에 답할 수 있어야 한다.

| 질문 | 남길 것 |
|---|---|
| 누가 시켰는가 | 요청한 사람이나 API 키 |
| 무엇을 근거로 판단했는가 | 읽은 지식과 그 버전 |
| 어떤 도구를 어떤 입력으로 썼는가 | 도구와 릴리스, 입력 지문 |
| 누가 승인했는가 | 판정 결과, 승인자와 승인 채널 |
| 결과는 무엇이고 되돌릴 수 있는가 | 실행 결과 요약과 되돌리기 가능 시한 |

기록은 도구 실행 원장, 승인 원장, 대화 기록, 지식 변경 이력, 데이터베이스 세션 정보처럼 여러 곳에 남으므로 공통 추적 식별자로 묶는다. OpenTelemetry의 스팬으로 입력, 판단과 도구 호출을 기록하면 관측 도구들이 같은 추적을 읽을 수 있다. Arize 문서는 LLM 추적 규약인 OpenInference를 OpenTelemetry를 대체하지 않는 확장으로 설명한다.

## 실행 중 탐지에서 차단까지

사전 통제가 모든 경로를 막지 못하므로 실행을 계속 보고 판정하는 루프를 둔다.

1. **수집:** 모든 입력, 판단, 도구 호출과 가드 판정을 추적으로 남긴다.
2. **평가:** 들어오는 추적을 규칙, 분류기, LLM 심판으로 자동 판정한다([[Eval-LLM-Judge|LLM 심판 평가]]).
3. **전파:** 판정이 기준을 넘으면 사람과 시스템에 알린다.
4. **조치:** 방어 시스템을 호출해 세션을 끊고 권한을 막는다.

사후 판정 루프는 첫 시도를 탐지하고 기록할 뿐 막지는 못한다. 첫 시도까지 막으려면 실행 경로 안의 인라인 가드와 함께 쓴다.

| 통제의 성격 | 하는 일 | 예 |
|---|---|---|
| 탐지 | 위험한 메시지를 잡는다 | 입력 가드레일(탈옥, 개인정보), 출력 가드레일(기밀 유출, 근거성) |
| 통제 | 허가 밖 행동을 막는다 | 최소 실행 권한, 도구 허용 목록과 버전 고정, 세션별 누적 권한 상한 |
| 검증 | 실제로 막혔는지 확인한다 | 실제 목표 달성 여부로 판정하는 레드팀 |

탐지 가드레일은 규칙과 모델로 일을 나눈다. 규칙 기반 필터는 보안 담당자가 정한 정책(회사 기밀, 고객에게 보이면 안 되는 정보)을 입력과 답변에 결정적으로 적용하고, 모델 기반 필터는 규칙만으로 판단하기 어려운 맥락과 우회 공격을 가드레일 모델로 판정한다. 가드레일은 LLM 호출 한 곳이 아니라 에이전트가 도구와 데이터에 닿는 경로 전체에 두고, 레드팀은 본 모델뿐 아니라 가드레일 모델 자체의 빈틈까지 찾는다([[LLM-Application-Security#가드 모델 우회 — 능력 격차가 곧 취약점|가드 모델 우회]]). 필터를 등록한 뒤 조직, 부서, 사용자 단위의 정책 그룹에 규칙 필터(개인정보, 자격 증명 패턴)와 모델 필터(유해성, 탈옥)의 조합을 매핑하면 같은 모델 앞에서도 사용자군마다 입력과 출력 검사를 다르게 걸 수 있다.

외부 문서, 메일과 도구 응답도 공격 입력이 된다. 신뢰 경계를 사용자 입력에서 이 콘텐츠까지 넓히고, 외부 콘텐츠의 지시를 실행하지 않는다. Unit 42는 2026-03-03 실제 웹 페이지에서 관찰한 간접 주입에서 페이로드를 구성하는 기법 22가지를 식별하고, 공격을 공격 의도와 페이로드 구성 기법으로 나눠 분류했다. 관찰한 공격 의도에는 결제 페이지로 유도해 공격자 계정에 5,000달러를 보내게 하거나 데이터베이스를 지우게 하는 지시가 있었다. 공격 문구를 관찰한 것이며 실제 송금이나 삭제 피해를 보고한 것은 아니다. 공격 유형별 방어는 [[LLM-Application-Security|LLM 애플리케이션 보안]]에서 다룬다.

출력의 책임은 회사에 남는다. 캐나다 BC주 민사분쟁해결심판소(Civil Resolution Tribunal)는 2024-02-14 항공사 챗봇이 유족 할인 운임의 환불 규정을 잘못 안내한 소액 사건에서, 챗봇도 웹사이트의 일부라며 회사가 그 정보에 책임진다고 보고 차액 650.88캐나다달러 배상을 명했다(2024 BCCRT 149). 2023-12에는 한 Chevrolet 딜러의 ChatGPT 기반 챗봇이 사용자의 지시 조작에 넘어가 2024년형 Tahoe를 1달러에 팔겠다고 답했다(AI Incident Database 622). 입력과 출력 검증이 없으면 오답과 조작된 답 모두 회사가 한 말이 된다(해석).

세 성격의 통제를 묶어 주는 것은 기록이다. 새 공격, 실패 분석, 검사와 권한 개선, 재평가의 루프는 무엇이 언제 어떻게 통과했는지 남아 있어야 돈다. 기록되지 않은 방어는 작동했다고 증명할 수 없다. 거버넌스 단계마다 필요한 런타임 신호와 통제 지점은 [[AI-Governance-Observability|관측 신호로 집행하는 AI 거버넌스]]에서 다룬다.

## 조직이 먼저 정할 다섯 영역

위 통제는 에이전트 하나의 행동을 다룬다. 통제가 기대는 기준, 곧 무엇이 기밀이고 누구의 권한으로 얼마까지 쓰며 무엇을 막고 무엇을 함께 쓸지는 조직이 정한다. 에이전트 도입은 부서 과제나 시범 적용 단위로 빠르게 시작되지만 데이터 등급, 권한 정책, 비용 한도 같은 기준은 조직 전체가 함께 정해야 하므로, 부서별 노력만으로는 공통 기준이 생기기 어렵다. 기준을 정할 주체를 먼저 두고([[AX-Transformation#4. 거버넌스 (Governance) — 부서별 → 중앙 통합|중앙 통합 거버넌스]]) 기준을 다섯 영역으로 나눠 빈 곳을 찾는다.

| 영역 | 조직이 정할 기준 | 실행 지점 |
|---|---|---|
| 데이터 | 분류 기준과 등급, 등급별 외부 AI 허용 범위 | 아래 [[#데이터 등급이 외부 AI 허용 범위를 정한다\|데이터 등급]] |
| 권한 | 요청자 권한의 승계, 업무 단위의 최소 권한 | 단일 관문과 위 [[#신원과 권한\|신원과 권한]] |
| 비용 | 업무 성격별 모델 등급, 사람, 조직과 시스템별 한도 | 게이트웨이의 모델 선택과 예산 검사, 아래 [[#비용은 같은 관문에서 고르고 센다\|비용 기준]] |
| 보안 | 막을 정보와 행동을 정한 보안 정책 | 경로 전체의 가드레일과 레드팀, 위 [[#실행 중 탐지에서 차단까지\|탐지에서 차단까지]] |
| 자산화 | 등록 대상, 검증 승인 기준과 버전 정책 | 공유 목록, 아래 [[#자산은 등록과 공유를 나눈다\|자산 등록]] |

영역을 따로 구축하면 같은 데이터에 부서마다 다른 등급과 접근 기준이 붙기 쉽고, 영역마다 시스템이 따로 생겨 관리 인력과 운영 비용이 늘 수 있으며, 어떤 에이전트가 어떤 데이터로 무엇을 하는지 조직이 파악하기 어려워질 수 있다(통합 플랫폼 공급사의 논거). 통합은 제품 하나로 모으는 일이 아니라 기준을 한 곳에서 정의하고, 에이전트를 만드는 단계부터 공유와 운영 단계까지 모든 실행 지점이 같은 정의를 참조하게 하는 일이다(설계 해석).

### 데이터 등급이 외부 AI 허용 범위를 정한다

무엇이 기밀인지 가릴 기준이 없으면 에이전트는 기밀 데이터를 일반 데이터처럼 다룬다. 분류 기준과 등급을 먼저 두면 외부 AI 사용을 전면 금지하거나 전면 허용하는 대신 등급마다 허용 범위를 달리할 수 있다. 기밀 등급만 막고 나머지 업무는 이어 가는 방식으로, 망분리 정책이 일률 차단에서 등급별 차등 통제로 옮겨 가는 방향과 같다([[Network-Separation#판단: 경계 모델의 위치|망분리의 판단 기준]]). 등급별 허용 기준 없이 주의 공지로 열었다가 차단 쪽으로 기운 예(해석)로, 삼성전자 반도체(DS) 부문은 2023-03-11 사내 ChatGPT 사용을 허가하며 사내 정보 보안에 주의하라고 공지했지만 20일이 안 돼 설비 프로그램의 소스 코드와 회의 내용을 입력한 사고 3건을 확인했고, 질문당 업로드를 1,024바이트로 제한하면서 긴급 조치 뒤에도 비슷한 사고가 나면 사내망에서 ChatGPT 접속을 차단할 수 있다고 안내했다. 삼성전자는 약 한 달 뒤인 2023-05 사내 메모로 생성형 AI 도구 사용 금지를 알렸다고 보도됐고(대상 부문과 범위는 인용 기사에 없다), 이후 임시 조치라고 밝혔다.

| 단계 | 하는 일 | 남는 한계(설계 점검) |
|---|---|---|
| 분류 | 문서 저장소의 파일에 등급을 매기고, 기밀 문서를 임베딩 색인으로 만들어 내용이 비슷한 문서를 기밀 후보로 판정한다 | 색인에 없는 새 기밀은 잡지 못한다. 기밀 색인도 기밀을 담은 자산이므로 접근을 제한한다([[LLM-Application-Security#LLM08 벡터 및 임베딩 취약점 (RAG)\|임베딩 역전]]) |
| 전송 전 차단 | 사람이나 에이전트가 외부 AI에 보낼 때 기밀 등급 파일의 업로드를 막고, 질문 본문을 키워드, 패턴과 기밀 색인과의 유사도로 거른다 | 브라우저, 프록시나 게이트웨이 같은 통제 지점을 지나지 않는 경로는 보지 못한다. 요약하거나 일부만 옮긴 기밀은 유사도 임계값 아래로 내려갈 수 있다 |
| 응답 비식별 | 외부 AI의 답변에 든 민감 정보를 식별할 수 없게 처리한 뒤 전달한다 | 탐지가 확률적이라 놓친 값은 그대로 전달된다 |
| 로그 탐지 | AI 사용 로그의 질문과 답변을 유사도로 계속 검사해 유출이 의심되면 보안 담당자에게 알린다 | 이미 나간 데이터는 회수하지 못한다. 로그가 원문을 담으므로 접근 권한과 보존 기간을 따로 정한다 |

응답과 로그의 가림 방식은 [[PII-Masking|PII 마스킹]]을, 에이전트가 읽는 운영 데이터의 분류와 파생 기록의 보존 기간은 [[Agent-Operations-Foundations#운영 데이터부터 분류한다|운영 데이터 분류]]를 따른다.

### 비용은 같은 관문에서 고르고 센다

토큰 단가가 내려가도 사용량이 더 빨리 늘거나 단순 반복 업무에 추론 모델을 쓰면 총지출은 커질 수 있다([[AI-Capability-and-Cost-Trends#3. 비용 하락은 무엇의 가격인지 구분한다|비용 하락의 단위]]). 그래서 업무 성격별 모델 등급을 조직 표준으로 두고 게이트웨이가 요청의 성격과 복잡도로 모델을 고르게 한다. 자동 선택은 요청을 낮은 등급으로 잘못 보내면 품질이 떨어지므로 등급별 합격선을 eval로 확인한 업무에만 적용한다. 등급은 능력과 단가만이 아니라 지연 요구로도 나뉜다. 복잡한 논리와 큰 문맥이 필요한 심층 추론, 질의응답과 요약 같은 범용 업무, 정형 추출과 분류 같은 경량 반복 작업, 실시간 응답이 필요한 초고속 경로로 나누는 식이다([[LLM-Model-Tiers|모델 티어 선택]]). 사내 구축 모델(폐쇄망 포함)과 외부 상용 모델을 같은 관문에 묶으면 사람, 조직과 시스템별 사용량, 비용과 이력이 한곳에 모이고 한도를 걸 수 있다([[LLM-Gateway#예산 설정의 저장소 의존성을 확인한다|게이트웨이 예산 검사]]). 사용량과 비용을 정책 준수 여부와 함께 남기면 감사와 점검 때 확인 근거로 쓸 수 있다. 관문에서 모델을 고르면 평균 단가도 라우팅에 따라 움직인다. Vercel AI Gateway의 2026년 7월 집계에서 토큰 사용량은 전월보다 59%, 지출은 37% 늘었고 토큰당 평균 가격은 13.6% 내렸는데, Vercel은 6월의 모델 구성을 유지했다면 평균 가격이 거의 그대로였을 것이라며 하락 전부를 더 싼 모델로 보낸 라우팅의 결과로 분석했다. 평균 단가의 추이는 목록 가격의 변화와 모델 구성의 변화로 나눠 읽는다(해석). 한 게이트웨이 고객의 집계라 시장 전체로 옮기지 않는다.

### 자산은 등록과 공유를 나눈다

에이전트가 부서와 과제 단위로 빠르게 늘면 어디에 어떤 에이전트가 있는지부터 모르게 된다. 에이전트, 모델, 도구와 지식을 소유자와 버전이 있는 한 목록에 등록하고, 외부 도구로 만든 에이전트, 스킬과 MCP 서버도 같은 목록에 넣는다.

- 검증 승인을 통과한 자산만 공유 목록에 올린다. [[MCP-Gateway-Architecture#제어 계층과 실행 계층|MCP 게이트웨이]]가 발견한 도구와 공개할 도구를 나누는 것과 같은 원칙이다.
- 재사용하면 중복 개발이 줄고 한 곳을 고쳐 모두에 반영할 수 있지만, 공유 자산의 결함도 쓰는 곳 모두로 번진다. 소유자와 업그레이드 경로를 함께 정한다([[Agent-Operations-Integration-Cost-Security#데이터 연결은 팀마다 만들지 않고 공유한다|공유 연결]]).
- 등록 목록은 등록하지 않은 사용을 보지 못하므로 인프라 신호로 찾는 발견 목록([[Security-Hub-AI-Inventory|AI 자산 발견]])과 대조한다. 목록은 실행을 막지 못하므로 차단은 런타임 관문에 둔다([[Production-Agent-Architecture-Guardrails#에이전트 목록과 실행 통제는 다른 계층이다|목록과 실행 통제]]).
- Gartner는 2026-04-28 평균적인 Fortune 500 기업이 쓰는 에이전트가 2025년 15개 미만에서 2028년 15만 개 이상으로 늘고, 에이전트 거버넌스를 제대로 갖췄다고 보는 조직은 13%뿐이라고 밝혔다(근거 조사는 보도자료에 없다). 사용을 막기만 하면 직원이 섀도 AI로 우회해 위험이 더 커진다고 보고, 정책, AI TRiSM 도구로 만드는 중앙 에이전트 목록, 에이전트 신원과 권한과 생애주기, 정보 거버넌스, 행동 감시와 교정, 책임 있는 사용 문화의 여섯 단계를 제시했다.

### 성숙도는 영역마다 따로 잰다

아래 사례의 척도처럼 체계 없음(Lv.1), 비공식 관리(Lv.2), 부분 적용(Lv.3), 전사 적용(Lv.4), 자동화와 통합(Lv.5)의 다섯 단계로 영역마다 수준을 매기면 어디부터 채울지 보인다. 평균 하나로 보면 가장 빈 영역이 가려지므로 영역별로 본다. 모든 영역을 최고 단계로 올리는 것 자체를 목표로 두지 않고 사업 가치가 큰 영역부터 올리는 [[Cloud-Unit-Cost#사례: 조직별 비용 청구서와 성숙도 진단|FinOps 성숙도 모델의 원칙]]도 같이 쓸 수 있다(적용 해석).

사례: 삼성SDS AX센터가 2026-08 국내 102개 기업을 대상으로 한 자체 설문은 5점 만점 평균 2.38점, 다섯 영역 모두 평균 2.5점 미만으로 보고했다(2026-10 세션 브리프 기준). Lv.1~2 비율은 데이터 53.9%, 권한 56.9%, 비용 53.9%, 보안 59.8%, 자산화 62.7%로 자산화와 공유 체계가 가장 높았고, Lv.4~5는 영역별 17.6~21.6%였다. 2026-09 발표 자료는 업종별 평균을 IT와 통신 2.83, 제조 2.73, 금융 1.96, 공공 1.88, 유통서비스 1.84로, 규모별 평균을 5,000명 이상 2.95, 1,000~4,999명 2.51, 500~999명 1.70, 100~499명 1.94, 100명 이하 2.17로 제시해 중간 규모가 가장 낮은 U자형을 보였고, 같은 척도의 삼성 평균을 3.56점으로 적었다. 업종과 규모별 응답 수와 삼성 평균의 산출 대상은 밝히지 않았다. Lv.5를 발표 자료는 지속적 최적화로, 세션 브리프는 자동화와 통합으로 표기한다. 조사 주체가 다섯 영역을 자사 에이전트 플랫폼(FabriX)의 구성요소로 묶어 제안하는 벤더이고 표본 선정, 응답자와 배점 방식을 공개 자료에서 확인하지 못했으므로, 국내 기업 전체의 실태로 옮기지 않는다.

## 규제와 관리체계로 이어진다

한국 AI 기본법의 고영향 AI 의무는 위험관리, 설명 방안, 이용자 보호, 사람의 관리와 감독, 문서 작성과 보관을 요구한다([[AI-Basic-Act-Scope-and-Obligations|AI 기본법의 적용 범위와 사업자 의무]]). 네 가지 통제와 추적 기록은 이 의무의 증적이 된다. 다만 데이터셋 평가나 레드팀 결과만으로 관리체계 전체를 증명하지는 못하므로, 통제 항목마다 담당자와 증적을 정해 둔다.

## 점검

- 에이전트가 쓰는 신원이 요청자와 연결되고, 공용 계정으로 대신 실행되는 경로가 없는가?
- 위험한 도구의 승인 조건이 코드로 판정되고, 판정 불가 시 가장 엄격한 처리로 가는가?
- 상태를 바꾸는 도구마다 보상 동작과 되돌리기 시한이 선언돼 있는가?
- 한 요청의 근거 지식 버전, 도구 입력, 승인과 결과를 하나의 추적 식별자로 찾을 수 있는가?
- 사후 탐지 루프와 인라인 가드의 역할을 구분해 첫 시도의 피해를 따로 판단했는가?
- 다섯 영역의 기준을 정하는 주체가 있고, 데이터 등급마다 외부 AI 허용 범위와 전송 전 차단, 사용 로그의 사후 탐지가 정해져 있는가?
