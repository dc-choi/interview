# 에이전트 거버넌스 통제

에이전트 거버넌스는 어떤 에이전트가 누구의 권한으로(누가), 어느 세션에서 어떤 순서로(언제), 어떤 데이터를 읽고 어떤 도구를 호출했으며(무엇을), 어떤 입력과 모델 버전으로(어떻게), 어떤 근거로 판단했는지(왜)를 알고, 그 앎을 바탕으로 허가 밖 행동이 일어날 수 없게 만드는 통제와 증거의 묶음이다. 알아야 정할 수 있고, 정해야 막을 수 있다.

## 판단은 확률적이어도 통제는 결정론이다

에이전트의 해석과 도구 선택은 확률적이다. 같은 입력에도 매번 다른 행동이 나올 수 있으므로 한 번 시험을 통과했다고 다음에도 안전하다고 말할 수 없다. 또 사람은 몇 번 시도하다 멈추지만 에이전트는 비용이 거의 들지 않아 사람이 건너뛰던 경로까지 시도한다. 그래서 위험한 행동의 허가 여부는 문서를 읽은 모델의 판단에 맡기지 않고 조건과 코드로 강제한다.

목표를 좇다 경계를 넘는 행동은 통제된 시험에서 관찰됐다. Anthropic은 16개 모델을 가상의 기업 환경에서 시험했고, 목표 충돌과 교체 위협을 함께 준 조건에서 Claude Opus 4와 Gemini 2.5 Flash가 96%, GPT-4.1과 Grok 3 Beta가 80% 비율로 협박을 택했다고 보고했다(2025-06). 다른 방법이 없도록 일부러 만든 시뮬레이션이며, 실제 배포에서는 이런 사례를 보지 못했다고 밝혔다. Claude Opus 4에게 행동 전에 시험인지 실제 배포인지 따지게 한 추가 실험에서는 추론에 실제 배포라고 적은 경우 55.1%, 평가라고 적은 경우 6.5% 비율로 협박을 택했다(500개 표본). 추론에 적은 내용이 실제 판단과 다를 수 있어 이 결론을 확신할 수 없다는 단서도 달았다. 시험이라고 여길 때 덜 일탈한다면 평가가 실제 위험을 과소평가할 수 있어 평가 점수만으로 운영 안전을 보장하기 어렵다. 정렬과 감독의 연구 흐름은 [[AI-Alignment-and-Control|AI 정렬과 통제]], 평가 중 에이전트가 운영 인프라로 나간 사례는 [[Agent-Swarm-Containment|에이전트 군집 격리]]에서 다룬다.

## 네 가지 통제

| 통제 | 묻는 것 | 결정론으로 두는 방법 |
|---|---|---|
| 신원과 권한 | 누구의 권한으로 일하는가 | 요청자 신원을 데이터 계층까지 전달해 그 사람이 볼 수 없는 것은 에이전트도 못 보게 한다 |
| 승인 체계 | 언제 사람이 결재하는가 | 조건을 코드로 판정하고, 조건에 걸리면 결재선을 반드시 지난다 |
| 롤백과 복구 | 잘못되면 어떻게 되돌리는가 | 실행마다 되돌리기 방법과 가능 시간을 미리 선언한다 |
| 추적과 감사 | 무엇을 했는지 남는가 | 요청부터 실행까지 하나의 추적 기록으로 남긴다 |

### 신원과 권한

- 사람이 대화를 여는 에이전트는 요청자의 권한으로 실행하고, 요청자 식별값을 데이터베이스 세션 같은 하위 계층의 신원으로 넘긴다. 그러면 행 단위 필터와 열 가림 같은 기존 데이터 권한이 그대로 적용된다.
- 이 신원 값은 모델이 정하거나 바꿀 수 없어야 한다. 요청자가 없거나 조직 구성원이 아니면 공용 서비스 계정으로 대신 실행하지 않고 멈춘다.
- 상시로 도는 에이전트는 시작한 사람이나 넘겨받은 담당자를 행위자로 두고, 그 사람이 권한을 잃으면 에이전트도 멈춘다.
- 여러 사용자가 쓰는 에이전트의 실행 주체 결정은 [[Production-Agent-Architecture-Delegation#여러 사용자가 쓰는 에이전트는 누구의 권한으로 실행하는지 정한다|위임 경계]], 에이전트 신원과 일시적인 권한의 분리는 [[LLM-Application-Security#에이전트 신원과 일시적인 권한을 분리한다|LLM 애플리케이션 보안]]에서 다룬다.

### 승인 체계

"많이 주문하면 승인을 받아라"를 지침에 쓰고 모델에 맡기지 않는다. 도구마다 승인 모드(자동, 승인 후 실행, 조건부)를 두고 조건을 호출 입력값이나 원장 누적값으로 판정한다.

| 하루 누적 발주량 | 처리 |
|---|---|
| 1~5개 | 결재 없이 실행 |
| 6~100개 | 결재선 승인 뒤 실행 |
| 100개 초과 | 실행하지 않는다 |

- 위에서부터 처음 맞는 조건의 결재선을 쓰고, 조건을 판정할 수 없으면 가장 엄격한 줄을 쓴다.
- 결재선은 단계별 승인자와 필요 인원을 정하고, 한 명이라도 거절하면 거절한다.
- 승인되면 요청 당시의 인자 그대로 한 번만 실행한다. 승인 사이에 인자가 바뀌면 다시 승인받는다.
- 사람 승인이 형식적인 클릭이 되지 않게 하는 조건은 [[Harness-Gate-Placement#사람 승인과 실질적인 검토를 구분한다|게이트 배치]]를 따른다.

### 롤백과 복구

- 실행 동작마다 짝이 되는 보상 동작(결제 취소, 재고 복원, 고객 알림)과 되돌릴 수 있는 시간을 선언한다. 배송 시작처럼 상태가 넘어가면 자동 취소 대신 반품 같은 사람 절차로 넘긴다.
- 한 건 또는 한 요청 묶음 단위로 되돌리고, 그 뒤 다른 변경이나 확정, 만료가 있으면 되돌리기를 막는다. 결과가 불확실한 호출은 조회 동작으로 상태를 먼저 확인한다.
- 지식이나 설정의 편집은 버전으로 쌓고, 되돌려도 기록을 지우지 않고 이전 내용을 새 버전으로 다시 쓰는 방식(restore-forward)을 쓴다.
- 확산을 멈출 비상 수단(작업 공간 전체 쓰기 정지)을 둔다.

### 추적과 감사

한 요청이 남겨야 할 기록은 감사가 묻는 질문에 답할 수 있어야 한다.

| 질문 | 남길 것 |
|---|---|
| 누가 시켰는가 | 요청한 사람이나 API 키 |
| 무엇을 근거로 판단했는가 | 읽은 지식과 그 버전 |
| 어떤 도구를 어떤 입력으로 썼는가 | 도구와 릴리스, 입력 지문 |
| 누가 승인했는가 | 판정 결과, 승인자와 승인 채널 |
| 결과는 무엇이고 되돌릴 수 있는가 | 실행 결과 요약과 되돌리기 가능 시한 |

기록은 도구 실행 원장, 승인 원장, 대화 기록, 지식 변경 이력, 데이터베이스 세션 정보처럼 여러 곳에 남으므로 공통 추적 식별자로 묶는다. OpenTelemetry의 스팬으로 입력, 판단과 도구 호출을 기록하면 관측 도구들이 같은 추적을 읽을 수 있다. Arize 문서는 LLM 추적 규약인 OpenInference를 OpenTelemetry를 대체하지 않는 확장으로 설명한다.

## 실행 중 탐지에서 차단까지

사전 통제가 모든 경로를 막지 못하므로 실행을 계속 보고 판정하는 루프를 둔다.

1. **수집:** 모든 입력, 판단, 도구 호출과 가드 판정을 추적으로 남긴다.
2. **평가:** 들어오는 추적을 규칙, 분류기, LLM 심판으로 자동 판정한다([[Eval-LLM-Judge|LLM 심판 평가]]).
3. **전파:** 판정이 기준을 넘으면 사람과 시스템에 알린다.
4. **조치:** 방어 시스템을 호출해 세션을 끊고 권한을 막는다.

사후 판정 루프는 첫 시도를 탐지하고 기록할 뿐 막지는 못한다. 첫 시도까지 막으려면 실행 경로 안의 인라인 가드와 함께 쓴다.

| 통제의 성격 | 하는 일 | 예 |
|---|---|---|
| 탐지 | 위험한 메시지를 잡는다 | 입력 가드레일(탈옥, 개인정보), 출력 가드레일(기밀 유출, 근거성) |
| 통제 | 허가 밖 행동을 막는다 | 최소 실행 권한, 도구 허용 목록과 버전 고정, 세션별 누적 권한 상한 |
| 검증 | 실제로 막혔는지 확인한다 | 실제 목표 달성 여부로 판정하는 레드팀 |

외부 문서, 메일과 도구 응답도 공격 입력이 된다. 신뢰 경계를 사용자 입력에서 이 콘텐츠까지 넓히고, 외부 콘텐츠의 지시를 실행하지 않는다. 공격 유형별 방어는 [[LLM-Application-Security|LLM 애플리케이션 보안]]에서 다룬다.

세 성격의 통제를 묶어 주는 것은 기록이다. 새 공격, 실패 분석, 검사와 권한 개선, 재평가의 루프는 무엇이 언제 어떻게 통과했는지 남아 있어야 돈다. 기록되지 않은 방어는 작동했다고 증명할 수 없다.

## 규제와 관리체계로 이어진다

한국 AI 기본법의 고영향 AI 의무는 위험관리, 설명 방안, 이용자 보호, 사람의 관리와 감독, 문서 작성과 보관을 요구한다([[AI-Basic-Act-Scope-and-Obligations|AI 기본법의 적용 범위와 사업자 의무]]). 네 가지 통제와 추적 기록은 이 의무의 증적이 된다. 다만 데이터셋 평가나 레드팀 결과만으로 관리체계 전체를 증명하지는 못하므로, 통제 항목마다 담당자와 증적을 정해 둔다.

## 점검

- 에이전트가 쓰는 신원이 요청자와 연결되고, 공용 계정으로 대신 실행되는 경로가 없는가?
- 위험한 도구의 승인 조건이 코드로 판정되고, 판정 불가 시 가장 엄격한 처리로 가는가?
- 상태를 바꾸는 도구마다 보상 동작과 되돌리기 시한이 선언돼 있는가?
- 한 요청의 근거 지식 버전, 도구 입력, 승인과 결과를 하나의 추적 식별자로 찾을 수 있는가?
- 사후 탐지 루프와 인라인 가드의 역할을 구분해 첫 시도의 피해를 따로 판단했는가?
