# 에이전트 신원과 실행 권한

에이전트에게 실행 권한을 준다는 것은 어떤 에이전트가(누가) 어느 사용자를 대신해(누구를) 무엇을, 얼마나, 언제, 어디서 실행할 수 있는지를 정하는 일이다. AI의 쓰임이 질문과 답변, 메일과 문서를 다루는 업무 보조, 데이터를 조회해 시스템에 반영하는 업무 수행 에이전트, 역할을 나눠 함께 처리하는 여러 에이전트로 옮겨 가면 위험도 답변 내용의 오류에서 권한을 가진 실행의 오류(데이터와 시스템 변경, 과도한 접근)로 옮겨 간다. 보안의 중심도 답변의 정확성과 적절성 관리에서 실행 권한 통제로 이동한다. 승인, 복구와 감사를 묶는 통제는 [[Agent-Governance-Controls|에이전트 거버넌스 통제]]가, 사람과 에이전트의 담당 경계는 [[Production-Agent-Architecture-Delegation|위임 경계와 자율권]]이 다루고, 이 문서는 그 통제가 기대는 신원과 권한 모델을 다룬다.

## IAM이 묻는 질문이 바뀐다

| 구분 | 사람 중심 | 에이전트 대행 |
|---|---|---|
| 호출 구조 | 사람이 시스템을 직접 부르는 한 단계 | 에이전트가 다른 에이전트를 부르는 여러 단계 |
| 데이터 흐름 | 로그인 계정의 권한 범위에서 사람이 직접 조회 | 에이전트가 사용자 대신 조회하고 실행해 다음 단계로 넘긴다 |
| 역할 | 사람이 판단하고 실행 | 사람은 위임과 승인, 에이전트는 판단과 실행 |
| IAM의 질문 | 사용자가 누구이며 어떤 애플리케이션에 접근하는가 | 에이전트가 누구의 권한으로 어떤 업무를 실행하는가 |

계정을 한 번 인증하고 애플리케이션 단위로 접근을 허용하던 모델은 요청마다 실행 주체, 대신하는 사용자, 업무 목적과 범위를 따지는 모델로 넓어져야 한다. 모든 문을 열고 오래 유지되는 마스터 키(공용 API 키, 넓은 서비스 계정)는 누가 썼는지 추적하기 어렵고 탈취되면 피해가 크다. 그 대신 목적, 범위, 접근 대상과 시간으로 제한한 권한증을 요청마다 발급한다(설계 판단).

## 신원 모델 셋을 비교한다

| 모델 | 실행 방식 | 추적성 | 권한 통제 | 자율 실행 |
|---|---|---|---|---|
| 에이전트 신원 | 에이전트가 자기 신원과 자체 권한으로 실행 | 낮다. 어느 사용자의 요청인지 남지 않는다 | 부분적이다. 권한이 과하게 잡히기 쉽다 | 사용자 없이 실행할 수 있다 |
| 위임 신원 | 사용자 권한을 위임받아 사용자 대신 실행 | 부분적이다. 사용자는 남지만 실제로 실행한 에이전트는 구분되지 않을 수 있다(해석) | 사용자 권한 기준으로 걸린다 | 사용자가 있어야 하고 동의 요청이 잦다 |
| 결합(디지털 권한증) | 에이전트 신원과 위임을 함께 담은 권한증으로 실행 | 사용자와 에이전트를 모두 추적한다 | 위임할 수 있는 권한과 에이전트가 받을 수 있는 권한으로 좁힌다 | 승인 정책 안에서 허용한다 |

- **에이전트 신원**: 정규직, 협력직 같은 사람 신원, 서비스, 워크로드, API 클라이언트 같은 비인간 신원과 나란한 별도 범주로 에이전트에 독립된 신원을 준다. 사용자 없이 도는 배치나 이벤트형 에이전트에 맞지만, 여러 사용자의 요청을 한 신원으로 처리하면 시스템 기록만으로는 누구의 요청이었는지 알 수 없고 권한은 모든 요청의 합으로 커진다([[Production-Agent-Architecture-Delegation#여러 사용자가 쓰는 에이전트는 누구의 권한으로 실행하는지 정한다|실행 주체 비교]]).
- **위임 신원**: 사용자가 출장비 정산 초안을 요청하면 에이전트가 그 사용자 권한으로 메일과 영수증을 확인하고 정산 시스템에 접근한다. 시스템이 사용자 권한을 확인하므로 기존 접근 통제가 그대로 걸린다. 대신 에이전트가 사용자 권한 전체를 쓸 수 있어 사용자 권한이 넓을수록 위험도 넓고, 실행마다 동의를 받으면 승인이 형식이 되며, 사용자가 없는 시간에는 실행하지 못한다.
- **결합**: 인증과 권한 서버가 사용자 쪽 입력(인사 정보, 위임할 수 있는 권한), 에이전트 쪽 입력(자체 권한, 위임받을 수 있는 권한), 자료와 작업의 등급(일반, 기밀), 승인 정책(조건, 승인 주체, 시간)을 함께 판단해 권한증을 발급한다. 사용자, 에이전트, 시스템 세 쪽에 로그를 남기고 이상 탐지와 대응을 붙인다. 권한증에는 소속(대신하는 사용자), 에이전트 이름, 목적(예: 생산량 리포팅), 범위(예: 쓰기는 위임, 읽기는 권한 근거 표시 없음), 접근 대상(예: 생산 시스템), 유효 시간(예: 1시간 30분), 승인자(예: 그 사용자의 부서장)가 들어간다. 묻는 질문은 하나다. 누가(에이전트) 누구를(사용자) 대신해 무엇을, 얼마나, 언제, 어디서 적법하게 실행하려 하는가.

실효 권한을 요청자 권한과 에이전트에 준 범위의 교집합으로 두는 원칙은 [[Agent-Governance-Controls#신원과 권한|신원과 권한]]을 따른다. 발표 모델은 에이전트 자체 권한도 발급 입력으로 받으므로, 사용자에게 결과가 돌아가는 조회는 요청자 권한 안으로 제한하고 자체 권한은 사용자 없는 실행과 시스템 작업에만 쓴다(설계 판단).

### 표준 토큰 교환으로 옮기면

결합 모델에서 사용자를 대신하는 실행은 OAuth 2.0 Token Exchange(RFC 8693)의 위임 의미론에 대응한다(설계 판단). 사용자 토큰을 `subject_token`, 에이전트 신원을 나타내는 보안 토큰을 `actor_token`으로 제출하면(클라이언트 인증은 OAuth 2.0의 일반 절차로 따로 한다), 인가 서버가 정책과 설정에 따라 사용자가 주체이고 에이전트가 행위자인 토큰을 발급할 수 있다. RFC 8693은 `act` claim을 위임이 일어났음과 권한을 위임받은 행위자를 JWT 안에 표현하는 수단으로, `may_act` claim을 한 당사자가 다른 당사자를 대신해 행동할 수 있다는 진술로 정의한다. 위임에서 행위자는 자기 신원을 유지한 채 상대를 대표해 행동한다. 여러 단계의 위임은 `act`를 중첩해 남기고(맨 바깥이 현재 행위자), 토큰을 받는 쪽은 접근 통제에 최상위 claim과 현재 행위자만 쓰며 이전 행위자는 참고 정보로만 본다. 에이전트가 자기 권한으로 직접 하는 호출은 위임도 가장도 아니므로 에이전트 자신의 토큰으로 따로 다룬다. 목적과 대상, 시간은 `scope`, `audience` 또는 `resource`와 토큰 만료로 좁히고, 승인자와 업무 목적처럼 표준 claim에 없는 값은 발급 기록과 감사 로그에 둔다. 실제 행위자가 토큰에서 사라지는 가장(impersonation)은 이 용도에 맞지 않으며, 발표의 위임 신원도 실행한 에이전트가 토큰에 드러나지 않으면 RFC 기준으로는 가장이다(해석, [[OAuth2-Token-Exchange#가장과 위임|가장과 위임]]).

## 접근 통제의 다섯 질문

| 질문 | 확인할 것 | 통제 지점(설계 판단) |
|---|---|---|
| 누가 요청했는가 | 사용자 신원 | 조직의 통합 인증과 조건부 다중 인증 |
| 어떤 에이전트인가 | 등록 여부, 신뢰 수준, 역할 | 에이전트 등록부와 에이전트 신원 |
| 누구의 권한인가 | 에이전트 권한과 사용자 권한, 위임의 정당성 | 위임 정책과 권한증 발급 |
| 어디까지 허용하는가 | 대상, 범위, 시간, 위치 | 권한증의 범위와 만료, 접속 환경 조건 |
| 위험하지 않은가 | 이상 징후 | 위험 점수, 추가 인증, 권한 축소, 차단 |

다섯 질문은 앞 단계를 통과하면 끝나는 관문이 아니라 요청마다 함께 판단하는 조건이다. 인증을 통과했다는 사실만으로 위험한 행동이 허용되지 않도록 범위와 위험은 호출마다 다시 묻는다.

## 위협 시나리오 셋

### 계정 탈취

공격자가 사용자 계정을 탈취하면 정상 인증을 통과한 뒤 에이전트를 불러 민감 데이터를 조회하거나 권한 변경을 시도할 수 있다. 사용자는 정상처럼 보이므로 인증 여부만으로는 막지 못한다. 평소와 다른 AI 서비스 접근, 과도한 권한 요청, 고위험 업무, 비정상적인 위임을 신호로 삼아 위험할 때 추가 인증을 요구하고, 권한을 최소로 줄이고, 접근을 즉시 차단하며, 모든 행위를 자동으로 감사 기록에 남긴다.

### 오작동과 프롬프트 주입

승인된 정상 에이전트도 입력에 섞인 지시나 오작동으로 데이터 오류와 잘못된 업무 처리를 낼 수 있다. 같은 에이전트가 상황에 따라 다른 결과를 내므로 실행 권한도 상황마다 달라야 한다.

| 기준 | 나누는 값 |
|---|---|
| 권한 범위 | 조회 / 변경과 삭제 |
| 실행 근거 | 에이전트 자체 권한 / 사용자에게 위임받은 권한 |
| 승인 정책 | 저위험 업무는 자동 승인 / 고위험 업무는 관리자 승인 |

권한 범위와 주체별로 승인 정책을 나누면 한 번의 오작동이 과도한 변경이나 대량 오류로 번지는 것을 막는다.

공개 사례로 Noma Security가 2025-09-25 공개한 ForcedLeak(CVSS 9.4)은 Salesforce Agentforce의 취약점 연쇄다. 외부인이 Web-to-Lead 양식의 설명 필드에 지시를 숨겨 두면, 직원이 그 리드를 검토해 달라고 요청할 때 에이전트가 숨은 지시까지 실행해 CRM 데이터를 생성된 이미지 요청에 실어 외부로 보낼 수 있었다. 콘텐츠 보안 정책(CSP)의 허용 목록에 남아 있던 도메인이 만료돼 5달러에 다시 등록할 수 있었던 것이 유출 경로를 열었다. 연구자 공개 일정 기준으로 2025-07-28 보고됐고 Salesforce는 2025-09-08 Agentforce와 Einstein AI에 Trusted URLs 강제를 적용했다. 연구 과정의 개념 증명이며 실제 고객 데이터 유출을 보고한 것은 아니다. 외부 입력을 읽는 에이전트에 넓은 조회 권한과 외부 전송 경로가 함께 있었고, 허용 목록은 등록한 도메인의 만료까지 관리해야 경계로 작동한다(해석). 세 조건이 겹치는 위험은 [[LLM-Application-Security#적응형 공격과 피해 반경 제한|Rule of Two와 lethal trifecta]]에서 다룬다.

### 비인가 에이전트

부서나 개인이 승인 없이 만든 에이전트가 사내 API와 데이터베이스를 부르면 누가, 어떤 역할과 권한으로 호출하는지 알 수 없다. 섀도 IT가 섀도 에이전트로 바뀐 것이다. 승인된 에이전트와 서비스만 호출을 허용하고(신뢰된 에이전트 식별), 최소 권한을 적용하며, 인증 토큰과 권한 부여 이력을 감사하고, 비정상 호출과 오남용을 계속 감시한다. 등록 목록과 인프라에서 발견한 사용의 대조는 [[Agent-Governance-Controls#자산은 등록과 공유를 나눈다|자산 등록]]을 따른다.

## 등록부터 승인까지

1. **에이전트 등록**: 이름, 목적, 사용하는 모델과 엔드포인트를 등록하고 에이전트 ID와 시크릿을 발급한다(발표 화면에서는 에이전트 ID를 내부망용과 외부망용으로 따로 발급했다). 시크릿은 발급 뒤 다시 조회할 수 없게 하고 시크릿 저장소에 둔다(설계 판단, [[Secret-Management|시크릿 관리]]).
2. **자원과 권한 범위 등록**: 에이전트가 닿을 시스템과 MCP 서버를 자원 식별자로 등록하고, 자원마다 티켓 조회와 티켓 생성처럼 작업 단위의 권한 범위를 정의한다. 도구 목록에 보이는 것과 호출이 허용되는 것은 다르게 인가한다([[MCP-Security-Boundaries#게이트웨이: 신원, 정책과 자격 증명을 한곳에서|발견과 실행의 분리]]).
3. **접근 조건**: 신분 속성(보안 등급, 소속 그룹), 요청한 자원과 권한, 위치 같은 접속 환경, 이상 탐지 결과를 조건으로 둔다.
4. **승인 정책**: 승인 주체(에이전트 자체, 사용자, 부서장)와 유효 시간을 정한다. 일정 조율 에이전트라면 인사와 캘린더 조회는 자동 승인하고 외부로 문자를 보내는 단계에서만 승인을 요청하는 식이다.
5. **생애주기**: 정기 검토로 쓰지 않는 권한과 중복된 에이전트를 회수하고 폐기한다. 같은 세션 안에서 누적되는 행동을 평가하는 정책은 [[Bedrock-AgentCore-Operations#Temporal policy는 같은 세션의 이력을 평가한다|세션 이력 정책]]을 본다.

## 외부 AI 서비스도 같은 IAM에 붙인다

조직이 쓰는 외부 AI 서비스와 사내 에이전트를 기업 인증과 권한 체계에 연결해 같은 기준을 건다(설계 판단).

- **인증과 접근**: 회사 이메일 도메인 기반 SSO를 SAML이나 OIDC로 연동하고, 조건부 다중 인증으로 접속 조건을 건다. 예를 들어 관리자급의 사외 접속에는 생체 인증을 요구하고 퇴사자는 로그인할 수 없게 한다.
- **권한**: 사용자와 역할 그룹을 SCIM으로 동기화하고, 사용량 한도와 세부 권한을 그룹에 매핑한다(예: 핵심 개발자 그룹의 토큰 한도를 두 배로). 서비스와 요금제마다 SSO, SCIM과 그룹별 한도의 지원 범위가 다르므로 도입 전에 확인한다(미확인). 권한 속성을 토큰에 싣는 방식은 [[OIDC-Provider-Authorization-Claims|OIDC 권한 claim]]을 본다.

## IAM 운영에 AI를 붙일 때

- **분석 자동화**: 장기 미사용 권한, 역할과 정책의 충돌을 찾고 정책 설정을 돕는다. 진단 예로 앱마다 따로 인증해 비밀번호 재사용이 생기는 통합 인증 부재, 로그와 SIEM 연계와 이상행위 대응 부족, 인사 변동이 자동 동기화되지 않아 퇴사자 계정 회수가 늦고 권한이 남는 문제를 찾은 뒤, 사용자 수, 업무 중요도, 위험도로 상위 업무 앱 10개를 골라 SAML/OIDC 표준 템플릿으로 먼저 연동하고 비표준 맞춤 연동은 예외로 관리하는 순서가 있다(2026년 9월 발표 예시).
- **IAM 제어면을 MCP로 열 때**: 계정 생성과 삭제, 권한 부여와 회수, 감사 로그 조회를 MCP 도구로 열면 코딩 에이전트가 자연어 지시로 계정을 만들 수 있다. 이 도구들은 조직에서 가장 강한 권한이므로 조회 도구와 분리해 노출하고, 계정 생성과 권한 부여에는 위의 승인 정책을 그대로 적용한다(설계 판단).

## 권한 체계를 계속 공격해 본다

- **레드팀**: 에이전트 악용 시나리오, 과도한 권한 경로를 찾는 권한 오남용 시험, 비인가 데이터 접근 시도, 취약점의 지속 재검증. 공격자가 AI로 공개 전 취약점까지 먼저 찾을 수 있다는 전제에서 정적(SAST)과 동적(DAST) 보안 시험을 정기 점검이 아니라 지속 검증으로 돌린다(설계 판단).
- **블루팀**: 비정상 접근 패턴, 비정상이거나 과도한 권한 요청, 에이전트의 비정상 도구 호출과 데이터 접근을 탐지하고 위험도에 따라 경고하고 정책을 적용한다.
- **승인 단계도 공격면이다**: 수상한 권한 승인 요청을 잡으려면 IP별 요청 급증, 사람 승인(HITL) 세션 급증, 평소와 다른 승인 세션 지속 시간, 새로운 접속 환경과 위치를 함께 보고 접속 IP는 AbuseIPDB, VirusTotal 같은 외부 평판 정보로 보강한다(2026년 9월 발표 데모 기준). 승인 요청이 많아질수록 승인 자체가 형식이 되는 문제는 [[Harness-Gate-Placement#사람 승인과 실질적인 검토를 구분한다|게이트 배치]]를 본다.

## 사례

- VentureBeat Pulse Research의 2026년 6월 조사(직원 100명 초과 조직 107곳, 자기 선택 표본이며 확률 표본이 아니다, 2026-07-23 게재)에서 54%가 에이전트 보안 사건을 겪었다. 확인된 사고 18%와 피해 전에 잡은 아차사고 36%를 합친 값이다. 복수 응답인 신원 관리 질문에서 48%는 일부 에이전트만 범위가 정해진 신원을 갖고 나머지는 자격 증명을 공유한다고, 32%는 대부분 공용 API 키나 빌린 사람 계정과 서비스 계정으로 돈다고 답했고, 겹치는 응답을 합친 결과 69%(107곳 중 74곳)가 어딘가에서 자격 증명을 공유했다. 모든 에이전트에 범위가 정해진 고유 신원을 준다는 응답도 32%였지만, 사건 비율 비교에 쓰인 고유 신원 조직은 22곳(약 21%)이라 32%의 일부는 공유 응답과 겹친 것으로 보인다(수치에서 추정). 자격 증명을 공유하는 조직의 사건 비율은 63.5%(74곳 중 47곳), 모든 에이전트가 고유 신원을 가진 조직은 40.9%(22곳 중 9곳)로, 표본이 작아 인과가 아니라 연관이다.
- 이 조사를 95%, 80%, 54%, 18%로 요약한 2026년 9월 발표 자료가 있다. 발표 자료는 95%와 80%의 산식을 밝히지 않는다. 95%는 확보한 발췌에 없고 운영 중인 에이전트가 없다는 응답 5%에서 거꾸로 계산한 값으로, 80%는 겹치는 복수 응답 48%와 32%를 더한 값으로 보인다(둘 다 해석, 기사 전문은 미확인). 80%를 공용 자격 증명 비율로 쓰면 기사가 중복을 빼고 낸 69%보다 크다. 54%를 사고 경험률로, 18%를 피해 발생률로만 읽지 않는다.
- Gartner는 2025-08-26 기업 애플리케이션 가운데 업무 특화 AI 에이전트와 통합된 비율이 2025년 5% 미만에서 2026년 말 40%가 될 것으로 전망했다. 연결 대상이 늘수록 위의 권한 모델이 감당할 호출도 늘어난다(해석).

## 점검

- 에이전트마다 고유 신원이 있고 공용 API 키나 사람 계정을 빌려 쓰는 에이전트가 없는가?
- 권한증(토큰)에 사용자와 에이전트가 함께 남고 목적, 범위, 대상과 시간이 제한되는가?
- 범위와 위험을 호출마다 다시 판단하는가?
- 조회와 변경, 자체 실행과 위임 실행, 저위험과 고위험 업무의 승인 정책이 나뉘어 있는가?
- 등록하지 않은 에이전트의 호출을 거절하고 토큰 발급과 권한 부여 이력을 감사하는가?
- 외부 입력을 읽는 에이전트에 넓은 조회 권한과 외부 전송 경로가 함께 있지 않은가?
- IAM 제어면을 여는 도구에 승인 정책이 걸려 있고, 승인 요청 자체의 이상을 탐지하는가?
