# 멀티 에이전트의 조정 비용과 증설 판단

에이전트를 늘리면 처리 단위는 늘지만 작업 배분, 상태 동기화, 메시지 교환, 결과 통합과 검증 비용도 함께 늘어난다. 이 비용이 병렬화 이득보다 커지면 에이전트를 더해도 결과가 나빠진다. 증설 여부는 에이전트 수가 아니라 작업의 분해 가능성과 측정된 개선으로 정한다.

## 병렬화 이득의 상한

전체 작업 중 병렬로 처리할 수 있는 비율을 p, 처리 단위를 N이라 하면 Amdahl의 법칙에 따른 속도 향상의 상한은 1 / ((1 - p) + p / N)이다([[Concurrency-vs-Parallelism|동시성과 병렬성]]). p가 0.9이면 N이 4일 때 약 3.1배, 10일 때 약 5.3배이고 N을 무한히 늘려도 10배를 넘지 못한다. 이는 공식으로 계산한 가정값이다.

에이전트 작업의 직렬 구간은 요구사항 분해, 설계 결정, 결과 통합과 리뷰, 충돌 해결, 사람의 승인 대기다. Amdahl의 법칙은 조정 비용을 넣지 않은 낙관적 상한이며, 실제로는 N이 늘수록 통신과 통합 비용이 직렬 구간 자체를 키운다.

모든 에이전트가 서로 직접 대화하는 구조에서 통신 경로는 N(N-1)/2개다. 5개면 10개, 10개면 45개, 20개면 190개로 에이전트 수가 두 배가 되면 경로는 네 배 넘게(4.5배, 4.2배) 늘어난다. LLM 에이전트는 받은 메시지가 다음 호출의 입력 토큰이 되므로 비용이 경로 수보다 빠르게 늘 수 있고, 메시지 라운드마다 응답 대기가 누적된다.

## 측정 근거

### 작업 구조에 따라 효과의 방향이 바뀐다

Google Research, Google DeepMind와 MIT 연구진의 연구(arXiv 2512.08296, v3 2026-04-08)는 단일 에이전트와 네 가지 멀티 에이전트 구조(독립, 중앙 조정, 분산, 혼합)를 세 LLM 계열(OpenAI, Google, Anthropic)과 여섯 벤치마크의 260개 구성에서 비교했다. 도구, 프롬프트와 계산 예산은 같게 맞췄다.

- 분해 가능한 금융 추론(Finance-Agent)에서는 중앙 조정 구조가 단일 에이전트보다 80.8% 나았고, 순차 계획(PlanCraft)에서는 모든 멀티 에이전트 구조가 39~70% 나빴다. 저자들은 고정된 계산 예산에서 조정 부담이 추론 능력을 쪼갠다고 해석한다.
- 오류가 전파되는 정도는 구조에 따라 달랐다. 결과를 검증 없이 모으는 독립 구조는 실행 흐름의 오류를 17.2배로 키웠고, 오케스트레이터가 검증 병목을 두는 중앙 조정 구조는 4.4배로 억제했다.
- 회귀 분석에서는 단일 에이전트의 정확도가 약 45%를 넘는 과제일수록 에이전트를 더하는 이득이 줄거나 음수로 돌아서는 경향이 나왔다. 회귀로 도출한 경계이며 예외도 있어, Workbench에서는 분산 구조가 단일 에이전트보다 5.6% 나았다. 도구를 많이 쓰는 과제일수록 에이전트당 토큰 예산이 쪼개져 불리했다.
- 모델 역량, 도구 수, 에이전트 수, 단일 에이전트 기준 성능과 다섯 가지 조정 지표(오버헤드, 메시지 밀도, 중복, 효율, 오류 증폭)로 만든 회귀 모델은 교차검증 R²가 0.373(과제 기반 역량 지표를 쓰면 0.413)이었고, 학습에 쓰지 않은 구성의 87%에서 최적 구조를 맞혔다. 저자들은 절대 성능 예측보다 구조 간 선택이 더 안정적이라고 한정한다.

### 토큰을 더 쓰는 구조이고, 맞는 작업이 따로 있다

Anthropic의 연구 에이전트 사례(2025-06-13)에서 Claude Opus 4 리드 에이전트와 Claude Sonnet 4 하위 에이전트로 구성한 시스템은 내부 연구 평가에서 단일 Claude Opus 4보다 90.2% 나았다. 같은 글은 에이전트가 일반 채팅보다 약 4배, 멀티 에이전트 시스템이 약 15배의 토큰을 쓴다고 밝혔고, BrowseComp 성능 분산의 80%를 토큰 사용량 하나가 설명했다고 분석했다.

- 맞는 작업: 여러 독립 방향을 동시에 탐색하는 너비 우선 조사, 단일 컨텍스트 창을 넘는 정보, 많은 도구를 다루는 고가치 작업이다.
- 맞지 않는 작업: 글을 쓴 2025년 6월 기준으로 모든 에이전트가 같은 컨텍스트를 공유해야 하거나 에이전트 간 의존이 많은 영역이다. 대부분의 코딩 작업은 연구보다 진짜로 병렬화할 수 있는 부분이 적다고 봤다.
- 초기 실패: 단순 질의에 하위 에이전트 50개를 띄우거나 서로 과도한 업데이트로 방해했다. 작업 설명이 모호하면 하위 에이전트가 같은 일을 중복하거나 빈틈을 남겼다. 그래서 질의 복잡도별 에이전트 수와 도구 호출 수 기준을 프롬프트에 넣었다.
- 같은 시점의 구현에서는 리드 에이전트가 하위 에이전트 묶음이 모두 끝날 때까지 동기적으로 기다리므로 조정은 단순하지만, 실행 중 방향을 바꾸거나 하위 에이전트끼리 협력하지 못하고 느린 하나가 전체를 막는다. 비동기 실행은 결과 조정, 상태 일관성과 오류 전파 문제를 더한다.

### 게임 환경의 관찰은 실패 유형을 보여 준다

YC Labs와 Olam Labs가 2026년 10월 공개한 게임 환경 실험에서는 Minecraft 생존 월드에 GPT-6.1 Sol 에이전트 50개를 3시간 두고 문명을 세우게 했다. 에이전트들은 약 5,900개의 메시지를 보냈고, 디렉터리 순서의 첫 에이전트가 사실상 리더가 되어 승인 요청이 몰렸다. 배급 장부와 허가 규칙 같은 자체 관료제를 만들었고, 공유 기록에는 중복 수확, 중복 제작과 중복 운송을 피하라는 경고가 반복됐다. 다른 에이전트에게 보낸 음식을 엉뚱한 에이전트가 먹는 배송 착오도 기록됐다.

이 실험은 에이전트 수를 바꿔 가며 비교하지 않았다. 따라서 에이전트를 늘리면 나빠진다는 근거가 아니라, 군집에서 어떤 유형의 조정 실패가 생기는지 보여 주는 관찰로 읽는다. 게임은 목표와 상태가 관측 가능하지만 실무는 요구사항이 모호하고 실패 비용이 외부 시스템으로 번지므로 수치를 그대로 옮기지 않는다.

### 검증기가 있는 과제에서는 1,000개 규모의 자율 조정이 작동했다

Anthropic이 2026-11-09 claude.dev 블로그에 공개한 실험은 Claude Fable 5.2 초기 버전 에이전트 1,000개(리드 1, 헬퍼 999)에게 페르마의 마지막 정리의 Lean 형식 증명을 다시 만들게 했다. 같은 해 9월 공개한 형식화에서는 연구자의 간헐적인 방향 제시와 수학 전용 플랫폼(Prove2Me) 아래 수십 개 에이전트가 11일에 걸쳐 Lean 코드 약 1,300만 줄을 썼다. 이번에는 최종 정리와 중간 이정표 59개를 합친 명제 60개, 고전적 증명 경로의 한 문장 개요, 정의와 9월 형식화에서 증명한 보조정리 47개만 주고 조직 방법은 지시하지 않았다.

- **조정 수단은 범용 도구뿐이었다:** 에이전트마다 셸, 파일 편집기, Lean과 Mathlib, 자기 Git 브랜치가 있었고, 전용 메시징 도구 없이 공유 Postgres와 Git(자기 브랜치, main 병합 요청)으로만 협업했다. 리드는 처음 10분 안에 전체 지시(announce), 담당 배정(assign), 진행 보고 게시판(notes), 누구나 추가하고 먼저 잡은 쪽이 맡는 할 일(subtasks), 완료 기록(landed)의 표 5개를 만들었다. 아래 실패 패턴 표의 대응인 중앙 작업 큐, 단일 소유자와 공유 작업 보드에 해당하는 구조로 볼 수 있다. 머신 하나를 함께 쓰게 하면 약 100개에서 한계에 닿아 에이전트마다 경량 VM을 줬다.
- **난이도 판단은 비관적으로 틀렸다:** 리드는 명제마다 16~17개를 배정하고 난이도를 평가하게 했다. 약 27분에 3개는 이미 증명됐고, 리드는 대다수가 예산 안에 불가능하다고 본 47개를 미루고 나머지 10개에 인력을 몰았는데, 10개는 약 70분 안에 모두 증명됐다. 블로그는 에이전트가 어려운 문제를 쉽게 포기하고 난이도를 잘못 판단하는 경향을 한계로 적고, 사람의 방향 제시가 여전히 도움이 된다고 본다.
- **헬퍼가 리드의 배정을 기다리지 않게 됐다:** 첫 1시간 안에 헬퍼가 스스로 할 일을 만들기 시작했고, 3시간까지 리드는 일이 빈 헬퍼에게 자기를 기다리지 말라고 지시했다. 리드는 그 뒤에도 배정을 계속 썼다. 5.6시간에는 헬퍼 73개가 할 일 756개를 직접 등록했고 그중 crew 책임자(captain)는 16개뿐이었다.
- **재귀 분해와 가정 증명으로 병렬화했다:** 마지막 남은 Langlands–Tunnell 정리는 담당 captain이 Lean 70만~100만 줄 이상, 시간 안 완료 확률 1% 미만으로 평가해 미뤄 둔 명제였다. 약 18시간에 리드가 헬퍼 약 750개를 투입했고, 10개 영역으로 나눈 뒤 한 에이전트가 맡기 큰 조각을 다시 쪼개 할 일 2,418개, 최대 10단계의 트리가 됐다. 각 조각이 아래 조각을 이미 증명된 것으로 가정하고 작업해 아래가 끝나기 전에도 수백 개가 동시에 일했다. 28.4시간에 이 정리, 28.7시간에 최종 정리가 공식 검사기를 통과했다. 9월 대비 출력 토큰은 3분의 1, 증명 길이는 7분의 1이었다.

이 결과는 각 명제의 완료를 Lean 검사기가 판정하고 main 브랜치에 제출하면 채점기가 검사하는 과제의 관찰이다. 완료 판정이 모호한 업무로 옮기면 위의 책임 공백과 오류 증폭을 같은 방식으로 막을 수 없다. 블로그 스스로 장난감 실험이라 부르고, 도메인 전용 하네스나 플랫폼의 필요를 없애지 않는다고 적는다. 에이전트 수를 바꿔 비교한 실험도 아니다.

격리 설계도 함께 공개했다. 전용 메시징 도구 없이 DB와 Git으로만 조정하게 하고, 자기 브랜치에만 push하며 별도 작업이 충돌이나 결함 있는 병합을 거부했다. DB는 권한 없는 공용 역할로 문장당 5초 제한과 256 MiB 초과 쓰기 거부를 걸었고, 네트워크 대신 에이전트 신원을 붙이는 게이트웨이 파이프만 열었다. 프롬프트형 LLM 분류기가 실행 전에 도구 호출을 막는데, 리드가 막히면 실행 전체를, 헬퍼가 막히면 그 헬퍼만 끝내는 fail-closed 구성이다. 실행 중에는 행동만 보는 감시기를 썼고 사고 과정(chain of thought) 감시기는 그 직후에 더했다. 100만 건 넘는 도구 호출 중 차단 기준에 닿은 것은 없었지만, 사고 과정 감시기로 재생했을 때 root 접근 확인 1건이 기준에 근접했다고 적는다. 공유 자원이 통신 채널이 되는 위험은 [[Agent-Swarm-Containment|에이전트 군집 격리]]에서 다룬다.

## 네 가지 실패 패턴과 분산 시스템의 대응

| 패턴 | 증상 | 조기 신호 | 대응과 그 대가 |
| --- | --- | --- | --- |
| 중복 작업 | 같은 파일이나 질의를 여러 에이전트가 처리 | 같은 대상에 대한 중복 호출 비율 | 중앙 작업 큐나 lease로 한 작업을 한 에이전트만 가져가게 한다. 큐는 병목이 될 수 있다 |
| 상태 불일치 | 오래된 스냅샷으로 판단해 이미 바뀐 상태 위에 행동 | 읽은 시점과 쓰는 시점의 버전 차이, 병합 충돌과 이유 없는 재작업 | 단일 진실 원천, 쓰기 전 버전 확인, 에이전트별 작업 공간 분리. 분리는 충돌을 병합 시점으로 미룰 뿐이다 |
| 책임 공백 | 모두 완료를 보고하지만 테스트, 마이그레이션 확인, 보안 점검이 비어 있음 | 소유자 없는 작업, 실행되지 않은 체크 항목 | 작업마다 단일 소유자와 검증 가능한 완료 조건을 둔다 |
| 통신 폭증 | 진행 없이 메시지만 오감 | 작업당 메시지 수와 토큰 사용량 급증 | 허브 구조, 공유 작업 보드, 채널과 라운드당 메시지 상한 |

LLM 에이전트는 추론에 수 초에서 수십 초가 걸려 읽기와 쓰기 사이의 틈이 일반 프로그램보다 넓고, 컨텍스트 안의 정보는 갱신되지 않는다. 같은 모델에 같은 목표 목록을 주면 같은 선택을 해 중복이 생기기 쉽고, 검증자가 실행자와 같은 모델이면 같은 방향의 오류를 함께 놓칠 수 있다. 같은 파일을 두 에이전트가 고치면 텍스트 충돌은 도구가 알려 주지만 의미 충돌은 CI나 테스트 전까지 드러나지 않는다([[Agent-Terminal-Workspaces|에이전트 터미널 작업 공간]]).

조정 장치마다 비용이 있다. 락은 대기와 교착을, 큐는 병목을, 리더는 단일 장애점을 만든다. 멀티 에이전트의 장애도 중복 실행, 순서 꼬임, 상태 불일치와 부분 실패로 나타나므로 멱등성, 타임아웃, 재시도 예산과 백프레셔 같은 기존 분산 시스템의 수단을 쓴다. 다만 노드가 비결정적이고 메시지 비용이 토큰으로 청구된다는 점이 다르다.

## 구조 선택

| 구조 | 장점 | 비용 |
| --- | --- | --- |
| 중앙 조정 | 상태와 소유권이 한곳에 모여 중복과 충돌을 막기 쉽고 오류 검증 지점이 있다 | 오케스트레이터가 병목, 단일 장애점이 되고 그 컨텍스트에 메시지가 쌓인다 |
| 계층형 | 조정 범위를 나눠 병목을 줄인다 | 계층이 깊을수록 요약 과정의 정보 손실과 지연이 는다 |
| 분산형 | 병목이 적고 유연하다 | 경로 수가 빠르게 늘고 누가 무엇을 아는지 추적하기 어렵다 |
| 독립 실행 후 취합 | 조정 메시지가 거의 없다 | 검증 없이 모으면 오류가 그대로 증폭된다 |

어느 구조든 작업 경계(입력과 출력 계약), 단일 소유권, 상태 단일화, 메시지 최소화 순서로 원칙을 쌓는다. 경계가 흐리면 소유권을 정할 수 없고, 소유권이 없으면 상태를 단일화해도 누가 고칠지 모른다. 원칙은 문서에만 두지 않고 설정 검증으로 강제한다. 예를 들어 같은 자원에 쓰기 권한을 가진 작업이 둘이면 실행 전에 거부한다. 프레임워크별로 다음 단계를 누가 정하는지는 [[Production-Agent-Architecture-Orchestration#다음 단계를 누가 정하는가|프로덕션 에이전트 오케스트레이션]]에서 비교한다.

## 증설 판단 절차

1. 단일 에이전트로 기준선을 잡는다. 성공률, 작업당 토큰, 벽시계 시간을 기록한다.
2. 병목을 진단한다. 컨텍스트 초과라면 요약이나 검색 개선이, 도구 대기라면 병렬 도구 호출이 먼저일 수 있다. 에이전트 증설은 그다음 선택지다.
3. 작업이 독립적으로 쪼개지는지, 작업과 파일의 소유자가 한 명씩인지, 공유 상태가 작은지, 통신 예산을 정했는지 확인한다. 하나라도 불분명하면 증설을 미룬다.
4. 1개에서 2개, 4개처럼 한 단계씩 늘리고 같은 작업 세트로 성공률, 총 토큰, 시간, 충돌과 재작업 횟수, 에이전트 간 메시지 수를 비교한다.
5. 되돌릴 기준을 미리 숫자로 정한다. 예를 들어 비용은 오르는데 성공률이 기준선보다 오르지 않으면 이전 단계로 돌아간다. 기준이 없으면 실패해도 알아차리지 못하고 매몰 비용 때문에 계속 밀고 가게 된다.

에이전트 몇 개가 최적이라는 주장은 작업 유형, 모델, 컨텍스트 공유 방식과 도구 환경에 따라 달라지므로 자기 워크로드에서 다시 잰다. 단일 데모는 가장 약한 근거이고, 여러 조건에서 반복한 실험과 오래 검증된 원리가 함께 가리킬 때 설계 근거로 쓴다.

## 면접 체크포인트

- 에이전트를 늘리면 빨라지는가: Amdahl의 상한, 조정 비용이 직렬 구간을 키우는 이유, 작업 의존 구조에 따라 효과의 부호가 바뀐 측정 결과로 답한다.
- 중앙 조정과 독립 실행의 차이: 검증 지점 유무가 오류 증폭에 미치는 영향과 오케스트레이터 병목의 맞교환을 설명한다.
- 멀티 에이전트 도입 결과를 평가하는 질문: 무엇과 비교했는지(단일 에이전트 기준선), 무엇을 측정했는지(성공률, 비용, 시간, 재작업), 언제 되돌리는지.
