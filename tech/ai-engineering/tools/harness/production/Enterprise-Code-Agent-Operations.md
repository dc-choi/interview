# 기업 개발 조직의 코드 에이전트 운영 설계

코드 에이전트를 개인 도구가 아니라 조직의 개발 체계로 들이려면 모델 선택보다 넓은 설계가 필요하다. 코드를 쓰는 속도는 빨라졌지만 일을 정하고, 흩어진 맥락을 잇고, 결과를 검토하고 승인하는 방식은 여전히 사람 중심이어서 프로젝트 속도를 묶는다. 이 문서는 그 간극을 메우는 설계 관점(모델과 실행 환경, 작업 맥락, 실행 하네스와 변경 통제, 흐름 운영, 반복 판단의 자산화)을 규제가 강한 기업, 특히 망 분리가 있는 금융 개발 환경을 기준으로 정리한다.

출시 흐름에서 병목이 옮겨 가는 일반 원리는 [[AI-Native-Org#출시 흐름의 병목은 단계를 따라 옮겨 간다|AI 네이티브 조직]], 개발자 역할의 변화는 [[Developer-Role-AI-Era|AI 시대 개발자 역할]], 에이전트 통제의 공통 구조는 [[Agent-Governance-Controls|에이전트 거버넌스 통제]]에서 다룬다. 설계 관점과 단계 구분은 2026년 9월 공급사 발표 두 건을 일반화한 것이다.

## 코드 생성이 먼저 빨라진 이유와 남은 병목

코드는 무엇을 바꾸고 어디까지 하면 끝인지가 비교적 분명하고, 테스트, 빌드, 정적 분석으로 결과를 바로 판정할 수 있다. 그래서 에이전트가 실행과 검증을 짧게 반복하며 스스로 고칠 수 있다([[Agent-Loop-Engineering|루프 엔지니어링]]). 프로젝트는 다르다. 요구, 분석, 설계, 구현, 배포가 여러 사람과 조직을 거쳐 이어지고, 단계 사이의 인계와 대기가 전체 속도를 정한다.

판단에 필요한 것도 흩어져 있다. 목표는 회의와 요구사항 문서에, 맥락은 운영 시스템, 코드 저장소, 설계 문서와 담당자 경험에, 판정 기준과 책임은 품질과 보안 조직, 의사결정자에게 있다. 그래서 다음 세 지점마다 사람이 해석해 잇는다.

| 지점 | 사람이 하는 일 |
|---|---|
| 일의 정의 | 배경과 완료 기준 해석, 우선순위와 예외 판단, 이해관계자 결정 |
| 맥락 연결 | 시스템과 의존성 파악, 변경 영향과 위험 확인, 과거 이력 연결 |
| 결과 판단 | 변경 근거 검토, 품질과 적합성 판단, 승인과 예외 결정 |

개인의 체감과 조직 성과의 차이는 조사에도 나타난다. McKinsey의 2026년 조사(2026-05-04~06-08, 97개국 1,719명, 국가별 GDP 가중)에서 응답자 80%가 AI로 자기 생산성이 높아졌다고 답했지만, AI가 조직 EBIT에 기여했다는 응답은 37%로 전년과 거의 같았다. 둘 다 응답자의 자기 평가다. 리뷰 대기와 장애 지표의 관측 자료는 [[Code-Review-AI-Agent-Operations#리뷰 병목의 관측 자료|리뷰 병목의 관측 자료]]에 있다.

## 모델과 실행 환경은 정보 민감도로 고른다

질문이 어떤 모델이 좋은가에서 어떤 상황에 어떤 모델과 환경이 맞는가로 바뀐다. 성능, 비용, 보안을 함께 보고 작업 정의, 다루는 정보, 실행 환경, 에이전트와 통제 기준을 조합한다. 아래는 한 공급사가 제시한 배치 예시다.

| 개발 단계 | 다루는 정보 | 맞는 환경 |
|---|---|---|
| 기술 검토, PoC | 기술 대안, 공개 기술 문서, 구현 예제, 검증 방법 | 외부 LLM 서비스 |
| 프로젝트 구성, 공통 기반 개발 | 프로젝트 템플릿, 공통 프레임워크, 사내 개발 표준 | 기업 전용 AI 개발 환경(클라우드 사업자의 전용 환경 등) |
| 업무 로직 개발, 운영 반영 | 업무 규칙, 민감 데이터, 권한과 승인 로직, 운영 설정, 내부 시스템 연계, 장애와 감사 이력 | 내부 통제형 AI 환경 |

오른쪽으로 갈수록 정보 민감도, 내부 업무 맥락과 실행 책임이 커진다. 금융은 이 축이 구조적인 단절로 나타난다. 코드베이스, 설계서와 API 명세, 도메인 규칙과 예외, 데이터와 인터페이스, 변경과 운영 이력 같은 업무 맥락은 내부망에 있고, 최신 모델, 코드 에이전트 도구, 패키지와 플러그인은 외부 생태계에 있어 망 분리 경계를 넘어 직접 붙이기 어렵다. 규제 변화는 [[Financial-Network-Separation-Easing|금융권 망분리 완화]], 데이터 등급별 허용 범위는 [[Agent-Governance-Controls#데이터 등급이 외부 AI 허용 범위를 정한다|데이터 등급과 외부 AI]]를 따른다.

설계 판단:

- 경계는 개발 단계가 아니라 그 작업이 읽는 데이터로 정한다. PoC라도 사내 코드나 운영 설정을 붙여 넣는 순간 외부 서비스 단계가 아니다.
- 내부 통제형 환경의 모델은 외부 최신 모델보다 성능이 낮을 수 있다. 어떤 작업을 어느 등급의 모델로 돌릴지 평가 세트로 확인한다([[LLM-Model-Tiers|LLM 모델 등급]]).

## 작업 맥락을 실행 가능한 단위로 만든다

요구, 설계, 코드, 테스트, 운영 산출물과 판단 근거가 단계마다 따로 있으면 기능 하나를 만들 때마다 사람이 맥락을 다시 찾는다. 공통 식별자가 없으면 요구와 설계, 코드를 잇기 어려워 착수가 늦어지고, 관계와 판단 근거가 흩어지면 담당자마다 기준을 다르게 해석하며, 기준과 완료 조건이 따로 있으면 승인 조건을 뒤늦게 확인해 누락과 재작업이 늘어난다. 이 비용은 프로젝트마다 반복된다.

에이전트에 넘기는 작업은 여섯 항목을 갖춘다: 작업 목적, 변경 대상, 범위 제약, 관련 산출물, 적용 기준, 완료와 승인 조건. 이를 받치는 연결 기반은 산출물 공통 식별자, 산출물 사이의 관계, 기준의 버전과 접근 권한, 문서와 위키, RAG, 그래프로 구조화한 지식이다. 식별자와 관계를 유지하는 방법은 [[Requirements-Traceability#에이전트 작업 맥락으로 쓰는 추적 정보|요구사항 추적성]]을 따른다.

이름에 주의한다. 삼성SDS는 SDLC 전 과정의 정보와 판단 기준을 연결해 AI가 수행할 작업으로 구성하고 실행 결과를 다시 개발 흐름에 반영하는 체계를 AI DLC라고 부른다. AWS의 [[AI-DLC|AI-DLC(AI-Driven Development Life Cycle)]]와 이름이 겹친다. 같은 공급사의 다른 발표들은 이 이름을 AI 주도 개발 라이프 사이클(보험 코어 발표의 각주) 또는 AI 기반 개발 라이프사이클(FDE 발표, 자사 AI DLC 방법론으로 표기하고 분석, 아키텍처, 설계, 개발, 검증, 운영 단계를 든다)로 풀어 적는다. 어느 발표에도 AWS 방법론과의 관계는 나오지 않아 같은 것인지 별개인지 확인하지 못했다.

## 실행 하네스는 시스템에 직접 닿되 통제 안에서 돈다

사람이 조회해 전달하던 맥락을 에이전트가 직접 모으게 하려면 기업 시스템 앞에 AI 접근 계층을 둔다. 이슈 관리, 위키, 저장소, CI 같은 표준 개발 도구와 설계 표준(아키텍처, API), 환경과 배포(릴리스, 승인), 품질과 보안(테스트, 취약점), 서비스와 운영(로그, 정책) 같은 기업 고유 체계를 잇는다. 기존 커넥터를 재사용하고, 맥락을 구조화하고, 업무를 도구로 만들되 권한, 최신성, 승인, 감사를 이 계층에서 지킨다. 조회에서 끝내지 않고 허용된 도구로 변경과 검증까지 하며, 커넥터와 사내 업무 도구는 프로젝트마다 다시 만들지 않고 표준 자산으로 관리한다. 관문의 구조는 [[MCP-Gateway-Architecture|MCP 게이트웨이]]를 따른다.

| 하네스 요소 | 하는 일 |
|---|---|
| 맥락 경계 | 필요한 맥락만 준다 |
| 도구 사용 | 저장소(검색, 변경, 이력), 셸(허용 명령), 빌드 도구, DB(스키마 조회, SQL 실행), 테스트를 연결한다 |
| 상태와 피드백 | 작업 상태와 결과를 다음 시도에 반영한다 |
| 검증과 통제 | 권한, 검증, 중단 조건을 건다 |

모델은 추론하고, 에이전트는 이 도구로 탐색, 계획, 실행, 검증을 돌며, 실패하면 수정하고 다시 계획한다. 하네스는 상태와 종료 조건을 관리한다. 금융에서는 이 경로에 규제와 내부 정책을 넣어 권한, 승인, 검증, 감사 이력을 일관되게 남긴다. 호출마다 허용(즉시 실행), 승인 필요(사용자 검토 대기), 금지(차단)를 판정하는 구조와 신원, 승인, 롤백, 감사의 네 통제는 [[Agent-Governance-Controls|에이전트 거버넌스 통제]]와 같다.

## 금융 코드 변경은 영향 범위부터 통제한다

금융 시스템에서는 작은 수정도 바깥으로 번진다.

1. 코드와 설정: 소스 파일, 프레임워크, SQL
2. 데이터, 배치, 인터페이스: DB, 배치 순서, API 계약, 메시지
3. 업무 처리: 거래 처리, 정산 처리, 고객 서비스, 대외 연계
4. 운영과 통제: 회계, 모니터링, 규제 보고

그래서 영향 범위가 넓고, 거래 오류, 정산 불일치, 보고 오류로 이어질 수 있으며, 무엇을 왜 바꾸는지 설명해야 하고, 검증, 승인, 로그를 남겨 나중에 확인할 수 있어야 한다. 통제된 변경은 다음 순서로 흐른다.

| 단계 | 내용 |
|---|---|
| 업무 이슈 | 장애와 버그, 정책과 규정 변경, 신규 요구, 시스템 개선. 관련 코드, 설계 문서, 도메인 규칙, 인터페이스를 함께 모은다 |
| 영향 분석과 작업 계획 | 영향 범위, 수정 지점, 위험과 의존성, 작업 단위와 일정 |
| 통제 | 역할 기반 접근, 영향 범위 승인, 변경 티켓 발행, 정책과 규칙 가드레일 |
| 제한된 수정 | 허용 범위 안의 수정, 코딩 가이드 준수, 빌드와 단위 테스트, 변경 로그 |
| 검증과 리뷰 | 코드 리뷰와 승인, 빌드와 테스트, 정적 분석과 보안 검증 |

결과는 변경 검증 패키지로 묶는다: 변경 내역(diff), 영향 범위(영향받는 시스템과 데이터), 테스트 결과(자동, 수동), 로그(실행 로그와 오류), 승인 이력(승인자, 시각, 사유). 실행 범위를 저장소, 파일, 명령, 기간으로 미리 승인받으면 승인 범위 밖의 diff를 기계적으로 거부할 수 있다(설계 판단). 실행 권한은 읽기 전용 분석, 제안, 승인 범위 안의 수정, 빌드와 테스트 자동화, 반복 운영 순으로 근거가 쌓인 범위부터 넓힌다. 읽기 전용 분석의 산출물은 [[Agentic-Legacy-Code-Conversion#읽기 전용 분석부터 시작한다|레거시 분석]]에 있다.

## 작업 위임에서 흐름 운영으로

사람이 작업을 골라 지시하고 결과를 매번 확인하는 방식에서, 신규 이슈, 코드 변경, 테스트 실패, 보안 경고, 정기 작업 같은 개발 이벤트가 작업을 시작하고 에이전트가 다음 행동을 정하는 방식으로 옮긴다. 기준을 충족하면 다음 단계로 넘어가고, 사람은 승인 권한이 필요하거나 정보가 부족한 예외에만 개입하며, 예외가 보완되면 흐름이 재개된다. 트리거로 일감을 찾는 바깥 루프의 일반형은 [[Harness-Engineering|하네스 엔지니어링]], 트리거를 판단 파이프라인으로 두는 방법은 [[Production-Agent-Architecture-Delegation#트리거는 판단 파이프라인으로 둔다|위임 경계]]에 있다.

이벤트 기반 실행은 같은 이벤트의 중복 처리, 실패를 반복하는 루프와 비용 증가를 부를 수 있다. 이벤트마다 중복 제거 키, 재시도 상한과 예산을 둔다(설계 판단).

## 자동화 뒤에 남는 판단을 자산으로 바꾼다

자동으로 판정할 수 있는 결과(통과, 차단, 재시도)는 빨리 처리되지만 영향 범위 해석, 예외와 위험 판단, 승인과 책임 결정은 사람의 대기열에 쌓인다. 반복되는 판단은 다음 실행에 남겨 대기열을 줄인다.

1. 실행 이력(로그, 훅, 판단)에서 반복 패턴(예외, 실패, 수정)을 찾는다.
2. 원인을 진단하고, 룰과 평가, 스킬과 흐름, 맥락과 지식, 도구와 연계 가운데 어디에 반영할지 정한다.
3. 평가하고 승인해 버전을 붙인다.
4. 단계적으로 적용하고 감시한다. 효과를 잰 뒤 다시 수집한다.

자산화 원칙은 셋이다. 기록과 자산을 구분해 재사용 가치와 적용 조건을 검토한다. 반복성, 안정성, 변동성과 위험도, 책임 수준으로 자동화에 맞는지 판단한다. 운영 반영은 평가와 버전 승인, 단계 적용, 감시와 롤백으로 통제한다. 규칙과 스킬도 배포물이라 잘못 들어간 규칙 하나가 다음 실행 전체에 퍼지므로 코드처럼 버전과 롤백을 둔다(해석). 기록된 판단 원칙으로 결정 대기열을 줄인 사례는 [[AI-Native-Org#결정 병목을 기록된 판단 원칙으로 줄이는 시도|AI 네이티브 조직]]에 있다.

## 점검 질문

- 작업마다 읽는 데이터의 등급으로 모델 환경을 정했고, 내부 통제형 환경의 모델을 평가 세트로 확인했는가
- 에이전트에 넘기는 작업에 목적, 변경 대상, 범위 제약, 관련 산출물, 적용 기준, 완료와 승인 조건이 있는가
- 요구, 설계, 코드, 테스트를 잇는 공통 식별자와 기준의 버전이 있는가
- 변경마다 영향 범위 승인, 실행 범위 제한, 변경 검증 패키지가 남는가
- 이벤트 기반 실행에 중복 제거, 재시도 상한, 예산이 있는가
- 사람의 판단 대기열을 재고, 반복 판단을 규칙이나 스킬로 바꿀 때 평가, 버전, 롤백을 거치는가

## 사례 (2026년 9월 발표 기준, 공급사 발표)

- **사내 개발 처리량:** 2025년에서 2026년으로 1인당 개발 코드 줄 수가 3,239에서 32,841(10.1배), 총 기능 개발 건수가 1,146에서 2,640(2.3배), 변경 파일 수가 589에서 2,577(4.4배)로 늘었다고 밝혔다. 측정 범위와 품질 지표는 공개되지 않았고, 코드 줄 수는 생산성 척도가 아니다([[Software-Productivity-Measurement|소프트웨어 생산성 측정의 함정]]).
- **작업 맥락 구성:** 작업 맥락을 연결한 뒤 협업 생산성이 30% 올랐다고 밝혔지만 측정 방법과 기준선은 공개되지 않았다.
- **금융 프로젝트의 코드 에이전트 설문:** MAU 550명, 15개 프로젝트에서 지속 사용 의향 4.02점(5점 만점), 30% 이상 생산성 향상을 체감했다는 응답 75.5%였다. 주요 활용은 기존 코드 이해와 구조, 영향도 분석 60%, API와 SQL, 테스트 코드 구현 47%, 오류와 실행 로그 분석 44%(복수 응답)였다. 자기 보고 설문이며 측정한 생산성이 아니다([[Software-Productivity-Measurement#AI 도구 설문을 생산성 근거로 읽는 법|AI 도구 설문 해석]]).
- **권한 통제가 필요한 근거로 든 사고:** 발표는 과도한 권한을 받은 에이전트가 운영 환경을 지운 두 사례를 든다. 첫째는 발표가 A사(2026.02)로만 적은 사례로, 시기와 설명으로 보아 2026년 2월 Financial Times가 보도한 2025년 12월의 13시간 AWS 장애로 보인다(해석). 에이전트가 환경을 지우고 다시 만들었다는 이 보도에 대해 Amazon은 2026-02-20 공식 글에서 원인은 AI가 아니라 잘못 설정된 접근 통제(역할)에 따른 사용자 오류이며 영향은 한 리전의 단일 서비스(AWS Cost Explorer)였다고 반박하고, 운영 접근에 동료 검토를 의무화하는 등 보호 장치를 더했다고 밝혔다. 13시간과 삭제 경위는 보도 기준이며 보도 원문은 대조하지 못했다. 둘째는 2026년 4월 PocketOS 사례로, 과도한 권한의 API 토큰을 쓴 에이전트가 자기 판단만으로 운영 볼륨을 9초 만에 삭제했다는 내용이다(발표 자료 인용, 1차 자료 미대조). 두 사례 모두 작업에 필요한 범위보다 넓은 자격 증명이 핵심 조건이다(해석).
