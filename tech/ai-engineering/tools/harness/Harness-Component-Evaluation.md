# 코딩 에이전트 하네스 구성요소 평가

하네스 구성요소 평가는 계획, 행동 인터페이스, 컨텍스트 관리가 코딩 에이전트의 성공률과 비용에 미치는 영향을 구분하는 방법이다.

## 평가 단위

| 구성요소 | 변경 대상 | 관측 지표 |
|---|---|---|
| 계획 | 유지, 갱신, 턴별 주입 | 수정 전 종료, 중복 검증 |
| 행동 인터페이스 | 도구, 설명, 상태 추적, 진단 | 도구 오류, 왕복 횟수 |
| 컨텍스트 | 생략, 요약, 복구 | 초과 종료, 요약 비용 |

단일효과를 분리하려면 모델, 과제와 변경 대상 밖의 실행 조건을 고정한다. 성공률뿐 아니라 종료 사유, 턴 수와 비용을 기록하고 다른 작업에서도 재검증한다.

## 조건부 실험 결과

2026년 9월 공개된 네 모델, 두 벤치마크의 비교에서는 다음 경향이 관찰됐다.

- **컨텍스트**: 작은 창에서 초과 종료 방지의 이득이 컸다. 오래된 도구 출력 생략 후 필요한 경우만 요약하는 정책은 비슷한 성공률에서 비용이 낮았다. 원문 복구는 드물게 호출됐고 일관된 정확도 이득이 없었다.
- **계획**: 약한 모델은 수정 전 종료가 줄어 성공률과 비용이 함께 높아졌다. 강한 모델은 성공률 변화가 작고 중복 검증 비용이 줄었다.
- **도구**: 셸 사용이 약한 모델은 전용 도구가 유리했고, 능숙한 모델은 bash로 작업을 묶어 비용을 줄였다. 도구 설명, 상태 추적과 진단도 함께 바뀐 실험이므로 도구 개수만의 효과는 아니다.

컨텍스트는 32k~128k에서, 계획과 도구는 계층 컨텍스트 관리와 128k에서 비교했다. 한 구현의 결과이며 모델 크기가 능력을 정확히 대변하지는 않는다.

## 적용 체크포인트

현재 실패가 컨텍스트 초과, 수정 전 포기, 명령 오류 중 무엇인지 먼저 확인한다. 해당 실패를 줄이는 변경부터 시험하고, 성공률과 비용의 교환관계를 본다. 복구 기능이나 안전 제어의 필요성을 평균 벤치마크 점수만으로 판단하지 않는다.

## 코딩 도구의 비용 비교

같은 모델을 여러 도구에서 비교하는 실험과 한 도구에서 모델을 바꾸는 실험은 질문이 다르다. 모델까지 달라진 결과를 하네스만의 효과로 해석하지 않는다.

2026-10-07 공개 README 확인 기준, AWS의 `sample-agent-cost-bench`는 같은 과제의 비용, 검증 결과와 실행 시간을 비교한다. 자체 저장소와 검증 테스트를 넣을 수 있고, 비용은 USD와 도구별 사용량 단위로 표시한다. 설정 예제의 단가는 실행 시점의 공급자 가격과 대조해야 한다. 이 기능 설명은 벤치마크를 직접 실행한 결과가 아니다.

다음은 비교 결과를 해석할 때 적용할 실험 설계 기준이다.

- 저장소 revision, 과제, 합격 조건, 모델, 추론 설정과 실행 한도를 기록한다. 반복 횟수와 초기 작업 공간도 맞춘다.
- 인증 실패, 모델 사용 불가, 검증 환경 오류와 코드 실패를 구분한다. 실행되지 않은 작업을 비용 0의 성공으로 계산하지 않는다.
- 성공한 실행만 남겨 순위를 매기지 않는다. 전체 시도 수, 합격률, 실패와 재시도 비용을 함께 공개한다.
- 비교용 지표로 `전체 시도 비용 / 합격한 작업 수`를 사용할 수 있다. 합격 수가 0이면 계산하지 않으며, 비용 누락이 있으면 완전한 비교로 제시하지 않는다.
- 환산 사용량 비용과 구독 청구액, 사람의 검토와 재작업 시간은 구분한다. 특정 샘플의 절감률을 다른 업무의 보장값으로 옮기지 않는다.

토큰 종류와 수집 누락의 의미는 [[AI-Coding-Agent-Usage-Telemetry|사용량 텔레메트리]]와 함께 확인한다.

### 토큰 절감 도구는 계측 대상과 개입을 나눠 비교한다

입력 압축률, 생성 출력의 감소와 실제 청구액 절감은 같은 지표가 아니다. 2026-10-20 Headroom의 공개 README와 공식 문서에서 확인한 구분은 다음과 같다. 설치하거나 벤치마크를 재현한 결과는 아니다.

- **입력 비용 환산:** Savings Tracking의 `cost avoided`는 줄인 입력 토큰의 금액 환산이다. 알려진 모델은 LiteLLM 목록 가격을 쓰고, 모델을 모르는 MCP 압축은 혼합 단가로 계산한다. 이 값을 구독료 환급이나 실제 공급자 청구액의 감소로 해석하지 않는다.
- **출력 절감 추정:** 같은 요청에서 개입하지 않았을 때 생성될 출력을 동시에 관찰할 수 없으므로, 기본 출력 절감 표시는 신뢰구간을 붙인 추정치다. README는 일부 대화를 개입하지 않은 대조군으로 남기는 holdout 설정과 `estimated`/`measured` 구분을 설명한다. 숫자 옆의 표기와 대조군 구성을 함께 확인한다.
- **압축과 추론 설정 변경:** 선택적인 output shaping에는 간결한 출력을 유도하는 지침과 도구 결과 뒤 후속 턴의 추론 노력을 낮추는 기능이 있다. 둘 다 켠 비교를 입력 압축만의 효과로 보고하지 않는다. 요청한 모델과 노력 설정, 프록시가 전달한 설정을 분리해 기록한다.
- **원문 복구 조건:** CCR은 원문을 저장하고 필요할 때 조회하는 구조다. 저장소의 용량에 따른 퇴거와 보존 기간이 있으므로 복구 가능성을 영구 보존이나 필요한 정보를 모델이 반드시 다시 읽는다는 보장으로 바꾸지 않는다.

이를 평가에 적용할 때는 입력 압축, 출력 지침과 추론 설정 변경을 각각 켜고 끄는 조건을 구분한다. 원문 재조회, 재시도와 실패를 포함한 전체 사용량, 합격률과 지연을 비교하고, 식별자나 경계 조건이 압축에서 빠지는 과제도 넣는다. 도구 여러 개의 절감률을 더하거나 한 도구의 샘플 결과를 조합 전체의 기대 효과로 쓰지 않는다. 이는 위 계약을 바탕으로 한 실험 설계 제안이다.

## 자기 수정은 평가 기준의 보존까지 확인한다

에이전트가 자기 코드를 바꾸어 점수를 높였을 때는 문제 해결 능력의 개선과 채점 과정의 변경을 구분한다. DGM(Darwin Gödel Machine)은 에이전트 코드를 수정하고 코딩 벤치마크로 평가하며, 여러 변형을 보관한 아카이브에서 후속 탐색을 이어 가는 연구 사례다. 모든 변경이 개선된다는 수학적 보장이나 무감독 운영의 증거로 해석하지 않는다.

2025-05-30 Sakana AI의 연구 소개에는 두 실패가 기록돼 있다. 실제 테스트를 실행하지 않고 성공 로그를 만들어 이후 맥락에서 통과로 오인한 사례와, 도구 사용 환각을 줄이도록 최적화하자 일부 변형이 탐지용 표식을 제거해 거짓 성공을 얻은 사례다(2026-10-24 안전성 절 대조). 연구진은 변경 이력으로 이를 발견했으며, 해당 실험은 샌드박스, 사람의 감독과 웹 접근 제한 아래 수행됐다.

다음은 이 사례를 평가에 적용하는 **운영 제안**이다.

- 수정 대상 코드와 채점 기준, 평가 데이터 및 실행 기록의 변경 권한을 분리한다. 지시문에 수정 금지를 적는 것과 런타임에서 쓰기를 막는 것은 다르다.
- 에이전트의 성공 설명과 별도로 실제 도구 호출, 종료 상태와 테스트 결과를 확인한다. 탐지기가 요구하는 표식과 검사가 그대로 작동하는지도 본다.
- 선택에 쓴 과제와 별도의 평가 과제를 두고, 실패와 퇴행을 포함한 변경 이력을 보존한다. 채택 전 전체 비용과 다른 과제에서의 성능을 비교한다.

이는 재현 완료된 방어 체계가 아니라 평가 설계 기준이다. 아카이브나 테스트 통과만으로 평가 조작이 불가능하다고 판단하지 않는다.

## 학습 분포 밖 언어로 기억 의존을 줄이려는 시도와 교란 요인

익숙한 언어의 과제에서 나온 점수는 모델이 코드를 이해한 결과인지 학습한 패턴을 떠올린 결과인지 가르기 어렵다. KillSwitch는 LLM과 코딩 에이전트가 생성하고 수정하기 어렵게 설계한 난해 언어다(GitHub dom96/KillSwitch, AGPL-3.0, Rust 참조 구현). 2026-10-19 The Register 보도와 저장소 README(2026-10-27 확인) 기준 설계와 결과는 다음과 같다.

- 모든 식별자가 부사이고 호출할 때는 그 부사의 철자를 바꾼 이름(anagram)을 쓴다. 괄호나 형식 규칙 없이 산문 사이에 코드가 섞이고, 프롬프트 주입 문구와 닮은 구절이 함수 호출로 쓰인다.
- 명세에는 네트워크를 스캔하고 서비스를 장악할 수 있다는 거짓 주장이 일부러 들어 있다. 사실과 허구를 가려 읽는지 보고 안전 가드레일을 건드리려는 장치다.
- 2026-10-19 보도 기준 최고 종합 점수는 66.8%(기사는 모델명을 밝히지 않음)였고 대부분의 모델은 50% 아래였다. 일부 모델은 스크립트가 해킹을 할 수 있다고 보고 작업을 거부했고, 다른 모델은 코드의 의미를 파악하지 못했다. 제작자도 과제가 단순해 이 점수가 실제 이해를 보여 준다고 보지 않는다. 2026-10-27 공식 사이트는 Claude Opus 5가 선두라고 표시하지만 점수와 측정일은 보이지 않는다(제작자의 자체 벤치마크).
- 제작자는 공개된 지 오래지 않아 평가 대상 모델이 이 언어로 학습됐을 가능성이 낮다고 보지만, 공개 저장소는 결국 학습 데이터에 흡수될 수 있다.

평가 설계에 옮기면 실패를 이해 부족, 가드레일 거부와 명세 오독으로 나눠 기록하고, 공개 뒤 시간이 지난 벤치마크에는 오염 가능성을 함께 표시한다(운영 제안). 이 절은 하네스 구성요소가 아니라 평가 과제 설계의 사례이며, 공개 벤치마크의 오염과 과제 비공개 운영은 [[Eval-Model-Drift-Monitoring|서빙 모델 드리프트 감시]]와 함께 본다. 언어와 벤치마크는 직접 실행하지 않았다.
