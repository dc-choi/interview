# 코딩 에이전트 하네스 구성요소 평가

하네스 구성요소 평가는 계획, 행동 인터페이스, 컨텍스트 관리가 코딩 에이전트의 성공률과 비용에 미치는 영향을 구분하는 방법이다.

## 평가 단위

| 구성요소 | 변경 대상 | 관측 지표 |
|---|---|---|
| 계획 | 유지, 갱신, 턴별 주입 | 수정 전 종료, 중복 검증 |
| 행동 인터페이스 | 도구, 설명, 상태 추적, 진단 | 도구 오류, 왕복 횟수 |
| 컨텍스트 | 생략, 요약, 복구 | 초과 종료, 요약 비용 |

단일효과를 분리하려면 모델, 과제와 변경 대상 밖의 실행 조건을 고정한다. 성공률뿐 아니라 종료 사유, 턴 수와 비용을 기록하고 다른 작업에서도 재검증한다.

## 조건부 실험 결과

2026년 9월 공개된 네 모델, 두 벤치마크의 비교에서는 다음 경향이 관찰됐다.

- **컨텍스트**: 작은 창에서 초과 종료 방지의 이득이 컸다. 오래된 도구 출력 생략 후 필요한 경우만 요약하는 정책은 비슷한 성공률에서 비용이 낮았다. 원문 복구는 드물게 호출됐고 일관된 정확도 이득이 없었다.
- **계획**: 약한 모델은 수정 전 종료가 줄어 성공률과 비용이 함께 높아졌다. 강한 모델은 성공률 변화가 작고 중복 검증 비용이 줄었다.
- **도구**: 셸 사용이 약한 모델은 전용 도구가 유리했고, 능숙한 모델은 bash로 작업을 묶어 비용을 줄였다. 도구 설명, 상태 추적과 진단도 함께 바뀐 실험이므로 도구 개수만의 효과는 아니다.

컨텍스트는 32k~128k에서, 계획과 도구는 계층 컨텍스트 관리와 128k에서 비교했다. 한 구현의 결과이며 모델 크기가 능력을 정확히 대변하지는 않는다.

## 적용 체크포인트

현재 실패가 컨텍스트 초과, 수정 전 포기, 명령 오류 중 무엇인지 먼저 확인한다. 해당 실패를 줄이는 변경부터 시험하고, 성공률과 비용의 교환관계를 본다. 복구 기능이나 안전 제어의 필요성을 평균 벤치마크 점수만으로 판단하지 않는다.

## 코딩 도구의 비용 비교

같은 모델을 여러 도구에서 비교하는 실험과 한 도구에서 모델을 바꾸는 실험은 질문이 다르다. 모델까지 달라진 결과를 하네스만의 효과로 해석하지 않는다.

2026-10-07 공개 README 확인 기준, AWS의 `sample-agent-cost-bench`는 같은 과제의 비용, 검증 결과와 실행 시간을 비교한다. 자체 저장소와 검증 테스트를 넣을 수 있고, 비용은 USD와 도구별 사용량 단위로 표시한다. 설정 예제의 단가는 실행 시점의 공급자 가격과 대조해야 한다. 이 기능 설명은 벤치마크를 직접 실행한 결과가 아니다.

다음은 비교 결과를 해석할 때 적용할 실험 설계 기준이다.

- 저장소 revision, 과제, 합격 조건, 모델, 추론 설정과 실행 한도를 기록한다. 반복 횟수와 초기 작업 공간도 맞춘다.
- 인증 실패, 모델 사용 불가, 검증 환경 오류와 코드 실패를 구분한다. 실행되지 않은 작업을 비용 0의 성공으로 계산하지 않는다.
- 성공한 실행만 남겨 순위를 매기지 않는다. 전체 시도 수, 합격률, 실패와 재시도 비용을 함께 공개한다.
- 비교용 지표로 `전체 시도 비용 / 합격한 작업 수`를 사용할 수 있다. 합격 수가 0이면 계산하지 않으며, 비용 누락이 있으면 완전한 비교로 제시하지 않는다.
- 환산 사용량 비용과 구독 청구액, 사람의 검토와 재작업 시간은 구분한다. 특정 샘플의 절감률을 다른 업무의 보장값으로 옮기지 않는다.

토큰 종류와 수집 누락의 의미는 [[AI-Coding-Agent-Usage-Telemetry|사용량 텔레메트리]]와 함께 확인한다.

### 모델을 바꾸면 하네스 순위도 다시 잰다

하네스와 모델의 조합 전체를 같은 과제로 돌리면 하네스의 효과가 모델마다 같은지 볼 수 있다. Runta가 2026-11-17 공개한 FrontierHarness Eval v1.1은 18개 하네스에서 나온 22개 구성(DeepSeek Harness 프로필 4개와 OpenCode 두 버전을 따로 셈)과 Baseten이 서빙한 공개 모델 5개(GLM-5.3, GLM-5.3 Flash, DeepSeek V4.1 Flash 1017, Muse Spark Open, Kimi-K3)를 터미널 과제 62개에 4번씩, 모두 27,280번 돌렸다. Harbor 평가 프레임워크에서 하네스 기본 설정과 최대 추론 강도를 쓰고 시도마다 새 런타임을 만들었다가 지웠으며, 보상 해킹으로 판정한 216건(온라인 조회 163건 포함)은 0점으로 셌다. 2026-11-18 공개 글로 대조했고 재현하지 않았다.

- **통과당 비용과 선택 규칙**: 과제당 평균 비용을 통과율로 나눈 통과당 비용이 가장 낮은 하네스를 고르되, 통과당 비용이 30% 이내로 더 들면서 통과율이 5점 이상 높은 후보가 있으면 그쪽을 고른다. 비용은 Baseten 정가에 토큰 수를 곱한 추정치다.
- **비용의 대부분은 모델이 정한다**: 과제당 비용(로그)의 분산 분석에서 모델이 92.8%, 하네스가 2.3%, 조합(상호작용과 잡음)이 4.9%를 설명했다. 그래도 모델을 고정하면 하네스에 따라 과제당 비용이 1.8~5.0배, 통과당 비용이 1.9~4.9배 달랐다.
- **가장 싼 하네스가 모델마다 다르다**: Codex CLI는 GLM-5.3에서 통과당 비용 1위($0.803)였지만 Kimi-K3에서는 16위였다. 데이터를 반으로 나눠 다시 매긴 순위의 상관은 같은 모델끼리 0.71, 다른 모델끼리 0.26이었다. 과제를 4,000번 다시 뽑았을 때 GLM-5.3과 Codex CLI 조합은 99.6% 1위를 지켰지만, 나머지 네 모델의 1위는 근접한 후보들 가운데 가장 자주 이긴 하네스였다(25~53%).
- **비싼 하네스가 더 통과하지 않는다**: 모델별 과제당 비용과 통과율의 순위 상관은 −0.39에서 +0.22였고, 통과율 1위 하네스의 비용 순위는 22개 중 5위에서 20위였다.
- **단계 수가 비용을 설명한다**: 첫 요청 크기, 도구 수와 캐시 적중률은 통과당 비용을 예측하지 못했고 실행 단계 수만 순위 상관 +0.51(p = 0.015)이었다. 단계마다 전체 문맥을 다시 보내 시도당 평균 입력이 200만~480만 토큰이었다. 첫 요청이 가장 작은 mini-SWE-agent(882토큰)도 통과 한 번에 38단계가 들어 통과당 비용 17위였다.
- **실패에 쓴 비용**: 채점된 실행 비용의 64.5%가 통과하지 못한 시도에 들었다(실패 52.7%, 시간 초과 11.8%). 모델별 최적으로 고른 다섯 하네스에서도 실패한 시도의 68%(Pi)~82%(Codex CLI)는 시간 제한에 걸린 것이 아니라 최종 답을 내고 끝났으므로, 완료 선언을 검증 없이 성공으로 세지 않는다.
- **한계**: 공개 모델만 한 사업자에서 서빙했으므로 비공개 모델이나 다른 사업자의 캐시 동작과 단가에서는 순위가 달라질 수 있다. 통과율의 95% 구간이 약 ±10점이라 몇 점 차이는 동률로 본다. Runta는 토큰 효율을 내세우는 에이전트 실행 계층을 파는 회사이고 이 순위표를 서빙 사업자 Baseten과 협력해 27,280회 실행에 토큰 830억 개를 써서 만들었다고 밝히므로, 측정 주체의 이해관계도 결과와 함께 적는다.

적용하면, 모델을 바꿀 때 하네스 후보도 자기 과제로 다시 비교하고, 하네스를 고칠 때는 첫 요청의 토큰보다 통과까지 걸리는 단계 수를 먼저 줄인다. 통과당 비용은 실패 시도까지 넣은 위의 `전체 시도 비용 / 합격한 작업 수`와 같은 계산이다.

### 토큰 절감 도구는 계측 대상과 개입을 나눠 비교한다

입력 압축률, 생성 출력의 감소와 실제 청구액 절감은 같은 지표가 아니다. 2026-10-20 Headroom의 공개 README와 공식 문서에서 확인한 구분은 다음과 같다. 설치하거나 벤치마크를 재현한 결과는 아니다.

- **입력 비용 환산:** Savings Tracking의 `cost avoided`는 줄인 입력 토큰의 금액 환산이다. 알려진 모델은 LiteLLM 목록 가격을 쓰고, 모델을 모르는 MCP 압축은 혼합 단가로 계산한다. 이 값을 구독료 환급이나 실제 공급자 청구액의 감소로 해석하지 않는다.
- **출력 절감 추정:** 같은 요청에서 개입하지 않았을 때 생성될 출력을 동시에 관찰할 수 없으므로, 기본 출력 절감 표시는 신뢰구간을 붙인 추정치다. README는 일부 대화를 개입하지 않은 대조군으로 남기는 holdout 설정과 `estimated`/`measured` 구분을 설명한다. 숫자 옆의 표기와 대조군 구성을 함께 확인한다.
- **압축과 추론 설정 변경:** 선택적인 output shaping에는 간결한 출력을 유도하는 지침과 도구 결과 뒤 후속 턴의 추론 노력을 낮추는 기능이 있다. 둘 다 켠 비교를 입력 압축만의 효과로 보고하지 않는다. 요청한 모델과 노력 설정, 프록시가 전달한 설정을 분리해 기록한다.
- **원문 복구 조건:** CCR은 원문을 저장하고 필요할 때 조회하는 구조다. 저장소의 용량에 따른 퇴거와 보존 기간이 있으므로 복구 가능성을 영구 보존이나 필요한 정보를 모델이 반드시 다시 읽는다는 보장으로 바꾸지 않는다.

이를 평가에 적용할 때는 입력 압축, 출력 지침과 추론 설정 변경을 각각 켜고 끄는 조건을 구분한다. 원문 재조회, 재시도와 실패를 포함한 전체 사용량, 합격률과 지연을 비교하고, 식별자나 경계 조건이 압축에서 빠지는 과제도 넣는다. 도구 여러 개의 절감률을 더하거나 한 도구의 샘플 결과를 조합 전체의 기대 효과로 쓰지 않는다. 이는 위 계약을 바탕으로 한 실험 설계 제안이다.

### 경험 기반 비용 제어는 반복되는 환경 비용을 겨냥한다

입력을 압축하는 대신 과거 세션에서 반복된 낭비를 찾아 다음 세션의 하네스 설정을 바꾸는 방식도 있다. 모델과 에이전트 코드는 그대로 두고 바깥에서 제어한다. Microsoft와 UC Berkeley의 TokenEconomizer(논문 arXiv 2610.22732, 2026-10-15 제출, 저장소는 Apache-2.0)는 다음 세 개입을 쓴다. 2026-11-17 README와 논문으로 확인했으며 설치하거나 재현하지 않았다.

| 개입 | 줄이는 낭비 | README 기본값과 동작 |
|---|---|---|
| micro-skills | 테스트 명령, 필요한 환경 변수, 파일 위치를 세션마다 다시 시행착오로 찾는 비용 | 기본 꺼짐. 세 세션에서 확인된 사실을 세션 시작 지시로 넣고, 이후 세션이 반박하면 뺀다 |
| tool pruning | 쓰지 않는 도구 정의가 요청마다 차지하는 입력 토큰 | 기본 켜짐. 일정 횟수의 프롬프트나 세션 동안 호출되지 않은 도구를 각 에이전트의 설정 파일에 거부 목록으로 쓰고, `toolprune restore`로 되돌린다 |
| loop guard | 같은 실패를 반복하거나 오류가 쌓이는 실패 루프 | 기본 켜짐. 같은 실패가 반복되거나 오류가 쌓이는 턴은 사용자의 에이전트로 판정 모델을 불러 막혔는지 보고, 평소 길이의 일정 배수를 넘기며 같은 수정과 실패를 되풀이하는 턴은 판정 없이 처리한다. 막혔다고 보면 다른 접근을 권하는 메모를 한 턴에 한 번 넣는다. 잘 끝난 턴이 기본 5개 쌓인 뒤부터 개입한다. 제품은 턴을 직접 멈추지 않고 사용자에게 중단 방법을 안내한다 |

- **보고된 효과:** SWE-bench 6개 저장소의 277개 과제를 저장소별 시간 순서로 풀게 한 실험에서, 에이전트와 모델 조합 다섯 개 모두 캐시를 반영한 평균 비용이 18.4~30.9% 낮았다. 판정과 지식 제안 같은 제어기 자체의 모델 호출 비용을 포함한 값이다. Pass@1은 네 조합에서 올랐고 한 조합에서 1.0점 내렸다. 이 값은 세 개입을 모두 켜고, 리다이렉트 뒤에도 막히면 제어기가 실행을 끝내는 논문 구성의 결과다. micro-skills가 꺼져 있고 턴을 멈추지 않는 README 기본 설정의 기대치로 옮기지 않는다. Claude Code 두 조합의 단독 개입 실험에서 tool pruning은 13.2%와 17.7%, micro-skills는 11.8%와 14.3%를 줄였다.
- **효과의 전제:** 논문은 절감의 원천을 환경에 따라 되풀이되는 토큰 비용으로 설명한다. 저장소가 과제마다 바뀌는 보안 감사 과제에서도 micro-skills 없이 tool pruning과 loop guard만으로 6.4~19.6%를 줄였다고 보고했다. 제품의 학습 상태는 에이전트와 저장소별로 따로 쌓이므로 같은 저장소를 반복해 쓸 때 누적되고, 한 에이전트에서 배운 것이 다른 에이전트로 옮겨 가지 않는다. 논문은 SWE-bench 과제 흐름이 실제 사용자 세션이 아니라 관련된 별개 수정이라는 점, 오래된 지식, 필요해진 도구의 제거, 생산적인 작업을 루프로 오판할 위험을 한계로 든다.
- **판단 비용의 비교:** 추론 노력을 낮춘 기준선도 비용을 줄였지만 논문 실험에서 Pass@1을 1.8~10.3점 떨어뜨렸다. 절감 도구를 비교할 때는 같은 합격률에서의 전체 비용을 봐야 한다는 위의 기준과 같은 이유다.

도입 판단에 옮기면, 주로 쓰는 저장소 하나에서 켜고 끈 기간의 비슷한 작업을 합격률과 전체 비용으로 비교하고, 제거된 도구 목록과 주입된 지식을 주기적으로 검토한다(운영 제안). 도구 정의가 차지하는 고정 비용은 [[Agent-Context-Budget|컨텍스트 예산]]과 함께 본다.

## 자기 수정은 평가 기준의 보존까지 확인한다

에이전트가 자기 코드를 바꾸어 점수를 높였을 때는 문제 해결 능력의 개선과 채점 과정의 변경을 구분한다. DGM(Darwin Gödel Machine)은 에이전트 코드를 수정하고 코딩 벤치마크로 평가하며, 여러 변형을 보관한 아카이브에서 후속 탐색을 이어 가는 연구 사례다. 모든 변경이 개선된다는 수학적 보장이나 무감독 운영의 증거로 해석하지 않는다.

2025-05-30 Sakana AI의 연구 소개에는 두 실패가 기록돼 있다. 실제 테스트를 실행하지 않고 성공 로그를 만들어 이후 맥락에서 통과로 오인한 사례와, 도구 사용 환각을 줄이도록 최적화하자 일부 변형이 탐지용 표식을 제거해 거짓 성공을 얻은 사례다(2026-10-24 안전성 절 대조). 연구진은 변경 이력으로 이를 발견했으며, 해당 실험은 샌드박스, 사람의 감독과 웹 접근 제한 아래 수행됐다.

다음은 이 사례를 평가에 적용하는 **운영 제안**이다.

- 수정 대상 코드와 채점 기준, 평가 데이터 및 실행 기록의 변경 권한을 분리한다. 지시문에 수정 금지를 적는 것과 런타임에서 쓰기를 막는 것은 다르다.
- 에이전트의 성공 설명과 별도로 실제 도구 호출, 종료 상태와 테스트 결과를 확인한다. 탐지기가 요구하는 표식과 검사가 그대로 작동하는지도 본다.
- 선택에 쓴 과제와 별도의 평가 과제를 두고, 실패와 퇴행을 포함한 변경 이력을 보존한다. 채택 전 전체 비용과 다른 과제에서의 성능을 비교한다.

이는 재현 완료된 방어 체계가 아니라 평가 설계 기준이다. 아카이브나 테스트 통과만으로 평가 조작이 불가능하다고 판단하지 않는다.

## 팀이 만든 하네스도 정기적으로 평가한다

팀과 조직이 스킬, 플러그인, AGENTS.md와 결정론적 가드레일로 자기 하네스를 만들기 시작하면 그 하네스가 실제로 작동하는지가 평가 대상이 된다. Thoughtworks Technology Radar Vol.35(2026-11)는 조직 규모의 하네스 운영(Harness engineering at scale)을 네 테마 중 하나로 두고, 가드레일은 실제로 작동할 때만 코딩 에이전트에 도움이 된다는 이유로 harness quality evaluation을 Assess에 올렸다.

- 결정론적 부분(훅, 린트, 권한 규칙 같은 가드레일)은 테스트를 먼저 쓰는 방식으로 만들고, 가드레일마다 동작을 확인하는 테스트 묶음을 둔다.
- 비결정론적 부분(스킬, 플러그인)은 별도 평가 도구로 평가한다. 블립은 PluginEval을 예로 든다.
- 두 평가 모두 야간 실행이나 CI와 함께 정기적으로 돌린다.

같은 판은 여러 팀이 함께 쓸 스킬, 도구, 내부 맥락 연결, 승인된 기술, ADR, 배포 경로 안내, 훅과 보안 정책을 모은 조직 공용 계층을 enterprise harness(Assess)로 부르고 개발자 경험 플랫폼의 에이전트판에 비유한다. 잘하는 방법에 아직 합의가 없으므로 얇고 연합된(thin and federated) 형태로 시작해 실험의 여지를 남기고 효과가 확인된 것을 거둬들이라고 권한다. InfoQ의 2026 동향 보고서(2026-10-30)도 하네스 엔지니어링을 채택 곡선의 혁신가(innovators) 단계에 두었다. 두 자료 모두 편집진의 판단이며 채택률을 잰 결과가 아니다. 조직 공용 실행 계층의 구성은 [[AI-Native-Org|AI-Native 조직]], 어디에 게이트를 걸지는 [[Harness-Gate-Placement|게이트 배치]]를 본다.

## 하네스를 바꿀 때는 고정 지시와 확장 경로를 비교한다

같은 모델이라도 하네스가 요청마다 붙이는 시스템 프롬프트와 도구 설명, 편집기 연결과 확장 방식이 작업 경험을 바꾼다. 2026-09-21 공개(11-07 갱신)된 한 개발자의 이전 기록은 Claude Code에서 Pi로 옮긴 이유를 이렇게 든다. 개인의 경험과 집계이며 두 하네스를 같은 과제로 비교한 결과는 아니다.

- CLAUDE.md와 AGENTS.md를 복사나 심볼릭 링크로 함께 관리하는 부담. 작성자가 이전을 결정한 다음 날 Anthropic이 AGENTS.md 지원을 발표했다고 적었다(현재 동작은 [[Agent-Repository-Instructions-Hosts#Claude Code|호스트별 발견과 적용]]).
- VS Code에서 편집기 선택 영역을 한 세션만 받는 제약. Pi에서는 여러 탭에서 쓰는 확장을 약 20분 만에 직접 만들었다.
- 작성자 집계로 그해 244개 릴리스 중 4분의 3 넘게 시스템 프롬프트나 도구 설명을 바꿨다. 이런 변경은 모델 이름이 같아도 행동을 바꿀 수 있다([[Eval-Model-Drift-Monitoring#같은 이름 아래에서 바뀌는 네 층|드리프트의 하네스 층]]).
- 기본 Bash 도구 설명만 약 3,000토큰인 요청당 고정 비용([[Agent-Context-Budget|컨텍스트 예산]]).

Pi 공식 사이트(2026-11-09 확인)는 Pi를 MIT 라이선스의 최소 에이전트 하네스로 소개하고, 확장을 도구, 명령, 단축키, 이벤트와 TUI 전체에 접근하는 TypeScript 모듈로 설명한다. 하위 에이전트와 권한 확인 팝업은 기본으로 두지 않고 컨테이너나 확장으로 대신하라고 안내하므로, 이런 하네스로 옮기면 권한 경계를 직접 설계해야 한다(추론). 바꾸기 전 비교 항목(운영 제안)은 버전 고정과 변경 이력 추적, 요청당 고정 토큰의 실측, 확장 API와 그 확장의 신뢰 경계, 지침 파일의 이식성, 권한과 격리의 기본값이다.

## 학습 분포 밖 언어로 기억 의존을 줄이려는 시도와 교란 요인

익숙한 언어의 과제에서 나온 점수는 모델이 코드를 이해한 결과인지 학습한 패턴을 떠올린 결과인지 가르기 어렵다. KillSwitch는 LLM과 코딩 에이전트가 생성하고 수정하기 어렵게 설계한 난해 언어다(GitHub dom96/KillSwitch, AGPL-3.0, Rust 참조 구현). 2026-10-19 The Register 보도와 저장소 README(2026-10-27 확인) 기준 설계와 결과는 다음과 같다.

- 모든 식별자가 부사이고 호출할 때는 그 부사의 철자를 바꾼 이름(anagram)을 쓴다. 괄호나 형식 규칙 없이 산문 사이에 코드가 섞이고, 프롬프트 주입 문구와 닮은 구절이 함수 호출로 쓰인다.
- 명세에는 네트워크를 스캔하고 서비스를 장악할 수 있다는 거짓 주장이 일부러 들어 있다. 사실과 허구를 가려 읽는지 보고 안전 가드레일을 건드리려는 장치다.
- 2026-10-19 보도 기준 최고 종합 점수는 66.8%(기사는 모델명을 밝히지 않음)였고 대부분의 모델은 50% 아래였다. 일부 모델은 스크립트가 해킹을 할 수 있다고 보고 작업을 거부했고, 다른 모델은 코드의 의미를 파악하지 못했다. 제작자도 과제가 단순해 이 점수가 실제 이해를 보여 준다고 보지 않는다. 2026-10-27 공식 사이트는 Claude Opus 5가 선두라고 표시하지만 점수와 측정일은 보이지 않는다(제작자의 자체 벤치마크).
- 제작자는 공개된 지 오래지 않아 평가 대상 모델이 이 언어로 학습됐을 가능성이 낮다고 보지만, 공개 저장소는 결국 학습 데이터에 흡수될 수 있다.

평가 설계에 옮기면 실패를 이해 부족, 가드레일 거부와 명세 오독으로 나눠 기록하고, 공개 뒤 시간이 지난 벤치마크에는 오염 가능성을 함께 표시한다(운영 제안). 이 절은 하네스 구성요소가 아니라 평가 과제 설계의 사례이며, 공개 벤치마크의 오염과 과제 비공개 운영은 [[Eval-Model-Drift-Monitoring|서빙 모델 드리프트 감시]]와 함께 본다. 언어와 벤치마크는 직접 실행하지 않았다.
