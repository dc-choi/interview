# Claude Code 무인 장기 세션 — 사람이 하던 통제를 옮기는 자리

사람이 명령마다 승인하고 변경마다 읽던 세션에서는 사람이 방향 조정, 승인, 제한, 결과 확인과 세션 시작을 모두 맡았다. 여러 세션을 몇 시간씩 돌리면 이 일을 사람이 계속할 수 없다. 사람이 빠진 자리는 모델, 하네스, 실행 환경 가운데 하나가 맡아야 하고, 보장이 필요한 일은 모델이 아닌 하네스와 환경에 둔다. 이 문서는 그 배치를 정리한다. 규칙 문법은 [[Claude-Code-Config-Permissions|설정과 권한]], 게이트를 거는 위치의 일반 원칙은 [[Harness-Gate-Placement|게이트 배치]]에 있다.

## 사람이 하던 일의 새 자리

| 사람이 하던 일 | 맡는 곳 | 수단 | 보장 수준 |
|---|---|---|---|
| 방향 조정 | 모델 | 줄인 프로젝트 지침, 완료 기준을 적은 요청 | 대체로 따르지만 보장은 아님 |
| 명령 승인 | 하네스 | auto 권한 모드의 분류기, 신뢰 범위 설정 | 분류기의 판단이며 놓치는 경우가 있음 |
| 금지 | 하네스와 환경 | deny 규칙, 샌드박스, 클라우드 세션 | 규칙과 OS가 강제 |
| 결과 확인 | 하네스와 CI | 훅, 테스트, CI, 새 컨텍스트의 리뷰 | 통과와 실패로 판정 |
| 세션 시작과 추적 | 모델 | 코디네이터 세션이 작업 스레드를 시작 | 결과 보고와 실제 통과를 구분해 확인 |

## 프로젝트 지침은 코드에 없는 것만 남긴다

- 예전 모델에 맞춰 넣은 대문자 강조와 느낌표가 붙은 금지 문구는 지금 모델에서 과한 도구 호출과 엉뚱한 방향을 만든다고 한다(제품 팀의 발표 설명). 공식 문서도 무시되는 줄에 IMPORTANT를 붙이는 것으로는 고쳐지지 않고, 예외가 없어야 하는 규칙은 훅으로 옮기라고 안내한다.
- 사용하는 스택이나 어느 파일을 볼지처럼 코드에서 알 수 있는 내용은 지운다. 코드에 직접 참조가 없지만 다른 서비스가 아직 쓰는 부분처럼 코드만으로 알 수 없는 사실을 남긴다.
- `/doctor`는 코드에서 알아낼 수 있는 내용의 삭제를 제안한다. `/doctor prompt-audit`(v2.1.283 이상)는 예전 모델용으로 쓴 지시, 없는 파일이나 명령을 가리키는 지시와 서로 충돌하는 지시를 찾아 수정안을 보고하며, 적용을 요청하기 전에는 파일을 바꾸지 않는다. 기본 대상은 `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`와 `.claude/`, `~/.claude/` 아래의 rules, skills, commands, subagents, output styles다.

## 승인은 분류기에, 금지는 규칙에 둔다

- auto 모드에서 승인 요청이 잦으면 `autoMode.environment`에 신뢰하는 저장소, 버킷과 도메인을 평문으로 적는다. 분류기가 이 문장을 자연어 규칙으로 읽는다.
- 분류기는 보장이 아니다. 발표자는 사람이 승인하는 조건과 auto 모드를 비교한 자사 연구에서 명백히 위험한 명령을 사람은 약 14%만 막았고 auto 모드는 89%를 막았다고 소개했다. 사람보다 낫지만 열에 하나는 통과했다는 뜻이다. 이 연구의 원문은 찾지 못했다. Anthropic의 auto 모드 설계 글은 실제 과잉 행동 52건에서 전체 파이프라인의 미탐률을 17%로 적고 있어 수치의 출처와 측정 대상이 다르다.
- deny 규칙은 분류기보다 먼저 평가되고 모든 권한 모드에서 차단한다. 무엇을 규칙으로 둘지는 한 번 틀렸을 때 되돌릴 수 있는가로 정한다(발표의 기준). 잘못 쓴 코드는 되돌릴 수 있으니 모델에 맡기고, 커밋하지 않은 변경의 삭제나 트랜스크립트에 남는 키 읽기는 규칙으로 막는다.
- auto 모드의 기본 허용 목록에는 `.env`를 읽어 해당 API에 자격 증명을 보내는 동작이 들어 있다. 읽기 자체를 막으려면 `Read(.env)` deny를 둔다. 이 규칙은 `cat` 같은 인식 가능한 Bash 읽기 명령도 막는다.

## 권한 규칙이 못 보는 부작용은 환경이 막는다

권한 규칙은 도구 호출의 실행 여부만 정하고, 실행된 명령이 무엇에 닿는지는 제한하지 못한다. `npm test`는 정상 명령이라 사람이 보고 있었어도 허용했겠지만, 그 안에서 의존성 코드와 모델이 방금 쓴 스크립트가 함께 실행된다. 그중 하나가 악성이면 `.env`나 SSH 키를 읽어 외부로 보낼 수 있다.

- **샌드박스:** Bash 명령과 그 자식 프로세스의 파일, 네트워크 접근을 OS가 제한한다. `Read`와 `Edit` deny 규칙의 경로가 샌드박스 설정에 합쳐지므로, 테스트 도중 의존성이 `.env`를 열려 해도 OS가 막는다. 기본 읽기 범위는 넓으므로 SSH 키 같은 경로는 따로 막는다. 내장 파일 도구, MCP 서버와 훅은 샌드박스 밖에서 실행된다.
- **클라우드 세션:** 새 머신이 저장소 사본만 받아 일하므로 git에 없는 `.env`와 로컬 키가 따라가지 않는다. 필요한 키는 모델에 보이지 않게 주입하고, 네트워크는 패키지 레지스트리와 GitHub 등으로 제한된 상태에서 필요한 도메인을 추가한다(발표 설명, 세부는 [[Claude-Code-Cloud-Security|클라우드 실행과 보안]]). 노트북을 닫아도 세션이 이어진다.
- 머신은 버려도 머신 밖으로 나간 것은 남는다. 푸시한 커밋과 커넥터로 보낸 메시지는 되돌릴 수 없으므로 클라우드에서도 auto 모드와 저장소에 커밋한 deny 규칙을 그대로 쓴다.

## 결과 확인은 통과와 실패로 돌아오는 지점에 둔다

같은 요청(인증을 새 API로 옮기기)에서도 실행마다 옛 API를 남기거나, 새 로그인에만 적용하거나, 전원을 로그아웃시키는 결과가 나올 수 있고 모두 그럴듯해 보인다. 몇 시간 분량의 변경을 끝에서 전부 읽는 대신 테스트, 빌드, 스크린샷처럼 통과와 실패로 돌아오는 확인 지점을 중간에 두고 그 결과를 검토한다.

1. **요청에 적는다:** 완료의 모습을 적고, 각자 테스트를 가진 작은 작업으로 나누게 하고, 실제 실행 출력을 보여 달라고 한다. 지시이므로 보장은 아니다.
2. **반드시 돌아야 하는 것은 훅에 둔다:** 파일 편집 뒤 린터, 작업을 완료로 표시할 때 바꾼 부분의 테스트, 세션을 끝낼 때 전체 테스트를 실행한다.
3. **종료 코드는 2여야 한다:** 테스트 도구는 실패하면 보통 1로 끝나는데, 훅이 1로 끝나면 차단하지 않는 오류로 처리되어 작업이 완료로 표시된다. 2로 끝나야 `Stop`은 종료를, `TaskCompleted`는 완료 표시를 막고 실패 내용이 모델에 전달된다. 훅 스크립트가 테스트 실패를 2로 바꿔 내보내는지 확인한다.
4. **CI가 모든 세션에 같은 검사를 건다:** 세션이 어떻게 설정됐든 PR에서 같은 검사를 받는다. 실패한 검사를 모델이 보고 고치게 하면 사람의 리뷰가 검사로 잡힐 문제에 쓰이지 않는다.
5. **리뷰 강도는 위험에 맞춘다:** 발표한 팀은 모든 PR을 작성 세션이 아닌 새 컨텍스트의 모델이 먼저 리뷰하고, 발견한 버그는 별도 에이전트 묶음이 다시 확인한다. 문서와 문구 변경은 자동 검사만 통과하면 합치고, 일반 제품 변경은 한 명, 위험한 변경은 두 명이 리뷰한다(한 팀의 사례).

## 세션 시작까지 넘길 때

코디네이터 세션에 할 일을 주면 작업을 나눠 스레드를 시작하고 결과를 확인해, 끝나지 않은 결과는 돌려보낸다. 코디네이터에는 판단과 검토에 강한 모델, 스레드에는 구현에 강한 모델을 따로 지정할 수 있다. 구조와 한계는 [[Claude-Code-Projects|Projects의 조율과 작업 격리]]에 있다. 넘기기 전에 확인할 것은 CI가 중요한 문제를 실제로 잡는가, 환경의 네트워크 범위와 비밀 값, 설정 스크립트가 준비됐는가다. 평소보다 큰 작업 하나를 맡겨 어디서 멈추고 어디서 사람이 필요한지 본 뒤 그 지점을 다음에 넘긴다(발표의 제안).

## 한계

- 운영 방식과 수치(하루 변경 2,500건에서 3만 건, 14%와 89%)는 제품을 만드는 회사의 발표 내용이다. 변경 건수의 원 게시글과 비교 연구의 원문은 대조하지 못했다.
- 리뷰 강도 구분과 모델 배치는 한 팀의 사례이며 다른 조직의 코드베이스와 위험에서 같은 결과를 보장하지 않는다.
- 발표는 음성 인식 전사로 확인했다. 화면의 설정 예시와 시연은 확인하지 못했다.
- 병렬 세션은 사용량을 빠르게 늘린다. 비용은 이 발표가 다루지 않았다.
