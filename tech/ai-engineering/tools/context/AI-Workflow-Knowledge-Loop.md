# AI 업무와 지식 환류

## 정의와 적용 조건

업무를 분석하고 구현하는 과정에서 결정과 검증 근거를 기록하고, 다음 요청의 시작점으로 재사용하는 방식이다. 코드 생성 이후에도 분석, 인수인계와 운영 판단이 병목으로 남는 팀에 적용할 수 있다.

정책이 담당자의 기억과 코드에만 있으면 부재 시 원인 파악과 온보딩이 함께 느려진다. 인력 부족으로 기록을 미루고, 기록 부족 때문에 새 사람이 독립하지 못하는 악순환이 생긴다. 구현 속도 향상만으로 해소하기 어려운 지식 전달 문제다.

## 분석 공간과 구현 공간

여러 서비스가 연결된 요청은 저장소별 역할과 호출 관계를 함께 살핀다. 공통 분석 공간에는 서비스 지도와 업무 기록을 두고, 실제 변경은 각 저장소의 규칙과 검증 절차를 따른다. 저장소를 함께 조회하는 것은 Git 이력을 합치는 모노레포 전환과 별개다.

예를 들어 화면의 지급 실패가 외부 연동이나 데이터 수집에서 시작될 수 있다. 처음 보인 증상의 서비스만 고치지 않고 요청이 이동한 경계를 추적한다.

## 업무에서 기록으로 이어지는 절차

| 단계 | 남길 결과 |
|---|---|
| 접수 | 장애, 문의, 개발 요청의 분류와 해결 조건 |
| 분석과 설계 | 과거 기록, 원인 후보, 변경 범위, 전체 이슈와 저장소별 하위 작업 |
| 구현 | 대상 저장소의 변경과 작업 간 의존성 |
| 검증 | 자체 점검, 독립 리뷰, QA 결과와 사람의 최종 판단 |
| 기록 | 요청, 이슈, PR, 변경 이유와 결과를 연결한 이력 |

반복 절차는 실행 명령이나 스킬로 정형화한다. 다음 분석에서 기록을 먼저 찾고 현재 소스와 대조해야 환류가 성립한다. 문서 생성만으로 지식의 정확성이 높아지지는 않는다.

## 이력과 참조 문서를 나눈다

- **이력**: 개별 작업의 판단과 결과를 남긴다.
- **종합 문서**: 여러 이력을 인용해 한 주제의 흐름을 설명한다.
- **참조 문서**: 구조, 용어와 운영 방법의 진입점을 제공한다.

사람은 검색과 링크로, 에이전트는 작은 색인에서 필요한 원문으로 이동하게 한다. 오래된 문서, 고립된 문서와 충돌은 수정 후보로 검토한다. `llms.txt`는 LLM 친화적 안내와 링크를 제공하려는 **제안 형식**이다(2026-10-01 제안 사이트 확인). 모든 에이전트의 자동 탐색이나 읽기를 보장하는 규격으로 전제하지 않는다.

## 운영 표준, 작업 경험과 현재 환경을 분리한다

운영 지식을 Git으로 공유할 때는 변경 주기와 권위가 다른 정보를 나눈다. 다음은 공개 운영 사례를 재사용하기 위한 설계 기준이며, 특정 도구를 설치하면 자동으로 갖춰지는 기능은 아니다.

| 정보 | 예시 | 재사용할 때 확인할 것 |
|---|---|---|
| 운영 표준 | 승인된 작업 절차, 보안 정책, 코드 규약 | 누가 승인했고 어느 환경에 적용되는가 |
| 작업 경험 | 장애 원인, 업그레이드 실패와 해결 과정 | 당시 조건과 검증 결과가 현재에도 맞는가 |
| 현재 환경 | 대상 계정, 클러스터와 리소스 상태 | 이번 실행 시점에 조회한 값인가 |

표준과 경험은 담당 영역별 문서로 버전 관리하되, 경험 한 건을 곧바로 공통 정책으로 승격하지 않는다. 작업이 끝나면 조건, 실패한 시도, 해결 과정과 확인 결과를 검토해 공유하고, 다음 작업자는 동기화한 기록을 현재 환경과 대조한다. 과거에 성공한 명령도 지금의 대상과 상태가 다르면 다시 판단해야 한다.

환경을 컨텍스트에 넣는 단계와 위험 작업을 차단하는 단계도 구분한다. 프롬프트 제출 시 환경 정보를 수집하는 훅과 도구 실행 직전 호출을 검사하는 훅은 역할이 다르다. 운영 정책을 읽었다는 사실만으로 권한 통제를 입증할 수 없다. 적용 시에는 허용하지 않은 작업이 실제로 거절되는지, 검사 오류가 나도 실행되는 경로가 있는지 별도로 확인한다. 이 경계는 [[Harness-Engineering|하네스 엔지니어링]]과 함께 검토한다.

## 반복 리뷰를 규칙 후보로 바꾼다

별도 평가 버튼의 반응만 기다리기보다 평소 코드 리뷰에 남긴 판단을 규칙 후보의 근거로 활용할 수 있다. 다만 같은 말이 반복됐다는 사실은 팀 합의나 모든 코드에 대한 적용을 뜻하지 않는다. 다음은 공개 개발 사례를 재사용하기 위한 절차다.

1. 같은 취지의 리뷰를 묶고 원문 근거, 반복 횟수와 대상 코드를 연결한다. AI 리뷰의 반복도 별도 의견처럼 누적될 수 있으므로 횟수만으로 규칙의 타당성을 판정하지 않는다.
2. 기존 규칙과 대조해 새 규칙 후보와 기존 규칙의 보강 후보를 구분한다. 세 번 반복되면 검토한다는 기준은 운영 선택지이지 검증된 보편 임계값이 아니다.
3. 검토자는 반복된 사례의 조건이 같은지, 반대 의견이나 예외가 있는지 확인한다. 초안에는 적용 범위, 예외, 피할 코드와 권장 코드를 함께 남긴다.
4. 문서 내용뿐 아니라 저장 위치와 읽기 경로를 검토한다. 승인된 같은 기준을 코드 작성과 리뷰 양쪽에서 찾을 수 있어야 한다.
5. 후속 리뷰에서 같은 문제가 재발하는지 확인한다. 규칙 내용이 부족한지, 필요한 시점에 읽히지 않았는지 구분해 보완한다.

제품 정책, 구현 가이드, 필수 규칙과 아키텍처 결정 기록은 역할에 맞게 나눈다. 공통 규칙은 기본 진입점에 연결하고, 테스트나 특정 라이브러리의 상세 기준은 관련 작업에서 읽도록 연결한다. 이 구조는 특정 AI 도구가 자동으로 문서를 읽는다는 보장이 아니며, 실제 입력과 적용 결과를 확인해야 한다.

규칙 초안의 생성, 규칙 승인, 코드 리뷰 승인과 코드 병합도 별개 단계다. GitHub의 필수 리뷰와 상태 검사는 병합 조건으로 설정할 수 있지만, 모든 필수 조건을 만족했을 때 자동 병합하도록 설정하는 기능도 있다(2026-10-09 공식 문서 확인). 사람의 최종 병합을 운영 경계로 삼으려면 리뷰 프롬프트뿐 아니라 실제 권한과 저장소 설정도 그 경계에 맞는지 확인한다.

## 적용 시 보완할 검증 기준

다음은 이 패턴을 적용할 때 사용할 점검 기준이다.

- 과거 진단은 현재 원인의 후보로 두고 로그, 코드와 재현 조건을 다시 확인한다.
- 분석 초안, 승인된 결정, 구현 완료와 배포 확인을 기록에서 구분한다.
- 원문 접근 권한을 색인과 파생 문서에도 적용한다.
- 독립된 작업만 병렬화하고 공통 계약의 변경 순서를 정한다.
- 문서 수보다 분석 시간, 재작업, 결함 재발과 인수인계 시간을 함께 비교한다.

## 사례의 범위

올라핀테크의 2026년 7월 공개 사례는 팀 축소 후 공통 분석과 업무 기록을 도입한 경험이다. 업무 처리 시간이 평균 절반으로 줄었다는 자체 보고가 있지만, 대조군과 과업별 측정 방법이 공개되지 않아 일반적인 생산성 배수로 해석할 수 없다. 분석 검증, 문서 품질과 팀원 숙련도는 계속 관리해야 할 과제로 남았다.

2026-01-21 업로드된 AWS 공개 발표의 23~28분 구간은 Git 기반 지식 저장소에서 운영 표준과 누적 경험을 분리하고, 작업 시작 시 현재 환경을 확인하는 사례를 설명한다. 업로드 날짜는 발표일과 구분한다. 발표에서 제시한 생산성과 안정성 개선 배수는 일반 효과로 옮기지 않으며, 발표만으로 실제 권한 차단 구현을 검증했다고 보지 않는다. 위 설계 기준의 훅 역할 구분은 2026-10-07 AWS 공개 저장소의 Hooks 문서와 대조했다. 특정 CLI 버전의 설치나 운영 적합성을 검증한 것은 아니다.
