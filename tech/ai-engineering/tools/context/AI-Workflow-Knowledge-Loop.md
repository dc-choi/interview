# AI 업무와 지식 환류

## 정의와 적용 조건

업무를 분석하고 구현하는 과정에서 결정과 검증 근거를 기록하고, 다음 요청의 시작점으로 재사용하는 방식이다. 코드 생성 이후에도 분석, 인수인계와 운영 판단이 병목으로 남는 팀에 적용할 수 있다.

정책이 담당자의 기억과 코드에만 있으면 부재 시 원인 파악과 온보딩이 함께 느려진다. 인력 부족으로 기록을 미루고, 기록 부족 때문에 새 사람이 독립하지 못하는 악순환이 생긴다. 구현 속도 향상만으로 해소하기 어려운 지식 전달 문제다.

## 분석 공간과 구현 공간

여러 서비스가 연결된 요청은 저장소별 역할과 호출 관계를 함께 살핀다. 공통 분석 공간에는 서비스 지도와 업무 기록을 두고, 실제 변경은 각 저장소의 규칙과 검증 절차를 따른다. 저장소를 함께 조회하는 것은 Git 이력을 합치는 모노레포 전환과 별개다.

예를 들어 화면의 지급 실패가 외부 연동이나 데이터 수집에서 시작될 수 있다. 처음 보인 증상의 서비스만 고치지 않고 요청이 이동한 경계를 추적한다.

## 업무에서 기록으로 이어지는 절차

| 단계 | 남길 결과 |
|---|---|
| 접수 | 장애, 문의, 개발 요청의 분류와 해결 조건 |
| 분석과 설계 | 과거 기록, 원인 후보, 변경 범위, 전체 이슈와 저장소별 하위 작업 |
| 구현 | 대상 저장소의 변경과 작업 간 의존성 |
| 검증 | 자체 점검, 독립 리뷰, QA 결과와 사람의 최종 판단 |
| 기록 | 요청, 이슈, PR, 변경 이유와 결과를 연결한 이력 |

반복 절차는 실행 명령이나 스킬로 정형화한다. 다음 분석에서 기록을 먼저 찾고 현재 소스와 대조해야 환류가 성립한다. 문서 생성만으로 지식의 정확성이 높아지지는 않는다.

## 이력과 참조 문서를 나눈다

- **이력**: 개별 작업의 판단과 결과를 남긴다.
- **종합 문서**: 여러 이력을 인용해 한 주제의 흐름을 설명한다.
- **참조 문서**: 구조, 용어와 운영 방법의 진입점을 제공한다.

사람은 검색과 링크로, 에이전트는 작은 색인에서 필요한 원문으로 이동하게 한다. 오래된 문서, 고립된 문서와 충돌은 수정 후보로 검토한다. `llms.txt`는 LLM 친화적 안내와 링크를 제공하려는 **제안 형식**이다(2026-10-01 제안 사이트 확인). 모든 에이전트의 자동 탐색이나 읽기를 보장하는 규격으로 전제하지 않는다.

## 적용 시 보완할 검증 기준

다음은 이 패턴을 적용할 때 사용할 점검 기준이다.

- 과거 진단은 현재 원인의 후보로 두고 로그, 코드와 재현 조건을 다시 확인한다.
- 분석 초안, 승인된 결정, 구현 완료와 배포 확인을 기록에서 구분한다.
- 원문 접근 권한을 색인과 파생 문서에도 적용한다.
- 독립된 작업만 병렬화하고 공통 계약의 변경 순서를 정한다.
- 문서 수보다 분석 시간, 재작업, 결함 재발과 인수인계 시간을 함께 비교한다.

## 사례의 범위

올라핀테크의 2026년 7월 공개 사례는 팀 축소 후 공통 분석과 업무 기록을 도입한 경험이다. 업무 처리 시간이 평균 절반으로 줄었다는 자체 보고가 있지만, 대조군과 과업별 측정 방법이 공개되지 않아 일반적인 생산성 배수로 해석할 수 없다. 분석 검증, 문서 품질과 팀원 숙련도는 계속 관리해야 할 과제로 남았다.
