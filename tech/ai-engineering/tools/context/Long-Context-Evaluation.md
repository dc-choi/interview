# 긴 문맥 평가와 위치 민감도

컨텍스트 윈도우는 모델이 입력을 받을 수 있는 용량이다. 그 안의 근거를 정확히 찾아 답에 반영하는 능력과는 구분한다. **유효 문맥 길이**는 특정 과제와 평가 기준에서 허용할 품질을 유지하는 범위이며, 모든 과제에 통용되는 고정 토큰 수가 아니다.

## 길이와 위치를 나누어 평가한다

| 평가 축 | 바꾸는 조건 | 확인하는 실패 |
| --- | --- | --- |
| 위치 | 질문, 근거와 전체 길이를 유지하고 근거 위치를 앞, 중간, 뒤로 이동 | 같은 근거를 특정 위치에서 활용하지 못함 |
| 길이 | 정답에 필요한 근거를 유지하고 방해 문서를 늘림 | 정보량 증가에 따른 누락과 혼동 |
| 과제 | 단일 값 찾기, 여러 근거 연결, 전체 항목 집계 | 단순 검색 성공을 복합 추론 성공으로 오인 |

2023년 Lost in the Middle 연구는 다중 문서 질의응답과 키-값 검색에서 위치에 따른 성능 차이를 관찰했다. 평가된 모델은 대체로 앞이나 끝의 근거를 더 잘 활용했고 중간에서 성능이 낮아졌다. 이는 해당 모델과 과제의 관찰이다. 모든 최신 모델의 회수율이 절반으로 떨어진다는 법칙으로 쓰지 않는다.

2024년 RULER는 17개 모델을 13개 과제로 평가하며 단일 정보 검색 외에 여러 단계의 연결 추적과 집계를 포함했다. 단순 검색 점수가 좋아도 긴 입력과 복잡한 과제의 품질을 보장하지 않았다. 다만 논문의 평가는 길이별 점수이며 근거 위치별 성능을 통제해 보고하지 않았다. 따라서 RULER의 길이 효과를 중간 위치 취약성의 직접 증거로 바꾸지 않는다.

두 연구는 현재 서비스의 정확도나 특정 모델의 안전한 입력 상한을 제공하지 않는다. 모델, 프롬프트와 실제 질문이 바뀌면 다시 평가한다.

## 검색 실패와 근거 활용 실패

필요한 문서가 검색되지 않았거나 최종 프롬프트 조립 중 잘렸다면 입력 공급의 실패다. 근거가 실제 입력에 있는데도 위치를 바꿀 때 정답률이 달라지는 경우를 위치 민감도로 구분한다. 실패한 답변만 보고 내부 attention의 원인을 확정하지 않는다.

예를 들어 보존 기간을 묻는 설명용 과제에 정답이 37일인 정책을 넣는다. 동일한 정책을 앞, 중간, 뒤에 두고 정답과 인용한 근거를 함께 비교한다. 먼저 세 입력 모두에 정책 전문이 포함됐는지 확인해야 한다.

## RAG와 전체 투입의 비교

긴 윈도우는 전체 문서를 넣는 선택지를 넓힌다. RAG는 먼저 근거 후보를 줄이지만 검색 누락이 생길 수 있다. 검색 결과를 넉넉하게 모아 긴 문맥에 넣는 혼합 방식도 비교 대상이다. 검색 자체가 위치 민감도를 없애지는 않는다.

비교 시에는 입력 토큰 수만으로 전체 비용과 지연의 배수를 정하지 않는다. 가령 5,000토큰과 500,000토큰의 비는 100이지만, 이는 토큰 수의 비다. 비용에는 적용 단가, 캐시와 출력, 검색 비용을 함께 넣고 지연은 전체 요청에서 측정한다. 특정 제품의 가격이나 지원 윈도우를 가정하지 않는다.

다음은 연구의 평가 축을 실제 서비스에 적용하기 위한 설계 제안이다.

1. 같은 질문과 근거를 고정하고 전체 투입, 검색, 혼합 방식을 비교한다.
2. 입력 길이와 근거 위치를 나누어 바꾸고, 조건과 예외를 함께 요구하는 질문도 넣는다.
3. 정답률, 근거 누락과 인용 오류, 요청 비용과 지연을 따로 기록한다.
4. 검색과 요약에서 원문으로 돌아갈 경로를 보존한다. 짧아졌다는 사실만으로 개선으로 판정하지 않는다.
5. 입력 구성이나 모델을 바꾼 뒤 같은 평가를 반복한다. 배치 순서 조정은 검증할 가설이지 정확도 보장이 아니다.
