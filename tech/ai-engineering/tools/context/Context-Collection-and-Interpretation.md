# 컨텍스트 증강에서 수집과 해석을 분리하기

컨텍스트 증강은 모델이 학습하지 않은 사실, 판단 기준과 관점을 호출 시점에 공급하는 일이다. 대부분의 RAG 설계는 무엇을 가져올지(수집)에 집중한다. 이 문서는 가져온 정보를 질의 목적에 맞게 어떻게 읽을지(해석)를 별도 자원으로 관리하는 설계와, 그 설계가 나온 배경인 자기 증강의 한계와 앞선 기법들을 정리한다. 무엇을 윈도우에 넣고 뺄지의 수요 측 원리는 [[Context-Engineering|컨텍스트 엔지니어링]], 검색 품질 자체는 [[RAG-Retrieval-Engineering|RAG 검색 엔지니어링]]이 정본이다.

## 왜 모델에게 컨텍스트 구성을 통째로 맡기기 어려운가

- **자기 참조의 순환**: 좋은 컨텍스트를 만들라는 지시도 프롬프트다. 모델이 놓치는 관점은 모델이 만든 컨텍스트에서도 똑같이 빠지기 쉽고, 모델이 놓치는 것이 없다면 애초에 증강이 필요 없다. 이 논리는 실무 관찰에서 나온 설명이며 정량 법칙은 아니다.
- **외부 신호 없는 자기 교정의 한계**: Huang 외(ICLR 2024, 2023년 공개)는 외부 피드백 없이 모델 자신의 능력만으로 첫 응답을 고치는 것을 intrinsic self-correction으로 정의했다. GPT-3.5-Turbo, GPT-4, GPT-4-Turbo와 Llama-2로 GSM8K, CommonSenseQA, HotpotQA를 시험했을 때 이 방식은 정답률을 안정적으로 올리지 못했고 오히려 떨어지는 경우가 있었다. 앞선 연구의 개선 일부는 정답 여부를 알려 주는 oracle label에 기대고 있었고 label을 빼면 개선이 사라졌다. 논문 제목의 Yet처럼 그 시점 모델의 결과이며, 이후 모델이 같은 한계를 갖는지는 이 연구로 확정되지 않는다.
- **함의(이 문서의 해석)**: 실행 결과, 정답, 사람이 미리 정한 기준처럼 모델 밖에서 오는 신호가 있을 때 증강과 수정이 나아지는 경향이 있다. 무엇을 근거로 인정하고 어떤 관점으로 보며 언제 충분한지를 모델 밖에서 정해 두는 것을 이 문서의 전제로 둔다. 같은 맥락의 Reflexion은 평가자 신호의 정확도에 효과가 묶인다([[Agent-Loop-Engineering#실패를 글로 남겨 다음 시도에 쓰는 Reflexion|루프 엔지니어링의 Reflexion]]).

위 자기 참조 논리와 아래 고정 체인의 장단점은 출처의 강의에서 발표자가 제시한 실무 관점이다. 반대편 극단인 사람이 질의 유형마다 짠 고정 체인은 단계별 중간 결과를 사람이 검사할 수 있고 재현이 쉽다. 대신 유형이 늘수록 레시피 수와 유지 비용이 늘고, 단계 수만큼 지연과 오류 누적이 커지며, 설계자에게 도메인 경험과 단계 출력이 어떻게 쓰일지에 대한 이해를 함께 요구한다([[LLM-Workflow-Patterns-Chain-vs-Agent|체인과 에이전트]]). 수집과 해석의 분리는 이 둘 사이의 절충을 노린다.

## 앞선 접근의 계보

| 접근 | 외부에서 공급하는 것 | 대표 사례 |
|---|---|---|
| 입력 분류와 전용 처리기 | 사람이 정한 범주와 처리 경로 | 라우팅 |
| 작업 분해와 종합 | 사람이 정한 흐름과 작업자 역할(하위 작업은 실행 시 LLM이 나눈다) | 오케스트레이터와 작업자 |
| 출처 라우팅 | 질의와 관련된 데이터 출처 선택 | RAGRoute |
| 절차 템플릿 재사용 | 문제 유형별 풀이 틀 | Buffer of Thoughts |
| 관점 확장 | 관련 주제 Wikipedia 문서의 목차 | STORM |
| 모델의 맥락 자기 관리 | 기억과 playbook의 갱신 규칙 | 기억 계층, ACE |

- **라우팅과 오케스트레이터**: Anthropic은 2024-12-19 글에서 미리 정한 코드 경로로 LLM과 도구를 엮는 시스템을 workflow, LLM이 스스로 과정과 도구 사용을 정하는 시스템을 agent로 구분했다. 라우팅은 입력을 분류해 전용 후속 작업으로 보내고, 오케스트레이터와 작업자 패턴은 중심 LLM이 입력에 따라 작업을 나눠 작업자 LLM에 맡긴 뒤 결과를 종합한다.
- **출처 라우팅(RAGRoute)**: 여러 데이터 출처를 모두 조회하는 대신 얕은 신경망 분류기로 질의 시점에 관련 출처만 고른다. 저자들은 MIRAGE, MMLU, FeB4RAG에서 통신량을 최대 80.65%, 지연을 최대 52.50% 줄이면서 전체 조회와 비슷한 정확도를 보고했다. MMLU의 종단 정확도는 76.09%로 전체 조회의 77.10%보다 약간 낮았다.
- **절차 템플릿(Buffer of Thoughts)**: problem distiller가 과제에서 핵심 변수, 목표와 제약을 뽑고, 그 결과와 임베딩 유사도가 임계값을 넘는 thought-template을 meta-buffer에서 찾아 문제에 맞게 채운다. buffer manager는 새 풀이에서 템플릿을 증류하고 기존 템플릿과의 최대 유사도가 임계값보다 낮을 때만 추가한다. 비용은 다중 질의 방식(Tree/Graph of Thoughts 등)의 평균 12% 수준이라고 보고했다.
- **관점 확장(STORM)**: LLM이 관련 주제를 고르면 그 Wikipedia 문서의 목차를 추출하고, LLM이 이를 참고해 서로 다른 관점을 정한다. 그다음 관점을 가진 작성자 LLM과 인터넷 출처에 근거해 답하는 전문가 LLM의 대화를 모사해 자료를 모은다. Wikipedia 편집자의 사람 평가에서 개요 기반 RAG 기준선보다 조직성이 좋다고 평가된 글이 25%p(45.0%에서 70.0%), 범위가 넓다고 평가된 글이 10%p(57.5%에서 67.5%, p=0.084) 많았다. 이 문서의 해석으로는, 고정 프롬프트만으로는 같은 관점이 반복되기 쉬우므로 관점의 재료 일부(목차)를 모델 밖의 텍스트에서 가져온 설계다.
- **맥락 자기 관리**: 모델이 무엇을 넣고 뺄지 정하는 계열이다. 반복 재작성이 세부를 잃는 맥락 붕괴는 [[Agent-Memory-Write-and-Consolidation-Failures|기억의 쓰기와 정리 실패]]에 정리돼 있다.

여러 다단계 질의는 첫 검색만으로 필요한 문서가 나오지 않는다. 영화 A의 감독이 태어난 곳은 감독이 누구인지를 먼저 찾아야 하고, 그 답이 두 번째 검색의 입력이 된다. 질의 문장 그대로는 검색용 질의가 아니므로 정보 단위로 나눠 순서대로 확보해야 한다.

## Dual RAG: 사실과 절차를 따로 검색한다

Denis Rothman의 Context Engineering for Multi-Agent Systems(Packt) 3장은 하나의 Pinecone index 안에 두 저장소를 둔다. 사실 저장소는 Researcher가, 절차적 blueprint 저장소는 Context Librarian이 검색한다. Orchestrator가 사실 찾기는 Researcher에게, 작성 방식 검색은 Librarian에게 맡기고, Writer는 사실과 blueprint를 합쳐 제약된 출력을 만든다. Writer는 자기 스타일을 고르지 않고 Librarian이 찾은 지침을 따른다. 책의 3장 blueprint는 형식과 어조 중심이다.

강의 발표자의 해석으로는 이 구조의 핵심 아이디어가 같은 정보 출처라도 해석 절차가 다르면 다른 컨텍스트가 나온다는 것, 즉 무엇을 가져오는가와 어떻게 읽는가를 따로 관리한다는 것이다. 기존 RAG가 질의를 분석해 좋은 검색 결과를 가져오는 수집 쪽에 집중했다면, 이 구조는 검색 결과를 질의 의도에 맞게 해석하는 절차를 별도 자원으로 공급한다.

## 일반화한 설계: 수집기, 절차, 컨텍스트 작성기

아래는 2026-11-12 공개된 스터디 강의에서 발표자가 Dual RAG를 일반화해 제안한 구조다. 발표자 스스로 여러 논문으로 효과가 증명된 수준은 아니며 자신의 도메인에서만 통할 수 있다고 밝혔다. 실무 설계의 출발점으로만 쓴다.

| 역할 | 입력 | 출력 | 비고 |
|---|---|---|---|
| 수집기(Researcher) | 질의 | 출처에서 모은 원자료(문서 조각, 검색 결과, DB 행 등) | 해석하지 않는다. 내부 구현은 하이브리드 검색, 재순위, 질의 재작성, LLM 등 무엇이든 되는 블랙박스 |
| 절차 선택(Librarian) | 질의와 선택된 수집기 | 그 수집기의 출력을 읽는 절차 | 절차를 만들지 않고 미리 등록된 것에서 찾는다 |
| 컨텍스트 작성기(Writer) | 질의, 수집기 출력과 절차의 쌍(여러 쌍 가능) | 증강할 컨텍스트 | 최종 답은 뒤의 실행기가 만든다 |

- **절차의 내용**: 적용 조건, 수집한 정보를 분석하고 평가하는 순서, 질의 목적에 정보가 주는 영향(impact), 컨텍스트로 낼 형태를 담는다. 형식과 어조보다 정보를 어떻게 읽는지가 중심이다. 예를 들어 과거 장애 이력 수집기에 특정 사건 찾기 절차를 붙이면 시기와 서비스가 맞는 기록만 남기고 시점, 원인, 조치를 그대로 추출하며 기록이 없는 항목은 기록 없음으로 표시한다. 보안사고 이력 수집기는 같은 자료라도 원인 분석 질의에는 원인, 방어가 뚫린 지점과 막을 수단 순으로, 고객 공지 질의에는 영향 범위, 복구 시각과 사과 안내 순으로 추출하는 절차를 받는다.
- **조합으로 범위를 넓힌다**: 수집기는 출처, 범주나 권한별로 늘리고 절차는 수집기마다 여러 개를 둔다. 둘의 관계는 N:N이라 권한만 다른 수집기들은 같은 절차 집합을 공유할 수 있다. 새 질의 유형이 생기면 흐름 전체를 다시 짜는 대신 수집기나 절차 몇 개를 더한다.
- **만드는 시점의 경계**: 절차는 사람이 써도 되고 모델이 써도 된다. 중요한 것은 런타임 이전(빌드 시점)에 만들어 두는 것이다. 질의 시점에 모델이 자기 컨텍스트의 기준을 스스로 만들면 앞의 자기 참조 순환으로 돌아간다.
- **라우팅**: 질의로 수집기를 고르고, 질의와 수집기로 절차를 고른다. 설명문 임베딩 유사도나 열거값 하나만 출력하는 구조화 출력 LLM 판정 모두 가능하다. 시스템 전체가 라우팅 정확도에 의존하므로 분류 기준 프롬프트, 이력 기반 튜닝과 라우팅 실험에 투자한다. 하나의 질의에 여러 수집기와 절차를 붙이는 멀티 라우팅도 가능하다.
- **작성기는 하나의 프롬프트**: 질의, 정보와 절차로 컨텍스트를 만들라는 역할은 일반화되어 있어 작성기 종류를 늘릴 필요가 없다. 여러 쌍을 한 번에 넣으면 일부를 무시할 수 있고, 쌍마다 따로 부르면 출처 간 모순을 조정하지 못한다. 한 번에 병합한다면 절차 적용 결과가 서로 모순될 때의 해소 규칙을 프롬프트에 둔다.
- **출력은 덧붙일 수 있어야 한다**: 작성기의 결과는 기존 컨텍스트에 순서나 상호 의존 없이 추가해도 되는 형태여야 관리할 수 있다. 질의를 바꾸거나 가드레일 역할을 하지 않는다.

## 적용 판단

- **위험(발표자 제시)**: 엉뚱한 수집기나 절차를 고르는 라우팅 오류, 같은 정보에 다른 기준이 적용될 때의 절차 충돌, 수집기와 절차를 잘게 나눌수록 커지는 라우팅 혼동.

적용 제안(이 문서의 해석, 미검증):

- **맞을 수 있는 경우**: 같은 데이터 출처를 여러 목적으로 읽어야 하고(분석, 공지, 보고), 질의 유형이 계속 늘어나며, 유형마다 체인을 새로 짤 여력이 없을 때.
- **다른 선택이 나을 수 있는 경우**: 질의 유형이 몇 개로 고정되어 있으면 고정 체인이 더 단순하고 검사하기 쉬울 수 있다. 단일 출처, 단일 목적이면 절차 계층의 추가 비용이 이득보다 클 수 있다.
- **확인 방법**: 효과는 같은 평가 입력으로 일반 RAG와 비교해 확인한다([[Eval-Golden-Set-and-Deploy-Gates|골든셋과 배포 게이트]]).

## 점검 질문

- 이 시스템에서 컨텍스트의 기준(근거 인정, 관점, 충분성)은 누가 언제 정하는가? 질의 시점에 같은 모델이 정한다면 외부 신호는 무엇인가?
- 같은 출처를 서로 다른 목적으로 읽는 질의가 있는가? 그 차이가 프롬프트 분기로 흩어져 있는가, 절차 자원으로 관리되는가?
- 라우팅 오류를 측정하는 평가 세트가 있는가?
