# 팀 공유 지식층: 에이전트가 먼저 읽고 쓰는 팀 문서

팀 공유 지식층은 에이전트가 답하기 전에 먼저 읽고, 일하다 새로 알게 된 것을 그 자리에서 초안으로 반영하는 팀 단위 문서 저장소다. 개인의 기억(first brain)과 개인 메모 도구나 개인 작업 공간(second brain) 위에 팀원 각자가 알게 된 것을 모으는 층이라는 뜻에서 third brain이라고 부르기도 한다.

필요성은 에이전트의 실패에서 드러난다. 알람 원인 분석 에이전트가 데이터 수정 API의 not found 예외를 받아 코드 위치를 정확히 짚고, null 검사 PR을 제안하며, 최근 커밋 작성자를 담당자로 지정했다. 팀이 아는 답은 달랐다. 삭제된 데이터를 수정하려는 요청이라 정상 범위였고, 주간 정리 배치가 처리하므로 PR이 필요 없었으며, 담당자는 두 달 전에 바뀌었다. 이 세 가지는 코드, 로그와 어떤 문서에도 없었고, 더 큰 모델로 바꿔도 같은 답이 나왔다. 추론이 아니라 팀이 당연하게 아는 지식이 빠진 것이다. 신규 입사자가 묻는 질문과 에이전트가 틀리는 질문은 대체로 같다.

이력, 종합 문서와 참조 문서를 나누는 기록 체계는 [[AI-Workflow-Knowledge-Loop|AI 업무와 지식 환류]]에서, 원문을 위키로 합성하는 방식은 [[LLM-Wiki-Knowledge-Compilation|LLM 위키]]에서 다룬다. 이 문서는 팀 문서를 에이전트가 읽고 쓰게 만드는 구조와 그 효과의 측정을 다룬다.

## 무엇을 담고 무엇을 뺄까

모든 지식을 담지 않되, 어떤 지식이든 여기서 출발하면 찾아갈 수 있게 한다.

| 구분 | 대상 | 처리 |
| --- | --- | --- |
| 직접 담음 | 무엇이 어디에 있고 왜 그렇게 정했는지, 알람 원인과 대응, 설정 값과 그 이유 | 지식 페이지 |
| 링크로 넘김 | 코드, 이슈 상세, 절차 원문 | 원문 링크 |
| 담지 않음 | 진행 상태, 일정처럼 자주 바뀌는 값 | 조회 시점에 원문에서 읽음 |

담지 않은 것은 낡을 일도 없다. 대신 영역별로 무엇이 어디에 있고 원문에 어떻게 가는지 알려 주는 라우팅 인덱스 한 장을 둔다. 페이지가 아니라 영역 단위로 적으므로 문서가 늘어도 인덱스는 커지지 않는다.

반영할 때마다 남길지 판단하는 기준도 문서로 둔다. 자동으로만 모으면 다시 볼 일 없는 작업 기록이 쌓이고, 수동으로만 하면 빠진다.

- 팀 단위로 반복해서 참조될 것
- 알람 원인이나 설정 값처럼 잘 바뀌지 않는 것
- 원문, 코드나 실행 결과로 확인한 것

확인하지 않은 추론은 추정이나 확인 필요 표시를 붙여도 넣지 않는다. 읽는 사람이 결국 다시 확인해야 하므로, 확인한 뒤에 남긴다. 조회하면 그대로 믿고 쓰는 층이어야 하기 때문이다.

## 문서 틀

팀에 이미 쓰는 문서 형식이 있으면 바꾸지 않고 쓰기 컨벤션 문서에 적어 에이전트가 따르게 한다. 같은 프롬프트로도 LLM이 쓰는 문서가 매번 달라지는 문제는 저장 위치가 아니라 이 컨벤션으로 푼다.

형식이 없는 팀의 기본값으로는 Diátaxis가 맞다. Diátaxis는 문서를 tutorial, how-to, reference, explanation 네 종류로 나누고 한 문서에 종류를 섞지 않는다. 팀 지식층에서는 배포 절차는 how-to, 설정 값은 reference, 알람 원인 분석은 explanation처럼 절차, 값, 이유 중 무엇을 찾는지로 나누면 에이전트가 페이지를 어떻게 나눌지 흔들리지 않는다. 진행 중인지 끝났는지 같은 실행 상태로 나누는 PARA는 상태가 바뀔 때마다 문서를 옮겨야 하는데, 이 층은 바뀌는 상태를 담지 않고 프로젝트 단위 정리는 이슈 트래커가 맡으므로 맞지 않는다.

## 어디에 적고 어떻게 찾을까

| 기준 | Confluence 같은 위키 | 문서 전용 Git 저장소 | GitHub Wiki |
| --- | --- | --- | --- |
| AI가 읽기 쉬운 형식 | 매크로가 본문보다 많이 섞여 나옴 | Markdown | Markdown만 허용, 매크로 없음 |
| 에이전트 도구로 바로 접근 | 별도 연동 | clone, grep, commit | clone, grep, commit |
| 사람이 보던 곳과의 거리 | 가까움 | 사람이 찾아 읽기 불편 | 위키 뷰어가 따라옴 |

사람이 꾸미기 좋은 형식은 AI가 읽기 어렵다. 사람과 에이전트가 함께 계속 보는 저장소여야 하므로, 형식이 단순하고 clone 한 번으로 전체가 로컬에 오며 변경 이력이 남는 곳이 맞다.

검색은 규모와 질문 형태로 고른다. 문서 수백 장 규모면 전체를 grep해도 1초가 걸리지 않고, 팀 지식은 컴포넌트명, 호스트명, 설정 키처럼 식별력 높은 고유 명사로 찾으므로 키워드 검색이 잘 맞는다. 임베딩 색인은 문서가 바뀔 때마다 다시 만들어야 하지만 Git은 pull 한 번이면 최신이다. 링크로 이어진 Markdown을 에이전트가 따라 읽는 방식과 조각 임베딩 검색의 비교는 [[LLM-Wiki-Knowledge-Compilation#위키를 검색에 더한 효과는 질문 유형에 따라 다르다|LLM 위키의 검색 효과]]에 있다.

## 누가 갱신할까

문서는 만드는 것보다 최신으로 유지하기가 어렵다. 지식은 알람 대응이 끝날 때, 이슈를 닫을 때, 리뷰에서 정정받을 때 드러나는데 문서를 여는 순간은 한참 뒤에 오거나 오지 않는다. 하루 한 번 배치로 문서를 고치면 지식이 언제 드러났는지 모르고, 변경 요약 알림은 곧 노이즈가 된다. 그래서 각자 쓰는 에이전트에 스킬을 얹어, 지식이 드러난 자리에서 에이전트가 초안을 만들고 사람은 반영 여부만 정한다.

| 구성 | 역할 | 호출 |
| --- | --- | --- |
| init 스킬 | 처음 한 번 저장소를 연결 | 사람 |
| 진입 스킬 | 조회와 반영을 언제 호출할지 정한 원칙 한 장과 red flags 표 | 세션 시작 훅이 컨텍스트에 넣음 |
| search 스킬 | 라우팅 인덱스를 거쳐 지식 페이지 조회 | 에이전트가 스스로 |
| update 스킬 | 초안 작성, 자체 점검, diff 제시와 반영 | 에이전트가 스스로 |

설계에서 확인된 점은 다음과 같다. 세션 시작 훅으로 진입 지시문을 넣는 방식은 Superpowers 플러그인의 using-superpowers 구조를 따른 것이다.

- **훅은 통로이고 에이전트를 움직이는 것은 지시문이다.** 조회와 반영을 각각 훅에 붙이지 않고 진입 스킬 하나만 넣는다. 진입 스킬에는 원칙만 두고 실제 절차는 스킬이 호출될 때 불러와 매 세션의 비용을 한 장으로 줄인다.
- **요약 뒤에도 다시 넣는다.** 대화가 길어져 앞부분이 요약으로 접히면 처음 넣은 지시문도 흐려지므로, 요약 뒤와 세션을 이어 열 때 다시 넣는다.
- **red flags 표로 합리화를 막는다.** 에이전트는 이미 아는 내용이다, 너무 사소하다, 남길지 말로만 물어보자, push 성공이 나왔으니 됐다 같은 생각으로 할 일을 건너뛴다. 이런 생각이 들면 실제로는 무엇을 해야 하는지를 표로 적어 진입 스킬에 넣는다. 항목은 실제로 놓친 장면으로 채운다.
- **스킬 description이 곧 트리거다.** 키워드 나열보다 어떤 성격의 질문에 쓰는지로 적고, 일반 지식 질문은 제외한다고 적으면 더 정확히 호출된다.
- **새로 알게 된 순간을 잡는 훅은 없다.** 진입 지시문에 작업 단위가 끝날 때마다 남길 것이 있는지 스스로 점검하라고 적는다.

스킬과 훅의 역할 구분은 [[Agent-Skills#스킬 vs 훅 — 무엇을 할지 vs 언제 실행될지|에이전트 스킬]]에서 다룬다.

## AI가 쓴 문서를 믿을 수 있게

### 초안을 들고 묻는다

에이전트가 이거 팀 문서에 남길까요라고 빈손으로 물으면 사람은 어떤 문장이 들어갈지 모른 채 정해야 하고, 남기기로 하면 그제야 초안이 생겨 한 번 더 확인해야 한다. 순서를 바꿔 에이전트가 초안을 먼저 만들고 사실, 형식, 중복과 모호한 표현을 스스로 점검한 뒤 diff를 보여 주며 묻는다.

- 승인 전에는 commit은 물론 `git add`도 하지 않는다. 사람은 한 글자로 승인한다.
- 쓰기 컨벤션이 없는 저장소면 지식보다 컨벤션을 먼저 확정해 같은 diff에 넣는다.
- 사람이 없는 예약 작업에서는 push하지 않고 승인을 다음 대화로 미룬다.
- 마지막 보고는 원격을 다시 읽어 확인한 커밋 해시다.

예를 들어 문서 동기화가 모두 404로 실패한 원인이 코드가 아니라 동기화 bot 계정의 라이선스 회수였다. 대응이 끝나자 에이전트가 초안 diff를 보였는데 보조 주소를 fallback이라고 적었다. 사람이 staging이라고 바로잡았고, 에이전트가 고쳐 다시 승인받은 뒤 반영했다. 사람이 정정한 바로 그 자리가 승인 게이트의 역할이다.

### 세션마다 작업 공간을 나눈다

한 사람이 세션을 여러 개 띄우거나 팀원 여럿이 동시에 반영하면 공유 clone 하나에서 편집이 섞인다. 한쪽의 `git add`가 다른 쪽의 커밋 전 파일까지 올리고, 한쪽의 reset이 다른 쪽 편집을 지운다.

- 공유 clone은 fetch 전용으로 두고, 편집은 세션마다 자기 git worktree에서 한다.
- push가 충돌하면 rebase를 한 번 시도하고, 그래도 안 되면 worktree를 남겨 두고 사람이 처리한다.
- 성공하면 스크립트가 worktree를 정리한다.

## 스스로 호출되는지 측정한다

스킬 자동 호출의 평가는 시키지 않아도 제때 호출되는지와 가져온 답이 맞는지를 나눠 본다.

| 세트 | 내용 | 채점 |
| --- | --- | --- |
| S | search를 호출해야 하는 질문 | 호출한 도구 |
| U | update를 호출해야 하는 대화 | 호출한 도구 |
| N | 아무것도 호출하면 안 되는 질문 | 호출한 도구 |
| R | 팀 문서에 답이 있는 질문 | LLM judge로 정답 대조 |

N 세트가 핵심이다. 무조건 호출하는 스킬도 호출률은 100%가 나오므로, 호출하지 않는 것이 정답인 사례가 있어야 호출률을 믿을 수 있다. 비교는 기준 조건에서 요소 하나만 바꾸는 방식으로 한다. 요소는 문서 유무, 스킬 유무, 모델, 추론 강도, 함께 설치된 스킬과 도구, 세션 시작 훅 유무다.

발표 기준 측정 결과다. 기준 조건은 Sonnet 5.5, medium 추론 강도, 단독 설치, 문서, 스킬과 훅 모두 있음이다. 수치는 5% 단위 반올림이고 오차는 10% 안팎이다.

| 바꾼 요소 | 결과 |
| --- | --- |
| 기준 조건 | search 호출 100%, 조회 답 정답, update 호출 95%, 오호출 약 10%(주로 시스템 이름이 든 제품 질문) |
| 문서 없음 | 스킬은 호출됐지만 볼 문서가 없어 정답 0% |
| 스킬 없음, 문서는 사내 Git에 둠 | 약 60%만 찾음. 이슈와 코드에서 답을 찾아 예전 결정을 현재처럼 답한 경우가 있었고 시간이 3배 넘게 걸림 |
| 모델 Haiku, Sonnet, Opus 5.5 | update 호출 65%, 95%, 100%, 오호출 5%, 10%, 15%. Opus는 개인 설정이나 확정되지 않은 내용까지 남기려 함 |
| 추론 강도 low, medium, high | update 90%, 95%, 95%로 오차 범위 안 |
| 스킬 약 60개, 도구 약 130개를 함께 설치 | search 100%, update 85%, 오호출 5%로 오차 범위 안 |
| 세션 시작 훅 끔 | update 95%에서 70%. 확정되면 남기겠다, 원하시면 초안을 만들겠다처럼 반영을 미루고 끝냄 |

- 정답을 가른 것은 모델보다 문서였다. 문서가 없으면 Sonnet도 0%였고 문서가 있으면 Haiku도 100%였다.
- 호출을 더 하는 모델은 오호출도 더 한다. 상위 모델일수록 반영할 가치가 없는 내용을 팀 문서에 남기려는 위험을 같이 관리해야 한다.
- search 호출은 모든 조건에서 95% 이상이었고 조회 정답률은 모두 100%여서, 이 테스트셋으로는 모델 차이를 가르지 못했다.

이 수치의 한계도 함께 적어야 한다. 질문 하나로 끝나는 짧은 세션에 고정된 문장으로 물었고, 긴 대화나 개인 설정이 섞인 환경은 재지 않았다. 스킬을 만든 사람이 테스트셋도 만들었고, R 세트 질문은 문서의 표현을 그대로 쓰는 경향이 있었다. 실패 사례를 보고 스킬을 고친 뒤 같은 세트로 다시 재는 일을 반복했으므로 결과는 이 세트에 맞춰져 있다. 다른 팀 문서와 환경에서는 같은 방법으로 다시 재야 한다. 판정 모델 평가의 주의점은 [[Eval-LLM-Judge|LLM judge 평가]]에 있다.

## 트레이드오프와 남은 문제

- 새로 드러난 지식이 문서에 들어가는 경로는 생기지만, 이미 있는 문서가 낡는 문제는 따로 남는다.
- 확인한 것만 남기면 신뢰도는 오르지만 확인 전의 단서는 잃는다. 단서는 이슈나 개인 메모에 두고, 확인한 뒤 옮긴다.
- 사람의 절차는 늘지 않지만 승인 질문이 잦아지면 확인 없이 승인하는 습관이 생길 수 있다. 초안 diff를 작게 유지한다.
- grep 중심 검색은 문서 수백 장 규모와 고유 명사 질문에 맞는 선택이다. 규모가 커지거나 표현이 다른 질문이 늘면 다시 비교한다.

- 담을 것, 링크할 것, 담지 않을 것과 남길 기준이 문서로 정해져 있는가?
- 진입 지시문이 세션 시작과 요약 뒤에 다시 들어가고, red flags 표가 실제로 놓친 장면으로 채워져 있는가?
- 반영 전에 사람이 실제 diff를 보고, 무인 실행은 push하지 않는가?
- 호출 평가에 호출하면 안 되는 사례가 있고, 스킬 작성자와 다른 사람이 만든 질문으로도 쟀는가?
