# 컨텍스트의 생성, 평가, 배포와 관찰

컨텍스트 개발 수명주기는 에이전트에 공급하는 지침, 업무 정의, 예시와 기억을 버전 있는 변경물로 관리하는 방식이다. 코드처럼 관리한다는 말은 문법 검사만으로 품질을 증명한다는 뜻이 아니다. 같은 작업에서 결과와 개입량이 달라지는지 측정해야 한다.

## 네 단계와 남겨야 할 증거

| 단계 | 작업 | 검토할 증거 |
|---|---|---|
| 생성 | 원문에서 정의, 제약과 예시를 추출 | 출처, 적용 범위, 충돌과 불확실성 |
| 평가 | 대표 과업에 후보 컨텍스트 적용 | 기존 버전과 성공률, 회귀, 비용 및 개입량 비교 |
| 배포 | 리뷰한 버전을 필요한 에이전트에 공급 | 버전, 소유자, 의존 자료와 되돌릴 기준 |
| 관찰 | 운영 로그, 실패와 사람의 수정 수집 | 어떤 컨텍스트가 어떤 행동에 영향을 줬는지 추적 |

평가에서는 모델, 하네스, 저장소 revision과 과업을 맞춘다. 같은 조건에서도 결과가 달라질 수 있어 여러 실행과 실패 사례를 살핀다. 비밀 정보와 실행 명령이 포함된 외부 자료는 신뢰 경계에 맞춰 필터링하고, 배포 승인 강도는 행동 위험에 맞춘다.

## 공유 패키지로 다루는 조건

공유할 단위마다 소유권, 변경 이력, 출처와 적용 대상을 둔다. 운영 로그에서 발견한 해결책은 바로 전역 규칙으로 승격하지 않는다. 특정 환경의 우회인지 재사용 가능한 조건인지 확인하고 회귀 과업에 추가한 뒤 배포한다. 이 순환이 학습 효과를 만들 수 있지만 컨텍스트를 많이 쌓는 것 자체가 품질 향상을 보장하지 않는다.

## 조직 맥락 문서의 첫 판

모델은 회사의 이력을 모르는 독자다. 지표 정의, 정책과 내부 용어처럼 추측할 수 없는 정보를 먼저 문서로 만들고 업무 도구와 연결해 팀이 함께 쓴다. 직원과 에이전트가 같은 맥락에서 일하도록 쌓는 이 기록을 회사 두뇌(company brain)라 부르기도 한다.

- **분량과 독자:** 1~2쪽으로 시작하고, 신입 직원이 첫 주에 물을 질문에 답하는 수준으로 쓴다.
- **지표:** 보고하는 숫자마다 계산식, 기준 시스템과 소유자를 적는다. 같은 이름의 지표도 회사마다 정의가 다르다.
- **정책과 승인:** 지출 한도, 누가 얼마 이상을 승인하는지, 데이터 취급 규칙.
- **용어와 기준 시스템:** 약어, 제품과 팀 이름, 데이터 종류별 기준 시스템. 파이프라인은 CRM, 매출은 ERP를 기준으로 삼는 식이다.
- **바뀌는 값:** 가격과 인원처럼 변하는 사실에는 날짜를 붙여 낡은 정보가 드러나게 한다.

## 맥락을 두는 위치와 미세조정의 경계

맥락은 사용자 지정 지침, 프로젝트, 커넥터와 MCP, 사내 검색(RAG), 미세조정에 둘 수 있다. OpenAI의 정확도 최적화 안내는 모델이 학습하지 못했거나 낡았거나 사내에만 있는 지식이 부족하면 컨텍스트를 최적화하고, 형식, 어조와 추론이 일관되지 않으면 모델을 최적화하라고 나눈다(2026-11-09 대조). 정책처럼 자주 바뀌는 회사 지식은 미세조정보다 문서와 커넥터로 공급하는 편이 갱신에 맞다. 커넥터는 결정이 일어나는 도구 두세 개부터 연결하고, 답의 출처를 보여 주는 도구를 고른다.

## 평가와 정정 기록

- **아는 답으로 시험한다:** 답을 이미 아는 질문 10~20개로 출처 인용과, 정보가 없을 때 모른다고 답하는지를 함께 확인한다.
- **정정을 공유한다:** 틀린 답은 공유 기록에 남기고 원인을 분류한다. 빠진 사실이면 추가하고 낡은 사실이면 고친다. 한 사람의 대화에서 고치고 끝내면 다른 사람과 에이전트가 같은 오류를 반복한다.
- **소유자와 검토일:** 절마다 소유자(지표 정의는 재무, 정책은 인사)와 검토 날짜를 둔다.
- **권한:** 커넥터를 켤 수 있는 사람을 제한하고, 연결 전에 넓게 공유된 폴더와 채널을 점검한다. 행동하는 에이전트의 읽기와 쓰기 권한을 나누고, 공급사 약관이 회사 데이터를 학습에 쓰지 않는지 확인한다.
