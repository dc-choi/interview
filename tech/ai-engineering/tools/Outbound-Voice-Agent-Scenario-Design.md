# 아웃바운드 음성 에이전트의 시나리오 설계

아웃바운드 음성 에이전트는 서비스가 먼저 고객에게 전화를 걸어 정해진 목적(미납 안내, 주소 확인, 상담 희망 확인 등)을 처리하는 에이전트다. 고객이 먼저 걸어 오는 인바운드 상담과 달리 대화의 시작과 목표를 서비스가 정하므로, 예상 응답을 미리 분류하고 다음 행동을 결정적으로 묶어 둘 여지가 크다.

## 인바운드와 아웃바운드의 차이

| 구분 | 인바운드 | 아웃바운드 |
|---|---|---|
| 대화의 시작 | 고객이 용건과 맥락을 가져온다 | 서비스가 첫 질문을 정한다 |
| 응답의 범위 | 넓고 예측하기 어렵다 | 첫 질문에 대한 응답이 몇 갈래로 모인다 |
| 고객의 준비 상태 | 용건을 알고 전화한다 | 상황을 모른 채 받아 말을 번복하기 쉽다 |
| 설계 중심 | 이해와 검색, 넓은 대응 | 분기 분류, 정보 수집 완료 조건, 번복 처리 |

예를 들어 납부 가능 여부를 묻는 통화의 응답은 낼 수 있다, 낼 수 없다, 모르겠다로 모인다. 이때 LLM이 매번 답을 생성하게 하기보다 응답을 미리 정한 분기로 분류하고 분기마다 준비한 발화를 내보내면, 환각과 품질 감시 부담이 줄고 동작을 시험하기도 쉽다.

## 대화를 노드 그래프로 표현한다

### 노드마다 하나의 과제와 필요한 도구만 준다

시나리오를 노드 그래프로 두고 각 노드가 한 가지 과제만 다루게 한다. Pipecat Flows는 대화를 노드 그래프로 모델링하며 각 노드가 한 과제에 필요한 도구만 LLM에 제공한다고 설명한다. 노드에는 과제 메시지(`task_messages`)와 선택적인 역할 메시지, 함수, 진입 전후 동작을 둔다. 선언형 설정에서는 함수의 `transition_to`로 다음 노드를 정하고, Python 코드에서는 함수 처리기가 다음 노드 설정을 반환한다. Pipecat 문서는 도구를 많이 몰아 둔 단일 프롬프트가 환각과 정확도 저하로 이어진다는 점을 이 구조의 이유로 든다(2026-11-10 공식 문서 기준, `pipecat-ai` 1.5.0부터 `pipecat.flows` 네임스페이스로 코어 패키지에 포함, 별도 `pipecat-ai-flows` 패키지는 동결).

노드 그래프는 대화 상태를 LLM 맥락과 도구를 바꿔 끼우는 방식으로 옮긴다. 그래서 Pipecat Flows는 세션 중 맥락을 다시 쓸 수 없는 음성 대 음성(speech-to-speech) 모델을 지원하지 않는다고 밝힌다. 노드 그래프를 쓸지는 음성 구성([[Realtime-Voice-Architecture|연쇄 파이프라인과 단일 음성 세션]])과 함께 정한다.

### 어느 노드에서나 나오는 질문은 전역 분기로 둔다

"어디서 전화하셨어요?", "뭐라고 하셨죠?" 같은 말은 시나리오의 어느 단계에서나 나온다. 노드마다 같은 분기를 다는 대신 전역 분기 하나를 두고, 해당 상황으로 판정되면 그 노드를 반드시 실행하게 한다. 이벤트 리스너처럼 동작하는 결정적 규칙이며, 자연어로 적은 전역 지시를 LLM이 지키기를 기대하는 것과 다르다. Pipecat Flows의 `global_functions`(코드에서는 `FlowManager(global_functions=...)`)는 모든 노드에서 제공하는 도구라 노드마다 같은 분기를 다는 수고를 던다는 점에서 비슷하다. 다만 LLM 도구 목록에 들어가는 함수이므로 실행 여부는 LLM의 도구 선택에 달려 있어, 판정 결과로 반드시 실행하는 결정적 전역 분기와는 다르다.

## 정보 수집의 완료는 엔진이 판정한다

주소처럼 한 번에 받기 어려운 정보는 여러 턴에 걸쳐 수집된다. 고객이 시와 구를 나눠 말하거나 등록 주소가 아니라고 정정하기 때문이다. 이때 LLM이 도구 호출로 상태를 넘기게 두면 덜 모은 채 다음 단계로 건너뛸 수 있다.

1. 엔진이 현재 노드의 목표(예: 주소 수집)를 LLM에 알려 준다.
2. 한 턴이 끝날 때마다 엔진이 필수 값이 채워졌는지 완료 조건으로 검사한다.
3. 값이 비어 있으면 같은 노드에 머물고, LLM은 아직 수집 중이라는 상태를 받아 다시 묻는다.
4. 완료 조건을 만족해야 다음 노드로 넘어간다.

상태 전이 권한을 코드에 두는 방식이며, 텍스트 워크플로에서 체인과 에이전트를 나누는 기준과 같다 → [[LLM-Workflow-Patterns-Chain-vs-Agent|체인과 에이전트]].

## 번복과 끼어들기를 처리한다

고객은 "낼게요, 아 다음 달에, 못 낼 것 같아요"처럼 말을 이어 가며 답을 바꾼다. 발화 종료 이벤트에서 판단을 시작했는데 결과가 나오기 전에 발화 시작 이벤트가 다시 오면, 진행 중인 판단을 취소하고 앞뒤 발화를 합쳐 다시 판정한다. 고객이 말하는 도중 이전 판단으로 응답을 시작하는 일을 막는다.

에이전트가 말하는 중에 고객이 끼어드는 경우는 별도로 처리한다. LiveKit Agents는 입력 오디오에서 사용자 발화를 감지하면 에이전트 발화를 멈추고, 대화 기록을 사용자가 실제로 들은 부분까지로 자른다. 잡음 같은 거짓 끼어들기는 기본적으로 멈춘 지점부터 다시 말한다(Python 설정의 interruption 옵션 아래 `resume_false_interruption` 기본 `True`, 판정 대기 `false_interruption_timeout` 기본 2.0초, 2026-11-10 문서 기준). 턴 확정 전에 응답을 미리 만드는 preemptive generation은 최종 전사가 바뀌면 취소되어야 한다고 안내한다. 아래 사례의 발표 팀은 잡음과 발화를 가르는 판단 모델을 도입하기 전에는 잡음 때문에 AI 발화가 자주 끊겼다고 밝혔다.

## 트레이드오프

- **결정적 분기의 장점:** 짧은 개발 기간에도 동작을 시험하고 감시하기 쉽고, 분기 판정만 빠르면 응답 지연이 작다.
- **한계:** 정해 둔 분기 밖의 말은 처리하지 못한다. 대체 경로로 RAG 기반 응답이나 생성형 발화가 필요하며, 이 경로에는 다시 환각과 품질 감시가 따라온다.
- **적용 순서:** 쉬운 시나리오부터 반드시 동작하게 만든 뒤 분기를 넓힌다. 처음부터 모든 고객사의 모든 상황을 다루려 하지 않는다.

## 사례: 상담 서비스의 아웃바운드 콜 MVP (발표 기준)

채널톡 엔지니어링 발표(2026-10-30 공개)의 사례다. 수치는 발표자가 밝힌 자체 운영값이며 일반 기준이 아니다.

- 엔터프라이즈 고객의 음성 상담 수요를 보고 현장 배치 엔지니어(FDE) 조직이 아웃바운드 콜 MVP를 먼저 만들어 운영한 뒤 제품팀에 넘기는 방식으로 진행했다.
- 응답을 미리 정한 분기로 분류하는 판단 모델을 써서 분류 지연 P95 약 0.24초, 고객 발화 뒤 다음 발화 시작까지 약 0.3초라고 밝혔다.
- 2,500명에게 발신해 83명이 상담을 희망했고, 사람 상담사와 비슷한 전환율을 훨씬 낮은 비용으로 얻었다고 소개했다. 비용 배수는 음성 인식 전사에 3, 4배로만 적혀 있어 정확한 수치를 확정하지 않는다. 비용 비교 기준과 사람 상담사의 비교 수치는 발표에 나오지 않았다.
- 음성 인식 전사로 확인한 내용이며 판단 모델의 이름과 화면 슬라이드는 확인하지 못했다.

## 점검 질문

- 첫 질문에 대한 응답 분기가 몇 갈래로 모이는가? 분기 밖 응답의 비율을 운영 기록으로 재고 있는가?
- 노드마다 반복되는 질문을 전역 분기로 뺐는가?
- 정보 수집 노드의 완료 조건을 코드로 검사하는가, LLM의 판단에 맡겼는가?
- 판단 중 새 발화가 시작되면 판단을 취소하고 발화를 합쳐 다시 판정하는가?
- 에이전트 발화 중 끼어들기와 거짓 끼어들기의 처리, 들은 부분까지의 기록 정리를 시험했는가?
