# LLM 코딩 가드레일 — 실패 패턴과 교정 4원칙

코딩 에이전트의 사고는 능력 부족보다 행동 습관에서 온다. 확인 없이 가정하고 질주하는 것, 100줄이면 될 코드를 1000줄로 부풀리는 것, 태스크와 무관한 코드를 건드리는 것, 검증 기준 없이 완료를 선언하는 것. 이 반복 패턴은 모델 교체가 아니라 **짧은 행동 규칙을 영속 컨텍스트로 상시 주입**해 교정한다. 4원칙(Think Before Coding, Simplicity First, Surgical Changes, Goal-Driven Execution)이 대표 룰셋이고, CLAUDE.md 병합, 스킬/플러그인, Cursor rule 등 여러 경로로 배포된다. 규칙은 경직된 금지보다 판단 원칙 형태로 두는 것이 모델 세대가 올라도 유효하다 — 금지형 규칙이 새 세대에서 부채로 반전되는 이유는 [[Context-Engineering|컨텍스트 엔지니어링]]의 모델 세대와 지시 밀도 절 참조.

## 반복 관찰되는 실패 패턴

1. **가정 질주** — 사용자를 대신해 가정을 세우고 확인 없이 진행한다. 혼란을 관리하지 않고, 명확화를 구하지 않고, 불일치를 표면화하지 않고, 트레이드오프를 제시하지 않고, 반박해야 할 때 반박하지 않는다.
2. **과잉 복잡화** — 코드와 API를 부풀리고 추상화를 비대하게 만들고 dead code를 정리하지 않는다. 100줄이면 될 구현을 1000줄로 짓는다.
3. **부수효과 편집** — 충분히 이해하지 못한 주석과 코드를, 태스크와 직교인데도 변경하거나 삭제한다.
4. **낭비되는 루프 지렛대** — LLM은 구체적 목표를 만족할 때까지 루핑하는 데 탁월한데, "되게 해줘" 같은 모호한 지시는 이 강점을 쓰지 못하게 하고 상시 개입만 남긴다.

## 교정 4원칙

각 원칙은 위 실패 패턴 순서와 대응한다.

### 1. Think Before Coding — 가정을 표면화

구현 전에:

- 가정을 명시적으로 선언하고, 불확실하면 추측 대신 질문한다
- 해석이 여러 개면 모두 제시한다. 조용히 하나를 고르지 않는다
- 더 단순한 접근이 있으면 말한다. 필요하면 반박한다
- 혼란스러우면 멈추고, 무엇이 혼란스러운지 명명하고 묻는다

### 2. Simplicity First — 요청 범위의 최소 코드

- 요청 밖 기능 금지, 단일 사용 코드에 추상화 금지
- 요청받지 않은 유연성과 설정 가능성 금지
- 불가능한 시나리오의 에러 처리 금지
- 200줄을 썼는데 50줄이면 충분하다면 다시 쓴다

판정 질문: 시니어 엔지니어가 보면 과잉이라고 하겠는가. 그렇다면 단순화한다.

단, 줄이는 대상은 요청 밖 범위지 안전이 아니다 — 신뢰 경계 검증, 보안, 접근성, 데이터 손실 처리는 감축 대상에서 제외한다 ([[Agent-Overengineering-Guard|게으름 vs 태만]] 구분).

### 3. Surgical Changes — 닿아야 할 것만, 자기 뒷정리만

기존 코드를 편집할 때:

- 인접 코드, 주석, 포맷을 개선하지 않는다
- 안 깨진 것을 리팩토링하지 않는다
- 내 취향과 달라도 기존 스타일을 따른다
- 무관한 dead code를 발견하면 언급만 하고 삭제하지 않는다

내 변경이 고아를 만들면:

- 내 변경 때문에 안 쓰이게 된 임포트, 변수, 함수는 제거한다
- 원래 있던 dead code는 요청 없이는 제거하지 않는다

판정 질문: 변경된 모든 라인이 사용자 요청으로 소급되는가.

### 4. Goal-Driven Execution — 성공 기준과 검증 루프

명령형 지시를 검증 가능한 목표로 변환한다.

| 명령형 | 검증 가능한 목표 |
|---|---|
| 검증 추가해줘 | 잘못된 입력 테스트를 먼저 쓰고 통과시킨다 |
| 버그 고쳐줘 | 재현 테스트를 먼저 쓰고 통과시킨다 |
| X 리팩토링해줘 | 전후로 테스트 통과를 보장한다 |

단, 에이전트가 스스로 쓴 재현 테스트는 대칭 입력이나 출력 박제로 버그를 놓칠 수 있으므로 성공 기준의 정답 정의는 사람이 쥔다 ([[Agent-Test-Verification-Behavior|에이전트 검증 행동]]).

다단계 작업은 단계마다 verify를 붙인 계획을 먼저 선언한다 (단계, verify: 확인 방법). 강한 성공 기준은 에이전트의 독립 루프를 허용하고, 약한 기준은 상시 개입을 요구한다. 핵심 발상은 무엇을 할지 지시하는 대신 성공 기준을 주고 지켜보는 것.

## 우회 처방 경계 — AI의 답을 되돌려보내는 판단

AI의 제안은 원인을 찾기보다 문제를 돌아가는 쪽으로 기울 때가 있다 — 리소스를 늘려라, 타임아웃을 늘려라, 더 무거운 인프라를 깔아라. 그 자리에서는 다 말이 되는 답이지만, 받을지 되돌려보낼지 판단하는 기준은 사람에게 남는다.

- **눈앞 예시에 맞는 답이 규칙이 되지는 않는다** — 지금 열려 있는 입력 하나에 동작하는 해법인지, 입력마다 달라지는 변형까지 감당하는 해법인지 구분한다. 되돌려보낸 AI의 답도 버리지 않고 단순 케이스의 폴백 기본값으로 보존할 수 있다.
- **문제의 실제 위치를 내가 알아야 한다** — 예를 들어 연결을 끊는 주체가 중간 게이트웨이라면 클라이언트 타임아웃을 늘리라는 답은 엉뚱한 곳을 겨눈다. 어디서 끊기는지 알고 있어야 답이 과녁을 벗어났다는 것을 알 수 있다.
- **제품의 제약이 판단 기준이다** — 비용 제로, 데이터 로컬 유지 같은 초기 제약과 충돌하는 처방(하드웨어 증설, 클라우드 전환, 전용 인프라 설치)은 규모에 맞는 최소 해법(배치 크기 축소, 직접 계산)으로 대체할 수 있는지 먼저 본다. 성능을 양보했다면 진행률 표시처럼 사용 경험으로 보완한다.

## 전제 검증 — 구현 전에 AI로 내 가정을 반박시킨다

우회 처방 경계가 AI가 내놓은 답을 받을지 판단하는 쪽이라면, 그 반대편에는 내 전제를 AI에 먼저 검증받는 쓰임이 있다. 코딩 에이전트의 진짜 위험은 못 만드는 것이 아니라 내가 잘못 생각한 것을 정확히 만들어 주는 것이다. 능력이 오를수록 틀린 전제도 충실히 구현되므로, 구현을 바로 시키지 않고 구조와 전제부터 확인시키는 것이 방어선이 된다.

- 자명해 보이는 요구사항일수록 구현 전에 `구조부터 확인하고 결과만 보고 멈춰`처럼 지시해, 스키마와 전제의 모순을 먼저 드러낸다. 여기서 AI의 값은 코드 생성이 아니라 전제 반박이다.
- 사람은 표면을, AI는 구조를 보는 분업으로 쓴다. 직관적으로 당연해 보이는 연결(예: 이름을 바꾸면 태그도 함께 바꾼다)이 실제 데이터 구조에서는 독립이라 부작용을 낳는 경우를, 코드가 나오기 전에 잡는다.

## 의도 인터뷰 — 묻기를 기다리지 않고 흐름을 뒤집는다

Think Before Coding은 불확실하면 묻게 하지만, 모델이 모호함을 알아채고도 거의 묻지 않고 답부터 내며 근거 문서를 붙이면 더 덜 묻는다는 측정이 있다([[LLM-Abstention#모호한 요청에서 묻는가 — 알아채는 것과 묻는 것의 차이|알아채는 것과 묻는 것의 차이]]). 그래서 요구가 덜 정해진 작업은 모델이 물어 주기를 기다리지 않고 처음부터 모델이 사용자를 인터뷰하게 한다. Jules White 외(Vanderbilt University, 2023)의 프롬프트 패턴 카탈로그는 이를 Flipped Interaction 패턴으로 정리했다. 사용자가 대화를 이끄는 대신 모델이 목표 달성에 필요한 정보를 질문으로 모으게 하는 방식이며, 논문은 이를 제어의 역전(inversion of control)에 빗대고 목표는 반드시 밝히되 끝낼 조건과 한 번에 물을 질문 수도 정해 두면 좋다고 본다. 일부 실무자는 리버스 프롬프팅이라고 부른다.

- **무엇보다 왜를 먼저 맞춘다:** 상위 목표가 빠지면 모델은 빈칸을 그럴듯한 쪽으로 채운다. 같은 게임 요청도 새 모델의 실력을 혼자 시험해 보려는 것이면 HTML 파일 하나로 충분하고, 출시가 목표면 엔진, 저장 구조, 밸런스 데이터 분리와 배포 환경이 처음부터 달라진다. 목표를 공유하면 화면을 어디까지 챙길지, 예외 처리를 어느 수준으로 할지 같은 작업 중의 작은 선택도 의도 쪽으로 기운다. Anthropic 프롬프트 가이드도 지시의 이유를 함께 주면 Claude가 목표를 더 잘 알고 그 설명에서 일반화한다고 설명한다(2026-11-24 확인).
- **한 번에 하나씩, 추측을 붙여 묻는다:** 빈 화면에서 설명하기보다 틀린 추측을 고치는 편이 쉽다. 팀 스탠드업에서 볼 대시보드냐는 추측에 혼자 돌리는 실험을 잊지 않으려는 것이라고 답하는 순간, 필요한 것이 차트가 아니라 실험 목록이었음이 드러난다. 질문을 묶으면 훑고 넘어가기 쉽고 뒤 질문이 앞 답에 따라 바뀐다. 사용자가 예의상 추측에 동의하는 위험은 가끔 반박이 나올 방향으로 추측해 줄인다.
- **그래야 할 것 같은 답을 되묻는다:** 확장성, 깔끔한 아키텍처, 표준 방식처럼 모범 답안 같지만 구체적인 결과가 없는 답에는, 누구에게도 정당화할 필요가 없다면 실제로 무엇을 원하는지 묻는다. 혼자 쓸 도구가 불필요하게 커지는 것을 막는다.
- **범위 밖까지 요약하고 명시적 동의를 받는다:** 결과, 사용자, 지금인 이유, 성공 기준, 제약과 범위 밖을 몇 줄로 돌려 말하고 확인받는다. 알아서 해 달라는 답은 동의가 아니라 위임이므로 구체적인 두 선택지로 다시 묻는다.
- **끝낼 시점을 검사할 수 있게 둔다:** 다음에 물을 세 질문에 대한 사용자 반응을 예측할 수 있으면 멈춘다. 여러 번 물어도 예측이 안 되면 요청에 근본적인 공백이 있다는 신호로 보고 한 걸음 물러선다.

뒤의 네 장치는 Addy Osmani의 agent-skills 저장소(MIT)에 있는 `interview-me` 스킬 지침(2026-11-24 확인, 마지막 변경 2026-08-19)의 절차다. 지침은 어긋남의 절반이 무엇을 만들지 않을지에 대한 말 없는 불일치라고 보지만 측정값은 아니다. 의도가 확정되면 그 턴에 하위 작업을 시작하지 않고 멈춰 다음 경로를 사용자가 고르게 하고, 사용자가 원할 때만 의도 문서로 저장한다. CI, 예약 실행과 반복 루프처럼 답할 사람이 없는 실행에서는 쓰지 말고 요청이 모호하다는 사실을 막힌 지점으로 보고하라고 적는다.

Matt Pocock의 `grill-me`(MIT, 2026-11-24 저장소 문서 기준)는 장치가 다르다. 결정을 설계 트리로 보고 선행 결정이 끝난 질문 전부를 한 라운드에 번호와 추천 답을 붙여 묻고, 환경에서 찾을 수 있는 사실은 사용자에게 묻지 않고 서브에이전트로 조사하며, 트리의 모든 분기를 돌면 끝난다. 사용자가 직접 불러야 실행되고 파일을 남기지 않는다. 막연한 아이디어에서 시작해도 된다고 밝히므로 이미 세운 계획을 검증할 때만 쓰는 스킬로 구분하지 않는다. 같은 문서는 동의만 반복하면 아무것도 정하지 않은 채 확신만 높은 계획이 나온다고 경고하고, 긴 입력 폼 하나로 할지 세 페이지로 나눌지처럼 말로는 답할 수 없는 질문은 버릴 시제품을 만들어 보고 답하라고 권한다. 팀 SDD에서 이 스킬을 감싸 쓰는 예는 [[Spec-Decision-Records|에이전트 작업의 스펙과 결정 기록]]에 있다.

도구도 같은 흐름을 기본 기능으로 둔다(2026-11-24 공식 문서 기준). Claude Code는 요구를 모으거나 모호함을 풀 때 `AskUserQuestion` 도구로 객관식 질문을 던지고, 모범 사례 문서는 원하는 것이 아직 정해지지 않았으면 스펙을 쓸 수 있을 때까지 인터뷰하게 해 `SPEC.md`로 남기라고 권한다. Codex 문서는 어렵거나 모호한 작업이면 코딩 전에 계획하라며, 맥락을 모으고 확인 질문을 한 뒤 계획을 세우는 Plan mode(`/plan` 또는 Shift+Tab)와 막연한 아이디어를 먼저 질문하게 해 가정을 반박하고 구체화하는 인터뷰 요청을 함께 든다. 묻는 기능이 있다는 것과 필요한 순간에 묻는다는 것은 따로 확인한다.

운영에서 놓치기 쉬운 점은 다음과 같다(실무 제안).

1. **발동 조건을 상시 지침에 둔다:** 스킬은 설명만 상시 로드되고 본문은 관련 있다고 판단될 때 로드되므로([[Spec-Decision-Records#규칙과 스킬의 배치|규칙과 스킬의 배치]]), 목적이나 완료 기준이 빠진 요청이면 구현 전에 인터뷰부터 한다는 한 줄을 CLAUDE.md나 AGENTS.md에 둔다. Claude Code 모범 사례 문서도 그런 한 줄을 따를지는 매 턴 Claude의 판단이라고 설명하므로 보장은 아니다. 무인 실행은 조건에서 뺀다.
2. **인터뷰한 세션에서 구현하지 않는다:** 인터뷰 대화에는 틀린 추측과 버린 아이디어가 남는다. 확정한 의도, 특히 목적과 범위 밖을 파일로 쓰고 구현은 그 파일을 읽는 새 세션에서 시작한다. 명세는 인터뷰 맥락이 남은 세션에서 쓰라는 grill-me 문서의 안내와 SPEC.md가 생기면 새 세션에서 구현하라는 Claude Code 문서를 합치면, 정리는 인터뷰 세션에서 하고 구현만 새로 시작하는 순서가 된다. 넘길 것과 버릴 것은 [[Agent-Multi-Turn-Instructions#대응 3 — 세션을 새로 시작할 때와 넘길 내용|세션 교체]]를 따른다.
3. **아직 묻지 않은 선택지로 이해를 시험한다:** 세 질문을 예측할 수 있다는 판단도 모델의 자기 평가다. 요약을 받으면 인터뷰에서 다루지 않은 선택(데이터를 내 컴퓨터에 둘지 서버 DB를 붙일지)을 하나 물어 답이 앞서 말한 목적을 따르는지 본다. 혼자 쓰는 도구인데 큰 서버 구조를 권하면 상위 목표가 아직 전달되지 않은 것이다.
4. **이미 아는 요구는 처음에 준다:** Flipped Interaction 논문은 미리 알려진 요구를 프롬프트에 넣지 않으면 모델이 물을지 추측할지를 비결정적으로 고른다고 보고, 개입을 최소로 할지 핵심 결정을 모두 확인받을지도 명시하라고 권한다. 오타 수정 같은 모호하지 않은 요청, 단순 정보 질문과 속도를 원한다고 밝힌 요청에는 인터뷰를 돌리지 않는다(interview-me 지침).

## 왜 작동하나 — 복잡성은 옳고 그름이 아니라 타이밍 문제

과잉 설계된 코드는 명백히 틀린 코드가 아니다. 디자인 패턴과 모범 사례를 따른 코드다. 문제는 필요해지기 전에 복잡성을 넣는 타이밍이고, 이것이 이해를 어렵게 하고 버그를 늘리고 구현과 테스트를 느리게 한다. 단순 버전은 이해와 테스트가 쉽고, 복잡성이 실제로 필요해질 때 리팩토링하면 된다. 좋은 코드는 오늘의 문제를 단순하게 푸는 코드지, 내일의 문제를 미리 푸는 코드가 아니다.

## 배포 — 같은 룰셋, 여러 주입 경로

- **CLAUDE.md 병합**: 프로젝트 영속 컨텍스트에 append. 프로젝트 특화 규칙(테스트 규칙, 기존 에러 처리 패턴 준수 등)과 병합해 쓰는 전제
- **스킬/플러그인**: SKILL.md의 description 트리거로 코드 작성, 리뷰, 리팩토링 시 로드. 마켓플레이스 플러그인으로 설치하면 전 프로젝트 공용 ([[Agent-Skills]])
- **다른 호스트**: 같은 내용을 Cursor project rule(.mdc)로. 원칙을 도구별 주입 포맷으로 이식하는 패턴은 [[Agent-Overengineering-Guard]]의 다중 에이전트 이식성과 같은 축
- **적시 주입 (Hook 패턴 트리거)**: 규칙을 상시 컨텍스트에 얹으면 앞부분 지시가 덜 반영되는 Lost-in-the-Middle에 취약하다. 대신 코드 생성 시점에 필요한 규칙만 골라 넣는다 — 파일을 쓴 직후 Hook이 파일명과 코드 패턴(regex)으로 해당 규칙 소수만 즉시 주입하고, 작업 종료 전 변경 전체(git diff)를 다중 파일 규칙(예: 서비스가 구현이 아니라 인터페이스에 의존하는지)으로 검토한다. 규칙은 중앙 저장소에 두고 세션 시작 시 최신본을 받아 프로젝트마다 복제, 갱신하는 드리프트를 없앤다. 어떤 규칙이 언제 발동했는지 로그로 남겨 과잉, 과소 규칙을 교정한다. Hook의 실행 시점 특성과 성공률 한계는 [[Context-Engineering|컨텍스트 엔지니어링]]이 다룬다
- **이름 있는 원칙을 리뷰 기준으로**: 행동 규칙 대신 검증된 공학 원칙의 출처를 CLAUDE.md에 적어 생성과 리뷰의 판정 기준으로 쓰는 방식이다. Martin Fowler의 Refactoring 카탈로그(코드 냄새와 리팩터링 기법), Robert C. Martin의 Clean Code와 TDD 연습용 Bowling Game Kata, Jorma Sajaniemi의 변수 역할(roles of variables, stepper, fixed value, most-recent holder처럼 변수의 쓰임을 분류), Olaf Zimmermann 외의 Patterns for API Design이 예다. 원칙 이름은 짧은 토큰으로 넓은 판단 기준을 불러오지만 이름을 적는 것만으로 행동이 바뀌지는 않는다. 테스트 먼저 같은 기법 이름을 지시해도 실제 절차가 따라오지 않는 한계는 [[Agent-Test-Verification-Behavior|에이전트 검증 행동]]이 다루며, 원칙마다 이 프로젝트에서 무엇을 위반으로 볼지 판정 예시를 붙여야 효과를 확인할 수 있다. 원칙 목록을 길게 쌓거나 원칙별 페르소나 에이전트를 여러 개 돌리면 매 턴 컨텍스트와 호출 수가 늘어 토큰 비용과 구독 사용량 한도를 빠르게 소모한다
- **트레이드오프**: 신중 편향 룰셋이라 사소한 작업(오타 수정, 자명한 한 줄)엔 과잉이다. 목적은 단순 작업의 감속이 아니라 비단순 작업의 비싼 실수 감축

## 작동 확인 신호

- diff에 요청 밖 변경이 줄었다
- 과잉 복잡화로 인한 재작성이 줄었다
- 명확화 질문이 실수 뒤가 아니라 구현 앞에 온다
- 드라이브바이 리팩토링 없는 최소 PR이 나온다

## 기존 도구와의 관계

- [[Agent-Overengineering-Guard|YAGNI 사다리]]는 Simplicity First 하나를 결정 절차(7칸 사다리)로 정밀화한 도구다. 4원칙은 가정, 범위, 편집 반경, 목표 정의까지 커버하는 상위 행동 프레임
- Goal-Driven Execution의 성공 기준 정의는 [[Agent-Spec-Writing]]의 경계 시스템, 적합성 테스트와 같은 축
- 규칙을 매 턴 주입하는 메커니즘 자체는 [[Context-Engineering|영속 컨텍스트]] — 권장(CLAUDE.md)과 강제(Hook)의 구분도 거기서 다룬다

## 면접 체크포인트

- LLM 코딩의 반복 실패 패턴을 구체적으로 말할 수 있는가 (가정 질주, 과잉 복잡화, 부수효과 편집, 모호한 목표)
- 4원칙 각각의 판정 테스트 — 시니어가 과잉이라 보겠는가, 모든 변경 라인이 요청으로 소급되는가, 성공 기준이 독립 루프를 허용하는가
- 명령형 지시를 선언적 성공 기준으로 변환하는 예 (버그 수정이면 재현 테스트부터)
- 과잉 설계를 옳고 그름이 아니라 타이밍 문제로 설명할 수 있는가
- 행동 가드레일의 트레이드오프(신중 vs 속도)와 적용 예외
- 같은 룰셋의 주입 경로별 차이 — 상시 주입(CLAUDE.md)과 온디맨드 로드(스킬)의 구분
- 불확실하면 물으라는 지시와 인터뷰로 흐름을 뒤집는 설계의 차이 — 모호함 인식과 질문 행동의 괴리, 추측을 붙인 질문, 범위 밖 요약, 인터뷰와 구현의 세션 분리
