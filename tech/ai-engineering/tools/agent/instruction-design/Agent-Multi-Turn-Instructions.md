# 여러 턴에 걸친 지시 — 나눠 준 요구, 쌓이는 모순, 다시 묶는 시점

제품 수준의 요구는 한 번의 프롬프트에 빠짐없이 쓰기 어려워 에이전트와의 작업은 여러 턴으로 이어지기 쉽다. 문제는 턴의 수가 아니라 한 작업의 명세가 여러 턴에 흩어지는 데 있다. 아래 연구에서 요구를 턴마다 나눠 준 대화는 같은 정보를 한 번에 준 경우보다 결과가 나빴고 실행마다 크게 흔들렸다. 이 문서는 그 원인과 대응, 즉 한 작업을 완결된 지시로 묶는 법, 턴을 주고받는 순서, 세션을 새로 시작할 시점과 넘길 내용을 다룬다. 지시를 쓰는 법은 [[Agent-Spec-Writing|에이전트 스펙 작성법]], 입력 길이에 따른 성능 변화는 [[Context-Engineering|컨텍스트 엔지니어링]]의 Context Rot 절이 정본이다.

## 정의

- **여러 턴에 걸친 지시**: 한 작업의 요구를 대화 턴마다 나눠 전달하는 방식이다. 첫 턴에는 큰 의도만 있고 세부 조건은 뒤에서 드러나므로, 마지막 조건이 나오기 전까지 모델은 명세가 부족한(underspecified) 지시로 일한다.
- **세션 오염**(실무 용어): 실패한 시도, 철회된 요구와 서로 어긋나는 지시가 대화에 남아 이후 판단의 입력이 되는 상태다.
- **Context Rot과의 관계**: 대화가 길어지면 입력 길이에 따른 성능 변화와 겹칠 수 있다. 다만 아래 연구에서 같은 정보를 한 턴에 모아 준 조건은 성능이 거의 유지돼, 하락은 조각으로 나누며 생긴 정보 손실로는 설명되지 않는다. 그래서 정보를 나눠 받는 과정 자체를 따로 관리해야 한다. 모델 응답이 쌓여 길어진 대화의 길이 효과는 이 비교로 분리되지 않아 Context Rot과 겹치는 몫은 측정되지 않았다.

## 연구 근거 — 나눠 준 요구에서 길을 잃는다

Laban 외의 연구(arXiv 2025-05 공개, ICLR 2026 구두 발표)는 15개 LLM과 6개 생성 과제(코드, text-to-SQL, API 호출, 수학, data-to-text, 요약)로 20만 회가 넘는 대화를 시뮬레이션했다. 완결된 지시 하나를 합치면 정보가 같은 여러 조각(shard)으로 나누고 세 조건을 비교했다.

| 조건 | 전달 방식 | 결과 |
|---|---|---|
| FULL | 원래의 완결된 지시를 첫 턴에 준다 | 기준 |
| CONCAT | 조각을 한 턴에 목록으로 합쳐 준다 | FULL의 평균 95.1% |
| SHARDED | 시뮬레이션 사용자가 턴마다 조각을 최대 하나씩 공개한다 | FULL 대비 평균 39% 하락 |

- CONCAT이 거의 유지됐으므로 하락은 조각으로 다시 쓰며 잃은 정보가 아니라 여러 턴에 나눠 받는 과정에서 생긴다.
- 하락은 주로 능력이 아니라 신뢰도에서 왔다. 같은 지시를 반복 실행한 점수의 90번째 백분위(aptitude)는 평균 16% 줄었고, 90번째와 10번째 백분위의 차이(unreliability)는 평균 112% 늘었다. 한 번 잘 나온 결과가 다음 실행에서도 나온다는 보장이 약해진다.

### 왜 길을 잃는가

1. **이른 답 시도**: 정보가 덜 모인 초반에 가정을 세워 완성된 답을 낸다. Code와 Math에서 첫 답 시도가 대화의 처음 20% 구간에 나온 경우 평균 점수는 30.9, 마지막 20% 구간이면 64.4였다.
2. **이전 답에 대한 과의존**: 새 조건이 들어와도 앞선 가정을 무효로 돌리지 못하고 이전 시도를 고쳐 쓴다. 이를 잰 네 과제(Code, Database, data-to-text, 요약)에서 최종 답이 FULL과 CONCAT의 답보다 20~300% 길어지는 답 비대화(answer bloat)가 나타났다.
3. **중간 턴 손실**: 요약 과제에서 첫 턴이나 마지막 턴에 들어온 문서를 가장 많이 인용하고 중간 턴의 문서는 덜 반영했다.
4. **장황한 응답**: 길게 답할수록 사용자가 말하지 않은 가정이 늘어난다. 여섯 과제 중 다섯에서 가장 짧은 응답 구간이 가장 긴 구간보다 10~50% 높은 점수를 냈다.

### 효과가 작았던 처방

- **추론 모델**: o3와 DeepSeek-R1도 비추론 모델과 비슷하게 하락했다. 추가 추론 토큰이 명세 부족을 메우지 못했다. 추론 모델의 응답은 평균 33% 길었고, 저자들은 긴 응답일수록 가정이 더 많이 들어간다고 본다.
- **temperature 낮추기**: GPT-4o와 GPT-4o-mini 두 모델로 한 보조 실험에서 단일 턴 조건은 신뢰도가 크게 좋아졌지만, SHARDED에서 어시스턴트 temperature만 낮추면 개선이 작거나 없었다. 사용자와 어시스턴트를 모두 0으로 둬도 30% 안팎의 불안정이 남았다.
- **요구 다시 모아 주기**: 마지막 턴에 앞선 조각을 모두 다시 주는 RECAP과 매 턴 누적해 다시 주는 SNOWBALL은 일부만 회복했다. GPT-4o의 4개 과제(Code, Database, Math, Actions)에서 FULL 93.0, SHARDED 59.1, RECAP 76.6, SNOWBALL 65.3이었다. RECAP은 마지막 턴을 미리 알아야 하므로 실제 대화에 그대로 쓰기 어렵다.

### 적용 범위와 후속 근거

- 저자들은 생성형이고, 여러 명시 조건이 붙고, 답을 부분으로 나눠 완성할 수 없는 과제에서 모델이 길을 잃기 쉽다는 가설을 제시한다. 10문장 문서를 두 문장씩 나눠 준 번역 과제(GPT-4o와 GPT-4o-mini)에서는 하락이 없었는데, 번역도 생성형이므로 이 대조가 뒷받침하는 것은 문장 단위로 나눠 끝낼 수 있는지라는 세 번째 성질이다. 세 성질을 하나씩 통제해 검증한 실험은 아니다.
- 사용자는 시뮬레이션이고, 저자들은 실제 대화의 저하가 실험값보다 클 가능성이 높다고 본다. 평가 모델은 GPT-4o, GPT-4.1, Claude 3.7 Sonnet, Gemini 2.5 Pro, o3처럼 2025년 상반기까지 나온 모델이다.
- 2026-02 arXiv 사전 공개 논문은 같은 벤치마크의 4개 과제를 조각 공개 순서를 고정한 변형 조건으로 돌렸고, GPT-5.2도 FULL 평균 92.7에서 SHARDED 48.5로 떨어졌다고 보고했다. 과거의 실패 대화와 성공 입력을 비교해 뽑은 지침을 참고해 누적된 대화를 완결된 단일 지시로 다시 쓰는 중재자(Mediator)를 실행 모델 앞에 두자 72.6으로 일부 회복했다. 학회 게재가 확인되지 않은 사전 공개본의 소규모 벤치마크 결과다.
- 2026-11-02 확인한 OpenAI 안내는 GPT-6 Astra가 이전 모델보다 긴 작업에서 일관성을 더 잘 유지하고, 새 요구를 반영하며, 결과를 바꿀 수 있는 정보가 필요하면 가정 대신 질문하는 경향이 크다고 설명하지만 측정 수치는 없다. 쓰는 모델에서의 크기는 같은 과제를 완결 지시와 나눠 준 지시로 같은 횟수만큼 반복해 비교해야 알 수 있다.

## 동작 원리 — 대화는 매 턴 다시 읽는 누적 입력이다

- 모델은 매 턴 이전 대화 전체를 다시 입력으로 받는다([[LLM-Generation-Mechanics-Context-and-Agent|대화 누적]]). 사람은 앞의 요구를 취소했다고 생각해도 모델에게는 원래 지시와 취소 지시가 함께 남는다. Claude Code 문서도 같은 것을 두 번 고쳐도 틀리면 세 번째 수정은 대체로 실패한 시도 둘이 이미 담긴 대화에 더 보태는 일이 된다고 설명한다.
- 사람 쪽에서는 요구가 생각날 때마다 덧붙으면서 같은 요구가 다른 표현으로 되풀이되고, 앞선 요구와 어긋나는 지시가 철회 표시 없이 쌓인다. 어긋나는 두 지시가 함께 남으면 어느 쪽을 따를지는 모델이 판단하게 된다.
- 모순의 비용은 벤더 안내에도 있다(2026-11-02 확인). OpenAI의 GPT-5 프롬프트 가이드(보관 문서)는 모순되거나 모호한 지시가 GPT-5에 더 해로울 수 있고, 모델이 무작위로 하나를 고르는 대신 모순을 조정할 방법을 찾는 데 추론 토큰을 쓴다고 설명한다. GPT-6 안내는 skill 파일의 불명확하거나 충돌하는 지침이 GPT-6 Astra를 일찍 멈추게 할 수 있다며 사용자 지시와 skill 지시의 우선순위를 명시하라고 권한다. 두 안내의 대상은 프롬프트와 지침 파일이며, 대화에 쌓인 모순에도 같은 비용이 든다는 것은 이를 대화에 적용한 추론이다.
- 모델 쪽에서는 정보가 모자란 초반의 가정이 이후 답의 뼈대가 된다(이른 답 시도와 과의존). 결과가 요구와 어긋나면 모델 능력을 탓하기 전에 같은 정보를 한 번에 정리해 새 세션에서 다시 시도해 원인을 가른다. 연구의 FULL과 SHARDED 비교가 이 진단이며 [[Context-Engineering|빠른 진단]]과 같은 축이다.

## 대응 1 — 한 작업의 요구는 완결된 지시 하나로 준다

- 지시에는 목표, 작업 상세와 종결 조건(무엇이 확인되면 끝인지)을 함께 담는다. 작성법은 [[Agent-Spec-Writing|에이전트 스펙 작성법]], 긴 작업의 완료와 중단 조건은 [[Claude-Code-Workflows|Claude Code 개발 워크플로우]]를 따른다.
- 기대하는 범위도 모델이 코드에서 읽을 수 없는 정보다. Claude Code 문서는 모델이 요청을 보수적으로 읽고 이를 만족하는 가장 작은 결과를 만드는 경향이 있으니, 빈 상태와 오류 상태 처리처럼 원하는 범위를 처음에 말하라고 권한다.
- 요구가 아직 정리되지 않았다면 대화로 조금씩 흘리지 말고 먼저 모아 고정한다. Claude Code 문서는 스펙을 쓸 수 있을 때까지 모델이 사용자를 인터뷰하게 해 `SPEC.md`로 남기고, 새 세션에서 그 파일로 구현을 시작해 깨끗한 컨텍스트와 문서로 된 완료 정의에서 출발하라고 권한다. 결정을 질문으로 드러내는 방법은 [[Agent-Spec-Writing|숨은 결정 축 인터뷰]]를 따른다.
- 작업 분할과 명세 분할을 구분한다. 연구는 하위 과제로 나눠 끝낼 수 있는 과제에서는 모델이 하위 과제를 하나씩 완료하며 길을 잃지 않을 수 있다고 본다. 큰 제품을 독립적으로 끝낼 수 있는 작업으로 나누고 작업마다 완결된 지시를 주는 것은 이 구조를 의도적으로 만드는 적용이다. 한 작업의 조건을 턴마다 흘리는 것은 그 반대다.
- 한 번에 몰아넣기도 답이 아니다. 한 지시의 요구가 너무 많으면 준수율이 떨어지므로([[Agent-Spec-Writing|지시의 저주]], [[Production-Agent-Architecture-Cases-and-Interview|IFScale 실험]]), 분량을 줄일 때는 조건을 나눠 주지 말고 작업을 나눈다.
- 널리 알려진 과제는 짧은 지시로도 모델이 빈 부분을 일반적인 관례로 채워 그럴듯한 결과를 낼 수 있다. OpenAI 안내도 GPT-6 Astra가 해석의 여지가 있는 지시에서 가진 맥락으로 일상적인 빈틈을 채우고, 결과가 바뀔 수 있을 때 질문한다고 설명한다. 전용 SDK와 컴파일러로만 빌드되는 환경이나 표준과 다른 평가 방법처럼 분야 고유의 제약이 있으면 이렇게 채운 부분이 틀린 가정이 될 수 있다. 그런 과제는 그 분야에서 지켜야 하는 불변식과 일반 관례와 다른 점을 구현 지시보다 먼저 확인시킨다. 일반 지식으로 메울 수 없는 정보의 공급은 [[Context-Engineering|맥락 병목]]과 같은 축이다.

### 예시 — 흘린 요구를 하나로 묶기

회원 가입 API를 다섯 턴에 걸쳐 요청한 경우다. 3번째 턴은 2번째 턴의 예외이고, 4번째 턴은 이미 만든 인증 흐름을 다시 고치게 한다. 모델이 2번째 턴에서 모든 가입자에게 이메일 인증을 붙였다면 이후 턴은 그 답을 덧대는 수정이 된다.

| 턴 | 덧붙인 요구 | 정리된 지시에서의 자리 |
|---|---|---|
| 1 | 회원 가입 API를 만든다 | 목표 |
| 2 | 이메일 인증을 넣는다 | 요구 조건 |
| 3 | 소셜 로그인 가입자는 이메일 인증을 건너뛴다 | 2번 조건의 예외로 같은 항목에 |
| 4 | 인증 메일은 24시간 동안만 유효하다 | 2번 조건의 세부 |
| 5 | 테스트가 통과하면 끝낸다 | 완료 판정: 인증 만료와 소셜 가입 예외를 포함한 시나리오 통과 |

정리된 지시에서는 규칙과 예외가 한 항목에 함께 있고 완료 판정이 처음부터 주어진다.

## 대응 2 — 턴을 주고받는 순서를 정해 사람 쪽에 하네스를 건다

하네스가 모델의 행동을 묶듯, 정해진 순서로 지시를 주고받는 방식(절차적 프롬프트)은 즉흥적으로 덧붙는 사람의 지시를 묶는다. 목적은 지시 사이의 불일치를 줄여 모델이 일관된 요구 위에서 동작하게 하는 것이다. 다음은 개발 작업에 적용한 루프의 예다.

1. **명세 확정**: 요구와 완료 판정 기준을 파일로 쓴다. 사용자 흐름이 있는 서비스라면 인수 테스트 시나리오를 항목별로 먼저 문서화한다.
2. **구현 위임**: 이번 단계에 필요한 맥락과 범위만 준 한정된 임무로 맡긴다. 범위를 나누는 법은 [[Agent-Spec-Writing|태스크 분할]]을 따른다.
3. **독립 검증**: 구현 대화를 보지 않은 검토자(서브에이전트나 별도 세션)가 시나리오 파일과 대조하고, 시나리오별 실행 결과를 파일로 남긴다.
4. **판정과 재시도**: 실패하면 원인을 분석해 수정을 지시하되 재시도 횟수에 상한을 두고, 상한에 닿으면 멈춰 사람이 다시 판단한다.
5. **요구 변경**: 새 요구는 대화에 덧붙이기 전에 명세 파일에 반영하고 기존 항목과 충돌하는지 확인한다. 변경이 크면 새 세션에서 그 파일로 다시 시작한다.

- 지시의 정본을 대화가 아니라 파일에 두면 세션을 바꿔도 같은 요구를 다시 줄 수 있다. 대화로만 한 지시는 압축 중에 사라질 수 있다([[Claude-Code-Fundamentals|컨텍스트 관리]]). 명세 파일은 CLAUDE.md처럼 자동으로 읽히지 않고 압축 뒤에 다시 읽힌다는 보장도 없으므로, 새 세션의 첫 지시와 압축 뒤에 그 파일을 다시 가리키거나 CLAUDE.md에 파일 경로를 적어 둔다(운영 제안).
- Claude Code 문서는 무인 실행 전에 완료 정의, 자기 검증 수단, 접근 범위, 멈추는 조건(턴이나 지출 상한)과 결과 승인자를 확인하라고 안내한다. 독립 검증의 효과와 한계는 [[Agent-Test-Verification-Behavior|에이전트 검증 행동]], 재시도 상한을 지시가 아닌 하드 리밋으로 두는 이유는 [[Harness-Gate-Placement|게이트 배치]]와 [[Agent-Loop-Engineering|루프 엔지니어링]]이 다룬다.
- 대화에서 반복해 교정한 내용을 지침 파일로 옮기면 그 파일에도 모순이 쌓일 수 있다. 2026-11-02 문서 기준 Claude Code의 `/doctor prompt-audit`는 이전 모델용 지시, 없어진 파일을 가리키는 지시와 서로 모순되는 지시를 표시하고, OpenAI도 모델이 읽는 skill과 지침 파일에서 충돌하는 지침을 감사하라고 권한다.

## 대응 3 — 세션을 새로 시작할 때와 넘길 내용

| 신호 | 조치 |
|---|---|
| 방향이 틀어진 것을 막 봤다 | 바로 멈추고(Claude Code의 `Esc`), 필요하면 이전 지점으로 되감는다(`/rewind`) |
| 같은 문제를 두 번 고쳤는데도 틀린다 | 세 번째 수정 대신 새 세션에서 배운 것을 반영한 새 프롬프트 하나로 시작한다 |
| 요구가 여러 번 바뀌어 초기 가정 위에 덧댄 답이 반복된다 | 지금까지의 요구를 하나의 지시로 정리해 새 대화의 첫 지시로 준다 |
| 관련 없는 작업으로 넘어간다 | 세션을 비우고 시작한다(`/clear`) |
| 같은 작업이 길어졌지만 방향은 맞다 | 보존할 결정을 지정해 압축한다(`/compact`) |

- 연구도 시간이 허락하면 같은 정보를 담아 새 대화를 시작하는 편이 기존 대화를 이어 가는 것보다 훨씬 나을 수 있다고 보고, 다시 시도하기 전에 요구를 하나의 지시로 통합하라고 권한다. 지금까지 말한 내용을 모델에게 정리하게 한 뒤 그 결과로 새 대화를 시작하는 방법도 제안한다.
- **넘길 것**(운영 제안): 정리한 단일 지시, 완료 판정 기준(시나리오 파일), 확정한 결정과 그 근거 위치, 실패한 접근과 실패 이유, 미해결 질문.
- **버릴 것**(운영 제안): 철회된 요구, 실패한 답의 전문, 확인되지 않은 중간 가정.
- 모델이 만든 정리본도 생성물이다. 누락되거나 바뀐 요구가 없는지 사람이 원래 요구와 대조한 뒤 새 세션에 넣는다(운영 제안). 명령별 동작은 [[Claude-Code-Fundamentals|Claude Code 기초]]를 따른다.

## 트레이드오프

- **새 세션의 비용**: 새 세션은 이전 대화에서 모은 맥락을 다시 모아야 하고, 대화에만 남은 결정은 사라진다. 파일로 남긴 정본이 있을수록 교체 비용이 작다.
- **탐색 대화는 허용한다**: 무엇을 원하는지 찾는 단계에서는 막연한 지시로 시작해 여러 번 고치는 흐름이 자연스럽다. Claude Code 문서도 탐색 중의 막연한 프롬프트는 괜찮고 수정이 늘어나는 것이 그 대가라고 본다. 만들 것이 정해지면 그때 요구를 정리해 새로 시작한다.
- **절차는 고정되지 않는다**: 정해진 절차는 이미 검증된 과업에서 잘 맞고, 정답이 정해지지 않은 새 과제에서는 실행해 보며 배운 것으로 절차 자체를 고쳐야 한다. 절차가 늘수록 관리 비용도 늘므로 반복해서 깨지는 지점에만 단계를 더한다.
- **질문하게 하는 지시**: 정보가 모자라면 답하기 전에 묻게 하는 지시는 [[Agent-Coding-Guardrails|가정 표면화]]가 다룬다. 이 지시가 위 하락을 얼마나 줄이는지는 위 연구에서 측정하지 않았다.

## 운영 체크포인트

- 지금 작업의 요구가 한 곳(명세 파일이나 정리된 지시)에 모여 있는가, 여러 턴에 흩어져 있는가
- 새 요구를 덧붙이기 전에 앞선 요구와 겹치거나 충돌하는지 확인했고, 바꾼 요구가 이전 요구를 대체한다고 밝혔는가
- 결과가 어긋날 때 같은 정보를 한 번에 정리해 새 세션에서 다시 시도해 봤는가
- 같은 문제를 두 번 고쳐도 틀리면 세 번째 수정 대신 새 세션과 정리된 지시로 갔는가
- 완료 기준이 구현 대화 밖의 파일에 있고, 구현을 보지 않은 검토자가 그 기준과 대조하는가
- 재시도 횟수와 지출에 상한이 있는가
- 큰 작업을 조건이 아니라 독립적으로 끝낼 수 있는 작업 단위로 나눴는가
