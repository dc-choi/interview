# AGENTS.md, 저장소 작업 지침의 작성과 운영

## 정의와 역할

`AGENTS.md`는 코딩 에이전트가 프로젝트에서 작업할 때 필요한 맥락과 지침을 담는 개방형 Markdown 형식이다. 필수 필드나 고정 제목, frontmatter schema는 없다. 사람을 위한 README와 공존하며 설치, 검증과 변경 경계처럼 작업에 필요한 정보를 제공한다.

2026-10-09 공식 사이트는 Agentic AI Foundation(AAIF), Linux Foundation 아래에서 관리한다고 설명한다. 개방형 형식을 지원한다는 사실만으로 모든 도구의 읽기 방식과 우선순위가 같아지는 것은 아니다.

| 자료 | 답하는 질문 | 한계 |
| --- | --- | --- |
| `README.md` | 무엇을 하는 프로젝트이며 어떻게 시작하는가 | 에이전트 전용 규칙의 자동 발견은 별개 |
| `AGENTS.md` | 이 저장소에서 어떻게 작업하고 검증하는가 | 명령 실행, 규칙 준수와 권한 차단의 보증은 아님 |
| `llms.txt` | 웹에서 관련 문서를 어디서 찾는가 | 로컬 저장소 지침의 대체가 아님 |
| Skill | 특정 작업을 어떤 반복 절차로 수행하는가 | 일반 프로젝트 맥락과 현재 요구를 대신하지 않음 |
| 테스트, 권한과 CI | 결과가 조건을 만족하고 허용 범위 안에 있는가 | 자연어 의도와 예외의 설명은 따로 필요 |

읽은 문서는 컨텍스트가 된다. 이를 모델 자체의 영구 학습이나 실행 권한 획득으로 해석하지 않는다.

## 무엇을 기록할 것인가

다음은 형식의 필수 필드가 아니라 작성 시 검토할 항목이다.

| 항목 | 유용한 내용 | 피할 내용 |
| --- | --- | --- |
| 구조 | 진입점, 패키지 책임, 정본 문서 경로 | 폴더 전체 목록의 반복 복사 |
| 실행 | 실제 작업 디렉터리, 설치와 빌드 명령 | 다른 저장소에서 복사한 미확인 명령 |
| 검증 | 변경별 필요한 검사, 결과와 실패 보고 방식 | 테스트를 적었다는 이유로 통과했다고 가정 |
| 관례 | 기존 패턴, 네이밍과 적용 범위 | 포매터와 린터가 정하는 내용을 길게 중복 |
| 변경 경계 | 생성 파일, 비공개 데이터, 호환성 조건 | 프로젝트와 무관한 금지 목록 |
| 협업 | 사용자 변경 보존, 병렬 작업의 소유권 | 독립적이지 않은 파일의 무조건 병렬 편집 |
| 완료 | 변경 내용, 검사 결과와 남은 제한 | 근거 없는 완료 문구 |

원칙은 실행할 수 있는 조건으로 쓴다. 잘 검증하라는 지시보다 어떤 검사로 어떤 계약을 확인하고 실패를 어떻게 보고할지 적는 편이 검토 가능하다. 명령과 경로는 현재 소스, package 설정과 CI를 대조한다.

## 루트와 경로 지침

공통 사용법은 루트에 전체 규칙을 두고 특정 패키지에는 그 경로에 필요한 규칙을 두는 것이다. 가까운 지침 우선이라는 설명은 **적용 범위와 충돌 처리**에 관한 것이며 모든 하위 파일을 언제 읽는지까지 정하지 않는다.

예를 들어 저장소 루트와 `packages/api`에 지침이 있으면 API 작업에서는 둘의 적용 범위를 확인한다. 상위의 보안 원칙을 유지하면서 하위에 API 전용 검증 명령을 둘 수 있다. 형제 패키지의 지침까지 전부 읽을 필요가 있는지는 호스트와 실제 작업 범위에 따라 판단한다.

사용자 요청, 조직 정책, 시스템 지침과 도구 권한의 우선순위는 호스트가 결정한다. 사이트 FAQ의 사용자 채팅 우선 설명을 시스템 지침이나 실행 정책까지 무효화하는 공통 규격으로 확대하지 않는다. 구체적 발견 규칙은 [[Agent-Repository-Instructions-Hosts|호스트별 동작]]을 따른다.

## 짧은 작성 예시

다음은 가상 프로젝트의 내용 예시다. 문서 제목과 항목은 자유롭게 바꿀 수 있으며 실제 저장소에 적용할 때 명령부터 확인한다.

```markdown
# 프로젝트 작업 지침

## 구조
- 요청 처리 코드는 src/api, 도메인 규칙은 src/domain에 둔다.
- API 계약의 정본은 docs/api-contract.md다.

## 변경과 검증
- 기존 오류 응답 계약을 보존한다.
- 루트에서 npm run typecheck를 실행한다.
- 동작을 바꾸면 npm test로 관련 회귀를 확인한다.
- 실행하지 못한 검사는 통과한 검사와 나누어 보고한다.

## 경계
- generated 아래 파일은 생성 원본에서 수정한다.
- 비밀 키와 고객 데이터를 문서나 로그에 넣지 않는다.
- 다른 작업자의 변경을 되돌리지 않는다.
```

작업마다 달라지는 장문의 절차는 별도 문서나 Skill로 옮기고 찾는 경로를 제공한다. 경로를 적는 것, 호스트의 import 기능으로 시작 시 읽는 것, 작업 중 필요할 때 읽는 것은 서로 다르다.

## 도입, 이관과 유지

1. **현재 동작 확인:** 에이전트 종류와 버전, cwd, 활성 지침과 설정을 확인한다.
2. **기존 문서 대조:** README, 기여 안내, CI와 겹치거나 충돌하는 내용을 찾는다.
3. **범위 분리:** 저장소 공통 규칙과 패키지 규칙, 반복 절차를 나눈다.
4. **작은 작업 검증:** 경로 규칙이 다른 두 작업에서 실제 발견 파일과 명령을 확인한다.
5. **수정과 유지:** 실패 원인을 지침 누락, 잘못된 지침, 미로딩, 도구 제한과 실행 오류로 구분한다.

기존 `CLAUDE.md`, `AGENT.md` 등을 이름만 바꾸기 전에 소비 호스트와 import, 심볼릭 링크 지원을 확인한다. 한 정본을 공유할 수 있지만 링크 방식과 재로딩 시점은 도구별 계약이다. 본 문서화는 실제 저장소의 지침 파일이나 설정을 이관하는 작업이 아니다.

## 검증과 보안의 경계

- **명령 근거:** 파일에 적힌 명령을 실행하기 전에 현재 요구, 권한과 대상이 맞는지 확인한다.
- **외부 자료:** 다운로드한 예제와 의존성 안의 지침은 자동으로 프로젝트 정책이 되지 않는다.
- **강제 수단:** 데이터 접근과 파괴적 동작 제한은 자격 증명, 샌드박스와 도구 정책에서도 적용한다.
- **검사 증거:** 테스트 요청과 실제 실행, 성공 결과를 나누어 기록한다. 네트워크나 도구 부재로 검사를 못 했다면 미검증으로 남긴다.
- **효과 측정:** 같은 과제와 환경에서 지침 유무를 비교한다. 성공률뿐 아니라 탐색 시간, 불필요한 변경과 비용을 함께 본다.

더 긴 지침이나 더 많은 파일이 더 좋은 결과를 보장하지 않는다. 형식 지원, 파일 로드와 행동 준수는 각각 확인한다. 길이와 규칙 밀도의 평가는 [[Context-Engineering|컨텍스트 엔지니어링]]에서 이어진다.

## 사용자 판단 기준의 보존과 재정렬

작업 절차만으로 결과의 우선순위가 정해지지는 않는다. 단순함, 빠른 검증, 직접 유지보수 가능성처럼 선택을 바꾸는 기준에는 이유, 적용 범위와 예외를 함께 기록한다. 이미 확인된 선호와 에이전트가 추정한 선호를 구분한다.

`ALIGN.md`는 이런 합의를 별도 문서에 두고 주 지침에서 연결하는 프로젝트의 제안이다. 모델 재학습이나 모든 호스트가 자동 발견하는 표준 파일을 뜻하지 않는다. 반복 절차를 담는 align 스킬과 현재 사용자 합의도 별개다. 스킬 업데이트가 합의 내용이나 확인 날짜를 바꾸어서는 안 된다.

재정렬은 중요한 판단 불일치, 반복되는 수정 요구나 우선순위의 불확실성이 있을 때 수행한다. 이미 답한 질문을 반복하지 않고, 허용 범위의 명백한 오류는 바로 고친다. 긴 자율 작업 전에는 가상 선택 상황으로 기준을 점검할 수 있다. 결과를 정당화하려고 에이전트가 기준을 임의 변경해서는 안 된다.

예를 들어 익숙한 도구로 유지보수한다는 기준에서 새 의존성 도입이 필요해지면, 기존 도구로 충족할 수 없는 조건과 도입 비용을 제시한다. 이번 작업의 예외인지 앞으로 적용할 선호 변경인지 구분한다.

### 선호 유지 실험을 읽는 기준

2026-10-15 공개된 유지관리자 실험은 가상 사용자 4명에게 과제 3개씩을 주고 두 조건을 비교했다. 일반 지침 조건은 추가 답변 9회, 선호와 스킬을 미리 제공한 조건은 0회였고, 최종 적합성은 모두 12/12였다.

이는 **초기 정보와 검색 절차까지 포함한 묶음의 비교**다. 같은 정보를 가진 `AGENTS.md`보다 파일 이름 `ALIGN.md`가 우수하다는 증거가 아니다. 저장 승인을 위한 답변 4회는 실제 측정이 아닌 설정 비용 가정이며, 설치, 유지보수와 사람의 시간은 측정하지 않았다. 실제 사용자 대상 반복 실험이나 이 저장소에서의 재현 결과도 아니다.

2026-10-15 부분 확인: 이 절의 개념과 수치만 프로젝트 README와 실험 보고서에 대조했다. 기존 호스트 관련 사실 전체의 검증일은 갱신하지 않는다. 별도 파일의 도입 여부는 각 저장소의 정본 규칙을 따른다.
