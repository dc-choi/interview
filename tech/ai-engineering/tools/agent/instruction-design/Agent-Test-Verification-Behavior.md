# 에이전트 검증 행동 — 기법 이름은 행동을 바꾸지 않는다

코딩 에이전트에게 퍼징, property-based testing, TDD, 형식 검증 같은 기법 이름을 지시하면 정확도가 오를 것 같지만, 실제로는 모델의 기본 행동 분포가 거의 바뀌지 않는다. 에이전트는 이름을 받으면 그 프레임워크 안에 평소 쓰던 단위 테스트를 담고, 자기가 쓴 테스트를 통과시키는 데는 능하지만 실제 버그는 잡지 못한다. 효과가 있었던 쪽은 모델이 이미 아는 것을 설명하는 튜토리얼이 아니라, 알려진 실패 습관에서 밀어내는 짧은 행동 교정 서술이었다. [[Agent-Coding-Guardrails|코딩 가드레일]]의 Goal-Driven Execution이 성공 기준을 주라고 말한다면, 이 문서는 검증 자체를 어떻게 지시해야 행동이 바뀌는지를 다룬다.

## 실험이 보여준 것

한 실험은 Rust로 Zstd를 구현하는 동일 과제에 프롬프트 부록만 바꿔 붙여, 26개 지시 조건과 4개 스킬을 같은 하네스와 모델(Codex, 추론 강도 medium과 xhigh)에서 조건당 160회씩 돌리고 숨겨진 테스트를 100% 통과한 비율과 비용을 쟀다. 어떤 조건도 뚜렷이 우수하지 않았고, 지시가 없는 기본 조건이 평균보다 위였다. 아래는 지시가 실제 행동으로 이어졌는지 본 결과다.

| 지시 | 형식상 수행 | 실제 검증 효과 |
|---|---|---|
| Differential testing | 160회 중 135회가 수행 형태 | 완전한 두 구현을 만든 사례 0. 같은 로직을 두 번 써서 같은 버그를 양쪽에 심음 |
| TLA+ | 159회가 모델 생성 | 모델의 발견이 Rust 코드 변경으로 이어진 사례 없음 |
| QuickCheck | property 사용 | 63회가 property를 하나만 검사 |
| Fuzzing | 대부분 형식 수행 | 구조화된 랜덤 입력을 만든 10회 중 절반이 실제 버그를 찾음 |
| TDD | 실패 테스트를 먼저 보유한 run 67회(기본 조건 0회) | 테스트 수는 2배였지만 평가 테스트 실패율은 더 높음 |
| 내장 테스트 프레임워크 | 테스트 수 medium 2배, xhigh +25% | 정확도 개선 없음 |
| 독립 감사(Audit) | 152회가 수행, 151회가 이슈 발견 주장 | 독립 에이전트를 쓴 42회가 오히려 점수가 낮음 |
| SMT 증명 | 관련 property를 증명 | 증명해 놓고도 코드는 틀림 (더하기를 OR로 구현) |
| 저자의 짧은 행동 교정 스킬 | 5개 지시 | 최고 점수. 단, 일부 지시는 거의 실행되지 않음 |

## 왜 자기 작성 테스트가 버그를 놓치나

- 대칭 입력으로 스스로를 무력화한다. 네 스트림을 전부 같게 만들면 순서가 뒤바뀌는 버그를 못 잡고, 팰린드롬 입력은 역전 버그를 통과시킨다.
- 고정 입출력 방식은 코드의 출력을 정답으로 박제한다. 반복 실행을 늘리면 잘못된 기대값이 테스트에 고착된다. 입력을 생성하면 무엇이 정답인지 분류하는 코드를 따로 써야 하므로 정답의 정의를 생각하게 된다.
- 형식 기법은 공허하게 만족된다. `A => A` 형태의 증명, 하나뿐인 property, 코드로 이어지지 않는 모델처럼 기법의 형태는 갖추되 검증력은 없는 산출물이 나온다.

## 비용 대비 효과

- 효과가 있었던 것: 구조화된 랜덤 입력, property-based testing 라이브러리의 shrinking, 위험 영역 식별(에이전트가 비교적 잘하는 편), 짧은 행동 교정 스킬.
- 효과가 없었던 것: 형식 기법 이름 지시, TDD 지시, 테스트 수 늘리기, 대형 튜토리얼형 스킬, 라이브러리만 갈아끼우기.
- 스킬 비용은 곱셈으로 붙는다. 본문 길이가 재읽기 비용을 만들고(한 대형 스킬은 20k 토큰을 넘겨 비용 +26%에서 +41%), 지시된 절차가 작업량 자체를 늘린다. 정확도 이득이 없으면 순손실이다. 스킬이 실제로 읽혔는지도 확률적이어서, 한 스킬은 160회 중 108회만 열람됐고 다른 스킬은 늦게 읽은 run이 더 좋은 결과를 냈다. 카탈로그 비용은 [[Agent-Skills|에이전트 스킬]]의 수명주기 절과 같은 축이다.

## 행동 교정 스킬의 설계 원칙

가장 좋은 점수를 낸 스킬은 다섯 문장 수준이었고, 기법이 아니라 행동을 지시했다.

1. 구현 전에 버그가 나기 쉬운 영역과 오해 가능한 해석을 먼저 서술하고, 결과가 갈리는 체크를 만든다.
2. 고위험 영역은 프로덕션 코드 맥락 없이 새 컨텍스트에서 독립적으로 다시 유도한 뒤 비교한다.
3. 가능하면 property-based testing이나 랜덤 입력을 쓰되, 패닉이 없다는 확인에 노력을 낭비하지 않는다.
4. 랜덤화는 흥미로운 상태와 경로를 탐색하도록 구조화한다.
5. 불확실하면 독립 추론으로 확인한다.

이식성 한계도 있다. 모델, 하네스, 추론 강도마다 기본 행동이 달라 범용 테스트 스킬은 성립하기 어렵다. 스킬은 워크플로 실행이나 API 조작 안내처럼 모델이 원래 모르는 것에 더 잘 맞는다.

## 벤치마크 방법론 주의

- 조건당 160회도 LLM 노이즈를 평균화하기에 부족할 수 있다. 조건 간 순위 차이의 상당수는 랜덤일 수 있으므로 순위를 강한 결론으로 쓰지 않는다.
- 점수만 보지 말고 무엇을 실제로 했는지 본다. 스킬을 읽지 않은 run이 높은 점수를 내면 그 점수는 스킬의 효과가 아니다.
- 형식 기법이나 TDD 자체가 무용하다는 결론이 아니다. 에이전트가 제대로 쓰지 못한 결과이며, 왜 더 나쁜 테스트를 유도했는지는 밝혀지지 않았다.

## 마이그레이션에서는 기존 구현을 비교 기준으로 쓴다

새 구현과 기대값을 같은 생성 과정에서 만들면 동일한 오해가 양쪽에 들어갈 수 있다. 유지해야 할 동작은 기존 구현의 실행 결과와 비교하고, 의도적으로 바꾸는 동작은 별도의 요구사항으로 확정한다.

DB 프로시저를 API로 옮기는 경우에는 HTTP 성공 응답뿐 아니라 데이터 변경도 비교한다.

| 비교 항목 | 남길 근거 |
|---|---|
| 입력 | 기존 함수 인자와 API 요청 필드의 대응 |
| 초기 상태 | 양쪽 실행이 같은 조건에서 시작했는지 확인할 fixture |
| 출력과 효과 | 반환값, 오류, 변경 행과 필드, 변경되지 않아야 할 값 |
| 차이 | 의도된 변경인지 회귀인지 판단할 요구사항 |

이는 리파인의 AWS 공개 발표자료 56~57쪽에 나온 동일 입력의 DB 함수/API 비교와 실행 전후 상태 보고서를 확장한 검증 설계다. 자료의 예시는 함수 실행 후 롤백하고 API 결과를 비교한다. 외부 호출이나 메시지까지 DB 롤백으로 취소된다는 뜻은 아니므로, 부수효과는 격리된 환경에서 별도로 확인한다.

시간처럼 실행마다 달라지는 필드는 비교 규칙을 먼저 정한다. 기존 구현에도 오류가 있을 수 있어 양쪽 결과의 일치만으로 요구사항의 정확성이나 전체 입력 범위의 동등성을 증명하지는 못한다.

## 빌드 성공과 사용자 동작 검증을 분리한다

코딩 에이전트의 완료 조건에는 코드 생성뿐 아니라 실행 환경에서 확인할 동작을 넣는다. 리팩토링은 변경한 모듈과 연결된 기능의 동작 보존을, PoC는 화면 표시와 사용자 조작 뒤의 결과를 구분해 확인한다.

Android에서는 테스트의 실행 위치와 검증 범위가 서로 다른 축이다. 2026-10-09 공식 문서 대조 기준, local test는 개발 장비나 서버에서, instrumented test는 실제 기기나 에뮬레이터에서 실행한다. 단위 테스트가 전부 local인 것도, 큰 범위의 테스트가 전부 기기에서 실행되는 것도 아니다. 기기와 Android 프레임워크의 실제 동작이 필요한 범위를 골라 instrumented test를 사용한다.

다음은 이를 에이전트 작업의 완료 조건에 적용한 예시다.

| 단계 | 확인할 근거 | 통과만으로 알 수 없는 것 |
|---|---|---|
| 빌드 | 대상 변경으로 만든 산출물과 빌드 결과 | 기기에서의 화면과 기능 동작 |
| 로직 검사 | 요구사항으로 정한 기대값과 자동 테스트 결과 | 검사하지 않은 UI와 기기 의존 동작 |
| 사용자 흐름 검사 | 초기 상태, 조작 순서, 기대 상태와 실행 결과 | 다른 기기, API 수준과 미실행 경로 |

예를 들어 저장 버튼을 구현했다면 버튼이 보이는지만 검사하지 않고 입력, 누르기, 저장 결과 확인까지 연결한다. 스크린샷과 로그는 보조 근거이며 기대 상태의 검사를 대신하지 않는다. 기기를 연결하지 못했거나 도구 실행이 실패했다면 해당 범위를 미검증으로 남긴다.

당근 Android 팀의 공개 발표는 빌드 이후 화면, 로그와 기기 조작 도구를 에이전트에 연결한 적용 사례다. 특정 팀의 생산성 수치를 일반적인 효과로 옮기거나, 도구 연결만으로 제품 의도까지 검증됐다고 판단하지 않는다.

### 생성한 IaC는 템플릿과 배포 후 동작을 나눠 검증한다

아키텍처 그림에서 인프라 코드를 생성했거나 README의 요청 예제가 실행됐다는 사실만으로 서비스 전체의 정확성을 판단하지 않는다. 생성 코드, 설명과 테스트가 같은 오해를 공유할 수 있으므로 기대 동작은 요구사항에서 정한다.

2026-10-09 AWS CDK v2 공식 문서 기준, fine-grained assertion은 합성한 CloudFormation 템플릿의 특정 속성을 검사하고 snapshot test는 저장한 템플릿과 비교한다. CDK 업그레이드만으로도 스냅샷이 달라질 수 있어 스냅샷 하나로 구현의 정확성을 판단하지 않는다. 배포된 리소스의 통합 테스트는 실제 요청과 결과를 연결해 다른 범위를 확인한다.

다음은 이를 코딩 에이전트의 완료 조건에 적용한 점검 예시다.

- 템플릿 검사: 필요한 리소스, 연결과 권한 설정이 생성됐는지 확인한다.
- 배포 후 검사: 생성 API의 응답 ID로 조회해 저장 값이 입력과 일치하는지 확인한다. 삭제 기능을 추가했다면 삭제 후 조회 결과도 요구사항과 대조한다.
- 비동기 처리: 접수 응답과 최종 저장을 구분하고, 정해진 제한 시간 안에 기대 상태에 도달하는지 검사한다.

통합 테스트가 통과해도 실행하지 않은 오류 경로나 권한 거부까지 검증된 것은 아니다. 클라우드 실행을 못 했다면 템플릿 검사만 통과했다고 남긴다.

## 면접 체크포인트

- 에이전트에게 테스트 기법 이름을 지시하는 것이 왜 행동을 바꾸지 못하는지 설명할 수 있는가.
- 자기 작성 테스트가 버그를 놓치는 구조(대칭 입력, 출력 박제)와 생성 입력이 정답 정의를 강제하는 이유를 말할 수 있는가.
- 스킬 비용이 곱셈으로 붙는 이유와 튜토리얼형 스킬이 실패하는 이유를 말할 수 있는가.
- 에이전트 벤치마크에서 점수 대신 실제 행동을 봐야 하는 이유를 말할 수 있는가.
