# 데이터 분석 에이전트의 단계와 분석 시나리오

기업 데이터 위에서 일하는 분석 에이전트는 묻는 대로 조회하는 데서 시작해, 숫자가 왜 그렇게 나왔는지 분해하고, 무엇을 해야 하는지 제안하는 쪽으로 깊어진다. 단계가 깊어질수록 필요한 자산이 달라진다. 조회에는 업무 정의가, 원인 분석에는 비교와 분해의 순서가, 조치 제안에는 업무 절차와 데이터를 잇는 지식이 필요하다. 계획, 계산과 보고서의 실행 경계는 [[Agent-Data-Analysis-Workflow|에이전트 데이터 분석과 보고서]]에서 다룬다.

## 세 단계와 필요한 자산

| 단계 | 질문 예 | 필요한 자산 | 흔한 실패 |
|---|---|---|---|
| 조회 | 지난달 본부별 매출을 보여 줘 | 용어, 산식, 조인 경로와 권한을 정한 [[Semantic-Layer|시맨틱 레이어]] | 그럴듯한 조인, 서로 다른 매출 정의 |
| 원인 분석 | 계획 대비 차이가 난 원인은? 원가에서 늘어난 계정은? | 비교 기준과 분해 순서를 정한 분석 시나리오 | 차이를 다 설명하지 못하는 분해, 숫자와 이어지지 않는 서술 |
| 조치 제안 | 매출이 확정되지 않은 계약은? 확정하려면? | 업무 절차, 이상 상황별 조치 지식, 데이터와 업무 대상의 연결 | 절차에 없는 조치, 권한 밖의 실행 |

공급사 발표는 이 세 단계를 Semantic, Kinetic, Dynamic Layer라고 불렀다(2026년 9월 발표 기준). Palantir 공식 문서에서 semantic 요소는 object, property, link이고 kinetic 요소는 action, function, dynamic security다(2026-11-23 대조). 이름이 같아도 원인 분석 단계를 kinetic으로 부르는 쓰임은 Palantir의 정의와 다르므로, 용어를 옮겨 쓸 때 어느 뜻인지 밝힌다. 온톨로지의 행동 요소는 [[Ontology-Knowledge-Graph#Palantir Foundry Ontology|Palantir Foundry Ontology]]에서 다룬다.

## 원인 분석은 차이 분해의 순서다

사업계획 대비 실적이 미달한 이유를 묻는 질문은 조회 한 번으로 끝나지 않는다. 공급사 시연의 흐름을 일반화하면 다음 순서다.

1. 전체 차이를 확정한다. 계획과 실적의 정의, 기간과 단위를 맞춘 뒤 총 차이를 구한다.
2. 차이가 큰 축부터 나눈다. 사업부, 제품군, 채널과 고객 유형처럼 업무에서 뜻이 있는 차원별로 차이를 구하고 기여가 큰 축을 고른다.
3. 고른 축 안에서 한 단계 더 내려간다. 두 축을 교차해 볼 때는 결과를 합치는 방식(내부 조인인지 전체 외부 조인인지)을 정하고 한쪽에만 있는 값은 빈 값으로 드러낸다.
4. 결론과 권고를 각 단계의 숫자에 연결한다. 보고서의 문장마다 그 숫자를 만든 단계가 있어야 한다.

검산 규칙(설계 판단): 축별 기여의 합이 총 차이와 맞는지 확인하고, 맞지 않으면 남는 차이를 기타로 드러낸다. 부호와 단위(원, 천 원, 억 원)를 단계마다 맞춘다. 분해로 찾은 것은 차이가 모인 위치이지 원인 자체가 아니므로 상관을 원인으로 바꿔 쓰지 않는다. 계산 검산의 일반 계약은 [[Agent-Data-Analysis-Workflow#일반 분석의 최소 계약|일반 분석의 최소 계약]]을 따른다.

## 분석 시나리오를 검토할 수 있는 그래프로 둔다

자주 하는 복합 분석은 매번 에이전트가 계획을 새로 짜게 두기보다 노드와 연결로 된 시나리오로 고정할 수 있다.

| 노드 | 하는 일 | 주의 |
|---|---|---|
| 입력 파라미터 | 기간, 조직, 기준값을 받는다 | 기본값과 허용 범위를 정한다 |
| 데이터 카드 | 검증된 질의 하나를 실행한다 | 시맨틱 레이어의 지표로 만든다 |
| 병합 카드 | 두 결과를 키로 합친다 | 조인 방식과 빈 값 처리를 명시한다 |
| 규칙 분기 | 데이터 유무, 기준치 초과 같은 정확한 조건으로 나눈다 | 금액이나 승인 대상처럼 틀리면 안 되는 판정은 여기서 한다 |
| LLM 분기와 생성 | 해석이 필요한 판단과 인사이트 서술을 맡는다 | 계산 결과만 입력으로 받는다 |
| 보고서 출력 | 엑셀이나 문서로 내보낸다 | 출력 수치를 데이터 카드와 대조한다 |

공급사 제품에서는 자연어 요청으로 코파일럿이 시나리오 초안(노드 4개 등)을 만들고, 업무 담당자가 디자인 도구에서 고쳐 배포하고 공유하며, 자주 쓰는 분석 패턴은 도구로 바꿔 에이전트의 스킬로 쓰게 했다(2026년 9월 발표 기준). 단일 질의를 승인된 도구로 올리는 [[LLM-Workflow-Patterns-Text-to-SQL#반복 질의는 검증된 도구로 승격한다|반복 질의의 도구 승격]]을 여러 단계 분석으로 넓힌 형태다(해석).

| 기준 | 고정 시나리오 | 동적 계획 |
|---|---|---|
| 재현성 | 같은 입력에 같은 단계 | 실행마다 단계가 달라질 수 있다 |
| 검토 | 실행 전에 그래프를 읽고 승인한다 | 실행 기록을 사후에 읽어야 한다 |
| 비용 | 계획 단계의 모델 호출이 준다 | 계획과 재시도에 호출이 는다 |
| 범위 | 정한 질문에만 답한다 | 처음 보는 질문도 시도한다 |

정기 보고와 반복 원인 분석은 고정 시나리오로, 처음 보는 질문은 동적 계획으로 처리하고, 동적 계획이 같은 경로를 반복하면 시나리오 후보로 올린다(운영 제안).

## 조치 제안에는 업무 지식과 데이터의 연결이 필요하다

숫자가 무엇을 뜻하고 무엇을 해야 하는지는 데이터베이스에 없다. 담당자가 직접 입력한 업무 지식, 파일로 된 매뉴얼과 웹 자료를 모으고 그 지식의 대상을 데이터의 대상과 잇는다. 제조 공정 시연에서는 문서에서 설비, 공정, 파라미터와 대책을 개체로, causes(원인이 된다), mitigates(완화한다), affects(영향을 준다), part_of(일부다), measures(측정한다) 같은 관계를 뽑아 그래프를 만들었다. 불량이 예측된 배치에서는 공정 단계별 편차를 비교해 편차가 큰 공정을 원인 후보로 보여 줬다(2026년 9월 발표 기준).

- 문서에서 뽑은 인과 관계는 후보다. 도메인 담당자가 원문 근거로 확인한 관계만 판단에 쓰고, 추출 규칙과 식별자 관리는 [[Ontology-Knowledge-Graph#통제된 지식 그래프를 만드는 순서|통제된 지식 그래프]]를 따른다.
- 그래프의 연결은 정의한 관계이지 이번 불량의 원인을 입증한 결과가 아니다. 편차 순위는 조사 순서를 정하는 근거로 쓰고 원인 확정은 엔지니어가 한다([[IoT-Edge-Cloud-Pipeline#설비 관계 조회와 원인 판단을 구분한다|설비 관계 조회와 원인 판단]]).
- 제안한 조치가 데이터를 바꾸거나 외부로 나가면 승인과 규칙을 거친다. 읽기와 쓰기의 분리는 [[Ontology-Question-Driven-Design#쓰기는 사람과 규칙을 거친다|질문에서 시작하는 온톨로지 설계]]를 따른다.

## 어떤 분석부터 맡길까

과제를 고를 때는 해결할 문제와 기업에 주는 가치를 먼저 묻고, 누가(담당자와 조직, 수행 인원), 얼마나(수행 주기, 1회 소요 시간), 어떻게(필요 지식, 업무 절차)를 적어 가치를 판단한다(2026년 9월 발표의 기준). 이를 계산으로 옮기면 연간 투입 시간은 수행 인원, 연간 수행 횟수와 1회 소요 시간의 곱이다(운영 제안). 투입 시간이 같다면 필요 지식과 절차가 문서로 있는 업무가 먼저 맡기기 쉽다. 업무 단계별 점검 질문은 [[Work-Stage-AI-Adoption#업무를 고를 때의 점검 질문|업무를 고를 때의 점검 질문]]을 따른다.

## 성과는 보이는 효과와 구조 변화로 나눠 본다

AI 성과는 운영 비용 절감, 생산성(분석 리드타임 단축, 문서 초안), 매출(개인화 추천 전환, 이탈 예측) 같은 보이는 효과와, 확장 기반, 데이터 기반 문화, 의사결정 속도 같은 구조 변화로 나눠 본다(2026년 9월 발표의 구분). 보이는 효과는 같은 업무와 같은 품질 기준의 전후로 재고, 구조 변화는 지표를 미리 정하지 않으면 사후 설명이 되기 쉽다(해석). 시간 단축률의 범위는 [[AI-Marketing-Analysis#시간 단축률의 측정 범위를 고정한다|시간 단축률의 측정 범위]]를 따른다.

## 사례

비아이매트릭스의 발표(2026년 9월)는 사내 구축 환경의 보안과 권한 관리, DBMS 직접 연결과 Text-to-SQL에서 시작해 분석 에이전트로 넓히는 순서를 제시했다. 추론과 알고리즘을 결합하면 사내 구축 오픈소스 LLM으로도 정확하게 답한다는 주장에는 모델, 질문 집합과 정확도 측정 조건이 없다. 챗봇 인력 20~40% 감소와 분석 리드타임 30~70% 단축이라는 수치도 출처와 측정 조건이 표시되지 않아 효과의 크기로 쓰지 않는다.
