# 에이전트 데이터 분석과 보고서의 실행 경계

데이터 분석 에이전트는 질문을 분석 계획으로 바꾸고, 코드를 실행해 집계한 뒤 그 결과로 보고서를 만드는 시스템이다. 모델이 숫자를 추측하는 단계와 계산 도구가 실제 데이터를 처리하는 단계를 분리한다.

## 계획, 계산과 보고서

| 단계 | 산출물 | 확인할 경계 |
|---|---|---|
| 계획 | 질문, 사용할 데이터와 분석 항목 | 지표 정의, 기간과 누락된 조건 |
| 계산 | 실행 코드, 집계 결과와 차트 | 실행 성공, 입력 범위와 집계 정합성 |
| 추적 | 완료 항목과 추가 분석 필요 여부 | 실제 산출물과 계획의 일치 |
| 보고서 | 검토 가능한 설명과 결과 파일 | 모든 수치와 주장을 계산 결과에 연결 |

AWS의 공개 구현은 Planner, Coder, Supervisor와 Reporter 역할을 나누고, 계산 결과를 파일에 누적해 보고서 작성자가 읽도록 한다. 이 역할 구분을 에이전트 수의 필수 요건으로 보지는 않는다. 고정된 정기 집계라면 기존 SQL과 보고서 템플릿으로 처리하고, 분석 경로가 달라지는 질문에 동적 계획을 검토한다.

## 원본 데이터와 모델 문맥을 분리한다

큰 파일 전체를 프롬프트에 넣기보다 파일 위치, 스키마와 업무 정의를 주고 실행 도구가 대상 데이터를 읽게 한다. 모델에는 필요한 집계와 진단 결과를 반환한다. 다만 코드 실행도 메모리, 시간과 접근 권한의 제약을 받는다. 파일 전체를 읽었다는 사실은 올바른 분석의 증거가 아니다.

실행 환경의 선택지로 AgentCore Code Interpreter는 격리된 환경의 코드 실행과 데이터 분석을 제공한다. 이것이 앞선 공개 구현의 실행 환경과 같다는 뜻은 아니다. 네트워크 모드, 실행 역할과 접근 가능한 데이터는 별도로 설정하고 확인한다.

## 정기 보고서는 데이터 확정과 최종 승인을 분리한다

보고서 항목과 계산식이 정해져 있으면 매번 SQL이나 계산 코드를 생성하기보다 검토한 조회 조건과 계산 로직을 재사용한다. 아래는 공식 APQR 구축 사례의 조회, 계산, 서술 분리를 일반 보고서에 적용한 설계 예시다(2026-10-07 확인).

1. **근거 준비:** 대상, 기간과 원본 버전을 확인하고 누락된 자료와 수기 보완 항목을 구분한다. 원본 참조를 조회 결과에도 남긴다.
2. **데이터 확정:** 검토자가 포함하거나 제외한 항목을 반영해 이번 보고서의 데이터셋을 확정한다. 이후 데이터가 바뀌면 계산과 검토를 다시 수행한다.
3. **계산과 서술:** 통계, 단위, 반올림과 차트 축은 검토한 코드와 템플릿으로 처리하고, LLM에는 확인된 결과의 설명을 맡긴다. 정형 표만 필요한 부분은 LLM 없이 만든다.
4. **조립과 승인:** 필요한 절과 첨부가 준비됐는지 확인한 뒤 최종 문서를 만든다. 파일과 필수 항목 누락 검사는 코드로, 의미상 모순 검토는 필요할 때 모델로 보조하며 최종 확정은 검토자가 맡는다.

입력 자료 확정, 보고서 생성 완료와 최종 승인은 서로 다른 상태다. 내부 데이터만 사용해도 필터 오류나 잘못된 해석은 남을 수 있다. 이 구조 자체가 특정 산업의 규제 준수나 무오류를 보장하지 않는다.

## 운영 보고서는 과거 지식과 현재 관측을 구분한다

과거 장애 문서와 답변은 점검 절차를 찾는 근거다. 지금 실행 중인 인스턴스나 방금 바뀐 설정을 증명하려면 대상 환경을 조회해야 한다. 다음은 클라우드 운영 자동화 사례의 조회와 분석 분리를 보고서에 적용한 설계 기준이다.

- 질문의 대상 계정, 리전, 리소스와 관측 기간을 먼저 정한다. 생략된 조건을 과거 답변에서 가져와 현재 요청의 사실로 채우지 않는다.
- API 응답이나 로그 조회 결과에 조회 시각과 범위를 연결한다. 문서 검색 결과, 실제 관측과 모델의 원인 가설을 보고서에서 구분한다.
- EC2 `DescribeInstances`는 eventual consistency를 따른다. 생성 또는 변경 직후의 상태가 후속 조회에 즉시 반영되지 않을 수 있고, 최근 종료한 인스턴스도 결과에 남을 수 있다. 단일 조회 결과로 변경 실패나 현재 가동 상태를 단정하지 않는다(2026-10-08 EC2 API 문서 확인).
- 필요한 ID나 필터로 범위를 좁히고 페이지네이션을 처리한다. 일부 페이지만 읽은 결과를 전체 리소스 목록으로 보고하지 않는다.

조회와 보고서 생성을 자동화했어도 생성, 변경과 삭제는 별도 실행 경계다. 점검 결과를 근거로 조치안을 제안하는 단계와 승인된 변경을 수행하는 단계를 나눈다. 프롬프트에 운영 규칙을 적는 것만으로 실제 IAM 권한이나 승인 절차가 생기지는 않는다.

## 조사 보고서는 자료 선택과 인용 보존을 확인한다

계산 결과를 설명하는 보고서와 여러 자료를 종합하는 조사 보고서는 근거가 다르다. 조사에서는 어떤 자료를 포함했는지, 각 주장에 연결된 원문이 무엇인지와 요약 뒤에도 그 근거를 찾을 수 있는지를 확인한다.

부분 검증(2026-10-09): Amazon Quick Research의 자료 선택, 보고서 조회와 요약 기능을 공식 문서로 대조했다.

- 자료 선택에서 웹 검색, 업로드 파일과 Quick 자산 등을 지정한다. 선호 웹사이트를 등록해도 실제 조사에 사용된다는 보장은 없다. 필요한 출처가 최종 보고서에 포함됐는지 확인한다.
- 보고서의 번호 인용은 출처 페이지로 연결되고, `Understand the statement`는 문장의 근거 요약과 결론 도출 설명을 보여준다. 이 설명을 원문 대조를 대신하는 독립 검증으로 취급하지 않는다.
- 기본 요약 유형 중 `Executive summary`는 인용을 포함하지 않고, `General share out`은 핵심 인용을 포함한다. 본문에 출처가 있었다는 사실만으로 모든 요약본에도 출처가 남는다고 가정하지 않는다.

검토 절차 제안: 의사결정에 쓰는 수치와 핵심 주장부터 출처 원문, 기준일과 적용 범위를 대조한다. 짧은 요약본을 공유할 때는 인용이 있는 원본 보고서로 돌아갈 경로를 함께 제공한다. 접근하지 못한 자료와 서로 충돌하는 근거는 확인된 결론과 분리한다. 조사 도구가 보고서를 생성했다는 사실만으로 제안의 정확성이나 사업 성과가 입증되지는 않는다.

## 지속되는 업무 맥락과 현재 데이터 조회를 나눈다

업무 정의나 계정별 목표를 여러 세션에서 재사용하는 것과 현재 실적을 조회하는 것은 다른 기능이다. 저장된 지침의 적용 범위와 실제 조회한 데이터의 시점을 함께 확인한다.

부분 검증(2026-10-10): Pixis Prism의 Brand Knowledge 공식 문서는 기본 지침과 발동 조건, 정적 참고 자료인 Advanced, 이름으로 조회할 수 있는 실시간 Google Sheets 연결인 Attribution을 구분한다. Advanced에 시트를 연결했다는 사실만으로 실시간 질의 경로가 생겼다고 가정하지 않는다. 지식의 생성, 수정과 활성화는 Admin 역할의 기능으로 설명한다.

이를 적용한 설계 점검에서는 누가 운영 지침을 바꿀 수 있는지, 어떤 계정과 질문에 적용되는지, 숫자가 저장된 참고 자료와 이번 조회 중 어디에서 왔는지를 확인한다. 지속되는 기억이나 다른 에이전트의 재검토만으로 데이터 최신성과 계산 정확성이 입증되지는 않는다.

## 검증할 최소 계약

### 채널 분석에서는 수집 범위와 지표의 분모를 고정한다

전수 분석을 요청했다는 사실과 전체 자료를 확보했다는 사실은 다르다. 공개된 채널 분석 절차와 YouTube Analytics 정의를 대조한 다음 점검은 **분석 설계 제안**이다(2026-10-24 부분 검증). 이후 datapitfalls 등의 추가와 부분 대조는 기존 제품 설명 전체의 재검증을 뜻하지 않는다.

1. 대상 영상 목록, 수집 성공 목록과 미확보 목록을 남긴다. 댓글은 수집 건수와 공개 표시 건수를 구분하며, 수집한 댓글을 모두 분류했어도 전체 댓글 확보로 보고하지 않는다.
2. 분류 결과를 원문 식별자와 대조해 누락과 중복을 검사한다. 채널 운영자의 답글, 시청자의 질문과 이벤트 참여 댓글을 분리한다. 전량 분류와 분류 정확도는 별도 검증 대상이다.
3. 공개 조회 수와 소유자만 확인한 Studio 지표를 구분한다. 경쟁 채널에서 확보하지 못한 유지율을 추정값으로 채우지 않는다. 각 값에 관측 시점, 집계 기간과 게시 후 경과 시간을 붙인다.
4. 생성한 영상 보고서도 표와 같은 검산을 거친다. 음성, 화면의 숫자와 원본 계산이 일치하는지 확인하고, 관찰한 차이와 원인 가설, 다음 실험을 구분한다.

`audienceWatchRatio`는 영상의 특정 구간이 재생된 횟수를 전체 조회 수와 비교한 비율이며, 반복 재생 때문에 1을 넘을 수 있다. 이를 고유 시청자의 생존 확률로 해석하지 않는다. 구간 시작과 끝의 유지율 차이를 구간 길이로 나눈 값도 곡선의 변화 요약이지, 그 편집 때문에 사람이 이탈했다는 인과 추정은 아니다.

`subscribersGained`는 채널 보고서와 특정 영상으로 제한한 보고서의 집계 범위가 다르다. 영상 차원이나 필터를 적용하면 해당 영상 시청 페이지에서 발생한 구독만 포함한다. 조회당 구독 지표를 만들 때는 같은 기간과 범위의 분자 및 분모인지 확인하고, 획득 수와 순증을 섞지 않는다. 원시 데이터와 실제 실행 결과를 확보하지 못한 사례의 성과 수치는 이 절차의 효과로 채택하지 않는다.

### 일반 분석의 최소 계약

다음은 계산과 보고서의 분리 원리를 적용한 설계 제안이다.

1. 입력 파일 버전, 필터, 집계 기간과 코드 실행 결과를 연결한다. 같은 파일명에 내용이 바뀌는 경우도 구분한다.
2. 필터 전후 행 수, 결측값, 중복과 조인에 따른 행 증가를 검사한다. 전량 집계여도 잘못된 조인이나 지표 정의는 결과를 왜곡한다.
3. 실행이 실패하면 이전 실행의 결과를 이번 결과로 보고하지 않는다. 실패 지점과 남은 작업을 구분한다.
4. 보고서의 수치와 차트를 계산 산출물에 대조한다. 보고서 작성자가 빈 결과를 임의로 채우지 않게 한다.
5. 상관관계에서 원인을 단정하거나 자동으로 캠페인을 집행하지 않는다. 분석 완료, 사업 판단과 외부 실행은 서로 다른 상태다.

분석 결과의 사업 적용과 성과 측정은 [[AI-Marketing-Analysis|AI 마케팅 분석의 판단 경계]]에서 다룬다. 모델의 자기 검토는 계산 검산이나 독립 검토를 대신하지 않는다.

### 분석 함정 점검표로 질문부터 결론까지 검토한다

계산이 맞아도 질문 설정, 수집, 변환, 해석과 전달 단계의 함정은 남는다. 2026-10-28 대조한 공식 저장소 README(커밋 1061f48778) 기준 datapitfalls는 Ben Jones의 책 Avoiding Data Pitfalls를 바탕으로 만든 규칙으로 차트 이미지, Python, SQL, R 코드, 분석 설명과 문서를 검사한다. 책의 2019년 1장은 일곱 유형을 설명하지만, 도구의 카탈로그는 편향된 기준(biased baseline)을 별도 영역으로 둔 여덟 영역이다. 도구의 분류와 책의 장 구성을 같은 것으로 보지 않는다. 도구의 함정은 인식 오류(확증 편향, 상관과 인과의 혼동), 기술적 오류(조용한 null 제거, 조인 폭증, 형 변환), 수학적 오류(퍼센트와 퍼센트포인트 혼동, 분모 누락), 통계적 오류(심슨의 역설, 기저율 무시, 표본과 생존자 편향), 분석 왜곡(유리한 기간 선택, 부적절한 집계), 시각화 오류(축 자르기, 이중 축), 디자인 문제와 편향된 기준(대표성 없는 출처)으로 나뉜다. 예를 들어 사용자와 주문을 내부 조인하면 주문 없는 사용자가 조용히 빠지고, 올해와 작년 가입자를 비교하면서 지금도 활성인 사용자만 세면 생존자 편향이 된다.

- **실행 방식:** CLI와 라이브러리는 Claude API로 입력과 관련 규칙을 함께 추론해 문제, 심각도, 이유와 수정 방법을 돌려주고 `--ci` 종료 코드로 파이프라인에 연결한다. MCP 서버는 규칙과 점검표를 제공하고 검사는 연결한 Claude가 맡는다. README의 네트워크를 쓰지 않는다는 설명은 로컬 MCP 서버 자체에 관한 것으로, 연결한 모델 제공자가 검사할 내용을 처리한다는 데이터 흐름까지 없애지는 않는다. 서버 자체에는 Anthropic API 키가 필요 없으며 원격 커넥터는 별도 네트워크 연결이다. 웹 스캐너의 입력은 Claude API로 전송되며 앱에는 저장하지 않는다고 밝힌다.
- **판정의 성격:** 입력에서 확인된 문제(active)와 추가 데이터를 봐야 하는 잠재 문제(latent)를 나눈다. 모델이 규칙을 적용한 검토 의견이므로 위 2번의 행 수, 결측과 조인 검사 같은 계산 검산을 대신하지 않는다.
- **라이선스:** 코드는 MIT, 규칙 분류와 문구는 CC BY-NC 4.0이다. README는 업무에서 자기 자료를 검사하는 사용에는 라이선스 비용이 없고 규칙을 유료 제품이나 강의에 넣으려면 별도 라이선스가 필요하다고 설명한다(API 사용료 등 실행 비용은 별도). 0.11.0 이하 릴리스에 MIT로 배포된 규칙 사본은 그 라이선스를 유지하므로 배포본도 확인한다.

## 생성형 대시보드는 작성 코드를 신뢰하지 않는 실행 경계에 둔다

모델이 만든 HTML 대시보드를 사내에 공유하면, 누구나 올린 JavaScript가 동료의 브라우저에서 실행되는 구조가 된다. 직원 약 500명 회사의 데이터 플랫폼 팀이 Looker 대신 이런 도구를 만들어 운영한 2026-10-14 회고에서 재사용할 설계는 다음과 같다.

- **조회 권한은 보는 사람의 신원으로:** 대시보드의 질의를 조회자의 Snowflake OAuth 토큰으로 실행해 데이터 웨어하우스의 기존 역할을 그대로 권한 모델로 쓴다. 대시보드를 공유해도 데이터 접근권은 공유되지 않는다.
- **대시보드 코드는 적대적이라고 가정:** 대시보드마다 별도 origin의 샌드박스 iframe에서 쿠키 없이 엄격한 CSP로 실행하고 부모 페이지와 postMessage로만 통신한다. 부모가 발신자를 확인한 뒤 세션을 붙여 API를 부르므로 대시보드 코드는 자격 증명을 만지지 않는다. 콘텐츠 토큰은 한 시간, 한 대시보드, 한 조회자, 한 호스트로 제한한다.
- **발행 뒤 비동기 검사:** 새 버전마다 질의, 불러오는 스크립트와 데이터를 보내는 곳을 추출해 규칙으로 판정한다. 대부분은 보고만 하고, 처음 보는 패키지의 스크립트나 CSP로 막을 수 없는 WebRTC 연결은 차단해 조회자가 경고를 수락해야 열린다.
- **AI 업로드는 초안으로:** 여러 사본으로 흩어진 업로드 스크립트를 회사 단일 원격 MCP 커넥터로 바꾸고, AI가 올린 결과는 초안으로 두어 사람이 발행한다.

초기에는 대시보드 JavaScript가 세션과 같은 origin에서 돌고 모든 직원이 모든 대시보드를 읽을 수 있었다고 팀 스스로 밝힌다. 사내망과 SSO만으로는 이 구조의 XSS 위험이 사라지지 않는다는 반례다. 비용 비교(8개월 구축비 약 8,300달러 대 같은 기간 Looker 평균 라이선스 환산 약 10만 달러, 대시보드 하나에 약 100만 토큰과 약 0.5달러)는 작성자의 자체 측정이며, 엔지니어 3명이 다른 업무와 병행한 8개월의 인건비는 넣지 않았다고 함께 밝힌다. 웨어하우스 권한, dbt 의미 계층과 운영 플랫폼을 이미 갖춘 조직의 사례로 읽는다.
