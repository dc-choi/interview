# 상시 실행 에이전트의 구조 — 이벤트 수신함, 타이머, 메모리, 권한과 발신함

상시 실행(always-on) 에이전트는 세션을 넘어 맥락을 유지하고(stateful) 사람의 직접 감독 없이 먼저 행동하는(proactive) 에이전트다. 이름과 달리 늘 깨어 있지는 않다. 대부분의 시간을 잠들어 있다가 이벤트가 오면 짧게 일하고 다시 잔다. 모델 호출과 도구 실행을 반복하는 핵심 루프는 다른 에이전트와 같고, 차이는 언제 깨어나는지, 실행 사이에 무엇을 넘기는지, 결과가 어떻게 사용자에게 닿는지를 정하는 주변 구조에 있다.

## 실행과 세션의 순환

- **실행(run):** 이벤트를 받아 일을 마치고 일어난 일을 저장하는 한 번의 작업 구간이다.
- **세션(session):** 메시지와 도구 호출의 기록이며 실행은 세션 안에서 돈다. 사용자의 답장처럼 이전 일을 잇는 이벤트는 기존 세션을 이어 가고, 나머지는 새 세션을 연다.
- **순환:** 실행이 끝나면 에이전트는 잠들고, 타이머나 사용자의 답장이 수신함에 이벤트를 넣어 다시 깨운다. 실행 하나는 짧지만 순환이 계속되어 늘 켜져 있는 것처럼 보인다.

## 다섯 가지 구성 요소

| 구성 요소 | 맡는 일 | 저장소 |
|---|---|---|
| 이벤트 수신함 | 웹훅, 예약 작업, 백그라운드 작업과 사용자 메시지 같은 깨움 신호를 모아 작업자에게 넘긴다 | 이벤트 목록(보통 DB 테이블) |
| 타이머 | 에이전트가 스스로 정한 후속 확인과 반복 일정을 때가 되면 수신함에 넣는다 | 수신함과 분리한 타이머 테이블 |
| 메모리 | 끊어진 실행 사이의 연속성을 유지한다 | 작업자보다 오래 남는 DB나 객체 저장소 |
| 권한 | 도구 호출마다 스스로 진행, 차단, 승인 대기 중 하나를 고른다 | 에이전트 밖의 자격 증명 저장소와 정책 |
| 발신함 | 결과와 질문을 사용자에게 내보낸다 | 보내는 메시지 테이블(필요할 때만) |

### 이벤트 수신함

이벤트 출처마다 에이전트를 직접 호출하면 동시에 온 두 이벤트가 경쟁하는 실행을 만들고, 충돌이 나면 이벤트를 잃는다. 수신함은 이벤트를 쌓는 내구성 있는 목록, 이벤트를 목록에 적는 처리기(보통 HTTP 엔드포인트), 목록을 읽는 작업자(보통 백그라운드 서비스)로 구성한다. 이벤트마다 상태를 추적하고 출처가 준 고유 식별자로 중복을 거르며, 사용자당 수신함 하나로 시작해 병렬성이 필요할 때 나눈다.

- **처리기는 빨리 응답한다:** 웹훅 제공자는 느린 응답을 실패로 본다. 처리기는 가벼운 검사만 하고 프롬프트 주입 검사 같은 깊은 확인은 실행 안에서 한다.
- **수신함이 진실의 원천이다:** 작업자는 깨어나면 수신함에서 최신 이벤트부터 읽는다. 실행 도중 작업자가 죽어도 새 작업자가 같은 이벤트를 다시 시도할 수 있다.
- **수신함 하나에 활성 작업자는 하나다:** 두 실행이 같은 일을 하거나 서로 덮어쓰지 않게 한다. 실행 중 새 이벤트가 오면 다음 실행으로 미루거나, 현재 실행에 합치거나, 중단하고 다시 시작한다.
- **쌓인 이벤트는 묶는다:** 사용자가 연달아 보낸 메시지를 한 실행에 합치면 답도 한 번만 보낸다.

죽은 작업자의 이벤트를 다시 시도한다는 것은 같은 이벤트가 두 번 실행될 수 있다는 뜻이다. 결제나 발송처럼 외부에 흔적을 남기는 도구에는 멱등 키를 붙이고([[Idempotency|멱등성]]), 웹훅의 서명 검증과 중복 처리는 [[Production-Agent-Architecture-Delegation#트리거는 판단 파이프라인으로 둔다|트리거 판단 파이프라인]]과 [[NestJS-Webhooks-Verification-and-Inbox|웹훅 검증과 inbox]]를 따른다(적용 제안).

### 타이머

타이머는 수신함과 함께 에이전트가 먼저 움직이게 한다. 후속 확인(follow-up)은 답장 확인처럼 에이전트가 스스로 정한 기한이고, 일정(schedule)은 매일 보내는 소식지처럼 알려진 주기로 반복하는 작업이다. 둘은 비슷한 스키마를 쓸 수 있지만 일정은 반복 규칙도 저장한다.

타이머는 수신함과 분리한 내구성 저장소에 둔다. 수신함에는 바로 처리할 이벤트만 있어야 하기 때문이다. 타이머가 스스로 실행을 시작하지는 않는다. 스케줄러가 일정한 간격으로 저장소를 훑어 기한이 된 타이머를 찾고, 후속 확인은 완료로, 일정은 다음 시각으로 갱신한 뒤 수신함에 이벤트를 넣고 작업자를 깨운다. 스케줄러는 직접 만들거나 내구성 실행 엔진(durable execution engine)을 쓴다. 제품에서 두 종류를 나눈 사례는 [[ChatGPT-Dots#고정 예약과 스스로 정하는 후속 확인을 구분한다|ChatGPT dots의 고정 예약과 후속 확인]]이다. 에이전트의 행동이 다시 자신을 깨우는 연쇄는 [[Production-Agent-Architecture-Delegation#트리거는 판단 파이프라인으로 둔다|트리거 판단 파이프라인]]의 출처 표시와 발송 상한으로 막는다.

### 메모리

메모리도 따로 저장한다. Anthropic은 Claude Code의 auto memory와 Messages API의 memory tool을 파일 디렉터리로 구현했고, 상시 실행 에이전트에서는 그 디렉터리를 DB나 객체 저장소에 연결해 작업자보다 오래 남기라고 권한다. 다시 조회할 수 없는 것만 저장하고, 이슈 트래커처럼 다른 시스템에 이미 있는 정보는 위치만 남긴다.

| 종류 | 담는 것 | 실행을 시작할 때 읽는 범위 |
|---|---|---|
| 사용자 지시 | 에이전트의 행동에 관한 사용자의 지시 | 별도 파일 전체를 매번 |
| 사용자 노트 | 역할, 선호와 사용자가 준 교정 | 커지면 여러 파일로 나누고 색인만 |
| 지난 메시지 | 사용자에게 이미 한 말(반복 방지) | 별도 파일 또는 최근 메시지 몇 개 |
| 작업 진행 | 진행 중인 작업마다 한 일과 남은 일 | 색인만, 필요할 때 개별 파일 |

실행 중 저장 외에 지난 세션을 돌아보며 낡은 항목을 바꾸고 여러 실행에 걸쳐서만 보이는 패턴을 찾는 정리 과정(Anthropic은 dreaming이라 부른다)을 더할 수 있다. 시스템 프롬프트, 도구 정의와 메모리 파일은 실행마다 붙는 고정 비용이므로 가볍게 유지하고 프롬프트 캐싱으로 비용을 줄인다. 새 세션은 이 고정 비용과 실행을 부른 이벤트로만 시작하고, 기존 세션은 이전 실행의 메시지와 도구 호출을 다시 가져온다. 세션이 길어지면 오래된 메시지를 압축하거나 새 세션을 여는데, 둘 다 세부를 잃으므로 남겨야 할 것은 진행 중에 메모리에 적는다. 예산 설계는 [[Agent-Context-Budget|에이전트 컨텍스트 예산]], 에이전트가 쓴 메모리를 검토한 뒤 신뢰하는 원칙은 [[Hermes-Agent#에이전트가 쓴 스킬과 메모리는 검토한 뒤 신뢰한다|Hermes Agent]]를 본다.

### 권한

실행은 사용자의 접근 권한을 쥔 채 감독 없이 돌기 때문에 위험이 가장 큰 곳이다. 구성 요소는 다른 에이전트와 같다.

- **자격 증명 저장소:** 비밀번호나 액세스 토큰은 에이전트 환경 밖의 프록시가 나가는 요청에 끼워 넣는다. 에이전트는 자격 증명 없이 요청을 보낸다.
- **자동 승인 모드:** Claude Code의 auto mode처럼 분류기가 위험도가 높은 행동을 검토해 위험한 것을 막고 더 안전한 길을 찾게 한다. 가장 중요한 결정은 여전히 사람이 검토한다.
- **미룬 도구 호출:** 승인이나 추가 입력이 필요하면 훅이 도구 호출을 미루고, 실행은 끝나며 세션은 호출 도중의 상태로 저장된다. 요청은 MCP Apps로 만든 대화형 카드 같은 방식으로 사용자에게 보이고, 답은 수신함의 이벤트로 돌아와 새 실행이 저장된 세션을 이어 간다. 답을 기다리는 동안 작업자는 다른 이벤트를 처리하므로 에이전트가 막히지 않는다. Claude Code 훅의 `defer` 결정은 [[Claude-Code-Extension-Reference|Claude Code 확장 레퍼런스]]에 있다.

누구의 권한으로 실행하는지, 승인을 기다리다 시간이 지나면 어떻게 할지는 [[Production-Agent-Architecture-Delegation#여러 사용자가 쓰는 에이전트는 누구의 권한으로 실행하는지 정한다|실행 주체와 무응답 처리]]를 함께 적용한다.

### 발신함

상시 실행 에이전트는 대부분 배경에서 일하므로 사용자는 단계별 추론 대신 결과와 몇 가지 세부를 받는다. 실행은 발신함에 메시지를 보내거나, 보낼 것이 없다고 판단하거나, 미룬 도구 호출로 허락이나 입력을 요청하는 셋 중 하나로 끝난다. 대부분은 메시지를 사용자에게 바로 전하는 send 도구로 충분하다. 메시지 속도를 조절하거나 전송 오류에서 복구해야 할 때만 발신함 테이블과, 작업자에 대응해 보낼 메시지를 고르고 내보내는 디스패처를 둔다.

너무 많이 보내면 시끄럽고 너무 적게 보내면 사용자가 알아야 할 것을 놓친다. Anthropic은 평가(eval)로 균형을 찾고, 조용히 시작해 사용자의 주의를 조금씩 얻어 가라고 권한다. 알림 등급과 발송 직전의 수신자 인가 재검사는 [[Production-Agent-Architecture-Delegation|위임 경계]]를 본다.

## 제품 사례: 이벤트에 반응하는 하네스 Pine

2026-11-25 공식 저장소의 README와 이벤트 참고 문서 기준, Pine은 파일, 메시지와 기기의 변화 같은 이벤트에 에이전트가 반응하게 하는 오픈소스 하네스다(MIT, npm 배포). 터미널 UI와 데스크톱 앱 외에 UI 없이 이벤트에 계속 반응하는 데몬 모드가 있다. 위 구성 요소에 대응시키면 다음과 같다.

- **출처와 구독:** 이벤트 출처는 스키마를 가진 TypeScript 서비스이며, 문서의 출처 유형에는 폴더, MQTT, 웹훅, FTP, Telegram, HTTP, 명령, 피드, 캘린더, 메일, Slack, ONVIF 카메라, Modbus와 시리얼 장치 등이 있다. 사용자가 감시할 대상과 할 일을 말하면 메인 에이전트가 관리용 도구 호출로 에이전트, MCP, 출처, 스킬과 일정을 구성한다. 설정을 에이전트가 바꾸므로 그 변경도 권한과 검토 대상으로 둔다(적용 제안).
- **수신함의 동작:** 이벤트는 MQTT식 와일드카드(`+`, `#`)를 쓰는 토픽으로 흐른다. 기본 경로는 구독이다. 문서는 대부분의 구성에 경로(route)가 필요 없다고 적고, 출처에 반응하는 에이전트는 그 출처를 구독하며 이벤트는 구독한 대화의 다음 메시지로 들어간다. 구독의 throttle 기본값은 10초이고 그 사이에 온 이벤트는 이벤트 로그에만 남을 뿐 에이전트를 깨우지 않으며 나중을 위해 보관되지도 않는다(모든 이벤트가 중요한 출처는 `0s`로 끄고, 에이전트에게 쓴 메시지를 전하는 `talks` 유형 출처에는 기본 throttle이 적용되지 않는다). debounce는 잠잠해질 때까지 기다렸다 마지막 것만 처리하고, 구독한 대화가 일하는 중이면 이벤트는 차례를 기다린다. 경로는 에이전트를 깨우지 않고 값을 저장하거나 다른 토픽으로 내보내는 작은 일에 쓰며, 경로에서 에이전트를 부를 때의 `whenBusy`는 기본값 `steer`이면 진행 중인 작업에 넘겨 실행 한 번과 답 한 번으로 묶고(답이 다른 곳으로 가는 이벤트는 기다린다) `queue`면 작업이 끝날 때까지 기다린다. throttle 기본값은 위 수신함의 이벤트를 잃지 않는다는 원칙과 다른 선택이므로 출처마다 확인한다(이 문서의 판단).
- **타이머:** cron, 간격(`every`), 한 번(`at`, `in`) 일정을 둔다. 데몬이 꺼진 동안 지난 일회성 일정과 작업이 붙은 cron 일정(7일 이내)은 다시 켜질 때 한 번 실행하며 늦었다고 알리고, 간격 일정은 따라잡지 않는다.
- **신뢰 등급:** 웹훅과 외부 출처의 이벤트는 기본으로 신뢰하지 않는(untrusted) 등급이고, 출처 항목에 `"trust": "owner"`가 있으면 owner 등급이다(계정을 직접 짝지은 Telegram 출처는 추가할 때 이 값이 들어간다). 문서는 서명이 맞아도 보낸 사람을 확인할 뿐 내용이 따를 만하다는 뜻은 아니라고 적는다. 보호 방식은 전달 경로에 따라 다르다. 기본 구독에서는 이벤트가 데이터로 표시돼 들어가고 에이전트는 그 대화의 파일과 도구를 그대로 가지며(외부 이벤트가 시작한 실행에는 다른 대화를 읽는 `read_source`만 빠진다), 대신 그 대화에 외부 내용을 읽었다는 표시가 붙어 정보를 밖으로 보내는 행동은 실행 전에 사용자에게 묻고(소유자에게 알리는 전송은 예외) 우회(bypass) 모드가 멈춘다. 구독에 `separate: true`를 주면 이벤트가 전용 대화로 들어가고, 내 것이 아닌 출처에는 줄인 도구 묶음(파일 읽기)만 준다. 경로를 거친 신뢰하지 않는 이벤트에 대해서는 출처와 데이터임을 알리는 앞머리 줄이 예의일 뿐이고(본문은 정해진 길이에서 잘린다) 실제 보호는 그 실행이 쓸 도구를 줄이는 데 있다고 밝힌다. 경로의 신뢰를 owner로 올리는 설정은 소유자 말고는 아무도 쓸 수 없는 출처에만 쓰라고 한다. 따라서 기본 구독은 도구를 줄이지 않으며, 낯선 사람의 글이 실리는 출처나 권한이 큰 무인 에이전트에는 `separate`를 쓰라는 것이 문서의 권고다.
- **실행 격리:** `safe` 모드는 macOS와 Linux의 시스템 샌드박스를 쓴다. Docker 안에서는 권한을 더 주지 않으면 에이전트 전용 샌드박스를 만들 수 없어 `auto` 모드로 돌고, 에이전트와 Pine 자신의 비밀 값이 같은 컨테이너에 있다고 적는다. 이벤트가 이벤트를 부르는 고리는 일정 단계에서 끊고 로그에 남긴다.

README는 소유자가 설정한 모델 서버, 웹 주소, 출처와 MCP 서버 말고는 정보를 보내지 않는다고 적는다(앱의 새 버전 확인 요청은 예외). 보안 문서는 신뢰하지 않는 이벤트가 시작한 작업의 기본 도구를 읽기와 검색(`read`, `grep`, `find`, `ls`)으로 한정하고 셸, 쓰기, MCP 서버, 위임, 이벤트 발행과 설정 변경 도구를 등록하지 않으며, 그 작업을 사용자 대화와 분리된 세션에서 돌린다고 적는다. 이 범위는 에이전트별로 넓힐 수 있고 넓힌 만큼은 묻지 않고 쓰이므로, `pine check`가 셸이나 쓰기를 가진 프로필을 알려 준다. 확인한 문서에서 같은 이벤트의 재전달과 장애 뒤 재시도의 중복 방지, 발신량 조절은 찾지 못했으므로 위의 [[Idempotency|멱등성]]과 발신함 평가는 직접 확인한다. 설치와 이벤트 처리는 시험하지 않았다.

## 모델 비용 수치를 읽는 조건

Anthropic은 상시 실행 에이전트가 다시 늘어난 이유로 사용자 의도와 확인 시점을 더 잘 판단하는 모델, 특히 장기 과업에서 싸진 비용을 든다. 근거 수치는 한 장기 코딩 벤치마크에서 Opus 5.5의 해결 과업당 비용이 Opus 5보다 78% 낮고 일반 작업에서는 40% 낮다는 것이다.

링크된 공식 문서 기준 78%는 Anthropic 하네스에 맞춰 고른 SWE-bench Pro 부분집합(482문제로 정의, 공개 리더보드와 비교할 수 없다)에서 각 모델의 기본 노력 수준인 Opus 5의 high와 Opus 5.5의 medium을 비교한 값이다. 문서는 Opus 5.5 비교에 채점 환경이 바뀌며 4문제를 뺀 478문제를 썼고 업그레이드 비교도 모든 모델을 478문제로 셌다고 적지만, 2026-08-04 Opus 5 실행의 설명에는 문제 수를 따로 밝히지 않는다. 해결률은 91.9%와 92.8%로 비슷했고, 캐시 읽기와 쓰기를 반영한 청구 기준이며 Opus 5의 가격을 그대로 적용하면 약 69%다. 40%는 그 문서가 직접 잰 값이 아니라 출시 글을 인용한 값이다. 자기 과업의 비용은 과업 길이, 노력 수준과 캐시 비율을 맞춰 직접 잰다. 발표 수치 일반의 조건은 [[Model-Release-Claims|모델 발표 수치 읽기]]를 본다.

## 설계 점검

다음은 위 구조에서 도출한 적용 제안이다.

- 어떤 출처가 수신함에 쓸 수 있는지, 그 내용을 신뢰할 지시로 볼지 외부 입력으로 볼지 정했는가.
- 외부 입력이 깨운 실행에 줄 도구를 신뢰 등급에 따라 줄였는가. 도구가 기본으로 줄어드는지, 따로 설정해야 하는지 확인했는가.
- 같은 이벤트를 다시 실행해도 외부 부작용이 두 번 생기지 않는가.
- 에이전트가 스스로 거는 후속 확인에 개수와 최소 간격의 상한이 있는가.
- 메모리에 넣지 않을 것(다시 조회할 수 있는 정보, 비밀 값)을 정했는가.
- 자격 증명이 에이전트의 컨텍스트와 로그에 들어가지 않는가.
- 보낸 메시지와 보내지 않기로 한 판단을 평가할 기준이 있는가.
