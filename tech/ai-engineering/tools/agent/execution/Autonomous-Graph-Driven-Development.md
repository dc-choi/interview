# 자율 그래프 주도 개발 (Autonomous Graph-Driven Development)

사람이 프롬프트로 에이전트를 부르는 대신, 서버에서 주기적으로 도는 실행 그래프가 요구사항을 스펙, 구현과 검증 단계로 밀고 나가는 개발 방식이다. 에이전트는 사람의 판단이 필요할 때만 이슈와 PR로 사람을 부르고, 사람은 질문에 답하고 결과를 승인하는 결정자로 참여한다. 사람이 AI를 호출하던 주도권이 뒤집히는 셈이다. 진행 상태가 노트북의 대화 세션이 아니라 저장소와 예약 실행(발표 구성은 GitHub 워크플로)에 있으므로, 사람이 자리를 비워도 결정이 필요 없는 작업은 계속 진행된다.

아래 구성과 수치는 한 사내 신규 서비스(AI 고객지원 포털 백엔드)에 이 방식을 적용한 발표를 기준으로 정리했다. 효과 수치는 자기 보고이며 같은 조건의 비교군은 없다.

## 이름과 범위

- 이름은 발표자가 붙인 것이고 합의된 정의는 없다. 발표는 프로젝트 시작 무렵(2026년 7월) 등장한 그래프 엔지니어링과 발상은 비슷하지만 세부가 다르다고 구분했다. 노드, 엣지, 상태와 판정 분담의 일반 원리는 [[Agent-Graph-Engineering|그래프 엔지니어링]]을 따르고, 이 문서는 그 원리를 몇 달 걸리는 개발 프로젝트에 무인으로 적용할 때의 구조와 운영 문제를 다룬다.
- 스펙 주도 개발(SDD)에서도 스펙 작성과 구현을 에이전트에 맡길 수 있지만, 스펙 작성과 구현을 지시하고 다음에 할 일을 정하는 진행은 보통 사람이 맡는다. 이 방식은 그 진행을 그래프로 옮긴다. SDD 정의는 [[RFC-Writing#Spec-Driven Development (SDD)|SDD]], 팀 단위의 스펙과 결정 기록 운영은 [[Spec-Decision-Records|에이전트 작업의 스펙과 결정 기록]]을 본다.
- 한 실행 안에서 interrupt로 멈췄다 재개하는 [[Agent-Graph-Engineering#사람 승인 노드의 실행 경계|사람 승인 노드]]와 달리, 사람의 응답을 노드 실행 사이에서 기다린다. 응답을 기다리는 요구사항만 멈추고 다른 요구사항은 계속 진행된다.

## 풀려는 문제

- 대화형으로 쓰면 사람이 지시하고 결과를 확인하고 다시 지시한다. 응답을 기다리지 않으려고 세션을 여러 개 띄우면 어느 세션에 무엇을 시켰는지 추적하는 일이 사람의 인지 부담이 된다([[Agent-Terminal-Workspaces-Human-Bottleneck#사람이 병목이 되면 위임 계층을 나눈다|사람이 병목이 될 때]]).
- 기능 요구사항은 계속 바뀌고, 바뀔 때마다 영향받는 스펙과 코드를 다시 찾아 고치는 비용이 쌓인다. 변경은 모델 밖의 기획 문서에서 생기므로 더 좋은 모델로는 이 비용이 줄지 않는다. 기획 변경을 기계적으로 감지해 영향받은 항목을 다시 확정하게 만드는 구조가 필요하다.

## 세 원칙

1. **단일 원장(SSOT, Single Source of Truth):** 노드 안의 에이전트 루프는 실행마다 새 세션이라 이전 실행의 맥락이 없다. 요구사항, 진행 상태, API 계약, 인수 조건과 E2E 테스트를 스펙 저장소 한 곳에 두고 요구사항 ID로 묶으면, 세션이 끊기거나 다른 노드가 이어받아도 ID 하나로 필요한 맥락을 다시 모은다.
2. **서로 부르지 않는 노드:** 노드는 다른 노드를 호출하지 않고 원장의 진행 상태만 보고 자기 일을 찾으며, 같은 상태에서 다시 실행해도 결과가 같게(멱등) 만든다. 그래서 한 노드가 멈춰도 나머지는 돌고, 일시적인 서버 장애나 모델 오류는 다음 사이클이 이어받으며, 여러 요구사항이 서로 다른 단계에서 동시에 진행된다. 모델 출력은 실행마다 달라질 수 있으므로 멱등성은 대상 선별과 상태 전이를 맡는 코드가 지킨다. 이미 PR이 열린 요구사항을 다시 고르지 않는 식이다(이 문서의 해석, 외부 작업의 중복 방지는 [[Harness-Anatomy#상태 복구와 외부 작업의 중복 방지는 별도다|상태 복구와 중복 방지]]).
3. **열린 질문:** 기획의 모호함이나 구현 중 찾은 스펙 결함처럼 사람의 판단이 필요한 일은 질문 이슈로 올리고, 이슈가 풀릴 때까지 해당 요구사항의 스펙 작성과 구현만 멈춘다. 사람이 코멘트로 답하면 다음 사이클이 반영해 남은 일을 진행한다. 무인 실행 전에 결정 공백을 인터뷰로 없애는 방식([[BMad-Method#무인 실행으로 확장할 때|BMad 확장 사례]])과 달리 실행 중에 생긴 질문을 항목 단위로 격리하며, 두 방식은 함께 쓸 수 있다.

노드가 공유 원장의 상태를 읽고 한 단계씩 옮기는 반복은 원하는 상태와 실제 상태의 차이를 controller가 줄여 가는 [[K8s-Core-Workloads-and-Service|Kubernetes reconciliation 모델]]과 같은 방향으로 읽을 수 있다. 원장이 Git 저장소이고 상태 전이가 PR 병합이라는 점은 GitOps와도 닮았다(이 문서의 해석).

## 노드와 엣지

- **노드:** 결정론적 코드와 에이전트 루프로 이뤄진다. 코드는 루프 앞에서 이번 사이클에 처리할 대상을 고르고, 뒤에서 상태 전이가 타당한지 검사한다. 고른 대상이 없으면 모델을 부르지 않는다.
- **엣지:** 스펙의 상태 전이다. 전이된 스펙이 다음 노드의 처리 대상이 된다.
- **전이 규칙:** 상태는 앞으로 한 단계씩만 움직인다. 확정된 계약을 바꾸려면 강등했다가 다시 확정해야 하는데, 바뀌기 전 스펙 위에서 구현과 테스트가 이어지는 것을 막는 규칙이다.
- **승인:** 전이는 코드 게이트가 타당성을 검사한 뒤 사람이 승인(PR 병합)해 이뤄진다. 예외로 E2E 테스트를 통과한 검증 완료 승격은 사람 없이 자동 병합한다.

발표의 그래프는 다섯 노드다. 노드 이름은 전사로 확인하기 어려워 역할로 적는다.

| 노드 | 대상을 고르는 코드 | 에이전트가 하는 일 | 사람의 개입 |
|---|---|---|---|
| 기획 반영 | 화면 단위로 발행한 기획 파일의 해시를 기준점과 비교해 바뀐 파일이 있을 때만 | 바뀐 부분을 읽어 요구사항 카탈로그에 반영한다. 새 요구사항은 등록, 영향받은 것은 재확정 필요로 강등, 사라진 것은 폐기한다. 의도가 모호하면 질문 이슈를 올린다. 리뷰 에이전트가 카탈로그 PR을 기획 원문과 대조한다 | 에이전트의 기획 해석을 승인한다. 카탈로그 PR이 병합된 시점의 해시가 다음 변경 감지의 기준점이 된다 |
| 스펙 확정 | 등록이나 재확정 필요 상태에서 우선순위, 선행 요구사항과 동시 작업 한도로 고른다. 질문 이슈나 열린 PR이 있으면 뺀다 | API 계약, 인수 조건과 E2E 테스트를 한 PR로 쓴다. 리뷰 에이전트가 기획 원문과 이슈에 대조하고, 지적이 남으면 다음 사이클의 재작업 세션이 같은 PR을 이어 고친다. 풀 수 없는 기획이나 스펙의 논리 오류는 질문 이슈로 올린다 | 지적이 없으면 코드가 자동 승인하고, 병합은 사람이 누른다 |
| 구현 | 확정된 요구사항마다 개발 저장소에 티켓을 하나만 만들고, 동시 작업 한도 안에서 착수할 티켓을 고른다. 버그 티켓이 먼저다 | 스펙이 최신인지 확인하고 구현 PR을 쓴다. 리뷰 에이전트가 계약과 대조하고, 지적이 없어질 때까지 같은 PR을 이어 고친다. 스펙 결함을 찾으면 스펙 저장소에 질문 이슈를 올리고 구현을 멈춘다. 작업 이력과 토큰 비용은 티켓 스레드에 쌓인다 | 구현 PR을 병합한다 |
| 검증 | 구현 완료 커밋이 배포되면 대상이 된다 | 스펙에 정의된 E2E 테스트는 자동화 코드가 실행한다. 실패하면 에이전트가 현상과 원인을 분석해 개발 저장소에 버그 티켓을 올린다 | 없다. 통과하면 승격 PR이 자동 병합되어 검증 완료 상태가 되고 프런트엔드 저장소에 API 연동 요청 이슈가 올라간다 |
| 전체 감사 | PR 하나가 아니라 스펙 저장소 전체를 본다 | PR마다는 문제가 없어도 전체로 보면 생기는 결함(폐기된 스펙의 인용, 한 곳은 허용하고 다른 곳은 거부하는 규칙)을 찾아 이슈로 올린다 | 결함이 맞는지, 지금 고칠 가치가 있는지 판단해 라벨만 붙이면 스펙 확정 노드가 다음 사이클에 고친다 |

진행이 이슈와 PR에 흩어져 있어 어느 요구사항이 어느 단계에서 왜 멈췄는지 알기 어렵다. 그래서 진행 상태, 처리 우선순위, 대기 사유, 사람의 결정을 기다리는 요구사항과 토큰 비용을 모은 진행 현황 대시보드를 따로 둔다.

## 무인 세션의 한도와 이어받기

- **턴 한도:** 끝없이 돌며 토큰만 쓰는 세션을 막는 첫 안전장치다. 발표 구성은 구현과 재작업 세션에 최대 100턴을 두었다. 한도를 다 채워도 약 45분 안에 끝나 매시간 도는 다음 사이클과 겹치지 않고, 턴이 늘수록 컨텍스트가 커져 비용이 오르고 속도와 코드 품질이 나빠져 실측으로 정한 값이다. 한도는 다른 곳의 권장값을 옮기기보다 실행 주기와 턴별 비용, 품질을 재서 정한다(적용 제안). 루프 가드의 일반 원리는 [[Agent-Loop-Engineering|루프 엔지니어링]]을 따른다.
- **진행분 보존:** 실행기가 강제하는 턴 한도에 닿으면 에이전트는 남은 턴을 모르는 채로 세션이 끊긴다. 그래서 세션을 시작하자마자 draft PR을 열고 진행분을 주기적으로 커밋하게 하며, 강제 종료되면 코드가 서버에 남은 커밋을 draft PR로 푸시한다. 다음 사이클의 재작업 세션은 그 브랜치에서 이어 가 최종 PR까지 마무리한다. 마지막 커밋 뒤의 작업만 잃는다.
- **연속 중단 상한:** 같은 티켓이 턴 한도로 연속 10번 끊기면 Need Decision 라벨을 붙여 재작업을 멈추고 사람에게 확인을 요청한다. 잘못된 방향의 구현에 토큰이 계속 들어가는 것을 막는 두 번째 안전장치로, 세션 단위 한도 위에 작업 단위 한도를 겹으로 둔 것이다.
- **실행 겹침과 지연:** 세션 길이를 실행 주기보다 짧게 잡는 것은 겹침을 줄이는 추정일 뿐이다. GitHub Actions의 `concurrency` 그룹은 같은 그룹에서 동시에 도는 실행을 하나로 제한하고, 진행 중인 실행이 있으면 새 실행은 대기하며 이미 대기 중이던 실행은 기본적으로 취소된다. 대기한 실행의 순서는 보장하지 않는다. `schedule` 이벤트는 부하가 클 때 늦어질 수 있고 문서는 매시 정각을 부하가 큰 시간으로 들며, 부하가 충분히 크면 대기 중인 작업 일부가 버려질 수 있다고 적는다(2026-11-18 GitHub.com 문서 기준). 겹침은 실행기 설정으로 막고 정각을 피해 예약하며, 취소되거나 버려진 실행은 멱등한 노드의 다음 사이클이 이어받게 둔다(적용 제안).

## 운영에서 드러난 문제와 대응

발표 사례가 그래프를 안정화하며 겪은 문제다. 대응은 그 프로젝트의 선택이며 다른 프로젝트에서 효과를 검증한 것은 아니다.

1. **세션이 끊기면 코드가 사라졌다.** 턴 한도로 강제 종료된 세션의 코드는 PR에 닿지 못해 유실됐고, 다음 사이클은 새 세션이라 이어받을 방법이 없어 같은 스펙을 처음부터 구현하다 끊기기를 반복했다. 위의 draft PR과 재작업 흐름이 이 문제에서 나왔다.
2. **변경 감지 단위가 영향 범위보다 컸다.** 처음에는 기획서 전체를 해시 하나로 기록해 매시간 비교했다. 화면 하나만 바뀌어도 모든 스펙 기록이 낡은 것이 됐고, 기획이 자주 바뀌는 시기에는 카탈로그 PR이 병합되기 전에 다음 변경이 감지되어 PR이 닫혔다 다시 열리기를 반복했다. 지문을 파일 단위로 바꿔 실제로 바뀐 문서만 비교하고, 스펙을 쓰기 전에 참조하는 기획 페이지만 부분 갱신하게 했다.
3. **사람의 검토가 그래프를 따라가지 못했다.** 그래프는 쉬지 않는데 사람의 검토와 승인이 늦어지는 사이 기획이 바뀌어, 검토 중이던 PR이 그래프 규칙에 막혔다. 동시 작업 한도를 넘으면 새 작업을 시작하지 못하게 해 에이전트가 사람의 속도에 맞추게 했고, 먼저 검토할 이슈와 PR은 대시보드로 찾게 했다. 동시에 굴리는 작업의 양을 사람이 실제로 검토할 수 있는 양으로 정하는 원칙([[Agent-Terminal-Workspaces-Human-Bottleneck#위임 계층 없이 한 사람이 여러 세션을 돌릴 때|병렬 세션의 검토 용량]])과 같은 결론이다.
4. **승인이 형식이 됐다.** 그래프가 PR을 잘 만들자 스펙 PR을 훑어보고 승인하게 됐다. 사내 상담 시스템과 연동해야 한다는 내용이 빠진 스펙이 승인되어, 상담 시스템으로 보내야 할 문의 접수가 DB에 저장되도록 구현됐고 폐기 뒤 다시 작업했다. 이후 외부 연동 가이드를 개발 저장소에 미리 두고 구현 전에 읽게 해, 스펙이 놓쳐도 구현이 어긋나지 않게 했다. 사람에게 남는 역할이 승인일수록 형식적 승인의 비용이 커진다([[AI-Code-Delegation-Review-Cognitive-Surrender|위임과 인지적 항복]]).
5. **모든 검사가 같은 오해를 통과시켰다.** 기획서의 "세션 종료 이후의 대화는 새 세션으로 시작"이라는 문장을 기획자는 종료 뒤 대화를 막고 사용자가 새 세션을 직접 열게 한다는 뜻으로 썼다. 에이전트는 종료 뒤 들어온 대화를 새 세션으로 자동으로 넘겨 이어 간다는 뜻으로 읽었고, 그 해석대로 인수 조건과 E2E 테스트까지 만들어 모든 검사를 통과했다. 그래프의 규칙은 근거가 있는지는 검사해도 근거를 맞게 이해했는지는 검사하지 못한다. 정책과 조건을 한 가지 뜻으로만 읽히게 쓰기로 기획팀과 합의했다. 스펙, 테스트와 구현이 같은 해석에서 나오면 서로는 맞아도 의도와 어긋날 수 있다([[Test-Pyramid-Blind-Spots#구현과 기대값이 같은 오해를 공유하는 경우|같은 오해를 공유하는 기대값]], [[LLM-Hallucination-Verification#지시문으로 줄이고 검사로 막는다|존재와 지지 검사의 구분]]).

## 리드타임은 결정 대기 시간으로 수렴한다

발표 사례의 자기 보고 수치다.

- 그래프 가동 8주 뒤 주간 병합 PR의 87%를 루프가 썼다. 사람이 쓴 PR은 주로 그래프 운용 도구였다.
- 기획 변경부터 검증 완료까지 그래프가 실제로 처리한 시간은 몇 분에서 2시간 남짓이었고, 나머지는 사람의 결정을 기다린 시간이었다.
- 루프가 쓴 PR의 54%가 야간이나 주말에 나왔다. 노드가 매시간 돌아 사람이 결정하면 다음 실행에서 바로 이어지고, 한 요구사항이 기다리는 동안 다른 요구사항이 진행된다.

처리 시간이 줄면 리드타임은 사람의 결정 대기 시간에 가까워지고, 다음 개선 대상은 결정 시간이 된다. 발표가 밝힌 다음 과제는 카탈로그 PR과 구현 PR의 병합 자동화다. 자동 병합으로 넘어가기 전에 어떤 변경을 저위험으로 볼지와 사람 대신 무엇을 검사할지부터 정한다(적용 제안, [[AI-Native-Org#출시 흐름의 병목은 단계를 따라 옮겨 간다|단계를 따라 옮겨 가는 병목]], [[Developer-Role-AI-Era#구현이 싸질 때 옮겨 가는 병목 — 결정과 승인 대역폭|결정과 승인 대역폭]]). PR 비율은 PR의 크기, 품질과 되돌림이 함께 공개되지 않아 생산성의 근거로 바로 쓰지 않는다.

## 사례: 비용과 범위

발표 사례의 자기 보고 수치다.

- **진행과 코드량:** 착수 약 3개월 시점 개발 진행률은 약 92%였다. 제품 코드는 약 2만 5천 줄이었고, 그래프 운용 도구의 코드와 문서는 6만 2천 줄이 넘어 제품의 2~3배였다. 이 기간 사람은 대부분 도구 개발과 안정화를 맡았다.
- **사람 시간:** 기존 방식 산정은 백엔드 개발자 2명이 3개월, 6인월(MM)이었다. 실제로는 12주 동안 약 348시간(2.2MM, 63% 절감)을 썼고 그중 약 60%가 그래프 운용 도구 개발이었다. 제품과 스펙에 쓴 시간은 137시간(0.86MM, 약 86% 절감)이다.
- **토큰 비용:** 제품을 개발한 루프가 2,555달러(최상위가 아닌 Sonnet 계열 모델, 전사 기준 Sonnet 5), 사람이 로컬에서 루프의 질문에 답하거나 제품 작업을 할 때 2,800달러(초기 시행착오 포함), 그래프 운용 도구 구축에 3,600달러를 썼다. 요구사항 1건의 구현 완료 비용은 약 36달러였다. 원화로 합산한 전체 비용은 도구 구축을 포함해 약 3천만 원, 제외하면 약 1,470만 원이며, 후자를 연봉 1억 원 기준 6MM과 비교해 약 71% 절감으로 계산했다. 같은 기준으로 도구 구축을 포함하면 절감은 약 40%다(이 문서의 계산).
- **복잡한 기능 하나:** MySQL, MongoDB, Redis, AI 에이전트와 외부 API가 얽히고 결과를 비동기 스트리밍 이벤트로 돌려주는 AI 대화 기능은 스펙 변경에 따른 강등과 재확정으로 구현 티켓이 9번 다시 열렸고, 버그 티켓 5건을 처리해 완성됐다. 토큰은 약 200달러였다.

읽을 때의 경계: 6MM은 실제로 수행한 비교군이 아니라 사전 산정이고, 도구 구축 비용이 다음 프로젝트에서 거의 들지 않는다는 것은 전망이다. 스펙이 명확하면 최상위 모델이 아니어도 충분했다는 판단도 이 프로젝트 하나의 관찰이다. 도구에는 특정 제품의 문서와 코드가 없어 다른 프로젝트에도 쓸 수 있다고 했지만, 요구사항을 받는 입력 어댑터와 배포 시스템을 잇는 출력 어댑터는 프로젝트마다 맞춤이 필요하다고 함께 밝혔다.

## 사람에게 남는 일

발표 사례에서 개발자의 일은 코드를 쓰거나 에이전트에게 지시하는 일에서 결정과 승인으로 옮겨 갔다. 프로젝트에서 사람이 한 여섯 가지 일(목록은 화면 자료라 확인하지 못함) 가운데 에이전트의 질문에 답하기, 기능 제안, 결과 승인은 앞으로도 남고 나머지는 모델이 좋아지면 줄거나 사라질 수 있다는 전망이다. 남는 일이 모두 판단이므로, 기획 문장의 명확성과 승인의 실질이 결과 품질을 좌우한다(이 문서의 해석).

## 적용 점검

- 노드가 서로를 부르지 않고 원장의 상태만 보고 일하며, 같은 상태에서 다시 돌려도 같은 작업을 중복으로 만들지 않는가
- 다음 사이클이 이어받을 수 있게 진행분이 세션 밖(브랜치, draft PR, 티켓 스레드)에 남는가
- 세션 한도가 실행 주기 안에 끝나고, 같은 작업이 계속 끊기면 사람에게 넘기는가
- 확정된 계약을 바꿀 때 바뀌기 전 스펙 위의 구현과 테스트를 멈추는 강등 경로가 있는가
- 질문을 기다리는 항목만 멈추고, 동시 작업 한도가 사람의 검토 용량에 맞춰져 있는가
- 변경 감지 단위가 영향 범위와 맞는가
- 스펙, 테스트와 구현이 같은 해석에서 나와 서로만 맞는 상태를 무엇으로 잡는가
- PR 단위 리뷰 밖에서 스펙 전체의 정합성을 보는 감사가 있는가
- 리드타임을 그래프 처리 시간과 결정 대기 시간으로 나눠 재는가
