# 대규모 코드베이스 지식 지도 — 기계의 추출, AI의 연결, 사람의 판단

코드베이스 전체를 RAG나 MCP로 질의할 수 있는 지식으로 만들 때, 대상이 커지면 문서를 더 넣거나 에이전트를 더 돌리는 것만으로는 해결되기 어렵다. 사실은 기계가 결정론적으로 추출하고, AI는 그 사실 사이의 근거를 연결하며, 사람은 목적을 정하고 결과를 판단하도록 역할을 나눈다. [[Agent-Code-Search|에이전트 코드 인텔리전스]]가 코딩 에이전트가 작업 중 쓰는 탐색 도구와 증거 수준을 다룬다면, 이 문서는 팀이 반복해서 질의할 코드베이스 지식 자산을 만들고 유지하는 방법을 다룬다.

원리와 절차는 2026-09-15 AWSKRUG DevOps 소모임 발표에서 공유된 구축 경험을 일반화한 것이고, 수치와 회고는 아래 사례 절에 발표 기준으로 모았다. 표의 연구와 도구, Self-Refine 설명은 2026-11-02에 각 1차 출처와 대조했고, Graphify와 REA는 연결 문서의 확인 기준을 따른다.

## 먼저 규모를 잰다

같은 RAG 구성도 대상 규모에 따라 결과가 달라진다. 저장소와 문서 공간이 몇 개인 수준이면 시판 RAG나 노트북형 문서 질의 도구로 충분할 수 있지만, 수십, 수백 개로 늘면 같은 방식에서 다른 문제가 나타날 수 있다(아래 사례 절).

시작 전에 저장소와 서비스(배포 단위) 수, 코드 라인과 파일 수, 문서 공간 수, 연결에 쓸 식별자(API 경로, 메시지 토픽, DB 테이블)의 종류를 센다.

## 전체를 한 번에 읽히는 방식의 한계

- **병렬 에이전트의 정본 부재**: 공통 판단 기준, 출력 형식과 병합 규칙 없이 코드를 나눠 여러 에이전트에 읽히면 에이전트마다 판단 기준이 달라지고 결과 사이의 연결이 끊기며 환각이 섞여, 결과를 모아도 하나의 정본으로 쓰기 어렵다.
- **통째 요약의 한계**: 전체 소스를 AI에게 분석시켜 만든 요약 Markdown을 RAG 근거로 쓰면 단편 검색에는 쓸 수 있어도 서로 연결된 운영 지식으로 쓰기 어렵다.
- **대응**: 전체를 한 번에 이해시키는 목표를 버리고, 질문에 필요한 범위와 깊이를 정해 지식을 쌓는다.

## 차원과 질문에서 연결할 사실을 정한다

1. 지식을 나눌 차원을 정한다. 예를 들어 코드베이스와 설정, 데이터 접근 구조, 운영 지식처럼 나눈다.
2. 차원마다 답해야 할 질문을 먼저 쓰고, 그 답에 필요한 사실과 연결을 도출한다.
3. 공통 식별자로 원본 위치를 묶는다. API 경로의 prefix, 메시지 토픽, 테이블, 클래스와 패키지가 후보다. 무엇을 공통 식별자로 삼는지가 지도의 품질을 좌우한다.

## 결정론적 추출 계층을 먼저 세운다

- **관점별 파서**: 관점마다 구조를 뽑는 파서를 둔다. 파서 코드는 AI에게 쓰게 할 수 있지만, 같은 입력에서 같은 결과가 나와야 다시 만들고 비교할 수 있다.
- **AI에게 맡길 분류**: 커밋 이력, 작성자와 PR 메시지로 저장소의 성격을 분류하거나 패키지 명명 규칙으로 서로 다른 저장소를 묶는 일은 AI에게 맡길 후보다. 그 결과는 파서 출력과 분리해 추론 상태와 근거(커밋, PR, 패키지명)를 함께 저장하고 표본을 검수한다(적용 제안).
- **호출 관계의 보강**: 소스에서 뽑은 선언과 구조만으로 호출 흐름이 부족하면 빌드 산출물(바이트코드 등)에서 호출 트리를 추출해 보강할 수 있다. 바이트코드 분석도 정적 분석이라 DI, 리플렉션, 프록시 같은 런타임 연결은 누락되거나 부정확할 수 있다.
- **참조 빈도는 후보다**: 참조 횟수가 많은 상수와 메서드를 뽑아 주석과 커밋 이력을 붙이면 핵심 업무 로직의 후보가 드러난다. 다만 [[Agent-Code-Search#그래프 계층 — 저장소 전체 관계를 지도화한다|그래프 중심성]]처럼 빈도는 중요도의 증명이 아니다.

## 확인, 추론, 미해결을 나눠 저장한다

연결을 만들었다고 끝나지 않는다. 각 연결이 확인된 사실인지, 추론인지, 추론에 실패해 미해결인지 분류해 저장한다. 미해결을 분류하지 않은 채 RAG에 함께 넣으면 MCP 응답에 섞여 나와 결과 전체를 신뢰하기 어려워진다. [[Agent-Code-Search#그래프 계층 — 저장소 전체 관계를 지도화한다|Graphify]]의 extracted, inferred, ambiguous edge 구분, REA의 관찰, 추론과 미해결 구분([[AI-Assisted-Legacy-Onboarding#소스가 없을 때는 분석 산출물과 실행 관찰을 구분한다|레거시 온보딩]])과 같은 원칙이다.

정적 분석의 호출 관계가 런타임에서도 맞는다는 보장은 없다. Java처럼 프레임워크가 런타임에 대신 연결하는 동작이 많은 환경에서는 특히 그렇다. 확신한 연결도 검수 대상으로 남기고, 검수를 반복해 돌릴 파이프라인을 둔다.

## 뼈대를 만든 뒤 문서로 살을 붙인다

API 경로의 prefix에서 시작해 관계 그래프를 정한 깊이까지 따라가며 API별 연결 지도를 만들고, 지도에 엮인 소스로 문서를 생성한다. 업무 문서가 뼈대의 식별자(API 경로, 토픽, 테이블)를 가리키면 그 위치에 내용을 연결할 수 있어, 서비스별 문서와 서비스 사이의 업무 흐름을 쌓아 갈 수 있다. 연결하지 못한 문서는 미해결로 남긴다(적용 제안).

깊은 단계의 탐색을 AI 에이전트에게 맡기면 무관한 연결까지 엮으려 해 한 번의 탐색 시간이 크게 늘 수 있다. 추출한 그래프는 코드로 깊이와 분기 수에 상한을 두고 순회한 뒤 AI에는 결과 부분 그래프만 주고, 상한으로 잘린 경로에서 필요한 근거가 빠지는지도 대표 질문으로 센다([[GraphRAG-Retrieval#기존 그래프에서는 시작점과 경로를 따로 고른다|GraphRAG의 시작점과 경로 선택]], 적용 제안).

관련 연구와 도구는 다음과 같다. 핵심 열은 각 1차 출처 기준이고, 셋째 열은 이 문서의 적용 해석이다.

| 방법 | 핵심 | 적용 해석 |
|---|---|---|
| RAPTOR | 청크를 재귀적으로 임베딩, 클러스터링, 요약해 아래에서 위로 요약 수준이 다른 트리를 만들고 여러 추상 수준에서 검색한다 | 세부 근거와 상위 요약을 계층으로 잇는다([[RAG-Retrieval-Engineering#계층적(Hierarchical) RAG\|계층적 RAG]]) |
| Contextual Retrieval | 청크에 문서 안의 맥락을 붙여 임베딩과 BM25 색인을 만든다 | 저장하는 사실에 그래프상의 위치와 맥락을 함께 붙인다([[RAG-Retrieval-Engineering#청크별 문서 맥락 보강 (Contextual Retrieval)\|청크별 맥락 보강]]) |
| Aider repository map | 저장소의 파일과 각 파일에 정의된 핵심 심볼(클래스, 함수와 시그니처)을 담은 지도를 만들고, 파일을 노드로 의존 관계를 간선으로 둔 그래프의 순위로 토큰 예산 안에 들어갈 부분을 고른다(2026-11-02 문서 기준 `--map-tokens` 기본 1k 토큰) | 다른 코드가 많이 참조하는 식별자를 우선해 지도의 범위를 줄인다 |
| C4 model | 소프트웨어 시스템, 컨테이너(애플리케이션이나 데이터 저장소), 컴포넌트, 코드의 계층적 추상화로 구조를 나눈다 | 결과 문서의 계층을 서비스, 모듈과 코드 수준으로 나눌 때 참고한다 |

## 재현성: 형식은 사람이 정하고 AI는 채운다

- **갱신 절차를 먼저 설계한다**: 프롬프트를 반복해 한 번 만든 결과는 같은 과정을 다시 돌릴 방법이 없으면 갱신하기 어렵다. 관점별 산출물이 쌓인 뒤에 정리하기보다 처음부터 재실행으로 갱신하는 과정을 만든다.
- **템플릿 고정**: 결과 문서 생성까지 AI에게 맡기면 실행마다 분석 형식이 깨지기 쉽다. 목차와 형식을 담은 템플릿을 주고 AI는 그 틀을 채우게 한다.
- **동일성 검사**: 같은 입력으로 여러 번 다시 파싱, 임베딩과 구축을 했을 때 추출한 사실, 간선과 템플릿 구조가 같은지 확인한다. 생성 문장은 글자 그대로가 아니라 구조와 근거 연결로 비교한다(적용 제안). 동일성을 확인하지 못하면 유지보수와 운영이 어렵다.
- **개선 기록**: 추출, 해석, 보강과 재검증의 과정을 파일로 남겨 다음 실행의 피드백으로 쓴다. 같은 모델이 출력에 피드백을 주고 다시 고치기를 반복하는 Self-Refine과 반복 구조는 닮았지만, 같은 모델의 자기 피드백은 외부 검증과 재현 기록을 대신하지 않는다.

## 벡터 DB와 실행 구조는 규모와 사용 방식으로 정한다

수천 개 문서 규모에서는 상시 벡터 DB 없이 임베딩 사이의 코사인 유사도를 직접 계산하는 편이 빠르고 쌀 수 있다. 판단은 [[Vector-Similarity-Search|벡터 유사도 검색]]처럼 exact 결과를 기준선으로 두고 규모, 실행 주기와 지연 목표로 측정한다.

MCP를 상시 띄우지 않고 연결할 때마다 로컬에서 새로 시작하는 사용 방식이면 cold start가 체감 지연을 크게 좌우할 수 있다. 벡터 DB, LLM 프록시와 런타임을 함께 띄우는 구성보다 색인 데이터를 빌드 산출물에 넣은 단일 검색 프로세스가 더 빨리 기동할 수 있다. 대신 실행 파일이 커지고 색인을 바꿀 때마다 다시 빌드해야 한다.

색인과 MCP를 로컬에 두면 외부 서비스 노출은 줄지만, 원격 모델을 쓰는 에이전트라면 에이전트가 받은 도구 결과와 코드 조각은 모델 제공자에게 전달된다. 규제가 강한 환경에서는 모델 제공자의 데이터 처리 정책과 전송 범위를 별도로 확인한다(적용 제안).

## 질의는 그래프 탐색의 진입점이 된다

- **업무 질문**: 가입 처리 흐름에서 청구 연계가 어디서 일어나는지 물으면, 문서에서 업무 개념을 찾고 연관 API, DB와 작업 이력을 따라 코드 위치와 호출 관계를 찾은 뒤 원문과 코드를 조합해 설명한다.
- **장애 영향 질문**: 어떤 메서드나 연동 시스템이 실패하면 어떤 업무가 실패하고 담당자가 누구인지 물으면, 연관 API, 테이블과 호출 서비스를 탐색해 답한다.
- **MCP의 위치**: MCP는 구축한 지도를 에이전트에 연결하는 마지막 단계일 뿐이고, 답의 품질은 구조화된 지도와 검증에서 나온다.

## 사례: 통신 BSS 코드베이스 (2026-09-15 발표 기준)

- **규모와 목적**: 약 2천만 라인, 약 15만 파일, 50~60개 서비스로 나뉜 통신 BSS 시스템이다. 시스템의 이력을 가진 핵심 인력이 빠진 뒤, 발표자가 시스템을 파악해 남은 팀원에게 업무를 나눠 맡길 수 있도록 AI로 지식 베이스를 만들려 했다. 발표자는 저장소와 문서 공간이 2~3개일 때와 20~30개, 200~300개일 때 문제가 다르게 나타났다고 정리했다.
- **실패한 시도**: 에이전트 약 200개에 코드를 나눠 읽혔지만 에이전트마다 판단 기준이 달라지고 환각이 섞여 결과를 정본으로 쓸 수 없었다.
- **추출 계층**: 관점별 파서를 수십 개(발표 중 30~50여 개로 언급) AI로 만들었다. 커밋 이력, 작성자와 PR 메시지로 저장소 성격을 분류하는 일은 AI가 잘 해냈고, 패키지 명명 규칙으로 저장소를 묶는 분류도 AI에게 맡겼다. 소스에서 얻은 정적 사실로는 호출 흐름을 알 수 없어 빌드할 때 바이트코드의 호출 흐름을 추적해 트리로 남겼다. 참조 횟수를 뽑자 180~200번씩 호출되는 것과 한 번만 쓰이는 것이 갈렸다.
- **탐색 시간**: AI 에이전트에게 추적 깊이를 높여 맡기자 무관한 연결까지 엮으면서 한 번의 탐색이 50분씩 걸리기도 했고, 4단계를 넘어 1시간 50분이 걸린 경우도 있었다. 탐색을 효과적으로 잘라 엮는 방법은 발표 시점의 미해결 과제였다.
- **검색 구조**: 약 15만 클래스, 수천 개 문서, 약 15 GB 규모의 대상에서 Qdrant 같은 벡터 DB 없이 로컬 모델 임베딩과 코사인 유사도 직접 계산을 썼다. 발표자는 문서가 100만 단위를 넘을 때부터 벡터 DB가 중요해지고 10만 단위 안쪽이면 직접 계산하는 편이 훨씬 빠르고 저렴하다고 봤다. 발표 본문에서는 측정 근거 없이 느낀 점으로 제시한 기준이며, 발표에서 언급한 부록의 실측 근거는 확인하지 못했다. 벡터 DB, LLM 프록시와 Python 런타임을 함께 쓰던 구성은 cold start가 약 3.7초였고, 임베딩 데이터를 빌드 때 바이너리에 넣은 Rust 단일 검색 워커로 바꾸자 MCP 크기는 조금 커졌지만 첫 검색이 0.5초 안에 끝나며 외부 임베딩 호출도 없어졌다.
- **재현과 검수**: 발표자는 결과를 한 번 만드는 데서 멈추지 말고 세 번, 네 번 다시 파싱하고 임베딩해 만들었을 때 동일한 결과가 나오는지 확인하라고 권했다. 여러 조직의 교차 검수는 받지 못했고 부수효과(사이드 이펙트)가 어디까지 미치는지 추적하는 일은 남은 과제로 꼽았으며, 이 지도를 장애 주입 시나리오 도구로 넓히려 한다고 밝혔다.
- **관련 연구**: 발표자는 RAPTOR, Anthropic의 Contextual Retrieval과 Aider repository map을 자신의 방식과 닮았거나 보강할 연구로, C4 model을 결과를 정리하는 방법의 예로 들었다.
- **구축 기간**: 기초 구조에 하루 반, 첫 동작에 이틀, 이후 주말까지 약 5일 만에 동작하는 틀을 만들었고 AI 도구 사용량도 컸다. 발표자는 외부 업체가 수억 원 규모로 몇 달 만든 결과물이 업체가 떠난 뒤 방치되던 경험과 대비해 작게 동작하는 틀을 계속 쌓을 수 있다는 점을 의미로 꼽았고, 전체를 이해했다거나 큰 ROI를 증명했다는 주장은 아니라고 밝혔다.

## 적용 점검 (적용 제안)

- 대상 규모와 공통 식별자 종류를 먼저 세었는가
- 차원별 질문이 있고, 각 질문에 필요한 연결이 정의돼 있는가
- 구조 추출이 결정론적 파서로 재실행 가능한가
- 연결마다 확인, 추론, 미해결 상태가 있고 미해결은 답변 근거에서 분리되는가
- 결과 문서의 형식이 템플릿으로 고정돼 있고 재구축 결과의 동일성을 검사하는가
- 그래프 순회에 깊이와 분기 수의 상한이 있고, 잘린 경로의 누락을 세는가
- 벡터 DB 도입 전에 exact 비교의 지연과 비용을 쟀는가
- 모델 제공자에게 전달되는 코드와 도구 결과의 범위를 확인했는가
