# 에이전트 역공학과 실행 가능한 시스템 하네스

역공학 에이전트는 실행 파일, 스크립트와 실제 동작에서 기능의 규칙을 복원한다. 코드 생성보다 먼저 관찰, 가설과 재현 가능한 검증 경로를 마련하는 작업이다.

## 관찰과 재구현을 분리한다

1. 입력, 초기 상태와 기대하는 관찰값을 고정한다.
2. 정적 분석으로 분기, 호출 관계와 데이터 표현을 찾는다.
3. 실행 중 상태와 출력으로 가설을 반증한다.
4. 복원한 규칙으로 구현하고 원래 프로그램과 같은 입력을 비교한다.
5. 관찰하지 못한 분기와 지원하지 않는 환경을 남긴다.

디컴파일한 의사코드는 원래 소스 자체가 아니며 호출 이름이나 타입 추론이 틀릴 수 있다. 비슷한 화면은 파일 호환성, 성능과 예외 동작의 동등성을 보장하지 않는다.

## REA: 분석 도구와 에이전트의 해석

2026-10-20 upstream 저장소(morluto/rea) README 기준, REA는 MCP 서버로 에이전트를 분석 도구에 연결하고 같은 도구를 터미널의 CLI(npm 패키지 `rea-agents`)로도 쓸 수 있게 한다. 네이티브 바이너리에는 Hopper, Ghidra나 IDA를 쓰는데, Ghidra와 IDA는 이미 설치한 것을 쓰고 Hopper는 사용자 승인을 받아 setup이 설치할 수도 있다(같은 저장소 `docs/installation.md` 기준 이 자동 설치는 macOS 12+와 일부 Linux 배포판만 지원하고 Windows에서는 제공하지 않는다). Android APK에는 headless JADX와 JDK를 쓰며, README는 분석 대상으로 JavaScript/Electron, .NET, 웹사이트, APK, 펌웨어, 기록한 패킷과 프로세스 동작을 든다. 반환하는 명령어, 의사코드, 문자열과 호출 참조를 에이전트가 연결해 설명과 재구현에 사용한다. 분석 엔진과 대상에 따라 필요한 도구 및 호스트가 다르다. README는 REA의 용도를 합법적 연구, 교육, 상호운용, 소프트웨어 보존, 사용자가 소유하거나 분석 권한을 받은 소프트웨어의 분석으로 밝힌다. 상용 분석 도구는 사용자가 적법하게 취득하고 사용 권한을 갖춰야 하며 REA가 그 라이선스, 키나 활성화 권리를 주지 않는다고도 적는다. 쇼케이스는 DX-Ball의 사운드 팬 계산 복원, Notion의 Electron 클립보드 경로 추적, PC-98용 TH04의 DOS 원형 탄막 각도 계산 복원이다.

README는 공식 배포 경로를 morluto/rea 저장소, rea.tools와 npm `rea-agents`로 밝히고, 비슷한 저장소 이름이나 복사한 README가 공식 배포의 근거가 되지 않는다고 경고한다. levelupsoft/rea-reverse는 morluto/rea의 fork다(2026-10-20 확인). MCP 서버는 에이전트에게 로컬 분석 도구의 실행을 맡기므로 설치 전에 upstream 저장소와 패키지 이름을 대조한다(적용 제안, [[Supply-Chain-Security|공급망 보안]]).

제공된 2026-10-11 GeekNews 발췌는 Chrome 공룡 게임의 가속 규칙, Windows Calculator의 연산자별 `%` 처리 복원을 소개한다. 두 데모는 upstream README의 쇼케이스에는 없지만, README가 공식 배포 경로로 밝힌 rea.tools에 예시로 실려 있다(2026-10-20 확인). 공룡 게임 예시는 Chrome에 내장된 게임이 아니라 제3자가 Chromium 코드에서 파생해 만든 브라우저판을 대상으로, 장애물과 자동 스케줄링을 끈 통제된 브라우저 검사에서 원래 게임의 update 함수를 호출해 속도 규칙을 확인했다. Calculator 예시는 REA 4.1.0으로 Windows Calculator 11.2508.4.0(x64)을 살펴 `%` 버튼이 ×와 ÷에서는 소수로, +를 비롯한 그 밖의 연산자에서는 첫 수의 백분율로 바꾸는 두 규칙을 복원하고, Microsoft의 공개 소스와 교차 확인하게 한다. 해당 데모의 모든 분기와 재구현 결과는 이번에 실행하지 않았다. 사례의 핵심은 동작 규칙을 확인할 관찰점을 찾는 데 있다.

## 디컴파일과 정적 재컴파일이 확인하는 동등성을 구분한다

바이너리에서 얻은 코드를 이식, 보존이나 학습의 근거로 쓰기 전에 그 코드의 어떤 동등성이 확인됐는지 구분한다. 정적 재컴파일은 실행 전에 원본 기계어를 다른 플랫폼에서 실행할 코드로 옮기는 방식이며 디컴파일과 다르다. 아래 표의 정적 재컴파일은 명령어마다 C 코드로 직역하는 N64Recomp 기준이다.

| 방식 | 확인하는 것 | 남는 한계 |
|---|---|---|
| 매칭 디컴파일 | 원래 컴파일러(SM64는 IDO, iQue판의 일부 파일은 EGCS gcc)로 다시 빌드한 산출물이 원본 바이너리와 해시까지 같은지 | 맞추지 못한 함수, 이름과 구조의 가독성, 원래 설계 의도 |
| 정적 재컴파일(N64Recomp 기준) | README는 원본과 대조하는 절차를 설명하지 않는다. 직역한 C 코드를 런타임과 함께 빌드한 결과가 원본처럼 동작하는지는 같은 입력의 실행 결과를 따로 비교한다(적용 제안) | 사람이 읽을 구조는 복원하지 않고, 런타임과 함수 경계, 이름 같은 메타데이터가 필요 |

2026-10-20 Super Mario 64 디컴파일 저장소(master 브랜치)의 README와 Makefile 기준, 저장소는 지원하는 다섯 판의 ROM SHA-1을 제시하고 `COMPARE=1`로 빌드 결과의 해시를 비교한다. 기본 컴파일러는 일치하는 원본 ROM을 빌드하는 SGI IDO다. `NON_MATCHING`을 켜면 일치하지 않는 부분에 기능적으로 동등한 C 구현을 쓰고 정의되지 않은 동작도 피한다. 이 빌드는 일치하는 ROM을 만들지 않아 해시 비교가 꺼지므로, 그 기능적 동등성은 해시로 확인되지 않는다. `COMPILER=gcc`로 빌드해도 `NON_MATCHING`이 켜진다. 이 옵션과 별개로 iQue(cn)판의 일치 빌드는 일부 게임과 메뉴 파일, libultra 대부분과 libgcc를 저장소에 든 iQue의 EGCS gcc로 컴파일한다. 저장소에는 빌드에 필요한 자산이 모두 들어 있지 않아 각자 가진 원본 ROM(baserom)에서 추출한다.

N64Recomp는 README 기준 N64 바이너리를 어느 플랫폼용으로든 컴파일할 수 있는 C 코드로 정적 재컴파일하며, 복잡도를 낮추려고 명령어마다 매우 직역적으로 옮긴다. 출력은 필요한 기능을 제공하는 런타임과 함께 쓴다. README는 심볼 같은 메타데이터를 현재 ELF 파일로만 받는다고 적지만, 2026-10-20 main 브랜치 소스는 ELF 대신 심볼 파일과 ROM을 함께 받는 입력도 처리한다. 적용 사례인 Zelda 64: Recompiled(dev 브랜치)는 게임 ROM을 재컴파일하는 `us.rev1.toml`에서 이 방식을 쓰고, 패치용 `patches.toml`은 패치 C 소스로 빌드한 ELF를 입력한다.

해시 일치는 빌드 동등성의 엄격한 기준이지만 코드가 읽기 쉽거나 원래 설계를 설명한다는 뜻은 아니다. decomp.dev 공지는 2026년 초 Opus 4.6과 GPT-5.4가 나오면서부터 모델이 기반이 갖춰지고 정돈되었으며 문서가 빠짐없는 코드베이스 안에서는 괜찮은 결과를 낼 수 있었지만, 명백한 문제와 편법(같은 기계어로 컴파일되지만 원래 개발자가 썼다고 보기 어려운 코드)을 바로잡는 사람의 정리와 수정이 상당히 필요했고 작업당 비용도 결과에 비해 감당하기 어려울 만큼 컸다고 적는다. 같은 공지는 최근 모델이 복잡한 지시를 따르고 충분한 안내가 있을 때 자연스러운 코드를 쓰는 데 크게 나아졌고 이런 결과를 이전 모델보다 빠르고 싸게 낼 수 있다고 보며, 올바른 안내, 사람의 입력과 코드 리뷰가 있으면 AI가 디컴파일을 크게 앞당길 수 있다고도 적는다. 직역형 재컴파일 결과나 AI가 정리한 코드를 원래 구조의 설명으로 쓰려면 함수 단위 대조와 사람의 정리를 따로 거친다(적용 제안).

매칭 디컴파일 진행 상황을 모으던 decomp.dev는 메인 인덱스와 신규 프로젝트 추가를 닫았고, 기존 프로젝트의 진행 추적과 개별 프로젝트 페이지, 이력 데이터 제공은 계속한다(공지에 날짜 없음, 2026-10-20 확인). 운영자는 오픈소스로 공개한 프로젝트를 악용하는 사례로 기존 디컴파일 프로젝트를 fork해 AI로 완성하려는 시도, 기여하지 않은 디컴파일을 가져다 거의 동작하지 않는 포트를 서둘러 공개하는 일, 디컴파일과 PC 포트의 혼동을 들고, 공개 인덱스와 리더보드가 이제 득보다 해가 크다고 판단했다. AI를 활용한 프로젝트를 금지하면 되지 않느냐는 물음에는 AI 자체가 문제는 아니며 올바르게 쓰면 큰 도움이 된다고 보고, 품질 낮은 결과물은 정의하기 어렵고 중재는 더 어려우며 혼자 취미로 운영하는 입장이라 사이트의 수백 개 프로젝트에 좋은 디컴파일의 기준을 정하고 일관되게 집행할 여력도 의향도 없다고 답했다. 진행률을 순위로 보여 주던 공개 인덱스가 기여 없는 결과물을 부추기고 품질 기준의 집행 부담을 키운 사례로 볼 수 있다(해석).

## 게임 상태를 읽고 반복할 수 있게 만든다

게임은 이미지, 애니메이션과 실행 중 상태가 코드 밖에 있어 파일 읽기만으로 검증하기 어렵다. 아래는 게임 하네스 설계 기준이다.

| 요소 | 반복 검증에서 맡는 역할 |
|---|---|
| seed, 고정 시간 단계 | 같은 입력에서 같은 시뮬레이션 경로 재현 |
| 상태 스냅샷과 저장/불러오기 | 버그 직전 상태에서 다시 시작 |
| 명령 기반 상태 변경 | 에이전트가 행동을 구조화해서 실행 |
| 외부 데이터 | 재컴파일 없이 수치와 레벨 조건 비교 |
| 엔진과 분리한 시뮬레이션 | 화면 없이 규칙과 성능을 시험 |
| 스크린샷, 이미지 차이와 텍스트 프로파일 | 시각 회귀와 병목을 구체적 증거로 반환 |

화면 차이만으로 버그를 판정하면 랜덤 효과나 폰트 렌더링을 오류로 셀 수 있다. 상태 불변식, 허용 오차와 의미 있는 사용자 흐름을 함께 확인한다.

**구성 사례 (2026-10-10 공개 글, 2026-10-20 대조):** 게임 프로그래머가 발표 슬라이드를 바탕으로 다시 쓴 설계 권고이며 효과를 측정한 결과는 아니다.

- 비결정적 호출은 게임 시작 시 만든 하나의 seed 난수원에서만 값을 받게 한다. 정확한 상태를 효율적으로 저장하고 불러오는 전략을 개발 초기부터 갖추는 것을 상태 재현의 가장 중요한 요소로 본다.
- 상태 변경은 느슨한 함수 호출 대신 가능하면 직렬화할 수 있는 명령 객체로 남긴다. 텍스트로 쓴 명령열을 실행 중인 게임에 재생할 수 있어 에이전트도 같은 형식으로 조작을 작성한다.
- 시뮬레이션은 엔진의 실행 로직 밖 별도 라이브러리(DLL)로 떼고, 게임 데이터는 코드가 아닌 외부 데이터로 둔다.
- 화면 비교는 CLI 이미지 비교 도구가 내는 변경 후 화면과 목표 이미지의 차이 수치를 에이전트 턴마다 비교하는 평가 기준선으로 삼아 그 차이를 줄여 간다. 사례가 권한 odiff는 차이가 픽셀 차이일 때 Node.js API와 server mode에서 다른 픽셀 수와 전체 이미지 대비 백분율(`diffCount`, `diffPercentage`)을 반환하고, CLI도 같은 두 값을 출력한다(2026-10-20 main 브랜치의 README, 타입 정의와 소스 기준). 프로파일러 화면은 에이전트가 읽기 어려워 캡처를 텍스트로 출력하는 도구를 쓴다.
- 스크린샷 잡음은 [[Context-Engineering#Context Rot|Context Rot]]으로 진행 판단을 흐릴 수 있다. 저자는 글 말미에서 출시 중인 작은 프로젝트에는 이 기법을 쓰지 않았고 대상 규모는 더 큰 프로젝트라고 밝혔다. 한 번의 에이전트 반복이 수초에 끝난다는 서술은 측정값이 아니다. 저장과 불러오기의 세부 복잡성은 다루지 않았다.

별도 공개 템플릿에서는 snapshot, dispatch, reset 계약을 확인했다. 이 템플릿은 위 사례의 구현이 아니다.

## 재구현 사례와 생태계 보강의 범위

- **브라우저 게임 이식:** 2026-10-12 발췌는 Halo, The Simpsons: Hit and Run과 GTA 이식, 일부 온라인 플레이와 240fps 목표를 소개한다. Opus 5.5의 디컴파일 기여와 단기간 작업량도 발췌의 주장이다. 프로젝트, 원본 자산, 비교 장비와 실제 프레임 분포는 미확인이다. 목표 fps를 실측 평균으로 옮기지 않는다.
- **Ruby 생태계 보강:** 2026-10-12 공개 경험 글은 AI로 PDF, GUI, Parquet와 gRPC 등 기존 빈틈을 메울 수 있다고 제안한다. 재작성만이 AI 활용법은 아니다. 좋은 API, 경계 조건, 패키지 유지와 실제 사용자의 피드백은 생성 이후에도 남는다. 개별 라이브러리의 완성도와 유지 상태는 따로 확인한다.

## Xbox Labs: 탐색 조직의 발표와 제품 지원은 다르다

2026-10-13 Xbox Wire의 공식 발표를 2026-10-16 확인했다. Xbox Labs는 게임 제작자, 엔지니어와 과학자가 새로운 기술을 플레이어와 개발자가 경험할 수 있는 형태로 탐색하는 소규모 조직이다. 공개적으로 개발하고 사용자의 행동에서 배우며 플레이와 창작 참여가 늘어나는지를 보겠다는 방향을 제시했다.

발표는 Windows PC 게임을 Apple Silicon에서 실행하도록 변환하거나 WebAssembly와 WebGPU로 브라우저에 이식하고, 다른 게임의 소스에 결합하는 실험을 배경으로 든다. 소프트웨어를 작성, 실행하고 시험할 수 있다는 속성을 게임과 에이전트 활용의 접점으로 설명한다. 이 사례 언급은 Xbox가 모든 대상 게임의 포팅 도구, 호환성이나 성능을 제공한다는 약속이 아니다.

도구를 업계 개발자와 공유하겠다는 방향은 확인되지만 구체적인 공개 목록과 일정은 이 발표에 없다. IP와 커뮤니티를 책임 있게 다룬다는 입장도 함께 명시한다. 조직 출범을 타사 코드와 자산의 자유로운 복제, 모드의 일괄 승인이나 재배포 허가로 해석하지 않는다.

발표의 WebGPU 브라우저 지원율 약 90%와 연간 Xbox 게임 이용 720억 시간 이상은 회사가 제시한 수치다. 집계 방법과 개별 게임의 대상 환경은 검증하지 않았다. 실제 이식에서는 [[WebGPU-Cross-Runtime|환경별 GPU 초기화와 지원 범위]]뿐 아니라 저장, 입력, 음향과 네트워크의 동작도 원본과 비교해야 한다.

## 국내 저작권법의 프로그램코드역분석 요건

2026-08-11 시행 저작권법(법률 제21336호) 기준이다. 2026-10-29부터는 법률 제21595호 판이 시행되지만, 이 절에서 인용한 제2조 제28호 가목과 제34호, 제101조의4, 제104조의2 제1항 본문과 제6호의 문구는 그 판의 두 시행일(2026-10-29, 2027-01-01)에서 모두 바뀌지 않는다(2026-10-20 확인).

법이 말하는 프로그램코드역분석은 독립적으로 창작된 컴퓨터프로그램저작물과 다른 컴퓨터프로그램과의 호환에 필요한 정보를 얻으려고 컴퓨터프로그램저작물코드를 복제하거나 변환하는 것이다(제2조 제34호). 정당한 권한으로 프로그램을 이용하는 자나 그의 허락을 받은 자는 호환에 필요한 정보를 쉽게 얻을 수 없고 그 획득이 불가피할 때, 해당 프로그램의 호환에 필요한 부분에 한정해 프로그램의 저작재산권자의 허락 없이 프로그램코드역분석을 할 수 있다(제101조의4 제1항). 이렇게 얻은 정보는 호환 목적 외의 다른 목적에 쓰거나 제3자에게 제공하는 경우, 대상 프로그램과 표현이 실질적으로 유사한 프로그램을 개발, 제작, 판매하거나 그 밖에 프로그램의 저작권을 침해하는 행위에 쓰는 경우에는 이용할 수 없다(같은 조 제2항). 제2조 제28호 가목의 기술적 보호조치는 저작권, 그 밖에 이 법에 따라 보호되는 권리의 행사와 관련해 이 법에 따라 보호되는 저작물등에 대한 접근을 효과적으로 방지하거나 억제하려고 그 권리자나 권리자의 동의를 받은 자가 적용하는 기술적 조치다. 제104조의2 제1항은 누구든지 정당한 권한 없이 고의 또는 과실로 이 기술적 보호조치를 제거, 변경하거나 우회하는 등의 방법으로 무력화하지 못하게 하고, 같은 항 제6호는 정당한 권한으로 프로그램을 사용하는 자가 다른 프로그램과의 호환에 필요한 범위에서 하는 프로그램코드역분석을 예외로 둔다.

다음은 이 조문을 재구현 작업에 적용할 때의 제안이다. 분석한 프로그램 자체를 다른 플랫폼으로 옮기거나 같은 기능을 다시 구현하는 작업이 이 조항의 호환에 해당한다고 전제하지 않는다. 역분석 과정에서 접근 통제 보호조치를 제거, 변경하거나 우회했다면 두 조항의 범위를 따로 확인한다. 클린룸 재작성이나 공개 명세 사용을 표방했다는 사실만으로 적법성을 판단하지 않고 개별 사안은 법률 검토를 받는다.

## 재구현 검토 질문

- 분석 대상의 사용 권한과 재배포할 소스 및 자산의 범위를 구분했는가.
- 관찰한 동작과 추정한 내부 구조를 구분했는가.
- 정상 경로 외 오류, 저장 호환성, 부하와 입력 경계를 비교했는가.
- 재현용 상태와 입력, 코드 revision과 측정 환경을 남겼는가.
- 국내 저작권법이 적용되는 역분석이라면 그 작업이 호환을 위한 프로그램코드역분석의 요건에 해당하는지와 얻은 정보의 이용 제한을 앞의 저작권법 절로 확인했는가.
