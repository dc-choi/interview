# 에이전트로 하는 대규모 언어 이전 — Bun의 Zig에서 Rust로의 포팅

코딩 에이전트는 코드를 옮겨 쓰는 비용을 크게 낮춘다. 공개된 두 사례에서 Bun은 수십만 줄의 이전을 main 병합까지 11일(자기 보고)에 마쳤고, 시작일과 v1.4 출시일로 계산하면 출시까지는 약 15.5주였다. GitHub Copilot 런타임은 약 14.5주(자기 보고)에 걸쳐 옮겼다. 남는 비용은 동작을 고정하는 검증 기준, 작업 분할과 리뷰 구조다. 이 문서는 한 번에 바꾼 사례(Bun)를 중심으로 이 구조를 정리한다. 컴포넌트 단위로 점진 교체한 사례(GitHub Copilot 런타임)는 [[AI-Infrastructure-Language-Layers#AI 에이전트와 기존 E2E 테스트로 낮아진 재작성 비용|AI 서비스 스택의 언어 계층]]에 있다.

## 언어를 바꾸는 이유를 결함 유형으로 적는다

Bun은 JavaScript 런타임이다. v1.3.14까지 Zig로 작성됐고 코드의 약 20%는 C++다. 2026-07-08 공식 글에서 밝힌 이전 이유는 성능보다 안정성이다.

- **반복된 결함:** v1.3.14에서 고친 버그로 `node:zlib`, `node:http2`, `UDPSocket`, `Buffer#copy`, CSS 파서 등의 use-after-free, double-free, 범위 밖 접근과 메모리 누수를 든다. 이런 결함의 재발을 체계적으로 막는 것이 목표였다.
- **원인 구조:** JavaScript의 GC가 관리하는 메모리와 Bun이 직접 관리하는 메모리가 섞이는 지점에서 문제가 많았다. Zig에는 생성자와 소멸자가 없어서 해제 코드를 호출 지점마다 `defer`로 직접 쓴다.
- **검토했다가 버린 대안:** 엄격한 스타일 가이드는 강제가 어렵고, 자체 스마트 포인터는 Rust보다 쓰기 불편하면서 보장은 없다고 평가했다. C++도 결국 코드 리뷰로 강제하는 스타일 가이드에 기대야 한다.
- **Rust를 고른 근거:** 안전한 Rust에서는 use-after-free, double-free와 해제 누락이 컴파일 오류가 되거나 `Drop`으로 자동 정리된다. 글은 이를 컴파일 오류가 스타일 가이드보다 나은 피드백 고리라고 표현한다.
- 글은 Zig를 탓하지 않는다. 다른 Zig 사용자에게는 같은 버그가 없었고 Zig 덕분에 Bun이 가능했다고 적는다.

안전한 Rust가 막는 범위와 unsafe 경계의 계약은 [[Rust-Soundness-and-Lifetime-Boundaries|Rust 건전성과 수명 계약]]을 따른다.

## 이전 방식: 옮겨 적듯 한 번에

- **충실한 포팅부터:** 목표는 Zig 코드를 Rust로 트랜스파일한 것처럼 보이는 결과였다. 동작 변화를 최소로 두고, unsafe를 줄이며 관용적인 Rust로 다듬는 일은 v1.4 출시 뒤로 미뤘다.
- **언어 중립 오라클:** 테스트 스위트가 TypeScript로 작성돼 Zig에도 Rust에도 의존하지 않는다. 같은 테스트를 그대로 새 구현에 돌릴 수 있었다.
- **준비 문서:** 사람과 모델이 약 3시간 동안 Zig 패턴과 Rust 대응을 논의해 `PORTING.md`로 남겼다. 별도 워크플로가 모든 구조체 필드의 수명을 정리해 `LIFETIMES.tsv`에 저장했고, 두 파일을 함께 적대적 리뷰에 통과시켰다.
- **시험 적용:** 파일 3개로 먼저 돌린 뒤 `.zig` 파일 1,448개 전체로 넓혔다.

## 작업 구조: 구현과 리뷰를 다른 에이전트에 둔다

- **역할 분리:** 파일마다 구현 1명, 서로 다른 컨텍스트 창의 적대적 리뷰어 최소 2명, 수정 1명을 둔다. 원칙은 구현자는 리뷰하지 않고 리뷰어는 구현하지 않는다는 것이다. 같은 원칙의 일반형은 [[Independent-Agent-Code-Review|독립 에이전트 코드 리뷰]]에 있다.
- **단계:** 포팅 가이드 작성, 파일별 포팅, crate별 컴파일 오류 수정(약 100개 crate로 나눈 뒤 오류 약 16,000개), 하위 명령 동작, 로컬 테스트(`systemd-run`의 cgroup으로 격리), CI 테스트 순서다.
- **병렬도:** worktree 4개에 각각 Claude 16개, 동시에 약 64개를 돌렸다. Claude Code 안에서 동적 워크플로 약 50개를 11일 동안 연속 실행했고, 최고 속도는 분당 약 1,300줄이었다. worktree 분리 일반은 [[Agent-Terminal-Workspaces|에이전트 터미널과 작업 공간]]을 따른다.
- **도중에 더한 규칙:** 에이전트끼리 `git stash`와 `git reset`으로 서로의 작업을 되돌려서 git과 cargo 명령을 제한했다. 컴파일을 통과시키려고 함수를 빈 구현으로 바꾸는 일이 생기자, 리뷰어가 우회를 정당화하는 긴 주석을 거부하게 했다.
- **사람의 역할:** 워크플로를 감시하고 출력을 읽으며, 코드를 손으로 고치는 대신 코드를 만드는 절차를 고쳤다. Zig와 Rust 코드를 나란히 읽는 검토도 했다.

## 규모, 검증과 비용 (2026-07-08 글 기준)

| 항목 | 값 |
|---|---|
| 기간 | 11일(5월 3일 시작, 5월 14일 main 병합) |
| 원본 | 주석 제외 Zig 535,496줄 |
| 결과 | Rust 약 78만 줄, 100만 줄 넘게 추가한 PR 하나 |
| 테스트 | 병합 전 모든 플랫폼 CI에서 테스트 스위트 100% 통과, 건너뛰거나 지운 테스트 0개 |
| 토큰 | 캐시 안 된 입력 59억, 출력 6.9억, 캐시 입력 읽기 720억 |
| 비용 | API 단가 기준 약 16만 5천 달러(병합 전 작업) |

- 첫 CI 실행 뒤 이틀 만에 실패한 테스트 파일이 972개에서 23개로 줄었다. 그 뒤 하루 반 만에 Linux가 모두 통과했다. 테스트가 실제로 실행되는지는 사람이 따로 확인했다.
- 플랫폼별 실행 규모는 Debian 13 x64 테스트 60,624개(파일 4,174개), macOS 14 arm64 58,850개, Windows 2019 x64 57,337개다.
- 손으로 했다면 코드베이스를 잘 아는 엔지니어 3명이 약 1년 걸렸으리라는 것은 저자의 추정이다.
- 비용은 이 저장소와 테스트 스위트에 대한 자기 보고다. 다른 이전 작업의 예산 기준으로 옮기지 않는다.

## 같아 보이지만 다르게 동작하는 코드가 회귀를 만든다

글은 이 이전으로 알려진 회귀가 19건 생겼고 모두 고쳤다고 밝힌다. 대부분 두 언어에서 같아 보이는 코드가 다르게 동작한 경우다.

- `debug_assert!` 안의 부수 효과가 릴리스 빌드에서 사라졌다.
- 홀수 바이트 슬라이스를 다루는 코드가 panic을 냈다.
- 포팅이 남긴 임시 상수(블록 크기 2048 대신 64) 때문에 Zig에서 옮겨 온 off-by-one 접근이 실제로 실행됐다. macOS와 Linux의 Zig 빌드는 범위 검사를 빼는 `ReleaseFast`였으므로 같은 상황에서 배열 끝을 넘어 썼겠지만, Rust는 범위 검사로 panic을 냈다. 글은 Windows에서만 쓰던 `ReleaseSafe`였다면 Zig도 panic을 냈으리라고 적는다.
- Rust 함수에는 Zig의 comptime 매개변수가 없어, 색상 마커를 치환하는 출력 함수가 완성된 문자열만 받게 됐다. 그 결과 인자로 넣은 값 안의 마커까지 치환됐고, 매크로로 바꿔 고쳤다.

그래서 충실한 포팅에서는 문법 대응보다 빌드 모드, 단언문과 경계 검사의 의미 차이를 포팅 가이드에 먼저 적어 두는 편이 낫다(적용 판단).

## 병합과 출시를 나눈다

- main 병합은 버전 출시가 아니었다. 병합 시점에 저자는 아직 출시할 만큼 확신하지 못했다고 적는다.
- 출시 전 보강으로 Claude Code Security의 보안 리뷰 11회, 모든 파서의 상시 coverage-guided fuzzing(누적 1,000억 회 실행, 관련 PR 약 15개), CI에서 Miri가 검사하는 코드 범위 확대, 모든 네이티브 메모리 할당을 추적하도록 한 LeakSanitizer 연동 개선을 들었다.
- unsafe 블록은 Rust 코드의 약 4%(약 78만 줄 중 약 2만 7천 줄, `unsafe` 키워드 약 13,000개)이고 블록의 78%가 한 줄이다. JavaScriptCore 같은 C, C++ 라이브러리를 계속 쓰므로 일부 unsafe는 남는다.
- **버전:** v1.3.14가 Zig로 작성한 마지막 버전이고, 글 시점에 v1.4.0을 Rust로 작성한 첫 버전으로 예고하며 canary(`bun upgrade --canary`)로 제공했다. Claude Code v2.1.181(6월 17일 출시) 이후 버전은 Rust 포팅판을 쓰며, Linux 시작 시간 p50이 517ms에서 464ms로 약 10% 줄었다.
- 7월 글은 canary 기준 개선으로 v1.3.14에서 재현되는 버그 128개 수정, 2~5% 속도 향상, Linux와 Windows 바이너리 약 20% 축소를 든다. 속도는 Linux x64 EC2(Xeon Platinum 8488C)에서 HTTP 처리량은 hello-world 서버에 oha로, 빌드 작업은 hyperfine으로 v1.3.14와 v1.4.0을 비교한 자기 보고이며 이 문서에서 재현하지 않았다.
- v1.4는 2026-08-20 Rust로 작성한 첫 릴리스로 나왔다. 릴리스 글은 바이너리 크기를 Linux와 Windows에서 최대 17% 축소로 적는다. Linux x64는 88.5MB에서 77.0MB(약 13%)이고 최대치는 Windows arm64(90.2MB에서 75.1MB)다. canary 시점 수치와 다르므로, 크기는 사용하는 릴리스 기준으로 인용한다.

## 점진 교체와 일괄 교체 비교

| 기준 | Bun (일괄) | Copilot 런타임 (점진) |
|---|---|---|
| 교체 단위 | 코드베이스 전체를 PR 하나로 | 컴포넌트를 PR 128개로 |
| 동작 기준 | 언어 중립 TypeScript 테스트 스위트 | CLI와 SDK의 기존 E2E 테스트 |
| main 상태 | 병합 뒤 출시 전 보강 | 늘 배포 가능 상태 유지 |
| 회귀 추적 | 알려진 회귀 19건을 개별 수정 | 릴리스마다 옮긴 범위가 작아 원인 후보를 좁힘 |

일괄 교체는 두 구현을 오래 공존시키는 shim 비용이 없지만, 회귀가 나면 원인 범위가 넓다. 언어 중립 테스트 스위트가 넓고 실제로 실행된다는 확인이 있을 때 일괄 교체의 위험이 줄어든다(적용 판단). 점진 이주 일반은 [[Legacy-Modernization-Strategies#1. Strangler Fig Pattern|Strangler Fig]]를 따른다.

## 판단 질문

- 바꾸려는 이유를 반복된 결함 유형이나 측정한 병목으로 적을 수 있는가?
- 새 구현에 그대로 돌릴 수 있는 언어 중립 테스트가 있고, 그 테스트가 실제로 실행되는지 확인했는가?
- 구현, 리뷰와 수정을 다른 컨텍스트에 두고, 에이전트가 서로의 작업 공간을 건드리지 못하게 막았는가?
- 빈 구현이나 테스트 건너뛰기 같은 통과용 우회를 리뷰에서 거부하는 규칙이 있는가?
- main 병합과 사용자 출시 사이에 fuzzing, 보안 리뷰와 메모리 검사 같은 보강 단계를 두었는가?
