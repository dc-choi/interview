# 독립 에이전트 리뷰의 발견, 검증과 전달 범위

코드를 작성한 실행과 리뷰 실행을 분리하면 구현자의 가정을 다시 검토할 기회가 생긴다. 별도 세션도 같은 오류를 만들 수 있으므로 세션 분리 자체를 정확성의 증거로 삼지 않는다.

## 세 가지 검사를 나눈다

| 층 | 확인하는 것 | 한계 |
|---|---|---|
| 정적 스캐너 | 정해진 규칙, 의존성 권고와 패턴 | 업무 의미나 실제 도달 가능성의 추가 확인 필요 |
| 발견 에이전트 | 변경과 호출 관계에서 문제 후보 제안 | 잘못된 경로, 인용과 추정 가능 |
| 검증 에이전트 | 후보를 코드와 재현 근거로 확인 또는 반박 | 실행하지 못한 조건과 도구의 누락이 남음 |

검증자에게는 결론 동의가 아니라 대상 코드, 주장과 재현 조건을 준다. 실제 파일에 인용문이 존재하는지 검사하는 것은 근거의 존재 검사다. 그 코드가 주장한 실패를 일으키는지는 별도 의미 검증이다.

## 변경 범위와 검토 전달 범위를 비교한다

미푸시 커밋과 미커밋 변경, 특정 브랜치와 PR, 저장소 전체는 서로 다른 범위다. 리뷰 직전의 기준 ref와 diff를 고정하고 변경한 줄이 실제 리뷰 입력에 들어갔는지 확인한다. 스캐너가 건너뛴 경로와 지원하지 않는 언어도 남긴다.

## 구현 사례: OpenQodex

2026-11-02 공식 저장소 README는 기본 변경 범위를 미푸시 커밋과 미커밋 변경 전체로 설명한다. 22개 내장 스캐너와 별도의 Claude Code 또는 Codex 프로세스를 사용하고, finder와 verifier 세션을 나눈다. 스크립트는 인용문의 실재, 스캐너 발견의 응답 누락과 변경 줄의 리뷰 전달을 검사한다.

리뷰어는 사용자의 기존 로그인을 사용한다. 별도 API 키가 없다는 설명이 네트워크 전송이나 사용량 소모가 없다는 뜻은 아니다. README는 모델 서비스에 변경 코드가 전달된다고 밝힌다. 전체 리뷰에는 로그인된 Claude Code 또는 Codex가 필요하고 일부 스캐너는 별도 언어 런타임이 필요하다.

설치가 훅과 파일을 만들 수 있으므로 스킬 문서만 읽는 것과 설치를 구분한다. 이번에는 설치, 리뷰 실행과 성능 비교를 하지 않았다. 스캐너 수와 존재 검사를 결함 탐지율이나 무결함 보장으로 바꾸지 않는다.

## 확인 질문

- 인용문이 코드에 있다는 검사만으로 결함이 입증되는가?
- 리뷰 후 코드가 바뀌면 어떤 기준으로 다시 검토할 것인가?
- 스캐너 성공, 테스트 성공과 업무 요구사항 만족을 구분하는가?
