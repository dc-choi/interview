# 독립 에이전트 리뷰의 발견, 검증과 전달 범위

코드를 작성한 실행과 리뷰 실행을 분리하면 구현자의 가정을 다시 검토할 기회가 생긴다. 별도 세션도 같은 오류를 만들 수 있으므로 세션 분리 자체를 정확성의 증거로 삼지 않는다.

## 세 가지 검사를 나눈다

| 층 | 확인하는 것 | 한계 |
|---|---|---|
| 정적 스캐너 | 정해진 규칙, 의존성 권고와 패턴 | 업무 의미나 실제 도달 가능성의 추가 확인 필요 |
| 발견 에이전트 | 변경과 호출 관계에서 문제 후보 제안 | 잘못된 경로, 인용과 추정 가능 |
| 검증 에이전트 | 후보를 코드와 재현 근거로 확인 또는 반박 | 실행하지 못한 조건과 도구의 누락이 남음 |

검증자에게는 결론 동의가 아니라 대상 코드, 주장과 재현 조건을 준다. 실제 파일에 인용문이 존재하는지 검사하는 것은 근거의 존재 검사다. 그 코드가 주장한 실패를 일으키는지는 별도 의미 검증이다.

## 변경 범위와 검토 전달 범위를 비교한다

미푸시 커밋과 미커밋 변경, 특정 브랜치와 PR, 저장소 전체는 서로 다른 범위다. 리뷰 직전의 기준 ref와 diff를 고정하고 변경한 줄이 실제 리뷰 입력에 들어갔는지 확인한다. 스캐너가 건너뛴 경로와 지원하지 않는 언어도 남긴다.

## 구현 대화와 분리하되 저장소 맥락은 남긴다

독립 리뷰의 입력은 요구사항, 기대 결과, 기준 diff와 관련 소스다. 구현자가 해법을 정당화한 대화 전체를 기본 입력으로 삼지 않는다. 다만 대화를 비운다는 이유로 업무 제약이나 인수 조건까지 빼면 리뷰어가 다른 문제를 풀 수 있다.

다음은 공개 개발팀 발표의 운영 방식을 적용한 점검 절차다. 세션 분리의 성능 우위를 통제 실험으로 입증한 결과는 아니다.

1. diff를 탐색의 출발점으로 삼고 호출부, 같은 패턴의 구현, 테스트와 문서까지 확인한다. 변경 파일만 보면 다른 위치의 동일 결함이나 문서 갱신 누락을 놓칠 수 있다.
2. 지적에는 위치, 실패 조건과 수정 이유를 남긴다. 코드 교체안만 제시하면 실제 문제와 취향을 구분하기 어렵다.
3. 작성자는 지적을 자동 수용하지 않고 소스와 실행 결과로 반박할 수 있다. 리뷰어도 반증된 지적을 철회한다.
4. 종료 기준은 지적 수가 아니라 요구사항 충족과 남은 위험이다. 합의나 수정 비율만으로 무결함을 선언하지 않는다.

작성 단계의 자체 검증에는 실제 실행 경로도 포함한다. 예를 들어 버튼 처리 함수의 테스트가 통과해도 화면의 다른 요소가 버튼을 가리면 사용자는 클릭할 수 없다. 테스트 결과와 실행 관찰을 함께 남겨 검토자가 확인할 수 있게 한다.

## 리뷰 깊이는 토큰 예산과 제품 의도로 정한다

리뷰 에이전트를 더 겹치고 더 꼼꼼히 돌리면 결함을 더 찾지만, 그 비용은 변경마다 다시 든다. 아래는 2026-11-14 공개 대담에서 오간 실무자들의 경험과 판단이며(발표 기준), 효과를 잰 결과는 아니다.

- **평가 묶음이 리뷰 비용을 붙잡는다:** 한 진행자는 변경을 줄마다 훑는 자기 리뷰 skill이 한 번에 수천만 토큰을 쓴다고 했다. 약 5,000만 토큰을 1,000만으로 줄이려 했지만, 놓치면 안 되는 버그 유형 약 30개를 모은 held-out 평가 때문에 3,000만까지만 내려갔다고 털어놓았다(자기 보고). 리뷰가 잡을 범위를 평가가 정하면, 그 평가에 실제로 고칠 가치가 있는 결함만 들어 있는지가 비용을 정한다(이 문서의 정리).
- **제품 의도를 모르는 리뷰는 과적합한다:** 다른 모델 계열의 에이전트들이 diff를 깨뜨리려 하는 적대적 리뷰(pstack의 `interrogate`)는 여전히 쓸모가 있지만, 리뷰어가 제품의 목표와 로드맵을 모르면 좋은 지적과 아닌 지적을 가르지 못한다. 두 달 뒤 폐기할 코드를 이상적인 형태로 다듬자는 지적이나 거의 일어나지 않는 일반 정확성 버그를 고치자는 지적이 섞인다. pstack 작성자는 이 때문에 리뷰 skill의 비중을 줄였다고 했고, 진행자는 제품 요구사항 문서를 리뷰 입력에 넣어 무엇이 고칠 버그인지 정하게 하는 방안을 내놨다(시험 결과 없음). 위의 입력 분리에서 구현 대화는 빼되 업무 제약과 인수 조건은 남기라는 것과 같은 원리다.
- **투자는 거꾸로 된 피라미드로 둔다:** pstack 작성자는 투자의 대부분을 코드베이스(아키텍처, API 설계)와 정적 분석(린트 규칙, 컴파일러, CI)에 두고, 그 위에 규칙, skill과 AGENTS.md를 얹으며, 사람 리뷰는 가끔 하되 인프라, 데이터베이스와 배포처럼 민감한 영역에서는 사람이 루프에 남는다고 설명했다. 코드베이스를 기억의 한 형태로 보면 강제 장치로 옮긴 규칙은 이후 변경마다 리뷰 토큰을 쓰지 않는다. 리뷰 비용은 변경 수에 비례하고 강제 장치의 비용은 주로 만들 때 든다(이 문서의 정리). Electron의 main 프로세스 코드와 renderer 코드 사이의 import를 린트 규칙과 의존성 그래프 검사로 막아 renderer가 끊기는 회귀를 리뷰 전에 없앤 사례와 강제 층의 순서는 [[AI-Native-System#가장 짧은 경로를 올바른 경로로 만든다|가장 짧은 경로를 올바른 경로로]]와 [[Pstack#반복 실수를 강제 층으로 내린다|pstack의 correct]]에 있다.

같은 작성자는 이런 투자 뒤에 에이전트가 자기 PR을 병합하게 하고 사람은 산출물만 본다고 했으며, 월 4,000건이 넘는 PR을 올린다고 밝혔다(자기 보고, 병합 수와 변경 크기는 밝히지 않음). 사람 리뷰를 빼는 경로의 위험 등급과 승인 조건은 [[Code-Review-AI-Agent-Operations#위험에 따른 검증|에이전트 시대 코드 리뷰 운영]]을 본다.

## 동작을 보존하는 이관의 리뷰

언어나 런타임을 옮기는 변경은 새 코드가 그럴듯한지보다 기존 동작을 그대로 옮겼는지가 리뷰 대상이다. GitHub의 Copilot 런타임 Rust 이관(2026-09-16 게시, 2026-09-23 갱신된 공식 글 기준)은 다른 개발자가 같은 저장소를 계속 바꾸는 중에 이 확인을 반복한 사례다.

- **기준선 따라잡기:** 재사용 지침(`rust-rebase-review`)으로 변경을 최신 main 위에 rebase하고 충돌을 푼 뒤, 그사이 들어온 TypeScript 변경이 Rust 쪽에도 옮겨졌는지 확인하게 했다. 컴포넌트를 옮기는 PR에서 기존 TypeScript를 함께 지웠으므로, 다른 사람이 지워진 파일을 고치면 rebase가 충돌로 알려 준다. 옛 구현을 남겨 두면 이 신호가 사라진다(적용 판단).
- **대조 리뷰:** 서로 다른 모델의 리뷰 에이전트가 옛 TypeScript와 새 Rust를 줄 단위로 비교해 동작과 호환성 변화를 찾고, 낡은 코드와 임시 연결 코드가 지워졌는지, 기존 E2E 테스트가 지워지거나 바뀌지 않았는지 확인했다. 지적이 없어질 때까지 고치고 다시 리뷰했다.
- **사람의 몫:** 사람은 아키텍처, API 계약과 위험 요소에 집중했고 merge 결정은 작성자가 했다. 필수 테스트를 통과하지 못한 PR은 들어가지 않았다.

그래도 정수가 소수로 바뀌는 직렬화 차이, 빈 문자열과 시간대 처리, 취소 전파 누락 같은 회귀가 나왔고, 원문은 E2E 테스트 부족과 잘못된 동작을 확인하던 테스트도 원인으로 든다. 기존 E2E 테스트를 정답 판정 기준(oracle)으로 쓰려면 에이전트가 감독이나 명시적 승인 없이 테스트를 약하게 고치거나 스냅숏을 갱신해 정답을 바꾸지 못하게 해야 한다. 세부는 [[Agent-Test-Verification-Behavior#포팅에서는 기존 E2E 테스트를 오라클로 지킨다|포팅의 테스트 오라클]]을 본다. 옮기는 단계에서 재설계를 섞지 않은 이유로 원문은 언어와 동작을 함께 바꾸면 무엇이 실패를 일으켰는지 알기 어렵다는 점을 든다. 이 사례는 한 팀의 기록이며 다중 모델 리뷰가 회귀를 모두 잡는다는 근거가 아니다.

## 구현 사례: OpenQodex

2026-11-02 공식 저장소 README는 기본 변경 범위를 미푸시 커밋과 미커밋 변경 전체로 설명한다. 22개 내장 스캐너와 별도의 Claude Code 또는 Codex 프로세스를 사용하고, finder와 verifier 세션을 나눈다. 스크립트는 인용문의 실재, 스캐너 발견의 응답 누락과 변경 줄의 리뷰 전달을 검사한다.

리뷰어는 사용자의 기존 로그인을 사용한다. 별도 API 키가 없다는 설명이 네트워크 전송이나 사용량 소모가 없다는 뜻은 아니다. README는 모델 서비스에 변경 코드가 전달된다고 밝힌다. 전체 리뷰에는 로그인된 Claude Code 또는 Codex가 필요하고 일부 스캐너는 별도 언어 런타임이 필요하다.

설치가 훅과 파일을 만들 수 있으므로 스킬 문서만 읽는 것과 설치를 구분한다. 이번에는 설치, 리뷰 실행과 성능 비교를 하지 않았다. 스캐너 수와 존재 검사를 결함 탐지율이나 무결함 보장으로 바꾸지 않는다.

## 구현 사례: 앱 안의 PR 리뷰 탭에서 별도 스레드로 리뷰를 시작한다

2026-11-17 공개 발표에서 소개된 Codex 앱의 코드 리뷰 탭이다. 2026-11-21 공식 Code Review 문서로 대조했고, 이 절만 대조했으므로 문서의 `verified_at`은 그대로 둔다. GitHub를 연결하면 내가 만들었거나 배정받은 PR을 모아 보여 주고, 앱을 떠나지 않고 diff와 GitHub 링크를 볼 수 있다. 문서 기준으로는 데스크톱 앱에 들어 있는 Code Review 플러그인이고 사이드바에 고정할 수 있으며, 수신함을 나에게 배정됨, 내 팀에 배정됨, 내가 작성함으로 거르고 Changes에서 diff와 댓글을 본다. GitHub 리뷰는 정식 제공이고 GitLab 병합 요청은 프리뷰다. 발표는 다른 사람이 에이전트로 쓴 코드가 검토 요청으로 넘어오는 상황을 배경으로 들었다. 리뷰 버튼을 누르면 별도 스레드에서 서브에이전트가 미리 만든 프롬프트로 PR을 검토하고 결과를 그 대화로 돌려준다고 했는데, 문서는 Review with Codex가 새 대화에서 리뷰를 시작한다고만 적고 서브에이전트와 미리 만든 프롬프트는 언급하지 않는다. 보게 할 부분은 Review instructions(설정의 Code Review에서도 수정)에 기준과 보고 형식을 적어 정하며, 이 지침은 리뷰 전반에 적용된다. 시연은 리뷰 결과를 보여 주지 않았으므로 지적의 정확도와 검증 방식은 확인하지 못했다.

적용 점검(이 문서의 해석): 구현 대화와 다른 스레드에서 리뷰가 도는 구조는 위의 입력 분리와 맞는다. 다만 같은 모델과 같은 저장소 지침을 쓰면 같은 가정을 되풀이할 수 있으므로 다른 모델이나 별도 지침을 줄 수 있는지 본다. 사용자 지침에는 위치, 실패 조건과 수정 이유를 남기게 한다. 시연의 PR은 작성자가 모바일 화면을 포함한 스크린샷으로 동작을 확인한 증거를 붙였는데, 검토자는 그 증거가 주장한 동작을 실제로 보여 주는지 대조하고 스크린샷이 있다는 사실만으로 통과시키지 않는다.

## 확인 질문

- 인용문이 코드에 있다는 검사만으로 결함이 입증되는가?
- 리뷰 후 코드가 바뀌면 어떤 기준으로 다시 검토할 것인가?
- 스캐너 성공, 테스트 성공과 업무 요구사항 만족을 구분하는가?
- 리뷰가 잡을 결함의 범위를 무엇이 정하는가(제품 의도, 평가 묶음), 같은 지적이 반복되면 코드베이스의 강제로 옮겼는가?
