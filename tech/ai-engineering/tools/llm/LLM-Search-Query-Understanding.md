# LLM으로 검색 쿼리 이해하기

커머스 검색에서 사용자는 카탈로그의 표기와 다른 말로 찾는다. `bread no gluten`, `x large zip lock`처럼 어순이 뒤집히거나 단위와 속성이 섞인 입력이 많다. 쿼리 이해(Query Understanding, QU)는 입력 문자열에서 쇼핑 의도를 뽑아 뒤 단계에 넘기는 처리다.

## 검색 세 단계와 QU의 산출물

상품 검색은 QU, 후보 검색(retrieval), 순위 매기기(ranking)로 나눌 수 있다. QU의 결과가 뒤의 두 단계를 모두 안내한다.

| 산출물 | 내용 | 쓰이는 곳 |
|---|---|---|
| 카테고리 | 카탈로그의 어느 구역이 답에 해당하는지 | 후보 범위 제한, 순위 신호 |
| 대체 쿼리(rewrite) | 원래 쿼리로 부족할 때 쓸 다른 검색어 | 결과가 비거나 적을 때 recall 보강 |
| 구조화 태그 | 상품, 브랜드, 속성으로 나눈 쿼리 조각 | 검색, 순위, 필터, 광고 |

규칙 기반 전처리(오타 교정, 동의어, 초성)는 [[OpenSearch-Query-Understanding|OpenSearch 쿼리 이해]]에 있다. 이 문서는 그 위에 LLM을 얹는 설계를 다룬다.

## 기존 방식이 막히는 지점

- **로그는 불완전한 정답이다.** 검색, 클릭, 구매 로그는 쿼리를 제대로 이해했는지 직접 말해 주지 않는다. 빵을 검색하고 바나나를 샀다고 빵이 과일 쿼리인 것은 아니다. 사람 라벨은 깨끗하지만 비싸다.
- **롱테일에는 이력이 없다.** 드물게 나오는 구체적인 쿼리는 하나하나는 작아도 모이면 큰 비중이다. 로그로 학습한 모델은 이 구간에서 약하다.
- **넓은 쿼리는 모호하다.** `healthy food`처럼 여러 카테고리에 걸친 쿼리를 한 해석으로 좁히면 틀린다.
- **과업별 모델이 따로 놀면 비용과 불일치가 쌓인다.** 카테고리 분류기와 세션 기반 rewrite 엔진을 따로 두면 데이터 처리, 학습, 배포가 각각 필요하고 같은 쿼리를 서로 다르게 해석할 수 있다.

LLM은 세상 지식으로 처음 보는 쿼리도 해석한다(같은 허브의 다른 이름, 대체 가능한 품종). 그러나 자사 카탈로그와 고객 행동은 모른다. 그래서 세 가지를 덧댄다.

1. **맥락 주입(RAG)**: 카탈로그 레코드와 과거 전환 이력을 검색해 프롬프트에 넣는다.
2. **출력 검증**: 결과가 카탈로그와 맞는지 후처리 guardrail로 거른다.
3. **미세조정**: 검증한 고품질 예시로 작은 모델을 학습시킨다.

## 과업별 설계 패턴

### 카테고리: 열린 분류 대신 후보 재순위

카탈로그가 `육류 > 소고기 > 갈비 > 찜갈비`처럼 계층이면 평면 라벨 분류기는 같은 계층의 부모와 자식을 따로 점수 매긴다. LLM에게 전체 카테고리 중 하나를 고르게 하는 대신 다음 세 단계로 나눈다.

1. 과거에 그 쿼리 뒤 구매가 많았던 상위 K개 카테고리를 후보로 뽑는다.
2. LLM이 쿼리와 도메인 맥락으로 후보 경로를 재순위한다.
3. 쿼리 임베딩과 예측한 카테고리 경로의 의미 유사도가 임계값보다 낮으면 버린다.

후보를 먼저 좁히면 LLM이 카탈로그에 없는 경로를 지어낼 여지가 줄고, 마지막 유사도 검사가 그럴듯하지만 무관한 결과를 거른다. 생성형 재순위기는 후보 밖의 경로를 낼 수도 있으므로 출력이 후보 집합 안에 있는지도 검사한다(적용 제안). 대신 후보 단계에서 빠진 정답은 복구할 수 없으므로 후보 recall을 따로 측정한다(적용 제안).

### 쿼리 재작성: 목적별로 프롬프트를 나눈다

Instacart 사례에서 하나의 범용 재작성 프롬프트는 `1% milk`를 `one percent milk`로 바꾸는 식으로, 맞는 동의어지만 대체 상품을 찾는 데는 도움이 안 되는 결과를 냈다. 재작성의 목적을 나누면 각 프롬프트의 지시와 예시가 분명해진다.

| 유형 | 의미 | 설명용 예 (`1% milk`) |
|---|---|---|
| 동의어 | 같은 요청의 다른 표현 | `one percent milk` |
| 상위 개념 | 구체성을 덜어낸 쿼리 | `milk` |
| 대체재 | 다른 상품이지만 대안이 되는 것 | `2% milk` |

세 결과 모두 의미 필터와 후처리를 거친다. 대체재는 사용자가 원한 상품이 아니므로 원래 결과가 충분할 때까지 섞을지는 순위 정책으로 따로 정한다(적용 제안).

### 구조화 태그: 오프라인 teacher와 온라인 student

Semantic Role Labeling(SRL)은 쿼리를 상품, 브랜드, 속성 같은 역할로 나눈다. 모든 쿼리를 실시간으로 큰 모델에 보내면 지연과 비용이 맞지 않으므로 트래픽 분포에 따라 경로를 나눈다.

```text
쿼리 ─▶ 캐시 조회 ─ hit ─▶ 검증된 태그 반환
              └ miss ─▶ 미세조정한 작은 모델(student) 실시간 추론

[오프라인] 자주 나오는 head 쿼리
  ─▶ 큰 모델(teacher) + RAG(전환 이력, 임베딩 점수로 고른 유사 브랜드명)
  ─▶ 카탈로그 대조 guardrail ─▶ 캐시 적재 + student 학습 데이터
```

- teacher의 검증된 출력이 캐시와 학습 데이터를 동시에 채운다. 이는 지식 증류의 한 형태다([[Task-Specific-Small-Models|작은 특화 모델]]).
- 맥락 검색이 해석을 바꾼다. 일반 단어처럼 보이는 브랜드명은 세상 지식만으로는 기계류로 읽히지만, 내부 근거가 음료 브랜드를 가리키면 그 카테고리로 태깅된다.
- LoRA는 원래 가중치를 고정하고 적은 수의 추가 파라미터만 학습한다. 서빙 전 adapter를 기본 가중치에 병합하면 추론 경로가 단순해진다.

### 실시간 경로의 지연 예산

캐시가 대부분을 흡수해도 miss 경로가 검색 응답 시간 안에 끝나야 한다. 조정 수단은 다음과 같고, 품질과 지연을 같이 측정해 고른다.

- adapter 병합, 더 빠른 GPU, 양자화를 각각 적용해 지연과 recall을 비교한다. 양자화로 지연이 줄어도 recall이 떨어지면 채택하지 않는 선택도 있다.
- 사용량이 적은 시간대에는 GPU 수를 줄여 비용을 맞춘다.
- 서빙 엔진 선택은 [[LLM-Inference-Serving-Engines|LLM 추론 서빙 엔진]]에서 다룬다.

## 사례: Instacart의 QU 재구축 (2025-11 공개 글 기준)

| 항목 | 공개된 내용 |
|---|---|
| 이전 구성 | FastText 다중 라벨 카테고리 분류기, 세션 로그에서 캐낸 rewrite(검색 트래픽의 50%만 커버) |
| 재작성 | 세 유형 프롬프트로 커버리지 95% 이상, 세 유형 모두 정밀도 90% 이상 |
| student 모델 | Llama-3 8B를 LoRA로 미세조정. 그림의 기준 대비 precision 96.4%(기준 95.4%), recall 95%(기준 96.2%), F1 95.7%(기준 95.8%). 글은 비슷한 F1에 더 높은 precision이라고 요약한다 |
| 지연 | A100에서 약 700ms로 시작. adapter 병합과 H100 전환으로 300ms 목표 도달(글의 정리 부분은 병합으로 30% 단축이라고 쓴다). FP8 양자화는 10% 더 줄였지만 recall이 조금 떨어져 양자화하지 않은 모델을 배포 |
| 실시간 추론 비중 | 캐시 덕분에 쿼리의 2%만 실시간 추론이 필요 |
| A/B 결과 (실시간 SRL, tail 쿼리) | 평균 스크롤 깊이 6% 감소, 지연 증가는 미미 |
| 출시 뒤 보고 | 매주 수백만 건의 cold-start 쿼리 처리, tail 쿼리의 검색 결과 불만 50% 감소 |

teacher 모델의 이름, 카테고리 유사도 임계값, 학습 데이터 크기와 A/B 실험 설계(표본, 기간, 유의성)는 공개되지 않았다. 위 수치는 한 회사의 자체 보고이므로 다른 서비스의 기대 성능이나 인과 효과로 옮기지 않는다.

## 트레이드오프와 점검

- **후보 재순위의 상한**: 이력 기반 후보에 없는 카테고리는 LLM이 고를 수 없다. 신상품과 신규 카테고리의 경로를 따로 둔다.
- **캐시 신선도**: 카탈로그와 브랜드가 바뀌면 캐시된 태그가 낡는다. 캐시 키에 카탈로그 버전을 넣거나 갱신 주기를 정한다(적용 제안).
- **student의 오류 방향**: student는 teacher를 흉내 내므로 teacher의 체계적 오류도 배운다. guardrail로 걸러낸 데이터만 학습에 쓰는 이유다.
- **평가 지표의 분리**: 태그 precision과 recall, rewrite 커버리지와 정밀도, 최종 검색 지표(스크롤 깊이, 불만, 전환)를 따로 본다. QU 지표가 좋아도 순위 단계가 그 신호를 쓰지 않으면 사용자 지표는 움직이지 않는다.
- **head와 tail의 분리 측정**: 전체 평균은 head 쿼리가 지배한다. LLM 도입의 효과는 tail 구간에서 따로 본다.

## 면접 체크포인트

- LLM을 열린 분류기로 쓰지 않고 후보 재순위로 쓰는 이유를 설명할 수 있는가
- 큰 모델을 오프라인 teacher로, 작은 모델을 온라인 student로 나누는 기준(트래픽 분포, 지연 예산)을 말할 수 있는가
- 양자화가 지연을 줄였는데도 채택하지 않을 수 있는 조건을 설명할 수 있는가
