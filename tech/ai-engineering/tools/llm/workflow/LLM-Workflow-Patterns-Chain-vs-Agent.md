# LLM 워크플로우 패턴: 체인과 에이전트, 그리고 절충

업무의 예측 가능성에 따라 체인과 에이전트를 고르고, 두 방식 사이의 절충과 통제 지점을 다룬다. 현장 제어와 대화 지원의 분리, 그래프 워크플로우, Plan-and-Execute, 되돌릴 수 없는 행동 직전 승인, 콘텐츠 승인 대기열과 시각적 워크플로우의 오류 처리를 포함한다. 상위: [[LLM-Workflow-Patterns|LLM 워크플로우 패턴]].

## 체인 워크플로우 vs 에이전트 워크플로우, 그리고 절충

LLM은 모델이고 에이전트는 그 모델과 도구, 실행 상태를 연결한 시스템이다. 단일 모델 호출로 답을 생성하는 구성과, 실행 결과를 받아 다음 행동을 고르는 루프를 구분한다. 채팅 화면을 제공하는 시스템도 내부에서는 에이전트로 동작할 수 있으므로 화면이나 제품 이름만으로 구분하지 않는다. 판단 기준은 다음 행동과 도구 사용을 미리 정한 코드가 통제하는지, 모델이 실행 중 동적으로 고르는지다(2026-10-24 Anthropic의 Building effective agents 대조).

에이전트는 도구 결과 같은 환경의 피드백을 받아 계획을 수정하고, 막히면 사람에게 판단을 요청할 수 있다. 목표를 맡겼다는 사실만으로 완수를 보장하지 않으며, 최대 반복 횟수와 종료 조건도 필요하다. 루프의 정지 조건과 트리거 층 설계는 [[Agent-Loop-Engineering|루프 엔지니어링]]에서 다룬다.

| 구분 | 체인 워크플로우 | 에이전트 워크플로우 |
|------|----------------|---------------------|
| 흐름 | 정해진 순서대로 처리 | 상황에 따라 다음 행동을 동적 결정 |
| 적합 | 목적이 명확하고 흐름이 단순 (문서 요약, 고정 포맷 변환) | 질문 유형이 다양하고 단계별 정확도 점검이 필요 (서포트 채널 답변) |
| 실행 리스크 | 낮음, 예측 가능 | 높음, 비결정성 증가 |
| 통제/감사 | 미리 정한 단계에 기록과 승인 지점을 배치하기 쉬움 | 동적 경로의 도구 결과와 판단을 기록하고, 중간 확인과 사람 개입 지점을 별도로 설계해야 함 |
| 구축과 변경 비용 | 초기 설계가 무겁고 계획이 바뀌면 재설계 비용 발생 | 시작은 가볍지만 같은 절차를 반복할 때마다 탐색 비용 재발생 |

핵심 원칙은 **모든 문제를 에이전트로 풀지 않는 것**이다. 단순하고 결정론적인 작업에 에이전트를 쓰면 토큰과 비결정성만 늘어난다(오버엔지니어링).

판단 축은 **업무의 예측 가능성** — 무엇을 할지 미리 알 수 있는가다. 버그 원인 찾기, 시장 조사, 일회성 분석처럼 탐색적인 업무는 에이전트가 맞고, 월 마감 정산, 규제와 감사 보고, 정기 리포트 생성, 입사자 계정 세팅처럼 절차가 미리 확정되고 감사 추적이 필요한 업무는 절차를 통제하는 체인 쪽이 맞다.

### 체인을 고르기 전에 모델 호출이 필요한지 확인한다

단계가 고정된 LLM 체인과 모델을 쓰지 않는 규칙 기반 처리는 다르다. 체인의 제어 흐름이 일정해도 각 단계의 생성 결과까지 결정론적이라는 뜻은 아니다. 2026-10-26 Anthropic의 workflow 정의와 단순한 해법부터 선택하는 원칙을 대조했다. 기존 문서 전체의 검증일은 유지한다.

다음은 이 구분을 업무에 적용하는 설계 제안이다.

- 계산식, 필드 검증과 허용 상태 전이처럼 규칙이 명시된 부분은 코드로 처리한다.
- 자유 형식 문서의 의미 해석이나 초안 생성이 필요한 부분에 모델을 사용하고, 결과를 규칙 기반 검사와 연결한다.
- 모델 사용 여부만으로 사람 검토를 생략하지 않는다. 입력의 모호성, 실패 영향과 검증 가능한 완료 기준으로 검토 지점을 정한다.

예를 들어 문서에서 금액 후보를 추출하는 일과 확정한 값의 합계를 계산하는 일을 나눌 수 있다. 모델을 제거해도 잘못된 규칙이나 입력은 잘못된 결과를 만들므로, 결정론적 실행과 업무상 정확성을 구분한다.

### 현장 제어와 대화 지원의 지연 예산을 나눈다

하나의 서비스 안에서도 인식, 제어와 상담은 다른 경로다. 번호판 인식과 출입문 개방, 문제가 생긴 이용자의 음성 상담을 모두 같은 LLM 루프로 처리해야 하는 것은 아니다. 아래는 경로를 나누는 설계 제안이다.

- 정상 출입은 확인된 인식 결과와 출입 권한으로 처리하고, 대화가 필요한 예외를 별도 지원 경로로 보낸다.
- 인식부터 제어 장치 응답까지의 시간과 음성 상담의 첫 응답, 문제 해결까지의 시간을 따로 측정한다.
- 대화 지원이 지연되거나 실패했을 때의 사람 호출과 기존 지원 경로를 정한다. 모델의 설명이 실제 장치 동작을 대신하지 않는다.

Get My Parking의 AWS 공개 사례는 컴퓨터 비전과 AI 상담을 함께 다루면서 게이트 지연의 중요성을 설명한다. 게이트의 수백 밀리초 요구를 음성 에이전트가 전체 대화를 그 안에 끝낸다는 실측으로 해석하지 않는다. 위 분리안은 공개 사례를 바탕으로 한 설계 제안이며 해당 회사의 내부 구현을 확인한 결과는 아니다.

### 그래프 워크플로우

에이전트 워크플로우를 그래프로 구성하면, 각 노드가 **프롬프트와 LLM을 가진 작은 처리 단위**처럼 동작한다. 일반 처리 노드 사이에 **검색 결과나 생성 답변을 평가하는 노드**를 끼워, 품질이 미달이면 재검색이나 재생성으로 분기시킨다. 질문 분류 → 유형별 체인 선택(SQL 생성인지, 문서 검색인지, 채널 답변인지) → 동적 프롬프트 조합으로 이어진다. 결정론적 함수와 사람 승인까지 노드로 두고 노드, 엣지, 상태와 조건을 설계하는 관점, 실패 노드로의 복귀와 재시도 한도는 [[Agent-Graph-Engineering|그래프 엔지니어링]]에서 다룬다.

### Plan-and-Execute: 절충 패턴

실제 업무는 확정적 구간과 탐색적 구간이 섞여 있어 순수 자율도 순수 절차도 맞지 않을 때가 많다. Plan-and-Execute는 역할을 셋으로 나눈다.

- **Planner**: 목표를 받아 단계 계획을 통째로 수립
- **Executor**: 계획에서 한 단계씩 꺼내 자율 루프로 실행
- **Replanner**: 실행 결과를 보고 계속할지, 계획을 고칠지, 끝낼지 판정

큰 흐름은 계획의 단계 목록으로 통제하고 각 단계 안은 Executor의 자율 루프에 맡긴다. 구조는 절차를 미리 확정해 집행하는 쪽을 닮았지만 **계획의 저자가 모델**이다 — 모델이 실행 시점에 만든 계획을 코드가 데이터로 들고 관리한다. 계획이 모델 머릿속이 아니라 밖의 데이터로 존재하므로 실행 전에 사람이 목록을 통째로 검토, 승인할 수 있고 진행 중에도 목록과 진행률을 들여다볼 수 있으며 독립 단계는 병렬 실행할 수 있고, 큰 판단을 한 번만 하므로 매 단계에 비싼 모델을 부를 필요도 없다(단계별 모델 배분은 [[LLM-Model-Tiers|모델 티어 라우팅]]). 단계를 잘게 쪼갤수록 계획이 어긋날 확률이 올라가므로, 완화책은 계획을 3~5개 수준의 큰 덩어리로만 굵게 잡는 것이다. 재계획이 잦으면 계획 비용 분산과 병렬 실행 이득이 사라지고, 극단에서는 자율 루프에 Planner 호출 비용과 상태 관리 부담만 얹은 꼴이 되어 차라리 순수 자율이 낫다 — 다만 계획이 데이터로 나와 있어 검토와 승인이 가능하다는 통제 이득은 그때도 남는다.

### 되돌릴 수 없는 행동 직전 승인: 또 하나의 절충

에이전트를 자율로 돌리되 메일 발송, 결제, 삭제처럼 **되돌릴 수 없는 행동 직전에만 사람 승인을 두는** 방식도 있다 — 모든 단계를 통제하는 대신 위험이 몰린 지점에 통제를 집중하는 [[Harness-Engineering|HITL]] 배치다. 발신만 사람 게이트로 남기는 [[Agent-Email-Interface|에이전트 이메일 인터페이스]]가 전형이다.

### 콘텐츠 초안과 승인 대기열

콘텐츠 생성과 외부 발행을 분리하면 반복 제작을 맡기면서도 공개 범위를 통제할 수 있다. 아래는 사전 승인 정책을 선택한 서비스의 설계 예시다. 특정 앱의 기본 기능이나 조회수 증가를 보장하는 운영법은 아니다.

1. **초안 생성:** 자료를 읽고 문안과 이미지를 검토 대기 상태로 저장한다. 이 단계에는 발행 권한을 주지 않는다.
2. **최종본 검토:** 내용, 첨부, 대상 계정과 공개 범위를 함께 보여준다. 승인 후 이 값이 바뀌면 기존 승인을 그대로 재사용하지 않는다.
3. **예약과 실행:** 승인된 항목만 정해 둔 시간대의 대기열에 넣는다. 생성 시각, 승인 시각과 발행 시각을 구분하고, 발행 전 승인된 내용과 대상을 다시 대조한다.
4. **결과 확인:** 외부 서비스의 게시 결과와 식별자를 기록한다. 응답이 끊겼으면 기존 게시 여부를 먼저 확인하고 재시도해 중복 발행을 피한다([[LLM-Failure-Handling-Recovery|실패 처리와 멱등성]]).

승인 화면만 추가하고 생성 에이전트에 게시 권한을 그대로 주면 우회 경로가 남는다. 도구 권한과 실행 경로에서도 경계를 집행한다. 사람이 미리 정한 목적과 범위를 검토하는 통제 원칙은 Anthropic의 공식 설명과 대조했으며, 위 대기열과 재승인 절차는 이를 콘텐츠 발행에 적용한 설계 예시다(2026-10-06 확인).

처음에는 한 종류의 초안을 수동으로 검토하고, 반복되는 수정 이유를 다음 입력의 규칙으로 남긴다. 품질이 안정된 뒤 예약을 추가한다. 승인 대기열이 쌓이면 생성량을 늘리기보다 검토 가능한 처리량에 맞춘다.

### 시각적 워크플로우의 오류 처리

시각적으로 노드를 연결해도 실패를 감지하고 후속 동작을 정하는 운영 계약은 필요하다. n8n의 오류 처리 기능은 정상 경로를 구성하는 것과 실패 경로를 검증하는 것이 별개임을 보여 준다(2026-10-07 공식 문서 기준).

- 각 워크플로우의 설정에서 `Error Trigger`로 시작하는 오류 워크플로우를 지정하고, 여러 워크플로우가 이를 공유할 수 있다.
- `Stop And Error`로 업무상 허용할 수 없는 결과를 실패로 처리해 오류 워크플로우를 실행할 수 있다.
- `Error Trigger`는 자동 실행에서 발생한 오류에 반응한다. 편집기에서 수동 실행한 실패만으로 오류 처리 경로가 검증됐다고 판단하지 않는다.

예를 들어 LLM 결과의 필수 필드가 없으면 저장 전에 실패로 분기하고, 자동 트리거로 그 경로를 시험하는 구성을 검토할 수 있다. 이는 위 기능을 활용한 설계 예시다. 재시도 시 DB 저장이나 외부 발행이 중복되지 않는지는 별도로 확인한다([[LLM-Failure-Handling-Recovery|실패 처리와 멱등성]]). 워크플로우 개수만으로 도구의 운영 한계나 코드 전환 시점을 확정하지 않는다.

## 면접 체크포인트

- 체인 워크플로우와 에이전트 워크플로우의 선택 기준 (단순/결정론은 체인, 다양/단계점검은 에이전트, 다 에이전트로 풀지 않기)
- 판단 축은 업무의 예측 가능성 — 탐색적이면 에이전트, 절차가 확정되고 감사가 필요하면 체인, 비용의 비대칭(에이전트는 같은 절차 반복마다, 체인은 계획 변경마다 비용)
- Plan-and-Execute(Planner, Executor, Replanner) — 구조는 절차를 미리 확정해 집행하는 쪽을 닮았는데 계획의 저자는 모델, 계획이 데이터로 외부화되어 검토, 승인, 진행률 표시 가능, 재계획이 잦아도 통제 이득은 남음
- Plan-and-Execute와 되돌릴 수 없는 행동 직전 승인 — 서로 다른 두 절충, 굵은 계획(3~5단계)은 전자의 완화책
