# LLM 웹 검색 게이트웨이: 내장 검색과 근거 수집의 분리

모델 제공사 API에 내장된 웹 검색을 켜는 대신, 애플리케이션이 운영하는 검색 계층을 도구로 노출해 근거를 모으는 구성이다. 추론 모델과 검색 공급자를 따로 바꿀 수 있고, 공급자, 결과 수, 캐시와 대체 경로 같은 검색 정책을 모델 통합 코드 밖의 설정으로 관리한다. 모델 호출 자체의 키, 예산과 캐시 경계는 [[LLM-Gateway|LLM 게이트웨이]]가 다룬다.

## 내장 검색이 운영에서 막히는 지점

| 문제 | 내장 검색에서 생기는 일 |
|---|---|
| 통제 | 검색 여부와 백엔드를 애플리케이션이 고르기 어렵다. 모델을 바꾸거나 검색 단가가 바뀌면 모델 통합 코드를 고쳐야 한다 |
| 재사용 | 두 에이전트가 같은 질문을 하면 검색 요금을 두 번 낸다. 결과를 가로채 재사용할 지점이 없다 |
| 관측 | 검색 단위의 비용과 지연이 따로 보이지 않는다 |
| 출력 계약 | 검색 근거 설명이 답에 섞여, JSON, enum이나 boolean만 받아야 하는 중간 단계의 파싱이 깨질 수 있다 |

서버 도구와 애플리케이션이 실행하는 도구의 구분은 [[LLM-Workflow-Patterns-Function-Calling|함수 호출 패턴]]에 있다.

## 구성 요소

| 구성 요소 | 책임 |
|---|---|
| 단일 도구 인터페이스 | 에이전트는 공급자를 모른 채 같은 도구를 호출한다. MCP 호환 서버로 노출할 수 있다 |
| 공급자 레지스트리와 어댑터 | 엔드포인트, 요청 템플릿, 응답 매핑과 비용 메타데이터를 설정으로 추가한다 |
| 정책 설정 | 공급자 선택, 대체 순서, 캐시 정책과 결과 수를 워크로드별로 정한다 |
| 결과 정규화 | 결과마다 제목, 출처 URL과 본문 발췌를 같은 형식으로 돌려줘 인용, 로그와 출처 필터링에 쓴다 |
| 요청 단위 기록 | 공급자, 캐시 결과, 분기, 결과 수, 지연과 비용을 남긴다 |

검색 근거를 생성 텍스트에 섞지 않고 구조화된 도구 응답으로 돌려주면 출력 계약을 지키기 쉬워진다. 그래도 장황한 출력이 완전히 사라지지는 않으므로 출력 검증은 따로 둔다([[LLM-Failure-Handling|LLM 실패 처리]]).

## 요청 흐름과 캐시

1. 질의를 정규화해 사소한 표현 차이를 같은 캐시 키로 모은다.
2. 정확 일치 캐시를 본다. 적중하면 공급자를 부르지 않는다.
3. 의미 캐시를 본다. 임베딩 유사도가 문턱을 넘으면 기존 결과를 쓴다.
4. 둘 다 빗나가면 공급자 체인을 부른다. 시간 초과나 오류면 다음 공급자로 넘어간다.
5. 응답을 공통 형식으로 바꿔 두 캐시에 저장하고 도구 응답으로 돌려준다.

- **TTL은 정보가 낡는 속도에 맞춘다:** 시간에 민감한 질의는 짧게, 안정된 사실은 길게 둔다. 공급자별 캐시 항목을 나누면 서로 덮어쓰지 않는다.
- **의미 캐시의 오답:** 날짜, 장소나 부정어만 다른 질문에 이전 결과를 줄 수 있다. 문턱과 질의 유형별 예외를 오답 사례로 시험한다(설계 점검).
- **공유 범위:** 여러 워크로드가 캐시를 공유하면 적중률이 빨리 오르지만, 권한이나 테넌트가 다른 결과가 섞이지 않게 키의 범위를 정한다(설계 점검). 모델 응답 캐시의 키와 공유 범위는 [[LLM-Gateway#게이트웨이 경로의 캐시는 계층별 적중 조건과 정산을 나눈다|게이트웨이 경로의 캐시]]와 같은 기준으로 본다.

## 평가 설계

- **같은 조건으로 비교한다:** 같은 질문 세트, 같은 추론 모델과 같은 결과 수에서 내장 검색 기준선과 비교한다. 공개 QA 벤치마크와 자기 업무의 정확도를 함께 본다.
- **비용을 나눈다:** 검색 요금과 모델 추론 비용을 따로 기록한다. 검색 요금만 줄인 수치를 전체 비용 절감으로 옮기지 않는다.
- **결과 수 곡선:** 결과 수를 바꿔 정확도를 재면 일정 수 이후 이득이 작아진다. 결과가 늘면 입력 토큰도 는다.
- **캐시 상태를 나눈다:** 빈 캐시로 처음 돈 실행과 앞선 실행이 채운 캐시로 다시 돈 실행을 따로 보고, 반복 실행의 절감을 평상시 운영 절감으로 옮기지 않는다.
- **질문 유형을 나눈다:** 최신성이 중요한 질문과 여러 단계를 거치는 질문은 따로 잰다.

## 트레이드오프

- **최신성:** 일반 검색 API가 모델 제공사의 내장 검색만큼 최신 색인을 갖추지 못할 수 있다. 최신성이 통제보다 중요한 워크로드는 내장 검색으로 보내는 경로를 남긴다.
- **다단계 질문:** 한 번의 검색으로는 개선이 작을 수 있다. 반복 검색과 충분성 판정은 [[RAG-Retrieval-Engineering|RAG 검색 엔지니어링]]의 에이전틱 RAG 절을 따른다.
- **외부 의존:** 공급자의 가용성, 지연, 데이터 품질과 가격이 바뀌면 비용 비교가 달라진다. 오래 남는 가치는 특정 단가가 아니라 교체할 수 있는 인터페이스다.
- **신뢰 경계:** 검색 결과는 외부 웹의 내용이므로 지시가 섞인 입력으로 다룬다([[LLM-Application-Security|LLM 애플리케이션 보안]]).

## 사례: DoorDash의 검색 게이트웨이

DoorDash 엔지니어링 블로그 원문(2026-10-29 게시)을 2026-11-09 대조했고 수치는 자체 보고다.

- **용도:** 마켓플레이스 검색 질의의 의도 분류에 카탈로그와 웹 근거를 쓴다. 같은 회사의 논문은 카탈로그 검색과 콜드 스타트 질의용 에이전틱 웹 검색 도구로 LLM 분류를 근거화하고, 이 시스템이 일일 검색 노출의 95% 이상에 쓰인다고 보고한다. 이 논문은 게이트웨이와 검색 비용을 다루지 않는다.
- **구성:** Serper, BrightData, Firecrawl, Exa와 Tavily를 공급자로 두고, 내장 검색도 같은 인터페이스 뒤의 공급자로 등록할 수 있다. 새 HTTP 공급자는 YAML 어댑터로 추가한다.
- **정확도와 비용:** Gemini Flash와 내장 Google Search 근거화를 기준선으로, 일반 비식품 소매 질의 7,988개에서 Serper 경로 93.90% 대 기준선 93.40%, 합성 롱테일 2,335개에서 87.79% 대 87.62%였다. 검색 요금은 두 세트 모두 98% 이상 줄었고 모델 추론 비용은 이 수치에 들어 있지 않다.
- **캐시:** 캐시 적중률이 처음 실행 6.2%에서 반복 실행 99.4%로 오르자 평균 지연이 68%, 1,000건당 검색 비용이 99% 이상 줄었다. 앞선 실행이 채운 캐시 조건의 값이다.
- **결과 수:** SimpleQA에서 결과를 2개에서 6개로 늘리면 세 모델 평균 정확도가 78.7%에서 84.9%로, 10개에서는 85.5%였다.
- **출력 계약:** HotpotQA에서 Claude Sonnet 4에 내장 검색을 켜면 답만 내라는 지시를 78.1% 어겼다.
- **한계:** FreshQA에서는 비교한 다섯 모델 모두 내장 검색이 앞섰고, HotpotQA는 어느 쪽도 크게 나아지지 않았다.

## 점검 항목

- 검색 정책이 모델 통합 코드 밖의 설정에 있는가?
- 공급자 장애 때의 대체 순서와 시간 초과가 정해져 있는가?
- 요청마다 공급자, 캐시 결과, 지연과 비용이 남는가?
- TTL이 질의 유형의 최신성 요구와 맞는가?
- 의미 캐시 문턱을 오답 사례로 시험했는가?
- 정확도 비교가 같은 질문, 같은 모델, 같은 결과 수에서 이뤄졌는가?
- 최신성 질문과 다단계 질문을 따로 쟀는가?
