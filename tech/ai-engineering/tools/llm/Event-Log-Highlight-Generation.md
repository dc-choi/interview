# 이벤트 로그 기반 하이라이트 생성

실시간 서비스의 모든 로그를 LLM에 넣기보다, 사실 추출과 계산을 코드에 맡기고 의미 있는 사건의 선택과 설명에 모델을 사용한다. 입력 축소, 통계 조회와 공개 전 검증을 나누는 패턴이다.

## 처리 흐름

| 단계 | 책임 | 확인할 실패 |
|---|---|---|
| 로그 선별 | 필요한 이벤트 유형과 필드를 선택 | 맥락에 필요한 이벤트가 빠짐 |
| 정규화 | 코드로 주체, 대상, 시각과 수치를 변환 | 단위 오류나 주체와 대상 뒤바뀜 |
| 후보 생성 | 모델이 사건을 선택하고 유형과 인물을 추출 | 서로 다른 사건을 합치거나 의미를 과장 |
| 통계 조회 | 유형에 대응하는 SQL 템플릿에 검증한 매개변수를 전달 | 기간, 집계 범위와 인물 식별 오류 |
| 검토와 표현 | 사실을 대조한 뒤 독자에게 필요한 문장으로 정리 | 근거가 없는 평가나 수치 왜곡 |

하이라이트의 흥미도와 사실 정확도는 별도 평가다. 드문 사건이나 최고 기록이라는 설명에는 비교 대상과 기간을 가진 통계가 필요하다. 표현을 자연스럽게 만드는 단계에서 확인하지 않은 이유나 인과관계를 덧붙이지 않는다.

## SQL 템플릿의 적용 조건

이벤트 유형과 조회 패턴이 한정되어 있고 지연 예측이 중요하면, 자유 SQL 생성 대신 유형 분류와 매개변수 추출로 범위를 줄일 수 있다. 새로운 질문을 지원하려면 템플릿을 추가해야 하는 비용이 있다.

다음은 적용 시의 설계 제안이다. 허용한 유형만 템플릿에 매핑하고 매개변수의 형식, 범위와 대상 존재를 확인한다. 문자열 치환으로 SQL을 조립하지 않고 값 바인딩을 사용한다. 템플릿을 사용해도 잘못 고른 인물이나 기간, 조인 중복으로 결과가 틀릴 수 있다.

## 평가와 처리량

원본 이벤트와 출력의 주체, 행위, 시간과 수치를 대조한다. 모델 판정 점수는 오류 후보를 찾는 보조 자료로 쓰고, 실제 오류 사례와 사람이 검토한 표본으로 함께 평가한다. 특정 점수를 넘었다는 이유만으로 사실성을 보장하지 않는다.

생성량은 최종 검토자가 처리할 수 있는 양과 맞춘다. 낮은 품질의 후보를 많이 보내면 선택과 검토가 병목이 된다. 전체 지연은 입력 수집 구간, 각 처리 단계와 최종 검토 대기를 나눠 측정한다.

## 적용 근거와 한계

2025년 PNC 사례 발표는 필요한 게임 로그 선별, 규칙 기반 텍스트 변환, SQL 템플릿 매핑과 추가 검증을 결합한 구현을 소개한다. 위 패턴의 적용 사례이며, 발표의 특정 모델 속도와 평가 점수는 다른 워크로드의 성능 보장으로 사용하지 않는다. 본문에 적은 바인딩과 입력 검증은 적용을 위한 설계 제안이며 발표 구현의 확인 사실과 구분한다.
