# LLM 위키와 지식 합성의 영속화

LLM 위키는 여러 원문에서 조합한 지식을 주제별 Markdown으로 저장하고 갱신하는 패턴이다. 질문마다 근거를 찾는 검색에 재사용할 합성 결과를 더한다. RAG를 대체해야 하는 구조는 아니며, 위키가 커지면 위키 자체를 검색할 수도 있다.

## RAG, 에이전틱 검색과 파인튜닝을 구분한다

네 방식은 서로 배타적인 제품 종류가 아니라 지식을 처리하는 위치가 다른 방법이다.

| 방법 | 주로 바꾸는 것 | 구분할 점 |
|---|---|---|
| RAG | 요청에 맞춰 검색한 외부 근거를 모델 컨텍스트에 넣는다 | 검색한 내용을 읽히는 동작 자체가 모델 재학습은 아니다 |
| 에이전틱 RAG | 에이전트가 검색 시점, 도구와 추가 검색 필요성을 판단한다 | 근거가 부족한지 평가하고 반복할 수 있지만 성공을 보장하지 않는다 |
| LLM 위키 | 원문에서 합성한 내용을 지속되는 문서와 연결로 저장한다 | 합성 결과를 재사용하며 위키를 읽을 때 검색을 함께 쓸 수 있다 |
| 파인튜닝 | 특정 과제에 맞게 모델을 추가 학습한다 | 위키 파일 수정이나 요청 시점 검색과 별개의 학습 단계다 |

LLM 위키가 검색을 지원하지 않는다는 구분은 맞지 않는다. 공개 아이디어 문서는 작은 규모에서 목차로 탐색하고, 규모가 커지면 검색 도구를 붙이는 방법을 설명한다. 약 100개 원문과 수백 페이지는 저자의 경험상 예시이며, 문서 10만 개를 보편적인 전환 기준으로 정한 규격이 아니다. 또한 외부 관리형 모델은 파인튜닝할 수 없다는 일반화도 맞지 않는다. Amazon Bedrock은 지원 모델과 리전을 정해 파인튜닝을 제공한다(2026-10-24 공식 안내 확인).

적용 제안: 같은 질문 묶음으로 근거 누락, 갱신 지연, 응답 시간과 비용을 비교한 뒤 방식을 조합한다. 위키 파일의 존재나 에이전틱이라는 이름만으로 답변 품질과 접근 권한이 보장되지는 않는다.

## 원문, 위키와 규칙의 분리

| 층 | 책임 |
|---|---|
| 원문 | 대조할 근거를 보존한다. 위키 작성 과정에서 원문을 수정하지 않는다 |
| 위키 | 개념, 엔티티와 비교를 정리하고 원문 및 관련 페이지를 연결한다 |
| 규칙 | 문서 구조, 출처 표기, 충돌 처리와 갱신 절차를 정한다 |

수집한 자료 하나가 기존 페이지 여러 개를 바꿀 수 있다. 질문의 답을 저장할 때도 기존 개념과 연결하고, 주기적으로 충돌, 오래된 주장과 끊긴 링크를 점검한다. 목차는 내용 탐색을, 변경 기록은 갱신 이력 확인을 맡는다.

## 채팅 링크 수집과 지식 반영의 구분

채팅에 올라온 링크를 표에 모으는 단계와 원문을 읽고 기존 개념에 연결하는 단계는 완료 조건이 다르다. 제목, 분류와 요약 열이 채워졌더라도 링크 본문을 확보했는지, 요약의 주장을 확인했는지는 별도로 남긴다. 다음은 원문과 파생 위키의 분리를 수집 자동화에 적용한 설계 예시다.

| 단계 | 남길 내용 | 완료 조건 |
|---|---|---|
| 수집 | 원문 위치, 수집 시각과 처리 식별자 | 나중에 원문을 다시 찾을 수 있다 |
| 초안 | 확보한 본문 범위, 생성 요약과 분류 | 제목만 본 경우와 본문을 읽은 경우가 구분된다 |
| 지식 반영 | 대조한 근거, 반영 문서와 검토 상태 | 기존 내용과의 중복 및 충돌을 확인했다 |

예를 들어 Slack Events API의 HTTP 전달은 실패한 요청을 재시도하며, 이벤트에는 고유한 `event_id`가 있다. Google Sheets의 `spreadsheets.values.append`는 지정 범위에서 표를 찾아 다음 행에 값을 추가한다. 따라서 이벤트를 받을 때마다 행을 추가하는 설계에는 재전달로 같은 자료가 여러 행에 들어갈 위험이 있다. 이 동작에서 도출한 설계 점검으로, 수집 식별자별 처리 상태와 저장 결과를 확인하고 중복 저장을 막는 절차를 둔다. 단순한 사전 조회만으로 동시 처리 경쟁까지 해결됐다고 보지 않는다.

위 API 사실은 2026-10-14 공식 문서 기준이다. 이는 직접 구성하는 수집 파이프라인의 검토 기준이며, 특정 AI 제품의 채팅 연동이나 자동 요약 기능이 같은 방식으로 구현되었다는 뜻은 아니다. 비공개 채팅의 원문 위치와 식별자는 접근이 제한된 수집 기록에 두고, 공개 위키에는 공개 가능한 근거와 개념만 반영한다.

## 자동 갱신의 검증 경계

다음은 2026-10-06 공개 강의의 위키 빌더 사례를 일반화한 설계 점검 항목이다. 특정 도구의 기본 기능이나 검증 정확도 보장이 아니다.

1. 변경할 문서와 근거를 먼저 정한다. 관련 없는 페이지까지 갱신하지 않는다.
2. 작성 중인 결과와 사용자가 조회하는 문서를 분리한다. 형식과 링크 검사는 코드로, 주장의 근거 대조는 별도 검토로 나눈다.
3. 검토자는 일정 제안을 확정 결정으로 바꿨는지, 원문의 조건을 빠뜨렸는지 확인한다. 두 문서가 상충하면 최신 날짜 하나로 해결하지 않고 권한, 적용 범위와 결정 상태를 대조한다.
4. 검토 실패, 판정 누락과 시간 초과를 통과로 간주하지 않는다. 근거를 확인하지 못한 변경은 보류한다.
5. 자동 생성 초안, 사람이 검토한 문서와 폐기된 내용을 구분한다. 형식 검사 통과가 사람의 사실 검토를 대신하지 않는다.

## 규모가 커질 때 목차와 링크를 구조로 지킨다

목차 한 파일과 문장 속 위키링크로 시작한 위키는 커지면서 두 문제가 드러난다.

| 문제 | 증상 | 구조로 푸는 방법 |
|---|---|---|
| 목차가 커진다 | 모든 페이지를 담은 목차를 읽는 데 컨텍스트를 쓰고 고르는 정확도가 떨어진다 | 목차를 계층으로 나눠 한 겹씩 내려가게 하고 인덱스 하나의 자식 수에 상한을 둔다 |
| 링크가 텍스트다 | LLM이 파일 이름을 바꾸거나 본문을 고쳐 쓰다 링크를 끊어 고아 페이지와 깨진 참조가 생긴다 | 링크를 저장소가 지키는 관계로 두거나, 쓰기 전후에 링크와 동명 파일을 코드로 검사한다 |

한 세미나 발표는 목차 한 파일이 약 200페이지를 넘으면 성능이 떨어지는 경험을 들었다. 발표사의 관찰이며 일반 기준은 아니다. 해결 방향은 둘로 나뉜다.

- **저장소가 구조를 지킨다:** 목차 트리와 페이지 사이 관계를 DB가 관리하고, LLM은 옮기거나 잇는 동작만 요청한다. 관계에 종류와 라벨을 두고 검색에 권한을 함께 건다. 구조가 깨질 여지는 줄지만 Markdown 파일을 직접 고치는 단순함을 잃는다.
- **원본은 Markdown, 구조는 검사로 지킨다:** 폴더별 인덱스로 목차를 나누고, 깨진 링크와 동명 파일을 편집 직후 결정론적으로 검출하고 커밋에서 막는다. 이 vault에서는 도메인 지침이 카테고리 인덱스 갱신을 정하고, `.claude/hooks/vault_guard.py`가 편집 뒤 훅과 pre-commit 훅으로 링크와 동명 파일을 검사한다. Markdown 원문을 색인해 조회하는 구성은 [[Development-Ontology|개발 판단 온톨로지]]에 있다.

어느 쪽이든 모르는 사실을 추측해 채우지 않는다. 에이전트가 코드값의 뜻처럼 확인되지 않은 내용을 만나면 담당자에게 묻고, 확정된 내용을 페이지에 기록해 다음 질의부터 쓴다. 재임베딩이나 재학습 없이 반영되는 대신 잘못 확정된 내용도 바로 퍼지므로, 편집에 승인 모드와 버전 기록을 둔다. 페이지의 문장은 이유를 설명하고, 반드시 지켜야 하는 판정은 페이지에 연결한 워크플로나 도구가 맡는다([[Agent-Governance-Controls|에이전트 거버넌스 통제]]).

## 위키를 검색에 더한 효과는 질문 유형에 따라 다르다

답의 근거가 한 문서에 모여 있으면 원문 검색으로 충분할 수 있다. 여러 문서를 엮거나 판단이 필요한 질문에서 미리 합성한 위키의 이득이 커진다. 위키는 검색을 대체하기보다 함께 쓸 때 효과를 재 볼 대상이다.

**사례: Anthropic의 위키 생성 실험.** 에이전트가 원문 문서 묶음을 탐색하며 서로 연결된 위키 페이지를 쓰고 고치는 과정(Anthropic은 이 과정도 dreaming이라 부른다)을 Stainless 내부 문서, 합병 관련 문서(주로 공개 공시)와 Harvey LAB 과제 문서로 잰 값이다. 기억 노트나 세션 기록에서 위키를 만든 측정은 아니다. 2026-11-06 공개 글을 2026-11-09 대조했다.

| 자료와 조건 | 보고한 결과 |
|---|---|
| Stainless 내부 자료 약 35만 파일(약 4.2억 토큰), 질문 25개, Opus 5, 128세션 | 위키만 쓰면 정리 토큰을 200만에서 1.28억으로 늘릴 때 채점 기준 충족률 13%에서 48%. 원문 검색만 53%. 위키와 검색을 함께 쓰면 54%에서 61%이고 질문당 약 2만 토큰을 덜 썼다 |
| 합병 관련 문서 질문 24개(주로 공개 공시, Harvey LAB과 별도 시험) | 여러 문서를 엮거나 판단, 계산이 필요한 문항에서 위키 87%, 검색 73%. 채점 기준 57개 대부분을 한 문서(주로 거래 개요 메모)에서 찾을 수 있던 Harvey LAB 과제에서는 위키가 검색보다 뚜렷한 이득을 보이지 않았다 |
| 10개 문서, 115KB | 68페이지, 255링크, 203KB의 위키가 나와 원문의 1.77배였고 연결되지 않은 페이지도 있었다 |

두 번째 정리 과정은 존재하지 않는 페이지를 가리키던 링크 9개를 기존 페이지로 고치고 색인(index), 지시 이메일, 에스컬레이션 페이지 3개를 더했다. 위키가 원문보다 커질 수 있고 링크가 끊길 수 있다는 점은 위의 구조 검사가 필요한 이유와 같다. 수치는 발행사가 자기 모델과 자료로 잰 값이며 대부분 반복 횟수와 분산을 밝히지 않았다. 기억 층과 정리 과정 자체는 [[Agent-Memory-Retain-Recall-Reflect#기억의 층과 세션 사이의 정리|에이전트 기억의 층]]에서 다룬다.

## 비용과 실패 조건

갱신은 여러 페이지의 재작성과 검토 비용을 만든다. 원문 변경이 위키에 반영되기 전에는 두 내용이 어긋나고, 잘못된 합성을 다음 답변의 근거로 반복하면 오류도 누적된다. 원문 링크와 변경 이력을 유지하며, 저장할 만한 재사용 가치와 검토 비용을 함께 판단한다.

문서 수가 늘었다는 사실만으로 답변 품질이 좋아졌다고 보지 않는다. 같은 질문으로 근거 누락, 잘못된 확정과 갱신 지연을 확인한다. 검색의 권한과 삭제 전파는 [[RAG-Retrieval-Engineering|RAG 검색 엔지니어링]]에서 함께 다룬다.
