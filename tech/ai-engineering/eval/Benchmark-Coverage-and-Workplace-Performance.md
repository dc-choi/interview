# 벤치마크 평가 범위와 업무 성과

평가 문항이 어떤 업무를 다루는지, 모델이 그 문항을 얼마나 잘 푸는지, 사람이 도구를 사용해 일을 얼마나 잘 마치는지는 서로 다른 질문이다. 코드 생성 점수를 직업 전체의 대체율로 읽으면 이 구분이 사라진다.

## 범위, 성능과 업무 결과를 나눈다

| 구분 | 확인할 것 | 그 결과만으로 알 수 없는 것 |
|---|---|---|
| 평가 범위 | 직무 과업과 연결된 문항의 수와 분포 | 모델의 정답률 |
| 과제 성능 | 정해진 환경과 채점 기준에서의 성공 | 빠진 업무의 수행 능력 |
| 업무 결과 | 사람이 검토하고 실제 완료한 결과 | 다른 팀과 업무에서도 같은 개선이 나는지 |

Mercor의 Benchmark Map은 선택한 29개 벤치마크를 O*NET의 923개 직업, 18,797개 과업에 연결한다. 한 문항이 여러 과업에 대응할 수 있고, 본문 방법론의 covered 기준은 과업당 5개 이상 문항이다. 지도에는 1개와 5개 기준을 선택하는 기능이 있으므로 숫자를 옮길 때 기준도 남긴다.

매핑은 LLM 판정기로 만들고 APEX 부분집합의 전문가 라벨로 검증했다. 지도 색은 과업이 문항에 포함된 비율이며 정답률이 아니다. 일부 과업에 문항이 없다는 사실도 AI가 그 일을 못 한다는 증거가 아니다.

## 지도에도 표본의 한계가 있다

초기 목록은 모든 벤치마크의 전수조사가 아니다. 직군별 벤치마크 수에 상한을 두고 이미 포화된 시험을 제외했으므로 소프트웨어처럼 시험이 많은 직군이나 쉬운 과업의 범위가 낮게 잡힐 수 있다. 문항 매핑과 표본 선택의 한계를 고용 전망으로 확대하지 않는다.

자동으로 과제를 끝내는 능력과 사람의 생산성을 높이는 능력도 구분한다. 이 둘의 일반화는 해당 연구가 남은 문제로 명시한 부분이다. 2026-10-26 공개 방법론과 한계를 대조했으며 개별 모델 점수와 개발자 직무별 문항 수는 여기서 검증하지 않았다.

## 실제 위임에서는 완료 조건을 맞춘다

다음은 위 구분을 개발 업무에 적용한 측정 제안이다. 연구가 입증한 생산성 효과나 표준 지표는 아니다.

1. 맡길 일을 버그 수정, 요구사항 탐색, 설계 대안 비교처럼 나누고 성공 조건을 적는다.
2. 이미 정해진 요구를 찾아오는 작업과 이해관계자 사이에서 요구를 합의하는 작업을 분리한다.
3. 설명, 구현, 검토와 수정에 쓴 작업 시간을 기록한다. 승인이나 외부 의존성 때문에 기다린 시간은 별도로 남긴다.
4. 과업 크기, 난도와 품질 기준을 맞춰 비교한다. 완료 건수만으로 생산성을 판정하지 않는다.
5. 통과한 테스트와 실제 사용 흐름, 배포 뒤 결과를 구분한다. 위임 가능 범위는 관찰한 결과에 맞춰 조정한다.
