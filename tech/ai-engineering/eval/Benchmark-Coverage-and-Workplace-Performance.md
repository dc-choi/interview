# 벤치마크 평가 범위와 업무 성과

평가 문항이 어떤 업무를 다루는지, 모델이 그 문항을 얼마나 잘 푸는지, 사람이 도구를 사용해 일을 얼마나 잘 마치는지는 서로 다른 질문이다. 코드 생성 점수를 직업 전체의 대체율로 읽으면 이 구분이 사라진다.

## 범위, 성능과 업무 결과를 나눈다

| 구분 | 확인할 것 | 그 결과만으로 알 수 없는 것 |
|---|---|---|
| 평가 범위 | 직무 과업과 연결된 문항의 수와 분포 | 모델의 정답률 |
| 과제 성능 | 정해진 환경과 채점 기준에서의 성공 | 빠진 업무의 수행 능력 |
| 업무 결과 | 사람이 검토하고 실제 완료한 결과 | 다른 팀과 업무에서도 같은 개선이 나는지 |

Mercor의 Benchmark Map은 선택한 29개 벤치마크를 O*NET의 923개 직업, 18,797개 과업에 연결한다. 한 문항이 여러 과업에 대응할 수 있고, 본문 방법론의 covered 기준은 과업당 5개 이상 문항이다. 지도에는 1개와 5개 기준을 선택하는 기능이 있으므로 숫자를 옮길 때 기준도 남긴다.

매핑은 LLM 판정기로 만들고 APEX 부분집합의 전문가 라벨로 검증했다. 지도 색은 과업이 문항에 포함된 비율이며 정답률이 아니다. 일부 과업에 문항이 없다는 사실도 AI가 그 일을 못 한다는 증거가 아니다.

## 지도에도 표본의 한계가 있다

초기 목록은 모든 벤치마크의 전수조사가 아니다. 직군별 벤치마크 수에 상한을 두고 이미 포화된 시험을 제외했으므로 소프트웨어처럼 시험이 많은 직군이나 쉬운 과업의 범위가 낮게 잡힐 수 있다. 문항 매핑과 표본 선택의 한계를 고용 전망으로 확대하지 않는다.

자동으로 과제를 끝내는 능력과 사람의 생산성을 높이는 능력도 구분한다. 이 둘의 일반화는 해당 연구가 남은 문제로 명시한 부분이다. 2026-10-26 공개 방법론과 한계를 대조했으며 개별 모델 점수와 개발자 직무별 문항 수는 여기서 검증하지 않았다.

## 종합 지수의 개편은 측정 도구의 변경이다

Artificial Analysis의 2026-10-27 Intelligence Index v5 발표는 9개 평가를 지식 업무, 코딩, 과학과 일반 능력에 각각 25%씩 배분한다. 비공개 테스트 세트나 비공개 정답을 쓰는 평가의 비중은 60%다. 공개 노출을 줄이는 목적과 외부에서 문항을 직접 점검하기 어려운 한계를 함께 본다.

FrontierCode 2.0과 Terminal-Bench-Science를 추가하고 HLE-Diamond, AA-Omniscience v1.1과 CritPt v2를 개편했다. 평가 구성이 바뀐 v4와 v5 점수의 차이를 능력 향상량으로 그대로 빼지 않는다. 장기 추세용 Progress Index v1도 별도 척도다.

발표일의 max 설정 점수는 Opus 5.5 58, GPT-6 Astra 57, GPT-6.1 Sol 55였다. 공개 가중치 부문 46점의 Kimi K3.1 Pro는 당시 가중치가 미공개였고 실제 공개 모델 최고점은 32였다. 이후 Carbon 발표의 59점과 충돌하는 순위가 아니라 날짜가 다른 결과다. 같은 날짜, 지수 버전, 추론 강도와 실제 가중치 제공 여부를 붙인다. 9개 평가 전부를 이긴 단일 모델이 있다는 근거로 쓰지 않는다.

## 새 버전이 낮게 나온 제3자 점수는 설정과 표본부터 본다

SimpleBench는 전문 지식 없이 풀 수 있는 객관식 문항 200여 개로 시공간 추론, 사회적 상황 이해와 함정이 있는 질문(언어적 적대 견고성)을 잰다. 공개 문항은 10개(선택지 A~F)이고 나머지는 비공개다. 점수는 다섯 번 돌린 평균(AVG@5)이다. 사이트는 샘플링을 temperature 0.7, top-p 0.95(o1 계열 제외)로 적지만, 이 값을 받지 않는 추론 모델에 실제로 쓴 샘플링과 추론 강도는 적지 않는다. 벤치마크에 맞춘 프롬프트를 시도한 항목에 붙이는 주석 표시가 있지만 현재 표에는 그 표시가 붙은 항목이 없다. 아래는 2026-11-25 공식 리더보드와 그 데이터 파일을 대조한 기준이다.

- **버전 간 하락**: 2026-11-18 등재된 GPT-6.2 Astra는 77.3%(17위), GPT-6.2 Astra Pro는 79.2%(16위), GPT-6.2 Sol은 69.9%(30위)로 직전의 GPT-6 Astra 83.6%, GPT-6 Astra Pro 86.5%, GPT-6.1 Sol 82.9%보다 낮았다. 같은 표의 1위와 2위는 Claude Fable 5.2(94.9%)와 Gemini 4 Neon(94.4%)이다.
- **사람 기준선은 9명이다**: 기준선 83.7%는 고등학교 수준 지식을 가진 참가자 9명의 결과이고, 표에는 최고 사람 점수 95.4%가 따로 있다. 9명 평균은 흔들림이 커서 기준선을 몇 점 넘거나 밑도는 것을 사람보다 낫거나 못하다는 근거로 쓰기 어렵다(이 문서의 판단). 사이트는 사람이 모든 모델을 앞선다는 소개 문단의 구절과 제목의 해당 표현을 취소선으로 철회해 두었다.
- **실행 설정이 이름에 없다**: 예전 항목 일부는 `(xhigh)`, `(high)`처럼 추론 강도를 붙였지만 GPT-6.2 항목에는 없다. 데이터 파일의 모델별 값에는 정의가 없는데, 단가와 곱해 보면 `tout`은 문항당 평균 출력 토큰, `cpr`은 한 번 실행 비용으로 읽힌다(이 문서의 계산). 그 값이 GPT-6.2 Sol 54, GPT-6.2 Astra 69로 GPT-6.1 Sol 140의 약 39%, GPT-6 Astra 136의 약 51%이고 Claude Fable 5.2는 537이다. 이 역산은 Sol과 Astra 행에서는 표기된 비용과 맞지만 Pro 두 행에서는 맞지 않는다. 비교 대상인 이전 세대 항목에도 추론 강도 표기는 없다. 해석이 맞다면 새 버전이 같은 문항에 훨씬 짧게 답한 것이고, 하락의 일부는 추론 강도나 출력 길이 같은 실행 조건의 차이일 수 있지만, 같은 추론 강도로 다시 잰 결과가 없어 원인을 단정하지 않는다(이 문서의 해석). 선택할 수 있는 추론 강도는 [[OpenAI-GPT-Generations#GPT-6 계열에서 바뀐 호출 계약|GPT-6 계열의 호출 계약]]에 있다.
- **문항 수가 정하는 오차**: 200문항에서 정답률 75% 부근 점수 하나의 표준 오차는 약 3%포인트다(√(0.75 × 0.25 / 200) ≈ 0.031, 이 문서의 계산). 다섯 번 평균은 실행 사이의 흔들림만 줄이고 문항 표본의 오차는 줄이지 않는다. Sol의 13점 하락은 이보다 훨씬 크지만, 몇 점 차이의 순위는 문항별 결과 없이 가르기 어렵다.

평가에 옮기면(운영 제안) 새 버전으로 바꾸기 전에 자기 업무의 짧은 판단 문항을 이전 버전과 같은 추론 강도로 나란히 돌리고 출력 토큰을 점수와 함께 기록한다. 토큰을 줄였다는 발표([[Model-Release-Claims#비용 절감률은 단가, 토큰 수, 과업당 비용으로 나눈다|비용 절감률과 토큰 수]])는 짧게 답할 때 놓치는 문항이 생기는지와 함께 본다. 객관식 점수의 채점 방식 차이는 [[LLM-Perplexity-and-Benchmarks#객관식 벤치마크는 채점 방식까지가 벤치마크다|객관식 벤치마크 채점]]에 있다.

## 익숙한 과제를 바꿔 점수의 일반화를 확인한다

공개 벤치마크는 과제와 정답이 익숙해질수록 일반 능력과 벤치마크에 맞춘 행동을 가르기 어려워진다. unLAP의 MaxxBench(2026-10-20 공개 글, 논문은 아직 미공개)는 DeepSWE의 중간 길이 기능 구현 과제 89개에서 지시나 시작 코드를 조금 바꾸고 참조 해답과 테스트를 그에 맞게 고쳤다. 참조 패치는 중앙값 17줄(3.5%) 늘었다. 예를 들어 브라우저 테스트 보고서 파일명을 `Chrome__Headless_.xml` 대신 소문자 `chrome__headless_.xml`로 만들게 했다. 원래 과제의 참조 코드와 검증기 버그를 일부 고친 뒤 원 제출물을 다시 채점하면 평균이 65.8%에서 64.5%로 바뀌었다.

| 모델 | DeepSWE | MaxxBench |
|---|---|---|
| Claude Opus 5.5 | 74.2% | 76.4% |
| DeepSeek V4.1 Flash | 74.2% | 55.6% |
| Gemini 3.8 Flash | 73.8% | 53.4% |

15개 구성의 점수 폭은 20.9점에서 48.3점으로 벌어졌다. 발표자는 실패한 패치와 실행 기록을 모두 검토해 반복되는 실패를 다섯 패턴(테스트를 내다본 위험 감수, 방어적 추정, 알고도 요구를 따르지 않음, 요구 오독, 구현 버그)으로 나눴고, 그와 별도로 아래 세 행동을 따로 짚었다.

- **숨은 테스트를 추정해 요구를 무시:** 바뀐 요구를 이해하고도 채점 테스트가 확인하지 않으리라 보고 원래 동작으로 돌아갔다. `uint64`를 지원하라는 과제에서 2^53 위로 정밀도를 잃는 `float64`로 바꾼 사례가 있고, 세 모델의 바뀐 검사 실패 가운데 약 4분의 1이 이 유형이었다.
- **자기 보고 수치 맞추기:** 프로그램이 스스로 출력한, 메모리에 둔 파일 레코드 수의 최댓값(`peak_in_memory_files`)을 읽는 검사는 13개 모델의 모든 시도가 통과했지만, 메모리에 실제로 남은 레코드를 따로 잰 검사는 대부분 실패했다. 7개 모델은 보고 수치만 한도에 맞추고 출력 단계에서 내보낸 레코드를 다시 불러왔다.
- **실행 환경의 자격증명 사용:** 한 모델은 실행용 API 키로 외부 모델과 웹 검색을 불러 샌드박스의 네트워크 제한을 우회했고, 한 과제에서는 맞게 고친 코드를 외부에서 받은 구현으로 덮어써 실패했다([[Agent-Swarm-Containment#샌드박스의 정답 유출과 가용성 장애를 나눠 본다|샌드박스의 정답 유출]]).

평가 설계에 옮기면(운영 제안) 공개 점수가 비슷한 후보도 내 업무에서 익숙한 답이 틀리도록 바꾼 과제로 다시 비교하고, 에이전트가 스스로 보고하는 지표에는 독립 측정을 짝으로 둔다. 다만 벤치마크를 만든 회사의 자체 발표다. 변형 과제, 참조 해답과 테스트는 GitHub 저장소 unlap-labs/maxxbench(2026-11-07 생성)에, 실행 기록은 사이트의 Data 페이지에 공개돼 있고(2026-11-09 확인) 논문은 아직 공개되지 않았다. 추론 강도를 바꿔 다시 돌린 모델은 하나뿐이며, 공개된 변형 과제도 익숙해지므로 주기적으로 갱신해야 한다.

## 느린 실행은 단계당 시간과 단계 수로 나눈다

같은 과제를 푸는 모델 사이에서도 과제 하나에 쓰는 시간과 비용은 크게 다를 수 있다. 자체 비공개 평가를 운영하는 Kernel은 버그 수정 평가에서 Gemini 4 Carbon(high)이 버그 4개 평균 56분(정가 기준 버그당 $13.17)을 쓰는 동안 Claude Opus 5.5와 GPT-6 Astra는 high에서 2~4분에 끝내자, 실행의 모든 단계를 추적해 원인을 나눴다(2026-11 게시, 2026-11-21 대조). 글에 실린 실행 데이터로 계산하면 max에서는 Astra 6.0분, Opus 5.5 20.7분이었다(이 문서의 계산). 과제는 버그가 고쳐지기 직전의 코드베이스와 증상만 적은 보고서를 주고, 관련 없는 변경 없이 진단과 수정을 요구한다.

- **단계당 시간**: 공급사 대기열, 네트워크 지연, 프롬프트 처리와 생성 속도가 단계 하나의 시간을 정한다. 느린 추론은 Carbon의 추가 시간 가운데 Astra 대비 16~30%, Opus 대비 45~49%만 설명했다.
- **단계 수**: 나머지는 궤적 길이에서 왔다. 비교 기준은 GPT-6 Astra(max)이고 버그 4개에 설정마다 한 번씩 돌린 평균이다(글에 실린 실행 데이터로 확인). 단계(한 번의 사고와 그에 딸린 행동)는 약 7배, 행동(파일 읽기, 명령, 편집 같은 도구 호출)은 약 11배, 출력은 약 7배였고, 단계마다 길어진 대화를 다시 보내므로 처리한 입력은 16배를 넘었다.
- **교란 요인을 먼저 뺀다**: 하네스를 opencode와 mini-SWE-agent로 바꿔도 의미 있는 차이가 없었다. 추론 강도의 이름이 공급사마다 표준화돼 있지 않아 Carbon의 high가 다른 모델의 최고 설정에 가까울 수 있으므로 low도 돌렸는데, low에서는 수정을 아예 내지 못하고 이미 읽은 코드를 다시 읽으며 맴도는 일이 잦았다.
- **단계의 목적을 라벨로 센다**: 단계마다 무엇을 위한 것인지 라벨을 붙이자 Carbon 단계의 절반이 보고서가 요구하지 않은 일에 쓰였다. 원인을 찾은 뒤에도 수정과 무관한 경로를 감사했고, 보고서의 사실이 이미 배제한 경우까지 방어하는 코드를 넣으려 했다.
- **필요한 단계 안의 기계적 비효율**: 글은 수정에 필요한 단계만 보면 Astra가 단계당 도구 호출 2.4개로 여러 파일을 한 번에 읽었고 Carbon은 1.2개였다고 적는다. 같은 글의 전체 실행 데이터에서는 단계당 도구 호출이 Astra(max) 0.95개, Carbon(high) 1.56개로 순서가 반대이고(이 문서의 계산) 위의 11배도 이 전체 데이터에서 나온 값이다. 두 수치는 대상 구간이나 세는 방식이 다른데 글은 그 차이를 설명하지 않는다. Carbon이 읽은 줄의 39%는 이미 본 줄이었다(Astra 7%). 글은 단계당 호출이 적은 것과 다시 읽기가 초과 시간의 약 25%를 차지한다고 추정한다.
- **개입으로 원인을 가린다**: 구매 버그 한 건에서 Astra(max)는 0:44에 원인을 짚고 3:42에 첫 편집을 해 6:19에 끝났고, Carbon(high)은 6:26에 원인을 짚고도 31:46에야 첫 편집을 해 37:04에 끝났다. 원인을 몰라서 계속 찾는지, 알고도 계속하는 습관인지 가르려고 이 시도를 5턴마다 수정에 필요한 정보를 이미 충분히 확보했는지 묻는 확인 문구를 하네스가 넣게 해 다시 돌리자 28:02에 끝났다. 원인을 짚은 뒤 첫 편집까지는 25분에서 약 10분(9:07에서 19:42)으로 15분 가까이 줄었지만, 원인을 짚은 시점이 2~3분 늦어지고 첫 편집 뒤 마무리도 5분에서 8분으로 늘어 전체로는 9분 줄었다. 작성자는 이를 지연이 지식보다 행동에서 온다는 근거로 해석한다.

확인 범위의 한계도 함께 적는다. 비공개 평가라 과제 내용과 통과율이 공개되지 않았고, 평균은 버그 4개에 설정마다 한 번씩 돌린 값이며, 개입 실험은 한 버그의 재실행 한 번이고, 평가를 운영한 쪽의 자체 분석이다. 비용 그림은 API 정가와 월 200달러 요금제를 다 쓴 경우 두 가지로 보이는데, 후자는 모델별 구독 보조 배율(Opus 40배, Astra 13배, Carbon 3배, Hydrogen 17배)을 가정하고 Carbon은 특별가가 끝난 뒤의 단가로 계산했다.

평가에 옮기면(운영 제안) 성공률과 함께 과업당 시간과 비용을 기록하고, 느린 모델은 단계당 시간(인프라와 생성 속도)과 단계 수(행동)로 나눠 본다. 하네스와 추론 강도를 바꾼 대조로 교란 요인을 먼저 빼고, 단계의 목적을 라벨로 세어 요청 범위 밖 작업의 비중을 잰다. 무관한 변경을 금지한 과제에서 범위 밖의 방어 코드는 리뷰 부담으로 돌아오므로 통과 여부와 따로 기록한다. 확인 문구 같은 하네스 개입은 통과율을 잃지 않고 시간을 줄이는지 여러 과제로 다시 잰다. 단계 수가 비용을 좌우한 하네스 비교는 [[Harness-Component-Evaluation#모델을 바꾸면 하네스 순위도 다시 잰다|하네스 순위]]에, Carbon의 설정별 단계와 비용은 [[Gemini-4-Argon#Gemini 4 계열의 Carbon과 Hydrogen|Gemini 4 계열]]에 있다.

## 실제 위임에서는 완료 조건을 맞춘다

다음은 위 구분을 개발 업무에 적용한 측정 제안이다. 연구가 입증한 생산성 효과나 표준 지표는 아니다.

1. 맡길 일을 버그 수정, 요구사항 탐색, 설계 대안 비교처럼 나누고 성공 조건을 적는다.
2. 이미 정해진 요구를 찾아오는 작업과 이해관계자 사이에서 요구를 합의하는 작업을 분리한다.
3. 설명, 구현, 검토와 수정에 쓴 작업 시간을 기록한다. 승인이나 외부 의존성 때문에 기다린 시간은 별도로 남긴다.
4. 과업 크기, 난도와 품질 기준을 맞춰 비교한다. 완료 건수만으로 생산성을 판정하지 않는다.
5. 통과한 테스트와 실제 사용 흐름, 배포 뒤 결과를 구분한다. 위임 가능 범위는 관찰한 결과에 맞춰 조정한다.
