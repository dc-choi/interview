# 평가 주도 개발 (Evaluation-Driven Development)

감이 아니라 채점 점수로 개발 방향을 정하는 방식이다. 이 문서는 개발 프로세스로서의 EDD, 즉 만드는 축과 채점하는 축을 어떻게 나누고 어느 순서로 성숙시킬지를 다룬다. 무엇을 성공으로 볼 것인가라는 상위 철학은 [[LLM-Eval-Strategy]], 배포 전 자동 검증의 실행 4축은 [[Production-Agent-Architecture]], 채점 장치의 실물은 [[Eval-Rubric-and-Score-Gate]], 데이터셋과 배포 관문은 [[Eval-Golden-Set-and-Deploy-Gates]]가 맡는다.

## 왜 필요한가 - 소모하는 루프와 축적하는 루프

| 루프 | 흐름 | 한 바퀴 뒤에 남는 것 |
|---|---|---|
| 반응적 | 사용자 불만 → 수동 재현 → 급한 수정 → 새 실패 → 다시 불만 | 없다. 회귀인지 노이즈인지도 모른 채 반복한다 |
| 복리 | 실패 발견 → 테스트로 기록 → 회귀 방지 → 지표 축적 | 한 번 잡은 실패가 자산으로 남는다 |

검증 게이트가 없는 팀은 버그를 운영에서 발견하고 품질이 나빠진 것 같다는 논쟁을 반복한다. 진짜 위험은 틀렸다는 사실이 아니라 틀렸는지조차 모른다는 데 있다. 두 루프를 가르는 것은 실패가 기록으로 남는지 여부다.

## 게이트를 다 세워도 남는 세 구멍

하네스를 성실히 쌓아 통과와 실패 게이트까지 갖춰도 남는 것이 있다.

| 구멍 | 증상 | 메우는 장치 |
|---|---|---|
| 정도를 모른다 | 통과와 실패만 있고 몇 점인지는 없다 | 루브릭 점수와 합격선 |
| 추이를 모른다 | 지난주보다 나아졌는지 기록이 없다 | 고정된 문제 집합과 점수 기록 |
| 배포 후가 깜깜하다 | 배포 뒤 나빠져도 알아채지 못한다 | 배포 후에도 계속 채점 |

셋을 메운 층이 Evaluator다. AI 개발의 병목은 코드 생성보다 검증 쪽에 있다. 구현 완료라는 선언과 실제 사이의 간극이 문제이고, 점수와 추이와 감시가 생겨야 그 간극이 눈에 보인다.

## 두 축 - 만드는 축과 채점하는 축

| 축 | 흐름 |
|---|---|
| Generator | 기능 계획 → 구현 → 배포 |
| Evaluator | 문제 집합 → 채점기 → 게이트 |

두 축은 서로에게 피드백을 준다. 점수가 합격선에 못 미치면 배포가 막히고, 운영에서 터진 실패는 새 문항으로 바뀌어 문제 집합을 키운다. 문제 집합이 자랄수록 다음 배포가 안전해진다.

두 축은 분리해 두되 함께 키운다. 분리는 만든 쪽이 스스로 채점하지 않는다는 뜻이고, 함께 키운다는 것은 만드는 축이 빨라진 만큼 채점하는 축도 고도화해야 한다는 뜻이다. 축이 하나뿐인 팀이 반응적 루프에 빠진다. 만드는 속도만 늘고 확인하는 속도는 그대로이기 때문이다.

## Eval은 테스트와 무엇이 다른가

| 관점 | 결정론적 단위 테스트의 예 | 에이전트 Eval의 예 |
|---|---|---|
| 판정 | 맞다 또는 틀리다 | 통과율과 점수 분포 |
| 기준 | 코드가 정답을 안다. 기대값을 미리 적어 둔다 | 성공이란 무엇인가의 정의부터 만든다 |
| 대상 | 함수의 입력과 출력 | 모델과 컨텍스트와 도구와 규칙을 합친 시스템 전체 |

Eval도 테스트이며, 위 표는 배타적 분류가 아니다. 코드로 판정하는 검사와 모델 채점, 사람 검토를 조합할 수 있다. 비결정적 결과는 반복 실행으로 분포를 확인한다. 성공 기준과 Pass@k 논의는 [[LLM-Eval-Strategy]]를 따른다.

## 성숙도 계단

| 단계 | 상태 | 얻는 것 |
|---|---|---|
| Lv.0 | 감으로 확인하고 몇 개 돌려본 뒤 배포 | 없음 |
| Lv.1 | 고정된 문제 집합으로 채점 | 깨진 케이스가 보인다 |
| Lv.2 | 자동 채점 | 실험 속도가 오른다 |
| Lv.3 | CI 게이트 | 배포 전에 걸러진다 |
| Lv.4 | 배포 후 감시 | 성능 저하가 지표로 드러난다 |
| Lv.5 | 완전한 루프 | 실패가 자산으로 쌓인다 |

하네스 계단([[Harness-Adoption-Ladder]])을 올린 팀은 이 계단의 부품을 이미 상당 부분 갖고 있다. 두 사다리는 같이 오른다. Lv.0이라면 실패 사례를 스무 건쯤 모으는 것부터 시작한다.

성공 기준과 평가 문항은 구현 전에 정의할 수 있다. 실행 평가에는 모델과 도구를 구동할 환경이 필요하지만, 하네스 완성을 기다려 평가 설계를 시작할 필요는 없다.

## 하네스 부품의 승격

EDD 도입은 제로 구축이 아니라 이미 있는 부품의 업그레이드에 가깝다.

| 이미 만든 하네스 부품 | 승격 결과 | 무엇이 더해지나 |
|---|---|---|
| 검증 서브에이전트 (문제 있음과 없음만 판정) | LLM-as-Judge | 루브릭, 점수, 합격선, 사람과의 일치율 검증 |
| 계획 파일의 체크박스 (한 번 쓰고 버리는 대조표) | 골든셋 | 영속성. 실패가 새 문항으로 쌓인다 |
| 차단 훅 (이번 호출 하나를 결정적으로 차단) | 점수 기반 차단 | 배포 후에도 작동하는 재시도와 폴백 |
| 점검 커맨드 (사람이 불러야 실행) | CI 평가 게이트 | 자동 실행. PR마다 회귀를 검사 |

승격의 공통 원리는 하나다. 있던 부품에 점수와 영속성과 자동 실행을 부여한다.

## 무엇부터 채점할 것인가

실전 팀이 쓰는 채점 프레임은 세 질문이고, 순서가 곧 우선순위다.

1. **망가뜨리지 않았나.** 멀쩡하던 기능이 되돌아가지 않았는지. 회귀 확인이 첫째다.
2. **시킨 것을 했나.** 요구한 내용이 실제로 이행됐는지.
3. **잘했나.** 같은 결과라도 더 좋은 방식인지. 품질은 마지막에 다듬는다.

평가 도입 시점은 달라도 채점 기준과 실행 증거를 함께 다룰 수 있다. 2026년 1월 공개 사례에서 영상 편집 에이전트 Descript는 이 세 질문으로 평가를 설계하고 수동 채점에서 LLM 채점으로 옮기면서 주기적인 사람 교정을 유지했다. 웹 앱 빌더 Bolt는 서비스 운영 중 약 3개월에 걸쳐 정적 분석, 브라우저를 통한 앱 실행과 LLM 판정을 조합했다. 두 사례 모두 같은 도입 순서를 따라야 한다는 근거는 아니다.

## 응답, 실행 기록과 실제 결과를 대조한다

행동 주장 검증의 기본 원리는 [[LLM-Hallucination-Verification#행동 주장은 실행 기록으로만 인정한다|실행 기록 대조]]를 따른다. 여기서는 그 증거를 평가 문항과 회귀 검사에 연결한다.

에이전트의 완료 문장과 환경의 최종 상태는 다를 수 있다. 도구를 실행했다고 답해도 실제 호출이 없거나 실패했을 수 있다. 평가는 답변뿐 아니라 도구 호출, 인자와 반환값, 최종 산출물을 대조해야 한다. Anthropic의 평가 지침도 실행 기록과 환경의 결과를 구분한다(2026-10-08 확인).

예를 들어 정책 조회가 필수인 상담 평가라면 도구 호출 여부, 조회한 정책 버전과 답변의 일치를 함께 본다. 조회 호출이 존재한다는 사실만으로 정답을 보장하지 않는다. 반대로 특정 호출 순서가 요구사항이 아니라면 다른 유효한 해결 경로도 인정한다.

운영 적용 예시는 오류율과 만족도 외에 단계별 실패, 폴백, 지연과 토큰 사용량을 함께 보는 것이다. 낮은 점수의 실행 기록을 읽고 모델 오류와 채점기 오류를 구분한 뒤 회귀 문항으로 옮긴다. 요청 본문을 기록할 때는 민감정보 제거, 접근 권한과 보존 범위를 별도로 정한다.

## 자동 개선 후보도 별도 평가를 거친다

GEPA(Genetic-Pareto)는 실행 경로와 피드백을 자연어로 분석해 프롬프트 수정 후보를 만들고 평가하는 최적화 기법이다. 서로 다른 사례에서 강점을 가진 후보의 교훈을 결합한다. 단순히 프롬프트를 짧게 만드는 기법이나 전역 최적해를 보장하는 방법으로 해석하지 않는다.

이를 운영에 적용할 때는 수정에 사용한 문항과 릴리스 판정용 문항을 구분한다([[Eval-Golden-Set-and-Deploy-Gates#문항 구성과 홀드아웃|문항 구성과 홀드아웃]]). 개선안이 프롬프트, 도구 계약, 근거 문서 중 무엇을 바꾸는지도 남긴다. 후보 생성과 배포 승격을 분리하고 기존 버전과 같은 조건에서 정확도, 지연과 비용을 비교하는 것이 설계상 점검사항이다. 논문의 성능 수치를 개별 서비스의 개선율로 옮기지 않는다.

## 적용 범위

평가의 규모는 오류 비용과 반복 변경 빈도에 맞춘다. 프로토타입도 작은 성공 기준부터 둘 수 있으며, 정답이 하나가 아닌 작업은 근거와 제약 준수 같은 차원을 평가한다. 모든 변경에 큰 점수 체계를 도입할 필요는 없다.

## 면접 체크포인트

- 하네스의 통과와 실패 게이트만으로 남는 세 구멍과 Evaluator 층이 메우는 지점
- Generator와 Evaluator를 분리하되 함께 키워야 하는 이유
- Eval과 전통 테스트의 세 가지 차이, 특히 성공의 정의가 선행되는 이유
- 하네스 부품이 EDD 부품으로 승격될 때 더해지는 세 속성
- 채점 순서를 회귀, 이행, 품질로 두는 이유
