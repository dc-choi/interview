# LLM 애플리케이션의 세 간극과 분석, 측정, 개선 루프

LLM 애플리케이션이 실패할 때 원인을 세 간극(gulf)으로 나눠 진단하는 틀이다. 개발자와 데이터 사이의 이해 간극(Gulf of Comprehension), 개발자와 LLM 파이프라인 또는 에이전트 사이의 명세 간극(Gulf of Specification), 데이터와 LLM 사이의 일반화 간극(Gulf of Generalization)이다. 실패가 어느 간극에서 왔는지에 따라 고칠 대상(데이터를 더 볼지, 프롬프트를 고칠지, 실패 빈도를 재고 더 강한 개입을 할지)이 달라진다.

## 출처와 계보

이 틀은 Norman의 실행 간극과 평가 간극(gulfs of execution and evaluation)에서 착안해, 사용자, 데이터, LLM 파이프라인 세 주체의 쌍마다 간극을 둔 2025년 DocWrangler 논문(대량 비정형 문서를 LLM 파이프라인으로 처리하는 IDE 연구)에서 나왔다. 논문 제1저자 Shankar가 Husain과 함께 쓴 책 Evals for AI Engineers(O'Reilly)는 이를 일반 LLM 애플리케이션 개발에 맞게 고쳐 쓰고, 논문의 사용자를 개발자로, LLM 파이프라인을 LLM 에이전트로 부른다. 아래 책의 내용은 책 1장 발췌로 확인한 범위다.

| 간극 | 사이에 있는 것 | 드러나는 증상 | 논문의 대응 기능 |
|---|---|---|---|
| 이해 | 개발자와 데이터(입력과 출력) | 상상한 입력을 기준으로 설계했다. 실제 출력의 흔한 성공과 실패 유형을 모른다 | 문서와 출력 위에 바로 남기는 메모 |
| 명세 | 개발자의 의도와 실제로 LLM에 준 지시 | 형식, 상세도, 경계 사례 처리를 LLM이 추측하므로 실행마다 결과가 달라질 수 있다 | 메모를 바탕으로 한 LLM 보조 프롬프트 개선 |
| 일반화 | 데이터와 LLM | 지시가 명확해도 실제 입력의 다양성 앞에서 일부 입력에 실패한다 | 처리 단계를 쪼개자고 제안하는 LLM 보조 분해 |

## 세 간극의 동작

이메일을 받아 발신자 이름을 뽑고, 핵심 요청을 요약하고, 메일을 분류하는 에이전트로 보면 차이가 선명하다.

- **이해 간극**: 실제 메일에는 전달 메일, 긴 인용 스레드, 여러 언어의 서명, PDF에서 붙여 넣은 글이 섞인다. 이를 모르고 쓴 프롬프트는 인용된 옛 스레드를 요약하거나 서명을 본문 요청으로 착각한다. 출력 쪽에도 같은 간극이 있다. 출력을 전부 읽을 수는 없으므로 여러 이름이 나올 때 잘못 고르기, 긴 메일에서 세부 누락, 기밀 고지문 같은 상투 문구의 혼입처럼 흔한 실패 유형을 알아보는 능력이 필요하다.
- **명세 간극**: "발신자 이름을 뽑고 핵심 요청을 요약하라"에는 문단인지 목록인지, 표시 이름인지 주소인지, 암묵적 요청을 포함하는지, 얼마나 짧게 쓸지가 빠져 있다. 빠진 부분은 LLM이 추측하므로 두 번 실행한 결과의 형식과 상세도가 다를 수 있다.
- **일반화 간극**: 데이터를 잘 알고 지시가 명확해도 LLM은 가끔 본문에 언급된 유명인을 헤더의 발신자 대신 반환한다. 이런 오류는 대개 실제 데이터의 전체 다양성을 만나야 드러난다. 책은 이런 오류를 모델이 아무리 발전해도 피할 수 없다고 본다(틀린 출력을 내는 경우는 언제나 남는다).

같은 틀을 다른 도메인에 대면 다음과 같다.

| 사례 | 이해 | 명세 | 일반화 |
|---|---|---|---|
| 고객 지원 챗봇 | 여러 언어, 오타, 한 메시지에 여러 질문 | 좋은 응답의 정의. 사람 상담원에게 넘겨야 할 때 사과만 하는 봇은 잘못된 지시를 따르고 있는 것이다 | 결제 질문은 잘 답하지만 드문 제품별 질문에서 실패 |
| 코드 생성 도우미 | 모호한 요청, 불완전한 맥락, 문서 없는 내부 API | 출력 형식, 오류 처리와 코드 스타일 | Python은 맞지만 덜 쓰는 언어나 여러 파일 변경에서 실패 |

## 명세 실패와 일반화 실패를 가르는 질문

출력을 보다 실수를 찾으면 먼저 그 요구사항이 프롬프트나 에이전트 로직에 명시돼 있었는지 확인한다.

- 명시돼 있지 않았다: 명세 실패다. 지시나 에이전트 설계를 고친다.
- 명시돼 있었는데도 실패한다: 일반화 실패다. 자동 평가기로 발생 빈도를 잰다.
- 아직 실패 양상을 설명할 수 없다: 이해가 부족한 상태다. 무언가를 바꾸기 전에 trace를 더 읽는다.

이 구분은 팀이 같은 단어로 실패를 부르게 해 진단을 빠르게 한다. 명세가 모호한 상태에서 일반화 실패율을 재면 측정값이 프롬프트의 빈칸까지 섞어 세므로, 명세를 먼저 메운 뒤 측정하는 순서가 자연스럽다(이 문서의 해석).

## 분석, 측정, 개선 루프

책은 평가를 한 번의 검사가 아니라 Analyze-Measure-Improve의 반복으로 다룬다. 요구사항은 실제 출력과 상호작용한 뒤에야 분명해지기 때문이다.

| 단계 | 하는 일 | 주로 닿는 간극 | 이메일 예 |
|---|---|---|---|
| 분석(Analyze) | 실제 입력과 출력, 요청마다 에이전트가 한 일의 전체 기록(trace)을 읽고 실패 유형 목록을 만든다. 무엇이 정답인지는 사용자와 도메인 전문가에게 묻는다. 아직 수치화하지 않는다 | 이해 중심, 세 간극 모두 드러남 | 요약에 서명 문구가 섞이거나 가장 중요한 요청이 빠진다 |
| 측정(Measure) | 실패 유형마다 얼마나 자주 일어나는지, 그 비율이 쓸 만한 수준인지 잰다. 사람이 보지 않아도 trace를 채점하는 평가기를 코드 규칙이나 LLM 판정기로 만든다 | 일반화 | 상투 문구를 잡는 규칙 검사를 수천 건에 돌려 8%에서 발견 |
| 개선(Improve) | 원인에 맞춰 고친다. 명세 빈틈은 프롬프트와 에이전트 로직을, 일반화 실패는 예시 추가, 검색 개선, 라벨 데이터 미세조정 같은 더 강한 개입을 쓴다 | 명세, 일반화 | 요청 누락은 상세도 미지정 탓이라 "발신자의 요청을 짧은 글머리표 세 개로 요약하라"로 고친다. 명확한 지시에도 남는 이름 혼동은 라벨 데이터를 더하거나 본문 대신 메일 메타데이터에서 발신자를 뽑도록 설계를 바꾼다 |

몇 개의 trace에서 받은 인상은 실패를 과대평가하게도, 과소평가하게도 만든다. 측정 단계가 필요한 이유다. 마지막 예처럼 LLM이 계속 틀리는 일을 LLM에게 맡기지 않고 결정론적 경로로 옮기는 것도 일반화 실패의 해법이 될 수 있다(책의 예를 넓힌 이 문서의 해석).

## 분석을 시작하는 실무 기준

책의 두 저자가 공개한 평가 FAQ(2026-09-21 수정판)는 위 루프의 첫 단계를 다음처럼 구체화한다. 실무자의 권장이며 실증된 표준 수치는 아니다.

- **몇 개를 읽고 언제 멈추는가**: 다양한 실제 trace 100개쯤을 모아 적어도 처음 30개는 직접 주석을 단다. 새 trace가 새 실패 유형을 드러내지도 기존 유형을 바꾸지도 않는 지점(이론적 포화)에서 멈추고, 아직 배우는 중이면 100개를 넘겨 계속 읽는다.
- **첫 실패에 주석을 단다**: trace마다 자유 메모(open coding)를 남기되 앞 단계의 오류가 뒤 단계의 오류를 낳으므로 첫 실패에 집중한다. 메모를 실패 분류 체계로 묶고(axial coding) 범주마다 개수를 세면 가장 흔한 실패부터 평가기를 만들 순서가 정해진다. FAQ는 이 묶기를 가장 중요한 단계로 꼽는다.
- **실제 기록이 부족하면 차원으로 합성 입력을 만든다**: 구조 없이 테스트 질문을 만들게 하면 비슷한 문장만 반복된다. 먼저 사용자 질문을 가르는 차원(예: 식단 제약, 요리 종류, 질의 복잡도)을 정하고 차원 값의 조합(튜플) 20개쯤을 손으로 쓴 뒤, 튜플을 늘리는 생성과 튜플을 자연어 질문으로 바꾸는 생성을 다른 프롬프트로 나눈다. 대부분의 조합이 말이 되면 곱집합을 만든 뒤 거르고, 말이 안 되는 조합이 많으면 LLM이 조합을 직접 제안하게 한다. 맡겨 둔 합성은 모델의 기본 답으로 쏠리기 쉽다([[LLM-Default-Answer-Convergence#지어낸 값은 평가 데이터와 세상으로 퍼진다|지어낸 값의 쏠림]]).
- **코드로 잡을 수 있는 실패는 코드로 잡는다**: 객관적 규칙으로 판정되는 실패는 정규식, 구조 검증, 실행 테스트 같은 코드 검사로 먼저 잡고, 판단이 필요한 실패에만 사람 라벨로 검증한 LLM 판정기를 쓴다([[Eval-Rubric-and-Score-Gate|루브릭과 점수 게이트]], [[Eval-LLM-Judge|LLM 판정기]]).
- **RAG는 검색부터 따로 고친다**: 검색은 Recall@k, Precision@k, MRR 같은 정보 검색 지표로 먼저 디버깅하고, 그다음 검색 결과를 쓰는 생성 품질을 검증한 판정기로 본다([[RAG-Retrieval-Engineering#품질을 분해하는 평가 모델|RAG 품질 분해]]).
- **에이전트는 최종 성공 다음에 단계를 본다**: 먼저 과제마다 정한 성공 규칙으로 사용자의 목표를 이뤘는지 판정하고, 이어 도구 선택, 인자 추출, 오류 처리, 문맥 유지와 효율(단계 수, 시간, 토큰)을 본다. 도구 호출은 이름, 인자, 결과와 그 결과로 바뀐 상태를 따로 검사한다. 행을 마지막 성공 상태, 열을 첫 실패가 난 단계로 둔 전이 실패 행렬을 만들면 어디서 먼저 깨지는지 보인다(FAQ의 예에서는 SQL 생성에서 실행으로 넘어가는 칸이 12건으로, 도구 결정에서 일정 계획으로 넘어가는 칸의 2건보다 먼저 볼 곳이었다). 실행 기록과 최종 결과의 대조는 [[Evaluation-Driven-Development#응답, 실행 기록과 실제 결과를 대조한다|평가 주도 개발]]을 따른다.
- **대화 상태 버그는 대화로 재현한다**: 실패가 대화 문맥에 기댈 때만 여러 턴 테스트를 쓰고, 실제 대화의 앞부분을 그대로 재생하는 N-1 테스트로 재현한다.
- **평가 세트가 바뀌면 점수의 기준도 바뀐다**: 오류 분석으로 문항과 참조 답을 갱신하면 이전 점수와 바로 비교할 수 없으므로 세트의 판을 함께 기록한다([[Eval-Golden-Set-and-Deploy-Gates#데이터셋을 확장하면 기존 점수와 새 점수를 분리한다|기존 점수와 새 점수의 분리]]).

## 사용자가 간극을 얼마나 메울 수 있는가

책은 애플리케이션마다 사용자가 스스로 간극을 메울 수 있는 정도가 다르다고 본다.

- 코딩 도우미의 사용자인 프로그래머는 agency가 높다고 가정해 볼 수 있다. 요구를 정확히 말할 줄 알고, 생성된 코드를 읽고 디버깅할 수 있으며, 테스트로 일반화 실패를 드러낼 수 있다.
- LLM 개인 스타일리스트의 사용자는 요구를 분명히 말하지 못할 수 있다(앱이 날씨나 격식을 되물어야 할 수 있다). 겨울 평상복 추천이 좋았다고 겨울 결혼식 추천도 좋다는 보장이 없는데 사용자는 그 실패를 알아차리기 어렵다.

사용자가 실수를 잡기 어렵거나 오류의 비용이 큰 애플리케이션일수록 간극을 메우는 절차를 더 엄격하게 설계한다.

## 적용 체크포인트

- 실패를 고치기 전에 이해, 명세, 일반화 중 어디에 속하는지 이름을 붙였는가
- 프롬프트를 고치기 전에 실제 입력의 변형(인용, 서명, 다국어 등)을 trace로 확인했는가
- 일반화 실패를 인상이 아니라 실패 유형별 빈도로 쟀는가
- 반복 실패를 프롬프트 대신 메타데이터 같은 결정론적 경로로 옮길 수 있는가
- 사용자가 스스로 실패를 알아챌 수 있는 제품인지에 따라 평가 강도를 정했는가
