# 루브릭과 점수 게이트 (Eval Rubric and Score Gate)

채점을 숫자로 남기고 그 숫자로 다음 단계를 막는 장치를 다룬다. 왜 점수가 필요한지는 [[Evaluation-Driven-Development]], 무엇을 성공으로 볼 것인지는 [[LLM-Eval-Strategy]], 채점에 쓸 문제 집합과 배포 관문은 [[Eval-Golden-Set-and-Deploy-Gates]]가 맡는다.

## 채점기는 세 종류

| 종류 | 채점 방식 | 강점 | 약점 |
|---|---|---|---|
| 코드형 | 정규식, 테스트, 정적 분석 | 빠르고 싸고 재현 가능 | 표현이 조금만 달라져도 놓친다 |
| 모델형 (LLM-as-Judge) | 별도 모델이 루브릭으로 점수를 매긴다 | 뉘앙스를 잡는다 | 결과가 흔들리고 비싸며 사람과 맞춰봐야 한다 |
| 사람형 | 전문가 검토와 표본 확인 | 가장 정확하고 정답지 품질을 만든다 | 비싸고 느려 소량만 가능 |

조합 원칙은 하나다. 가능하면 코드로, 필요하면 모델로, 검증에는 사람을 쓴다. 셋은 대체재가 아니라 조합이다.

## 게이트는 3층

| 층 | 검사 | 통과하지 못하면 |
|---|---|---|
| 결정론 | 컴파일, 테스트, 린트 | 그 자리에서 정지 |
| 모델 채점 | 루브릭 점수가 기준 미만 | 반려 |
| 사람 | 애매한 것과 새 유형만 | 좁은 출구 |

첫 층은 언제나 결정론 게이트다. 빠르고 싸고 흔들리지 않기 때문이다. 결정론이 못 재는 것(뉘앙스, 설계 품질, 문서 톤)만 모델이 재고, 그래도 애매한 것만 사람에게 올린다. 채점기를 배치하는 순서가 곧 비용 구조다.

합격 임계값은 항목 유형별로 다르게 둔다. 발표가 제시한 예는 규약 위반 5%, 정합성 3%, 도메인 안전 0%의 허용 실패율이다. 안전 불변식 위반은 한 건도 통과시키지 않는다는 뜻이다. 구체적인 수치는 도메인마다 다시 정한다.

## 규칙을 결정론 검사로 번역하기

팀 관례를 문장으로 두는 대신 자동 실행되는 검사로 옮기면 사람이 안 봐도 걸린다.

| 팀 규칙 (사람의 문장) | 결정론 검사 (자동 실행) |
|---|---|
| 빌드가 깨지지 않는다 | 컴파일과 전체 테스트 자동 실행 |
| 코드 스타일 통일 | 린터 자동 실행 |
| 화면 계층에서 DB 객체 직접 반환 금지 | 구조 검사 도구가 반환 타입을 확인 |
| 무거운 호출은 응답 경로에서 금지 | 금지 패턴 검색으로 확인 |
| 과거 마이그레이션 파일 수정 금지 | CI가 기존 파일 변경을 감지하면 실패 |

AST 기반 아키텍처 테스트로 의존 방향까지 강제하는 형태는 [[AI-Native-System]]을 본다.

## 루브릭 실물 1 - 산출물 품질

배점이 곧 정책이다. 아래는 100점 만점 구성의 예이고 합격선은 팀이 정한다.

| # | 항목 | 배점 | 점수 규칙 |
|---|---|---|---|
| G1 | 빌드와 타입체크 | 25 | 성공 25, 실패 0 |
| G2 | 테스트 통과 | 25 | 전체 성공 25, 실패 0 |
| G3 | 안전 위반 0건 | 15 | 0건 15, 1건이라도 0 |
| 4 | 린트 | 10 | 통과 10, 실패 0 |
| 5 | 회귀 없음 | 10 | 기존 테스트 전부 유지 10, 하나라도 깨지면 0 |
| 6 | 커버리지 | 5 | 유지나 상승 5, 하락 0 |
| 7 | 디자인 규칙 | 10 | 검사 도구 오류 0건 10, 1건 이상 0 |

7번 디자인 규칙은 정확성과 별개로 구조와 표현 품질이 미끄러지는 것을 잡는 자리다. 같은 문제를 관문 단위로 다루는 논의는 [[AI-Slop-Quality-Gate]]에 있다.

G1에서 G3은 거부권을 가진다. 하나라도 0점이면 나머지가 만점이어도 실패다. 총점은 그다음 이야기다. 모든 항목이 명령어 실행 결과로 판정되므로 좋은 결과라는 주관이 개입할 자리가 없다. 이렇게 나온 점수가 이후 변경을 비교할 베이스라인이 된다.

## 루브릭 실물 2 - 구현 주장 검증

구현했다는 주장을 검증하는 용도의 루브릭은 항목이 다르다. 코드 리뷰어가 늘 하던 질문에 점수를 붙인 것에 가깝다.

| # | 질문 | 배점 | 무엇을 보나 |
|---|---|---|---|
| 1 | 진짜 있나 | 25 | 껍데기나 TODO뿐이면 0점 |
| 2 | 말과 같나 | 25 | 구현했다는 주장과 코드를 대조 |
| 3 | 돌려봤나 | 25 | 검증 명령을 실제로 실행해 통과 |
| 4 | 안전한가 | 15 | 에러 처리, 입력 검증, 권한 경계 |
| 5 | 깨뜨렸나 | 10 | 기존 기능이 되돌아가지 않았는지 |

배점 설계의 의도가 드러나는 지점이 3번이다. 돌려보지 않은 코드는 구조적으로 높은 점수를 받을 수 없다. 각 항목은 따로 두 번 채점해 낮은 점수만 인정하는데, 후한 채점 한 번이 통과를 만들지 못하게 하려는 낙관 편향 차단 장치다.

## 미달 항목만 다시 도는 루프

1. 개발이 끝났다고 주장한다.
2. 만든 쪽과 분리된 채점기가 주장을 전부 목록으로 만들어 코드와 대조하고 점수를 매긴다.
3. 전 항목이 합격선 이상이면 통과하고, 사람은 루프 밖에서 결과만 확인한다.
4. 미달이면 부족한 항목만 다시 개발한다. 통과한 항목은 건드리지 않는다.
5. 2번으로 돌아가 재채점한다.

전체 재생성이 아니라 미달만 고치므로 빠르고, 이미 통과한 것을 망가뜨리지 않는다. 합격선 아래는 전부 같은 미달이다. 거의 됐다는 구간을 인정하지 않는 것이 이 게이트의 요점이다.

발표의 예제는 쿠폰 적용 API를 채점 항목 넷, 합격선 95로 돌린 것이다.

| 채점 항목 | 1회차 | 2회차 |
|---|---|---|
| 쿠폰이 적용되나 | 97 | 유지 |
| 중복 사용을 막나 | 70 | 96 |
| 만료를 검사하나 | 92 | 97 |
| 응답 형식이 맞나 | 100 | 유지 |

읽을 점이 둘이다. 테스트가 없던 항목이 70점으로 크게 깎였다. 배점이 곧 정책이라는 말의 실물이다. 그리고 92점도 차단이다. 미달 두 항목만 지목해 다시 돌리자 2회차에 전부 합격선을 넘었고, 이미 통과한 둘은 손대지 않았다.

무한정 돌게 두면 안 되므로 안전장치 셋이 함께 간다.

- **반복 상한**: 정한 바퀴 수 안에 수렴하지 못하면 멈추고 사람을 부른다.
- **교착 감지**: 같은 오류가 정해진 횟수 반복되면 즉시 멈추고 보고한다.
- **역할 분리**: 채점하는 쪽에 수정 권한을 주지 않는다. 끝까지 분리를 유지한다.

루프의 기억은 대화가 아니라 파일에 둔다. 확인할 항목 목록, 항목별 현재 점수, 바퀴마다 남는 채점 리포트를 파일로 남기면 세션이 끊겨도 다음 바퀴가 이어진다. 루프 가드 일반론은 [[Agent-Loop-Engineering]]의 3종 가드와 같은 결이다.

## 거짓 완료를 막는 Stop 게이트

다 됐다는 선언은 도구 호출이 아니라 응답 종료라서 `PreToolUse`로는 잡히지 않는다. Claude Code 공식 문서 기준으로 `Stop` 이벤트는 차단 가능한 이벤트이고, exit 2를 반환하면 종료를 막고 대화를 계속시키며 stderr가 차단 사유로 전달된다. 이를 이용하면 점수 파일을 읽어 합격선 미달일 때 완료 선언 자체를 막을 수 있다.

| 훅 판정 | 결과 |
|---|---|
| 전 항목 합격 | exit 0. 종료를 허용한다 |
| 미달 항목 있음 | exit 2. 사유가 모델에 전달되고 수정이 이어진다 |
| 점수 파일이 깨짐 | exit 2. 확인할 수 없으면 막는다 |

세 번째 줄이 fail-closed 원칙이다. 확인 불가를 통과가 아니라 차단의 기본값으로 둔다. 새 장치를 만든 것이 아니라 기존 차단 훅의 검사 조건만 바꿔 끼운 것이다. 금지 패턴이 보이면 차단하던 자리에 점수가 미달이면 차단을 넣었다.

재진입을 다루는 장치는 둘로 나눠 본다. 공식 문서의 `stop_hook_active`는 **Stop 훅 때문에 Claude Code가 이미 대화를 이어가는 중일 때** `true`가 되는 불리언이다. 차단으로 이어질 때뿐 아니라 `additionalContext`로 피드백을 주어 대화가 이어질 때도 같은 보호 장치가 적용된다. 해소되지 않을 조건으로 계속 막는 것을 피하라고 이 값을 확인하게 한다. 또한 공식 문서는 연속 8회 차단에 이르면 Claude Code가 훅을 무시하고 턴을 끝낸다고 밝힌다. 따라서 재시도 상한은 이 내장 한도와 별개로 자체 카운터 파일을 두어 그보다 앞에서 걸리게 잡고, 상한에 닿으면 exit 0으로 풀어 사람에게 넘긴다. 또한 이 게이트는 평가 루프를 켠 작업에서만 의미가 있고, 점수 파일을 쓰지 않는 일반 세션에는 개입하지 않도록 조건을 좁혀 둔다. 훅 이벤트별 동작의 정본은 [[Claude-Code-Extension-Reference]]다.

## 점수가 이상할 때 - 의심하는 순서

통과율이 갑자기 떨어지거나 이상하게 높으면 에이전트를 의심하는 것은 맨 마지막이다.

1. **채점기부터 의심한다.** 채점기가 제대로 동작하지 않아 0점 처리된 케이스가 있는지 본다. 발표 사례에서는 채점기를 고치자 통과율이 42%에서 95%로 올랐다.
2. **그다음 문항을 의심한다.** 지시를 따른 모델이 벌점을 받고 무시한 모델이 만점을 받으면 명세가 모순이다. 그런 문항은 고치거나 버린다.
3. **에이전트는 마지막이다.** 앞의 둘이 아닐 때만, 실제 대화와 실행 기록을 직접 읽고 나서 판단한다.

극단값 자체가 경보다. 전원 0%는 채점 환경이 깨졌다는 신호이고, 전원 100%는 문제가 너무 쉬워졌다는 신호다. 둘 다 문항을 손볼 때다. 기록을 직접 읽기 전까지 점수를 액면 그대로 믿지 않는 것이 규율이고, 무엇을 왜 틀렸는지 기록만으로 설명될 때 공정한 판정이 된다.

## 면접 체크포인트

- 채점기 세 종류의 강약과 조합 순서, 그리고 그 순서가 곧 비용 구조인 이유
- 게이트 항목에 거부권을 주는 설계와 총점만 보는 설계의 차이
- 이중 채점에서 낮은 점수만 인정하는 이유
- 완료 선언을 `Stop` 이벤트에서 막아야 하는 이유와 fail-closed 기본값
- 점수가 이상할 때 채점기, 문항, 에이전트 순으로 의심하는 이유
