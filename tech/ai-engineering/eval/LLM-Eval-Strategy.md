# LLM 평가 전략 (LLM Eval Strategy)

LLM, 에이전트 시스템은 같은 입력에도 출력이 흔들린다. 결정론적 소프트웨어처럼 성능을 한 점에 고정하는 건 사실상 불가능하고, 어려운 시나리오일수록 더 그렇다. 그래서 평가는 통과/실패 한 줄이 아니라, 분산을 전제로 한 설계 문제가 된다.

## 성능은 고정되지 않는다

배포 때 통과한 케이스가 다음 호출에서 깨질 수 있다. 비결정성을 없애려 애쓰기보다, 분산을 측정하고 허용 범위를 정하는 쪽이 현실적이다. 사용자가 한 번의 답만 받는 경로에서는 Pass@1이 기본 품질이고, 여러 후보를 실제로 생성하고 검증해 하나를 선택하는 경로에서는 그 선택 절차를 포함한 성공률도 측정해야 한다.

## Pass@k: k개 후보 안에 정답이 존재할 가능성

코드 생성 평가에서 Pass@1은 한 번 생성한 후보가 테스트를 통과할 비율이고, Pass@k는 k개 후보 중 테스트를 통과하는 후보가 하나 이상 있을 확률이다. 원래 지표는 테스트라는 oracle이 모든 후보를 판정할 수 있다는 전제를 둔다. 따라서 Pass@k가 높아도 운영 시스템에 합격 후보를 찾는 검증기와 선택 절차가 없으면 사용자가 받는 답의 신뢰도를 뜻하지 않는다.

- 사용자가 한 답만 받으면 Pass@1과 실제 전달 답의 합격률을 기준선으로 둔다
- k개 후보를 생성한다면 자동 테스트, 규칙 기반 검증이나 신뢰할 수 있는 grader로 후보를 판정하고 선택 비용을 함께 측정한다
- 재시도와 워커 교체는 Pass@k 자체가 아니라 실제 복구 정책의 성공률, 지연과 비용으로 별도 평가한다

이는 [[Production-Agent-Architecture]]의 고가용성(워커 풀 교체), Closure-loop과 같은 사고다. 한 번에 맞히게 만들기보다, 틀려도 루프 안에서 회복하게 만든다.

## Multi-gate 데이터 품질

학습, 지식 베이스에 들어가는 데이터는 다단계 게이트로 거른다. 한 번의 자동 필터로는 노이즈가 새기 때문이다.

1. 노이즈 제거 — 유저 질문, 응답을 다른 유사 상담과 비교해 이상치, 오류 응답을 걸러냄
2. 인간 검토 승인 — 지식 수정, 추가 제안을 사람이 직접 검토하고 승인 (자동 반영 금지)
3. Precision 우선 — 재현율보다 정밀도를 최대화. 틀린 지식이 들어가는 것보다 일부 누락이 낫다

잘못된 지식 한 줄이 이후 모든 답변을 오염시키므로, 추가는 보수적으로, 검증은 인간이 게이트한다. [[Production-Agent-Architecture]]의 Auto Memory 비활성화(명시적, 검증된 정의만 인정)와 같은 원칙.

## 지표 충돌: CSAT vs 사실 정확도

평가 지표는 종종 서로 충돌한다. 대표적으로 고객 만족도(CSAT)와 사실 정확도다.

- 규정대로 환불 불가를 정확히 안내하면 사실 정확도는 100점이지만 CSAT는 낮다
- 반대로 고객을 달래려 부정확하게 가능하다고 답하면 CSAT는 오르지만 사실이 틀린다

해법은 하나의 절대 기준을 강제하는 게 아니라, 상황별로 우선순위를 유연하게 조정하는 것이다. 규정, 금전, 법적 리스크가 걸린 답변은 정확도 우선, 단순 안내, 응대 톤은 만족도 우선으로 분기한다. 단일 지표 최적화는 다른 축을 망가뜨린다.

## 평가는 좋은 답변의 정의에서 시작한다

좋은 프롬프트를 만들려면 먼저 **무엇이 좋은 답변인지** 정의해야 하고, 그 정의가 곧 평가 기준이 된다. 프롬프트와 평가는 분리할 수 없다. 좋은 답변의 기준은 도메인마다 다르다 — 글쓰기 서비스의 좋은 답변과 데이터 분석 서비스의 좋은 답변은 다르므로, **평가 기준은 도메인 전문가와 함께** 만든다.

- **LLM-as-Judge**: LLM이 생성한 답변을 다시 LLM으로 평가하는 방식. 비용 효율적이지만 평가 프롬프트와 기준 설계가 품질을 좌우한다(근거 충분성 이중 검증은 [[LLM-Abstention]], 판정 방식과 편향, 사람 라벨 교정은 [[Eval-LLM-Judge]]).
- **평가 프레임워크(G-Eval, RAGAS 등)**: 참고하되 그대로 적용하지 않는다. 서비스 목적에 맞게 지표와 프롬프트를 조정해야 의미가 있다. RAGAS는 RAG 파이프라인(검색 적합성, 답변 충실도 등) 측정에 특화된다.

## 평가 인식과 운영 환경의 차이

평가 인식(evaluation awareness)은 모델이 상황을 테스트로 추정하는 현상이다. 평가를 눈치챈 뒤 행동이 달라지면, 테스트에서 관찰한 행동을 실제 운영에 그대로 일반화하기 어렵다. 모든 모델이 매번 평가를 알아차린다거나 의도적으로 속인다는 뜻은 아니다.

Claude Sonnet 4.5의 2025년 안전성 평가에서는 특히 인위적이거나 극단적인 시나리오에서 이런 현상이 관찰됐다. 비현실적인 시나리오를 거르는 필터는 평가를 개선하는 수단이지만 운영 행동과의 일치를 보장하지 않는다(2026-10-07 Anthropic Transparency Hub 대조).

에이전트 평가에 적용할 점검 제안은 다음과 같다.

- 파일명, 작업 설명과 도구 응답에 실제 운영에는 없는 테스트 단서가 섞였는지 확인한다.
- 최종 답뿐 아니라 실제 파일 읽기, 도구 호출과 실행 결과를 확인한다. 확인했다는 문장과 확인 동작을 구분한다.
- 단서를 줄인 조건에서도 같은 과제를 반복하고, 모델 버전과 환경별 행동 차이를 기록한다. 디렉터리 이름만 바꾸는 것으로 평가 인식이 해소됐다고 판단하지 않는다.

이는 평가 설계의 보완책이다. 특정 코딩 에이전트의 환각 원인이 평가 인식이었다고 확정하거나, 기존 평가를 전부 무효화하는 근거가 아니다.

## 시각 검수: 정밀도, 누락과 전체 처리 시간을 나눈다

이미지에서 필요한 부품이 보인다는 판정과 설비가 정상 동작한다는 판정은 다르다. 검수 자동화의 성공 조건은 객체 검출뿐 아니라 실제로 넘겨받을 업무 단계까지 정해야 한다.

2026-02-10 공개된 Amazon의 IORA 사례는 대표 테스트 모듈에서 정밀도 92%, 이미지당 지연 2~5초와 전체 ORT 시간 60% 감소를 보고했다. 이는 해당 팀의 사례 수치이며 독립 재현 결과나 다른 현장의 기대 성능이 아니다. 정밀도를 전체 정확도나 재현율로 바꿔 읽지 않고, 이미지 한 장의 처리 지연을 현장 검수 전체 시간과 구분한다. ORT에는 설치 확인 외에 전원과 연결 등의 기능 시험도 포함된다.

이 사례를 적용할 때의 평가 제안은 다음과 같다.

- **거짓 통과와 누락**: 없는 부품을 있다고 판정한 비율과 실제 부품을 놓친 비율을 따로 본다. 검출되지 않은 항목을 곧바로 부재로 확정하지 않는다.
- **입력 조건**: 조명, 촬영 각도와 이미지 안의 부품 수로 결과를 나눠 본다. 특정 사례의 부품 수 임계값을 모델의 보편 한도로 사용하지 않는다.
- **업무 시간**: 촬영, 업로드, 추론, 사람 재검토와 기능 시험을 포함해 전체 소요 시간을 비교한다. 자동 통과 비율과 재작업도 함께 기록한다.
- **정답 수정**: 모델이 기존 라벨의 누락을 제기하면 원본을 사람이 재검토한다. 모델의 이의를 검증 없이 정답으로 반영하지 않는다.

## 평가 축 정리

| 관점 | 질문 | 비고 |
|---|---|---|
| Pass@1 | 사용자가 한 번에 받는 답의 합격률이 기준선 이상인가 | 단일 결과 경로의 기본 지표 |
| Pass@k | k개 후보 안에 합격 후보가 존재하는가 | oracle과 후보 선택 절차 필요 |
| 정확성 | 수치, 사실이 맞는가 | CSAT와 충돌 가능 |
| 만족도(CSAT) | 사용자가 만족했는가 | 정확도와 충돌 가능 |
| 데이터 품질 | 지식 베이스에 노이즈가 없는가 | Precision 우선, 인간 게이트 |

배포 전 자동 검증의 실행 축(정확성, 행동 경로, 안정성, 형식)은 [[Production-Agent-Architecture#Eval 시스템과 운영 루프]] 참고. 본 문서는 그보다 상위의 평가 철학(무엇을 성공으로 볼 것인가)을 다룬다.

## 면접 포인트

Q. LLM 시스템 성능을 어떻게 평가하나?
- 단일 결과 경로는 Pass@1을 보고, 여러 후보를 생성해 검증할 수 있는 경로는 Pass@k와 실제 선택 성공률을 함께 본다. 평균뿐 아니라 분산, 지연과 비용도 서비스 기준선과 비교한다.

Q. 정확하기만 하면 좋은 답변인가?
- 아니다. 사실 정확도와 CSAT는 충돌한다. 규정대로 환불 불가를 안내하면 정확하지만 만족도는 낮다. 상황별 우선순위로 분기한다.

Q. 데이터 품질은 어떻게 지키나?
- 다단계 게이트. 노이즈 제거 후 인간이 검토 승인하고, 재현율보다 Precision을 우선한다. 틀린 지식 한 줄이 전체를 오염시키기 때문이다.
