# 운영 에이전트의 피드백 기반 평가와 리플레이

운영 중인 LLM 에이전트는 운영자가 남긴 판단을 정답으로 삼아 계속 평가한다. 평가는 두 갈래로 나눈다. 과거 결과를 그때 기준으로 채점하는 현황 집계, 그리고 과거 입력을 현재 코드로 다시 실행해 현재 기준으로 채점하는 리플레이다. 알람마다 장애 심각도와 원인을 1분 안에 판정해 리포트를 남기는 장애 진단 에이전트가 대표 사례다. 같은 구조는 비결정적 결과를 내는 다른 운영 에이전트에도 쓸 수 있다.

평가 일반의 설계와 골든셋은 [[LLM-Eval-Strategy|LLM 평가 전략]]과 [[Eval-Golden-Set-and-Deploy-Gates|골든셋과 배포 관문]]에서 다룬다. 이 문서는 운영 피드백으로 정답을 모으고 시점이 다른 결과를 해석하는 방법을 다룬다.

## 코드처럼 테스트할 수 없는 이유

| 성질 | 생기는 문제 |
| --- | --- |
| 프롬프트 수정은 모든 입력에 적용된다 | 사례 A를 고친 수정이 잘 되던 사례 C를 깨도, 과거 사례를 다시 돌리지 않으면 모른다 |
| 모델은 직접 만들지 않은 부품인데 계속 바뀐다 | 다음 달 판단이 좋아져도 우리 개선 때문인지 모델 교체 때문인지 가를 수 없다. 들어오는 알람 구성에 따라서도 정확도가 달라진다 |
| 같은 입력에도 답이 달라진다 | 같은 알람의 원인을 한 번은 외부 장애로, 한 번은 배포로 판정한다. 첫 실행이 우연히 맞으면 더 고치지 않는다 |
| 답이 자연어라 통과와 실패로 세기 어렵다 | 사람 눈에 띈 이상한 리포트만 고치게 되고, 어느 영역이 약한지 모른다 |

정확도가 낮은 상태가 이어지면 리포트를 받는 사람이 결과를 믿지 않고 노이즈처럼 무시하게 된다. 그래서 한 번의 평가가 아니라 계속 돌아가는 평가가 필요하다. 무시되는 알림의 비용은 [[Alert-Fatigue|알림 피로]]에서 다룬다.

## 정답의 기준부터 세운다

정답이 있어야 채점할 수 있고, 정답은 기준이 있어야 생긴다. 사람이 헷갈리는 판단은 에이전트도 헷갈리므로 기준의 모호함을 먼저 없앤다.

- **상태의 뜻을 나눈다.** 심각도를 장애, 진행 중, 해소로 두면 진행 중이 모호하다. 분석 시점에 에이전트가 보는 지표는 정점을 지나 내려오는 중간까지라 이후 해소될지 다시 오를지 모른다. 진행 중은 아직 평소로 돌아오지 않은 상태로, 정점을 지나 내려오는 상태는 회복 중으로 따로 표기한다.
- **확정 단계를 더한다.** 진행 중으로 판정한 알람을 사람이 열어 보면 20~30%는 이미 해소돼 있었다. 사람이 바로 확인하기 어려운 야간과 주말에는 진행 중 판정 뒤 60초 후 한 번 더 분석해 확정한다.
- **위치와 원인을 다른 축으로 둔다.** 원인 카테고리를 하위 시스템 장애, 외부 서비스 이슈, 비정상 트래픽, 배포로 두면 비정상 트래픽 때문에 하위 시스템이 느려진 알람이 두 곳에 걸린다. 장애가 난 위치와 장애를 일으킨 원인을 별도 축으로 나누면 두 알람 모두 위치는 하위 시스템, 원인은 각각 비정상 트래픽과 배포로 하나씩 정해진다.

## 운영 피드백을 정답으로 쓴다

리포트를 본 담당자가 이슈에 자연어 댓글로 틀린 점을 고치거나 맞다고 확인하거나 빠진 내용을 적는다. 판정 단계가 이 댓글과 에이전트 출력을 항목별로 비교해 케이스마다 정답 기록(기대값, 실제값, 해설)을 만든다. 따로 라벨링하지 않고 운영에서 사람이 남긴 말이 그대로 정답이 된다.

정답 기록은 두 도구가 쓴다.

- **현황판**: 알람 한 건을 한 칸으로 두고 에이전트 판정, 사람이 정정한 판정, 둘의 일치 여부를 나란히 그린다. 사람이 아직 보지 않은 알람은 비운다. 기간을 바꿔 다시 집계하고, 서브 에이전트별과 원인 카테고리별 정확도를 본다.
- **리플레이**: 정답이 확정된 알람을 현재 코드로 다시 돌려 고친 것이 제대로 고쳐졌는지, 회귀는 없는지 확인한다.

카테고리별 정확도는 리포트가 말한 원인이 아니라 사람이 확인한 원인으로 묶는다. 리포트 기준으로 묶으면 틀린 케이스가 엉뚱한 카테고리에 들어가 진짜 약점이 숨는다. 원인이 배포인데 하위 시스템 장애로 판정했다면 배포 쪽의 오답으로 센다.

## 시점을 맞춰 다시 실행한다

평가 시스템이 답해야 할 질문은 셋이다. 지금 정답률은 얼마인가, 틀려서 고쳤다는데 정말 맞는가, 저절로 해결된 것은 무엇인가. 셋 모두 어느 시점의 기준과 어느 시점의 코드로 보느냐에 따라 답이 달라진다.

| 구분 | 대상 | 기준 |
| --- | --- | --- |
| 현황 평가 | 과거 리포트 | 알람이 울린 시점의 기준 |
| 리플레이 | 과거 알람을 현재 코드로 다시 실행한 결과 | 현재 기준 |

리플레이는 다음 규칙으로 돌린다.

- 분석이 보는 데이터의 시각을 알람 시점으로 되돌린다. 어제 15시 알람을 오늘 10시에 다시 돌려도 어제 15시 데이터를 본다. 옛 데이터가 없으면 재현 불가로 따로 둔다.
- 비결정성 때문에 같은 케이스를 3~5번 돌리고, 답이 흔들리면 틀림으로 본다. 네트워크 실패 같은 실행 환경 차이도 있으므로 재시도 상한을 둔다.
- 값으로 비교할 수 있는 항목은 코드가 채점하고, 근거와 요약처럼 정답이 하나가 아닌 항목은 LLM judge에 맡긴다.
- 케이스마다 상태를 둔다. 과거에 맞았고 지금도 맞아야 하면 회귀, 과거에 틀렸던 것이 지금 해결됐는지 보면 개선, 규칙이 바뀌어 답이 달라져야 하면 진화다.

정답과 다른 결과는 바로 실패로 두지 않는다. 같아야 하는 케이스가 달라졌으면 회귀 실패다. 달라진 값이 개선이나 진화일 수 있으면 코드, PR과 결정 기록에서 바뀐 이유를 찾고, 이유가 분명하면 정당한 변화로 본다. 근거가 없으면 사람에게 확인을 넘긴다. 깨진 테스트를 스스로 고치는 Playwright의 healer 에이전트와 같은 판단 방식이다.

리플레이 대상은 매주 생기는 리포트와 장기 확인용 골든셋을 함께 쓴다. 매주 쌓이는 리포트를 모두 남기면 실행 시간이 계속 늘므로 3주 연속 통과한 케이스는 졸업시키고, 골든셋은 매번 포함한다. 대상 풀이 커지면 연속 통과하지 못한 케이스가 있거나 특정 주에 이슈가 몰린 것이고, 골든셋이 커지면 꼭 봐야 할 지점이 늘어난 것으로 읽는다.

## 기준은 그 시점에 적절했던 동작으로 둔다

처음에는 에이전트가 지향하는 이상적인 동작을 기준으로 채점해 로드맵에 얼마나 가까워졌는지 보려 했다. 운영하면서 세 가지 문제가 생겼다.

- 로드맵이 바뀌면 과거 판정이 모두 흔들려 전부 다시 검수해야 한다.
- 외부 시스템의 개선을 기다려야 하는 항목은 계속 틀림으로 남아 낮은 지표에 무감각해진다.
- 서브 에이전트와 필드가 늘거나 줄 때마다 이상 기준을 새로 써야 한다.

그래서 알람이 울린 시점에 적절했어야 하는 동작을 기준으로 바꿨다. 그 시점의 기준 문서(코드, PR, 릴리스, 결정 기록)에서 채점할 수 있는 필드를 역산하고, 리포트 본문, 담당자 댓글과 그 시점의 기준을 함께 놓고 판정한다. 결과는 이 시점에 이런 알람이 이런 데이터로 울렸고, 사람은 이 점을 문제로 봤으며, 당시 시스템으로는 이것은 잘 동작했고 저것은 어쩔 수 없었다는 형태가 된다.

### 피드백이 없다고 맞은 것은 아니다

담당자는 문제가 없으면 댓글을 잘 쓰지 않으므로 처음에는 피드백 없는 케이스를 통과로 봤다. 담당자가 놓쳤거나 파악이 늦어 댓글이 없던 오답이 섞여 있었다. 그래서 다음 조건을 모두 만족할 때만 자동 통과시키고 나머지는 사람의 검수 세션으로 보낸다.

- 댓글의 기조가 긍정이다.
- 오판 라벨과 회의록 언급이 없다.
- 점검 항목을 통과한다.
- 이 케이스를 고치려는 PR이 없다.
- 과거 결함 패턴의 신호가 없거나 모두 설명된다.

검수 세션은 사람의 피로를 줄이고 판정을 일정하게 유지하도록 원칙으로 운영한다. 결과와 피드백을 1대1로 대응시키고, 근거를 댈 수 있는 의심만 묻는다. 회의에서 합의된 의견은 근거로 쓰고, 의견이 갈리면 검토자에게 재확인을 요청한다. 조금이라도 의심스러우면 억지로 반영하지 않는다. 검수 결론은 다음 판정의 학습 자료로 남긴다.

## 채점기의 변천에서 배운 것

| 단계 | 방식 | 한계 |
| --- | --- | --- |
| 규칙 채점 | 오판 라벨과 정해진 형식의 정정 댓글을 GitHub Actions가 YAML 기대값으로 합치고, 평가 담당자가 서브 에이전트별 기대 키워드를 따로 적음. 최종 결과는 기대값과 대조(블랙박스), 서브 에이전트 출력은 키워드 포함 여부로 대조(화이트박스) | 한영 표기와 띄어쓰기처럼 뜻이 같은 다른 문자열을 오답 처리. 원인이 여럿이어도 최종 결과만 비교. 해결 불가 케이스를 넣으면 늘 실패하고 빼면 나중의 개선을 못 잼. 틀린 케이스만 추가돼 계속 맞아야 할 케이스가 빠짐. 담당자 부담이 케이스 수만큼 늘어남 |
| 컨텍스트 파일(memory bank) | 시스템 설명, 서브 에이전트 명세, 판정 규칙을 Markdown으로 두고 판정 세션마다 읽힘 | 사람이 파일을 계속 고쳐야 하고, 파일을 고치면 과거 판정도 따라 고쳐야 하는 순환 수정이 생김. 개념 단위로 정리해 이슈 시점과 판정 시점이 어긋남 |
| LLM 위키 | 원문(raw), LLM이 쓰는 위키, 사람과 함께 고치는 스키마의 세 층과 ingest, query, lint | 특정 노트 앱의 웹 클리퍼는 접힌 댓글, 첨부 이미지와 참조 링크를 놓침. 앱 고유 링크 문법과 앱 상태 파일이 다른 저장소와 호환을 막음 |
| 도구 독립 위키 | 순수 Markdown 디렉터리, 디렉터리별 index.md와 시간순 log.md, 필수 frontmatter는 type 하나 | 위키가 가정한 원문 불변이 평가 데이터에는 성립하지 않음 |

LLM 판정에는 두 조건이 필요하다. 리포트를 해석할 컨텍스트가 매번 같아야 하고, 리포트의 비결정성과 판정 LLM의 비결정성을 함께 다뤄야 한다. LLM 위키의 구조는 [[LLM-Wiki-Knowledge-Compilation|LLM 위키]]에서 다룬다.

마지막 단계에서 원문을 세 가지로 다시 정의한 것이 핵심이다.

| 원문 구성 | 내용 | 다루는 방식 |
| --- | --- | --- |
| 대상 | 리포트 본문, 결과 JSON, 실행 시점의 상태와 시각, 알람 정보 | 불변 |
| 피드백 | 리포트 댓글, 이미지와 링크, 평가자의 검수 결과 | 덮어쓰지 않고 날짜를 붙여 추가 |
| 기준(SSOT) | 코드 스냅샷, 이슈와 PR, 릴리스, 개발자나 LLM이 정리한 문서, 회의 결정 | 덮어쓰지 않고 날짜를 붙여 추가 |

피드백과 기준은 시점마다 바뀌므로 덮어쓰면 판정과 기준의 시점을 맞출 수 없다. 모든 것에 시점을 붙이고 시점 목록을 매니페스트로 관리한다. 데이터가 일정량 쌓이거나 규칙을 바로 바꿔야 할 상황이 보이면 스킬과 지시 파일의 수정안을 만들어 검토자에게 적용, 수정, 보류, 기각을 묻는다. 이렇게 하면 과거 데이터를 과거 기준으로 판정할지 현재 기준으로 판정할지를 명확히 가를 수 있다.

## 남은 과제

- 평가 시스템 자체를 어떻게 평가하고, 그 반복을 어디서 멈출지 정해야 한다.
- 자동 통과, 사람 검수와 healer 판단을 두어도 사람이 개입할 지점은 남고, 그만큼 사람의 오판도 생긴다. 정보 사이의 충돌을 가리는 비용도 작지 않다.
- 여러 요인이 겹쳐 생기는 알람은 비슷한 것끼리 묶어 패턴으로 만들기 어렵다.

보완 방향은 세 가지다. LLM judge가 달라진 결과의 적절성을 먼저 판정해 사람이 볼 대상을 줄이고 케이스를 가로지르는 오류 패턴을 찾는다. 에이전트가 어떤 데이터를 조회해 어떤 판단을 내렸는지 실행 궤적을 결과와 함께 남겨 판정 재료로 쓴다. 어느 릴리스에서 어떤 규칙이 바뀌었는지 연대기로 정리해 이후 판정이 어떻게 달라질지 예측한다. 판정 모델의 편향과 검증은 [[Eval-LLM-Judge|LLM judge 평가]]에 있다.

## 점검 질문

- 정답 기준에 사람이 헷갈리는 상태가 남아 있지 않은가? 위치와 원인처럼 다른 축이 한 카테고리에 섞여 있지 않은가?
- 정답을 따로 라벨링하지 않고 운영 피드백에서 모으는가? 피드백이 없는 케이스를 통과로 세고 있지 않은가?
- 카테고리별 정확도를 사람이 확인한 원인으로 묶는가?
- 리플레이가 알람 시점의 데이터를 보고, 여러 번 실행해 흔들림을 오답으로 세는가?
- 결과가 달라졌을 때 회귀, 개선, 진화를 코드, PR과 결정 기록으로 가르는가?
- 기준 문서와 피드백을 덮어쓰지 않고 시점을 붙여 남기는가?
