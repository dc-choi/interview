# 실제 질문으로 Ontology를 검증하기

Schema와 link가 구조적으로 맞아도 사용자와 에이전트가 업무 질문에 답할 수 있다는 증거는 아니다. 설계자가 구현 기억으로 길을 찾는 것도 모델 자체의 사용성 증거로는 부족하다.

## 질문을 기존 모델 밖에서 가져온다

리더가 반복해서 묻는 문제, 팀 간 결정을 위해 필요한 정보, 숙련자만 조사할 수 있는 질문과 수작업 보고서에서 평가 항목을 만든다. 이미 있는 type을 보고 답하기 쉬운 질문만 만들면 누락된 개념을 발견하지 못한다.

질문은 상황 확인, 원인 추적, 영향 판단으로 이어지게 한다. 배송 지연이 많은 지역을 찾고, 관련 물류센터와 주문을 따라가며, 같은 병목을 통과할 예정인 배송의 위험을 판단하는 식이다. 모델이 표현하지 못하는 중요한 질문은 삭제하지 않고 실패 사례로 유지한다.

## 미리 만든 앱의 도움을 분리한다

평가에는 범용 분석 도구를 쓰고 문제에 맞춘 dashboard나 Workshop 앱을 제외한다. 맞춤 앱이 올바른 출발점, filter와 join을 이미 제공하면 모델의 탐색 가능성을 검증할 수 없다.

참가자는 모델을 만들지 않은 도메인 전문가와 신규 사용자를 포함한다. 팀 평가에서도 먼저 도움 없는 시도를 기록한다. 설계자의 지식과 코칭이 원래 혼란을 가리지 않게 해야 한다.

## 정답뿐 아니라 경로를 기록한다

| 관찰 | 우선 확인할 원인 |
| --- | --- |
| 출발 type을 찾지 못함 | 이름, alias, 설명과 노출 type 수 |
| 같은 개념에 서로 다른 type 선택 | 중복이나 의미 경계 |
| 예상한 관계를 따라갈 수 없음 | 빠진 link, 방향, 이름 또는 권한 |
| export와 수동 join에 의존 | 모델에 없는 재사용 관계/계산 |
| 합리적인 경로가 다른 수치를 반환 | 실체의 단위, 중복 식별, 날짜와 집계 의미 |
| 설계자만 성공 | 모델 밖의 암묵 지식 |
| 맞는 경로가 지나치게 느림 | query, 색인, 데이터 규모와 모델링 |

정확도, 소요 시간, 탐색어, 시도한 type/link와 도움을 받은 지점을 함께 기록한다. 실패 원인이 모델인지 데이터, 권한, 분석 앱 또는 교육인지 구분한다. 한 번의 실패와 여러 사용자가 반복해서 겪는 혼란은 같은 무게로 다루지 않는다.

## 사람과 에이전트를 별도로 비교한다

같은 질문을 에이전트에도 주되 사람이 찾은 경로를 알려주지 않는다. 둘 다 성공하면 해당 질문의 표현과 발견 가능성을 확인한 것이다. 에이전트만 성공하면 사람용 이름과 화면 구조를, 사람만 성공하면 모델에 없는 업무 지식과 로직을 검토한다. 둘 다 실패하면 데이터와 관계, 의미 및 연산의 공백을 찾는다.

AI만 통과한 결과로 사람의 사용성을 대신 검증하지 않는다. 반대로 사람이 성공했어도 경험으로 채운 맥락이 많으면 자동화나 신규 사용자에게 이전되지 않는다.

## 회귀 평가로 유지한다

독립 질문을 넓게 푸는 quiz와 하나의 문제를 깊게 추적하는 timed drill-down을 함께 쓸 수 있다. 경쟁은 선택사항이고 근거 경로를 설명하는 것이 필수다. 개선 뒤 일부 질문을 반복해 변화량을 보고, 보지 못한 질문을 추가해 일반화를 확인한다.

이 Vault에도 실제 판단 질문에서 원문 근거까지 돌아갈 수 있는지, 정답과 추정이 구분되는지 평가하는 방식으로 적용할 수 있다. 문서 개수나 색인 성공만을 학습 품질로 삼지 않는다는 적용 제안이며, 실제 사용자 평가를 수행한 기록은 아니다.
