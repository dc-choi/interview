# 바이브 코딩과 에이전틱 엔지니어링

바이브 코딩(vibe coding)은 코드를 읽지 않고 자연어 지시만으로 소프트웨어를 만드는 방식이다. 에이전틱 엔지니어링(agentic engineering)은 틀리기 쉽고 확률적으로 동작하는 에이전트를 조율해 속도를 얻으면서도 전문가 수준의 품질 기준을 유지하는 일을 가리킨다. 두 말은 같은 도구를 쓰는 서로 다른 책임 수준을 구분한다. 결과에 대한 책임이 만든 사람에게 그대로 남는 작업은 뒤쪽에 속한다.

## 두 말이 가리키는 것

| 구분 | 바이브 코딩 | 에이전틱 엔지니어링 |
|---|---|---|
| 얻는 것 | 누구나 만들 수 있게 진입 장벽을 낮춘다 | 품질을 유지한 채 속도를 높인다 |
| 코드와의 거리 | 읽지 않고 결과만 본다 | 스펙, 설계와 감독을 사람이 맡는다 |
| 책임 | 실험과 개인용 도구에서 가볍다 | 보안과 정확성의 책임이 작성자에게 남는다 |
| 맞는 자리 | 시제품, 일회성 도구 | 결제, 개인정보와 운영 서비스 |

이 구분을 제시한 연구자는 에이전트를 능력은 크지만 들쭉날쭉한 인턴에 비유하고, 잘 다루는 사람의 속도가 10배를 크게 넘는다고 말했다. 이 배수는 발언자의 체감이며 측정값이 아니다.

## 사례: 이메일로 결제와 계정을 잇는 설계

한 웹 앱을 코드를 직접 쓰지 않고 만든 제작 기록에 다음 일이 있다. 가입은 Google 계정으로 하고 크레딧은 Stripe로 결제하는 구조에서, 모델은 결제 성공과 사용자 크레딧을 두 서비스의 이메일 주소를 맞춰 연결하려 했다. 결제 때 적는 이메일은 가입한 계정의 이메일과 다를 수 있으므로 돈을 내고도 크레딧을 받지 못하는 사용자가 생기는 설계다. 제작자가 지적하자 모델은 요청 메타데이터에 고유 사용자 ID를 실어 보내는 방식으로 고쳤다.

- 오류는 문법이나 실행 실패가 아니었다. 간단한 테스트는 통과하는 코드였고 가입 이메일과 결제 이메일이 다른 사용자에게서만 드러난다.
- 막은 것은 코드 리뷰 기술보다 식별자에 관한 설계 지식이다. 사람이 바꿀 수 있는 속성(이메일, 이름)이 아니라 고정된 식별자에 돈과 권한을 묶는다.
- 그래서 돈, 권한과 개인정보가 어떤 식별자에 묶이는지는 구현을 맡기기 전에 사람이 스펙에 적는다(적용 제안). 구현 전에 정할 계약은 [[AI-Code-Delegation-Review#아키텍처를 정하지 않으면 에이전트가 대신 정한다|아키텍처를 정하지 않으면 에이전트가 대신 정한다]]에서 다룬다.

## 사람에게 남는 일

- **자세한 스펙:** 모델이 혼자 세운 계획을 승인하는 데서 그치지 않고, 에이전트와 함께 문서 수준의 스펙을 설계한다. 사람은 큰 범주와 감독을 맡고 세부는 에이전트가 채운다. 작성 방법은 [[Agent-Spec-Writing|AI 에이전트 스펙 작성법]]에 있다.
- **원리의 이해:** 라이브러리마다 다른 인자 이름(`keepdim`과 `keepdims`, `dim`과 `axis`)은 외우지 않아도 된다. 반면 텐서의 뷰가 같은 저장 공간을 공유하는지 복사하는지 같은 원리는 알아야 생성된 코드의 불필요한 메모리 복사를 잡아낸다. 세부 기억은 넘기고 동작 원리는 남긴다.
- **취향과 판단:** 생성된 코드는 동작하더라도 비대하고, 복사한 부분이 많고, 깨지기 쉬운 추상화를 품는 경우가 있다. 발언자는 그 원인을 학습 보상에 코드의 간결함이 반영되지 않기 때문으로 추정했고, 근본적인 한계가 아니라 아직 다뤄지지 않은 영역이라고 봤다(발언자의 추정).
- **의심하는 태도:** 모델을 사람이나 동물처럼 대하며 압박하거나 달래는 방식은 결과를 바꾸지 못한다고 보고, 어떤 지시가 통하는지 의심하며 시간을 두고 확인하라고 권한다. 정해진 요령 목록은 없다는 것이 발언자의 입장이다.

생각은 맡길 수 있어도 이해는 맡길 수 없다는 말이 이 분업을 요약한다. 무엇을 왜 만드는지, 에이전트를 어디로 이끌지 아는 일이 사람 쪽 병목으로 남는다. 위임이 이해를 대신하게 될 때의 위험은 [[AI-Code-Delegation-Review-Cognitive-Surrender|위임과 인지적 항복]]에서 다룬다.

## 보안 근거와 평가 방식

- 한 보안 회사가 2025년에 100개가 넘는 LLM에 Java, Python, C#, JavaScript 코드 작성 과제를 주고 검사한 결과 생성된 코드 표본의 45%가 보안 테스트에 실패해 OWASP Top 10에 해당하는 취약점을 넣었다. Java의 실패율은 72%였고, 더 새롭고 큰 모델에서도 보안 통과율은 나아지지 않았다고 보고했다. 보안 제품 회사의 자체 평가이며 과제가 취약점이 생길 수 있는 지점을 겨냥해 설계됐으므로, AI가 쓴 모든 코드의 45%가 취약하다는 뜻으로 읽지 않는다.
- 발언자는 채용 평가도 알고리즘 퍼즐에서 벗어나, 큰 프로젝트를 안전하게 구현하게 한 뒤 여러 에이전트로 배포된 결과물을 공격해 견디는지 보는 방식을 제안했다(제안이며 시행 사례는 확인하지 못함). 채용 과제의 변화는 [[AI-Assisted-Hiring-Assessments|AI 활용 채용 평가]]에 있다.

## 한계

- 두 말의 구분, 10배를 넘는 속도와 사람에게 남는 일의 목록은 한 연구자의 대담 발언이다. 조직 단위의 측정이나 비교 연구가 아니다.
- 제작 기록의 사례는 2025년 4월의 모델과 도구에서 나왔다. 같은 실수가 현재 모델에서 같은 빈도로 나온다는 근거는 아니다.
- 대담 발언은 원본의 음성 인식 전사로 대조했다. 화면 자료는 확인하지 못했다.

## 판단 질문

- 이 작업은 결과의 책임이 가벼운 실험인가, 돈과 개인정보가 걸린 서비스인가?
- 돈, 권한과 개인정보가 묶이는 식별자를 구현 전에 적었는가?
- 맡긴 세부 가운데 원리를 몰라서 검토하지 못하는 부분은 어디인가?
