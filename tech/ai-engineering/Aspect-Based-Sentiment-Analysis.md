# 속성 기반 감성 분석

리뷰 전체의 긍정과 부정을 하나로 정하는 대신, 평가 대상의 **어떤 속성에 어떤 감정이 표현됐는지** 추출하는 작업이다. Aspect-Based Sentiment Analysis를 줄여 ABSA라고 한다.

예를 들어 `보습은 좋은데 용기가 새서 불편하다`는 리뷰는 보습에 대한 긍정과 용기에 대한 부정을 함께 담는다. 전체 감성 하나로 압축하면 서로 다른 개선 지점이 사라진다.

## 추출 대상과 분류를 나눈다

| 작업 | 질문 | 예시 |
|---|---|---|
| 속성 표현 추출 | 원문에서 무엇을 평가했는가 | 보습, 용기 |
| 속성 표현의 감성 분류 | 그 대상에 어떤 감정을 표현했는가 | 보습은 긍정, 용기는 부정 |
| 속성 카테고리 탐지 | 미리 정한 어느 분류에 속하는가 | 사용감, 포장 |
| 카테고리 감성 분류 | 해당 분류에 대한 평가는 무엇인가 | 포장에 대한 부정 |

카테고리는 원문에 같은 단어가 없어도 표현될 수 있다. 따라서 키워드 존재 여부와 속성 분류를 같은 작업으로 취급하지 않는다. SemEval-2014 과제는 긍정, 부정, 중립과 상충 감성을 구분했다. 제품에 적용할 라벨과 상충 처리 규칙은 대상 도메인에 맞게 정한다.

## 리뷰 요약으로 연결하는 설계

구문과 감성을 먼저 추출하고 그 결과를 집계하거나 요약하는 파이프라인을 구성할 수 있다. 다음은 이 구조를 적용할 때의 설계 기준이다.

1. 리뷰 원문과 추출한 구문을 연결해 결과의 근거를 찾을 수 있게 한다.
2. 상품, 채널, 기간과 속성별로 분석 결과를 집계한다.
3. 요약에는 선택한 근거 구문을 전달한다. 추출 누락과 잘못된 분류가 요약으로 전파될 수 있음을 고려한다.
4. 요약 결과가 원문의 부정 의견이나 상충 의견을 지우지 않았는지 확인한다.

빈도 수치를 표시한다면 분모를 명시한다. 전체 리뷰 수, 특정 속성을 언급한 리뷰 수와 추출 구문 수는 다르다. 하나의 리뷰가 여러 속성을 언급할 수 있으므로 속성별 건수를 더한 값을 리뷰 수로 해석하지 않는다.

## 감성 분류와 고객 응대 결정을 분리한다

감성 결과를 답글 생성에 사용할 때는 분류 라벨, 응대 정책과 실제 조치를 나눈다. 긍정과 부정이 섞였다는 라벨만으로 상품 추천을 넣을지, 담당자가 확인할지까지 정할 수는 없다. 예를 들어 제품에는 만족하지만 배송 파손을 호소하는 리뷰라면, 전체 감성보다 해결되지 않은 문제를 먼저 확인할 수 있다.

다음은 리뷰 응대에 적용할 설계 제안이다.

1. 원문에서 불만 대상과 근거 구절을 추출하고, 감성 분류의 오류와 추출 누락을 따로 점검한다.
2. 상품 추천 허용 여부와 담당자 검토 조건은 서비스 정책으로 정한다. 부정 리뷰에서 추천을 생략하는 것은 가능한 정책이며 감성 분석 자체의 필수 규칙은 아니다.
3. 답글에 상품을 넣으면 조회한 후보와 상품 정보를 전달한다. 답변 생성과 추천 후보 선정의 품질은 각각 평가한다.
4. 사과문 생성, 담당자 알림과 실제 환불이나 교환을 별도 단계로 둔다. 생성된 문구를 조치 완료의 증거로 쓰지 않는다.
5. 공개 전 검토에서는 해결하지 않은 문제에 완료를 약속했는지, 원문에 없는 사실이나 부적절한 상품 추천을 덧붙였는지 확인한다. 승인과 발행 흐름은 [[LLM-Workflow-Patterns-Chain-vs-Agent#콘텐츠 초안과 승인 대기열|초안과 승인 대기열]]로 연결한다.

## 평가와 한계

속성 추출을 잘하는지와 주어진 속성의 감성을 잘 맞히는지는 별도로 평가한다. SemEval-2014는 추출과 카테고리 탐지에 F1을, 정답 속성이 주어진 감성 분류에 accuracy를 사용했다. 정답 속성을 입력한 점수는 추출 오류까지 포함한 전체 파이프라인의 성능이 아니다.

실무 평가에서는 도메인과 언어별 예시, 부정문, 복수 속성과 상충 감성을 포함한 검토 데이터를 준비한다. 도메인 특화 모델이 범용 모델보다 좋은지는 같은 데이터와 평가 조건에서 비교한다. 특정 서비스의 개선 수치를 다른 제품의 기대 성능이나 구매 전환 효과로 옮기지 않는다.
