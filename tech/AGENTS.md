# Technical Knowledge Domain Rules

이 파일은 `tech/` 아래의 기술 지식 문서, 카테고리 인덱스와 기술 메모에 적용한다. 메모 입력을 문서화할 때는 `memo` 스킬도 함께 사용한다.

`tech/senior/`에서 조직 문화, 의사결정, 피드백, 회고와 OKR을 다루거나 `tech/ai-engineering/org-role/`에서 조직과 역할 변화를 다룰 때는 `fit/AGENTS.md`도 읽는다.

## 현재 실무 기술 축

- NestJS를 활용한다.

## 개인 코딩 선호

2026-09-12 대화에서 확인한 기본 선호다. 기술 지식을 개인 선호로 추정하지 않고, 현재 요구사항과 대상 프로젝트의 규칙을 확인해 적용한다. 확인 사례와 관련 지식은 [코딩 선호 기록](computer-science/code-quality/coding-preferences/Coding-Preferences.md)에 둔다.

- 실제로 두 곳에 반복된 로직은 일찍 공통화해 이후 재사용에도 대비한다. 구현이 하나이고 확장 계획이 불확실하면 클래스, 인터페이스와 전략을 미리 나누지 않는다.
- 공통 함수에 호출처별 옵션이 누적되면 책임을 더 나눈다. 이미지 처리처럼 같은 역할에 서로 다른 처리 방식이 생긴 사례에서는 전략 패턴 같은 객체지향 구조를 선호한다.
- 입력과 권한 검증처럼 실패 조건을 먼저 판단할 수 있으면 early return/throw로 중첩을 줄이고 정상 흐름을 평평하게 둔다.
- 짧고 한 곳에서만 쓰는 검증은 해당 함수 안에 둔다. 이를 모든 단일 호출 함수의 분리 금지로 확대하지 않는다.
- 여러 조건이 결합된 식은 한 번만 사용하더라도 `canPublish`처럼 의미가 드러나는 변수로 이름을 붙여 가독성을 높이는 것을 선호한다.
- 간단한 조건에 따라 두 값 중 하나를 선택할 때는 삼항 연산자를 선호하고, 삼항 연산자를 중첩해서 사용하지 않는다.
- 컬렉션 가공은 `filter`, `map`, `flatMap`, `reduce`를 연결해 처리 흐름을 드러내는 함수형 표현을 선호한다.
- `forEach`는 동기, 비동기 여부와 관계없이 사용하지 않는다. 최적화 이후의 성능을 근거로 이 규칙의 예외를 두지 않는다.
- 서로의 결과에 의존하지 않고 하나라도 실패하면 전체를 실패 처리하는 비동기 작업은 `Promise.all`로 묶어 동시에 실행하는 것을 선호한다.
- 독립적인 작업의 일부가 실패해도 성공한 결과를 활용해야 하면 `Promise.allSettled`로 모든 결과를 모아 작업별 성공과 실패를 처리하는 것을 선호한다.
- 대량의 독립적인 비동기 작업은 동시 실행 수를 제한하는 것을 기본으로 한다.
- 앞선 작업의 완료나 결과에 의존하거나 업무상 실행 순서가 필요하면 다음 작업을 미리 시작하지 않고 순서대로 호출해 `await`한다. 응답 전에 끝나야 하는 작업은 완료를 기다린 뒤 응답한다.
- 항목별 순차 처리가 필요한 루프는 일반 `for` 또는 `for...of` 안에서 각 작업을 호출하고 `await`한다. 이 경우에는 컬렉션의 함수형 표현 선호보다 실행 순서와 완료 대기를 우선한다.
- 중간 함수에서 오류를 잡아 로그를 남긴 뒤 원래 오류를 다시 던지는 형태를 허용한다. 모든 함수에 로깅용 `try/catch`를 의무화하는 규칙으로 확대하지 않으며, 구체적인 로깅 계층과 중복 로그 처리 정책은 별도로 확인한다.
- 오류 로그는 메시지, 관련 식별자와 오류를 객체로 묶어 남기는 방식을 선호한다. 상품 조회 실패의 `message`, `productId`, `error`처럼 해당 작업의 맥락을 함께 기록한다.
- 호출부에서 구분해야 하는 업무 오류는 `OrderAlreadyCancelledError`처럼 전용 에러 클래스로 표현하는 것을 선호한다.
- 조회 함수는 단건 `findOne`, 목록 `findAll`처럼 조회 개수로 이름을 구분하는 것을 선호한다. `findOne`은 결과가 없으면 `null`을 반환하고, 호출부에서 `null`을 확인해 업무 예외를 던진다.
- `findAll`은 조회 결과가 없으면 예외 없이 빈 배열 `[]`을 정상 결과로 반환한다.
- 독립 함수와 콜백은 가능한 한 화살표 함수로 작성한다. 여러 줄 체이닝을 반환하는 화살표 함수는 중괄호와 `return`을 명시해 본문과 반환 지점을 드러낸다.
- 화살표 함수 선호보다 호출 계약을 우선한다. 호출자가 지정한 `this`나 함수 자신의 `arguments`가 필요한 경우에는 일반 함수 또는 메서드를 사용한다. `new` 호출이 필요한 대상은 생성 가능한 함수나 클래스로, `yield`가 필요한 본문은 generator 문법으로 작성한다. 실제 초기화 전 호출을 보존해야 하면 함수 선언식을 사용한다.
- 클래스 메서드는 `method() { ... }` 문법으로 작성하고 화살표 함수 필드로 정의하지 않는다. 메서드를 콜백으로 전달하면서 인스턴스의 `this`를 유지해야 하면 호출부에서 wrapper arrow 또는 `bind`로 처리한다.
- 반환 타입을 명시하는 데 거부감은 없지만 코드가 지나치게 길어지지 않도록 가독성을 고려한다. 모든 함수의 반환 타입 명시를 요구하는 선호로 해석하지 않는다.
- TypeScript에서 객체 구조는 `interface`로 정의하고, 복잡한 타입을 표현해야 할 때는 `type`을 사용한다. 여러 인터페이스를 합성할 때도 `type Combined = A & B`처럼 교차 타입을 사용한다.
- 새 프로젝트에서 런타임 상태 코드와 선택값 집합은 `as const` 객체와 값 타입을 기본으로 사용한다. 서로 다른 도메인의 값이 섞이는 것을 타입으로 막아야 하거나 기존 프로젝트의 enum 계약과 규칙을 유지해야 하면 문자열 `enum`을 사용한다.
- enum을 사용할 때는 모든 멤버가 문자열 값을 갖는 문자열 enum만 허용한다. 숫자 enum과 문자열, 숫자를 섞은 혼합 enum은 사용하지 않는다.
- 도메인의 값을 enum으로 구분할지는 서로 다른 개념이 같은 문자열을 쓰는지, 같은 호출 흐름에서 혼용될 가능성이 있는지, 잘못 전달하면 업무 결과가 달라지는지를 함께 확인해 판단한다. `asc`/`desc`처럼 동일한 의미로 공유하는 값에는 `as const`를 사용한다.
- 리치 도메인이 상태를 내부에 두고 `account.isActive()` 같은 메서드를 제공하면 상태값을 직접 잘못 전달할 지점이 줄어든다는 점을 고려한다. 추가 enum 구분의 필요성은 실제 호출부에서 확인한다.
- 주석을 남기는 것을 선호하며, 코드의 이유나 외부 제약을 설명하는 주석도 긍정적으로 본다. TypeScript에서도 JSDoc에 함수 설명과 인자(`@param`), 반환값(`@returns`) 설명을 남기되, 짧고 동작이 자명한 내부 함수에는 생략한다.
- 테스트 케이스의 이름은 한국어로 작성하는 것을 선호한다.
- 도메인 테스트는 내부에 private 메서드가 있어도 공개된 동작과 결과를 통해 검증하는 것을 기본으로 한다.
- 기능 개발은 스펙을 먼저 작성한 뒤 진행하고, 테스트는 구현이 스펙을 만족하는지 검증하는 데 사용한다. 테스트부터 작성하는 TDD 흐름을 기본 규칙으로 강제하지 않는다.
- 인자가 늘어나는 함수는 이름 있는 프로퍼티를 가진 객체로 묶어 전달하는 것을 선호한다. 검색어, 카테고리와 페이지 조건처럼 같은 작업의 입력을 한 객체로 받는다. 모든 단일 인자까지 객체로 감싸는 규칙으로 확대하지 않는다.
- 일반 함수가 받는 최상위 인자는 최대 3개로 제한한다. 각 인자는 객체일 수 있으므로 최대 3개의 객체를 각각 전달할 수 있다. 객체 내부의 프로퍼티 수를 3개로 제한하는 뜻은 아니다. DI 생성자에는 이 제한을 기계적으로 적용하지 않고 필요한 의존성에 맞춰 유연하게 정한다.
- 함수 입력 객체의 속성에는 TypeScript `readonly`를 기본으로 붙여 원본을 변경하지 않겠다는 의도를 타입에 표현한다.
- 배열 입력도 `readonly T[]`처럼 읽기 전용 타입으로 받는 것을 기본으로 한다. 정렬 등 변경이 필요한 가공은 원본 대신 새 배열에 적용한다.
- 객체나 배열에서 필요한 값을 꺼낼 때 JavaScript 구조 분해 할당을 선호한다. 반환 객체의 필요한 값을 호출부에서 바로 구조 분해하는 형태도 선호한다.
- 일반 데이터 가공에서는 원본을 최대한 변경하지 않고 새 값과 객체를 만드는 것을 기본으로 한다.
- 도메인 객체가 의미 있는 메서드로 자기 상태를 변경하고 규칙을 지키는 리치 도메인 모델을 선호한다.
- 도메인 객체가 소유한 상태의 불변조건은 그 객체가 보호하고, 애플리케이션 서비스는 조회, 저장, 트랜잭션과 실행 흐름을 조정한다. 여러 객체에 걸치거나 소유가 불명확한 규칙은 요구사항과 책임 경계를 확인한 뒤 배치한다.
- 서비스가 사용하는 저장소나 메일 발송 객체는 생성자로 주입받는 것을 기본으로 한다. 사용자는 NestJS를 활용하는 맥락에서 이 방식을 중요하게 본다.
- ORM은 특정 제품에 우선순위를 두지 않고 프로젝트의 요구사항과 기존 구성에 따라 판단한다.

## 기술 문서 최신성

- AWS, OpenAI, Anthropic, Node.js, TypeScript, Kubernetes, 데이터베이스 제품과 보안 표준처럼 변동성이 큰 기술 문서는 공식 1차 출처를 확인한 날짜를 frontmatter의 `verified_at: YYYY-MM-DD`로 기록한다. 비공식 출처가 정본인 경험 기반 문서는 아래 예외를 따른다.
- `verified_at`은 그 문서의 본문과 출처를 실제로 대조한 경우에만 갱신한다. 문서 일부만 대조한 부분 검증도 갱신 사유이지만, 새로 추가하거나 수정한 사실을 공식 1차 출처와 대조했고 문서에 남은 버전 민감 주장이 그 출처와 상충하지 않음을 확인했을 때만 갱신하며, 문서 전체를 다시 대조했다는 뜻은 아니다. 다른 문서에서 검증한 사실을 링크로 참조만 하거나 자동 스캔, 파일 이동만 한 경우에는 갱신하지 않고, `## 출처`가 없는 순수 TOC 인덱스에는 두지 않는다.
- 분할로 새로 만든 문서의 `verified_at`은 옮긴 내용을 마지막으로 공식 출처와 대조한 날짜로 쓴다. 옮긴 내용의 대조 날짜가 섞여 있으면 가장 오래된 날짜를 쓰고, 분할 시점에 전부 다시 대조했으면 그날로 쓴다. 부모의 현재 날짜를 자동으로 물려받지 않는다.
- 발표, 밋업 같은 비공식 출처만이 정본인 경험 기반 문서에는 `verified_at`을 두지 않고, 버전 민감 주장에는 본문에 기준을 명시한다 (예: 발표 기준, MySQL 8.4 문서 기준). 공식 1차 출처가 본문의 버전 민감 주장 전부를 직접 뒷받침하게 되면 그때 `verified_at`을 둘 수 있다.
- 가격, quota, 지원 정책, 시험 범위, 제품 버전과 API 동작은 공식 출처와 검증 기준일 없이 현재 사실처럼 단정하지 않는다. 검증 기준일은 frontmatter `verified_at` 또는 본문의 기준 명시로 제공한다.
- `항상`, `무조건`, `제한 없음`, `지원 종료`, `무료`, `동일`과 `완전` 같은 절대 표현은 공식 규격이나 정책이 전체 범위를 보장하고 출처를 함께 제시할 때만 쓴다. 그렇지 않으면 버전, 리전, 에디션, 시점과 예외 조건을 명시한다.
- 사실 관계를 수정했다면 관련 문서의 상충 표현과 출처를 함께 확인하고, 위의 갱신 조건을 만족한 문서에 한해 `verified_at`을 갱신한다.

## 출처 표기

- `## 출처`의 유형은 셋으로 나눈다: 1) 블로그, 아티클과 발표(그 밖의 출처 포함) 2) 레퍼런스 매뉴얼과 명세(버전 표기가 없는 벤더 제품 문서인 Documentation, User Guide, Reference류 포함) 3) 강의. 항목을 추가할 때는 그 문서에 있는 같은 유형 항목의 표기를 그대로 따르고, 표기가 섞여 있으면 같은 유형의 다수 표기, 동수면 기본형을 따른다. 기존 항목을 다른 표기로 일괄 변환하지 않는다. 단, 루트 표기 규칙이 금지한 표기는 선례라도 따르지 않고 그 자리에서 고친다. 2026-08-25 벤더 제품 문서 표기 정규화는 사용자 지시로 수행한 일회성 예외다.
- 같은 유형의 선례가 없으면 기본형을 쓴다. 블로그, 아티클과 발표는 제목 뒤에 em-dash로 매체나 저자를 붙인 `- [제목 — 매체](URL)`를 쓰고, 매체와 저자를 함께 쓰면 `- [제목 — 매체, 저자](URL)`로 잇는다. 책, 저장소, 릴리스 노트 같은 그 밖의 출처도 이 형태를 쓴다. 레퍼런스 매뉴얼과 명세는 매체를 앞에 둔 쉼표형 `- [매체, 문서명](URL)`을 쓴다. 강의는 `- [플랫폼, 강좌명 또는 강사명, 강의명](URL)`을 쓰고 가운데 항목은 식별에 필요하지 않으면 생략한다.
- 문서 전체를 인용해 라벨이 매체명 자체일 때는 쉼표형 대신 구분자 없이 그대로 쓴다 (예: `- [MySQL 8.4 Error Message Reference](URL)`).
- 새 지식 문서 하단 절 순서는 `## 출처` 다음 `## 관련 문서`를 기본으로 한다. 기존 문서의 반대 순서는 재배치하지 않고 유지한다.

## 카테고리 인덱스

- `tech/` 카테고리 최상위 인덱스는 루트의 leaf 폴더 분할 규칙에서 제외한다.
- 기술 메모를 추가하거나 이동할 때 대상 카테고리 인덱스를 함께 갱신한다.
