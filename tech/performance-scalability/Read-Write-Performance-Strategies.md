# 읽기와 쓰기 성능 전략

성능 개선은 캐시나 메시지 큐 같은 제품을 먼저 고르는 일이 아니다. 읽기와 쓰기 중 어느 경로가 느린지, 그 경로의 어느 계층이 병목인지 측정한 뒤 해당 비용을 줄이는 일이다. 읽기를 빠르게 만드는 선택이 쓰기를 느리게 할 수 있으므로 두 경로를 함께 본다.

## 먼저 확인할 것

1. 사용자 요청에서 느린 구간을 네트워크, 애플리케이션, 데이터베이스로 분해한다.
2. 읽기와 쓰기의 비율, 피크 시 요청량과 허용 지연을 측정한다.
3. 평균뿐 아니라 p95, p99 지연과 오류율, 포화 지표를 확인한다.
4. 병목 하나를 바꾸고 같은 부하 조건에서 다시 측정한다.

키워드를 나열하는 것보다 계층별로 비용과 해결책을 연결하면 선택의 근거가 분명해진다.

## 계층별 전략 지도

| 계층 | 읽기 경로 | 쓰기 경로 | 주요 대가 |
|------|-----------|-----------|-----------|
| 웹과 엣지 | 브라우저 캐시, CDN, 연결 재사용 | 요청 압축, 작은 요청 묶기 | 오래된 응답, 무효화와 재시도 |
| 애플리케이션 | 로컬 캐시, 분산 캐시, 요청 병합 | 비동기 큐, 배치, 동시성 제한 | 정합성, 중복 처리, 완료 지연 |
| 데이터베이스 | 인덱스, 읽기 복제본, 파티션 가지치기, 미리 계산한 조회 모델 | 배치 쓰기, 샤딩, 파티셔닝, 인덱스 최소화 | 복제 지연, 분산 트랜잭션, 운영 복잡도 |
| 아키텍처 | CQRS 조회 모델, 비정규화 | 이벤트 전파, 최종 일관성 | 모델 동기화와 수렴 실패 처리 |

## 읽기 성능 전략

### 요청 자체를 줄인다

- 브라우저 캐시와 [[CDN]]은 원본 서버까지 오는 반복 요청을 줄인다.
- 애플리케이션의 로컬 캐시는 가장 짧은 경로지만 인스턴스별 값이 달라질 수 있다.
- 분산 캐시는 여러 인스턴스가 같은 값을 재사용할 수 있지만 네트워크 왕복과 운영 비용이 생긴다.
- 캐시는 반복 조회나 계산 재사용이 충분할 때 효과가 있다. 히트율이 낮으면 계층만 하나 더 늘어난다.

캐시 적재, 갱신과 실패 처리는 [[Cache-Strategies|캐시 전략]]에서 선택한다.

### 검색 범위를 줄이고 읽기를 분산한다

- [[Index|인덱스]]는 탐색할 데이터 범위를 줄이지만 INSERT, UPDATE마다 함께 갱신된다.
- [[Read-Replica-Routing|읽기 복제본]]은 stale read를 허용하는 조회를 분산한다. 방금 쓴 값을 읽거나 transaction 일관성이 필요하면 primary 경로가 필요하다.
- 파티셔닝은 조건과 파티션 키가 맞을 때만 읽는 범위를 줄인다. 모든 파티션을 훑으면 이점이 사라진다.
- 통계와 복잡한 조인은 미리 계산한 table이나 read model로 옮길 수 있다. 이 경우 계산 비용과 정합성 책임이 쓰기 경로로 이동한다.

## 쓰기 성능 전략

### 사용자 응답 경로에서 작업을 분리한다

즉시 완료할 필요가 없는 이메일, 이미지 변환과 통계 갱신은 큐에 접수하고 worker가 처리할 수 있다. 이는 동기 응답 지연과 producer의 순간 부하를 줄이지만 실제 작업량을 없애지는 않는다. consumer의 지속 처리량보다 유입량이 크면 backlog가 계속 증가한다.

큐를 사용할 때는 접수와 완료를 구분하고, 중복 처리, 순서, 재시도, DLQ와 멱등성을 설계한다. 캐시와 큐의 역할 차이는 [[Cache-vs-Queue]]를 따른다.

### 한 번의 쓰기 비용을 줄이거나 분산한다

- 배치 쓰기는 여러 건을 묶어 네트워크와 commit 왕복을 줄인다. 큰 batch는 개별 요청의 대기 시간과 실패 범위를 키운다.
- 쓰기 경로에 필요하지 않은 인덱스를 제거하면 index page 갱신과 저장 공간 비용을 줄일 수 있다.
- [[Sharding|샤딩]]은 shard key를 기준으로 쓰기를 여러 노드에 분산하지만 cross-shard query와 transaction을 어렵게 한다.
- 파티셔닝은 한 DB 안의 관리와 접근 범위를 나누지만 단일 writer의 물리 한계를 자동으로 없애지는 않는다.
- 최종 일관성은 동기화 대기를 줄이는 대신 일시적 불일치와 수렴 전략을 요구한다.

## 읽기와 쓰기의 대표적인 상충

| 선택 | 얻는 것 | 지불하는 것 |
|------|---------|-------------|
| 인덱스 추가 | 조회 탐색 단축 | 쓰기, 저장 공간과 유지 비용 증가 |
| 비정규화와 read model | 조인 없는 빠른 조회 | 쓰기 시 여러 모델 갱신, 정합성 복잡도 |
| 동기 복제 | 최신 읽기와 낮은 데이터 손실 위험 | 쓰기 지연과 장애 시 가용성 저하 |
| 비동기 복제 | 빠른 쓰기와 읽기 분산 | 복제 지연, read-after-write 불일치 |
| 큰 batch | 높은 처리량, 왕복 감소 | 개별 지연, 메모리와 재처리 범위 증가 |
| 캐시 | 반복 읽기 지연과 원본 부하 감소 | stale data, 무효화와 stampede |

## 선택 예시

### 상품 조회가 많은 서비스

CDN과 cache-aside로 반복 요청을 줄이고, DB에는 조회 조건에 맞는 인덱스를 둔다. 상품 수정 직후 최신값이 필요하면 cache evict나 write-through 정책을 명시한다. 읽기 복제본을 사용한다면 관리자 확인처럼 최신성이 필요한 조회는 primary로 보낸다.

### 이벤트 적재가 많은 서비스

짧은 시간의 burst는 bounded queue로 흡수하고 consumer가 batch write한다. shard나 partition key가 한 값에 몰리지 않는지 확인한다. backlog 증가율과 처리 완료 시간을 함께 보며, 큐가 쌓이는 것을 처리량 증가로 오해하지 않는다.

## 검증 체크포인트

- 병목을 [[Application-Performance-Monitoring|APM]], slow query와 분산 trace로 확인했는가?
- read/write 비율과 최신성 요구를 숫자로 정했는가?
- 최적화 전후의 p95, p99, RPS/TPS, 오류율과 자원 포화를 같은 부하에서 비교했는가?
- 읽기 개선이 쓰기 비용에, 쓰기 개선이 일관성과 완료 지연에 미친 영향을 확인했는가?
- 부하가 포화점에 접근할 때의 변화는 [[Throughput-vs-Latency|처리량과 지연시간]] 기준으로 검증했는가?
