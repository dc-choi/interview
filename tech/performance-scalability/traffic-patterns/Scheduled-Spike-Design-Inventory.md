# 예정된 피크 이벤트 설계 목록

공연 예매, 수강 신청, 한정 판매처럼 공지된 시각에 요청이 몰리는 서비스는 평균 부하가 아니라 가장 바쁜 1초를 기준으로 설계한다. 이 문서는 구현 기법(원자 감소, 락, 대기열)보다 앞 단계인 수치 역산, 실패 응답 설계와 오픈 전에 문서로 남길 세 가지 목록을 다룬다. 구현 기법은 [[First-Come-Coupon-Patterns|선착순 이벤트 패턴]]과 [[Virtual-Waiting-Room-Architecture|가상 대기열 아키텍처]]를 본다.

## 평균은 피크를 숨긴다

아래 수치는 설명을 위한 가정이다. 평소 초당 1,000건을 받는 서비스는 하루 8,640만 건을 처리한다. 오픈 순간 50만 명이 한 번씩 누르면 그 1초에 평소의 500배가 들어오고, 화면 하나가 로그인 확인, 회차, 좌석 현황 같은 API 4개를 부르면 초당 200만 건이 된다. 하루 합계에는 거의 티가 나지 않으므로 일 평균이나 시간 평균으로 서버를 고르면 이 벽을 놓친다.

그래서 피크를 그대로 받는 진입과 대기 등록 계층은 피크 1초에서 거꾸로 계산한다. 대기열을 두면 입장 제어 뒤의 예매, 결제 계층과 외부 API는 대기열이 흘려보내는 입장률과 계약 한도에서 역산하고, 입장률은 그 계층의 검증된 지속 처리량에 맞춘다([[Virtual-Waiting-Room-Architecture-Admission-Reservation|입장 제어와 예매 처리]]). 대기열 없이 모든 계층이 피크를 직접 받는 구조라면 모든 계층을 피크 1초에서 역산해야 한다. 평소에는 대부분 자원이 논다. 대신 오픈 시각이 미리 공지되므로 그 시간대에만 증설하거나 대기열을 준비할 수 있다는 점이 갑작스러운 장애와 다른 유리한 조건이다. 예약 증설과 진입 계층 사전 용량은 [[Media-Event-Traffic|미디어 공개와 중계 이벤트 트래픽]]과 같은 문제다.

## 실패 응답도 기능이다

좌석 5만 석에 50만 명이 몰리고 한 사람이 한 장씩 산다면 구매를 시도한 사용자의 90%는 실패가 정상이다. 실패를 예외 경로로 미뤄 두면 실패한 사용자가 시스템을 계속 붙잡는다. 실패 응답에는 두 가지 품질이 필요하다.

- **빨리 실패한다.** 매진을 30초 뒤에 알리면 그동안 실패할 요청이 연결과 메모리를 점유하고, 성공할 요청까지 느려진다. 과부하에서 빨리, 싸게 실패하라는 것은 SRE의 연쇄 장애 대응 권고와 같은 방향이며, 대기 중인 요청은 메모리를 쓰고 지연을 늘린다. 남은 좌석 여부를 매번 DB에서 확인하면 실패 응답 하나에도 비용이 들므로, 매진 상태를 앞단에서 판정할 수 있게 만든다. 거절을 싸고 일찍 하는 방법은 [[Load-Shedding|부하 차단]]을 본다.
- **정확하게 실패한다.** 잠시 후 다시 시도하라는 일반 오류는 책임을 사용자에게 넘기고, 사용자는 새로고침을 반복한다. 45만 명이 초당 한 번 새로고침하면 오픈 순간과 비슷한 부하가 계속 이어진다. 선택한 좌석이 방금 팔렸다, 전 회차가 매진됐다, 카드 승인이 거절됐다처럼 상황을 구체적으로 알리면 사용자가 다음 행동을 고를 수 있다. 일시적 제한이라면 상태 코드와 `Retry-After`로 다시 시도할 시점을 알려 준다. 특정 사용자나 클라이언트의 한도 초과는 429, 서버의 일시 과부하 거절은 503이 해당하며 둘 다 `Retry-After`를 보낼 수 있다([[Rate-Limiting#응답 설계|Rate limiting 응답 설계]]).

재시도는 과부하를 키운다. 여러 계층이 각자 재시도하면 시도 수가 최대 계층별 시도 횟수(최초 요청 포함)의 곱까지 늘 수 있으므로, 여러 계층의 중복 재시도를 피하고 무작위 지수 백오프와 요청당 상한, 서버 전체 재시도 예산을 둔다. 자세한 내용은 [[Retry-Backoff-Jitter|재시도, 백오프와 jitter]]를 본다.

가장 나쁜 실패는 돈은 나갔는데 좌석이 없는 경우다. 환불, 고객 문의와 재방문 이탈이 함께 온다. 느린 실패나 부정확한 실패보다 이 경우를 최종 상태에서 0건으로 만드는 것이 우선이다.

## 오픈 전에 남길 세 가지 목록

테이블과 ERD를 성급하게 확정하면 그 구조를 지키는 방향으로만 고치기 쉬워 충돌과 실패 경로를 늦게 발견할 수 있다(강의의 경험적 주장). 흐름(좌석 선택, 선점, 결제 요청, 확정, 알림)을 먼저 펼치고 아래 목록을 저장소의 문서로 관리한다. 회의에서만 나온 내용은 오픈 시점에 잊히기 쉽고, 문서가 있으면 새 팀원도 통제 중인 실패 경로를 첫날부터 안다.

### 1. 동시 요청이 부딪히는 곳

같은 데이터를 두 요청이 같은 순간에 바꾸는 지점이다. 1ms 차이의 두 요청은 로드 밸런서에서 다른 서버로 갈 수 있고, 두 서버 모두 좌석이 비어 있다고 읽은 뒤 각자 기록할 수 있다. 읽기와 쓰기 사이의 틈이다.

- 같은 좌석을 두 사용자가 동시에 선택
- 남은 좌석 수 같은 단일 카운터를 수만 요청이 동시에 갱신(갱신 손실과 단일 행 대기)
- 같은 사용자가 결제 버튼을 여러 번 눌러 다른 서버가 각자 결제사를 호출

로컬에서 한 번씩 눌러 보는 테스트는 이 틈을 재현하지 못한다. 막는 방법과 비용은 지점마다 따로 따진다. 검증 방법은 [[First-Come-Coupon-Patterns-Failure-and-Verification|선착순 이벤트 경계 실패와 검증]]을 본다.

### 2. 외부 호출과 실패 시 동작

우리 서버가 부르는 외부 시스템마다 누구를 부르는지, 어떻게 실패하는지, 실패하면 무엇을 하는지를 표로 남긴다.

| 호출 대상 | 실패 모양 | 실패 시 동작의 쟁점 |
| --- | --- | --- |
| 결제사 | 응답 없음, 지연(가정: 평소 0.5초가 5~10초), 승인됐는데 응답 유실 | 응답 없음과 응답 유실은 서버에서 같아 보인다. 좌석을 풀면 돈만 나간 실패가, 붙잡으면 미결제 좌석 묶임이 생긴다 |
| 소셜 로그인 | 오픈 직전 로그인 집중으로 외부 인증 지연이나 제한 | 로그인 단계에서 막히면 예매 기회 자체를 잃는다. 제공자별 한도와 차단 정책은 공식 문서에서 확인한다 |
| 문자 발송 대행 | 실패나 지연 | 예매는 이미 끝났으므로 문자가 실패해도 예매를 취소하지 않는다 |

같은 외부 호출이라도 실패의 무게가 다르다. 결제 실패는 예매 취소로 이어지지만 알림 실패는 예매를 유지하고 따로 재발송한다. 결제 응답이 사라졌을 때의 처리는 한 줄로 답이 나오지 않으므로 칸을 비워 두더라도 질문을 목록에 남긴다. Stripe 같은 일부 결제 API는 연결 오류 뒤 같은 멱등 키로 안전하게 다시 요청할 수 있다고 설명한다. 다만 같은 키의 재요청은 조회가 아니어서, 첫 요청이 도달하지 않았다면 재요청 시점에 승인이 실행된다. 설계 제안: 결제 결과가 확정될 때까지 선점을 풀지 않거나, 선점 만료 뒤 승인이 확인되면 취소한다. 재요청은 선점이 유효한 동안에만 하고 그 뒤에는 원거래 조회나 취소로 결과를 확정한다. 원 요청이 아직 처리 중이면 조회 결과 없음이 미승인의 증거가 아니다. 공급자마다 키 조건과 조회 방법이 다르므로 [[Payment-Unknown-Outcome-and-Reversal|결제 결과 미확인과 망취소]]와 [[Idempotency-Key|멱등 키]]를 본다.

### 3. 숫자로 정해진 자원 한도

평소에는 보이지 않다가 한도에 닿는 순간 한꺼번에 무너지는 자원이다.

| 자원 | 역산 예시(가정) | 연결되는 한도 |
| --- | --- | --- |
| 커넥션 풀 | 풀 10개, 쿼리 20ms면 서버 한 대가 초당 500쿼리. 사용자당 요청 1건, 요청당 쿼리 1개로 보면 50만 요청은 1,000초(약 16분 40초) | 서버를 100대로 늘리면 10초로 줄지만 DB에는 연결 1,000개와 초당 5만 쿼리가 새 한도가 된다. PostgreSQL `max_connections` 기본값은 보통 100이다 |
| 결제사 처리량 | 가맹점 한도가 초당 200건이면 5만 건 결제에 250초 | 좌석 선점 제한 시간이 2분이면 뒤쪽 사용자는 결제 전에 선점이 풀린다. 선점 시간과 결제 처리량을 함께 정한다 |
| 문자 발송 한도 | 초당 100통이면 5만 통에 500초 | 사용자를 기다리게 할 일이 아니므로 비동기로 늦게 보내도 된다 |
| 서버 메모리 | 대기 요청 하나 50KB. 결제사가 멈춘 동안 초당 500건씩 쌓이면 5분에 15만 개, 7.5GB | 메모리 4GB는 약 8만 건(약 160초)에서 찬다. 동시에 붙잡을 요청 수에 상한을 둔다 |

외부 API 한도는 서비스마다 다르다. 예를 들어 Stripe는 라이브 모드 계정 전체 한도를 초당 100요청, 별도 표기가 없는 개별 엔드포인트를 초당 25요청, 동시 처리 중 요청을 기본 50개로 안내하고 초과하면 429를 돌려준다. 단일 결제 엔드포인트 기준이면 5만 건에 최소 2,000초가 걸린다. 응답이 2초를 넘으면 동시 처리 50개 한도가 먼저 차서 더 길어진다(지연 5~10초면 초당 5~10건). 예정된 대형 행사는 한도 증설을 미리 요청하는 대상이며, 큰 폭의 증설은 최소 6주 전에 요청하라고 안내한다(2026-11-25 확인). 실제 계약의 한도는 결제사와 가맹점 조건에서 확인한다. 캐시 서버나 본인 인증처럼 기능이 늘면 해당 목록의 줄도 늘린다.

세 목록은 로컬 개발의 세 가지 착각과 짝을 이룬다. 요청은 하나씩 온다(동시 요청), 네트워크는 늘 답한다(외부 호출), 자원은 충분하다(자원 한도).

## 목표의 재정의

오픈 순간의 목표는 50만 명을 모두 성공시키는 것이 아니다. 좌석을 가져갈 5만 명은 문제없이 성공시키고, 나머지에게는 최대한 빨리, 정확하게 매진을 알리며, 돈만 나가고 좌석이 없는 사용자를 최종 상태에 한 명도 남기지 않는 것이다. 외부 결제와 내부 DB는 원자적으로 묶이지 않으므로 이 목표는 대사와 취소로 수렴시키는 최종 상태 기준이다.

## 체크포인트

- 진입 계층은 피크 1초에서, 입장 제어 뒤 계층은 입장률과 계약 한도에서 역산했는가(일 평균이 아닌가)
- 실패 응답이 빨리(앞단 판정), 정확하게(사유와 다음 행동) 나가는가
- 결제 결과 불명 상태에서 좌석을 풀지, 붙잡을지, 어떻게 확정할지 정했는가
- 앱 서버 증설이 DB 연결 수와 외부 API 한도를 넘기지 않는가
- 세 목록이 코드 옆 문서로 남아 있고 기능이 늘 때 갱신되는가
