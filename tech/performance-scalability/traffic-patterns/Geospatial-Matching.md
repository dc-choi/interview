# 실시간 위치 기반 매칭 (공간 분할)

주문과 배달원처럼 **움직이는 두 집합을 실시간으로 짝짓는** 문제. 지역을 나눠 계산하면 병렬화가 쉬워 보이지만, 공간은 단순 파티셔닝만으로 나뉘지 않는다. 경계 문제와 동시 계산 충돌을 함께 설계해야 한다.

## 공간은 단순 파티션보다 어렵다

지역을 행정구역이나 격자로 딱 잘라 각 구역을 독립 계산하면 **경계 문제**가 생긴다.

- 주문은 A구역, 가장 가까운 배달원은 바로 옆 B구역에 있으면, 구역을 잘라 계산했을 때 서로 보이지 않는다.
- 매칭은 "내 구역 안"이 아니라 "일정 반경 안"의 후보를 함께 봐야 한다. 즉 계산 단위(구역)와 탐색 범위(반경)가 어긋난다.

그래서 공간 분할은 데이터를 나누는 것(where)뿐 아니라 **언제 계산할지(when)**까지 설계해야 안정적이다.

## H3 — 육각형 격자 인덱싱

지구 표면을 주로 육각형 셀로 나누는 공간 인덱싱 라이브러리(Uber). 위치(위도, 경도)를 셀 ID로 변환해 공간 계산의 단위로 쓴다. 다음 H3 설명은 2026-10-08에 확인한 4.x 공식 문서 기준이다.

- **해상도 계층**: 해상도는 0~15이고 숫자가 커질수록 셀이 작아진다. 육각형 부모의 바로 아래 논리적 자식은 7개지만 부모의 지리적 경계와 자식들의 합집합은 정확히 일치하지 않는다. 각 해상도에는 오각형 12개도 있다.
- **육각형의 장점과 한계**: 평면 정육각형은 사각형의 변 방향과 대각선 방향처럼 이웃 거리가 갈리지 않는다. 다만 실제 H3는 구면 투영 격자이므로 전 지구의 셀 크기나 이웃 중심 거리가 같다는 보장은 없다.
- **grid disk, 이전 k-ring**: `gridDisk(origin, k)`는 격자 이동 거리 k 이내의 이웃을 구한다. k는 km 단위 반경이 아니다. 큰 k에서는 결과가 O(k²) 규모로 늘 수 있어 상한이 필요하다. 정확한 원형 반경 검색은 누락 없이 후보를 덮는 셀 집합을 구한 뒤 실제 거리로 다시 거른다.
- 격자 ID는 정수라, R-Tree 같은 공간 인덱스 없이 **정수 인덱스, 해시 키**로 조회를 단순화할 수 있다.

H3만 쓴다고 경계 문제가 사라지지는 않는다. 이웃 셀과의 겹침, 계산 순서, 동시 처리 충돌을 함께 봐야 한다. (DB 저장, 배송 영역 판별 관점의 H3는 [[Spatial-Index-MySQL#사례: 쿠팡 로켓배송 — H3 공간 색인|공간 색인]] 참고.)

## 위치 기반 피드: 쓰기 복제와 읽기 fan-out

셀별 최신 콘텐츠 목록을 미리 만들면 조회 시 공간 조건을 셀 ID 목록으로 바꿀 수 있다. 여러 해상도의 목록을 저장하면 넓은 범위는 거친 셀로, 경계는 세밀한 셀로 조회하는 설계가 가능하다. 이는 쓰기 시 복제 비용을 지불하고 읽기 시 여러 목록을 병합하는 교환이다.

- 조회 셀 수와 셀별 반환 건수를 함께 제한한다. 셀 수만 제한해도 payload 크기, 재조회 횟수와 동시 요청에 따라 총비용은 달라진다.
- `compactCells`는 같은 해상도의 셀 집합에서 완성된 자식 묶음을 재귀적으로 부모 ID로 줄인다. 압축된 부모 키를 읽으려면 쓰기 경로도 공통 기준 해상도의 셀에서 `cellToParent`로 상위 키를 만들어야 논리적 포함 관계가 맞는다. 좌표를 해상도마다 독립 변환한 결과가 같은 계층이라고 가정하지 않는다.
- 거친 셀에 조회가 집중되면 [[Hot-Partition|핫 파티션]]과 네트워크 대역폭을 함께 본다. 요청 수가 줄어도 목록당 응답이 커지면 전송량은 늘 수 있다.

### 적게 읽고도 최신 목록을 보존하는 조건

각 셀에서 최종 페이지 크기만큼 모두 읽으면 많은 후보를 버릴 수 있다. 먼저 일부만 읽고, 병합 결과의 마지막 순위보다 앞서는 미조회 후보가 남을 수 있는 셀만 추가 조회한다. 이 방식은 모든 셀을 충분히 읽은 기준 결과와 비교해 검증한다.

1. 각 목록은 같은 정렬 기준을 쓴다. 같은 시각의 항목은 ID 등으로 순서를 결정하고, 중복 제거와 필터 규칙도 통일한다. 동일 ID의 정렬값은 모든 목록에서 같아야 한다.
2. 1차 조회를 병합한 뒤 페이지가 찼으면 마지막 항목을 cutoff로 잡는다. 페이지가 부족하면 아직 끝나지 않은 목록을 더 읽는다.
3. 소진되지 않은 목록에서 마지막으로 읽은 항목이 cutoff보다 앞서면 더 좋은 후보가 남을 수 있다. 아직 항목을 읽지 못한 목록도 확인한다. 해당 셀을 이어 읽고 병합과 cutoff 계산을 반복한다. 필터나 저장소의 응답 제한으로 요청보다 적게 반환될 수 있으므로, 짧은 응답만으로 소진을 단정하지 않고 cursor와 저장소의 종료 조건을 확인한다.
4. 모든 미조회 구간이 cutoff보다 뒤이거나 목록이 소진됐을 때 끝낸다. 재조회 상한으로 먼저 멈췄다면 정확한 상위 목록을 보장한다고 하지 않는다.

이 조건은 비교 중 목록이 고정됐거나 일관된 스냅샷을 읽는 경우를 전제로 한다. 실시간 추가와 삭제가 있는 저장소에서는 중복, 누락의 허용 범위와 페이지 일관성을 별도로 정해야 한다. 특정 셀에 항상 일정 비율만 읽거나 추가 조회 한 번만으로 정확성을 보장할 수는 없다.

## 시간 분할 — 경계 충돌을 시간으로 푼다

모든 지역을 **동시에** 계산하면, 인접한 두 구역이 같은 배달원을 동시에 후보로 잡아 이중 배차하는 충돌이 생긴다.

해법은 공간을 여러 그룹으로 나눠 **시간 순서로 처리**하는 것.

- 예: 전체 격자를 7개 그룹으로 나누고, 짧은 주기 안에서 1번 → 2번 → 3번 그룹 순으로 계산.
- 서로 인접해 후보가 겹칠 가능성이 큰 영역이 **같은 시각에 계산되지 않도록** 그룹을 배치(체스판처럼 인접끼리 다른 그룹).
- 후보가 겹치는 모든 작업을 직렬화하고 이전 계산이 끝난 뒤 다음 그룹을 실행하면 충돌을 줄일 수 있다. 작업 지연, 재시도와 그룹 간 후보 중첩이 남는다면 별도의 원자적 배차 확정이 필요하다. 고정된 그룹 수만으로 락이 불필요해지는 것은 아니다.

공간 분할 + 시간 분할을 합치면, "어느 격자를(공간) 언제(시간) 누가(파티션, 인스턴스) 계산하는가"가 모두 정해진다.

## Kafka Streams와의 결합

이 매칭 계산을 [[MQ-Kafka-Streams|Kafka Streams]]로 구성한다면 다음처럼 상태와 키를 나눌 수 있다.

- 주문, 배달원 위치 이벤트를 **H3 셀 ID를 키로** 발행 → 같은 셀 이벤트가 같은 파티션에 모여 지역 지역성 확보.
- 셀별 현재 주문 수, 후보 배달원 목록을 **상태 저장소**에 누적 → 매번 DB 조회 없이 최신 상황판 유지.
- 시간 분할 그룹은 스케줄, 윈도우와 맞물려 처리 순서를 제어.

단, H3 셀을 키로 삼을 때 특정 도심 셀에 트래픽이 몰리는 [[Hot-Partition|핫 파티션]] 위험이 있다. 셀 해상도, 키 조합으로 분산을 조정해야 한다.

## 면접 체크포인트

- 지역을 격자로 잘라 독립 계산하면 왜 문제인가 → 경계의 후보를 놓친다
- H3의 장점과 경계 → 이웃 탐색과 계층 연산, 구면 왜곡과 근사 포함은 별도 고려
- 공간 그룹의 시간 분할만으로 충돌이 없어지는가 → 후보 중첩, 작업 지연, 재시도와 최종 배차 확정까지 확인
- 셀 목록을 적게 읽으면서 최신순을 보존하려면 → 공통 정렬과 cutoff, 미조회 구간 검증, 일관된 조회 시점
- 위치를 파티션 키로 쓸 때의 리스크 → 도심 셀 핫 파티션
