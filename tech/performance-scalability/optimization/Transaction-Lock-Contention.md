# 트랜잭션경합과Lock문제

> 출처: [[Elegant-OOP-Design|우아한 객체지향]]

## 문제: 객체 그래프를 그대로 변경 경계로 삼을 때

객체 참조 자체가 트랜잭션이나 데이터베이스 lock 범위를 자동으로 넓히지는 않는다. 실제 범위는 애플리케이션의 트랜잭션 경계와 실행된 SQL, ORM의 flush, cascade, loading 방식, 데이터베이스의 locking과 isolation에 따라 정해진다. 다만 연관 객체를 한 유스케이스에서 함께 조회하고 수정하도록 모델링하면 넓은 트랜잭션과 더 많은 lock을 선택하기 쉬워진다.

### 예시:배달완료
배달 완료 처리에서 가게, 주문, 배달을 한 트랜잭션 안에서 모두 조회하고 수정하면:
- 3개 도메인을 **하나의 트랜잭션**으로 처리하게 됨
- 각 도메인의 **변경 빈도가 다름** (주문은 자주, 가게 정보는 드물게)
- 실제 SQL이 갱신하거나 명시적으로 잠근 row에 lock이 걸림. 단순히 객체가 참조됐다는 이유만으로 lock이 생기지는 않음

### 추가문제
- **N+1 문제**: 어디까지 조회할 것인가? (Lazy Loading의 함정)
- **결합도**: 참조로 연결된 모든 객체를 따라가서 기능을 구현하게 됨

## 해결방법

### 1.Aggregate경계분리
- 반드시 함께 일관성을 지켜야 하는 객체만 하나의 변경 경계로 묶기
- 경계 안: 객체 참조 / 경계 밖: **ID + Repository**
- 트랜잭션 범위가 줄어들어 Lock 경합 감소

### 2.도메인이벤트
- Aggregate 간 통신을 이벤트로 분리
- 주문 완료 → 이벤트 발행 → 가게, 배달이 각자 처리
- 각 도메인이 **독립적인 트랜잭션**으로 동작

### 3.시스템분리
- 도메인별로 패키지를 잘게 쪼개면 시스템 단위 분리 가능
- 시스템 간에는 **메시지 브로커**를 통한 이벤트 기반 통신

## 면접포인트
- "트랜잭션 범위를 어떻게 결정하나?" → Aggregate를 일관성 판단 단위로 삼되 실제 SQL과 lock 범위를 함께 확인
- "Lock 경합을 어떻게 해결하나?" → 경계 분리, 이벤트 기반 비동기 처리
- "MSA에서 트랜잭션 관리?" → Saga 패턴, 이벤트 기반 최종 일관성
