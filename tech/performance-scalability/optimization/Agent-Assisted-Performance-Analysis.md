# 에이전트를 활용한 성능 분석과 검증

에이전트 성능 분석은 실행 중 수집한 프로파일을 코드 위치와 연결하고 수정 후보를 만드는 흐름이다. 분석 결과가 그럴듯하다는 판단과 수정 후 서비스가 개선됐다는 측정은 별도로 다룬다.

## 프로파일의 측정 단위부터 확인한다

Flame graph는 호출 스택을 계층으로 보여 준다. 일반적인 CPU flame graph에서 프레임의 폭은 수집한 스택에 해당 프레임이 나타난 빈도를 나타내며, 가로축은 시간 순서가 아니다. 부모 프레임의 폭에 포함된 자식의 비용과 부모 자체의 실행 비용을 혼동하지 않는다.

에이전트에 프로파일을 전달할 때 다음 정보를 함께 남기는 방식을 제안한다.

- 수집한 이벤트가 CPU 실행, 메모리 할당 또는 대기 중 무엇인지.
- 수집 기간, 부하 조건과 실행 중인 코드 버전.
- 함수명과 소스 위치의 대응, 분석에서 제외한 구간.
- 관측된 현상과 원인 가설, 추가로 확인할 측정.

넓은 프레임을 찾았다는 사실만으로 제거 가능한 낭비를 발견했다고 결론 내리지 않는다. 그 경로가 수행해야 할 업무와 호출 조건을 소스에서 확인한다. CPU 프로파일만으로 전체 요청의 대기 시간을 설명했다고 보지도 않는다.

## 발견, 수정과 검증을 분리한다

다음은 프로파일 분석을 변경 절차에 연결하기 위한 설계 제안이다.

| 단계 | 남길 근거 | 다음 단계로 넘기기 전 확인 |
|---|---|---|
| 발견 | 프로파일, 코드 버전과 호출 경로 | 어떤 자원을 얼마나 쓰는지와 분석 범위 |
| 수정 후보 | 변경 코드와 예상 효과 | 입력, 출력과 오류 처리 계약을 보존하는지 |
| 기능 확인 | 관련 테스트와 실패 사례 | 빨라져도 결과가 달라지지 않는지 |
| 제한 배포 | 카나리와 대조군의 측정 | 지연, 오류와 자원 사용에 회귀가 없는지 |
| 확대 판단 | 판정 기준과 측정 결과 | 확대 또는 롤백 조건을 충족했는지 |

Google SRE의 카나리 방식은 변경을 일부에 한시적으로 배포하고 대조군과 비교해 확대 여부를 판단한다. 서비스 전체의 오류율만 보면 작은 카나리 집단의 회귀가 가려질 수 있으므로 버전별 지표를 나누어 본다.

이를 성능 개선에 적용할 때는 처리량과 요청 구성이 비교 가능한지 먼저 확인하고, 성공 요청당 자원 사용과 지연 분포를 함께 본다. 요청 실패가 늘거나 처리한 요청이 줄어 CPU 사용량이 내려간 경우를 최적화 성공으로 처리하지 않는 검수 기준을 제안한다. 관측 기간과 중단 기준은 배포 전에 정한다.

## 공개 사례로 확인한 범위

P99 CONF 2026의 Netflix 발표 공개 소개는 운영 서비스에서 비효율을 찾고, 소스까지 추적하며, 수정을 제안하고 카나리 배포로 검증하는 에이전트 흐름을 설명한다. 모델의 확신보다 측정 결과를 기준으로 둔다는 설계 방향도 명시한다(2026-11-04 확인).

확인 범위는 공개 소개문이다. 등록이 필요한 발표 녹화, 내부 코드와 측정 원본은 확인하지 않았다. 개별 최적화의 개선 배수, 내부 패턴 저장소와 승인 절차는 이 소개만으로 확정하지 않는다. 위 표는 적용을 위한 설계 제안이며 해당 회사의 상세 구현을 복원한 것이 아니다.

## 검토할 질문

- 수정 후보의 근거를 프로파일과 정확한 코드 버전까지 추적할 수 있는가?
- 실행 계약을 보존하는지와 자원 사용을 줄였는지를 따로 검사했는가?
- 카나리와 대조군을 나눠 오류율과 지연을 확인했는가?
- 측정 실패나 불충분한 관측을 개선 성공으로 처리하지 않는가?
