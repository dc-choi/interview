# 부하 테스트 자동화

이 문서는 성능 테스트를 **파이프라인에서 자동으로 돌리고 자동으로 판정하는 방법**을 소유한다. 테스트 유형과 지표, 부하 모델, threshold 값을 SLO에서 역산하는 방법은 [[performance|성능 테스트]]가 정본이고, 도구 선택과 executor 설정은 [[Load-Test-K6|성능 테스트 도구]]가 정본이다. 여기서는 그 판정을 어느 단계에 걸고, 어떤 축으로 판정하며, CI 환경이 만드는 거짓 판정을 어떻게 걸러내는지만 다룬다.

## 파이프라인 어디에 거는가

k6 공식 자동화 가이드는 실행 지점을 세 갈래로 나눈다.

| 트리거 | 무엇을 돌리는가 | 목적 |
|---|---|---|
| 브랜치 변경마다 (PR) | smoke test — 최소 부하, 반복 1~3회 수준 | 스크립트가 깨졌는지와 최소 트래픽에서 동작하는지 |
| 스케줄 (야간, 정기) | baseline, average-load, stress, spike | 회귀 감지와 추세 기록 |
| 수동 트리거 | heavy stress, soak | 감독이 필요한 장시간 검증 |

가이드가 제시하는 자동 실행 빈도 예시는 staging 주 2~3회, 릴리스 직전 기간 하루 3회, production 주 1회다. 수동 QA 절차 예시는 soak test 분기 1회, heavy stress test는 중요한 계절 이벤트 2개월 전, heavy load test는 주요 release의 pre-release 환경 실행이다.

모든 PR에 전체 부하 시나리오를 거는 구성이 실패하는 지점은 세 가지다.

- **실행 시간** — 램프업을 포함한 평균 부하 테스트는 수십 분, soak는 수 시간이다. PR 피드백 루프의 예산을 넘는다.
- **대기열** — 부하를 받는 환경이 하나면 PR 두 개가 겹치는 순간 서로의 측정을 오염시킨다. 직렬화하면 이번엔 대기 시간이 피드백을 늦춘다.
- **비용** — 러너 시간과 대상 환경 인스턴스가 PR 수에 비례해 늘어난다.

[[Test-Pyramid|테스트 피라미드]]의 배포 파이프라인 스케치를 성능 축으로만 확장하면 PR 단계는 짧은 스모크 부하, merge 후 야간은 전체 시나리오와 추세 기록, 릴리스 전은 게이트 판정이 된다.

## 판정을 자동화하는 두 축

| 축 | 기준 | 잡는 것 | 놓치는 것 |
|---|---|---|---|
| 절대 임계값 | SLO에서 역산한 고정값 | SLO 위반 | SLO 안쪽에서 서서히 나빠지는 회귀 |
| 상대 회귀 | 직전 베이스라인 대비 증가율 | 이번 변경이 만든 열화 | 기준선이 함께 나빠지는 표류 |

- **절대 임계값**은 k6 threshold로 표현한다. 임계값을 만족하지 못하면 테스트가 실패 상태로 끝나고 0이 아닌 종료 코드가 나오므로 CI가 그대로 실패로 받는다. 값을 어떻게 정하는지는 [[performance#SLO 대비 판정 기준|성능 테스트]] 위임.
- **상대 회귀**는 k6가 내장으로 제공하지 않는다. 이전 실행의 요약 지표를 저장해 두고 이번 run과 비교하는 단계를 파이프라인에 따로 둬야 한다.
- 절대값만 걸면 p95 예산이 200ms일 때 120ms에서 190ms로 나빠져도 계속 통과한다. 원인이 된 커밋이 수십 개 쌓인 뒤 임계값을 넘는 순간에야 알게 되고, 그때는 어느 변경이 범인인지 좁힐 수 없다.
- 상대값만 걸면 매 릴리스 3%씩 나빠지는 변화가 각각은 통과한다. 20회 누적이면 약 81% 나빠지고 24회쯤 두 배가 된다. 베이스라인이 함께 따라 올라가므로 릴리스 태그 시점의 고정 베이스라인을 하나 더 두어야 이 표류가 드러난다.

## 결과 보존과 추세

- **run 단위 아티팩트** — 요약 지표와 로그를 커밋 SHA, 워크플로 run id와 함께 남긴다. 실패 판정이 났을 때 어느 커밋의 결과인지 되짚을 수 없으면 판정이 원인 추적으로 이어지지 않는다.
- **시계열 저장** — k6는 Prometheus remote write 출력을 지원한다. `K6_PROMETHEUS_RW_SERVER_URL`을 주고 `k6 run -o experimental-prometheus-rw`로 실행하면 시계열이 `k6_` 접두사로 적재되고, Prometheus 2.40.0 이상에서는 `K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true`로 trend를 네이티브 히스토그램에 매핑해 분위수 질의 정밀도를 높일 수 있다.
- **보존 정책** — k6 가이드는 오래된 결과의 삭제 정책을 정하되 비교 기준이 되는 핵심 결과는 남기라고 안내한다. 전량 보존은 스토리지 비용, 전량 삭제는 베이스라인 상실로 이어진다.
- **베이스라인 선택** — 직전 main run 하나를 기준으로 삼으면 그 실행의 노이즈가 그대로 기준이 된다. 최근 N회 롤링 중앙값은 노이즈에 덜 흔들리지만 서서히 나빠지는 추세를 함께 끌고 내려가므로, 위에서 말한 고정 베이스라인과 병행한다.
- **비교 조건** — k6 가이드는 동일한 워크로드, 동일 시나리오, 동일 테스트 데이터, 동일 환경에서 돌린 run끼리만 비교하라고 못 박는다. 스크립트를 손댄 run은 이전 베이스라인과 비교하지 않고 새 베이스라인을 다시 잡는다.

## CI 환경이 만드는 거짓 판정

- **공유 러너의 성능 변동** — GitHub 문서 기준 호스티드 표준 러너는 Linux x64에서 private 저장소가 2 vCPU와 8GB, public 저장소가 4 vCPU와 16GB다. 이 사양에서 부하 생성기를 돌리면 대상보다 생성기가 먼저 포화한다. 생성기가 병목인지 가려내는 절차는 [[performance#부하 생성기 자체 병목 확인|성능 테스트]] 위임. 러너 사양과 네트워크 위치가 실행마다 달라지면 절대 지연값은 커밋이 아니라 러너를 측정하는 값이 된다. GitHub도 고정 IP 대역이 필요한 경우 larger runner나 self-hosted를 권한다.
- **데이터 시드** — 매 실행을 동일한 데이터 상태에서 시작한다. 이전 run이 남긴 행이 누적되면 쿼리 지연이 코드 변경과 무관하게 증가해 상대 회귀 판정이 통째로 거짓이 된다.
- **워밍업 제외** — 램프업 구간은 판정 대상에서 뺀다. JIT 컴파일, 캐시 적재, 커넥션 풀 초기화가 섞인 구간을 함께 집계하면 p95가 위로 끌려간다.
- **환경 안정성** — k6 가이드는 staging과 pre-release 환경이 안정적이어야 결과가 일관된다고 명시하고, 워크로드 규모를 그 환경의 인프라에 맞춰 조정하라고 안내한다. 운영의 1/10 규모 환경에서 잰 절대값을 운영 SLO와 직접 비교할 수는 없다.

## 게이트 운영

- **등급 분리** — k6 가이드는 QA 스모크 테스트가 CI 흐름을 막고, pre-release와 staging 테스트는 비블로킹으로 두어 판단 근거로 쓰는 구성을 제시한다. 같은 문서가 검증 프로세스가 성숙하기 전에는 pass/fail 결과만으로 릴리스 신뢰성을 보장하지 말라고 덧붙인다.
- **알림 규칙** — 단일 실패가 아니라 연속 실패로 거는 편이 노이즈가 적다. 가이드의 예시도 6회 연속 실패 시 알림처럼 우선순위별 임계 규칙을 세우라는 형태다.
- **flaky 게이트의 붕괴 경로** — [[Test-Pyramid|테스트 피라미드]]의 flaky E2E 방치와 같은 기전이다. 성능 게이트는 통계 판정이라 더 쉽게 흔들리고, 재실행 한 번이면 통과하는 게이트는 곧 아무도 읽지 않는 빨간불이 된다.
- **재실행 정책** — 자동 재시도로 감추지 않는다. 재실행은 명시적 조작으로 두고 횟수를 기록해 flaky 비율 자체를 지표로 만든다. 임계값 여유를 늘려 무마하기 전에 실행 조건 고정을 먼저 시도한다.
- **소유자** — 게이트마다 실패를 받아보는 소유자를 정한다. 소유자가 없으면 재실행 버튼이 사실상의 소유자가 된다.
- **승격 경로** — 새 게이트는 경고로 도입하고 몇 주간 오탐률을 관측한 뒤 블로킹으로 올린다. 처음부터 블로킹으로 넣으면 첫 오탐 때 게이트가 통째로 제거된다.

## 흔한 실수

- 모든 PR에 전체 부하 시나리오를 걸어 대기열과 비용으로 곧 비활성화되는 구성
- 절대 임계값만 걸어 SLO 안쪽의 서행 회귀를 놓침
- 상대 회귀만 걸어 기준선이 함께 나빠지는 표류를 놓침
- 스크립트를 바꾼 run을 이전 베이스라인과 그대로 비교
- 공유 러너에서 잰 절대 지연값을 블로킹 게이트로 사용
- 워밍업 구간을 판정에 포함
- 실패 알림만 있고 게이트 소유자가 없음

## 면접 체크포인트

- PR 스모크와 야간 전체 시나리오를 트리거로 나누는 근거
- 절대 임계값과 상대 회귀를 함께 거는 이유와 각각이 놓치는 것
- 공유 러너에서 측정한 절대 지연값을 게이트로 쓸 수 없는 이유
- 베이스라인을 직전 실행으로 둘 때와 롤링 중앙값으로 둘 때의 트레이드오프
- flaky 성능 게이트를 블로킹으로 유지할지 판단하는 기준과 재실행 정책
- 성능 회귀를 커밋 단위로 되짚기 위해 무엇을 보존해야 하는지
