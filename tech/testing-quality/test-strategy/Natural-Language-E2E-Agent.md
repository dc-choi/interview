# 자연어 E2E 테스트 에이전트 — 셀렉터 대신 목표를 준다

스크립트형 E2E 도구(Espresso, UI Automator, Appium, Playwright)는 셀렉터와 단계를 사람이 코드로 명시한다. 자연어 E2E 에이전트는 로그인한 뒤 팝업이 뜨는지 확인하라는 문장을 받아, 모델이 화면을 읽고 다음 액션을 스스로 생성해 실제 기기나 에뮬레이터를 조작한다. 작성 비용이 낮고 UI 변경 내성이 높은 대신, 실행마다 경로가 달라질 수 있다. 여러 앱을 오가는 워크플로도 같은 방식으로 자동화된다.

## 동작 원리 — 세 단계

1. 화면 상태 획득: 접근성 트리를 우선 읽는다. 구조화된 텍스트라 토큰이 싸고 정확하며 좌표나 XPath 하드코딩보다 레이아웃 변경에 덜 깨진다. Canvas, Compose, Flutter 같은 커스텀 렌더링 UI에서는 스크린샷과 비전 모델로 폴백한다. 웹 자동화의 DOM 우선과 스크린샷 폴백과 같은 패턴이다. 별도 접근성 서비스로 화면을 읽으면 UiAutomation 연결을 점유하지 않아 다른 계측 도구와 충돌하지 않는다.
2. 행동 계획: 반응형 루프는 하나의 모델이 매 단계 관찰하고 사고하고 행동하며 히스토리를 압축한다. 계획형 워크플로는 작업 계획을 먼저 세우고 실행 전 안전 점검, 체크포인트 검증, 최종 리포트를 붙이며 멀티 에이전트 그래프로 구성된다.
3. 실행과 검증: 요소 인덱스를 우선 쓰고 없으면 좌표와 시각적 위치 추정으로 폴백한다. 실행 전에 타깃을 UI 트리와 대조하는 안전망을 둔다.

## 결정성 문제

모델이 매 실행마다 계획을 세우므로 같은 지시가 같은 액션 시퀀스를 보장하지 않는다. 회귀 테스트에서는 이 비결정성이 flaky test와 구분되지 않는다. 그래서 계획형 프로파일이 사전 계획, 안전 점검, 체크포인트 검증을 붙이고 실행 전 UI 트리 대조를 둔다. 결정성 부족을 검증 게이트로 보완하는 설계이며, 재현 가능한 테스트의 조건은 [[Deterministic-Test|Deterministic test]]를 따른다.

## 속도와 신뢰성의 트레이드오프를 프로파일로 노출

한 도구 기준으로 반응형은 단계당 약 3~5초, 계획형은 단계당 약 15~40초다. 100단계 워크플로면 계획형 한 케이스에 25~67분이 든다. 회귀 스위트의 실행 시간과 모델 API 비용이 실질 제약이므로, 탐색적 테스트와 버그 재현에는 반응형, 장기 워크플로와 회귀 검증에는 계획형을 배정하는 운영이 가능하다. 반응형은 작업 계획, 실행 전 안전망, 체크포인트 검증, 최종 리포트가 없다는 한계를 명시한다.

## 테스트 전략에서의 위치

- [[Test-Pyramid|테스트 피라미드]] 상단의 핵심 여정 소수에 쓴다. 스크립트형 E2E의 대체가 아니라, 작성 비용이 높은 탐색적 시나리오와 크로스 앱 흐름의 보완이다.
- 코딩 에이전트에 MCP 서버로 연결해 버그 재현과 에러 로그 분석에 쓰는 흐름이 있다. 실기기 풀은 [[Device-Farm|Device Farm]]이 다룬다.
- 벤치마크 수치(예: 한 벤치마크에서 99% 이상 완료)는 어떤 모델, 어떤 프로파일, 몇 회 시도 기준인지 없이는 인용하지 않는다. 실행 비용, flaky 비율, 반복 실행 간 결정성 측정치는 공개된 것이 없다.
- 에이전트가 스스로 쓴 테스트가 실제 버그를 놓치는 구조는 [[Agent-Test-Verification-Behavior|에이전트 검증 행동]]과 같은 축이다. 자연어 검증 지시도 무엇을 정답으로 볼지 사람이 정해야 한다.

## 사례 — ARTEMIS

Google이 공개한 오픈소스(Apache-2.0, Python) 도구로, 자연어로 Android 앱을 조작하고 테스트한다. 아래 기능 목록은 2026년 9월 README 기준이다. 접근성 헬퍼 서비스와 비전 폴백, Flash(반응형)와 Pro(계획형) 프로파일, 실행 전 UI 트리 대조 안전망, 실시간 화면 보기와 리플레이, CLI와 Python SDK, pytest와 CI 연동, MCP 서버를 제공한다. 여러 모델 공급자를 지원하고, USB 디버깅이 켜진 기기나 에뮬레이터와 모델 API 자격증명이 필요하다.

## 면접 체크포인트

- 자연어 E2E 에이전트가 접근성 트리를 우선하고 비전을 폴백으로 두는 이유를 말할 수 있는가.
- 스크립트형 E2E와의 트레이드오프(작성 비용과 변경 내성 대 결정성)를 설명할 수 있는가.
- 비결정성을 검증 게이트로 보완하는 설계와, 회귀 스위트에서 남는 문제를 말할 수 있는가.
- 단계당 시간과 API 비용이 CI 적합성을 어떻게 제한하는지 계산해 볼 수 있는가.
