# 요구사항 추적성

요구사항 추적성은 요구사항과 설계, 구현, 검증 근거의 연결을 유지하는 방법이다. 양방향으로 연결하면 요구사항에서 구현과 검증을 찾고, 구현이나 테스트에서 그 존재 이유인 요구사항으로 돌아갈 수 있다.

## 링크와 검증 결과를 구분한다

요구사항과 테스트가 연결됐다는 사실은 테스트가 실행됐거나 요구사항을 충족했다는 뜻이 아니다. 변경 영향 분석에는 연결 관계가, 완료 판단에는 해당 버전의 검증 결과가 필요하다.

다음은 일반 소프트웨어 프로젝트에 적용할 기록 예시다.

| 요구사항 | 구현 근거 | 검증 근거 | 상태 |
|---|---|---|---|
| 동일 요청을 재처리해도 작업은 한 번만 반영 | 중복 처리 방지 코드와 변경 버전 | 반복 요청 테스트의 실행 결과 | 결과 확인 전에는 미검증 |

요구사항이 바뀌면 연결된 설계, 코드와 테스트를 함께 검토한다. 역방향으로는 요구사항이 없는 구현, 목적이 불명확한 테스트를 찾아 유지 이유를 확인한다.

## 식별자와 컨텍스트를 바꿔도 근거를 연결한다

요구사항마다 고유 식별자를 두고 상위 요구사항이나 원천 문서를 연결한다. 같은 요구사항이 여러 상위 요구사항을 만족하면 본문을 중복 작성하기보다 한 항목에 관계를 여러 개 기록한다. 상위 근거가 없는 항목은 누락인지, 설계 결정에서 생긴 필요한 요구사항인지 검토하고 이유를 남긴다.

다음은 이 원칙을 컨텍스트별 요구사항 정리에 적용한 예시다. 특정 창고 시스템의 구현 사실이나 NASA가 정한 WMS 설계 절차가 아니다.

| 연결 단계 | 기록 예시 | 확인할 질문 |
|---|---|---|
| 원래 요구사항 | 적재 완료 뒤 재고 조회에 반영되어야 한다 | 누가 필요한 결과이며 완료 조건은 무엇인가? |
| 유스케이스 | 입고 컨텍스트의 적재 완료 처리 | 원래 요구사항 식별자로 돌아갈 수 있는가? |
| 설계 | 입고와 재고 컨텍스트 사이의 반영 흐름 | 시퀀스의 각 상호작용은 어떤 요구사항을 구현하는가? |
| 검증 | 재고 반영 여부와 실패 후 처리 결과 확인 | 해당 구현 버전에서 실행한 근거가 있는가? |

유스케이스에 코드만 붙이거나 시퀀스 그림을 생성하는 것으로 추적성이 완성되지는 않는다. 컨텍스트별로 요구사항을 재분류한 뒤에도 원래 요구, 설계와 검증의 연결을 점검한다. 액터의 목표와 정상, 대안 흐름을 적는 방법은 [[Layered-Clean-Hexagonal#유스케이스로 경계를 드러낸다|유스케이스로 경계 드러내기]]를 참고한다.

## 자동 문서 생성의 검토 경계

운영 적용 제안: 문서를 자동 생성해도 연결 대상의 버전, 누락된 검증과 실패 결과를 별도로 검사한다. 문서 분량이나 생성 속도를 완료 기준으로 삼지 않는다. 관계가 오래되었거나 잘못 연결됐으면 표를 채워도 변경 영향을 정확히 설명하지 못한다.

## 적용 범위

NASA SWE-052는 NASA 소프트웨어 분류에 따라 요구사항, 설계, 코드, 검증과 부적합 사항 사이의 추적 범위를 정한다. 여기서는 연결과 변경 영향 분석 원리를 참고한다. 이를 일반 서비스나 의료기기의 인증 요건으로 확대하지 않으며, 추적 표 작성만으로 규정 준수를 입증했다고 판단하지 않는다.
