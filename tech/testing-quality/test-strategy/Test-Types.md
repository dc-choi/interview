# 테스트 종류 — 레벨, 유형, 변경 관련 테스트를 축으로 나눠 고르기

스모크, 회귀, 인수, 성능, 보안 테스트처럼 흔히 나열되는 이름들은 한 줄에서 하나를 고르는 선택지가 아니다. ISTQB CTFL 실라버스 v4.0.1(2024-09-15)은 테스트 레벨(어느 범위를 개발의 어느 단계에서 보나), 테스트 유형(어떤 품질 특성을 보나), 확인 테스트와 회귀 테스트(수정 뒤 무엇을 다시 보나)를 따로 설명하고, 탐색 테스트는 테스트 기법으로 다룬다. 실라버스는 테스트 유형과 확인, 회귀 테스트를 모든 레벨에 적용할 수 있다고 보므로 하나의 테스트가 여러 축에 함께 속한다. 시스템 레벨에서 자동으로 반복하는 보안 회귀 테스트가 그런 예다(이 문서의 예). 아래 표의 변경 관련과 진입 판정은 이 문서가 붙인 축 이름이다.

## 축으로 정리한 테스트 이름

| 축 | 묻는 것 | 속하는 이름 |
|---|---|---|
| 테스트 레벨 | 어느 범위를 어느 단계에서 보나 | 컴포넌트(단위), 컴포넌트 통합, 시스템, 시스템 통합, 인수(UAT, 운영, 계약, 규제, 알파, 베타) |
| 테스트 유형 | 어떤 특성을 보나 | 기능, 비기능(성능 효율, 호환성, 사용성, 보안 등), 블랙박스, 화이트박스 |
| 변경 관련 | 수정 뒤 무엇을 다시 보나 | 확인 테스트, 회귀 테스트 |
| 기법 | 테스트를 어떻게 설계하나 | 탐색 테스트 같은 경험 기반 기법 |
| 진입 판정 | 본격 테스트를 시작해도 되나 | 스모크 테스트 |

## 테스트 레벨 — 인수 테스트의 자리

실라버스는 다섯 레벨을 설명한다. 컴포넌트 테스트(단위 테스트)는 컴포넌트를 격리해 보고(서비스 하나를 띄우고 다른 서비스를 대역으로 바꾸는 마이크로서비스의 [[Test-Pyramid-Component-Test|컴포넌트 테스트]]와는 다른 뜻이다), 컴포넌트 통합 테스트는 컴포넌트 사이의 인터페이스와 상호작용을 본다. 시스템 테스트는 시스템 전체의 동작과 품질 특성을, 시스템 통합 테스트는 대상 시스템과 다른 시스템, 외부 서비스의 인터페이스를 본다.

인수 테스트는 밸리데이션(validation, 사용자 요구 충족 여부의 확인)과 배포 준비 상태의 입증에 초점을 둔다. 시스템이 사용자의 업무 요구를 충족하는지 보는 것이며, 이상적으로는 실제로 쓸 사용자가 수행한다. 주요 형태로 사용자 인수 테스트(UAT), 운영 인수 테스트, 계약 인수 테스트와 규제 인수 테스트, 알파 테스트와 베타 테스트를 든다. 실라버스는 알파와 베타를 인수 테스트의 형태로 나열할 뿐 이 절에서 둘의 차이를 정의하지 않으므로, 누가 어떤 환경에서 미리 써 보는지는 출시 계획에 따로 적는다(운영 제안).

레벨은 테스트 대상, 목적, 테스트 베이시스, 찾으려는 결함과 장애, 접근 방식과 책임 같은 속성(비한정 목록)으로 구분한다. 순차 모델에서는 한 레벨의 종료 조건이 다음 레벨 진입 조건의 일부가 되도록 정하는 경우가 많지만 일부 반복 모델에서는 적용되지 않을 수 있다. 피라미드에서의 비중은 [[Test-Pyramid|테스트 피라미드]]가 다룬다.

## 테스트 유형 — 기능과 비기능

- **기능 테스트**: 대상이 무엇을 해야 하는지를 본다. 기능의 완전성, 정확성과 적절성을 확인한다.
- **비기능 테스트**: 시스템이 얼마나 잘 동작하는지를 본다. 실라버스는 ISO/IEC 25010의 분류로 성능 효율, 호환성, 사용성(interaction capability), 신뢰성, 보안, 유지보수성, 이식성(flexibility), 안전성을 든다.
- **블랙박스 테스트**: 내부 구조와 무관한 명세에서 테스트를 도출해 명세 대비 동작을 확인한다.
- **화이트박스 테스트**: 코드, 아키텍처, 워크플로와 데이터 흐름 같은 내부 구조에서 테스트를 도출해 구조를 충분히 커버하는 것이 목적이다.

네 유형은 모든 레벨에 적용할 수 있고 레벨마다 초점이 다르다. 2.2.2절의 목록은 테스트 이름이 아니라 품질 특성의 목록이다. 흔한 테스트 이름을 이 특성에 대면(이 문서의 해석) 성능과 부하 테스트는 성능 효율, 호환성 테스트는 호환성, 사용성 테스트는 사용성, 보안 테스트는 보안을 보는 비기능 테스트다. 접근성이라는 이름의 항목은 이 목록에 없고 실라버스가 대응 관계를 밝히지 않으므로 여기서는 분류하지 않는다. 부하 테스트의 설계와 판정은 [[performance|성능 테스트]]와 [[Load-Test-Automation|부하 테스트 자동화]]를 따른다.

많은 비기능 테스트는 같은 기능 테스트를 쓰면서 제약을 함께 확인한다(정해진 시간 안에 끝나는지, 새 플랫폼으로 옮겨도 동작하는지). 실라버스는 비기능 테스트를 리뷰나 컴포넌트 테스트처럼 이른 단계에서 시작하는 것이 적절할 때가 있다고 보고, 비기능 결함을 늦게 발견하면 프로젝트 성공에 심각한 위협이 될 수 있다고 설명한다. Shift left 절(2.1.5)도 가능하면 컴포넌트 레벨부터 비기능 테스트를 하라고 권한다. 반대로 사용성처럼 완성된 시스템과 대표성 있는 테스트 환경에서 보는 편이 나은 특성도 있고, 사용성 실험실 같은 전용 환경이 필요한 경우도 있다. 그래서 특성마다 언제 어디서 볼지를 따로 정한다(운영 제안).

## 변경 관련 — 확인 테스트와 회귀 테스트

- **확인 테스트(confirmation testing)**: 원래 결함이 고쳐졌는지 확인한다. 결함 때문에 실패했던 테스트를 다시 실행하거나, 수정에 필요했던 변경을 덮는 새 테스트를 더한다. 시간과 비용이 부족하면 장애를 재현하던 절차만 다시 실행해 장애가 나지 않는지 보는 수준으로 줄일 수 있다.
- **회귀 테스트(regression testing)**: 변경이 나쁜 결과를 일으키지 않았는지 확인한다. 이미 확인 테스트를 마친 수정도 대상이다. 영향은 변경한 컴포넌트, 같은 시스템의 다른 컴포넌트, 연결된 시스템과 환경까지 미칠 수 있으므로 먼저 영향 분석으로 범위를 정한다.

회귀 스위트는 반복 실행되고 반복과 릴리스마다 케이스가 늘어나므로 자동화의 유력한 대상이다. CI를 쓰면 자동 회귀 테스트를 함께 두는 것이 좋은 실천이다. 우선순위와 CI 게이트는 [[Regression-Test-Automation|회귀 테스트 자동화]]가 다룬다.

sanity test라는 이름은 실라버스 2.2절에 없고, 이 문서는 그 뜻을 ISTQB 용어집과 대조하지 않았다. 이 이름을 쓰는 팀은 그것이 확인 테스트를 뜻하는지 스모크 테스트를 뜻하는지 먼저 맞춘다(운영 제안).

## 스모크 테스트 — 본격 테스트의 진입 판정

실라버스는 진입 조건의 전형적인 예로 테스트 대상의 초기 품질 수준을 들고, 그 예시로 모든 스모크 테스트의 통과를 든다. 실라버스는 스모크 테스트 자체를 정의하지 않는다. 이 문서는 스모크를 계획한 테스트를 시작해도 되는지 판단하는 진입 관문으로 쓰고, 통과를 이후 테스트를 대신하는 품질 확인으로 해석하지 않는다(운영 제안). 배포 환경에서의 스모크 실행이 잡는 결함은 [[Test-Pyramid-Blind-Spots|초록불이 못 잡는 것]], 부하 스크립트의 PR 스모크는 [[Load-Test-Automation|부하 테스트 자동화]]가 다룬다.

## 탐색 테스트 — 배우면서 설계하는 기법

탐색 테스트는 테스터가 대상을 배우면서 테스트를 동시에 설계하고 실행하고 평가한다. 대상을 더 알아내고, 초점을 맞춰 깊이 탐색하고, 테스트되지 않은 영역의 테스트를 만드는 데 쓴다.

- **세션 기반으로 구조화할 수 있다**: 때로 세션 기반으로 진행하며, 정해진 시간 상자 안에서 테스트 목적을 담은 차터를 따르고, 끝난 뒤 보통 이해관계자와 결과를 논의하는 디브리핑을 한다. 따라간 절차와 발견은 세션 시트에 남길 수 있다.
- **쓸 때**: 명세가 적거나 부실할 때, 시간 압박이 클 때, 더 형식적인 기법을 보완할 때 유용하다. 경험과 도메인 지식이 있고 분석력과 호기심, 창의성을 갖춘 테스터일수록 효과가 크다.
- **다른 기법과 섞는다**: 동치 분할 같은 기법을 탐색 중에 함께 쓸 수 있다.

세션 기반으로 하면 시나리오 없이 써 보더라도 목적과 기록이 남는다. 세션에서 찾은 결함을 고친 뒤에는 재현 절차를 회귀 케이스로 옮겨 다음 변경에서 다시 확인한다(운영 제안).

## 상황별로 고르기 (운영 제안)

| 상황 | 먼저 | 이어서 |
|---|---|---|
| 새 빌드가 나왔다 | 스모크로 진입 판정 | 계획한 레벨별 테스트 |
| 결함을 고쳤다 | 확인 테스트 | 영향 분석으로 범위를 정한 회귀 테스트 |
| 출시해도 되는지 판단한다 | 해당하는 인수 테스트 형태(UAT, 운영, 계약, 규제, 알파, 베타) | 인수 기준과 결과의 추적([[Requirements-Traceability|요구사항 추적성]]) |
| 사용자가 몰릴 것으로 예상된다 | 성능과 부하 테스트 | 임계값 기반 CI 판정 |
| 명세가 부족하거나 시간이 없다 | 세션 기반 탐색 테스트 | 발견한 결함의 회귀 케이스화 |

## 면접 체크포인트

- 테스트 레벨과 테스트 유형이 서로 다른 축인 이유와, 둘을 함께 쓴 예
- 확인 테스트와 회귀 테스트의 차이, 회귀 범위를 영향 분석으로 정하는 이유
- 스모크 테스트를 진입 조건으로 두는 이유와 통과의 의미
- 탐색 테스트를 세션 기반으로 구조화하는 방법과 쓰기 좋은 조건
- 비기능 테스트를 늦게 시작할 때의 위험
