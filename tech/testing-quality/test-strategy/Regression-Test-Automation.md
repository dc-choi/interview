# 회귀 테스트 자동화 — 우선순위, 선택, CI 게이트

회귀 테스트는 기존 기능이 변경으로 깨지지 않았는지 확인한다. 수동으로 전체를 반복하면 릴리스마다 시간이 불어나 QA 기간이 길어지고 배포 주기를 늦춘다. 자동화의 목표는 모든 케이스를 자동화하는 것이 아니라, 변경마다 빠르게 도는 신뢰할 수 있는 회귀 그물을 CI에 두는 것이다.

## 무엇부터 자동화하나 — 우선순위

- 사용자 경험과 매출에 직접 영향을 주는 핵심 흐름부터 잡는다 — 로그인, 결제, 주문 같은 경로.
- 변경이 잦아 회귀 위험이 높은 영역.
- 수동으로 자주 반복해 누적 비용이 큰 케이스.
- 뒤로 미룰 대상: 거의 바뀌지 않거나 실패 파급이 작은 영역, UI 세부처럼 자주 깨져 유지비가 큰 케이스.

## 실행 비용과 테스트 선택

- 전체 스위트를 매 변경마다 돌리면 느려져 개발 흐름을 막는다. 변경 영향 분석으로 바뀐 코드와 연관된 케이스를 우선 돌리고, 전체 스위트는 야간이나 배포 전에 돌리는 계층화가 흔하다.
- 계층 비중은 피라미드를 따른다 — 느리고 깨지기 쉬운 E2E는 최소로, 단위와 통합에서 최대한 잡는다 ([[Test-Pyramid|테스트 피라미드]]).

## CI 통합 — 피드백 시점

- 회귀 스위트를 CI/CD 파이프라인에 넣어 머지 전 또는 배포 전에 자동 실행하고, 실패하면 배포를 막는 게이트로 둔다.
- 피드백이 빠를수록(수십 분 이내) 자동화가 개발 흐름을 방해하지 않는다. 느린 스위트는 병렬 실행과 선택 실행으로 시간을 줄인다.
- 부하와 성능 같은 비기능 회귀의 CI 판정은 [[Load-Test-Automation|부하 테스트 자동화]]가 다룬다.

## 유지 비용과 신뢰성

- 자동화 스위트도 부채가 된다. flaky 테스트는 초록불의 신뢰를 무너뜨리므로 시간, 난수, 외부 상태, 순서 의존을 통제한다 ([[Deterministic-Test|결정적 테스트와 flaky 대응]]).
- 실패 파급이 작은데 유지비만 큰 케이스는 자동화 대상에서 뺀다. 스위트는 늘리기만 하지 말고 가치 낮은 케이스를 정리한다.

## 반복 회귀와 새 결함 탐색을 구분한다

같은 테스트와 데이터만 반복하면 새로운 결함을 찾는 효과가 줄 수 있다. ISTQB CTFL v4.0.1의 `Tests wear out` 원칙은 기존 테스트와 데이터를 보완하거나 새 테스트를 추가할 필요를 설명하면서, 자동 회귀 테스트의 반복은 여전히 유익할 수 있다고 구분한다.

따라서 오랫동안 통과했다는 이유만으로 회귀 케이스를 지우지 않는다. 변경이 기존 기능에 미친 영향을 확인하는 역할과, 아직 시험하지 않은 조건을 탐색하는 역할을 함께 유지한다. 다음은 이 원칙을 적용한 점검 예시다.

- 기존 실패를 재현한 입력과 기대 결과는 회귀 사례로 보존한다.
- 요구사항이 바뀌거나 운영에서 결함을 놓쳤다면 누락된 경계값, 상태 전이와 입력 조합을 추가한다.
- 테스트 수와 연속 통과 횟수만 보지 않고, 현재 요구사항과 위험 중 시험하지 않은 조건을 확인한다.

이 절은 2026-10-15 공식 syllabus의 1.3절과 2.2.3절을 대조했다. 반복 테스트가 무용해진다거나 테스트 보강이 무결함을 보장한다는 뜻은 아니다.

## 운영 거래 기록을 재현해 회귀 기준을 만든다

거래가 원장(업무 데이터의 정본)을 누적해 바꾸는 시스템에서는 손으로 만든 케이스가 실제 거래 조합을 다 담기 어렵다. 운영에서 일어난 거래를 검증 환경에서 다시 돌려 결과를 비교하면 케이스 누락을 줄일 수 있다. 보험 코어 시스템 사례(2026년 9월 공급사 발표)의 흐름은 일곱 단계다.

1. 운영 환경에서 특정 시점의 주요 원장(계약, 보험, 급부 등)을 스냅샷으로 백업한다.
2. 그 뒤의 업무 거래 로그(계약자 변경, 보험료 입금, 해지, 지급 등)를 모은다.
3. 운영에서 처리된 결과로 정답지를 만든다.
4. 검증 환경에 백업 원장을 복구한다.
5. 거래 로그를 일괄 재현한다. API로 열린 업무 모듈을 그대로 호출하므로 검증용 로직을 따로 만들지 않는다.
6. 재현 결과로 결과지를 만든다.
7. 정답지와 결과지를 원장 항목(계약 상태, 입금 상태, 유지 연월), 계산 항목(환급금), 거래 내역(지급 금액)별로 비교하고 차이를 보고한다.

특이한 거래를 따로 저장해 두면 맞춤형 회귀 세트가 되고, 테스트 대상과 정답지를 직접 올리면 운영 로그가 없는 신상품에도 같은 도구를 쓸 수 있다. 업무 요건을 반영하기 전에 돌리면 변경 영향을 미리 확인할 수 있다.

설계 점검(해석):

- 정답지는 운영 결과일 뿐 올바른 결과의 증명이 아니다. 운영에 있던 결함도 기준이 되므로, 차이가 나면 회귀인지 의도한 수정인지 가르는 승인 절차를 둔다([[Legacy-Code-Testing#승인 테스트 Approval Test|승인 테스트]]).
- 시각, 채번, 외부 시스템 응답처럼 재현할 때마다 달라지는 값은 고정하거나 비교에서 정규화하고, 외부 기관 호출과 고객 알림 같은 부수효과는 검증 환경에서 막는다([[Shadow-Traffic#부수효과 차단이 전제조건|부수효과 차단]]).
- 운영 원장과 거래 로그에는 개인정보가 있으므로 검증 환경으로 복제할 때 가명 처리와 접근 통제를 함께 설계한다.
- 같은 계약에 대한 거래 순서가 결과를 바꾸면 재현 순서 규칙을 정한다.

### 계산 규칙은 외부 참값과 비교한다

보험료와 환급금처럼 상품 인가나 규제 제출용 산출 자료가 있으면 그 값을 참값으로 두고 시스템 계산식의 결과를 자동 비교한다. 같은 사례는 상품 기획 단계에서 가입 설계(시나리오)와 계산식을 검증하고, 출시 뒤에도 계산식이나 상품 정보가 바뀔 때마다 사전 저장한 참값과 비교한다. 신상품의 선후행 업무(입금, 지급, 출금)는 대체 상품 코드로 함께 시험한다. 참값 자료의 버전과 출처를 함께 관리하지 않으면 틀린 기준으로 통과시킬 수 있다(해석).

## 실행은 자동화해도 테스트 설계는 역량으로 남는다

AI가 테스트 케이스와 스크립트를 만들고 실행해도, 무엇을 얼마나 강하게 어떤 방법으로 시험할지 정하고 서비스와 정책이 바뀔 때마다 케이스를 갱신하는 일은 남는다. 배포가 잦아지고 케이스가 쌓일수록 이 설계와 갱신이 병목이 된다. 그래서 테스트 실행은 자동화하되 범위, 강도, 방법의 정의와 케이스 설계, 갱신 체계를 따로 키우고 회귀 자동화를 전담 운영하는 방식이 제시된다(2026년 9월 유통사와 IT 서비스사의 공동 발표). 이 역할을 외부 조직에 맡기는 구조는 [[AI-Era-IT-Outsourcing|AI 시대 IT 아웃소싱]]에서 다룬다.

## 사례

한 커머스 QA 팀은 수동 회귀에 하루 넘게 걸리던 부담을, 사용자 영향이 큰 기능의 회귀 케이스부터 자동화하고 CI/CD에 통합해 배포 전 자동 실행으로 바꿔 회귀 소요를 크게 줄였다. 시작점을 전체가 아니라 사용자 영향이 큰 흐름으로 잡은 것이 핵심이다.

- 한 유통사는 상시 확인하는 테스트 케이스가 1.5만 개이고 하루 1회 이상 배포하며 정책이 바뀔 때마다 설계와 갱신이 필요해 계속 늘 것으로 본다고 밝혔다(2026년 9월 발표).
- 같은 발표에서 IT 서비스사는 테스트 자동화 전문 인력 60여 명이 12개 프로젝트를 상시 수행하며 자동화 테스트 케이스 58,000개 이상을 운영하고, 한 업무 포털 GUI의 회귀 테스트 2만 개를 하루 안에 끝낸다고 밝혔다. 업무 로직 기반 케이스 자동 생성으로 시간 70%, 생성과 실행, 자가 수정을 반복하는 스크립트 생성으로 20%를 줄였다고 했지만 기준 시간과 측정 방법은 공개되지 않았다.

## 면접 체크포인트

- 무엇부터 자동화할지의 우선순위 기준 — 사용자 영향, 변경 빈도, 반복 비용.
- 전체 스위트가 느릴 때의 계층화 — 영향 분석 기반 선택 실행과 전체 야간 실행.
- 자동화 스위트의 유지 비용과 flaky 대응.
