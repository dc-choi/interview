# 회귀 테스트 자동화 — 우선순위, 선택, CI 게이트

회귀 테스트는 기존 기능이 변경으로 깨지지 않았는지 확인한다. 수동으로 전체를 반복하면 릴리스마다 시간이 불어나 QA 기간이 길어지고 배포 주기를 늦춘다. 자동화의 목표는 모든 케이스를 자동화하는 것이 아니라, 변경마다 빠르게 도는 신뢰할 수 있는 회귀 그물을 CI에 두는 것이다.

## 무엇부터 자동화하나 — 우선순위

- 사용자 경험과 매출에 직접 영향을 주는 핵심 흐름부터 잡는다 — 로그인, 결제, 주문 같은 경로.
- 변경이 잦아 회귀 위험이 높은 영역.
- 수동으로 자주 반복해 누적 비용이 큰 케이스.
- 뒤로 미룰 대상: 거의 바뀌지 않거나 실패 파급이 작은 영역, UI 세부처럼 자주 깨져 유지비가 큰 케이스.

## 실행 비용과 테스트 선택

- 전체 스위트를 매 변경마다 돌리면 느려져 개발 흐름을 막는다. 변경 영향 분석으로 바뀐 코드와 연관된 케이스를 우선 돌리고, 전체 스위트는 야간이나 배포 전에 돌리는 계층화가 흔하다.
- 계층 비중은 피라미드를 따른다 — 느리고 깨지기 쉬운 E2E는 최소로, 단위와 통합에서 최대한 잡는다 ([[Test-Pyramid|테스트 피라미드]]).

## CI 통합 — 피드백 시점

- 회귀 스위트를 CI/CD 파이프라인에 넣어 머지 전 또는 배포 전에 자동 실행하고, 실패하면 배포를 막는 게이트로 둔다.
- 피드백이 빠를수록(수십 분 이내) 자동화가 개발 흐름을 방해하지 않는다. 느린 스위트는 병렬 실행과 선택 실행으로 시간을 줄인다.
- 부하와 성능 같은 비기능 회귀의 CI 판정은 [[Load-Test-Automation|부하 테스트 자동화]]가 다룬다.

## 유지 비용과 신뢰성

- 자동화 스위트도 부채가 된다. flaky 테스트는 초록불의 신뢰를 무너뜨리므로 시간, 난수, 외부 상태, 순서 의존을 통제한다 ([[Deterministic-Test|결정적 테스트와 flaky 대응]]).
- 실패 파급이 작은데 유지비만 큰 케이스는 자동화 대상에서 뺀다. 스위트는 늘리기만 하지 말고 가치 낮은 케이스를 정리한다.

## 반복 회귀와 새 결함 탐색을 구분한다

같은 테스트와 데이터만 반복하면 새로운 결함을 찾는 효과가 줄 수 있다. ISTQB CTFL v4.0.1의 `Tests wear out` 원칙은 기존 테스트와 데이터를 보완하거나 새 테스트를 추가할 필요를 설명하면서, 자동 회귀 테스트의 반복은 여전히 유익할 수 있다고 구분한다.

따라서 오랫동안 통과했다는 이유만으로 회귀 케이스를 지우지 않는다. 변경이 기존 기능에 미친 영향을 확인하는 역할과, 아직 시험하지 않은 조건을 탐색하는 역할을 함께 유지한다. 다음은 이 원칙을 적용한 점검 예시다.

- 기존 실패를 재현한 입력과 기대 결과는 회귀 사례로 보존한다.
- 요구사항이 바뀌거나 운영에서 결함을 놓쳤다면 누락된 경계값, 상태 전이와 입력 조합을 추가한다.
- 테스트 수와 연속 통과 횟수만 보지 않고, 현재 요구사항과 위험 중 시험하지 않은 조건을 확인한다.

이 절은 2026-10-15 공식 syllabus의 1.3절과 2.2.3절을 대조했다. 반복 테스트가 무용해진다거나 테스트 보강이 무결함을 보장한다는 뜻은 아니다.

## 사례

한 커머스 QA 팀은 수동 회귀에 하루 넘게 걸리던 부담을, 사용자 영향이 큰 기능의 회귀 케이스부터 자동화하고 CI/CD에 통합해 배포 전 자동 실행으로 바꿔 회귀 소요를 크게 줄였다. 시작점을 전체가 아니라 사용자 영향이 큰 흐름으로 잡은 것이 핵심이다.

## 면접 체크포인트

- 무엇부터 자동화할지의 우선순위 기준 — 사용자 영향, 변경 빈도, 반복 비용.
- 전체 스위트가 느릴 때의 계층화 — 영향 분석 기반 선택 실행과 전체 야간 실행.
- 자동화 스위트의 유지 비용과 flaky 대응.
