# 에이전트 기반 검증

코딩 에이전트에 검사 수단을 제공하면 변경, 실행, 실패 분석과 수정의 반복을 구성할 수 있다. 성공 기준을 에이전트의 자기평가에만 맡기지 않고, 외부에서 관찰할 결과와 불변조건으로 표현한다.

## 검증 수단을 조합한다

| 수단 | 잡으려는 오류 | 한계 |
| --- | --- | --- |
| 핵심 E2E | 실제 사용자 흐름에서 연결되지 않은 기능, 로그인과 저장 실패 | 느리고 환경 의존적이므로 중요한 소수 흐름에 집중 |
| 속성 기반 테스트 | 예제로 빠뜨린 경계와 입력 조합 | 잘못된 속성과 좁은 생성 범위는 오류를 놓침 |
| 기존 구현과 비교 | 재작성에서 바뀐 계약과 출력 | 기존 버그까지 정답으로 복제할 수 있어 차이를 판단해야 함 |
| 성능 검사 | 지연, 처리량과 자원 회귀 | 비교 전제와 측정 방식이 다르면 결과를 해석할 수 없음 |

정렬 테스트라면 결과의 순서뿐 아니라 원소와 중복 개수 보존을 검사한다. 결제 같은 상태 변경은 한 요청의 반복 실행이 중복 차감하지 않는지도 검증한다. 테스트 개수를 늘리는 것보다 틀린 구현을 실제로 거절하는 판정식이 중요하다.

기능이 다른 기능과 겹치는 문맥이 많아 사람이 시험 사례를 열거할 수 없는 시스템에서는 LLM 보조 퍼징이 조합 결함을 빨리 찾는다는 보고가 있다. 다만 발견이 늘면 고칠 사람의 시간이 먼저 바닥날 수 있으므로 발견과 수정 용량을 함께 계획한다([[AI-Code-Delegation-Review-Fix-Capacity#AI 리뷰가 결함을 더 빨리 찾으면 수정 용량이 병목이 된다|PostgreSQL 19 사례]]).

## 반복을 끝내는 조건

1. 요구사항과 변경 전 기준선을 정한다.
2. 에이전트가 제한된 환경에서 구현과 검사를 반복한다.
3. 실패 입력, 명령, 실행 환경과 결과를 남긴다.
4. 테스트 삭제나 기대값 변경으로 통과시키지 않았는지 별도로 검토한다.
5. 확인하지 못한 외부 연동과 비결정적 결과를 완료 보고에서 분리한다.

별도 검토자도 같은 잘못된 전제를 물려받을 수 있다. 검토자 수나 테스트 통과를 전체 정확성의 증명으로 삼지 않는다. 빠른 로컬 검사와 실제 CI/배포 환경의 검사를 연결한다.

## TDD 절차, 검증력과 비용을 따로 잰다

테스트를 먼저 썼는지와 틀린 구현을 거절하는지는 다른 질문이다. Red가 나와도 요구한 동작의 실패인지, import나 환경 오류인지 확인해야 한다. 기대값을 구현 함수로 다시 계산하면 같은 오류를 정답에도 복제할 수 있다.

2026-11-03 대조한 Birgitta Böckeler의 탐색 실험은 Sonnet 4.6으로 작은 신규 비즈니스 로직 과제를 구현하고, 생성 방식을 가린 Opus 4.8로 결과를 비교했다. 다섯 비교 묶음은 TDD와 비TDD 결과를 각각 두 개씩 포함하지만, 중간 과제의 후속 두 묶음은 최초 비TDD 코드베이스를 재사용했다. 따라서 중간 과제의 독립 실행 수는 비TDD 2회, TDD 6회다. 한 묶음에는 단순 테스트 선작성 두 번을 추가했다. TDD의 설계나 변이 점수 우위를 확인하지 못했지만, 표본이 작고 품질 판단을 대부분 LLM에 맡겼으며 어느 실행도 TDD를 완벽히 따르지 않았다. 이를 모든 에이전트에서 TDD가 해롭다는 결론으로 확대하지 않는다.

부록의 TDD/비TDD 평균 토큰 배수는 작은 과제 8.50배, 중간 과제 2.96배, 큰 과제 4.89배다. 여기서 합계는 `input + output + cacheRead + cacheWrite`이며 매 턴 누적 문맥을 다시 읽은 양도 센다. 저렴한 캐시 읽기와 새 토큰을 같은 무게로 합쳤으므로 실제 청구액 배수가 아니다. 세 단계로 나뉜 절차라는 이유만으로 비용이 최소 세 배라고 계산할 수도 없다.

적용할 때는 절차 준수 로그, 회귀를 잡는 테스트, 책임 경계와 변경 용이성, 토큰 종류별 사용량을 각각 비교한다. 이 실험은 장기 유지보수 효과나 다른 모델의 성능을 검증하지 않았고, 여기서 재현하지 않았다.

## 검증 계층을 변경이 닿지 않는 곳에 둔다

Claude Code 팀은 코드의 약 90%를 Claude가 쓰고 리뷰한다고 밝히며, 사람이 모든 diff를 읽는 대신 에이전트가 실행 결과로 작업을 입증하게 하는 운영을 2026-11-16에 공개했다. 2026-11-18 원문과 대조했다. 한 팀의 자체 보고이고 효과 수치는 아래 하나뿐이다.

- **변경한 앱을 실제로 실행한다**: 시뮬레이터나 앱을 띄우고 조작하는 방법을 `verify` 스킬로 적어 저장소의 `.claude/skills/`에 관련 코드와 가깝게 두고, 필요한 만큼 여러 개 만든다. Claude는 커밋 전에 이 스킬을 쓴다. 팀은 이 스킬을 smoke test 하네스로 보고 Claude에게 반복 개선과 스트레스 테스트를 맡겨 빠르고 안정적으로 만든다.
- **먼저 투자할 검사**: E2E는 실제 사용자 흐름을 보고 속이기 어려우며, 실패하면 일반적인 시간 초과 대신 단계 기록과 스크린샷이 남는다. 속성 기반 테스트는 왕복 변환, 잔액이 음수가 되지 않는 불변조건, 멱등성, 최적화 구현과 단순 구현의 동등성을 생성 입력으로 검사한다. 차등 테스트는 기존 시스템과 새 시스템에 같은 입력(무작위 생성이나 운영 트래픽 표본)을 넣어 차이를 조사하되, 무관한 차이는 정규화하고 승인한 변경은 목록으로 관리한다.
- **불안정하고 느린 검사의 부작용**: flaky 테스트는 에이전트에게 고치는 대신 다시 돌리는 법을 가르치고, 느린 테스트는 실행 횟수를 줄여 원인 위치를 좁히기 어렵게 한다. 이 팀은 flaky 테스트를 건너뛰거나 sleep을 넣거나 통과할 때까지 재시도하지 못하게 하고, 근본 원인을 찾지 못하면 테스트를 지운 뒤 이유를 적는다. 무거운 검사는 커밋 전에 둔다([[Deterministic-Test|결정적 테스트]]).
- **세 라운드 뒤에는 사람에게 넘긴다**: 실패한 검사는 Claude가 고치되, 세 라운드 뒤에도 실패하면 멈추고 사람을 부른다.
- **검사 규칙은 변경이 고칠 수 없는 곳에 둔다**: 리뷰 규칙(REVIEW.md)은 PR의 변경이 아니라 기본 브랜치에서 읽고, 리뷰 결과는 리뷰한 커밋에만 유효하다. 커밋마다 어떻게 검증했는지(검증 없음 포함)를 기록하고, 세션에 `/code-review`나 `/verify`가 없으면 커밋을 막는 게이트를 off, observe, enforce 모드로 둔다. observe는 막았을 커밋을 기록만 해 오탐을 먼저 본다. enforce에서는 커밋 메시지에 검증하지 않은 이유를 적을 수 있고, 한 세션에서 두 번 막힌 뒤의 커밋은 통과시켜 에이전트가 갇히지 않게 한다.
- **놓친 결함을 규칙으로 바꾸는 조건**: 사람의 리뷰 코멘트와 되돌림에서 뽑은 패턴은 PR 두 건 이상에서 나오고 diff에서 식별할 수 있어야 규칙 후보가 되며, 에이전트 셋이 반증을 시도한 뒤 사람이 PR로 승인한다. 장애와 PR에서 나온 39개 항목의 신뢰성 체크리스트는 항목마다 diff에서 읽을 수 있는 발동 조건을 두어 보통 3~10개만 검사한다. 규칙, 검증 단계와 테스트는 정기적으로 정리해 계속 불어나지 않게 한다.
- **별도 채점기의 효과**: 구조화된 파일 생성에 대한 사내 시험에서 별도 채점기가 루브릭으로 검사하자 일반 프롬프트 루프보다 과제 성공률이 최대 10점 올랐고 어려운 문제에서 이득이 컸다. 시험 조건은 공개하지 않았다.

리뷰어 자체를 평가하는 방법(알려진 사고 재현과 단계별 재현율)은 [[Code-Review-AI-Agent-Operations#지적 처리와 도입 점검|에이전트 시대 코드 리뷰 운영]]에 둔다. 이 운영을 옮길 때는 검사와 그 규칙이 변경과 같은 권한 아래 있는지부터 확인한다(적용 제안).

## 실행 중인 앱의 내부 신호로 판정한다

화면만 보는 검사는 화면에 드러나지 않는 실패를 놓친다. 결제 버튼이 조용히 500을 받거나, 배지는 12를 보이는데 상태 저장소는 0을 갖거나, 한 번의 클릭이 주문 요청을 두 번 보내도 화면은 정상으로 보일 수 있다. 에이전트가 변경을 마쳤다고 보고하면 조작 하나에 이어진 요청과 응답, 콘솔 오류, 화면 변화와 앱 상태를 묶어 판정하고 판정마다 근거를 남긴다.

판정은 통과, 실패와 판단 불가로 나눈다. 근거가 모자라 판단할 수 없는 경우를 통과로 세지 않아야 검증이 조용히 초록불을 내지 않는다. 한 번 통과한 흐름은 저장해 두고 이후 변경마다 모델 없이 결정적으로 다시 돌리면, 매번 에이전트가 화면을 다시 조작하는 비용과 비결정성을 피하면서 새 수정이 이전 기능을 깨뜨리는 회귀를 잡을 수 있다.

사례: Reticle은 개발 빌드에만 들어가는 SDK(production mode를 따로 켜면 운영 빌드에도 들어간다)를 앱에 넣고 MCP 도구로 에이전트에게 보기, 조작, 관찰과 판정을 제공한다(2026-11-21 README 기준, npm 패키지는 Apache-2.0). 설치하거나 실행해 보지는 않았다.

- **판정과 근거:** `verified`는 yes, no, unknown(판단 불가)이고 yes만 통과다. 확인할 결과를 선언하지 않은 검사는 no-fault를 낸다. 판정에는 결론을 정한 요청, 상태 변화, 콘솔 줄과 원인 요소의 소스 `file:line`이 붙는다.
- **읽는 신호:** 클릭에 묶인 네트워크 응답과 요청 수, 콘솔, 앱이 등록한 상태 저장소(zustand, Redux 등)와 React 렌더를 읽는다. 등록한 저장소를 읽으면 화면에 그린 것이 아니라 앱이 믿는 상태를 검증한다. 웹(React, Next.js 등)과 데스크톱(Electron, Tauri)을 지원한다.
- **흐름 저장과 CI 게이트:** 검사가 들어간 조작은 세션이 끝날 때 흐름으로 저장되고 이후 모델 없이 다시 돈다. `reticle gate --since HEAD~1`은 변경이 건드린 저장 흐름마다 새 통과 기록이 없으면 실패하므로, 에이전트가 자기 diff를 근거로 통과를 주장할 수 없다. 앞 절의 검사 규칙을 변경이 고칠 수 없는 곳에 두는 원리와 같다.
- **한계:** README는 IndexedDB, Web Worker, 닫힌 shadow root와 교차 출처 iframe을 아직 보지 못하고, 단일 조작 주변의 경쟁 상태는 끝나지 않은 요청과 두 번 보낸 요청만 잡는다고 밝힌다. 88개 결함을 심은 앱에서 Playwright 스크립트(59/88)보다 많이 잡았다(85/88)는 결과는 저장소에 커밋된 하네스로 낸 개발사 측정이며 여기서 재현하지 않았다. 내부 신호를 읽는 방식은 소유하지 않은 사이트, 여러 브라우저와 실제 픽셀 비교를 대신하지 않는다.
- **설치 범위:** `init`은 개발 의존성과 빌드 설정 외에 `CLAUDE.md`와 `AGENTS.md`에 규칙을 덧붙이고, 찾은 에이전트마다 MCP 서버를 등록하며, 민감 값을 가린 프롬프트를 `.reticle/`에 남기는 훅을 설치한다. 별도 설치 스크립트(`reticle setup install`)는 PATH에 `codex`가 있으면 Codex 설정에 Reticle 도구의 승인 모드를 approve로 적되 사용자가 이미 정한 모드는 바꾸지 않는다. 익명 사용 통계는 기본으로 켜져 있다. 도입 전 `init --dry-run`으로 바뀔 파일을 보고 `--no-mcp`, `--no-prompt-capture` 같은 선택을 팀 정책과 대조한다(적용 제안).

화면 바깥에서 접근성 트리로 조작하는 방식은 [[Natural-Language-E2E-Agent|자연어 E2E 테스트 에이전트]], 실패 영상과 실행 증거의 보관은 [[Browser-Test-Recording|브라우저 테스트 녹화와 실행 증거]]가 다룬다.
