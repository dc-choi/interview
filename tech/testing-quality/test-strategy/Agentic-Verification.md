# 에이전트 기반 검증

코딩 에이전트에 검사 수단을 제공하면 변경, 실행, 실패 분석과 수정의 반복을 구성할 수 있다. 성공 기준을 에이전트의 자기평가에만 맡기지 않고, 외부에서 관찰할 결과와 불변조건으로 표현한다.

## 검증 수단을 조합한다

| 수단 | 잡으려는 오류 | 한계 |
| --- | --- | --- |
| 핵심 E2E | 실제 사용자 흐름에서 연결되지 않은 기능, 로그인과 저장 실패 | 느리고 환경 의존적이므로 중요한 소수 흐름에 집중 |
| 속성 기반 테스트 | 예제로 빠뜨린 경계와 입력 조합 | 잘못된 속성과 좁은 생성 범위는 오류를 놓침 |
| 기존 구현과 비교 | 재작성에서 바뀐 계약과 출력 | 기존 버그까지 정답으로 복제할 수 있어 차이를 판단해야 함 |
| 성능 검사 | 지연, 처리량과 자원 회귀 | 비교 전제와 측정 방식이 다르면 결과를 해석할 수 없음 |

정렬 테스트라면 결과의 순서뿐 아니라 원소와 중복 개수 보존을 검사한다. 결제 같은 상태 변경은 한 요청의 반복 실행이 중복 차감하지 않는지도 검증한다. 테스트 개수를 늘리는 것보다 틀린 구현을 실제로 거절하는 판정식이 중요하다.

기능이 다른 기능과 겹치는 문맥이 많아 사람이 시험 사례를 열거할 수 없는 시스템에서는 LLM 보조 퍼징이 조합 결함을 빨리 찾는다는 보고가 있다. 다만 발견이 늘면 고칠 사람의 시간이 먼저 바닥날 수 있으므로 발견과 수정 용량을 함께 계획한다([[AI-Code-Delegation-Review#AI 리뷰가 결함을 더 빨리 찾으면 수정 용량이 병목이 된다|PostgreSQL 19 사례]]).

## 반복을 끝내는 조건

1. 요구사항과 변경 전 기준선을 정한다.
2. 에이전트가 제한된 환경에서 구현과 검사를 반복한다.
3. 실패 입력, 명령, 실행 환경과 결과를 남긴다.
4. 테스트 삭제나 기대값 변경으로 통과시키지 않았는지 별도로 검토한다.
5. 확인하지 못한 외부 연동과 비결정적 결과를 완료 보고에서 분리한다.

별도 검토자도 같은 잘못된 전제를 물려받을 수 있다. 검토자 수나 테스트 통과를 전체 정확성의 증명으로 삼지 않는다. 빠른 로컬 검사와 실제 CI/배포 환경의 검사를 연결한다.
