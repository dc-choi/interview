# TDD 리팩토링 연습법 — 의식적인 연습과 작은 변화

TDD와 리팩토링은 지식이 아니라 **기술**이다. 글쓰기나 운동처럼 상황마다 정답이 달라지고, 반복하며 감각을 키워야 한다. 중요성을 아는 데 그치지 않고 **꾸준히 연습하는 방식**이 필요하다 — 작은 목표와 제약을 두고 피드백을 받으며 반복하는 것.

## 반복만으로는 늘지 않는다 — 의식적인 연습

이를 매일 닦아도 양치 실력이 늘지 않는 이유는 무의식적으로 하기 때문이다. 기존 방식대로만 코드를 쓰면 경험은 쌓여도 실력은 도약하지 않는다. 성장은 편한 영역을 살짝 벗어나는 연습에서 나온다.

의식적인 연습(deliberate practice)의 조건:

1. **현재 실력보다 약간 높은 난이도** — 너무 쉬우면 변화가 없고, 너무 어려우면 포기한다
2. **구체적인 목표** — 클린 코드를 짜자(X) → 메서드 길이를 10줄 이하로(O)
3. **피드백 장치** — 코드 리뷰, 페어 프로그래밍, 테스트 결과, 정량적 제약
4. **한 번에 한 가지에 집중** — 한 주는 메서드 분리만, 다음 주는 else 제거만

## 좋은 연습은 정량적 제약에서 시작된다

메서드는 한 가지 일만 하라는 말은 초보자에게 추상적이다. 바로 확인 가능한 제약이 스스로 피드백을 만든다 (객체지향 생활체조 계열의 규칙들):

- **메서드 15줄 이하** — 넘으면 분리를 고민하게 됨
- **들여쓰기 1단계까지만** — 중첩 조건, 반복문이 메서드 추출을 강제
- **else 금지** — 조기 반환(early return), 조건 분리를 고민하게 됨
- **원시값 포장** — int 대신 의미 있는 타입
- **인스턴스 변수 3개 이하** — 자연스럽게 새로운 객체를 찾게 됨

이런 제약은 처음엔 불편하지만, 기존 방식으로 풀 수 없는 문제를 만나게 해 새 설계 감각을 만든다.

## 연습 경로 — 쉬운 것부터 단계적으로

### 1. 장난감 프로젝트로 시작

회사 프로젝트에는 일정, 레거시, DB, UI, 외부 API 같은 변수가 많아 첫 시도가 실패하기 쉽다. 문자열 계산기, 자동차 경주, 사다리 타기, 체스처럼 **도메인은 단순하지만 설계 연습이 되는 문제**가 적합하다. 거창한 서비스가 아니라 작은 문제에서 반복 훈련이 목적.

### 2. TDD 전에 학습 테스트부터

학습 테스트 = 사용하는 API, 라이브러리의 동작을 확인하려고 작성하는 테스트 (문자열 분리, 날짜 처리, 컬렉션 동작 등). 코드보다 테스트를 먼저 생각하는 습관을 부드럽게 만들어 준다.

### 3. TDD 사이클은 쪼개서

Red → Green → Refactor 세 단계를 처음부터 완벽히 하려 하면 부담스럽다. 처음엔 테스트 작성과 통과만, 그다음 리팩토링에 집중. **많은 사람이 통과에서 멈추고 리팩토링을 생략하는데, 진짜 학습은 리팩토링 단계에서 일어난다.** 테스트는 안전망, 리팩토링이 설계 훈련이다. (사이클 자체는 [[TDD-BDD|TDD, BDD]] 참조)

### 4. 메서드 분리 → 5. 클래스 분리 (원시값 포장)

- **메서드 분리**: 조건문, 반복문, 변환이 한 메서드에 몰린 코드에 들여쓰기, 길이 제약을 걸면 자연스럽게 나뉜다. 역할이 드러나면 읽는 순서도 좋아진다 — 좋은 코드는 모든 세부사항을 한 번에 보여주지 않고, 필요할 때 안쪽으로 들어가게 한다
- **클래스 분리**: 문자열 숫자를 int로만 다루지 않고 `PositiveNumber`처럼 감싼다. 변환, 음수 검증, 값 보관의 책임이 한곳에 모인다. 처음엔 코드가 늘어 보여도 검증이 흩어지지 않고, 의미 있는 타입이 생기고, 변경에 강해진다

### 6. 의존성 있는 코드는 나중에

DB, UI, 외부 API가 얽힌 코드부터 TDD를 시도하면 테스트 작성에 지쳐 포기한다. 순수 로직으로 연습한 뒤, **테스트하기 쉬운 부분과 어려운 부분을 분리**하는 연습으로 넘어간다 (DB 접근은 바깥으로, 계산과 판단은 별도 객체로). 핵심 감각: 테스트하기 어려운 코드를 억지로 테스트하는 것이 아니라 **테스트하기 쉬운 구조로 바꾸는 것** (경계 설계는 [[Service-Layer-Testing|서비스 레이어와 테스트 경계]]).

### 7. 레거시는 마지막에

레거시는 의존성이 많고 설계 의도가 흐려졌고 안전망도 없는 **가장 어려운 대상**. 작은 프로젝트에서 자신감을 만든 뒤, 회사 코드에는 영향 범위가 작은 부분부터. 작은 성공이 쌓여야 업무 코드에 적용할 힘이 생긴다.

## 다음 테스트와 구현의 보폭을 정하기

가장 작은 입력부터 시작하되, 다음 테스트가 어떤 새 규칙을 요구하는지 확인한다. 테스트 입력마다 조건문을 하나씩 추가하면 예제 목록만 외운 코드가 된다. 도메인 규칙을 알고 있어야 올바른 기대값과 일반화 방향을 정할 수 있다.

| 기법 | 쓰는 시점 | 주의점 |
|---|---|---|
| Assert First | 관찰할 결과부터 정하고 실행, 준비를 역으로 채울 때 | 작성 순서의 기법이다. 최종 테스트는 AAA나 Given-When-Then으로 읽혀야 한다 |
| Fake It | 알고리즘이 불분명해 우선 상수로 한 사례를 통과할 때 | 임시 구현이다. 다른 입력의 테스트로 상수가 부족함을 드러내고 일반화한다 |
| Triangulation | 두 번째 이상의 다른 사례로 일반 규칙이 필요함을 드러낼 때 | 매번 두 사례를 기다릴 의무는 없다. 명확한 구현이면 바로 작성할 수 있다 |
| One-to-Many | 비어 있음, 원소 하나, 여러 원소로 범위를 넓힐 때 | 중복, 순서, 용량과 종료 조건도 검증한다 |
| Stair-step 테스트 | 생성, 호출 같은 임시 발판으로 구조를 만들 때 | 후속 행위 테스트가 같은 보장을 포함하면 중복 발판을 지울 수 있다. 독립 규칙의 테스트는 보존한다 |

볼링 점수는 0점 경기, 모든 투구가 1점인 경기, 스페어, 스트라이크, 마지막 프레임의 추가 투구로 규칙을 확장할 수 있다. 누적 합만으로 스페어를 처리하기 어렵다면 기존 테스트가 통과하는 상태에서 투구 기록과 점수 계산의 책임을 나눈다. 예상 클래스 다이어그램은 가설이며, `Frame` 같은 객체를 처음부터 전부 구현할 필요는 없다.

소인수분해는 `1 -> []`, `2 -> [2]`, `4 -> [2, 2]`, `8 -> [2, 2, 2]`, `9 -> [3, 3]`으로 반복 횟수와 다른 약수를 드러낸다. 줄 바꿈은 빈 문자열, 너비 이하, 너비 경계, 공백 없는 긴 단어, 공백 경계, 여러 줄을 구분한다. 이름 변환은 빈 값, 한 단어, 여러 공백, 접두와 접미 호칭을 구분하되, 실제 제품의 이름 규칙을 예제의 공백 분리 방식으로 일반화하지 않는다.

### Getting Stuck에서 빠져나오기

새 사례 하나가 큰 재작성을 요구하면 테스트와 구현의 보폭을 다시 살핀다.

1. 요구사항과 기대값을 확인하고 마지막 Green 상태를 보존한다.
2. 신규 실패 사례를 더 작은 사례로 나누거나 기존 공개 계약을 유지하며 구조를 먼저 정리한다.
3. 알고리즘을 연습용 코드에서 다시 구성해 볼 수 있지만, 업무 코드의 기존 회귀 테스트를 지워 실패를 숨기지 않는다.
4. 일시적으로 제외한 신규 테스트는 복구하고 전체 테스트를 실행한 뒤 완료한다.

## Transformation Priority Premise: 일반화를 고르는 휴리스틱

TPP는 테스트를 통과시키는 변환을 더 단순한 것부터 선택하면 큰 도약을 줄일 수 있다는 가설이다. **변환**은 새 입력에서의 행위를 바꾸어 Green으로 가는 작업이고, **리팩토링**은 기존 외부 행위를 유지하며 구조를 정리하는 작업이다. 코드에 구조 변화가 전혀 없어야만 변환인 것은 아니다.

- 상수 반환이 부족하면 입력값이나 계산으로 바꾼다.
- 실행 경로가 달라야 하면 분기를 추가하고, 한 번으로 부족하면 반복이나 재귀를 검토한다.
- 한 값을 다루던 로직을 컬렉션으로 넓힐 때 중복된 사례별 구현 대신 공통 규칙을 찾는다.

TPP의 변환 목록과 우선순위는 확정된 규격이나 알고리즘의 최적성을 증명한 법칙이 아니다. 원 제안에도 순서와 형식화에 대한 미해결 질문이 있다. 재귀가 반복보다 낫거나, 우선순위를 지키면 퀵 정렬이 보장된다고 결론 내리지 않는다. 동작을 유지하는 `while`에서 `for`로의 변경은 리팩토링일 수 있다. 실제 선택은 입력 규모, 시간과 공간 복잡도, 종료 조건으로 확인한다.

## 외부 연동은 실행을 확인하고 빠른 루프를 만든다

소켓이나 API를 처음 쓰면 연결과 최소 요청부터 확인하는 학습 테스트가 큰 유즈케이스 하나보다 오류를 좁히기 쉽다. 올바른 응답뿐 아니라 서버 중단, 잘못된 응답이나 상태를 주었을 때도 테스트가 실패하는지 확인한다. 설치 명령, 포트와 오래된 프로토콜 코드는 현재 계약을 대조한 뒤 사용한다.

- **Inside-Out**: 순수한 계산과 도메인 규칙부터 만들고 애플리케이션 경계로 넓힌다.
- **Outside-In**: 사용자가 관찰할 인수 기준부터 정하고 필요한 협력을 채운다. 모든 내부 객체를 Mock으로 만들 필요는 없다([[Classicist-vs-Mockist-Testing]]).
- **Working Skeleton**: API 진입부터 필요한 저장소까지 최소 경로를 실제로 연결해 조립과 연동 위험을 일찍 확인한다. 응답을 상수로 돌려주는 테스트만 통과했다면 연결 확인은 아직 끝나지 않았다.

GraphQL로 컬렉션을 생성하는 사례라면 반환 ID뿐 아니라 요청한 소유자와 항목이 저장되는지, 검색과 페이지 순서가 계약을 지키는지도 확인한다. 빠른 도메인 테스트에는 인메모리 저장소를 쓰고 실제 저장소 어댑터의 매핑, 제약과 트랜잭션은 통합 테스트로 검증한다. 시각과 자동 ID가 중요한 결과라면 값을 고정하거나 관계를 검증하고, 스냅샷에서 무조건 지우지 않는다([[Legacy-Code-Testing#승인 테스트 Approval Test]]).

테스트 안에서 구현을 탐색한 뒤 운영 코드로 추출하는 방법도 선택할 수 있다. 추출 후에는 운영 클래스를 호출하고 테스트에 별도 구현을 남겨 자체 검증하지 않는다. 기능별 수직 모듈과 계층 경계의 배치는 [[Layered-Clean-Hexagonal]]에 연결한다.

## 성능보다 가독성이 먼저인 경우가 많다

역할별로 메서드를 나누면 반복문을 여러 번 돌 수도 있다. 그래도 대부분의 병목은 애플리케이션 코드가 아니라 DB, 네트워크, 외부 API에서 발생한다. 먼저 읽기 쉽고 변경하기 쉬운 코드를 만들고, **측정된 병목에 대해서만 최적화** ([[Cognitive-Biases-Programming|Premature Optimization]]).

## 팀에 전파하기 — 강요보다 신뢰

- 사람은 변화를 부담스러워하고, 경험 많은 개발자는 과거 실패 탓에 새 시도를 경계한다. 처음부터 팀 전체를 바꾸려 하면 반발이 생긴다
- 먼저 자신의 영향 범위 안에서 좋은 코드를 만들고, 관심을 보이는 동료와 작게 공유 — **변화는 설득보다 증거에서 시작된다**
- 리더는 답을 지시하기보다 어떻게 하면 좋을지 질문한다. 팀원 입에서 나온 개선안이 실행 가능성이 높다. 1대1 면담으로 신뢰를 쌓고, 작은 개선 주제 하나에 익숙해질 때까지 집중
- 팀 변화도 TDD 연습과 같은 구조 — 작게 시작해 피드백 받으며 키운다 ([[Growth-Principles|성장의 7가지 원칙]]의 반복, 소셜화)

## 면접 체크포인트

- 의식적인 연습의 4조건과 **정량적 제약이 피드백 장치가 되는** 원리
- 들여쓰기 제한, else 금지 같은 제약이 **설계 감각을 만드는** 메커니즘 (제약 → 기존 방식 불가 → 새 구조 탐색)
- TDD에서 리팩토링 단계가 **진짜 학습 지점**인 이유
- 원시값 포장의 효과 (검증 응집, 의미 있는 타입, 변경 내성)
- 테스트하기 어려운 코드에 대한 태도 — 억지 테스트가 아니라 구조 변경
- 레거시보다 장난감 프로젝트부터 시작해야 하는 이유
- 팀에 TDD 문화를 도입한다면? — 강요 대신 증거, 작은 성공, 질문하는 리더
