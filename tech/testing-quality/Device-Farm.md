# Device Farm

여러 대의 실제 모바일 기기를 호스트에 연결하고, 원격 사용자가 API나 콘솔을 통해 점유하고 제어하며 테스트할 수 있게 만든 테스트 인프라다. 핵심은 기기를 모아 두는 것이 아니라 **물리 기기를 검색, 할당, 격리, 복구할 수 있는 공유 자원으로 추상화**하는 데 있다.

## 핵심 mental model

> 실기기는 공유 희소 자원이고, 테스트 실행 권한은 만료 가능한 lease다.

이 관점에서 테스트 코드는 기기가 어느 호스트의 어느 포트에 연결되었는지 몰라도 된다. 플랫폼, OS 버전, 모델과 같은 조건으로 기기를 요청하고, 할당받은 기기에 명령을 보낸 뒤 결과와 산출물을 회수하고 반납한다.

팀별로 기기와 자동화 환경을 따로 운영하면 다음 비용이 반복된다.

- 호스트, 케이블, 드라이버와 OS 버전을 팀마다 관리한다.
- 사용하지 않는 기기가 다른 팀에는 보이지 않아 전체 이용률이 낮아진다.
- 연결 끊김과 프로세스 장애를 각 팀이 직접 복구한다.
- 보안 정책과 테스트 데이터 정리 기준이 환경마다 달라진다.

중앙화는 이 비용을 플랫폼 운영 책임으로 모으고, 제품 팀이 테스트 시나리오와 품질에 집중하게 한다. 대신 물리 설비와 제어 소프트웨어를 24시간 운영할 책임도 함께 중앙화된다.

## 참조 아키텍처

```text
Web console / SDK / CLI / CI
              |
      Orchestration API
       /      |       \
Registry   Scheduler   Execution queue
              |              |
           Host agent ---- Runner
              |
       Device controller ---- Physical device
              |
       Capture / broadcaster ---- Browser viewer
```

| 계층 | 책임 |
|---|---|
| 클라이언트 | 기기 요청, 테스트 실행, 수동 원격 제어와 결과 조회 |
| 오케스트레이터 | 기기 목록, 조건 검색, lease, 권한, 실행 상태와 감사 기록 관리 |
| 실행 큐와 러너 | 실행 요청을 분산하고 처리량 증가에 맞춰 수평 확장 |
| 호스트 에이전트 | 호스트에 연결된 기기를 발견하고 상태를 보고하며 로컬 명령 전달 |
| 기기 컨트롤러 | 화면 탐색, 탭, 입력, 앱 설치와 같은 플랫폼별 동작 수행 |
| 미러링 경로 | 화면을 캡처하고 인코딩해 원격 사용자에게 전달 |
| 실기기 | 실제 OS, 하드웨어와 앱이 동작하는 최종 테스트 대상 |

오케스트레이터는 자원과 정책을 다루는 **control plane**, 컨트롤러와 미러링은 명령과 영상을 운반하는 **data plane**으로 볼 수 있다. 둘을 분리하면 화면 스트리밍 트래픽이 커져도 할당과 상태 관리가 함께 느려지는 일을 줄일 수 있다.

## 기기 점유 생명주기

기기의 정상 경로는 다음 상태 머신으로 표현할 수 있다.

```text
AVAILABLE -> RESERVED -> PREPARING -> RUNNING -> CLEANING -> AVAILABLE
                    \         |           /
                     ------> QUARANTINED
```

1. **발견과 등록**: 에이전트가 연결된 기기와 속성을 등록하고 heartbeat를 보낸다.
2. **선택과 예약**: 요청 조건에 맞는 기기를 고르고 하나의 lease만 발급한다.
3. **준비**: 앱, 계정, locale, 네트워크와 초기 화면을 테스트 조건에 맞춘다.
4. **실행**: 자동화 명령이나 사람이 보낸 원격 명령을 수행한다.
5. **수집**: 로그, 스크린샷, 영상과 테스트 결과를 저장한다.
6. **정리**: 앱 데이터와 테스트 계정을 초기화하고 민감한 산출물을 회수한다.
7. **반납 또는 격리**: 건강한 기기는 풀로 돌려보내고, 복구되지 않은 기기는 격리한다.

lease에는 TTL과 소유자, heartbeat, 가능하면 fencing token을 둔다. 클라이언트가 사라져도 TTL 뒤에는 기기를 회수할 수 있고, 만료된 소유자의 늦은 명령은 fencing token으로 거부할 수 있다. `release`는 여러 번 호출해도 결과가 같게 만들되, 탭이나 결제 같은 기기 동작은 재시도가 안전하지 않을 수 있으므로 명령별 재시도 정책을 구분한다.

## 스케줄링과 용량

기기 선택 조건은 단순한 Android와 iOS 구분보다 넓다.

- 모델, OS 버전, 화면 크기, locale과 접근성 설정
- 설치할 앱 빌드와 테스트 계정 유형
- 네트워크 프로필, SIM이나 특정 하드웨어 기능
- smoke, regression, 수동 탐색과 같은 용도 태그

스케줄러는 조건 일치뿐 아니라 대기 시간, 팀별 공정성, 우선순위와 호스트 부하를 함께 봐야 한다. 희귀 모델을 일반 테스트가 오래 점유하면 중요한 호환성 테스트가 굶을 수 있다. 예약 큐와 사용량 quota를 두고, 장애와 정비를 감당할 여유 용량도 남긴다.

## 제어 API와 드라이버

모바일 UI 자동화는 공통 명령을 Android와 iOS의 서로 다른 자동화 기술로 번역하는 어댑터 문제다. Appium은 WebDriver 기반의 공통 API와 플랫폼별 드라이버 생태계를 제공한다. 범용성과 상호운용성이 중요한 환경에서는 먼저 검토할 가치가 크다.

전용 드라이버는 다음 조건이 측정으로 확인될 때 고려한다.

- 세션 준비나 안정화 대기가 전체 실행 시간의 큰 병목이다.
- 사내 앱 전용 입력, 신호, 빌드 설치나 보안 정책이 공통 인터페이스에 필요하다.
- 범용 도구의 확장 지점으로는 필요한 실시간성이나 운영 제어를 만들기 어렵다.
- 드라이버, OS 업데이트와 장애 대응을 지속해서 소유할 팀이 있다.

한 가지 설계는 기기별 컨트롤러를 미리 띄워 두고 명령을 독립적인 HTTP 호출로 받는 것이다. 다만 API 요청이 stateless여도 기기, 앱과 점유 상태까지 stateless인 것은 아니다. 상태의 소유 위치를 명확히 하고, 명령 중복과 순서 뒤바뀜을 처리해야 한다.

속도와 견고성도 교환 관계다. 화면이 안정될 때까지 기다리면 전환 중인 요소를 누르는 실패는 줄지만 명령 지연은 늘어난다. 대기를 없애기보다 시나리오별 명시적 조건, 제한 시간과 측정된 p50/p95 지연으로 정책을 정한다.

## 원격 조작과 화면 미러링

서버실의 기기를 사람이 직접 볼 수 없으므로 제어 경로와 관찰 경로가 모두 필요하다.

- **제어 경로**: 탭, 입력, 스와이프와 앱 제어 명령을 기기로 전달한다.
- **관찰 경로**: 화면을 캡처하고 H.264 같은 형식으로 인코딩한 뒤 브라우저로 방송한다.

두 경로가 같은 USB 자원이나 프로세스를 독점하면 조작과 미러링이 서로 막을 수 있다. 플랫폼별 캡처 제약은 어댑터 아래에 숨기되, API에서는 해상도, frame rate, 지연과 연결 상태를 공통 지표로 노출한다. 시청자가 늘 때는 기기마다 다시 인코딩하지 않고 한 스트림을 broadcaster가 분배하는 구조가 유리하다.

## 테스트 조건 준비와 격리

기기 조작보다 테스트 전제 조건을 만드는 시간이 더 클 수 있다. 준비 단계를 별도 기능으로 취급한다.

- 자주 쓰는 로그인, 권한과 화면 상태를 preset으로 제공한다.
- 테스트 계정과 데이터를 조건에 맞게 만들고 실행 뒤 되돌린다.
- 기기 상태와 서버의 비즈니스 데이터를 함께 초기화한다.
- 이전 실행의 알림, 사진, 클립보드, 앱 캐시와 인증 정보가 다음 실행에 남지 않게 한다.

기기 lease만으로 테스트 격리가 완성되지는 않는다. 동일 계정, 백엔드 데이터와 외부 sandbox를 공유하면 서로 다른 기기에서도 충돌한다. 기기, 계정, 데이터 namespace를 하나의 실행 단위로 묶어야 한다.

## 안정성 운영

| 장애 층 | 대표 문제 | 대응 |
|---|---|---|
| 물리 설비 | USB 연결 끊김, 케이블과 허브 불량, 불안정한 전원 | 검증된 부품, 포트별 상태 감지, 예비 용량과 현장 교체 절차 |
| 호스트 | 에이전트 종료, OS 업데이트, 자원 고갈 | 프로세스 supervisor, 자동 재시작, 배포 drain과 host 격리 |
| 기기 | 응답 없음, 앱 멈춤, 저장 공간 부족 | 단계적 복구, 재부팅, health check와 quarantine |
| 제어 계층 | orphan lease, 중복 명령, 오래된 registry | TTL, heartbeat, fencing, 멱등한 상태 전이 |
| 테스트 상태 | 잔여 데이터, 계정 충돌, flaky 시나리오 | 실행별 namespace, cleanup 검증과 실패 산출물 보존 |

복구는 프로세스 재시작, 컨트롤러 재연결, 기기 재부팅, 물리 점검 순으로 비용이 커지는 단계적 절차로 만든다. 배포할 때는 사용 중인 기기를 drain하고 새 실행만 새 버전으로 보내면 진행 중인 테스트를 끊지 않고 교체할 수 있다.

## 관측 지표

- **공급**: 전체와 조건별 가용 기기 수, quarantine 비율, host별 연결 상태
- **수요**: 큐 길이, 할당 대기 p50/p95, 팀별 요청량과 거절률
- **사용**: lease 이용률, 유휴 시간, 평균 점유 시간과 만료 회수 횟수
- **실행과 미디어**: 명령 지연 p50/p95, 테스트 시간, 성공률, flaky 재실행률, frame rate와 end-to-end 지연
- **복구**: 연결 끊김 빈도, 자동 복구 성공률, MTTR과 물리 개입 횟수

가용률만 보면 고장 난 기기를 빠르게 제외해 수치가 좋아 보일 수 있다. 큐 대기 시간과 조건별 공급 부족을 함께 봐야 사용자가 체감하는 품질을 알 수 있다.

## 보안과 컴플라이언스

중앙화의 장점은 정책을 한 번 정의해 모든 기기에 강제할 수 있다는 점이다. 동시에 한 플랫폼에 권한과 데이터가 모이므로 통제 실패의 영향도 커진다.

- 사용자와 CI 주체별 인증, 역할 기반 기기와 명령 권한
- lease 소유자 외 명령 차단과 모든 제어 명령의 감사 기록
- 승인된 앱 빌드만 설치하고 설치 출처와 해시 기록
- 로그, 영상과 스크린샷의 민감 정보 분류, 보존 기간과 접근 통제
- 반납 전 인증 정보와 사용자 데이터 삭제 검증
- 기기 네트워크 분리와 외부 통신 정책
- 분실, 물리 접근과 폐기 절차를 포함한 자산 관리

## 구축, 구매와 범용 도구 선택

| 선택 | 적합한 상황 | 주된 비용 |
|---|---|---|
| 관리형 디바이스 팜 | 빠른 도입, 다양한 모델과 외부 운영 활용 | 커스텀 제약, 데이터 경계, 사용량 비용과 외부 의존 |
| 사내 팜과 범용 드라이버 | 기기와 정책은 소유하되 자동화 표준을 재사용 | 물리 운영, 세션과 드라이버 장애 대응 |
| 사내 팜과 전용 드라이버 | 낮은 지연, 깊은 사내 연동과 정책 강제가 핵심 | 가장 큰 개발비, OS 변화 추적과 장기 유지보수 |

판단 순서는 문제 측정, 기존 도구 설정과 확장 지점 검토, 작은 팜으로 운영 비용 검증, 마지막으로 전용 드라이버 내재화가 안전하다. 전용 구현의 성능 이득만 비교하지 말고 장애 대응 인력, 보안 검토, 하드웨어 교체와 OS 업데이트 비용까지 총소유비용에 넣는다.

## 테스트 전략에서의 위치

디바이스 팜이 있어도 모든 테스트를 실기기 E2E로 옮기지는 않는다. 빠른 단위와 통합 테스트는 아래 계층에 유지하고 다음 범위에 실기기를 집중한다.

- 로그인, 결제와 같은 핵심 사용자 여정의 smoke와 회귀 테스트
- 카메라, 생체 인증, 알림과 같이 실제 하드웨어나 OS 연동이 필요한 동작
- 특정 모델과 OS 조합에서만 발생하는 호환성 문제
- 배포 후보 빌드의 최종 검증과 수동 탐색 테스트

실기기 테스트는 높은 현실성을 얻는 대신 실행 시간, 자원 경합과 운영 비용을 지불한다. 에뮬레이터와 시뮬레이터도 빠른 피드백과 조합 확대에 유용하므로 서로 대체재가 아니라 테스트 목적별 포트폴리오로 운영한다.

## 설계와 면접 체크포인트

- 기기 중복 점유와 만료된 클라이언트의 늦은 명령을 어떻게 막는가?
- 테스트 종료와 클라이언트 장애 뒤에 기기와 데이터가 어떻게 정리되는가?
- 희귀 기기 부족, 팀별 공정성과 긴급 테스트 우선순위를 어떻게 조정하는가?
