# 내부 개발자 플랫폼의 셀프서비스와 운영 경계

내부 개발자 플랫폼은 개발팀이 필요한 환경과 기능을 일관된 방식으로 요청하고 사용할 수 있도록 연결한 내부 제품이다. 포털 화면뿐 아니라 API, CLI, 템플릿과 문서도 인터페이스가 된다. 목표는 공통 작업의 중복과 개발팀의 인지 부담을 줄이는 것이다.

## 반복되는 사용자 작업에서 범위를 정한다

먼저 요청이 자주 들어오고 완료 조건이 분명한 작업을 고른다. 기존 CI/CD와 클라우드 서비스를 연결할 수 있으면 그 구현을 재사용한다. 플랫폼 팀이 모든 기반 서비스를 직접 만들 필요는 없다.

다음은 적용 예시다. 개발 환경 생성 요청이 반복된다면 신청 화면 수보다 생성 이후 연결 정보 확인, 상태 조회, 변경과 정리까지 사용자가 스스로 끝낼 수 있는지를 본다. 화면만 만들고 후속 작업마다 운영팀 티켓이 필요하다면 병목이 다른 단계로 이동했을 수 있다.

| 경계 | 사용자가 확인할 것 | 플랫폼 설계에서 정할 것 |
|---|---|---|
| 요청 | 대상 환경, 용도와 선택한 옵션 | 허용 옵션, 권한과 정책 검증 |
| 처리 중 | 접수 여부와 현재 상태 | 장시간 작업의 상태 추적, 오류 전달 |
| 사용 가능 | 연결 정보와 실제 사용 결과 | 준비 완료 기준과 관측 경로 |
| 변경과 종료 | 변경 영향과 남길 데이터 | 승인, 복구, 삭제와 공유 자원 보호 |

이 표는 설계 점검 기준이다. 모든 플랫폼에 동일한 UI나 승인 단계를 강제하지 않는다. 플랫폼이 운영하는 기반 서비스와 개발팀이 운영하는 애플리케이션의 책임을 명시한다.

## API 응답과 리소스 준비 완료를 구분한다

2026-10-23 ElastiCache API 문서 대조 기준, `CreateReplicationGroup` 응답 예시는 상태가 `creating`인 복제 그룹을 반환한다. 요청 응답이 왔다는 사실만으로 연결 가능한 상태라고 표시하지 않는다. VPC 배포에서는 subnet group을 먼저 준비해야 한다.

여러 API를 연결할 때는 각 작업의 계약을 확인한다. 다음은 비동기 프로비저닝에 적용할 설계 예시다.

1. 요청 대상과 생성한 자원의 식별자를 연결하고 처리 중 상태를 제공한다.
2. 상태 조회로 완료와 실패를 구분하고, 연결 검증 등 서비스 사용에 필요한 준비 조건을 확인한다.
3. 일부 단계만 성공했을 때 남은 자원을 기록한다. 자체 생성한 전용 자원과 기존 공유 자원을 나누고 정리 대상을 판단한다.
4. 재시도 전에 이전 요청이 이미 반영됐는지 확인한다. 응답 유실을 생성 실패로 단정해 같은 자원을 중복 생성하지 않는다.

직접 조합한 API 호출을 하나의 원자적 트랜잭션으로 가정하지 않는다. 실패 시 보상과 재개는 플랫폼이 제공할 계약이며, 특정 IaC 도구의 사용이나 제거를 이 설계의 필수 조건으로 삼지 않는다.

## 네임스페이스 제공과 테넌트 격리를 구분한다

부분 검증(2026-10-26): Kubernetes의 멀티테넌시 문서를 대조했다. EKS 같은 Kubernetes 기반 플랫폼에서 네임스페이스를 생성해 주는 것만으로 테넌트 격리가 완성되지는 않는다. 네임스페이스는 API 자원의 논리적 관리 단위이며 별도 정책과 네트워크 구현이 필요하다.

- **API 접근:** RBAC로 사용자와 ServiceAccount의 권한을 필요한 네임스페이스에 제한한다. 클러스터 범위 자원을 바꿀 권한은 별도로 관리한다.
- **네트워크:** NetworkPolicy로 허용 통신을 정하고 이를 지원하는 CNI를 확인한다. 지원하지 않는 구현에서는 NetworkPolicy 객체가 있어도 정책이 적용되지 않는다.
- **자원:** ResourceQuota로 사용량을 제한할 수 있지만 네트워크 같은 모든 공유 자원 간섭을 막지는 못한다.
- **격리 수준:** 상호 신뢰가 낮거나 강한 격리가 필요하면 전용 클러스터와 노드 격리 등을 비교한다. 운영 비용과 복잡성을 함께 판단한다.

플랫폼 설계 예시: 네임스페이스 생성의 완료 조건에 다른 테넌트의 자원 조회와 통신이 거부되는지 확인하는 검사를 둔다. 생성 성공과 정책의 실제 적용을 분리하고, 정책 변경과 클러스터 운영 책임자를 정한다. 실제 격리 시험은 수행하지 않았으며 기존 API 설명의 검증일은 유지한다.

## 편리한 기본 경로와 예외 경로를 함께 둔다

문서와 템플릿에는 지원하는 선택과 운영 기준을 담는다. 다만 플랫폼이 제공하는 기능만 쓰기 쉬우면 기술 선택도 그 기능에 쏠릴 수 있다. 기본 경로로 해결되지 않는 요구를 접수하고 검토할 통로를 둔다.

CNCF 플랫폼 백서(2026-11-14 대조)는 빌드, 검사, 시험, 배포와 관측을 잇는 재사용 가능한 워크플로에 초기 프로젝트 템플릿과 문서를 함께 제공한 묶음을 흔히 golden path라고 부른다고 설명한다. 같은 백서는 플랫폼을 사용자 요구에 맞춰 설계하고 발전시키는 제품으로 다루고(platform as a product), 애플리케이션 개발자 같은 내부 사용자를 고객으로 본다. 제품 팀이 제공 기능의 일부만 골라 쓸 수 있어야 하며(optional and composable), 위에서 내린 강제에 기대어 채택을 얻는 방식은 경계한다. 따라서 golden path는 기본값을 쉽게 만드는 장치로 읽는다(해석). 다만 백서는 기업 요구에 따라 플랫폼 위 활동을 제한하는 정책 기능도 따로 들기 때문에, 선택적 사용이 보안이나 규정 통제까지 선택 사항이라는 뜻은 아니다.

역할 분담 예시(설계 제안): 장애 사후 분석에서 나온 개선을 한 팀의 수정으로 끝내지 않고 플랫폼 경로에 넣는다. 예를 들어 작은 사용자 비율에 먼저 내보내는 canary 배포와 자동 rollback을 공유 배포 워크플로처럼 중앙에서 갱신되는 경로에 넣으면 그 경로를 쓰는 서비스에 함께 적용된다. 생성 시점에 복사되는 프로젝트 템플릿에만 넣으면 이후에 만든 서비스에만 반영되므로, 기존 서비스에 반영할 방법을 따로 정한다. 이때 애플리케이션 코드는 개발 팀이, 배포 경로와 템플릿은 플랫폼 팀이 소유한다. SLO와 사후 분석 운영은 [[SRE]]를 따른다.

CNCF 백서는 성공 지표를 사용자 만족도와 생산성, 조직 효율, 제품과 기능 전달의 세 묶음으로 나눈다. 활성 사용자와 유지율, 만족도 설문, 서비스나 기능의 요청부터 제공까지 걸린 시간, 장애 뒤 복구 시간 등이 여기에 든다. 이 문서의 판단으로는 기능의 수보다 반복 요청 감소, 요청부터 사용 가능까지의 시간, 실패와 복구, 사용자의 후속 수작업을 우선 본다(적용 제안). 플랫폼 사용률이나 생성 자원 수만으로 생산성 개선을 확정하지 않는다. 보안과 비용 통제를 생략해 빨라진 경우도 구분한다.

2024년 AWS 공개 발표의 셀프서비스 사례를 출발점으로 CNCF의 플랫폼 원칙과 현재 ElastiCache API를 대조했다. 발표의 성과 수치를 일반 목표로 옮기지 않았고, 실제 플랫폼 배포나 클라우드 생성 작업은 수행하지 않았다.

## 애플리케이션 선언과 환경별 운영 설정을 나눈다

Infrastructure from Code는 애플리케이션의 자원 선언과 의존 관계에서 인프라 모델을 도출하는 접근이다. 내부 개발자 플랫폼을 구성할 때 개발자가 필요한 자원을 표현하는 인터페이스로 활용할 수 있다. 임의의 업무 코드만 읽으면 모든 운영 설정을 알아낸다는 뜻은 아니다.

Encore의 경우 TypeScript나 Go의 SDK primitive로 API, 데이터베이스와 Pub/Sub 같은 자원을 선언하고, 코드를 실행하지 않는 정적 분석으로 Application Model을 만든다. 자원 크기, 확장과 리전 같은 환경별 설정은 플랫폼 담당자가 정한다(2026-11-03 공식 문서 대조).

| 경로 | 자동화 범위 | 남는 설정과 책임 |
|---|---|---|
| 관리형 플랫폼 | Application Model과 플랫폼 설정을 결합해 사용자 AWS 또는 GCP 계정에 인프라를 프로비저닝 | 환경별 용량, 네트워크와 백업 설정, 변경 결과 확인 |
| 셀프호스팅 | `encore build docker`로 애플리케이션 이미지를 생성 | 인프라를 별도로 준비하고 infra config로 자원 연결, 서비스 주소, 관측 설정과 시크릿을 전달 |

셀프호스팅 이미지는 서비스를 실행하지만 데이터베이스 migration이나 cron 호출은 수행하지 않는다. 이미지 빌드 성공을 스키마 적용과 예약 작업 준비 완료로 간주하지 않고 별도 실행 절차를 둔다. 로컬에서는 선언한 SQL 자원을 Postgres 컨테이너로, 관리형 클라우드에서는 RDS 또는 Cloud SQL로 구성하므로 같은 선언을 쓴다는 사실과 실행 환경의 완전한 동일성도 구분한다.

설계 점검 제안: 기본 경로가 처리하는 자원, 외부에서 관리할 자원, 실패 복구와 데이터 이전 담당을 정한다. 플랫폼의 자동 생성 기능만으로 AI가 만든 코드의 업무 정확성이나 운영 안전성이 보장되지는 않는다. 위 설명은 문서 대조이며 실제 Encore 빌드, 배포와 이전은 시험하지 않았다. 기존 AWS와 Kubernetes 설명의 검증일은 유지한다.
