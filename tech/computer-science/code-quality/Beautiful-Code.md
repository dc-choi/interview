# 아름다운 코드의 조건과 유지

좋은 코드를 물으면 가독성, 유지보수성, 재사용성 같은 답이 나오고 곧 상황에 따라 다르다는 결론으로 끝나기 쉽다. 정답이 하나가 아니라는 말이 기준을 세우려는 노력을 대신하지 않도록, 여기서는 읽는 사람 입장의 기준을 정한다. 아름다운 코드는 읽으면서 걸리는 곳이 없는 코드다. 교과서적 품질 지표(응집, 추상화, 책임, 이름)는 [[Code-Quality-Criteria]], 읽기의 인지적 원리는 [[Readable-Code-Cognition]]에 있다.

## 왜 아름다워야 하는가

사람은 이해할 수 없는 대상 앞에서 아름다움 대신 불안을 느낀다. 이해되지 않는 코드가 더럽게 느껴지는 이유다. 다만 코드가 정말 읽기 어렵게 쓰였는지, 읽는 사람의 지식이 부족한지는 구분해야 한다.

코드는 혼자 보지 않는다. 동료가 읽고, 소유권이 넘어가고, 몇 달 뒤의 나는 사실상 남이다. 동작하는 코드가 먼저지만, 읽기 쉽게 만드는 일은 팀을 위한 배려다.

코드에서 느끼는 아름다움은 두 종류다. 생각지 못한 방식으로 문제를 깔끔하게 푸는 놀라운 아름다움은 드물고, 경력이 쌓일수록 더 드물어진다. 협업에서 추구할 것은 위화감 없이 편안하게 읽히는 자연스러운 아름다움이다.

## 자연스럽게 읽히는 코드의 네 조건

| 조건 | 보장하는 것 | 핵심 |
|---|---|---|
| 사회적 | 안정성 | 언어와 커뮤니티의 관습, 팀 규칙, 풀어야 할 문제(미션)를 따른다 |
| 신뢰적 | 안정성 | 들어가 확인하지 않아도 믿고 쓸 수 있다 |
| 선형적 | 읽기 쉬움 | 위에서 아래로 한 번만 읽으면 된다 |
| 선언적 | 읽기 쉬움 | 무엇을 하는지 이름으로 드러난다 |

### 사회적인 코드

- **관습**: 언어의 공식 스타일 가이드와 커뮤니티 표준, 언어다운 표현(Python의 Pythonic처럼)을 따른다.
- **규칙**: 팀의 네이밍, 설계 규칙, 사내 스타일 가이드를 따른다. 관습과 다르게 정했더라도 팀 규칙이 우선한다.
- **미션**: 문제가 가독성보다 성능을 요구하거나 도메인 자체가 복잡하면 코드도 그에 맞춘다. 미션이 마음에 안 든다고 무시하지 않는다.

합의되지 않은 문법 설탕과 직접 만든 DSL은 혼자 보기에는 멋져도 처음 보는 동료에게 당혹감을 준다. 옳은 방향이라도 혼자 급진적으로 바꾸기보다 합의를 거쳐 서서히 바꾼다.

### 신뢰적인 코드

믿을 수 없는 코드는 결국 열어서 확인해야 한다. 신뢰는 다음으로 판단한다.

- 부수 효과가 있는가, 있다면 알려져 있는가. 호출 시점에 따라 결과가 달라지는 함수(전역 카운터를 올리며 더하는 `sum`)는 믿을 수 없다.
- 같은 입력에 같은 출력을 내는가(순수 함수).
- 여러 번 실행해도 한 번 실행한 것과 결과가 같은가(멱등성). 순수성과 멱등성은 다른 성질이다. 부수 효과가 있어도 멱등할 수 있고, 멱등성은 재시도 안전성과 직결된다. [[Idempotency-Key]]
- 실패 조건을 알 수 있는가. `divide(a, 0)`처럼 실패할 수 있는 경우를 타입, 문서, 예외 선언으로 알린다. [[Railway-Oriented-Programming]]

### 선형적이고 선언적인 코드

루프를 머릿속으로 돌려야 하는 코드는 위아래로 왕복하며 읽게 만든다. 단계가 이름 붙은 함수 호출로 이어지면 한 번에 읽힌다. 이름은 작업 기억이 한 번에 붙잡아야 할 조각 수를 줄인다. 무의미한 문자열보다 아는 단어 세 개가 훨씬 기억하기 쉬운 것과 같다.

```ts
// 선언적이지만 한 번 더 해석해야 한다
const oddSumInline = range(1, 10).filter((n) => n % 2 === 1).reduce((acc, n) => acc + n, 0);

// 이름에서 의도가 바로 읽힌다
const oddSum = sum(oddNumbersUpTo(10));
```

두 코드의 차이가 작아 보여도 이런 차이가 쌓여 코드베이스의 읽기 비용을 만든다.

## 마음가짐: 한 번에 완성하지 않는다

네 조건을 모두 지킨 코드는 드물다. 현실에서는 알면서도 중첩된 if, 애매한 이름, 일관성 없는 규칙을 남기게 되고, 반대로 무조건적인 디자인 패턴과 과도한 추상화 같은 과설계도 아름답지 않다. 부수 효과는 필요하고, 성능이 중요하면 선형성과 선언성을 양보하기도 한다.

그래서 처음부터 완벽을 목표로 하기보다 점검과 개선을 반복해 적당한 품질(대략 70~80%)을 계속 유지한다. 쓰지 않는 기계가 녹슬듯 주변 코드가 바뀌면 품질은 떨어진다. [[Tidy-First]]

### 점검할 때 1: 코드 오너십이 흐려질 때

| 형태 | 뜻 |
|---|---|
| 강한 오너십 | 모듈마다 담당자가 있고 담당자만 수정한다 |
| 약한 오너십 | 담당자가 있지만 다른 사람도 수정하고, 담당자가 변경을 지켜본다 |
| 집단 오너십 | 코드베이스 전체를 팀이 소유하고 누구나 수정한다 |

Martin Fowler는 모듈 경계를 넘는 작은 변경까지 담당자를 기다리게 만드는 강한 오너십을 피하고, 약한 오너십과 집단 오너십을 현실적인 선택으로 본다. 집단 오너십에서도 오너십이 흐려지는 지점은 생긴다.

- **오래 방치된 코드**: 안정적이라 바꿀 일이 적지만 의존성 업그레이드와 보안 대응은 온다. 설계 의도를 문서로 남겨 두면 오너십을 빨리 되찾는다.
- **한 사람만 아는 코드**: 어려운 일을 한 사람에게만 맡기는 작은 조직에서 흔하다. 코드 리뷰, 분석 시간, 페어 프로그래밍으로 지식을 나눈다.
- **누구나 넣는 공통 모듈**: 각자 자기 기능에만 관심을 두면 중복과 비대화로 쓰레기통이 된다. 관리 책임자를 정하고 약한 오너십처럼 담당자가 변경을 검토하게 한다. [[Common-Code-Management]]

### 점검할 때 2: 악취가 날 때

목적을 알 수 없거나, 읽기 힘들거나, 너무 많은 클래스와 함수를 따라가야 하거나, 제대로 동작하는지 의심될 때다. 네 조건 중 사회적 조건을 뺀 나머지가 부족하다는 신호다. 바로 고칠 수 있으면 고치고, 아니면 주석이나 이슈로 남긴다.

## 코드를 꾸미는 수단

- **테스트**: 동작을 보장하고, 함수 안을 들여다보지 않아도 어떤 입력이 거부되는지 알려 주는 문서가 된다. [[TDD-BDD]]
- **코드 리뷰**: 여러 사람의 검증으로 신뢰를 높이고 오너십을 퍼뜨린다. 다만 모든 변경에 의무화하면 병목이 될 수 있어, 팀 문화에 따라 상황 공유, 핵심 로직, 교육처럼 필요한 경우에 집중하는 방식도 있다. [[Code-Review-Primary-Purpose]]
- **문서화**: 새 사람이 맥락, 설계, 규칙을 알아야 할 때 쓴다. 도식은 도움이 되지만 지나치게 정교할 필요는 없다.
- **주석**: 코드로 드러내기 어려운 이유를 적는다. 예외 상황, 복잡한 도메인 규칙, 라이브러리 한계를 우회한 구현, 시간이 없어 남긴 하드코딩, 애니메이션처럼 규칙 없는 숫자가 필요한 곳이다.

## 작은 리팩터링 기법

- **규칙 정하고 바꾸기**: 팀 규칙을 지키되, 더 나은 방향은 팀 발표, 스터디, 회고처럼 모두가 듣는 자리에서 합의해 바꾼다.
- **단계 분리**: 전처리, 계산, 후처리가 섞인 함수는 데이터 생성과 계산을 나누면 읽기 쉽고 각 단계를 재사용할 수 있다.
- **반복문 정리**: 반복문은 함수로 추출하거나 `filter`, `map`, `reduce` 같은 고차 함수로 바꿔 무엇을 하는지 드러낸다.
- **조건문 정리**: 복잡한 조건식은 의미 있는 이름의 함수나 변수로 추출하고, 가드 절로 중첩을 없앤다. 숫자 리터럴은 단위가 드러나는 상수로 바꾼다.

```ts
const PAYMENT_VALID_MS = 30 * 24 * 60 * 60 * 1000; // 30일, 밀리초

const canAccess = (user: User, now: number): boolean => {
  if (user.role === 'ADMIN') return true;
  if (user.isBlocked) return false;
  return now - user.paidAt <= PAYMENT_VALID_MS;
};
```

`60 * 60 * 24 * 30`처럼 초 단위 숫자를 밀리초를 돌려주는 `Date.now()`와 비교하면 유효 기간이 1000배 짧아진다. 단위를 이름에 담은 상수는 이런 실수를 드러낸다. [[Avoid-Hard-Coding]]

- **try-catch 정리**: 긴 try 블록은 어디서 예외가 났는지 알기 어렵다. 내부를 함수로 추출하거나 실패를 값으로 다룬다. [[Railway-Oriented-Programming]]

## 코드를 넘어서

코드 품질이 제품의 성공을 보장하지는 않는다. 설계, 업무 프로세스, 제품 품질이 더 중요할 때가 있다. 코드 품질 때문에 화가 난다면 너무 지엽적인 데 갇힌 것은 아닌지 돌아본다.

## 체크포인트

- 아름다운 코드를 읽는 사람 기준으로 정의하는 방법
- 사회적, 신뢰적, 선형적, 선언적 조건이 각각 무엇을 보장하는지
- 순수성과 멱등성의 차이
- 세 가지 코드 오너십과 오너십이 흐려지는 상황별 대응
- 점진적 개선을 택하는 이유와 과설계도 아름답지 않은 이유
