# 코딩 선호: 설계와 제어 흐름

2026-09-12 대화에서 사용자가 직접 확인한 코딩 선호와 적용 맥락을 기록한다. 사용자 선호의 정본은 [tech/AGENTS.md의 개인 코딩 선호](../../../AGENTS.md#개인-코딩-선호)이며, 이 문서는 조회를 위한 확인 사례와 관련 지식의 연결을 제공한다.

자료 역할은 사용자 선호의 확인 기록이다. 연결된 학습 문서 전체를 사용자 규칙이나 모든 프로젝트의 채택 결정으로 해석하지 않는다. 현재 요구사항과 대상 프로젝트의 규칙을 확인해 적용한다.

## 실제 중복의 조기 공통화와 추상화 시점

- 확인 상황: 비슷한 로직이 두 곳에 생겼고 앞으로 함께 바뀔지는 모른다.
- 사용자 답변: 미리 공통화한다. 두 곳에서 한 번에 처리하고 다른 곳에서 다시 쓸 수 있다는 점을 이유로 들었다.
- 경계 확인: 프로필 이미지 처리 하나만 필요하고 게시글 이미지 기능은 계획이 없는 상황에서는 구조를 미리 나누지 않는다고 답했다.
- 적용: 실제 반복이 있는 경우의 조기 공통화와 미래 가능성만 있는 경우의 선행 추상화를 구분한다.
- 관련 지식: [[Object-Design-Principles#SOLID를 변경 축으로 읽는다]]. 이 연결은 기존 설명과 비교하기 위한 것이다.

## 옵션이 누적된 공통 처리와 전략 패턴

- 확인 상황: 이미지 업로드 함수에 크기 조정, 워터마크, 썸네일, 알림 옵션이 붙고 호출처마다 조합이 달라졌다.
- 사용자 답변: 더 세분화하며 객체지향적으로 풀고 싶다고 했고, 같은 이미지 처리에 다른 전략을 적용하는 전략 패턴을 제안했다.
- 확인된 선호: 같은 역할의 처리 방식이 갈라진 사례에서는 전략 객체로 차이를 표현하는 방식을 선호한다.
- 미확인: 전략이 이미지 가공만 맡을지 업로드 전체를 맡을지, 저장과 알림을 어떤 객체에 둘지는 결정하지 않았다.
- 관련 지식: [[Strategy패턴이란]], [[Responsibility-Driven-Design]].

## Early return과 짧은 검증의 위치

- 확인 상황: 로그인, 활성 계정, 작성자 여부를 중첩된 `if`로 확인한 뒤 게시물을 발행했다.
- 사용자 답변: early return을 강하게 선호한다고 답했다. 실패 조건을 먼저 `throw`하는 형태로 질문을 이어갔다.
- 경계 확인: 평평하게 정리한 세 가지 검증이 짧고 해당 함수에서만 쓰인다면 그 자리에 둔다고 답했다.
- 적용: 실패 조건을 먼저 끝내고 정상 흐름을 평평하게 유지한다. 이 사례를 단일 호출 함수의 분리를 전부 금지하는 기준으로 넓히지 않는다.
- 미확인: 한 곳에서만 쓰이지만 길거나 복잡한 로직을 분리할 기준은 아직 확인하지 않았다.

## 조건식에 의미 있는 이름 붙이기

- 확인 상황: `user.isActive && user.isVerified && !user.isBlocked`를 `canPublish`에 담고, `if (!canPublish)`에서 발행 불가 오류를 던졌다.
- 사용자 답변: 한 번만 쓰는 조건도 이렇게 변수로 이름을 붙이는 방식은 가독성이 매우 좋다고 답했다.
- 적용: 여러 조건이 결합된 식은 한 번만 사용하더라도 의미가 드러나는 변수로 이름을 붙이는 것을 선호한다.

## 단순 값 선택과 삼항 연산자

- 확인 상황: `const statusLabel = isActive ? "활성" : "비활성";`처럼 간단한 조건으로 두 값 중 하나를 선택했다.
- 사용자 답변: 이런 값 선택을 삼항 연산자로 쓰는 것을 매우 선호한다고 답했다.
- 적용: 간단한 조건에 따른 두 값 선택에는 삼항 연산자를 선호한다.
- 경계 확인: 차단 여부와 활성 여부를 차례로 검사해 세 가지 문구 중 하나를 고르는 중첩 삼항 연산자는 싫다고 답했다. 삼항 연산자는 중첩해서 사용하지 않는다.

## 컬렉션의 함수형 가공

- 확인 상황: 결제 완료 주문을 `filter`하고, 상품을 `flatMap`으로 펼친 뒤 취소 상품을 제외하고 `reduce`로 총액을 계산했다.
- 사용자 답변: 이런 함수형 표현을 매우 선호한다고 답했다.
- 적용: 배열 변환의 흐름을 메서드 체이닝으로 표현하는 것을 선호한다.
- 후속 확정: 사용자는 비동기 루프에 한정하지 않고 `forEach` 자체를 피하도록 요청한 뒤, 최적화되기 전의 문제를 이유로 사용하지 않는 규칙으로 강화했다. 동기, 비동기 여부와 관계없이 `forEach`를 사용하지 않으며, 최적화 이후의 성능을 근거로 예외를 두지 않는다.
- 근거의 역할: 최적화 전의 성능과 최적화에 대한 의존을 우려한 사용자의 선택 이유를 기록한다. 특정 실행 환경이나 작업에 대한 성능 측정 결과를 기록한 것은 아니다.
- 미확인: 허용할 체이닝 길이, 성능 제약에서 반복문을 택할 기준, 중간 함수를 추출할 기준은 결정하지 않았다.

## 독립적인 비동기 작업의 동시 실행

- 확인 상황: 사용자 정보와 주문 목록 조회가 서로의 결과에 의존하지 않고, 하나라도 실패하면 전체 요청을 실패 처리해도 되는 상황에서 `Promise.all([getUser(userId), getOrders(userId)])`을 사용했다.
- 사용자 답변: 두 조회를 묶어서 동시에 실행하는 방식이 좋다고 답했다.
- 적용: 서로 독립적이고 하나라도 실패하면 전체를 실패 처리하는 비동기 작업은 `Promise.all`로 묶는 것을 선호한다.
- 후속 확인: 이미지 3개를 변환하면서 일부가 실패해도 성공한 결과는 활용해야 하는 상황에서 `Promise.allSettled(images.map(image => resizeImage(image)))`로 모든 성공과 실패 결과를 모아 각각 처리하는 방식에 동의했다.
- 적용: 독립적인 작업의 부분 성공을 활용해야 하면 `Promise.allSettled`로 결과를 모아 작업별 성공과 실패를 처리한다.
- 대량 작업: 외부 API에서 독립적인 상품 정보 1,000건을 조회하는 예시에서 사용자는 동시 실행 수를 제한하는 것을 기본으로 삼는 데 동의했다. 구체적인 상한값과 제한을 구현할 도구는 아직 정하지 않았다.
- 적용 경계: 사용자는 서버에서 작업 순서를 보장해야 하는 경우와 완료 전에 응답하면 안 되는 경우를 지적했다. 앞선 작업의 완료나 결과에 의존하거나 업무상 순서가 필요하면 다음 작업을 미리 시작하지 않고 순서대로 호출해 `await`하고, 응답에 필요한 작업은 완료를 기다린다.
- 루프 경계: 사용자는 `for` 같은 반복문에서의 순차 처리도 포함한다고 명시했다. 일반 `for` 또는 `for...of` 안에서 각 작업을 호출하고 `await`해 앞 항목이 끝난 뒤 다음 항목을 처리하며, 응답에 필요한 반복 작업은 모두 완료한 뒤 응답한다. 이 경우에는 함수형 컬렉션 표현보다 순서와 완료 대기를 우선한다.
- 관련 지식: [[Promise-Async#순차와 동시 실행]], [[Promise-Async#async/await의 의미]]. 여러 요청 사이의 순서와 데이터 변경의 원자성은 별도의 설계 범위다.
- 반복문 참고: [[JavaScript-Array-Mutation-Iteration-and-Sorting#검색과 callback 순회]]. `forEach(async ...)`는 callback Promise의 완료를 기다리지 않으므로 순차 실행과 전체 완료 대기를 위한 형태로 사용하지 않는다.

## 오류 로그와 재전파

- 확인 상황: 상위 공통 오류 처리기가 최종 오류 로그를 남기는 구조에서, 상품 조회 함수도 `catch`에서 `logger.error(error)`를 호출하고 같은 오류를 `throw error`로 다시 던졌다.
- 사용자 답변: 일반적으로 쓰는 형태 아니냐며 이 방식에 동의하고 다음 질문으로 진행하도록 했다.
- 적용: 중간 함수에서 오류를 기록한 뒤 원래 오류를 다시 던지는 형태를 허용한다. 모든 함수에 로깅용 `try/catch`를 의무화하는 규칙으로 확대하지 않는다.
- 후속 확정: 사용자는 `logger.error({ message: "상품 조회에 실패했습니다.", productId, error })`처럼 메시지, 관련 식별자와 오류를 객체로 묶어 남기는 방식에 동의했다. 오류와 함께 해당 작업의 맥락을 기록한다.
- 경계: 예시의 상위 처리기도 오류를 기록하므로 같은 오류가 중복 기록될 수 있다. 구체적인 로깅 계층과 중복 로그 처리 정책은 아직 확정하지 않았다. 로깅 라이브러리와 고정 필드 이름을 선택한 것은 아니다.
- 관련 지식: [[Error-Handling#async/await]]. 기존 문서에도 로그 후 오류를 상위로 전파하는 예시가 있다.

## 업무 오류의 전용 에러 클래스

- 확인 상황: 이미 취소된 주문을 다시 취소하려는 경우 `throw new OrderAlreadyCancelledError({ orderId: order.id });`로 표현했다.
- 사용자 답변: 호출부에서 구분해야 하는 업무 오류마다 전용 에러 클래스를 두는 방식이 좋다고 답했다.
- 적용: 호출부에서 구분해야 하는 업무 오류는 전용 에러 클래스로 표현한다. 모든 기술 오류에 개별 클래스를 만드는 규칙으로 확대하지 않는다.

## 조회 함수의 이름과 결과 부재

- 확인 상황: 결과가 없으면 `null`을 반환하는 `findUser`와, 없으면 예외를 던지는 `getUser`로 이름을 구분하는 방식을 제안했다.
- 사용자 제안: `findOne`, `findAll`로 이름을 구분하고, `null`이 오면 예외 처리하는 방식을 제시했다.
- 후속 확정: `findOne`은 조회 결과를 반환하고, 호출부에서 `null`을 확인해 `UserNotFoundError`를 던지는 예시에 동의했다.
- 적용: 조회 이름은 단건 `findOne`, 목록 `findAll`로 구분한다. `findOne`은 결과가 없으면 `null`을 반환하고, 호출부가 이를 확인해 업무 예외를 던진다.
- 목록 조회 확정: 주문 이력이 없는 사용자의 주문 목록을 `findAll`로 조회하면 예외 없이 빈 배열 `[]`을 정상 결과로 반환하는 방식에 동의했다.

```ts
const user = await findOne({ userId });

if (user === null) {
  throw new UserNotFoundError({ userId });
}
```

```ts
const orders = await orderRepository.findAll({ userId });
// 주문 이력이 없으면 [] 반환
```

## 원본 보존과 도메인 객체의 상태 변경

- 확인 상황: `map` 안에서 원본 상품 객체의 이름을 수정하고 품절 여부를 추가해 응답 배열을 만들었다.
- 사용자 답변: 원본은 최대한 건드리지 말라고 했다.
- 경계 확인: 계정 객체의 `activate()`가 자기 활성 상태를 바꾸는 사례에는 리치 도메인과 연결된다며 동의했다.
- 적용: 일반 데이터 가공은 원본 보존을 기본으로 하고, 도메인의 의미 있는 상태 전이는 객체의 메서드로 표현한다.
- 미확인: 복사의 깊이와 비용, 일반 객체의 제자리 변경을 허용할 구체적인 예외는 결정하지 않았다.
- 관련 지식: [[Defensive-Copy]], [[OOP-vs-Procedural-In-Practice#Rich Domain Model (풍부한 도메인 모델)]].

## 도메인 규칙과 애플리케이션 서비스의 책임

- 확인 과정: 사용자는 이메일 인증 요구사항과 책임이 먼저 정해져야 배치를 판단할 수 있다고 지적했다. 기존 문서의 원칙을 확인한 뒤 그 기준을 채택하는 데 동의했다.
- 예시 전제: 별도 이메일 인증 기능이 인증 완료 사실을 반영한다. `Account`는 자신의 인증 상태를 알고 있으며, 미인증 계정은 어떤 경로에서도 활성화될 수 없다.
- 채택한 적용: `Account.activate()`가 인증 여부를 검사하고 자기 활성 상태를 변경한다. 애플리케이션 서비스는 조회, 도메인 메서드 호출, 저장과 트랜잭션을 조정한다.
- 기본 기준: 도메인 객체가 자기 상태의 불변조건을 보호하고, 애플리케이션 서비스는 실행 흐름을 조정한다. 여러 객체에 걸치거나 소유가 불명확한 규칙은 요구사항과 책임 경계를 먼저 확인한다.
- 범위: 이메일 발송과 토큰 검증의 구체적인 구현, 여러 Aggregate에 걸친 규칙의 배치는 결정하지 않았다. 위 이메일 사례는 대화에서 만든 예시다.
- 관련 지식: [[Responsibility-Driven-Design#애플리케이션 객체와 NestJS 경계]], [[DDD#도메인 서비스]].

## 서비스의 생성자 주입

- 확인 상황: `OrderService`가 외부에서 만든 `OrderRepository`를 생성자로 전달받는 예시를 제시했다.
- 사용자 답변: 저장소나 메일 발송 객체를 생성자로 주입받는 것을 기본으로 삼는 데 동의했다. 특히 NestJS를 활용하므로 중요하다고 덧붙였다.
- 적용: 서비스가 사용하는 저장소나 메일 발송 객체는 생성자로 주입받는다.
- 후속 확정: 저장소, 결제, 재고, 알림 의존성 4개를 받는 생성자에도 최대 3개 인자 규칙을 적용할지 물었고, 사용자는 이런 경우에는 유연하게 판단하도록 했다. DI 생성자에는 일반 함수의 3개 제한을 기계적으로 적용하지 않는다.

```ts
class OrderService {
  constructor(
    private readonly orderRepository: OrderRepository,
  ) {}
}
```

## ORM 선택의 범위

- 확정 선호: ORM은 특정 제품에 우선순위를 두지 않고 프로젝트의 요구사항과 기존 구성에 따라 판단한다.

## 테스트 이름의 언어

- 확인 상황: `이미 취소된 주문을 다시 취소하면 예외가 발생한다`라는 이름의 테스트를 제시했다.
- 사용자 답변: 테스트는 한글 이름으로 남기는 것이 좋다고 명시했다.
- 적용: 테스트 케이스의 이름은 한국어로 작성한다.

## 도메인 테스트의 검증 대상

- 확인 상황: `order.cancel()`을 실행한 뒤 `order.isCancelled()`가 `true`인지 확인하는 테스트를 제시했다.
- 사용자 답변: 내부에 private 메서드가 있어도 공개된 동작과 결과를 통해 검증하는 것을 기본으로 삼는 데 동의했다.
- 적용: 도메인 객체의 공개 메서드를 실행하고 외부에서 확인할 수 있는 결과를 검증한다.

## 스펙과 테스트의 역할

- 확인 상황: 실패하는 테스트를 먼저 작성하고 구현한 뒤 코드를 정리하는 TDD 흐름을 기본으로 삼을지 물었다.
- 사용자 답변: 스펙을 작성하고 개발한 뒤, 테스트는 이를 검증하는 용도로 쓰면 된다고 답했다.
- 적용: 기능 개발은 스펙을 먼저 작성한 뒤 진행하고, 테스트로 구현이 스펙을 만족하는지 검증한다. TDD의 작성 순서를 기본 규칙으로 강제하지 않는다.
