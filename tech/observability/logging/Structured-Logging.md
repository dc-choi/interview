# Structured Logging

사람이 읽는 문장이 아니라 **기계가 파싱할 수 있는 형태**로 로그를 남기는 방식이다. 보통 한 이벤트를 JSON 한 줄로 출력한다. 목적은 예쁘게 찍는 것이 아니라 **필드로 검색, 집계, 마스킹이 가능해지는 것**이다.

평문 로그는 정규식으로 뜯어야 해서 포맷이 조금만 달라져도 파싱이 깨지고, 마스킹 누락도 잦다. 필드가 있으면 특정 사용자의 실패 요청만 골라내거나 엔드포인트별 에러를 집계하는 일이 쿼리 한 줄이 된다.

## JSON 스키마와 필드 명명 규약

전 팀이 같은 이름을 쓰는 것이 스키마 설계보다 중요하다. 이름이 흔들리면 서비스 간 조인이 안 되고, 검색 store에서 mapping 충돌이 난다([[Log-Pipeline]]).

최소 공통 필드:

| 필드 | 내용 | 비고 |
|---|---|---|
| `timestamp` | 이벤트 발생 시각 | ISO 8601, UTC 고정. 수집 시각과 발생 시각은 다르다 |
| `level` | 심각도 | 아래 레벨 기준 참조 |
| `message` | 사람이 읽을 한 줄 요약 | 변수를 문자열에 끼워 넣지 말고 별도 필드로 뺀다 |
| `service` | 서비스 또는 애플리케이션 이름 | 버전, 환경(`env`)도 함께 |
| `trace_id`, `span_id` | 분산 추적 식별자 | W3C Trace Context 값 그대로 ([[Correlation-ID]]) |
| `request_id` | 요청 단위 식별자 | trace가 없는 경로에서도 요청을 묶는다 |
| `error.type`, `error.message`, `error.stack` | 예외 정보 | 스택을 message에 섞지 않는다 |
| `duration_ms` | 처리 시간 | 단위를 이름에 박아 해석 오류를 막는다 |

명명 규약:

- **한 가지 표기법으로 통일한다.** snake_case든 dot notation이든 하나만 쓴다. 같은 값이 `traceId`와 `trace_id`로 갈리면 검색이 반으로 쪼개진다.
- **같은 이름에는 같은 타입을 쓴다.** `user_id`가 어떤 로그에서는 숫자, 다른 곳에서는 문자열이면 색인이 충돌한다.
- **단위와 통화는 이름에 넣는다.** `duration_ms`, `size_bytes`.
- **고카디널리티 필드를 남발하지 않는다.** 로그는 메트릭과 달리 상세를 담아도 되지만, 무한히 늘어나는 키(요청마다 새 필드명)는 store를 망가뜨린다([[Cardinality]]).

OpenTelemetry 로그 데이터 모델은 이 자리를 표준화한 참고점이다. 최상위에 `Timestamp`, `ObservedTimestamp`, `TraceId`, `SpanId`, `TraceFlags`, `SeverityText`, `SeverityNumber`, `Body`, `Resource`, `InstrumentationScope`, `Attributes`, `EventName`을 둔다. 발생 시각(`Timestamp`)과 수집 시각(`ObservedTimestamp`)을 분리하고, 이벤트의 종류는 `EventName`으로 식별하며, 자유 형식 본문은 `Body`, 나머지 구조화된 값은 `Attributes`로 나눈다. 자체 스키마를 정할 때 이 구분을 따라가면 나중에 OTel 파이프라인으로 옮길 때 손해가 적다.

## 로깅 레벨 운영 기준

레벨은 개발자의 기분이 아니라 **누가 언제 반응하는가**로 정한다.

| 레벨 | 판단 기준 | 반응 |
|---|---|---|
| `error` | 요청이나 작업이 실패했고 사용자 영향이 있다 | 알림 대상, 대시보드 집계 |
| `warn` | 아직 실패는 아니지만 열화 중이다. 재시도 성공, 폴백 사용, 임계 근접 | 추세로 감시 |
| `info` | 상태 전이 기록. 시작과 종료, 배포, 주요 도메인 이벤트 | 사후 조사용 |
| `debug` | 개발과 재현용 상세 | 평시 비활성, 필요할 때 한시 상향 |

OpenTelemetry는 `SeverityNumber`로 이 구간을 수치화한다. TRACE 1-4, DEBUG 5-8, INFO 9-12, WARN 13-16, ERROR 17-20, FATAL 21-24이며, 숫자가 낮을수록 덜 심각하다. 프레임워크마다 다른 레벨 이름을 이 범위로 정규화하면 서비스 간 비교가 가능해진다.

운영 규칙:

- **레벨은 런타임에 바꿀 수 있어야 한다.** 코드에 하드코딩하면 장애 때 상세 로그를 못 켠다.
- **레벨 필터와 샘플링은 다른 도구다.** 레벨은 종류를 자르고 샘플링은 같은 레벨 안의 양을 줄인다. 둘을 함께 쓴다([[Log-Sampling]]).
- **error를 남기고 예외를 다시 던지면 같은 실패가 여러 번 찍힌다.** 처리하는 곳에서 한 번만 error로 남긴다.
- **적재 레벨을 올려 비용을 줄이는 선택은 진단 능력과의 맞교환이다.** warn 이상만 적재하면 실패 직전의 정상 흐름이 사라져 원인 추적이 어려워질 수 있다.

## 요청 컨텍스트 전파

`trace_id`를 모든 로그에 넣으려면 컨텍스트가 호출 스택을 따라 흘러야 한다. 함수 인자로 매번 넘기는 방식은 곧 무너진다.

Node.js에서는 `AsyncLocalStorage`(`node:async_hooks`)를 쓴다. 공식 문서 설명대로 콜백과 프로미스 체인 전반에 상태를 연결해 전파하며, 웹 요청 수명 동안 데이터를 보관하는 용도로 설계됐다. v16.4.0부터 Stable이다.

- `run(store, callback)` — 콜백을 컨텍스트 안에서 실행한다. 그 안에서 만들어진 비동기 작업은 store에 접근할 수 있고, 밖에서는 접근할 수 없다.
- `getStore()` — 현재 store를 반환한다. `run()`이나 `enterWith()`로 만든 컨텍스트 밖에서 부르면 `undefined`다.

적용 형태는 요청 진입점(미들웨어, 인터셉터)에서 `trace_id`와 `request_id`를 담아 `run()`으로 감싸고, 로거가 출력 직전에 `getStore()`로 꺼내 모든 레코드에 자동으로 붙이는 것이다. 공식 문서의 예제도 HTTP 서버에서 요청마다 id를 부여하고 이후 비동기 단계에서 그 id로 로그를 찍는 구조다.

주의할 점:

- **`getStore()`가 `undefined`인 경로가 반드시 생긴다.** 스케줄러, 큐 컨슈머, 부팅 시점 로그가 그렇다. 없으면 새 id를 만들어 넣고, 없다고 예외를 던지지 않는다.
- **컨텍스트를 벗어나는 지점을 관리한다.** 이벤트 이미터에 넘긴 콜백, 외부 라이브러리의 풀링된 콜백은 컨텍스트가 끊길 수 있다.
- **store에 큰 객체를 담지 않는다.** 요청 수명 동안 유지되므로 그대로 메모리 압박이 된다.

Java, Spring 계열은 같은 역할을 MDC가 맡는다. 스레드 로컬 기반이라 비동기 경계에서 명시적으로 넘겨줘야 하는 제약이 있다.

## 필드 단위 마스킹

구조화 로깅의 실질적인 이득 중 하나가 마스킹의 정확도다. 평문 문자열은 정규식으로 잡아내야 해서 누락이 잦지만, 값이 필드로 나뉘어 있으면 로거 직렬화 단계에서 필드 단위로 허용목록과 마스킹 규칙을 강제할 수 있다.

마스킹 대상, 기법 선택과 컴플라이언스 연계는 [[PII-Masking]]에 정리했다.

## 사례

이전 환경에서 겪은 문제와 대응이다.

- **로그를 볼 수 없었던 상황** — 에러 발생 시 EC2의 CPU와 메모리가 함께 치솟아 정작 로그 파일을 열 수 없었다. 로그가 인스턴스에 묶여 있으면 장애 순간에 접근이 가장 어렵다.
- **보존과 검색의 부재** — 로그가 일정 기간이 지나면 삭제됐고, 빠르게 찾아볼 수 있는 환경 자체가 없었다.
- **중앙집중형 적재로 전환** — 분산 처리 환경에서 어떤 요청과 응답인지 묶어보기 어려워 중앙 적재를 택했다. 요청 단위로 묶는 식별자가 함께 필요했다([[Correlation-ID]]).
- **레벨 필터링** — warn 이상만 적재하는 전략을 택하고 애플리케이션 인터셉터와 FluentBit 양쪽에서 필터링했다. 적재량은 줄었지만 실패 직전의 info 흐름이 남지 않는 대가가 있다.
- **전역 마스킹** — 개인정보는 웬만하면 전송하지 않고, 필요한 경우 전역 처리 지점에서 마스킹한 뒤 적재했다.

## 면접 체크포인트

- 평문 로그 대비 구조화 로그의 이득을 검색, 집계, 마스킹으로 설명
- 필드 명명 통일과 타입 일관성이 깨졌을 때 생기는 문제
- 발생 시각과 수집 시각을 나누는 이유
- 레벨을 반응 주체 기준으로 나누고 런타임에 조정 가능하게 두는 이유
- AsyncLocalStorage로 요청 컨텍스트를 전파하는 구조와 컨텍스트가 없는 경로 처리
- 구조화 로깅이 필드 단위 마스킹을 정확하게 만드는 이유
