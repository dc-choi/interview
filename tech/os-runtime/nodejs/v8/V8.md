# V8 엔진

Google이 개발한 오픈소스 C++ JavaScript 엔진. Chrome, Electron, Node.js의 핵심 컴포넌트.

## 왜 엔진을 이해해야 하는가

엔진은 **개발자가 정해진 룰을 따른다는 가정** 아래 코드를 최적화한다. 엔진이 모든 코드를 최적화할 수는 없고 GC도 모든 메모리를 완벽하게 관리하지 못한다. 우리가 짠 코드가 엔진의 전략 조건을 만족하지 못하면 GC, Inline Cache, TurboFan의 **최적화 이점을 일부 또는 전부 잃을 수 있다**. 예를 들어 megamorphic 접근도 일반화된 cache 경로를 쓰므로 이점이 모두 사라지지는 않는다([[V8-Inline-Cache|인라인 캐시]]). 엔진 관점의 시야를 가진 개발자와 그렇지 않은 개발자 사이에는 분명한 간극이 있다.

- 최적화 팁은 대부분 동적 언어의 유연성과 맞바꾸는 트레이드오프다. hot path에서는 객체 모양과 타입을 고정하는 편이 유리하지만, 동적 구조가 주는 이점이 더 크면 얻고 잃는 것을 알고 고른다([[V8-Hidden-Class#최적화 팁|히든 클래스 최적화 팁]]).
- 학습 깊이: 컴파일러를 직접 만들지 않는다면 내부 구현 세부까지 외울 필요는 없다. 플래그, 임계값, 계층 이름은 버전마다 바뀌어 분석 내용이 금방 낡는다. 계층이 추가되고 교체된 흐름, 아키텍처와 쓰는 최적화 기법(히든 클래스, 인라인 캐시, 인라이닝, 역최적화)을 따라가고, 실제 병목은 프로파일링으로 확인한다.

## 등장 배경

초창기 JavaScript 엔진은 동적 HTML을 가볍게 실행하는 것이 우선이라 인터프리터 방식이었다. 메모리는 아꼈지만 큰 애플리케이션을 빠르게 돌리기에는 부족했다. Google Maps 같은 대규모 웹 애플리케이션을 돌리기에는 당시 엔진이 무리라는 판단에서 고성능 엔진 V8이 나왔다. 2008년 9월 Chrome 공개 글도 V8을 기존 브라우저에서는 불가능한 차세대 웹 애플리케이션을 위한 더 강력한 JavaScript 엔진으로 소개하고, 코드 전체를 오픈소스로 공개한다고 밝혔다. 이후 실행 구조는 설계 목표를 따라 바뀌었다. 처음에는 곧바로 기계어를 만드는 Full-codegen과 Crankshaft로 성능을 쫓았고, 모바일 메모리 압박이 커지자 5.9에서 바이트코드 인터프리터 Ignition을 앞단에 뒀다. 초창기 엔진이 인터프리터를 쓴 이유였던 메모리 효율이 다시 설계 목표가 된 셈이다([[V8-Ignition-TurboFan-History|파이프라인의 변천]]).

## 역할

JavaScript 소스코드를 받아 기계어로 컴파일하고 실행한다. 메모리 할당, 가비지 컬렉션, 최적화를 모두 V8이 담당한다.

## 주요 JS 엔진

| 엔진 | 개발사 | 사용처 |
|---|---|---|
| **V8** | Google | Chrome, Electron, Node.js |
| **JSC** (JavaScriptCore) | Apple | Safari, React Native |
| **SpiderMonkey** | Mozilla | Firefox, MongoDB |

1, 2차 브라우저 전쟁을 거쳐 살아남은 세 엔진. 모든 엔진은 공통적으로 **JIT 컴파일**과 **다계층 컴파일러** 아키텍처를 채택한다.

## 고수준 언어 vs 저수준 언어

- **고수준 언어**: C, C++, JS, Java 등. 가독성, 유지보수성 좋음, 성능은 상대적으로 낮음
- **저수준 언어**: 어셈블리, 기계어. 실행 속도 빠르고 성능 좋음, 가독성 낮고 유지보수 어려움

개발자가 작성한 고수준 JS를 CPU가 이해할 수 있는 저수준 언어로 변환하는 작업을 엔진이 한다.

## 인터프리터 vs 컴파일러 vs JIT

| 방식 | 특징 | 예시 |
|---|---|---|
| **인터프리터** | 중간 표현이나 소스를 실행하며 시작 비용을 낮춘다. 반복 실행의 dispatch 비용이 남는다 | V8 Ignition, CPython |
| **AOT 컴파일러** | 실행 전에 대상 기계어나 배포용 중간 표현을 만든다 | C, C++, TypeScript의 JS 변환 |
| **JIT 컴파일러** | 런타임 관찰값으로 자주 실행되는 코드를 기계어로 컴파일한다 | V8 Maglev, TurboFan, JVM HotSpot |

언어를 인터프리터 언어와 컴파일 언어로 고정 분류하지 않는다. 같은 언어도 구현체가 interpreter, baseline JIT, optimizing JIT, AOT를 조합할 수 있고, V8도 시작 시간과 최고 성능 사이를 여러 실행 계층으로 나눈다.

## 컴파일 파이프라인

```
JS 소스
  ↓ Parser → AST
  ↓ Ignition → Bytecode 실행 + 프로파일링
  ↓
  ├─ Sparkplug → 비최적화 기계어
  ├─ Maglev    → 빠른 최적화 기계어
  └─ TurboFan  → 최고 계층 최적화 기계어 (가정이 깨지면 Deopt)
```

상세: [[V8-Ignition-TurboFan|V8 컴파일 파이프라인]]

## 역사 요약

- **~5.9 (2017 이전)**: Full-codegen(실행 직전에 비최적화 기계어 생성) + Crankshaft(최적화). 메모리 과소비, ES6 최적화 한계
- **5.9+ (2017, Chrome 59)**: Ignition(인터프리터) + TurboFan(최적화)로 전면 재설계
- **9.1 (2021)**: Sparkplug 비최적화 baseline compiler 도입 → Ignition과 TurboFan의 간극 축소
- **Chrome 117 (2023)**: Maglev 빠른 최적화 compiler 도입 → Sparkplug와 TurboFan 사이 추가 계층

## 바이트코드

Ignition이 생성하는 중간 표현(IR). 플랫폼 독립적인 V8 전용 명령어 셋.

```bash
node --print-bytecode app.js
```

```
LdaSmi [1]            // accumulator에 정수 1 로드
Star r0               // r0에 저장
LdaSmi [2]
Add r0, [0]           // r0과 accumulator 더하기
Return
```

## 메모리 할당 (TLAB)

V8은 Young Generation에 객체를 할당할 때 스레드마다 미리 확보된 **TLAB(Thread-Local Allocation Buffer)**에서 **포인터 범프(pointer bump)** 방식으로 즉시 할당한다.

- 중앙 할당자 락 경합 없음
- free-list 탐색 불필요 → **O(1) 할당**
- TLAB 꽉 차면 새 TLAB 배정 또는 GC 트리거

세대 가설(대부분 객체는 금방 죽는다)과 맞물려 극도로 빠른 할당 속도를 낸다.
