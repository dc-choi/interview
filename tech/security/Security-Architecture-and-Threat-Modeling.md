# 보안 아키텍처와 위협 모델링

보안 설계는 보호할 자원, 접근 경로와 실패 조건을 연결하는 작업이다. 위협 모델링은 시스템을 공격자의 관점에서 분석하고 대응을 정하는 반복 과정이며, 설계 초기에 시작해 시스템 변경과 함께 갱신한다.

## 데이터 흐름에서 시작한다

OWASP의 위협 모델링 절차는 대상 이해, 위협 식별, 대응과 검증을 연결한다. 데이터 흐름도에는 외부 주체, 처리 과정, 저장소, 데이터 이동과 신뢰 경계를 표시한다. 신뢰 경계는 서로 다른 권한이나 신뢰 가정을 가진 영역 사이의 접점을 드러낸다.

| 질문 | 남길 근거의 예 |
| --- | --- |
| 무엇을 만드는가? | 사용자, 관리자, 외부 서비스와 데이터 흐름 |
| 무엇이 잘못될 수 있는가? | 계정 탈취, 타인 데이터 접근과 외부 입력의 악용 경로 |
| 어떻게 대응하는가? | 경로별 통제, 담당자와 남은 위험 |
| 대응이 충분한가? | 허용과 거부 시험, 우회 경로와 변경 후 재검토 |

표의 산출물은 작은 서비스에 적용한 예시다. 특정 도구나 문서 양식을 의무화한 표준으로 해석하지 않는다.

## 내부망과 인증 성공만으로 접근을 허용하지 않는다

NIST SP 800-207은 네트워크 위치나 자산 소유만으로 사용자와 자원에 암묵적인 신뢰를 부여하지 않는다. 자원에 세션을 맺기 전에 주체와 장치에 대한 인증과 인가를 수행하며, 보호의 중심은 네트워크 구역보다 자원이다.

이는 모든 요청에서 사용자가 비밀번호를 다시 입력해야 한다는 뜻이 아니다. 로그인 성공, 내부 주소와 실제 자원 접근 권한을 같은 사실로 취급하지 않는 것이 설계의 출발점이다.

## 작은 서비스에 적용한 설계 점검

다음은 위 원칙을 적용한 가상 예시다. 특정 제품의 보장이나 금융 규제 준수 판정이 아니다.

| 경로 | 실패 가정 | 통제와 확인 예시 |
| --- | --- | --- |
| 사용자에서 조회 API | 요청의 객체 ID를 타인의 것으로 바꾼다 | 서버에서 소유권이나 허용 역할을 검증하고 거부 사례를 시험한다 |
| 운영 계정에서 관리자 API | 계정 하나가 탈취된다 | 필요한 작업만 허용하고 권한 회수 후 재접근을 확인한다 |
| 애플리케이션에서 DB | 애플리케이션이 침해된다 | 연결 경로와 DB 권한을 좁히고 다른 데이터로의 접근 가능성을 확인한다 |

심층 방어를 적용할 때는 한 통제가 실패한 뒤 다른 통제가 어떤 경로를 막는지 검토한다. 방어 장비 수만 세지 않고 공유 계정이나 우회 경로처럼 함께 실패할 조건을 찾는다. 네트워크 분할도 구역 사이의 허용 경로와 권한을 함께 확인하는 대상으로 둔다. 구역을 나눴다는 사실만으로 침해 확산 차단을 보장하지 않는다.

## 권한 검사 실패와 입력 검증의 경계를 명시한다

**안전한 실패는 인가 오류를 허용으로 바꾸지 않는 설계다.** 기본 거부를 명시하고, 권한 검사에서 발생한 예외와 거부 결과를 처리해 보호 자원에 우회 접근하지 못하게 한다. 예를 들어 권한 저장소 조회가 실패했을 때 관리자 권한으로 계속 실행하지 않는 것은 이 원칙을 적용한 설계 예시다. 이를 모든 오류에서 서비스 전체를 잠그라는 요구로 확대하지 않는다. 자원별 허용 조건과 실패 경로를 정의한다.

예상하지 못한 오류의 외부 응답에는 내부 경로, SQL과 스택 추적을 노출하지 않는다. 조사에 필요한 오류 상세는 서버 측에 기록한다. 오류 응답을 숨기는 것과 실패한 작업이 실행되지 않도록 하는 것은 별개로 확인한다.

**입력 형식이 유효해도 접근 권한이나 쿼리 안전성이 증명되지는 않는다.** 서버에서 타입, 길이와 범위, 필수 필드 및 필드 사이의 업무 조건을 검증한다. 정상 형식의 계정 ID에도 별도 인가가 필요하며, SQL 값은 검증을 통과했더라도 매개변수로 바인딩한다. 테이블명이나 정렬 방향처럼 값 바인딩을 쓸 수 없는 쿼리 구조는 애플리케이션이 정한 허용 목록에 매핑한다.

다음은 위 원칙을 확인하는 시험 제안이며 실제 서비스에서 수행한 결과는 아니다.

- 권한 검사 중 예외가 나도 보호 데이터 조회나 상태 변경이 실행되지 않는지 확인한다.
- 유효한 형식의 타인 객체 ID를 보내 인가가 별도로 적용되는지 확인한다.
- 필수 값 누락, 범위 밖 값과 잘못된 중첩 항목을 부분 검증 상태로 처리하지 않는지 확인한다.
- 예상하지 못한 오류 응답에 구현 상세가 없고, 서버 측에서는 원인을 조사할 수 있는지 확인한다.

2026-10-27 OWASP의 인가, 입력 검증, 오류 처리와 SQL 인젝션 방지 안내를 대조했다. 이 절의 근거만 확인했으며 기존 사례와 다른 절 전체를 재검증하지 않아 문서의 기존 `verified_at`은 유지한다.

## 통제 목록을 보호 목표와 검증 근거에 연결한다

다음은 2026-10-27 NIST CSF 2.0을 대조해 만든 설계 점검 예시다. 다섯 행은 설명을 위한 묶음이며 표준이 정한 필수 제품 구성이나 침해 방지 보증이 아니다. CSF는 달성할 보안 결과를 분류하며 구현 방법 하나를 강제하지 않는다.

| 통제 영역 | 확인할 결과 | CSF 연결 |
| --- | --- | --- |
| 경계 보안 | 외부에서 허용한 진입점으로만 접근하는지, 별도 공개 경로가 있는지 확인한다 | PR.IR-01, 비인가 논리 접근과 사용으로부터 네트워크 및 환경 보호 |
| 네트워크 분할 | 침해된 구역에서 다른 구역으로 갈 수 있는 경로와 차단 시험을 확인한다 | PR.IR-01을 구역 사이 경로에 적용한 예시 |
| 신원과 접근 관리 | 주체별 권한을 정의하고 실제로 강제하며 정기 검토한다 | PR.AA-05, 최소 권한과 직무 분리 |
| 데이터 보호 | 저장, 전송과 사용 중 데이터의 보호 및 백업 복구 시험을 확인한다 | PR.DS-01/02/10/11 |
| 모니터링과 분석 | 네트워크 등의 이상 신호를 수집하고 여러 출처를 연결해 사고 여부를 판단한다 | DE.CM, DE.AE-03 |

암호화나 로그 수집의 도입 여부와 실제 보호 결과를 구분한다. 예를 들어 암호화된 DB에서도 과도한 읽기 권한으로 데이터가 노출될 수 있고, 로그가 모여도 대응 담당자가 없으면 조치로 이어지지 않을 수 있다. 통제마다 담당자, 실패 시 영향과 확인 근거를 연결하는 것이 적용 방법이다. 탐지 이후 대응과 복구는 [[Security-Incident-Response|보안 사고 대응]]으로 이어서 설계한다.

## 물리 접근으로 우회하는 경로도 포함한다

디지털 문서의 접근 권한만 모델링하면 같은 정보가 회의에서 말로 전달되거나 화면에 표시되는 경로를 놓친다. 직원 계정 보유, 건물 출입과 특정 회의의 정보 접근을 각각 다른 권한으로 모델링한다.

2026-10-13 미국 법무부 발표 사례에서는 OpenAI 직원이 회의실 TV의 USB 포트에 녹음 장치를 설치했다는 혐의와 장치 발견, 수사에 사용된 CCTV 및 도구 조회 기록을 제시했다. 이는 수사기관이 공개한 혐의와 증거 설명이며 유죄 확정이나 모든 행위의 독립 검증을 뜻하지 않는다. 개인 식별 정보는 재사용할 위협 모델에 필요하지 않다.

이 사례를 적용한 설계 제안은 회의실의 민감 정보 흐름, 장치 반입 및 연결 가능 지점, 허용된 출입과 실제 접근 기록을 함께 점검하는 것이다. 네트워크 인증만으로 물리 녹음 경로가 막힌다고 가정하지 않고, 이상 장치를 발견했을 때의 증거 보존과 대응은 [[Security-Incident-Response|보안 사고 대응]]에 연결한다.

## 시연의 성공 범위와 전체 장악을 구분한다

취약점 시연을 평가할 때 입력 경로, 얻은 프로세스 권한, 재부팅 뒤 유지 여부와 다른 기기/버전으로의 적용 범위를 각각 확인한다. 한 앱에서 코드가 실행됐다는 사실을 커널 장악이나 영구적인 기기 제어와 같은 뜻으로 쓰지 않는다.

2026-10-28 확인한 ns2jb 개발자의 글은 Switch 2의 특정 펌웨어에서 일반 sysmodule과 내장 `fs` 권한의 실행을 설명하며, 재연결이 필요한 tethered 방식이라고 밝힌다. 개발자는 에이전트의 단일 목표 지시로 전체 탈옥이 성공했다는 해석도 정정했다. 자동 시도는 성공하지 않았고 전체 작업에는 약 2주간 상당한 사람의 노력이 들었다는 자기 보고다. 이 사례에서 재사용할 원칙은 서명 검증 결과와 실제로 읽어 실행하는 콘텐츠 사이의 무결성 연결을 끝까지 점검하는 것이다. 중간 파일 제공 프로세스를 신뢰하는 가정도 위협 모델에 넣는다.

Calif의 2026-10-16 발표 페이지는 Signal, iMessage와 지속성 관련 시연을 제시한다. 페이지 본문만으로는 모든 기기와 OS 버전의 영향, 전체 취약점 체인과 수정 상태를 확인할 수 없다. 입력에서 제시된 iPhone 18 Pro, iOS 27.0.1과 PDF 경로는 영상 화면 및 Apple 보안 공지의 추가 대조 대상으로 남긴다. 시연 제목을 범용 도구 출시나 모든 최신 기기의 침해 가능성으로 확대하지 않는다.

이 절은 공개 글의 주장과 확인 범위를 정리한 것이다. 하드웨어 재현은 하지 않았고 기존 `verified_at`은 유지한다.

## 검토를 마칠 때

- 보호 목표는 [[CIA-Triad|기밀성, 무결성과 가용성]]으로 구분한다.
- 위협별 통제와 확인 결과를 연결하고 미확인 경로는 남은 위험으로 기록한다.
- 새 외부 연동, 관리자 기능이나 데이터 이동이 생기면 모델을 다시 검토한다.

2026-10-24 OWASP의 절차와 NIST의 제로 트러스트 정의를 대조했다. 예시 시스템의 실제 구현이나 방어 성능을 시험한 결과는 아니다.
