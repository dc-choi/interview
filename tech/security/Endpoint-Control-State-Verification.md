# 엔드포인트 보안 통제의 상태 검증과 기기 신뢰

EDR, DLP, MDM, SASE 같은 보안 솔루션을 설치했다는 사실은 모든 단말에서 그 통제가 동작한다는 증거가 아니다. 단말마다 설치, 동작, 보호 기능, 정책이 실제로 기준을 충족하는지 데이터로 판정하고 근거를 남겨야 모든 단말이 회사가 요구한 보안 수준을 지키는지 답할 수 있다. 같은 판정을 접근 통제의 기기 신뢰 신호로 쓰면 제로 트러스트의 정책 정보로 이어진다.

아래 구조와 수치는 증권사와 그 계열 조직의 보안팀이 2026-11 발표한 자체 도구 사례 기준이며, 특정 제품의 API 필드와 동작은 각 제품 문서로 확인한다.

## 콘솔마다 따로 보면 답할 수 없는 네 질문

- **동작**: agent가 설치돼 있는데 실제로 실행되고 서버와 통신하는가.
- **정책**: 회사가 요구한 설정대로 적용돼 있는가.
- **예외**: 업무상 허용한 예외에 대체 통제가 있고, 회수 절차가 동작하는가.
- **사고 대응**: 사고가 나면 해당 단말의 모든 통제 상태를 바로 모을 수 있는가.

솔루션별 콘솔과 담당자가 나뉘어 있으면 이 답을 사람이 취합해야 한다. 그래서 모든 솔루션의 상태를 단말 한 대 기준으로 모아 판정하는 도구를 만든다. 이벤트 분석은 SIEM의 몫으로 두고 설정과 동작 현황에 집중한다는 경계를 먼저 정한다.

## 판정 파이프라인

1. **수집**: 솔루션 API로 agent 상태, 정책, 보안 설정, 로그를 가져오고, 단말의 client sensor가 점검 script로 agent 실행과 보호 기능 상태를 직접 확인한다. 솔루션마다 API 요청 제한이 달라 수집 배치는 개별 주기로 돈다. API 응답은 판정에 쓰지 않는 필드까지 원본으로 저장해 둔다.
2. **단말 식별**: 솔루션마다 장치 ID가 다르므로 시리얼 번호를 우선 key로 쓰고, 없으면 hostname과 MAC 주소를 조합한다. hostname과 MAC은 다른 장치에서 겹치거나 사용 중에 바뀔 수 있으므로 일치하는 장치가 정확히 한 대일 때만 같은 장치로 확정한다. 다른 장치의 데이터가 섞이는 오판이 빠진 데이터보다 해롭다.
3. **통제 판정**: 발표의 조직은 10분마다 설치, 동작, 보호, 정책 네 항목을 판정하고, 항목 안의 기준 중 하나라도 어기면 그 항목을 오류로 둔다.
4. **근거와 이력**: 판정 결과에 당시 수집값과 적용한 기준을 함께 저장하고, 정상에서 오류로 바뀐 변경 이력을 남긴다. 나중에 왜 오류였는지 다시 설명할 수 있어야 한다.

| 항목 | 정상 조건의 예 | 데이터 출처 |
| --- | --- | --- |
| 설치 | 서버 장치 목록이나 단말 sensor 중 한쪽에서 설치 확인 | 서버 API 또는 sensor |
| 동작 | agent가 실제 실행 중이고, 단말이 쓰이는 동안 마지막 통신이 기준 시간 안 | 서버 API와 sensor, 다른 솔루션의 활동 기록 |
| 보호 | 실시간 보호가 켜져 있고 필요한 system extension이나 driver가 등록됨 | 서버와 sensor 결과가 모두 기준을 충족해야 정상 |
| 정책 | 승인 목록의 정책이 적용되고 상세 설정(자동 업데이트 등)이 기준과 같음 | 서버 API. 목록에 없는 테스트나 예외 정책은 오류가 아닌 검토 필요로 표시 |

### 기준을 코드에서 분리한다

기준은 점검 대상, 데이터 출처, 원본에서 값을 읽을 필드 경로와 정상 비교 규칙을 DB에 저장한다. 그러면 새 응답 필드를 판정에 쓸 때 코드를 고치지 않고 기준만 더한다. SaaS 솔루션은 회사가 업그레이드하지 않아도 API 응답이 바뀌고, 설치형도 새 버전에서 필드가 늘어난다. 발표의 조직은 저장한 원본을 AI가 주기적으로 훑어 새 필드(예: exploit 차단 활성화 여부)를 찾고, 벤더 정의를 근거로 보호 기준을 제안하게 한다. 담당자가 채택하면 모니터링 판정으로 결과를 본 뒤 정식 승인한다.

### 단일 콘솔이 놓치는 상태

- 단말 sensor는 EDR 설치와 실행을 확인했는데 관리 콘솔에 장치가 없다. 방화벽에 막혀 등록 요청을 못 보냈거나 등록 중 오류가 난 경우다. 사유를 서버 등록 확인 실패로 남긴다.
- 같은 단말의 IAM 로그인, DLP 사용자 활동, SASE 트래픽은 이어지는데 EDR만 오래 통신하지 않는다. 장기 미통신이면 보안 이벤트가 늦게 오거나 안 와서 대응이 늦어진다. 발표의 화면에서는 4시간 안 통신이 정상 기준이었고 실제 미통신은 3일이었다.
- 콘솔은 마지막 보고 상태인 정상과 현재 오프라인을 보여 단말이 꺼진 것처럼 보이지만, sensor로 보면 단말은 켜져 있고 DLP agent만 멈춰 있다.

여러 솔루션을 엮으면 판정이 바뀐다. 다른 agent는 정상인데 MDM만 문제인 단말은 사용 중인 단말의 MDM 오류로 판정해 재등록이나 사용자 안내로 잇는다. 디스크 암호화가 꺼진 단말이 업무 앱에 인증하고 있으면 암호화 설정을 바로 배포한다.

### 예외는 위험과 대체 통제를 같이 기록한다

USB 읽기와 쓰기 허용 같은 예외에는 그로 생기는 위험(파일 반출)과 대체 통제의 유무를 함께 식별한다. 식별되지 않은 예외 허용이 있거나 대체 통제가 없으면 모른다로 판정한다. 모른다는 정상도 오류도 아닌 별도 결과로 세어 알아내야 할 과제 목록으로 쓴다. 판정할 수 없는 상태를 정상에 섞지 않는다는 점에서 [[Security-Alert-Triage-Automation|보안 알림 triage]]의 보류 판정과 같은 원칙으로 볼 수 있다(해석).

## 위험 규칙과 AI 후보 발굴

모든 데이터가 DB에 있으면 SQL로 조회할 수 있는 조건은 모두 위험 규칙이 된다. 담당자는 SQL과 이름, 설명을 쓰고 조회된 단말과 판정 근거를 본 뒤 등록하며, 등록된 규칙은 매 배치에 적용돼 같은 위험의 다른 단말도 찾는다.

규칙 후보는 AI로 넓힌다. 배치가 데이터 분포와 현황 요약, 테이블 정보, 기존 규칙을 탐색 agent에 넘기면 탐색 agent가 탐지 SQL과 제안 이유를 쓰고, 반박 agent가 기존 규칙과의 중복과 오탐 가능성을 지적한다. SQL은 실제 DB에서 실행해 오류와 결과 건수를 확인하고, 지적이 있으면 보완을 반복한다. 담당자에게는 제안 근거, 실행 결과와 남은 반박을 함께 넘긴다. 채택한 규칙도 모니터링 모드로 오탐을 본 뒤 정식 규칙으로 올린다. 작성과 반증을 다른 agent로 나누는 구조는 [[Vulnerability-Operations-AI-Agents|취약점 운영의 AI 에이전트]]와 같다.

예로, 여러 agent의 통신이 짧은 간격으로 끊긴 단말에서 그 직전 EDR의 방어 회피(defense evasion) 탐지와 그 뒤 사내 시스템 접속 시도 급증이 함께 보이면 보안 통제 무력화 의심으로 묶는다. 통신 중단만으로는 장애와 우회를 구분할 수 없어서다. 반박 agent는 끊긴 솔루션 수 조건이 높으면 공격을 놓칠 수 있다고 지적했고, 그 판단은 담당자에게 남는다.

## 기기 신뢰 점수와 접근 통제

판정 결과를 통제(필수 솔루션의 설치와 동작, 위험한 정책), 노출(OS와 소프트웨어 취약점, 공격 표면), 위협(솔루션의 탐지 이벤트), 권한과 인증(과도한 앱 권한, 인증 기록) 네 축의 규칙으로 감점해 기기 신뢰 점수와 등급을 만든다. 설치 소프트웨어 버전은 공개 CVE 피드와 대조한다. 필수 통제가 빠지면 점수와 관계없이 일정 등급 위로 오르지 못하게 하는 과락 규칙을 둔다. 다른 축이 깨끗해도 필수 통제 하나가 빠진 단말을 안전하다고 하지 않기 위해서다. 퇴직 상태인 사용자의 단말이 온라인이고 최근 IAM 인증이 남아 있는 경우처럼 인사 정보와 활동 기록의 어긋남도 권한과 인증 축에서 잡는다.

이 도구는 제로 트러스트 구성 요소로 보면 정책 정보 지점(PIP)이자 단말의 안전 여부를 정하는 정책 결정 지점(PDP) 역할을 한다. 결과는 IAM과 ZTNA 같은 정책 집행 지점(PEP)으로 보낸다. 발표의 조직은 안전하지 않다는 신호를 Shared Signals Framework로 IAM에 보내 인증 차단이나 재인증을 요구하고, ZTNA의 device posture로 내부 앱 접근을 허용하거나 막는 방향을 계획 중이었다. 신호를 보내는 것과 수신 앱이 실제로 세션을 끊는 것은 다르므로 수신 쪽 처리 규칙을 따로 시험한다. 이 표준의 범위와 한계는 [[Session|세션]]의 SSF와 CAEP 항목, PDP와 PEP의 역할은 [[Access-Control-Models|접근 제어 모델]]에 있다.

## 보안 솔루션 설정의 기준선과 드리프트

통제 상태 판정이 단말 쪽이라면, 솔루션 자체의 설정이 기준에서 벗어나지 않았는지도 따로 본다. 관리에 틈이 생기는 지점은 대개 변경이다. 예외를 준 뒤 회수하지 않거나, 정책을 바꾸면서 여러 장비 중 일부에 빠뜨리거나, 취약점 패치와 EOL 대상을 늦게 식별하거나, 업그레이드와 교체 뒤 기존 설정을 다시 구성하지 못하는 경우다.

- **기준 설정의 버전 관리**: 솔루션마다 다른 콘솔의 메뉴와 설정값을 수집해 같은 형식의 설정 목록으로 만들고, 대시보드나 이벤트 화면처럼 기준이 필요 없는 메뉴는 잠근다. 관련자가 현재 값을 검토해 기준값을 정하면 기준 v1이 되고, 정책이 바뀌면 새 버전으로 저장한다.
- **수집 방식의 adapter**: 현재 설정을 가져오는 방법은 API, 화면 수집, CSV 내보내기 등 솔루션마다 다르다. 정해진 규격의 모듈과 결과 형식으로 감싸면 관리 시스템은 adapter만 주기적으로 호출하고, 새 솔루션을 붙일 때 시스템을 고치지 않는다. 발표의 조직은 adapter 작성 지침을 AI용으로 만들어 솔루션 담당자가 직접 만들게 했다.
- **비교와 알림**: 현재 값과 최신 기준을 비교해 어긋난 메뉴와 값을 알린다. 코드가 정의한 상태와 실제 인프라가 어긋나는 [[IaC|IaC의 구성 드리프트]]를 보안 솔루션 설정에 적용한 것이다.
- **인증 심사 항목의 통합**: 발표의 조직은 7개 규정과 심사 항목(따로 대응하면 약 300개)을 9개 범주, 58개 점검 항목으로 묶고 각 항목을 원래 조항과 연결했다. 항목마다 Level 0(취약)부터 Level 3(최적)까지 기준을 정의해 담당자가 달라도 같은 기준으로 평가하게 하고, 증적은 사내 문서 시스템에 두고 유효 기간(예: 3개월)이 지나면 갱신 알림을 보낸다. 심사마다 관련 항목만 골라 미리 제출된 증적으로 대응한다.
- **정기 점검 양식 통일**: EOL과 라이선스 정보는 공통 시트로, 솔루션 고유 점검은 별도 시트로 나눈 양식으로 월 정기 점검을 받고, 점검 문서를 모아 월별 EOL, 라이선스와 특이 사항 보고를 만든다. 점검이 진행되지 않은 솔루션은 알림을 보낸다.

AI를 쓰기 전부터 무엇이 어떤 상태여야 하는지 기준을 정하고 흩어진 정보를 표로라도 모아 둔 것이 나중에 시스템을 빠르게 만든 기반이 됐다는 것이 발표의 교훈이다. 기준을 사람이 정하지 않으면 AI가 빠르게 만든 결과물이 쓰이지 않는 시스템으로 남는다.

## 같은 방식을 개인정보 업무에 쓴 사례

같은 행사의 다른 세션은 개인정보 보호 업무의 반복 작업을 AI로 보조한 결과를 공유했다. 모두 사람이 최종 검수하는 구조였다.

- **문의 답변 초안**: 법령, 감독 규정, 내부 정책, 가이드라인을 Markdown으로 정리해 주고, 문의 채널을 하나로 모아 과거 팀 답변을 링크로 참조하게 한 뒤, 15분마다 새 문의의 취지 요약, 근거 문서, 과거 답변과 참고 법령을 묶은 초안을 팀 채널에 올린다. 1시간 주기는 답이 늦다는 재문의를, 5분 주기는 토큰 비용을 키웠다. 약 두 달간 86건을 담당자 답변과 대조하니 결론과 핵심 조건이 같은 34건, 결론은 같고 근거 표기만 다른 42건, 쟁점이나 결론이 다른 10건이었다(일치 88%, 발표자 분류). 어긋난 답에는 회사 정책과 맞지 않는 조건부 가능 같은 답이 많아 자동 발송은 하지 않았다.
- **수탁사 점검**: 안전성 확보 조치 항목별 점검 기준을 이행, 부분 이행, 미이행, 해당 없음 수준까지 나눠 주면 제출된 체크리스트와 증적 묶음을 항목별로 매핑하고 판정 사유와 보완 요청 문구를 만든다. 증적을 OCR 텍스트로 읽어 관련 문구가 있기만 하면 이행으로 판정하는 오류가 있었고, 업체가 정해진 형식으로 보내야 잘 동작한다.
- **처리 흐름표와 흐름도**: 수집부터 파기까지 생애주기 순서의 인터뷰 체크리스트로 서비스 담당자를 인터뷰하고, 정리된 내용에서 출발지와 도착지를 가진 node를 뽑아 흐름표를 만든 뒤 흐름도를 그리게 한다.

처리 흐름과 위탁 관리의 법적 기준은 [[Privacy-Operations-for-Small-Business|대표의 개인정보 운영]]에 있다.

## 서버와 인프라 진단으로 넓히기

같은 행사에서 같은 금융 그룹의 다른 보안팀은 수천 대 규모 인프라의 정기 취약점 진단을 자동화한 사례를 발표했다(2026-11 발표 기준, 자체 보고). 수집, 공통 형식 적재와 근거 보존은 위 판정 파이프라인과 닮았다(해석). 이전에는 대상 목록과 접근 조건을 회차마다 다시 확인하고, 담당자에게 스크립트를 보내거나 엑셀 인터뷰로 답을 받고, 결과 파일을 업무 PC로 반출해 보고서로 바꾸는 수작업이 반복됐다. 진단 전용 경로를 새로 만들지 않고 인프라 팀이 이미 쓰는 배포와 관리 도구에 진단을 얹은 것이 핵심이다.

| 대상 | 이미 있던 운영 체계 | 진단을 얹은 방식 |
| --- | --- | --- |
| Linux 서버 | Ansible(대상 서버에 agent 없이 SSH로 작업 배포) | 운영 팀의 Inventory를 진단 대상 목록으로 그대로 쓰고, Playbook에 스크립트 배포, 실행과 결과 회수 순서를, Role에 진단 작업을 둔다. 규제 점검 기준 항목에 과거 침해 사례에서 뽑은 감염 징후 점검을 더했다 |
| 네트워크 장비 | 저장소에 모이는 장비 설정 파일 | 원격 접속, SNMP community, 로그처럼 설정 파일로 판정할 수 있는 항목만 OS별 parser로 자동 판정하고, 운영 정책이나 승인 절차는 인터뷰로 남긴다 |
| Kubernetes | Helm chart 배포 | 기존 스크립트 대신 kube-bench와 Kubescape를 chart의 template과 values(이미지, 주기)로 배포해 규제 필수 항목 밖의 설정까지 본다 |
| OpenStack | Helm chart 배포 | 직접 맞는 규제 기준이 없어 서비스 설정, API 자원(권한, 이미지, 볼륨, 네트워크), 노드 OS 세 영역으로 나누고 공개 체크리스트에 관리망 접근 통제와 이미지 신뢰성을 더해 기준을 만든다. 노드 점검은 읽기 전용이다 |

결과는 대상마다 공통 형식으로 바꿔 한 DB에 넣고, 실행 ID로 언제 어떤 자산을 진단했는지와 양호, 취약, 인터뷰 필요를 나눠 본다. 취약 항목을 열면 점검 기준과 원본 증적이 함께 보이고, 담당자는 실제 설정값을 근거로 조치 상태나 조치하지 못한 사유를 적는다. 자산별 잔여 취약, 조치율과 중요도를 묶으면 취약점 건수가 아니라 위험 순서로 회차를 평가할 수 있다. 인터뷰 필요를 양호에 섞지 않고 따로 세는 점은 위 예외의 모른다 판정과 같은 원칙이다(해석).

## 내규 성숙도와 이행 검증

정보보호 관리체계는 법령, 인증 기준과 위험 평가에서 통제 요구 사항을 정하고, 내규에 누가 언제 어떻게 할지 기준을 두고, 실제 자산이 그 기준을 지키는지 점검한다. 같은 행사의 다른 세션 발표자는 통제 수와 자산 유형이 많아지자 사람이 챙기는 방식에서 누락이 생겼다고 했다. 바꿀 기준이 담긴 문서를 기억으로 찾다 놓치고, 여러 문서를 고치다 일부에 옛 기준이 남고, 점검 대상 자산과 항목이 빠지거나 주기가 길어져 문제를 늦게 찾는 경우다. 발표는 이 세 단계를 AI로 보조하는 체계를 설계했다고 밝혔고, 일부는 구현하고 있다고 표현했다.

통제 요구 사항 목록은 금융보안원 자율보안 프레임워크의 요구 사항, 적용 법령과 인증 요건, 위험 평가 결과를 한 목록으로 묶은 것이며 요구 사항마다 5단계 성숙도 기준을 둔다.

| 단계 | 상태 |
| --- | --- |
| 1 | 어떤 자산과 업무 절차에 어떤 기준을 적용할지 정해져 있다 |
| 2 | 담당자, 주기, 절차와 방법이 구체화돼 있다 |
| 3 | 적용 여부를 검증하고 미흡 사항을 보완한 뒤 재확인하는 절차가 있다 |
| 4 | 이행과 점검 절차가 시스템으로 구현돼 자동으로 반복된다 |
| 5 | 위반을 자동으로 사전 차단하거나 발생 시 복구해 준수 상태가 항상 유지된다 |

- **내규 평가와 개정 제안**: 모든 규정, 지침, 절차서와 가이드에서 통제마다 관련 조항을 찾아 성숙도 기준과 대조하고 현재 단계를 매긴다. 다음 단계로 가려면 어느 문서 몇 조 몇 항 뒤에 어떤 조문을 넣을지까지 기존 문체에 맞춰 제안하게 한다. 예를 들어 역할과 책임 문서화 통제가 2단계면 조직 변경 뒤 일치 여부를 확인하는 절차를 더하라는 제안이 나온다.
- **통제별 이행 인벤토리**: 통제마다 점검 대상 자산, 확인할 시스템과 자료, 판단 방법과 주기를 저장해 두면 AI가 그 자료에 접근해 점검하고 미흡 사항을 정리하며 정한 주기로 반복한다. 퇴직자 권한 회수라면 퇴직자 명단과 시스템별 권한 목록을 매일 대조해 남은 권한을 찾는다.

이 구조에서 판단 근거는 사람이 정한 요구 사항, 기준 단계와 인벤토리이고 AI는 빠짐없이 자주 대조하는 역할이다. 발표는 오탐률, 제안 조문의 채택률과 점검 정확도를 공개하지 않았으므로, 개정 제안과 미흡 판정은 담당자 검토를 거쳐 반영하는 것으로 읽는다(해석).

## 점검 질문

- 모든 단말에서 각 보안 솔루션이 설치, 동작, 보호, 정책 기준을 충족하는지 한 번에 답할 수 있는가.
- 콘솔의 마지막 보고 상태 말고 단말에서 직접 확인한 실행 상태와 다른 솔루션의 활동 기록을 대조하는가.
- 장치 식별 key가 모호할 때 두 장치를 하나로 합치지 않는가.
- 판정마다 당시 수집값과 기준을 근거로 남기는가.
- 예외마다 위험과 대체 통제를 기록하고, 모르는 상태를 별도로 세는가.
- 보안 솔루션 설정의 기준이 버전으로 관리되고, 현재 값과의 차이가 알림으로 오는가.
- 기기 신뢰 신호를 보낸 뒤 IAM과 ZTNA가 실제로 접근을 바꾸는지 시험했는가.
- 인프라 진단이 운영 팀의 대상 목록과 배포 도구를 그대로 쓰는가, 진단용 목록을 따로 관리하는가.
- 통제마다 내규의 성숙도 단계와 이행 점검의 대상, 자료, 방법과 주기가 정해져 있는가.
