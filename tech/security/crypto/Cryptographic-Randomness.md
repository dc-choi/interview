# 암호학적 난수와 실제 키의 불확실성

키 길이는 저장 형식이고, 공격자가 구분해야 할 실제 후보 수는 생성 과정에 달려 있다. 256비트 공간에 저장된 키라도 예측 가능한 시각과 작은 상태에서 결정되면 그 작은 후보 공간을 검색하는 공격을 받는다. 강한 해시로 약한 입력을 처리해도 입력에 없던 비밀의 불확실성이 생기지는 않는다.

## 난수의 용도부터 구분한다

| 용도 | 필요한 성질 |
|---|---|
| 시뮬레이션과 재현 실험 | 분포 특성, 재현 가능한 시드가 유용할 수 있음 |
| 암호 키와 인증 토큰 | 관찰한 출력으로 다음 값이나 내부 상태를 예측하기 어려워야 함 |
| salt와 nonce | 사용하는 암호 방식이 요구하는 고유성 또는 무작위성 조건을 따름 |

nonce마다 비밀성이 필요한 것은 아니며, salt도 비밀번호 대신 비밀로 보관하는 값이 아니다. 요구사항은 알고리즘과 프로토콜별로 확인한다. Python 공식 문서는 비밀값에 운영체제 난수원을 사용하는 `secrets`를 권하고 `random`을 보안 용도로 사용하지 않도록 한다.

## 비밀번호와 파일 키는 다른 값일 수 있다

PDF의 AES-256 암호화에서는 무작위 파일 키가 본문을 암호화하고, 비밀번호에서 파생한 별도 키가 파일 키를 보호한다. 파일 키 자체가 예측 가능하면 느린 비밀번호 해싱이나 긴 비밀번호만으로 이를 보완하지 못한다.

검토 순서는 다음과 같다.

1. 실제 콘텐츠 키를 만드는 함수와 난수원을 찾는다.
2. 시드가 시각, 프로세스 ID, 여유 메모리 같은 관측 가능한 값에 의존하는지 본다.
3. 비밀로 남는 상태의 후보 수와 출력 바이트를 고르는 방식을 확인한다.
4. 문서 ID, salt와 검증 블록 등 공개된 값이 후보 판별에 쓰일 수 있는지 본다.
5. 프로세스 시작, 재시작과 동시 실행에서 키나 nonce가 반복되는지 시험한다.

## 사례: PDF 구현의 작은 난수 상태

2026-10-27 V12의 구현 분석과 MuPDF 릴리스 기록을 2026-11-02 대조했다. 아래 시간은 연구자의 특정 구현과 장비에서 얻은 측정이며 일반 복호화 시간으로 사용하지 않는다.

| 분석한 구현 | 확인한 문제와 범위 |
|---|---|
| MuPDF 1.28.5 이전 | 시간으로 초기화한 LCG의 출력 바이트에 시드 9비트만 영향을 줘 512개 스트림이 남는 경로. 연구자의 Python 탐색은 약 11ms |
| Foxit Reader 2026.1.3.36551 | 시각과 분석 환경에서 0으로 채워진 메모리가 파일 키를 결정. Ryzen 9 7950X, 32스레드에서 1970년 이후 초 단위 후보 탐색 약 4.85초 |
| OpenPDF 3.0.5, iText 9.7.1 | 밀리초 시각과 JVM 여유 메모리로 초기화한 ARC4 스트림이 파일 키와 공개 salt에 함께 사용됨. 위 두 사례보다 상태 변화 폭이 큼 |

MuPDF 1.28.5 릴리스 기록에는 Bug 709668의 ChaCha20 기반 암호학적 PRNG 전환이 있다. 이 수정이 다른 제품에도 적용됐다고 가정하지 않는다. Foxit, OpenPDF와 iText의 수정 버전은 이번에 확인하지 못했다.

## 수정 뒤 기존 산출물도 확인한다

라이브러리 업데이트는 이후의 키 생성 경로를 고친다. 이미 배포된 약한 키의 문서를 소급해 보호하지는 못한다. 영향받은 생성기와 생성 기간을 확인하고, 안전한 난수원으로 **새 키를 생성해** 재암호화할 필요를 판단한다. 기존 암호화 설정을 유지하며 저장하는 동작이 새 키 생성과 같은지는 별도 확인한다.

복호화 시험은 소유하거나 허가받은 자료로 수행한다. 이 문서 작성 중 PDF 생성, 복호화와 성능 재현은 하지 않았다.
