# Password Hashing

## 저장과 검증의 기본 흐름

비밀번호는 평문이 아니라 단방향 해시로 저장한다. 해시는 평문으로 복원할 수 없으므로 DB가 유출돼도 원본 비밀번호가 바로 드러나지 않고, 같은 ID와 비밀번호를 재사용하는 다른 서비스로의 2차 피해(credential stuffing)를 줄인다.

로그인 검증은 복호화가 아니라 재계산 비교다. 사용자가 입력한 값을 저장할 때와 같은 방식으로 해싱해 DB의 해시와 일치하는지 확인한다. salt를 쓰는 현대 패스워드 해싱 함수(Argon2id, bcrypt 등)는 salt가 해시 문자열에 함께 저장되므로, 라이브러리의 verify 함수가 그 salt로 재계산해 비교한다.

## 해싱과 타이밍 누출 방어는 별개다

해시는 원래 비밀번호의 접두사를 그대로 비교하지 않게 하지만, 비교 함수와 로그인 분기의 시간 차이까지 없애지는 않는다. OWASP는 언어나 프레임워크의 안전한 비밀번호 검증 함수를 우선 사용하고, 직접 비교해야 한다면 입력 길이와 타입을 제한하며 상수 시간 비교를 적용하도록 안내한다.

- 비밀번호는 해싱 라이브러리의 `verify` 함수로 검증한다. 일반 문자열 비교나 직접 만든 바이트 비교 루프로 대체하지 않는다.
- Node.js의 `crypto.timingSafeEqual`은 같은 바이트 길이의 값 비교를 위한 도구다. 길이가 다르면 예외가 나며, 이 함수만으로 주변 코드까지 타이밍에 안전해지지는 않는다. 비밀번호 해싱과 salt 처리의 대체물도 아니다.
- 존재하지 않는 계정만 해싱 없이 즉시 반환하면, 같은 오류 문구를 써도 계정 존재 여부가 처리 시간으로 드러날 수 있다. 실패 경로의 계산과 응답 차이를 함께 점검한다.

여기서 상수 시간은 비밀값의 일치 위치에 따라 비교 시간이 달라지지 않게 한다는 뜻이다. 네트워크를 포함한 모든 요청이 정확히 같은 시간에 끝난다는 보장이 아니다. 로그인 속도 제한은 반복 관측을 어렵게 하는 보조 방어이며 안전한 비교를 대신하지 않는다. 이 절은 2026-10-23 OWASP와 Node.js 공식 문서로 대조했으며 기존 알고리즘 권고 전체의 재검증 날짜는 유지한다.

## 비밀번호 분실은 원문 조회가 아니라 재설정으로 처리한다

비밀번호를 잊은 사용자에게 기존 비밀번호를 보내는 대신, 복구 증거를 확인한 뒤 새 비밀번호를 설정하게 한다. OWASP는 재설정 토큰을 암호학적으로 안전하게 생성하고, 충분한 길이, 안전한 저장, 만료와 일회 사용을 적용하도록 권고한다. 계정 존재 여부에 따라 응답 문구와 처리 시간이 갈리지 않게 하고, 반복 요청을 제한한다.

새 비밀번호를 저장한 뒤에는 변경 사실을 알리되 비밀번호를 이메일에 넣지 않는다. 재설정만으로 자동 로그인시키지 않고 일반 로그인 절차를 거치게 하며, 기존 세션을 무효화하거나 사용자에게 무효화 선택을 제공한다. 침해가 의심되면 비밀번호 변경만으로 복구가 끝났다고 보지 않는다. 공격자가 바꾼 복구 수단과 MFA, 남아 있는 세션도 확인한다.

외부 서비스 계정은 제공자의 공식 복구 경로를 따른다. Google은 계정 소유 확인 질문과 재설정을 안내하며, 계정이나 비밀번호 지원을 제공한다고 주장하는 외부 서비스와 협력하지 않는다고 명시한다. 복구 대행자에게 비밀번호나 인증 코드를 넘기지 않는다. 이 절은 2026-10-24 OWASP와 Google 공식 안내를 대조했으며, 특정 계정의 복구 성공을 보장하지 않는다.

## 해시 vs 암호화 해시

현대 암호는 보통 한 방향 함수, 이산로그, 소인수분해, 격자 문제처럼 특정 계산이 현실적으로 어렵다는 가정에 기대며, 단순히 NP 문제를 활용한다고 설명하면 부정확하다.
패스워드 해싱은 비밀번호 후보를 대량으로 시도하는 공격을 늦추기 위해 의도적으로 느리고 메모리를 많이 쓰는 KDF를 사용한다.

암호화 해시가 만족해야 하는 조건:
- **역상 저항성**: 해시를 보고 입력값을 찾기 어려워야 함
- **제2역상 저항성**: 입력의 해시를 유지하면서 입력을 변경하기 어려워야 함
- **충돌 저항성**: 같은 해시를 가진 두 입력을 찾기 어려워야 함
- 입력이 조금만 달라져도 출력이 예측 불가능하게 달라져야 함

## 해시 DoS

해시 DoS는 공격자가 같은 해시 버킷에 몰리는 서로 다른 입력을 대량으로 보내 해시 테이블 연산을 느리게 만드는 공격이다.
입력이 같으면 출력이 같다는 성질 때문이 아니라, 서로 다른 입력이 같은 버킷이나 해시값으로 몰리는 충돌을 악용한다.
패스워드 저장용 암호화 해시의 충돌 저항성과는 별개의 운영 리스크로 봐야 한다.

## 알고리즘 선택 주의사항

| 알고리즘 | 이유 |
|---|---|
| MD5, SHA-1 | 패스워드 저장에 부적합한 빠른 일반 해시. 알려진 충돌 취약점과 별개로 비밀번호 후보의 고속 대입을 늦추지 못함 |
| SHA-256 | 일반 목적 해시라 너무 빠름. 단독으로 패스워드 저장에 쓰면 GPU와 ASIC 대입 공격에 취약 |
| bcrypt | Argon2id나 scrypt가 가능하면 우선순위가 낮음. 다만 충분한 work factor와 72바이트 입력 제한 처리를 전제로 레거시 환경에서는 여전히 사용 가능 |

## Salt의 올바른 이해

- Salt는 **레인보우 테이블 방어용**이지, 해시를 암호화하는 역할이 아님
- "salt + 복잡한 password = 안전"이라는 생각은 위험
- DB가 침해당해도 암호화되어 있으니 괜찮다는 생각도 위험
- salt는 비밀번호마다 새로 만드는 고유한 무작위 값이다. salt 없이 SHA-256 같은 빠른 해시만 쓰면 같은 비밀번호는 같은 해시가 되어, 유출된 DB에서 어떤 계정들이 비밀번호를 공유하는지 드러나고 한 번 계산한 해시를 저장된 모든 해시와 비교할 수 있다. 미리 계산한 레인보우 테이블이나 조회용 DB에 들어 있는 비밀번호라면 새로 대입하지 않고도 찾아낼 수 있다.
- 계정마다 salt가 다르면 같은 비밀번호도 저장값이 달라진다. 공격자는 해시를 하나씩 해당 salt로 깨야 하므로 걸리는 시간이 해시 개수에 비례해 늘어난다.
- Argon2id, bcrypt와 PBKDF2는 명세상 호출자가 salt를 넘겨야 하지만, 널리 쓰는 구현과 라이브러리 대부분은 salt를 내부에서 생성하고 관리한다.

## 권장 패스워드 해시 알고리즘

메모리 하드 함수는 각 비밀번호 후보의 계산에 메모리 용량과 대역폭을 요구한다. 공격자가 대량 병렬 대입을 늘릴 때의 자원 비용을 높이는 전략이며, 메모리 가격이 내려가지 않는다는 가정에 의존하지 않는다.

| 알고리즘 | 설명 |
|---|---|
| **Argon2id** | OWASP가 우선 권장하는 메모리 하드 패스워드 해시 |
| **scrypt** | Argon2id를 쓸 수 없을 때 권장되는 메모리 하드 대안 |
| **bcrypt** | Argon2id와 scrypt를 쓸 수 없는 레거시 환경의 차선책. work factor 10 이상과 입력 길이 제한 처리가 필요 |

OWASP의 최소 Argon2id 구성 예시는 메모리 19 MiB, 반복 2회, 병렬도 1이다. 최소값을 그대로 성능 보장으로 쓰지 않고 로그인 부하와 메모리 한도를 측정해 비용을 조정한다. 느린 해싱 자체도 CPU와 메모리 고갈의 표면이므로 입력 길이, 동시 검증 수와 로그인 요청률을 제한한다.

bcrypt의 72바이트 제한은 글자 수가 아니라 사용하는 인코딩의 바이트 수다. 구현체의 한도를 확인하고 초과 입력을 조용히 잘라 저장하지 않는다. 알고리즘, salt와 비용을 해시와 함께 보존하고, 로그인 검증 성공 시 오래된 비용이나 알고리즘을 새 정책으로 재해싱한다.

## 오프라인 공격과 온라인 공격

패스워드 해싱이 막는 것은 **오프라인 공격**이다. DB를 탈취한 공격자가 해시를 가져가 자기 장비에서 무한히 대입하는 상황으로, 미리 계산한 해시 표(레인보우 테이블)는 salt가, 대입 속도는 느리고 메모리를 많이 쓰는 해시 함수가 늦춘다.

로그인 화면에 직접 비밀번호를 넣어 보는 **온라인 공격**은 해싱으로 막을 수 없다.

| 공격 | 방식 |
|---|---|
| 사전 공격 | 흔한 단어와 비밀번호 목록을 한 계정에 차례로 대입한다. 무차별 대입의 한 형태다 |
| 패스워드 스프레잉 | 흔한 비밀번호 하나를 많은 계정에 시도해 계정별 실패 횟수 제한을 피한다 |
| 크리덴셜 스터핑 | 다른 서비스에서 유출된 아이디와 비밀번호 쌍을 그대로 시도한다. 비밀번호 재사용을 노린다 |

- **다중 인증**이 가장 효과적인 방어다. 새 기기, 낯선 위치, 알려진 프록시처럼 의심스러운 로그인에만 조건부로 요구할 수도 있다. [[FIDO-WebAuthn]]
- **추가 확인을 이메일 승인에 맡기지 않는다**: 비밀번호 재사용으로 메일함까지 열리면 공격자가 낯선 위치 로그인을 확인하는 메일의 승인 링크를 직접 눌러 이 단계를 통과할 수 있다. NIST SP 800-63B-4(2025-07 최종본) §3.1.3.1은 비밀번호만으로 접근될 수 있고, 전송 구간이나 중간 메일 서버에서 가로채일 수 있으며, DNS 스푸핑 같은 경로 변경 공격에 노출된다는 이유로 이메일을 out-of-band 인증에 쓰지 못하게 한다. 이메일 주소 확인 코드와 복구 코드는 인증 절차가 아니어서 이 금지에서 빠진다. 추가 확인은 OTP 앱이나 패스키처럼 기기 소지를 증명하는 수단으로 받고, 메일은 이상 징후를 알리는 통지에 쓴다.
- **유출된 비밀번호를 거부한다**: 가입과 변경 시 흔한 단어와 유출 데이터셋에 있는 비밀번호를 막는다.
- **시도 속도를 늦춘다**: 계정과 출처 기준으로 속도를 제한하고, CAPTCHA는 자동화 비용을 올리는 보조 수단으로 쓴다. IP 차단은 우회가 쉬워 단독 방어가 되지 못한다. [[Rate-Limiting]]
- **계정 잠금은 신중하게**: 고정 잠금은 공격자가 남의 계정을 일부러 잠가 서비스를 거부하게 만들 수 있다. 실패할수록 대기 시간을 두 배로 늘리는 방식이나 잠금 중에도 비밀번호 재설정 경로를 열어 두는 방식을 검토한다.
- **계정 존재를 드러내지 않는다**: 아이디가 없든 비밀번호가 틀리든 같은 오류 메시지를 준다.
- 정상 비밀번호로 로그인했는데 다중 인증에서 실패한 경우처럼 의심스러운 로그인은 사용자에게 알린다.
- 같은 기준 §4.6은 인증수단 등록과 계정 복구 같은 계정 이벤트를 사용자에게 따로 알리도록 하고, 알림은 우편 주소를 제외한 모든 알림 주소로 보내며 계정마다 알림 주소를 2개 이상 지원하도록 요구한다. 이 알림은 사용자가 계정과 관련된 사기를 알아차리게 돕는다. 두 절 모두 NIST 기준을 따르는 시스템의 요건이며 모든 민간 서비스의 법적 의무로 일반화하지 않는다.

## 출처
