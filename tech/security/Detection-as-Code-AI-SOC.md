# 탐지 룰의 코드화(Detection as Code)와 AI 에이전트 보안관제

보안관제(SOC)에서 AI는 탐지 룰을 만들고 배포하는 일, 울린 경보를 분석하고 판정하는 일, 분석가의 해석을 돕는 일에 쓰인다. 아래 사례에서 AI의 결과를 믿을 수 있게 만든 것은 프롬프트 다듬기보다 구조였다. 룰과 예외, 필드 규칙을 코드로 관리하고, 코드로 확인할 수 있는 것은 코드가 확인하며, 사람은 의도와 최종 승인을 맡는다.

아래 운영 방식과 수치는 2026년 한 금융 회사 보안팀들의 공개 발표를 바탕으로 한다. 수치는 각 팀의 자체 보고이며 측정 방법의 세부는 공개되지 않았다. 일반 원칙과 운영 제안은 따로 표시한다.

## 콘솔에서 고치던 탐지 룰의 문제

분석가가 SIEM 콘솔에서 탐지 쿼리를 직접 쓰고 고치면 다음이 생긴다.

- **형상 불일치:** 콘솔 편집은 이력이 남지 않아 지금 배포된 룰이 어떤 모습인지 아무도 확신하지 못한다.
- **필드명 불일치:** 작성자마다 같은 대상(호스트, 디바이스 등)을 다른 필드명으로 써서 SOAR나 분석가가 룰의 결과를 소비하기 어렵다.
- **사람이 동기화하는 지점:** 룰이 참조하는 lookup 파일을 따로 등록하던 시기에는 등록을 빠뜨린 룰이 배포 뒤 울리지 않았다.

## Detection as Code의 구조

룰 작성, 룰 원본, 배포 형상을 분리한다.

| 계층 | 역할 |
|---|---|
| 룰 생성 도구(control plane) | AI 기반 생성. 룰 컨벤션, 문법 강제, 전문 에이전트를 담고 오류 없이 실행되는 쿼리를 만드는 것을 목표로 한다 |
| 룰 저장소(data plane) | 탐지 룰의 단일 원천. 검증, 변환, 배포 형상과의 drift 대조, 알려진 필드명과 공통 정보 모델(CIM) 관리 |
| 배포(GitOps) | PR 검증과 설정 sandbox를 거쳐 SIEM에 자동 배포하고 실패하면 자동 rollback |

구조를 잡으며 거친 시행착오는 일반화할 만하다.

- AI에게 작성 규칙 문서만 주면 세션마다 필드명과 제목 형식이 조금씩 달라진다. 공통 필드와 배포 설정(스케줄, 알림, 억제)은 컴파일러가 주입하게 바꿨다.
- 원본과 배포 설정을 따로 관리하자 둘이 어긋났다. 룰 하나에 YAML 파일 하나를 두고 배포 설정은 그 생성물로만 관리했다.
- lookup은 폴더에 넣으면 자동 배포되게 하고 수동 등록을 없앴다.
- 룰 하나를 배포하는 데 명령이 8개가 넘던 절차를 검증부터 PR 생성까지 한 명령으로 묶었다.

AI가 참고할 맥락도 코드로 둔다. 인덱스별 필드와 시간 기준, 정규화 규칙(source profile), 운영 중인 모든 룰의 탐지 대상과 로그 소스, ATT&CK 매핑(rule inventory), 룰 이름과 심각도 산정 규칙, 실제 운영 중인 검증된 쿼리 패턴이다.

## 룰 생성에서 배포까지

1. **중복과 커버리지 판정:** 같은 위협을 이미 탐지하는 룰이 있는지 찾아 기존 룰에 편입할지 새로 만들지 정한다.
2. **로그 소스 선택:** 인덱스별 필드 정보로 탐지 가능한 소스를 고른다. 요청에 인덱스나 필드가 없어도 도구가 먼저 확인한다.
3. **쿼리 작성과 검수:** 해당 인덱스에 존재하는 필드만 쓰도록 강제한다. 리뷰 에이전트가 스키마를 검사하고 실제 데이터로 실행해 본다.
4. **컴파일:** 통과하면 배포용 설정 파일로 컴파일된다.
5. **배포 PR:** 룰 원본이 병합되면 봇이 배포 PR을 만들고 검증 결과와 바뀐 설정을 첨부한다. AI 코드 리뷰가 오탐 가능성, 필터 누락, 다른 룰과의 일관성을 짚고, 사람은 확인하고 병합한다. 예를 들어 AI 에이전트 스캐너를 User-Agent만으로 잡는 조건에 대해, 리뷰가 정상 모니터링 도구도 걸릴 수 있으니 민감 경로 접근을 조건에 더하라고 제안했다.
6. **반영:** 배포 CI가 백업, 검증, 반영을 하고 실패하면 rollback한다.

변경이 PR 단위로 남으면 탐지는 싼 실험이 된다. 여러 룰을 코드로 일괄 바꾸고, 관측하고, 안 되면 이전 형상으로 일괄 되돌린다. 발표 팀은 배포 형상 변경 1,500건 이상, 배포 룰 약 980개, 룰 컨벤션 200개를 보고했다.

### 활용 사례

- **임시 탐지 룰:** 취약점이 제보되면 제보를 구조화하고, 실제 악용 여부를 찾는 헌팅 쿼리와 취약 지점 반복 접근 같은 공격 징후용 임시 룰을 자동 배포한다. 개발자가 패치하면 임시 룰은 자동으로 내려간다. 패치 전 공백을 탐지로 메우는 방식이다.
- **커버리지 매트릭스:** 배포한 룰을 ATT&CK 기법 위에 자동으로 매핑해 무엇을 보고 있는지 한 화면에 본다. AI 관련 위협은 MITRE ATLAS(AI 시스템을 겨냥한 공격 전술과 기법 지식 베이스)에, 내부자 위협과 로그 모니터링은 직접 정의한 매트릭스에 올렸다. 빈칸은 다음 룰 후보가 되고 겹치는 룰은 정리 대상이 된다.
- **에이전트용 입력 계약:** 룰에서 나온 경보가 모두 같은 스키마와 CIM 필드로 도착하면 룰마다 파서를 만들지 않아도 에이전트가 바로 triage한다. 룰의 탐지 의도와 로직, ATT&CK 매핑이 에이전트의 맥락이 된다. 에이전트의 판정은 다시 룰 튜닝 PR로 돌아간다.

## 경보 분석을 에이전트에 맡길 때

경보 한 건만으로는 판정이 어렵다. 인코딩된 PowerShell 실행 경보를 디코딩하면 평범한 폴더 이동인데, 실행한 바이너리의 서명이 위조됐고 해시가 다르며 실행 직후 외부로 접속했다는 앞뒤 기록을 붙여야 공격으로 보인다. 반대로 재무 담당자가 온라인 PDF 변환 페이지에 문서를 올린 건은 회사에 데스크톱 라이선스가 있어 정상처럼 보이지만, 웹 서비스는 다른 약관이 적용돼 보안 위반이 될 수 있다. 이런 맥락 수집을 주당 수천 건의 티켓마다 사람이 하기는 어렵다.

### 판정 흐름

1. 서버 코드가 먼저 자료를 모은다. 요청이 서비스까지 실제로 닿았는지(서비스 로그), TI 평판, 노린 취약점이 우리 자산에 해당하는지(공격 표면 관리 데이터), 저장소의 룰과 예외 지식이다.
2. 모델이 이를 엮어 판정하고 부족하면 직접 더 조회한다.
3. 종결 판정이면 반박 모델이 놓친 것이 없는지 다시 따진다.
4. 최종 판정의 근거와 선례를 코드가 대조한다.
5. 담당자가 결론과 근거를 보고 차단이나 소명을 승인한다. 종결 결과는 다음 경보의 선례가 된다.

공격자가 노린 제품이 우리에게 없으면 그 탐지 룰을 튜닝 후보로 올린다. 룰과 예외가 이미 저장소에 코드로 있어 별도 RAG 없이 에이전트가 저장소에서 맥락을 읽었다.

### 보고된 결과

| 보고 | 내용 | 읽을 때의 경계 |
|---|---|---|
| 침해 탐지 판정 | 일주일 1,000건 이상을 관제 요원 판정과 비교해 약 98.7% 일치. 어긋난 13건 중 8건은 에이전트가 맞음 | 자체 보고. 기준 판정 자체의 오류율은 제시되지 않았다 |
| 데이터 반출 판정 | 최근 4주, 특이 사항 없음 종결은 약 97% 일치, 소명 필요는 약 94% 탐지 | 자체 보고. 반출은 변수가 많아 아직 미완이라고 밝혔다 |
| 지침 축소 | 470줄 가까이 불어난 IDS 분석 지침에서 분석 순서를 하나하나 적은 지시를 지우고 필요한 데이터는 서버가 미리 모으게 하자, 틀린 판정이 2주 전 약 29건에서 8건, 토큰 약 29%, 분석 시간 35% 감소 | 침해 분석 에이전트의 자체 보고. 판정 건수의 모수는 공개되지 않았고 같은 시기에 바뀐 다른 요인은 분리되지 않았다 |

### 발표 팀이 보고한 교훈

아래는 한 팀의 운영 경험이며 별도 측정 없이 밝힌 체감도 섞여 있다.

- **최종 답은 코드로 검증한 결과로 만든다:** open-weight 모델은 없던 업로드 기록을 지어내 보고서에 쓴 적이 있다. LLM이 조사한 결과를 그대로 내보내지 않고 코드로 검증한 결과로 답을 만들게 한 것이 가장 도움이 됐다. 코드 대신 LLM으로 사실을 한 번 더 검증하게 하자 응답만 느려지고 환각은 별로 줄지 않았다고 한다(open-weight 환경, 수치 미공개). 판정 흐름의 반박 모델은 놓친 가능성을 따지는 용도이고, 근거가 원본에 있는지의 사실 대조는 코드가 맡는다.
- **확인 못 함과 없음을 구분한다:** 조사와 판정을 나눈 멀티 에이전트 구조에서 조회 실패, 0건, 권한 오류가 문제 없음으로 읽히곤 한다. 무엇을 어디까지 확인했는지 그대로 남긴다. 0건을 없었다고 말할 수 있는 것은 그 로그가 제대로 수집되고 있을 때뿐이며, 수집되지 않은 로그는 에이전트도 볼 수 없다.
- **LLM과 코드의 역할을 나눈다:** API 호출처럼 정해진 일은 코드가 하고, 결과 해석은 LLM이 한다. 서비스 장애를 일으킬 수 있는 조치는 사람이 승인한다.
- **싼 모델로 도구를 부르게 하는 분업은 보안 판정에서 나빴다:** 입력 토큰은 줄었지만 싼 모델이 비효율적인 쿼리를 여러 번 주고받아 호출이 늘고, 무관한 결과가 맥락에 섞여 정확도와 응답 시간이 나빠졌다. 비용은 도구 호출 구조 개선과 캐싱으로 줄이는 편이 나았다. 에이전트 분업의 일반 판단은 [[Multi-Agent-Coordination-Cost|멀티 에이전트 조정 비용]]과 함께 본다.
- **모델 교체보다 하네스:** 초기 모델 교체에서 큰 향상이 있은 뒤로는 다른 open-weight 모델과 추론 수준을 바꿔도 성능이 크게 달라지지 않았다. 지침, 단계 연결, 도구, 그리고 모델이 학습하지 않은 데이터(룰과 예외, 처리 이력)의 정확성이 더 중요했다.
- **흩어진 지침의 모순:** 여러 파일의 시스템 프롬프트에 서로 어긋난 규칙이 있으면 판정이 흔들린다. 지침을 한곳에 모아 점검한다([[Agent-Repository-Instructions|에이전트 저장소 지침]]).

### 망분리 환경의 구성

발표 팀은 내부망에서 외부 AI 연결을 막는 정책에 따라 내부망의 보안 로그 분석에는 IDC에서 직접 서빙하는 open-weight 모델을 썼다. 금융권 망분리 규제와 예외는 [[Network-Separation|망분리]]에서 따로 본다. 모델은 사내 LLM gateway, 도구는 MCP gateway를 거쳐서만 쓰게 했다. 내부망 에이전트는 여러 모델을 연결할 수 있는 Google ADK로, 인터넷망의 분석 보조 에이전트는 Claude Agent SDK로 만들었다. ADK는 Gemini에 최적화돼 있지만 다양한 모델과 통합하도록 설계됐고, Python ADK는 LiteLLM connector로 다른 제공자와 자체 호스팅 endpoint를 연결한다(2026-11-19 공식 문서 기준). 공격 로그 분석이나 탐지 룰 작성이 상용 모델의 안전 장치에 막히면 gateway의 open-weight 모델로 넘기도록 보완했다.

## 분석가 보조로 쓰는 로컬 LLM

자동 판정과 달리 분석가가 자료와 질문을 골라 해석 초안을 받는 방식이다. 인코딩된 명령줄, 난독화된 JavaScript, 디스어셈블한 바이너리 함수처럼 읽는 데 도구와 시간이 드는 대상에 쓴다. 로컬에서 돌리는 이유는 내부 데이터의 외부 전송과 반복 호출 비용을 줄이기 위해서지만, 연결한 도구의 외부 전송 여부와 장비 자원은 따로 확인해야 한다.

- **답변 범위를 정한다:** 행위 요약 세 줄, 위험도와 근거, 가능한 ATT&CK 기법, 다음 조사 항목을 요청하고 확인되지 않은 내용은 추정으로 표시하게 한다. 형식이 갖춰졌다고 답이 정확한 것은 아니다.
- **해석과 실행 사실을 구분한다:** 명령의 해석은 실행 성공의 증거가 아니다. 파일 생성과 실행, 코드에 있는 기능과 실제로 실행된 기능은 EDR 기록으로 따로 확인한다. 읽기 쉽게 정리한 코드가 원래 동작을 보존했는지도 원본과 대조한다.
- **통째로 넣지 않는다:** 명령줄 전체를 한 번에 넣었을 때 정상 행위를 악성으로 오판한 사례가 있었다. 나눠 보내고 정리해 다시 물으면 결과가 달라지기도 했다.
- **로그 속 문장은 지시가 아니다:** 로그나 코드에 공격자가 심은 문장을 지시로 따르는 prompt injection은 로컬 실행으로 사라지지 않는다. 분석 자료와 지시를 나누고 도구 사용 범위를 제한한다([[LLM-Application-Security|LLM 애플리케이션 보안]]).

### AI 에이전트의 실행이 EDR에 남기는 흔적

코딩 에이전트가 보편화되면서 PowerShell, curl 같은 실행이 사람의 실행과 비슷하게 EDR에 남는다. 명령줄만으로는 실행 주체를 알 수 없어 프로세스 관계와 에이전트의 요청, 도구 호출 기록을 대조해야 한다. 실행 주체를 찾는 일과 정상, 악성을 판단하는 일도 다르다. 에이전트가 실행했어도 요청 범위를 벗어난 위험한 작업일 수 있다.

`-ExecutionPolicy Bypass`를 조사 신호로 쓰던 환경에서는 에이전트의 일상 작업에도 이 옵션이 반복해서 나타났다. Microsoft 문서(2026-11-19 확인)상 Bypass는 아무것도 막지 않고 경고나 확인도 없는 정책이다. 실행 정책은 악성 스크립트 실행을 막는 데 돕는 안전 기능이지만 보안 경계가 아니라 심층 방어의 한 겹이다. 정상 자동화에서도 쓰이므로 옵션 하나보다 실행한 프로세스, 요청 내용, 실제 스크립트와 후속 행위를 함께 본다.

인코딩된 명령(EncodedCommand)도 같다. 디코딩해 보니 에이전트의 알림음 파일을 재생하는 명령이었던 사례가 있다. 다만 디코딩 결과만으로 이벤트 전체를 정상으로 확정하지 않고, 원문 문자열과 대조하고 어떤 작업 중에 실행됐는지 전후 실행 관계를 확인한다.

## 점검 체크포인트

- 배포된 룰의 형상을 저장소에서 재현할 수 있는가, 콘솔 직접 편집이 남아 있는가
- 사람이 손으로 동기화하는 지점(lookup, 배포 상태)이 남아 있는가
- 경보가 같은 스키마와 필드로 도착해 에이전트가 파서 없이 읽을 수 있는가
- 에이전트 판정의 근거를 코드가 원본 데이터와 대조하는가
- 조회 실패, 0건, 권한 오류를 문제 없음과 구분해 기록하는가
- 0건 판정의 전제인 로그 수집 범위를 알고 있는가
- 차단과 격리 같은 조치에 사람 승인이 있는가
- 일치율을 말할 때 비교 기준과 기간, 함께 바뀐 요인을 밝히는가
