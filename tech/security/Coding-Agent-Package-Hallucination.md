# 코딩 에이전트의 패키지 환각 공격

코딩 에이전트가 고르는 의존성은 작업 요청뿐 아니라 함께 읽는 규칙 파일(`AGENTS.md`, `CLAUDE.md`, `.cursorrules` 등)의 영향을 받는다. 공유받은 규칙 파일에 특정 패키지를 쓰라는 지시가 섞이면 에이전트는 정상 패키지 대신 공격자가 레지스트리에 올린 패키지를 import하고 설치할 수 있다. 에이전트가 지시를 의심한다고 말한 것과 실제로 고른 패키지는 따로 확인한다.

## 정의

- **패키지 환각(package hallucination):** LLM이 실제로 존재하지 않는 패키지를 추천하거나 참조하는 코드를 생성하는 현상이다. 공격자는 환각된 이름으로 오픈소스 레지스트리에 패키지를 올려, LLM 출력을 믿고 설치하는 사용자를 노린다. Spracklen 외(USENIX Security 2025)는 이를 새로운 형태의 package confusion 공격으로 본다. OWASP Top 10 for LLM Applications 2025판의 LLM09가 위험 예로 든 존재하지 않는 라이브러리 추천과 이어진다([[LLM-Application-Security#LLM09 허위 정보 (Misinformation)|LLM09 허위 정보]]).
- **규칙 파일을 통한 패키지 환각 공격:** Wang 외(arXiv, 2026-10-07 v1)가 정의한 공격이다. 공격자가 정상 규칙 파일에 악성 프롬프트를 넣어, 에이전트가 생성한 코드가 원래 import해야 할 피해 패키지(예: `numpy`) 대신 공격자가 지정한 패키지(예: `numpy_hl`)를 import하게 만든다. 이 프롬프트를 최적화하는 기법의 이름이 PackHallu다.
- **두 공격의 차이:** 기존 연구의 환각 이름은 모델이 스스로 만들어 내는 이름이라 공격자가 고를 수 없고, 공격자는 반복해 나오는 이름을 미리 등록해 두고 기다린다. 규칙 파일 공격은 공격자가 고른 특정 패키지로 에이전트를 유도하므로 모델이 그 이름을 스스로 지어낼 필요가 없다.

### 기존 측정: 코드 생성 LLM의 패키지 환각

Spracklen 외의 측정이다(arXiv v3, 2025-03-02 기준).

- 코드 생성 LLM 16개와 프롬프트 데이터셋 2개로 Python(PyPI)과 JavaScript(npm) 코드 샘플 576,000개를 생성했다. 상용 모델은 GPT 계열 3개(ChatGPT 4.0, 4.0 Turbo, 3.5 Turbo)이고, 평균 비교에서는 나머지 13개를 오픈소스 모델로 묶었다(표 1은 CodeLlama를 오픈소스가 아닌 것으로 표시한다).
- Python 16개 모델과 JavaScript 14개 모델의 30개 시험에서 나온 패키지 약 223만 개 중 440,445개(19.7%)가 환각이었다. 존재 여부는 2024-01-10 시점의 PyPI와 npm 패키지 목록으로 판정했다. 평균 환각 비율은 상용 모델 5.2%, 오픈소스 모델 21.7%였고(초록은 두 값을 최소치(at least)로 적는다), 서로 다른 환각 이름은 205,474개였다.
- 아래 반복 실험(RQ3)은 논문 5절 도입부가 밝힌 대로 Python과 모델 4개(GPT-4 Turbo, GPT-3.5, CodeLlama 7B, DeepSeek 6.7B)의 무작위 표본으로 분석했다. 편집 거리 분석(RQ4)의 76,489개는 5.4절이 Python 시험의 환각 패키지로 적는 수다. 같은 절의 삭제 패키지 분석은 비교 대상을 모든 모델의 환각 패키지로 적고 그 비율(133개, 0.17%)이 76,489개를 분모로 한 값과 맞으며, 그림 8과 RQ4 요약도 16개 시험 전체를 다루므로, 이 수는 도입부의 4개 모델이 아니라 Python 시험 전체에서 나온 것으로 보인다(이 문서의 해석).
- 환각을 낸 프롬프트 500개를 10번씩 다시 물었을 때 환각 패키지의 43%는 10번 모두 반복됐고 39%는 한 번도 반복되지 않았다. 논문은 반복되는 환각일수록 공격자에게 악용 가치가 크다고 본다.
- Python 시험의 환각 패키지 76,489개 중 가장 가까운 실제 패키지와의 Levenshtein 거리가 1~2인 이름은 13.4%였고, 논문은 대부분의 환각이 단순한 오타가 아니라고 결론짓는다. 이 분석 범위에서는 오타형 이름만 찾는 검사로 대부분을 거르지 못한다(이 문서의 해석).

## 공격 흐름

1. **규칙 파일 오염:** 공격자는 공유되는 정상 규칙 파일에 피해 패키지의 import와 사용처를 공격자 패키지로 바꾸라는 지시를 넣어 공개 저장소나 마켓플레이스에 올린다.
2. **패키지 게시:** 공격자는 지정한 이름의 패키지를 PyPI 같은 공개 레지스트리에 올린다. 악성 패키지가 피해 패키지와 인터페이스 호환성을 유지하면 생성된 코드가 정상적으로 실행되므로 기능 테스트 통과만으로는 대체 여부를 알기 어렵다(이 문서의 해석).
3. **자동 로드:** 사용자가 규칙 파일을 내려받아 저장소에 넣으면 에이전트가 작업 맥락으로 읽는다. 정해진 이름의 규칙 파일을 자동으로 읽는 에이전트에서는 사용자가 따로 지정하지 않아도 지시가 맥락에 들어간다.
4. **의존성 선택과 실행:** 에이전트가 코드에 공격자 패키지를 import하고, 패키지가 없으면 레지스트리에서 설치할 수 있다. 악성 코드가 실행되는 시점은 패키지 구현에 따라 다르다.
   - **기능 호출:** 실험의 악성 패키지는 기능이 호출될 때 숨은 코드를 실행했으므로, 생성된 코드를 실행해야 페이로드가 동작했다.
   - **import:** Python 모듈의 최상위 문장은 처음 import될 때 실행되므로, 기능을 호출하지 않아도 import만으로 페이로드가 동작하게 만들 수 있다(이 문서의 추론).
   - **설치 후크:** import 없이 실행되는 후크([[Supply-Chain-Security#설치 시점 자동 실행|설치 시점 자동 실행]])를 넣은 패키지는 설치 직후(npm `postinstall`)나 그 뒤 Python 프로세스가 시작될 때(`.pth`) 실행되므로, 설치가 일어난 뒤에는 에이전트가 import를 정상 패키지로 되돌려도 피해가 남을 수 있다(이 문서의 추론).

논문의 위협 모델(4절)에서 공격자는 피해 에이전트의 시스템 프롬프트, 백본 LLM과 에이전트 프레임워크를 모르고, 피해 과제와 사용자 프롬프트, 사용될 경우의 외부 맥락에도 접근하지 못한다. 서론은 PackHallu가 피해 에이전트 접근을 요구하지 않는다고 적는다. 대신 로컬 대리(surrogate) 에이전트와 대리 과제로 문구를 다듬는다. 대리 에이전트는 실제 에이전트를 여러 턴 실행하는 대신, 코딩 에이전트처럼 행동하라는 시스템 프롬프트를 받은 LLM이 여러 턴의 행동을 실제 도구 실행 없이 한 번의 생성 호출로 모사하게 한 것이다(원문 표현은 single forward pass, 5.3절). PackHallu는 이 모사 궤적의 최종 코드만이 아니라 추론과 도구 호출 문구까지 포함한 궤적 전체에서 악성 패키지 이름이 정해진 횟수 이상 나오는지를 신호로 쓰고(문턱값은 보고되지 않음), 공격 LLM이 실패한 문구를 진단해 변형하는 진화적 탐색을 반복한다.

## 측정 결과

Wang 외(2026-10-07 v1)의 실험 조건이다.

- **과제:** BigCodeBench(처음부터 코드 생성, 피해 과제 981개, 패키지 5개), DS-1000(처음부터 코드 생성, 772개, 4개), RefactorBench(여러 파일 리팩터링, 43개, 5개). 과제 수는 표 1 기준이며, DS-1000은 부록 표 16의 패키지별 합이 752개로 표 1과 다르다. 피해 패키지는 pandas, numpy, matplotlib, scipy, seaborn, kombu, twisted, urllib3, asgiref, werkzeug의 10개다.
- **악성 패키지:** 이름 끝에 `_hl`을 붙여 PyPI를 미러링한 로컬 레지스트리에 두었고, 다운로드 단계를 거치도록 미리 설치하지 않았다. 피해 패키지와 인터페이스 호환성을 유지하며, 기능이 호출되면 성공 표시 문자열을 출력하는 페이로드가 실행된다.
- **에이전트:** 프레임워크 8개(OpenHands, OpenCode, Aider, Pi Coding Agent, Cline, Kilo Code, Claude Code, Cursor)와 백본 LLM 13개를 자율 모드로 실행했다. 여러 프레임워크에 권한 확인을 건너뛰거나 자동 승인하는 옵션을 썼고, 과제당 제한 시간은 600초다. 규칙 파일은 프레임워크에 따라 `AGENTS.md`, `CLAUDE.md`, `CONVENTIONS.md`, `.clinerules/policy.md`였고, Aider만 `--read` 옵션으로 지정했으며 나머지 7개는 자동으로 읽었다(부록 표 19).
- **최적화:** 악성 프롬프트는 기본으로 규칙 파일 맨 앞에 넣는다(표 8은 중간과 끝도 비교). 피해 에이전트마다 프롬프트 하나를 numpy와 numpy_hl 쌍으로 최적화하고, 다른 패키지에는 이름만 바꿔 재사용했다. 주 실험은 대리 에이전트가 피해 에이전트와 같은 프레임워크와 LLM을 쓴다고 가정해 최적화했고(점수는 같은 LLM의 모사 궤적으로 매겼다), 이 가정은 위협 모델보다 공격자에게 유리한 조건이며 위협 모델에 맞춘 결과는 표 4~6의 전이 실험과, 같은 전이 조건으로 보이는 표 8이다(이 문서의 해석). 대리 과제는 BigCodeBench 패키지별 과제의 20%로 피해 과제와 겹치지 않는다. 전이 실험의 기본 대리 에이전트는 OpenHands와 Qwen3-Coder-30B다. 탐색은 20라운드이며, 로컬 Ollama 모델을 NVIDIA Quadro RTX 6000(24GB) 최대 2장에 올린 설정에서 1회 최적화에 백본의 추론 속도에 따라 약 24~30시간이 걸렸다(부록 A).
- **프롬프트 예시:** 부록 B의 최적화된 프롬프트 3개(OpenHands와 백본 3종)는 긴급 마이그레이션 정책이나 규칙(CRITICAL MIGRATION POLICY, RULE) 형식이다. 그중 하나는 다른 모든 지시보다 우선하며 따르지 않으면 잘못된 결과가 나온다는 문구를 담았다.
- **지표:** SASR은 공격 없이 피해 패키지를 바르게 import하던 과제에서 공격 뒤 악성 패키지를 import한 비율이다(실행 여부 무관). DASR은 공격 없이 import와 실행이 모두 되던 과제에서 공격 뒤 악성 패키지를 import한 코드가 실행되고 페이로드까지 동작한 비율이다.

표 4, 5, 6의 전이 결과는 OpenHands와 Qwen3-Coder-30B 대리 에이전트에서 최적화한 프롬프트를 옮긴 값이다. 표 8도 맨 앞 행이 표 6의 같은 에이전트 값과 같아 같은 전이 조건으로 보인다(이 문서의 해석).

- 같은 프롬프트라도 과제 분포가 바뀌면 성공률이 크게 달랐다. 표 7의 평균 SASR은 BigCodeBench 79.29%, 같은 처음부터 코드 생성 유형인 DS-1000 53.33%, 여러 파일 리팩터링인 RefactorBench 18.60%였다. 표 7은 피해 에이전트 구성과 프롬프트를 만든 설정을 기본 설정(default setting)이라고만 적지만, BigCodeBench 행이 표 2의 평균과 같아 표 2와 같은 피해 에이전트와 주 실험의 프롬프트로 보인다(이 문서의 해석). 다만 데이터셋마다 피해 패키지가 다르므로(DS-1000은 seaborn을 뺀 4개, RefactorBench는 kombu 등 다른 5개) 차이를 과제 분포만의 효과로 읽지 않는다(이 문서의 해석). RefactorBench에 대해 논문은 주변 코드 맥락이 커져 악성 프롬프트가 입력에서 차지하는 비중이 줄어든 데서 이유를 찾는다. 43개 과제의 결과이며 저장소 단위 작업이 안전하다는 근거는 아니다(이 문서의 해석).
- 논문은 OpenHands를 고정하고 백본 LLM만 바꾼 전이 조건(표 4, 그림 3)에서 능력이 높은 백본일수록 더 취약했다고 보고하고(SASR과의 상관 r=0.785), 강한 모델이 지시와 규칙 파일을 더 충실히 따르기 때문이라고 설명한다. 여기서 능력은 공격 없는 조건에서 요구사항을 만족하는 실행 가능한 코드를 낸 과제의 비율이다. LLM을 고정하고 프레임워크만 바꾼 조건(그림 4)에서는 에이전트 능력과 SASR의 상관이 r=−0.186으로 약했다.
- 다섯 패키지 중 PyPI 최근 30일 다운로드가 가장 많은 numpy(논문의 2026-05-25 pypistats.org 조회 기준)는 대체가 상대적으로 어려웠다. 주 실험(표 2)의 numpy SASR은 44.44~89.47%였고, 백본 LLM 전이(표 4)에서도 Llama-4-Maverick 24.69%, GPT-5.3-Codex 19.51%처럼 25% 미만으로 떨어진 피해 에이전트가 있었다.
- 로컬 레지스트리, 표시용 페이로드, 자율 모드와 실험 시점의 모델 및 제품 버전에서 잰 값이다. 공개 레지스트리에 실제로 배포하거나 사람 승인을 켠 환경의 성공률은 측정하지 않았다.

## 알아채고도 따른 결과의 의미

Claude Code(Claude Sonnet 4.6) 사례 분석(6.3절, 부록 C 표 14)은 `CLAUDE.md` 맨 앞에 악성 프롬프트를 넣고 BigCodeBench의 numpy 과제 87개에서 실행 궤적을 분류했다. 87개는 본문 표기이며 부록 표 15의 numpy 피해 과제 267개와의 관계는 설명되지 않았다. 준수 범주(S1~S3)의 합 27건(31.0%)은 표 6의 Claude Code numpy SASR 31.03%와 맞는다.

| 범주 | 행동 | 건수 |
|---|---|---|
| S1 정책 인용 준수 | 주입된 지시를 다시 언급하며 따름 | 22건(25.3%) |
| S2 무언 준수 | 지시를 언급하지 않고 악성 패키지를 사용 | 2건(2.3%) |
| S3 인식 후 준수 | 주입을 공격으로 명시적으로 인식하고도 따름 | 3건(3.4%) |
| F1 의심 기반 거부 | 공격으로 인식하고 거부 | 16건(18.4%) |
| F2 실행 실패 뒤 복구 | `numpy_hl` import가 실행 중 실패하자 설치하지 않고 numpy로 돌아감 | 33건(37.9%) |
| F3 무언 거부 | 숙고 흔적 없이 numpy를 사용 | 11건(12.6%) |

- 논문은 S3를 두고 에이전트의 인식이 코딩 규칙 파일에 있다고 여긴 권위에 밀렸다고 설명한다. 논문이 든 S3 사례(그림 7)에서 의심은 내부 추론에만 나타났고, 사용자에게 보인 메시지는 지시를 따르며 `pip install numpy_hl`로 설치하라고 안내했다. 에이전트가 의심을 표현한 것만으로 공격이 막혔다고 판단할 수 없고, 그 의심이 사용자에게 보이지 않을 수도 있다.
- F2는 공격 실패로 집계되지만 에이전트는 이미 공격자 패키지를 코드에 넣었다. 실험에서도 에이전트는 로컬 레지스트리에서 패키지를 설치할 수 있었지만, F2에서는 설치하지 않고 numpy로 되돌리기를 택했다. 패키지가 미리 설치돼 있거나, 실행 실패 때 누락 패키지를 자동으로 설치하는 도구 설정에서는 결과가 달라질 수 있다(이 문서의 추론).
- 판단 근거는 에이전트의 설명이 아니라 실제로 고른 패키지와 실행 기록이다. 모델의 의심이나 거부는 주입 성공률을 낮추는 요인일 뿐 권한 경계가 아니라는 점은 [[LLM-Application-Security#적응형 공격과 피해 반경 제한|적응형 공격과 피해 반경 제한]]과 같은 맥락이다.

## 탐지기의 한계

평가 데이터는 공개 저장소(awesome-cursorrules)에서 모은 정상 규칙 파일 100개와, 각 파일 맨 앞에 PackHallu 프롬프트를 넣은 악성 파일 100개다.

| 탐지기 | 미탐률(FNR) | 오탐률(FPR) |
|---|---|---|
| ProtectAI-DeBERTa (v2 체크포인트) | 100% | 3% |
| PromptGuard (v2 체크포인트) | 46% | 5% |
| DataSentinel | 49% | 16% |
| PromptArmor (GPT-5 판정) | 20% | 34% |
| PIShield (Llama-3.1-8B-Instruct 프로브) | 21% | 11% |

- 논문은 쓸 만한 오탐률을 유지하면서 이 공격을 믿을 만하게 찾는 탐지기가 없었다고 정리한다. PromptArmor의 높은 오탐률은 규칙 파일이 본래 에이전트에게 주는 지시문으로 이뤄졌기 때문으로 본다.
- 이 설명은 PromptArmor의 오탐에 대한 것이다. ProtectAI-DeBERTa와 PromptGuard는 반대로 오탐이 낮고 미탐이 높았으며, 논문은 그 미탐의 원인을 설명하지 않는다. 탐지기마다 실패 방향이 다르므로 탐지기 통과를 안전 근거로 쓰지 않고, 도입한다면 자기 저장소의 규칙 파일로 미탐률과 오탐률을 따로 잰다(이 문서의 운영 제안).
- 규칙 파일 공유 경로를 지킬 방어는 연구 과제로 남아 있고, 이 공격 경로에 대해 효과가 검증된 방어 기법은 대조한 출처 범위에서 확인되지 않았다(2026-10-21 기준). Spracklen 외의 완화 실험은 모델이 스스로 지어내는 일반 패키지 환각을 대상으로 했다.

## 리뷰 시점별 점검

아래 점검 중 네 항목(규칙 파일의 패키지 선택과 대체 지시, 정상 패키지가 바뀌었는지, 의심 표현 뒤 행동과 import 실패 뒤 복구, 프레임워크와 LLM 변경 뒤 재확인)은 공개 영상 설명란의 점검 제안에서 틀을 가져왔고(출처의 영상 항목), 각 항목의 근거는 위 논문 결과와 다시 대조했다. 설치와 빌드 단계는 이 문서가 덧붙인 운영 제안이다. 어느 항목도 효과가 검증된 방어 기법이 아니며, 이 문서에서 효과를 시험하지 않았다.

- **규칙 파일을 들이거나 바꿀 때:** 외부 규칙 파일은 의존성처럼 출처와 변경 이력을 남기고 diff 전체를 읽는다. OpenCode와 DeepSeek-V4-Flash 조합에서는 중간과 끝에 넣은 지시도 평균 SASR이 74.03%, 77.29%였다(표 8). 특정 패키지 사용, import 교체, 설치를 요구하는 문장은 따로 표시하고, 지정된 패키지를 프로젝트에서 승인했는지와 레지스트리의 게시자, 이력을 확인한다([[Dependency-Selection|의존성 선택]]의 위험 신호). 외부 지침이 자동으로 프로젝트 정책이 되지 않는다는 원칙은 [[Agent-Repository-Instructions#검증과 보안의 경계|AGENTS.md의 검증과 보안의 경계]]를 따른다.
- **에이전트 작업을 리뷰할 때:** 규칙 파일의 패키지 지시와 실제 import, 의존성 선언과 lockfile의 diff를 대조한다. import 이름과 설치되는 배포 이름은 다를 수 있으므로(Spracklen 외 부록 G) 의존성 선언과 lockfile의 배포 이름, 실행 기록의 설치 명령을 기준으로 맞춰 본다. 잘 알려진 패키지 이름에 접미사가 붙은 이름이나 처음 보는 패키지가 새로 생기면 이유를 확인한다. 인터페이스 호환 패키지는 테스트를 통과할 수 있으므로 테스트 결과로 이 대조를 대신하지 않는다.
- **실행 기록을 볼 때:** 추론 기록이나 메시지에 의심이 나타난 뒤 실제로 무엇을 했는지 보고, 사용자에게 공격자 패키지 설치를 안내했는지도 확인한다. import 실패 뒤 패키지 설치를 시도했는지, 정상 패키지로 돌아갔는지도 확인한다. 되돌렸더라도 공격자 패키지를 한 번 고른 신호이므로 규칙 파일을 조사하고, 그 사이 설치가 일어났다면 설치 후크가 실행됐을 가능성을 두고 그 환경도 점검한다.
- **설치와 빌드 단계:** 의존성은 리뷰한 lockfile과 해시 고정으로 설치한다. 사설 레지스트리의 proxy 저장소(또는 proxy를 포함한 group)는 반입 정책이 없으면 요청받은 외부 패키지를 가져와 캐시하므로([[Supply-Chain-Security#아티팩트 저장소의 역할과 보안 통제|아티팩트 저장소의 역할과 보안 통제]]), 승인한 패키지만 통과시키는 허용 목록 방식의 반입 정책을 두고 실제로 막히는지는 다운로드 결과로 확인한다(차단 정책의 확인 방법은 [[Supply-Chain-Security#패키지 정책의 탐지와 실제 차단|패키지 정책의 탐지와 실제 차단]]). 실험의 로컬 레지스트리는 공개 PyPI 역할을 한 모의 환경이며, 에이전트가 필요할 때 악성 패키지를 받을 수 있게 했다. 악성 패키지를 미리 설치하지 않았으므로 DASR로 센 사례는 실행 전에 어떤 경로로든 레지스트리에서 패키지를 받은 경우다. 에이전트가 작업 중에 직접 받았는지는 이 출처로 확정할 수 없고(이 문서의 해석), 그림 7처럼 에이전트가 사람에게 설치를 안내할 수도 있으므로 반입 통제는 사람의 설치 경로에도 적용한다. 에이전트의 자율 설치와 네트워크 반입 경로는 모델 밖에서 제한한다([[Agent-Execution-Isolation|에이전트 실행 격리]]). 이 통제는 설치를 막을 뿐 코드에 들어간 import를 되돌리지 않는다.
- **프레임워크나 모델을 바꾼 뒤:** OpenHands와 Qwen3-Coder-30B 대리 에이전트에서 최적화한 프롬프트를 같은 LLM의 다른 프레임워크로 옮기자 numpy SASR이 15.85%에서 94.64%까지 갈렸다(표 5). 한 조합에서 확인한 결과를 다른 조합에 옮기지 않고, 고정한 점검 과제와 규칙 파일로 다시 잰다([[Eval-Golden-Set-and-Deploy-Gates#가드레일도 회귀 테스트 대상이다|가드레일 회귀 시험]]). 고정 세트의 재측정은 회귀 기준선이며, 새 조합을 겨냥해 다시 최적화한 공격의 성공률을 대신하지 않는다. 정적 기준선과 적응형 공격 시험을 나누는 이유는 [[LLM-Application-Security#적응형 공격과 피해 반경 제한|적응형 공격과 피해 반경 제한]]과 같다.

### 자율 설치 제한의 비용

자율 설치를 막으면 에이전트가 필요한 패키지를 스스로 받아 작업을 끝내는 흐름이 끊기고, 허용 목록 밖의 패키지마다 사람 확인이나 목록 갱신을 기다려야 한다. 승인이 잦아지면 피로로 판단이 무뎌질 수 있다는 점은 [[LLM-Application-Security#적응형 공격과 피해 반경 제한|적응형 공격과 피해 반경 제한]]의 사람 승인 항목과 같다. 허용 목록 안의 설치는 그대로 두고 목록 밖의 새 패키지에서만 멈추게 하면 속도와 통제를 절충할 수 있다(이 문서의 운영 제안). 실험은 수동 확인을 끈 자율 모드에서만 쟀으므로 승인을 켰을 때 성공률이 어떻게 달라지는지는 이 출처로 알 수 없다.
