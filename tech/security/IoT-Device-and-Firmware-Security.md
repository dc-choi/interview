# IoT 기기 인증과 펌웨어 보안

IoT 보안은 연결 상대의 인증, 실행할 소프트웨어의 검증, 업데이트 이후의 운영을 나눠 설계한다. 인증서, secure boot와 서명된 업데이트는 서로 다른 경계를 보호한다.

## 기기 식별과 인증

기기를 구분하는 식별자와 연결 상대를 인증하는 증거는 다르다. NISTIR 8259A는 논리적 식별자와 물리적 식별자를 자산 관리의 기반으로 다룬다. 식별자만 제시했다고 인증이 완료되는 것은 아니다.

인증서 기반 연결에서는 공개키가 담긴 인증서와 대응하는 개인키의 보유 증명이 함께 필요하다. AWS IoT Core는 등록된 인증서의 상태와 계정을 확인하고 개인키 보유를 검증한다. 인증서는 활성 상태이고 만료 전이어야 한다. 기기별 인증서를 사용하면 개별 폐기와 교체가 쉬워지며, 만료에 대비한 회전도 필요하다. 공장 출하 때 인증서를 넣었다는 사실만으로 평생 신뢰가 유지되지는 않는다.

## 부팅 검증과 업데이트 검증

| 경계 | 확인하는 것 | 별도로 확인할 것 |
| --- | --- | --- |
| 연결 인증 | 접속 상대가 허용된 자격증명과 개인키를 보유하는지 | 자격증명 폐기, 교체와 허용 작업 |
| Secure boot | 부팅할 소프트웨어가 신뢰 정책에 맞는지 | 실행 중 취약점과 신뢰 키 관리 |
| OTA 업데이트 | 설치할 소프트웨어의 진위와 무결성 | 설치 실패 복구, 적용 버전과 지원 기간 |

ETSI EN 303 645 V3.1.3의 5.7-1은 secure boot를 통한 소프트웨어 검증을 권고한다. 네트워크로 전달하는 업데이트는 5.3-10에 따라 신뢰 관계를 통해 진위와 무결성을 검증해야 한다. 디지털 서명과 인증된 통신 채널은 그 수단의 예이며, 이 조항을 모든 기기에 두 수단을 동시에 강제하는 규칙으로 확대하지 않는다.

OTA는 네트워크를 통한 업데이트 전달 방식이다. 전송이 끝난 상태, 설치가 끝난 상태와 새 버전으로 정상 부팅한 상태를 나눠 확인하는 것이 운영상 유용하다. Secure boot 통과를 실행 중 취약점 부재의 증거로 삼지 않는 것도 같은 경계 구분이다.

## 수명주기 점검

다음은 표준의 요구와 기능을 실제 운영에 연결하는 점검 제안이다.

1. 자산별 식별자, 인증서와 적용 소프트웨어 버전을 대응시킨다.
2. 공통 기본 비밀번호에 의존하지 않는지 확인한다. ETSI 5.1-1은 비밀번호 인증을 쓰는 기기가 공장 기본 상태를 벗어났을 때 기기별 고유 비밀번호 또는 사용자가 정한 비밀번호를 요구한다.
3. 인증서 만료, 유출과 기기 폐기 시 교체하거나 접근을 끊는 절차를 확인한다.
4. 업데이트 중단 뒤 정상 버전으로 복구할 수 있는지 시험한다. 복구 파티션이나 이중 flash bank는 가능한 구현 예다.
5. 제조사가 공개한 보안 지원 기간을 확인하고, 실제 적용 버전과 업데이트 실패를 관찰한다.

NISTIR 8259A의 기본 역량은 기기 식별, 구성 변경, 데이터 보호, 인터페이스 접근 제한, 소프트웨어 업데이트, 보안 상태 인지다. 인증과 부팅 검증만으로 전체 운영 요건이 충족됐다고 판단하지 않는다.

## 검증 범위

2026-11-03 NISTIR 8259A, ETSI EN 303 645 V3.1.3과 AWS IoT Core의 인증서 문서를 대조했다. 특정 기기, 펌웨어나 인증서 교체 동작을 시험하지 않았다. 영상의 공격 비중, 영구 신원 보장과 공격 완전 차단 주장은 채택하지 않았다.
