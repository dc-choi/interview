# 아카이브 파서의 해석 차이와 검사 우회

아카이브를 검사하는 도구와 실제로 추출하는 도구가 같은 바이트열을 다르게 해석하면, 검사한 파일과 설치한 파일이 달라질 수 있다. 메모리 안전한 언어로 작성한 파서도 형식과 상태를 잘못 해석하면 이 문제를 만들 수 있다.

## 파일 목록보다 해석 계약이 먼저다

tar는 한 가지 고정 형식이 아니라 V7, UStar/pax, GNU 등의 형식과 확장이 쌓인 계열이다. 확장 레코드가 파일 이름과 크기를 바꾸며, 크기 해석은 다음 헤더를 어디서 읽을지도 바꾼다. 검사기가 본 이름만 나중에 재검사해도 앞 단계의 프레이밍 차이를 복구하지 못할 수 있다.

| 검사기와 추출기의 차이 | 가능한 결과 |
|---|---|
| 한쪽만 뒤에 붙은 파일을 읽음 | 검사에 없던 추가 파일 설치 |
| 확장 이름의 우선순위가 다름 | 같은 항목이 서로 다른 경로로 추출 |
| 크기와 다음 헤더 위치의 해석이 다름 | 두 도구가 서로 다른 파일 집합을 봄 |
| 링크와 파일 경로의 해석이 다름 | 허용한 추출 경계를 벗어나는 쓰기 위험 |

마지막 행의 경로 안전성과 파서 간 일관성은 별도 통제다. 파싱 결과가 같더라도 절대 경로, 상위 경로 이동, 링크와 덮어쓰기 정책을 검사해야 한다([[File-Upload-Security|파일 업로드 보안]]).

## 형식과 상태를 일찍 확정한다

방어 설계는 첫 헤더의 식별자로 형식 계열을 확정하고, 그 뒤 다른 계열을 섞는 입력을 거부하는 방식으로 모호성을 줄일 수 있다. 확장 상태의 수명, 적용 순서와 실패 전이를 명시하며, 검사와 설치가 같은 해석을 사용하게 한다.

1. 원본 아카이브의 해시와 파서 버전을 함께 기록한다.
2. 파일 이름뿐 아니라 크기, 유형과 링크 대상을 정규화된 목록으로 비교한다.
3. 서로 다른 파서와 경계 입력을 비교하는 differential test를 수행한다.
4. 추출은 비어 있는 제한된 디렉터리에서 수행하고, 경로 이탈과 자원 고갈도 별도로 제한한다.
5. 검사 성공과 빌드 코드의 실행 허가를 분리한다. Python sdist는 빌드 단계에서 코드를 실행할 수 있다.

이 절은 운영 점검 제안이다. 이 문서를 작성하며 아카이브를 추출하거나 공격 입력을 실행하지 않았다.

## 구현 사례: tar-codec

2026-10-27 Astral 발표는 uv 0.13부터 sdist 파싱에 tar-codec를 사용한다고 밝힌다. 첫 블록의 magic/version으로 UStar/pax 또는 GNU 계열을 고정하고 계열 혼용을 거부한다. 이전 구현보다 약 2배 빠르다는 수치는 uv의 자체 벤치마크다. 다른 작업과 시스템의 처리량을 보장하거나 tar의 모든 위험을 제거했다는 뜻은 아니다.
