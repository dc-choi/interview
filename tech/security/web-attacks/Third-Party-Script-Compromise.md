# 서드파티 스크립트 침해

분석, 성능 측정, 채팅, 광고처럼 다른 회사가 호스팅하는 JavaScript를 `<script src>`로 페이지에 넣으면 그 코드는 자기 회사 코드와 같은 권한으로 실행된다. 공급자가 침해되면 공격자는 공급자의 파일만 바꿔서 그 스크립트를 쓰는 모든 사이트의 사용자 세션 안에서 코드를 실행할 수 있다. 스크립트의 원래 용도(속도 측정, 방문 집계)는 브라우저가 강제하는 권한 경계가 아니다.

패키지 설치와 빌드 단계의 공급망 공격은 [[Supply-Chain-Security|공급망 보안]]이 다룬다. 이 문서는 사용자의 브라우저가 실행 시점에 외부에서 받아 오는 스크립트를 다루고, 같은 방식으로 원격 스크립트를 받는 데스크톱 앱의 사례도 함께 본다.

## 권한은 용도가 아니라 실행 위치가 정한다

- **같은 권한** — 페이지에 직접 넣은 스크립트는 DOM을 읽고 바꾸며, 페이지가 이미 올려 둔 함수와 라이브러리를 호출하고, 로그인한 사용자의 세션으로 요청을 보낼 수 있다. OWASP는 서드파티 코드가 사용자에게 주어진 권한과 정확히 같은 권한으로 실행된다고 정리한다.
- **변경 통제 상실** — 공급자 서버의 파일이 바뀌면 다음 페이지 로드부터 바뀐 코드가 실행된다. 공급자 쪽 코드가 그대로 유지된다는 보장은 보통 없다.
- **검토 부재** — 호출하는 쪽이 공급자 코드를 검토하는 경우는 드물다. 처음 넣을 때 검토했더라도 위 이유로 지금 실행되는 코드와 같다는 보장이 없다.
- **정보 노출** — 브라우저가 공급자 서버에 직접 요청하므로 일반 HTTP 헤더, referrer와 그 공급자가 이전에 심어 둔 쿠키가 공급자에게 간다.

## 사례: 성능 측정 스크립트로 거래 세션을 쓴 침해

2026-10-29 예측 시장 Polymarket은 polymarket.com에 로드하던 서드파티 공급자의 스크립트가 침해됐다고 공지했다. 다음 날 사후 보고는 그것이 성능 모니터링 스크립트였고, 공격자가 그 스크립트를 Polymarket 사용자를 노린 코드로 바꿨고, 짧은 시간 동안 사이트를 열어 둔 일부 사용자의 활성 세션으로 포지션을 팔고 지갑에서 자금을 옮겼다고 설명했다.

| 항목 | 사후 보고의 내용 |
| --- | --- |
| 즉시 대응 | 침해된 스크립트 제거와 모든 캐시 삭제, 추가 유출을 막기 위한 거래와 relayer 중단, 모든 활성 로그인 세션 초기화 |
| 장애 시간 | 상태 페이지 기록 37분(17:38~18:15 UTC, Major outage 표시는 18:06까지) |
| 보상 | 유출된 지갑 환급과 강제 매도 포지션의 가치 보전(슬리피지 포함), 중단 중 손실 보전. 합계 3.9백만 달러(2.7백만 달러와 중단 관련 1.2백만 달러) |
| 재발 방지 계획 | 서드파티 스크립트를 무결성 통제와 지속 검증을 더해 재배포. 예시로 더 강한 CSP, 명시적인 버전 고정, 샌드박싱을 들었다 |

사후 보고는 공급자 이름, 영향받은 사용자 수와 지갑 유형, 거래 승인 요청이 화면에 떴는지를 밝히지 않았다. 언론과 보안 업체가 보도한 공급자 이름과 피해 지갑 수는 사후 보고에 없어 이 문서에 사실로 쓰지 않는다.

이 사례에서 일반화할 교훈은 공급자를 믿을 수 있느냐보다 그 코드가 무엇에 닿을 수 있느냐다. 속도를 재는 스크립트가 돈을 옮기는 코드와 같은 페이지, 같은 세션에서 실행되면 공급자 한 곳의 침해가 곧 거래 권한의 침해가 된다.

## 사례: 공급자 계정 경로로 여러 고객의 설정 코드를 바꾼 침해

2026-11-16 A/B 테스트 서비스 Optimizely Web의 여러 고객 프로젝트에서 Project JavaScript에 외부 스크립트를 부르는 로더가 들어갔다. Project JavaScript는 고객이 프로젝트 설정에서 작성하고 스니펫 코드보다 먼저 실행되는 사용자 정의 코드다(Optimizely 문서). 아래 표는 2026-11-17 StepSecurity 분석(같은 날 여러 차례 수정) 기준이다. 규모와 iOS 단계는 그 분석이 인용한 Scott Helme(Report URI)의 조사이며, Helme의 원 글과 Optimizely의 공식 공지는 대조하지 못했다.

| 항목 | 분석 기준 내용 |
| --- | --- |
| 주입 위치 | 모든 페이지에서 실행되는 Project JavaScript 필드. 스니펫의 나머지는 그대로였고 파일은 공급자 CDN에서 공급자 인증서로 제공됐다. CDN 캐시 오염이 아니라 CDN이 받은 내용을 그대로 전달한 경우다 |
| 규모 | 확인한 스니펫 1,611개 중 188개, 178개 조직. 찾아낸 스니펫만 확인한 수치다 |
| 노출 시간 | 첫 주입 04:21 UTC, 일괄 정리 20:40~21:10 UTC, 모든 파일 정리 확인 23:11 UTC. 대부분 사이트에서 약 16시간 |
| 페이로드 | 결제 문맥의 암호화폐 주소 바꿔치기, 바꿔치기 뒤 화면 캡처와 `document.cookie` 전송, 결제 폼의 카드 정보 수집. iOS 기기에는 2단계 스크립트를 붙였고 Helme는 이를 알려진 iOS 공격 키트(Coruna, DarkSword)와 연결했다. 분석 업체는 그 파일을 분석하지 않았고, 공개 스캔은 공격 페이지가 제공된 사실만 보여 준다 |
| 공급자 대응 | 취약한 경로 차단과 수정, 주입 코드 제거, 세션 종료와 토큰 폐기, 영향 고객 통지. 원인을 계정 가입 흐름으로 설명했지만 그것이 서로 무관한 고객 프로젝트의 쓰기 권한으로 이어진 방식은 분석 시점까지 밝혀지지 않았다 |

이 사례에서 통제별로 드러난 점은 다음과 같다.

- **자체 도메인 제공도 피하지 못했다.** 스니펫을 자기 도메인에서 내려 주던 사이트도 같은 프로젝트 내용을 받아 와 영향을 받았다. 공급자 설정을 그대로 받아 오는 자체 호스팅은 공급자 쪽 변경을 그대로 옮긴다(해석).
- **SRI를 걸 고정 파일이 없다.** Optimizely 문서는 스니펫을 SDK 갱신 때만 바뀌는 정적 부분과, 실험 설정, 변형, 사용자 정의 코드처럼 자주 바뀌는 동적 부분으로 나눈다. 해시 비교로는 정적 부분만 검증할 수 있고 동적 부분은 내부 거버넌스로 다룬다고 적는다. 이번 주입은 동적 쪽인 사용자 정의 코드에서 일어났다(해석).
- **CSP는 지시어에 따라 갈렸다.** `script-src` 호스트 허용 목록은 외부 로더 다운로드를, `connect-src` 허용 목록은 수집한 데이터의 전송을 막는다. `strict-dynamic`과 nonce 정책은 신뢰한 스크립트가 추가한 스크립트도 신뢰하므로 이 로더를 막지 못한다. 도메인이 막히면 페이로드 전체를 인라인으로 담아 `eval`로 실행하는 변형도 있었으므로 로더 차단만으로 끝났다고 보지 않고 전송 단계까지 막는다(해석).
- **교차 출처로 뺀 입력은 남았다.** 카드 수집 코드는 교차 출처 결제 iframe 안을 읽지 못했고, `document.cookie`로는 HttpOnly 쿠키를 읽지 못한다. 결제 제공자가 호스팅하는 입력 필드를 교차 출처 iframe으로 쓰면 이 단계의 피해가 준다.
- **자기 저장소를 보는 통제는 닿지 않는다.** 코드 리뷰와 저장소 스캔은 공급자가 호스팅하는 설정 코드를 보지 못한다. 동의 배너는 스크립트를 언제 실행할지 정할 뿐 무엇을 실행할지는 정하지 않는다.

## 사례: 브라우저 밖, 게임 런처가 받는 CDN 스크립트를 바꾼 침해

실행 시점에 원격 코드를 받는 구조는 웹 페이지가 아닌 데스크톱 앱에도 있다. 게임 승리의 여신: 니케의 Windows PC 런처 사고(2026-11-04 X로 1차 공지, 2026-11-05 사과와 상세 공지)에서는 런처가 내려받는 공식 CDN 스크립트가 2026-09-27에 변조됐고, 공지 기준 2026-10-30 03:52부터 런처를 켠 PC에 악성 프로그램이 배포됐다. 변조된 파일은 다른 회사가 아니라 운영사 자신의 CDN에 있었으므로 엄밀한 서드파티 침해는 아니다. 앞 사례들과 공유하는 교훈은 실행 시점에 받아 오는 코드가 바뀌면 받는 쪽의 권한으로 실행된다는 점이다. 아래는 운영사 레벨 인피니트의 사고 공지와 수동 점검 안내를 전한 Inven 보도(점검 안내는 전문 인용, 시각은 기자 요약이며 시간대 표기는 없다)를 2026-11-24 대조한 내용이다.

| 항목 | 보도가 전한 공지 내용 |
| --- | --- |
| 시작점 | 일부 게임 서비스에 쓰이던 도메인 `insightjs.com`이 9월 27일 10:59 제3자에게 탈취됐다. Inven 보도에는 탈취 방식이 없다. BleepingComputer가 전한 연구자 분석은 변조된 파일이 이 도메인에서 다음 단계 코드를 받아 오게 했다고 적는다(공지로는 미확인) |
| 변조 | 같은 날 15:41~15:42에 런처가 내려받는 공식 CDN 스크립트 파일 4개가 변조됐다 |
| 배포 | 10월 30일 03:52부터 변조된 스크립트를 통해 이용자 PC에 악성 프로그램이 배포됐다 |
| 대응 | 11월 4일 0시경 이상 확인, 02:23까지 3개 파일 교체, 같은 날 12:09 나머지 1개 파일의 CDN 캐시 갱신. 11월 5일 08:00부터 공식 PC 클라이언트 실행 때 악성 프로그램을 자동 탐지하고 삭제한다. BleepingComputer가 인용한 공식 X 게시물은 1차 조치를 11월 4일 약 02:30(UTC+9)으로 적는다 |
| 범위 | PC 런처에서 일어났고 모바일 버전은 영향을 받지 않았다. 점검 대상은 9월 27일 15:41 이후 Windows PC 런처를 한 번이라도 실행한 사용자다 |
| 사용자 조치 | 감염되지 않은 다른 기기나 점검을 마친 PC에서 그 PC에서 쓴 계정의 비밀번호를 바꾸고, 그 PC에서 쓰거나 저장한 API 키와 액세스 토큰은 폐기하고 새로 발급한다. 백신 전체 검사와 Microsoft Defender 오프라인 검사도 안내했다 |
| 재발 방지 계획 | 보안 모니터링 강화, 런처 외부 리소스 무결성 검증 체계 구축, 런처 기능별 최소 권한 적용을 진행할 계획이라고 밝혔다 |

수동 점검 안내는 네트워크를 끊고 게임, 런처와 Chrome을 닫은 뒤 런처 로그에서 지표 문자열(`k2f_chan registered`)을 찾게 한다. 정리는 사용자 레지스트리 `HKEY_CURRENT_USER\Software\Classes\CLSID` 아래 특정 CLSID 키를 지우고 재부팅한 다음, Chrome 사용자 데이터 폴더 아래 DLL이 든 64자리 16진수 이름의 하위 폴더만 지우고(상위 폴더 전체가 아니다), 런처 로그 폴더에 로그 이름으로 남은 비정상 다운로드 파일(크기로 식별)과 런처 로컬 캐시 폴더도 지우는 순서다. 세부 경로는 공지의 안내를 따른다. BleepingComputer가 전한 연구자 권고는 갱신된 런처가 감염 흔적을 지울 수 있으니 다시 실행하기 전에 런처 로그와 캐시 폴더를 백업하라는 것이어서, 조사가 필요하면 정리 전에 증거부터 보존한다(운영 제안). 런처를 지워도 런처 밖에 심은 흔적은 남는다는 뜻이다(해석). 공지는 문자열이 없어도 위험을 완전히 배제할 수 없다고 적는다.

이 사례가 웹 사례에 더하는 점은 다음과 같다.

- **스크립트의 권한이 브라우저 샌드박스가 아니라 앱의 권한이다.** 웹 페이지의 스크립트는 그 출처의 세션에 닿지만, 업데이트를 내려받고 실행하는 런처 안의 스크립트는 그 기능을 통해 PC에 실행 코드를 내려받아 심을 수 있다. 공지가 안내한 흔적은 모두 사용자 계정 범위(사용자 레지스트리와 사용자 데이터 폴더)에 있었다. 앱이 원격 스크립트에 노출하는 기능이 곧 피해 범위다(해석). 운영사가 계획한 최소 권한 적용도 이 범위를 줄이는 조치다.
- **브라우저 엔진 밖에서 받는 스크립트는 무결성 검증을 앱이 맡는다(해석).** 내장 브라우저 엔진(CEF, Electron, WebView2 등)이 앱에 번들된 로컬 HTML 문서의 `integrity` 속성을 처리하는 구성이면 SRI와 CSP를 그 엔진에 맡길 수 있다. 호스트 문서를 원격에서 받으면 그 문서의 해시와 정책도 같은 경로의 침해로 함께 바뀔 수 있다. 앱의 네이티브 다운로드 기능으로 받아 실행하는 코드에는 엔진의 SRI와 CSP가 닿지 않으므로, 서명이나 해시 검증을 앱이 구현하지 않는 한 그런 검사가 없다. BleepingComputer가 전한 연구자 분석도 페이로드가 런처의 네이티브 기능으로 받아져 실행됐다고 적는다. 니케 런처가 어느 구성이었는지는 확인한 자료에 없다. 운영사의 외부 리소스 무결성 검증 계획이 이 공백에 해당한다.
- **점검 대상은 공지가 밝힌 배포 시작 시각이 아니라 변조 시각부터 잡는다.** 공지는 악성 프로그램 배포를 10월 30일부터로 적으면서도 점검 대상은 변조가 일어난 9월 27일 15:41 이후 실행자로 정했다. 배포 시각 추정이 바뀌어도 대상에서 빠지는 사용자가 없게 하는 범위 설정이다(해석).
- **개인 PC의 침해가 업무 자격 증명으로 이어진다.** 공지가 비밀번호뿐 아니라 API 키와 액세스 토큰 재발급을 안내한 것은 그 PC에 저장된 모든 자격 증명을 유출된 것으로 보라는 뜻으로 읽는다(해석). 회사 키를 같은 PC에서 쓴 적이 있으면 회사 쪽에서도 교체한다(운영 제안, [[Supply-Chain-Security#대응 플레이북 (사고 발생 시)|공급망 사고 대응]]).

## 공급자를 침해하지 않아도 되는 경로: 만료, 주소 변경, 오타

공급자 서버를 뚫지 않고도 그 주소의 주인이 되면 같은 결과가 난다. 2012년 Alexa 상위 1만 개 사이트를 크롤링한 연구(약 330만 페이지, 원격 스크립트 포함 8,439,799건)는 이런 취약점 유형을 네 가지 보고했다. 아래 표는 그중 주소의 주인이 바뀌는 세 가지이고, 나머지 하나인 `localhost`와 사설 IP 포함은 표 아래에서 다룬다.

| 경로 | 생기는 방식 | 연구에서 확인한 규모 |
| --- | --- | --- |
| 만료된 도메인(stale domain-name-based inclusion) | 스크립트를 제공하던 도메인이 갱신되지 않고 만료됐는데 포함하는 사이트가 `<script src>`를 그대로 둔다. 포함하는 쪽이 오류를 정기적으로 점검하지 않으면 제공 사이트가 응답을 멈춘 것을 알아채지 못한다 | 등록 가능한 상태였던 도메인 56개가 상위 1만 사이트 중 47곳에 포함돼 있었다. 그중 6개는 오타 도메인이었다. 연구진이 두 도메인을 직접 등록해 15일 동안 요청을 기록했다 |
| IP 주소 직접 지정(stale IP-address-based inclusion) | 도메인 대신 IP로 스크립트를 부르는데 그 IP가 바뀌거나 반납된다. 같은 IP를 할당받은 쪽이 응답을 제공한다 | IP 지정 페이지 299개를 석 달 뒤 다시 보니 IP 주소 39개(논문 표기 13.04%)가 그대로 남은 채 스크립트를 주지 않았고, 그중 35개는 연결 시간 초과였다. 그 IP를 얻는 일은 도메인 등록보다 확실히 어렵다고 연구는 한정한다 |
| 오타 도메인(Typosquatting Cross-site Scripting) | 개발자가 스크립트 URL을 잘못 적는다. 오타 도메인을 등록한 쪽이 그 페이지의 모든 방문자에게 코드를 준다 | 연구진이 오타 도메인 하나를 등록하자 15일 동안 고유 방문자 163,188명이 들어왔다 |

연구는 만료 도메인 경로를 저장형 XSS와 같은 효과로 본다. 취약한 페이지가 이미 스크립트 태그를 들고 있어서 공격자는 피해자와 상호작용하거나 특정 페이지로 유인할 필요 없이 도메인만 등록하면 된다. 같은 연구는 공급자의 유지 관리 수준을 평가하는 지표에 도메인 등록 만료 여부와 IP가 사설 대역인지를 넣었다. 둘 다 공격자가 도메인 등록이나 IP 확보로 제공자를 사칭할 수 있게 하기 때문이다.

이 경로에서 통제의 효과는 다음과 같이 갈린다. 연구는 로컬 사본, 샌드박싱과 CSP를 다뤘고, 그 밖의 정리는 이 문서의 다른 통제를 경로에 맞춰 본 것이다. 연구는 거친(coarse-grained) 샌드박싱이 스크립트 프로필에 이미 허용된 접근을 공격자가 그대로 쓸 수 있어 충분하지 않다고 결론 낸다.

- **CSP 허용 목록은 경로마다 다르다.** 연구는 URL에 오타가 있을 때 같은 오타를 담지 않은 CSP 정책이 그 URL의 로드를 막는다고 적는다. 만료 도메인은 호스트 이름이 그대로라 새 주인이 보낸 코드도 허용 출처에서 온 코드가 되므로, 호스트 허용 목록 정책은 막지 못한다.
- **SRI는 파일 내용이 달라지면 막는다.** 해시를 고정한 태그는 새 등록자가 다른 파일을 주면 로드를 거부한다. 버전 없는 URL이라 SRI를 쓰지 않았다면 효과가 없다.
- **로컬 사본은 외부 주소 의존을 없앤다.** 연구는 로컬 사본이 원격 사이트의 보안과 포함하는 사이트의 보안을 분리한다고 본다. 갱신을 직접 해야 하는 비용이 따른다.
- **로컬 사본으로 옮기지 못하면 목록과 만료를 감시한다.** 페이지가 실제로 부르는 외부 호스트를 정기적으로 수집해 서드파티 스크립트 목록과 맞추고, 응답하지 않거나 등록이 만료된 호스트는 태그에서 지운다. 자기 회사가 소유한 스크립트 도메인과 예비(fallback) 도메인도 갱신 일정을 관리한다. 등록을 놓친 도메인은 다른 사람이 등록할 수 있다.
- **IP 직접 지정과 개발 환경 주소를 배포 코드에 남기지 않는다.** 같은 연구는 `localhost`나 사설 IP에서 스크립트를 부르는 태그도 발견했다. 다중 사용자 환경이나 같은 네트워크의 다른 사용자가 그 주소를 차지하면 코드를 주입할 수 있다.

## 통제별로 막는 것과 못 막는 것

| 통제 | 막는 것 | 못 막는 것 |
| --- | --- | --- |
| CSP `script-src`, `connect-src` | 허용하지 않은 출처의 스크립트 로드와 연결 | 허용한 출처에서 온 바뀐 코드의 실행, 허용한 출처로 보내는 요청의 내용 |
| SRI(`integrity` 속성) | 검토한 파일과 해시가 다른 파일의 실행. 불일치하면 브라우저가 로드를 거부하고 네트워크 오류를 낸다 | 공급자가 파일을 정상 갱신할 때의 기능 중단, 처음부터 악성인 파일 |
| 버전 고정과 자체 호스팅(미러링) | 공급자 서버의 파일 교체가 곧바로 반영되는 것 | 고정한 버전 자체의 결함, 페이지 안에서 실행되는 동안의 권한, 공급자 설정을 받아 와 그대로 내려 주는 구성 |
| 샌드박스 `iframe` | 호스트 페이지 DOM과 쿠키에 대한 직접 접근 | iframe 안 자체 기능의 악용, 잘못 연 sandbox 토큰 |
| 서버 측 수집 | 해당 수집을 브라우저 밖으로 빼 페이지 코드 수를 줄임 | 여전히 페이지에서 실행되는 다른 스크립트 |
| 데이터 레이어 | 공급자에게 넘길 값을 정하는 약속 | 페이지에서 실행되는 스크립트의 권한 제한. 데이터 레이어는 샌드박스가 아니다 |

- **CSP 허용 목록은 행위 단위가 아니다.** 연결을 허용한 출처라는 사실은 그 출처로 가는 모든 요청이 안전하다는 뜻이 아니다. 공급자 출처 자체가 침해되면 허용 목록은 공격을 통과시킨다. nonce, `strict-dynamic`과 지시어별 설정은 [[Security-Headers|보안 헤더]]와 [[NextJS-Content-Security-Policy|Next.js CSP와 nonce]]를 따른다.
- **SRI는 교차 출처 요청에 CORS가 필요하다.** `<script>`에 `crossorigin`을 붙이고 공급자가 CORS를 허용해야 하며, 교차 출처 `no-cors` 요청에서는 SRI가 항상 실패한다. 해시 접두사는 `sha256`, `sha384`, `sha512`를 쓴다. 공급자가 같은 URL의 파일을 갱신하면 안전하지만 동작하지 않는 상태가 될 수 있으므로 버전이 붙은 URL이나 자체 호스팅과 함께 쓴다.

```html
<script
  src="https://cdn.example.com/rum/v4.2.1/rum.min.js"
  integrity="sha384-<검토한 파일의 base64 해시>"
  crossorigin="anonymous"></script>
```

- **sandbox 토큰 조합을 확인한다.** 빈 `sandbox`는 모든 제한을 적용하고 토큰을 더할 때마다 제한이 풀린다. `allow-same-origin`이 없으면 내부 문서는 항상 동일 출처 정책에 실패하는 특수 출처로 다뤄진다. 내장 문서가 호스트 페이지와 같은 출처일 때 `allow-scripts`와 `allow-same-origin`을 함께 주면 내부 코드가 `sandbox` 속성을 제거할 수 있어 샌드박스가 없는 것과 같아진다.

## 설계 체크리스트

- 결제, 송금, 거래 승인, 인증 화면처럼 세션으로 돈이나 권한을 움직이는 페이지에는 측정과 마케팅 스크립트를 싣지 않거나, 싣는다면 샌드박스 iframe이나 별도 출처로 분리한다. 측정 범위가 약간 줄어드는 비용과 공급자 침해의 피해 범위를 비교한다.
- 서드파티 스크립트 목록에 공급자, 목적, 로드하는 페이지, 버전 고정 여부, SRI 적용 여부와 담당자를 둔다. 목적이 끝난 스크립트는 제거한다.
- 버전 없는 최신 URL은 공급자가 갱신할 때마다 해시가 어긋나 SRI를 유지하기 어렵다는 점을 기록하고 대신 쓸 통제(자체 호스팅, 격리)를 정한다.
- 사고 대응 절차에 스크립트 제거, 캐시 삭제(CDN과 서비스 워커 포함), 민감 기능의 일시 중단, 활성 세션 일괄 초기화를 넣는다. 위 사례의 사후 보고도 스크립트 제거와 캐시 삭제, 거래 중단, 세션 초기화를 조치로 들었다.
- CSP 위반 보고와 실제 로드되는 스크립트 해시의 변화를 모니터링해 공급자 파일 교체를 감지한다.
- 공급자 관리 화면의 사용자, API 토큰과 모든 페이지에서 실행되는 설정 코드 필드를 서드파티 목록에 함께 올려 정기적으로 검토한다. 공급자 쪽 설정 변경은 자기 저장소의 리뷰를 거치지 않는다.
- 공급자 침해가 알려지면 지표 문자열 하나만 검색하지 않고 설정 코드 전체를 점검하며, 첫 주입 시각부터 프록시와 DNS 로그, CSP 위반 보고를 본다. 노출 시간에 결제 폼에 입력된 카드는 유출된 것으로 다룬다. 위 Optimizely 사례의 분석도 같은 조치를 권했다.

## 면접 체크포인트

- 성능 측정 스크립트가 거래를 실행할 수 있는 이유와 브라우저의 실제 권한 경계
- CSP 허용 목록, SRI, 버전 고정, 샌드박스가 각각 막는 단계의 차이
- SRI와 공급자의 무버전 URL 갱신이 충돌하는 지점
- 만료된 스크립트 도메인을 재등록한 공격을 CSP가 막지 못하는 이유와 SRI, 외부 호스트 목록 감시의 역할
- `allow-scripts`와 `allow-same-origin` 조합의 위험
- 서드파티 침해 사고에서 세션 초기화와 캐시 삭제가 필요한 이유
- 공급자 설정 코드에 주입된 공격을 자체 도메인 제공과 SRI가 막지 못한 이유, `strict-dynamic`이 로더를 신뢰한 이유
- 데스크톱 런처가 받는 원격 스크립트의 침해가 사용자 계정 권한 범위의 PC 장악으로 커지는 이유와 앱이 직접 갖춰야 할 무결성 검증, 최소 권한
