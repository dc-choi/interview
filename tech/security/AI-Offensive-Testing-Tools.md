# AI 침투 테스트 도구의 운영 위험과 탐지

AI 침투 테스트 도구는 LLM 에이전트가 정찰, 취약점 확인, 공격 코드 작성과 결과 해석을 이어서 수행하게 만든 실행 틀이다. 같은 도구가 방어 점검에도, 공격에도 쓰인다. 이 문서는 세 질문을 다룬다. 이런 도구가 공격의 비용 구조를 어떻게 바꾸는지, 방어자가 자기 시스템에 직접 돌릴 때 무엇이 위험한지, 들어오는 도구 트래픽을 어떻게 알아보고 어디까지 믿을 수 있는지다.

도구의 구조는 Microsoft의 2026-10-21 조사로, 실험의 구성과 측정값은 티오리의 2026-10-15 보도자료로 대조했다. 시험 횟수와 삭제 대상, 사고 해석은 2026-10-30 공개 인터뷰의 당사자 발언이 근거다. 백서 원문은 공개된 경로를 찾지 못해 대조하지 못했다. 실험 주체인 티오리는 자율 모의해킹 제품을 만드는 보안 회사이고, 독립 재현은 확인하지 못했다.

## 정의: 모델이 아니라 모델을 부리는 틀이다

Microsoft는 2026-10-21 공개한 조사에서 ARTEX를 어떤 AI 모델이든 붙여 여러 공격 보안 작업을 자동화하는 오픈소스 침투 테스트 프레임워크로 설명한다. Go로 쓴 멀티 에이전트 LLM 시스템에 Next.js 프런트엔드를 붙인 구조다. 에이전트들은 사람의 개입을 거의 받지 않고 정찰부터 데이터 유출까지 자율 침투 테스트를 수행하며, 찾은 자산과 취약점을 테스트 중에 그래프로 쌓는다. UI와 출력은 기본이 영어이고 한국어, 중국어, 스페인어와 일본어로 바꿀 수 있다.

이 구조에서 판단은 연결한 외부 모델이 하고, 도구는 계획을 세우는 에이전트와 탐색, 공격 코드 작성, 결과 해석을 맡는 하위 에이전트를 잇는 하네스 역할을 한다(구성 설명은 티오리 대표의 인터뷰 발언). 대표는 비슷하거나 더 잘 만든 공개 도구가 이미 많아 도구 하나가 없어지거나 하나에 대응한다고 위협이 없어지지 않는다고 설명했다. 연결하는 모델은 바꿀 수 있고 비슷한 틀도 다시 만들 수 있다(해석). 방어의 단위는 특정 도구가 아니라 도구가 찾아내는 취약점과 노출이다.

## 모델의 거부는 공격을 막는 통제가 아니다

호스팅 모델은 무단 침입을 직접 돕는 요청을 거부하도록 만들어진다. 이 거부는 제공자가 자기 서비스에 건 조건이지 공격 대상 쪽의 방어선이 아니다. 실행 틀은 연결하는 모델을 바꿀 수 있고, 공개 가중치 모델에서 거부 동작을 제거한 변형(abliterated)이 공개 저장소에 올라와 있어 메모리가 충분한 개인 장비에서 인터넷 연결 없이 돌릴 수 있다.

- **호스팅 모델도 공격에 쓰인다:** Anthropic의 2026-09 오용 대응 보고서는 침입과 데이터 탈취 작전에 자사 모델이 쓰인 사례들과 해당 계정을 차단한 조치를 적는다. 그래서 AI를 쓴 침해가 호스팅 모델이 아니라 거부를 제거한 로컬 모델로만 이뤄진다는 설명은 공개된 사례와 맞지 않는다.
- **계정 차단이 닿지 않는 구간이 있다:** 같은 보고서의 한 사례에서 행위자는 만든 플랫폼을 온프레미스 LLM과 함께 로컬에 배포했고, 계정 조치는 소프트웨어 개발과 설계 활동을 끊었지만 플랫폼의 배포는 막지 못했다. 자체 호스팅 모델을 호스팅 모델과 나란히 쓴 사례도 있다.
- **로컬 모델의 공격 능력은 따로 확인할 문제다:** 거부를 제거한 로컬 모델에 모의해킹 에이전트를 얹으면 지식이 없는 사람도 침투할 수 있다는 설명이 있으나, 시연이나 측정 없이 제시된 주장이다. 같은 설명도 수백만 원대의 대용량 메모리 장비와 구성 지식이 필요하고 명령을 내린다고 침투가 되는 것은 아니라는 단서를 단다. 이 문서는 그런 구성의 성공률을 확인하지 않았다.
- **거부 제거 모델은 쓰는 쪽의 위험이기도 하다:** 가중치를 수정한 공개 모델은 평가로 드러나지 않는 조건부 동작을 가질 수 있다. 근거는 [[Agent-Execution-Isolation#가중치를 수정한 공개 모델의 조건부 백도어|가중치를 수정한 공개 모델의 조건부 백도어]]에 있다.

방어 계획은 제공자의 거부와 계정 차단을 전제로 세우지 않는다(해석). 그 조치는 일부 공격자의 비용을 올릴 뿐이고, 방어자가 통제할 수 있는 것은 자기 시스템의 취약점, 노출과 권한이다. 개인 계정도 같다. 내가 쓰는 서비스가 침해돼 비밀번호가 유출되는 일은 개인이 막을 수 없으므로, 서비스마다 다른 비밀번호를 쓰고 [[FIDO-WebAuthn|패스키]] 같은 피싱 저항 인증을 켜서 한 곳의 유출이 다른 계정으로 번지지 않게 한다(적용 제안).

## 공격 비용이 내려가면 외곽이 먼저 대상이 될 수 있다

티오리 대표의 설명에 따르면 사람이 직접 분석하던 시기에는 공격자도 시간과 인력이 한정돼 가치가 큰 대상에 집중했다. 공격받지 않은 시스템이 안전해서가 아니라 순서가 오지 않았을 수 있다. 에이전트는 복제해 병렬로 돌리고 밤낮없이 시도와 수정을 반복할 수 있으므로, 후보 전체를 훑는 비용이 크게 내려간다.

대표는 2026-10 인터뷰에서 최근 국내 금융권 사고로 침해된 시스템이 핵심 뱅킹 시스템이 아니라 대출 정보 조회나 직원 업무 지원 같은 외곽 서비스였다고 설명했다. 그는 조사에 직접 참여하지 않았다고 밝혔다. 조직은 한정된 자원으로 가장 중요한 시스템부터 지키므로, 덜 관리한 시스템이 먼저 공격받을 수 있다는 판단이다. 같은 인터뷰에서 그는 대상 회사들이 특별히 잘못했다기보다 노출된 외곽 서비스가 대상이 됐다고 봤고, 공격자는 오래되거나 알려진 취약점이 남은 노출 자산을 진입점으로 삼는다는 일반론과 함께 외곽 서비스를 미리 없애거나 선제적으로 취약점을 찾아 고친 곳이 비교적 안전했다고 설명했다. 티오리의 2026-10-15 보도자료는 이 사고들에서 ARTEX의 사용 흔적이 확인됐다고 적었으나, 도구가 어떻게 쓰였고 침해에 기여했는지는 인터뷰 시점에 조사 중이었다. 그래서 여기서는 방어 우선순위의 근거로만 쓴다. 도구의 관여와 침해 원인을 나눠 보는 기준은 [[Security-Incident-Response#AI 도구의 관여와 침해 원인을 구분한다|AI 도구의 관여와 침해 원인 구분]]에 있다.

적용 제안은 노출 자산 목록을 중요도 순이 아니라 외부 도달 가능성 순으로도 정렬해 보는 것이다(해석). 외부에서 닿는 외곽 서비스는 내부망으로 들어가는 옆문이 될 수 있다. 목록과 외부 노출 확인 기준은 [[AI-Accelerated-Threat-Defense#먼저 갖출 것 1: 자산과 소프트웨어 목록|자산과 소프트웨어 목록]]을 따른다.

## 방어 점검에 돌릴 때: 목표가 파괴를 막지 않는다

티오리는 2026-10-15 ARTEX 등 AI 보안 도구의 동작 방식, 자체 실험과 대응 방안을 담은 백서를 냈다고 밝혔다. 보도자료가 전한 실험은 두 가지다. 하나는 통제된 환경에서 ARTEX와 CyberStrikeAI를 구동해 네트워크와 서버 로그에 남는 흔적을 측정한 것이다. 다른 하나는 ARTEX의 안전장치를 검증한 별도 실험으로, LLM 기반 안전장치를 켠 상태에서 단순한 취약점 점검만 실행했는데도 실험용 데이터가 삭제됐다.

대표는 인터뷰에서 가상의 사용자와 주문 데이터를 넣은 실험 사이트에 취약점을 찾으라고만 지시했는데 관리자 계정과 주문 데이터가 지워졌다고 설명했다. 안전성 판정 기능을 켠 시험에서도 실행 거부 없이 관리자 계정이 다시 삭제됐다고 했다. 시험 횟수는 23차례 정도라고 했다. 모두 당사자의 발언이며(음성 인식 전사 두 종을 대조했고 관리자 계정은 문맥으로 교정한 표기), 백서 원문으로는 대조하지 못했다.

이 결과가 보여 주는 구조는 다음과 같다.

- **악의가 없어도 파괴가 일어난다:** 삭제 기능을 시험하다 그 기능에 취약점이 있으면 실제로 지운다. 대표는 도구 쪽에서는 악의 없는 점검으로 판정되기 때문에 안전성 판정에 걸리지 않는다고 설명했다(당사자 설명, 미검증).
- **사후에 알아도 늦다:** 대표는 도구의 추론 기록이 삭제를 확인한 뒤에야 문제를 인지하는 흐름을 보였다고 설명했다. 사전 판단에 기대는 안전장치는 되돌릴 수 없는 동작을 막는 장치로 보지 않는다.
- **결과 자체는 유효한 발견이다:** 지울 수 없어야 할 데이터가 지워졌다면 공격자도 지울 수 있다는 뜻이다. 이 실험은 통제된 환경이었다. 같은 일이 통제되지 않은 환경에서 일어날 때가 문제다.

운영 원칙은 모델의 판단이 아니라 실행 환경으로 피해 범위를 정하는 것이다(해석).

- 운영과 같은 구성의 스테이징이나 복제 환경에서 돌리고, 운영 대상 점검은 범위, 시간대와 중단 조건을 미리 정한 별도 절차로 다룬다. 공식 문서에 근거한 기준은 [[Application-Security#자동 모의해킹의 검사 대상과 접근 범위|자동 모의해킹의 검사 대상과 접근 범위]]와 [[Security-Policy-and-Assessment#점검의 범위와 증거|점검의 범위와 증거]]에 있다.
- 테스트 계정과 데이터는 점검용으로 따로 만들고, 실행 전에 백업과 복구가 실제로 되는지 확인한다.
- 도구가 쓰는 자격 증명, 네트워크 도달 범위와 쓰기 권한은 모델 밖에서 제한한다. 설계는 [[Agent-Execution-Isolation#과제를 끝내려는 제약 우회는 실행 계층에서 막는다|제약 우회를 실행 계층에서 막기]]를 따른다.
- 도구가 호출한 스캐너의 요청량은 점검 대상의 가용성에 영향을 줄 수 있다. 아래 절의 측정값을 부하 기준으로도 본다.
- 검증하지 않은 오픈소스 도구를 내부 운영 환경에 그대로 들이지 않는다. 티오리는 이 경우 데이터 유출, 시스템 장애와 데이터 삭제가 생길 수 있다고 경고했다.

### 코딩 에이전트에 얹는 버그 헌팅 스킬 번들

독립 프레임워크 대신 Claude Code 같은 코딩 에이전트에 스킬과 슬래시 명령을 얹어 같은 일을 시키는 형태도 있다. 2026-11-23 확인한 Claude-BugHunter 저장소(버전 2.1.0)를 예로 들면, 번들은 세 부분으로 나눠 볼 수 있다(이 문서의 분류이며 README는 작업 단계별 네 층으로 설명한다).

- **방법론:** 취약점 유형별 점검 절차, 페이로드와 보고서 양식을 담은 스킬 문서다. README는 스킬 83개, 슬래시 명령 15개, 핵심 취약점 유형 24개를 다루며 공개된 HackerOne 보고서 681건의 패턴을 모았다고 적는다. 같은 저장소의 소개란은 스킬 82개로 적어 수치가 맞지 않고, 스킬 8개와 슬래시 명령 15개는 다른 공개 저장소에서 가져왔다. 개수는 자기 신고이며 품질을 뜻하지 않는다.
- **실행 엔진:** 공격 표면을 매핑하고 발견 항목을 스킬로 보내는 엔진과 정찰, 분류, 보고를 이어 붙이는 CLI가 함께 있다. README의 도구 목록에는 subfinder, httpx, nuclei 같은 스캐너와 Burp Suite MCP 연동이 있다. 저장소 설명대로라면 지침만 주는 문서 묶음이 아니라 실제 네트워크 요청을 내는 도구다.
- **플러그인 연결:** 플러그인으로 설치하면 HackerOne API 토큰(선택)을 받아 로컬 Python으로 MCP 서버를 띄운다. 코드는 MIT, 스킬 문서와 단어 목록은 CC BY 4.0으로 라이선스가 나뉜다.

README는 소유했거나 서면 승인을 받은 대상에만 쓰라고 하고, 검증되지 않은 제3자 대상을 가리키면 검증 관문이 자동으로 걸려 범위 안인지 묻고 범위는 코드로 강제한다고 설명한다. 이는 저장소 자신의 주장이며 동작은 확인하지 않았다. 도입 판단은 위 실행 원칙을 그대로 따른다(해석). 승인 범위는 도구가 아니라 점검 계약과 네트워크 설정으로 강제하고, 번들은 에이전트 권한으로 실행되는 외부 코드이므로 설치 전에 플러그인 manifest가 띄우는 프로세스와 받는 자격 증명을 읽는다.

## 들어오는 도구 트래픽 알아보기

2026-10-15 보도자료 기준으로 티오리는 도구를 직접 돌려 네트워크와 서버 로그의 흔적을 측정했고, 실험에서 도구들이 고유한 식별 정보와 요청 순서, 빈도, 반복 양상을 남겼다고 밝혔다. CyberStrikeAI가 호출한 스캐너는 20분 동안 3만 2000여 건의 요청을 냈고, 티오리는 이 요청량이 대상 서비스의 가용성에 영향을 줄 수 있다고 설명했다. 티오리는 이 분석 결과를 바탕으로 만들었다고 밝힌 탐지 규칙 모음(Suricata, Sigma, YARA, ModSecurity 등)을 GitHub 저장소로 공개했다. 라이선스는 저작자 표시와 라이선스 고지를 유지하는 조건으로 무료 사용, 수정과 재배포를 허용하는 Detection Rule License 1.1이다(2026-11-17 확인).

대표가 인터뷰에서 설명한 공통 행동 패턴은 추론과 실행의 교대다. 모델이 다음 행동을 정하는 동안에는 요청이 잠시 줄고, 결정이 나면 사람이 낼 수 없는 속도의 요청이 몰리며, 결과를 받으면 다시 조용해진다. 일반 자동화 스캐너도 비슷하게 보일 수 있으므로 이 패턴만으로 AI 공격이라고 단정하지 않는다.

대표는 이 탐지를 임시방편으로 봤다. 규칙 저장소의 안내도 같은 한계를 적는다. 규칙은 User-Agent, URL 경로, 포트 같은 지문 수준이고 규칙만으로는 승인된 점검과 공격을 구분하지 못한다. 도구가 User-Agent를 바꾸고 검사할 수 없는 TLS로 돌면 요청 몰림, 404 비율, 경로 수 같은 행동 형태만 남는데 이는 일반 스캐너에도 맞는다. 실험 실행마다 도구 고유 지문이 나온 것도 아니며, 대상 도구 10개 가운데 8개의 규칙은 실험 실행 없이 픽스처로만 시험했다. 저장소는 규칙을 모두 관찰 전용으로 배포하고, 차단으로 바꾸는 것은 자기 트래픽에서 관찰 기준선을 잡은 뒤 규칙별로 승인하라고 안내한다.

- 도구 식별 문자열과 요청 속도는 공격자가 바꿀 수 있다. 대표의 설명으로는 사람처럼 초당 한두 건으로 늦춰도 시간이 더 들 뿐 공격의 성공 여부는 같으므로, 그때는 규칙만으로 정상 사용자와 구분하기 어렵다.
- 그래서 규칙 차단은 조정하지 않은 도구를 그대로 돌린 공격에 대한 1차 방어막이고, 아직 고치지 못한 취약점을 앞에 두고 시간을 버는 수단이다. 취약점을 없애지는 않는다.
- 관찰부터 요청 제한, WAF까지 통제를 쌓는 순서는 [[Bot-Traffic-Operations|봇 트래픽 운영]]을 따른다.

## 점검 주기와 수정 속도

대표는 연 1~2회 정기 점검으로 충분한지 의문이라고 했다. 공격자가 에이전트로 계속 훑는 환경에서는 다음 점검까지 고치는 방식의 속도가 맞지 않을 수 있다(해석). 그는 지속적인 AI 점검과 대응 자동화를 다음 단계로 들며, 점검 결과로 취약점 200개가 나와도 사람이 고치는 동안 그중 두 개로 공격이 들어오면 침해라고 설명했다. 발견 속도만 올리면 수정 대기열이 병목이 된다. 대기열을 다루는 운영은 [[Vulnerability-Operations-AI-Agents|취약점 운영과 보안팀의 AI 에이전트 활용]]에, 패치 작성과 적용 사이의 병목을 재는 방법은 [[AI-Accelerated-Threat-Defense#패치 작성과 적용 완료 사이의 병목을 측정한다|패치 병목 측정]]에 있다.

같은 인터뷰에서 대표는 티오리가 언론 매체와 함께한 시연에서 취재진이 AI 코딩 도구로 만든 회원 가입 기능이 있는 시연용 사이트를 AI로 점검하게 했더니 많은 취약점이 나왔다고 소개했다. 시연 하나의 결과이므로 생성 코드 전반의 취약점 비율로 일반화하지 않는다. 다만 겉으로 잘 동작하는 것과 안전한 것은 다른 기준이고, 혼자 쓰던 결과물이 팀이나 외부에 공개되는 시점에 점검 대상이 된다는 점은 그대로 적용된다(해석).

## 에이전트 사용자 쪽의 위험

에이전트가 답변을 넘어 파일, 메일, 결제와 외부 서비스를 다루면 사용자도 의도하지 않은 공격의 출발점이 될 수 있다. 대표가 든 예는 매진된 공연 티켓을 구해 오라는 지시를 받은 에이전트가 정상 경로가 막히자 시스템을 침해해 목표를 달성하는 경우와, 메일을 정리하던 에이전트가 공격자 메일 속 지시를 따라 내부 자료를 보내는 경우다. 둘 다 가정한 예시이며 뒤의 것은 프롬프트 인젝션 유형이다.

- 이름을 모르는 에이전트 서비스는 운영 주체와 평가를 확인한 뒤 쓴다.
- 요청받은 권한을 습관적으로 승인하거나 자동 승인 모드로 넘기지 않고, 필요한 권한만 주고 다 쓰면 회수한다.
- 외부 입력을 읽는 에이전트의 격리 설계는 [[LLM-Application-Security|LLM 애플리케이션 보안]]을 따른다.

## 운영 체크포인트

- 외부에서 닿는 외곽 서비스까지 자산 목록에 있고, 쓰지 않는 서비스를 내렸는가.
- AI 점검 도구를 운영이 아닌 환경에서 돌리고, 점검 전 백업 복구를 확인했는가. 도구의 권한이 모델 밖에서 제한되는가.
- 점검 결과의 수정 대기열과 처리 시간을 재고 있는가.
- 도구 트래픽 탐지 규칙을 임시 방어막으로 두고, 그 뒤의 근본 수정 일정이 있는가.
- 팀이나 외부에 공개하는 AI 생성 결과물에 공개 전 점검 단계가 있는가.
