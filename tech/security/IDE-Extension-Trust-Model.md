# IDE 확장 신뢰 모델과 AI 코딩 도구의 공격 표면

IDE 확장과 AI 코딩 에이전트는 편집기 안의 편의 기능이 아니라 사용자 권한으로 파일, 네트워크와 프로세스를 다루는 실행 주체다. 그래서 확장 하나의 신뢰는 그 개발자 노트북에 있는 SSH 키, 클라우드 자격 증명과 레지스트리 토큰 전체의 신뢰로 이어진다. 이 문서는 VS Code를 기준으로 확장이 가진 권한, 편집기와 마켓플레이스가 제공하는 통제, 그리고 그 통제가 막지 못하는 범위를 정리한다. Cursor 마켓플레이스 변조 확장 사례와 사고 대응은 [[Supply-Chain-Security|공급망 보안]]에서 다룬다.

## 확장은 편집기와 같은 권한으로 돈다

VS Code 공식 문서는 extension host가 VS Code 자체와 같은 권한을 가진다고 설명한다. 확장은 로컬 파일을 읽고 쓰고, 네트워크 요청을 보내고, 외부 프로세스를 실행하고, 워크스페이스 설정을 바꿀 수 있다. 문서는 로컬에서 실행되는 확장을 위한 샌드박스를 설명하지 않는다(2026-11-15 확인). 따라서 다음 가정은 성립하지 않는다.

- 공식 마켓플레이스에 있으니 편집기 안에 갇혀 있다.
- 기능을 쓰지 않았으니 코드가 실행되지 않았다.
- 서명이 있으니 내용이 안전하다. 서명은 게시 이후 변조되지 않았음을 보이지만, 게시자가 올린 코드의 의도까지 보증하지 않는다.

AI 코딩 도구는 여기에 자율 실행을 더한다. 자동완성은 제안을 사람이 수락했지만, 에이전트는 파일을 직접 고치고 셸 명령을 실행하며 MCP 서버로 외부 도구를 호출한다. 권한 범위가 같아도 에이전트가 목표에 맞춰 명령을 고르므로, 공격자가 탐색 로직을 미리 짜 둘 필요가 줄어들 수 있다(해석). 에이전트 쪽 권한 경계는 [[Agent-Execution-Isolation|에이전트 실행 격리]]에서 다룬다.

## 매니페스트와 설정에서 위험이 커지는 지점

| 항목 | 공식 동작 | 위험이 커지는 경우 |
| --- | --- | --- |
| `activationEvents`의 `*` | VS Code가 시작될 때마다 확장을 활성화한다. 공식 문서는 다른 조합으로 안 될 때만 쓰라고 권하고, 시작을 늦추지 않는 대안으로 `onStartupFinished`를 둔다 | 사용자가 기능을 쓰지 않아도 편집기를 여는 것만으로 코드가 돈다 |
| `capabilities.untrustedWorkspaces.supported` | `true`는 Restricted Mode에서도 모든 기능을 켜고, `false`는 신뢰 전까지 확장을 끄며, `'limited'`는 일부 기능만 켠다. 아무것도 선언하지 않은 확장은 지원하지 않는 것으로 보고 Restricted Mode에서 끈다. `main` 진입점이 없는 테마와 문법 확장은 Workspace Trust가 필요 없어 예외다 | 확장이 스스로 `true`를 선언하면 낯선 저장소를 열어도 그 확장은 그대로 동작한다. 선언은 확장 작성자의 주장이다 |
| Workspace Trust | 신뢰하지 않은 워크스페이스는 Restricted Mode로 열린다. `restrictedConfigurations`로 지정한 설정은 워크스페이스 값 대신 사용자 값만 쓴다 | 신뢰 프롬프트를 끄거나 습관적으로 신뢰하면 저장소에 들어 있는 설정이 변조 경로가 된다 |
| 자동 업데이트 | VS Code는 확장 업데이트를 확인해 자동으로 설치한다. `extensions.autoUpdateDelay`는 게시 뒤 설치까지의 대기 시간(시간 단위, 기본 12시간)이며 자동 업데이트가 켜져 있을 때만 적용된다. VSIX로 설치한 확장은 자동 업데이트가 기본으로 꺼져 있다 | 한 번 신뢰한 확장의 새 버전이 검토 없이 들어온다. 계정 탈취나 배포 경로 침해가 정상 업데이트로 전달된다 |

설정 하나보다 여러 설정이 겹칠 때 공격이 쉬워진다. 시작 시 활성화, 신뢰 없는 워크스페이스 지원 선언, 검토 없는 자동 업데이트와 에이전트의 셸 전체 허용이 함께 있으면, 사용자가 아무 행동을 하지 않아도 새 버전의 코드가 편집기 시작과 함께 실행되고 프롬프트 인젝션 한 번이 확인 없는 명령 실행으로 이어진다.

## 편집기와 마켓플레이스가 제공하는 통제

VS Code 공식 문서(2026-11-15 확인)가 설명하는 보호 장치와 그 한계다.

- **게시자 신뢰 대화상자**: VS Code 1.97부터 서드파티 게시자의 확장을 처음 설치하면 게시자를 신뢰할지 묻는다. 확장 팩이나 의존성이 있는 확장의 게시자를 신뢰하면 의존 확장의 게시자도 신뢰한다. 이미 설치되어 있던 확장의 게시자는 자동으로 신뢰되며, 명령줄로 설치하면 게시자를 자동으로 신뢰하지 않는다.
- **설치 허용 목록**: `extensions.allowed` 애플리케이션 설정(VS Code 1.96부터)을 두면 허용 규칙에 맞지 않는 확장은 설치가 막힌다. 설정하지 않으면 모든 확장을 허용한다. 게시자나 확장 ID를 `true`로 허용하면 버전을 제한하지 않으므로 오염된 새 버전도 허용 범위에 든다. `"dbaeumer.vscode-eslint": ["3.0.0"]`처럼 버전 배열로 고정하면 목록 밖 버전은 막히고, 이미 설치된 확장이나 버전이 차단 대상이 되면 VS Code가 비활성화한다. 버전 범위는 지원하지 않아 버전마다 나열해야 한다. 조직 정책 `AllowedExtensions`는 사용자 설정보다 우선한다. 로컬 VSIX는 패키지 안에 선언된 식별자로 판정하므로 출처를 검증하지 않는다.
- **마켓플레이스 검사**: 새 확장과 업데이트마다 여러 백신 엔진으로 검사하고, 통과 전에는 공개하지 않는다. 격리 VM에서 런타임 동작도 확인하며, 게시 시 서명하고 설치 때 서명을 검증한다. 공식 게시자와 인기 확장의 이름 선점을 막고, API 키나 PAT 같은 비밀 값이 든 확장의 게시를 막는다.
- **검증된 게시자**: 파란 체크 표시는 게시자가 도메인 소유를 증명했고 마켓플레이스에서 최소 6개월 이상 문제없이 활동했다는 뜻이다. 코드 내용의 검토를 뜻하지 않는다.
- **차단 목록**: 악성으로 확인되거나 취약한 의존성이 있는 확장은 마켓플레이스에서 내려가 차단 목록에 오르고, 이미 설치된 VS Code에서는 자동으로 제거된다. 제거는 확장 파일에 대한 조치이며 그 확장이 남긴 영속성 흔적이나 유출된 자격 증명을 되돌리지 않는다.

이 보호는 Microsoft의 Visual Studio Marketplace와 VS Code를 기준으로 한 설명이다. 다른 레지스트리를 쓰는 VS Code 계열 편집기는 각 레지스트리의 정책을 따로 확인해야 하며, 같은 확장 ID라도 배포 채널이 다르면 다른 산출물일 수 있다.

## 공격 표면 네 갈래

| 경로 | 들어오는 방식 | 사례와 비고 |
| --- | --- | --- |
| 확장 마켓플레이스 | 이름과 아이콘이 비슷한 확장, 처음부터 악의적인 확장, 게시자 계정 탈취 뒤의 업데이트 | 특정 마켓플레이스의 변조 확장 사례는 [[Supply-Chain-Security#IDE 확장은 로드 시점의 실행 경로다\|공급망 보안]] |
| npm 등 패키지 | 에이전트 CLI와 프로젝트 의존성의 `postinstall` | Nx 악성 버전(아래) |
| MCP 서버 | 에이전트가 호출하는 도구가 패키지로 배포되는 경우가 많다. 도구 설명과 반환값이 에이전트의 입력이 된다 | `postmark-mcp`(아래) |
| 업데이트 채널 | 한 번 신뢰한 배포 경로가 침해되면 정상 도구가 정상 업데이트로 악성 코드를 받는다 | 위 세 경로 모두 자동 업데이트로 전달될 수 있다 |

네 경로는 서로 이어진다. 2025-08-26 Nx 사고에서 악성 버전은 `postinstall` 스크립트로 파일 시스템을 훑어 경로와 자격 증명을 모았고, 수집물을 피해자 GitHub 계정에 만든, 이름에 `s1ngularity-repository`가 들어간 저장소에 올렸으며, `.zshrc`와 `.bashrc`에 `sudo shutdown -h 0`을 넣었다. 공식 advisory는 VS Code용 Nx Console 18.6.30부터 18.65.1까지가 버전 확인을 위해 `nx@latest`를 설치했기 때문에, 악성 버전이 `latest`였던 시간에는 편집기를 여는 것만으로 악성 코드가 실행될 수 있었다고 적는다. Nx Console 18.66.0에서 이 확인이 제거되었고 JetBrains 확장은 해당하지 않는다. 확장의 정상 기능이 패키지 공급망을 끌어들인 경우다. 같은 advisory의 부록에는 파일 탐색 에이전트에게 설정 파일과 환경 정의 파일의 경로 목록을 만들게 하는 프롬프트가 실려 있다. 이 프롬프트를 어떤 도구가 어떤 옵션으로 실행했는지는 advisory 본문에서 확인하지 못했다.

`postmark-mcp`는 Postmark와 무관한 제3자가 npm에 올린 MCP 서버 패키지다. Postmark의 2025-09 공지는 이 패키지가 15개 버전 동안 신뢰를 쌓은 뒤 1.0.16에서 보내는 메일의 숨은 참조 사본을 외부 서버로 보내는 백도어를 넣었다고 설명한다. 공식 이름처럼 보이는 MCP 서버도 게시자를 확인해야 하며, 메일 발송 도구처럼 업무 데이터를 직접 다루는 서버는 유출 범위가 그 데이터 전체가 된다.

## 개발자 노트북이 노려지는 이유

개발자 노트북은 목적지가 아니라 입구다. `~/.ssh`의 개인 키, `~/.aws/credentials` 같은 클라우드 자격 증명, `~/.npmrc`의 레지스트리 토큰, 셸 프로필과 `.env`의 환경 변수, Git 자격 증명 헬퍼와 브라우저 세션이 한곳에 있다. 같은 사용자 권한으로 도는 프로세스는 이 값을 읽을 수 있는 경우가 많고(OS 키체인에 둔 값은 별도 보호를 받을 수 있다) 에이전트 도구도 환경 변수를 상속한다. 레지스트리 게시 토큰을 빼앗기면 그 개발자의 패키지가 다음 피해자를 만드는 배포 경로가 된다.

피해 범위는 자격 증명의 수명과 권한 범위가 정한다. 장기 SSH 키와 넓은 클라우드 키는 횡적 이동으로 번지고, 만료가 짧은 토큰은 피해 기간이 좁다. 또 컴파일러, 패키지 매니저와 빌드 도구는 원래 많은 파일을 만들고 외부 코드를 받아 실행하므로, 오탐을 줄이려고 엔드포인트 보안 제품에서 개발 디렉터리와 개발 프로세스를 예외로 두는 경우가 있다(빈도는 확인하지 않음). 그런 환경에서는 그 위에서 도는 확장이 자격 증명 파일을 읽고 외부로 요청을 보내도 평소의 개발 활동과 구분하기 어렵다.

## 의도된 데이터 전송과 침해의 구분

AI 코딩 도구는 정상 기능으로도 프롬프트와 함께 작업 맥락(열린 파일, 터미널 출력, 이전 대화 등)을 모델 서버에 보낼 수 있다. 정확한 전송 항목과 보관 기간은 도구, 요금제와 설정마다 다르므로 각 벤더 문서로 확인한다. 이 전송과 공급망 침해는 확인 방법과 대응이 다르다.

| 기준 | 의도된 수집 | 침해 |
| --- | --- | --- |
| 공개성 | 문서, 약관과 설정 화면에 항목이 있고 끄는 옵션이 있는 경우가 많다 | 문서에 없는 방식으로 설치 직후나 숨겨진 경로로 보낸다 |
| 목적지 | 벤더의 공식 도메인 | 낯선 호스트, 사용자 계정에 만든 저장소 등 |
| 범위 | 작업에 필요한 파일과 출력 | SSH 키 디렉터리, 브라우저 저장소처럼 기능과 무관한 경로 |
| 대응 | 설정 조정, 보관과 학습 정책, 계약 조건 검토 | 격리, 자격 증명 폐기, 로그 조사 |

의도된 수집도 데이터 분류 정책에 맞는지는 따로 판단한다. 엔터프라이즈 요금제의 보관과 학습 제외 정책은 서버 쪽 데이터 처리를 다루며, 로컬에서 확장이 악성으로 동작하는 위험은 다루지 않는다. 터미널 출력에 찍혀 대화에 들어간 비밀 값은 전송되었다고 보고 폐기한다.

## 보도를 읽는 기준

출처의 층을 나눈다. 최초 게시글, 그것을 재인용한 보도, 커뮤니티 반응, 벤더 공지는 증거의 수가 다르다. 같은 주장이 여러 곳에서 반복되어도 출처가 하나면 증거는 하나다. 커뮤니티 점수는 주목도이지 정확도가 아니다. 판단을 바꾸는 신호는 재현 가능한 분석(샘플 해시와 절차), 벤더의 영향 범위와 대상 버전 공지, 도메인과 파일 해시 같은 침해 지표(IOC), 독립된 두 곳 이상의 교차 확인이다.

진위가 확인되기 전에는 금지와 무시 사이에서 가정 위반 시나리오를 준비한다. 이 확장이 악성이라면 어떤 자격 증명이 노출되는지, 얼마나 빨리 폐기할 수 있는지, 로그에서 무엇을 찾을지를 미리 적어 두면 보도가 오보로 밝혀져도 다음 사고에 그대로 쓸 수 있다.

## 방어 계층과 적용 순서

아래 순서와 비용 판단은 운영 제안이다.

| 계층 | 효과 | 한계 |
| --- | --- | --- |
| 비밀 분리 | 장기 SSH 키와 토큰을 에이전트가 도는 환경에서 빼서 침해 시 피해 반경을 줄인다. 도입 비용이 낮은 편이다 | 작업에 꼭 필요한 자격 증명은 남는다 |
| 권한 최소화 | devcontainer나 별도 OS 계정으로 홈 디렉터리와 환경 변수를 가린다 | 작업 흐름이 바뀌어 도입 비용이 있다 |
| 확장 허용 목록 | `extensions.allowed`에 게시자나 확장 ID를 허용 | 버전을 고정하지 않으면 승인된 확장의 오염된 새 버전도 들어온다 |
| 버전 고정 | `extensions.allowed`의 버전 배열 | 버전마다 나열해야 해서 갱신 부담이 크고, 고정한 버전 자체가 악성이면 막지 못한다 |
| 업데이트 지연 | `extensions.autoUpdateDelay` | 지연 시간 안에 탐지되지 않은 오염 버전은 시간이 지나면 들어온다. 수동 Update 버튼은 지연을 건너뛴다 |
| 네트워크 통제 | 프록시와 egress 허용 목록, 낯선 도메인으로의 주기적 연결 탐지 | 허용된 도메인을 악용한 전송은 남는다 |

비밀 분리와 권한 최소화를 먼저 하고 허용 목록과 네트워크 통제를 얹는 순서를 제안한다. 통제가 업무를 막으면 개발자가 승인되지 않은 장비와 계정으로 우회할 수 있고 그러면 오히려 가시성을 잃으므로, 통제를 넣기 전에 우회할 이유가 생기는지를 먼저 묻는다.

- **개인과 소규모 팀**: 자동 업데이트를 받는 확장 목록과 게시자 변경을 점검한다. 만료 없는 토큰을 범위가 좁은 단기 토큰으로 바꾼다. 에이전트 작업은 devcontainer나 별도 계정에서 돌린다. SSH 키를 용도별로 나누고 passphrase나 하드웨어 키를 쓴다. `.env`와 키 파일은 에이전트가 읽지 못하게 제외 규칙을 건다.
- **팀 리드**: 게시자, 매니페스트(`activationEvents`, `untrustedWorkspaces` 선언, 의존 확장), 업데이트 이력과 소스 공개 여부로 확장을 승인하고 허용 목록에 올린다. 개발 환경의 아웃바운드를 프록시로 모아 처음 보는 도메인에 알림을 건다. 토큰을 SSO에 묶어 수명을 줄인다. 의심 확장이 나왔을 때 누가 제거하고 어떤 키를 어떤 순서로 회수하며 어느 접근 로그를 볼지 플레이북으로 미리 정한다.

라이브러리 의존성 방어와 확장 방어는 출처와 버전 고정, 새 버전 지연, 실행 환경 권한 축소라는 공통 패턴을 가진다. 차이는 위치다. 라이브러리는 lockfile, 해시와 CI의 SCA로 관문을 만들 수 있지만([[Dependency-Release-Cooldown|의존성 릴리스 쿨다운]]), 확장은 개인 노트북에 직접 설치되고 자동 업데이트되므로 파이프라인보다 엔드포인트 관리의 문제에 가깝다.

## 체크포인트

- 확장의 권한은 편집기 권한과 같다고 보고, 서명과 검증 표시를 내용의 안전으로 읽지 않는다.
- `activationEvents`의 `*`, `untrustedWorkspaces` 선언과 자동 업데이트 설정을 함께 본다.
- 차단 목록에 의한 자동 제거는 확장의 제거일 뿐이다. 영속성 흔적과 유출된 자격 증명은 따로 처리한다.
- MCP 서버와 에이전트 CLI도 패키지 공급망의 일부로 게시자와 버전을 확인한다.
- 보도는 출처의 층과 IOC로 판단하고, 진위와 무관하게 자격 증명 폐기 절차를 준비한다.
