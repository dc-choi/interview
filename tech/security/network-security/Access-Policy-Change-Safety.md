# 접근 정책의 변경 안전성과 실효 검증

ZTNA, SASE, 방화벽과 웹 필터의 접근 정책은 저장하는 순간이 아니라 집행 지점이 읽는 순간 사용자의 업무를 바꾼다. 그래서 정책 변경은 코드 배포처럼 발행 전 검증과 발행 후 복구를 갖춰야 하고, 발행한 정책도 켜져 있다는 사실만으로 동작한다고 믿지 않고 로그와 대조해 계속 확인한다. 사용자와 기기를 요청마다 다시 검증하는 제로 트러스트의 태도를 정책 자체에 적용하는 셈이다.

아래 구조와 수치는 자체 개발한 ZTNA를 운영하는 한 조직의 2026-11 발표 기준이며, 다른 제품의 동작은 해당 제품 문서로 확인한다.

## 정책 한 줄은 세 곳에서 바뀐다

정책 한 줄은 대상(사용자 그룹), 목적지(도메인, IP, 경로를 담은 그룹)와 처리(허용이나 차단, 평가 순서)로 나눌 수 있다. 처리는 관리자가 설계하고 배포할 때 정하지만, 사용자 그룹은 LDAP이나 IdP의 계정 변동에, 목적지 그룹은 대상 서버의 교체와 서비스의 API 경로 변경에 따라 배포 뒤에도 계속 바뀐다. 정책을 한 줄씩 검토하면 문제없어 보여도 이 의존 관계를 엮어 보지 않으면 의도와 다르게 동작하는 정책을 찾지 못한다.

의도와 실제가 어긋나는 대표 유형은 넷이다.

| 유형 | 정책 화면에서 보이는 것 | 실제 동작 |
| --- | --- | --- |
| 앞 단계 예외가 뒤 단계를 덮음 | 업로드 경로 차단 정책이 활성 | TLS 복호화 예외에 `*.example.net` 같은 wildcard가 있으면 그 도메인은 복호화되지 않아 뒤의 HTTP와 DLP 정책이 판단하지 못하고 통과한다 |
| 목적지 표현이 단계마다 다르게 쓰임 | 서버 IP를 목적지 그룹에 넣어 차단 | 발표의 제품에서는 그룹 안의 IP 항목이 TLS 검사 단계에는 적용되지만 HTTP 정책에는 적용되지 않아, 도메인으로 들어온 요청이 막히지 않았다. 제품마다 다르므로 단계별 매칭 규칙을 확인한다 |
| 정책 밖의 변화 | 변경 기록이 없음 | 그룹에 의도하지 않은 사람이 들어가거나, 허용한 IP와 도메인이 다른 서버에 재사용되거나, 서비스가 `/export`를 `/exporting`으로 바꾸면 정책은 그대로인데 대상이 달라진다 |
| Hit count 0 | 쓰이지 않는 정책으로 보임 | 우선순위에 밀림, 목적지 표현 불일치, 복호화 예외, 정책 밖 변화, 실제로 요청이 없음 같은 여러 원인이 있다. 삭제 근거가 아니라 점검 신호다 |

정책 수가 많아지면 사람이 이 관계를 따라가기 어렵다. 발표의 환경은 정책 약 1,700개, 목적지 그룹 약 1,800개, 그룹 안의 도메인과 IP 약 16만 개였다. 발표는 상용 제품의 사전 정의 카테고리라면 포함된 도메인을 하나씩 조회해야 알 수 있어 추적이 더 어려울 수 있다고 본다.

## 발행 전: 큰 변화를 멈추고 의도를 실행해 본다

- **대상 급감 보류**: IdP 동기화 범위를 실수로 줄이면 정상 사용자가 정책 대상에서 빠진다. 마지막 발행본과 후보의 발행 대상 사용자 수(IdP 전체 계정 수와 다르다)를 비교해 감소율이 임계값을 넘으면 발행을 보류하고 기존 발행본을 유지한다. 1,000명에서 600명이면 40%라 30% 임계값을 넘는다. 운영자는 누가 왜 빠졌는지와 업무 영향을 확인해 원인이 불명확하면 보류를 유지하고, 실수면 반려하고 원본을 고치며, 계획된 변경이면 승인한다. 승인(진행해도 된다는 판단)과 발행 성공(이후 처리 결과)은 다른 기록이다. 이 보류는 정책 발행만 멈추며 IdP의 계정 비활성화를 되돌리지 않는다.
- **정책 평가 가드**: 저장한 정책이 의도대로 판정하는지는 실제로 평가해야 안다. 유지해야 할 업무 접근(누가, 어디에, 기대 결과)을 미리 등록하는 사전 정의 가드와, 바꾼 규칙의 대상과 조건에서 대표 요청을 자동으로 만들어 그 규칙이 실제 평가 흐름에서 효력을 내는지 보는 자동 파생 가드를 둔다. 새 허용 규칙이 앞쪽의 차단 규칙에 밀려 반대 결과가 나오면 후보 발행을 막는다.
- **집행과 같은 판정 코드**: 평가기는 집행 지점(발표에서는 VPN)이 쓰는 정책 판정 구현을 그대로 실행한다. 평가 전용 해석기를 따로 두면 두 구현 사이에 차이가 생길 수 있고, 같은 구현을 쓰면 그 차이를 줄인다. 판정을 전송 처리와 분리해 두어야 터널을 열거나 실제 요청을 보내지 않고 평가할 수 있다. 같은 평가기를 운영 중 특정 사용자가 왜 막혔는지 확인하는 수동 진단에도 쓴다.
- **결과 3분류**: 기대와 일치하면 진행, 확인된 불일치면 차단한다. 평가 오류나 시간 초과는 미확인이며, 다른 불일치가 없으면 경고를 남기고 진행해 평가기 장애가 모든 발행을 멈추지 않게 한다. 미확인을 검사 성공으로 세지 않고 운영자가 이어서 확인한다. 불일치가 나면 정책이 틀렸는지(규칙의 조건과 순서 수정) 기대값이 낡았는지(계획된 차단인데 기대가 허용으로 남음)를 변경 의도와 영향으로 가른다.

## 발행 후: 포인터를 되돌리고 변경 흐름은 보존한다

정책 본문을 버전별로 객체 저장소에 두고 집행 지점은 발행 head가 가리키는 본문을 읽게 하면, 복구는 정책을 다시 렌더링하지 않고 head를 마지막 정상 본문으로 옮기는 일이 된다. 복구를 시작하면 자동 발행을 멈추고 head를 고정한다. 그동안 운영자의 정책 변경은 계속 저장되지만 집행 지점은 읽지 않는다. 서비스 상태(복구한 정상 정책)와 현재 정책(장애 중 변경과 원인 수정이 쌓이는 흐름)을 분리했기 때문에 복구가 다른 운영자의 변경을 되감지 않는다. 원인을 고친 현재 정책을 검증한 뒤 운영자가 발행을 재개한다. 발표의 설명 예시에서는 복구도 새 버전 번호를 받고 그 버전이 과거 본문을 다시 가리킨다.

## 감사 로그: 연쇄 변화까지 남기고 유실을 다룬다

우선순위 기반 정책에서는 정책 A를 5번에서 7번으로 옮기면 B와 C의 순위도 한 칸씩 당겨지고, 먼저 선택되는 정책이 바뀌어 결과가 허용에서 차단으로 뒤집힐 수 있다. 감사 이벤트에는 행위자, 시각, 대상, 결과와 변경 전후 snapshot을 남기고, 함께 순위가 바뀐 다른 정책의 식별자와 전후 순위도 같은 이벤트에 담는다. 일반 원칙은 [[Audit-Log|감사 로그]]에 있다.

정책 변경과 감사 이벤트를 같은 DB transaction의 outbox에 쓰면 이 경로에서는 정책만 바뀌고 기록이 빠지는 경우를 막는다. 발표의 조직은 outbox를 거치지 않는 직접 전달 경로도 두고 그 실패는 지표와 로그로 따로 본다. 원장 적재는 commit 뒤 비동기라 같은 이벤트가 다시 올 수 있으므로 이벤트 ID로 멱등하게 적재한다. 전달 대기(pending)의 건수와 가장 오래 기다린 시간, 재시도 한도를 넘어 자동 재시도를 멈춘 실패(failed), 브로커 전달 완료와 원장 적재 완료를 각각 다른 상태로 본다. 패턴은 [[Transactional-Outbox|Transactional Outbox]]와 같다.

장애 문의가 오면 변경 이력에서 시작 시각과 대상을 좁히고, 그 변경이 언제 어떤 버전으로 발행됐는지 대조하고, 해당 사용자와 목적지로 수동 평가해 선택된 규칙을 확인한다. 놓친 업무 접근은 다음 가드의 기대값으로 넣는다.

## 발행 뒤의 지속 검증

1. **변경 후 기대 동작**: 추가, 수정, 켜고 끈 정책을 찾아 그 정책과 같은 도메인에 걸린 다른 정책의 기대 동작을 로그와 대조한다. 배포한 정책은 로그가 쌓인 뒤 실제로 맞는지 다시 본다.
2. **정책 밖 변화**: IdP 그룹은 구성원이 속한 다른 그룹과 견줘 이상치를 찾고, 내부 대상 서버는 자산 목록과 대조하며, 외부 서비스의 차단 경로(개인 계정 로그인, 세션 중계처럼 반출 위험이 있는 API)는 주기적으로 직접 요청해 여전히 막히는지 확인한다.
3. **Hit count 급변**: 변경 이력이 없는데 하루 hit count가 크게 늘거나 줄면 원인을 몰라도 잡는다. 사용자의 출발지나 경로 변경, 앱 업데이트로 켜진 인증서 pinning이나 IP 직접 접속처럼 1, 2번이 보지 않는 원인이 여기서 드러난다. 코드로 판별할 수 있게 된 원인은 1, 2번 점검에 추가한다.

같은 방식은 다른 장비에도 쓴다. 방화벽 정책과 웹 필터를 판정 순서대로 계산하면 위 정책에 가려 동작하지 않는 필터를 찾을 수 있고, 인터넷에 열린 클라우드 리소스는 WAF, 보안 그룹, LB 규칙으로 막혀 있어야 할 경로에 직접 요청해 본다. 시작에는 정책 읽기 권한과 로그만 있으면 된다. 복호화 예외에 덮인 DLP 정책 하나를 골라 설정상 기대 동작을 적고 로그와 맞춰 보는 정도로 출발할 수 있다.

### LLM에 맡기는 범위

이상 징후 중 코드가 아는 원인을 뺀 나머지의 원인 추정, 잘못된 정책의 변경안, 새 차단 요구의 정책안까지를 LLM에 맡기고, 수정 여부 판단과 배포는 담당자가 하며 LLM이 쓴 변경안도 배포 전에 코드로 다시 검사한다. 발표의 자체 보고로, 정책 목록만 주고 의도대로 동작하는지 물었을 때는 절반이 틀렸고 틀린 답 대부분이 동작하지 않는 통제를 동작한다고 답한 쪽이었다. 발표는 정책 목록만으로는 제품이 요청을 어떤 순서로 평가하는지 알 수 없으니 당연한 결과일 수 있다고 본다. 현재 설정과 코드가 찾은 이상 징후, 제품의 평가 방식(순서대로 보다가 처음 맞는 하나로 결정), 조직의 배포 규칙(이름 규칙, 우선순위, 알려진 edge case)을 함께 주자 같은 질문을 모두 맞혔다고 한다. 자막에서 표본 크기를 확인하지 못했으므로 정확도 수치로 일반화하지 않고, 안전을 과대 보고하는 방향의 오류가 위험하다는 점을 기억한다.

## 정책 조건과 연결 방식의 설계 선택

- **요청 내용까지 조건으로**: Method와 Path만 보면 GraphQL의 조회(`pullRequests`)와 생성(`createPullRequest`)이 모두 `POST /graphql`이다. 주소를 막으면 조회도 막히고 열면 생성까지 열린다. Body의 operation 필드나 값(로그인 email의 회사 도메인)까지 조건으로 쓰면 도구와 주소를 바꾸지 않고 작업 단위로 통제한다. 대가는 TLS 복호화와 본문 파싱이 필요하다는 점과, 위의 복호화 예외가 이 조건을 무력화할 수 있다는 점이다. TLS 검사의 대가는 [[Next-Generation-Firewall|NGFW]]에 있다.
- **원래 주소 유지**: DB 접근 제품 중에는 gateway의 별도 주소나 포트 번호로 접속하게 하는 방식이 있다. 사용자가 접속 방법을 새로 익혀야 하고 권한이 재할당되면 포트가 바뀔 수도 있으며, 공식 경로를 거치지 않는 직접 접속과 기존 DB 계정이 남아 있으면 gateway에서 권한을 회수해도 접속이 계속될 수 있다. 사용자가 원래 DB 주소를 그대로 쓰게 하면 관리하지 않던 DB로 가는 연결(shadow IT)도 발견할 수 있다는 것이 발표의 설계 목표이며, 발표 시점(2026-11)에는 개발 중이었다. 클라이언트가 어떤 방식으로 이 연결을 잡는지는 발표에서 확인하지 못했다.
- **신규 등록 도메인(NRD) 차단**: RDAP이나 WHOIS로 도메인 등록일을 조회해 최근 등록된 도메인 접근을 기본 차단하면 평판 데이터가 아직 없는 시간 창을 메운다. 2026-03 axios 공급망 공격에서 C2 도메인은 2026-03-30 16:03 UTC에 등록됐고 악성 axios 1.14.1은 2026-03-31 00:21 UTC에 게시돼, 그 사이가 약 8시간이었다. 업무상 새 도메인이 필요한 경우의 예외 절차를 함께 둔다. 설치 시점 방어는 [[Dependency-Release-Cooldown|의존성 릴리스 대기]]와 짝을 이루고, 사건 자체는 [[Supply-Chain-Security|공급망 보안]]에 있다.

## 직접 만든 접근 제품의 운영 비용

내부망 접근과 인터넷 보호를 한 클라이언트로 묶으면 권한 변경이 네트워크와 서비스 정책에 함께 반영되고, 접속 실패나 감사 때 여러 제품의 기록을 같은 접속 기준으로 맞출 필요가 줄어든다. 대신 보안 패치, OS와 다른 보안 프로그램과의 호환성, 장애 대응을 스스로 책임진다. 판단 틀은 [[Build-vs-Buy|직접 만들기와 사기]], 같은 조직의 내재화 동기는 [[Security-as-Enabler|가능하게 하는 보안]]에 있다. 발표가 든 운영 문제는 다음과 같다.

- **이동 뒤 재연결**: UDP 기반 VPN을 NLB 뒤에 두면 NLB는 출발지와 목적지 IP, 포트로 UDP flow를 유지해 같은 flow를 같은 target으로 보낸다. 2026-11-25 AWS 문서 기준 UDP flow의 idle timeout은 120초로 고정이며, 지나면 다음 패킷을 새 flow로 보고 다른 target에 보낼 수 있다. 엘리베이터에서 Wi-Fi가 끊겨 통신이 120초 넘게 멈추거나 이동으로 IP나 포트가 바뀌면 세션 정보가 없는 서버로 갈 수 있고, 그러면 연결이 돌아오지 않는다. NLB의 UDP 처리는 [[ELB]]에도 있다. 발표의 조직은 서버 목록을 받아 클라이언트가 health check로 접속 서버를 고르게 바꿨다. 서버 교체 시 새 연결을 막고 기존 연결을 마무리하는 drain은 여전히 ingress에 의존한다.
- **터널 안의 TCP**: 여러 연결의 데이터를 IP 패킷으로 다시 만들어 하나의 TCP 터널에 실으면 앞선 데이터가 지연될 때 뒤의 모든 흐름이 함께 기다린다. 커넥터 수를 늘려 부하를 나눈 뒤, 연결에서 읽은 애플리케이션 데이터를 그대로 전달하고 목적지와의 TCP/IP 처리는 커넥터 쪽 OS 커널에 맡기도록 바꿨다. 전송은 TCP 기반 다중화(yamux)와 QUIC 중 대상 인프라의 방화벽과 스위치 특성에 맞춰 고른다. 이 변경이 없앤 것은 TCP 안의 TCP다. yamux의 stream들은 아래의 TCP 연결 하나를 공유하므로 그 연결이 지연되면 stream끼리 여전히 서로 기다릴 수 있고, stream이 독립적인 QUIC은 이 대기를 피한다. 그 뒤에도 남은 병목은 커넥터별 응답 시간, 트래픽, 동시 stream 수로 물리 스위치, 회선 대역폭, 같은 자원을 쓰는 다른 워크로드의 간섭에서 찾았다.
- **DNS와 다른 보안 프로그램의 충돌**: macOS 개발 환경에서 약 10분 뒤 Redis에 연결하지 못하는 문제는 앱의 DNS 질의 방식(connected UDP socket)과 EDR의 패킷 재작성이 겹쳐 OS가 VPN 경로를 찾지 못하는 문제였고, DNS 서버를 바꾸면 잠시 회복돼 증상이 늦게 나타났다. 가상 DNS 서버 수를 늘려 증상 시점을 약 30분으로 늦춘 뒤, 공통 라이브러리가 일반 UDP 방식으로 질의하게 고쳤다. 원인 분석은 발표의 설명이며 OS 버그 여부는 확인하지 않았다.
- **송신 비용**: 클라우드에서 외부로 나가는 전송 비용이 월 약 24,000달러였고, 트래픽 지표로 클라우드 안에서 끝낼 통신을 정리하고 일부를 전용선(Direct Connect)으로 돌려 월 약 1만 달러를 줄였다고 한다. 발표 시점에는 정액 회선을 쓰는 데이터센터 전환을 준비 중이었다.

## 점검 질문

- 정책 발행 전에 집행 지점과 같은 판정 코드로 후보를 평가하는가. 평가 오류를 성공으로 세지 않는가.
- 복구가 정책 재생성 없이 저장된 정상 본문으로 head만 옮기는가. 복구 중 들어온 변경이 사라지지 않는가.
- 발행 대상 사용자 수가 크게 줄면 자동 발행이 멈추는가.
- 앞 단계의 복호화 예외가 뒤 단계의 HTTP, DLP 정책을 무력화하는 도메인을 계산해 본 적이 있는가.
- Hit count 0이나 급변을 삭제 근거가 아니라 점검 신호로 다루는가.
- 정책 밖에서 바뀌는 그룹 구성원, 자산, 외부 API 경로를 주기적으로 대조하는가.
