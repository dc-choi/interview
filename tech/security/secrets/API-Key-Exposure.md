# API 연동 키 노출과 최소 권한 스코프

외부 서비스 연동에 쓰는 API 키(연동키, 시크릿 키)는 그 자체가 자격증명이다. 노출되면 공격자가 시스템을 침입하지 않고도 정당한 요청으로 위장해 그 키의 권한 범위 전체에 접근한다. 침입 흔적이 없다는 사실이 안전을 뜻하지 않는다. 탈취한 키로 보낸 요청은 서버 입장에서 인증을 통과한 정상 요청이기 때문이다.

## 멘탈 모델 — 키의 권한 범위가 곧 공격 표면

키가 유출되는 순간 방어선은 그 키에 부여된 권한까지로 좁혀진다. 그래서 두 축이 피해 크기를 결정한다.

- 노출 여부: 키가 클라이언트, 저장소, 로그, URL처럼 공격자가 닿는 경계에 있는가.
- 권한 범위: 그 키로 무엇까지 할 수 있는가. 결제 요청용 키가 전체 결제내역 조회까지 가능하면, 노출 시 요청 권한만이 아니라 조회 권한까지 함께 넘어간다.

두 축은 곱으로 작동한다. 노출 확률을 0으로 만들 수는 없으므로, 권한 범위를 최소로 줄이는 것이 노출이 발생했을 때의 피해를 상수배 낮춘다.

## 노출 지점

- 클라이언트 노출: 서버 전용 시크릿 키를 프런트엔드 번들, 모바일 앱, HTML에 넣으면 사용자가 곧 열람자가 된다. 결제 연동은 보통 클라이언트에 노출해도 되는 키(결제창 호출용)와 서버에만 두는 키(승인, 조회용)를 나눈다. 이 구분을 어기고 서버 키를 클라이언트에 두면 노출된다.
- 버전 관리, 로그, URL: Git 히스토리 평문, 접근 로그의 쿼리스트링, 리퍼러 헤더로 새어 나간다. 저장과 주입 계층의 방어는 [[Secret-Management|시크릿 관리]]에서 다룬다.
- 서드파티 경계: 연동을 맡긴 외부 플랫폼이나 가맹점 쪽에서 키가 새면, 키 발급자 시스템은 멀쩡해도 그 키가 가리키는 데이터가 열린다.
- 사용자 키를 맡는 서비스(BYOK): 사용자가 공급자에게서 발급받은 키를 저장해 대신 쓰는 서비스가 뚫리면, 공격자는 그 키의 권한과 과금 노출을 그대로 얻고 비용은 키가 연결된 사용자 계정에 청구될 수 있다. 통제와 사고 후 조치는 아래 BYOK 절에서 다룬다.

## 로컬 에이전트의 파일 접근과 런타임 주입

2026-11-02 Git과 1Password 공식 문서 대조 기준이다. 도구에 저장해 둔 키와 도구가 실행 권한으로 읽을 수 있는 키를 나누어 점검한다(적용 제안).

- `.gitignore`는 Git이 추적하지 않는 파일을 무시하도록 정하는 규칙이다. 이미 추적 중인 파일에는 적용되지 않는다. 따라서 `.env`를 여기에 적었다는 사실을 에이전트의 파일 읽기 차단 근거로 쓰지 않고, 실제 실행 계정과 파일 접근 권한을 따로 확인한다(적용 제안).
- `op run`은 시크릿을 런타임 환경 변수로 자식 프로세스에 전달해 평문 하드코딩을 피하게 한다. 그러나 1Password는 같은 사용자로 실행한 다른 프로세스가 환경 변수에 접근할 수 있다고 가정하라고 안내한다. 환경 변수 주입만으로 에이전트와 시크릿을 격리했다고 판단하지 않는다.
- 시크릿이 필요한 애플리케이션에만 값을 주입하고 에이전트 실행 환경에는 운영 키를 넣지 않는 구성을 검토한다(적용 제안). 같은 사용자 권한으로 실행하는 프로세스 사이의 접근 가능성과 출력, 로그 노출까지 별도로 확인해야 한다. 저장과 주입 방식의 선택은 [[Secret-Management|시크릿 관리]]에서 다룬다.

## 최소 권한 스코프

- 용도별로 키를 분리하고 각 키에 필요한 스코프만 부여한다. 조회, 승인, 환불 권한을 한 키에 몰지 않는다. 권한 모델의 일반 원리는 [[Access-Control-Models|접근 제어 모델]]을 따른다.
- 키를 IP, 도메인, 호출 출처로 제한할 수 있으면 건다.
- 유효기간과 로테이션을 전제로 설계한다. 정적 장수 키는 유출 시 피해 기간이 길다. → [[Refresh-Token-Rotation|토큰 로테이션]]

## 정상 요청으로 위장한 유출은 탐지가 어렵다

피해는 데이터 조회에 그치지 않는다. 과금되는 API의 키가 노출되면 제3자의 호출로 키가 연결된 계정에 예상하지 못한 비용이 발생할 수 있다. Google Cloud의 API 키 관리 문서(2026-10-13 확인)는 이러한 비용과 무단 데이터 접근을 함께 경고하며, 키 사용 제한과 사용량 모니터링을 권고한다. 실제 과금 주체와 허용 작업은 공급자의 키 유형과 계약을 확인한다.

새 키 발급만으로 기존 키가 무효화됐다고 가정하지 않는다. 정기 교체에서는 새 키를 발급하고 애플리케이션을 전환한 뒤 이전 키를 삭제하는 단계가 필요하다. 이미 노출된 키는 아래 사고 대응 절차에 따라 폐기와 영향 확인을 진행한다.

탈취한 키로 보낸 요청은 인증을 통과한 정상 트래픽이라 인증 실패 로그로는 잡히지 않는다. 조회량 급증, 평소와 다른 출처, 대량 순회 같은 행위 기반 이상 탐지와 키별 rate limit이 필요하다. → [[Rate-Limiting|Rate limit]], [[Audit-Log|감사 로그]]

노출이 확인되면 침입 흔적 유무와 무관하게 키를 즉시 폐기하고 회전하며, 접속 기록 전수를 분석해 영향 범위와 정보주체를 특정한다.

## 사용자 키를 맡는 서비스(BYOK)의 통제와 사고 후 조치

키를 맡은 서비스가 거는 예산과 rate limit은 그 서비스를 거친 호출에만 적용된다. 새어 나간 키로 공급자에 직접 호출하면 이 통제가 닿지 않으므로, 한도와 탐지는 키를 발급한 공급자 쪽에도 둔다(적용 제안).

Anthropic의 API 키 관리 도움말(2026-11-02 확인)은 공급자 쪽 안전장치로 다음을 안내한다.

- 개발, 테스트, 운영 환경마다 다른 키를 쓰면 키가 노출됐을 때 그 용도만 빠르게 끄고 피해를 줄일 수 있다.
- custom rate limit 조직은 Billing 페이지의 지출 한도와 Rate limits 페이지의 워크스페이스 rate limit을 유출된 키나 잘못 동작하는 스크립트로 인한 예상 밖 사용량의 안전장치로 쓴다. standard rate limit 조직은 auto-reload 한도를 신중히 정하며, 이 한도도 유출된 키로 인한 과다 사용의 안전장치가 된다.
- Claude Console의 Logs와 Usage 페이지를 정기적으로 확인한다.
- 노출이 의심되면 키를 즉시 폐기한다. 공개 GitHub 저장소에서 Claude API 키가 감지되면 GitHub secret scanning 파트너 프로그램을 거쳐 Anthropic이 키를 자동으로 비활성화하고 사용자에게 메일로 알린다.

키를 맡는 서비스와 맡기는 사용자에게 옮기면 다음과 같다(적용 제안).

- 외부 서비스에 맡기는 키는 그 서비스 전용으로 발급해, 사고 때 그 키만 폐기하면 되게 한다.
- 지출 한도를 걸 때는 그 한도가 알림만 보내는지 호출을 막는지 공급자 문서에서 확인한다. 한도 초과가 호출 오류로 오는 방식은 [[LLM-Failure-Handling-Classification|LLM 실패 분류]]에서 다룬다.
- 키별 사용량과 비용에 기준선을 두고 급증, 평소 쓰지 않던 고가 모델 호출, 낯선 시간대 사용을 알린다(운영 제안).
- 위의 자동 비활성화는 공개 GitHub 저장소에 올라간 키를 대상으로 한다. 서비스의 키 보관 DB(저장 계층)에서 유출된 키는 이 경로 밖이다. 공급자가 노출된 것으로 본 키를 차단하기도 하지만(아래 사례, 보도 기준) 대상과 시점은 공급자가 정하므로, 공지를 받으면 사용자가 직접 폐기한다. 키를 맡은 서비스는 유출 범위의 키 목록을 공급자에 알려 차단을 요청한다.
- 공급자가 범위를 줄인 키, 위임이나 단기 자격증명을 지원하면 원본 장수 키 대신 그것을 맡긴다. 임시 자격증명은 [[Hardcoded-Credentials|하드코딩된 자격증명]]에서 다룬다.
- 레거시 시스템을 폐기할 때는 저장된 키 사본부터 지우고, 폐기가 끝날 때까지 운영 시스템 수준의 접근 통제와 감시를 유지한다(운영 제안).

사고 공지를 받은 사용자는 다음 순서로 조치한다(적용 제안).

1. 키를 발급한 공급자 콘솔에서 해당 키를 폐기하고 새로 발급한다. 맡긴 서비스에서 키를 지우거나 바꾼 것으로 공급자가 발급한 이전 키가 무효화됐다고 가정하지 않는다.
2. 같은 키를 쓰던 다른 연동도 새 키로 옮긴다.
3. 노출 추정 시점부터 공급자의 사용량, 로그와 청구 내역을 확인하고, 본인이 만들지 않은 사용은 공급자에 문의한다.
4. 서비스가 조치 완료를 알리기 전에는 새 키를 다시 맡기지 않고, 다시 맡길 때는 그 서비스 전용 키로 발급한다.

## 사례 — 결제 연동키 노출로 결제내역 조회

한 결제대행사(토스페이먼츠)에서 특정 가맹점이 쓰던 결제연동 플랫폼의 연동키가 노출돼, 제3자가 그 키로 해당 가맹점의 결제내역 4131건(정보주체 2671명, 구매자 성명과 마스킹된 카드번호, 승인번호 등 영수증 수준 항목)을 조회했다. 결제대행사 시스템 자체에 대한 침입은 확인되지 않았고, 노출된 정보로 추가 결제나 취소는 불가능했다. 핵심은 자격증명 노출과 그 키로 조회까지 가능했던 권한 범위이며, 침입이 없었다는 점이 조회 유출을 막지는 못했다.

## 사례 — 코딩 에이전트 서비스에 저장된 AI 공급자 키 노출

코딩 에이전트 OpenCode는 2026-10-17 18:08 UTC(한국 시각 10-18 03:08) 공식 X 계정에서, 시간대를 밝히지 않은 전날 밤(last night)에 보안 침해가 있었고 OpenCode Console 사용자의 1.4%가 영향을 받았으며, 영향받은 사용자는 외부 공급자를 연결한 사용자 중 일부라고 공지했다. 해당 사용자에게는 메일로 알렸고 메일을 받지 않았다면 영향이 없다고 했으며, Anthropic, OpenAI, Google과 함께 대응 중이라고 밝혔다. 2026-11-02 문서 기준 Console은 OpenCode 팀이 검증한 모델을 크레딧과 API 키로 쓰게 하는 서비스로, 팀 워크스페이스의 소유자와 관리자는 예산을 정하고 자체 공급자를 연결할 수 있다. 이는 현재 문서가 설명하는 구성이며 침해된 시스템의 구조를 뜻하지 않는다. OpenCode는 이 침해를 대규모 증류 공격과 관련된 것으로 설명했다. 증류는 한 모델의 출력으로 다른 모델을 학습시키는 방법이다([[Task-Specific-Small-Models|작은 특화 모델]]). 공지는 사고가 진행 중이라 세부 내용을 공유할 수 없다고 했고, 2026-11-02까지 확인한 OpenCode의 공개 공지에는 침입 경로, 키 저장 방식, 증류 공격과 키 노출의 관계에 대한 설명이 없다. 아래 보도된 안내 메일도 침입 경로와 증류 공격과의 관계는 밝히지 않았다.

보도 기준으로는 사용자에게 간 안내 메일이 폐기 절차 중인 레거시 시스템에 대한 무단 접근과 워크스페이스에 저장된 외부 공급자 키(OpenAI, Anthropic 등)의 노출 가능성을 알렸다(Infosecurity Magazine). 같은 메일은 가장 이른 노출 가능 시점을 2026-10-17 00:30 UTC로 적었다(BleepingComputer). 공동창업자는 문제가 OpenCode 자체가 아니라 OpenCode Console이라고 했고(Infosecurity Magazine, TechCrunch), TechCrunch는 노출된 키가 일부 사용자가 워크스페이스에 둔 Console 키로 한정됐다고 보도했다. 공급자 세 곳의 지출 알림이 한꺼번에 울렸다는 개발자의 글과 수백 달러, 일부는 1,000달러를 넘는 청구 사례가 나왔고, Anthropic과 Google은 노출된 것으로 본 키를 차단했으며, OpenAI는 OpenCode와 협력해 접근을 복구하고 공격에 쓰인 크레딧을 API 고객에게 환불했다고 밝혔다(TechCrunch). 침해 지점이 키 발급자가 아니라 키를 맡은 서비스였고, 보도된 청구와 키 차단으로 보면 앞의 결제 연동키 사례처럼 서드파티 경계에서 키가 샌 것으로 보이는 경우다(보도에 근거한 이 문서의 해석).

2026-11-02에는 Anthropic 도움말, OpenCode 문서와 OpenCode의 X 공지(미러로 본문 확인)를 대조했고, 결제 연동키 사례와 보도 내용은 다시 대조하지 않았다.

## 사례 — 배포 플랫폼의 환경 변수 저장소 침해

배포 플랫폼 Railway는 2026-10-21 보안 공지에서 고객 환경 변수를 저장하는 시스템의 이상 활동을 탐지했으며, 무단 제3자가 암호화된 환경 변수에 접근해 그중 일부는 복호화된 값까지 얻었을 수 있다고 밝혔다. 환경 변수에는 API 키, DB와 레지스트리 자격증명 같은 비밀이 들어 있을 수 있으며, 조사 동안 모든 배포를 멈췄다. 같은 공지는 이 사고를 AI 추론 공급자를 침해하려고 최근 플랫폼 기업을 연이어 노린 공격의 일부로 본다고 적었다. 10-22 예비 보고서는 초기 조사상 증류 공격에 쓸 AI 공급자 API 키를 얻으려던 공격으로 설명했고, FAQ에는 공격자가 모델 가중치 증류를 위해 AI와 플랫폼 API 키를 찾았을 가능성이 높다고 적었다. 모두 조사 중의 판단이다. 앞의 OpenCode도 침해를 증류 공격과 관련지었지만 키 노출과의 관계는 설명하지 않았고, 두 사례는 AI 공급자 키를 맡은 곳이 침해됐다는 점이 같다(이 문서의 해석).

예비 보고서(10-26 갱신 포함)는 공격 기간을 10-20 13:58 UTC부터 공격자가 더는 내부 시스템에 접근하지 못한다고 확인한 10-22 03:32 UTC까지로 적는다. 빌드 인프라에서 공격자의 권한 상승 가능성과 이후의 추가 접근 경로를 언급했지만, 2026-11-08에 확인한 세 게시물 기준 구체적인 악용 방식과 규모는 공유하지 않았다. 시각표에는 공격자가 10-21 04:24~05:23에 비밀을 암호화된 상태로 가져갔지만 당시에는 복호화하지 못했고, 05:27~07:25에 CI 환경에 접근하는 자격증명을 얻어 추가 API 접근 정보가 담긴 산출물을 복호화했다고 적혀 있다. 암호화된 환경 변수를 조회한 무단 query의 흔적이 DB에 남아 있었고, 그중 일부는 탈취한 자격증명의 조합으로 복호화됐다. 사용자 계정 접근은 없었다고 밝혔지만 사용자 소스 코드 접근은 최종 포렌식 보고서 전까지 배제하지 않았다. 실행 중인 서비스는 사고 내내 온라인이었고, 빌드는 여러 차례 멈췄다가 10-22 모든 요금제의 배포가 정상화됐다. 2026-11-08에 확인한 예비 보고서에는 복구 기간 동안 신규 가입을 멈췄다는 문장이 있다.

영향 범위는 상한으로 제시됐다. 보고서는 환경 변수 일부가 노출됐을 수 있는 워크스페이스를 전체의 최대 1.85%(약 10만 개)로 적으면서, 키 전체가 봉투 암호화(envelope encryption)돼 있어 이 query만으로는 영향받은 프로젝트나 서비스의 어떤 키가 노출됐는지 특정할 수 없다고 밝혔다. 교체 권고는 이 상한 밖의 고객까지 포함한다. 공지 당일 블로그는 Railway에 저장한 환경 변수와 비공개 레지스트리 자격증명을 즉시 모두 교체하라고 했고, 10-23 변경 기록은 모든 고객에게 10-21 전(before October 21)에 Railway에 저장한 민감한 자격증명을 폐기하고 교체하라고 권했다. 예비 보고서도 모든 사용자에게 저장한 민감한 환경 변수를 폐기하고 다시 적용하라고 권했다. 공격 기간은 10-22 03:32 UTC까지이므로 그 사이에 저장하거나 바꾼 값을 교체 범위에 넣을지도 따로 판단한다(이 문서의 해석). 공급자의 키 재설정 요청이 닿은 사용자는 10만보다 많았지만, Railway는 공급자의 폐기 안내를 받았다는 사실이 그 자격증명이 이번 사고로 노출됐다는 뜻은 아니라고 덧붙였다.

Railway는 고객에게 변수와 키 교체 외에 DB의 공개 네트워크 접근 제거, GitHub 감사 로그와 설치된 앱 접근 검토, 컨테이너 레지스트리 감사 로그 확인을 권했다. 자체 조치로는 모든 키를 교체하고 침입자가 시스템에서 밀려났음을 확인한 뒤 다시 교체했으며, Railway에 배포된 모든 스토리지 버킷의 자격증명과 모든 GitHub App 설치를 교체하고 Railway access token을 모두 폐기했다.

이 사례에서 옮길 점은 다음과 같다(이 문서의 해석과 운영 제안).

- 비밀을 저장한 플랫폼이 뚫리면 사용자가 직접 키를 유출하지 않았어도 그 플랫폼에 저장한 비밀 전체가 교체 대상이 될 수 있다. 플랫폼마다 어떤 키를 어느 서비스에 저장했는지와 각 키의 발급처, 폐기 방법을 목록으로 둔다. 외주로 고객 서비스를 운영하면 고객이 발급한 키와 운영자 키, 교체 주체를 함께 적는다. 위 BYOK 절처럼 플랫폼 전용 키와 단기 자격증명을 쓰면 교체 범위와 피해가 줄어든다.
- 플랫폼의 변수를 바꾸는 것만으로 발급처의 이전 키가 무효화되지 않는다. 위 사고 후 조치의 1번처럼 발급처에서 폐기하고 새로 발급한 값을 넣는다.
- IP 허용 목록 같은 다른 네트워크 제한 없이 DB를 공개 네트워크에 열어 두면 DB 자격증명이 새는 순간 그대로 접속 경로가 된다. 사설 네트워크 접근만 허용하면 유출된 자격증명만으로는 접속하기 어려워진다. 다만 배포 토큰이나 저장소 연동까지 침해되면 같은 네트워크에 서비스를 배포해 우회할 수 있으므로, 그 자격증명의 보호와 함께 본다.

2026-11-08에는 Railway의 공지, 예비 보고서와 변경 기록만 대조했다.

## AI 공급자 키가 표적이 되는 이유 — 무단 증류

증류(distillation)는 더 강한 모델의 출력으로 덜 강한 모델을 학습시키는 방법이다. 프런티어 연구소가 자사 모델을 작고 싼 버전으로 만드는 데 쓰는 정상적인 학습 방법이지만, 경쟁자가 다른 연구소의 능력을 허가 없이 짧은 시간에 가져오는 데도 쓸 수 있다(Anthropic, 2026-02-23). 대상 모델의 가중치를 훔치지 않아도 대량의 질의와 응답을 얻으면 되므로, 정상 고객으로 보이는 API 접근 자체가 자원이 된다(이 문서의 해석). 이 절은 키가 표적이 되는 측면만 다룬다. API를 통한 모델 추출 방어는 [[LLM-Application-Security|LLM 애플리케이션 보안]]에서, 공급자 약관의 증류 제한은 [[LLM-Provider-Usage-Policy|LLM 공급자 이용 정책]]에서 다룬다.

Anthropic이 공개한 접근 방식은 다음과 같다.

- **프록시와 계정 네트워크:** 프런티어 모델 접근을 대량으로 재판매하는 상업 프록시 서비스를 거치고, 사기 계정 네트워크로 트래픽을 Anthropic API와 서드파티 클라우드 플랫폼에 나눠 보낸다. 한 계정이 차단되면 다른 계정이 그 자리를 채우고, 증류 트래픽을 무관한 고객 요청과 섞어 탐지를 어렵게 한다. 2026-02 게시물은 세 연구소가 약 2만 4천 개의 사기 계정으로 1,600만 건이 넘는 교환을 만들었다고 적었다.
- **도난 키의 사용:** 2026-09 위협 보고서는 이런 프록시를 transfer station이라고 부르며, 지역 제한과 관련 통제를 우회하려고 허위 신원, 위조나 도난 신용카드와 도난 API 키로 수천 개의 새 계정을 만들며, 정당한 회사나 개인의 도난 API 자격증명을 자주 쓴다고 적었다. 증류와 별개로 같은 보고서의 사이버 범죄 사례는 여러 표적 환경에서 훔친 AI API 키를 공격 작업의 추가 연산에 썼다.
- **추론 과정 추출:** 증류에 쓸 사고 과정(chain-of-thought) 자료를 얻으려고 모델의 추론 내용을 출력시키는 요청을 보낸다. 2026-09 보고서는 한 무단 주체가 요청마다 다른 기법을 쓴 1만 2천 건이 넘는 시험 요청으로 어떤 방법이 통하는지 확인했고, 대부분은 거부됐지만 성공한 기법을 더 큰 증류 공격에 썼다고 적었다.

Anthropic이 밝힌 자사 대응은 API 트래픽에서 증류 패턴을 찾는 분류기와 행동 지문(behavioral fingerprinting), 추론 추출 요청과 여러 계정에 걸친 조직적 활동의 탐지, 다른 연구소와 클라우드 사업자, 당국과의 기술 지표 공유, 교육용, 보안 연구와 스타트업 계정의 검증 강화, 불법 증류에 쓰일 출력의 효용을 낮추는 제품, API와 모델 수준의 안전장치다(2026-02 게시물 기준).

키를 맡거나 쓰는 쪽에서 옮길 점은 다음과 같다(이 문서의 해석과 운영 제안).

- 도난 키는 위 보고서가 든 지역 제한 우회 수단이 되고, 결제 수단이 붙은 신뢰된 고객 계정이라는 점에서도 증류 공격자에게 가치가 있다. Railway는 증류에 쓸 키 확보를 공격 목적으로 설명했고, OpenCode는 침해를 증류 공격과 관련지었지만 키 노출과의 관계는 밝히지 않았다. 사용자 키를 대신 보관하는 서비스는 많은 고객의 키를 한곳에 모은 표적이 된다.
- 도난 키로 보낸 증류 트래픽은 공급자의 탐지에 걸려 차단될 수 있고, 그때 정상 서비스도 같은 키로 함께 멈춘다. 환경과 서비스별로 키를 나누고 지출 한도를 걸어 두면 차단과 청구의 범위가 줄어든다.

2026-11-10에는 Anthropic의 2026-02 게시물 본문과 2026-09 위협 보고서의 일부 구간을 대조했다. 위협 보고서의 연구소별 수치와 추출 프롬프트 예시는 원문 전체를 확인하지 못해 옮기지 않았다.

## 면접 체크포인트

- 시스템 침입이 없어도 자격증명 노출만으로 데이터가 유출되는 경로를 설명할 수 있는가.
- 결제 연동에서 클라이언트에 노출해도 되는 키와 서버 전용 키를 왜 나누는가.
- 노출 확률을 0으로 못 만들 때 권한 최소화가 피해를 왜 줄이는가.
- 탈취 키로 위장한 정상 요청을 어떻게 탐지하는가 (행위 기반 이상 탐지, 키별 rate limit, 감사 로그).
- 사용자 키를 맡은 서비스(BYOK)가 뚫리면 비용이 누구에게 청구되며, 그 서비스의 예산과 rate limit이 왜 피해를 막지 못하는가.
- 외부 서비스에서 키 노출 공지를 받았을 때 어디서 키를 폐기하고 무엇을 확인하는가 (공급자 콘솔에서 폐기와 재발급, 연동 전환, 사용량과 청구 확인).
- 공개 GitHub 저장소에 올라간 키와 서비스의 키 보관 DB에서 유출된 키에서 secret scanning 기반 자동 폐기가 닿는 범위는 어떻게 다른가.
- AI 공급자 키가 증류 공격의 표적이 되는 이유와, 도난 키가 탐지돼 차단될 때 정상 서비스가 받는 영향을 설명할 수 있는가.
- 비밀을 저장한 배포 플랫폼이 침해됐는데 어떤 키가 노출됐는지 특정할 수 없을 때 무엇을 교체 범위로 잡는가 (영향 상한과 무관하게 해당 시점 전에 저장한 비밀 전체 교체, 발급처에서의 폐기).
