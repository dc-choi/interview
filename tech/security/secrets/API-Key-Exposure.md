# API 연동 키 노출과 최소 권한 스코프

외부 서비스 연동에 쓰는 API 키(연동키, 시크릿 키)는 그 자체가 자격증명이다. 노출되면 공격자가 시스템을 침입하지 않고도 정당한 요청으로 위장해 그 키의 권한 범위 전체에 접근한다. 침입 흔적이 없다는 사실이 안전을 뜻하지 않는다. 탈취한 키로 보낸 요청은 서버 입장에서 인증을 통과한 정상 요청이기 때문이다.

## 멘탈 모델 — 키의 권한 범위가 곧 공격 표면

키가 유출되는 순간 방어선은 그 키에 부여된 권한까지로 좁혀진다. 그래서 두 축이 피해 크기를 결정한다.

- 노출 여부: 키가 클라이언트, 저장소, 로그, URL처럼 공격자가 닿는 경계에 있는가.
- 권한 범위: 그 키로 무엇까지 할 수 있는가. 결제 요청용 키가 전체 결제내역 조회까지 가능하면, 노출 시 요청 권한만이 아니라 조회 권한까지 함께 넘어간다.

두 축은 곱으로 작동한다. 노출 확률을 0으로 만들 수는 없으므로, 권한 범위를 최소로 줄이는 것이 노출이 발생했을 때의 피해를 상수배 낮춘다.

## 노출 지점

- 클라이언트 노출: 서버 전용 시크릿 키를 프런트엔드 번들, 모바일 앱, HTML에 넣으면 사용자가 곧 열람자가 된다. 결제 연동은 보통 클라이언트에 노출해도 되는 키(결제창 호출용)와 서버에만 두는 키(승인, 조회용)를 나눈다. 이 구분을 어기고 서버 키를 클라이언트에 두면 노출된다.
- 버전 관리, 로그, URL: Git 히스토리 평문, 접근 로그의 쿼리스트링, 리퍼러 헤더로 새어 나간다. 저장과 주입 계층의 방어는 [[Secret-Management|시크릿 관리]]에서 다룬다.
- 서드파티 경계: 연동을 맡긴 외부 플랫폼이나 가맹점 쪽에서 키가 새면, 키 발급자 시스템은 멀쩡해도 그 키가 가리키는 데이터가 열린다.

## 최소 권한 스코프

- 용도별로 키를 분리하고 각 키에 필요한 스코프만 부여한다. 조회, 승인, 환불 권한을 한 키에 몰지 않는다. 권한 모델의 일반 원리는 [[Access-Control-Models|접근 제어 모델]]을 따른다.
- 키를 IP, 도메인, 호출 출처로 제한할 수 있으면 건다.
- 유효기간과 로테이션을 전제로 설계한다. 정적 장수 키는 유출 시 피해 기간이 길다. → [[Refresh-Token-Rotation|토큰 로테이션]]

## 정상 요청으로 위장한 유출은 탐지가 어렵다

탈취한 키로 보낸 요청은 인증을 통과한 정상 트래픽이라 인증 실패 로그로는 잡히지 않는다. 조회량 급증, 평소와 다른 출처, 대량 순회 같은 행위 기반 이상 탐지와 키별 rate limit이 필요하다. → [[Rate-Limiting|Rate limit]], [[Audit-Log|감사 로그]]

노출이 확인되면 침입 흔적 유무와 무관하게 키를 즉시 폐기하고 회전하며, 접속 기록 전수를 분석해 영향 범위와 정보주체를 특정한다.

## 사례 — 결제 연동키 노출로 결제내역 조회

한 결제대행사(토스페이먼츠)에서 특정 가맹점이 쓰던 결제연동 플랫폼의 연동키가 노출돼, 제3자가 그 키로 해당 가맹점의 결제내역 4131건(정보주체 2671명, 구매자 성명과 마스킹된 카드번호, 승인번호 등 영수증 수준 항목)을 조회했다. 결제대행사 시스템 자체에 대한 침입은 확인되지 않았고, 노출된 정보로 추가 결제나 취소는 불가능했다. 핵심은 자격증명 노출과 그 키로 조회까지 가능했던 권한 범위이며, 침입이 없었다는 점이 조회 유출을 막지는 못했다.

## 면접 체크포인트

- 시스템 침입이 없어도 자격증명 노출만으로 데이터가 유출되는 경로를 설명할 수 있는가.
- 결제 연동에서 클라이언트에 노출해도 되는 키와 서버 전용 키를 왜 나누는가.
- 노출 확률을 0으로 못 만들 때 권한 최소화가 피해를 왜 줄이는가.
- 탈취 키로 위장한 정상 요청을 어떻게 탐지하는가 (행위 기반 이상 탐지, 키별 rate limit, 감사 로그).
