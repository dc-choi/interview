# 기술 의사결정

기술적 선택이 비즈니스에 미치는 영향을 고려하여 근거 기반으로 결정하는 역량이다. "왜 이 기술을 선택했는가?"에 트레이드오프를 포함한 답변을 할 수 있어야 한다.

## 의사결정 프레임워크

1. **문제 정의** — 현재 상태와 목표 상태의 차이를 명확히 한다
2. **선택지 나열** — 가능한 대안을 최소 2개 이상 도출한다
3. **트레이드오프 분석** — 각 선택지의 장단점, 리스크, 비용을 비교한다
4. **결정 + 근거 기록** — 선택한 이유와 배제한 이유를 문서화한다
5. **검증 기준 정의** — 결정이 올바른지 판단할 지표를 사전에 정한다

## Design It Twice

중요한 선택은 첫 번째로 떠오른 설계를 곧바로 구현하지 않고, 같은 제약을 만족하는 **서로 다른 설계 두 개 이상**을 짧게 만든 뒤 비교한다.

- 같은 문제와 성공 기준을 두고 경계, 데이터 흐름이나 운영 방식이 다른 대안을 만든다.
- 인터페이스 복잡도, 실패 모드, 마이그레이션, 관측과 되돌리기 비용을 같은 기준으로 비교한다.
- 다이어그램, 얇은 prototype이나 AI 브레인스토밍으로 탐색 비용을 줄일 수 있지만, 생성된 선택지를 실제 근거로 검증한다.
- 선택 뒤에는 채택 이유뿐 아니라 버린 대안과 다시 검토할 조건을 남긴다.

이는 시스템을 두 번 완성하라는 뜻이 아니다. 가역적인 결정은 탐색을 짧게 하고, 되돌리기 어렵고 영향 범위가 큰 결정일수록 비교에 더 투자한다.

## 트렌드 도입 판단 — 업계 표준이라는 이유는 근거가 아니다

어떤 기술이 업계 표준처럼 자리 잡아도, 그 이점이 우리 서비스에서도 유효한지는 별개 문제다. 남들이 쓴다는 사실이 아니라 우리에게도 이득인지가 도입 판단의 출발점이다.

- 이점을 우리 맥락에서 측정한다. 그 기술이 내세우는 장점(예: 렌더링 방식, 성능)을 실제 서비스와 유사한 조건에서 재현해, 우리 화면과 트래픽에서 체감 개선이 실제로 나오는지 데이터로 확인한다.
- 이득과 전환, 운영 비용을 저울질한다. 판단 축은 둘이다. 얻는 이득이 우리 서비스에서 유효한가, 전환과 이후 운영 비용을 감당할 수 있는가. 학습 곡선, 경계 설정의 복잡도, 점진적 마이그레이션의 리스크가 운영 비용에 들어간다.
- 커뮤니티 규모가 우리 문제를 대신 풀어 주지는 않는다. 많이 쓰이는 기술이라도 우리가 부딪힌 구체적 문제의 해결이 먼저 오는 것은 아니다.
- 도입하지 않음도 정당한 결론이다. 측정 결과 이득이 비용을 넘지 못하면 기존 방식 유지가 근거 있는 결정이며, 재검토 조건과 함께 기록한다.
- 채택의 근거 가정을 적어 두고 가정이 무너질 때 재평가한다. 재평가 트리거는 도구의 성능 저하가 아니라 전제 붕괴다. 코딩 에이전트가 두 번 구현하는 비용을 낮추자 코드 공유라는 크로스플랫폼의 전제가 흔들린 사례는 [[Mobile-App-Architectures|모바일 앱 개발 방식]]을 참고한다.

## 에이전트가 제안한 의존성도 기술 결정이다

기능 구현을 맡겨도 새 데이터베이스, 발송 서비스와 라이브러리를 채택할지는 별도로 판단한다. 에이전트의 구현 성공과 팀의 장기 운영 가능성은 다른 검증 대상이다.

1. 기존 스택만으로 해결하는 안을 먼저 만든다. 어렵다면 구체적인 제약과 비용을 적는다.
2. 새 도구의 구현 시간뿐 아니라 요금, 관측, 장애 복구, 팀의 이해와 제거 비용을 비교한다.
3. 기존 도구와 겹치면 대체 범위와 이전 계획을 정해 중복 운영이 무기한 남지 않게 한다.
4. 에이전트가 내놓은 제품 비교와 요금 주장은 해당 제품의 공식 자료로 다시 확인한다.

성숙한 기술을 우선한다는 것은 오래됐다는 이유만으로 고르라는 뜻이 아니다. 기능과 실패 양상을 이해하고 현재 문제를 감당할 수 있는지가 기준이다.

### 선택 빈도 실험을 읽는 경계

2026-09-03 공개된 Armature 실험은 16,893회 실행 중 51개 코드베이스, 18개 분야의 5,292개 세션을 첫 분석으로 공개했다. 저장소는 합성했으며 모의 사용자와 LLM 판정기를 사용했다. 같은 이메일 발송 요구도 저장소 언어에 따라 선택된 공급자가 달랐다.

이는 해당 실험 조건의 선택 경향이다. 실제 운영 품질, 전체 개발자의 선호나 특정 도구의 우월성을 입증하지 않는다. 연구 주체가 개발자 도구 성장 서비스를 판매한다는 이해관계도 함께 읽는다. 기술 선정에는 선택 빈도보다 자신의 요구와 실패 조건에 대한 검증이 필요하다.

## 에이전트가 직접 쓸 코드를 줄이는 쪽으로 스택을 고른다

에이전트는 짧은 시간에 많은 코드를 만들지만, 만든 코드는 이후 수정, 보안 패치와 운영의 대상으로 남는다. 시스템을 안정적으로 유지하는 장기 비용은 거의 언제나 만들 때 겪는 어떤 불편보다도 훨씬 크다(Choose Boring Technology). 생성된 코드의 수정 용이성 같은 비기능 요구를 매번 사람이 보정하기보다, 에이전트가 새로 작성할 코드의 양과 선택지를 처음부터 줄이도록 기술을 고를 수 있다.

1. 작업을 맡기기 전에 쓸 프레임워크, 라이브러리와 관리형 서비스를 정해 저장소 지시 파일에 적는다. 정해진 부품으로 조립하게 하면 같은 문제를 매번 다른 직접 구현으로 푸는 일을 줄일 수 있다. 확인한 범위에서는 이 효과를 직접 잰 자료를 찾지 못했으므로 새 의존성 추가와 중복 구현은 리뷰와 CI에서 확인한다. 2026-10-12 기준 Claude Code 문서는 Claude가 CLAUDE.md를 강제 설정이 아닌 맥락으로 다룬다고 설명하므로, 승인하지 않은 패키지 설치 명령은 실행 전 훅으로, 의존성 목록 변경은 CI의 허용 목록 검사로 막는다([[Agent-Repository-Instructions|저장소 지시 파일 작성과 운영]]). managed settings 밖 훅의 차단은 `tool.check`를 처리하는 mod가 승인으로 바꿀 수 있으므로 최종 확인은 CI에 둔다.
2. 인증, 결제, 메일 발송처럼 그 기능 자체가 사업이 아니어서 차별화와 거리가 먼 기능은 에이전트에게 직접 구현시키기 전에 기존 스택의 부품, 성숙한 라이브러리와 관리형 서비스를 위 의존성 판단 절차로 비교한다. AWS Well-Architected의 운영 우수성 설계 원칙도 가능한 곳에서 AWS 관리형 서비스로 운영 부담을 줄이고 운영 절차를 그 서비스와의 상호작용에 맞춰 짜라고 권한다. 관리형 서비스를 파는 공급자의 지침이라는 점도 함께 읽는다. 인증과 결제를 직접 만들지 않는 근거는 [[Build-vs-Buy|Build vs Buy]]를 따른다.
3. 모듈과 레이어 경계, 데이터 소유처럼 코드를 어디에 둘지 정하는 설계는 위임하지 않는 판단으로 남긴다([[Developer-Role-AI-Era|AI 시대 개발자 역할]]). 사람이 정한 분할이 에이전트의 유지보수에도 맞는지 판단할 정립된 기준을 찾지 못했으므로 경계는 테스트와 [[Architecture-Fitness-Functions|fitness function]]으로 확인한다.

AI 보조 코드의 유지보수 근거는 엇갈린다. 코드 분석 업체 GitClear의 2025년 보고서는 2020년부터 2024년까지 바뀐 2억 1,100만 줄을 집계해, 2024년에 처음으로 복사해 붙인 줄(한 커밋 안에서 여러 파일이나 함수에 같은 내용으로 들어간 줄)이 옮긴 줄(이 업체가 리팩터링의 신호로 보는 지표)보다 많아졌다고 보고했다. AI가 쓴 줄을 구분하지 않은 전체 변경 줄의 추이이고, 옵트인 고객사와 오픈소스로 된 표본의 구성이 해마다 바뀌며, 학술 심사를 거치지 않았고 이 지표를 재는 자사 제품을 파는 업체의 보고서다. DORA의 2024년 조사 분석은 AI 도입이 25% 늘 때 문서 품질 약 7.5%, 코드 품질 약 3.4% 개선과 함께 전달 처리량 약 1.5%, 전달 안정성 약 7.2% 감소의 연관을 추정했다. 2025년 보고서에서는 처리량과의 관계가 양으로 바뀌었고 안정성과의 음의 관계는 이어졌다([[AX-Transformation|AX 조직 전환]]). 설문 기반 모형의 연관이지 원인 증명은 아니다. 통제 실험도 있다. 두 단계로 나눈 실험(전체 151명, 95%가 현업 개발자)에서 AI 도움 여부를 달리해 Java 웹 앱에 더한 기능을 다른 개발자들이 AI 없이 이어서 개발했을 때 완료 시간과 코드 품질에 유의한 차이가 없었다. 사람이 AI 보조 도구를 쓴 조건이라 에이전트가 자율로 쓴 코드에 그대로 옮기지 않으며, 세 자료 모두 사용하는 스택을 제한하거나 관리형 서비스로 옮긴 효과를 잰 것은 아니다.

이 방향은 위험을 없애지 않고 옮긴다. 외부 서비스는 요금, 장애와 정책 변경, 데이터 위치와 이전 비용을, 라이브러리는 공급망과 버전 갱신 부담을 들여온다. 각 후보는 위 의존성 판단 절차로 비교한다. 기능이 적은 프레임워크를 여러 개 조합하면 한 프레임워크가 맡던 통합과 버전 호환을 팀이 직접 맞춰야 하므로, 기능 수가 적다는 이유만으로 결함이 줄어든다고 가정하지 않는다. AI 생성 코드의 구조 품질을 재는 방법과 한계는 [[AI-Slop-Quality-Gate|AI 슬롭과 판단 관문]]을 따른다.

## 결정의 전달과 진화

아키텍처 결정은 결정권자의 머릿속에서 끝나지 않는다. 기술 팀에는 구현 제약과 검증 방법을, 비기술 이해관계자에게는 비용, 위험과 전달 속도에 미치는 영향을 설명해야 실제로 같은 방향으로 움직일 수 있다.

- ADR에는 맥락, 검토한 선택지, 결정, 결과와 재검토 조건을 기록한다.
- 결정과 함께 품질 속성을 측정할 [[Architecture-Fitness-Functions|fitness function]]을 정해 의도가 코드와 운영에서 유지되는지 확인한다.
- 설계자는 코드와 팀의 피드백에서 떨어지지 않고, 새 정보가 생기면 기록과 결정을 함께 갱신한다.

## 사례 1: 계정 모델 전환

한 협업 서비스에서 여러 사용자가 하나의 계정을 공유하면 권한 분리, 활동 추적과 리소스 소유권 검증이 모두 불명확해진다. 단기 편의성은 있지만 기능 확장과 보안 검증의 기반이 약해진다.

**선택지:**
1. 공유 계정을 유지하고 표시 이름만 구분한다 — 변경은 작지만 소유권 문제는 남는다.
2. 개인 계정과 조직 경계를 도입한다 — 마이그레이션 비용은 크지만 소유권과 권한을 명확히 한다.

**결정: 선택지 2**
- 근거: IDOR의 구조적 원인을 줄이고 향후 협업 기능의 기반을 만든다.
- 리스크: 마이그레이션 실패와 데이터 손실 → 완화: 백업, 작은 범위의 단계적 적용과 수동 검증.
- 검증 기준: 합류 흐름의 완료, 권한 경계 회귀 테스트와 데이터 정합성을 함께 확인한다.

## 사례 2: 포지셔닝 전환 (Pivot)

한 제품이 특정 세그먼트의 문제를 해결하고 있을 때 인접 세그먼트로 확장하면 성장 기회가 생길 수 있지만, 기존 사용자의 문제를 흐리거나 새로운 결제 및 운영 가정을 만들어낼 수 있다.

**검토:** 기존 세그먼트에 집중하는 선택과 인접 세그먼트로 확장하는 선택을 비교한다.

**결정 기준:** 기존 세그먼트의 활성화, 반복 사용과 지불 의향을 검증하기 전에는 확장을 가설로만 보존한다. 확장이 필요한 증거와 실험 범위를 문서화한 뒤에만 제품 용어, 채널과 UI를 바꾼다.

**영향 범위:** 확정을 전제로 하지 않고, 확정 뒤 변경될 데이터 모델, 브랜딩, 채널과 UI 문구를 미리 식별한다.

## 사례 3: 보안 취약점 대응 (IDOR)

**문제:** 계정과 리소스 소유권이 직접 연결된 구조에서는 수평 권한 상승 가능성이 생길 수 있다.

**단기 대응:** 취약한 요청 경로를 즉시 차단하거나 검증을 추가한다.
**구조적 해결:** 공통 소유권 검증과 회귀 테스트를 만들어 같은 유형의 누락을 줄인다.

**결정 기준:** 보안 취약점은 단기 패치와 구조적 해결을 병행. 패치만으로 끝내지 않고 같은 유형의 취약점이 재발하지 않도록 공통 유틸을 만들었다.

## 결정을 기록하는 이유

- 미래의 자신과 팀원에게 "왜 이렇게 했는지" 설명
- 상황이 변했을 때 재검토 근거 제공
- 같은 실수를 반복하지 않기 위한 학습 자산

## 면접 포인트

Q. 중요한 기술적 의사결정 경험은?
- 계정 모델 전환: 공유 계정의 한계를 개인 계정과 조직 경계로 해결하고, 마이그레이션과 회귀 검증을 함께 설계
- 포지셔닝 피벗: 확장 가설을 현재 정책처럼 말하지 않고, 기존 세그먼트 검증 뒤에 재평가
- 보안 대응: 핫픽스(단기) + 공통 유틸(구조적) 병행

Q. 의사결정을 어떻게 문서화하는가?
- PRD 형식: 배경/문제 → 목표/성공 기준 → 범위 → 요구사항 → 리스크 → 롤아웃/검증
- 결정 근거, 배제 이유, 검증 기준을 명시

## 비용, 변화와 팀의 이해를 함께 설계한다

베스트 프랙티스를 적용했다는 사실만으로 현재 팀에 적절한 설계가 되지는 않는다. 원칙이 해결하려는 문제를 먼저 확인하고, 이번 요구와 제약에서 얻는 이득을 비교한다. 영상의 비용, 시간, 인간이라는 세 관점은 이 비교를 넓히는 질문으로 사용할 수 있다.

| 관점 | 설계에서 확인할 질문 |
|---|---|
| 비용 | 지금 구현, 검토와 운영에 쓰는 자원은 무엇이며 어떤 위험을 줄이는가 |
| 변화 | 요구가 달라졌을 때 어느 경계를 바꾸며 얼마나 되돌리기 쉬운가 |
| 팀 | 다른 구성원이 이해, 수정과 운영을 지속할 수 있는가 |

미래의 모든 변화를 예측해 추상화하기보다 실제 변경 압력과 되돌림 비용을 기록한다. 이해하기 쉬운 구조와 존중하는 코드 리뷰는 팀이 판단을 공유하는 데 도움이 된다. 다만 팀의 속도와 분위기를 이유로 보안, 데이터 정합성이나 필수 품질을 희생하지 않는다. 단순함과 품질을 어떤 기준에서 함께 만족할지 합의한다. 이 틀은 시니어의 사고를 설명하는 경험적 관점이며 연봉과 승진을 결정하는 보편 법칙이 아니다.
