# 문제 발견 — 해결할 가치가 있는 문제를 찾는 법

주어진 과제를 잘 해결하는 것도 인정받는 경로다. 그러나 스태프 레벨에서 더 큰 영향은 조직이 아직 이름 붙이지 못한 문제를 발견해 무엇을 만들지 결정에 참여하는 데서 나온다. 전략적 사고를 위해 일정을 비우는 방식보다, 일상의 소음을 흡수하는 스펀지처럼 일하면서 문제를 건져 올리는 방식이 현실적이다. 적용 범위에는 조건이 있다 — 이 방식은 상향식 자율성이 큰 팀(대기업 인프라, 개발자 도구류) 경험에 기반하며, 톱다운 조직에서는 이렇게 일할 여지가 작을 수 있다. [[Strategic-Slack|전략적 여유]]와 모순되지도 않는다 — 그쪽은 관찰과 사고에 쓸 여유 자체를 확보하라는 것이고, 이쪽은 문제 발견에 한해서는 그 여유가 백지 앞 사고보다 일상 관찰에서 더 잘 작동한다는 경험칙이다.

## 1. 요청이 아니라 마찰을 흡수한다

- 회의, 채팅, 발표에서 사람들이 겪는 어려움을 계속 수집한다. 요청은 해결책의 형태로 오지만, 필요한 것은 그 밑의 문제다.
- 요청된 해결책과 실제 필요를 구분하는 질문: X가 생기면 정말 이 문제가 사라지는가. 요청 뒤의 문제를 읽는 질문 패턴은 [[Cross-Functional-Product-Collaboration|직군 간 프로덕트 협업]]도 다룬다.
- 근본 원인을 이해할 때까지 파고들고, 가능하면 실제 업무 흐름을 직접 관찰한다.
- 여러 팀을 가로질러 보는 사람이나 핵심 시스템 소유자와의 1:1은 패턴 발견을 앞당긴다.

## 2. 문제를 축적한다 — 대기는 초능력

- 대부분의 요청은 처음 들었을 때 바로 프로젝트로 만들 필요가 없다. 기다리면 서로 다른 팀에서의 독립적 재발, 겉모습이 달라도 같은 구조, 또는 요청 자체의 소멸이 드러난다.
- 축적된 사례가 많을수록 공통 형태의 신뢰도가 올라가고, 해법이 특정 팀의 특수 요구에 과적합되는 것을 막는다.
- 이 대기는 [[Own-Your-Core|즉시 실행]]과 축이 다르다 — 문제가 진짜인지 증거를 모으는 대기이지, 이미 내린 결정의 착수를 미루는 것이 아니다.

## 3. 공통 형태를 찾고, 가설로 검증한다

- 개별 요청들 뒤의 근본 필요를 찾는다. 좋은 공통 형태는 요청 목록의 합집합이 아니라 요청들을 만들어 낸 하나의 결핍이다.
- 우아함은 증거가 아니다. 공통 형태가 보여도 가설로 취급하고 구체적으로 검증한다.

### 짧은 사례 — 트레이싱 도구 UI (2026-07 글 기준)

성능 트레이싱 도구(Perfetto)에 약 2년에 걸쳐 팀마다 다른 UI 요청이 쌓였다 — 선호 트랙 고정, 열 때 특정 지점으로 확대, 팀 맞춤 집계, 심지어 북마클릿으로 내부 API를 직접 호출하는 팀까지. 공통 형태는 개별 기능이 아니라, 자기 팀의 선택을 남에게 강요하지 않으면서 UI를 개인화하는 능력이었다. 해법은 플러그인 작성 없이 UI 작업을 자동화하는 경량 매크로와 팀 간 매크로 공유 서버였고, 개별 요청 하나하나만 봐서는 드러나지 않던 방향이었다.

반례도 있다. 투명 캐시 하나로 반복 질의와 대용량 트레이스 재개방을 동시에 풀려던 설계는 RFC와 프로토타입 검증 과정에서 두 문제가 서로 다른 해법을 요구한다는 것이 드러나 분리됐고, 분리된 두 해법은 이후 실제로 배포됐다. 공통 형태 가설이 검증에서 깨지는 것은 실패가 아니라 검증이 일한 것이다.

## 구현 강도는 확신과 위험으로 정한다

| 상황 | 접근 |
|---|---|
| 위험 낮고 유용성 확신, 비용이 작음 | 바로 구현하고 사후 공유 (비용이 커지는 glue work는 먼저 가시화해 우선순위를 받는다 — [[Strategic-Slack|전략적 여유]]) |
| 불확실 | 일회용 프로토타입으로 실패 지점을 먼저 노출 |
| 규모 크고 확신 높음 | 수주에서 수개월의 투입 — RFC와 발표, 다수의 1:1로 조직 지지를 만든 뒤 장기 개발 ([[RFC-Writing|RFC 작성]]) |
| 시기가 맞지 않음 | 보류하고 조직 우선순위가 바뀔 때까지 대기 |
| 검증에서 가치가 확인되지 않거나 기술적 벽 | 폐기 — 아무도 쓰지 않을 것을 만드느니 지금 접는다 |

표의 즉시 구현과 프로토타입, RFC 행은 가역성 관점으로도 읽을 수 있다 — 되돌리기 쉬운 변경일수록 빠른 실행 쪽, 되돌리기 어려운 변경일수록 검증과 합의 쪽이다 ([[One-Way-vs-Two-Way-Door|가역성 기반 의사결정]]).

## 신뢰 누적 순환

유용한 문제를 발견하고 해결하는 일이 반복되면 순환이 생긴다.

1. 사람들이 더 이른 단계에 문제를 들고 온다.
2. 비슷한 문제를 겪는 대화에 초대받는다.
3. 판단에 대한 조직의 신뢰가 쌓인다.
4. 모든 구현을 직접 맡지 않고도 로드맵에 영향을 준다.

초기에는 판단을 증명하기 위해 직접 구현이 필요하지만, 신뢰가 쌓이면 발견과 방향 제시 자체가 기여가 된다. 이 영향력의 가시화 축은 [[Engineering-Influence|엔지니어링 영향력]]과 같은 근육이다.

## 면접 체크포인트

- 요청된 해결책과 실제 필요를 구분해 다른 해법을 낸 사례가 있는가.
- 한 번의 요청을 바로 구현하지 않고 반복 패턴을 기다린 판단의 근거를 설명할 수 있는가.
- 확신과 위험에 따라 실행 강도(즉시 구현, 프로토타입, RFC, 보류, 폐기)를 조절한 사례가 있는가.
- 발견한 문제의 해결이 신뢰 자산으로 이어져 이후 일의 방식이 달라진 경험이 있는가.
