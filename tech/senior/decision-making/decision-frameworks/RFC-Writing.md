# RFC / PRD 작성

기술적 의사결정이나 제품 변경을 구조화된 문서로 정리하여 팀과 공유하는 역량이다. RFC(Request for Comments)와 PRD(Product Requirements Document)는 같은 문서가 아니지만, **결정의 배경, 범위와 리스크를 명시해 검토 가능하게 만든다**는 기능을 공유한다.

## RFC vs PRD

| 구분 | RFC | PRD |
|---|---|---|
| 초점 | 기술적 설계와 구현 방향 | 제품 요구사항과 사용자 시나리오 |
| 독자 | 엔지니어 | 엔지니어 + PM + 디자이너 |
| 핵심 질문 | "어떻게 만들 것인가?" | "무엇을 왜 만들 것인가?" |

실무에서는 둘을 혼용하거나 하나로 합치는 경우가 많다.

## PRD 구조 (실전 템플릿)

### 1. 배경/문제 요약
- 현재 상태와 문제점을 구체적으로 기술
- 관련 문서 참조 링크
- **"무엇이 문제인가"를 데이터와 사례로 증명**

예: "공유 계정 구조가 여러 사용자의 권한과 활동 추적을 흐려 이탈 위험을 만든다. 사용자 인터뷰와 행동 로그로 재현 조건을 확인한다."

### 2. 목표/성공 기준
- 검증 가능한 성공 기준을 사전에 정의하고, 가능하면 기준선과 정량 지표를 둔다
- 측정 기간 명시

예: "활성화 완료율, 데이터 정합성, 관찰 기간을 사전에 정의하고 기준선과 비교한다."

### 3. 사용자/대상
- 주요 사용자와 사용 맥락
- 사용자 시나리오 (최소 3개: 신규, 기존, 예외)

### 4. 범위
- **포함(In Scope):** 이번에 구현할 것
- **제외(Out of Scope):** 의도적으로 빼는 것과 이유

범위를 명시적으로 정의하면 스코프 크립(scope creep)을 방지한다.

### 5. 요구사항
- **필수(Must):** 없으면 출시 불가
- **선택(Should):** 있으면 좋지만 없어도 출시 가능
- **제외(Out):** 명시적으로 하지 않는 것

MoSCoW 우선순위 기법과 동일한 원리다.

### 6. 제약/가정/리스크
- **제약:** 변경 불가능한 조건 (인력, 기술 스택, 일정)
- **가정:** 검증이 필요한 전제 (사용자가 거부감이 없을 것)
- **리스크:** 실패 가능성과 완화 방안

리스크에는 반드시 **완화(mitigation) 방안**을 함께 기술한다.

### 7. 의존성
- 내부 의존: 다른 기능, 스키마 변경
- 외부 의존: 사용자 동의, 외부 서비스

### 8. 롤아웃/검증
- 출시 단계 (점진적 배포 계획)
- 추적할 이벤트/로그
- 검증 방법과 성공 판단 기준

## 좋은 RFC/PRD의 특징

1. **의사결정을 내릴 수 있다** — 읽은 후 "하자/말자/이렇게 바꾸자"를 판단할 수 있음
2. **이유가 있다** — "무엇"뿐 아니라 "왜"와 "왜 다른 것은 아닌가"가 포함
3. **범위가 명확하다** — 포함/제외가 명시적이어서 스코프 논쟁을 줄임
4. **검증 가능하다** — 성공/실패를 판단할 기준, 증거와 관찰 기간이 존재
5. **오픈 이슈가 있다** — 아직 결정하지 못한 것도 투명하게 기록

## Spec-Driven Development (SDD)

명세(Spec)가 개발 전 과정을 주도하는 접근 방식이다. 코드를 먼저 쓰는 것이 아니라, **"왜 만드는가 → 어떻게 동작하는가 → 어떻게 구현하는가"를 문서로 먼저 정의**한 뒤 구현에 들어간다.

### 적용 예: 7단계 워크플로우

SDD는 다음처럼 문제 정의부터 검증까지의 흐름으로 구체화할 수 있다.

| 단계 | 설명 | 핵심 질문 |
|---|---|---|
| 0 | 작업 선택 + 목표와 제약 확인 | 무엇을 할 것인가? |
| 1 | PRD 작성 | 왜 만드는가? |
| 2 | 기능 설계 작성 | 어떻게 동작하는가? |
| 3 | Task 작성 (역할별 업무 분할) | 누가 무엇을 하는가? |
| 4 | Development 작성 (역할별 구현 명세) | 어떻게 구현하는가? |
| 5 | 구현 + 테스트 | 코드 작성 |
| 6 | 자동 검증 + 문서 정리 + PR 생성 | 품질 보장 |

### 문서 계층 구조

PRD(왜) → 기능 설계(어떻게 동작) → Task(누가 무엇을) → Development(어떻게 구현) → 코드

각 계층이 상위 문서를 기반으로 하며, 하위로 갈수록 구체화된다.

### SSoT (Single Source of Truth)

기능 설계 문서는 의도한 계약을, 코드와 설정은 선언된 구현을 보여준다. 둘만으로 어떤 산출물이 배포됐고 운영에서 실제로 실행되는지까지 증명하지는 못하므로 배포 기록, 런타임 계측과 사용자 경로 검증을 별도 진실 원천으로 둔다. Task/Development 문서 중 코드와 기능 설계를 그대로 반복하는 일회성 구현 초안은 완료 뒤 삭제할 수 있다. 그러나 의사결정 근거, 실제 결과와 회고는 삭제하지 않고 archive 또는 `superseded` 상태로 보존한다.

### 역할 분리

- **기획 역할:** 문제 정의, 가치, 우선순위와 로드맵 정리
- **구현 역할:** 문서 작성, 구현과 자동 검증 수행
- **사용자:** PR 리뷰 → 머지 결정

### 자동 검증 + 서브에이전트 리뷰

구현 완료 후 lint, typecheck, build, test를 자동 실행하고, PR 생성 전 독립 검토 역할이 보안, 설계와 성능 관점의 누락을 추가로 확인한다. 정적 검사와 리뷰 통과는 배포 및 운영 결과 검증을 대신하지 않는다.

### 비기능 요구사항은 간소화

성능, DX 개선 등 비기능적 변경은 Task/Development를 생략하고 기능 설계 → 바로 구현 → 자동 검증으로 진행할 수 있다. 선언된 구현은 코드와 설정을 기준으로 보되, 배포된 버전과 실제 동작은 배포 기록과 런타임 증거로 확인한다. 선택 근거, 기준선, 검증 결과와 후속 판단은 재현 가능한 기록으로 보존한다.

## 면접 포인트

Q. 기술 문서 작성 경험은?
- SDD(스펙 주도 개발)를 프로젝트 흐름에 맞게 적용
- PRD와 기능 설계 문서를 코드와 함께 관리
- 문서 계층: PRD(왜) → 기능 설계(동작) → Task(역할 분할) → Development(구현 명세) → 코드
- SSoT 원칙: 의도한 계약, 선언된 구현, 배포와 운영 증거를 구분하고, 중복 구현 초안만 정리하며 결정, 결과와 회고는 보존

Q. 문서와 코드의 관계는?
- 기능 설계는 "동작 명세" 수준만 유지, 구현 상세는 코드에 위임
- PRD의 성공 지표가 테스트 케이스와 롤아웃 검증의 기반
- 서브에이전트(보안/디자인/성능)가 PR 전에 자동 리뷰하여 품질 게이트 역할
