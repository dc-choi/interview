# 코드 리뷰의 추론과 훈련

코드 리뷰 역량은 변경의 목적을 이해하고, 성립에 필요한 조건을 찾아, 구현과 환경이 그 조건을 지키는지 확인하는 능력이다. 결함 발견, 설계 점검, 지식 공유와 팀 규범 유지가 함께 포함된다.

리뷰는 판단 과정을 훈련하는 기술로 볼 수 있다. 훈련 효과와 AI 대비 우위는 별도 검증이 필요하다.

## 불변조건에서 시작하기

불변조건은 작업 도중에도 유지해야 하는 관계다. 공유 쓰기 충돌 방지, 산출물의 버전 일치와 요청별 상태 격리가 예다.

리뷰에서는 다음 순서로 작은 근거를 쌓을 수 있다. 아래 흐름은 여러 출처의 검토 항목을 작업 절차로 묶은 적용 예다.

1. **목적과 범위**: 사용자 동작, 입력과 출력, 변경 전후 차이를 확인한다.
2. **보존할 조건**: 상태, 자원과 외부 계약에서 깨지면 안 되는 관계를 적는다.
3. **반례**: 실행 순서 역전, 부분 실패, 취소와 환경 차이를 대입한다.
4. **직접 증거**: 호출부, 테스트, 설정과 배포 경로에서 그 조건을 확인한다.
5. **판정**: 재현된 결함, 조건부 위험, 개선 제안과 미검증 영역을 구분한다.

테스트 코드도 리뷰 대상이다. 테스트가 깨진 구현에 대해 실제로 실패하는지, 불필요하게 복잡하거나 과도하게 구현 세부에 묶이지 않았는지 본다.

## diff 바깥에서 확인할 세 경계

| 변경 | 숨어 있는 조건 | 리뷰 질문 |
|---|---|---|
| 백그라운드 실행 | 공유 자원 동시 접근 | 잠금 범위와 순서는? |
| CLI 옵션 변경 | 실제 설치 버전 | CI에서도 지원하는가? |
| 파일과 체크섬 업로드 | 두 파일의 버전 일치 | 중간에 중단되면? |

제안의 지원 환경을 명시한다. 작성자도 같은 위험을 생각했을 것이라는 가정은 회귀를 만들 수 있다.

### 단일 쓰기의 원자성과 묶음의 원자성

Amazon S3의 객체 키 하나에 대한 갱신은 원자적이지만, 서로 다른 키의 갱신을 하나의 원자적 작업으로 묶어주지는 않는다. 새 파일 업로드 뒤 체크섬 갱신 전에 작업이 중단되면, 두 읽기는 각각 유효한 객체를 반환해도 서로 다른 버전을 가리킬 수 있다.

이 실패 모델에서 도출한 설계 후보는 버전별 산출물을 모두 저장한 뒤 공개 참조를 전환하는 방식, 또는 하나의 산출물에 검증 정보를 함께 담는 방식이다. 실제 선택 전에는 읽기 경로와 공개 참조의 원자성, 동시 작성자 및 복구 조건을 확인해야 한다.

## 피드백에 가정을 함께 적기

관찰한 코드, 발생 조건과 예상 결과를 함께 전달한다. 단정 대신 의문형을 쓴다고 근거가 생기지는 않는다. 확인된 오류는 명확히 설명하고, 확인하지 않은 환경은 조건으로 남긴다.

예시: 두 업로드 사이에 중단되면 파일은 새 버전이고 체크섬은 이전 버전일 수 있습니다. 읽는 쪽이 불일치를 오류로 처리하는지 확인하고, 이 중간 상태를 노출하지 않는 게시 계약이 필요합니다.

피드백의 길이와 댓글 수를 품질 지표로 삼지 않는다. 필요한 근거와 해결 조건을 충분히 전달하는지가 중요하다. 차단 여부와 우선순위는 [[Code-Review-Pn-Priority|리뷰 우선순위]]에 연결한다.

## 리뷰 판단을 훈련하는 후보

질문과 공유가 비난으로 바뀌지 않는 환경에서 시험할 후보이며, 효과가 검증된 보편 처방은 아니다.

- **판단 과정 설명**: 작성 이유와 가정을 먼저 묻는다.
- **아차 사고 공유**: 발견 조건을 공유하고 가상의 피해를 사실로 기록하지 않는다.
- **별도 모델 만들기**: 위험한 상태 전이를 코드와 독립적으로 표현해 비교한다.
- **전문가 관찰**: 의심한 단서와 확인 순서를 설명하게 한다.

훈련 효과는 이후 변경에서 같은 조건을 스스로 찾았는지 확인하는 방식으로 점검할 수 있다. 이 점검은 적용 제안이며, 위 방법들의 효과가 이미 입증됐다는 뜻은 아니다.

## Linus의 법칙과 검토의 다양성

Linus의 법칙은 충분한 베타 테스터와 공동 개발자가 참여하면 문제를 빠르게 특징짓고, 누군가는 해결 방법을 알아볼 가능성이 커진다는 개발 원칙이다. 검토 인원수만으로 무결함이 보장된다는 정리는 아니다.

핵심은 서로 다른 사용 환경, 지식과 분석 도구다. 문제를 처음 발견하는 사람과 원인을 이해해 고치는 사람도 다를 수 있다. 발견과 해결을 연결하려면 재현 조건, 관찰 결과와 수정 내용을 전달할 수 있어야 한다.

이를 팀 리뷰에 적용할 때는 같은 시각의 승인 수보다 놓친 조건을 볼 관점을 고른다. 예를 들어 API 계약, 동시성, 운영 환경을 나누어 검토할 수 있다. 이는 원칙에서 도출한 적용 예이며 리뷰어를 늘릴수록 품질이 비례해 오른다는 주장이 아니다.

## 자동화와 사람 검토의 역할

린터, 타입 검사와 테스트는 반복 가능한 오류를 검사한다. 사람 리뷰는 요구와 테스트가 빠뜨린 조건, 설계와 시스템의 상호작용을 확인한다. AI 리뷰의 결론도 코드, 환경과 재현 결과에 대조한다.

단일 결함 사례로 사람과 AI의 우열을 일반화하지 않는다. 검토를 줄일지는 변경 위험, 자동 검증 범위와 운영 결과로 판단한다.
