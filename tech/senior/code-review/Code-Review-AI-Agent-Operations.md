# 에이전트 시대 코드 리뷰 운영

AI가 작성한 변경도 요구사항, 호출부와 실패 조건에 대조해야 한다. 리뷰 운영에서는 오류 발견, 병합 승인, 배포 후 복구를 구분한다.

## 위험에 따른 검증

검토 강도는 변경의 영향과 복구 가능성으로 정한다. 자동 검사 결과와 사람이 판단할 조건을 함께 남긴다.

2026-10-15 공개된 Claude Code 팀 사례에는 다음 운영 방식이 있다. 조직의 사례이며 다른 팀의 기본 정책이나 효과 보장은 아니다.

- 자동 검사와 AI 리뷰에 보안 검토를 더하고, 위험 등급에 따라 사람 승인 수를 달리한다. 분류기가 변경을 읽어 등급을 정한다. 저위험(문서, 문구, 내부 전용 기능, 플래그 뒤에 기능을 더하기만 하는 변경)은 자동 리뷰와 보안 검사를 통과하면 사람 승인 없이, 일반 제품 변경과 캐싱, 자동 업데이트, 시스템 프롬프트 같은 민감 영역의 변경인 중위험은 한 명, 고위험은 두 명이 승인한다. 이런 가벼운 경로(글은 어느 등급까지인지 밝히지 않는다)는 주로 저장소를 소유한 팀인 저장소 신뢰 목록의 작성자에게만 열리고, 그 밖의 작성자는 두 번째 사람의 승인이 필요하다. 두 번째 분류기는 등급상 필요 없더라도 그 변경에 사람이 더 필요한지 다시 묻는다.
- 에이전트 승인은 필요한 사람 승인을 대신하지 않는다.
- 머지 큐에서 통합 결과를 검사하고 플래그, 단계적 배포와 롤백을 사용한다.
- 리뷰 시간 절감과 함께 되돌림, 장애를 관찰한다.
- 과거 사고 PR과 수정 기록을 리뷰어 평가에 쓰며, 문제가 없는 PR에서도 해로운 오탐을 점검한다.
- 리뷰 에이전트는 매일 밤 기존 코드도 검토해 오래된 버그를 찾는다.
- 반복 검토에는 상한을 둬 세 라운드가 지나면 리뷰어가 작성자에게 접근 방식을 다시 생각하라고 요청한다. 초기 검토 뒤에는 새 diff에 집중하며 같은 지적을 반복하지 않는다.
- 공개 당시 장애 지표에 따라 승인을 자동 강화하는 장치는 아직 없었다.

Thoughtworks Technology Radar Vol.35(2026-11)는 이런 방식을 risk-tiered human oversight로 Trial에 올렸다. 가장 위험하거나 되돌리기 어려운 변경은 사람이 직접 만들고, 중간 위험은 사람이 리뷰하며, 저위험은 CI를 거쳐 코딩 에이전트가 자동 병합하는 3단 분류다. 더 볼 변경은 상향 검토 구역(특정 파일과 디렉터리) 지정과 LLM 기반 변경 분류를 함께 써서 고르되, 후자는 틀릴 수 있다고 적는다. 반대로 사람이 실제로 판단할 수 없는 승인을 모든 변경에 반복하는 상태는 human-in-the-loop theater(Caution)로 경고한다. 그런 승인은 아무도 결정을 실제로 소유하지 않는 책임의 구멍(accountability sink)이 되므로, 사람이 판단할 수 없는 나머지 변경은 mutation testing, property-based testing, TLA+나 Quint 같은 형식 모델과 에이전트 보조 의미 검토로 다루라고 권한다.

## 사례의 공개 수치

위 사례 글이 밝힌 사내 수치를 2026-10-26 원문과 대조했다. 팀의 자체 보고이며 원자료는 공개되지 않았다.

- 글은 Claude가 Claude Code 자체 코드의 약 90%를 쓴다는 기존 발언을 전제로 리뷰 방식을 설명한다. Claude Code는 사내 모노레포와 분리된 별도 저장소다(모노레포의 병합 규모는 [[Server-Centric-Version-Control|서버 중심 버전 관리]]).
- 2026년 6월부터 9월까지 Claude Code 코드베이스의 병합 PR은 두 배 넘게 늘었고 되돌려야 했던 PR 비율은 상대적으로 40% 넘게 줄었다. 글은 되돌림 비율의 변화만 밝히고 되돌림 건수와 장애 지표는 공개하지 않았으므로, 이 값만으로 되돌림 건수 자체가 줄었는지는 판단할 수 없다.
- 2026-03-09 research preview 출시 글은 사내 거의 모든 PR에 Code Review를 돌리기 전에는 실질적인 리뷰 코멘트를 받은 PR이 16%였고 출시 시점에는 54%라고 밝혔다. 사례 글도 이 수치를 다시 인용했으며 비교 기간은 공개하지 않았다.
- CLI PR 하나는 밤사이 리뷰와 수정을 50회 넘게 반복한 뒤 작성자가 멈췄다. 리뷰어가 반복해서 지적한 코드를 git blame으로 보니 약 59%는 리뷰어의 첫 검토 때부터 있던 코드였다(그 PR 하나의 수치인지는 밝히지 않았다). 수렴 조치(convergence changes) 전후의 사내 PR을 비교하면 한 번의 리뷰와 수정으로 통과한 비율은 65%에서 78%로, 다섯 라운드 이상이 필요한 비율은 8.9%에서 1.5%로, 통과까지의 평균 리뷰 횟수는 2.08에서 1.32로 바뀌었다. 비교 기간은 밝히지 않았다.
- 작성자가 에이전트이면 사람은 몇 초 만에 넘길 사소한 지적도 커밋과 리뷰 한 라운드를 더 만든다. 그래서 리뷰어의 노이즈는 에이전트가 작성한 PR에서 비용이 더 크다.

## 제품의 발견과 저장소 승인 규칙

2026-10-18 공식 문서 기준, 관리형 Claude Code Review는 Team과 Enterprise의 GitHub 저장소를 대상으로 한다. 후보 발견을 검증하고 중복을 제거해 심각도별 코멘트를 남기지만, 자체적으로 PR을 승인하거나 차단하지 않는다. 발견이 없다는 결과도 무결함의 증거는 아니다.

Quick, Standard, Deep은 검토 강도이며 Standard가 기본값이다. 조직의 데이터 보존과 암호화 설정 등에 따른 이용 제한은 도입 시 공식 문서에서 확인한다. 설정 상세는 [[Claude-Code-Operations|Claude Code 운영]]을 따른다.

## 승인 자동화의 자격은 검사로 판정한다

빠른 승인 경로는 작성자가 붙이는 라벨만으로 열지 않는다. 변경 범위, 작성자의 해당 서비스 경험, 자동 검사와 민감 경로의 제외 조건을 기계가 확인하고, 승인 대상 커밋이 바뀌면 다시 검사한다. 수치 임계값은 조직의 위험과 검증 능력에 맞춰 정한다.

Imprint의 2026-10-17 `small-change` 사례는 1,000줄 미만, AI 리뷰의 p1/p2 지적 없음, 영향받는 각 서비스에서 작성자의 과거 병합 10건 이상, 영향 서비스 수 제한과 공유 라이브러리 제외를 결합했다. 결제와 보안 같은 경로도 빠른 승인에서 제외한다. 승인 스킬은 승인하거나 건너뛰며 댓글을 중계하지 않고, PR 묶음을 따로 검토해 지식 공유와 반복 결함을 찾는다.

이전 2년의 엔지니어당 병합 4배와 리뷰 중앙값 33분에서 77분 증가는 이 방식을 도입한 배경이다. 이 정책의 효과가 아니다. 공개 당시 약 10%가 자격을 얻었고 장기 성과 판단은 이르다고 밝혔다. 사고 감소 수치도 이 정책의 인과 효과로 연결하지 않는다.

## 사람 리뷰 없이 병합하면 사고를 리뷰어의 검사 항목으로 되돌린다

2026-11-03 The Pragmatic Engineer에 실린 한 엔지니어의 에세이는 작은 스타트업(Tano)의 운영을 이렇게 설명한다. 작성자 개인의 기록이며, 수치는 본문 서술, 표 이미지와 대화형 차트(집계값)로 제시됐고 PR 단위 원자료는 공개되지 않았다.

- 모든 PR에 CI의 Claude Code GitHub Actions 리뷰가 돌고, 대부분은 그것이 유일한 리뷰다. 사람은 자기 코드와 새 팀원의 코드를 보고 숙련된 동료의 코드는 드물게 보며, 위험한 변경에는 더 강한 리뷰 에이전트를 따로 돌린다. 작성자는 입사 3주 뒤 자동 리뷰만으로 병합하는 데 익숙해졌고 경험에 따라 8주까지 걸린다고 적었다.
- 새로 드러난 실패 방식은 리뷰 에이전트에 추가한다. 약 25GB, 600만 행 테이블에 쓰기를 막는 마이그레이션이 적재를 멈추고 배포 시간 초과를 낸 뒤, 리뷰 에이전트는 가장 큰 테이블 목록을 갖고 그 테이블의 블로킹 마이그레이션을 허용하지 않는다.
- 같은 글에는 화폐의 보조 단위를 늘 100으로 가정해(바레인 디나르는 1,000필스) 보고 수치가 어긋나고 기존 통화 유틸리티도 무시한 사례, 두 번째 마이그레이션의 가드를 빠뜨려 일부 크리에이터에게 두 번 지급한 사례가 있다. 작성자는 중복 지급을 빠른 확장의 대가로 받아들였다고 적었다.

적용 제안: 자동 리뷰만으로 병합하는 경로를 열면 사고 기록을 리뷰어의 검사 항목이나 결정론적 검사로 바꾸는 루프를 함께 둔다([[AI-Native-Org#엔지니어만 알던 규칙을 자동 검사로 바꾼다|규칙의 자동 검사화]]). 다만 돈과 데이터처럼 되돌리기 어려운 경로는 사후 수정에 기대지 않고 아래 작은 팀 적용 예처럼 중복 실행 검사와 사람 판단을 남긴다. 같은 사례의 PR 수 증가와 새 병목은 [[AI-Work-Output-and-Employment#산출이 늘면 병목은 다음 단계로 옮겨 간다|산출 증가 뒤의 병목 이동]]에 있다.

## 직접 만든 다중 에이전트 리뷰어

LinkedIn 엔지니어링 블로그(2026-08-13)가 밝힌 사내 리뷰어 구성이다. 회사의 자체 보고이며 사용 모델과 필터 임계값은 공개하지 않았다.

- **방식 선택:** 모델 벤더의 호스팅 리뷰 제품을 평가했으나 같은 학습 편향을 공유하는 단일 모델, 계층 정책을 표현하지 못하는 규칙 파일, 카나리 배포와 장애 전환과 전체 관측이 불가능한 소비 전용 제품이라는 구조적 한계를 이유로 직접 만들었다.
- **독립 리뷰와 병합:** 오케스트레이터가 서로 다른 모델과 하네스 조합의 서브에이전트들에게 같은 diff를 나눠 주고, 각자는 다른 서브에이전트의 결과를 보지 않고 검토한다. 여러 서브에이전트가 겹쳐 낸 지적은 높은 신뢰로 올리고 중복을 합친다.
- **단독 지적의 검증:** 한 서브에이전트만 낸 지적은 먼저 유효성을 검증한 뒤 중요도를 따로 매긴다. 원문 예시에서는 그 지적을 놓쳤던 모델에 되돌려 실제 결함임을 확인했다. 검증에 실패하거나 관련성 점수가 낮은 지적은 필터 후보가 되고, 외형만의 지적, 뒤 커밋에서 이미 고친 지적, 저장소의 확립된 패턴과 어긋나는 지적은 게시 전에 억제한다.
- **계층 규칙:** 조직 전체 정책, 저장소 수준 규칙, 개별 상황 지침을 조합하는 3단 규칙을 쓴다(원문 예시에 전역 YAML 예외 처리 규칙이 있다). 규칙 파일 하나로는 계층 정책을 표현하지 못한다는 것이 직접 구축의 이유 중 하나다.
- **출시 전 평가:** 후보와 운영 버전을 블라인드 pairwise 방식의 LLM 심판으로 세 라운드 맞비교하고 위치를 바꿔 편향을 줄인다. 판정은 가중치를 둔 여섯 개 예/아니오 기준의 합이며, 합계에서 이기거나 비겨야 배포한다.
- **운영 지표:** 좋아요 반응 대신 LLM 평가기가 지적과 최종 병합 코드를 비교해 수용, 부분 수용, 미수용, 조치 불가로 분류한다. 7일 동안 1,727개 PR의 지적 5,230개 표본에서 합산 수용률은 63.9%였다. 부분 수용을 어떻게 셌는지는 밝히지 않았다. 범주별로는 동시성 버그 100%, 논리 오류 80%, 버그 수정 58.1%, 리팩터링 43.5%, 보안 40.6%였고 저장소별로는 0%에서 100%까지 흩어졌다. 이 범주별 수치의 측정 기간과 표본은 밝히지 않았다.
- **규모:** 한 주에 7,500개 넘는 저장소의 PR 4만 건 이상에 리뷰 7만 9천 건 이상을 돌리고 대부분 10분 안에 끝나 첫 사람 리뷰어보다 먼저 올라간다고 보고했다.
- **다음 계획:** diff 영역별 예측 위험을 보여 주는 위험 히트맵, 심각 장애(SEV0/SEV1)를 분석해 리뷰 규칙을 만드는 파이프라인, 수용률 하락을 특정 변경에 귀속하는 평가 루프를 밝혔다.

적용 제안: 수용률은 LLM 평가기의 판정이므로 평가기 자체의 오판을 표본으로 사람이 확인한다. 범주별 수용률 차이는 어떤 규칙을 끄고 어떤 프롬프트를 고칠지 정하는 재료로 쓰되, 보안처럼 수용률이 낮은 범주를 곧바로 끄지 않고 오탐인지 미조치인지부터 나눈다.

| 안내 문구 | 렌더링 결과와 링크 확인 | 의미나 고객 약속이 바뀌는지 |
| 인증과 결제 | 거부 경로, 재시도와 중복 실행 검사 | 권한 경계와 금전 영향 |
| 배포와 데이터 변경 | 적용 순서, 복구 절차와 실행 결과 | 복구 가능 범위와 중단 기준 |

1인 개발이라면 요청자가 위험 판단과 결과 책임을 맡는다. 두 사람이 필요한 고객의 승인 규칙은 자동 검토나 롤백으로 대체할 수 없다. 추가 검토자를 확보하거나 승인 전 배포를 보류한다.

리뷰어가 문제를 지적하면 재현 조건과 영향 경로부터 확인한다. 같은 유형의 결함은 연결된 호출부까지 찾되, 증거 없는 전면 수정으로 넓히지 않는다. 반복 검토가 멈추지 않으면 미해결 조건을 적고 사람이 접근 방식을 다시 판단한다.

## 지적 처리와 도입 점검

아래 항목은 위 Claude Code 팀 사례를 정리하고 관리형 Code Review와 GitHub 설정에 맞춘 적용 메모를 덧붙인 것이며, 작은 팀이나 1인 개발에서 골라 쓰자는 것은 이 문서의 적용 제안이다. 2026-10-25에 사례 글과 Code Review, GitHub 공식 문서에 다시 대조했으며, 다른 저장소에서 효과를 검증한 결과는 아니다.

- **지적 처리:** AI 리뷰 지적에 Important, Nit, Pre-existing 분류를 붙여 이번 변경이 만들지 않은 결함을 작성자 책임과 구분한다. 버그 리뷰와 보안 리뷰의 지적은 고치거나 이유를 적어 닫아야 머지한다. 관리형 Code Review는 PR을 승인하거나 차단하지 않으므로 이 머지 조건은 제품이 아니라 브랜치 보호의 대화 해결 요구(Require conversation resolution before merging) 같은 저장소 규칙으로 건다. 사람 리뷰의 블로킹 표시는 [[Code-Review-Pn-Priority|Pn 룰]]을 본다.
- **발견과 검증 분리:** 결함 후보를 찾는 에이전트와 지적마다 투표하는 검증 에이전트를 나눠 충분히 동의한 지적만 올린다. 스타일, 진단과 정리만 다루는 지적은 버리고, 이런 필터는 자기 PR에서 A/B 비교한 뒤 채택한다.
- **PR 전 검증:** 에이전트가 테스트, 빌드와 린터를 실행해 완료 주장 대신 출력을 보여 주고, 새 컨텍스트의 서브에이전트가 diff를 다시 검토한다. 자동 리뷰어가 같은 지적을 반복하면 스킬, 린트 규칙이나 지침 파일을 고쳐 원인에서 막는다.
- **승인 자리:** 이 팀은 내부 정책으로 에이전트에게 일을 시킨 사람을 직접 작성한 경우처럼 필요한 리뷰어 한 자리로 센다. GitHub에서는 PR 작성자가 자기 PR을 승인할 수 없으므로, 1인 저장소에서 본인이 연 PR은 이 정책에 따른 승인도, 필수 사람 승인도 GitHub에서 채울 수 없다. 이 정책은 앞 절의 두 사람 승인이 필요한 고객 규칙도 대신하지 않는다. 승인은 특정 커밋에 대한 것이므로 새 커밋이 올라오면 기존 승인을 해제한다.
- **사람에게 남길 결정:** 만들지 여부(방향, 취향, 범위), 위험 코드 검토(과금, 자동 업데이트, CI 워크플로), 다른 사람이 따라 할 구조 검토, 증거 읽기(테스트 출력, 실행한 명령, 스크린샷, 리뷰 지적), 누가 입력했든 배포된 변경의 결과 책임이다.
- **코드 익히기:** 코드의 한 부분을 이해해야 하면 그 부분의 설명서를 에이전트에게 요청한다. 몇 분이면 현재 코드 기준의 설명이 나오고, 사소한 diff를 읽기보다 곧 바꿀 모듈의 설명서에서 배울 것이 많다. 설명서는 아래 운영 점검처럼 코드와 대조한다.
- **측정:** PR당 사람 승인 수의 중앙값과 95퍼센타일, 사람 댓글 수, PR이 사람을 기다린 시간으로 사람 시간을 재고 되돌림과 장애 비율을 안전선으로 둔다. 되돌림과 장애 비율이 오르면 사람 시간을 아낀 것이 아니라 옮긴 것이다. 리뷰어의 프롬프트, 도구나 모델을 바꾸면 사고와 되돌림으로 만든 평가 세트로 다시 채점한다. 위 필터 A/B 비교와 이 재채점은 직접 구성한 리뷰어에 맞는 방식이다. 관리형 Code Review는 리뷰에 쓸 모델을 서비스가 고르고 관리자 설정에 모델 선택이 없으므로, 같은 평가 세트를 정기적으로 다시 돌리는 형태로 적용한다.

사례 글의 도입 점검표는 PR 전, 모든 PR, 승인, 머지와 이후라는 PR 단계로 항목을 묶었을 뿐 실행 순서를 정하지 않는다. 도입 과정에 순서를 둔 권고는 AI 리뷰어를 저장소 하나에서 몇 주 다듬은 뒤 넓히는 것과 위험 등급을 엄격하게 시작해 근거가 쌓이면 완화하는 것 두 가지다.

- **PR 전:** 에이전트가 직접 돌릴 수 있는 검사를 짧은 CLAUDE.md에 적고 포매터와 린터는 훅으로 실행한다([[Code-Review-Sustainability|도구 자동화]]). 반복되는 리뷰 지적은 REVIEW.md로 옮긴다(리뷰 방식별 반영 여부는 [[Claude-Code-Operations|Claude Code 운영]]).
- **모든 PR:** CI를 필수로 두고 PR 템플릿에 테스트 방법, 위험, 되돌리는 법을 넣는다([[Code-Review-Reviewer-Guide|PR 템플릿]]). AI 리뷰어는 저장소 하나에서 몇 주 동안 REVIEW.md를 다듬은 뒤 넓히고, 모든 리뷰 스레드가 해결돼야 머지하며 리뷰 횟수에 상한을 둔다.
- **승인:** 인증, 과금, CI와 릴리스 워크플로, 설치 프로그램 변경에는 CODEOWNERS와 브랜치 보호로 사람 승인을 늘 요구한다. 위험 등급은 작성자가 아니라 변경 내용으로 정하고 엄격하게 시작해 근거가 쌓이면 완화하며, 가벼운 경로는 저장소 신뢰 목록에 있는 작성자에게만 연다.
- **머지와 이후:** 머지 큐, 플래그, 단계적 배포와 롤백은 위험에 따른 검증 절의 운영 방식을, 평가 세트와 사람 시간 측정은 위 측정 항목을 따른다.

## 운영 점검

- 검토 시간과 장애 복구 시간을 함께 기록한다. 승인 수 감소만으로 생산성 향상을 판단하지 않는다.
- 지적이 실제 결함, 의도한 동작, 오탐 중 무엇이었는지 남긴다.
- 평가에는 과거 사고뿐 아니라 새 실패 유형과 정상 변경도 포함한다.
- 변경을 설명하는 AI 문서는 코드와 대조한다. 문서 생성 자체를 담당자의 이해로 계산하지 않는다.
