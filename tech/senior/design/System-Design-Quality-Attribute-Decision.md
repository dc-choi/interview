# 시스템 설계 품질 속성과 의사결정 증거

시스템 설계는 컴포넌트 목록을 그리는 일이 아니라, 서비스 목표를 **측정 가능한 품질 시나리오**로 바꾸고 가장 작은 설계 변경으로 달성하는 과정이다. 면접 답변의 전체 순서는 [[System-Design-Interview|시스템 설계 인터뷰 대응]], 개별 성능 수단은 [[성능&확장성(Performance&Scalability)|성능과 확장성]]에서 다룬다. 이 문서는 목표에서 선택과 검증까지 이어지는 판단 기록을 소유한다.

## 컴포넌트보다 목표가 먼저다

캐시, 큐, 샤딩과 서비스 분리는 목적이 아니라 후보 수단이다. 요구사항을 듣자마자 구성요소부터 추가하면 다음을 설명하지 못한다.

- 어떤 사용자 행동과 실패를 보호하는가
- 어느 부하와 비용 범위에서 목표를 만족해야 하는가
- 무엇을 얻는 대신 어떤 복잡성과 위험을 받아들이는가
- 도입 뒤 목표 달성을 무엇으로 증명하는가

먼저 핵심 기능 하나와 우선 품질 속성 하나를 고른다. 나머지는 non-goal이나 후속 단계로 명시한다.

## 품질 시나리오로 요구사항 구체화

좋다, 빠르다, 안정적이다 같은 표현은 검증할 수 없다. 다음 다섯 필드를 채우면 설계 입력으로 사용할 수 있다.

| 필드 | 확인 질문 |
|---|---|
| 맥락 | 정상, 피크, 의존성 장애 중 언제인가 |
| 자극 | 어떤 요청, 부하 증가, 데이터 증가나 실패가 발생하는가 |
| 대상 | 어떤 사용자 기능과 경로를 보호하는가 |
| 기대 반응 | 성공, 거절, 지연 허용, 축소 제공이나 복구 중 무엇인가 |
| 측정 기준 | 어떤 관찰 구간과 부하에서 어느 수치를 만족해야 하는가 |

예를 들어 빠른 피드가 아니라 **피크 읽기 부하에서 피드 조회의 p95 지연이 목표 안에 있고, 캐시 장애 때는 제한된 결과로 축소 제공한다**처럼 적는다. 숫자는 외워 넣지 않고 제품 기대, 현재 기준선, 비용 한도와 실험 결과로 정한다.

## 네 품질 속성을 구분한다

| 속성 | 설계 질문 | 대표 증거 |
|---|---|---|
| 신뢰성 | 같은 입력과 실패 조건에서 기대한 결과와 데이터 불변조건을 지키는가 | 오류율, 불변조건 위반, 중복 처리, 복구 후 검증 |
| 성능 | 정해진 자원과 부하에서 요청을 충분히 빠르게 처리하는가 | 지연 백분위, 처리량, 큐 대기, CPU와 메모리 |
| 가용성 | 핵심 기능을 필요할 때 성공적으로 제공하거나 합의한 축소 모드로 유지하는가 | 성공 제공 시간, 장애 감지와 복구 시간, 축소 모드 성공률 |
| 확장성 | 요청과 데이터가 증가해도 목표 품질을 유지하도록 자원을 늘리거나 구조를 나눌 수 있는가 | 안전 처리량, 부하별 지연 곡선, 확장 효율, 파티션 편향 |

네 속성은 독립 체크박스가 아니다. 재시도는 일시 오류를 줄일 수 있지만 지연과 부하를 키울 수 있고, 캐시는 읽기 성능을 높이지만 최신성 계약과 장애 경로를 추가한다. 우선순위와 허용할 대가를 함께 적는다.

## 목표에서 검증까지의 결정 루프

1. **사용자 목표**: 가장 중요한 사용 흐름과 실패 시 영향을 정한다.
2. **워크로드**: 읽기와 쓰기 비율, 피크와 평균, fan-out, hot key, 데이터 증가와 의존성 실패를 가정한다.
3. **품질 시나리오**: 우선 속성, 측정 기준, non-goal과 비용 한도를 합의한다.
4. **기준선**: 같은 조건에서 현재 지연, 처리량, 오류, 자원 사용과 병목을 측정한다.
5. **선택지 비교**: 현 구조 유지까지 포함해 대안, 이득, 대가와 실패 방식을 적는다.
6. **최소 변경 검증**: 가장 작은 후보를 적용하고 동일한 부하와 환경에서 다시 측정한다.
7. **운영 계약**: 알림, 축소 모드, 롤백 조건과 설계를 다시 볼 임계값을 남긴다.

이 루프는 처음부터 큰 구조를 예측하는 대신, 새 증거가 생길 때 설계를 발전시킨다. 모놀리스와 MSA도 출발점과 종착점이 아니라 제약에 따른 선택지다.

## 수단을 고를 때 남길 근거

| 후보 수단 | 도움이 되는 조건 | 함께 생기는 대가 | 확인할 증거 |
|---|---|---|---|
| 캐시 | 반복 읽기와 원본 조회 비용이 큼 | 최신성, 무효화, miss 폭주 | hit rate, 원본 호출, 지연 분포 |
| 요청 합치기 | 같은 키의 동시 요청이 겹침 | 느린 선행 요청 공유, 프로세스 범위 한계 | 키별 동시 요청과 실제 원본 호출 수 |
| 비동기 큐 | 접수와 완료를 분리할 수 있음 | 중복, 순서, 재시도와 backlog | 접수 지연, 완료 지연, backlog 증가율 |
| 복제와 파티셔닝 | 읽기나 데이터 소유권을 나눌 수 있음 | 복제 지연, 재분배, hot partition | 복제 지연, shard별 부하와 오류 편향 |
| 서비스 분리 | 확장, 배포나 장애 경계를 독립시켜야 함 | 네트워크, 직렬화, 분산 운영 비용 | 독립 확장 필요량, 호출 수, 장애 격리 결과 |

동일 키 요청 합치기와 캐시 miss 폭주는 [[Cache-Stampede|Cache Stampede 방지]], 접수와 완료 지표의 차이는 [[Cache-vs-Queue|캐시와 큐]]를 따른다.

## 설계 결과의 최소 증거 묶음

- **재현 조건**: 데이터 크기, 요청 분포, 동시성, 실행 환경과 테스트 시간
- **전후 비교**: 같은 조건의 기준선과 변경 후 지연 분포, 처리량, 오류와 자원 사용
- **실패 경계**: 어느 부하나 장애에서 목표를 벗어나며 시스템이 어떻게 축소되는지
- **결정 이유**: 선택한 안, 기각한 대안, 받아들인 트레이드오프
- **재검토 조건**: 트래픽, 데이터, 비용, 팀 구조가 어느 수준이 되면 다시 설계할지

면접에서는 이 묶음을 **목표와 제약 → 기준선과 병목 → 대안과 선택 → 검증 결과 → 남은 한계** 순서로 설명한다. 실제 측정하지 않은 수치는 가정으로 표시하고, 팀 결과와 본인 판단 범위를 분리한다.
