# 운영 및 생산성 효율화 (Operational Efficiency)

나 혼자 잘하는 것을 넘어 **팀 전체가 잘하게 만드는 것**이 시니어급 개발자의 핵심 성과이다. 이 문서는 그 성과를 어떤 축으로 재고 서술할지에 대한 프레임이고 실측 기록이 아니다. 아래 수치는 표현 형식을 보여주는 플레이스홀더이므로 N, M 자리에 실제 측정값을 넣어 쓴다.

## 운영 효율 성과의 측정 축

### 1. 반복 작업 시간

- **재는 법**: 단위 작업 소요 시간과 기간 내 실제 반복 횟수로 총량을 구한다. 여러 사람이 수행했다면 각자의 실제 기록을 합산하고, 추정 시간에 전체 인원수를 일괄 곱하지 않는다. 개선 전후를 같은 방식으로 잡아야 비교가 성립한다.
- **대표 지표**: 월 반복 작업 시간, 전체 업무 중 반복 운영 작업이 차지하는 비율, 수작업 단계 수.
- **예시 표기**: 릴리즈 전 수동 점검 N단계를 자동화해 릴리즈당 M분, 월 기준 N시간을 줄였다.
- **주의**: 추정으로 계산한 절감 시간은 추정이라고 밝힌다. 절감된 시간이 실제로 다른 일에 쓰였는지는 별도 확인 대상이다.

### 2. 온콜 부담

- **재는 법**: 온콜 로테이션 한 주기를 단위로 호출 로그를 집계한다. 체감이 아니라 기록으로 잡는다.
- **대표 지표**: 주당 페이지 수, 업무 시간 외 호출 비율, 실제 조치가 필요했던 알람의 비율, 특정 인원에게 쏠린 정도.
- **예시 표기**: 알람 규칙 정리 후 주당 야간 호출이 N건에서 M건으로 줄었고, 조치가 필요한 알람의 비율은 N%에서 M%로 올랐다.
- **주의**: 호출 건수만 목표로 삼으면 알람을 끄는 방향으로 굽는다. 놓친 장애가 없었는지 함께 본다 ([[Alert-Fatigue|알람 피로 방지]]).

### 3. 리드타임

- **재는 법**: 시작점과 끝점을 먼저 정의한다. 커밋에서 배포까지인지, 요구사항 접수에서 릴리즈까지인지에 따라 값도 의미도 달라진다.
- **대표 지표**: 변경 리드타임, 리뷰 대기 시간, 환경 셋업 시간, 배포 빈도.
- **예시 표기**: 파이프라인 개선 후 커밋에서 배포까지 걸린 시간의 중간값이 N시간에서 M시간으로 줄었다.
- **주의**: 총합만 보면 병목을 못 찾는다. 대기 시간이 어느 구간에 쌓이는지 나눠 봐야 개선 지점이 보인다.

### 4. 개발자 경험(DX)

- **재는 법**: 개선 대상 작업(로컬 환경 구축, boilerplate 작성, 신규 입사자 온보딩)의 소요 시간을 개선 전후 같은 기준으로 잰다. 체감 개선은 설문으로 보조하되 시간 지표와 함께 둔다.
- **대표 지표**: 로컬 환경 구축 시간, 신규 엔드포인트 추가 소요 시간, 신규 입사자가 첫 PR을 올리기까지 걸린 시간.
- **예시 표기**: 로컬 환경을 Docker Compose 하나로 묶어 셋업이 N시간에서 M분으로 줄었다. 커스텀 데코레이터/인터셉터로 boilerplate를 자동화해 엔드포인트 추가가 N분에서 M분이 됐다.
- **주의**: 절감 시간을 인원수로 곱해 부풀리기 쉽다. 실제로 반복된 횟수 기반으로만 환산한다.

### 5. 문서화와 표준화

- **재는 법**: 문서와 표준의 부재가 만들던 비용(반복 질문, 명세 불일치 재작업, 스타일 논쟁 리뷰)을 빈도로 잡고 전후를 비교한다.
- **대표 지표**: API 명세 관련 문의와 불일치 건수, 컨벤션과 스타일 지적 리뷰 코멘트 수, 같은 질문이 반복된 횟수.
- **예시 표기**: API 명세서(Swagger)를 코드에서 자동 생성해 명세 불일치 문의가 월 N건에서 M건으로 줄었다. 코딩 컨벤션 정립 후 스타일 지적 코멘트가 N% 줄어 리뷰가 설계 논의에 집중됐다.
- **주의**: 문서의 양은 성과가 아니다. 찾아 쓰이는지(조회 수, 질문 감소)로 잰다.

다섯 축 모두 절감 자체가 목적이 아니다. 확보한 여유가 어디로 갔는지가 성과 서술의 마지막 칸이다 ([[Strategic-Slack|의도적 여유]]).
