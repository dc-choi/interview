# 기술적 탁월함과 안정성 (Technical Reliability)

신뢰성 성과를 어떤 지표로 재고 어떻게 서술할지에 대한 프레임 문서다. 아래 수치는 실측값이 아니라 표현 형식을 보여주는 플레이스홀더이므로 N, M, A, B 자리에 실제 측정값을 넣어 쓴다.

## 신뢰성 성과의 측정 지표

| 지표 | 무엇을 재나 | 주의 |
|---|---|---|
| **에러율** | 전체 요청 대비 실패 비율. 사용자 영향의 1차 신호 | 전체 평균은 소수 핵심 API의 악화를 가린다. 엔드포인트와 사용자 세그먼트로 나눠 본다 |
| **MTTR** | 감지에서 복구까지 걸린 시간 | 평균은 긴 장애 한 건에 끌려간다. 중간값과 분포를 함께 본다. 감지 시간과 복구 시간을 나누면 개선 지점이 드러난다 |
| **장애 빈도, 재발률** | 일정 기간의 사용자 영향 장애 건수와 같은 원인의 재발 비율 | 재발률이 안 떨어지면 복구만 빨라진 것이다 |
| **SLO 준수율, 에러 버짓 소진율** | 정한 목표를 지킨 기간의 비율과 버짓을 태운 속도 | SLO가 없으면 준수율도 없다. 사용자 대면 SLI와 목표를 먼저 합의한다 ([[SLI-SLO]]) |
| **변경 실패율** | 배포 중 롤백이나 핫픽스를 유발한 비율 | 배포 빈도와 함께 봐야 한다. 배포를 줄여서 낮춘 실패율은 개선이 아니다 |

지표는 하나만 쓰지 않는다. 하나를 목표로 걸면 그 지표만 좋아지는 방향으로 행동이 굽는다 ([[Software-Productivity-Measurement|생산성 측정의 함정]]).

## 전후 비교 서술 구조

신뢰성 성과는 개선 후 숫자 하나가 아니라 비교 가능한 두 구간으로 말한다.

1. **기준선(before)**: 개입 전에 같은 지표를 어떤 기간, 어떤 트래픽 조건에서 측정했는가.
2. **개입**: 무엇을 언제 바꿨는가. 여러 변경을 동시에 넣었다면 그 사실을 밝힌다.
3. **관측 창(after)**: 전후 기간의 길이와 조건을 맞춘다. 이벤트 트래픽이 낀 주와 평시 주를 비교하면 결론이 무너진다.
4. **결과**: 지표별 전후 값과 변화폭.
5. **교란 요인**: 같은 기간의 트래픽 변화, 계절성, 배포량 변화, 동시에 진행된 다른 개선.
6. **유지 여부**: 개선이 N주 뒤에도 유지되는가. 초기 며칠만 좋아진 것은 아직 성과가 아니다.

예시 표기: 배포 후 N주 동안 5xx 비율이 A%에서 B%로, MTTR 중간값이 N분에서 M분으로 움직였고 같은 기간 요청량은 비슷했다.

## 고가용성 확보 (Scalability)
- 트래픽 N배 증가 상황에서도 시스템 안정 유지
- Redis 캐싱, Message Queue(BullMQ, Kafka) 도입으로 안정적 처리
- 예시 표기: 사용자가 N배 늘어도 인프라 비용 증가폭은 M배 이내로 억제했다

## 기술 부채 해결
- 스파게티 코드 → Clean Architecture / DDD 적용 리팩토링
- 기능 수정 시 버그 발생률 감소
- 예시 표기: 유지보수 비용이 줄어 신규 기능 개발 리드타임이 N% 단축되었다

## 테스트 자동화
- 테스트 커버리지 향상 → 배포 시 Regression 장애 감소
- 커버리지 숫자 자체를 목표로 걸면 의미 없는 테스트가 늘어난다. 변경 실패율과 재발률로 효과를 확인한다
