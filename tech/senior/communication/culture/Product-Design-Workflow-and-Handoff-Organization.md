# 프로덕트 조직 구조와 업무 루프

프로덕트 조직은 조직 형태, 업무 프로세스, 오너십 세 축으로 볼 수 있다. 업무 프로세스는 조직마다 비슷해 보여도 조직의 규모와 형태에 강하게 묶여 있어서, 같은 프로세스를 들여와도 조직 형태가 맞지 않으면 돌지 않는다. 핸드오프 계약과 SSOT는 상위 문서인 [[Product-Design-Workflow-and-Handoff|프로덕트 디자인 워크플로와 개발 핸드오프]]가 다룬다.

## 마찰은 어느 체계의 빈틈에서 오는가

협업 마찰은 개인 역량보다 체계의 빈틈에서 반복된다. 한 실무 분류는 업무 환경의 체계를 조직, 업무 프로세스, 커뮤니케이션, 운영관리, 자산관리, 문화, 개선의 일곱 가지로 나누고, 이 가운데 조직, 업무 프로세스, 커뮤니케이션, 운영관리 중 하나만 부실해도 구성원의 고통과 불만족이 커진다고 본다. 표준 프레임워크가 아니라 경험적 분류이므로 진단 체크리스트로 쓴다. 아래 신호와 볼 곳의 대응은 정리를 위한 제안이다.

| 체계 | 빈틈의 신호 | 볼 곳 |
|---|---|---|
| 조직 | 결정권자, metric 소유, 분석 주체가 불분명 | 아래 조직 형태와 업무 루프 |
| 업무 프로세스 | 단계마다 산출물과 진입 조건이 사람마다 다름 | [[Product-Design-Workflow-and-Handoff-Stages|디자인 단계별 산출물]] |
| 커뮤니케이션 | 같은 질문이 반복되고 최신본을 되물음 | 상위 문서의 SSOT와 Ready for development 계약 |
| 운영관리, 자산관리 | file과 component의 최신 상태를 찾기 어려움 | 상위 문서의 Figma file 구성과 design system |
| 문화, 개선 | feedback이 무겁고 회고 action이 사라짐 | 상위 문서의 Review와 rollout |

디자이너는 일의 순서상 기획과 개발 사이에 끼어 앞단의 모호함과 뒷단의 질문을 함께 받는다. 체계 정비의 중심에 서기 쉽고 디자인 쪽에 hub가 생기는 경우가 많은 이유다. 다만 체계를 한 직군이 혼자 책임진다는 뜻은 아니다.

규모가 큰 회사라고 구조가 완벽하지 않고, 구성원, 목표와 상황이 바뀌면 구조도 다시 흔들린다. 구조가 없다고 느끼는 것은 비정상이 아니라 개선할 지점이 보인다는 신호이며, 구조에 아무 문제가 없다고 느끼는 상태가 오히려 점검 대상이다. 빈틈을 인지했다면 관찰한 비용과 개선안을 함께 내는 행동으로 옮긴다.

## 조직 형태는 숫자로 결정하지 않는다

기능 조직은 전문성 표준화와 사람의 성장에 유리하고, cross-functional squad는 목표별 의사결정과 feedback을 가까이 둔다. 회사 인원 수만으로 어느 구조가 맞는다고 정할 수 없다.

- 제품 영역 사이 의존성과 공유 platform의 비중
- 목표와 metric을 독립적으로 소유할 수 있는 정도
- 출시 뒤 결과를 직접 분석할 역량과 데이터 접근이 있는 정도
- designer, engineer, analyst 같은 희소 역량의 분포
- 일관된 design system과 engineering standard를 유지할 장치
- 팀을 자주 재편할 때 생기는 context 손실

matrix나 chapter/guild를 섞는 hybrid 구조도 가능하다. 여러 squad를 공통 OKR 아래 묶고 squad 사이의 우선순위 충돌을 OKR로 조율하는 형태도 hybrid의 하나이며, 조직이 커질수록 더 맞을 수 있다. 보고선 이름이 아니라 **결정권, 의존성 조정, 품질 기준과 성과 책임이 명확한가**가 중요하다.

## 직군 통합은 인계 대기를 줄이는 작은 실험으로 시작한다

프론트엔드와 백엔드를 합칠지는 같은 사용자 기능이 서로 다른 작업 큐와 일정 사이에서 얼마나 기다리는지로 판단한다. 직군이 둘이라는 이유만으로 통합할 필요는 없다. 팀 전체가 필요한 역량을 갖추는 것과 모든 개인이 모든 영역의 전문가가 되는 것도 구분한다. Scrum Guide의 cross-functional은 팀이 매 Sprint에 가치를 만드는 데 필요한 역량을 갖춘다는 의미다.

### 역할을 넓힐 때 필요한 지원

다음은 직군 통합의 경험을 다른 팀에 적용할 때 대조할 조건이다. 특정 조직의 성공을 보장하는 절차는 아니다.

- 기존 제품 과제에서 이어지는 작은 화면 또는 서버 작업부터 맡고, 학습과 검토 시간을 계획에 포함한다.
- 낯선 영역의 담당자가 기능을 끝까지 진행하더라도 전문 동료의 설계 검토와 코드 검토를 유지한다.
- 운영 책임을 넓힐 때는 서비스 구조, 첫 확인 지점과 대응 순서를 담은 런북, 현재 상태를 보여주는 대시보드를 함께 제공한다.
- 먼저 수행한 사람이 발견한 제약과 검증 방법을 기록해 다음 담당자가 같은 탐색을 반복하지 않게 한다.

당근 광고주 플랫폼팀의 공개 발표에서는 작은 반대 직군 과제, 문서와 동료 검토를 기반으로 역할을 넓혔다. 완료량은 크게 떨어지지 않았다는 회고와 함께 계획하지 않은 작업, 서로의 진행 상황 파악 저하, 전문성 심화와 지식 편중의 위험도 남겼다. 한 팀의 경험이며 통합이나 AI 도구의 독립적인 인과 효과를 입증한 결과는 아니다.

### 완료량과 예측 가능성을 따로 본다

팀 구성과 추정 기준이 달라졌다면 스토리 포인트 합계만으로 통합 전후 생산성이 같다고 판단하지 않는다. 다음은 통합 실험을 평가하기 위한 점검 항목이다.

| 확인할 것 | 구분할 관측 |
|---|---|
| 인계 병목 | 담당자가 실제로 작업한 시간과 다른 담당자를 기다린 시간 |
| 계획 신뢰도 | 처음 계획한 작업, 도중 유입된 작업, 목표 달성 여부 |
| 전달 품질 | 변경 전달 속도와 배포 실패, 복구 부담 |
| 협업 지속성 | 동료의 진행 상황 파악, 검토 가능한 사람의 수와 특정인 의존 |

DORA의 전달 성과 지표도 처리량과 불안정성을 함께 보며, 맥락이 다른 서비스의 단순 비교를 경계한다. 조직 통합의 효과를 볼 때도 완료량 하나에 결론을 맡기지 않는다. 측정의 한계는 [[Software-Productivity-Measurement|소프트웨어 생산성 측정]]을 참고한다.

## 업무 루프와 조직 형태의 결합

이상적인 업무 루프는 목표 설정, 디자인, 개발, 분석의 네 단계이고, 분석 결과가 다음 목표 설정으로 돌아가야 iteration이 성립한다.

| 형태 | 맞는 루프 | 이유 |
|---|---|---|
| 목적 조직(squad) | 목표 설정, 디자인, 개발, 분석 | 같은 목표와 metric을 계속 맡으므로 분석을 다음 목표로 되돌릴 수 있다 |
| 기능 조직 | 목표 설정, 디자인, 개발 | 프로젝트 단위로 모였다 흩어져 출시 뒤 분석을 이어받을 주체가 약하다 |

실패 양상은 분석할 수 없는 squad다. 계측, 데이터 접근과 분석 인력이 없는 상태에서 squad로 운영하면 출시 뒤 무엇이 효과였는지 알 수 없어 iteration을 돌리지 못한다. 현실에서 흔한 상태지만 방향은 분석 역량을 먼저 갖추거나 squad 운영을 재고하는 것이다. 퍼널과 코호트 분석은 [[Data-Driven-Decision|데이터 기반 의사결정]]을 따른다.

## 오너십은 R&R이다

오너십은 역할과 책임(R&R)의 문제다. 결과물마다 최종 결정권자는 있지만([[Product-Design-Workflow-and-Handoff#결정권은 결과물마다 정한다|결과물별 결정권]]), 직군과 무관하게 모든 구성원이 루프의 모든 단계에 owner로 참여한다. product designer의 오너십은 화면에 그치지 않고 목표 설정, 개발 중 trade-off 판단, 출시 뒤 분석까지 이어진다.

## 디자인 엔지니어: 디자인과 구현 사이의 문제를 소유한다

디자인 엔지니어는 디자인 의도를 실제 동작으로 연결하고, 반복되는 UI/UX 문제를 재사용 가능한 기준으로 만드는 역할로 설계할 수 있다. 직함의 범위는 조직마다 다르므로 아래를 모든 회사의 공통 직무 정의로 보지는 않는다. 당근의 공개 직무 설명을 2026-10-08에 확인해 정리한 역할 범위다.

| 책임 영역 | 결과물의 예 |
|---|---|
| 경험의 기준 정의 | 모션, 입력 방식, 접근성과 성능을 고려한 상호작용 기준 |
| 디자인과 구현 연결 | 실제 화면에서 확인할 수 있는 컴포넌트와 프로토타입 |
| 반복 문제의 시스템화 | 여러 제품에서 재사용하는 토큰, 패턴과 프리미티브 |
| 채택 지원 | 사용 가이드, 디자인 원칙, 동료와의 설계 검토와 개선 |

역할을 도입할 때는 디자인과 개발을 모두 할 수 있는지보다 어느 경계의 반복 문제를 끝까지 맡길지 먼저 정한다. 다음은 역할 배분을 위한 적용 체크리스트다.

- 정적인 화면만으로 판단하기 어려운 동작은 프로토타입으로 확인하고, 탐색 결과와 출시 가능한 구현을 구분한다.
- 한 화면의 개선을 공통 패턴으로 옮길 때는 실제로 반복되는 요구인지 확인한다.
- 역할의 범위가 넓어져도 디자인 검토, 구현 품질과 출시의 최종 결정권자를 명시한다. 한 직함이 기존 책임 구분을 자동으로 대체하지는 않는다.

## 조직 규모에 대한 경험 관찰 (미검증)

아래는 여러 산업과 규모의 조직을 거친 한 실무자의 관찰이며 통계로 확인하지 않았다. 기준 인원이 전사인지 제품 조직인지도 분명하지 않다. 특정 인원 수가 기능 조직과 squad의 정답을 결정하지 않으므로 회사 평가나 역질문에서 비교 기준으로만 쓴다.

- 제품 조직 인원은 전체의 약 1/3, product designer는 제품 조직의 약 1/10로 맞춰지는 경향이 있었다는 관찰.
- 제품 조직이 커질수록 기능 조직에서 squad로 옮기려는 시도가 생겼다는 관찰.
- 100명 이하에서는 기능 조직이 맞았고, 100~200명은 둘 다 가능하지만 장단점이 뚜렷한 과도기였으며, 200명부터는 기능 조직이 거의 동작하기 어렵고 squad가 잘 돌았다는 관찰.

규모가 커질수록 의존성과 조정 비용이 늘어 목적 조직의 이점이 커진다는 해석과 어긋나지 않지만, 위 판단 요소를 대신하지 않는다.

## 개인이 할 일

- 자기 조직의 규모, 형태와 업무 루프가 어긋나는 지점을 파악한다.
- 구조가 맞지 않으면 관찰한 비용(반복 질문, 재작업, 분석 부재)과 함께 의견을 낸다.
- 자신에게 맞는 조직 형태를 알고 지원할 때 역질문으로 확인한다. 목적 조직이라면 출시 뒤 지표 분석을 squad가 직접 하는지, 분석 인력과 데이터 접근이 있는지, squad 사이의 우선순위를 무엇으로 조율하는지 묻는다.

## 면접 체크포인트

- 조직 구조는 규모보다 dependency, decision latency와 전문성 공유로 판단한다.
- 분석 단계가 빠진 squad는 iteration을 돌릴 수 없다는 점을 조직 형태 판단에 넣는다.
