# AI 코딩 에이전트 사용량 텔레메트리

여러 코딩 에이전트의 로컬 세션 기록을 공통 지표로 모으면 도구별 활동량과 추세를 볼 수 있다. 그러나 토큰 수는 **활동량**이지 생산성, 코드 품질이나 비용이 아니다. 측정 시스템은 수집 파이프라인과 함께 지표의 의미, 중복 제거, 개인정보 경계와 보존 정책을 계약으로 가져야 한다.

## 목적과 비목적

| 질문 | 필요한 데이터 | 토큰 집계만으로 답할 수 있나 |
|---|---|---|
| 언제 어떤 도구와 모델을 많이 썼나 | 날짜, 공급자, 모델, 토큰 종류 | 가능 |
| 비용이 얼마인가 | 위 데이터 + 시점별 단가와 과금 규칙 | 불가능 |
| 작업이 빨라졌나 | 작업 유형, 소요 시간, 승인과 재작업 | 불가능 |
| 코드 품질이 좋아졌나 | 테스트, 리뷰, 결함과 롤백 | 불가능 |

공개 배지나 순위는 참여 동기를 만들 수 있지만 Goodhart's Law의 대상이 되기 쉽다. 총 토큰을 목표로 삼지 않고 비용, 완료 시간, 검증 통과율과 재작업률을 별도 축으로 본다.

## 수집 파이프라인

```text
로컬 transcript
  -> 공급자별 parser와 중복 제거
  -> 공통 토큰 스키마
  -> 날짜와 모델별 집계
  -> 인증된 동기화
  -> 멱등 upsert
  -> 대시보드 또는 공개 배지
```

### 공급자 어댑터가 보존할 의미

공통 레코드는 최소한 `date`, `provider`, `model`, `input`, `output`, `cache_read`, `cache_create`를 구분한다. 공급자마다 누적값과 증분값, reasoning token 포함 여부, 캐시 토큰의 과금 의미가 다르므로 파서에서 성급히 하나의 total로 뭉치지 않는다.

- 스트리밍 응답은 같은 응답의 누적 snapshot이 반복될 수 있다.
- 재개한 세션과 fork된 자식은 부모 기록을 replay할 수 있다.
- 같은 날짜를 다시 읽더라도 결과가 늘어나지 않게 안정적인 중복 키가 필요하다.
- 알 수 없는 모델이나 손상된 레코드를 건너뛰면 누락 횟수와 원인을 관측해야 한다.
- transcript는 제품의 내부 저장 형식이므로 fixture와 schema drift 경고를 둔다.

파서가 출력하는 정규화 레코드와 화면에서 보여 줄 파생 지표를 분리한다. 그래야 캐시율이나 총량의 정의가 바뀌어도 원래 집계를 다시 해석할 수 있다.

## 동기화와 멱등성

클라이언트가 날짜와 모델별 최신 집계값을 보내고 서버가 `(account, device, date, model)` 같은 키로 교체하면 재시도에 강한 멱등 동기화가 된다. 매번 증가량을 더하는 API는 응답 유실 뒤 재시도에서 이중 집계되기 쉽다.

운영 시 다음 경계를 확인한다.

- cursor가 마지막 파일 위치인지 날짜인지에 따라 늦게 복구된 과거 기록의 처리 방식이 달라진다.
- 설정 삭제로 device ID가 바뀌면 같은 전체 이력이 새 장치 사용량으로 다시 올라갈 수 있다.
- 여러 장치가 같은 transcript를 읽으면 계정 합계가 중복될 수 있다.
- 클라이언트 날짜와 서버 시간대가 다르면 일별 heatmap과 streak 경계가 달라진다.
- 부분 실패 뒤에는 전체 재처리보다 마지막 확정 checkpoint부터 재개한다.

## 최소 전송과 실제 신뢰 경계

업로드 payload에 토큰 집계만 있다는 사실과 로컬 파일을 읽지 않는다는 주장은 다르다. 파서는 토큰 필드를 찾기 위해 프롬프트, 도구 출력과 경로가 함께 들어 있을 수 있는 transcript 파일을 열고 JSON 레코드를 해석한다. 따라서 다음 네 경계를 따로 검토한다.

1. **로컬 접근**: 어떤 파일을 읽으며 하위 프로세스나 로그에 원문을 남기는가
2. **네트워크 전송**: payload, header와 오류 보고에 어떤 필드가 포함되는가
3. **서버 보존**: 집계 외에 계정, IP, User-Agent와 감사 로그를 얼마나 보존하는가
4. **공개 노출**: 사용자명만 알면 배지나 통계를 조회할 수 있는가

device UUID는 계정과 연결되면 익명값이 아니라 가명 식별자다. 인증 토큰은 파일 권한뿐 아니라 만료, 개별 폐기와 secret 회전 범위를 확인한다. Reset이라는 이름도 사용량 행만 지우는지 계정과 감사 로그까지 지우는지 구현으로 확인한다.

## 보존 기간의 역설

집계 누락을 줄이려고 transcript 보존 기간을 크게 늘리면 측정 완전성은 좋아지지만 프롬프트, 코드, 경로와 도구 출력의 로컬 노출 기간과 디스크 사용량도 늘어난다. 텔레메트리의 요구가 원본 보존 정책을 역으로 지배하게 두지 않는다.

- 원본과 집계 데이터의 보존 기간을 분리한다.
- 필요한 경우 집계 후 원본을 정리하거나 일회성 실행 모드를 쓴다.
- 삭제, archive와 Reset의 의미를 각각 문서화한다.
- 백업과 진단 자료에도 같은 민감도 규칙을 적용한다.

## TokenPhage 구현에서 배우는 점

TokenPhage는 Claude Code, Codex와 opencode의 로컬 기록을 공급자별로 파싱해 날짜와 모델별 사용량을 동기화하고 GitHub용 공개 SVG 배지로 표현한다. 전송 레코드는 토큰 집계 중심으로 최소화되어 있지만, 구현 검토에서는 다음 경계도 드러난다.

- 공급자별 streaming, 누적값과 fork replay를 서로 다른 방식으로 중복 제거한다.
- 사용량 upsert는 같은 장치와 날짜, 모델의 최신 집계로 교체한다.
- 공개 배지는 활동량을 보여 주며 비용과 품질을 계산하지 않는다.
- 서버 감사 로그와 Reset 범위는 배지 설명과 별도로 확인해야 한다.
- 매우 긴 로컬 transcript 보존 제안은 집계 완전성과 개인정보 보호의 tradeoff다.

이 사례의 재사용 포인트는 배지 자체보다 **공급자별 원본 의미 보존, replay-safe 집계, 최소 전송과 검증 가능한 삭제 경계**다.

## 도입 체크리스트

- [ ] 지표를 활동량, 비용, 속도와 품질로 분리했는가
- [ ] 공급자별 토큰 의미와 중복 키를 문서화했는가
- [ ] 재전송과 재개, fork를 포함한 fixture test가 있는가
- [ ] payload와 서버 metadata를 실제 코드 또는 네트워크로 확인했는가
- [ ] 원본, 집계, 감사 로그의 보존과 삭제 범위가 다른가
- [ ] device 교체와 다중 장치의 이중 집계 복구 절차가 있는가
- [ ] 공개 통계가 조직과 개인에게 미칠 노출을 검토했는가
