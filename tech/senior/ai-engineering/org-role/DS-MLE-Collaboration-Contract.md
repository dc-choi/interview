# ML 협업 계약 — 노트북과 서빙 사이

DS(모델을 만드는 사람)와 MLE(모델을 서비스로 굳히는 사람)의 협업이 어려운 지점은 모델 자체가 아니라 **일을 어디서 나누느냐**다. 모델링 코드와 서빙 코드 사이에 명확한 약속이 없으면 모델이 늘수록 전달 비용이 커진다. 협업 경계는 사람 → 파일 → 인터페이스(계약) 순서로 내릴수록 단단해진다.

## 경계의 3단계 진화

### 1. 사람 사이 — 노트북 통째 전달

DS가 노트북에 학습과 추론 코드를 다 적어 전달하면 MLE가 서빙 코드를 처음부터 다시 작성하는 방식. 초기엔 역할이 딱 나뉘어 오히려 빠르지만, 노트북에서 도는 것과 다른 사람 손에서 그대로 재현되는 것은 완전히 다른 문제다 — 흩어진 라이브러리와 설정 파일을 하나하나 다시 요청하게 되고, 전처리 의도가 다르게 해석되고, 모델 수가 늘면 소통 비용이 감당이 안 된다.

### 2. 파일 — 핵심 로직만 .py로 분리

노트북은 학습과 실험에만 쓰고 추론 로직은 `.py`로 빼서 리뷰와 CI를 통과시키는 방식. 소통 비용이 줄지만 **파일의 모양을 정하지 않으면** 문제가 남는다 — 모델마다 실행 함수 이름이 제각각이고(`predict`/`run`/`inference`), 서빙 환경으로 옮길 때마다 수정이 생기고, 로깅과 메트릭 같은 공통 기능을 전 모델에 일괄 적용할 방법이 없다. 노트북에서는 무해했던 공용 라이브러리 전역 설정 한 줄이, 여러 모델이 한 프로세스에 올라가는 서빙에서는 다른 모델까지 영향을 줄 수 있는 식의 환경 차이도 이 단계에서는 못 막는다.

### 3. 인터페이스 — 추상화 클래스가 계약서

전처리, 추론, 후처리 인터페이스를 가진 추상화 클래스를 공용 패키지로 두고, DS는 그 구현체를 패키지로 만들어 올리고 MLE는 설치해 서비스에 올린다. 감싸는 층(`run`)이 로그, 메트릭, 추적을 자동으로 남기므로 DS는 모델 동작에만 집중하고, MLE는 함수 이름을 물어볼 필요가 없다. 새 관측 항목은 추상화 클래스 한 곳만 고치면 모든 모델에 적용된다. 역할 구분이 말이 아니라 코드에 정해진 계약이 된다.

## 모노레포와 스타일 통일

- 계약(추상화 클래스)과 구현(모델 패키지)을 **한 레포**에서 관리하면 둘을 한 PR로 같이 고치고, 같은 자리에서 리뷰하고, CI와 버전 정책을 한 번만 세팅한다. 대가는 공통 패키지 변경의 영향권 확대와 레포 비대화다 — [[Monorepo-Architecture|모노레포 아키텍처]]의 공통 패키지 함정과 같은 축.
- AI로 코드를 작성하는 시대의 새 협업 문제: 인터페이스(구조)는 맞아도 **코드의 결이 제각각**이 된다. 팀 컨벤션을 AI가 코드 작성 시점부터 따르게 하는 규칙 모음을 두고, 규칙이 적용된 자리에 표시를 남겨 리뷰어가 이유를 바로 알게 한다. 구조 통일과 스타일 통일은 다른 층위이고, 둘 다 맞아야 리뷰가 매끄럽다.

## 운영에서 배운 것

- **경계 강성은 트레이드오프다** — 너무 엄격하면 DS가 커스터마이징하기 어렵고, 너무 느슨하면 다시 인터페이스가 제각각이 된다.
- **러닝 커브는 설계로 낮춘다** — 가이드 문서를 초기에 만들고, 첫 모델은 페어로 작업하며, 이후에는 기존 패키지가 참고 코드가 된다.
- 협업 방식이 진화할수록 **하는 일은 섞이고 책임은 더 또렷해진다**.

## 사례

토스뱅크 ML Service Team(2026): 노트북 통째 전달에서 시작해 1년간 세 번에 걸쳐 인터페이스 계약 + 모노레포(uv 워크스페이스)로 개선. 모델 서빙 이관이 며칠 단위에서, 새 서비스 하나는 첫 커밋 당일 배포까지 단축. 패키지 매니저를 poetry에서 uv로 바꿔 빌드 속도를 3~5배 개선.

## 면접 체크포인트

- 직군 간 핸드오프를 사람의 소통에서 코드 계약으로 내리는 3단계를 설명할 수 있는가
- 추상화 클래스 계약에서 DS 몫과 MLE 몫(관측의 자동화)이 어떻게 갈리는가
- 노트북과 서빙 환경의 차이(재현성, 전역 설정, 다중 모델 프로세스)를 예로 들 수 있는가
- AI 코드 작성 시대에 구조 통일과 스타일 통일이 왜 다른 문제인가
