# 시맨틱 레이어: 업무 정의를 질의 경로에서 강제하는 계층

시맨틱 레이어는 데이터 저장소와 그 데이터를 쓰는 도구(BI, AI 에이전트, 스프레드시트, 애플리케이션) 사이에서 업무 용어, 지표 산식, 테이블 관계와 접근 권한을 한 번 정의하고, 질의가 그 정의를 거쳐 실행되게 하는 계층이다. 특정 BI 도구 안에 두지 않고 여러 소비자가 같은 정의를 쓰게 만든 것을 유니버설 시맨틱 레이어라고 부른다. 매출 같은 지표를 대시보드와 에이전트가 서로 다르게 계산하는 일을 막는 것이 목적이다.

dbt 문서는 지표 정의를 BI 계층에서 모델링 계층으로 옮기면 도구가 달라도 같은 정의를 쓰고, 정의를 바꾸면 그 지표를 부르는 모든 곳에 반영된다고 설명한다. Gartner는 2030년까지 유니버설 시맨틱 레이어가 데이터 플랫폼, 사이버보안과 나란히 핵심 인프라로 다뤄질 것이라고 예측했다(2026-03-11 보도자료, 측정값이 아니라 예측). 지표 계층이 데이터 인프라의 어디에 놓이는지는 [[Data-Infrastructure-Workloads|분석과 머신러닝의 데이터 인프라]]에 있다.

## 무엇을 담는가

| 요소 | 담는 내용 | 예 |
|---|---|---|
| 업무 용어 | 정식 이름, 동의어, 약어와 부서별 표현 | 생산라인명, 라인명, 라인 명칭을 한 항목으로 |
| 지표 정의 | 산식, 기본 필터, 집계해도 되는 차원 | 순매출 = 주문 금액 - 할인 - 반품 |
| 논리 모델 | 차원(누가, 무엇, 언제, 어디서)과 측정값 | 거래처, 기준월 / 매출액, 수량 |
| 물리 매핑 | 테이블, 조인 키와 허용한 조인 경로 | 판매 사실 테이블과 거래처 차원의 조인 키 |
| 권한 | 행과 열 단위 접근 범위, 조회자 신원 | 본부장은 자기 본부 데이터만 |
| 검증된 질문 | 자주 묻는 질문과 확인한 답의 쌍 | 지난달 본부별 매출 |
| 사용 기록 | 어떤 질의가 어떤 정의와 버전을 썼는지 | 감사와 회귀 확인의 근거 |

AI 분석 제품이 화면에 드러내는 구성도 이 범위와 겹친다. 한 제품은 업무 정의, 지표 정의, 보안, 보강과 사용 기록을 시맨틱 그래프로 묶고, 다른 제품은 논리 모델, 물리 모델, 용어 사전, 계산식, 관계 지도와 예상 질문을 한 화면에서 관리한다(2026년 9월 발표 기준 공급사 두 곳의 화면). Snowflake 시맨틱 뷰의 구성 요소와 검증 쿼리는 [[Agent-Ready-Data#시맨틱 뷰로 지표 정의를 공유할 때의 점검|시맨틱 뷰 점검]]에서 다룬다.

## 흔한 오해

| 오해 | 실제로 필요한 것 |
|---|---|
| BI 메타데이터다 | 시각화용 별칭 목록이 아니다. 질의가 실행되는 경로에서 산식, 조인과 권한을 강제해야 한다 |
| DW 안에만 있으면 된다 | 원천은 여러 저장소에, 소비자는 여러 도구에 있다. 한 저장소나 한 도구 안의 정의는 그 밖의 경로가 우회한다 |
| AI가 알아서 해결한다 | LLM은 정의가 없으면 확률로 추측해 그럴듯한 조인과 틀린 지표로 자신 있게 답한다 |
| 한 번 구축하면 끝이다 | 스키마와 업무 정의는 바뀐다. 정의를 버전 관리하고 바뀔 때마다 대표 질문으로 회귀를 확인한다 |

특정 BI 도구 안에 정의를 넣은 일회성 구현은 대시보드에서는 동작해도, AI 에이전트를 붙이거나 도구를 바꿀 때마다 같은 로직을 다시 정의하게 만든다. Gartner 보도자료가 유니버설 시맨틱 레이어로 줄일 수 있다고 한 AI debt는 이렇게 도구마다 쌓이는 중복 정의와 불일치로 읽을 수 있다(해석).

## 원시 스키마를 LLM에 바로 줄 때의 다섯 문제

CFO가 반품을 뺀 순이익 기준으로 지난 분기 지역별 수익을 묻는 경우다.

| 문제 | 일어나는 일 | 시맨틱 레이어의 대응 |
|---|---|---|
| 프롬프트 비대 | 어느 테이블이 중요한지 몰라 스키마 전체를 넣고 모델이 고르게 한다 | 질문에 필요한 지표와 차원의 정의만 보낸다 |
| 조인 추측 | 공유된 관계 정의가 없어 정확한 조인 대신 그럴듯한 조인을 고른다 | 허용한 조인 경로만 쓴다 |
| 지표 환각 | 반품 차감 같은 조건이 테이블마다 다른 뜻으로 있어 엉뚱한 정의를 쓴다 | 지표 하나에 정본 정의 하나를 둔다 |
| 권한 우회 | 프롬프트 경로에는 행 단위 보안이 걸리지 않고 민감 정보가 프롬프트에 섞인다 | 조회자 신원으로 실행하고 정의에 권한을 묶는다 |
| 책임 추적 불가 | 어떤 정의로 계산했는지 기록이 없어 숫자의 근거를 되짚지 못한다 | 질의마다 쓴 정의와 버전을 남긴다 |

다섯 범주는 공급사 발표의 구분이다(2026년 9월 발표 기준). 실제 오답 유형은 [[LLM-Workflow-Patterns-Text-to-SQL#오류 없는 오답의 원인을 나눠 센다|오류 없는 오답]]의 코드값, 저장값 표기, 선언되지 않은 관계와 같은 축으로 센다. 상세 수준이 다른 사실 테이블을 잇다가 금액이 부풀려지는 팬아웃은 [[Data-Infrastructure-Layers#웨어하우스: 분석용 테이블과 행의 상세 수준|행의 상세 수준]]에서 다룬다.

## 에이전트는 문제를 키운다

- **질의량:** 에이전트는 사람이 대시보드를 열던 빈도보다 훨씬 자주 질의한다. 정의 하나가 틀리면 같은 오류가 더 많은 답으로 퍼진다.
- **재시도 루프:** 모호한 질문에서 에이전트가 되묻지 않고 추측을 바꿔 재시도하면 매번 스키마 맥락을 다시 보내 토큰이 는다. 모호하면 확인하거나 보류하는 규칙이 재시도보다 싸다([[LLM-Abstention|답변 보류]]).
- **맥락 부채:** 스키마가 바뀌면 도구마다 따로 들고 있던 프롬프트와 예시를 손으로 고쳐야 하고, 도구가 하나 늘 때마다 고칠 곳도 하나 는다. 정의를 한곳에 두면 고칠 곳이 하나로 준다.

## 정의를 질의에 연결하는 두 방식

| 방식 | LLM이 하는 일 | 강점 | 약점 |
|---|---|---|---|
| 맥락 제공형 | 정의, 관계와 검증 쿼리를 맥락으로 받아 SQL을 직접 쓴다 | 정의에 없는 탐색 질문에도 답을 시도한다 | 맥락을 받아도 조인과 산식을 틀릴 수 있다 |
| 질의 생성 위임형 | 지표, 차원과 필터만 고르고 SQL은 시맨틱 엔진이 만든다 | 산식과 조인 경로가 정해져 같은 지표, 차원과 필터 선택에는 같은 SQL이 나온다 | 정의되지 않은 지표나 관계는 답할 수 없다 |

dbt의 MetricFlow는 두 번째 방식이다. 시맨틱 모델과 지표를 YAML로 정의하면 MetricFlow가 SQL을 만들고, 정의된 관계로 테이블 사이의 경로를 찾는다. AI 도구는 dbt MCP 서버로 연결해 원시 테이블을 추측하는 대신 관리된 지표로 답할 수 있다. 맥락 제공형의 구성과 평가는 [[Agent-Ready-Data|에이전트용 데이터 준비]]의 시맨틱 뷰 절에 있다.

설계 판단: 보고와 KPI처럼 정답 정의가 있는 질문은 질의 생성 위임형으로 처리하고, 정의 밖의 탐색 질문은 맥락 제공형으로 시도하되 결과에 정의 밖이라는 표시와 검토 경로를 붙인다. 질문이 정의된 지표로 매핑되는지를 먼저 판정해 두 경로를 나눈다. 산식과 조인을 엔진이 맡으면 LLM의 일이 의도 해석과 선택으로 줄어 작은 모델이나 사내 구축 모델로도 감당할 여지가 커진다(해석).

## 정의를 강제하는 운영 조건

1. **질의 경로에서 강제한다.** 정의를 문서로 공유하는 데 그치지 않고 BI, 에이전트와 스프레드시트가 모두 같은 정의를 거쳐 실행되게 한다. 직접 DB 접속이나 개인 SQL 같은 우회 경로가 남아 있으면 그 경로의 숫자는 다를 수 있다고 표시한다.
2. **정의를 도구 밖에 둔다.** 특정 도구 형식에 묶이면 도구를 바꿀 때 다시 만든다. MetricFlow는 Apache Ossie 형식과 함께 쓸 수 있고 dbt v1.12부터는 Ossie 문서로 시맨틱 모델을 정의할 수도 있다. 정의를 옮긴 뒤에는 대표 질문의 결과를 원래 도구와 대조한다.
3. **조회자의 권한으로 실행한다.** 에이전트의 서비스 계정으로 조회하면 행과 열 보안이 사라진다. 권한 모델은 [[Agent-Ready-Data#거버넌스 — 귀속을 파괴하지 않는 접근|위임 접근]]을 따른다.
4. **질의마다 쓴 정의를 남긴다.** 지표 이름, 정의 버전, 생성 SQL, 조회자와 시각을 남기면 숫자의 근거를 되짚고 정의 변경 전후를 비교할 수 있다([[Audit-Log|감사 로그]]).
5. **바뀔 때마다 회귀를 확인한다.** 대표 질문과 기대 결과를 두고 정의나 모델이 바뀌면 다시 돌린다. 결과 건수가 아니라 식별자 집합과 집계값을 비교한다([[LLM-Workflow-Patterns-Text-to-SQL#실행 계획과 결과 건수만으로 정답을 판정하지 않는다|결과 비교]]).

## 대화형 분석은 이전 결과를 집합으로 잇는다

1. 2023년 11월 모바일로 전자기기를 산 고객 목록은?
2. 이 중에서 12월에 전자기기를 사지 않은 고객은?
3. 이 고객들의 지역, 연령과 11월 매출을 보여 줘.

BI의 비정형 리포트로 하려면 11월 구매 고객과 12월 구매 고객을 각각 리포트로 만들고, `{11월 구매 고객} AND NOT {12월 구매 고객}` 조건으로 세 번째 리포트를 만든다. 대화형 분석도 같은 집합 연산이 필요하므로 앞 질문의 결과를 화면의 행이 아니라 조건 정의로 보관하고 다음 질문이 그 집합을 참조하게 한다. 앞 질문을 가리키는 표현이 어느 집합인지, 사지 않았다는 조건이 전 채널인지 모바일만인지는 모호하므로 실행 전에 해석을 보여 주고 확인한다. 평가는 고객 식별자 집합의 일치로 한다(설계 판단, 질문 예시는 공급사 발표의 시연).

## 운영 관측

시맨틱 레이어를 거치는 질의는 한곳에서 관측할 수 있다. 다음은 공급사 발표 화면의 항목을 일반화한 운영 제안이다.

| 축 | 볼 지표 |
|---|---|
| 위험 | 민감 데이터 접근, 권한 거부, 규제 대상 데이터 조회 이벤트 |
| 성능 | 평균 질의 시간, 느린 질의(예: 5초 초과), 실패와 재시도, 대량 스캔 질의 |
| 비용 | 원천 엔진별 비용을 각 엔진의 과금 단위(크레딧, DBU 등)로 집계하고 절감 후보와 실현 절감을 구분 |
| 사용 | 질의량, 활성 사용자, 쓰이지 않는 모델과 지표(정리 후보) |

과금 단위가 다른 엔진의 비용을 한 통화로 합칠 때는 환산 기준과 시점을 함께 남긴다.

## 도입 점검

- 자주 쓰이고 틀리면 비싼 지표 몇 개부터 정의했는가? 전체 스키마를 한 번에 옮기지 않는다.
- 지표마다 정본 정의, 소유자와 변경 승인 절차가 있는가?
- BI와 에이전트가 같은 정의로 실행되고 우회 경로가 표시되는가?
- 조회자의 권한으로 실행되며 질의마다 쓴 정의가 기록되는가?
- 정의 밖 질문을 판정해 보류하거나 표시하는 경로가 있는가?
- 대표 질문의 회귀 평가가 정의 변경과 배포 절차에 들어 있는가?

## 사례와 수치의 확인 수준

- **Gartner 예측:** 2030년 핵심 인프라 예측(2026-03-11)과, 시맨틱을 우선한 조직이 2027년까지 에이전틱 AI 정확도를 최대 80% 높이고 비용을 최대 60% 줄일 것이라는 예측(2026-05-11)은 보도자료 원문으로 확인했다. 둘 다 예측이다. 발표 자료의 정확도 최대 +80%는 출처 표기가 없지만 뒤 예측과 수치가 같다.
- **발표 자료가 Gartner를 출처로 든 나머지 수치:** AI 프로젝트 5개 중 4개 ROI 없음(2025)은 Gartner 공개 자료에서 찾지 못했다. Gartner의 2026-03-09 보도자료에 나오는 5분의 4는 AI 배포 도입률이다. D&A 리더 92%의 2027년까지 도입 계획은 원문을 찾지 못했고, 2차 정리 글은 2025년 도입 44%와 2027년까지 계획 48%로 나눠 전한다. 에이전틱 AI 프로젝트 60%의 2028년 실패 예측도 원문을 찾지 못했다. 관련 공개 초록(2025-09)은 MCP를 제품 중심 접근, 시맨틱 레이어와 지식 그래프로 보완하면 확장 가능하고 신뢰할 수 있는 에이전틱 분석 흐름을 만들 수 있다고만 요약한다.
- **공급사 벤치마크(Strategy 자체 백서):** 보험 데이터 모델(테이블 28개)에 대한 질문 17개를 같은 LLM 도구로 원시 PostgreSQL과 시맨틱 계층에 각각 질의해 정답이 15개 대 17개였다. 틀린 2개는 여러 사실 테이블을 잇다 금액이 부풀려진 팬아웃과 브리지 테이블의 귀속 오류였다. 스키마 맥락은 질의당 4,428에서 2,073 토큰(53% 감소), 입력 토큰은 약 50% 감소, 질의당 비용은 37% 감소로 계산했고(토큰 수는 API 응답 측정값과 DDL, 질의 문자 수를 4로 나눈 근사를 섞은 값, 단일 세션, 캐시와 대화 이력 제외), 운영 규모의 50~70% 절감은 추정이라고 밝힌다. LLM 추론 시간은 두 방식 모두 약 13~14초였다. 발표 제목의 비용 50% 절감은 이 자체 측정의 입력 토큰 감소와 가깝지만, 분석 10배 속도에 해당하는 측정은 백서에 없다. 슬라이드의 48.9%, 10 가운데 5에서 9(무엇을 센 값인지 표시 없음), 실제 고객 벤치마크 92~100%는 측정 조건이 표시되지 않았다.
- **질의량과 재시도 수치:** 발표 자료의 질의량 3~5배, 모호한 질의의 평균 재시도 3.8회, 재시도당 약 17만 5천 토큰, 스키마 변경 때 월 12~40시간의 프롬프트 유지보수는 출처와 측정 조건이 없다. 기업 프롬프트의 13%에 민감 정보가 있다는 수치는 보안 공급사 Lasso의 2025-04 자체 조사(2023년 12월~2025년 2월 데이터)와 같다.
- **롯데백화점:** 생성형 BI와 내부 고객 분석 시스템을 합친 BI 에이전트를 2025년 5월 말부터 운영해 한 달 만에 고객 분석 시간이 최대 70% 줄고 복잡한 심층 분석 건수가 10% 이상 늘었다고 회사와 공급사가 밝혔다. 기준 업무와 측정 방법은 공개되지 않았고, 최대값이므로 평균 효과로 읽지 않는다([[AI-Marketing-Analysis#시간 단축률의 측정 범위를 고정한다|시간 단축률의 측정 범위]]).
