# Shadow Traffic (트래픽 미러링)

Shadow Traffic은 **운영 요청을 복제해 새 경로에도 흘려보내되, 그 결과를 사용자 응답에는 반영하지 않는 검증 기법**이다. 응답을 버리면 신 경로의 직접 응답 실패는 사용자에게 전달되지 않는다. 다만 쓰기 부수효과나 공유 자원 고갈은 운영 경로에 영향을 줄 수 있으므로 이를 격리해야 사용자 무영향이 성립한다. 그 조건 아래에서 스테이징에서는 재현되지 않는 실제 입력 분포와 실제 부하로 신 경로를 시험할 수 있다.

배포 전략 비교표(Blue-Green, Canary, Rolling, Shadow)는 [[Blue-Green|무중단 배포 전략]]에, 코드 배포와 기능 릴리스를 분리하는 개념은 [[CICD-Basics|CI/CD 기초]]에 정본이 있다. 이 문서는 그 위에서 메시징과 데이터 파이프라인 관점의 운영 상세만 다룬다. 비교표는 shadow를 읽기 경로 미러로 요약하지만, 실무 구성은 쓰기 요청까지 미러하고 부수효과만 끊는 쪽이 일반적이다. 미러 범위와 차단 방법의 판단 기준은 아래 부수효과 차단 절을 정본으로 본다.

## 무엇을 검증하려고 미러하나

- **정합성** — 구 경로 대비 응답 본문, 산출물 레코드, 집계값의 차이. 재작성과 엔진 교체에서 가장 큰 목적이다.
- **지연과 처리량** — 실제 요청 크기와 동시성 분포에서의 p95, p99와 초당 처리 건수. 합성 부하([[Load-Test-K6|부하 테스트]])가 재현하지 못하는 꼬리 지연이 여기서 드러난다.
- **자원 사용과 다운스트림 부하** — 신 경로가 유발하는 DB 쿼리 수, 캐시 미스율, 외부 API 호출량.
- **운영 데이터에서만 나오는 엣지 케이스** — 빈 배열, 초장문 입력, 레거시 스키마가 섞인 레코드, 예상 못 한 인코딩.

반대로 shadow로 **얻을 수 없는 것**을 명확히 해야 Canary와의 경계가 선다. 응답을 버리므로 클릭률, 전환율, 체류 시간 같은 **사용자 행동 지표와 UI 반응은 측정되지 않는다**. 사용자가 신 경로 결과를 실제로 받아봐야 알 수 있는 것은 Canary의 몫이다.

## 미러링 지점 4가지

| 지점 | 방식 | 충실도 | 운영 경로 영향 | 적용 조건 |
| --- | --- | --- | --- | --- |
| **L7 프록시** | Envoy `request_mirror_policies`, Istio VirtualService `mirror`, Nginx `mirror` 지시어 | 높음 (실제 요청 그대로) | 낮음 (fire and forget) | HTTP 경계에서 갈리는 변경 |
| **애플리케이션 내 dual-call** | 핸들러에서 신 경로를 비동기로 함께 호출 | 중간 (직렬화 이후 관점) | 중간 (같은 프로세스 자원 공유) | 프록시가 없거나 내부 함수 단위 비교 |
| **브로커 팬아웃** | 같은 토픽에 신규 컨슈머 그룹 추가, 또는 shadow 토픽 복제 | 높음 (메시지 원본) | 낮음 (브로커가 분리) | 파이프라인, 스트림 처리의 기본형 |
| **캡처 후 리플레이** | 요청 로그를 저장했다가 나중에 재생 | 중간 (타이밍과 동시성 손실) | 없음 | 운영 중 미러가 금지된 환경 |

- **L7 프록시** 계열은 세 구현 모두 응답을 버리는 방식을 명시한다. Envoy 문서 기준 미러링은 fire and forget이며 shadow 클러스터 응답을 기다리지 않고 primary 응답을 반환한다. Istio는 미러 요청의 Host, Authority 헤더 뒤에 `-shadow`를 붙여 보내므로 수신 측이 shadow 여부를 구분할 수 있다. Nginx `ngx_http_mirror_module`은 백그라운드 서브요청을 만들고 그 응답을 무시하며, `mirror_request_body`로 본문 미러 여부를 고른다.
- **비율 조절**은 Envoy `runtime_fraction`, Istio `mirrorPercentage`로 준다. 두 문서 모두 해당 필드를 지정하지 않으면 대상 트래픽 전체가 미러된다고 설명하므로, 기본값을 그대로 두면 100퍼센트 미러가 된다는 점을 전제로 용량을 잡아야 한다.
- **Node.js 매핑** — NestJS에서 dual-call을 쓸 때는 미러 호출을 `await` 하지 않는 대신 반드시 `.catch()`로 종결한다. 처리되지 않은 Promise 거부는 프로세스 종료 정책에 따라 운영 경로까지 죽일 수 있어, 미러 실패가 운영 실패로 번지는 가장 흔한 경로다. 미러 호출에는 짧은 타임아웃과 동시성 상한을 따로 건다.

## 부수효과 차단이 전제조건

shadow 경로가 실제 쓰기를 하면 그 순간부터 검증이 아니라 사고다. 미러를 켜기 전에 아래를 먼저 확정한다.

- **쓰기 대상 분리** — shadow 전용 테이블, 별도 스키마, 별도 인덱스, 별도 버킷. 같은 레코드에 두 경로가 쓰지 않게 물리적으로 가른다.
- **읽기 전용 커넥션** — shadow 프로세스에는 읽기 전용 계정과 리플리카 엔드포인트만 준다. 코드 실수를 DB 권한이 막게 하는 마지막 방어선이다.
- **no-op 어댑터와 샌드박스 자격증명** — 결제, 알림, 이메일, 외부 웹훅 어댑터를 shadow 프로파일에서 기록만 하는 구현으로 교체한다. 샌드박스 키를 쓰더라도 상대 시스템에 부하는 그대로 가므로 호출 자체를 끊는 편이 안전하다.
- **shadow 플래그 전파** — 요청 헤더(예: Istio의 `-shadow` 접미사 또는 자체 헤더), 메시지 속성, 컨텍스트 객체로 shadow 여부를 전 구간에 전달한다. 중간 서비스 한 곳이라도 플래그를 떨어뜨리면 그 아래부터는 운영 요청과 구분되지 않는다. 추적 연계는 [[Correlation-ID|상관관계 ID]]를 따른다.
- **배포 전 검증** — 미러 비율 1퍼센트 미만으로 시작해 shadow 계정의 쓰기 권한 거부 로그, 외부 API 대시보드의 호출량 변화, 알림 발송 카운터를 먼저 확인한다. 여기서 0이 아니면 즉시 끈다.

## 응답 비교와 판정

원본과 shadow 결과를 그대로 문자열 비교하면 실제 결함이 노이즈에 묻힌다. 비교 전에 **정규화**가 필요하다.

- 타임스탬프, 처리 시간, 서버 식별자, 자동 생성 ID와 UUID는 마스킹하거나 비교에서 제외한다.
- 순서 보장이 없는 배열은 키 기준 정렬 후 비교한다.
- 부동소수와 스코어는 절대 오차, 상대 오차 허용치를 필드별로 정의한다. 추천, 랭킹처럼 순위가 결과인 도메인은 값 대신 상위 K개 집합의 겹침률로 본다.
- 필드별 중요도를 나눠 핵심 필드 불일치와 부가 필드 불일치를 따로 집계한다.

판정 기준은 미러를 켜기 전에 정한다: 관찰 기간(예: 주중과 주말, 피크 시간대를 모두 포함), 핵심 필드 일치율 임계값, 불일치 샘플 저장량과 보관 기간, 종료 조건. 불일치 샘플은 원인별로 분류하고, **불일치가 곧 신 경로 버그라고 단정하지 않는다**. 구 경로의 오래된 버그를 신 경로가 고쳐서 생긴 차이인 경우가 실제로 나오며, 이때는 어느 쪽을 정답으로 삼을지 제품 결정이 필요하다.

## 메시징과 파이프라인 적용

브로커 기반 파이프라인에서 shadow는 프록시 설정 없이도 **신규 컨슈머 그룹 하나로** 만들 수 있다. Kafka 4.0 Javadoc 기준 하나의 토픽에 여러 컨슈머 그룹을 두어도 데이터가 복제되지 않고 각 그룹이 전체 레코드를 받으며, 커밋 오프셋은 그룹별로 따로 관리된다. 즉 shadow 그룹의 지연이나 실패가 운영 그룹의 오프셋을 건드리지 않는다.

- **시작 오프셋** — 최신부터 볼 것인지(현재 트래픽 검증), 특정 시점부터 재생할 것인지(과거 구간 재현)를 고른다. 오프셋이 없는 새 그룹의 시작 위치는 컨슈머 설정에 따르므로 기본값에 기대지 말고 명시한다.
- **파티션과 순서** — 순서 보장은 파티션 단위이므로, shadow 컨슈머의 파티션 배정이 다르면 전역 순서 기준으로 비교하면 안 된다. 파티션 키 단위로 묶어 비교한다. 특정 키에 쏠린 트래픽은 [[Hot-Partition|핫 파티션]] 문제를 shadow 쪽에서 먼저 드러낸다.
- **상태 있는 스트림 처리** — 윈도 집계, 세션 상태를 가진 처리는 상태가 채워지기 전 구간의 결과가 원래 다르다. 워밍업 기간을 정하고 그 구간은 판정에서 제외한다.
- **중복 처리** — 재시작과 리밸런싱으로 shadow 그룹도 같은 메시지를 다시 볼 수 있다. shadow 저장소에도 [[Idempotent-Consumer|멱등 컨슈머]] 규칙을 그대로 적용해야 중복이 불일치로 잘못 집계되지 않는다.
- **Backfill과의 차이** — [[Backfill-Resource-Isolation|백필]]은 과거 데이터를 다시 처리해 결과를 채우는 것이고, shadow는 현재 트래픽을 병행 처리해 두 결과를 비교하는 것이다. 목적이 다르므로 종료 조건도 다르다. 백필은 대상 구간을 다 채우면 끝나고, shadow는 판정 기준을 통과하면 끝난다.

## 비용과 위험

- **자원** — 100퍼센트 미러는 해당 경로의 계산 자원을 두 배로 요구한다. 샘플링 비율을 낮추면 비용은 줄지만 드문 엣지 케이스를 만날 확률과 통계적 신뢰구간이 함께 줄어든다. 희귀 케이스가 목적이면 낮은 비율의 무작위 샘플링보다 조건부 미러(특정 경로, 특정 사용자 세그먼트)가 낫다.
- **공유 자원 오염** — 계산은 분리해도 DB 커넥션 풀, 캐시, 외부 API의 rate limit은 공유되기 쉽다. shadow 전용 커넥션 풀과 캐시 네임스페이스를 나누는 원리는 [[Backfill-Resource-Isolation|자원 격리]]와 같고, 차이는 shadow가 **관찰 기간 내내 운영과 나란히 돌아간다**는 점이라 격리 실패의 노출 시간이 백필보다 길어지기 쉽다는 것이다.
- **흐름 제어** — shadow 컨슈머가 밀리면 브로커 랙이 쌓이고 저장소 쓰기가 몰린다. [[Backpressure|백프레셔]] 규칙을 shadow 경로에도 건다.
- **개인정보** — 트래픽 복제는 운영 개인정보의 사본을 하나 더 만드는 행위다. 저장하는 불일치 샘플에는 [[PII-Masking|마스킹]]을 적용하고 보관 기간을 명시적으로 짧게 잡는다.

## 언제 Shadow, 언제 Canary

- **Shadow가 맞는 경우** — 읽기 위주 경로의 재작성, 검색과 추천 엔진 교체, 저장소 마이그레이션 검증, 계산 로직 리팩터링처럼 **정답이 기존 결과로 정의되는** 변경.
- **Canary가 맞는 경우** — 사용자 반응이 판단 근거인 변경, 응답을 실제로 내보내야 의미가 있는 UI와 정책 변경.
- **실무 순서** — shadow로 정합성과 부하를 통과시킨 뒤 canary로 비율을 올린다. 추천 서빙에서의 구체적 게이트 절차는 [[Recommendation-System-Serving-Operations|추천 서빙 운영]]에 있다.
- **한계** — 쓰기와 상태 변경이 본질인 변경은 부수효과를 끄는 순간 검증 대상 자체가 사라진다. 이런 변경은 shadow 대신 데이터 이중 기록 후 대조나 canary로 간다. 어느 쪽이든 되돌릴 수 있게 만드는 판단 프레임은 [[One-Way-vs-Two-Way-Door|일방향과 양방향 문]]을 따른다.

## 흔한 실수

- 부수효과 차단을 빼먹고 미러를 켜서 shadow가 실제 알림과 결제를 발생시킴.
- 정규화 없이 diff를 돌려 타임스탬프와 ID 차이가 불일치의 대부분을 차지하고 진짜 결함이 묻힘.
- 샘플링 없이 100퍼센트 미러해 공유 DB와 외부 API를 포화시킴. 미러가 운영 장애의 원인이 되는 전형적 경로다.
- 종료 조건 없이 shadow를 방치해 이중 운영이 영구화되고, 아무도 보지 않는 대시보드만 남음.
- 미러 호출을 동기로 기다리거나 예외를 삼키지 않아 shadow 실패가 운영 응답 지연과 오류로 전파됨.

## 면접 체크포인트

- 미러링 지점 4가지의 차이와 선택 기준 (충실도, 침습성, 운영 경로 지연 영향)
- 부수효과 차단 수단과, 차단 실패가 곧 실제 사고가 되는 이유
- diff 정규화가 필요한 이유와 정규화 대상 (타임스탬프, 자동 생성 ID, 정렬, 부동소수 오차)
- Shadow와 Canary의 역할 분담, shadow로는 측정할 수 없는 지표
- 브로커 컨슈머 그룹 이중 소비의 오프셋, 파티션 순서, 상태 워밍업 이슈
