# 외부 수집 파이프라인 신뢰성

계약이 없는 외부 소스(공개 웹 페이지, 비공식 엔드포인트, 파트너가 스펙을 보장하지 않는 피드)에서 주기적으로 데이터를 긁어와 자기 서비스의 정본으로 쓰는 파이프라인의 신뢰성 패턴이다. 타임아웃, 벌크헤드, 서킷은 [[External-Service-Resilience|외부 서비스 장애 대응]], 거래형 연동과 대사는 [[External-API-Integration-Patterns|외부 API 연동 실전 패턴]]이 다루므로 여기서는 수집 고유의 문제만 둔다.

이 문서 대부분은 공식 1차 규격이 없는 운영 패턴 지식이다. robots.txt, 429, 조건부 요청처럼 규격이 존재하는 항목만 출처를 달았고, 나머지는 수집 파이프라인 운영에서 반복 관찰되는 패턴으로 읽어야 한다.

## 계약 API와 무엇이 다른가

| 축 | 계약 API | 비계약 수집 소스 |
|---|---|---|
| 스펙 변경 | 버저닝과 사전 공지 | 예고 없이 마크업, 필드, 경로가 바뀜 |
| 실패 신호 | 4xx, 5xx 상태 코드 | 200 응답에 다른 페이지가 담겨 옴 |
| 정상 판정 기준 | 상태 코드 | 데이터의 모양과 양 |
| 장애 대응 | 상대 지원 채널, SLA | 없음, 자력 감지가 유일 |
| 부하 제어 | 문서화된 rate limit | 추정, 차단당하며 학습 |

즉 수집 파이프라인에서 신뢰성 작업의 무게중심은 재시도와 서킷이 아니라 **무엇이 실패인지 스스로 정의하는 일**로 옮겨간다.

## 1. 조용한 실패를 시끄러운 실패로 승격

가장 위험한 실패는 예외가 아니라 성공으로 처리되는 오염이다. 소스가 마크업을 바꾸면 selector가 빈 결과를 내고, 파이프라인은 200 OK와 빈 배열을 받아 정상 반영한다. 결과는 예외 로그 0건과 함께 구독 가능 작품 0건이 서비스에 노출되는 상태다.

방어의 핵심은 파싱 직후를 신뢰 경계로 잡는 것이다. 파싱 결과는 검증을 통과하기 전까지 도메인 객체로 승격하지 않고, 스키마 검증 실패는 데이터가 아니라 오류로 취급한다 ([[Runtime-Validation-Libraries|런타임 검증 라이브러리]]).

검증은 세 층으로 나누면 놓치는 구간이 줄어든다.

1. **구조** — 필수 필드 존재, 타입, 배열 여부. 스키마 검증기가 담당하는 층.
2. **값 범위** — 음수 가격, 미래 날짜, enum 밖의 코드, 비정상 길이 문자열. 구조는 맞지만 의미가 깨진 값을 잡는다.
3. **집합 수준** — 이번 수집 건수와 직전 수집 건수의 비교, 소스별 필드 결측률. 개별 항목이 모두 통과해도 집합이 이상할 수 있다. 건수가 직전 대비 크게 급감했다면 소스 구조 변경을 먼저 의심한다.

반영 정책도 함께 정한다. 수집 결과를 그대로 덮어쓰는 전량 반영은 조용한 실패가 곧바로 대량 삭제로 이어진다. 건수가 0이거나 임계 이하로 떨어지면 반영을 보류하고 직전 스냅샷을 유지한 채 알림을 올린다. 잘못 쓴 데이터를 되돌리는 비용이 갱신을 한 주기 미루는 비용보다 크다.

## 2. 항목 단위 부분 실패 격리

수집 대상은 항목마다 마크업이 미묘하게 다르다. 특정 작품만 배지가 하나 더 붙거나 가격 표기가 다른 식이라, 개별 항목 파싱 실패는 상시 발생하는 정상 상태에 가깝다. 배치 1000건 중 3건 실패로 전체를 abort하면 나머지 997건의 신선도까지 같이 잃는다.

- 항목 루프는 건별로 예외를 격리하고, 실패 건은 **격리 큐(quarantine)** 에 원본 응답 스냅샷과 함께 적재한다.
- 원본 스냅샷 보관이 중요한 이유는 재현이 불가능하기 때문이다. 조사 시점에는 소스 페이지가 이미 바뀌어 있을 수 있다.
- 배치 종료 조건은 성공 건수가 아니라 **성공 비율과 집합 검증 결과**로 판단한다. 실패가 소수면 부분 반영, 실패가 임계를 넘으면 반영 자체를 중단한다.

### 실패 분류와 다른 대응

| 분류 | 신호 | 대응 |
|---|---|---|
| 일시 (transient) | 타임아웃, 5xx, 커넥션 리셋, DNS 실패 | 백오프 재시도, 재시도 예산 안에서 ([[Retry-Backoff-Jitter|지수 백오프와 지터]]) |
| 차단 (blocked) | 429, 403, 챌린지 또는 캡차 페이지, 응답 크기 급변 | 재시도 대신 수집 속도 하향, 429는 Retry-After 준수 |
| 구조 변경 (structure change) | 200인데 특정 소스에서 스키마 검증 실패가 집단 발생 | 재시도 무의미, 파서 수정 티켓과 사람 개입 |

분류를 틀리면 대응이 정확히 반대로 간다. 구조 변경을 일시 실패로 오인해 재시도하면 소스에 부하만 주고 차단을 자초하고, 차단을 일시 실패로 오인해 재시도하면 차단이 더 강해진다. 그래서 분류는 단건이 아니라 **소스 단위 집계**로 판단한다. 한 건의 검증 실패는 노이즈지만, 같은 소스에서 연속 또는 비율 임계를 넘으면 구조 변경으로 승격한다.

## 3. 신선도와 재수집 주기

모든 소스를 같은 주기로 도는 스케줄은 변동이 잦은 소스에는 지연이고 안정적인 소스에는 낭비다.

- **변화율 기반 주기** — 소스별 실제 변경 빈도를 로그로 측정해 재수집 간격을 조정한다. 초기값은 감으로 두되 관측치로 수렴시킨다. 변경이 거의 없는 카탈로그 메타와 수시로 바뀌는 가용성 정보는 다른 주기를 가져야 한다.
- **조건부 요청** — 소스가 ETag나 Last-Modified를 제공하면 If-None-Match, If-Modified-Since로 요청해 304 Not Modified를 받고 파싱을 건너뛴다 (RFC 9110). 304 비율이 높다는 것은 주기를 늘려도 손실이 적다는 신호다 ([[HTTP-Caching|HTTP 캐싱]]).
- **신선도 SLO** — 수집 성공률이 아니라 데이터 나이로 정의한다. 예: 전체 항목의 p95 데이터 나이가 N시간 이내. 성공률만 보면 성공했지만 오래된 데이터가 지표상 정상으로 잡힌다 ([[SLI-SLO|SLI와 SLO]]).
- **정지 감지** — 스케줄러가 조용히 죽으면 에러 로그가 0건이라 실패 기반 알림은 울리지 않는다. 소스별 마지막 성공 수집 시각을 기록하고 임계를 넘으면 알리는 deadman 방식이 필요하다.

## 4. 실패 누적 임계와 알림

단건 실패마다 알리면 알림 피로로 전부 무시된다 ([[Alert-Fatigue|알림 피로]]). 누적 신호로 승격 조건을 만든다.

- **비율** — 최근 윈도우의 실패율이 기준선을 초과.
- **연속** — 같은 소스에서 연속 실패 횟수 초과.
- **지속** — 임계 초과 상태가 일정 시간 유지.

집계 단위는 소스별이 기본이다. 전체 성공률로만 보면 소스 하나가 완전히 죽어도 다른 소스에 희석돼 임계에 닿지 않는다. 알림 본문에는 분류 결과와 격리 큐의 원본 샘플을 함께 실어 수신자가 파서 수정인지 속도 조절인지 바로 판단하게 한다.

자동 대응도 단계로 둔다. 1차 임계에서는 수집 속도를 낮추고, 2차 임계에서는 해당 소스 수집을 일시 중단한 뒤 직전 스냅샷을 유지한 채 사람에게 넘긴다.

## 5. 백필과 재수집의 자원 격리

파서를 고친 뒤 과거분을 다시 긁는 재수집은 평상시의 몇 배 부하다. 워커 풀, 큐, DB 커넥션을 실시간 경로와 나누는 일반 원칙은 [[Backfill-Resource-Isolation|데이터 백필과 자원 격리]]에 있다.

수집 파이프라인에서 추가로 나눠야 하는 자원은 **소스에 대한 요청 예산**이다. 백필이 소스의 rate limit을 모두 소진하면 자원을 아무리 격리해도 실시간 수집이 429를 맞는다. 소스별 초당 요청 예산을 실시간과 백필로 분배하고, 백필은 남는 몫만 쓰도록 우선순위를 낮게 둔다 ([[Rate-Limiting|Rate Limiting]]).

## 6. 규범 준수의 기술적 기준선

- **robots.txt** — RFC 9309는 `/robots.txt`에 놓인 UTF-8 text/plain 파일과 user-agent 매칭, Allow, Disallow 규칙을 표준화한다. 크롤러는 캐시본을 24시간 넘게 쓰지 않는 것이 권고(SHOULD NOT)이고, 서버 오류나 네트워크 오류로 robots.txt에 도달하지 못하면 전체를 disallow로 가정해야 한다(MUST). 4xx로 파일이 없는 경우는 접근 제한이 없는 것으로 다룰 수 있다.
- **429 Too Many Requests** — RFC 6585가 정의하며 응답에 Retry-After를 포함할 수 있다(MAY). 다만 서버가 사용자를 어떻게 식별하고 요청을 어떻게 세는지는 규격이 정하지 않는다. 소스마다 기준이 다르므로 Retry-After가 없으면 보수적인 백오프로 대응한다.
- 규격 준수와 별개로 이용약관, 저작권, 개인정보 같은 법적 허용 범위는 기술 규격이 답해주지 않는다. 소스별로 별도 확인이 필요한 영역이다.

## 흔한 실수

- 200 응답을 성공으로 처리하고 모양 검증을 생략
- 수집 0건을 정상으로 반영해 대량 삭제 유발
- 항목 한 건의 파싱 실패로 배치 전체 롤백
- 구조 변경과 차단까지 포함해 모든 실패를 재시도
- 수집 성공률만 모니터링하고 데이터 나이는 보지 않음
- 스케줄러 정지 감지 부재, 에러 0건을 정상으로 오독
- 백필이 실시간 수집의 소스 요청 예산을 잠식

## 면접 체크포인트

- 계약 API 연동과 비계약 수집의 실패 신호 차이
- 200 응답이 오염 데이터가 되는 경로와 파싱 직후 스키마 검증 게이트의 역할
- 집합 수준 검증(건수 급감 감지)이 개별 항목 검증으로 대체되지 않는 이유
- 항목 단위 격리와 격리 큐, 원본 스냅샷을 남기는 이유
- 실패 분류 3종과 각각 다른 대응, 오분류가 만드는 2차 피해
- 신선도 SLO를 성공률이 아니라 데이터 나이로 정의하는 이유
- 백필에서 자원 격리만으로 부족하고 소스 요청 예산까지 나눠야 하는 이유
