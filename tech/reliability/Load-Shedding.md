# 부하 차단 (Load Shedding)

## 정의

부하 차단은 서버가 과부하에 가까워질 때 초과 요청을 일찍 거절하고, 받아들인 요청을 제시간에 끝내는 데 자원을 쓰는 과부하 방어 기법이다. 모든 요청을 받아 모두 늦게 처리하는 대신 일부를 버려 나머지의 성공을 지킨다.

[[Rate-Limiting|rate limit과 throttling]]이 클라이언트별 한도로 클라이언트 사이의 공정성을 지키고 [[Backpressure|배압]]이 생산자에게 속도를 늦추라고 알린다면, 부하 차단은 보호 대상(서버 자체나 앞단 계층)의 처리 여력을 넘는 초과분을 거절하는 데 초점을 둔다.

## 과부하에서 goodput이 무너지는 과정

1. 사용률이 오르면 지연도 함께 오르고, 변곡점을 넘으면 지연이 훨씬 빠르게 나빠진다.
2. 지연이 클라이언트 타임아웃을 넘으면 요청이 실패한다. 서버가 늦게라도 끝낸 응답은 서버에게는 성공이지만 클라이언트에게는 오류이고, 그때까지 쓴 자원은 낭비된다. 용량이 모자란 순간에 일을 버리는 셈이다.
3. 클라이언트가 실패한 요청을 재시도하면 서버에 들어오는 부하가 몇 배로 늘어난다([[Retry-Backoff-Jitter|재시도, 지수 백오프와 지터]]).

처리량(throughput)은 서버로 보내지는 초당 전체 요청이고, goodput은 그중 오류 없이 클라이언트가 쓸 수 있을 만큼 빠르게 처리된 요청이다. 부하 차단이 없으면 처리량이 한계를 넘는 지점부터 goodput이 줄다가 급격히 떨어진다. 부하 차단을 하면 한계 근처부터 초과 요청을 거절해 goodput을 최대 수준에서 유지한다. 다만 거절에도 비용이 들어 유입이 계속 늘면 결국 goodput도 떨어진다.

납부 마감일처럼 예상을 넘는 트래픽이 몰릴 때 부하 차단은 한계 직전의 goodput을 지키면서 용량을 늘리거나 설정을 바꿀 시간을 번다. 과부하 자체를 해결하지는 않으므로 대응의 우선순위는 용량 추가와 병목 해소다. 평소에는 성능 시험으로 한계를 알고, 용량을 확보하고, 필요할 때 용량을 더하는 자동화를 둔다.

## 거절은 싸고 일찍 한다

- 거절 비용이 작을수록 goodput을 오래 지킨다. 무거운 처리를 마친 뒤 거절하면 거절만으로 자원이 소진되고, 거절 경로에 무심코 넣은 로그나 소켓 설정 하나로도 거절이 훨씬 비싸질 수 있다. 거절 기록은 남기되 가볍게 남긴다.
- 앞단일수록 싸다. 로드 밸런서에서는 초과 요청을 대기열에 쌓기보다 바로 실패시키는 spillover 설정이 일반적으로 안전한 기본값이다. 운영체제는 서버 프로세스보다 훨씬 싸게 초과 연결을 거절할 수 있다. API Gateway를 앞에 두면 API가 받을 최대 요청률을 정할 수 있고, API Gateway REST API, ALB나 CloudFront를 앞에 둔 서비스에서는 AWS WAF로 여러 기준에 따라 초과 트래픽을 걸러 낼 수 있다.
- 앞단 거절은 가시성을 잃는다. 앞단에서 버린 요청은 무엇을 버렸는지 알기 어렵다. 그래서 서버가 처리할 수 있는 것보다 많이 받아 초과분을 버리면서 버린 트래픽을 기록하고 자기 정보로 더 정확하게 차단하게 하며, 서버도 버틸 수 없는 극단적인 양은 앞단이 막도록 계층을 둔다.
- 프록시의 최대 연결 수 같은 고정 상한은 중요한 트래픽을 우선하기 어렵고 처리 중 요청 수가 실제 과부하를 잘못 나타낼 때가 있어 마지막 수단으로 쓴다. 상한을 너무 낮게 잡으면 여유가 있는데도 거절하게 된다.

## 무엇을 먼저 지킬까

- 로드 밸런서의 헬스 체크: 과부하 중에 헬스 체크에 응답하지 못하면 로드 밸런서가 한동안 새 요청을 보내지 않아 서버가 놀게 되고, 용량이 가장 필요한 때에 플릿이 줄어든다.
- 이미 시작한 작업의 마무리: 시작과 종료 API를 모두 불러야 끝나는 작업이면 종료 요청을 시작 요청보다 우선한다. 시작 요청을 우선하면 클라이언트가 시작한 작업을 끝내지 못해 브라운아웃이 된다.
- 헬스 체크 다음의 우선순위 기준은 서비스마다 다르다. 예를 들어 amazon.com 화면 데이터를 주는 서비스에서 검색 크롤러를 위한 요청은 사람이 보낸 요청보다 덜 중요할 가능성이 크다. 크롤러 요청도 처리해야 하지만 가능하면 한산한 시간으로 미룬다. 다만 여러 서비스가 협력하는 환경에서 서비스마다 상충하는 우선순위 기준을 쓰면 전체 가용성이 나빠지고 일이 낭비될 수 있으므로, 이런 조정은 클라이언트의 첫 요청을 받는 서비스처럼 가능한 한 앞에서 한다.
- 클라이언트별 한도 안의 요청을 한도를 넘긴 버스트보다 우선한다. 우선순위와 throttling을 함께 쓰면 엄격한 한도를 두지 않고도 과부하를 막을 수 있다.

## 버려질 일을 하지 않는다

- 클라이언트가 요청에 남은 시간을 실어 보내면 서버는 이미 늦은 요청을 싸게 버릴 수 있다. 큐에서 요청을 꺼낼 때 기한을 확인하고, 처리 중에 클라이언트가 포기한 것을 알면 거기서 멈춘다. 하위 서비스를 호출할 때도 남은 시간을 넘겨 각 단계가 같은 판단을 하게 한다.
- 요청이 큐에서 기다리는 시간에 상한을 둔다. 프로토콜이 허용하면 LIFO 큐로 최신 요청부터 처리해 성공 가능성이 높은 요청에 자원을 쓴다.

## 자동 확장과의 간섭

- CPU 기준으로 자동 확장하는 서비스에서 비슷한 CPU 수준부터 요청을 거절하면, 부하 차단이 CPU를 낮게 묶어 확장 정책이 증설 신호를 받지 못하거나 늦게 받는다.
- 부하 차단을 하는 플릿은 시스템 지표가 보여 주는 것보다 거절 지점에 더 가까이 운영될 수 있고, 그러면 가용 영역 하나만큼의 용량을 잃었을 때 버틸 여유가 없을 수 있다([[N-1-Capacity-Headroom|N-1 가용량 헤드룸]]). CPU 사용률만으로 여유를 판단하지 않고, 한계를 넘기는 시험으로 실제 용량과 여유를 확인한다.

## 관측과 시험

- 거절할 때 어느 클라이언트가 어떤 작업을 호출했는지처럼 차단 기준을 조정하는 데 필요한 정보를 계측하고, 거절량이 의미 있게 늘면 알람을 보낸다.
- 거절된 요청의 지연은 서비스 지연 지표와 분리한다. 빠르게 실패한 요청이 섞이면 성공 요청의 지연이 나빠도 중앙값은 좋아 보인다.
- 여유가 있는데도 거절하는 오탐은 0을 목표로 한다. 오탐률이 꾸준히 0이 아니면 차단 기준이 너무 민감하거나 개별 호스트가 계속 실제로 과부하인 것이므로 확장이나 부하 분산 문제를 함께 본다.
- 부하 시험은 한계를 넘는 부하까지 넣고 서버 지표뿐 아니라 클라이언트가 본 가용성과 지연을 잰다. 이상적인 결과는 사용률이 거의 찼을 때 goodput이 평탄하게 유지되는 것이다. 한계를 넘겨 시험하지 않은 서비스는 가장 원치 않는 방식으로 실패한다고 가정한다([[Capacity-and-Load-Testing|캐퍼시티와 부하 검증]]).

DDoS 같은 악의적 트래픽 폭증은 부하 차단으로 버티기보다 비정상 트래픽을 탐지해 걸러 내는 방어를 앞단에 둔다([[Shield-WAF-NetworkFirewall|Shield, WAF, Network Firewall]]).

## 점검 질문

- 거절 경로가 보호하려는 처리보다 충분히 싼가?
- 헬스 체크와 이미 시작한 작업의 마무리가 새 요청보다 우선하는가?
- 요청의 남은 시간을 확인하고 하위 호출로 넘기는가?
- 부하 차단 기준이 자동 확장 신호를 가리지 않는가?
- 성공 요청과 거절 요청의 지연을 나눠 보는가?
- 한계를 넘긴 부하 시험에서 goodput이 평탄하게 유지되는가?
