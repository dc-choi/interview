# N-1 가용량 헤드룸 — 최대가용배수와 부하증가배수

복제 서버군에서 1대가 빠졌을 때 나머지가 전체 부하를 감당할 수 있는가를 두 개의 배수 비교로 판단하는 장애 예방 지표. 고전적 가용성 공식이 장애가 난 뒤에야 계산되는 사후 지표인 것과 달리, 이 지표는 장애가 발생하기 전에 실시간으로 계산할 수 있어 미래 장애의 예견 신호로 쓸 수 있다.

## 고전적 가용성 공식의 한계

가용성 = MTBF / (MTBF + MTTR). 1년에 10분 장애면 525,590 / 525,600 ≈ 99.998%지만, 이 값이 충분한지는 서비스의 SLO와 사용자 영향으로 판단한다. 이 공식의 실무적 한계:

- **사후 지표** — 관측된 장애 이력을 집계한 값만으로 현재 남은 처리 용량을 알 수 없다.
- **장애의 기준이 불명확** — 부분 성능 저하, 일부 요청 실패를 어디부터 장애로 셀지 애매하다.
- **시간대별 차이 미반영** — 새벽 10분과 피크 10분의 영향이 같은 값으로 계산된다.
- **적정 목표가 애매** — 몇 개의 9가 우리 서비스에 적합한지 공식 자체는 답하지 않는다.

그래서 결과(중단 시간) 집계 대신, 장애로 이어질 조건(가용량 부족)을 직접 수치화하는 접근이 나온다.

## 두 배수의 정의

**최대가용배수 = 한계 사용량 / 현재 사용량**

서버 1대가 현재 받고 있는 부하의 몇 배까지 처리할 수 있는가, 즉 남은 헤드룸. 용량 4L 양동이에 물 2L면 2배, 3L면 약 1.33배.

**부하증가배수 = n / (n-1)** (n = 복제 서버 수)

이 식은 n이 2 이상이고, 처리 용량이 같은 서버에 부하가 균등하게 분산되며 장애 뒤에도 총부하가 같다는 가정의 계산이다. 한계 처리량은 허용 지연과 오류율을 만족하는 부하 시험으로 정한다. 서버별 용량 차이, 불균등 분산이나 재시도 증폭이 있으면 각 서버가 실제로 받을 부하를 따로 계산한다.

서버 1대에 문제가 생기면 나머지 장비에 현재 부하의 몇 배가 들어오는가. 3대 중 1대가 빠지면 나머지 2대가 각각 1.5배(3/2)를 받는다. n이 클수록 1에 수렴 — 복제 수가 많을수록 1대 손실의 충격이 작아진다.

## 임계 상황 — 장애의 사전 신호

**부하증가배수 > 최대가용배수**인 상태를 임계 상황이라 한다. 지금 당장은 정상이지만, 1대만 빠지면 나머지가 부하를 다 받지 못해 장애로 이어지는 상태다.

| 구성 (서버 3대, 용량 4) | 최대가용배수 | 부하증가배수 | 판정 |
|---|---|---|---|
| 서버당 현재 부하 2 | 4/2 = 2.0 | 3/2 = 1.5 | 안전 — 1대 장애에도 처리 가능 |
| 서버당 현재 부하 3 | 4/3 ≈ 1.33 | 3/2 = 1.5 | 임계 — 1대 장애 시 용량 초과로 지연이나 처리 실패 가능 |

두 값 모두 장애 전에 계산 가능하므로, 전 서버를 실시간 감시하다 임계 상황이 감지되면 경보를 보내 장애가 나기 전에 조치(증설, 부하 이전, 최적화)할 수 있다. 감지 후 대응이 아니라 발생 전 예방이라는 점이 이 지표의 핵심 가치다.

## 왜 1대 장애(N-1)만 기준으로 하나

서버 장애가 서로 독립이고 서버 1대의 일일 장애 확률이 1/365라고 가정하면, 3대 중 같은 날 정확히 1대 장애는 약 0.817%, 정확히 2대는 약 0.002%, 3대는 약 0.000002%다. 이는 가정에 따른 확률 계산이며 공통 전원, 네트워크와 배포로 발생하는 상관 장애에는 그대로 적용할 수 없다.

- N-1은 한 장애 단위의 손실을 평가하는 출발점이다. 실제 장애 단위가 서버인지 가용 영역인지 먼저 정하고 목표에 맞는 여유 용량을 선택한다.
- 서버 1대 손실만 점검하면 가용 영역 전체 손실을 놓칠 수 있다. 리전 단위 손실은 [[DR-Strategy|DR 전략]]과 함께 다룬다.

## 정적 안정성 — 장애 중 증설에 의존하지 않는다

여유 용량이 있어도 장애 때 새 서버 생성이나 설정 변경이 꼭 필요하면 복구 경로가 제어 기능에 의존한다. **정적 안정성(static stability)**은 의존 시스템이 손상됐을 때 기존 자원과 상태로 필요한 처리를 이어가도록 준비하는 설계다.

- **Control plane:** 자원 생성, 삭제와 설정 변경을 처리한다.
- **Data plane:** 이미 준비된 자원으로 요청과 데이터 처리를 수행한다.
- **복구 경계:** 두 영역을 나눴다는 이름만으로 무중단이 보장되지는 않는다. 장애 대응에 필요한 자원이 이미 준비돼 있는지 확인한다.

동일한 처리 용량의 3개 가용 영역에서 한 영역 손실을 버티려면, 남은 2개가 전체 부하를 처리할 수 있어야 한다. 균등 분산 가정에서는 평시 각 영역의 부하가 검증된 한계 처리량의 2/3 이하가 되는 계산이다. CPU 사용률 66%를 보편적인 안전선으로 정한다는 뜻은 아니다.

Auto Scaling은 평시 수요 변화 대응에 쓸 수 있지만, 장애 중 신규 자원 확보를 유일한 복구 수단으로 두지 않는다. 위 개념과 가용 영역 예시는 2026-10-07 AWS Builders' Library로 대조했다.

## 운영 원칙 — 지표는 단순하게

분산 시스템은 계층 간 의존으로 장애가 연쇄 전파되어 증상과 원인이 뒤얽힌다. 기준 없이 지표를 늘리면 불필요한 정보가 핵심 정보를 덮어 대응이 오히려 느려진다.

- 실시간 감시 지표는 핵심 위주로 단순하게 구성한다. 지표가 단순할수록 원인 분석이 쉽다.
- 계산의 전제가 맞는 복제 서버군에서는 두 배수로 용량 위험을 요약할 수 있다. 원시 지표를 압축하는 [[Ops-Level-Indicator|운영 레벨 지표]]와 연결하되, 부하 분포와 한계 처리량이 바뀌면 기준도 다시 확인한다.
- 경보의 거짓 양성을 방치하면 담당자가 둔감해져 진짜 장애 대응이 늦어진다 — [[Alert-Fatigue|Alert Fatigue 방지]].

## 사례 — 검색 시스템의 예방 효과

수만 대 규모 검색 시스템에서 전 서버의 두 배수를 실시간 계산하고 임계 상황 경보를 도입한 결과, 초기 월 백수십 건이던 임계 상황이 2~3개월 만에 기존의 10~20% 수준으로 감소했고 이후 그 수준을 유지했다. 장애 집계가 아니라 장애 전 신호를 관리 대상으로 삼은 것이 효과의 원천.

## 면접 체크포인트

- 가용성을 어떻게 측정, 관리하나 → 9s(nines)와 MTBF 기반 가용성은 사후 집계라는 한계. 사전 예방에는 헤드룸 기반 지표(1대 장애 시 재분배 부하 vs 남은 여유)가 필요하다는 구분.
- 부하증가배수 n/(n-1)의 유도와 함의 → 스케일 아웃으로 n을 늘리면 배수가 1에 수렴해 단일 장애 충격이 줄어든다. 복제는 처리량만이 아니라 장애 내성의 수단.
- 왜 N-1 기준인가 → 한 장애 단위 손실 시 남은 용량을 점검하는 출발점. 독립 장애 가정과 상관 장애를 구분하고, 서버와 가용 영역 중 실제 실패 단위를 정한다.
- 임계 상황 개념의 가치 → 장애가 나기 전에 계산 가능한 선행 지표라는 점. 모니터링을 사후 알림에서 사전 예방으로 바꾼다.
