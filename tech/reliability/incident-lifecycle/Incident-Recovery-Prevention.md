# 장애복구와재발방지

> 출처: [[Toss-Runners-High-Seminar|토스 러너스하이 세미나]] 기술 운영 평가

## 장애복구설계

### 스스로에게물어볼질문
1. 재시작이 필요한가, 수동 작업이 요구되는가?
2. 일부 기능만 멈추는가, 서버 전체가 중단되는가?
3. 내가 설계한 요소가 예기치 못한 상황을 만나도 충분히 회복할 수 있는가?

### 복구수준
| 수준 | 설명 | 목표 |
|------|------|------|
| 수동 복구 | 사람이 개입하여 수동으로 복구 | 최소화해야 함 |
| 자동 재시작 | 프로세스/컨테이너 자동 재시작 | 기본 수준 |
| 부분 장애 격리 | 일부 기능만 멈추고 나머지는 정상 운영 | 권장 수준 |
| 자동 복구 | 시스템이 스스로 상태를 감지하고 복구 | 이상적 수준 |

## 재발방지(RootCause분석)

### 스스로에게물어볼질문
1. 현재 대처가 문제를 회피하는 것인가? **Root Cause**는 무엇인가?
2. 동일한 장애가 다시 발생하지 않을 수 있는가?
3. **사람에 의존하는가, 시스템에 의존하는가?**

### 참고사례
- SLASH24 - eBPF를 활용한 Root Cause 분석
- Pay Cluster: 사람 의존 → 시스템 의존으로 전환

### 재발방지프로세스
```
장애 발생 → 임시 대응 → Root Cause 분석 → 재발 방지 대책 수립 → 시스템에 반영 → 검증
```

### 짧은 장애의 증거를 알림 뒤에도 남긴다

부분 검증(2026-10-15): BCC의 `profile`, `offcputime` 설명과 Linux 6.17 BPF ring buffer 문서를 대조했다. 아래 보존 절차는 eBPF 운영 사례를 바탕으로 한 설계 제안이며 특정 시스템에서 실행한 검증 결과가 아니다.

- **수집과 저장을 분리한다:** 장애 전에 필요한 훅에서 이벤트나 집계를 수집하고, 알림이 오면 해당 노드와 컨테이너의 자료를 내보내는 구조를 검토한다. 알림 뒤에 처음 계측을 켜는 것만으로 이미 사라진 사건을 복원할 수는 없다. 수집 구간과 내보낸 시각을 함께 남긴다.
- **표본과 원인을 구분한다:** On-CPU 프로파일의 표본 수는 일정 간격에 관측된 스택의 빈도이며 함수 호출 횟수 자체가 아니다. Off-CPU 집계는 CPU를 벗어나 있던 시간을 보여 주지만 정상적으로 일을 기다리는 스레드도 포함한다. 큰 스택이나 긴 대기만으로 장애 원인을 확정하지 않고 해당 요청의 타임라인과 다른 관측 신호를 대조한다.
- **주소를 해석할 자료를 보존한다:** 종료한 컨테이너의 스택을 분석하려면 해당 실행 파일과 심볼, 주소 매핑을 연결할 수 있어야 한다. 배포 시점의 바이너리 식별 정보와 필요한 메타데이터를 수집하는 방식을 검토한다. 심볼이 없거나 스택을 풀 수 없는 경우를 원인 없음으로 처리하지 않는다.
- **증거의 소실을 관측한다:** 용량이 제한된 수집 경로는 자료를 잃을 수 있다. 예를 들어 BPF ring buffer는 공간이 없으면 예약에 실패한다. 유실과 예약 실패를 집계하고, 주기적인 집계 초기화가 OOM 같은 드문 사건의 스택까지 지우지 않도록 보존 경로를 나누는 방식을 검토한다. Ring buffer와 stack map의 동작을 같은 것으로 가정하지 않는다.
- **관측 비용을 실측한다:** Scheduler 훅을 추적하고 스택을 걷는 비용은 이벤트 빈도에 따라 커질 수 있다. 대상 프로세스와 수집 범위를 제한하고 CPU, 메모리와 요청 지연을 비교한다. 한 환경의 낮은 오버헤드를 다른 노드와 부하의 보장값으로 사용하지 않는다.

## 운영자동화와지속적개선

- 성능 최적화/운영 자동화를 위해 지속적으로 노력하는가?
- **사업의 확장은 최전선에서 일어남**
- 지나간 일에 파묻히면 앞으로 나아갈 동력을 잃게 됨
- 과거 장애 대응에만 매몰되지 않고, 미래를 위한 자동화에 투자

## 장애 등급 분류

| 등급 | 정의 | 대응 SLA |
|------|------|---------|
| **P1** | 서비스 전체 중단 | 즉시 대응, 30분 내 1차 조치 |
| **P2** | 주요 기능 장애 (결제, 로그인 등) | 1시간 내 대응 |
| **P3** | 일부 사용자 영향 | 당일 내 대응 |
| **P4** | 성능 저하, 경미한 이슈 | 다음 스프린트에 처리 |

## 장애 대응 프로세스

```
1. 감지 (Grafana Alerting → Slack 자동 알림)
2. 영향 범위 파악 (`x-request-id`로 로그 추적, 같은 시간대의 method, route와 status 집계 메트릭 대조)
3. 판단: 점진 배포 중이면 가능한 경우 추가 노출을 먼저 멈추고 완화 수단 선택
   - 데이터 정합성 문제는 코드 롤백의 호환성과 이미 기록된 데이터의 별도 보정 필요성을 먼저 확인
   - 롤백, 기능 비활성화, 핫픽스와 다음 정기 배포는 [[Hotfix-Decision-Loop|핫픽스 판단과 학습 루프]]의 영향 범위, 가역성과 수정 위험으로 결정
4. 근본 원인 분석 (Loki 로그 + Prometheus 메트릭 교차 분석)
5. 재발 방지 (알림 임계값 조정 + 테스트 케이스 추가 + 포스트모템)
```

## 포스트모템 (Blameless Postmortem)

### 작성 항목
1. **타임라인**: 발생 → 감지 → 대응 → 복구 시각
2. **근본 원인**: 왜 발생했는가 (5 Whys 기법)
3. **영향 범위**: 몇 명의 사용자, 어떤 기능, 얼마나 오래
4. **재발 방지 액션 아이템**: 담당자 + 기한 명시
5. **교훈**: 잘한 점 + 개선할 점

### 핵심 원칙
- **비난 없는 문화**: 사람이 아니라 시스템/프로세스의 문제를 찾는 것
- 포스트모템은 문서화하여 팀 전체에 공유 → 조직의 학습 자산

## 장애 사전 예방

| 방법 | 설명 |
|------|------|
| 경보 설계 | 사용자 영향 SLO burn-rate와 Slow SQL 같은 원인 임계 경보를 구분해 조기 감지 |
| 카나리 배포 | 일부 트래픽만 새 버전으로 → 문제 시 빠른 롤백 |
| 로드 테스트 | k6, Artillery 등으로 병목 사전 발견 |
| 코드 리뷰 + 테스트 게이트 | PR 단계에서 품질 확보 |
| Circuit Breaker | 외부 의존성 장애 시 연쇄 장애 차단 |

### 출시와 트래픽 급증 전 운영 준비

부분 검증(2026-10-14): AWS ORR의 예시 질문과 game day 지침을 대조했다. ORR은 고객에게 영향을 주는 API와 의존성, 실패 시 영향, 재시작 런북과 부하 시험 계획을 확인한다. 부하 시험에서는 병목을 찾고 수정한 뒤 다시 시험하며, 일부 대형 고객의 급증과 여러 소형 고객의 부하처럼 서로 다른 분포를 고려한다.

Game day는 시스템뿐 아니라 실제 대응 인력과 절차도 시험한다. 운영과 유사한 환경에서 감지, 호출, 진단과 완화를 연습하고 참여자에게 일정과 시나리오를 미리 알린다. 부정적 영향이 관측되면 시험을 되돌리고 런북에 따라 조치한다. 설계 검토나 부하 시험 성공만으로 대응 준비가 끝났다고 판단하지 않는다.

적용 제안: 출시 전에는 예상 트래픽과 실패 시나리오별 결과를 함께 기록한다. 처리량뿐 아니라 오류율, 꼬리 지연과 대응 흐름을 확인하고 미해결 병목, 완화 수단과 담당자를 남긴다. 특정 출시 사례의 가용성이나 확장 배수를 다른 서비스의 보장값으로 사용하지 않는다.

### 행사 종료 뒤 개선을 다음 운영에 반영한다

AWS Unified Operations는 이벤트 지원 이후에도 과거 사고 분석, 관측 임계값과 용량 계획 조정, 런북 갱신을 설명한다(2026-10-14 공식 서비스 소개 대조). 지원 계약 자체를 장애 예방이나 복구 완료의 증거로 보지 않는다.

적용 제안: 예정된 대규모 이벤트가 끝나면 예상과 실제 부하, 경보, 병목과 수동 개입을 비교한다. 장애가 없었어도 드러난 운영 공백을 개선 대상으로 남기고, 다음 이벤트 전 관련 시험을 반복한다. Game day에서 발견한 개선 항목도 담당자와 후속 조치를 정해 완료까지 추적한다. 이 절은 운영 검토 방법이며 특정 서비스의 배포나 부하 시험 결과가 아니다.

### 지원 응답 시간과 서비스 복구 시간을 구분한다

2026-10-14 AWS 공식 제품 안내 대조 기준, Unified Operations는 중요 장애에 5분 이내 응답을 안내한다. Enterprise Support는 production-critical 문제에 15분 이내 최초 응답을 안내하며, 해당 시간 내 응답을 위해 합리적인 노력을 다한다는 조건을 붙인다. **최초 응답 시간은 장애 해결이나 서비스 복구 완료 시간의 보장이 아니다.** 위의 내부 P1~P4 분류도 공급자의 심각도 기준과 자동으로 일치하지 않는다.

Unified Operations의 해결 효과는 확보한 맥락에 영향을 받는다. 알람을 온보딩한 workload는 사전 맥락을 활용하고, 온보딩하지 않은 workload는 서비스 상태와 고객이 제공한 정보에서 시작한다. Enterprise Support의 지정 TAM은 전략적 운영 지침과 아키텍처 검토를 제공하는 역할이며, 최초 기술 응답을 맡는 지원 엔지니어와 역할을 구분한다.

운영 적용 제안: 내부 감지, 공급자 문의, 최초 응답, 완화와 복구 완료 시각을 따로 기록한다. 문의에는 영향 범위, 발생 시각, 최근 변경과 관측 근거를 준비하고, 지원을 기다리는 동안 실행할 내부 런북과 담당자를 정한다. 지원 플랜 가입만으로 애플리케이션 복구 목표가 충족됐다고 판단하지 않는다. 이번 확인은 문서 대조이며 실제 지원 요청과 응답 시간을 시험하지 않았다.

### AI 지원, 기술 응답과 보안 사고 지원의 범위를 나눈다

2026-10-14 AWS Support 가이드와 Business Support+ 제품 안내 대조 기준이다. Basic의 계정, 청구와 서비스 할당량 지원을 프로덕션 기술 장애 지원과 구분한다. Business Support+는 생성형 AI의 맥락 기반 응답과 24시간 지원 엔지니어 접근을 제공한다. **30분 미만 사람 응답은 business-critical system down 등급에 대한 안내**이며 모든 문의의 응답 시간이 아니다. 제품 안내에는 최초 요청에 해당 시간 내 응답하도록 합리적인 노력을 다한다는 조건이 있다.

Enterprise Support는 지정 TAM과 AWS Security Incident Response 접근을 추가로 제공한다. 보안 사고 지원은 계정 탈취, 데이터 유출과 랜섬웨어 등의 준비, 대응과 복구 지침을 다룬다. 일반 기술 장애 문의와 보안 사고 대응 경로를 같은 것으로 취급하지 않는다.

운영 적용 제안: AI가 제시한 진단, 사람의 최초 기술 응답과 실제 복구를 별도로 기록한다. 외주 서비스의 운영 인수인계에는 가입 플랜, 심각도 기준, 문의 권한과 보안 사고 연락 경로를 함께 남긴다. AI 응답을 받았다는 사실만으로 원인 확인이나 지원 엔지니어 연결이 완료됐다고 판단하지 않는다.

## 면접포인트
- "장애 경험?" → 감지 → 대응 → Root Cause → 재발 방지까지 전체 사이클로 답변
- "사람 의존 vs 시스템 의존?" → 수동 대응을 자동화로 전환한 경험
- "운영 자동화 경험?" → 반복 작업을 시스템화하여 본업에 집중할 수 있도록 개선
- "장애 등급을 어떻게 나누나?" → P1~P4 등급별 대응 SLA 차등
- "포스트모템에 뭘 쓰나?" → 타임라인, 근본 원인, 영향 범위, 액션 아이템. 비난 없는 문화가 핵심
