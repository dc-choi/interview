# 핫픽스 판단과 학습 루프

핫픽스는 심각도가 높은 버그의 동의어가 아니다. 지금 새 변경을 배포할 위험과 다음 정기 배포까지 사용자 피해를 방치할 위험을 비교해 선택하는 완화 수단이다. 점진 배포 중이라면 먼저 추가 노출을 멈출 수 있는지 확인하고, 이미 노출된 사용자까지 회복시킬 방법을 별도로 결정한다.

## 핵심 명제

- **심각도와 조치를 분리한다.** 즉시 완화가 필요한 문제라도 기능 플래그 비활성화나 롤백이 핫픽스보다 안전할 수 있다.
- **관측 비율의 분모를 확인한다.** 전체 사용자의 1%와 신버전 사용자 중 1%는 전혀 다른 위험이다.
- **현재 피해와 잠재 피해를 함께 본다.** 낮은 배포율에서 작게 보인 결함도 배포 확대 뒤 같은 비율로 커질 수 있다.
- **진행하지 않은 결정도 남긴다.** 다음 배포로 넘긴 이유가 없으면 비슷한 상황에서 기준이 다시 흔들린다.
- **완료는 기록이 아니라 이행 증거다.** 재발 방지 조치는 추적 가능한 작업과 검증 결과까지 닫혀야 한다.

## 점진 배포의 1%를 분해한다

관측 기간의 예상 영향은 다음처럼 근사할 수 있다.

`예상 영향 사용자 수 ≈ 대상 사용자 수 × 신버전 노출률 × 조건 진입률 × 조건 진입 시 실패율`

예를 들어 신버전이 1%에만 노출됐고 노출 사용자 대부분이 특정 경로에서 실패한다면, 현재 전체 영향은 작아 보여도 배포 확대 뒤 잠재 영향은 크다. 반대로 신버전 노출률이 100%여도 매우 드문 조건에서만 실패하고 우회 경로가 있다면, 핫픽스가 추가하는 회귀 위험이 대기 비용보다 클 수 있다.

다음 분모를 분리해 수집한다.

- 전체 대상 사용자와 실제 신버전 사용자
- 신버전 사용자 중 문제 경로에 진입한 사용자
- 진입 사용자 중 실패한 고유 사용자와 반복 이벤트 수
- 플랫폼, 앱 버전, OS, 기기와 기능 플래그 코호트
- 최초 발생 시각, 관측 기간과 다음 배포 확대 시각

이 근사는 코호트가 대표적이고 결함이 사용자별로 독립적일 때만 유용하다. 공유 DB 오염, 중복 결제, 외부 API 부수효과와 자원 고갈은 배포 비율보다 넓게 전파될 수 있으므로 별도 차단 신호로 다룬다.

## 완화 수단을 고른다

| 선택 | 유리한 조건 | 남는 위험 |
|---|---|---|
| 배포 확대 중단 | 점진 배포 중 신뢰할 만한 이상 신호가 감지됨 | 이미 업데이트한 사용자는 그대로 남음 |
| 기능 플래그 비활성화, 트래픽 롤백 | 문제 경로가 격리되고 이전 상태가 호환됨 | 이미 발생한 쓰기와 외부 부수효과는 별도 복구 필요 |
| 핫픽스 | 피해가 계속되고 원인과 최소 수정 범위가 명확하며 다른 완화 수단이 부족함 | 새 빌드의 회귀, 검토와 스토어 배포 지연 |
| 다음 정기 배포 | 영향이 제한적이고 우회 경로가 있으며 대기 비용이 핫픽스 위험보다 작음 | 대기 기간 동안 알려진 피해가 지속됨 |

Google Play의 staged rollout을 중단하면 추가 사용자는 해당 버전을 받지 않지만 이미 받은 사용자는 그 버전에 남는다. Apple의 phased release도 자동 업데이트 코호트를 단계적으로 늘리는 기능이며, 사용자는 배포 단계와 무관하게 수동으로 최신 버전을 내려받을 수 있다. 따라서 확대 중단은 노출 제어이지 이미 노출된 사용자의 복구가 아니다.

## 판단 입력과 책임을 고정한다

단일 점수보다 즉시 완화가 필요한 거부 조건과 맥락 변수를 나눠 본다.

- **사용자 피해**: 핵심 기능 중단, 데이터 손상, 금전 손실, 보안과 규제 영향
- **영향 범위**: 현재 고유 사용자 수, 배포 확대 뒤 잠재 범위, 증가 속도
- **우회 가능성**: 사용자가 스스로 피할 수 있는지, 지원 조직이 안내할 수 있는지
- **가역성**: 플래그, 트래픽 복귀, 이전 아티팩트와 데이터 보정 수단
- **수정 신뢰도**: 재현 경로, 원인 확신, 변경 범위, 회귀 테스트와 관측 가능성
- **시간 비용**: 정기 배포까지의 시간, 빌드와 검토 시간, 앱 스토어 반영 지연

최종 결정권자와 검토 역할을 사전에 정한다. 릴리스 위험과 품질 위험을 서로 다른 관점에서 검토하되, 긴급 빌드를 미리 시작하는 것과 최종 배포 승인을 생략하는 것을 혼동하지 않는다. 합의가 늦어질 때의 에스컬레이션 경로와 중단 권한도 런북에 둔다.

## 재현 근거를 한 묶음으로 만든다

판단 전에 다음 증거를 같은 사건 기록에 모은다.

- 앱 버전과 배포 단계, 발생 시각
- 사용자가 겪은 증상과 영향 분모
- 재현 순서, 기기와 OS 같은 환경
- 관련 로그, 크래시와 트레이스 링크
- 알려진 우회 경로와 후보 원인

로그와 대화에서 이 정보를 자동 수집하고 초안을 만드는 것은 기록 시간을 줄인다. 다만 화면 이름, 이벤트 의미와 재현 신호처럼 결과를 좌우하는 매핑은 명시적 규칙으로 고정하고, AI 요약은 근거 링크를 보존한 채 사람이 검토한다. 기록 자동화가 새로운 판정자가 되어서는 안 된다.

## 실행한 결정과 실행하지 않은 결정을 함께 기록한다

최소 결정 기록은 다음 질문에 답한다.

- 어떤 버전과 조건에서 무엇을 관측했는가
- 현재 영향과 배포 확대 뒤 잠재 영향을 어떤 분모로 계산했는가
- 중단, 롤백, 기능 비활성화, 핫픽스와 정기 배포를 어떻게 비교했는가
- 무엇을 선택했고 누가 승인했는가
- 선택하지 않은 대안과 이유는 무엇인가
- 언제 어떤 지표로 결정을 다시 검토할 것인가

핫픽스를 실행한 경우에는 원인과 기여 요인, 수정 내용, 검증 결과와 재발 방지 조치를 연결한다. 실행하지 않은 경우에도 우회 가능성, 제한된 영향과 다음 배포 계획을 남긴다. 안 한 일도 운영 결정이며 다음 판단의 기준 데이터가 된다.

기록을 어렵게 만들어 핫픽스를 억제하려 하면 사건보다 기록이 먼저 사라질 수 있다. 채널 대화, 배포 메타데이터와 관측 링크로 초안을 채우고 사람은 누락과 판단 근거를 보완하는 편이 낫다.

## 재발 방지 이행을 닫는다

주기적인 검토에서는 지난 결정의 옳고 그름만 토론하지 않는다.

1. 반복되는 원인과 놓친 탐지 신호를 묶는다.
2. 예방, 완화와 탐지 조치를 구분해 정한다.
3. 각 조치에 오너, 우선순위, 기한과 추적 이슈를 붙인다.
4. 티켓 종료와 배포, 테스트, 대시보드 같은 증거로 이행을 확인한다.
5. 결과에 따라 판단 기준과 런북을 갱신한다.

Google SRE Workbook도 포스트모템 액션을 중앙 이슈 추적 시스템에 연결하고 완료 상태를 추적해야 조치가 빠지는 일을 막을 수 있다고 설명한다. 사람이 완료라고 적은 상태보다 검증 가능한 종료 조건이 중요하다.

## 지표가 행동을 왜곡하지 않게 한다

핫픽스 건수만 줄이면 미보고와 다음 배포로의 지연도 개선으로 보인다. 최소한 다음 지표를 함께 본다.

- 릴리스당 핫픽스 수와 핫픽스로 유입된 회귀 비율
- 사용자에게 빠져나간 결함 비율과 반복 원인별 재발률
- 탐지부터 추가 노출 중단, 완화와 정상화까지의 시간
- 결정 기록의 영향 분모 기재율
- 재발 방지 조치의 기한 내 완료율과 완료까지 걸린 시간

도입 전 기준선, 목표, 영향 대상, 기대 인과, 관측 기간과 관측 뒤 결정을 정한다. 단일 조직의 전후 감소만으로 이 프로세스가 원인이라고 단정하지 않고, 릴리스 수와 사용자 규모, 다른 품질 투자와 보고 정책 변화를 함께 확인한다.

## 운영 루프

`신호 감지 → 추가 노출 중단 → 증거 묶음 생성 → 완화 수단 결정 → 결과 검증 → 결정 기록 → 재발 방지 이행 → 기준 갱신`

이 루프의 목적은 핫픽스를 어렵게 만드는 것이 아니다. 불필요한 긴급 배포는 피하고, 필요한 완화는 신중하고 빠르게 실행하며, 같은 사고의 반복 비용을 줄이는 것이다.

## 면접 체크포인트

- 배포 노출률과 결함 발생률의 분모를 구분해 설명할 수 있는가
- rollout 중단이 이미 업데이트한 사용자를 복구하지 못하는 이유를 아는가
- 롤백, 기능 플래그, 핫픽스와 다음 정기 배포를 어떤 조건으로 고르는가
- 실행하지 않은 결정까지 기록해야 기준이 축적되는 이유는 무엇인가
- 핫픽스 건수 감소만으로 품질 개선을 증명할 수 없는 이유는 무엇인가
