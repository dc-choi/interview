# 클라우드 단위 비용

## 총비용과 처리 효율을 함께 본다

클라우드 단위 비용은 정한 범위의 비용을 같은 기간의 서비스 제공량으로 나눈 값이다. 총비용이 늘어도 제공량이 더 빠르게 늘면 단위 비용은 낮아질 수 있다. 반대로 청구액이 줄었다는 사실만으로 효율 개선을 확정할 수 없다.

`평균 단위 비용 = 대상 워크로드의 기간 비용 / 같은 기간의 제공량`

이 식은 평균 비용이다. 한 건을 추가 처리할 때 늘어나는 한계 비용과 같다고 보지 않는다. 고정 용량과 유휴 자원이 있으면 두 값의 차이가 커질 수 있다.

## 분모를 서비스 결과에 연결한다

리소스 효율과 고객에게 제공한 결과는 서로 다른 질문에 답한다. FinOps는 두 지표의 관계를 명시하도록 권고하고, AWS Well-Architected는 워크로드의 주요 결과를 사업 지표로 정의하도록 안내한다.

| 지표 층 | 측정 예시 | 확인할 질문 |
|---|---|---|
| 리소스 효율 | 저장 GB당 비용, 토큰당 비용 | 같은 기술 작업을 얼마나 효율적으로 처리했는가 |
| 서비스 결과 | 고객에게 전달한 보고서당 비용, 완료된 거래당 비용 | 사용자가 얻은 결과 한 건에 얼마를 썼는가 |

API 호출 수를 줄이는 최적화에서는 호출당 비용만 보면 개선을 놓칠 수 있다. 같은 사용자 과업이 완료됐는지와 과업당 비용을 함께 확인한다. AI 작업도 토큰 수 외에 완료 결과와 품질 기준을 정한다.

## 비교 전에 고정할 측정 정의

다음은 비용과 결과 데이터를 연결할 때 사용할 실무 점검 기준이다.

- **대상과 기간:** 같은 워크로드, 고객군, 시작일과 종료일의 비용 및 결과를 비교한다.
- **비용 범위:** 직접 사용 비용만인지, 공유 인프라 배분액까지인지 명시한다. 할인과 크레딧을 반영한 기준도 유지한다.
- **결과 집계:** 완료 조건과 중복 집계 기준을 정한다. 실패나 재시도가 소비한 비용은 남기고, 성공 결과의 수를 중복해서 늘리지 않는다.
- **누락과 변경:** 결과 수가 없거나 비용 귀속이 불완전하면 한계를 표시한다. 분모가 0인 기간은 단위 비용을 0으로 적지 않는다.

태그 활성화와 공유 비용 배분의 도구별 범위는 [[AWS-Cost-Allocation-Tags|AWS 비용 할당 태그]]를 따른다. 클라우드 비용만 측정한 값을 인건비까지 포함한 총원가로 제시하지 않는다.

## 가상 계산: 비용 증가와 효율 개선의 공존

아래 숫자는 설명용 가정이다. 두 달의 비용 포함 범위와 보고서 완료 기준이 같다고 둔다.

| 기간 | 월 비용 | 전달 완료 보고서 | 보고서당 평균 비용 |
|---|---:|---:|---:|
| 첫 달 | 100만 원 | 10,000건 | 100원 |
| 다음 달 | 120만 원 | 15,000건 | 80원 |

총비용은 20% 증가했지만 단위 비용은 20% 감소했다. 이는 예산 여유나 이익 증가까지 증명하지 않는다. 품질, 지연, 실제 고객 가치와 총지출 한도를 별도로 확인한다.

## 운영에 적용하기

처음에는 비용이 큰 워크로드 하나와 주요 결과 지표를 고르고, 청구 데이터와 결과 집계의 출처를 연결한다. 기준 기간을 남긴 뒤 변경 전후의 총비용, 제공량, 단위 비용과 서비스 품질을 함께 비교한다.

단위 비용이 낮아진 원인이 자원 최적화인지, 할인인지, 처리량 증가에 따른 고정비 분산인지 구분한다. 고객군이나 작업 난도가 바뀌었다면 같은 조건으로 나누어 확인한다. 낮은 숫자 자체를 목표로 삼아 실패를 숨기거나 결과 품질을 낮추지 않는다.

이 문서는 인프라 측정 기준을 다룬다. 고객 획득 비용과 공헌이익을 포함한 사업의 수익성 판단은 [[Business-Model#Unit Economics|비즈니스 모델의 Unit Economics]]와 구분한다.

### 공유 지표에는 데이터 기준 시점과 조치 책임을 붙인다

2026-10-10 FinOps Unit Economics 지침 대조 기준, 지표의 데이터 원천과 계산식을 문서화하고 의사결정자가 사용하는 채널로 제공하며 정기적으로 검토한다. 서로 다른 제품을 하나의 순위로 비교하기보다 같은 범위의 추세부터 본다.

다음은 비용 보고에 적용할 설계 예다. 총비용, 완료 건수와 단위 비용을 함께 보여주고, 증감이 큰 서비스에서 실제 리소스와 담당자까지 내려갈 수 있게 한다. 보고서 배포만으로 끝내지 않고 원인 가설, 개선 조치, 담당자와 재측정 시점을 남긴다. 배포 시각과 비용 증가가 겹쳐도 사용량, 단가와 비용 배분 변경을 확인하기 전에는 배포를 원인으로 확정하지 않는다.

AWS CUR는 월중 비용을 추정치로 제공하고 적어도 하루 한 번 갱신하며, 서비스마다 사용량 정보가 도착하는 시점이 다를 수 있다(2026-10-10 공식 문서 확인). 따라서 지연된 비용을 실시간 요청 수로 나눈 값을 확정 효율로 제시하지 않는다. 비용과 제공량의 집계 범위, 마지막 갱신 시각과 잠정 여부를 표시하고, 청구 확정 및 환불이나 크레딧 반영 뒤 다시 계산할 수 있게 한다.

### 사례: 조직별 비용 청구서와 성숙도 진단

배달 플랫폼 운영사 우아한형제들이 AWS Industry Week 2024에서 발표한 자체 운영 방식이다. 회사가 설명한 사례이며, 발표 당시 파일럿이던 조직별 청구서 메일과 준비 중인 계획을 포함한다. 효과와 수치는 독립 검증하지 않았다. 회사는 이 청구서 메일을 쇼백 관점의 보고라고 설명했다. 실제 청구 없이 조직별 비용을 보여주는 이 방식은 [[AWS-Cost-Optimization#Showback을 엔지니어의 작업 흐름에 연결한다|Showback 보고]]의 한 형태다.

- **결과 지표와 효율 지표를 함께 둔다:** AWS 비용을 전사 배달 주문 건수로 나눈 주문당 비용과, 요청을 ELB, 데이터 전송, CloudFront로 나누어 본 요청당 비용을 함께 쓴다. 앞의 표로 보면 주문당 비용은 서비스 결과 지표이고 요청당 비용은 리소스 효율 지표다.
- **기준 시점과 비교 기준을 밝힌다:** 발표에서 소개한 일간 메일은 대상 조직, 비용 추출 기준 일자와 기준 환율을 먼저 밝힌다. 총비용은 전일과 최근 3개월 평균 대비, 주문당과 요청당 비용은 전주와 최근 3개월 평균 대비 증감을 보여준다. 주간과 월간 메일의 구성은 발표에서 설명하지 않았다.
- **조사 경로를 같이 준다:** 증감 상위 3개를 AWS 제품, 서비스 태그, 역할 태그 순으로 보여주고, 전사 평균과 백분위에서 해당 조직의 위치를 보여주려 한다. 메일 하단 링크로 여는 상세 대시보드는 2개월 전, 1개월 전과 진행 중인 당월의 비용을 보여주고, 월마다 비용 계산 일수가 달라 증감은 일평균 비용으로 환산해 비교한다. 발표는 당월 값의 확정 여부를 설명하지 않았지만, 앞 절의 CUR 설명에 따르면 진행 중인 달의 비용은 청구가 확정되기 전의 추정치다(이 문서의 해석). 회사는 배포 횟수와 비용의 상관관계를 보려고 일별 비용 차트에 배포 횟수도 함께 표시했다.
- **과제의 출처를 옮기려 한다:** 중앙 FinOps 담당이 최적화 과제를 내던 방식에서 각 개발팀이 자기 KPI에 맞춰 도출한 과제를 중앙이 접수하는 방식으로 바꿀 준비를 하고, 모니터링과 배치 같은 공통 플랫폼 비용을 간접비로 배분하는 로직을 설계 중이라고 밝혔다.
- **성숙도 진단:** FinOps Foundation 성숙도 모델과 AWS 엔터프라이즈 서포트의 비용 관리 진단으로 현재 단계를 확인하고, AWS 진단을 바탕으로 단계별 과제를 정의했다고 설명한다.

이 문서의 기준으로 사례를 읽으면, 배포와 비용 증가가 겹친다는 사실만으로 배포를 원인으로 확정하지 않는다. 조직 간 백분위를 효율 비교로 읽으려면 비용 범위가 같고, 분모가 각 조직의 제공량을 같은 정의로 센 값이어야 한다. 전사 주문 건수처럼 모든 조직에 같은 값을 쓰는 분모로 나누면 순위는 절대 비용의 순위와 같아진다. 절대 비용의 백분위에는 규모와 효율의 차이가 섞여 있으므로 효율 순위로 읽지 않는다. 순위보다 같은 범위의 추세를 먼저 본다.

FinOps Foundation의 성숙도 모델은 Crawl, Walk, Run 단계를 쓰고 역량과 기능 활동마다 성숙도가 다를 수 있다고 본다. 모든 역량을 Run으로 만드는 것 자체를 목표로 삼지 말라고 명시하고, 사업 가치가 가장 큰 역량의 성숙을 우선하라고 권한다(2026-10-18 확인). 단위 비용 지표를 다루는 Unit Economics도 FinOps Framework의 Quantify Business Value 도메인에 속한 하나의 역량이라 다른 역량과 성숙도가 다를 수 있다(2026-10-19 확인). 따라서 단계 진단은 개선 후보를 찾는 데 쓰고, 우선순위는 그 역량이 주는 사업 가치로 정한다.

### 리소스 연결과 비용 귀속을 분리한다

부분 검증(2026-10-16): AWS의 FinOps 그래프 설계 자료와 VPC Flow Logs 제한을 대조했다. 리소스 관계, 태그, 사용 지표와 청구 데이터를 연결하면 태그가 빠진 의존 자원이나 비용 증가의 조사 범위를 찾는 데 도움이 된다. 그래프에 연결돼 있다는 사실만으로 비용 배분이 확정되지는 않는다.

- **관계의 의미:** 같은 네트워크에 속함, 실제 통신함, 특정 서비스가 사용함을 구분한다. 공용 네트워크를 거쳐 연결된 모든 자원을 한 제품의 비용으로 합산하지 않는다.
- **공유 비용:** 여러 제품이 사용하는 자원은 배분 기준과 가중치를 별도로 정한다. 운영 설계 예로, 같은 청구 항목이 여러 탐색 경로에 등장해도 한 번만 집계하고 배분 전후 합계를 대조한다.
- **미관측과 미사용:** Flow Logs는 모든 IP 트래픽을 기록하지 않으며 수집 중 일부 기록이 생략될 수도 있다. 연결이나 트래픽이 보이지 않는다는 이유만으로 유휴 자원 또는 삭제 대상으로 확정하지 않는다. 관측 기간 밖의 배치와 복구 용도도 확인한다.

처음에는 비용 귀속이 불명확한 질문 하나를 기존 청구 내역과 리소스 목록으로 조사한다. 관계 탐색이 반복적으로 필요할 때 그래프 도입을 검토하는 것은 적용 제안이며, 그래프 구축 자체를 절감 성과로 계산하지 않는다. 실제 계정의 비용이나 귀속 정확도는 시험하지 않았고 앞 절들의 검증 기준일은 유지한다.

### 추천 절감액을 실현 성과로 합산하지 않는다

부분 검증(2026-10-23): AWS Cost Optimization Hub는 서로 영향을 주는 추천의 중복을 고려해 예상 절감액을 집계한다. 같은 EC2 인스턴스를 삭제하는 추천과 크기를 줄이는 추천은 동시에 실행할 수 없으므로 두 절감액을 더하지 않는다. Savings Plans와 Reserved Instances 추천 사이의 중복도 고려한다.

다음은 추천을 실제 변경과 측정으로 연결하는 운영 예시다.

- 추천마다 대상 자원, 사용 근거, 담당자와 변경 조건을 연결한다. 청구 담당자가 찾은 절감 후보와 자원 담당자가 실행할 변경을 같은 기록에서 추적한다.
- 서로 배타적인 조치와 순차 실행할 조치를 구분한다. 먼저 자원을 줄였다면 이후 약정 구매의 대상 사용량도 다시 계산한다.
- 예상 절감액, 실제 변경 완료, 변경 뒤 관측한 비용을 별도 상태로 둔다. 완료 시점 이후의 같은 비용 범위와 업무량을 비교하고, 할인과 트래픽 변화의 영향을 분리한다.

추천이 정확하다는 설명이나 빠른 투자 회수 사례만으로 자체 환경의 절감액을 확정하지 않는다. 이번에는 집계 원리만 공식 문서와 대조했으며 실제 계정 변경과 비용 측정은 하지 않았다. 기존 절의 검증일은 유지한다.

## 비용 절감과 자원 효율을 구분한다

2026-10-09 AWS Sustainability Pillar 대조 기준. 비용 지표와 함께 작업 한 건을 제공하기 위해 할당한 자원도 측정한다. 할인으로 청구액이 줄어도 같은 자원을 계속 사용한다면 자원 효율이 개선됐다고 볼 수 없다.

`작업 단위당 자원 = 해당 자원의 대리 지표 / 같은 범위의 업무 결과 수`

| 자원 | 대리 지표 예시 | 작업 단위당 비교 예시 |
|---|---|---|
| 컴퓨팅 | 할당한 vCPU 시간(분) | 완료 거래당 할당 vCPU 분 |
| 저장소 | 할당한 GB | 같은 기간 완료 거래 수로 정규화한 할당 GB |
| 네트워크 | 전송한 GB | 완료 거래당 전송 GB |

대리 지표는 개선 대상 자원을 추적하는 수단이며 탄소 배출량의 직접 측정값은 아니다. AWS 대시보드도 자원 대리 지표와 carbon data export에서 가져온 배출 데이터를 구분한다. 따라서 비용 감소율이나 vCPU 시간 감소율을 같은 비율의 탄소 감축으로 바꾸어 적지 않는다.

캐시로 계산을 줄이면 저장소가 늘 수 있고, 전송량을 줄이려고 전처리하면 컴퓨팅이 늘 수 있다. 변경 전후에는 대상 자원의 총량과 작업당 지표, 비용 및 성능을 함께 비교한다. 다음은 적용 예다. 보고서 생성 캐시를 도입했다면 생성당 vCPU 시간 외에 캐시 저장량, 갱신 작업과 결과의 최신성도 확인한다. 절감 효과가 구현과 운영 비용을 넘는지 평가하고 보안, 신뢰성 요구를 유지한다.
