# 현재 맥락과 지식을 판단 및 학습으로 연결하기

> 기준: 2026-09-22 사용자 합의. AI의 판단과 학습 지원 방식에 관한 문서이며 사업 현황이나 학습 진도의 정본은 아니다.

사용자는 프로젝트에 사업과 업무의 맥락을 기록하고, 이 Vault에는 판단에 활용할 지식을 축적한다. AI는 두 자료를 연결해 현재 무엇을 판단해야 하는지, 어떤 지식이 필요한지, 그 지식이 왜 적용되는지 설명한다. 자료를 찾는 절차는 `development-context` 스킬, 근거의 역할은 [[Development-Ontology-Contract]]를 따른다.

## 자료마다 맡는 역할

| 자료 | 확인할 내용 | 판단에서의 역할 |
| --- | --- | --- |
| 현재 요청과 사용자 설명 | 목표, 변경된 상황, 이해하기 어려운 부분 | 이번 판단의 문제와 범위 |
| 프로젝트의 맥락 정본 | 현재 상태, 합의, 제약, 관찰과 미정 사항 | 지식을 적용할 조건 |
| Vault의 지식 원문 | 개념, 원리, 비교, 사례와 예외 | 선택지와 판단 근거 |
| AI의 해석 | 현재 조건과 원리의 연결, 대안과 비용 | 검토할 제안 |
| 사용자가 채택한 결정 | 선택, 이유, 범위와 재검토 조건 | 기록이 허용된 대상 정본에 반영할 결정 |

프로젝트 맥락은 조회할 때 해당 정본과 최신 사용자 설명으로 다시 확인한다. 과거 학습 문서에 남은 사업 상태를 현재 사실로 쓰지 않는다. 기록이 충돌하면 같은 대상과 사실을 다루는지, 무엇을 근거로 언제 확인했는지 대조한다. 미해결 충돌은 그대로 밝힌다.

검색 서버는 원문과 연결을 찾는 역할을 맡고, AI host는 원문을 읽어 적용 여부를 판단한다. 조회 성공, 문서 수와 링크 수만으로 판단의 정확성이나 사용자의 숙련을 증명할 수 없다.

## 맥락에서 판단으로 넘어가는 기준

판단 요청에는 중요한 선택을 중심으로 아래 연결이 드러나야 한다. 모든 답변에 같은 표를 강제하지 않으며 간단한 요청은 짧은 설명으로 충분하다.

| 연결 | 답변이 설명해야 할 것 |
| --- | --- |
| 현재 맥락 → 문제 | 지금 어떤 결정을 내려야 하며 무엇이 제약인가 |
| 문제 → 지식 | 어느 원문과 개념이 이 문제를 설명하는가 |
| 지식 → 적용 | 원문의 전제가 현재 조건에 맞는 이유와 맞지 않는 부분은 무엇인가 |
| 적용 → 선택 | 어떤 선택을 제안하며 대안에 비해 얻고 포기하는 것은 무엇인가 |
| 선택 → 재검토 | 어떤 사실이나 결과가 달라지면 판단을 바꿀 것인가 |

원문에 없는 연결은 AI의 해석으로 밝힌다. 근거가 부족하면 필요한 조건을 한정해 확인하거나 조건부 제안으로 남긴다. 사용자가 답한 내용과 접근 가능한 정본에 있는 사실을 반복 질문하지 않는다. 읽지 못한 자료를 확인했다고 표현하지 않는다.

Vault에서 지식이 충분히 나오지 않으면 검색 범위와 누락을 확인하고 필요한 원문을 직접 읽는다. 누락되거나 변할 수 있는 사실은 공식 외부 자료로 보완한다. 해당 분야에 지식이 없다고 단정하거나 검색 결과에 맞춰 질문의 의미를 바꾸지 않는다.

## 판단에서 학습으로 이어가기

학습 요청에서는 분야 목록보다 현재 결정에 필요한 능력을 먼저 설명한다. 사용자의 자가 진단이나 짧은 설명, 적용 질문으로 이해도를 확인하고, 어려운 부분과 선택에 미치는 영향에 따라 학습 후보를 좁힌다.

- 개념을 배우는 이유를 실제 결정과 연결한다. 예를 들어 현금흐름은 대금 수령과 비용 지급의 시점을 판단하는 데 연결할 수 있다.
- 추천 순서에는 현재 필요한 이유와 순서를 바꿀 조건을 붙인다. 추천을 확정된 학습 계획이나 사업 투자 결정으로 저장하지 않는다.
- 선택한 개념은 예시와 작은 적용으로 확인한다. 설명, 계산, 비교 또는 글쓰기 중 주제에 맞는 방식을 고르며 모든 주제에 사업 산출물을 요구하지 않는다.
- 배운 내용을 문서 없이 설명하거나 조건을 바꿔 적용할 수 있는지 확인한다. 한 번의 통과를 영구 숙련으로 보지 않고 후속 학습에서 짧게 다시 확인한다.
- 사업 성과와 학습 성과를 구분한다. 계약 체결이 회계 지식의 숙련을 뜻하지 않고, 개념을 설명했다고 제품의 사업성이 검증되는 것도 아니다.

학습 우선순위와 진행 상태를 기록할 때는 `fit/AGENTS.md`와 `fit/growth/learning/AGENTS.md`를 적용한다. 승인된 학습 기록은 해당 도메인에 두며, 이 가이드에는 개인의 진행률을 누적하지 않는다.

## 무엇을 지식으로 남길 것인가

프로젝트를 조사하는 과정에서 만든 목록과 추천은 그 자체로 영구 지식이 되지 않는다. 로컬 경로, 체크아웃 상태, 계약 진행과 당장의 학습 순서는 현재 작업에 필요한 맥락으로 읽는다. 별도 조사 보고서나 학습 계획의 보관을 요청받지 않았다면 이를 Vault의 관리 대상으로 추가하지 않는다.

남길 내용은 다른 프로젝트에서도 판단에 쓸 수 있는 개념, 적용 조건, 예외와 검증된 교훈이다. 기존 원문에 같은 설명이 있으면 중복 문서 대신 필요한 부분만 보완한다. 예를 들어 개별 외주 계약의 진행 상태 대신 견적에 수정 범위와 운영 지원 비용을 반영하는 방법을 가격 지식에 남긴다. 경험에서 얻은 해석은 적용 조건을 붙이며 실제 성과로 검증되지 않았다면 일반 법칙으로 표현하지 않는다.

## 외주와 자체 제품을 병행하는 상황의 예시

아래는 자료를 연결하는 방법을 보여주는 일반화한 사례다. 특정 프로젝트의 현재 상태나 고정된 학습 순서가 아니다.

| 확인할 맥락 | 찾아 검토할 지식 | 도출할 판단과 학습 후보 |
| --- | --- | --- |
| 홈페이지 계약을 체결하고 수행 중 | 프로젝트 원가, 손익과 현금흐름 | 대금, 남은 수행비와 지급 시점을 구분하는 능력 |
| 대표가 개발과 고객 대응을 함께 담당 | 기회비용, 가격과 업무 범위 | 직접 수행과 협업, 견적을 판단하는 능력 |
| 외주와 자체 제품을 함께 고려 | 자원 배분과 사업성 검증 | 현재 수입과 제품 검증에 시간과 돈을 배분하는 능력 |
| 사업 주체와 제품 브랜드를 구분 | 브랜드 구조, 포지셔닝과 구매 기준 | 대상별로 제공 가치를 설명하는 능력 |

이 표의 지식은 탐색 후보이며 해당 원문의 적용 검증을 대신하지 않는다. 실제 학습 순서는 현재 결정의 중요도, 미확인 조건과 사용자의 이해도를 확인한 뒤 제안한다. 예를 들어 지급 계획이 이미 정리되어 있고 다음 고객 확보가 당면 문제라면 영업과 마케팅을 먼저 다룰 수 있다.

프로젝트의 정본 위치는 해당 작업에서 확인하고 필요한 원문을 읽는다. 접근할 수 없으면 확인하지 못한 범위를 밝히고 판단을 바꿀 최소 정보만 묻는다. 계약 금액, 연락처와 비공개 운영 정보를 이 사례에 복제하지 않는다. 프로젝트 결정은 해당 프로젝트, 지식은 해당 지식 원문, 재사용할 판단 방식은 온톨로지 문서와 스킬에서 관리한다.
