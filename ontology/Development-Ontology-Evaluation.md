## 자연어 검색 관찰

입력은 다음 합성 요청이다. 실제 사용자 프로젝트나 과거 작업을 재현한 사례가 아니다.

Semble `search`를 저장소 루트 대상으로 `content=docs`, `top_k=6`, `max_snippet_lines=4`로 한 번 호출했다. 이 요청은 실패와 재시도를 직접 언급하므로 사용자가 고려사항을 말하지 않은 상황의 능동 제안 성능까지 평가하지 않는다.

비교할 필수 원문은 지도 설계 전에 이미 읽은 [[Transactional-Outbox]], [[Idempotent-Consumer]], [[Idempotency-Key]] 세 문서로 정했다. 정답 자료를 아는 설계 조정 사례이므로 이를 독립 평가로 사용하지 않는다.

이 응답의 상위 6개 파일에는 미리 정한 필수 원문 3개가 없었다. Semble 내부 색인 revision과 검색기 버전은 결과에 표시되지 않아 확인하지 못했다. 이 관찰만으로 검색 도구의 일반적인 성능이나 다른 질의의 결과를 단정하지 않는다.

## 스킬 행동 점검과 보완

정답과 기존 대화는 전달하지 않고 스킬 경로와 아래 요청만 별도 에이전트에 제공했다. 이 기록은 최초 2개, 보완 후 1개와 같은 사례의 최종 재점검이다. 설계자가 만든 시나리오이므로 일반적인 정확도나 독립 holdout 통과를 뜻하지 않는다.

| 요청 | 관찰한 결과 | 남은 한계와 보완 |
|---|---|---|
| 회원과 감사 레코드를 같은 MySQL 트랜잭션으로 저장하며 외부 전달은 없음 | Outbox와 Relay를 제외하고 트랜잭션/감사 원문을 추가로 찾음 | version과 UNIQUE 제약을 충분한 조건 없이 필수처럼 제안한 부분이 있어, 원문의 선택지를 현재 요구의 필수사항으로 옮기지 않는 기준을 스킬에 추가 |
| DB 저장 뒤 외부 알림 API를 호출하고 응답이 끊기면 재시도 | 외부 효과, 응답 불명확, 멱등 키와 재시도 원문을 찾음 | provider 지원을 확인하기 전에 멱등 키 사용을 지시하는 표현이 있어, 미확인 지원은 확인할 조건으로 제시하도록 보완 |
| 보완 후, 프로필과 이력을 같은 DB에 기록한 뒤 멱등 기능 지원이 불명확한 업체 API 호출 | 업체 멱등 키, 결과 조회와 웹훅 지원을 확인할 조건으로 제시함 | Relay의 claim과 lease를 조건 없이 요구하는 과도한 제안은 남음. 지도에 있는 다중 인스턴스와 claim 선택 조건을 답변에서도 보존하는지 추가 검증 필요 |

재점검 뒤에는 스킬에 제안별 `원문 전제 / 현재 확인된 조건 / 적용 상태`를 대조하는 단계를 추가했다. 특정 선택지를 채택한 뒤의 조건을 모든 구현의 필수 구조로 일반화하지 않는 기준도 명시했다.

그 뒤 같은 세 번째 요청을 새 에이전트로 다시 실행했을 때 업체 기능은 확인 조건으로 남았고, claim과 lease를 모든 Relay에 요구하는 표현도 나오지 않았다. 다만 재시도 횟수, 지연과 보존 기간을 한 문장에 묶어 기간끼리 비교하는 듯 표현하는 오류가 있었다. 이 문장은 기술 지식이나 권고로 채택하지 않으며, 값과 단위의 의미를 원문 및 실제 계약에 대조하는 검토가 여전히 필요하다.

코드가 제공되지 않았으므로 실제 버그 검출이나 구현 검증은 수행하지 않았다. 원문을 찾는 경로가 생겨도 적용 조건의 정확한 보존까지 보장되는 것은 아니다. 남은 과도한 제안을 해결했다고 표시하거나 현재 표본을 전체 통과로 처리하지 않는다.

## 다음 검증의 성공 기준

1. 실패나 패턴명을 직접 언급하지 않은 개발 요청에서도 관련 조건을 찾아 원문으로 설명한다.
2. 같은 DB 안에서 끝나는 작업과 외부 API 호출을 구분하며, 조건이 다른 방법을 기계적으로 추천하지 않는다.
3. 현재 코드로 확인한 사실과 자료에서 가져온 지식을 구분한다. 코드가 없으면 미확인으로 표시한다.
4. 사용자에게 이미 읽을 수 있는 사실을 재설명하도록 요구하지 않는다. 미기록 의도만 질문한다.
5. 기록된 기술 지식을 사용자의 선호나 채택 결정으로 승격하지 않는다.

실제 작업 사례가 생기면 필수 근거와 제외할 제안을 먼저 기록하고, 조정용 사례와 별도로 평가한다. 실행 구현의 parser, snapshot, query, MCP protocol 검증은 [[Ontology-Operations#runtime 검증]]을 따른다. 이 문서의 수동 관찰을 runtime 품질 또는 실제 버그 검출 결과로 해석하지 않는다.

## 상황 질문 4개로 조회기 확인

2026-09-05에 조회 구현을 읽지 않은 별도 작업자가 기존 원문에서 상황 질문 4개와 기대 파일/heading을 먼저 정했다. 질문과 정답은 `evaluation/cases.json`, 첫 실행의 전체 결과는 `evaluation/initial-report.json`에 보존한다. 이 표본은 실제 과거 개발 작업의 재현이 아닌 합성 질문이다.

첫 실행은 위 입력 commit, extractor 7, query 코드 SHA-256 `7dd089089488ad04668ea2d2c7838dbc02ff321bf3cefdabf218010dd4a92611`에서 했다. 요청 scope는 `tech`, 깊이는 1, 예산은 24,000 byte다. 원문은 Git commit에 고정했고 dirty worktree 상태를 결과에 표시했다.

| 상황 | 기대 문서 | 문서 포함 | 기대 heading 포함 |
|---|---|---|---|
| 인기 조회 결과가 사라질 때 요청 폭주 | [[Cache-Stampede]] | 아니오 | 아니오 |
| 배포 도중 처리 중인 요청 단절과 502 | [[Graceful-Shutdown]] | 예 | 예 |
| 같은 데이터를 반대 순서로 갱신하다 실패 | [[Lock-Deadlock]] | 예 | 아니오 |
| 큰 계산 중 다른 요청도 지연 | [[Thread-vs-Event-Loop]] | 아니오 | 아니오 |

기대 문서는 2/4, 기대 heading은 1/4였다. 응답은 13,154~15,145 byte, 실행 시간은 747~968ms였다. 관련된 다른 문서가 반환된 경우도 있으므로 이 일치율을 전체 의미 정확도로 해석하지 않는다. 문서와 section을 놓친 사례가 있어 긴 상황 설명만으로 필요한 지식을 충분히 찾는다고 주장하지 않는다.

이후 근거와 출력 예산, 링크 해석 오류를 수정했으며 같은 질문의 재실행은 회귀 관찰로 취급한다. 이미 결과를 본 표본을 새 독립 평가라고 부르지 않는다. 새로운 상황 표본은 별도로 준비해야 한다.

최종 extractor 9와 query 코드 `6e2bd9f82851e7749c0df234a23196523053a3a971dc24e88d1d1681729c0c49`의 재실행은 `evaluation/regression-report.json`에 보존했다. 기대 문서 2/4, 기대 heading 1/4로 같았으며 응답 13,945~18,236 byte, 실행 시간 706~844ms였다. 원문 근거와 예산 처리의 수정이 일반적인 의미 검색을 해결한 것은 아니다.

2026-09-07에 extractor 10과 현재 query 코드로 revision `bf77c848` 색인에서 다시 실행했고 결과는 `evaluation/regression-report-2026-09-07.json`에 보존했다. 기대 문서 2/4, 기대 heading 1/4로 같았고 응답 14,148~18,122 byte, 실행 시간 660~975ms였다. 이번 실행부터 기록하는 `relations_returned`는 4건 모두 0, `budget_exhausted`와 `traversal_limit_reached`는 모두 true였다. 같은 snapshot과 query에서 예산을 65,536 byte로 올린 대조에서는 기대 문서와 heading 일치 수가 그대로였고, 관계는 11~22개가 남았으며 `budget_exhausted`는 모두 false였다. 따라서 24,000 byte 예산은 관계 누락을 설명하지만 문서와 heading 미일치의 원인으로 단정할 수 없다. candidate ranking, root 상한 6개와 traversal 제한은 미일치의 원인 후보이며 각각의 영향은 분리 검증하지 않았다. 같은 날 clean worktree에서의 별도 실행도 일치 수가 같았다.

현재 스킬은 중요한 실패와 제약에서 검색 용어 후보를 추리고, 근거가 부족하면 표현을 바꾸거나 반환된 문서 경로와 heading으로 좁혀 다시 조회한다. 이는 재검색 절차이며 최초 일치율 개선을 검증한 결과는 아니다.

## 검색 순위와 관계 응답 보강

2026-09-07에 검색 순위와 응답 구성을 수정하면서 사례를 아래처럼 분리했다. 원문은 revision `8f99192e3253b3dcf1a2e135b9321bddd07d5727`에 고정했다. 질문은 실제 사용자 작업의 재현이 아닌 합성 표본이다.

| 사례 파일 | 수 | 용도와 한계 |
|---|---:|---|
| `evaluation/cases.json` | 4 | 기존 기술 회귀 질문. 원문 파일과 heading만 검사 |
| `evaluation/diagnostic-cases.json` | 2 | 짧은 Outbox 검색의 일반어 잡음과 24KB 내 관계 반환 검사 |
| `evaluation/holdout-cases.json` | 9 | 구현 담당과 분리해 선정한 첫 표본. tech, biz, econ, fit 각 2개와 명백한 무지식 토큰 1개. 첫 결과를 수정에 사용했으므로 이후 실행은 회귀 검사 |
| `evaluation/validation-cases.json` | 4 | 첫 표본의 회귀를 수정하는 동안 원문만 보고 별도로 선정한 두 번째 표본. 각 도메인 1개이며 구현 조정에 사용하지 않음 |

새 양성 사례는 허용 원문과 heading뿐 아니라 응답에 남아야 할 본문 문자열도 지정한다. 대안 원문 또는 section을 여러 개 허용할 수 있지만, 경로와 heading, 본문 조건은 같은 evidence unit에서 충족해야 한다. ATX와 Setext 제목만 남은 응답은 본문 적중으로 세지 않는다. 원문에 없는 기대 경로나 본문은 평가 시작 전에 오류로 처리한다.

첫 구현은 희소한 질의 토큰이 없는 문서를 제외했다. 첫 분리 표본에서 본문 적중이 6/8에서 4/8로 떨어졌고, 음성 사례를 포함한 통과 수는 7/9에서 5/9로 감소했다. 이 후보를 최종 개선으로 채택하지 않고 제외 규칙을 짧은 용어 검색으로 한정했다. 긴 자연어 질문은 기존 본문 점수로 후보를 유지한다. 첫 표본을 다시 독립 holdout으로 부르지 않는다.

관계는 양 끝 entity, 소유 문서와 해당 원문 근거를 함께 넣을 수 있을 때 반환하도록 바꿨다. 관계만 제거된 뒤 전용 근거나 entity가 남는 경우와, 같은 문서의 직접 근거 하나를 줄이면서 소유 문서를 지우는 예산 경계도 회귀 검사에 포함한다. 원문 근거는 기존 byte anchor와 hash를 유지하며, excerpt가 원문 section 전체보다 짧으면 `truncated`로 표시한다.

최종 전후 비교는 `evaluation/retrieval-comparison-2026-09-07.json`에 둔다. 동일 사례와 snapshot에 대한 변경 전, 폐기한 첫 후보, 최종 코드 결과를 구분하고 각 query 코드와 사례 파일의 hash를 기록한다. 실행 중 원문은 커밋에 고정되고 코드 변경은 미커밋이므로 결과의 `unindexed_worktree`를 보존한다.

| 최종 비교 항목 | 변경 전 | 변경 후 |
|---|---:|---:|
| 기존 4개 질문의 기대 문서 / heading | 2/4, 1/4 | 2/4, 1/4 |
| 기존 4개 질문의 반환 관계 수 | 각 0개 | 각 4~5개 |
| 짧은 검색 진단 통과 | 0/2 | 2/2 |
| 첫 표본 재실행의 본문 적중 | 6/8 | 7/8 |
| 첫 표본 재실행의 전체 조건 통과 (음성 1개 포함) | 7/9 | 8/9 |
| 두 번째 분리 표본의 본문 적중 | 3/4 | 3/4 |

진단의 `outbox pattern`은 금지한 UX 문서 2개가 응답에서 빠졌고 관계 2개가 남았다. 한국어 정확 alias 조회는 관계 5개를 반환했다. 모든 비교는 24,000 byte 안에서 실행했다. 기존 상황 질문과 두 번째 표본의 적중 수는 같으므로 일반적인 자연어 검색 성능이 향상됐다고 결론짓지 않는다.

본문 문자열 적중은 제한된 회귀 기준이다. 모든 관련 원문을 정답에 열거한 것은 아니며, 조건과 예외를 보존한 최종 답변인지, 불필요한 기술을 권하지 않는지, 실제 작업 시간을 줄이는지는 별도 평가가 필요하다. 두 번째 표본 역시 이후 조정에 사용하면 회귀 표본으로 전환하고 새 질문을 준비한다.

## 필수 근거와 잘린 예외의 진단

2026-09-07에 `kino-doc`의 일반화 가능한 설계 인사이트를 [[Ontology-Evidence-Lifecycle]]에 대조하고, 평가기에 모든 필수 그룹과 같은 본문의 필수 문구를 검사하는 기능을 추가했다. 단위 테스트는 82개 모두 통과했고 기존 짧은 검색 진단도 2/2를 유지했다. 이 테스트 통과와 아래 실제 조회의 근거 완전성은 서로 다른 검증이다.

`evaluation/context-integrity-cases.json`의 세 질문은 원문 경로와 heading을 알고 만든 합성 진단이다. 독립 holdout이나 일반적인 자연어 검색 평가는 아니다. 원문은 revision `6f80dbe387b73a56e8642bf2824e27706abb0e2a`에 고정했고, 결과와 코드/사례 hash는 `evaluation/context-integrity-report-2026-09-07.json`에 보존했다. 새 문서와 코드 변경은 미커밋이라 `unindexed_worktree`를 유지했다.

| 진단 | 조회 응답의 필수 그룹 충족 | 별도 전체 section 읽기로 보완 후 |
| --- | ---: | ---: |
| 자료 역할과 문서 작성 상태 구분 | 0/1 | 1/1 |
| 원문 연결과 현재 구현 확인의 경계 | 1/2 | 2/2 |
| 제안의 비용과 미확인 조건 보존 | 1/1 | 1/1 |

세 질문 모두 문서와 heading은 찾았지만, 최초 발췌만으로 모든 조건을 충족한 질문은 1/3, 필수 그룹은 2/4였다. 앞의 두 질문은 해당 section이 잘려 필요한 문장이 반환되지 않았다. 기존의 대안 하나 적중만 보는 평가와 문서/heading 적중만으로는 이 누락을 충분히 구분할 수 없다.

누락한 두 section은 반환된 revision, path와 byte anchor로 Git blob을 별도로 읽고 `content_hash`를 대조했다. 같은 필수 근거 검사를 전체 section 본문으로 보완하면 3/3 질문과 4/4 그룹을 충족했다. 이는 사람이 정한 진단에 원문 읽기를 추가한 확인이며, MCP가 자동으로 전체 section을 반환하거나 모델이 자동으로 후속 읽기를 수행했다는 결과가 아니다. 원래 응답과 보고서는 수정하지 않았다.

현재 조회기의 1,400 byte 발췌 상한은 유지된다. 중요한 잘린 근거를 전체 원문으로 보완하는 절차를 두 `development-context` 스킬에 반영했으며, 실제 과업에서의 자동 사용과 최종 판단 품질은 아직 별도 검증이 필요하다. 이 진단의 `--check` 실패를 숨기거나 검색 누락을 해결한 것으로 기록하지 않는다.

## MCP 후속 읽기로 필수 근거 회수

같은 날 [[Ontology-Evidence-Read]]의 `context_read`를 구현하고, 새 SDK stdio 연결에서 `tools/list`, `context_lookup`과 후속 읽기를 실행했다. 원문은 revision `19df3d8159689f41ab8d5a2b5def14c864016cf8`에 고정했다. `evaluation/read-followup.mjs`는 위 세 진단을 재사용하며, 정답을 보고 후속 대상을 고르지 않고 반환된 근거 중 `truncated: true`인 항목을 모두 읽는다. 결과와 실행 코드/사례 hash는 `evaluation/evidence-read-report-2026-09-07.json`에 보존한다. 코드와 문서 수정은 미커밋이라 `unindexed_worktree`를 유지했다.

| 항목 | 첫 조회 | 후속 읽기 후 |
| --- | ---: | ---: |
| 모든 조건을 충족한 질문 | 1/3 | 3/3 |
| 충족한 필수 근거 그룹 | 2/4 | 4/4 |
| 잘린 채 남은 근거 | 2개 | 0개 |

첫 조회 3회의 JSON payload는 합계 12,108 byte였고, 후속 읽기 2회는 합계 6,821 byte였다. 각 응답은 요청 예산 24,000 byte 이내였다. 이 수치는 MCP envelope를 제외한 payload 크기이며, 여러 호출의 근거를 합친 평가 본문을 단일 MCP 응답으로 계산하지 않는다. 각 후속 원문의 ID/revision/hash, byte 연속성, 전체 길이와 SHA-256을 대조했다. 근거당 32페이지와 전체 읽기 응답 1MiB의 중단 조건에 걸린 사례는 없었다. 이 두 section은 각각 한 페이지에 담겼으며, 여러 페이지 연결은 별도 runtime fixture로 검증했다.

재실행은 `ontology/`에서 `node src/cli.mjs build --committed-only --cache <저장소-밖-cache>`로 snapshot을 준비한 뒤 `node evaluation/read-followup.mjs --cache <같은-cache> --check`로 한다. `--cases`로 다른 사례 파일을 지정할 수 있다. 실패한 첫 조회 보고서는 그대로 유지하며 후속 읽기 결과로 덮지 않는다. 이 결과는 이미 알려진 진단의 근거 회수 회귀 검사다. 모델이 스스로 도구를 선택하는지, 일반적인 검색 적중이나 실제 작업의 판단 품질이 개선되는지는 확인하지 않았다.
