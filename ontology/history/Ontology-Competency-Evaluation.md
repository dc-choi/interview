# 타입 스키마 도입과 판단 질문 평가

2026-11-19에 schema 2(타입 개념, 정의역과 치역이 있는 관계, 검증, 개념 질의)를 도입하면서 관측한 결과와 한계를 기록한다. 현재 계약은 [[Ontology-Schema]]와 [[Ontology-Concept-Query]]를 따른다.

## 측정 대상

모든 측정은 `HEAD` `1fa6f657`에 미커밋 `ontology/` 변경(선언 문서와 이 문서를 포함한 새 문서)을 임시 clone에서 커밋해 build한 snapshot에서 수행했다. 실제 저장소의 커밋에서 재현한 결과가 아니다. 아래 표는 검증에서 나온 수정을 모두 반영한 마지막 build의 값이다.

| 항목 | 값 |
| --- | --- |
| 문서, 근거 단위, 관계 | 5,358, 53,655, 113,627 |
| 개념 | 547 (Topic과 Category 421, 판단 개념 126) |
| 작성 가능 predicate의 관계 | 493 (선언한 판단 관계 127, `broader` 113, 선언의 `evidence`에서 파생한 `supported_by` 253) |
| 태그 대응 | 서로 다른 태그 4,225개 중 384개. 어휘 작성 시 집계한 사용 횟수 기준 대응률은 66.4%(22,972회 중 15,256회)이며, 그중 426회는 Topic이 아닌 Category 개념에 대응한다. 어휘 검증 뒤의 수정(개념 3개 삭제, 1개 추가)은 이 비율에 반영하지 않았다 |
| 카테고리 미대응 | 0 |
| 온톨로지 gap | 0 (`validate` 종료 코드 0) |

선언이 없는 `HEAD` `1fa6f657`을 schema 1 코드와 schema 2 코드로 각각 build해 비교했다. 문서 5,339개, 근거 단위 52,905개, 관계 91,087개, gap 0으로 같다. `entities.jsonl`의 SHA-256은 양쪽 모두 `49761d55...b75891`이고, `relations.jsonl`은 `extraction_version`을 가리면 차이가 0줄이다. 이 동일성은 `ontology_relations`가 없는 저장소에서 성립한다. `supported_by`, `contradicted_by`, `mentions`를 Document나 Section 사이에 선언한 저장소는 schema 2에서 정의역 또는 치역 위반이 된다.

## 후보 검증

이벤트 발행 영역의 원문 12개에서 후보 267건을 추출하고, 제안자와 다른 검증 에이전트가 세 차례 원문과 대조했다.

| 종류 | 승인 | 반려 |
| --- | --- | --- |
| 개념 | 126 | 5 |
| 관계 | 127 | 9 |

반려 사유는 원문에 없는 계층 관계, 특정 제품 설정을 일반 접근에 붙인 관계, 평가 질문을 그대로 옮긴 관계, 승인된 관계가 남지 않은 개념이다. 기록은 `ontology/candidates/event-publishing.jsonl`에 있고 `candidates --check`는 267줄에서 문제 0건이다.

1차 추출은 개수 목표(개념 15~30개)를 준 탓에 원문을 덜 다뤘다. 원문 전체를 범위로 준 2차 추출에서 192건이 추가됐다. 통제 어휘의 alias와 `broader` 판단은 별도 검증을 거쳤으며 결과는 아래 검증 절에 기록한다.

## 판단 질문

사례는 `ontology/evaluation/competency-cases-2026-11-19.json`의 24건이다. 보정용 12건과 미공개용 12건이며, 분할마다 `addresses`, `requires`, `has_tradeoff`, `alternative_to`에 3건씩이고, 그 12건 중 2건은 결과가 없어야 하는 부정 사례다. 파일의 SHA-256은 `9bcb76926bdf70863cc8cbcba74e851464c8b2e8d9968ee8bb2a91ffc4064209`다.

실행기 `evaluation/competency.mjs`는 두 방식을 같은 사례에 실행하고, 기대한 (원문, heading) 근거 중 반환된 비율을 점수로 삼는다.

- **문장 조회**: 질문 문장을 `context_lookup`에 24,000 byte 예산으로 전달한다.
- **개념 질의**: 사례의 `start` 개념과 `predicate`를 `context_concept`에 depth 2로 전달한다.

개념 질의에는 시작 개념과 predicate를 사례가 알려 준다. 문장 조회는 이 정보를 받지 않는다. 따라서 두 점수의 차이는 검색 품질의 우열이 아니다. 구조 질문에 구조 질의로 답할 수 있는지를 확인하는 측정이다.

| 분할 | 실행 | 문장 조회 | 개념 질의 | 용어 점수 | 개념 해석 |
| --- | --- | --- | --- | --- | --- |
| 보정 | 1차 | 0.167 | 0.750 | 0.308 | 8/12 |
| 보정 | 2차, 3차 | 0.167 | 0.833 | 0.508 | 10/12 |
| 미공개 | 1차 | 0.139 | 0.347 | 0.350 | 4/12 |
| 미공개 | 2차, 3차 | 0.222 | 0.431 | 0.350 | 4/12 |

위 표는 부정 사례를 합친 평균이라 개념 질의에 유리하다. 부정 사례 4건에서 개념 질의는 시작 이름이 해석되지 않아 전부 빈 결과로 통과했고, 문장 조회는 질문 문장에 겹치는 단어가 있으면 항상 근거를 반환하므로 전부 실패했다. 아무것도 반환하지 않는 시스템도 이 평균에서 0.167을 얻는다. 검증에서 이 점이 지적돼 실행기가 긍정과 부정 사례를 따로 보고하도록 고쳤다. 3차 실행의 분리 결과는 다음과 같다.

| 분할 | 긍정 사례의 문장 조회 | 긍정 사례의 개념 질의 | 이름이 해석된 긍정 사례 | 해석된 사례만의 개념 질의 |
| --- | --- | --- | --- | --- |
| 보정 | 0.200 | 0.800 | 10/10 | 0.800 |
| 미공개 | 0.267 | 0.317 | 4/10 | 0.792 |

개념 질의의 수치는 상한에 가깝다. 사례가 시작 개념의 이름과 predicate를 알려 주는데, 이 둘은 실제 작업에서 AI가 질문으로부터 스스로 정해야 하는 단계다. 미공개 긍정 사례에서 두 방식의 차이는 0.05이고 사례는 10건이므로 우열을 말할 수 없다.

1차와 2차 사이의 변경은 셋이다.

- 보정 사례에서 해석되지 않은 표현 2개를 alias로 추가했다(`dual-write-problem`, `row-level-claim`).
- 미공개 사례 1건의 기대 heading에서 backtick을 제거했다. 색인이 heading의 backtick을 제거해 저장하므로 원래 표기는 어떤 방식으로도 맞을 수 없었다. 미공개 개념 질의 점수의 변화(0.347에서 0.431)는 이 수정에서 나왔다.
- 검색어 확장을 껐다. 미공개 문장 조회 점수의 변화(0.139에서 0.222)는 이 변경에서 나왔다.

3차 실행은 검증에서 나온 수정(허용 범위 처리, 후보 순위, 관계 병합, 실행기의 분리 보고)과 어휘 수정을 반영한 뒤의 실행이며 합산 점수는 2차와 같다. 미공개에서 이름이 해석되지 않은 6건 중 2건은 2차 실행 시점에 부분 일치 후보를 받았다. 실행기는 후보를 따라가지 않는다.

## 결과의 해석

- 개념이 해석된 사례에서는 선언된 관계가 기대 근거로 이어졌다. 보정 점수는 선언을 그 질문들을 보며 다듬은 결과라 일반화 근거로 쓰지 않는다.
- 미공개 점수가 낮은 주된 원인은 이름 해석이다. 질문이 쓰는 표현과 선언된 label, alias가 정확히 같지 않으면 개념 질의가 시작되지 않는다. 미공개 사례를 보고 alias를 추가하지 않았으므로 이 수치는 그대로 둔다.
- 용어 점수는 기대 용어가 상대 개념의 label에 포함되는지를 본다. 원문 표현과 label이 다르면 근거가 맞아도 0이 된다.
- 문장 조회 점수가 낮은 것은 기대 근거를 (원문, heading) 정확 일치로 채점하기 때문이기도 하다. 같은 문서의 다른 절을 반환해도 0이다. 문장 조회는 scope 없이 전체 범위로 실행했다.
- 개념 질의는 개념의 정의 근거도 점수에 넣는다. 이름만 해석돼도 predicate와 무관하게 점수 일부를 얻을 수 있다.
- 미공개 사례 1건의 시작 표현 `stale update`는 선언의 alias와 같고 원문의 표기(`오래된 update`)와는 다르다. 이 alias는 질문을 보지 않은 2차 추출 작업자가 제안했지만 유출 가능성을 배제할 근거는 없다. 3차 실행의 사례별 점수로 계산하면, 이 사례를 0점으로 둘 때 미공개 긍정 사례의 개념 질의는 0.25(10건)이고 사례를 뺄 때 0.278(9건)이다.

## 검색어 확장의 측정

개념 label로 `context_lookup`의 검색어를 넓히는 확장은 구현 작업자가 같은 snapshot에서 켜고 끈 결과를 비교했다. 이 절의 사례 묶음 수치는 메인 세션에서 재현하지 않았다.

- 정답 문구가 아직 있는 기존 사례 묶음 6개의 엄격 채점에서는 나빠진 묶음이 없었다.
- 115건 전체를 경로와 heading으로 느슨하게 채점하면 4건이 좋아지고 3건이 나빠졌다. 양쪽 모두 긴 질문 안의 한 단어가 넓은 Topic(결제, DB, 투자)에 걸린 경우였다.
- 판단 질문의 미공개 문장 조회는 켰을 때 0.139, 껐을 때 0.222였다. 이 수치는 메인 세션의 1차와 2차 실행과 일치한다.

개별 사례가 나빠졌으므로 `CONCEPT_QUERY_EXPANSION = false`로 출하했다. 다시 켜려면 넓은 Topic의 한 단어 일치를 제외하는 규칙을 넣고 기존 사례 묶음을 전후 비교한다.

## 검증

- `npm test`는 190건 통과다(schema 1 기준 153건). 검증 전 181건 시점의 두 번의 전체 실행 중 한 번은 기존 동시성 테스트 `concurrent builds retry when the previous cache lock disappears`가 `cache lock is not a valid owner symlink`로 실패했다. lock 코드의 변경은 0줄이고 단독 3회와 이후의 전체 실행은 모두 통과했다. 원인은 조사하지 않았다.
- hook 자체 테스트 `python3 .claude/hooks/test_vault_guard.py`는 `ok`로 통과했다.
- 코드 2개 영역과 통제 어휘는 구현자와 다른 검증 에이전트가 반증 관점에서 검토했다. 코드 검증 에이전트 둘은 실행 권한이 없어 소스와 데이터를 읽어 판정했고, 재현은 수정 작업자와 메인 세션이 했다. 지적과 조치는 아래 표와 같다.

| 영역 | 확정 결함 | 조치 |
| --- | --- | --- |
| schema, parser, 검증, hook | hook이 본문 코드 블록의 예시도 선언으로 인식해 자동 학습이 고치는 문서 1개가 이미 검증 대상이었다. 선언 문서의 삭제와 `ontology/instances/` 경로는 검증하지 않았다. 순환 판정이 목록 위치에 따라 달라졌다. 근거 없는 첫 선언이 slug를 선점했다. 후보 검사가 반려 줄을 schema로 검사했다. 통과와 실패를 구분하지 못하는 테스트가 있었다 | 모두 고쳤고 각 수정에 실패를 재현하는 테스트를 붙였다. `undeclared_category`는 Category 선언이 바뀐 커밋에서만 막도록 바꿨다. 근거가 가리키는 원문을 고치는 커밋은 검사하지 않기로 하고 [[Ontology-Schema#검증 명령과 커밋 차단]]에 사각으로 기록했다 |
| 개념 질의, 조회 연결, 평가 실행기 | 허용 범위 밖 문서가 선언한 관계가 근거 없이 반환됐다(당시 데이터로는 발생하지 않음). 선언 위반 gap의 문구가 범위 밖 개념을 언급할 수 있었다. 부분 일치 후보와 조회의 개념 목록이 ID 순으로 잘려 핵심 개념이 빠졌다. 같은 관계의 두 번째 근거가 버려졌다. 평가가 부정 사례를 합산했다 | 모두 고쳤다. 조회의 개념 목록은 근거를 담고 남은 byte에만 담기므로 24,000 byte 예산에서는 0개 또는 1개만 실린다. 이 한계는 [[Ontology-Concept-Query#context_lookup과의 연결]]에 기록했다 |
| 통제 어휘 | 같은 대상의 중복 개념 2건(`integrations`, 면접 준비 Category), 틀린 alias 1건(`retention`의 `리텐션`), 서로 다른 두 태그가 한 키로 합쳐진 개념 1건(`querydsl`), 틀린 계층 1건(`inheritance`의 상위 `oop`) | 5건을 고치고 `micro` Topic을 추가했다. 한 태그가 여러 뜻으로 쓰여 어휘로 나눌 수 없는 개념은 [[Ontology-Vocabulary#뜻이 섞인 개념]]에 기록했다. 문서의 태그는 고치지 않았다 |
| 2차 검증(수정분과 문서) | 출하를 막는 코드 결함은 없었다. 문서가 추론을 규칙 4종으로 한정한다고 적었으나 하위 개념의 문서 전파가 더 있었다. 관계 수 493이 parser가 만든 근거 연결 253을 포함한다는 설명이 없었다. 이 기록의 수치 4곳과 옛 계약을 서술한 문장들이 코드와 달랐다. 후보 검사가 `subject` 생략을 통과시켰다 | 문서를 고쳤고 후보 검사가 `subject` 생략을 문제로 보고하게 했다. `--staged` 비교가 같은 모양의 위반 교체를 놓치는 점과 hook이 따옴표로 적은 key를 인식하지 못하는 점은 고치지 않고 [[Ontology-Schema#검증 명령과 커밋 차단]]에 사각으로 기록했다 |

## 한계

- 판단 개념은 이벤트 발행 한 영역에만 있다. 다른 영역의 구조 질문에는 `concept_not_found`가 정상이다.
- 사례와 기대 근거는 AI가 작성했다. 사람이 채점한 정답이 아니다.
- 미공개 분할의 독립성에는 흠이 있다. 질문 내용이 사례 작성 보고를 통해 메인 세션에 노출됐다. 2차 후보 추출 작업자에게는 질문을 보여 주지 않았다. 검증 에이전트가 미공개 사례를 그대로 옮긴 alias 하나와 관계 하나를 발견해 제거했다. 미공개 분할은 구현 작업자와 메인 세션이 각각 실행했고 2차로 한 번 더 실행했다.
- 개념 질의가 실제 작업에서 답변을 개선하는지는 측정하지 않았다. 측정한 것은 근거 회수다.
- 색인은 커밋된 내용만 읽는다. 이 기록의 수치는 선언 문서가 커밋된 뒤 실제 `HEAD`에서 다시 확인해야 한다.

## 후속 작업

- 미공개 분할을 새로 만들고, 이름 해석 실패를 줄이는 방법(부분 일치 후보의 자동 선택 기준, alias 보강)을 보정 분할로만 조정한다.
- MySQL 범위의 binlog 보존 조건, relay 방식과 `transactional-outbox`의 관계처럼 반려한 항목을 범위를 한정한 개념으로 다시 제안한다.
- 방법이 문제를 남겨 둔다는 서술을 담을 predicate가 없다. 필요한 사례가 쌓이면 schema에 추가한다.
- 미대응 태그 3,841개 중 사용 빈도가 높은 것부터 어휘에 추가한다.
