# 추천시스템 선언과 LLM 호스트 측정

2026-11-21에 판단 개념과 관계를 이벤트 발행 밖으로 넓혀 추천시스템 문서에 선언하고, 그 효과를 실제 질의 형태의 미공개 질문과 LLM 호스트 시뮬레이션으로 쟀다. 전체 지식 문서로 넓히기 전에 비용과 이득을 재는 1단계였다.

## 왜 추천시스템인가

이 기기의 Claude Code 세션 기록에 남은 실제 호출은 18건이었다. `context_lookup` 17건은 모두 12~33단어의 키워드 나열이었고, 개념 이름을 넣어 `context_concept`를 부른 호출은 시험 1건뿐이었다. 중복을 뺀 실제 질의 10건을 2026-11-21 색인으로 다시 돌리면 10건 모두 `concepts`가 비어 있었다. 질문은 추천시스템, 커머스, 광고, 커리어와 AI 엔지니어링 영역이었고, 판단 선언은 이벤트 발행 영역에만 있었다. 이름 해석보다 선언 범위가 먼저라고 보고, 실제 질의에 나왔고 학습 목표와도 맞는 추천시스템을 골랐다. 실제 질의의 원문은 이 저장소에 남기지 않는다.

## 선언

| 항목 | 값 |
| --- | --- |
| 원문 | `tech/architecture-design/recommendation-system/`의 지식 문서 25개(색인 7개, 학습 계획과 설계 제안 각 1개 제외) |
| 후보 | 다섯 묶음 1,588건. 추출자는 평가 질문과 이 기록을 읽지 못했다 |
| 검증 | 묶음마다 문서 기준으로 둘로 나눠 검증자 10명이 원문과 대조했다. Fable 5.2 사용 한도로 모두 Opus 5.5가 맡았다(`reviewed_by`에 기록) |
| 반려 | 120건(7.6%). 이벤트 발행 때의 약 22%보다 낮다. 추출 지침에 이전 반려 사유를 미리 넣었다 |
| 묶음 병합 | 같은 slug 15쌍과 검증자가 같은 대상으로 짚은 다른 slug 쌍을 합쳐 61개를 정리했다. 합쳐진 쪽의 label과 alias는 충돌하지 않으면 남은 쪽 alias로 옮겼다 |
| 결과 | 선언 1,403건을 `Instances-Recommendation-System-*` 11개 문서에 담았다. 색인 전체의 개념은 691개에서 1,511개, 타입 관계는 891개에서 2,877개, 선언 위반 0건 |

같은 slug인데 클래스가 다른 쌍(`common-genre-dominance`, 한쪽은 Tradeoff, 한쪽은 Problem) 하나는 합치지 않고 한쪽 slug를 바꿨다.

## 기계 측정

평가 질문은 선언과 후보를 보지 않은 작성자가 실제 질의 형태(키워드 나열)로 만든 20건이다(`competency-cases-2026-11-21-recsys.json`, 긍정 16, 부정 4, 네 predicate 각 4건).

| 방식 | 선언 전 | 선언 후 |
| --- | --- | --- |
| 문장 조회 | 0.719 | 0.719 |
| 조회와 bridge의 합 | 0.719 | 0.719 |
| bridge 긍정 / 부정 | 0 / 1 | 0.250 / 0.25 |
| `concepts`를 받은 질문 | 0 | 19 |
| bridge가 기대 이름을 돌려준 비율 | 0 | 0.063 |

키워드 나열 질의에서는 문장 조회만으로 0.719였고, 개념 경로가 문장 조회가 못 찾은 근거를 더한 사례는 없었다. 선언을 넣은 뒤 이벤트 발행 묶음은 기본 묶음이 그대로였지만 unseen-a의 follow가 0.750에서 0.667로, unseen-b의 bridge 부정 점수가 0.75에서 0.5로 떨어졌다. 새 개념이 이름 후보와 힌트 자리를 차지한 영향으로 보인다.

## LLM 호스트 측정

기계적인 bridge는 관계가 있는 첫 힌트를 고르므로 실제 호스트보다 불리할 수 있다. 그래서 Opus 5.5가 질문만 받고 CLI로 조회, 검색과 읽기를 해 답하고 근거 절과 답 이름을 적게 했다. 조건 A는 개념 질의를 쓰지 않고 힌트를 무시하며, 조건 B는 개념 질의와 힌트를 쓴다. 같은 사례를 한 에이전트가 두 조건으로 풀지 않도록 조건마다 에이전트를 나눴고, 질문당 명령은 4번까지 허용했다. 에이전트는 정답과 평가 폴더를 읽지 못했다.

| 묶음 | 조건 | 근거 | 답 이름 | 부정 정답 | 명령 수 |
| --- | --- | --- | --- | --- | --- |
| 추천시스템 | A | 1.000 | 0.635 | 4/4 | 44 |
| 추천시스템 | B | 1.000 | 0.656 | 4/4 | 42 |
| 이벤트 발행 unseen-b | A | 0.722 | 0.625 | 4/4 | 27 |
| 이벤트 발행 unseen-b | B | 0.653 | 0.542 | 4/4 | 35 |

- 호스트가 직접 읽고 판단하면 문장 조회만으로 추천시스템의 기대 근거 절을 모두 찾았다. 기계 측정의 문장 조회 점수가 낮았던 것은 호스트가 읽고 고르는 단계가 빠졌기 때문이다.
- 개념 질의를 더한 이득은 추천시스템 답 이름 +0.021로 사례 한 건에 못 미친다. 이벤트 발행에서는 근거와 답 이름이 사례 한 건 정도 낮고 명령은 30% 더 썼다.
- 사례가 묶음당 12~16건이고 호스트 모델은 Opus 하나다. 작은 모델이 호스트일 때는 재지 않았다.

## 비용

에이전트가 보고한 토큰으로 추출 약 185만, 검증 약 366만, 평가 질문 작성 약 29만, 호스트 시뮬레이션 약 134만을 썼다. 선언까지의 비용은 원문 문서당 약 23만 토큰이고, 같은 방식으로 지식 문서 약 4,200개 전체를 하면 약 10억 토큰이다.

## 결론과 결정

판단 선언의 병목은 범위나 이름 해석이 아니었다. 실제 질의 형태에서는 문장 조회가 근거를 찾고 LLM 호스트가 대안, 조건과 비용을 스스로 읽어 내므로, 개념 질의가 더하는 것은 측정 범위 안에서 거의 없다. 이 결과를 보고 사용자는 검증을 통과한 추천시스템 선언을 지식 구조로 커밋하기로 했다. 같은 방식의 전체 확장은 이 측정만으로는 근거가 없으므로, 넓힐 때는 작은 호스트 모델이나 다른 질문 유형에서 이득이 있는지를 먼저 잰다.
