# 개발 판단 지식의 연결 계약

> 상태: 2026-09-05. Markdown 구조를 결정론적으로 색인하고 조회하는 최소 실행 경로가 있다. 의미 추론과 코드 저장소 색인은 후속 설계다.

## 목표와 자료의 역할

현재 작업에서 관련 지식을 먼저 찾아 적용 조건을 검토하고, 근거와 비용이 있는 개선안을 제안한다. `interview`는 지속해서 축적할 개인 지식 기반이다. `kino-doc`은 회사에서 진행한 업무 기록이며 이번 파일럿의 수집 대상이 아니다.

자료가 저장되어 있다는 사실만으로 그 내용이 사용자의 선호나 모든 프로젝트의 규칙이 되지는 않는다.

| 역할 | 판별 근거 | 개발 판단에서의 사용 |
|---|---|---|
| 사용자 규칙 | 현재 요청과 적용되는 `AGENTS.md` | 해당 범위의 작업 제약 |
| 학습 지식 | 기술 원리, 패턴, 비교와 참고 문서 | 적용 여부를 검토할 선택지와 근거 |
| 프로젝트 결정 | 채택 사실, 대상 프로젝트와 이유가 명시된 기록 | 해당 프로젝트와 시점에 적용할 기준 |
| 경험 기록 | 당시 상황, 관찰과 결과 | 현재 조건과 비교할 사례 |
| AI 제안 | 아직 채택되지 않은 가설과 개선안 | 현재 근거로 검토할 후보 |
| 온톨로지 기록 | `ontology/`의 설계, 운영과 평가 문서 | 조회 계약과 관찰의 근거, 학습 원리나 현재 구현, 실행 사실과는 별도 확인 |

한 문서에 역할이 섞이면 section이나 주장 단위로 구분한다. `status: done`은 문서 작성 상태이며 기술 채택이나 현재 동작을 뜻하지 않는다. 프로젝트와 적용 시점이 없는 결정은 전역 규칙으로 해석하지 않는다.

## 첫 개념과 관계

아래 이름은 사람이 읽는 지도에 사용할 내부 어휘다. 실행 색인은 `Document`, `Section`, `RelationAssertion`, `contains`, `links_to`를 사용하며 이 지도는 그것을 교체하지 않는다.

| 개념 | 담을 내용 |
|---|---|
| 문제 `Problem` | 현재 요청에서 해결하려는 실패, 제약 또는 목표 |
| 방법 `Approach` | 원문이 설명하는 해결 방법이나 설계 선택지 |
| 조건 `Condition` | 방법의 적용 여부를 바꾸는 전제와 제외 조건 |
| 비용 `Tradeoff` | 추가 운영, 구현 복잡도, 지연과 포기하는 성질 |
| 근거 `EvidenceUnit` | 원문 파일과 heading, 확인 시 revision |

| 관계 | 방향 | 필요한 한정 |
|---|---|---|
| 해결 후보 `addresses` | 방법 → 문제 | 어떤 조건에서 문제를 완화하는가 |
| 적용 전제 `requires` | 방법 → 조건 | 조건을 확인할 원문 또는 코드 위치 |
| 동반 비용 `has_tradeoff` | 방법 → 비용 | 비용이 발생하는 상황 |
| 비교 대상 `alternative_to` | 방법 → 방법 | 같은 문제를 다루는 범위와 차이 |
| 근거 `supported_by` | 검토 항목 → 원문 단위 | 해당 항목을 실제로 지지하는 section |

`requires`는 문맥에 한정된 전제다. 논리 추론기의 공리나 모든 구현에 대한 필수 조건으로 사용하지 않는다. 이 파일럿은 관계의 역방향, 추이성과 대체 가능성을 자동 추론하지 않는다.

## 검토 항목의 최소 내용

지도에는 아래 내용을 짧은 표나 항목으로 기록한다. 본문을 복사하거나 기존 문서 전체에 새 frontmatter를 일괄 추가하지 않는다.

- **상황**: 어떤 개발 요청과 관찰에서 이 항목을 찾아야 하는가.
- **고려사항**: 검토할 문제와 해결 후보.
- **적용 조건과 비용**: 조건이 맞지 않을 때의 대안 또는 제외 이유.
- **근거**: 실제 원문 파일과 heading. 지도 작성 기준 revision은 문서에 기록한다.
- **현재 확인할 것**: 소스, 호출부, 테스트, 설정이나 운영 근거에서 확인할 조건.
- **판단 상태**: 검토 후보, 조건 충족, 조건 불충족 또는 근거 부족.

조회 시 상태는 해당 요청의 작업 메모에 둔다. 현재 코드와 확인 시점이 달라지면 이전의 조건 충족 판단을 그대로 재사용하지 않는다.

## 근거 확인과 채택의 경계

- 위키링크가 해석된다는 것은 원문 연결이 존재한다는 뜻이다. 그 자체로 의미 관계나 현재 코드의 적합성을 증명하지 않는다.
- `links_to`의 선택적 `link_role`은 기존 목차 소속, 상위 문서, 관련 문서 표기를 구분하는 구조 정보다. 폴더 소속이나 링크 역할을 선행 조건, 인과관계 또는 기술 채택으로 승격하지 않는다. 원문 표기의 추출 규칙은 [[Ontology-Operations]]를 따른다.
- 이 지도에서 AI가 정리한 의미 관계는 검토 후보로 취급한다. 질문 시 원문을 읽어 확인한 지식과 현재 프로젝트에 대한 추론을 분리한다.
- 후보 지도는 AI가 원문을 찾는 탐색 보조 자료다. `context_lookup`은 후보 의미 관계를 생성하거나 확정하지 않는다.
- 확정 typed relation은 canonical Markdown의 `ontology_relations`에서만 읽는다. `predicate`, `target`과 선택적인 `subject`가 모두 schema와 현재 snapshot entity ID에 맞을 때만 serving relation으로 승격한다. 지원하지 않는 필드, 후보 상태와 YAML alias는 coverage gap으로 남기고 별도 assertion unit이나 edge로 승격하지 않는다. `contains`와 `links_to`는 parser 전용 관계이며 typed relation으로 직접 작성하지 않는다.
- 위 지도 관계 5종 중 `ontology_relations`에 쓸 수 있는 predicate는 `supported_by`뿐이다. `addresses`, `requires`, `has_tradeoff`, `alternative_to`는 사람이 읽는 지도 어휘이며 frontmatter에 적으면 `UnsupportedOntologyPredicate` gap이 된다.
- 순환 위키링크와 `links_to` 탐색은 pinned revision의 유한 snapshot에서 depth 1 또는 2까지만 따른다. 연결이 있다는 사실은 의미 관계, 인과관계나 기술 채택을 확정하지 않는다.
- 학습 원문에 설명된 방법을 현재 요청에 제안할 수 있다. 사용자가 채택하거나 명시적인 프로젝트 결정 근거가 생기기 전까지 결정 기록으로 저장하지 않는다.
- 원문과 현재 코드가 충돌하면 양쪽의 역할과 시점을 확인한다. 현재 구현 사실은 현재 코드에서 확인하고, 설계 의도는 문서에서 확인한다.

`source_confirmed`는 원문에서 관계를 추출했다는 상태다. 주장 자체의 진실성, 최신성이나 현재 프로젝트 적용을 확인했다는 뜻이 아니다. 원문의 마지막 변경 시각과 `verified_at`도 구분한다. 검증 시각이 있어도 무엇을 어느 환경에서 검증했는지 확인해야 하며, 날짜만으로 다른 프로젝트의 기록을 우선하지 않는다.

발췌의 `truncated`가 true이면 적용 조건이나 예외가 잘렸을 수 있다. 중요한 판단은 반환된 `source_revision`, `source_uri`, anchor가 가리키는 전체 section을 읽고 내린다. 현재 작업 파일을 대신 읽었다면 pinned 원문과의 차이를 표시한다. 원문을 더 읽을 수 없으면 잘린 발췌만으로 조건 충족을 확정하지 않는다.

## 제안의 결과물

제안에는 관찰한 상황, 현재 조건에 맞는 이유, 원문 근거, 추가 비용과 아직 확인하지 못한 조건이 있어야 한다. 중요도가 낮거나 현재 요구와 관계없는 개선안은 붙이지 않는다.

읽을 수 있는 자료와 코드에서 먼저 확인한다. 그 뒤에도 유실 허용 여부, 응답 지연 목표처럼 선택을 바꾸는 의도가 남으면 필요한 질문만 한다. 현재 프로젝트가 지정되지 않았다면 코드 적합성은 미확인으로 남긴다.

## 갱신과 확장 기준

- 지식 정정은 해당 원문에 반영하고 지도는 해당 heading을 계속 가리킨다. 원문을 다시 읽을 수 없으면 근거 부족으로 처리한다.
- 새 파일은 실제 존재할 때 연결한다. 원문 이동과 제목 변경 뒤에는 경로와 heading의 해석 여부를 확인한다.
- 실제 요청에서 지도에 없어서 놓친 고려사항이 확인될 때 해당 주제의 지도를 추가한다. 정해진 문서 수를 채우기 위해 확장하지 않는다.
- 결정이 바뀌면 이전 결정의 적용 범위와 대체 이유를 정본에 남긴다. 서로 다른 기록은 프로젝트, 환경과 관측 시점을 대조한 뒤 해석하며, 미해결 충돌을 최신 날짜 하나로 없애지 않는다.
- 구현과 실행 방법은 [[Ontology-Operations]]에 둔다. [[Development-Ontology-Evaluation|평가 기록]]의 수동 관찰과 runtime 검증을 구분한다.
- 근거의 역할, 잘린 발췌와 필수 조건 누락을 다루는 적용 기록은 [[Ontology-Evidence-Lifecycle]]을 따른다.
