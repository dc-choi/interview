# 같은 AI, 다른 결과 (2026-11-06)

밋업에서 들은 21분 발표의 기록이다. 현장 녹음의 자동 전사문을 근거로 정리했고, 오인식된 용어는 문맥으로 교정했다. 슬라이드는 전사문에 없다. 행사 이름과 주최는 전사문에서 확인되지 않아 적지 않았고 발표자는 이름 없이 적는다. 발표자는 정답이 아니라 써 보며 정리한 생각이라고 밝혔다.

주장은 하나다. 모델이 모두 좋아져서 차이는 모델이 아니라 모델을 쓰는 기술에서 나온다. 그 기술을 등장 순서대로 프롬프트, 컨텍스트, 하네스, 루프, 그래프 다섯으로 나눴고, 이 흐름을 AI에 맡기는 범위가 넓어진 과정으로 봤다.

## 1. 출발점: 무엇에 연결돼 있고 믿고 맡길 수 있는가

- 처음에는 묻고, 답을 읽고, 고쳐서 다시 묻는 반복을 사람이 돌렸다. 사람이 AI의 관리자였다. 지금은 AI가 관찰, 판단, 실행과 재시도를 스스로 한다.
- 영수증 정리는 잘한다. 그러나 회사 양식에 맞춰 경비 시스템에 올리고, 금액이 이상하면 다시 확인하고, 카드 번호를 가리라고 맡기면 원하는 결과가 쉽게 나오지 않는다. 모델의 능력이 아니라 연결과 신뢰의 문제다.
- 회사 시스템에 올리려면 권한과 개인정보 보안 기준이 필요하다. 그래서 기업은 AI를 직원이 각자 쓰는 도구가 아니라 회사가 깔아 주는 환경으로 보기 시작했다. AWS를 예로 IT 팀용 모델 접근(Bedrock), 개발자용 설계와 구현 도구(Kiro), 현업용 분석과 자동화(Quick)로 나뉜다고 소개했다(제품명은 문맥으로 교정).
- 환경이 생기면 한 사람의 요령이 스킬이나 에이전트로 나뉘어 팀의 기본값이 된다.
- 맡기는 범위가 넓어졌다고 다 맡기는 것이 좋지는 않다. 간단한 일에 에이전트를 여러 개 붙였더니 비용만 늘고 어디서 꼬였는지 찾기 어려웠다. 무엇을 쓸 수 있는지가 아니라 이 일에 무엇이 필요한지부터 확인한다.

## 2. 프롬프트: 누구인 척하느냐에서 무엇을 알려 주느냐로

- 예시 없이 묻는 방식도 잘 되지만 원하는 출력이 한 번에 나오지 않는다. 예시 두세 개는 모델을 똑똑하게 만드는 용도가 아니라 형식과 어조를 맞추는 용도다. 단계별 사고 유도는 추론 모델이 알아서 하므로 큰 방향만 잡는 데 쓴다.
- 초기에는 전문가 역할을 부여하는 것이 요령이었다. 지금은 사람에게 일을 맡기듯 목적과 판단 기준을 알려 주는 쪽이 낫다. 회의록 요약에서 역할 대신 목적(팀장 보고), 기준(결정 사항, 담당자와 기한만), 형식(표)을 적으니 메일에 바로 붙일 표가 나왔다.
- 한계: 회사의 분기 매출처럼 정보가 없는 질문은 프롬프트로 풀리지 않는다. 지어내지 말라고 적어도 증상만 준다.

## 3. 컨텍스트: 많이 넣기에서 필요한 것만 넣기로

- 신입 온보딩에 비유했다. 똑똑해도 회사 양식과 규칙을 모르면 다시 써야 한다. 그렇다고 첫날 자료를 산더미로 주면 중요한 것을 놓친다.
- 넣는 방법은 시스템 프롬프트, 검색해서 함께 넣는 RAG, 그리고 커진 컨텍스트 윈도우다. RAG에서는 모델을 바꾸는 것보다 문서를 잘 찾아오게 고치는 효과가 컸고, 답이 이상하면 엉뚱한 문서를 보고 있는 경우가 많았다.
- 많이 넣을수록 비용이 들고 답이 흐려진다. 업무별 지침을 파일로 두고 필요할 때만 꺼내 보게 하는 스킬 방식은 필요한 것을 필요할 때 준다는 원칙을 구조로 만든 것이다.

## 4. 하네스: 믿는 대신 막는다

- 잘 알려 줘도 형식이 조금씩 다르거나 넣으면 안 되는 내용이 섞인다. 관심이 모델을 둘러싼 틀 전체로 넓어졌다. 도구 연결, 권한의 범위, 결과 검증, 실행 기록이 모두 하네스다. 같은 모델을 쓰는 서비스의 신뢰 차이는 상당 부분 여기서 나온다고 봤다.
- 대표 부품 셋: 구조화 출력(영수증을 날짜, 금액, 가게 항목으로만 받아 경비 시스템이 바로 쓴다), 가드레일(응답이 나가기 전 모델 바깥에서 개인정보와 부적절한 내용을 한 번 더 거른다), 도구 연결(MCP 같은 표준 방식. 도구 설명이 애매하면 엉뚱한 도구를 부르므로 도구 설명도 프롬프트다).
- 지침과 하네스의 차이는 누가 지키게 하느냐다. 지침과 스킬은 AI가 읽고 따르는 글이라 대부분 지키지만 가끔 놓친다. 하네스는 시스템이 지키게 한다. 항목으로 정리하라는 지침은 가끔 설명 문장이 섞이지만 구조화 출력은 형식에 안 맞는 답이 나오지 않는다. 카드 번호를 가리라는 요청은 대부분 지켜지지만 가드레일은 반드시 가린다.
- 지침은 AI를 믿는 것이고 하네스는 믿지 않아도 되게 만드는 것이다. 한 번 틀리면 문제가 되는 것은 믿는 대신 막는다.

## 5. 루프: 종료 조건과 검증 신호

- 하네스가 일할 틀이라면 루프는 그 틀 안에서 멈추지 않고 일하게 하는 것이다. 생각, 행동, 관찰을 반복하는 ReAct 패턴을 예로 들었다.
- 어려운 것은 루프 자체가 아니라 두 가지다.
- **언제 멈추는가:** 영수증 금액을 읽지 못하면 에이전트가 같은 도구를 계속 호출하며 토큰만 썼다. 최대 반복 횟수, 토큰 예산, 같은 호출이 연속되면 끊는 규칙을 걸고, 그래도 안 되면 사람에게 넘겼다.
- **무엇으로 잘됐다고 판단하는가:** 형식은 스키마 검증으로 걸러지지만 금액 0원이나 미래 날짜는 형식상 문제가 없다. 그 위에 업무 규칙 검증을 한 겹 두고, 애매한 것은 다른 모델이 한 번 더 채점하게 했다. 이런 기준이 있어야 AI의 완료 보고를 믿을 수 있다.
- 검증 신호가 가장 잘 갖춰진 곳이 코딩이다. 테스트가 실패하면 메시지를 읽고 다시 고치고, 통과하면 멈춘다. 테스트가 없는 일은 기준을 만들어 준다(표 정리라면 형식이 맞을 때까지).
- **어디까지 맡기는가:** 기준은 되돌릴 수 있는가다. 조회와 정리는 틀려도 다시 하면 되므로 AI가 혼자 한다. 메일 발송과 고객 응대처럼 밖으로 나가는 일은 사람이 한 번 확인한다. 결제, 삭제와 계약처럼 되돌리기 어려운 일은 사람이 직접 결정한다. 고객 문의 메일이라면 분류와 답변 초안은 AI가, 발송 직전 승인은 담당자가, 애매한 예외는 사람이 맡는다.
- 중요한 것은 얼마나 맡기느냐보다 어디서 사람이 들어갈지를 미리 정하는 것이다.

## 6. 그래프: 나누는 이점과 대가

- 에이전트 하나에 여러 일을 몰면 맥락이 길어지고 엉킨다. 감독 역할이 작업을 쪼개 하위 에이전트에 넘기고 결과를 합치는 orchestrator-worker 구조가 가장 흔하다.
- 이점은 역할 분담과 컨텍스트 분리다. 하위 에이전트는 독립된 컨텍스트에서 자기 일만 하고 요약된 결과만 돌려준다. 검증 에이전트는 작성 과정을 모르고 결과물만 보고 판단한다. 작성자가 아닌 사람이 코드 리뷰를 하는 것과 같다.
- 대가: 넘겨주는 과정에서 맥락이 빠지고, 토큰 비용이 단일 에이전트의 몇 배가 되고, 어디서 틀렸는지 보려면 추적을 따로 갖춰야 한다. LangGraph, Strands Agents SDK 같은 프레임워크가 계속 나오는 것은 가장 좋은 방법을 아직 찾는 중이라는 뜻으로 봤다.
- 자주 보이는 세 형태: 순차형(수집, 작성, 검증을 차례로 넘긴다), 병렬형(여러 에이전트가 동시에 처리하고 마지막에 모은다), 검토형(작성과 검토를 나눠 통과할 때까지 주고받는다).
- 자료가 너무 많거나, 역할마다 볼 정보가 다르거나, 따로 검증이 필요한 경우가 아니면 에이전트 하나로 충분한 경우가 많았다.
- 예: 주간 경쟁사 리포트는 수집, 분석, 작성 에이전트가 차례로 일하고, 검증 에이전트가 출처 없는 문장을 찾아 작성 단계로 되돌린다. 순차형과 검토형이 섞인 구조다.
- 프레임워크부터 고르지 않는다. 에이전트 하나로 돌려 보고 감당하기 어려운 부분이 보이면 그 부분만 나눈다.

## 7. 맺음

- 관심이 모델에게 어떻게 말할까에서 모델이 일할 환경을 어떻게 만들까로 옮겨 왔다.
- 나온 순서는 있지만 필요한 것만 골라 쓰는 것이 가장 효율적이다.
- 혼자 잘 쓰는 것보다 쓰는 방법을 나누고 팀에 남길 때 차이가 난다.
- 판단과 책임은 사람의 몫이고, 검증 기준을 설계하는 것까지가 사람의 일이다.

## 확인 범위

- 발표의 경험담(RAG에서 검색 개선의 효과, 다중 에이전트의 비용 배수, 영수증 사례)은 발표자의 경험이며 측정값이 제시되지 않았다.
- AWS 제품의 역할 구분은 전사 오인식을 문맥으로 교정한 것이고 공식 문서로 대조하지 않았다.
