# 이력서 버전 관리와 갱신 주기

[[Resume-15-Second-Rules|이력서 15초 승부]]의 원칙 4(역할 맞춤)를 운영 절차로 푼 문서다. 원천 기록, 마스터, 지원본의 층 구분은 [[Resume-Experience-Narrative-and-Evidence#원천 기록에서 지원본까지|원천 기록에서 지원본까지]]가 정본이고, 여기서는 버전을 어떤 단위로 몇 개 만들고 층마다 언제 갱신하는지를 다룬다.

## 버전의 단위: 회사가 아니라 강조점

- 처음부터 특정 회사를 겨냥하지 않은 제너럴 이력서 한 장은 많은 회사에 매력을 주지 못한다. 그렇다고 회사마다 새로 쓰면 유지할 수 없다.
- 강조점별 버전을 만든다. 예: DB 강조형, 도메인 강조형, 문제 해결 강조형, 협업 강조형. 지원 직전에는 고른 버전 위에서 순서와 공고의 언어만 회사에 맞게 조정한다.
- 회사마다 요구가 다른 경력기술서는 지원마다 맞춤 편집한다([[Career-Description-and-Pivot#버전 관리|경력기술서 버전 관리]]).

## 공고를 군집으로 묶어 버전에 연결한다

1. 가고 싶은 회사를 리스트업한다([[Job-Search-Strategy|이직 전략]]의 지원 리스트 설계).
2. 공고와 기술 블로그, 발표 영상 같은 외부 자료로 그 회사의 현재 고민(도메인 문제, 기술적 난항, 레거시 개편)을 파악한다. 공고는 채용팀만 쓰는 문서가 아니라 개발팀, 면접관, CTO 같은 리더의 요구가 종합된 문서라 필요한 스택과 인재상의 가장 직접적인 증거다. 상시 채용 공고는 회사 사정에 따라 내용이 바뀌므로 자주 본다.
3. 우대 조건과 지원 자격을 내 경험(운영 중인 개인 프로젝트 포함)과 매칭하고, 비슷한 공고끼리 묶어 버전 하나에 연결한다. 공고의 기술 스택은 더 공부할 범위와 나올 면접 질문을 예측하는 데도 쓴다.
4. 공고 키워드는 실제 경험이 있는 범위에서 공고의 언어로 표현하는 데만 쓴다. 공고의 모든 키워드를 넣으라는 조언도 있지만, 면접에서 책임질 수 없는 키워드와 기술 나열은 높은 기대를 만들었다가 감점으로 돌아온다([[Resume-Experience-Narrative-and-Evidence#이력서에서 면접 질문을 역으로 만든다|면접 질문 역설계]]). 공고를 사실, 가설, 검증 질문으로 나눠 읽는 법은 [[Job-Search-Strategy-JD-Analysis|채용공고 분석]].

## 도메인별 강조와 유사 도메인 연결

- 금융은 멱등성, DB 락과 동시성 경험을 중요하게 볼 수 있다. 동시성 경험이 없으면 가장 가까운 DB 경험을 앞세운다.
- 커머스는 다양한 도메인 문제를 해결한 경험을 녹인다.
- 같은 도메인 경험이 없으면 비슷한 복잡성으로 잇는다. 웹툰 서비스에서 복잡한 정산 문제를 푼 경험을 커머스의 복잡한 도메인 문제 해결 경험으로 연결하는 식이다.
- 검토자는 내 회사와 도메인을 모른다. 누구나 아는 회사가 아니거나 특이한 도메인이면 무슨 서비스이고 무엇을 하는 곳인지 짧게 설명해야 매력을 느낄 차례가 온다. 사람은 이해할 때 집중한다.

## 버전을 실험으로 쓴다

- 100곳에 같은 이력서를 내면 실험 기회를 버리는 것이다. 결과가 나쁘면 패턴을 바꾼 버전을 보내 통과 여부를 관찰한다.
- A, B 두 버전을 동시에 만들어 어느 쪽이 나은지 비교 피드백을 받는 것도 방법이다.
- 서류 통과율과 면접에서 막힌 질문을 조정 신호로 쓰는 루프는 [[Job-Search-Strategy|이직 전략]]의 이력서 1버전과 공고 역산과 같다.

## 층별 갱신 주기

| 층 | 담는 것 | 갱신 |
|---|---|---|
| 원천 기록 | 실제로 한 일, 처리 방식, 문제점, 운영 이슈, 트러블 해결 과정을 장황하게 | 큰 프로젝트 완료, 진척, 사건이 생길 때마다 |
| 명세(선택) | 원천이 방대해져 헷갈리기 시작하면 규칙 기준으로 한 번 가공한 사양서 | 원천이 크게 늘었을 때 |
| 마스터(제너럴 버전) | 강조형 버전의 공통 기반인 0번째 이력서 | 분기, 늦어도 6개월마다. 적극 구직 중이면 최소 월 1회 |
| 강조형 지원 버전 | 공고 군집별 버전 | 마스터 변경을 반영하고 지원 직전 공고에 맞춰 조정 |

- 이직 생각이 없어도 마스터를 갱신한다. 1년 치 업무를 한 번에 적으려 하면 기억나지 않듯, 3~4년 만에 이직하려는 사람이 쓸 거리를 기억하지 못하는 일이 흔하다.
- 여러 버전을 써 보는 과정 자체가 연습이다. 관리 도구는 비공개 저장소의 Markdown 파일이든 메모장이든 상관없다.
- 원천 기록에는 공개 가능 여부를 표시하고 지원본으로 옮길 때 기밀정보를 걸러낸다([[Resume-Experience-Narrative-and-Evidence#기밀정보 필터|기밀정보 필터]]).

### 완료 시점의 기록과 후속 결과를 나눈다

프로젝트를 배포한 날에는 실제 기여와 확인된 결과를 적고, 효과가 뒤늦게 드러나면 같은 기록에 관측 시점과 결과를 덧붙인다. 출시 완료와 사용자 이용, 비용 절감 같은 후속 효과는 서로 다른 사실이다. 목표 수치를 실제 성과로 옮겨 쓰지 않는다.

다음은 성과 기록을 지원본으로 옮기기 위한 운영 예시다. 정해진 갱신 주기가 효과를 보장한다는 뜻은 아니다.

1. **당시 기록**: 문제, 직접 맡은 변경, 완료일과 확인 방법을 적는다.
2. **수치 근거**: 지표 정의, 비교 기간, 계산식과 근거 위치를 함께 남긴다. 이 정보는 권한이 있는 원천 기록 안에서 관리한다.
3. **후속 확인**: 실제 결과가 나왔을 때 관측값을 보완하고, 아직 확인되지 않았다면 결과 대기로 둔다.
4. **지원본 반영**: 공개 가능한 결과와 본인 기여만 요약한다. 내부 자료, 비공개 지표와 제3자 정보는 옮기지 않는다.

리팩터링, 온콜 개선과 협업처럼 숫자로 표현하기 어려운 일도 목적, 행동과 관찰된 변화를 기록한다. 숫자가 없다는 이유로 빼거나 임의의 개선율을 만들지 않는다.
