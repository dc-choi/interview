# 포트폴리오 작성 가이드

포트폴리오의 구성 요소, 신입 프로젝트의 우선순위, 주제 선정과 평가 축, 면접용 프로젝트를 운영하는 절차와 활동별 실행 기준. 이력서 본문과 자기소개서 작성은 [[Resume-Portfolio-Guide|이력서 & 포트폴리오 가이드]] 참조.

## 필수 포함 요소

- 개발 목표와 의도: 무엇을 해결하려고 했나? 무엇을 제공하려고 했나?
- 주요 기능, 시스템 개요 (아키텍처)
- 본인이 담당한 영역과 기여도
- 깃 레포 주소
- 도식화 (최대한 간결하게, 한눈에 들어오게)

## 작성 원칙

- 노션보다는 PDF나 구글 Docs 사용, 두 장 이내로 압축. 노션 링크는 장애, 별도 접근 권한 관리, URL 체계 때문에 깨진 채 도착하는 경우가 많다는 면접관 관찰이 있어 구글 Docs나 GitHub의 공개 링크, PPT를 PDF로 바꾼 첨부를 쓴다
- 두 장 제한과 깊이는 링크 계층으로 함께 지킨다. 상위 문서에는 목표, 기대 효과, 아키텍처, 개발 스택, 핵심 기능만 두고 소스 수준 스펙, API 명세, 상세 설명은 내부 링크로 내린다. 개발 규모가 큰 기능의 플랫폼화도 A4 한 장으로 요약할 수 있고, 스터디 저장소 README(개발 환경, 요구사항, 라이브러리, 소스 설명, 아키텍처, API 명세)나 재사용 컴포넌트 문서(개요, 구조, 사용 방법, 속성)도 같은 구조를 쓴다
- 운영 중인 서비스: 외부에서 접근 가능하게, 앱이나 웹으로 서비스를 올린 경험이 중요. 소스만 보여 주지 말고 데모 페이지라도 동작하는 화면을 보여 준다
- 선택과 집중 (양보다 질, 구색맞추기 금지)
- 나의 강점, 내가 만든 제품/서비스를 한눈에 볼 수 있도록

## 신입 프로젝트의 우선순위와 운영의 기준선

한 서류 검토자의 우선순위다. 컴공 전공, 독학, 개인과 팀 프로젝트 모두 무엇을 했느냐보다 얼마나 했느냐로 읽힌다.

1. **서비스를 런칭해 실제로 운영 중인 팀 프로젝트**가 가장 강하고, 다음이 개인 프로젝트다. 기획부터 운영까지 겪은 개인 프로젝트는 그 과정의 문제와 선택의 이야기가 있을 때 차별화된다.
2. **AI 도구 활용 경험**은 학습 의지를 보여 주는 긍정 요소다. AI로 새 시도를 한 신입이 그렇지 않은 신입보다 매력적일 수 있으나 어떻게 쓰느냐가 관건이다([[Resume-Experience-Narrative-and-Evidence#AI 활용 경험을 쓰는 법|AI 활용 경험을 쓰는 법]]).
3. **정보처리기사 같은 범용 자격증**은 이를 요구하는 일부 산업군 밖에서는 비중이 낮다.

- **운영의 최소 기준**: 도메인을 사고 서버를 띄워 실제 사용자 트래픽을 받으며 계속 고쳐야 서비스 운영이다. GitHub에 올리기만 한 프로젝트는 운영 경험으로 읽히지 않고 크게 어필되지도 않는다.
- **공동 저장소는 협업의 증거가 아니다**: 한 저장소에 함께 올린 수준은 실무가 원하는 협업이 아니다. 운영 중 문제가 생겨 마이그레이션하고 장애를 겪으며 함께 푼 이야기가 원하는 경험이다. 팀 단위 성과를 쓰라는 조언([[Resume-Portfolio-Guide#자기소개서 작성 팁|자기소개서 작성 팁]])도 이런 경험이 있는 팀 프로젝트에서 힘을 얻는다.
- **서류에는 태도 대신 노력의 흔적을 쓴다**: 검토자는 서류에서 태도를 보기 어렵고, 유사 실무 경험과 그 과정의 고민을 얼마나 잘 풀어내는지를 본다. 무엇을 문제로 봤고 왜 풀고 싶었으며 어디까지 해 봤는지를 쓴다.
- **AI 시대의 차별점은 배경이다**: 만드는 일은 누구에게나 쉬워졌으므로 왜 그 선택을 했는지를 넘어 왜 그 선택이 필요했는지, 선택 없이도 가능했는지까지 설명한다. 신입 이력서에는 그만한 공간이 있다. 신입에게 기대하는 것은 접근과 해결 과정을 논리적으로 설명하고 허점을 이해해 대안을 내는 사고력이므로, 실험, 모의 테스트, 트래픽 분석으로 과정을 깊게 보여 준다.

## 주제 선정 기준

- 지원하고자 하는 분야와 얼라인
- 마켓에 런칭했을 때 실제 사용자가 있을까?
- 기존의 어떤 불편함을 해결했나?
- 본인이 관심을 가지고 공부한 분야를 구현
- 적당한 규모에 누구에게나 익숙한 문제 상황: 해결한 문제가 왜 어려운지 설명해야 하는데 익숙한 문제일수록 면접관이 빨리 이해한다. 주제 선정 자체에 시간을 과하게 쓰지 않는다

## 주제 예시

- 대형 서비스 지원: 알림 시스템 (조회수/댓글 실시간 알림 → 재접속 유도 푸시)
- 현실 문제 해결: 스터디 모임 앱 (인증, 발제, 모임/신청 중계)
- 내용이 많다면 블로그나 깃허브를 포트폴리오로 활용

## 면접관이 보는 3축 — 깊이의 증명

포트폴리오는 다룬 기술의 가짓수가 아니라 하나의 문제를 얼마나 깊게 팠는지로 평가된다.

1. **선택의 기준** — 왜 이 기술인지 물었을 때 다들 써서라는 답은 실격이다. 스택 10개 나열보다 병목을 확인하고 도구를 도입해 수치로 개선한 경험 1건이 강렬하다. 면접 답변에 적용하는 같은 원칙은 [[FIT-Framework|FIT 프레임워크]]의 의사결정 복기.
2. **트러블슈팅의 과정** — 다이어그램에 몇 주를 쓰고 본문에 성능 개선을 수행함 한 줄만 남기지 않는다. 면접관이 궁금한 것은 결과가 아니라 과정이다: 실행 계획 캡처, 재현 코드, 단계별 기록. 실패한 시도와 이를 극복한 디버깅 기록이 가장 강한 무기다.
3. **비즈니스 맥락** — CRUD 몇 개를 완성했다는 사실은 감흥이 없다. 결제 실패율을 낮추는 예외 처리 설계, 재고 차감의 동시성 방지처럼 현실 문제에서 출발한 흔적이 필요하다. 개발은 문법을 자랑하는 자리가 아니라 요구사항을 코드로 변환하는 작업이다.

## 면접용 프로젝트 4단계

흘러가는 대로 기능을 붙이면 면접에서 말할 가장 어려운 문제가 남지 않는다. CORS 오류나 offset 페이지 조회처럼 검색으로 풀리는 문제만으로는 차별성이 없고, 규모 있는 시스템도 해낼 성장 가능성과 왜 그 기술인지(왜 Redis, 왜 Kafka)를 보여야 한다. 그래서 위 3축이 드러나도록 기획 단계부터 의도적으로 설계한다.

1. **기획하기**: 주요 기능과 우선 품질을 정하고 기능별 목표 수치와 예상 사용자 수를 적는다. 사용자와 데이터가 늘 때 생길 병목(실시간 정렬 저하, 포인트 적립의 DB 부하 같은)과 해결 후보(캐시, 이벤트 발행)를 미리 정한다. 전 과정의 예시는 [[System-Design-Practice-Topics|시스템 설계 연습 주제]]의 Q&A 커뮤니티 변형.
2. **만들기**: 단순한 구조에서 출발해 문제 해결에 직접 도움이 될 때만 컴포넌트를 더한다. 아키텍처로 큰 그림을 잡은 뒤 구현 단계에서 구체 스택을 정하고, 모든 기능보다 기획에서 정한 주요 기능을 깊게 판다. 저장소는 협업 프로젝트처럼 커밋 메시지, PR, 디렉터리 구조, 테스트 코드를 갖춘다. 목표 달성은 API 응답 시간, 쿼리 실행 계획(EXPLAIN), 시스템 메트릭, 부하 테스트, APM의 호출 흐름과 에러 구간으로 측정한다([[Capacity-and-Load-Testing|캐퍼시티와 부하 검증]]).
3. **다듬기**: 예상 밖 수치가 나오면 병목을 개선한다. 아키텍처 수준(메시지 큐, 캐시, 읽기와 쓰기 분리)과 세부 수준(캐시 TTL, 인덱스, 쿼리 리팩터링, 비동기 로직 최적화)이 있다. 프로젝트 소개, 인원과 역할, 기능, 디렉터리 구조, 아키텍처 그림, ERD, API 명세, 핵심 화면, 기능 흐름도를 누구나 읽을 수 있게 남기고 가장 어려웠던 문제와 해결 과정을 설득력 있게 기록한다. 측정 기록의 최소 단위는 [[System-Design-Quality-Attribute-Decision#설계 결과의 최소 증거 묶음|설계 결과의 최소 증거 묶음]].
4. **설명하기**: 결과보다 과정이다. 가장 어려웠던 문제를 중심으로 흐름을 만들고 트레이드오프와 판단 근거를 구체적으로 댄다. 참고한 기술 블로그를 언급하며 대화를 이끌 수 있다. 면접관의 반대 의견에는 논리로 답하되 타당하면 유연하게 받아들인다.

## 포트폴리오 자산을 만드는 활동

[[Resume-Portfolio-Guide#눈에 띄는 이력서 만들기|눈에 띄는 이력서 만들기]]의 활동 목록에 붙이는 실행 기준이다.

- **운영 중인 서비스**: 오래 운영한 서비스만을 뜻하지 않는다. 과제나 팀 프로젝트를 할 때부터 운영할 수 있는 서비스를 염두에 두고 주제를 정하면 게임 프로젝트나 취업 과제도 외부에서 접근 가능한 포트폴리오가 된다.
- **가시적 성과**: 만들어 봤다는 한 줄보다 실제로 동작하는 앱이나 웹이 있을 때 검토자가 흥미를 갖고 읽는다.
- **기술 문서 공유**: 커뮤니티, 블로그, GitHub에 꾸준히 발행하고 홍보는 개발 커뮤니티, 오픈 채팅, SNS로 한다. 검색 상위 노출 같은 반응은 수치로 바꿔 이력서에 넣는다([[Running-A-Tech-Blog|기술 블로그 운영]]).
- **팀 프로젝트**: 결과물 품질이 개인 프로젝트보다 높기 쉽고 협업, 역할 분담, 커뮤니케이션을 조직처럼 겪는다. 실패한 팀 프로젝트도 실수와 보완점, 무엇이 성장했는지로 쓸 수 있다.
- **테크 세미나 연사**: 기업 기술 컨퍼런스와 기술 커뮤니티 컨퍼런스의 발표자 모집에 기회가 있지만 모집 자격은 경력자에게 유리한 편이다. 평소 발표를 염두에 두고 팀 스터디나 커뮤니티 세미나에서 먼저 발표해 내공을 쌓으면 서너 달 만에도 도전할 수 있다는 관찰이 있다([[Deferred-Life-Plan|미뤄 놓은 인생 설계]]의 작은 무대).
- **선택과 완주**: 이직용 체크리스트가 아니라 성장 단계로 보고 자신에게 맞는 것을 골라 결과물이 나올 때까지 이어 간다. 중도에 포기하면 들인 시간을 회수하기 어렵다. 하나를 하더라도 제대로 해서 이력서에 한 줄을 더하는 것이 목표다.
