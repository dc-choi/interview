# 이력서 15초 승부, 5원칙

채용담당자가 이력서 한 장을 판단하는 시간은 **수 초, 길어야 15초**. 첫 페이지에서 "면접으로 이어갈 만한가"가 결정된다. **30초 광고 영상을 설계하듯** 임팩트, 성취, 정량화, 맞춤, 가독성 5원칙으로 써야 한다. 기본 구성, 포맷, 자소서 작성법은 [[Resume-Portfolio-Guide]]에 있고, 이 문서는 **읽히기 위한 원칙**에 집중.

검토 방식은 가점을 찾는 정독이 아니라 **탈락 사유부터 거르는 네거티브 필터링**이다. 거를 이유를 먼저 찾고, 통과한 서류만 따로 모아 두었다가 다음 사이클에 서로 비교한다. 첫 페이지에서 감점 요소를 없애는 것이 가점을 쌓는 것보다 먼저다. 검토 조직과 판정 규칙, 지원자 풀 안의 상대 평가, 궁금증과 기대가 깎이는 감점 모델은 [[Resume-Reviewer-Perspective|서류 검토자의 시선]]. 검토자는 코드를 먼저 보지 않는다 — 이력서에 적힌 문장을 본다. 어떤 문제를 얼마나 개선했는지는 본인만 알고 있으므로, 꺼내서 쓰지 않으면 없는 일이 된다.

## 원칙 1 — 임팩트에 집중

첫 페이지의 밀도가 전체 운명을 결정한다.

- **첫 페이지가 가장 중요** — 본편(면접)으로 관심을 끌어오는 트레일러
- **짧은 문장** — 한 줄, 최대 두 줄. 장문은 반드시 글머리 기호로 분해
- **기술 스택 나열은 아래로** — 단순 "Python, Java, AWS"는 정보 가치 낮음. 긴 스택 목록은 오히려 깊이 없이 이것저것 해봤다는 의심 신호로 읽힐 수 있다. 잘 안다고 증명할 수 있는 것만 최대 5개로 추리고, 적어 놓고 설명 못 하는 기술은 면접에서 바로 걸리므로 적지 않는 편이 낫다. 대신:
  - **난이도 있는 자격증**(AWS Solutions Architect Associate 등) 학습 노력 증빙
  - **실체 기여**로 증명 (프로젝트, 블로그, OSS 링크)
- 추가 정보는 **블로그, GitHub, 포트폴리오 링크**로 확장 — 링크는 본문 설명을 대신하지 않는다
- 검토자가 실제로 읽는 방식(F자 스캔, 첫 장 집중과 중간 누락)과 거기서 나온 자기소개 3줄, 최신순과 매력순, 분량의 총량과 배분은 [[Resume-15-Second-Rules-Layout|이력서 배치와 분량]]

### 흔한 실수

- 첫 페이지에 학력, 자격증, 긴 자기소개를 몰아넣어 **본인 성과가 2페이지부터** 시작
- 기술 스택을 **분홍, 파랑 배지**로 화려하게 나열 → 정보보다 시선 분산
- 첫 줄을 "안녕하세요 ...입니다"로 시작 → 생산성 저하

## 원칙 2 — 성취 중심

"했다"가 아니라 **"이만큼 했다"**.

### 구체적 서술

- "담당 개발"(X) → **"DAU 10만 서비스에서 결제 모듈 신규 개발"**(O)
- 개선 작업은 **Before/After 수치** 필수:
  - "API 성능 개선"(X) → "API 응답시간 220ms → 80ms (64% 감소)"(O)
  - "비용 절감"(X) → "월 운영비 300만원 → 50만원"(O)

### 큰 성취 우선 배치

- 여러 프로젝트 중 **기여도가 높은 프로젝트**를 최상단
- 대표 프로젝트는 "무엇을 물어봐도 술술 나올 수준" — **10분 분량 서사** 준비
- 면접관이 **먼저 배치된 것부터** 질문함을 전제로 순서 배치

### 대표 프로젝트 필수 구성

1. **프로젝트 소개** — 무엇을 만들었는가
2. **시스템 구성** — 아키텍처, 기술 스택
3. **기여 사항** — 본인이 담당한 범위
4. **성과** — 수치화된 결과
5. **트러블슈팅** — 겪은 문제, 해결 과정
6. **아쉬운 점** — 돌이켜봤을 때의 개선점

## 원칙 3 — 정량화

숫자 없는 성과는 **기억에 남지 않는다**.

### 숫자로 영향력 강화

- "많은 사용자"(X) → **"1,000명 중 65.7%"**(O)
- 감소보다 **개선율로 표현** — "에러 70% 감소" vs **"에러율 3.3배 축소"** — 후자가 임팩트
- "빨라졌다"(X) → **"P99 응답시간 800ms → 180ms"**(O)

### 다양한 측정 항목

프로그래머의 성과는 코드 속도에 국한되지 않는다.

- **수익, 비용** — 매출 기여, 운영비 절감, FinOps
- **프로세스** — 배포 시간, 리드타임, MTTR
- **사용자** — DAU, MAU, 리텐션, 전환율
- **리더십** — 멘토링 대상자 수, 신규 채용 기여
- **지식 공유** — 사내 세미나, 블로그, 기술 문서

코딩 외 **기획, 회의, 장애 대응** 성과도 함께 기록할 가치가 있다.

### 신입이라 수치가 없다면

수치가 없다고 생각하지만 대부분은 있다 — 못 보고 있을 뿐이다. 사이드 프로젝트에서 API를 직접 테스트했다면 응답 시간이 있고, DB에 데이터를 넣어봤다면 그 양이 있다. DAU가 없어도 팀원 수, 개발 기간, 구현한 API 개수도 수치다 — 없는 것보다 훨씬 낫다. 그 프로젝트에서 무엇을 판단하고 결정했는지가 중요하다. 단, 이런 규모 수치는 성과 근거가 없는 신입의 보완재이고 경력직의 성과 지표로는 약하다(아래 정량화의 한계).

### 정량화의 한계

숫자는 시선을 붙잡는 앵커이지 성과 자체가 아니다.

- **규모 지표는 성과가 아니다**: 코드 줄 수, API 수, 엔티티 수, 테스트 수 같은 프로젝트 규모는 경력직 이력서에서 검토자에게 거의 와닿지 않는다. 경력직은 사용자, 운영, 비용에 생긴 변화를 쓴다.
- **배경 없는 수치는 궁금증을 만들지 못한다**: 서비스와 회사 설명 없이 MAU, DAU와 성능 개선 수치만 나열하거나, 어떤 알림을 얼마나 보내야 했는지 없이 처리량만 적으면 맥락이 사라진다. 배경 없이 수치를 과하게 쓰면 오히려 눈에 덜 들어온다.
- **숫자는 배경 이야기 안에 넣는다**: 사용자가 어떤 상황에서 서비스를 쓰는지, 동시 접속 증가로 왜 DB 커넥션 풀이 고갈됐는지, DB 스펙 상향의 비용과 데이터 특성을 따진 판단까지 쓰고 그 안에 수치를 두면 흥미와 이해도가 함께 오른다. 기준점, 측정 범위, 내 기여 범위를 붙이는 법은 [[Resume-Experience-Narrative-and-Evidence#숫자는 맥락과 함께 쓴다|숫자는 맥락과 함께 쓴다]].

## 원칙 4 — 각 역할에 맞게 수정

### 은탄환은 없다

- **모든 회사에 통용되는 이력서는 불가능**
- 지원 포지션 JD의 **요구사항 키워드**를 이력서에 반영 — 실제 경험이 있는 범위에서 공고의 언어로 표현한다. 책임질 수 없는 키워드와 기술 나열은 면접에서 감점으로 돌아온다
- 관련 경험이 있다면 반드시 **전진 배치**
- JD에 "대용량 트래픽 경험"이 있으면 해당 경험을 최상단으로

### 필요 없는 내용은 삭제

- 해당 역할과 무관한 프로젝트, 경험은 **제거**
- 단, **특정 산업 관련 경력**은 상황 따라 강점 — 핀테크, 커머스, 게임, 의료
- 고민 포인트: "이 문장이 이 포지션 채용에 0.1%라도 기여하는가?"

### 버전 관리

- 공통 마스터 이력서 위에 **강조점별 버전**(DB, 도메인, 문제 해결, 협업 강조형 등)을 두고 비슷한 공고 군집에 연결한다. 회사마다 새로 fork하기보다 지원 직전에 고른 버전의 순서와 공고의 언어만 조정한다
- 지원 시점마다 최신 정보 반영
- 공고 군집 만드는 법, 도메인별 강조, 버전을 실험으로 쓰는 법과 층별 갱신 주기는 [[Resume-15-Second-Rules-Versioning|이력서 버전 관리와 갱신 주기]]

## 원칙 5 — 보기 좋은 떡

가독성이 떨어지면 **아무리 내용이 좋아도 안 읽힌다**.

### 템플릿

- **글꼴 3개 이하** (제목, 본문, 코드)
- **색상 최소** — 강조 1~2색
- **적절한 여백** — 섹션 구분이 명확
- **인쇄했을 때 잘 읽히는가** 테스트 — 화면에서만 예쁜 건 신호
- 유행 템플릿의 역전, 노션 인터랙티브 이력서, 가로 형식, 과한 꾸밈 같은 형식 금기는 [[Resume-15-Second-Rules-Layout#형식 금기|형식 금기]]

### 피드백 받기

- **소리 내어 읽어보기** — 막히는 문장이 곧 고칠 부분이다. "구현했습니다", "개발했습니다" 같은 동사를 지우고 어떤 문제가 있었고 어떻게 해결했는지로 바꾼다
- **직무를 모르는 사람**에게도 이해되는가 체크 — 전문용어 과다 방지
- **종이로 인쇄**해서 빨간 펜으로 피드백 받기 — 화면보다 집중도 높음
- 지인에게 **JD와 함께 전달**하면 모의 면접관 역할 가능
- 전문 리쿠르터, 채용 담당 경험자 리뷰는 **유료라도 가치** 있음
- **매력 점검**: 검토자가 같이 일해 보고 싶다고 느끼면 사실상 끝난다. 내 매력을 최소 3~4개로 이름 붙이고 각각을 이력서 어디에 의도적으로 넣었는지 짚는다. 남의 이력서를 검토하는 시선으로 읽고, 친한 동료에게 이 이력서에서 보이는 내 매력이 무엇인지 물어 서로 피드백한다. 이력서를 쇼츠라고 보고 검토자가 끝까지 봐야 할 이유를 스스로 설득할 수 있는지, 매력 없는 내용을 뺐는지 묻는다
- **AI 첨삭의 한계**: 생성형 AI 첨삭은 일반적인 조언에 머물기 쉽다. 회사가 원하는 상황과 검토자의 시선을 AI가 알기 어렵고 매력은 사람이 느끼는 것이기 때문이다. AI가 써 준 이력서를 그대로 내지 말고 근본 질문을 던져 내 경력을 이해하고 업그레이드하는 데 쓰며, 그 내용은 면접에서 스스로 설명할 수 있어야 한다([[LLM-Assisted-Editing|LLM 활용 편집]])

### 포맷

- **PDF**로만 제출 — Word, HWP 호환성 문제
- 파일명에 이름, 포지션 포함 — `홍길동_백엔드개발자_2026.pdf`
- 3장 안팎 — 3장을 넘기면 끝까지 읽히지 않을 가능성이 높고, 경력직 1장 축약은 성의 없어 보일 수 있다([[Resume-15-Second-Rules-Layout#분량: 총량과 배분|분량의 총량과 배분]])

## 반복이 원칙

이력서는 한 번에 완성되지 않는다.

- **분기 단위 업데이트** — 최근 성과 즉시 반영. 원천 기록은 사건마다, 마스터는 늦어도 6개월마다, 적극 구직 중이면 월 1회 이상 갱신한다([[Resume-15-Second-Rules-Versioning#층별 갱신 주기|층별 갱신 주기]])
- 구직 시작 후 쓰려 하면 **기억이 흐려져** 성과를 숫자화 못 함
- 평소 **성과 로그**를 별도로 관리 → 이력서 갱신 시 참조
- **리쿠르터 질의**를 이력서 개선 신호로 활용

## 흔한 실수

- 수치 없는 "많이, 크게, 빠르게"
- 팀 성과를 개인 것처럼 — 꼬리 질문에서 드러남
- JD와 무관한 내용이 페이지 상단 차지
- 기술 스택을 **배지 나열**로만 — 증빙 없음
- 모든 회사에 같은 파일 제출
- 화려한 디자인으로 **가독성 훼손** — 인포그래픽 이력서의 함정
- 3페이지 넘는 "모든 걸 다 썼다" 이력서
- 코드 줄 수, API 수 같은 규모 지표를 성과처럼 나열
- 모든 항목을 같은 틀(문제-해결-기술-성과)로 반복 — 뻔한 패턴으로 읽혀 이탈을 부른다

## 체크리스트

- [ ] 첫 페이지만 보고도 "누구이고 어디에 강한 사람인지" 15초 내 파악 가능한가
- [ ] 성과 수치에 배경과 기준점이 붙어 있는가(측정할 수 없는 성과에 억지 숫자를 만들지 않았는가)
- [ ] 내 매력 3~4개가 이력서 어디에 있는지 짚을 수 있는가
- [ ] 대표 프로젝트가 **10분 분량 STAR**로 답변 가능한가
- [ ] 지원 회사별로 **JD 키워드 매칭**을 했는가
- [ ] 모르는 사람에게 **종이 피드백**을 받았는가
- [ ] 분기 단위 업데이트 습관이 있는가
