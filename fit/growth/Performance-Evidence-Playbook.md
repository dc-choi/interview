# 성과 증거 플레이북

한 작업의 결과를 과장 없이 점검하고 개인 성장 기록으로 전환하는 공개용 체크리스트다. 특정 회사의 평가 기준이나 업무 계획을 대신하지 않으며 실제 업무의 원문, 수치, 고객 정보와 운영 상세는 팀의 승인된 기록에만 남긴다.

## 2026-08 기록 스냅샷

당시 vault를 점검하며 문서의 범위와 정확성이 좋아진 것과 실제로 일을 해낸 증거는 다르다고 판단했다. `status: done`과 문서 수는 숙련이나 실행의 증거가 아니며, 남은 공백은 다음과 같이 정리했다.

- 내가 직접 수행한 판단, 검증과 결과를 1인칭으로 설명할 증거
- 기준선, 개입, 관찰 결과와 한계를 구분한 기록
- 장애나 실패의 영향, 원인 사슬, 복구와 재발 방지를 닫은 회고
- 구현 완료와 실제 사용자 또는 운영 결과를 구분하는 습관

이 점검에서 세운 성장 가설은 맡은 일을 결과 확인까지 닫고, 기회가 있을 때 측정 가능한 개선과 반복 운영 통증 제거를 증거로 남긴다는 것이었다. 실제 실행 여부는 문서만으로 추정하지 않고 확인된 기록으로만 갱신한다.

## 사용 순서

1. 작업 전에 목적과 확인 방법을 합의한다.
2. 진행 중에는 사실, 가정, 위험과 필요한 결정을 구분한다.
3. 완료 뒤에는 확인된 결과와 아직 모르는 점을 나눠 기록한다.
4. 공개 가능한 설명이 필요할 때만 아래 공개 기준을 통과한 내용을 사용한다.

## 결과 주장 gate

수치나 실제 결과를 성과로 적을 때는 아래 항목을 함께 확인한다.

- 기준선: 변경 전 상태는 무엇인가
- 목표: 어떤 변화가 성공인지
- 대상: 영향을 받는 사용자, 팀 또는 운영 범위는 무엇인가
- 인과 사슬: 변경이 어떤 경로로 결과에 영향을 준다고 보았는가
- 관찰 기간: 언제부터 언제까지 어떤 방법으로 확인했는가
- 후속 결정: 관찰 뒤 유지, 확대, 되돌림 또는 추가 확인 중 무엇을 할 것인가

항목 하나라도 근거로 확인하지 못했다면 결과는 `미확인`으로 남긴다. 구현이나 문서 작성만 끝난 상태는 결과 달성이 아니라 해당 작업의 완료일 뿐이다. 인과 사슬을 검증하지 못했다면 결과와 변경의 관계를 가설로 표현한다.

## 작업 전 체크리스트

- [ ] 해결하려는 사용자 또는 팀의 문제를 한 문장으로 설명할 수 있다.
- [ ] 변경하지 않을 범위와 성공 조건을 구분했다.
- [ ] 비교할 기준선, 관찰 방법과 다시 확인할 조건을 정했다.
- [ ] 소비자 영향, 호환성, 배포와 복구 경계를 확인했다.
- [ ] 내가 결정할 일과 다른 역할의 결정이 필요한 일을 구분했다.

## 진행 중 체크리스트

- [ ] 확인된 사실과 아직 검증하지 않은 가정을 분리했다.
- [ ] 범위, 위험 또는 결정이 바뀌면 관련 역할에 알렸다.
- [ ] 변경이 예상과 다를 때 중단하거나 되돌릴 조건을 확인했다.
- [ ] 반복 가능한 확인 절차를 남겼다.

## 완료 후 체크리스트

- [ ] 무엇이 바뀌었는지와 확인한 환경을 설명할 수 있다.
- [ ] 결과를 즉시 확인, 관찰 후 확인, 아직 측정 불가로 구분했다.
- [ ] 결과를 확인하지 못했다면 대리 근거와 다시 확인할 조건을 남겼다.
- [ ] 남은 위험, 후속 결정과 담당 경계를 명확히 했다.

## 증거 기록 형식

| 항목 | 공개 가능한 서술 |
| --- | --- |
| 문제 | 어떤 사용성, 안정성 또는 반복 마찰을 줄이려 했는가 |
| 판단 | 어떤 선택지와 제약을 비교했는가 |
| 변화 | 무엇을 바꾸고 어떤 검증을 했는가 |
| 결과 | 확인된 변화, 한계와 다음 확인 조건은 무엇인가 |
| 기여 | 개인 또는 팀의 기여 범위를 과장 없이 어떻게 표현할 것인가 |

숫자가 필요하면 공개 데이터나 독립 재현 환경에서 얻은 값만 사용한다. 내부 지표의 값, 변화율, 임계값과 관찰 기간은 공개 문서에 옮기지 않는다.

## 공개 전 점검

자기평가를 외부에 공유하기 전에는 아래 기준으로 근거를 먼저 점검한다.

- [ ] 회사, 제품, 고객, 팀원, 내부 도구와 프로젝트 식별자를 제거했다.
- [ ] 내부 구조, 접근 경로, 운영 절차와 취약점을 재현할 수 있는 세부를 제거했다.
- [ ] 승인되지 않은 수치, 일정, 계약, 비용과 인사 정보를 제거했다.
- [ ] 실제 업무를 설명해야 한다면 공개 자료 또는 독립 예제로 일반화했다.
- [ ] 확인할 수 없는 효과를 성과처럼 표현하지 않았다.

## 자기평가는 행동 근거로 교정한다

자신감의 높낮이만으로 역량 수준을 판단하지 않는다. 22개 메타분석을 종합한 연구에서 능력 자기평가와 수행 결과의 관계는 중간 정도였으며, 포괄적인 평가보다 특정 영역에 대한 평가에서 관계가 더 강했다. 이 결과는 자신을 낮게 평가하는 사람이 고성과자라는 판별 규칙이 아니다.

성과 기록은 직무에 필요한 역량을 구체적인 문제, 행동과 결과로 설명하고, 해당 직무의 행동 기준과 대조할 수 있어야 한다. 자기보고 점수와 사실 확인을 거친 성과 기록은 같은 근거 수준으로 취급하지 않는다.

다음은 자기평가 연구와 OPM의 성과 기록 평가 방식을 개인 성장 점검에 적용한 절차다. 특정 회사의 인사 평가 제도를 뜻하지 않는다.

1. 비교할 역량 하나와 기대 행동을 정한다. 개발을 잘한다는 총평보다 장애 원인 가설을 로그와 재현 결과로 검증한다는 식으로 좁힌다.
2. 위 증거 기록 형식에 따라 직접 한 행동과 확인된 결과를 적는다. 팀 전체 성과와 본인 기여를 분리한다.
3. 그 행동을 검토할 수 있는 사람에게 같은 기준으로 확인을 요청한다. 자기평가와 의견이 다르면 사람의 등급을 정하기보다 빠진 증거나 기준 차이를 찾는다.
4. 아직 입증하지 못한 역량은 부족함이 확정된 것으로 처리하지 않는다. 다음 작업에서 관찰할 행동과 확인 방법을 정하고 다시 대조한다.

타인의 이름, 연락처와 비공개 피드백 원문은 이 문서에 남기지 않는다. 제출용 경험 서술은 [[Resume-Experience-Narrative-and-Evidence|이력서 경험 서술과 증거 설계]]를 따른다.

## 되짚기 질문

- 이번 작업에서 무엇을 증거로 확인했고 무엇은 아직 가설인가?
- 더 이른 공유나 작은 검증으로 줄일 수 있었던 위험은 무엇인가?
- 같은 종류의 작업에 재사용할 질문이나 확인 절차는 무엇인가?
- 공개 가능한 학습으로 남길 만한 일반 원칙이 있는가?
