# 엔지니어 업무 성장 루프

구현만 끝내는 데서 멈추지 않고 목적을 확인하고 협업하며 결과를 검증하는 습관을 위한 범용 체크리스트다. 특정 조직의 공식 절차나 평가 기준을 대신하지 않는다.

## 이미 가진 기반

- 복잡한 기술 문제를 구조화하고 끝까지 파고드는 힘
- 코드, 문서와 측정 가능한 근거를 선호하는 판단 방식
- 혼자 탐색하고 구현까지 진행할 수 있는 실행력
- 동료와 피드백을 주고받으며 문제를 해결한 경험
- 모르는 영역을 빠르게 학습하고 따라잡는 끈기

성장 과제는 이 강점을 제품 목표, 직군 간 언어 번역, 의사결정 공유와 결과 확인까지 넓히는 것이다.

## 2026-08 기록 스냅샷

당시 자기평가에서는 기술 문제를 혼자 구조화하고 구현하는 힘은 이미 가진 기반으로 봤다. 새 성장 가설은 커뮤니케이션 양을 무작정 늘리는 것이 아니라, 목적, 열린 결정, 위험과 결과를 필요한 시점에 연결하면 협업 결과가 좋아진다는 것이었다.

이를 확인하기 위해 4주 행동 실험을 계획했다. 정확한 회사 일정이나 업무 내용은 기록하지 않고 실험의 구조와 완료 판단만 보존한다.

1. 시작 전에 목적, 우선순위, 인수 기준과 완료 조건을 확인한다.
2. 열린 결정이나 의존성을 조기에 공유하고 승인된 팀 기록을 갱신한다.
3. 완료한 작업의 결과를 즉시 확인, 관찰 후 확인 또는 측정 불가로 구분한다.
4. 협업 역할에게 개선점 하나를 요청하고 다음 기간에 유지할 행동 하나를 고른다.

계획 횟수나 문서 작성 자체는 성공으로 계산하지 않는다. 실행 여부와 효과는 확인 가능한 증거와 월간 되짚기로 판단한다.

## 시작 전

- [ ] 이 일이 지금 필요한 이유와 해결하려는 문제를 설명할 수 있다.
- [ ] 성공 조건, 보호 조건과 완료 범위를 확인했다.
- [ ] 우선순위, 소비자 영향과 의존성을 확인했다.
- [ ] 내가 결정할 부분과 다른 역할의 판단이 필요한 부분을 구분했다.
- [ ] API, 데이터 또는 배포 변경이라면 호환성, 활성화와 복구 경계를 확인했다.

### 요청한 기능과 해결할 문제를 구분한다

사용자가 하려는 일, 현재 처리 방식과 막히는 지점을 먼저 적는다. 기능 제안은 그 문제를 해결할 후보로 두고, 사용자 조사나 관찰로 확인한 필요와 팀의 가정을 구분한다. 예를 들어 알림 기능을 요청받았다면 먼저 무엇을 놓치고 있으며 어떤 결과가 필요한지 확인한다.

이 원칙을 업무에 적용할 때는 코드 추가 외에 기존 기능의 안내나 업무 절차 변경도 비교 후보로 둘 수 있다. 이는 문제와 해결책을 분리하는 원칙에서 도출한 점검 방법이며, 코드가 적을수록 성과가 좋다는 보장은 아니다. 문제 정의의 세부 판단은 [[Problem-Framing|문제 정의와 대응]]을 참조한다.

## 진행 중

상태 공유에는 다음 정보를 짧게 담는다.

1. 목표와 현재 상태
2. 확인된 사실과 검증 환경
3. 필요한 결정 또는 위험
4. 다음 행동과 확인 조건

다음 경우에는 결론을 기다리지 말고 관련 역할에 알린다.

- 범위나 성공 조건이 달라졌을 때
- 일정, 품질 또는 안전에 영향을 줄 위험을 발견했을 때
- 다른 역할의 정보나 결정을 기다려야 할 때
- 되돌리기 어려운 선택을 하기 전

### 이해하지 못한 부분을 질문으로 드러낸다

코드 리뷰에서 이해되지 않는 동작은 작성자에게 설명을 요청한다. 이해는 했지만 보안, 동시성 등 특정 영역을 검토할 전문성이 부족하다면 해당 역량을 가진 검토자를 연결한다. 설명을 들은 것과 그 범위를 직접 검증한 것은 구분한다.

작성자는 줄 수를 줄인 정도보다 다음 사람이 동작을 빠르게 이해하고 안전하게 수정할 수 있는지 확인한다. 현재 필요가 확인되지 않은 범용화와 기능 추가도 검토 대상에 넣는다. 이를 개인의 능력 평가로 쓰지 않고 이번 변경의 읽기 비용과 검증 범위를 맞추는 데 사용한다.

## 완료 후

- [ ] 무엇이 바뀌었는지와 확인한 범위를 설명할 수 있다.
- [ ] 결과를 즉시 확인, 관찰 후 확인, 아직 측정 불가로 구분했다.
- [ ] 미확인 결과에는 대리 근거와 다시 확인할 조건을 남겼다.
- [ ] 남은 위험, 후속 행동과 책임 경계를 기록했다.
- [ ] 팀의 승인된 기록에 필요한 결정과 상태를 갱신했다.

## 역할별 설명 점검

| 대상 | 우선 설명할 내용 |
| --- | --- |
| 제품 및 기획 역할 | 사용자 영향, 정책과 우선순위 |
| 클라이언트 개발 역할 | 계약, 오류 조건, 적용과 검증 방법 |
| 서버 개발 역할 | 선택 근거, 호환성, 운영 위험과 복구 |
| 의사결정 역할 | 왜 지금인지, 선택지와 필요한 판단 |

## 행동 실험

| 구간 | 행동 | 남길 공개 가능 증거 |
| --- | --- | --- |
| 시작 | 작업 전에 목적과 완료 조건을 확인한다. | 목적, 우선순위 근거와 인수 기준 |
| 진행 | 열린 결정이나 의존성을 조기에 공유한다. | 공유한 판단 유형과 갱신한 상태 |
| 완료 | 결과 상태를 구분해 정리한다. | 즉시 확인, 관찰 후 확인 또는 측정 불가 |
| 회고 | 협업 역할에게 개선점 하나를 요청한다. | 역할 기반 피드백 요약과 다음 행동 하나 |

실제 완료 여부는 확인된 기록으로만 갱신하고 횟수 자체를 성과로 해석하지 않는다.

## 공개 기록 안전선

공개 문서에는 배운 원칙과 독립 재현 결과만 남긴다. 회사, 제품, 고객, 사람, 내부 도구, 원문 수치, 일정, 접근 경로와 운영 상세는 기록하지 않는다. 실제 경험을 설명해야 하면 공개 자료 또는 별도 재현 예제로 일반화하고 확인하지 못한 결과는 추정하지 않는다.

## 되짚기 질문

- 목적과 완료 조건을 충분히 이른 시점에 확인했는가?
- 어떤 가정이 나중에 틀렸고 더 작은 검증으로 확인할 수 있었는가?
- 누가 어떤 결정을 내려야 했는지 충분히 분명했는가?
- 다음 작업에서 유지할 행동 하나와 바꿀 행동 하나는 무엇인가?
