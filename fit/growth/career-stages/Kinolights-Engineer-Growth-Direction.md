# 키노라이츠에서의 엔지니어 성장 방향

기술 문제를 독립적으로 푸는 엔지니어에서, **팀이 왜 이 문제를 지금 풀고 있으며 어떤 결정과 결과가 필요한지 연결하는 엔지니어**로 성장한다.

이 문서는 역량 부족을 판정하는 평가표가 아니다. 이미 가진 기술적 강점을 제품팀의 목표, 의사결정, 협업과 결과까지 확장하기 위한 행동 계획이다.

## 자기평가: 이미 가진 기반

다음은 기존 자기분석에서 출발한 자기평가다.

- 복잡한 기술 문제를 구조화하고 끝까지 파고드는 힘
- 코드, 문서와 측정 가능한 근거를 선호하는 판단 방식
- 혼자 탐색하고 구현까지 진행할 수 있는 실행력
- 동료 피드백을 주고받으며 문제를 해결한 경험
- 모르는 영역을 빠르게 학습하고 따라잡는 끈기

42서울에서 쌓은 동료 학습과 문제 해결 경험은 유효하다. 다만 회사의 제품팀에서는 여기에 **직군 간 언어 번역, 조직의 우선순위 파악, 의사결정 과정 공유와 결과 확인**이 추가로 필요하다. 지금 느끼는 어려움은 기존 강점의 부정이 아니라 적용 범위가 넓어지는 과정이다.

## 전제로 두는 팀 맥락

제품팀의 일은 구현 정확성만으로 끝나지 않는다. 일반적으로 다음 세 종류의 일이 함께 진행된다.

- 사용자 가치를 키우는 제품 실험
- 기존 기능의 안정화와 기술 부채 해소
- 팀의 개발 및 운영 효율 개선

제품팀 업무에서는 실험의 지표와 QA, 변경의 호환성과 모니터링, 작업 상태와 중요 결정의 기록이 일반적으로 함께 요구된다. 아래 흐름은 이를 바탕으로 **내 업무를 설계하기 위한 작업 모델**이며, 팀의 모든 업무에 적용되는 공식 절차라고 단정하지 않는다.

- 제품 실험: 문제 → 가설 → 핵심 지표와 보호 지표 → 로그 → 검수 → 배포 → 결과
- 안정화: 필요한 이유 → 계약과 호환성 → 배포와 롤백 → 모니터링 → 이전 방식의 종료 조건
- 효율 개선: 현재 마찰 → 개선안 → 영향을 받는 역할 → 절감되는 시간이나 오류 → 정착 여부

이 작업 모델에서 좋은 기술 결정은 코드 안에서만 옳은 결정이 아니다. **팀의 목표와 연결되고, 관련 역할이 이해할 수 있으며, 확인 가능한 범위에서 결과와 다음 판단까지 남기는 결정**이어야 한다.

## 검증할 성장 가설

기존 업무 기록에도 변경 영향, 단계적 전환, 로깅과 운영 모니터링을 먼저 공유한 사례가 있다. 따라서 처음부터 배우는 문제가 아니라, 좋은 행동을 여러 종류의 업무에서 반복 가능한 습관으로 만드는 문제에 가깝다.

현재 가설은 **커뮤니케이션 양을 무작정 늘리기보다 필요한 맥락을 제때 연결하면 협업 결과가 좋아진다**는 것이다. 아래 네 행동을 실험하고 실제 피드백으로 검증한다.

### 1. 작업을 팀의 결과와 연결하기

작업을 받으면 구현 방법보다 먼저 다음을 파악한다.

- 왜 지금 해야 하는가
- 어떤 사용자 문제나 팀 문제를 줄이는가
- 성공과 실패를 무엇으로 판단하는가
- 다른 업무와 비교했을 때 우선순위가 어디인가

### 2. 머릿속 판단을 팀이 볼 수 있게 만들기

충분히 고민한 뒤 공유하는 것은 강점이지만, 공유 시점이 늦어지면 팀이 중간의 가정과 위험을 알기 어렵다. 완성된 결론을 기다리지 않고 다음 항목은 일찍 공유한다.

- 아직 열려 있는 결정
- 다른 역할의 판단이 필요한 지점
- 일정이나 품질에 영향을 주는 위험
- 현재 선택한 방향과 그 근거

### 3. 기술 언어를 역할별 결과로 번역하기

같은 변경도 듣는 역할에 따라 필요한 설명이 다르다.

- 기획 및 제품 역할: 사용자 영향, 지표, 정책과 우선순위
- 프론트엔드 역할: API 계약, 오류 조건, 적용 시점과 검증 방법
- 백엔드 역할: 설계 선택, 호환성, 운영 위험과 롤백
- 리더 역할: 왜 지금인지, 선택지와 비용, 필요한 결정

### 4. 구현 완료에서 결과 확인까지 닫기

PR 병합이나 배포는 중간 상태다. 완료 후 결과를 다음 세 상태로 구분해 남긴다.

- 즉시 확인: 배포 상태, QA, 로그와 운영 이상 여부
- 관찰 후 확인: 사용자 행동이나 팀 효율처럼 시간이 필요한 결과, 관찰 기간과 확인 시점
- 아직 측정 불가: 사용할 수 있는 대리 근거, 불확실성과 다시 확인할 조건

## 인재상을 행동으로 번역하기

회사 인재상은 나를 평가하는 추상적인 문구가 아니라, 업무 중 선택을 돕는 기준으로 사용한다.

| 가치 | 업무에서 보일 행동 |
|---|---|
| 발전적 의심 | 요구사항과 기존 방식을 그대로 받지 않고 목적, 가정과 성공 기준을 확인한다 |
| 훌륭한 실패 | 시도 전에 가설과 보호 조건을 세우고, 결과가 좋지 않아도 학습과 다음 결정을 남긴다 |
| 신뢰와 존중의 팀워크 | 관련 역할이 늦게 알게 될 정보를 먼저 공유하고, 상대의 맥락을 확인한다 |
| 파격적 집중 | 가능한 일을 모두 잡기보다 현재 가장 중요한 결과 하나를 명확히 고른다 |
| 불굴의 실행 | 구현에서 멈추지 않고 배포, 검증과 후속 조치까지 닫는다 |
| 용기 있는 솔직함 | 불확실성, 반대 의견과 위험을 숨기지 않고 근거와 함께 일찍 드러낸다 |

## 업무 운영 루프

### 시작 전

아래 질문에 답하지 못하면 구현 전에 맥락을 더 확인한다.

- 이 일의 목적은 무엇인가
- 왜 지금 하는가
- 우선순위의 근거와 그 근거의 강도는 어느 정도인가
- 현재 스프린트에서 완료 가능한 범위인가
- 성공 기준, 보호 조건과 반드시 통과할 인수 기준은 무엇인가
- 필수 QA와 선택 QA는 무엇인가
- 내가 결정할 것과 다른 역할이 결정할 것은 무엇인가
- 완료는 구현, 배포, 검증과 측정 중 어디까지인가
- API 또는 마이그레이션이라면 소비자 영향, 활성화 조건, 배포 순서와 롤백 경계는 무엇인가

### 진행 중

상태 공유는 길게 설명하기보다 네 줄로 정리한다.

1. 목표와 현재 상태
2. 확인된 사실과 작업 또는 QA 환경
3. 필요한 결정 또는 위험
4. 다음 행동과 예상 시점

중요한 결정, 범위, 인수 기준과 상태는 개인 메모에만 두지 않고 팀이 정한 Task 또는 프로젝트 기록에도 갱신한다.

### 완료 후

결과 공유는 작업 목록이 아니라 변화 중심으로 정리한다.

1. 무엇이 달라졌는가
2. 어떤 환경과 범위에서 정상임을 확인했는가
3. 결과는 즉시 확인, 관찰 후 확인과 아직 측정 불가 중 어디에 있는가
4. 측정 가능한 결과나 대리 근거는 무엇인가
5. 남은 위험, 확인 시점과 다음 결정은 무엇인가

## 앞으로 4주간의 행동 실험

| 기간 | 행동 | 남길 증거 |
|---|---|---|
| 1주차 | 맡은 작업 3건에서 시작 전 질문에 답한다 | 목적, 우선순위 근거, 인수 기준과 완료 조건 |
| 2주차 | 열린 결정이나 의존성을 최소 2번 조기에 공유하고 팀 기록을 갱신한다 | 결정 시점, 실제로 받은 답과 갱신한 상태 |
| 3주차 | 완료한 작업 1건의 결과 상태를 구분해 정리한다 | 즉시 확인, 관찰 후 확인 또는 측정 불가와 후속 조치 |
| 4주차 | 리더 또는 협업 역할에게 개선점 하나를 요청한다 | 받은 피드백과 다음 달에 유지할 행동 하나 |

횟수 자체가 목표는 아니다. 다음 변화가 나타나는지 관찰하기 위한 최소 실험량이다.

- 늦게 발견한 계약이나 인수 기준 때문에 생기는 재작업이 줄어드는가
- 팀원이 별도로 묻기 전에 현재 상태와 위험을 알 수 있는가
- 다른 역할의 결정이 필요한 시점이 앞당겨지는가
- 배포 이후 확인된 결과, 불확실성과 다음 확인 시점이 남는가
- 기술 기여가 팀의 목표와 연결되어 설명되는가

## 증거 기록 템플릿

| 날짜 | 작업 | 연결된 팀 목표 | 조기에 공유한 결정 또는 위험 | 팀 기록 갱신 | 결과 상태와 근거 | 피드백과 다음 행동 |
|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |

이 표는 행동을 회고하기 위한 개인 색인이다. 실제 결정과 상태는 팀의 공식 기록에 남긴다. 사람 이름 대신 제품 역할, 프론트엔드 역할, 백엔드 역할과 리더 역할처럼 기록하고, 내부 링크, 비공개 수치와 민감한 운영 정보는 이 저장소에 옮기지 않는다.

## 월간 점검 질문

- 이번 달에 구현 전에 목적과 성공 기준을 확인한 작업은 무엇인가
- 늦게 공유해서 재작업한 일과 일찍 공유해서 줄인 위험은 무엇인가
- 내가 설명한 기술 결정이 다른 역할의 판단에 실제로 도움이 되었는가
- 배포 직후와 관찰 기간 후의 결과를 구분해 남긴 작업은 무엇인가
- 다음 달에는 어떤 행동 하나만 더 자연스럽게 만들 것인가

## 가정과 한계

- 이 문서의 작업 모델은 내 업무 설계를 위한 가정이며, 개인 역량 평가나 모든 업무의 공식 절차를 증명하지 않는다.
- 실제 운영 지표는 이 저장소에 옮기지 않으며, 결과를 추정해 채우지 않는다.
- 실제 기대 수준은 업무 결과와 리더 및 협업 역할의 피드백으로 계속 교정한다.
- 팀의 목표와 일하는 방식은 바뀔 수 있으므로 매달 다시 확인한다.
