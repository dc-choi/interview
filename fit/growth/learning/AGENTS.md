# Learning Domain Rules

이 파일은 `fit/growth/learning/`의 학습 계획, 로드맵, 우선순위와 진행 판단에 적용한다.

ORM 관련 학습 우선순위를 다룰 때는 `tech/AGENTS.md`도 읽는다.

## 학습 원칙

- **판단을 위한 학습 로드맵:** 지식 저장소에 축적한 내용을 사용자가 이해하고 직접 판단에 활용할 수 있도록 개발과 대표 역할의 학습 로드맵을 함께 유지한다. 관련 지식 원문에 학습 목적, 순서와 이해 확인 방법을 연결하며, 로드맵에 남긴 전체 범위와 현재 실행할 진도는 구분한다.
- **현재 대표 역할의 학습 맥락:** 대표 역량을 중심으로 관련 기술과 운영 지식을 연결한다. 과거 재직, 인계와 기술 트랙 선택지는 현재 사업 학습의 범위를 제한하지 않는다. 현재 필요한 학습은 프로젝트 맥락을 조회해 제안하고, 별도 요청 없이 로컬 프로젝트 목록이나 추천 지도를 상시 문서화하지 않는다. 지식 보완으로 새 정규 트랙이나 제품 실험이 자동 활성화되지는 않는다.
- **개발 기반 유지:** 2026-09-22 사용자는 기존 개발자 커리어 학습 로드맵도 자신의 기반이므로 계속 유지하도록 요청했다. 대표 역할의 브랜딩, 마케팅, 경제와 재무 학습은 이 기반에 추가하는 영역이며 기존 개발 로드맵을 폐기하거나 대체하는 이유가 아니다. 로드맵 유지와 개별 트랙의 재개는 구분하고, 기존 로드맵 수만으로 사업 학습의 필요성을 낮게 판단하지 않는다.
- **아웃풋 우선**: 블로그, 말하기와 쓰기에 시간을 쓴다. 강의와 아웃풋이 충돌하면 아웃풋을 우선한다. 다만 수학 기초 단계에서는 개념 입력과 손계산 반복 자체를 필수 과정으로 인정하고 블로그나 코드 산출물을 억지로 요구하지 않는다.
- **단일 주축 원칙**: 체계적인 개인 학습은 한 번에 한 트랙만 진행한다. 실무에서 만난 짧은 보충은 공개 로드맵 진도로 계산하지 않는다. 주일학교 출석부는 사용자가 별도로 활성화하기 전까지 선택지 보존 범위를 넘어 운영하거나 학습 실습 대상으로 열지 않는다. 사업 실험이 활성화되더라도 학습 진도가 아니라 제품 운영으로 관리한다.
- **업무 연계 기술 우선**: 실무에서 필요한 기술은 미래 투자와 범용 학습보다 먼저 다룰 수 있다. 학습 트랙의 선택과 시간 배분은 개인의 결정이며 회사 지시나 평가 기준으로 표현하지 않는다. 구체적인 조직 스택, 과제와 내부 사용 방식은 공개 로드맵에 기록하지 않는다.
- **공통 실무 기반**: GraphQL, Redis와 Git은 별도 정규 목표가 아니라 개인이 반복 학습할 기반이다. 공개 예제와 로컬 실습으로 요청 흐름, key 설계와 Git ref 변화를 추적하고 작은 설명이나 안전한 복구 결과로 빈칸을 닫는다.
- **그 밖의 기술**: JS, TS, Node.js, gRPC, Kafka와 그 밖의 기술도 실제 필요가 생기면 미래 투자보다 먼저 다룬다. 별도 정규 트랙을 동시에 열거나 읽은 분량을 숙련으로 계산하지 않는다.
- **검증**: AI는 자료 탐색, 설명과 검산에 활용하되 중요한 결론은 소스, 실행 결과나 계산으로 확인한다.
- **전체 그림 우선 이해형**: 부분 개념보다 전체 아키텍처가 먼저 보여야 이해가 붙는다. 2026-07-14 OpenSearch 학습에서 확인한 방식대로 전체 구조를 먼저 보고 세부 내용을 학습한 다음 문서를 보지 않고 구조를 재현한다.
- **모듈별 재선택**: Terraform, Kubernetes, 검색, 추천과 Node.js의 한 성공선을 닫을 때마다 다음 모듈을 자동으로 열지 않고 장기 목표와 가용 시간을 다시 확인한다. 문서의 연도는 가장 이른 시작 목표이지 마감일이 아니다.

## 학습 상태와 계획의 정본

- 생활과 업무의 우선순위, 트랙 선택과 자격증 전환 조건은 `fit/growth/Current-Goals-and-Roadmap.md`를 참조한다. 과거 전환기의 조건을 현재 역할에 그대로 적용하지 않고 최신 사용자 설명과 대조한다.
- 개발 학습 후보와 장기 기술 축은 `roadmaps/roadmaps.md`, 트랙별 진행 상태와 재개 지점은 해당 로드맵에서 관리한다. 이 지침에는 현재 활성 여부나 진도를 복제하지 않는다.
- 수학의 교재 범위와 학습 절차는 `roadmaps/2026-H2-Math-Roadmap.md`, DevOps의 실습 순서와 통과 조건은 `roadmaps/2027-DevOps-Practical-Roadmap.md`, 검색 재개 지점은 `tech/database/nosql/opensearch/OpenSearch.md`를 따른다.
- 정본의 상태는 확인된 진행만 갱신하고, 지침 정리를 이유로 기존 학습 범위를 삭제하거나 트랙을 재개하지 않는다.

## 집중도별 학습 모드

- 집중할 수 있는 시간에는 글쓰기나 현재 선택한 트랙의 개념 이해와 손계산처럼 깊이가 필요한 일을 한다.
- 자투리 시간에는 짧은 강의, 책 복습, 이미 푼 문제와 용어 복습을 한다. 새로운 개념은 시작하지 않는다.
- 기술 강의는 짧은 챕터, 훑기와 복습 같은 자투리 시간 적합도로 판단한다. 깊은 집중이 필요하면 별도의 집중 시간으로 옮긴다. 수학에서는 손으로 풀이 과정을 남기는 것을 아웃풋으로 인정한다.

## 학습 상태 판단

- 저장소의 `status: done` 수량과 문서 완성 비율을 숙련도 프록시로 사용하지 않는다. 이는 문서 상태이지 숙련도가 아니다.
- 사용자가 CS는 밀린다고 자가 진단했다. 정리된 문서가 있어도 면접이나 글에서 스스로 설명하지 못하면 숙련으로 보지 않는다. 숫자만 보고 CS 강의가 필요 없다고 결론 내리지 않는다.
- 학습 우선순위를 제안하기 전에 자가 진단을 묻거나 해당 주제가 말이나 글로 바로 나오는지 확인한다. 문서 수는 맥락 참고로만 사용한다.

## CS 학습 이유

- CS를 배우는 이유는 웹 인프라의 논리적 흐름과 구조 이해, 비용과 성능 효율, 장애와 디버깅, 설계 의사결정의 언어를 확보하기 위해서다. ORM 이상 쿼리, 커넥션 풀 고갈과 GC처럼 추상화가 새는 문제에서는 밑단 지식이 원인 파악의 근거가 된다.
- AI는 코드 초안과 반복 작업을 보조할 수 있지만, 무엇을 왜 만들지와 결과를 검증하는 책임은 개발자에게 있다는 멘토링 합의를 따른다.
- 학습 깊이는 해당 CS 주제가 실제 설계 의사결정으로 말이나 글에 나오는지를 기준으로 정한다. 인덱스 내부 구조를 외우는 데서 끝내지 않고 특정 쿼리에 그 인덱스를 선택한 이유를 설명할 수 있어야 한다. 메시지 브로커 비교와 ORM 실행 계획 검증처럼 조건, 대안과 측정 결과를 연결한다.
