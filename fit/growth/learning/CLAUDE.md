# Learning Domain Rules

이 파일은 `fit/growth/learning/`의 학습 계획, 로드맵, 우선순위와 진행 판단에 적용한다.

ORM 관련 학습 우선순위를 다룰 때는 `tech/CLAUDE.md`도 읽는다.

## 학습 원칙

- **아웃풋 우선**: 블로그, 말하기와 쓰기에 시간을 쓴다. 강의와 아웃풋이 충돌하면 아웃풋을 우선한다. 다만 수학 기초 단계에서는 개념 입력과 손계산 반복 자체를 필수 과정으로 인정하고 블로그나 코드 산출물을 억지로 요구하지 않는다.
- **기존 장기 기술 축**: JS, TS와 Node.js 코어 및 블로그, CS와 OOP 및 디자인 패턴과 헥사고날 및 클린 아키텍처, 시스템 디자인, MySQL 순서다. 2026-07-22 이후 개인 학습 일정은 아래 수학 우선순위가 덮어쓴다.
- **단일 주축 원칙**: 체계적인 개인 학습은 한 번에 한 트랙만 진행한다. 현업에 필요한 짧은 보충은 수행하되 학습 로드맵 진도로 계산하지 않는다. 주일학교 출석부는 최하위 백로그이므로 학습 실습 대상으로 열지 않는다.
- **회사 기술 상시 우선**: 회사에서 실제로 쓰며 현재 결과에 연결되는 기술은 미래 투자와 범용 학습보다 항상 먼저 다룬다. 현재 역할 기술의 1순위는 검색이다. 그 다음에는 현재 Task를 막는 빈칸, 사용 빈도와 결과 영향으로 하나를 고른다.
- **공통 실무 기반**: GraphQL, Redis와 Git은 검색보다 앞선 별도 목표가 아니라 실무에서 자주 쓰이는 기반이다. GraphQL과 Redis는 실제 요청 및 key 흐름을, Git은 commit graph, working tree/index와 local/remote ref의 상태 변화를 추적한다. Task, PR, QA, 운영 또는 안전한 복구 결과와 공개 가능한 작은 설명으로 빈칸을 닫는다.
- **그 밖의 회사 기술**: JS, TS, Node.js, gRPC, Kafka와 그 밖의 기술도 현재 Task나 반복 책임이 생기면 미래 투자보다 먼저 다룬다. 별도 정규 트랙을 동시에 열거나 읽은 분량을 숙련으로 계산하지 않는다.
- **미래 DevOps 방향**: DevOps는 회사 기술을 밀어내지 않는 미래 역할 투자다. 선택 gate에서 여력이 확인된 경우 Terraform을 먼저 실습하고, 그 성공선을 닫은 뒤 다시 선택한 경우에만 Kubernetes로 진행한다. 둘 중 하나가 회사의 현재 책임이 되면 미래 투자 순서를 기다리지 않고 회사 기술로 다룬다.
- **검증**: AI는 자료 탐색, 설명과 검산에 활용하되 중요한 결론은 소스, 실행 결과나 계산으로 확인한다.
- **전체 그림 우선 이해형**: 부분 개념보다 전체 아키텍처가 먼저 보여야 이해가 붙는다. 2026-07-14 OpenSearch 학습에서 확인한 방식대로 전체 구조를 먼저 보고 세부 내용을 학습한 다음 문서를 보지 않고 구조를 재현한다.
- **수학 출발점**: 2026-07-23 기준, 《개발자를 위한 필수 수학》 1장부터 6장과 《컴퓨팅 사고력을 키우는 이산수학 3판》 1장부터 12장을 장기 기반 범위로 끝까지 학습한다. 필수 수학 7장 신경망은 제외하고 8장 경력 조언은 선택 독서로 두며 수학 gate에 포함하지 않는다. 외부 기초 자료를 먼저 완주하지 않고 교재 예제에서 막힌 선행 개념만 보충한다. 6주 완주 가정이나 교재 진도율로 압박하지 않고 손계산, 풀이 설명과 작은 코드 검산으로 확인한다.
- **현재 실행 트랙**: 업무와 역할 학습의 1순위는 검색이고, `2026-H2-Math-Roadmap.md`의 수학은 현재 유일한 정규 개인 학습 트랙이다. 검색 업무가 바쁘면 수학 속도를 낮추거나 현재 위치를 기록하고 보류하며 다른 정규 트랙을 병행하지 않는다.
- **선택형 전환**: 수학 2단계 gate와 입사 첫 90일 회고를 마친 뒤 `Current-Goals-and-Roadmap.md`의 전체 후보 목록을 적용한다. 검색을 포함한 회사 기술 심화, 미래 DevOps 투자, Node.js부터 시작하는 범용 백엔드 대기열과 보류 순서로 비교해 하나만 고른다.
- **모듈별 재선택**: 회사 기술, Terraform, Kubernetes, 검색, 추천과 Node.js의 한 성공선을 닫을 때마다 다음 모듈을 자동으로 열지 않고 현재 업무 수요, 장기 목표와 가용 시간을 다시 확인한다. 문서의 연도는 가장 이른 시작 목표이지 마감일이 아니다.
- **자격증 대기**: AWS와 Kubernetes 자격증은 대응하는 실습 gate와 업무 필요를 확인한 뒤 판단한다. 정보처리기사는 기술사 경로의 필요성과 시험 일정이 확정된 경우에만 현재 정규 트랙을 대체한다. 자격증을 정규 트랙과 병행하지 않는다.

## 시간대별 학습 모드

- 퇴근 후에는 기술 아웃풋이나 수학 개념 이해와 손계산처럼 집중이 필요한 일을 한다.
- 근무 중 자투리 시간에는 짧은 강의, 책 복습, 이미 푼 문제와 용어 복습을 한다. 새로운 수학 개념은 시작하지 않는다.
- 기술 강의는 짧은 챕터, 훑기와 복습 같은 자투리 시간 적합도로 판단한다. 깊은 집중이 필요하면 퇴근 후 아웃풋 트랙으로 옮긴다. 수학에서는 손으로 풀이 과정을 남기는 것을 아웃풋으로 인정한다.

## 학습 상태 판단

- 저장소의 `status: done` 수량을 숙련도 프록시로 사용하지 않는다. CS 64/65나 Node.js 45/53 같은 수치는 문서 상태이지 숙련도가 아니다.
- 사용자가 CS는 밀린다고 자가 진단했다. 정리된 문서가 있어도 면접이나 글에서 스스로 설명하지 못하면 숙련으로 보지 않는다. 숫자만 보고 CS 강의가 필요 없다고 결론 내리지 않는다.
- 학습 우선순위를 제안하기 전에 자가 진단을 묻거나 해당 주제가 말이나 글로 바로 나오는지 확인한다. 문서 수는 맥락 참고로만 사용한다.

## CS 학습 이유

- CS를 배우는 이유는 웹 인프라의 논리적 흐름과 구조 이해, 비용과 성능 효율, 장애와 디버깅, 설계 의사결정의 언어를 확보하기 위해서다. ORM 이상 쿼리, 커넥션 풀 고갈과 GC처럼 추상화가 새는 문제에서는 밑단 지식이 원인 파악의 근거가 된다.
- 코딩은 AI에 위임할 수 있어도 무엇을 왜 만들지에 대한 의사결정과 설계는 개발자의 책임이라는 멘토링 합의를 따른다.
- 학습 깊이는 해당 CS 주제가 실제 설계 의사결정으로 말이나 글에 나오는지를 기준으로 정한다. 인덱스 내부 구조를 외우는 데서 끝내지 않고 특정 쿼리에 그 인덱스를 선택한 이유를 설명할 수 있어야 한다. EventBridge와 SQS 비용 비교, 트래픽 정량 비교 및 Prisma `relationLoadStrategy` 실행계획 cost 검증처럼 실제 판단과 연결한다.
