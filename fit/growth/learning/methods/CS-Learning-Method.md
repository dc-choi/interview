# CS 지식 학습법, 키워드 기반 책 탐색

실무 문제를 해결할 때는 문제, 키워드, 목차와 필요한 장의 순서로 탐색할 수 있다. 기초 체계를 익히는 목적이라면 교재를 순서대로 읽고 연습하는 방법도 적합하다. 아래는 문제 중심 탐색의 운영 제안이며, 완독보다 언제나 효율적이라는 학습 법칙은 아니다.

## 핵심 명제

- **목적에 맞는 범위**: 긴급한 문제 해결과 기초 학습을 구분해 읽을 범위를 정한다
- **키워드 기반 접근** — 문제에서 출발해 목차를 검색
- **순환 탐색** — 모르는 단어 등장 시 그 단어로 다시 들어감
- **책 폭증 경계** — 참고 책이 너무 많아지면 **지금은 그만두기**
- **동료, 검색 병행** — 책만이 답은 아님

## 학습 루프

### 1. 문제, 호기심에서 출발

- 업무에서 부딪힌 개념, 면접 꼬리 질문, 코드 리뷰 피드백
- "왜 이 함수가 이렇게 동작하나", "이 에러 메시지의 근본 원인은?"
- 학습 목적을 적고, 어떤 설명이나 문제 풀이로 이해를 확인할지 정한다

### 2. 키워드로 목차 검색

- 책의 **목차 인덱스**에서 해당 키워드 찾기
- 관련 섹션만 **핀포인트 읽기**
- 배경 체계가 필요한지, 특정 절의 확인으로 충분한지 판단한다

### 3. 모르는 단어 발견 → 순환 탐색

- 현재 섹션에 **앞에서 언급된 듯한 단어**가 있으면 그 섹션으로 이동
- 그 섹션에서 또 모르는 단어가 있으면 또 이동
- 필요한 **선행 개념**까지 거슬러 올라간 뒤, 다시 원래 섹션으로 복귀

### 4. 책 바꾸기 판단

- **현재 책에 해당 키워드가 없거나 너무 부실**하면 다른 책 참고
- 참고 책이 늘면서 원래 문제로 돌아오지 못하면 탐색 범위를 줄인다
- 한 권을 기본, 한 권을 보조로 두는 방법을 시도할 수 있다. 책 수는 운영 기준의 예시이며 학습 효과의 임계값은 아니다

### 5. 동료, 구글링 활용

- 동료에게 **핵심 질문**으로 묻기 (본인 가설을 먼저 덧붙여서)
- Google, Stack Overflow로 실전 사례 탐색
- **공식 문서, 표준 명세**도 일종의 "책" — 같은 원리로 접근

### 6. 반복

- 필요한 개념을 다시 찾고 설명과 적용 결과를 확인하며 이 사이클을 반복한다
- 반복해서 읽은 횟수보다 나중에 설명하고 적용할 수 있는지 확인한다

## 탐색과 체계적 학습의 균형

필요한 절만 찾으면 당장의 문제를 빠르게 확인할 수 있지만, 앞 절의 정의와 가정을 놓칠 수 있다. 반대로 전체 교재를 읽는 계획은 필요한 배경을 연결할 수 있지만 현재 해결의 범위를 넘을 수 있다.

읽을 범위는 시간만으로 정하지 않고 필요한 선행 지식과 이해 확인 방법을 함께 고려한다. 지금 쓰지 않는 개념을 모두 일주일 안에 잊는다는 고정 기간은 가정하지 않는다.

## 책 폭증 경계

### 신호

- 책상에 참고 도서 3권 이상이 펼쳐져 있다
- "이 책 다 읽으면 저 책으로 넘어가야지" 계획이 누적
- 실제로는 진도가 거의 없음

### 대응

- **1~2권으로 제한** — 필요 시 한 권만 기본, 한 권만 보조
- 책 탭보다 **코드, 실전** 비중을 늘림
- 답이 안 나오면 책을 덮고 **동료, 검색**으로 전환

## 기초가 부족할 때는 순서 있는 학습을 병행한다

모르는 선행 개념이 계속 이어지면 현재 문제만 따라가는 탐색보다 기초 과정을 순서대로 공부하는 편이 적합할 수 있다. 교재의 설명, 예제와 연습문제로 이해를 확인한다.

교과서 10권 암기나 목차 키워드의 전부 재현을 입문자의 공통 선행 조건으로 두지 않는다. 필요한 지원을 고르는 관점은 [[Dreyfus-Skill-Model#학습 지원을 고르는 질문]]을 참고한다. 이 모형은 학습자의 독서량이나 코칭 수용 가능성을 판정하는 기준이 아니다.

## 낯선 분야는 용어부터 (First Word 법칙)

새 분야가 어렵게 느껴지는 큰 이유는 직관적으로 이해되지 않는 용어다. 모르는 용어가 많을수록 그 분야 전체를 어렵다고 느끼므로, 낯선 분야에 들어갈 때는 어려운 용어부터 먼저 정리한다.

- 처음 듣거나 곧 잊을 것 같은 용어는 반드시 기록한다. 블로그든 노트든 형식은 상관없고, 필요할 때 다시 꺼내 볼 수 있으면 된다.
- 뜻은 사전식 정의보다 내가 바로 떠올릴 수 있는 직관적 의미로 적는다. 목표는 용어를 봤을 때 머릿속에 의미가 떠오르는 것이다. 클라우드 서비스처럼 용어가 많은 분야에서 효과가 크다.
- 순환 탐색과 역할이 다르다. 순환 탐색은 읽다가 막힌 단어의 선행 개념으로 거슬러 가는 탐색이고, 용어집은 새 분야에 들어가는 초기에 미리 만드는 준비다. 이렇게 모은 용어집은 자투리 시간의 용어 복습 재료가 된다.
- 용어집은 암기 목록이 아니라 이해의 발판이다. 자기 말로 뜻을 쓰지 못하면 아직 정리된 것이 아니고, 직관적 정의는 출발점일 뿐 나중에 원전과 명세의 정의로 고친다([[Technical-Terminology-Precision|기술 용어의 엄밀성]]). 예를 들어 컨테이너를 작은 컴퓨터로 이해하고 시작해도 되지만, 실행 수명주기를 다룰 때는 독립된 작은 VM이 아니라는 정의로 바로잡아야 한다([[Docker-Core|Docker 기본]]).
- 기술 밖의 새 영역(브랜딩, 마케팅, 재무)에 들어갈 때도 같은 방식이 통한다.

## 어려운 개념을 분해하는 질문

이름이 어려워 보이는 개념의 상당수는 단순한 아이디어에 무거운 이름이 붙은 것이다. 정의를 외우기보다 다음 질문으로 개념을 쪼갠다. 순서는 고정이 아니며 막힌 지점에 맞는 질문을 고른다.

- **어떤 고통을 없애는가**: 정의는 무엇인지는 알려 주지만 왜 생겼는지는 알려 주지 않는다. 생성자 안에서 DB 연결을 직접 만드는 클래스를 단위 테스트해 보면 실제 DB와 자격 증명이 필요해진다. 연결을 생성자로 주입받으면 가짜 객체로 빠르게 테스트할 수 있고, 그제야 의존성 주입이 존재할 이유가 보인다.
- **가장 단순한 버전을 직접 만든다**: 배열 하나로 해시맵을 만들어 키를 숫자로 바꾸고 배열 길이로 나눈 나머지 칸에 저장한다. 두 키가 같은 칸에 떨어지는 충돌을 겪으면 체이닝과 리사이징이 왜 필요한지 이해된다.
- **비유를 깨질 때까지 밀어붙인다**: 이벤트 루프를 주문을 주방에 넘기고 다음 테이블로 가는 웨이터로 비유할 수 있다. 웨이터가 10분짜리 요리를 직접 하면 모든 테이블이 멈추는데, 이것이 Node.js 서버에서 무거운 JSON 파싱이나 동기 루프가 하는 일이다. 비유가 깨지는 지점이 실제 제약을 알려 준다.
- **실제 값으로 손으로 추적한다**: `factorial(3)`의 호출과 스택 되감기를 종이에 적거나, HTTP 요청 하나가 브라우저에서 서버까지 거치는 구간을 모두 적는다. 작은 입력을 손으로 돌릴 수 있으면 큰 입력도 두렵지 않다.
- **없으면 무엇이 깨지는가**: 0에서 시작한 카운터를 두 스레드가 동시에 증가시키면 둘 다 0을 읽고 1을 써서 오류 없이 결과가 1이 된다. 락은 두 번째 스레드를 기다리게 해 결과를 2로 만든다. 인덱스를 빼면 매 쿼리가 전체 테이블을 훑는다.
- **이름을 실제 장면으로 바꾼다**: 결제 요청이 타임아웃되어 앱이 재시도할 때 엔드포인트가 멱등하지 않으면 두 번 결제된다. 최종 일관성은 한 서버에 쓴 값을 다른 복제본이 잠시 뒤 따라잡는 사이에 읽으면 이전 값을 받는 현상이다.
- **소리 내어 설명하고 막힌 곳을 공부 목록으로 쓴다**: OAuth를 러버덕에게 설명하다가 토큰이 어디로 가고 누가 보관하는지에서 막히면 그 조각만 공부하고 다시 설명한다. 박스와 화살표로 그리거나 한 문장으로 줄여 봐도 같은 효과가 있다. 그림이 중간에 무너지는 곳이 빠진 조각이다.

이 질문들은 이해의 빈칸을 찾는 도구다. 빈칸을 메운 뒤에는 위의 순환 탐색과 아래의 회상 연습으로 명세 수준의 정의와 조건을 확인한다.

## 실전 팁

- **핵심 챕터 목차를 종이로** 뽑아 책상에 둠 — 순환 탐색의 지도
- 읽은 섹션은 **1문단 요약**을 메모 — 재탐색 시 빠르게 복귀
- 실행 동작은 코드 재현으로, 수학적 조건은 계산과 반례로 확인하는 등 학습 목표에 맞는 방법을 고른다
- 면접 대비 목적이면 **질문, 답변 형식**으로 변환해 기록
- 일주일 단위로 **본인 지식 트리** 갱신 — 공백, 누락 지점 파악

## 조직 관점

- 해당 과제를 잘 아는 동료에게 키워드와 선행 개념을 확인할 수 있다. 드레퓌스 단계가 코칭 자격은 아니다.
- [[Code-Review-Culture|코드 리뷰]]가 자연스러운 키워드 학습 계기
- **내부 위키, 스터디**는 순환 탐색의 앵커 역할
- 문제 탐색을 시작하기 어렵다면 상황과 키워드를 함께 제시할 수 있다. 선행 지식이 부족하면 기초 설명과 완성 예제도 제공한다

## 읽기, 회상과 적용을 연결한다

읽은 내용이 익숙하다는 느낌과 자료 없이 설명하거나 적용하는 능력은 구분한다. Roediger와 Karpicke(2006)의 글 회상 실험에서는 5분 뒤 평가에는 반복 읽기가 유리했고, 2일 또는 1주 뒤 평가에는 앞서 회상 시험을 본 조건의 기억 유지가 더 높았다. 따라서 회상 연습의 근거를 읽기는 무의미하다거나 모든 학습에서 항상 우월하다는 주장으로 바꾸지 않는다. 이 실험이 개발자의 실무 역량이나 면접 성과를 직접 검증한 것도 아니다.

IES 지침은 완성 풀이 읽기와 독립 문제 풀이의 교대, 시간 간격을 둔 학습과 회상 퀴즈를 함께 권한다. 처음 보는 개념에는 정확한 설명과 예제가 필요할 수 있다. 성장이 더디다는 이유만으로 학습 방법이나 의지 하나를 원인으로 단정하지 않고, 선행 지식, 과제 난도와 이해 확인 기회를 함께 살핀다.

다음은 이 근거를 CS 학습에 적용한 제안이며 사용자가 채택한 진도는 아니다.

1. 개념 설명과 정확한 예제를 읽고 필요한 가정을 확인한다.
2. 자료를 닫고 원리와 조건을 설명하거나 작은 문제를 푼다.
3. 원문, 계산이나 실행 결과와 대조해 틀린 부분을 고친다.
4. 간격을 두고 다시 회상하고, 조건을 바꾼 문제에서 적용 여부를 확인한다.

시험과 면접 모두 설계에 따라 기억, 설명과 적용을 평가할 수 있으며 한 번의 결과가 역량 전체를 정확히 나타내지는 않는다. 면접 준비에서는 내가 언제 써봤는지, 아직 쓰지 않았다면 어떤 조건에서 쓸 수 있는지, 없으면 어떤 문제가 생길지를 구분해 설명한다. 가상 적용을 실제 수행 경험으로 바꾸어 말하지 않는다.

### 한 번 맞힌 내용도 다시 회상한다

한 번 정답을 냈다는 이유만으로 이후 연습에서 빼지는 않는다. Karpicke와 Roediger(2008)의 대학생 외국어 단어쌍 실험에서는 처음 맞힌 항목도 계속 회상한 조건이 일주일 뒤 기억 유지에 유리했다. 처음 맞힌 뒤 읽기만 반복한 조건에서는 같은 이득을 관찰하지 못했다. 이미 회상한 단어쌍에 대한 결과이므로 처음 배우는 개념의 읽기나 설명까지 불필요하다는 뜻은 아니다.

복습 간격에도 모든 목표에 맞는 고정 정답은 없다. Cepeda 등(2008)의 사실 학습 실험에서는 평가까지 남은 시간이 길수록 가장 효과적인 학습 간격도 길어졌지만, 같은 평가 시점에서 간격을 계속 늘리면 성과가 다시 낮아졌다. 매일 같은 자료를 반복하거나 간격을 길게 벌리는 것 자체를 숙련의 기준으로 삼지 않는다.

CS 학습에 적용할 때는 한 번 통과한 설명이나 작은 문제도 후속 학습에서 간격을 두고 1~2회 다시 확인하고, 틀린 부분만 원문과 대조해 보강할 수 있다. 이 횟수는 운영 제안이며 두 실험이 검증한 최적 횟수가 아니다. 단어와 사실의 기억 유지 결과를 설계, 디버깅이나 면접 성과 전체의 보장으로 확대하지 않는다.

### 읽기 속도와 되읽기의 역할

Schotter, Tran과 Rayner(2014)의 실험에서는 시선이 지나간 단어를 가려 되읽을 수 없게 했을 때 이해도가 낮아졌다. 이 효과는 중의적인 문장에만 한정되지 않았다. 이는 되읽기가 이해에 기여할 수 있다는 근거이며, 느리게 읽을수록 항상 잘 이해한다거나 모든 속독 훈련이 실패한다는 증거는 아니다.

CS 문서를 읽을 때는 먼저 필요한 절을 찾고, 정의와 조건이 연결되지 않으면 앞 문장으로 돌아가 확인하는 방식으로 적용할 수 있다. 읽은 속도보다 자료를 닫은 뒤 조건과 반례를 설명할 수 있는지 확인한다. 이 절차는 연구를 연결한 학습 제안이며 특정 시험의 답안을 매일 읽는 방법의 효과를 검증한 결과는 아니다.

## 흔한 함정

- 책을 다 읽어야 **준비가 끝난다**는 강박
- 모든 참고서를 동시에 펼쳐두고 **진도 제로**
- 키워드 접근이라면서 **정답만 긁기** — 순환 탐색으로 이해 깊이를 만들지 않으면 지식이 얕음
- 기초 없이 **최신 기술 키워드**로 점프 → 용어 암기만 쌓이고 본질 이해 누락
- 동료에게 **완성된 답**을 기대 → 답보다 사고 과정을 물어야 남음

## 면접 체크포인트

- CS 교과서를 읽는 **본인의 루틴**을 설명할 수 있는가
- 모르는 개념을 만났을 때 **순환 탐색**이 몸에 있는가
- 완독 vs 키워드 접근의 **시간 대비 효용** 판단
- 선행 지식에 따라 설명, 완성 예제와 독립 풀이의 비중을 조절할 수 있는가
- 참고 도서가 폭증할 때의 **멈춤 신호**를 자각하는가
