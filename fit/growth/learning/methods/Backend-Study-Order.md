# 백엔드 공부 순서 (요청 흐름 먼저, 프레임워크는 도구)

백엔드 학습의 중심은 특정 프레임워크가 아니라 **HTTP 요청이 서버와 DB를 거쳐 응답으로 돌아오는 전체 흐름**이다. 프레임워크는 밑단의 네트워크와 DB 처리를 감춰 개발 속도를 높이는 도구일 뿐이므로, 흐름을 이해한 뒤에 배워야 도구의 가치가 보인다. 도구가 바뀌어도 유지되는 책임의 관점은 [[Backend-Developer-Career-Overview|백엔드 개발자 진로 개요]], 도구보다 근본에 무게를 두는 선택 기준은 [[Tech-Trend-Learning-Strategy|기술 변화와 학습 전략]]과 같은 축이다.

이 순서는 백엔드 요청 흐름이라는 축에서 전체 그림을 처음 쌓는 입문 경로다. CS 교과 전반(자료구조, 알고리즘, OS 등)의 기초를 순서대로 익히는 학습은 [[CS-Learning-Method|CS 지식 학습법]]이 다루는 별개 축이고, 이미 구체적인 목표가 있다면 순서는 그 목표에서 도출한다([[Purpose-Driven-Learning|목적 있는 학습]]). 기초가 잡힌 뒤 실무 문제를 풀 때는 완독 대신 문제에서 출발하는 키워드 학습을 쓸 수 있다.

## 프레임워크 먼저의 함정

프레임워크로는 기초 없이도 며칠 만에 동작하는 API를 만들 수 있다. 문제는 데이터가 쌓이고 에러가 터지기 시작할 때다 — 트랜잭션 추상화(TypeORM의 [[NestJS-Database|QueryRunner]], Spring의 `@Transactional`)가 실제 DB 커넥션과 어떻게 상호작용하는지 모르면 코드를 고치지 못하고, 도구가 내부에서 대신 처리해 주는 네트워크와 DB 동작 방식을 모르면 프레임워크가 뱉는 에러 메시지조차 읽기 어렵다. 기초가 학습곡선을 낮추는 원리는 [[CS-Fundamentals-Value|CS 기초의 가치]] 참고.

## 이론 먼저와 프로젝트 먼저 (학자형과 야생형)

반대 입장도 있다. 학습 스타일을 이론을 체계적으로 먼저 쌓는 학자형과, 실무나 토이 프로젝트를 먼저 하며 필요한 것을 그때 찾아 배우는 야생형으로 나누고, 취업 준비생과 주니어에게 야생형을 권하는 관점이다. 풀어야 할 문제를 모른 채 이론만 이어 가면 왜 배우는지 모르고, 이해도 어렵고, 무엇보다 중간에 포기하기 쉽다는 이유다. 겪어 본 문제가 이해를 만드는 원리는 [[Purpose-Driven-Learning#겪어 본 문제가 공감을 만든다 (늦게 배우는 이점)|목적 있는 학습]].

야생형에도 순서 구조가 있다. 활용 과정으로 전체 기술과 백엔드 서비스의 감을 먼저 잡고, 기본 원리 과정으로 내공을 쌓은 다음, 앞의 활용 과정을 다시 복습하고, 그 뒤에 성능 최적화와 API 개발 같은 심화, 반복 코드를 줄이는 생산성 도구로 넘어간다. 웹 애플리케이션 개발은 결국 웹과 DB 두 축을 배우는 일이라는 점은 아래 1, 2단계와 같다.

두 순서가 충돌하기만 하는 것은 아니다. 프레임워크 먼저의 함정은 활용 단계에서 멈출 때 생기고, 야생형은 활용 직후 원리 단계를 의도적으로 넣은 뒤 다시 활용으로 돌아와 확인하는 구조다. 어느 쪽으로 시작하든 만들어 본 경험과 밑단 원리를 잇는 두 번째 순회를 빠뜨리지 않는 것이 기준이다.

## 5단계 순서와 확인 방법

각 단계는 다음 단계의 전제다. 오른쪽 칸은 진도가 아니라 **스스로 설명하거나 재현해 보는** 확인 방법과 훈련이다.

| 단계 | 내용 | 확인 방법, 훈련 |
|---|---|---|
| 1. 네트워크와 HTTP | IP, TCP, HTTP 메소드, 헤더, 상태 코드 | URL 입력부터 응답까지의 과정을 글 10줄 이상으로 설명 |
| 2. RDB와 SQL | ORM보다 먼저 생 SQL로 JOIN, GROUP BY 작성 | 인덱스가 작동하는 원리를 100만 건의 가짜 데이터로 직접 실험 |
| 3. 프레임워크 | 의존성 주입(DI), 라우팅 | 기초를 먼저 겪은 뒤라야 프레임워크가 숨겨둔 DI와 라우팅의 가치가 체감된다 |
| 4. 예외 처리와 로깅 | 정상 코드보다 에러 추적 | 에러가 났을 때 어디서 터졌는지 추적할 수 있는 구조를 만드는 훈련 |
| 5. 동시성과 트랜잭션 | 동시성 문제와 트랜잭션 제어 | 수량 1개 상품에 동시 결제 2건이 들어오는 문제를 직접 해결 |

1, 2단계가 기초 흐름이고 프레임워크는 3단계에야 등장한다.

## 언어 수보다 데이터 모델

주니어 시기에는 언어를 여러 개 익히기보다 한두 언어를 충분히 쓰면서 데이터 관계(ERD)와 아키텍처를 이해하는 편이 오래 남는다. 데이터 모델과 구조 지식은 언어가 바뀌어도 그대로 쓰이고, 데이터는 사업이 이어지게 하는 핵심이기 때문이다. 대부분의 요구사항은 결국 데이터의 저장, 조회, 수정, 삭제, 집계로 환원된다. 현업이 기대하는 백오피스가 웹 화면의 필터, 정렬, 집계, 그래프, 보고서처럼 엑셀에서 하던 일인 것도 같은 이유이고, 이 요구는 곧 데이터 모델링과 집계 쿼리 역량이다.

- **먼저 쌓을 것**: ER 다이어그램 그리기, 업무를 분석해 엔티티 설계하기, 락과 캐싱 전략. 모델링 절차의 정본은 [[Data-Modeling-Workflow|데이터 모델링 절차]].
- **SQL**: 특정 DB의 방언보다 표준 SQL(ANSI SQL)로 먼저 익히면 DB를 바꿔도 다시 배울 부분이 줄어든다. 방언과 확장 기능은 쓰는 DB의 공식 문서로 확인한다.
- **ORM**: 애플리케이션에서는 ORM이나 타입 안전한 쿼리 빌더가 흔한 접근 계층이라 하나는 익혀야 생산성이 난다. 2단계에서 생 SQL로 JOIN과 GROUP BY를 먼저 짜 본 다음에 올려야 ORM이 만든 쿼리를 읽고 검증할 수 있다. 어떤 ORM을 쓸지는 프로젝트의 요구사항과 기존 구성으로 정한다.

## 수집이 아니라 제어 경험

기술 스택을 나열형으로 수집하는 공부는 남는 것이 적다. 남는 것은 기본 흐름을 직접 제어해 본 경험이다. 포트폴리오와 면접에서 보여야 하는 것도 스택 목록이 아니라 왜 그 순서로, 왜 그 도구를 도입했고 무엇이 달라졌는지의 서사다. 면접 서사 프레임은 [[Experience-Value-Framing|경험 가치 프레이밍]].

## 다음 층의 순서

5단계 뒤에도 같은 원칙이 이어진다. 아래 층이 약한 채 위의 도구를 쌓으면 도구 설정과 싸우느라 원리를 놓친다.

**DevOps로 넓힐 때**: 리눅스 핵심 원리, 네트워킹, Git을 먼저 익히고, 동작하는 MVP를 안전하게 반복 배포하는 자동화 루프(빌드, 배포, 롤백)를 만든다. 쿠버네티스 같은 오케스트레이션은 트래픽 확장과 장애 복구의 필요를 실제로 겪은 뒤에 도입해야 도구로서 의미가 생긴다. 오케스트레이션부터 배우면 YAML 설정에 시간을 쓰고 인프라 원리는 비어 있는 순서 오류가 된다. 1인 서비스에서도 먼저 필요한 것은 기본 배포 루프다. 개인 트랙의 실제 순서와 진행 판단은 [[2027-DevOps-Practical-Roadmap|2027 DevOps 실전 로드맵]]을 따른다.

**데이터 계층을 깊게 팔 때**: DB 지식은 다섯 층으로 쌓는 편이 학습 순서를 잡기 쉽다.

| 층 | 주제 | 이 층에서 답할 질문 |
|---|---|---|
| 1. 기초 | SQL과 NoSQL, ACID, 인덱스 | 이 쿼리는 어떤 인덱스를 왜 타는가 |
| 2. 읽기 확장 | Read Replica, 캐시, CDN | 복제 지연과 캐시 불일치를 어디까지 허용하는가 |
| 3. 쓰기 확장과 일관성 | 샤딩, CAP, 격리 수준 | 일관성을 어느 수준으로 선택하는가 |
| 4. 스토리지 내부 | WAL, B-Tree와 LSM, Bloom Filter | 쓰기와 읽기 비용이 어디서 생기는가 |
| 5. 분산 트랜잭션 | 2PC, Saga, Quorum | 여러 저장소에 걸친 변경을 어떻게 맞추는가 |

아래 층이 약한데 Redis, Kafka, MSA를 먼저 올리면 장애 원인을 설명하지 못한다. 층별 정본은 [[Isolation-Level|격리 수준]], [[Replication|복제]], [[Sharding|샤딩]], [[CAP-Theorem|CAP 정리]], [[B-Tree-Index-Depth|B-Tree 인덱스 깊이]], [[Distributed-Transaction-Strategies|분산 트랜잭션 전략]].

**시스템 디자인으로 넓힐 때**: 시스템 디자인은 정답이 정해진 문제가 아니라 상황에 맞는 구조를 고르는 일이라 실제 설계 경험이 가장 중요하다. 직접 설계할 기회는 드물어 간접 경험으로 보완하며, 방향은 넓이와 깊이 둘이다.

- **넓이**: 여러 사례에서 문제 해결 방식을 익힌다. 사례 방법론은 『가상 면접 사례로 배우는 대규모 시스템 설계 기초』 1, 2권, 아키텍처 스타일은 『소프트웨어 아키텍처 101』이나 『헤드 퍼스트 소프트웨어 아키텍처』, 분산 데이터 시스템은 『데이터 중심 애플리케이션 설계』가 출발점이 된다. 프로젝트에서 문제를 만나면 혼자 풀기 전에 기업 기술 블로그에서 키워드로 비슷한 사례를 먼저 찾는다. 모든 시스템을 구현할 수는 없으므로 무작위 요구사항으로 설계를 연습하는 아키텍처 카타나 시스템 디자인 면접 문제로 나라면 어떻게 설계할지 먼저 그리고 답과 비교해 고친다([[System-Design-Practice-Topics|시스템 설계 연습 주제]], 사례를 해부하는 방법은 [[Reverse-Engineering-Learning|역설계 학습]]).
- **깊이**: 도구가 실제로 어떻게 동작하는지 알아야 최적화해 쓸 수 있다. 배운 컴포넌트 중 궁금하거나 프로젝트에 쓰게 된 것은 공식 문서로 설정과 동작 방식을 끝까지 읽는다.

범용 백엔드 대기열에서 시스템 디자인을 언제 채택할지는 [[roadmaps|로드맵]]에서 정한다.

## 사례

- 한 멘토가 백엔드 멘티 200여 명을 만나며 가장 자주 본 패턴: Spring Boot나 Express로 3일 만에 게시판 API를 만들었지만, 4주 차에 데이터 10만 건이 쌓여 500 에러가 터지자 `@Transactional`이 실제 DB 커넥션과 어떻게 상호작용하는지 몰라 코드를 한 줄도 고치지 못했다.
- 반대편의 포트폴리오 서술 예: 1만 건의 조회 요청에서 DB 병목이 생겨 Redis 캐시를 도입했고 응답을 450ms에서 35ms로 줄였다.

## 체크포인트

- URL 입력부터 응답까지를 막힘없이 설명할 수 있는가
- ORM 없이 생 SQL로 JOIN, GROUP BY를 짤 수 있고 인덱스가 작동하는 원리를 실험해 봤는가
- 트랜잭션 추상화([[NestJS-Database|QueryRunner]], [[Spring-Transactional|@Transactional]])가 실제 DB 커넥션과 어떻게 맞물리는지 설명할 수 있는가
- 에러가 났을 때 어디서 터졌는지 추적할 수 있는 구조를 갖췄는가
- 사용 기술마다 도입 순서와 이유, 결과 수치를 말할 수 있는가
- 오케스트레이션 도구를 도입하기 전에 수동 배포와 자동 배포 루프의 한계를 직접 겪어 봤는가
