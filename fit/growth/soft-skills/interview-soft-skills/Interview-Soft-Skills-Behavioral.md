# 인성면접 가이드 — 행동양식 기반 면접(STAR)과 문제 해결 기법

## 행동양식 기반 면접 (STAR)

**과거의 행동이 미래의 행동을 예측하는 가장 좋은 지표**라는 가정에서 출발한다. 특정 상황에서 실제로 어떻게 대처했는지 묻고, 겪어 보지 못한 상황은 나라면 이렇게 하겠다를 끌어내는 가정형으로 묻는다.

- **묻는 상황**: 도전적인 목표 실행, 기술적 문제 대응, 요구사항 변경, 일정 지연, 리더십 발휘, 갈등, 실수
- **보는 것**: 커뮤니케이션, 상황 판단, 대처, 적응력, 사회성
- **대표 질문 유형**: 조직 적응력, 팀워크, 컬처핏, 문제를 원천 방지하려는 노력, 특정 상황에서의 대처

| 단계 | 내용 |
|------|------|
| **Situation (상황)** | 과거의 상황 설명 혹은 달성해야 할 목표 |
| **Task (과제)** | 수행해야 했던 업무 혹은 해결해야 할 과제 |
| **Action (행동)** | 실행으로 옮긴 행동 |
| **Result (결과)** | 행동의 결과, 결론 |

## STAR 답변 예시 — 비즈니스 임팩트까지

STAR는 경험 나열이 아니라 내 비즈니스 임팩트를 네 단계로 설명하는 틀이다.

- **S**: 이벤트 페이지 호출 시 트래픽 폭증이 예상됐다.
- **T**: 시스템 증설과 성능 튜닝을 병행하는 계획을 맡았다.
- **A**: 이벤트 페이지 호출을 비동기로 처리하고, 쿼리를 최적화하고, 애플리케이션 캐싱을 적용했다.
- **R**: 목표한 발송과 구매 건수를 달성했고 응답 속도를 개선하며 안정적으로 운영했다.

결과에 정량 지표(예: 응답 속도 20% 이상 개선, 목표 구매 건수 초과)를 붙이면 이상적이다. 수치에는 기준점과 측정 범위를 함께 둔다 ([[Resume-Experience-Narrative-and-Evidence#숫자는 맥락과 함께 쓴다|숫자는 맥락과 함께 쓴다]]).

## 문제 해결 기법을 답변 뼈대로 쓰기

생산과 품질 관리의 개선 기법, 일반적인 상황 기술 점검 목록을 인성면접과 기술면접 답변에 활용할 수 있다. 아래 항목 모두가 도요타 생산 방식에서 유래한 것은 아니다. 이름과 뜻을 구분해 쓴다.

| 기법 | 뜻 | 답변에 쓰는 법 |
|---|---|---|
| 카이젠(Kaizen) | 구성원 모두가 작은 개선을 매일 쌓아 전체 품질을 올리는 활동 | 성장과 개선 경험 질문 |
| 포카요케(Poka-yoke) | 부품 누락, 역방향 조립 같은 실수를 단순하고 값싼 장치로 막아 결함을 발생 지점에서 잡는 실수 방지 | 동료 실수를 막는 제도 질문 |
| 지도카(Jidoka)와 안돈 | 이상을 감지하면 작업을 즉시 멈추고, 알림판과 호출로 문제를 드러내 지원을 받는 원칙과 장치 | 장애 시 배포 중단과 공유 절차 |
| 5W1H | 누가, 무엇을, 언제, 어디서, 왜, 어떻게로 상황을 빠짐없이 기술하는 점검 목록 | 상황(S) 설명의 누락 점검 |
| 5 Whys | 왜를 반복해 드러난 증상 너머의 근본 원인을 찾는 기법 | 원인 분석 경험 질문 |

- **용어 교정**: 결함을 발견하면 공정을 멈추고 모두에게 공유해 근본 원인을 해결하는 제도를 포카요케로 설명하는 자료가 있는데, 이 설명은 지도카와 안돈에 가깝다. 포카요케는 실수가 일어나지 않게 막거나 즉시 드러나게 하는 장치 자체다. 마찬가지로 왜를 반복하는 근본 원인 분석은 5W1H가 아니라 5 Whys다([[RCA-Postmortem|RCA와 포스트모템]]).
- **장애 회고의 제도화**: 장애가 나면 경영진이 참여하는 논의 자리에서 기술 리더가 원인 분석과 해결책을 발표하게 한 대형 이커머스 사례가 있다. 포카요케의 예가 아니라 장애 회고와 재발 방지를 제도로 만든 예로 쓴다.
- **포카요케형 답변**: 실수의 경로를 막거나 즉시 드러내는 장치를 말한다. 소프트웨어에서는 테스트, 타입 검사 실패 시 병합을 자동 차단하거나 DB 제약으로 잘못된 상태를 거절하는 장치에 비유할 수 있다. 필수 코드 리뷰는 별도의 검사 절차이며, 결함 발견은 여전히 검토자의 판단에 의존한다.

### 카이젠형 답변 예시

운영 중인 서비스에서 아키텍처 수준의 변경은 위험이 크므로, API 병목 식별, 쿼리 튜닝, 캐싱 계층 도입처럼 작은 단위로 개선해 서버 자원 효율을 높이고 연동을 안정시켰다. 그렇게 확보한 여유로 아키텍처 개선에 착수했고, 점진적인 구조 개선이 서비스 확장에 효과적이었다는 결론으로 닫는다. 장애율 감소, 주문 실패 건 감소, 결제 전환율 상승 같은 지표를 붙이면 설득력이 커진다.

## 준비 방법

- 이 개념들을 본인 이력서의 경험 시나리오에 대입해 보고, 임팩트 있게 말하는 연습을 해 둔다. 인성면접뿐 아니라 기술면접에서도 쓴다.
- 질문 유형을 먼저 식별하고 행동형 답변 계약(실제 사건, 가치 충돌, 상호작용, 행동, 변화, 이후 원칙)에 맞춘다 ([[FIT-Framework|FIT 프레임워크]]의 질문 유형별 답변 계약).
- 질문 풀은 [[Common-Interview-Questions-Behavioral|자주하는 면접 질문 — Behavioral]].
