# 뛰어난 개발자의 행동 패턴

경력 많은 엔지니어들을 관찰하며 반복적으로 드러나는 7가지 행동 패턴. 주니어가 흔히 놓치는 지점과 개선 방향 포함. 성장 전반은 [[Developer-Hiring-Insights-Growth]] 참조.

## 1. 기본기에 충실

- 공식 문서 레퍼런스를 철저히 따름 (Stack Overflow 답변 복붙 금지)
- 가능한 **예외 케이스를 사전에 다룸** → 출처 사례에서는 서비스 개시일에 사소한 버그 외 장애가 없었음
- 라이브러리 기본값, 동작 원리를 확인 후 사용

**주니어의 함정**: "기술적 자부심으로 기본을 경시" → 화려한 패턴, 최신 프레임워크만 추구하고 기본 에러 처리, 테스트, 문서 확인 소홀

**개선 방향**: 거만함을 버리고 공식 문서 정독 + 예외 처리 꼼꼼히 수행

## 2. 주도적 역량 개발

- 업무 공백 시간을 **팀 발전 주제**에 투자 (공용 모듈, 도구, 문서)
- 학습 결과를 **팀에 전파** — 지식이 개인 자산에 머무르지 않음
- 미래 대비(기술 부채, 확장성)에 에너지 집중

**주니어의 함정**: 개인 공부나 기능 테스트로만 시간 소비. 팀 단위 레버리지 효과 부재

**개선 방향**: 남는 시간을 **팀 공동 주제**로 전환. 문서화, 테스트 헬퍼, 린터 룰 같은 공공재 기여

## 3. 빠른 코드 분석

- 장애 발생 시 **1시간 내 해결책 방향** 도출 — 평소 축적된 패턴 덕
- 오픈소스 코드를 **의도적으로 읽고** 분석
- **상향식**(세부 → 전체)과 **하향식**(전체 → 세부) 분석을 동시 진행
- 실패 가설을 **빠르게 버리고** 다른 가설로 전환

**주니어의 함정**: 자신이 써본 프레임워크, 코드 패턴에만 의존. 새 코드베이스 앞에서 무력

**개선 방향**: 주기적으로 다양한 오픈소스 코드 읽기 훈련. 특정 부분을 가져와서 내 프로젝트에 적용해보기

**에러 로그부터 읽는다**: 빨간 에러가 뜨면 스택 트레이스 첫 줄도 읽지 않고 검색창이나 AI로 직행하는 습관은 디버깅 실력을 제자리에 멈추게 한다. 에러 메시지는 질책이 아니라 문제의 시작 지점을 알려주는 안내서이고, 위치와 원인이 로그에 이미 적혀 있는 경우가 많다.

- 프레임워크 내부 예외의 긴 이름에 압도되지 말고, 수십 줄 로그에서 **내가 작성한 패키지와 파일명이 등장하는 지점**(내 코드와 프레임워크의 교차점)을 찾는다. 첫 줄만 긁어 검색하는 것은 전 세계의 비슷해 보이는 상황에서 답을 찾는 행동이고, 진짜 단서는 내 로컬 환경의 맥락에 있다
- 예외 이름이라는 결과에 집착하지 말고 그 값이 어디서부터 잘못 넘어왔는지 **역추적**한다
- 원인을 이해하지 못한 채 검색 결과나 AI의 코드를 복붙해 에러만 사라지게 하면 해결이 아니라 덮어둔 것이다
- **3분 로그 추적 습관**: 검색 전에 로그를 처음부터 끝까지 3분만 추적한다. 이 3분이 검색으로 날리는 몇 시간을 아낀다. 영어가 부담이면 메시지 전체를 번역기에 넣어 한국어로 읽는다
- AI가 대신 읽어주는 시대일수록 중요하다 — 로그의 맥락을 스스로 읽지 못하면 AI가 제시한 해결책도 검증할 수 없다 ([[CS-Fundamentals-Value|CS 기초의 가치]]의 판별 축). 에러가 뜨면 잠깐 손을 떼고 예외 이름, 파일명, 라인 번호부터 읽는다

**해결 뒤에 한 번 더 멈춘다**: 로그 읽기가 해결 전의 습관이라면 이것은 에러가 사라진 뒤의 습관이다. 해결 코드를 적용했으면 넘어가기 전에 에러가 왜 났는지, 실제로 어떤 값이 들어가 문제가 됐는지, 바꾼 옵션을 공식 문서가 어떻게 설명하는지까지 확인한다.

- 모든 에러를 이렇게 파면 일정이 감당되지 않는다. 하루 한 건처럼 끝까지 이해할 대상의 수를 정해 시간 비용을 통제한다
- 경험칙으로는 이렇게 쌓은 원인 이해 덕분에 같은 원인의 문제를 다시 만나면 바로 알아보고, 팀에서 이슈가 났을 때 해결책을 넘어 원인을 설명할 수 있다. 효과를 측정한 근거는 아니다

## 4. 논리적 증명 (엔지니어링 사고)

- 가설에 **논리적 빈틈**이 없는지 자가 점검
- 로그, 재현, 다이어그램으로 주장을 뒷받침
- 시퀀스 다이어그램, 상태 다이어그램으로 시각화해 동료와 공유
- 제안 방법의 **다른 영역 영향** 사전 점검

**주니어의 함정**: "이것 같은데", "아마"라는 직관만으로 여러 가설 제시. 근거 없이 리더를 설득하려 함

**개선 방향**: 근거(로그, 재현 스크린샷, 코드 스니펫, 다이어그램)로 주장 뒷받침. "저는 X라고 생각하는데, 이유는 Y 로그에서 Z를 관측했기 때문" 형태의 주장

> 엔지니어는 **증명**을 해야 한다. 가정, 가설만으로는 부족하며 로그, 재현, 시각화로 입증.

**해결책을 두 가지 이상 놓고 고른다**: 제일 먼저 떠오른 방법으로 구현하고 테스트 통과에서 멈추면 동작하는 코드는 남아도 선택의 이유는 남지 않는다. AI가 동작하는 코드를 빠르게 만들어 줄수록 남는 질문은 왜 이 방식인가다.

- 기능을 구현할 때 가능하면 A안과 B안을 나란히 적고 장단점을 비교한다. 예를 들어 A안은 구현이 빠르고 단순하지만 확장이 어렵고, B안은 구현이 복잡하지만 요구 변화에 유연하다
- 고른 뒤에는 지금 상황에서 이 방식을 택한 이유를 논리적으로 설명할 수 있는지 스스로 묻는다. 코드 리뷰나 면접에서 왜 이렇게 설계했는지 물을 때 상황에 따른 근거로 답하는 연습이 된다
- 비교의 깊이는 되돌리기 비용에 맞춘다. 가역적인 작은 결정은 몇 줄 비교로 끝내고, 영향이 큰 설계 결정은 [[Tech-Decision#Design It Twice|기술 의사결정의 Design It Twice]] 절차로 비교한다

## 5. 책을 실전과 연결

- 기술서를 정독 후 **실제 경험 중인 문제와 연결**
- 예: False Sharing, Cache Line, TCP 혼잡 제어 같은 교과서 개념을 **며칠 뒤 프로젝트에서 즉시 인지, 해결**
- 책 속 개념을 "언젠가 쓸 지식"이 아니라 "지금 내 문제의 렌즈"로

**주니어의 함정**: 책을 흘려 읽고 실무와 연결 못함. "이 책 봤는데 도움 안 돼"로 결론

**개선 방향**: 책 읽을 때 **내 현재 문제, 코드와 대조**하며 읽기. 읽는 중 떠오른 적용처를 메모해 뒀다가 즉시 실험

**권수보다 소화 깊이**: 기준은 몇 권을 읽었는가가 아니라 한 권을 어디까지 소화했는가다. 월 한 권처럼 주기를 정하더라도 진도보다 아래 방식으로 소화했는지를 본다.

- 예제가 나오면 직접 입력해 실행해 본다
- 이해되지 않는 부분은 표시해 두고, 나중에 돌아와 이해될 때까지 다시 확인한다
- 질문 단위로 받은 AI 답변은 질문한 범위의 조각에 머물기 쉽다. 경험칙으로는 한 권을 끝까지 소화하면 흩어져 있던 개념이 서로 연결되어 판단의 기준점이 되고, AI가 짠 코드를 볼 때도 왜 이 패턴을 썼는지 구조로 읽을 수 있다
- 모든 책을 처음부터 끝까지 읽으라는 뜻은 아니다. 당장의 문제 해결과 기초 체계 학습에서 읽을 범위를 나누는 기준은 [[CS-Learning-Method|CS 학습법]]을 따른다

## 6. 프로덕트 중심 마인드

- 기술 집착 ≠ 성과. **효율적 솔루션으로 가치 전달** 이 우선
- 여가 시간의 **Dev Toy**(개인 프로젝트)로 새 기술, 원리 이해, 포트폴리오를 동시 구축
- **문제 해결 범위를 넓게** — 기획, 설계, 운영까지 포함
- 장애 해결을 "개발을 방해하는 요소"가 아닌 **성장 기회**로

**주니어의 함정**: 기술 완벽주의로 일정 지연. 프로덕트와 코드를 분리된 영역으로 봄

**개선 방향**: "이 기술이 제품에 어떤 가치를 주는가"를 먼저 질문. Dev Toy는 실제 사용 가능한 형태까지 완성

## 7. 깊이 있는 학습

- "**가져다 쓰면서도, 이해하고 쓰기**"
- 프레임워크/패키지를 쓰더라도 원리를 이해해야 이슈 발생 시 **독립 해결** 가능
- 인접 분야 기초 이해 (백엔드가 프런트 일부 이해, 역도 동일) → **더 나은 기술 결정**
- 블랙박스 도구를 줄이고 **내부 모델**을 가질 것

**주니어의 함정**: "쓸 줄만 알면 되지"로 끝남. 해당 도구의 이슈 발생 시 문제 해결 능력 부재

**개선 방향**: 자주 쓰는 라이브러리 1~2개는 **소스 레벨**까지 들여다보기. 장애 시 내부 이해가 결정적

## 종합 — 주니어가 시니어로 가는 공통 지표

위 7가지 패턴의 공통점은 **현재의 나에 머무르지 않는 자세**.

- 기본기 충실 → **현재의 완성도**
- 주도적 역량 개발 → **팀 단위 임팩트**
- 빠른 코드 분석 → **학습 속도**
- 논리적 증명 → **의사결정 품질**
- 책을 실전과 연결 → **지식의 활용**
- 프로덕트 중심 → **가치 전달**
- 깊이 있는 학습 → **자립성**

이 7가지를 **매 스프린트 하나씩** 점검해보는 것이 실질적인 성장 루틴.

## 면접 활용

아래 답변은 예시 템플릿이며, 답변 속 경험은 사용자의 기록으로 확인되지 않았다(미확인). 실제 면접에서는 [[My-FIT-Answers|내 FIT 답변 마스터]]의 확인된 사례로 바꿔 쓴다.

### "어떻게 성장하고 있으신가요?"

> "세 가지 습관을 계속 다듬고 있습니다. 첫째, **기본기와 예외 처리** 를 공식 문서에서 재확인하는 것. 둘째, **오픈소스 코드를 주기적으로 읽고 분석** 하는 것. 셋째, **제 가설을 반드시 로그, 재현, 다이어그램** 으로 증명한 뒤 제안하는 것. 이 세 가지가 문제 해결 속도와 의사결정 품질에 가장 큰 영향을 줬습니다."

### "뛰어난 동료에게서 무엇을 배우셨나요?"

> "특히 **논리적 증명 습관**이 인상 깊었습니다. 같은 이슈를 봤을 때 주니어였던 저는 '이것 같은데요'로 말했는데, 그 동료는 로그 발췌, 재현 시나리오, 시퀀스 다이어그램까지 준비해서 근거로 제안했습니다. 그 이후로 저도 주장할 때는 근거를 먼저 준비하는 방식으로 바꿨습니다."
