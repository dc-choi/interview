# 라이브데이터 1차, JD 기반 기술 질문

> [[Interview-Prep-LaivData-1st|메인 문서]]의 하위 문서다. 공고의 업무와 자격 요건에서 나올 질문을 사실형과 설계형으로 나눴다. LLM Agent 제품 구현 경험은 없으므로 모든 답변은 경험한 범위와 학습한 범위를 먼저 구분하고 시작한다.
> 회사의 실제 구현은 모른다. 공식 사이트가 설명한 모듈 역할만 전제로 쓰고, 내부 구조를 아는 것처럼 말하지 않는다.

## J1. 어떤 구간에 Multi-Agent가 필요하고, 마스터와 서브 Agent의 역할은 어떻게 나누나요 (설계형)

- **의도**: 공고의 Multi-Agent 구간 식별과 R&R 정의, 산출물(Agent Flowchart, 상태와 이벤트 정의).
- **답변 골격**:
  1. 먼저 멀티로 나눌 이유가 있는지 묻는다. 절차가 확정되고 감사가 필요한 흐름은 단일 체인이 더 싸고 예측 가능하다. 탐색적이고 단계마다 판단이 필요할 때 에이전트를 쓴다.
  2. 나누는 기준은 컨텍스트, 권한, 실패 범위다. 한 에이전트에 모든 규칙과 도구를 주면 컨텍스트가 커지고 권한이 비대해지며 실패가 전체로 번진다.
  3. 마스터는 의도 정리, 라우팅, 정보가 부족할 때 재확인, 결과 조립을 맡는다. 서브는 도메인별 도구와 규칙만 갖고 자기 결과를 계약된 형식으로 돌려준다.
  4. 산출물로는 상태 전이표(대기, 실행, 사용자 확인 대기, 완료, 실패), 에이전트 간 입출력 계약, 예외별 정책(재시도, 사람에게 넘김, 거부)을 남긴다.
- **판단 기준**: 업무의 예측 가능성, 되돌릴 수 없는 행동의 유무, 도구 권한의 범위, 비용과 지연 예산.
- **대안과 트레이드오프**: 단일 에이전트는 단순하지만 규칙이 늘수록 불안정해진다. 멀티는 격리와 재사용이 좋지만 조율 비용, 호출 수와 지연, 디버깅 난도가 늘어난다. Plan-and-Execute처럼 계획을 데이터로 꺼내 두면 검토와 승인이 쉬워진다.
- **내 경험 연결**: 모듈 경계를 도메인과 사용자 의도로 나눈 경험(R1), 상태 전이 검증으로 중복을 처리한 경험(R3)을 근거로 든다.
- **꼬리**: 서브 Agent가 서로 호출하게 둘 것인가? 원칙적으로 마스터를 거치게 해 흐름을 추적 가능하게 한다. 세션과 히스토리는 어디에 두나? 대화 이력처럼 문서 단위로 읽고 쓰는 데이터는 NoSQL이 맞을 수 있고, 권한과 과금처럼 정합성이 중요한 데이터는 RDB에 둔다. 선택은 접근 패턴으로 한다.

## J2. 환각, 오답, 도구 실패, 권한 오류를 어떻게 분류하고 대응하나요 (설계형)

- **의도**: 공고의 실패 유형 분류와 대응 정책. 가장 강하게 연결할 수 있는 질문.
- **답변 골격**: 원인 위치와 복구 가능성으로 나눈다.

| 유형 | 탐지 | 대응 |
|---|---|---|
| 도구 실패(일시) | 타임아웃, 5xx, 408, 429(속도 제한) | 제한 재시도와 백오프(429는 Retry-After 헤더가 있으면 따름), 재시도 예산 초과 시 대체 경로나 사용자 안내 |
| 도구 실패(영구) | 스키마 불일치, 408과 429를 뺀 4xx(400, 404, 422 등) | 재시도하지 않고 격리, 로그와 경보, 도구 정의 수정 |
| 권한 오류 | 401, 403 같은 인가 거부, 범위 밖 요청 | 권한은 모델이 아니라 도구 서버와 다운스트림에서 강제. 모델에는 거부 사실만 돌려주고 우회 시도를 막는다 |
| 오답 | 골든셋과 규칙 검증, 구조화 조회 결과와 대조 | 정답이 원장에 있는 질문은 검색 대신 API 조회로 라우팅 |
| 환각(근거 없는 주장) | 인용이 실제 근거를 가리키는지 검사, 별도 판정 | 근거가 없으면 답을 거부하거나 사람에게 넘긴다. 모른다는 응답을 정상 응답으로 설계 |

- **판단 기준**: 틀렸을 때의 비용. 금융처럼 오류 비용이 큰 흐름은 정확도 우선과 강한 검증, 단순 안내는 사용자 경험 우선으로 분기한다.
- **대안과 트레이드오프**: 실패마다 모델에 재시도를 맡기는 방식은 구현이 쉽지만 비용과 지연이 늘고 같은 실패를 반복한다. 코드 레벨 분류와 재시도 예산은 예측 가능하지만 분류표를 계속 관리해야 한다. 판정을 강하게 할수록(인용 검사, 별도 판정 모델) 정확도는 오르지만 호출 수와 지연이 늘고, 거부율이 올라 사용자 경험이 나빠질 수 있다. 공개된 일반 기준 수치는 없으므로 허용 거부율과 판정 비용은 도메인별로 정한다(확인 필요).
- **내 경험 연결**: 외부 연동에서 영구 오류와 일시 오류를 나누고 DLQ와 수동 확인으로 보낸 설계(R3)와 같은 사고라고 연결한다.
- **흔한 오답**: 4xx는 전부 재시도하지 않는다고 단정하는 것(408, 429는 재시도 대상). 프롬프트에 하지 말라고 적는 것으로 권한 문제를 해결했다고 말하는 것. 시스템 프롬프트는 보안 경계가 아니다.
- **꼬리**: 가장 위험한 실패는? 모르는 영역에서 자신 있게 틀리는 것. 조용히 틀리므로 탐지 장치가 따로 필요하다.
- **출처와 정본**: OWASP LLM Top 10(2025)의 과도한 위임, 시스템 프롬프트 유출 항목. vault 정본 `LLM-Application-Security`, `LLM-Abstention`.

## J3. eval과 judge 기준, 루브릭은 어떻게 만들고 배포에 어떻게 연결하나요 (설계형)

- **의도**: 공고의 Agent 품질 시나리오와 루브릭 초안, 지표 기반 의사결정. 공식 사이트의 Veris 설명(시나리오 기반 테스트셋, LLM-as-a-Judge 루브릭 채점)과 맞닿는다.
- **답변 골격**:
  1. 좋은 답의 정의부터 도메인 전문가와 정한다. 정의가 곧 평가 기준이다.
  2. 대표 시나리오로 고정 테스트셋을 만든다. 실제 사용자 흐름과 실패했던 사례를 계속 추가한다.
  3. 채점은 가능하면 코드(형식, 필수 필드, 도구 호출 순서), 필요하면 모델(뉘앙스, 관련성), 애매한 것과 새 유형만 사람이 본다. 이 순서가 비용 구조다.
  4. 안전과 권한 위반처럼 한 건도 허용하지 않는 항목은 총점과 무관하게 거부권을 준다.
  5. 프롬프트, 모델, 도구 버전을 바꿀 때마다 같은 셋으로 돌려 기준선과 비교하고, 통과한 조합만 제한된 사용자에게 먼저 낸다.
- **판단 기준**: 코드로 판정할 수 있는가(형식, 필수 필드, 도구 호출 순서), 틀렸을 때의 비용(거부권 항목 여부), 판정 비용과 속도, 사람 판정과의 일치도.
- **대안과 트레이드오프**: 비교 축은 아래와 같다. 공개된 일반 수치가 없으므로 비용과 일치도는 팀 데이터로 확인할 항목이다(확인 필요).

| 축 | 코드 검사 | LLM-as-Judge | 사람 채점 |
|---|---|---|---|
| 비용과 속도 | 가장 낮고 빠름 | 중간 | 가장 높고 느림 |
| 재현성 | 결정론 | 흔들림, 편향 가능 | 평가자 간 편차 |
| 적합 | 형식, 규칙, 순서 | 뉘앙스, 관련성 | 애매한 사례, 새 유형 |
| 관리 | 규칙 유지 | 사람 판정과 주기적 보정 | 소량 표본만 가능 |
- **꼬리**: 점수가 갑자기 떨어지면? 에이전트보다 채점기와 문항부터 의심한다. 한 번에 맞히는 비율과 여러 후보 중 하나가 맞는 비율은 다른 지표다. 사용자가 한 답만 받으면 한 번에 맞히는 비율이 기준선이다.
- **내 경험 연결**: 팀 AI 회귀 루프(R8)에서 작업 종료 시점에 테스트와 변경 파일 검사로 AI가 스스로 품질을 확인하게 한 경험. 종료 차단 방식은 [사용자 확인 필요]. 단, Agent 제품 eval 운영 경험은 없다고 밝힌다.
- **내 경험 연결 (개인 프로젝트)**: 개인 프로젝트에서 74개 평가 질문으로 검색 방식을 비교하고, 리랭커는 94개 질문으로 따로 비교해 둘 다 측정으로 기각한 경험(R9). 질문은 대부분 합성이고 이력서의 145건 문구는 정정 대상이다. 회사 업무가 아니라 개인 프로젝트라고 먼저 밝힌다.
- **단순화 조건**: 합격선과 허용 실패율은 도메인마다 다시 정한다. 특정 숫자를 일반 기준처럼 말하지 않는다.

## J4. LangGraph 같은 상태 기반 워크플로우에서 중단과 재개는 어떻게 동작하나요 (사실형)

- **의도**: 공식 사이트가 LangGraph 기반을 표방하고 LangBridge를 오케스트레이션과 서빙 서버로 소개한다. 사용 경험이 없으므로 공식 문서로 확인한 동작만 답한다.
- **핵심 답변**: 체크포인터와 함께 컴파일하면 그래프 상태가 thread 단위로 저장된다. 노드 안에서 `interrupt()`를 호출하면 실행이 멈추고 상태가 저장되며, 같은 thread ID로 `Command(resume=...)`를 보내 재개한다. 재개하면 멈춘 줄이 아니라 해당 노드의 처음부터 다시 실행된다. 따라서 interrupt 앞의 부수효과(DB insert, 외부 호출)는 두 번 실행될 수 있어 멱등해야 한다. 운영에서는 메모리가 아닌 DB 기반의 영속 체크포인터를 써야 한다.
- **흔한 오답**: 멈춘 지점부터 이어서 실행된다고 답하는 것. 사람 승인 전 결제나 메일 발송을 해 두는 설계도 위험하다.
- **내 경험 연결**: 큐 소비자가 재전달을 정상 경로로 보고 멱등성 키와 상태 전이 검증을 둔 설계(R3)와 같은 원리다.
- **꼬리**: 되돌릴 수 없는 행동 직전 사람 승인은 어디에 두나? 부수효과를 승인 뒤 별도 노드로 분리한다. 한 노드 안의 interrupt 순서를 조건에 따라 바꾸면 재개 값이 인덱스로 매칭돼 어긋난다.
- **출처**: LangGraph 공식 문서 Interrupts, Graph API의 재실행과 멱등성 절 (2026-09-29 확인).

## J5. 문서를 에이전트가 쓰기 좋게 구조화하고 검색 품질을 평가하려면 (설계형)

- **의도**: 공식 사이트의 DataMart 설명(청크 분할, 검색 로직 설계)과 RDB, NoSQL 설계 업무.
- **답변 골격**: 품질을 검색, 컨텍스트 구성, 생성, 근거 충실성으로 나눠 어느 층에서 실패했는지 본다. 청킹은 고정 길이보다 제목과 섹션 같은 구조 기반이 표와 논리 단위를 덜 깨뜨리고, 어떤 방식이든 문서 ID, 청크 ID, 원문 위치, 버전을 보존해 답의 근거로 돌아갈 수 있게 한다. 벡터 검색은 의미에 강하지만 주문번호 같은 정확 식별자에 약해 키워드 검색과 병행해 비교한다. 정답이 구조화 시스템에 있는 질문은 검색하지 않고 조회로 라우팅한다.
- **판단 기준**: 정답이 구조화 시스템에 있는가(조회로 라우팅), 질의에 정확 식별자가 섞이는가(키워드 병행), 문서 구조가 명확한가(구조 기반 청킹), 대표 질문셋의 재현율 대비 토큰 비용.
- **대안과 트레이드오프**: 청크 크기와 겹침은 정답이 없는 변수라 대표 질문셋에서 재현율과 토큰 비용을 함께 비교한다. 계층 검색은 상위 단계가 틀리면 하위 근거를 통째로 놓친다.
- **꼬리**: 멀티 고객이 같은 벡터 저장소를 쓰면? 고객 간 교차 유출을 막는 접근 제어를 검색 단계에서 강제한다.
- **내 경험 연결**: 실행 계획으로 인덱스가 실제로 쓰이는지 검증한 습관(R4)처럼, 검색도 설정 이름이 아니라 측정으로 고른다. 검색 시스템 실무는 없다고 밝힌다. 개인 프로젝트에서 근거 그래프 기반 검색을 만들고 방식을 정량 비교한 경험(R9)은 개인 프로젝트로 밝히고 쓴다.

## J6. FastAPI를 써 본 적이 없는데 어떻게 적응하나요 (사실형과 학습 계획)

- **의도**: JD의 NestJS/FastAPI 기반 백엔드 개발. 경험 없는 스택에서 동시성 모델을 원리로 이해하는지, 학습 계획이 검증 가능한지 본다.
- **핵심 답변**: FastAPI는 `async def` 경로 함수를 이벤트 루프에서 실행하고, 일반 `def`로 선언한 경로 함수는 외부 스레드 풀에서 실행한다. 이 스레드 풀은 AnyIO 작업자 스레드 제한을 따르며 기본 한도는 40이다(AnyIO 공식 문서, 2026-09-29 확인). 동기 경로가 느린 I/O로 40개 스레드를 모두 점유하면 나머지 `def` 요청은 대기한다. 그래서 `async def` 안에서 블로킹 I/O를 호출하면 이벤트 루프 전체가 막힌다. 이는 Node.js에서 이벤트 루프를 막지 않도록 동기 작업을 피한 원리와 같다. 입력 검증은 Pydantic 모델로 선언해 NestJS의 DTO와 파이프가 하던 역할을 맡긴다.
- **흔한 오답**: 모든 경로를 `async def`로 바꾸면 빨라진다고 말하는 것.
- **꼬리**: `async def` 안의 블로킹 호출을 어떻게 찾나? 이벤트 루프 지연을 관측하거나 asyncio 디버그 모드의 느린 콜백 경고로 찾고, 코드 리뷰에서 동기 드라이버와 SDK 호출을 확인한다. 대안은 비동기 드라이버로 교체, `run_in_threadpool`로 감싸기, 경로를 `def`로 전환하는 것이다. 스레드 풀 한도를 올리면 대기는 줄지만 메모리와 DB 연결 수가 함께 늘어 연결 예산과 맞춰야 한다.
- **학습 계획**: 공식 튜토리얼로 경로, 의존성 주입, 검증을 익히고, 기존 NestJS API 하나를 같은 계약으로 옮겨 테스트를 통과시키는 작은 과제로 검증한다. 팀의 서비스 경계(어떤 서비스가 Python인지)는 역질문으로 확인한다.
- **출처**: FastAPI 공식 문서 Concurrency and async/await.

## J7. 프론트엔드(React) 개발은 어느 수준까지 가능한가요 (경험형, 갭)

- **의도**: JD의 React 기반 프론트엔드 개발과 원티드 skill_tags(React, Next.js). 갭을 숨기지 않는지, 첫 기여 범위를 현실적으로 제시하는지 본다.
- **답변**: React 실무 경험은 없다고 먼저 말한다. 백엔드에서 OpenAPI로 요청, 응답, 실패 조건을 계약으로 맞춰 온 경험이 있고, 서버 상태와 화면 상태를 구분하는 기본 개념은 학습했다. 합류하면 기존 화면의 작은 수정부터 맡아 API 계약과 로딩, 에러 상태 처리를 함께 책임지고 싶다.
- **주의**: 학습한 개념을 실무 숙련으로 말하지 않는다. 풀스택 중 프론트엔드 비중과 첫 과제는 역질문으로 확인한다.
- **꼬리**: 서버 상태와 화면 상태를 왜 나누나? 서버 상태는 캐시, 재검증, 동시 수정 충돌이 있고 화면 상태는 입력과 표시만 다뤄 관리 방식이 다르다. 에이전트 응답을 스트리밍으로 보여 준다면? 서버는 부분 결과와 종료, 오류 이벤트를 계약으로 정하고, 화면은 중간 실패 시 이미 받은 내용을 어떻게 표시할지 정해야 한다(학습 범위이며 실무 경험 아님).

## J8. Kubernetes 배포와 운영 경험이 있나요 (사실형, 갭)

- **의도**: 우대 사항의 Kubernetes/Docker 배포와 운영. 경험 없음을 인정하면서 대응 개념을 정확히 아는지, 공식 사이트가 밝힌 구축형 제공과 연결되는 판단 기준을 갖췄는지 본다.
- **답변**: 직접 운영 경험은 없고 Docker와 ECS Fargate로 배포 경로를 설계했다. 대응 개념으로 설명한다. Pod는 함께 실행돼야 하는 컨테이너의 공동 실행 단위이고 일시적이다. 운영 워크로드는 Deployment 같은 컨트롤러가 소유하게 한다. Kubernetes는 모든 replica가 새 버전으로 갱신되고 available(readiness와 `minReadySeconds` 기준)이며 이전 replica가 남지 않았을 때 Deployment를 complete로 표시하고, `progressDeadlineSeconds`(기본 600초) 안에 진행하지 못하면 `ProgressDeadlineExceeded`로 표시한다. 운영 판정은 이와 별개로 에러율, 지연 같은 서비스 SLO로 한다. RollingUpdate의 `maxSurge`와 `maxUnavailable`은 기본 각각 25%이며, 여유 용량과 롤아웃 속도의 교환이다. `rollout undo`는 DB 마이그레이션이나 외부 의존성까지 되돌리지 않는다. Service는 바뀌는 Pod 앞의 안정된 발견 계약이다.
- **판단 기준**: 여러 워크로드(API, 배치, 모델 서빙)를 한 플랫폼에서 운영하거나 고객사 온프레미스 설치가 필요하면 Kubernetes의 이점이 커진다. 그렇지 않으면 관리형 컨테이너가 운영 부담이 낮을 수 있다.
- **흔한 오답**: Pod가 Running이면 롤아웃이 끝났다고 보는 것. Running은 컨테이너가 떴다는 뜻일 뿐 readiness 통과나 서비스 정상과 다르다. `rollout undo`로 DB 스키마까지 되돌아간다고 말하는 것도 틀리다.
- **꼬리**: 고객사 환경에 설치형으로 납품한 경험은? 시솔지주에서 고객사 On-Premise 구축을 위해 AWS 기반 서비스를 이전한 경험이 있다(이력서 항목). Kubernetes는 아니었다고 구분한다. 공식 사이트가 SaaS와 구축형을 모두 제공한다고 밝히므로, 구축형 고객 환경에서 관리형 서비스 의존(큐, 스토리지, 모니터링)을 무엇으로 대체하는지가 이 경험과 가장 가까운 질문이다. 실제 구축형 배포 방식은 역질문으로 확인한다.
- **출처**: Kubernetes 공식 문서 Pods, Deployments, Service.
