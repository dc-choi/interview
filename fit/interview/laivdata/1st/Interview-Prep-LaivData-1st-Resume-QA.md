# 라이브데이터 1차, 이력서 기반 기술 질문

> [[Interview-Prep-LaivData-1st|메인 문서]]의 하위 문서다. `My-Tech-Cards` 마스터를 fork했다. 수치는 공개 이력서에 적힌 값만 쓰고, 측정 조건(기간, 비교 기준, 측정 방법, 본인 기여)을 설명할 수 있을 때만 말한다. 내부 운영 수치와 임계값은 말하지 않는다.
> 각 카드 끝의 **회사 연결**은 공개 JD 문구에만 근거한다.

## R1. PoC를 위한 모듈 중심 아키텍처는 어떻게 설계했나요 (경험형)

- **의도**: 공고의 PoC에서 본계약과 운영 고도화, 플랫폼 공통 역량 추상화와 가장 가까운 경험. 경계를 무엇으로 나눴고 무엇을 포기했는지 본다.
- **답변 (카드 7 fork)**:

> 대형 고객사 PoC 요구가 자주 바뀌는 상황이라, 기능을 한 서비스 계층에 계속 덧붙이면 변경 영향이 다른 흐름까지 퍼질 수 있다고 봤습니다. 그래서 도메인별 모듈로 나누고 Controller, UseCase, Domain, Repository port, 인프라 구현을 분리했습니다. 같은 도메인이어도 API 응답과 파일 내보내기처럼 사용자 의도가 다른 경로는 UseCase를 나눠 입출력 요구가 도메인 규칙에 스며들지 않게 했습니다. 다만 계층을 늘리는 것 자체가 목표는 아니어서, 실제로 교체되거나 독립적으로 바뀌는 경계에만 추상화를 뒀습니다.

- **사실 경계**: 실제로 어떤 흐름이 흔들렸는지 묻는 꼬리에는 [사용자 확인 필요: 분리 전 겪은 구체 사례]가 확정된 경우에만 답한다. 확정 전에는 이력서 표현(잦은 요구사항 변경을 유연하게 수용)과 위 조건형 판단으로만 말한다.
- **검증**: 도메인 규칙이 프레임워크 없이 테스트되는지, 인프라 변경이 호출자 전체로 퍼지지 않는지로 경계의 효과를 봤다.
- **꼬리**: `forwardRef()`가 반복되면 모듈 책임이나 의존 방향을 다시 나눠야 한다는 신호다. 고객별 요구는 설정, 전략 객체, 별도 모듈 중 무엇으로 흡수하나? 변경 빈도와 고객 간 공통성으로 고른다.
- **회사 연결**: 고객 프로젝트의 요구를 플랫폼 공통 역량으로 추상화하는 업무에서, 고객별 차이와 공통 규칙의 경계를 먼저 정하는 방식으로 기여할 수 있다.

## R2. 수천 대 기기의 동시 요청에서 재고 정합성을 어떻게 지켰나요 (경험형)

- **답변 (카드 1 fork)**:

> 같은 재고 상태를 여러 IoT 입력이 동시에 바꾸는 경로였습니다. 충돌이 잦은 갱신은 낙관적 잠금으로 늦게 충돌을 발견하면 작업 전체를 다시 해야 해서, `SELECT ... FOR UPDATE NOWAIT`와 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했습니다. 입력 검증과 외부 호출은 트랜잭션 밖에서 끝내고, 잠금 읽기 뒤 불변식을 다시 검증했습니다. 여러 대상을 함께 갱신할 때는 업무 키 순서를 통일했습니다. 동시 요청을 재현해 최종 수량과 재시도 뒤 상태를 확인했습니다.

- **비교 표 (Extended 카드 1 fork)**:

| 기준 | 낙관적 잠금 | 비관적 잠금 |
|---|---|---|
| 충돌 빈도 | 낮을 때 유리(읽기 많은 서비스) | 높을 때 유리(쓰기 경합 많은 서비스) |
| 충돌 시 비용 | 트랜잭션 전체 재실행 | 잠금 대기(NOWAIT면 즉시 실패 후 재시도) |
| 잠금 보유 시간 | 선점 없음(쓰기 시점 검증, 조건부 UPDATE의 X 잠금은 커밋까지) | 트랜잭션 동안 보유 |
| 데드락 위험 | 낮음(여러 행과 자원이 얽히면 가능) | 있음(업무 키 순서 통일로 완화) |
| 구현 | version 컬럼 | `SELECT ... FOR UPDATE` |

- **흔한 오답**: `NOWAIT`가 모든 대기를 없앤다고 말하는 것. 해당 잠금 읽기의 대기만 없애고 메타데이터 잠금 등은 남는다.
- **꼬리**: 멀티 인스턴스에서도 DB 잠금이면 충분한가? 같은 DB를 보호하는 한 충분하고, 여러 저장소나 외부 시스템을 한 임계 구역으로 묶을 때만 분산 잠금을 검토한다. 지금 다시 한다면 고정 간격 대신 지수 백오프와 지터를 검증한다.
- **회사 연결**: 여러 에이전트가 같은 세션 상태나 작업 결과를 갱신하는 구간도 결국 공유 상태의 동시성 문제이므로, 상태 소유자와 갱신 경로를 먼저 정한다.

## R3. EventBridge와 SQS로 발주를 자동화할 때 실패를 어떻게 다뤘나요 (경험형, 설계 꼬리)

- **답변 (카드 2 fork)**:

> 조직의 Kafka 도입 여력을 고려해 관리형 이벤트와 큐를 골랐습니다. 핵심 상태 변경을 먼저 확정한 뒤 후속 발주를 이벤트로 전달했고, 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했습니다. 영구 오류는 즉시 격리하고 일시 오류만 제한 재시도했으며, 재시도 예산을 넘기면 DLQ와 수동 확인 경로로 보냈습니다.

- **한계 (먼저 말할 것)**: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 실패가 나면 이벤트가 누락될 수 있었고, 당시에는 발행 재시도와 운영 확인으로 다뤘다. 지금이라면 상태 변경과 outbox 레코드를 같은 트랜잭션에 저장하고 릴레이가 발행하게 한다.
- **대안과 트레이드오프**: 리플레이, 강한 순서, 매우 높은 처리량이 핵심이면 Kafka를 다시 비교한다. 운영 부담과 필요한 전달 보장이 선택 기준이었다. Outbox를 도입한다면 릴레이 방식도 비교한다(Extended 카드 2 fork).

| 축 | Outbox(폴링 릴레이) | CDC(Debezium 등) |
|---|---|---|
| 인프라 | 단순(앱과 DB) | Kafka Connect 등 별도 구성 |
| 지연 | 폴링 주기에 좌우 | 변경 스트림 수준의 낮은 지연 |
| 적합 | 운영 단순성이 우선인 흐름 | 높은 처리량이나 낮은 지연이 핵심인 흐름 |
| 운영 부담 | 낮음 | 높음 |

- **SQS 수치 (AWS 공식 문서, 2026-09-29 확인)**: 가시성 타임아웃 기본값은 30초이고, 메시지를 처음 받은 시점부터 최대 12시간까지 연장할 수 있으며 연장해도 12시간 한도는 초기화되지 않는다. 처리 시간이 타임아웃을 넘으면 메시지가 다시 보여 중복 처리되므로, 타임아웃은 예상 처리 시간에 맞추고 긴 작업은 `ChangeMessageVisibility`로 연장한다. 표준 큐는 타임아웃 안에서도 중복 전달을 보장하지 않는다(at-least-once).
- **워커 선택 비교 (Extended 카드 2 fork)**:

| 축 | ECS 워커 유리 | Lambda 유리 |
|---|---|---|
| 도메인 로직 재사용 | NestJS 모델과 로직 그대로 | 별도 패키지로 분리 필요 |
| DB 연결과 동시성 | 상시 풀과 워커 수를 직접 제한 | 이벤트 소스 매핑 동시성과 DB 연결 예산 제한, 필요 시 RDS Proxy |
| 스케일 패턴 | 상시와 점진적 확장 | 불규칙하고 유휴 시간이 긴 워크로드 |
- **꼬리**: 정확히 한 번 처리라고 말할 수 있나? 아니다. 릴레이와 큐 소비 모두 중복될 수 있으므로 업무 키 단위 중복 제거와 상태 전이 검증을 유지한다.
- **회사 연결**: 공고의 도구 실패 유형 분류와 대응 정책은 이 영구 오류와 일시 오류 분리, 재시도 예산, 격리 경로와 같은 설계 문제다.

## R4. 슬로우 쿼리를 99.3% 개선했다는 근거는 무엇인가요 (경험형, 사실 꼬리)

- **답변 (카드 3 fork)**:

> 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했습니다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 설계하고, 인덱스가 실제로 정렬과 상위 레코드 접근에 쓰이는지 실행 계획으로 다시 확인했습니다.

- **측정 경계**: 이력서의 99.3%는 [사용자 확인 필요: 측정 대상 쿼리, 전후 비교 조건]을 말할 수 있을 때만 쓴다. 서브쿼리 관측값과 단건 쿼리 전후 결과, 배치 전체 시간은 같은 지표로 비교하지 않는다.
- **흔한 오답**: 카디널리티가 높은 컬럼을 무조건 앞에 둔다고 답하는 것. 동등 조건, 범위, 정렬, 반환 컬럼을 실제 쿼리에서 판단한다.
- **꼬리**: 인덱스 추가의 쓰기 비용은? 쓰기 경로와 다른 조회 영향을 함께 모니터링한다. NoSQL은 언제 검토하나? 최적화를 다 소진한 뒤가 아니라 접근 패턴과 일관성 요구가 맞을 때 처음부터 비교한다.
- **회사 연결**: 공고의 관계형 데이터베이스 및 NoSQL 설계와 최적화 업무에서, 인덱스와 저장소 선택을 설정 이름이 아니라 실행 계획과 전후 측정으로 판단하는 방식으로 기여한다.

## R5. Prisma N개 쿼리를 단일 쿼리로 합쳐 API 응답속도 90% 향상 (경험형)

- **답변 (카드 4 fork)**:

> 관계를 포함한 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했습니다. 당시 `relationJoins` Preview 기능이 비활성인 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했습니다. 기능을 켜고 `relationLoadStrategy: 'join'`을 적용한 뒤, MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했습니다. 성능이 중요한 경로만 바꾸고 나머지는 타입 안정성과 변경 용이성을 유지했습니다.

- **측정 경계**: 이력서의 API 응답속도 90% 향상은 [사용자 확인 필요: 지표(p50 또는 p99 지연), 대상 API, 전후 측정 조건]을 말할 수 있을 때만 쓴다. 응답 시간 90% 감소(약 10배 개선)로 바꿔 말하지 않고 이력서 문구 그대로 쓴다.
- **단순화 조건**: 옵션 이름만으로 SQL `JOIN`이라고 단정하지 않는다. Prisma 버전과 관계 로딩 설정에 따라 동작이 다르다.
- **꼬리**: 조인 전략의 비용은? 반환 데이터 중복, 집계 비용, DB 부하. 발표 경험(커뮤니티 발표)을 물으면 설명하며 이해의 빈틈을 점검했다고 답한다.
- **회사 연결**: 공고의 관계형 데이터베이스 설계와 최적화 업무에서, ORM이 실제로 만드는 쿼리를 확인하고 성능이 중요한 경로만 바꾸는 기준으로 기여한다.

## R6. 관측 체계를 어떻게 만들었고 장애 대응에 어떻게 썼나요 (경험형)

- **답변 (카드 5 fork)**:

> Grafana, Prometheus, Loki를 썼습니다. 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증했고, 식별자를 구조화 JSON 로그 본문으로 옮겨 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼습니다. 메트릭은 추세와 사용자 영향을, 로그는 개별 원인을 보는 데 쓰고, 경보는 과거 숫자를 복사하지 않고 사용자 영향 신호와 정상 구간을 관찰해 정했습니다.

- **꼬리**: 고유 식별자를 라벨로 넣으면? 직접 겪었다. 시계열 수가 급증했고, 그래서 식별자는 로그로 옮겼다. 대시보드와 경보도 불안정해진다. 장애 대응 순서는? 영향 범위 공유, 복구 우선, 타임라인과 원인, 재발 방지 포스트모템.
- **회사 연결**: Agent 서비스는 요청 하나가 여러 모델 호출과 도구 호출로 퍼지므로, 요청 단위 추적 식별자와 단계별 지연, 토큰 비용, 도구 실패율을 같은 원칙으로 분리해 본다.

## R7. 단일 서버에서 CloudFront, ELB, ECS Fargate로 옮긴 판단 (경험형)

- **답변 (카드 6 fork)**:

> 트래픽 증가에 따라 단일 NGINX 서버 구조를 관리형 컨테이너 환경으로 옮겼습니다. Docker 멀티스테이지 빌드로 빌드 도구와 실행 의존성을 분리했고, 이력서 기준 이미지 크기 909MB에서 513MB, 배포 시간 3분 10초에서 2분 20초로 줄였습니다. 읽기 부하는 RDS Read Replica로 나누되, 쓰기와 쓰기 직후 읽기는 primary로 보냈습니다.

- **왜 Kubernetes가 아니었나**: 멀티 클러스터, 복잡한 트래픽 라우팅, 여러 워크로드 동시 운영이 필요하지 않았고 운영 인력을 고려하면 관리형 태스크 환경이 부담이 낮았다.
- **꼬리**: 자동 확장 기준은? 큐 워커는 CPU만이 아니라 backlog와 가장 오래된 메시지 대기 시간으로 본다. 종료 신호를 받으면 새 요청을 막고 진행 중 작업의 완료 또는 재전달 경계를 명확히 한다.
- **회사 연결**: Kubernetes 우대 항목에는 이 판단 기준과 ECS에서 대응되는 개념으로 답하고, 직접 운영 경험이 없다는 점은 숨기지 않는다.

## R8. 팀 AI 협업 규약과 회귀 루프는 무엇을 했나요 (경험형)

- **의도**: 우대 사항의 바이브/에이전틱 코딩과 공고의 eval 업무. 규칙을 문장이 아니라 검사로 만들었는지 본다.
- **답변 (이력서 항목, FIT 10과 24 fork)**:

> AI가 건드릴 영역과 건드리면 안 되는 영역을 경로별 규약 문서로 명문화하고, 작업 종료 시점에 테스트와 변경 파일 검사로 AI가 스스로 품질을 확인하는 회귀 루프를 만들었습니다. 요구사항 해석과 설계 선택, 결과 채택은 제가 책임졌습니다.

- **사실 경계**: 검사 실패 시 작업 종료 자체를 막았는지는 [사용자 확인 필요: 종료 차단 방식]이 확정되기 전에는 말하지 않는다.
- **꼬리**: 프로토타입을 제품 코드로 옮긴 사례는? [사용자 확인 필요: 이력서 범위 안에서 테스트까지 이어진 구체 사례 하나]. 출석부 사이드 프로젝트는 1인 운영의 한계를 AI 협업 파이프라인 설계로 보완했다는 정성적 결론만 말한다.
- **한계**: 이는 개발 과정의 자동 검증이며 LLM Agent 제품의 eval 파이프라인을 운영한 경험과는 다르다고 먼저 구분한다.
- **회사 연결**: 제안형으로만 말한다. 예: 공개된 Veris의 LLM-as-a-Judge 루브릭 채점 앞단에 형식, 필수 필드, 도구 호출 순서 같은 결정론 검사를 두는 방식으로 기여할 수 있을지 확인하고 싶습니다. 실제 평가 파이프라인 구조는 단정하지 않는다.

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가요 (개인 프로젝트, 이력서)

- **의도**: 공고의 LLM 기능 품질 평가, 근거 기반 검색, AI 도구 활용을 실제로 해 봤는지 본다. LLM 서비스 운영 경험이 없는 갭을 가장 직접 메우는 근거다.
- **답변**:

> 회사 업무가 아니라 개인 프로젝트입니다. 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템입니다. Markdown 위키링크와 frontmatter의 근거 관계로 그래프를 구성하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색은 MCP 도구와 CLI로 노출했습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했고, 질문마다 반드시 돌려받아야 하는 근거(문서, 절, 본문 문구)가 응답 크기 예산 안에 모두 나와야 통과로 쳤습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어서 채택하지 않았습니다. 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했고, 통과가 41개에서 40개로 개선이 없는데 질문당 약 4.7초가 더 걸려서 채택하지 않았습니다. 이후 예산 안에서 절을 고르는 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다. 새 방식을 붙이는 것보다 측정으로 기각한 판단이 이 프로젝트의 핵심입니다.

- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 후보 단계의 이득이 있어도 바로 바꾸지 않는다. 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다.
- **골든 케이스 선정과 지표**: 평가 질문은 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본이 아니다. 양성은 필수 근거 그룹이 응답 크기 예산 안에 모두 나와야 통과, 음성은 빈 결과여야 통과다. 지표는 통과 개수와 후보 50개 안의 필수 근거 수다.
- **이력서 정정**: 이력서에는 골든 케이스 약 145건으로 BM25, 임베딩, 리랭커를 비교했다고 적혀 있으나 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **한계를 먼저 말할 것**: 합성 표본이고 실제 답변 정확도나 사용자 만족도를 잰 것이 아니다. 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- **꼬리**: 골든 케이스는 어떻게 만들었나, 어떤 지표로 비교했나. 위 선정과 지표 항목으로 답하고, 합성 표본이라는 한계를 함께 말한다.
- **회사 연결**: 공고의 Agent 품질 시나리오와 eval 업무, DataMart의 검색 로직 설계와 맞닿는다. 평가 세트를 먼저 만들고 방식을 고른 경험으로 JD QA J3, J5를 답한다. 프로덕션 LLM 운영 경험은 아니라고 먼저 구분한다.
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 면접에서 먼저 개인 프로젝트라고 밝힌다.
