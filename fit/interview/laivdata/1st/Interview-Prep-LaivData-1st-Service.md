# 라이브데이터 1차, 서비스 맥락 질문, 역질문, 체크리스트

> [[Interview-Prep-LaivData-1st|메인 문서]]의 하위 문서다. 서비스 질문은 공식 사이트가 공개한 모듈 설명과 공고의 업무에서만 출발한다. 회사의 실제 구현, 고객 수, 계약 규모는 모르므로 답변은 판단 기준과 확인 질문으로 끝낸다.

## 1. 서비스 맥락 질문

### S1. 저희 플랫폼을 보고 백엔드에서 가장 어려울 부분은 어디라고 생각했나요

- **공개 자료의 문제**: 공식 사이트는 도구 연결(MFlux), 지식 구조(DataMart), 오케스트레이션(LangBridge), 설계 허브(LaivStudio), 평가(Veris)를 한 흐름으로 설명한다.
- **답변 골격**: 관찰 사실 한 문장 → 가설로서의 어려움 → 확인하고 싶은 점. 예: 여러 단계의 추론과 도구 호출이 한 요청 안에서 이어지므로, 중간 실패 시 어디까지 완료됐는지 추적하고 재개할 수 있는 상태 관리와, 단계별 지연과 비용을 요청 단위로 관측하는 부분이 가장 어려울 것 같다. 실제로 어느 단계에서 가장 자주 문제가 되는지 듣고 싶다.
- **판단 기준**: 실패했을 때 사용자 영향이 큰 구간, 되돌릴 수 없는 부수효과가 있는 구간, 관측이 가장 약한 구간 순으로 어려움을 고른다.
- **대안과 트레이드오프**: 단계마다 상태를 영속 저장하면 재개와 추적이 쉬워지지만 저장 비용과 지연이 늘고 스키마 변경이 어려워진다. 요청 단위로 처음부터 다시 실행하면 단순하지만 비용이 반복되고 부수효과가 중복될 수 있다.
- **주의**: 가설을 사실처럼 말하지 않는다. 면접 전 공식 페이지와 공개 영상을 직접 보고 관찰 사실을 한 문장으로 준비한다.
- **내 경험 연결**: 상태 전이와 재처리 경계(R3), 관측 설계(R6).
- **꼬리**: 그 어려움을 줄이기 위해 첫 달에 무엇을 하겠나? 기존 요청 흐름에 요청 단위 추적 식별자가 끝까지 전달되는지부터 확인하고, 가장 자주 실패하는 단계를 지표로 확인한 뒤 고친다. 실제 구조를 모르므로 확인 순서로만 답한다.

### S2. 외부 API를 에이전트 도구로 연결할 때 무엇을 조심해야 하나요

- **공개 자료의 문제**: MFlux를 외부 API를 MCP Tool 형태로 자동 변환해 AI가 쓰게 하는 서버로 소개한다.
- **답변 골격**: 도구가 생기면 권한이 생긴다. 권한은 모델이 아니라 도구 서버와 다운스트림에서 강제하고 최소 범위로 준다. 읽기와 쓰기 도구를 나누고, 되돌릴 수 없는 호출 전에는 사람 승인을 둔다. 도구가 돌려준 외부 데이터에 숨은 지시가 모델을 오염시킬 수 있으므로 신뢰 경계를 둔다. 호출마다 누가 무엇을 실행했는지 남긴다. 도구를 많이 붙일수록 컨텍스트 비용과 오선택이 늘어 필요한 도구만 노출한다.
- **판단 기준**: 도구가 쓰기인가 읽기인가, 되돌릴 수 있는가, 호출 주체의 권한 범위가 어디까지인가, 외부 데이터를 모델 입력으로 되돌리는가.
- **대안과 트레이드오프**: 자동 변환은 연결 속도가 빠르지만 API 설명이 부실하면 모델이 잘못 고른다. 핵심 도구는 이름, 설명, 입력 스키마를 사람이 다듬는 편이 정확도가 높을 수 있다.
- **내 경험 연결**: 외부 API 연동에서 실패를 분류하고 재시도 예산을 둔 경험, 명세와 실제 동작을 대조해 오픈소스 문제를 찾은 경험(FIDO).
- **꼬리**: 쓰기 도구가 타임아웃으로 실패하면 재시도해도 되나? 성공했는데 응답만 늦었을 수 있으므로 멱등성 키 없이 재시도하면 중복 실행된다. 멱등성 키를 지원하지 않는 API는 상태 조회로 결과를 확인한 뒤 재시도한다(R3와 같은 원리).

### S3. 고객사 PoC 요구와 플랫폼 공통화가 충돌하면 어떻게 하나요

- **공개 자료의 문제**: 공고는 도메인 요구를 플랫폼 공통 역량으로 추상화하고 PoC에서 본계약과 운영 고도화로 잇는 업무를 명시한다.
- **답변 골격**: 요구를 고객 특화, 여러 고객에 반복될 가능성, 이미 반복된 것으로 나눈다. 실제로 두 번 반복된 로직만 공통화하고, 한 번뿐인 요구는 설정이나 확장 지점으로 흡수해 플랫폼 핵심에 넣지 않는다. PoC 일정이 급하면 임시 분기를 허용하되 본계약 전환 시 정리할 부채로 기록한다.
- **판단 기준**: 변경 빈도, 고객 간 공통성, 되돌리기 비용, 본계약 가능성.
- **대안과 트레이드오프**: 처음부터 공통화하면 재사용은 좋지만 한 고객의 요구가 플랫폼 핵심을 오염시키고 추상화가 틀릴 위험이 있다. 고객별 분기로 두면 PoC 속도는 빠르지만 본계약 뒤 정리 비용이 쌓인다. 설정과 확장 지점은 그 사이지만 설정 조합이 늘면 테스트 범위가 커진다.
- **내 경험 연결**: 대형 고객사 PoC를 위해 도메인별 모듈로 분리해 잦은 요구 변경을 흡수한 경험(R1).
- **꼬리**: 공통화할 시점을 누가 정하나? 기술 부채 기록과 반복 횟수를 근거로 PM, 사업과 함께 정한다. 개발자 혼자 정하면 고객 일정과 충돌한다.

### S4. 교육, 금융, 공공 고객의 데이터를 한 플랫폼에서 다룬다면

- **공개 자료의 문제**: 공고와 사이트는 교육, 금융, 공공 등 여러 산업 고객을 언급한다. 공식 사이트는 SaaS 및 구축형 AI 솔루션 제공을 명시한다(라이브데이터 공식 사이트, 2026-09-29 확인). 고객별 실제 배포 형태와 격리 기준은 미확인이다.
- **답변 골격**: 격리 단위를 먼저 정한다(행 단위 tenant 키, 스키마, DB, 배포 분리). 금융과 공공처럼 규제가 강한 고객은 분리 수준을 높이고 감사 로그와 데이터 보관 위치를 계약 요구로 받는다. 검색 저장소와 캐시도 고객 경계를 넘지 않게 조회 시점에 강제한다. 한 고객의 과부하가 다른 고객에게 번지지 않도록 고객별 속도 제한을 둔다.
- **판단 기준**: 규제와 계약 요구(데이터 보관 위치, 감사), 고객 간 데이터 혼입 시 피해, 고객별 부하 편차, 운영 인력.
- **대안과 트레이드오프**: 공유 SaaS의 행 단위 tenant 키는 운영 비용이 낮지만 조회 조건 하나를 빠뜨리면 유출로 이어진다. 스키마와 DB 분리는 격리가 강하지만 마이그레이션과 운영 대상이 고객 수만큼 늘어난다. 구축형은 데이터가 고객 경계 안에 머물지만 버전 관리와 장애 대응이 고객 환경마다 달라진다.
- **확인 질문**: 고객별 실제 배포 형태와 격리 기준. 이 질문은 역질문 C2와 연결한다.
- **내 경험 연결**: 시솔지주에서 고객사 On-Premise 환경 구축을 위해 AWS 기반 서비스를 이전한 경험(이력서 항목). 관리형 서비스 의존을 고객 환경에 맞게 바꾸는 일이 구축형 제공과 가장 가깝다. Kubernetes 기반은 아니었다고 구분한다(JD-QA J8 꼬리).
- **꼬리**: 구축형 고객에게 새 버전을 어떻게 배포하나? 고객 환경마다 승인 절차와 반영 시점이 달라 여러 버전이 동시에 운영된다. 그래서 하위 호환 기간과 마이그레이션 순서를 정해야 한다. 실제 방식은 역질문으로 확인한다.
- **한계**: 금융 규제 실무 경험은 없다고 구분한다.

### S5. LLM 호출의 비용과 지연은 어떻게 관리하나요

- **공개 자료의 문제**: 공식 사이트는 비용효율적 AI 구축과 합리적인 비용의 AI 도입을 내세우고, 공고는 서비스 운영과 장애 대응을 업무로 적는다. 요청 하나가 여러 모델 호출과 도구 호출로 퍼지는 구조에서 비용과 지연을 어떻게 통제하는지가 문제다.
- **답변 골격**: 요청 단위로 모델 호출 수, 토큰, 지연, 도구 호출 수를 기록한다. 요청 전에는 사용량 한도 초과 여부만 확인하고, 응답 후 실제 사용량을 사용자나 고객별로 누적해 한도를 관리한다. 에이전트 루프에는 호출 라운드 상한, 같은 도구와 인자의 반복 호출 차단, 결과 크기 제한을 코드로 둔다. 단계마다 필요한 모델 등급을 나눠 쓰는 것도 선택지다.
- **판단 기준**: 한도 초과를 얼마나 허용할 수 있는가(비용 정확도), 요청 실패를 얼마나 허용할 수 있는가(사용자 경험), 사용량 저장소 장애 시 요청을 막을지 통과시킬지.
- **대안과 트레이드오프**: 강한 상한은 비용을 막지만 어려운 요청을 중간에 끊는다. 상한에 닿으면 부분 결과와 이유를 사용자에게 알리는 경로가 필요하다. 사후 반영은 실측 기반이라 정확하지만 요청 전에는 초과 여부만 보므로 동시 요청이 함께 사전 검사를 통과하면 한도를 넘는다. 사전 예약은 초과를 막지만 예약한 양만큼 한도를 일시적으로 묶는다.
- **내 경험 연결**: 큐 워커의 동시성과 재시도 예산을 제한한 경험, 요청 식별자를 메트릭 라벨에 넣었다가 시계열 급증을 겪고 로그로 옮겨 카디널리티를 관리한 경험(R6), DB 잠금으로 동시 요청의 정합성을 지킨 경험(R2).
- **꼬리**: 동시 요청이 사전 검사를 함께 통과해 한도를 넘으면? `max_tokens` 기준으로 먼저 예약(원자적 차감)하고 응답 후 실측으로 정산해 차액을 돌려준다. 초과 허용 폭과 비용 정확도의 교환이며, 소량 초과를 허용할 수 있으면 사후 반영만으로 두는 것도 선택지다. 예약 차감은 한도 확인과 차감을 한 번의 원자적 연산으로 묶어야 한다(R2의 확인 후 갱신 경쟁과 같은 문제).

### S6. 기능 개선이 효과가 있었는지 어떻게 증명하나요

- **공개 자료의 문제**: 공고는 A/B, 퍼널, VOC를 연결해 느낌이 아니라 지표 개선으로 결정한다고 쓴다.
- **답변 골격**: 개선 전에 성공 지표 하나와 지키면서 봐야 할 보조 지표(오류율, 거부율, 지연, 비용)를 정한다. 오프라인 eval을 통과한 변경만 일부 사용자에게 내고, 같은 기간과 같은 조건에서 비교한다. VOC는 실패 사례를 테스트셋에 추가하는 입력으로 쓴다.
- **판단 기준**: 트래픽이 비교에 충분한가, 변경이 되돌릴 수 있는가, 보조 지표가 악화되면 멈추는 기준을 미리 정했는가.
- **대안과 트레이드오프**: A/B는 인과를 가장 잘 보여 주지만 트래픽이 적은 B2B 고객 환경에서는 결론까지 오래 걸린다. 그때는 오프라인 eval과 전후 비교, 고객 인터뷰를 함께 쓰되 계절성과 동시 변경의 영향을 한계로 적는다.
- **내 경험 연결**: 성능 개선을 같은 실행 환경과 조건에서 전후 비교하고, 서로 다른 측정값을 섞어 비교하지 않은 원칙(R4).
- **꼬리**: 성공 지표는 올랐는데 비용이 두 배가 됐다면? 보조 지표 기준을 미리 정하지 않은 것이 문제다. 개선 폭 대비 비용을 함께 보고 결정한다.
- **한계**: 제품 A/B 실험을 직접 설계한 경험은 없다고 구분한다.

## 2. 핵심 메시지 3개

1. 고객 요구가 자주 바뀌는 PoC 환경에서 모듈 경계로 변경을 흡수해 본 백엔드 개발자다.
2. 결과가 흔들리는 시스템을 믿을 수 있게 만드는 방법(실패 분류, 멱등성, 결정론 검증, 관측)을 운영에서 써 왔다.
3. LLM Agent 제품, React, FastAPI, Kubernetes는 없다고 먼저 말하고, 무엇이 전이되고 무엇을 새로 배울지 구분해 말한다.

## 3. 체크리스트

### 면접 시작 전

- [ ] 면접 일시, 형식(대면 또는 화상), 코딩테스트 여부, 참여 역할을 확인했다.
- [ ] [[Interview-Prep-LaivData-1st-FIT#3. 이직 사유와 현재 상태|이직 사유 답변]]을 30초 안에 말하고 트라이포드랩 경험으로 넘어갈 수 있다. 3-D 답변까지 말할 수 있다.
- [ ] 제출 이력서의 경력 기간 표기와 답변이 일치한다.
- [ ] 공식 사이트 solution 페이지와 공개 영상을 보고 관찰 사실 한 문장을 준비했다.
- [ ] 핵심 역질문 2~3개는 외우고, 보충 1~2개는 노트로 둔다.

### 보강할 기술 영역

| 영역 | 보강할 핵심 | 복습 |
|---|---|---|

| 평가 | 채점기 3종의 순서, 거부권 항목, 채점기부터 의심하는 순서 | [ ] |
| 오케스트레이션 | 체크포인트, interrupt와 재개 시 노드 재실행, 멱등성 | [ ] |
| 보안 | 과도한 위임, 권한의 다운스트림 강제, 간접 프롬프트 인젝션 | [ ] |
| 풀스택 | FastAPI 비동기 모델, React 서버 상태와 화면 상태 구분 | [ ] |
| 인프라 | Deployment, Service, probe와 ECS 대응 개념 | [ ] |

### 공개 전 점검

- [ ] 회사 사실에 공개 출처가 있거나 미확인으로 표시했다.
- [ ] 제3자 실명, 연락처, 발화 원문, 처우 금액이 없다.
- [ ] 전, 현 직장의 비공개 정보와 내부 지표, 출석부의 정량 수치가 없다.
- [ ] 성과 수치는 공개 이력서에 있는 값만 썼고 측정 조건을 설명할 수 있다.

## 4. 역질문

> `My-Reverse-Questions`에서 첫 면접과 도메인 전환 묶음을 기준으로 골랐다. 공개 자료로 확인할 수 없는 사실을 검증하는 질문만 둔다.

**마스터에서 고른 질문 4개**

1. **B1 초기 과제와 성공 기준**: 합류 후 가장 먼저 책임질 과제와, 잘하고 있다고 판단할 기준은 무엇인가요?
2. **A4 팀 구성과 협업 경계**: Agent Foundry팀은 어떤 역할로 구성돼 있고, 이 포지션은 누구와 어떤 결정을 함께 하나요?
3. **C2 데이터 경계와 확장 단계**: 여러 고객의 데이터와 업무 흐름이 섞일 수 있다면 격리 단위와 과부하 방지는 어떻게 하고 있나요?
4. **D2 학습과 검증**: 공고의 기술 중 제가 아직 깊지 않은 FastAPI와 React는 어떤 작은 과제로 검증하며 익히는 것이 효과적일까요?

**회사 특이 질문 2개**

5. **역할의 실제 비중**: 공고에 개발, 제품 기획, 품질 평가 업무가 함께 적혀 있는데, 이 포지션에서 실제 시간 비중과 우선순위는 어떻게 되나요? 백엔드와 프론트엔드 비중도 궁금합니다.
6. **PoC와 플랫폼의 연결**: 고객 프로젝트에서 얻은 요구가 플랫폼 공통 역량으로 들어가는 기준과 과정이 있나요? 평가 결과가 배포 결정에 어떻게 쓰이는지도 듣고 싶습니다.

**보충 (시간이 남을 때)**: E3 온콜과 장애 대응 운영 방식, 고객 프로젝트 마감과 플랫폼 일정이 겹칠 때의 우선순위 기준.

**기록 원칙**: 면접에서 들은 답은 비공개 정보이므로 이 문서에 적지 않고, 회고에는 본인의 학습과 역할 기반 요약만 남긴다.
