# 그립랩스 1차, 서비스 맥락 질문, 역질문, 체크리스트

> [[Interview-Prep-GripLabs-1st|1차 메인]]의 하위 문서다. 서비스 질문의 전제는 [[Interview-Prep-GripLabs-1st-JD|JD와 회사 분석]]에서 출처를 확인한 공개 설명뿐이다. 실제 구현, 트래픽, 파트너 계약은 모르므로 답변은 가정을 먼저 밝히는 설계 골격으로 준비하고, 확인할 것은 역질문으로 넘긴다.

## 1. 서비스 맥락 질문

### S1. LLM을 쓰는 기능(요약, 대화형 AI)의 백엔드를 설계한다면

- **공개 근거**: AI Chat은 직접 개발하고 운영하는 대화형 AI, 뉴밍 2.0은 유사 이슈를 묶어 생성형 요약을 제공한다고 공개했다. 모델이 자체 호스팅인지 외부 API인지는 미확인이다.
- **답변 골격**: 요청 경로와 생성 경로를 분리한다. 이미 계산 가능한 요약(이슈 묶음 요약)은 비동기 작업으로 미리 만들어 저장하고 조회만 한다. 사용자 입력에 따라 생성해야 하는 대화는 스트리밍 응답(SSE)으로 첫 토큰 지연을 줄이고, 모델 호출에는 타임아웃, 제한된 재시도, 동시 호출 수 제한을 둔다. 토큰 사용량과 비용, 지연, 오류율을 요청 단위로 기록한다. 모델이 실패하면 캐시된 요약이나 원문 링크로 기능을 낮춰 응답한다.
- **판단 기준**: 결과의 신선도 요구, 사용자당 비용 한도, 허용 지연, 결과 오류가 사용자에게 주는 영향.
- **대안과 트레이드오프**: 사전 생성은 비용과 지연이 예측 가능하지만 신선도가 떨어진다. 요청 시 생성은 개인화에 유리하지만 비용과 지연이 흔들린다. 같은 입력의 결과 캐시는 비용을 줄이지만 모델이나 프롬프트 버전을 키에 포함해야 한다.
- **유사 경험과 한계**: LLM 서빙 경험은 없다. 외부 API 연동의 타임아웃, 재시도, 캐시와 비동기 분리(R2)가 전이 근거다. 모델 품질 평가는 모르는 영역이라고 인정하고, 평가용 입력과 출력 로그를 백엔드가 남겨야 한다는 점까지만 말한다.
- **꼬리**: 긴 생성 중 서버가 재배포되면(연결 종료와 재시도 경계, 진행 중 요청 정리). 프롬프트 변경을 어떻게 배포하는가(버전 관리, 소량 적용 뒤 확대, 결과 비교).

### S2. 실시간 뉴스 클러스터링과 요약 파이프라인을 설계한다면

- **공개 근거**: NewsBlock은 실시간 뉴스 클러스터링과 요약, 키워드와 인사이트 자동 추출을 한다고 공개했다.
- **답변 골격**: 수집(언론사 원천별 어댑터) → 정규화와 중복 제거(원문 ID와 내용 해시) → 저장 → 임베딩이나 키워드 추출 → 클러스터 배정 → 요약 생성 → 서빙용 읽기 모델 순서로 단계를 나누고, 단계 사이는 큐로 잇는다. 각 단계는 기사 ID 기준으로 멱등하게 만들어 재처리해도 결과가 같게 한다. 원문 수정과 삭제는 별도 이벤트로 받아 클러스터와 요약을 다시 계산한다.
- **판단 기준**: 실시간성 요구(속보 반영까지 허용 시간), 원천별 형식 변경 빈도, 재처리 비용.
- **대안과 트레이드오프**: 주기 배치는 단순하고 재처리가 쉽지만 반영이 늦다. 스트림 처리는 빠르지만 순서, 늦게 도착한 기사, 상태 관리가 어렵다. 처음에는 짧은 주기 배치와 큐로 시작하고 측정된 지연이 요구를 넘을 때 바꾼다.
- **유사 경험**: 시솔지주의 배송 정보 스크래핑과 환율 배치, 외부 수집 배치의 오류를 자동 검증으로 줄인 경험(C8). 원천별 실패를 격리하고 마지막 성공 결과를 유지하는 원칙을 쓴다.
- **꼬리**: 원천 하나가 형식을 바꿔 파싱이 깨지면(원천별 실패 격리, 스키마 검증, 실패 누적 알림). 같은 사건이 여러 클러스터로 쪼개지면(클러스터 병합 규칙은 모델 영역이므로 확인 질문으로 둔다).

### S3. 여러 언론사에 같은 솔루션을 제공하는 B2B 백엔드의 격리

- **공개 근거**: 연구 결과를 파트너 환경에서도 운영한다고 공개했고, 댓글 모니터링(iRevue), 번역(Mingo), 퀴즈 생성(Crossword) 제품과 파트너 언론사 로고가 있다. 제공 방식(API, 임베드 위젯, 설치형)은 미확인이다.
- **답변 골격**: 모든 요청과 데이터에 테넌트 식별자를 두고 인증 단계에서 테넌트를 확정한다. 조회는 테넌트 조건을 강제하는 저장소 계층을 거치게 하고 테스트로 누락을 막는다. 테넌트별 요청 한도와 작업 큐 동시성을 나눠 한 파트너의 급증이 다른 파트너를 막지 않게 한다. 파트너별 설정(금칙어, 스타일, 노출 옵션)은 버전이 있는 설정으로 관리한다.
- **판단 기준**: 데이터 격리 요구 수준(계약, 보안), 파트너 간 부하 편차, 파트너별 커스터마이징 폭.
- **대안과 트레이드오프**: 공유 스키마와 테넌트 컬럼은 운영이 단순하지만 격리 실수가 곧 유출이다. 테넌트별 스키마나 DB는 격리가 강하지만 마이그레이션과 운영 비용이 늘어난다. 고객 수와 격리 요구를 확인한 뒤 고른다.
- **유사 경험**: 출석부 사이드 프로젝트에서 여러 조직의 권한 경계를 설계하고 검증했다(정성적 결론만). 시솔지주에서 고객사 요구에 맞춘 온프레미스 이전을 경험했다.
- **꼬리**: 파트너 하나만 기능을 먼저 켜려면(테넌트 단위 기능 플래그). 파트너 API 키가 유출되면(키 회전과 폐기, 테넌트별 감사 로그).

### S4. 기사 투표와 댓글 기반 이유 요약의 동시성

- **공개 근거**: Dynamic Poll은 본문과 댓글 두 모드로 작동하는 AI 투표 엔진이며, 뉴밍 2.0 보도는 투표 댓글에서 선택 이유를 묶어 실시간 표출한다고 설명했다.
- **답변 골격**: 한 사용자 한 표는 `(poll_id, user_id)` 유니크 제약으로 DB가 보장한다. 집계는 매 투표마다 같은 카운터 행을 갱신하면 인기 기사에서 경합이 커지므로, 투표 행을 정본으로 두고 집계는 주기 계산이나 분할 카운터로 만든다. 이유 요약은 투표 트랜잭션에서 분리해 비동기로 갱신하고, 화면에는 마지막 요약 시각을 함께 보여 준다.
- **대안과 트레이드오프**: 단일 카운터 행 갱신은 정확하지만 핫 키에서 잠금 대기가 쌓인다. Redis 원자 증가는 빠르지만 DB와 원자적으로 묶이지 않으므로 대사가 필요하다. 표시 지연을 얼마나 허용하는지로 고른다.
- **유사 경험**: IoT 동시 갱신의 잠금 판단(R1), 캐시 스탬피드 방어.
- **꼬리**: 비로그인 투표를 허용하면 중복을 어떻게 막는가(확정할 수 없음을 인정하고 기기 식별과 요청 한도로 완화). 투표 취소와 변경이 있으면 상태 전이를 어떻게 둘 것인가.

### S5. 다국어 번역 엔진과 고유명사 DB를 붙인다면

- **공개 근거**: Mingo는 한국어 기사를 글로벌 독자에게 전달하는 다국어 AI 번역 엔진이고, 고유명사 DB는 5개 언어의 인명, 지명, 고유 용어 매칭 DB라고 공개했다.
- **답변 골격**: 번역 전에 기사에서 고유명사 후보를 찾아 사전의 확정 표기로 고정하고, 번역 뒤에 표기가 지켜졌는지 검증한다. 사전은 버전을 두고, 사전이 바뀌면 영향을 받는 기사만 재번역 대상으로 표시한다. 번역 결과는 원문 해시, 대상 언어, 사전 버전, 모델 버전을 키로 저장해 같은 입력을 다시 호출하지 않는다.
- **판단 기준**: 표기 오류의 비용(인명 오역은 신뢰 문제), 재번역 비용, 기사 수정 빈도.
- **유사 경험**: 시솔지주에서 Google API를 연동한 번역 기능을 개선해 70% 성능 향상(이력서 공개 수치). 무엇을 70% 개선했는지(응답 시간, 처리량)와 측정 조건을 설명할 수 있을 때만 수치를 말한다.
- **꼬리**: 같은 이름이 문맥마다 다른 인물이면(동명이인 구분은 사전 모델링 문제, 운영자 검수 흐름이 필요). 사전 갱신과 번역 캐시 무효화 순서.

### S6. 속보로 트래픽이 한 기사에 몰릴 때

- **공개 근거**: 뉴밍은 주요 언론사 콘텐츠 흐름 위에서 매일 작동하는 B2C 앱이다. 실제 트래픽 규모는 미확인이다.
- **답변 골격**: 먼저 병목을 측정한다(p95, 오류율, DB 연결 대기, 캐시 적중률). 기사 본문과 요약처럼 모두에게 같은 응답은 CDN과 캐시로 흡수하고, 인기 키가 동시에 만료될 때 원본으로 몰리지 않게 TTL 지터, 요청 병합, 백그라운드 갱신을 둔다. 개인화 영역은 실패하면 인기 목록으로 낮춰 핵심 경로를 지킨다. 읽기 부하가 DB 병목이고 지연을 허용하는 조회만 replica로 보낸다.
- **대안과 트레이드오프**: 스케일 아웃은 빠르지만 DB가 병목이면 효과가 없다. 캐시는 부하를 줄이지만 정정 기사 반영이 늦어진다. 정정과 삭제는 이벤트 기반 무효화를 함께 둔다.
- **유사 경험**: CloudFront, ELB, ECS 전환과 Read Replica 도입(R6).
- **꼬리**: 캐시가 통째로 죽으면(원본 보호용 연결 풀 제한과 요청 제어). 속보 알림 발송이 겹치면 발송 큐를 분리한다.

## 2. 역질문

첫 면접이므로 역할 이해와 성공 기준을 우선하고, 깊은 기술 질문은 다음 단계에 아낀다. 핵심 2~3개는 외워서 묻는다.

1. **B1 초기 과제와 성공 기준**: 합류 후 가장 먼저 책임질 과제와, 잘하고 있다고 판단할 기준은 무엇인가요?
2. **A4 팀 구성과 협업 경계**: 현재 백엔드와 AI 연구 쪽은 어떤 역할로 구성돼 있고, 이 포지션은 누구와 어떤 결정을 함께 하나요?
3. **C1 기술 경계와 신규 개발 비중**: 이 역할이 직접 소유하는 서비스 경계는 어디이고, 신규 개발과 기존 제품 개선의 비중은 어떻게 되나요?
4. **F1 이후 단계 형식**: 2차 면접의 형식과 참여 역할을 미리 알 수 있을까요?
5. **회사 특이, 신규 사업 범위**: 공고의 신규 사업은 기존 제품의 확장인지 별도 서비스인지, B2B와 B2C 중 어디에 먼저 무게가 실리는지 들을 수 있을까요?
6. **회사 특이, AI 결과 서빙 책임**: 모델 호출과 결과 품질 평가에서 백엔드가 맡는 범위는 어디까지이고, 모델 쪽 구성원과 어떤 계약으로 협업하나요?

**아껴 둘 질문**: 현재 DB와 인프라 구성, 파트너 제공 방식과 격리 기준, 장애 대응과 온콜, 코드 리뷰와 배포 리듬.
**묻지 않을 것**: 투자와 매출, 파트너 계약 조건, 연봉(처우 협의 단계 전), 홈페이지에 있는 제품 소개.
