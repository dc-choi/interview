# 그립랩스 1차, 이력서 기반 기술 질문

> [[Interview-Prep-GripLabs-1st|1차 메인]]의 하위 문서다. 기술 카드 마스터를 fork했다. 이력서에 공개된 수치만 쓰고, 측정 조건을 설명할 수 없으면 수치 대신 문제, 선택, 검증 순서로 말한다. 전 직장의 고객, 내부 지표, 경보 기준은 말하지 않는다.

## R1. IoT 동시 요청의 Race Condition을 DB Lock으로 어떻게 해결했나

- **유형과 의도**: 경험형. 동시성 문제를 재현하고 잠금 방식을 근거로 골랐는지 본다.
- **핵심 답변**: 같은 재고 상태를 동시에 바꾸는 경로에서 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했다. 입력 검증과 외부 호출은 트랜잭션 밖에서 끝내고, 잠금 읽기 뒤 불변식을 다시 검증했다. 여러 대상을 갱신할 때는 업무 키 순서를 통일했다. 동시 요청을 재현해 최종 수량, 잠금 실패, 재시도 뒤 상태를 확인했다.
- **대안과 트레이드오프**: 충돌이 잦은 쓰기에서 낙관적 잠금은 늦게 충돌을 발견해 작업 전체를 다시 한다. 보호 대상이 단일 DB 트랜잭션 안에 있어 분산 잠금보다 DB 잠금이 단순했다. 충돌이 드문 편집은 버전 컬럼 조건부 갱신이 낫다.
- **한계**: 당시 재시도는 짧은 고정 간격이었다. 다시 설계하면 지수 백오프와 지터를 검증한다. `NOWAIT`는 행 잠금 대기만 없애고 메타데이터 잠금 대기는 남는다. 잠금은 유입량을 흡수하지 못하므로 급격한 유입에는 업무 키별 순서 큐와 워커 동시성 제한을 검토한다.
- **꼬리**: NOWAIT와 SKIP LOCKED 차이(특정 행을 반드시 처리하면 NOWAIT, 큐처럼 다음 행을 가져가면 SKIP LOCKED). 서버가 여러 대여도 같은 DB를 보면 DB 잠금으로 충분한가(충분하다, 보호 자원이 여러 저장소에 걸칠 때만 분산 잠금 검토). 데드락은 `SHOW ENGINE INNODB STATUS`의 최근 데드락 섹션으로 분석하고 새 트랜잭션에서 제한 재시도한다.
- **끝줄**: 여러 사용자가 같은 투표나 집계를 동시에 갱신하는 기능에서도 같은 판단 순서를 쓰겠다.

## R2. Kafka 대신 EventBridge와 SQS를 고른 이유와 이벤트 유실 대책

- **유형과 의도**: 설계형. 도구 선택의 기준과 전달 보장의 한계를 아는지 본다.
- **핵심 답변**: 상태 변경과 외부 연동을 한 요청에 묶으면 느린 의존성 하나가 핵심 상태 변경까지 실패시킨다. 핵심 상태를 먼저 확정하고 후속 발주 처리를 EventBridge와 SQS로 넘겼으며, 소비자는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했다. 영구 오류는 격리하고 일시 오류만 제한 재시도한 뒤 DLQ와 수동 확인으로 보냈다.
- **대안과 트레이드오프**: 조직의 운영 여력, 필요한 전달 보장, 재처리 요구를 비교해 관리형 큐를 골랐다. 장기 replay, 키 단위 순서, 독립 consumer group, 매우 높은 처리량이 핵심이면 Kafka를 다시 비교한다. Kafka를 직접 운영한 경험은 없다고 밝힌다.
- **한계**: DB 커밋 뒤 발행 전에 프로세스가 죽으면 이벤트가 빠질 수 있었다. 당시에는 발행 재시도와 운영 확인으로 다뤘다. 다시 설계하면 상태 변경과 Outbox 레코드를 같은 트랜잭션에 저장하고 릴레이가 발행한다. Outbox도 중복 발행이 가능하므로 정확히 한 번이라고 주장하지 않고 소비자 멱등성을 유지한다.
- **꼬리**: SQS visibility timeout은 관측한 처리 시간에 여유를 두고 긴 작업은 연장한다. FIFO는 MessageGroupId 안에서만 순서를 보장한다. ECS 워커를 고른 이유는 기존 도메인 로직 재사용과 DB 연결 수 제어였다.
- **끝줄**: 기사 수집 뒤 요약, 번역, 클러스터링을 비동기로 잇는 흐름에도 같은 실패 분리 원칙을 적용할 수 있다.

## R3. 복합 인덱스로 슬로우 쿼리 99.3% 개선은 어떻게 했나

- **유형과 의도**: 경험형과 사실형. 공고 요건(실행 계획 기반 튜닝)과 직결된다.
- **핵심 답변**: 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했다. 업무 키로 동등 조건을 건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 만들고 쿼리 구조를 함께 조정했다. 인덱스가 정렬과 상위 레코드 접근에 실제로 쓰이는지 실행 계획으로 다시 확인했다.
- **수치 말하기**: 99.3%는 이력서 공개 수치다. 말할 때는 같은 쿼리의 전후 비교인지, 실행 환경과 캐시 상태가 같았는지 설명할 수 있어야 한다. 설명이 어려우면 크게 줄었다고만 말하고 측정 방법을 설명한다.
- **대안과 트레이드오프**: 복합 인덱스는 읽기를 돕는 대신 쓰기와 저장 비용을 늘린다. 컬럼 순서는 카디널리티 하나가 아니라 동등 조건, 범위 조건, 정렬, 반환 컬럼으로 정한다. 커버링 인덱스는 테이블 접근을 줄이지만 인덱스를 무작정 넓히지 않는다.
- **꼬리**: `Using filesort`는 디스크 정렬이라는 뜻이 아니다. 예상 rows와 실제 rows 곱하기 loops가 크게 벌어지면 통계를 의심한다. 데이터 규모와 관계없이 안정적이라는 표현은 인덱스로 탐색 범위가 결과 수에 묶인다는 뜻이며, 분포가 바뀌면 다시 측정한다고 덧붙인다.

## R4. Prisma N개 쿼리를 SubQuery 기반 단일 쿼리로 바꿔 응답 90% 향상

- **유형과 의도**: 경험형. ORM이 만든 SQL을 직접 확인하는 습관을 본다.
- **핵심 답변**: 관계를 포함한 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했다. 당시 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 합쳤다. `relationJoins` 기능을 켜고 `relationLoadStrategy: 'join'`을 적용해 MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했다. 이 경험을 하코 커뮤니티에서 발표했다.
- **흔한 오답**: 옵션 이름이 join이라서 SQL JOIN이 나간다고 단정하는 것. 전통적인 lazy loading N+1과 같은 현상으로 뭉뚱그리는 것.
- **대안과 트레이드오프**: 단일 쿼리는 왕복을 줄이지만 반환 데이터 중복, 집계 비용, DB 부하가 늘 수 있다. 성능이 중요한 경로만 바꾸고 나머지는 타입 안정성을 유지했다. 윈도우 함수나 대량 연산처럼 ORM 생성 SQL이 맞지 않는 경로만 raw 쿼리로 낮춘다.
- **꼬리**: Prisma 버전과 설정에 따라 동작이 달라지므로 적용 전 SQL 로그와 실행 계획을 같은 환경에서 본다. JOIN과 Subquery 중 무엇이 빠른지는 옵티마이저와 데이터 분포에 달려 있다.

## R5. PoC 대응을 위한 모듈 중심 아키텍처는 무엇을 나눴나

- **유형과 의도**: 설계형. 공고의 레이어드 아키텍처와 OOP 요건을 실제 경험으로 확인한다.
- **핵심 답변**: NestJS에서 도메인별 모듈을 나누고 Controller, UseCase, Domain, Repository 포트, 인프라 구현을 분리했다. 의존 방향은 인터페이스 계층에서 애플리케이션, 도메인 순으로 두고 인프라가 도메인 포트를 구현하도록 Symbol 토큰으로 바인딩했다. 같은 도메인이라도 API 응답과 파일 내보내기처럼 의도가 다른 경로는 UseCase를 나눠 입출력 요구가 도메인에 스며들지 않게 했다.
- **대안과 트레이드오프**: 계층을 늘리는 것이 목표가 아니다. 실제로 교체되거나 독립적으로 바뀌는 경계에만 추상화를 두고, 단순 CRUD에는 인터페이스를 만들지 않았다.
- **검증**: 도메인 규칙이 프레임워크 없이 테스트되는지, 인프라 변경이 호출자 전체에 퍼지지 않는지로 경계의 효과를 본다.
- **꼬리**: `forwardRef()`가 반복되면 모듈 책임을 다시 나눠야 한다는 신호다. middleware, guard, interceptor, pipe, exception filter의 책임과 순서를 설명한다.
- **끝줄**: 신규 사업처럼 요구사항이 자주 바뀌는 단계에서 이 경계가 변경 비용을 줄인다.

## R6. 단일 NGINX에서 CloudFront, ELB, ECS로 전환하고 Read Replica로 40% 개선

- **유형과 의도**: 설계형. 전환 이유와 일관성 대가를 아는지 본다.
- **핵심 답변**: 트래픽이 늘며 단일 서버 구조의 확장과 배포 한계가 커져 관리형 컨테이너 환경으로 점진 전환했다. 읽기 부하는 Read Replica로 분산했고, 쓰기와 쓰기 직후 읽기는 primary로 고정하고 지연을 허용하는 조회만 replica로 보냈다. Docker 멀티스테이지 빌드로 이미지를 909MB에서 513MB로 줄이고 배포 시간을 3분 10초에서 2분 20초로 줄였다.
- **대안과 트레이드오프**: Kubernetes는 멀티 클러스터, 복잡한 라우팅, 다수 워크로드가 있을 때 검토하고, 그렇지 않으면 관리형 태스크 환경이 운영 부담이 낮다. Rolling은 자원 부담이 낮고 Blue/Green은 즉시 전환과 롤백에 유리하다.
- **한계와 꼬리**: 복제 지연을 숨기지 않는 것이 전제다. 자동 확장은 CPU만 보지 않고 큐 적체와 대기 시간도 본다. 컨테이너 종료 신호를 받으면 새 요청을 막고 진행 중 요청을 정리한다. 40%는 이력서 공개 수치이며 비교 조건을 설명할 수 있을 때만 말한다.

## R7. Grafana, Prometheus, Loki로 무엇을 관측했고 알림은 어떻게 정했나

- **유형과 의도**: 경험형. 관측 도구 이름보다 설계 원칙을 본다.
- **핵심 답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼다. 요청 지연은 histogram으로 봤다. 메트릭은 추세와 사용자 영향, 로그는 개별 원인, 트레이스는 서비스 경계를 넘는 흐름을 보는 조합이다.
- **흔한 오답**: userId나 requestId를 메트릭 라벨에 넣는 것. 시계열이 폭증해 저장소와 경보가 불안정해진다. 내가 실제로 겪은 실수이고, 그래서 라벨 설계 기준을 먼저 말한다.
- **알림**: 과거 숫자를 복사하지 않고 사용자 영향 SLI와 정상 구간을 관찰해 정한다. 내부 임계값은 말하지 않는다. API에는 RED, DB와 큐에는 USE 관점을 쓴다.
- **꼬리**: SaaS 관측 도구 대신 오픈소스를 고른 이유(보존, 운영 부담, 비용을 함께 비교). 장애가 나면 영향 공유, 복구 우선, 포스트모템 순서.

## R8. 팀 AI 협업 규약과 자동 검증 루프는 구체적으로 무엇인가

- **유형과 의도**: 경험형. AI 서비스 회사에서 도구 활용의 깊이와 검증 책임을 본다.
- **핵심 답변**: 경로별 지침 문서로 AI가 참고할 맥락과 건드리면 안 되는 영역을 나눴다. 공식 문서 조회, 역할별 검토, 변경 파일 검사를 거쳐 작업 종료 시점에 테스트와 점검이 자동으로 돌도록 구성했다. 처음에는 느려 보인다는 반응이 있을 수 있어 작은 영역부터 적용해 검토와 인수인계가 쉬워지는 결과를 보였다.
- **트레이드오프**: 규약이 늘면 문맥 비용과 유지 부담이 커진다. 반복되는 실수를 막는 규칙만 남기고 나머지는 지운다.
- **꼬리**: 도구 비교는 특정 제품의 우열보다 코드베이스, 검토 경로, 보안 경계에 맞는 흐름을 고른다고 답한다.

## R9. FIDO 서버를 개발하며 오픈소스 문제를 어떻게 발견했나

- **유형과 의도**: 경험형. 명세를 근거로 외부 라이브러리를 검증하는 태도를 본다.
- **핵심 답변**: WebAuthn 명세를 분석해 FIDO 아키텍처를 설계하고 인증을 통과했다. 사용하던 라이브러리의 동작이 명세와 다를 수 있다는 의견이 나와, 일정만 보고 넘어가지 않고 공식 명세와 재현 결과를 대조했다. 공개 이슈로 문제를 제기하고 팀과 안전한 방식을 골랐다.
- **꼬리**: 외부 라이브러리는 핵심 도메인 경계에서 직접 검증하고 대체와 기여 경로를 함께 검토한다. 누가 맞았는지보다 재현과 근거를 강조한다.
- **끝줄**: 외부 모델이나 번역 API를 쓰는 서비스에서도 결과를 경계에서 검증하는 습관이 필요하다고 본다.

## R10. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트)

- **유형과 의도**: 경험형. AI 서비스 회사에서 AI 도구 활용과 검색 품질을 근거로 비교해 본 경험이 있는지 본다.
- **핵심 답변**: 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템이다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했다. 검색은 MCP 도구와 CLI로 노출했다. 검색 방식을 바꾸기 전에 평가 질문부터 고정했다. 질문마다 반드시 돌려받아야 하는 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나와야 통과로 치고, 무관한 질문은 빈 결과여야 통과하는 음성 질문도 넣었다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데 BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어 채택하지 않았다. 그 74개를 포함한 94개 질문으로 bge 리랭커도 비교했지만 통과가 41개에서 40개로 개선이 없고 질문당 약 4.7초가 더 걸려 채택하지 않았다. 병목이 후보 검색보다 예산 안의 절 선택이라고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸다. 모두 기각한 판단이 강점이다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바꾸지 않고, 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다.
- **골든 케이스 선정과 지표**: 평가 질문은 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본이 아니다. 양성은 필수 근거 그룹이 응답 크기 예산 안에 모두 나오면 통과, 음성은 빈 결과여야 통과다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 쟀다.
- **이력서 정정**: 제출한 이력서의 골든 케이스 약 145건 문구는 부정확하다. 145건짜리 평가 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **한계를 먼저 말할 것**: 합성 표본이라 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- **꼬리**: 회사 업무가 아니라 개인 프로젝트인 이유와 범위.
- **이 회사 공고와의 연결**: 공고는 AI 활용 서비스의 백엔드를 주요 업무로 적는다. LLM 서비스 운영 경험은 없으므로 운영 경험처럼 말하지 않고, AI 도구를 실제 작업에 쓰고 검색 방식을 평가 질문으로 비교하고 개선 없는 방식을 기각한 근거로만 연결한다.
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 먼저 개인 프로젝트라고 밝힌다.
