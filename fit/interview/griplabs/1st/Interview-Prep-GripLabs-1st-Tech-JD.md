# 그립랩스 1차, JD 기반 기술 질문

> [[Interview-Prep-GripLabs-1st|1차 메인]]의 하위 문서다. 공고 자격 요건의 순서대로 뽑았다. 사실형은 결론, 동작, 적용 조건과 흔한 오답을, 설계형은 판단 기준, 대안과 꼬리를 준비한다. 마지막 줄에는 내 경험 한 장면을 붙인다.

## J1. TypeScript는 강타입 언어인가, Java나 Kotlin과 무엇이 다른가

- **의도**: 공고가 TypeScript, Java, Kotlin을 강타입 예시로 묶었다. 타입 시스템의 보장 범위를 정확히 아는지 본다.
- **핵심 답변**: TypeScript는 정적 타입 검사를 제공하지만 컴파일 뒤 타입 정보가 사라지므로 런타임 보장은 없다. 타입 호환은 이름이 아니라 구조로 판단하는 구조적 타이핑이다. Java와 Kotlin은 클래스 이름으로 호환을 판단하는 명목적 타이핑이고 객체의 런타임 타입이 남는다(제네릭 타입 인자는 Java도 소거된다). Kotlin은 nullable 타입을 컴파일 단계에서 구분한다.
- **흔한 오답**: TypeScript 타입이 런타임 입력까지 막아 준다고 말하는 것. 그래서 외부 입력은 DTO와 class-validator, zod 같은 런타임 검증으로 경계에서 확인한다.
- **꼬리**: `any`와 `unknown`(unknown은 좁히기 전 사용 불가), 타입 좁히기와 판별 유니언, `strict` 옵션 중 `strictNullChecks`의 효과. 구조적 타이핑 때문에 다른 도메인의 ID가 섞일 수 있어 브랜드 타입이나 값 객체를 쓴다.
- **내 경험**: NestJS 요청 DTO는 런타임 검증 파이프로 막고 내부 도메인은 타입으로 보호했다.

## J2. 레이어드 아키텍처가 왜 필요한가

- **의도**: 공고 원문이 왜 필요한지 이해하고 적용하는 사람을 요구한다. 계층 이름보다 변경 비용과 테스트 관점의 이유를 본다.
- **핵심 답변**: 표현, 애플리케이션, 도메인, 인프라처럼 책임을 나누면 한 종류의 변경(화면 계약, DB, 외부 API)이 다른 계층으로 번지지 않는다. 의존 방향을 한쪽으로 고정해 업무 규칙이 프레임워크와 저장소 구현에 끌려가지 않게 하고, 도메인 규칙을 DB 없이 테스트할 수 있게 한다. 트랜잭션 경계와 실행 흐름은 애플리케이션 서비스가 조정한다.
- **대안과 트레이드오프**: 단순 CRUD에서 계층마다 같은 데이터를 옮기기만 하면 코드만 늘고 가치가 없다. 헥사고날이나 클린 아키텍처는 의존성 역전을 더 강하게 적용한 변형이다. 실제로 교체되거나 독립적으로 바뀌는 경계에만 포트를 둔다.
- **꼬리**: 서비스가 비대해지면 UseCase 단위로 나눈다. 트랜잭션은 어느 계층에 두는가(애플리케이션 서비스). Repository가 도메인 엔티티 대신 ORM 모델을 반환하면 어떤 문제가 생기는가(인프라가 도메인으로 새어 들어온다).
- **내 경험**: 트라이포드랩 모듈 중심 설계 (이력서 질문 R5).

## J3. OOP의 역할, 책임, 협력과 메시지를 설명해 달라

- **의도**: 공고 괄호에 명시된 개념. 교과서 정의보다 설계에 쓰는지를 본다.
- **핵심 답변**: 객체는 자기가 아는 것과 하는 것이라는 책임을 가진다. 객체들은 메시지를 주고받으며 협력하고, 메시지를 받은 객체가 어떻게 처리할지 스스로 결정한다. 역할은 같은 메시지에 응답할 수 있는 객체들의 자리이며 인터페이스로 표현되고, 그래서 구현을 바꿔 끼울 수 있다(다형성).
- **예시**: 서비스가 재고 수량을 꺼내 계산하고 다시 넣는 대신 `stock.decrease(quantity)`를 호출하고, 재고 객체가 부족하면 `InsufficientStockError`를 던진다. 상태를 묻지 말고 시키라는 원칙이며, 불변조건을 그 상태를 가진 객체가 지킨다.
- **흔한 오답**: 상속, 캡슐화, 추상화, 다형성 네 단어만 나열하는 것. 데이터와 getter, setter만 있는 빈약한 도메인 모델을 객체지향이라고 부르는 것.
- **꼬리**: 상속보다 합성을 선호하는 이유(상위 클래스 변경이 하위로 전파된다). 같은 역할에 처리 방식이 여러 개면 전략 패턴으로 나눈다.

## J4. 테이블 설계와 JOIN, Subquery를 어떻게 쓰는가

- **의도**: 기본 SQL을 정확히 쓰는지, 흔한 함정을 아는지 본다.
- **핵심 답변**: 설계는 업무 규칙이 요구하는 무결성(PK, UNIQUE, 외래 키 여부)과 조회 패턴을 함께 보고 정규화한 뒤, 측정된 조회 병목이 있을 때만 비정규화한다. INNER JOIN은 양쪽에 모두 있는 행, LEFT JOIN은 왼쪽 행을 모두 유지한다. Subquery는 스칼라, FROM 절의 파생 테이블, 바깥 행에 의존하는 상관 서브쿼리로 나뉜다.
- **흔한 오답**: LEFT JOIN 뒤 오른쪽 테이블 조건을 WHERE에 두면 NULL 행이 걸러져 INNER JOIN처럼 동작한다. 오른쪽 조건은 ON에 둔다. `NOT IN (subquery)`는 서브쿼리 결과에 NULL이 하나라도 있으면 행을 반환하지 않으므로 `NOT EXISTS`를 쓴다.
- **꼬리**: JOIN과 Subquery 중 무엇이 빠른가(옵티마이저가 변환하기도 하므로 실행 계획으로 판단한다). 외래 키를 두지 않는 선택은 언제인가(외부 시스템 식별자나 대량 쓰기 경로, 대신 검증과 대사 경로를 둔다).
- **내 경험**: Prisma 관계 조회를 SubQuery 기반 단일 쿼리로 통합 (R4), MongoDB 영양정보를 MySQL로 정형화한 마이그레이션.

## J5. 실행 계획으로 인덱스와 쿼리를 튜닝한 과정을 설명해 달라

- **의도**: 공고 원문에 명시된 요건. 방법론이 DB 중립적인지 본다.
- **답변 골격**: 느린 쿼리를 특정한다(슬로우 로그, APM) → `EXPLAIN`으로 접근 방식과 추정 rows, `EXPLAIN ANALYZE`로 실제 rows와 loops를 비교한다 → 추정과 실제가 벌어지는 노드에서 통계나 조건식을 의심한다 → 동등 조건, 범위, 정렬 순서에 맞춘 복합 인덱스나 쿼리 재작성을 적용한다 → 같은 조건에서 전후를 측정하고 쓰기 비용을 확인한다.
- **MySQL 읽기**: `type`, `key`, `rows`, `filtered`, `Extra`. `Using filesort`는 추가 정렬이지 디스크 정렬이라는 뜻이 아니다. `Using index`는 커버링 접근이다.
- **PostgreSQL 읽기**: `cost`는 시간이 아니라 플래너의 임의 단위다. `EXPLAIN (ANALYZE, BUFFERS)`로 캐시 적중과 읽은 블록을 본다. `Index Cond`는 탐색 범위를 줄이고 `Filter`는 읽은 뒤 거른다. `Rows Removed by Filter`가 크면 인덱스 정의를 의심한다. `Index Only Scan`도 visibility map 상태에 따라 heap을 읽는다.
- **주의**: `EXPLAIN ANALYZE`는 실제로 실행하므로 운영에서는 replica나 제한된 환경에서 쓴다.
- **내 경험**: 복합 인덱스로 슬로우 쿼리 99.3% 개선 (R3).

## J6. HTTP와 RESTful API 설계 시 고려할 점

- **의도**: 기본기와 운영 관점을 함께 본다.
- **핵심 답변**: REST는 무상태, 캐시 가능, 균일한 인터페이스 같은 제약의 모음이다. 리소스 중심 URI와 메서드 의미를 지킨다. GET, HEAD는 안전하고, PUT, DELETE는 멱등이며, POST는 멱등을 보장하지 않으므로 결제나 투표처럼 중복이 위험한 요청에는 Idempotency Key를 설계한다. 상태 코드는 401(인증 필요)과 403(권한 없음), 409(상태 충돌), 422(검증 실패)를 구분하고, 에러 본문은 RFC 9457 Problem Details 같은 한 형식으로 통일한다.
- **대안과 트레이드오프**: offset 페이지네이션은 임의 페이지 이동이 쉽지만 깊은 페이지가 느리고 중간 삽입에 흔들린다. cursor는 성능과 일관성이 좋지만 정렬 키 제약이 있다. 뉴스 피드처럼 계속 쌓이는 목록은 cursor가 맞다.
- **꼬리**: PUT과 PATCH 구분, 버저닝 방식, HTTP/1.1 keep-alive와 HTTP/2 멀티플렉싱 차이, ETag와 조건부 요청.

## J7. 테스트 코드를 어떤 기준으로 작성하는가

- **의도**: 공고 필수 요건. 테스트 도구보다 무엇을 어느 수준에서 검증하는지 본다.
- **핵심 답변**: 도메인 규칙은 공개 동작을 기준으로 단위 테스트하고, private 메서드를 직접 테스트하지 않는다. NestJS에서는 `Test.createTestingModule`로 의존성을 `useValue` mock으로 바꿔 서비스 흐름을 검증한다. SQL, 트랜잭션, 제약 조건처럼 DB에 의존하는 경계는 Testcontainers로 운영과 같은 DB를 띄워 통합 테스트한다. HTTP 계약은 SuperTest로 E2E를 둔다.
- **흔한 오답**: SQLite in-memory로 MySQL이나 PostgreSQL을 대신하는 것(방언과 격리 수준이 다르다). 테스트마다 트랜잭션을 감싸고 롤백하는 방식이 서비스 계층의 커밋 시점과 전파를 가려 버리는 것.
- **꼬리**: 외부 API는 어디서 mock하는가(내 코드가 소유한 어댑터 경계에서). 커버리지 목표보다 회귀가 잦은 규칙과 실패 경로를 먼저 채운다. 기능은 스펙을 먼저 쓰고 테스트로 구현이 스펙을 만족하는지 확인한다.
- **내 경험**: Jest, Mocha, Chai, SuperTest, JUnit 5 사용, 부트캠프 팀 프로젝트에서 단위와 통합 테스트 작성을 주도.

## J8. Git 브랜치 전략은 무엇을 쓰고 어떻게 고르는가

- **의도**: 협업 습관과 배포 모델 이해를 본다.
- **핵심 답변**: 브랜치 전략은 릴리스 단위와 동시에 지원해야 하는 버전 수로 정한다. 지원 버전이 하나면 main 하나를 배포 가능하게 유지하는 GitHub Flow나 Trunk-Based가 단순하다. 여러 릴리스 계열을 동시에 유지하고 각각에 패치해야 하면 Git Flow처럼 release와 hotfix 브랜치가 필요하다.
- **트레이드오프**: 브랜치 수명이 길수록 머지가 크고 위험해진다. GitHub Flow는 PR 하나가 커밋 하나가 되는 squash와, Git Flow는 머지 흔적을 남기는 merge commit과 잘 맞는다.
- **꼬리**: hotfix는 어디서 출발해 어디로 전파하는가. 고객사마다 버전을 고정해야 하는 B2B라면 어떻게 바뀌는가(릴리스 계열 유지 비용과 기능 플래그를 비교한다).

## J9. 서버 장애 때 Linux에서 무엇부터 확인하는가

- **의도**: 기본 명령을 장애 확인 순서로 쓸 수 있는지 본다.
- **답변 골격**: 프로세스와 자원 확인(`ps`, `top`, `free -m`), 디스크(`df -h`, `du -sh`), 포트와 연결(`ss -tlnp`, `lsof -i`), 로그(`journalctl -u`, `tail -f`, `grep`), 외부 의존성 확인(`curl -v`), OOM 종료 흔적(`dmesg`). 권한 문제는 `ls -l`, `chmod`, `chown`.
- **꼬리**: 디스크가 가득 찼는데 파일을 지워도 공간이 안 돌아오면(열린 파일 핸들, `lsof`로 삭제된 파일을 잡은 프로세스 확인). 컨테이너 환경에서는 호스트 명령보다 태스크 로그와 메트릭을 먼저 본다.
- **내 경험**: Amazon Linux 2와 Ubuntu 운영, 42서울 Linux 과제, 리눅스마스터 2급.

## J10. MySQL과 PostgreSQL의 차이, PostgreSQL을 안 써 봤는데 괜찮은가

- **의도**: 공고가 두 DB를 함께 적었다. 갭을 정직하게 인정하고 전이 근거를 대는지 본다.
- **답변 골격**: PostgreSQL 실무 경험은 없다고 먼저 말한다. 이어서 차이를 설명한다. InnoDB는 PK 기준 클러스터드 인덱스에 행을 저장하고 이전 버전을 undo 로그로 관리한다. PostgreSQL은 heap 테이블에 새 버전 튜플을 쓰고 죽은 튜플을 VACUUM이 정리한다. 기본 격리 수준은 InnoDB가 REPEATABLE READ, PostgreSQL이 READ COMMITTED다. PostgreSQL은 JSONB와 GIN, 부분 인덱스, 표현식 인덱스 선택지가 풍부하다. upsert 문법도 `ON DUPLICATE KEY UPDATE`와 `ON CONFLICT`로 다르다.
- **전이 근거**: 실행 계획을 읽고 추정과 실제를 비교하는 방법론, 인덱스 설계 기준, 트랜잭션과 잠금 판단은 같다. 입사하면 현재 스키마의 실행 계획과 VACUUM, 통계 설정부터 확인하겠다.
- **꼬리**: 업데이트가 잦은 테이블에서 PostgreSQL의 bloat는 왜 생기는가. 같은 트랜잭션에서 읽은 뒤 쓰는 경로의 격리 수준 차이가 결과를 어떻게 바꾸는가.
