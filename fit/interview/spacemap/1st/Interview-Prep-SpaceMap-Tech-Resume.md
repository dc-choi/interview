## 1. DB Lock으로 동시 갱신 정합성 확보 — 데이터 수집 단계의 정합성

> 관련: [[Lock|DB Lock]], [[Transaction-Lock-Contention|트랜잭션, 락 경합]], [[Race-Condition-Patterns|레이스 컨디션 패턴]], [[Distributed-Lock|분산락]]

**답변 골격**
- 여러 요청이 같은 상태를 동시에 갱신하면 Lost Update가 생길 수 있다.
- 타임아웃, 재시도와 처리 주기는 서비스 요구와 실제 지연 분포를 기준으로 설계한다.
- 여러 행을 잠글 때는 일관된 순서로 획득한다. 잠금 대상과 독립적인 입력 검증과 외부 호출만 트랜잭션 밖에서 수행하고, 변경 가능한 상태의 불변식은 잠금을 얻은 뒤 다시 검증한다.

**스페이스맵 데이터 수집 맥락 연결**
- 여러 데이터 소스(관측소, 위성, 외부 API)가 같은 대상(특정 위성, 궤도 객체)의 상태를 동시에 보고하는 시나리오 = 동일한 동시 갱신 패턴
- 멱등성 키(객체 ID + 관측 시각)로 **중복 수집 차단**, Row Lock으로 최신 상태 갱신의 원자성 확보

**꼬리 질문 대비**
- "Optimistic vs Pessimistic?" → 수집 빈도가 높고 충돌이 잦으면 Pessimistic, 충돌이 드물면 version 컬럼 기반 Optimistic을 검토한다.
- "분산락은 왜 안 쓰나?" → 보호할 상태가 하나의 DB 트랜잭션 안에 있으면 DB Lock으로 충분할 수 있다. 여러 저장소나 외부 자원을 하나로 조정해야 할 때만 분산 조정을 검토한다.
- "`NOWAIT` vs `SKIP LOCKED`?" → 특정 레코드를 반드시 처리해야 하면 NOWAIT, 작업 큐처럼 아무거나 집어 분배하면 SKIP LOCKED

## 2. 복합 인덱스로 슬로우 쿼리 대폭 개선 — 대용량 시계열 데이터의 핵심

> 관련: [[Index|인덱스]], [[Covering-Index|커버링 인덱스]], [[Execution-Plan|실행계획]], [[B-Tree-Index-Depth|B-Tree 인덱스 깊이]], [[MySQL-Slow-Query-Diagnosis|슬로우 쿼리 진단]]

**경험 요약 (포트폴리오 STAR)**
- 최신 상태 조회의 실행계획에서 병목을 확인하고 equality 조건과 정렬 순서를 맞춘 복합 인덱스로 후보 범위를 줄였다. 구체적 데이터 규모와 지연 수치는 공개하지 않는다.
- `EXPLAIN ANALYZE`로 정렬과 후보 행 스캔을 확인해 병목 위치를 검증한다.
- 카디널리티 분석 → 복합 인덱스 `(entity_id, observed_at DESC, id DESC)`로 필터와 정렬을 함께 처리
- 당시 기록에는 조회에 포함된 서브쿼리, 단일 쿼리와 배치 전체처럼 서로 다른 측정 범위가 함께 있었다. 이를 같은 지표로 직접 비교하지 않는다.
- 실행계획과 지연을 전후 비교해 쿼리 전략을 조정했다. 실행 환경, 캐시 상태, 표본 수와 percentile이 남아 있지 않으므로 내부 전후 수치는 공개하지 않고, 데이터 분포가 바뀌면 같은 조건에서 다시 측정한다.

**스페이스맵 우주 데이터 맥락 연결**
- 우주 데이터에 시계열 이력이 쌓인다면, 특정 객체의 최신 상태나 기간별 상태 조회가 중요한 패턴이 될 수 있다. 실제 접근 패턴과 데이터 분포는 확인해야 한다.
- 핵심은 동등 조건을 앞에 둔 복합 인덱스로 특정 객체의 최신 1건 조회 범위를 좁히는 것. 데이터가 늘면 실제 실행계획과 지연 시간을 다시 측정해 인덱스, 파티션을 조정해야 함
- 시계열 특성상 파티셔닝([[MySQL-Partitioning]]), 커버링 인덱스도 함께 검토 가능

**꼬리 질문 대비**
- "복합 인덱스 컬럼 순서 기준?" → 실제 `WHERE`, `ORDER BY`, 선택도와 데이터 분포에서 시작한다. 동등 조건을 앞에 두고 범위 조건을 뒤에 두는 구성이 자주 유리하지만, 규칙으로 단정하지 않고 실행계획과 지연을 비교한다.
- "인덱스 많이 만들면?" → SELECT는 빨라지나 INSERT/UPDATE마다 인덱스 갱신 비용. 수집이 쓰기 중심이면 인덱스 개수 신중히
- "커버링 인덱스?" → 쿼리가 필요로 하는 컬럼을 인덱스에서 충족해 추가 테이블 또는 클러스터드 인덱스 조회를 줄이는 전략이다.

## 3. ORM 조회 전략 검증으로 API 응답 성능 개선 — ORM 한계 인식

> 관련: [[ORM-Impedance-Mismatch|ORM 임피던스 불일치]], [[ORM|ORM]], [[SQL-Joins|SQL 조인]], [[Execution-Plan|실행계획]]

**답변 골격**
- 관계 조회에서 응답 지연이 보이면 생성 SQL, 요청 추적과 실행계획으로 원인을 좁힌다.
- 당시 Prisma 버전과 설정에서는 `relationJoins` Preview 기능이 비활성이라 관계를 여러 쿼리로 읽고 애플리케이션에서 결합했다. 기능을 활성화한 뒤 `relationLoadStrategy: 'join'`을 적용했다.
- MySQL에서는 옵션 이름과 달리 correlated subquery와 JSON aggregation 형태의 SQL이 생성될 수 있으므로 공식 문서, 생성 SQL과 실행계획을 함께 확인한다. ([Prisma 관계 조회 공식 문서](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries))
- 조인 전략과 별도 조회 전략은 호출 수, 데이터베이스 부하와 결과 중복을 같은 조건에서 비교한다.

**스페이스맵 맥락 연결**
- 데이터 엔진은 ORM 추상화 뒤에서 실제로 어떤 쿼리가 나가는지가 성능을 좌우. ORM을 쓰되 **실행계획까지 검증**하는 습관
- "AI나 ORM에 의존하지 않고 공식 문서, 실행계획으로 검증" — 딥테크 환경에서 중요한 태도

**꼬리 질문 대비**
- "왜 Raw Query를 안 썼나?" → Raw Query는 마지막 수단. ORM 기능으로 해결되면 타입 안정성, 유지보수성 유지가 낫다고 판단. 실행계획상 우수함을 확인하고 결정
- "Prisma 말고 다른 ORM은?" → TypeORM, Kysely, Drizzle 등. 쿼리 빌더 성격이 강한 Kysely는 복잡 쿼리에 유리. 팀 표준, 타입 안정성 기준으로 선택

## 4. 이벤트와 큐 기반 처리 — 데이터 파이프라인 단계 분리

> 관련: [[EventBridge|EventBridge]], [[SQS|SQS]], [[Messaging-Patterns|메시징 패턴]], [[Delivery-Semantics|전달 보장]], [[Event-Driven-Patterns|이벤트 드리븐 패턴]], [[MQ-Kafka|MQ, Kafka]]

**답변 골격**
- 핵심 상태 변경과 독립적인 후속 작업을 분리하면 실패 격리와 재처리가 쉬워진다.
- 소비자는 안정적인 멱등성 키, 상태 전이와 DLQ로 중복 전달과 최종 실패를 다룬다.
- 관리형 큐와 브로커는 전달 보장, 순서, 리플레이 요구와 운영 부담을 기준으로 비교한다.
- 실시간 처리가 필수가 아니고 최종 일관성이 허용되는 후속 작업에는 관리형 큐가 적합할 수 있다.

**스페이스맵 데이터 파이프라인 맥락 연결**
- 데이터 수집, 처리 파이프라인 = 수집 → 검증 → 가공 → 저장 → API 노출의 단계 분리. 각 단계를 이벤트로 느슨하게 연결하면 단계별 독립 확장, 재처리 가능
- 수집은 빠르게 받아 큐에 적재, 무거운 연산(궤도 계산 등)은 워커에서 비동기 — backpressure 흡수

**꼬리 질문 대비**
- "언제 Kafka가 필요?" → 이벤트 리플레이, 키 또는 파티션 단위 순서, 지속적인 고처리량, 스트림 처리가 필요할 때 검토한다. 도메인 트래픽 특성과 복구 요구를 기준으로 결정한다.
- "메시지 유실은?" → 표준 큐의 at-least-once 전달을 전제로 소비자 멱등성과 상태 전이를 둔다. 서비스별 전달 보장과 중복 가능성은 계약을 확인한다.
- "순서가 중요하면?" → FIFO 큐의 메시지 그룹이나 파티션 기반 브로커를 검토하고, 실제 서비스 한도는 공식 문서에서 확인한다.

## 5. 서비스 확장과 배포 경로 분리 — 확장성

> 관련: [[ECS|ECS]], [[CDN|CDN]], [[Load-Balancer|로드 밸런서]], [[Scale-Up-vs-Out|스케일 업 vs 아웃]], [[Traffic-Scaling-Playbook|트래픽 스케일링]]

**답변 골격**
- 하나의 실행 환경에 서로 다른 요청 경로가 몰리면 포화와 배포 위험이 함께 전파될 수 있다.
- 정적 리소스, 요청 라우팅, 애플리케이션 실행과 데이터 읽기 경로를 필요에 따라 분리한다.
- 배포 전략과 오토스케일링은 롤백, 연결 유지, 포화 지표와 운영 가능성을 함께 고려한다.

**스페이스맵 맥락 연결**
- 데이터 엔진은 수집 부하와 조회 부하 성격이 다름 → 컴포넌트 분리, 독립 스케일링이 핵심
- 특수한 통신 요구를 가진 데이터 소스는 별도 경계와 장애 복구 기준을 두는 것이 안전하다.

**꼬리 질문 대비**
- "컨테이너 오케스트레이터 선택 기준은?" → 워크로드의 수, 트래픽 라우팅, 운영 인력, 장애 복구와 팀의 표준을 기준으로 비교한다.
- "오토스케일링 기준 지표?" → CPU, 메모리, 요청 포화와 큐 적체를 함께 보고 워커와 API의 기준을 분리한다.

## 6. 읽기 복제본으로 읽기 부하 분산 — 수집(쓰기), 조회(읽기) 분리

> 관련: [[Read-Replica-Routing|Read Replica 라우팅]], [[Replication|복제]], [[RDS-Aurora|RDS, Aurora]]

**답변 골격**
- 쓰기 중심 수집과 읽기 경로가 함께 있으면 읽기 부하 분리를 검토한다.
- 동시성 정합성이 중요한 로직은 정본에서 처리하고, 지연을 허용하는 조회만 복제본으로 라우팅한다.
- 복제 지연은 관측하고, 허용 범위를 넘으면 읽기 경로와 데이터 처리 방식을 재검토한다.

**스페이스맵 맥락 연결**
- 수집이 쓰기 중심이고 API 조회가 독립적으로 무거운 경우에는 Primary와 Replica의 읽기 경로 분리를 검토한다.
- Replication Lag을 어디까지 애플리케이션이 감내하고 어디부터 인프라로 처리할지 판단한 경험

**꼬리 질문 대비**
- "Replica에서 읽으면 stale data 문제는?" → 정합성이 중요한 읽기는 Primary, 통계, 대시보드성 읽기는 Replica. 라우팅 정책을 쿼리 성격별로 분리
- "Lag이 계속 커지면?" → Replica 스케일업, 쓰기 배치화, 읽기 캐시 계층 추가([[Cache-Strategies]])

## 7. 관측성 설계 — 데이터 엔진 안정성

> 관련: [[관측가능성(Observability)|관측 가능성]], [[Log-Pipeline|로그 파이프라인]], [[Structured-Logging|구조적 로깅]], [[Logs-vs-Metrics|로그 vs 메트릭]], [[Application-Performance-Monitoring|APM]]

**답변 골격**
- 로그, 메트릭과 트레이스를 같은 요청 문맥으로 연결하고, 고유 식별자는 라벨이 아닌 로그와 트레이스 연결에 사용한다.
- 경보는 사용자 영향 SLI와 정상 구간의 관측값을 바탕으로 정한다.
- 도구 선택은 탐색, 집계, 보존, 복원과 운영 부담을 비교해 결정한다.

**스페이스맵 맥락 연결**
- 데이터 엔진은 "조용히 틀리는" 게 가장 위험 — 수집 누락, 연산 지연, Lag을 메트릭으로 조기 탐지하는 체계가 필수
- 신뢰성이 중요한 도메인에서는 정합성, 감사 추적, 접근 통제, 복구 가능성을 요구사항으로 먼저 확인한다. 경보 기준은 사용자 영향 SLI와 정상 구간을 관측해 설계한다.

**꼬리 질문 대비**
- "관리형과 자체 운영 중 무엇을 고르나?" → 탐색과 경보 요구, 총소유비용, 이식성과 운영 인력을 비교한다.
- "트레이싱은?" → 수집→가공→저장 흐름의 지연과 실패를 추적해야 한다면 OpenTelemetry 기반 문맥 전파와 분산 트레이싱을 검토한다.
- "카디널리티 폭발은?" → userId, requestId 같은 고유 식별자는 라벨에서 제외하고 route를 정규화하며 불필요 필드를 제거한다.

## AI 도구 활용과 검증 책임

> 관련: [[Harness-Engineering|하니스 엔지니어링]], [[AI엔지니어링(AIEngineering)|AI 엔지니어링]]

**경험 요약**
- 저장소 영역별 지침으로 컨텍스트를 나누고, 공식 문서 조회, 목적별 검토 에이전트, 편집 뒤 lint와 typecheck, 작업 종료 시 자가 리뷰를 연결했다.
- AI 도구는 코드 생성 보조로 사용하되, 저장소 규칙, 테스트, 실행 결과와 코드 리뷰로 변경을 검증한다. 사람은 설계와 결과 채택의 책임을 가진다.
- 결과: 운영 경계와 배포 검증을 설계한 경험을 바탕으로, 권한과 데이터 이력을 다루는 개인 서비스도 검증했다.

**스페이스맵 맥락 연결**
- "강한 몰입, 업무 강도" 환경에서 *개인 생산성을 구조로 끌어올린* 사례 — 단순 야근이 아니라 파이프라인 설계로 처리량을 늘림
- 딥테크 스타트업에서 적은 인원으로 많은 걸 해내야 하는 상황과 직접 연결

**꼬리 질문 대비**
- "AI가 만든 코드 품질은?" → 편집 직후 정적 검사, 관련 테스트, 실제 실행 결과와 실행 계획을 확인하고 마지막에 독립 리뷰를 거친다. 도구의 제안을 채택할지는 사람이 결정한다.
- "면접 답변도 AI로 준비했나?" → 도구는 정리에 쓰되 판단, 근거는 내 것. (담백하게)
