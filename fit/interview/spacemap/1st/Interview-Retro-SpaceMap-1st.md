## 진행 흐름, 실제 받은 질문과 답변 요약

### 자기소개와 지원 동기

- 데이터 정합성, 이벤트 처리, 컨테이너 운영과 데이터베이스 성능 개선 경험을 소개하고, 우주 데이터라는 새로운 도메인에서 데이터와 백엔드 경험을 확장하고 싶다고 답했다.
- 근무 조건과 업무 수행 가능 범위를 확인하는 질문을 받았고, 당시 가능한 범위를 구분해 답했다. 개인 신상과 세부 일정은 공개 기록에 남기지 않는다.
- 해외 출장 경험과 외국어 소통 가능 범위도 확인받았다. 해외 출장은 경험이 없다고 답했고, 외국인 사용자의 기술 문제를 대응한 경험을 근거로 당시 가능한 소통 영역과 보완이 필요한 영역을 구분해 설명했다. 정확한 개인 상태와 세부 수준은 공개 승인 전 다시 적지 않는다.

### 데이터 처리와 데이터베이스

- **Q. 데이터 파이프라인 처리 경험이 있는가?** 전형적인 파이프라인 운영보다 데이터 정합성 경험에 가깝다고 정정하고, 동시 요청 충돌을 비관적 잠금으로 직렬화한 사례를 설명했다.
- **Q. 이벤트 스트리밍 대신 관리형 이벤트와 큐를 선택한 이유는 무엇인가?** 후속 작업을 분리하고 실패를 격리하려는 목적을 설명했다. 스트리밍 플랫폼을 실제 도입한 사례는 아니라고 바로잡았다. 비용과 트래픽은 무료 구간으로 단정하지 말고, 메시지량, 재시도, 폴링과 과금 가정을 분리해 말해야 한다.
- **Q. 서브쿼리와 관계 조회 성능 문제는 어떻게 풀었는가?** ORM의 관계 로딩 전략을 바꾸고 생성 SQL과 실행 계획을 확인해 병목을 개선한 경험으로 답했다.
- **Q. NoSQL 경험과 SQL, NoSQL 선택 기준은 무엇인가?** 문서형 모델과 관계형 모델의 접근 패턴, 스키마 변화와 정합성 요구를 비교하고, JSON 활용 뒤 필요한 곳을 정규화하는 접근을 설명했다.
- **Q. 정합성과 스키마 변화, 배치 작업은 어떻게 다루는가?** 데이터 모델링과 정규화, 관계형 데이터베이스를 우선하고, Airflow 운영 경험은 없다고 솔직히 말했다.

### 관측, 프레임워크와 아키텍처

- **Q. 모니터링을 어떻게 구성했고, 어떤 효과가 있었는가?** 상태를 여러 역할이 이해할 수 있게 만들고, 오류를 더 일찍 발견하는 관측 경험으로 답했다.
- **Q. 이전 역할과 이직 뒤 학습 선택은 무엇이었는가?** 사업 종료 경험을 외부 상황으로만 설명하지 않고, 재무와 사업 단계, 역할 범위를 미리 확인하는 기준을 배웠다고 답했다.
- **Q. NestJS의 장단점과 아키텍처 프레임워크의 가치는 무엇인가?** 구조와 소통 비용을 줄이는 장점, 생태계 제약과 상황별 선택 기준을 설명했다.
- **Q. 헥사고날 아키텍처를 실제로 구현했는가?** 이론적 이해는 있지만, 당시 외부 경계가 복잡하지 않아 전체 구조로 구현하지 않았다고 솔직히 답했다.
- **Q. 어떤 프레임워크를 선호하는가?** 배치와 웹 API의 요구, 팀의 운영 역량에 따라 고른다고 답했다.

### AI, 협업과 역질문

- **Q. 코딩을 좋아하는가, AI 도구를 어떻게 쓰는가?** 구현을 대체하는 도구보다 명세, 병렬 검토와 검증 흐름을 만드는 방식으로 사용한다고 답했다.
- **Q. 배경이 다른 리더와 충돌할 수 있지 않은가?** 세부 책임과 권한을 명확히 하고, 바텀업 제안과 지원을 결합하는 방식으로 답했다.
- 역할 경계, 데이터 파이프라인과 API의 연결, 관측성 개선 여지를 역질문했다. 면접에서 들은 시스템 구성과 조직 계획의 상세는 남기지 않는다.

## 질문별 당시 답변 상세와 현재 교정

### 데이터와 메시징

1. **데이터 파이프라인 경험의 의미**
   - 당시 답변: 전형적인 분석 파이프라인 운영보다 데이터 정합성 경험에 가깝다고 먼저 정정했다. 여러 요청이 같은 상태를 바꾸며 충돌하던 문제를 비관적 잠금으로 직렬화한 사례를 설명했다.
   - 현재 교정: 약점을 반복해서 강조하기보다 수집 입력의 검증, 동시성 정합성, 이벤트 기반 후속 처리와 조회 성능을 하나의 데이터 흐름으로 연결해 말한다.
2. **Kafka 대신 EventBridge와 SQS를 택한 이유**
   - 당시 답변: Kafka를 도입했다가 바꾼 것은 아니라고 바로잡고, 핵심 상태 변경과 후속 작업을 분리하려는 목적, 관리형 서비스의 운영 부담과 당시 트래픽을 비교했다고 답했다. 당시에는 비용이 무료 구간 안에 든다고 단정했다.
   - 현재 교정: 직접 운영한 것은 EventBridge와 SQS이며 전달은 at-least-once를 전제로 소비자 멱등성, 재시도, DLQ와 수동 복구 경계를 뒀다. 비용은 메시지 수만이 아니라 전송, 수신, 삭제, 재시도, 폴링과 리전별 과금을 계산해야 하므로 무료라고 단정하지 않는다.
3. **관계 조회와 서브쿼리 성능 문제**
   - 당시 답변: 당시 구성에서는 `relationJoins` Preview 기능이 비활성이라 관계를 여러 쿼리로 읽고 애플리케이션에서 합쳤다. 기능을 활성화한 뒤 `relationLoadStrategy: 'join'`을 적용하고 생성 SQL과 실행 계획을 확인했다고 설명했다.
   - 현재 교정: 옵션 이름만으로 SQL `JOIN`이라고 단정하지 않는다. MySQL의 correlated subquery와 JSON 집계 형태, 결과 행 중복, 실제 실행 계획과 지연을 같은 조건에서 비교했다고 설명한다.
4. **NoSQL 경험과 SQL, NoSQL 선택 기준**
   - 당시 답변: MongoDB 경험은 관계형 데이터베이스보다 얕다고 인정했다. 스키마 변화가 잦으면 문서형, 정형 관계와 정합성이 중요하면 관계형을 우선하고, JSON 컬럼으로 시작한 뒤 필요할 때 정규화할 수 있다고 답했다.
   - 현재 교정: 스키마 변경 빈도 하나로 결정하지 않고 접근 패턴, 트랜잭션 경계, 관계 조회, 마이그레이션과 운영 역량을 함께 비교한다.
5. **정합성, 타입 변화와 배치 처리**
   - 당시 답변: 데이터 모델링과 정규화를 우선한다고 답했고, Airflow 운영 경험은 없으며 재시작 가능한 배치 처리의 일반 원칙만 알고 있다고 구분했다.
   - 현재 교정: 미경험 도구를 숨기지 않되 DAG 의존성, 재시도, backfill과 멱등성 같은 학습 항목을 구체적으로 제시한다.

### 운영, 프레임워크와 학습

6. **모니터링을 어떻게 구성했고 어떤 효과가 있었는가**
   - 당시 답변: 컨테이너, 로드 밸런서와 데이터베이스의 메트릭을 로그, 대시보드와 알림에 연결했다고 설명했다. 초기의 단일 로그 수집 경로가 서버 증가를 따라가지 못해 컨테이너 로그 라우팅 방식으로 바꾼 과정도 말했다. 사업 효과를 묻는 후속 질문에는 자동화된 업무 흐름의 장애를 조기에 찾는 가치로 연결했다.
   - 현재 교정: 비공개 고객명과 내부 수치는 빼고, 사용자 영향, 탐지 시간, 복구 행동과 재발 방지라는 인과 관계로 설명한다.
7. **이전 역할과 교육을 다시 선택한 이유**
   - 당시 답변: 사업 종료로 역할을 마친 사실과 이후 학습 과정을 그대로 말했다. 재무와 사업 모델도 확인하는 개발자가 돼야 한다는 배움을 덧붙였지만 외부 귀책이 앞에 나왔다.
   - 현재 교정: 종료 사실은 짧게 두고, 이후 회사 단계, 역할 범위와 운영 책임을 확인하는 선택 기준을 만들었다는 변화로 닫는다.
8. **NestJS와 아키텍처 프레임워크의 장단점**
   - 당시 답변: 모듈 구조와 의존성 주입이 공통 언어를 만들어 소통 비용을 줄이고 비즈니스 규칙에 집중하게 한다고 답했다. 반면 더 큰 생태계와 비교하면 선택지가 적을 수 있다고 말했다.
   - 현재 교정: 생태계 크기를 절대 평가하지 않고 팀의 숙련도, 라이브러리 성숙도, 배포와 운영 요구를 기준으로 선택한다.
9. **헥사고날 아키텍처를 실제로 구현했는가**
   - 당시 답변: 이론은 알지만 전체 구조로 구현하지 않았고, 당시에는 외부 경계가 복잡하지 않아 유스케이스 분리만 적용했다고 솔직히 답했다.
   - 현재 교정: 포트와 어댑터 수, 변경 빈도와 테스트 대역의 가치가 분리 비용을 넘을 때 도입한다는 기준까지 붙인다.
10. **선호 프레임워크와 새 도구 선택**
    - 당시 답변: 대용량 배치는 Spring Batch, 웹 API와 간단한 작업 큐는 NestJS 생태계 같은 선택지를 상황에 따라 검토한다고 답했다.
    - 현재 교정: 특정 프레임워크를 정답으로 두지 않고 처리량, 재시작, 상태 관리, 팀 운영 역량과 실패 복구 요구를 먼저 확인한다.

### 일하는 방식과 역질문

11. **코딩과 AI 도구 사용 방식**
    - 당시 답변: 코딩을 좋아하지만 AI 도구 이후에는 손으로 모든 코드를 쓰기보다 명세를 만들고 여러 작업을 병렬화한 뒤 다른 도구로 검증하는 흐름을 쓴다고 답했다.
    - 현재 교정: AI 사용 자체보다 저장소 규칙, 테스트, 실행 결과와 사람의 리뷰로 결과를 채택하는 책임을 강조한다.
12. **배경이 다른 기술 리더와의 협업**
    - 당시 답변: 세부 구현은 담당자가 주도하고 리더는 인프라와 조사에서 지원하는 식으로 권한과 책임을 나누면 시너지가 난다고 답했다.
    - 현재 교정: 이 답변은 당시 재직 환경의 협업 방식에 관한 것이며, 지원 회사 조직에 대한 사실로 해석하지 않는다. 나이나 배경을 갈등 원인으로 전제하지 않고 의사결정 권한, 검증 기준과 에스컬레이션 경로를 먼저 합의한다고 말한다.
13. **근무 조건과 시작 가능 시점**
    - 당시 답변: 가능한 업무 범위를 사실대로 답했고, 입사 전 인수인계가 필요하다고 말했다. 개인 상태와 정확한 기간은 공개 기록에서 제외한다.
14. **본인의 역질문**
    - 당시에는 역할의 경계, 데이터 처리와 API 개발이 만나는 지점, 관측성을 어떻게 개선할 수 있는지를 깊게 물었다. 답변으로 들은 내부 시스템, 인력과 조직 계획은 보존하지 않는다.
    - 배움: 공개 자료로 확인 가능한 제품 문제와 내가 맡게 될 책임, 첫 기간의 성공 기준을 중심으로 질문하고 내부 구현을 공개 기록으로 옮기지 않는다.

## 잘 작동한 답변

1. 데이터 파이프라인 경험이 아니라 정합성 경험이라는 솔직한 정정.
2. 이벤트 처리의 목적과 선택 제약을 설명한 점.
3. ORM을 유지하면서 실행 계획으로 검증한 성능 개선 경험.
4. Airflow와 전체 헥사고날 구조의 미경험 범위를 숨기지 않은 점.
5. AI 도구를 명세와 검증 중심의 작업 흐름으로 설명한 점.
6. 서로 다른 배경의 동료와 권한과 책임을 나누는 협업 방식, 아키텍처와 관측성에 관한 역질문.

## 보완할 점

1. 데이터 파이프라인 경험 부족을 반복하지 말고, 정합성, 이벤트, 성능 경험이 데이터 엔지니어링의 토대라는 연결을 먼저 제시한다.
2. 지원 도메인의 공개 개념과 내 경험의 연결을 자기소개에서 먼저 말한다.
3. 이직 사유는 사업 종료보다 내가 바꾼 판단 기준과 다음 역할 조건으로 닫는다.
4. 처우나 고용 조건은 개인 금액을 기록하지 않고, 역할 범위와 서면 조건을 확인한다.

## 마스터 역반영 체크리스트

- [ ] 이직 사유를 [[My-Motivation-Reasons]]의 자기 책임과 학습 프레임으로 정리한다.
- [ ] 근거 있는 확장 임계와 관측성 답변을 [[My-Tech-Cards-Ops]]에 보강한다.
- [ ] 정합성, 이벤트, 성능을 데이터 처리 경험으로 연결하는 답변을 [[My-Tech-Cards-Data]]에 보강한다.
- [ ] 데이터 파이프라인의 핵심 개념과 미경험 영역의 학습 계획을 준비 문서에 보강한다.

## 후속 전형을 가정한 당시 준비와 종료 판단

- 데이터 도메인에서 실제로 다룰 수 있는 문제를 공개 자료로 확인하고, 정합성, 이벤트, 성능 경험과 연결한다.
- 미경험 도구는 숨기지 않고, 첫 기간에 학습하고 검증할 계획을 제시한다.
- 역할 범위, 고용 형태와 전환 기준은 추측하지 않고 공식 안내나 서면 조건으로 확인한다.
- 당시에는 받은 질문을 실행 역량과 설계 판단을 함께 보는 신호로 해석했고, 2차에서도 역할의 책임과 성장 환경을 직접 확인하기로 했다.
- 도메인 자체는 매력적으로 느꼈지만, 역할의 확장 가능성과 고용 조건은 다음 단계에서 확인할 핵심 변수라고 판단했다.
- 후속 일정 안내 뒤 별도 연락을 받지 못해 2026-06-09 탈락으로 정리했다. 공식 평가 사유는 확인되지 않았다.
