## 1. JD 분석

### 회사 개요

| 항목 | 내용 |
|------|------|
| 회사명 | 스페이스맵 (SpaceMap) |
| 서비스 | 공개 JD에서 우주 데이터 기반 웹 애플리케이션과 교육용 소프트웨어를 확인할 수 있다. 구체적인 데이터 종류와 계산 기능은 미확인이다. |
| 공개 이력 | 당시 공개 자료에서 미 우주군과 우주청 과제 수행, 방산혁신기업 100 선정 이력을 확인했다. 투자 단계, 실제 고객과 계약 형태는 미확인이다. |
| 공개 정보 | 공식 자료에서 확인되는 제품 문제와 역할의 책임 범위만 사용한다. |
| 규모 | 미공개 (역질문으로 백엔드 팀 규모 확인) |
| 도메인 | 우주 산업과 교육. 고객군과 계약 형태는 미확인이다. |
| BM | 공개 근거만으로 수익 모델을 단정하지 않고 고객, 과금 단위와 프로젝트성 매출 비중을 확인 질문으로 둔다. |

### 포지션 정보

| 항목 | 내용 |
|------|------|
| 포지션 | 백엔드 개발자 |
| 경력 요건 | 당시 공개 JD는 5년 이상이었다. 나는 4년차로 약 1년의 갭이 있어, 근속 기간 대신 해결한 문제와 검증 방식을 설명한다. |
| 주요 업무 | 우주, 교육용 SW 개발 / 데이터 수집, 처리 파이프라인 및 API 서버 / 웹 백엔드, 데이터 엔진 / 기존 서비스 유지보수 + 신규 개발 |
| 진행 방식 | 2026-05-22 1차 직무 대면 면접. 이후 전형은 현장에서 확인한다. |
| 근무 환경 | "강한 몰입과 업무 강도를 요구하는 환경", 책임, 권한 명확, 성과 기반 보상 |

### 핵심 키워드 (면접에서 반복 등장할 것)

- **데이터 수집, 처리 파이프라인** — JD 주요 업무 첫 줄. 가장 중요한 축
- **데이터 엔진** — 우주 데이터를 가공, 연산하는 백엔드 핵심
- **우주 데이터** — 데이터 형식, 규모, 갱신 주기와 지연 허용 범위를 먼저 확인한 뒤 수집, 정합성, 처리와 조회 원칙을 연결
- **API 서버** — 데이터 엔진 결과를 웹/외부에 노출
- **강한 몰입, 업무 강도** — 컬처핏에서 솔직하게 다룰 것

### 자격요건 vs 내 경험 매칭

| 자격요건 | 매칭도 | 내 근거 |
|---------|--------|--------|
| 이공계 학사 이상 | **중** | 고려사이버대 정보관리보안학과 학사 — 이공계 충족. 42Seoul, 멋사 이수로 CS 기반 보강 |
| JavaScript, TypeScript, NestJS | **강** | NestJS 기반 백엔드에서 모듈 경계, 의존성 주입, 요청 검증과 운영 흐름을 다뤘다. 이전 회사의 정확한 구조와 수치는 공개하지 않는다. |
| Python, FastAPI | **약** | 직접 경험 없음 — **갭**. NestJS의 데코레이터, DI 모델 깊이가 FastAPI 전이의 토대 (→ Tech-JD 문서) |
| Apache Airflow 데이터 파이프라인 | **약~중** | Airflow 직접 경험 없음 — **갭**. 다만 스케줄, 재시도, 실패 복구와 멱등성의 일반 원칙을 적용한 경험이 있어 DAG와 운영 모델을 학습해 연결할 수 있음 |
| RDB (PostgreSQL, MySQL) 운용 | **중~강** | MySQL 깊음 — InnoDB, 복합 인덱스, 격리수준, Read Replica 실무. PostgreSQL 직접 경험 없음 → MVCC, 인덱스 차이 학습 필요 |
| NoSQL (MongoDB, Redis) 운용 | **중~강** | 문서형과 관계형 데이터 모델의 선택 기준을 이해하고, Redis의 캐시와 동시성 제어 특성을 설명할 수 있음 |
| 관련 경험 | 트랜잭션, 비동기 처리, 조회 성능, 관측성을 문제와 검증 방식으로 연결한다. |
| 해외여행 결격사유 없음 | **강** | 결격사유 없음. 방산 과제 = 보안 적격 심사 가능성 인지 |

|---------|--------|--------|

| 웹 기반 백엔드 + 데이터 엔진 | **강** | NestJS API 서버 + 대용량 데이터 처리, 인덱스 최적화 |

| 기존 서비스 유지보수 + 신규 개발 | **강** | 기존 구조를 안전하게 개선하면서 새 기능을 추가할 때 변경 영향과 검증 경계를 관리한 경험 |

## 2. 회사 맞춤 FIT 답변

### 1분 자기소개
> 구조: 이름/역할 → 도메인 경험 → 핵심 성과 → 핵심 철학 → 왜 스페이스맵 → 마무리

안녕하세요, 데이터 흐름과 사용자 결과를 안정적으로 연결하는 백엔드 개발자 [이름]입니다.

이전 서비스에서 데이터 수집, 처리와 API 노출 파이프라인을 설계하고 운영했습니다. 동시성 정합성은 DB Lock으로 확보하고, 이벤트 기반으로 후속 처리를 분리했으며, 최신 상태 조회는 실행계획을 검증해 최적화했습니다. 내부 데이터 규모와 전후 성능 수치는 공개하지 않습니다.

저는 **데이터 규모가 커져도 깨지지 않는 구조**를 만드는 데 강점이 있습니다. 수집, 정합성, 성능 문제를 다룬 경험을 시계열 데이터 파이프라인에 연결할 수 있으며, 연차보다 문제의 깊이와 범위로 기여하겠습니다.

### 지원 동기
> 구조: 회사의 문제 → 내 경험 → 연결점 → 기여하고 싶은 것

- **회사의 문제**: 공개된 제품 설명에서 확인되는 데이터 수집, 처리, 결과 제공의 신뢰성 요구를 기술적으로 해석한다. 확인되지 않은 고객과 계약 사실은 추정하지 않는다.
- **내 연결점**: 동시 상태 갱신에서 정합성을 확인하고, 최신 상태 조회를 실행계획 기반으로 최적화하며, 후속 처리를 이벤트로 분리한 경험을 연결한다.
- **기여하고 싶은 것**: 데이터 수집, 처리 파이프라인이 데이터 규모 증가에도 안정적으로 돌아가도록 만드는 일. JD의 "데이터 수집, 처리 파이프라인 및 API 서버"가 제 경험의 정중앙에 있음.

### 이직 사유
> 구조: 충분히 성장한 점 → 한계(자기 기준) → 다음 도전 → 스페이스맵에서만 가능한 이유
> **외부 귀책 금지** — 회사 탓 아닌 자기 성장 기준으로

- 동시성, 비동기 처리, 조회 성능과 관측성을 문제와 검증 기준으로 설명한다.
- 다음 단계에서는 **데이터 자체가 어렵고 깊은 도메인** — 연산, 정합성, 규모가 본질인 영역에서 성장하고 싶다.
- 스페이스맵의 우주 데이터는 그 자체로 난이도가 높은 데이터(궤도 역학, 시계열, 대용량). 제가 쌓은 데이터 파이프라인, 성능 최적화 역량을 *더 어려운 데이터*에 적용하며 한 단계 깊어질 수 있는 환경.
- 꼬리 대비:
  - "우주 도메인 지식이 없는데?" → 도메인 지식은 학습 대상이고, 데이터 파이프라인 설계 역량은 전이 자산이다. 새 언어, 프레임워크와 데이터 모델을 학습해 적용한 방식으로 적응 계획을 설명한다.
  - "역할의 기대를 어떻게 충족할 수 있나요?" → 해결한 문제, 선택 기준, 검증 방식을 연결해 답한다.
  - "지금 회사 더 다니지?" → 성장 곡선의 다음 변곡점이 *데이터 난이도가 높은 도메인*이라 판단. 회사에 대한 불만이 아니라 내 커리어 설계상의 선택.
