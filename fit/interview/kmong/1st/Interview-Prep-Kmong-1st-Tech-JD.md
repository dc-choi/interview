# 크몽 1차, JD 기반 기술 질문 8개

> [[Interview-Prep-Kmong-1st|목차]]. 공고의 주요업무와 소개문에서 뽑았다. 크몽의 실제 구현은 모르므로 답변은 가정을 먼저 밝히고 판단 기준으로 말한다. Kotlin과 Spring 사실은 2026-09-29 Spring Framework 공식 문서와 대조했다.

## J1. PHP 서비스를 Kotlin 마이크로서비스로 무중단 전환한다면 (설계형)

- **의도**: 도메인 경계, 데이터 이관, 전환 순서, 롤백을 한 흐름으로 설계하는지 본다.
- **확인할 전제**: 어느 도메인이 PHP에 남아 있는지, 레거시 DB를 공유하는지, 쓰기 경로가 몇 개인지, 중단 허용치.
- **골격**:
  1. 도메인 경계를 먼저 정한다. 어떤 데이터의 쓰기 소유권을 새 서비스가 가질지 정하고, 레거시와 새 서비스가 같은 테이블에 동시에 쓰는 구간을 최소화한다.
  2. 요청 앞단(게이트웨이나 파사드)을 seam으로 두고 기능 단위로 트래픽을 옮기는 Strangler Fig를 기본으로 한다.
  3. 데이터는 새 스키마로 백필한 뒤 변경분을 CDC나 outbox로 따라잡는다. 애플리케이션 이중 쓰기는 한쪽만 성공하는 불일치가 생기므로 피한다.
  4. 건수, 체크섬, 샘플 비교로 대사하고, 필요하면 같은 요청을 두 경로에 보내 결과를 비교하되 외부 부수효과(결제, 알림)는 새 경로에서 막는다.
  5. 읽기를 먼저 옮기고 쓰기를 마지막에 옮긴다. 라우팅 한 지점에서 전환하면 두 경로가 동시에 처리하는 중첩 구간을 줄일 수 있다.
  6. 제거 조건은 날짜가 아니라 레거시 입구로 들어오는 쓰기 0건을 관측으로 확인하는 것이다. 드물게 도는 배치까지 포함한다.
- **트레이드오프**: 점진 전환은 한 번의 위험을 낮추지만 공존 기간의 운영 비용과 중간 상태의 영구화 위험이 있다.
- **내 경험 연결**: JSP에서 Spring으로의 이전, MongoDB에서 MySQL로의 이관, 인프라 전환. MSA 분리 자체는 해 보지 않았다고 먼저 말한다.
- **꼬리**: 전환 도중 롤백하면 새 서비스에만 쓰인 데이터는? 역방향 동기화나 쓰기 전환 전까지 레거시를 정본으로 두는 선택. 레거시 코드에 사양이 없다면? 실행 로그와 현재 동작에서 사양을 복원하고, 버그가 사양이 된 동작은 유지와 수정 중 하나를 팀과 명시적으로 고른다.
- **학습 정본**: [[Legacy-Modernization-Strategies]], [[Transactional-Outbox]], [[CDC&Outbox]]

## J2. 같은 요청이 두 번 들어오면 무엇을 기준으로 판단하나 (설계형)

- **의도**: 공고 소개문의 질문 그대로다. 멱등성을 어디서, 무엇으로 보장하는지 본다.
- **골격**: 클라이언트가 보낸 멱등성 키 또는 업무 키(주문 ID와 동작)로 요청을 식별한다 → DB 유일 제약으로 첫 요청만 성공시키고, 이후 같은 키는 저장된 첫 결과를 반환한다 → 처리 중 상태를 두어 동시에 도착한 두 요청 중 하나만 진행한다 → 같은 키에 다른 본문이 오면 오류로 거절한다 → 키 보관 기간을 정한다.
- **경계**: 메시지 소비도 같은 원칙이다. at-least-once 전달에서는 중복이 정상 경로이므로 소비자 쪽에서 처리 이력과 상태 전이 검증으로 거른다. 외부 결제처럼 DB 밖 호출은 같은 트랜잭션으로 되돌릴 수 없으므로 외부에 같은 멱등성 키를 전달하고, 지원하지 않으면 상태 조회와 대사로 닫는다.
- **흔한 오답**: 중복 체크 SELECT 뒤 INSERT(동시 요청이 둘 다 통과한다). Redis 키 하나로 충분하다(DB 결과와 원자적으로 묶이지 않는다).
- **내 경험 연결**: 발주 소비자의 멱등성 키와 상태 전이 검증.
- **학습 정본**: [[Idempotency-Key]], [[Idempotent-Consumer]], [[Delivery-Semantics]]

## J3. 주문과 결제가 다른 서비스일 때 상태는 누가 들고 있어야 하나 (설계형)

- **골격**: 각 상태의 정본 소유자를 하나로 정한다(결제 결과는 결제 서비스, 주문 진행 상태는 주문 서비스) → 다른 서비스는 이벤트로 받은 사본을 쓰고 직접 쓰지 않는다 → 여러 서비스에 걸친 흐름은 분산 트랜잭션 대신 Saga로 단계와 보상을 정의한다 → 결제 성공 뒤 주문 반영 실패처럼 한쪽만 된 상태를 탐지하는 대사 작업을 둔다.
- **판단 기준**: 즉시 확정 결과가 필요한가, 접수 상태로 응답해도 되는가. 보상이 가능한가(환불은 되돌리기가 아니라 새 거래다).
- **트레이드오프**: 오케스트레이션은 흐름이 한곳에 보이지만 조정자가 중심이 되고, 코레오그래피는 결합이 낮지만 흐름 추적이 어렵다.
- **꼬리**: 이벤트 순서가 뒤바뀌어 도착하면? 상태 전이 규칙과 버전으로 늦게 온 이벤트를 무시하거나 보류한다.
- **학습 정본**: [[Saga-Pattern]], [[Monolith-vs-Microservice]]

## J4. Kafka 기반 이벤트 파이프라인의 전달 보장과 순서 (사실형)

- **핵심 답변**: Kafka는 파티션 안에서만 순서를 보장한다. 같은 업무 키를 같은 파티션 키로 보내야 그 키의 순서가 유지된다. 컨슈머는 처리 후 오프셋을 커밋하면 at-least-once가 되고, 커밋 전에 죽으면 재처리되므로 멱등 소비가 필요하다. 프로듀서 멱등성은 재시도로 인한 파티션 내 중복 기록을 막지만 소비자의 중복 처리까지 막지는 않는다.
- **조건 표기**: 프로듀서 멱등성 기본값과 트랜잭션 지원 범위는 클라이언트와 브로커 버전에 따라 다르다. 운영 클러스터 설정으로 확인한다.
- **흔한 오답**: 토픽 전체 순서가 보장된다. exactly-once 설정이면 외부 DB 쓰기까지 한 번만 된다.
- **꼬리**: 처리 실패 메시지를 재시도 토픽과 DLQ로 나누는 기준, 파티션 수를 늘리면 키 매핑이 바뀌어 순서가 깨질 수 있는 점, 컨슈머 지연(lag) 모니터링.
- **내 경험 연결**: 운영 경험은 없다고 먼저 말하고, SQS에서 적용한 멱등 소비와 DLQ가 같은 문제의 다른 구현이라고 설명한다.
- **학습 정본**: [[MQ-Kafka]], [[Messaging-Broker-Comparison]]

## J5. Kotlin으로 Spring을 쓸 때 주의할 점, 그리고 첫 달 학습 계획 (사실형)

- **핵심 답변**: Kotlin 클래스와 멤버는 기본이 final이라 CGLIB 프록시가 필요한 Spring 빈에서 문제가 된다. `kotlin-spring` 플러그인(all-open)이 `@Component`, `@Async`, `@Transactional`, `@Cacheable`와 이를 메타 어노테이션으로 가진 타입을 자동으로 open한다. JPA는 기본 생성자가 필요해 `kotlin-jpa`(no-arg) 플러그인이 JPA 어노테이션 클래스에 합성 생성자를 만든다.
- **조건 표기**: 엔티티의 지연 로딩 프록시도 상속이 필요하므로 엔티티를 open으로 두는 설정을 따로 확인한다. data class 엔티티는 equals와 hashCode가 연관 필드와 프록시에 얽힐 수 있어 팀 규칙을 먼저 확인한다. 이 두 항목은 Hibernate 공식 문서로 재확인할 항목이다.
- **흔한 오답**: `@Transactional`이 붙은 같은 클래스 안 메서드를 `this`로 호출해도 트랜잭션이 적용된다(프록시를 통과하지 않아 적용되지 않는다).
- **학습 계획**: 1주차 팀 코드의 트랜잭션 경계와 예외 규칙 읽기, 2주차 작은 버그 수정으로 빌드, 테스트, 배포 경로 익히기, 3~4주차 도메인 하나의 조회 경로를 생성 SQL과 실행 계획까지 따라가기. 코루틴은 팀 사용 여부를 확인하고 필요할 때 익힌다.
- **출처**: [Spring Framework, Spring Projects in Kotlin](https://docs.spring.io/spring-framework/reference/languages/kotlin/spring-projects-in.html), [[Spring-Transactional]]

## J6. 대용량 데이터 배치를 설계한다면 (설계형)

- **골격**: 처리 단위(chunk)와 커밋 간격을 정한다 → 조회는 OFFSET 대신 키 기반 커서나 마지막 키 이후 조회로 깊은 페이지 비용을 피한다 → 쓰기는 멱등하게 만들어 재시작해도 결과가 같게 한다 → 실패 지점부터 재시작할 수 있도록 진행 상태를 저장한다 → 운영 DB 부하를 피하도록 처리 속도를 제한하고 필요하면 복제본에서 읽는다(복제 지연 허용 여부 확인).
- **Spring Batch 대응**: Job, Step, chunk 지향 처리와 JobRepository의 실행 이력이 재시작 기반이다. 이력서에 표기했지만 실무 운영 깊이는 제한적이라고 구분해 말한다.
- **트레이드오프**: 큰 chunk는 처리량이 늘지만 잠금 시간과 실패 시 재처리량이 커진다.
- **내 경험 연결**: 환율 정보 배치와 IoT 상태 집계 리포트. 배치 실패가 쌓였을 때 자동 검증과 배포 전 검사를 추가한 경험([[My-FIT-Answers]] 12번).
- **꼬리**: 배치와 API가 같은 행을 갱신하면 잠금 경합을 어떻게 피하나.

## J7. MySQL 스키마 설계와 대형 테이블 변경 (사실형)

- **핵심 답변**: 인덱스는 실제 쿼리의 동등 조건, 범위 조건, 정렬 순서로 설계하고 실행 계획의 type, rows, Extra(filesort, temporary)를 본다. 대형 테이블 변경은 호환 컬럼 추가, 배치 백필과 검증, 읽기 전환, 구 컬럼 제거의 expand-and-contract 순서로 하고 잠금과 복제 지연을 관측한다.
- **조건 표기**: 온라인 DDL 지원 범위와 잠금 수준은 MySQL 버전과 변경 종류에 따라 다르다. 적용 전 해당 버전 문서와 스테이징에서 확인한다.
- **흔한 오답**: 카디널리티가 높은 컬럼을 항상 맨 앞에 둔다.
- **학습 정본**: [[Schema-Migration-Large-Table]], [[Execution-Plan]]

## J8. 에이전트가 만든 결과를 어디까지 믿고, 어떻게 검증하고 되돌리나 (설계형)

- **의도**: 공고의 검증, 롤백, 모니터링 설계 요구에 대한 구조적 답을 본다.
- **골격**:
  1. 위임 범위를 작업 유형으로 나눈다. 기계적 변환과 반복 구현은 위임, 도메인 경계와 데이터 삭제는 사람 결정.
  2. 입력 명세를 skill로 고정하고, 완료 조건을 테스트, 타입 검사, 린트, 계약 테스트 같은 자동 게이트로 정의한다.
  3. 변경 범위를 좁혀 리뷰와 되돌리기 단위를 작게 만든다. 금지 영역은 문서가 아니라 Hook과 검사로 막는다.
  4. 운영 반영은 기능 플래그나 점진 배포로 하고, 오류율과 지연을 관측해 이상 시 되돌린다.
  5. 에이전트가 반복해서 틀린 유형은 skill과 규칙에 되먹임한다. 모델이 바뀌면 같은 평가 작업으로 다시 확인한다.
- **내 경험 연결**: 팀 AI 협업 규약의 영역 명문화와 종료 시 자기 검증 루프. 운영 모니터링까지 이은 경험은 제한적이라고 구분한다.
- **꼬리**: 마이그레이션 코드를 대량으로 에이전트가 만들면 무엇으로 동등성을 검증하나(기존 테스트와 입출력 비교, 샘플 대사).
