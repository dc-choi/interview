# 크몽 1차, 이력서 기반 기술 질문 9개

> [[Interview-Prep-Kmong-1st|목차]]. [[My-Tech-Cards]] 카드에서 fork했다. 이력서에 공개된 수치만 쓰고, 측정 조건을 설명하지 못하는 수치는 정성 표현으로 낮춘다. 각 카드 끝줄은 크몽 공고의 문제와 연결한다.

## R1. 수천 대 IoT 동시 요청의 재고 Race Condition을 어떻게 막았나 (경험형)

- **의도**: 동시성 판단 기준과 잠금의 한계를 아는지, 공고의 같은 요청이 두 번 오는 문제로 확장되는지 본다.
- **답변**: 같은 재고 행을 동시에 바꾸는 경로라 충돌이 잦았고, 늦게 충돌을 발견해 전체를 재실행하는 낙관적 잠금보다 먼저 경합을 조정하는 비관적 잠금이 단순하다고 판단했습니다. `SELECT ... FOR UPDATE NOWAIT`와 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했고 외부 호출과 입력 검증은 트랜잭션 밖으로 뺐습니다. 여러 대상을 갱신할 때는 업무 키 순서를 통일했습니다. 보호 대상이 한 DB 트랜잭션 안에 있어 분산 락은 쓰지 않았습니다.
- **한계**: 당시 재시도는 짧은 고정 간격이었다. 다시 한다면 지수 백오프와 지터를 검증한다. `NOWAIT`는 행 잠금 대기만 없애고 메타데이터 잠금 대기는 남는다. 잠금은 유입량을 흡수하지 못하므로 급증 흡수가 필요하면 업무 키별 순서 보장 큐를 함께 본다.
- **JPA 대응**: Spring Data JPA에서는 `@Lock(PESSIMISTIC_WRITE)`로 잠금 읽기를 표현한다. 대기 없이 실패시키는 lock timeout 힌트가 `NOWAIT`로 번역되는지는 Hibernate 버전과 MySQL dialect에서 생성 SQL로 확인한다(조건부).
- **꼬리**: NOWAIT와 SKIP LOCKED 차이(특정 행을 반드시 처리하면 NOWAIT, 작업 큐처럼 다음 행을 가져가면 SKIP LOCKED), 같은 행인데 데드락이 나는 S에서 X로의 승격 패턴, 분산 락이 필요해지는 조건.
- **크몽 연결**: 주문과 결제처럼 같은 상태를 여러 요청이 바꾸는 경계에서 잠금 범위를 먼저 정하는 기준으로 쓰겠다.

## R2. 왜 Kafka가 아니라 EventBridge와 SQS였나 (경험형, 설계형)

- **의도**: 우대 항목인 이벤트 드리븐 경험의 깊이와 선택 기준을 본다.
- **답변**: 조직 여건상 Kafka를 도입해 운영할 여력이 없었고, 필요한 것은 상태 변경 뒤 후속 발주 처리를 분리하고 실패를 재처리하는 것이었습니다. 리플레이, 강한 순서 보장, 매우 높은 처리량이 핵심 요구가 아니어서 관리형 큐를 골랐습니다. 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 영구 오류는 격리하고 일시 오류만 제한 재시도한 뒤 DLQ와 수동 확인으로 보냈습니다.
- **한계와 개선**: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 실패나 프로세스 중단이 나면 이벤트가 빠질 수 있었고, 당시에는 발행 재시도와 운영 확인으로 다뤘다. 다시 설계하면 상태 변경과 outbox 행을 같은 트랜잭션에 저장하고 릴레이가 발행한다. 그래도 중복은 남으므로 정확히 한 번이라고 말하지 않는다.
- **Kafka였다면**: 파티션 키를 업무 키로 두면 같은 키 안의 순서는 보장되지만 전체 순서는 아니다. 컨슈머 그룹의 리밸런스와 오프셋 커밋 시점에 따라 중복이 생기므로 멱등 소비는 그대로 필요하다. 운영 경험이 없다는 점은 먼저 밝힌다.
- **크몽 연결**: 도메인 서비스 사이의 이벤트 파이프라인에서도 발행 유실과 소비 중복을 따로 설계해야 한다는 점은 같다.

## R3. 슬로우 쿼리 99.3% 개선은 어떻게 측정했나 (경험형)

- **의도**: 수치의 근거와 인덱스 설계 기준을 본다.
- **답변**: 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했습니다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 만들고, 인덱스가 정렬과 상위 레코드 접근에 실제로 쓰이는지 실행 계획으로 다시 확인했습니다.
- **수치 경계**: 99.3%는 이력서 표기다. 비교한 쿼리 단위, 캐시 조건, 표본을 설명할 수 있을 때만 말한다. 전체 API 시간과 쿼리 1건 시간을 섞지 않는다. 데이터 규모와 관계없이 안정적이라는 이력서 표현은 데이터 분포가 바뀌면 다시 측정한다는 조건과 함께 말한다.
- **꼬리**: 컬럼 순서 판단(동등, 범위, 정렬 순), 커버링 인덱스를 무작정 넓히지 않는 이유, 인덱스 추가의 쓰기 비용, 대형 테이블에 인덱스를 추가할 때 온라인 DDL과 복제 지연.

## R4. Prisma의 N개 쿼리를 단일 쿼리로 합쳐 API 응답속도를 90% 향상했다. JPA라면? (경험형, 사실형)

- **답변**: 관계 포함 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했고, 당시 설정에서는 관계를 여러 쿼리로 읽어 애플리케이션에서 결합하고 있었습니다. 공식 문서와 실행 계획을 확인한 뒤 `relationLoadStrategy: 'join'`을 적용해 MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 나가는 것을 검증했습니다. 옵션 이름만 보고 SQL JOIN이라고 가정하지 않았습니다.
- **JPA 대응(사실형)**: 지연 로딩 연관을 반복 접근하면 N+1이 생긴다. fetch join이나 `@EntityGraph`로 한 번에 가져오거나, 컬렉션은 batch size로 IN 조회를 묶는다. 컬렉션 fetch join과 페이징을 함께 쓰면 메모리 페이징 경고가 나므로 페이징이 필요하면 batch size나 별도 조회를 쓴다.
- **흔한 오답**: EAGER로 바꾸면 해결된다(다른 조회 경로에서 불필요한 조인과 N+1이 여전히 생길 수 있다).
- **꼬리**: 조인 전략의 데이터 중복과 DB 부하, 어떤 경로만 명시적 쿼리로 낮추는지.
- **출처**: [Prisma, Relation queries](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries)

## R5. 단일 NGINX에서 CloudFront, ELB, ECS로 옮길 때 무중단은 어떻게 지켰나 (경험형)

- **의도**: 공고의 무중단 전환을 인프라 수준에서 해 봤는지 본다.
- **답변 골격**: 트래픽 증가로 단일 서버 구조의 한계가 보여 관리형 컨테이너 환경으로 옮겼다 → 실행 이미지와 설정 주입을 분리하고 배포, 중단, 롤백이 각각 재현되는지 확인했다 → 웹 요청과 기기 통신의 프로토콜과 고정 endpoint 요구가 로드밸런서 선택을 좌우했다 → 읽기 부하는 Read Replica로 분산해 응답 40%를 개선했고(이력서), 쓰기와 쓰기 직후 읽기는 primary로 고정했다.
- **[사용자 확인 필요]**: 전환 당일의 트래픽 절체 방식(DNS 가중치, 단계적 전환 등)과 롤백 기준은 기억으로 채우지 않는다.
- **꼬리**: 컨테이너 종료 신호와 진행 중 요청 정리, Rolling과 Blue/Green 비교, 복제 지연을 숨기지 않는 방법, 멀티스테이지 빌드로 이미지 909MB에서 513MB, 배포 3분 10초에서 2분 20초(이력서).

## R6. 관측 체계를 어떻게 만들었고 장애를 어떻게 따라갔나 (경험형)

- **답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었습니다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼습니다. 지연은 histogram으로 봤습니다. 메트릭으로 사용자 영향과 추세를, 로그로 개별 원인을 좁혔고 Grafana Alerting으로 경보를 만들었습니다.
- **흔한 오답**: 사용자 ID나 요청 ID를 메트릭 라벨에 넣는 설계. 제가 실제로 겪은 실수라서 라벨 설계 기준을 먼저 말한다.
- **크몽 연결**: 마이크로서비스 사이에서는 서비스 경계를 넘는 추적이 필요하다. 요청 식별자를 서비스와 메시지 헤더로 전파하고, 분산 추적을 도입하면 trace context를 같은 원칙으로 다루겠다. 크몽의 현재 관측 도구는 확인 질문으로 둔다.
- **꼬리**: RED와 USE 구분, 경보 기준을 과거 숫자로 복사하지 않는 이유, 포스트모템 순서.

## R7. 팀 AI 협업 규약은 구체적으로 무엇이었나 (경험형)

- **의도**: 공고 필수 항목. 실제로 에이전트에게 위임하고 검증하는 체계를 만들었는지 본다.
- **답변**: 도메인별 CLAUDE.md에 AI가 건드릴 영역과 건드리면 안 되는 영역을 코드와 규칙으로 명문화했습니다. Subagents, Custom Skills, Hooks로 반복 작업을 나누고, 작업이 끝나는 시점에 변경 파일 검사와 테스트 같은 품질 점검을 AI가 스스로 돌리는 회귀 루프를 두었습니다. 채택 여부는 사람이 결정합니다.
- **보강할 한 문장**: 되돌리기는 변경 범위를 작게 유지하고 커밋 단위로 되돌릴 수 있게 하는 것부터 시작한다. 운영 반영 뒤 관측까지 이어지는 부분은 크몽에서 더 넓히고 싶은 영역이라고 솔직히 말한다.
- **꼬리**: 금지 영역은 어떻게 강제했나(규칙 문서만으로는 약하므로 Hook과 검사 단계로 막는다), 모델이 바뀌면 규약은 어떻게 유지하나.

## R8. 데이터 이관과 레거시 전환을 해 본 경험 (경험형)

- **의도**: 공고의 데이터 이관, 기존 시스템 분석과 재작성 역량을 본다.
- **공개 가능한 사실(이력서)**: 영양정보 데이터 정형화를 위해 MongoDB에서 MySQL로 데이터를 이관했다. 고객사 온프레미스 구축을 위해 AWS 기반 서비스를 이관했다. 공공 프로젝트에서 JSP와 JDBC 구조를 Spring과 MyBatis로 옮겼다.
- **답변 골격**: 왜 옮겼나(정형화, 고객 환경 요구, 유지보수성) → 무엇을 기준으로 스키마를 다시 설계했나 → 이관 중 원본과 대상의 차이를 어떻게 확인했나 → 되돌릴 수 있는 경계는 어디였나 → 지금 다시 한다면.
- **[사용자 확인 필요]**: 각 이관의 실제 검증 방식(건수 대사, 샘플 비교 등)과 중단 시간 유무. 기억에 없는 절차는 지금이라면 이렇게 하겠다로 분리해 말한다.
- **지금이라면**: 신규 스키마로 백필한 뒤 변경분은 CDC나 outbox로 따라잡고, 건수와 체크섬으로 대사한 뒤 읽기를 먼저 옮기고 쓰기를 마지막에 전환한다. 상세는 [[Interview-Prep-Kmong-1st-Tech-JD|JD 기술 질문]] J1.

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- **의도**: 공고의 에이전트 위임과 결과물 검증 요구를 실제 도구 제작과 비교로 해 봤는지 본다.
- **답변**: 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템입니다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색은 MCP 도구와 CLI로 제공했습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했고, 질문마다 반드시 나와야 하는 문서, 절, 본문 문구를 근거 그룹으로 정해 응답 크기 예산 안에 모두 나오면 통과로 쳤습니다. 무관한 질문은 빈 결과가 나와야 통과하는 음성 질문으로 넣었습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃었습니다. 74개를 포함한 94개 질문으로 bge 리랭커도 비교했지만 통과가 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸습니다. 그래서 모두 채택하지 않았고, 문제가 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 이득이 있어도 바로 바꾸지 않는다. 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다. 새 방식을 측정으로 모두 기각한 것을 강점으로 말한다.
- **골든 케이스 선정과 지표**: 평가 질문은 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본이 아니다. 양성은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나와야 통과, 음성은 빈 결과여야 통과. 비교 결과는 위 답변의 수치가 전부다.
- **이력서 정정**: 이력서의 골든 케이스 약 145건 문구는 부정확하다. 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **한계**: 합성 표본이라 실제 답변 정확도나 사용자 만족도를 잰 것이 아니다. 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
