# 크몽 1차, 서비스 맥락 질문과 역질문

> [[Interview-Prep-Kmong-1st|목차]]. 공개된 사실은 프리랜서 마켓플레이스라는 점과 공고가 적은 도메인(회원, 상품, 주문, 결제, 알림)뿐이다. 거래 흐름, 수수료, 정산 주기, 트래픽 규모는 확인하지 못했으므로 답변은 가정을 먼저 말하고 역질문으로 확인한다.

## 서비스 맥락 예상 질문 6개

### S1. 결제는 성공했는데 주문 서비스 반영이 실패했다 (설계형)

- **공개 자료의 문제**: 공고가 주문과 결제를 별도 서비스로 운영한다고 적었다.
- **골격**: 먼저 사용자 영향 범위를 확인한다(결제 완료 화면을 봤는데 주문이 없는 상태) → 결제 쪽 이벤트를 재처리하거나 주문 쪽이 결제 상태를 조회해 따라잡게 한다 → 반영 로직이 멱등해야 재처리가 안전하다 → 일정 시간 안에 짝이 맞지 않는 결제를 찾는 대사 작업을 두고, 끝내 반영할 수 없으면 환불이라는 보상 거래로 닫는다.
- **판단 기준**: 금액이 걸린 불일치는 자동 복구와 사람의 확인 중 무엇이 싼지, 되돌릴 수 없는 외부 효과가 있는지.
- **유사 경험과 한계**: 발주 소비자의 DLQ와 수동 확인 경로. 결제 대사를 운영한 경험은 없다고 말한다.
- **꼬리**: 대사 작업이 같은 건을 두 번 환불하지 않게 하려면? 환불 요청에도 멱등성 키를 둔다.

### S2. 알림 서비스를 설계한다면 (설계형)

- **골격**: 알림 발생 사건과 채널별 발송을 분리해 큐로 넘긴다 → 사건의 안정적인 ID와 채널을 묶어 유일하게 만들어 로컬 중복을 막는다 → 외부 발송사가 수락했는지 불명확한 건은 상태 조회나 대사로 닫는다 → 일시 오류는 제한 재시도, 영구 오류(잘못된 수신처)는 즉시 격리한다 → 사용자 수신 설정과 야간 발송 같은 정책을 발송 직전에 다시 확인한다.
- **트레이드오프**: 실시간성을 높이면 외부 발송사 한도와 비용에 부딪힌다. 중요도에 따라 즉시 발송과 묶음 발송을 나눈다.
- **유사 경험**: IoT 배터리 부족과 통신 지연을 주기적으로 집계해 알림톡과 이메일로 보내는 리포트를 구축했다(이력서).

### S3. 서비스 경계에서 장애가 났는데 원인이 어느 쪽인지 모른다 (행동형, 설계형)

- **의도**: 공고의 end-to-end 추적과 담당 밖 문제 공동 해결을 같이 본다.
- **골격**: 영향과 현재 대응을 먼저 공유한다 → 요청 식별자로 경계를 넘는 로그를 이어 붙이고, 호출 쪽 지연과 오류, 제공 쪽 지연과 포화를 나란히 본다 → 최근 배포와 설정 변경을 양쪽에서 확인한다 → 가설을 하나씩 검증하고 복구를 우선한다 → 원인이 다른 팀 코드여도 재현 자료와 함께 같이 고치고, 포스트모템으로 경계의 계약(타임아웃, 재시도, 오류 형식)을 정리한다.
- **흔한 함정**: 우리 쪽 로그에 문제가 없으니 넘긴다. 공고가 명시적으로 피하려는 태도다.
- **내 경험 연결**: 오픈소스 라이브러리의 명세 불일치를 재현으로 추적한 경험, Grafana, Loki 기반 원인 추적.

### S4. 전문가 서비스 목록이나 카테고리 조회에 트래픽이 몰린다 (설계형)

- **가정**: 목록 조회가 읽기 중심이고 약간의 지연된 데이터를 허용한다고 가정한다. 실제 허용 범위는 확인한다.
- **골격**: 실행 계획과 인덱스, 커서 페이지네이션부터 본다 → 측정된 핫 경로 중 오래된 값을 허용하는 곳에만 Cache-Aside를 적용하고 쓰기 뒤 무효화한다 → 인기 키 동시 만료는 TTL 지터나 요청 병합으로 막는다 → 복제본 읽기는 쓰기 직후 읽기 경로를 primary로 고정한다 → 검색과 필터가 복잡해지면 검색 엔진 분리를 검토한다.
- **트레이드오프**: 캐시는 신선도를, 비정규화 조회 모델은 쓰기 복잡도를 대가로 낸다.
- **유사 경험**: 복합 인덱스와 Read Replica(응답 40% 개선, 이력서), 외부 메타데이터 초기 적재 캐시([[My-Tech-Cards]] 카드 8).

### S5. 금액 계산과 정산에서 조심할 것은 (사실형, 설계형)

- **핵심 답변**: 금액은 부동소수점을 쓰지 않고 정수 최소 단위나 고정 소수(Java와 Kotlin의 `BigDecimal`)로 다룬다. 수수료와 부가세 같은 계산은 반올림 규칙과 적용 시점을 명시하고, 항목별 반올림 합과 합계 반올림이 다를 수 있음을 정책으로 정한다. 확정된 금액 기록은 수정하지 않고 정정 거래를 추가한다. 주기적으로 결제사 기록과 내부 원장을 대사한다.
- **흔한 오답**: `Double`로 계산 뒤 표시할 때만 반올림.
- **유사 경험과 한계**: 정산과 연결된 환불 정책 변경에서 보호 조건을 먼저 둔 사례, 환율 배치. 세금계산서 발행 경험은 없다.
- **꼬리**: 환불이 부분 환불이면 수수료는 어떻게 되돌리나(정책 확인 질문으로 돌린다).

### S6. 크몽 서비스에서 개선하고 싶은 점이 있나 (행동형)

- **준비**: [사용자 확인 필요] 실제 이용 경험이 있으면 그 경험에서, 없으면 면접 전 공개 화면을 직접 보고 관찰 사실 하나만 말한다. 내부 구조는 추측하지 않는다.
- **골격**: 관찰한 사용자 흐름 → 그 흐름에서 백엔드가 영향을 줄 수 있는 지점(상태 표시, 알림 시점, 중복 요청) → 확인하고 싶은 지표 → 가설로 끝내고 팀의 실제 데이터를 묻는다.
- **주의**: 비판 톤이 아니라 제품을 써 본 사람의 개선 가설로 말한다.

## 역질문

[[My-Reverse-Questions]]에서 5개, 회사 특이 질문 2개를 골랐다. 1차에서는 1, 2, 6을 외워 두고 나머지는 흐름에 맞춰 쓴다.

1. **B1 초기 과제와 성공 기준**: 합류 후 가장 먼저 책임질 과제와, 잘하고 있다고 판단할 기준은 무엇인가요?
2. **C1 기술 경계와 신규 개발 비중**: 이 역할이 직접 맡게 될 서비스나 도메인 경계는 어디이고, PHP 운영, Kotlin 전환, 신규 제품 개발의 비중은 어떻게 되나요?
3. **C2 데이터 경계와 정합성 검증**: 주문과 결제처럼 서비스가 나뉜 경계에서 상태 불일치는 현재 어떤 방식으로 검증하고 있나요?
4. **C3 관측과 품질 기준**: 서비스 사이에서 생긴 장애는 어떤 신호로 감지하고, 해결 뒤에는 어떤 회고를 거치나요?
5. **D2 학습과 검증**: 공고의 기술 중 제가 깊이가 부족한 Kotlin과 Kafka 계열은 어떤 작은 과제로 익히는 것이 가장 효과적일까요?
6. **회사 특이, 에이전트 운영**: 한 번 푼 문제를 skill이나 workflow로 정리한다고 하셨는데, 에이전트 결과물의 검증과 롤백은 현재 어느 단계까지 자동화돼 있고 팀이 가장 어려워하는 지점은 어디인가요?
7. **회사 특이, 전환 현황**: PHP에서 Kotlin으로의 전환에서 데이터 이관과 무중단 전환은 어떤 기준으로 진행하고 있고, 남은 도메인 중 가장 까다로운 곳은 어디인가요?

**아껴둘 질문**: E3 온콜과 장애 대응, 메시지 브로커 실제 구성, 연봉 밴드(A3)는 이후 단계에서 묻는다. 겸업 규정은 C6 슬롯이 확정된 경우에만 묻는다.

**면접 전 확인(F1)**: 1차 형식, 참여 역할, 라이브 코딩이나 과제 여부. 라이브 코딩이 있다면 [[Live-Coding-Process]]의 명확화, 제약, 접근 비교, 구현, 개선 순서를 따른다.
