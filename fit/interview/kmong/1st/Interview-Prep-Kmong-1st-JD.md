# 크몽 1차, JD와 회사 분석

> [[Interview-Prep-Kmong-1st|목차]]. JD는 2026-09-29 원티드 공고 원문과 대조했다. 공개 출처로 확인되지 않은 회사 단계, 재무, 조직, 고객과 기술 구현은 확인 질문으로만 둔다.

| 기업 대상 상품 | 기업과 공공기관 대상 크몽 엔터프라이즈를 별도로 소개한다 | [크몽 공식 사이트](https://kmong.com/) |

### 핵심 키워드

서비스 경계와 상태 소유, 멱등성, 레거시 전환과 데이터 이관, 무중단 전환, 이벤트 파이프라인, end-to-end 추적, 에이전트 위임과 검증, 동료 문제 공동 해결.

## 4. 우대 사항과 내 경험 매칭

| 우대 사항 | 매칭 | 근거와 갭 대응 |
|---|---|---|
| 레거시의 MSA 전환 | 중 | 모듈 중심 아키텍처와 인프라 전환은 했지만 서비스 분리와 DB 분리는 해 보지 않았다. 전환 원리와 확인할 조건으로 답한다 |
| 대용량 서비스 | 중 | 수천 대 IoT 동시 요청의 경합을 다뤘다. 그 이상의 트래픽 규모는 과장하지 않는다 |
| 이벤트 드리븐(Kafka 등) | 중 | EventBridge와 SQS로 발주 자동화를 설계하고 멱등 소비와 DLQ를 적용했다. Kafka 운영은 없고, 조직 여건상 도입하지 않은 판단을 설명한다 |
| OOP, TDD, 리팩토링 | 중강 | 통합과 단위 테스트 주도, UseCase와 Repository port 분리. TDD는 기본 흐름으로 쓰지 않으므로 스펙 먼저, 테스트로 검증이라는 실제 방식을 말한다 |
| AWS ECS, RDS, ElastiCache, MSK | 중강 | ECS, ECR, RDS, SQS, EventBridge, Lambda 사용. ElastiCache와 MSK는 사용 경험으로 말하지 않는다 |
| DevOps, CI/CD, GitHub Actions | 강 | Jenkins 파이프라인으로 배포 속도 50% 단축(이력서), GitHub Actions 사용 |
| 노하우의 가이드, 자동화 도구화 | 강 | 팀 AI 협업 규약, 커뮤니티 발표, 문제 해결 문서화 |
| 새 도구의 빠른 검증과 흡수 | 강 | 도구 도입 전 문제 정의, 작은 검증, 비용과 운영 부담 비교 |
| 결제, 정산, 세금계산서 | 중 | 정산과 연결된 환불 정책 변경의 위험을 정리해 보호 조건을 먼저 두고 구독 결제를 출시한 사례. 세금계산서 경험은 없다 |

## 5. 기술 스택 비교

| 공개 JD 스택 | 내 경험 | 판정과 전환 근거 |
|---|---|---|
| Kotlin | 없음 | 보강 필요. Java와 TypeScript 경험, null 안전성과 타입 좁히기의 유사성 |
| Spring Boot | Java Spring MVC, 부트캠프, 멘토링 | 유사. 최근 운영은 NestJS이며 DI, 모듈 경계, AOP 인터셉터 개념이 대응된다 |
| JPA 계열 ORM | 이력서에 JPA, Hibernate, Querydsl 표기, 실무 ORM은 Prisma와 Sequelize | 유사. 생성 SQL과 실행 계획으로 검증하는 습관이 전이된다 |
| MySQL | MySQL, MariaDB | 동일 |
| NoSQL | MongoDB, Redis | 유사 |
| 마이크로서비스 | 모듈러 모놀리스, 이벤트 분리 | 보강 필요 |
| Kafka, MSK | 없음, SQS와 EventBridge | 유사 원리, 보강 필요 |
| AWS ECS, RDS | 동일 | 동일 |
| GitHub Actions | 동일 | 동일 |
| PHP | 없음 | 보강 필요. 읽기와 동작 복원 중심으로 접근 |
