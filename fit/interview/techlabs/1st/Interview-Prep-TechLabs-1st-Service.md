# 테크랩스 1차 서비스 맥락 질문

> [[Interview-Prep-TechLabs-1st|메인 문서]]로 돌아가기. 근거는 공개 JD의 주요 업무, 공식 사이트의 애드테크 제품 소개, 럭키버스 보도뿐이다. 테크랩스의 실제 이벤트 규모, 정산 주기, 제휴 연동 방식은 공개되지 않았으므로 모든 답변은 요구사항을 먼저 확인하는 설계 골격으로 둔다. 광고 도메인 실무 경험은 없으므로 경험처럼 말하지 않는다.

## S1. 광고 노출과 클릭 이벤트를 수집하는 트래킹 시스템을 설계한다면

- 공개 근거: JD 주요 업무 3번(광고 데이터 분석, 트래킹, 정산 시스템 개발과 최적화), 공식 사이트의 애드서버 리포트 플랫폼 소개.
- 먼저 확인할 것: 초당 이벤트 규모와 피크, 집계 지연 허용 범위, 이벤트 유실과 중복 중 무엇이 더 비싼지, 원본 보존 기간.
- 답변 골격:
  1. 수집 API는 가볍게 두고 검증 뒤 바로 수락한다. 이벤트마다 발급 시점의 고유 ID를 붙인다.
  2. 원본은 변경하지 않는 추가 전용 로그로 보존한다. 집계가 틀려도 원본에서 다시 계산할 수 있어야 한다.
  3. 수집과 집계 사이에 큐나 로그를 둬 피크를 흡수한다. 여러 소비자(실시간 지표, 일 집계, 과금 검증)가 같은 이벤트를 읽으면 로그 기반 브로커가 유리하다.
  4. 전달은 적어도 한 번이므로 이벤트 ID로 중복을 제거하고, 늦게 도착한 이벤트는 이벤트 발생 시각 기준 구간에 반영할지 기준을 정한다.
  5. 무효 트래픽(같은 사용자의 짧은 간격 반복 클릭 등) 필터는 집계 전에 규칙으로 분리해 적용 이력을 남긴다.
- 대안과 트레이드오프: 요청 경로에서 DB에 바로 쓰면 단순하지만 피크에 쓰기 경합이 생긴다. 큐를 두면 흡수력이 생기는 대신 집계 지연과 운영 요소가 늘어난다.
- 유사 경험과 한계: 수천 대 IoT 하드웨어의 동시 요청을 정합성 있게 받은 경험, 멱등 소비와 DLQ를 둔 이벤트 처리 경험. 광고 이벤트 규모의 수집 파이프라인을 운영한 경험은 없다.
- 꼬리: 클라이언트 재시도로 같은 클릭이 두 번 오면(이벤트 ID 중복 제거), 수집 서버가 죽으면 무엇이 유실되나(수락 응답 전 영속화 여부).

## S2. 럭키버스에서 광고 시청 후 리워드를 적립할 때 중복 지급과 부정 적립을 어떻게 막나

- 공개 근거: 럭키버스는 운세 콘텐츠를 이용하며 광고를 시청한 뒤 리워드를 적립하는 오퍼월 기반 콘텐츠로 소개됐다(이투데이, 2025-09-11).
- 먼저 확인할 것: 광고 시청 완료 신호를 누가 주는지(광고 SDK, 광고 네트워크 서버 콜백), 리워드를 테크랩스가 지급하는지 제휴 플랫폼이 지급하는지, 일일 한도 정책.
- 답변 골격:
  1. 클라이언트의 완료 신호만 믿지 않는다. 가능하면 광고 네트워크의 서버 간 콜백을 서명 검증한 뒤 적립한다.
  2. 적립 단위의 안정적인 키(사용자, 광고 노출 또는 거래 ID)를 유일 제약으로 두고, 같은 키는 한 번만 적립되게 한다. 재요청에는 기존 결과를 돌려준다.
  3. 잔액은 증감 원장(적립 이력 행)에서 계산 가능하게 두고, 잔액 컬럼을 갱신한다면 원장 기록과 같은 트랜잭션에서 처리한다.
  4. 사용자별 일일 한도와 빈도 제한은 적립 경로에서 원자적으로 검사한다.
  5. 제휴 플랫폼에 지급을 요청한다면 같은 멱등성 키를 전달하고, 결과가 불명확한 건은 상태 조회와 대사로 닫는다.
- 대안과 트레이드오프: Redis 카운터로 한도를 검사하면 빠르지만 원장과 어긋날 수 있다. 최종 기준은 DB 원장으로 두고 Redis는 1차 차단에만 쓴다.
- 유사 경험: 동시 갱신의 DB 잠금(R1), 멱등성 키와 상태 전이 검증으로 중복 전달을 처리한 소비자 설계(R2). 리워드와 광고 콜백 연동 경험은 없다.
- 꼬리: 콜백이 늦게 오고 사용자는 이미 적립 안 됐다고 문의하면(대기 상태 표시와 재조회), 부정 적립이 의심되면(규칙 기반 탐지, 지급 보류, 사후 회수 정책은 사업팀과 합의).

## S3. 광고 정산 시스템에서 집계 숫자와 외부 리포트가 어긋나면

- 공개 근거: JD 주요 업무 3번의 정산, 공식 사이트의 SSP와 DSP, 애드서버 리포트 소개.
- 먼저 확인할 것: 정산 대상(매체사 수익 배분, 광고주 과금, 제휴 플랫폼 정산 중 무엇), 정산 주기, 확정 뒤 정정 정책, 금액의 통화와 단위.
- 답변 골격:
  1. 한 번의 차이를 곧바로 오류로 보지 않는다. 늦게 도착한 이벤트, 구간 경계와 시간대 차이, 무효 트래픽 필터 기준 차이가 먼저 후보다.
  2. 양쪽을 같은 기준 구간과 같은 키로 정규화해 비교하고, 불일치를 건별로 기록한다.
  3. 정산은 잠정 집계와 확정을 나눈다. 확정 전에는 재계산을 허용하고, 확정 뒤 차이는 원래 값을 덮어쓰지 않고 정정 행으로 남긴다.
  4. 금액은 부동소수점을 쓰지 않고 최소 단위 정수나 scale을 아는 decimal로 계산하며, 반올림 규칙을 한 곳에서 정한다.
  5. 집계 배치는 같은 구간을 다시 돌려도 결과가 같게 만들고, 원본 이벤트 합과 집계 합을 자동으로 대조한다.
- 대안과 트레이드오프: 실시간 집계는 빠르지만 정정이 잦다. 배치 확정은 정확하지만 지연이 있다. 보통 실시간은 참고 지표, 배치 확정값이 정산 기준이다.
- 유사 경험과 한계: 주기 집계 리포트(R8), 시솔지주의 환율 정보 배치 처리. 금전 정산 시스템을 직접 운영한 경험은 [사용자 확정 필요: 마스터 FIT 2-A의 정산 연결 환불 정책 사례를 이 답변에 쓸지와 소속]이 확정되기 전에는 말하지 않는다.
- 꼬리: 정산 확정 뒤 버그가 발견되면(영향 구간 산정, 재계산, 정정 이력, 사업팀과 고지 범위 합의).

## S4. 토스 같은 외부 플랫폼에 럭키버스를 제공할 때 연동 API를 어떻게 설계하나

- 공개 근거: 럭키버스가 토스 미니앱, 하나머니 등에 제공된다는 보도, NH올원뱅크 제공 보도 제목.
- 먼저 확인할 것: 연동 방향(우리가 호출하나, 파트너가 호출하나), 인증 방식, 파트너별 정책 차이, 장애 시 책임 경계.
- 답변 골격: 파트너별 인증과 키 회전, 요청 서명 검증, 파트너 단위 rate limit과 격리(한 파트너의 폭주가 다른 파트너에 번지지 않게), 멱등성 키, 버전 관리된 계약과 호환 규칙, 파트너별 정책은 코드 분기 대신 설정이나 전략 객체로 분리. 외부 호출에는 타임아웃, 제한 재시도, 서킷 브레이커를 둔다.
- 대안과 트레이드오프: 파트너별 전용 엔드포인트는 단순하지만 중복이 늘고, 공통 API와 파트너 어댑터는 확장에 유리하지만 초기 설계 비용이 든다.
- 유사 경험: 시솔지주에서 Google API 번역 연동, 배송 정보 스크래핑, 고객사 요구에 따른 마이그레이션. FIDO 서버에서 명세를 분석해 인증 흐름을 설계한 경험.
- 꼬리: 파트너가 같은 요청을 재시도하면, 우리 쪽 장애를 파트너에게 어떻게 알리나.

## S5. 광고 리포트 조회가 느려지면

- 공개 근거: 공식 사이트의 애드서버 리포트 조회 플랫폼(Insight) 소개, JD의 광고 데이터 분석.
- 답변 골격: 실행 계획으로 병목을 먼저 확인한다. 원본 이벤트 테이블을 매번 스캔한다면 시간 단위, 일 단위 사전 집계 테이블로 분리하고, 조회 조건(매체, 캠페인, 기간)에 맞는 복합 인덱스를 둔다. 리포트는 지연을 허용하므로 replica나 캐시로 보낸다. 분석성 조회가 운영 DB를 흔들 정도면 OLTP와 OLAP 저장소 분리를 검토한다.
- 트레이드오프: 사전 집계는 조회를 빠르게 하는 대신 집계 기준이 바뀌면 재계산이 필요하다.
- 유사 경험: 복합 인덱스로 슬로우 쿼리 99.3% 개선(R3), Read Replica로 응답속도 40% 개선(R5).
- 꼬리: 사전 집계와 원본이 어긋나면(S3의 대조 배치).

## S6. 사업팀 요청과 시스템 개선을 어떻게 병행하나

- 공개 근거: JD 주요 업무 4번(사업팀 요청사항 처리와 시스템 개선).
- 답변 골격: 요청을 받으면 의도와 마감, 정산 숫자에 영향을 주는지부터 확인한다. 반복되는 요청은 기록해 자동화나 셀프 서비스 후보로 모은다. 개선 작업은 요청 처리에서 발견한 병목과 연결해 우선순위를 설명한다. 긴급 요청이 겹치면 사용자 영향, 오류 비용, 되돌리기 가능성으로 순서를 정하고 남은 위험을 공유한다.
- 유사 경험: 트라이포드랩에서 내부 업무 효율화를 위한 자동화(기기 상태 리포트, 발주 자동화), 잦은 요구사항 변경을 수용하려고 도메인별 모듈을 분리한 설계.
- 꼬리: 요청이 정산 로직 변경이라면 어떻게 검증하나(과거 구간 재계산 결과 비교, 확정값 영향 범위 확인).
