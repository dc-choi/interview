# 테크랩스 1차 이력서 기반 기술 질문

> [[Interview-Prep-TechLabs-1st|메인 문서]]로 돌아가기. [[My-Tech-Cards]] 마스터를 fork했다. 수치는 공개 이력서에 있는 것만 쓰고, 측정 조건을 설명할 수 있을 때만 말한다. 전 직장의 내부 지표와 구조는 말하지 않는다. 포트폴리오가 없어 아키텍처 도식 기반의 딥다이브는 반영하지 못했다.

## R1. 수천 대 IoT 동시 요청의 Race Condition을 DB Lock으로 어떻게 해결했나 (경험형)

- 질문 의도: 동시성 문제를 재현하고 잠금 방식을 근거로 골랐는지.
- 핵심 답변: 같은 재고 상태를 동시에 바꾸던 경로에 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했다. 충돌이 잦은 갱신이라 낙관적 잠금은 늦게 충돌을 발견해 전체를 다시 해야 하므로 비관적 잠금이 단순했다. 외부 호출과 독립 검증은 트랜잭션 밖으로 빼고, 여러 대상을 갱신할 때는 업무 키 순서를 통일했다. 동시 요청을 재현해 최종 수량과 잠금 실패, 재시도 뒤 상태를 확인했다.
- 대안과 트레이드오프: 충돌이 드물면 버전 컬럼 조건부 갱신이 낫다. 보호 대상이 단일 DB 트랜잭션 안이라 분산 락은 쓰지 않았다. 잠금은 유입량을 흡수하지 못하므로 급격한 유입에는 업무 키별 순서 큐와 워커 동시성 제한을 검토한다.
- 한계: 당시 재시도는 짧은 고정 간격이었다. 다시 한다면 지수 백오프와 지터를 검증한다. `NOWAIT`는 해당 잠금 읽기의 대기만 없앤다.
- 꼬리: NOWAIT와 SKIP LOCKED 차이(특정 행을 반드시 처리하면 NOWAIT, 큐처럼 다음 행을 가져가면 SKIP LOCKED). 데드락은 `SHOW ENGINE INNODB STATUS`로 분석하고 새 트랜잭션에서 제한 재시도. Spring이라면 JPA `@Lock(PESSIMISTIC_WRITE)`와 lock timeout 힌트로 같은 의도를 표현하되 생성 SQL을 확인한다.
- 회사 연결: 리워드 적립이나 예산 차감처럼 같은 행을 여러 요청이 동시에 바꾸는 경로에 같은 판단을 쓴다.

## R2. 발주 자동화를 왜 Kafka가 아니라 EventBridge와 SQS로 했나 (경험형)

- 질문 의도: 기술 선택을 조직과 운영 여력까지 고려해 했는지. JD 우대(메시지 큐)와 직결.
- 핵심 답변: 조직 내 Kafka 도입 한계를 고려했다. 필요한 것은 도메인 상태 변경 뒤 후속 발주 작업을 분리하고, 실패를 재시도와 수동 확인으로 나누는 것이었다. 리플레이, 강한 순서 보장, 매우 높은 처리량이 핵심 요구가 아니었으므로 운영 부담이 낮은 관리형 큐를 골랐다. 소비자는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 영구 오류는 격리, 일시 오류만 제한 재시도, 예산 초과는 DLQ로 보냈다.
- 한계: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 전에 프로세스가 중단되면 이벤트가 누락될 수 있었고, 당시에는 발행 재시도와 운영 확인으로 다뤘다. 다시 설계하면 상태 변경과 outbox 행을 같은 트랜잭션에 저장한다.
- 꼬리: 어떤 조건이면 Kafka로 가나(이벤트 리플레이와 장기 보존, 키 단위 순서, 독립 컨슈머 그룹 여러 개, 측정된 처리량에서 현재 큐가 병목). 광고 이벤트처럼 같은 원본을 트래킹, 집계, 정산이 각각 읽어야 하면 Kafka의 컨슈머 그룹 모델이 유리해진다.
- 회사 연결: 광고 이벤트를 여러 소비자가 독립적으로 읽는 구조라면 Kafka 쪽 요구가 강해질 수 있고, 실제 요구와 현재 구조는 확인하겠다고 닫는다.

## R3. 복합 인덱스로 슬로우 쿼리 99.3%를 어떻게 개선했나 (경험형)

- 질문 의도: 수치의 측정 조건과 인덱스 설계 근거.
- 핵심 답변: 업무 키별 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 큰 것을 `EXPLAIN ANALYZE`로 확인했다. 동등 조건 뒤에 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 만들고, 인덱스가 정렬과 상위 레코드 접근에 실제로 쓰이는지 실행 계획으로 재확인했다.
- 측정 경계: 99.3%는 특정 쿼리의 개선 전후 비교다. 전체 API 지연이나 배치 전체 시간과 같은 지표로 섞지 않는다. [사용자 확정 필요: 측정 환경과 비교 방법 한 문장]
- 트레이드오프: 인덱스는 쓰기와 저장 비용을 늘린다. 인접 쓰기 경로와 다른 조회 영향을 함께 봤다.
- 꼬리: 컬럼 순서 기준(동등, 범위, 정렬, 반환 컬럼), 커버링 인덱스, OFFSET 대신 커서 페이지네이션.
- 회사 연결: 광고 리포트 조회처럼 매체, 기간으로 좁히고 시간순으로 읽는 조회에 같은 설계를 적용한다.

## R4. Prisma N개 쿼리를 단일 쿼리로 통합해 90% 향상한 과정과 JPA에서의 대응 (경험형 + 사실형)

- 질문 의도: ORM 생성 SQL을 직접 확인하는지, JPA의 N+1을 아는지.
- 핵심 답변: 관계 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했다. 당시 `relationJoins` 기능이 꺼져 있어 include 관계를 여러 쿼리로 읽어 애플리케이션에서 합치고 있었다. 기능을 켜고 `relationLoadStrategy: 'join'`을 적용해 MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했다. 성능이 중요한 경로만 바꾸고 나머지는 유지했다.
- JPA 대응: JPA의 N+1은 지연 로딩된 연관을 반복 접근할 때 생긴다. fetch join, `@EntityGraph`, `default_batch_fetch_size`로 줄이고, 컬렉션 fetch join은 페이지네이션과 함께 쓰면 메모리에서 페이징되는 문제가 있어 batch size나 별도 조회로 푼다.
- 흔한 오답: 즉시 로딩(EAGER)으로 바꾸면 N+1이 해결된다고 답한다. JPQL 조회에서는 EAGER여도 추가 쿼리가 나갈 수 있다.
- 꼬리: 조인 전략의 비용(반환 데이터 중복, DB 부하), ORM을 버리고 native query로 내리는 기준.
- 학습 정본: [[JPA-Loading-and-Cascade]], [[Prisma-Query-Performance]]

## R5. 단일 NGINX에서 CloudFront, ELB, ECS(Fargate)로 전환하고 Read Replica로 40% 개선한 판단 (경험형)

- 질문 의도: 인프라 전환의 이유와 순서, 복제 지연을 이해하는지.
- 핵심 답변: 트래픽 증가에 따라 단일 서버의 확장과 배포 한계가 보였고, 관리형 컨테이너 환경으로 옮겨 수평 확장과 배포 절차를 표준화했다. 읽기 부하는 Read Replica로 분산했는데, 쓰기와 쓰기 직후 읽기는 primary로 보내고 지연을 허용하는 조회만 replica로 보냈다.
- 대안: Kubernetes는 운영 인력과 워크로드 수를 비교해 택하지 않았다. 캐시와 replica는 모두 오래된 값을 허용하는 경로에만 쓴다.
- 꼬리: 복제 지연이 생기면 무엇이 깨지나(방금 적립한 리워드가 조회에 안 보임). Spring에서는 `AbstractRoutingDataSource`와 `readOnly` 트랜잭션으로 라우팅할 수 있지만 `readOnly`는 힌트이고, 라우팅 기준과 지연 허용 범위를 먼저 정한다.
- 회사 연결: 정산 확정과 리워드 잔액처럼 최신값이 필요한 조회와, 리포트처럼 지연을 허용하는 조회를 나눠 라우팅한다.

## R6. Grafana, Prometheus, Loki 관측 체계를 어떻게 설계했나 (경험형)

- 질문 의도: 도구 나열이 아니라 신호 설계와 경보 기준.
- 핵심 답변: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼다. 지연은 histogram으로 봤다. 메트릭은 추세와 사용자 영향, 로그는 개별 원인에 쓰고, Grafana Alerting으로 실시간 장애 알림을 만들었다.
- 판단 기준: 사용자 ID나 요청 ID를 라벨에 넣으면 시계열이 폭증한다. 내가 실제로 겪은 실수라서 라벨 설계 기준을 먼저 말한다. 경보 기준은 과거 숫자를 복사하지 않고 정상 구간을 관찰해 정한다.
- 꼬리: API에는 RED, DB와 큐에는 USE. 큐 적체는 가장 오래된 메시지의 대기 시간으로 본다. Spring이라면 Micrometer와 Actuator로 같은 구조를 만든다.
- 회사 연결: 광고 트래킹에서는 수집 이벤트 수, 지연 도착 비율, 집계와 원본 차이를 운영 지표로 두겠다고 연결한다.

## R7. Docker 멀티스테이지로 909MB에서 513MB, 배포 3분 10초에서 2분 20초 (경험형)

- 질문 의도: 수치의 원인과 추가 개선 여지.
- 핵심 답변: 빌드 도구와 실행 의존성을 분리해 빌드 산출물과 운영 의존성만 실행 이미지에 넣었다. 이미지가 작아지면 레지스트리 전송과 태스크 기동이 빨라져 배포 시간이 줄었다.
- 꼬리: alpine의 musl과 네이티브 모듈 호환, distroless의 디버깅 비용. Java라면 JAR 레이어 분리(의존성 레이어와 애플리케이션 레이어)로 캐시 효율을 높이고 JRE 전용 베이스를 쓴다.
- 회사 연결: 자주 배포하는 사업팀 요청 대응에서 배포 시간과 롤백 경로가 곧 대응 속도라고 닫는다.

## R8. IoT 배터리 부족과 통신 지연을 주기 집계해 알림톡과 이메일로 보낸 리포트는 어떻게 만들었나 (경험형)

- 질문 의도: 주기 집계와 외부 발송의 실패 처리. 광고 집계와 정산 배치에 가장 가까운 경험.
- 핵심 답변 골격: 스케줄러가 기준 구간의 상태 데이터를 집계하고, 조건에 맞는 대상을 모아 알림톡과 이메일로 발송했다. 집계 구간은 반개구간으로 정해 경계 중복과 누락을 막고, 발송은 채널별로 실패를 분리해 한 채널 실패가 다른 채널을 막지 않게 한다.
- [사용자 확정 필요]: 당시 실제 구현의 세부(스케줄러 종류, 재실행 방식, 중복 발송 방지 방식). 이력서에는 자동 통보 리포트 구축까지만 공개돼 있으므로 그 이상은 확인한 사실만 말한다.
- 개선 기준: 같은 구간을 다시 돌려도 결과가 같도록 구간 키로 멱등하게 만들고, 알림 사건 ID와 채널을 유일 키로 묶어 중복 발송을 막는다. 외부 provider가 수락했는지 불명확한 건은 조회와 대사로 닫는다.
- 꼬리: 스케줄러가 여러 인스턴스에서 동시에 돌면(분산 환경의 단일 실행 보장, DB 잠금이나 리더 선출). Spring에서는 `@Scheduled`만으로 단일 실행이 보장되지 않는다.
- 회사 연결: 광고 성과 일 집계와 정산 배치도 구간, 멱등 재실행, 원본 대비 검증이라는 같은 구조라고 연결한다.

## R9. Java와 Spring은 어디서 얼마나 써봤나 (경험형)

- 질문 의도: 필수 스택의 실제 깊이.
- 핵심 답변: 이썸테크에서 Java, Spring MVC, MyBatis, Oracle로 농식품정보서비스 대시보드를 개발하고 Oracle 스키마를 설계했다. 국가소음정보시스템에서는 JSP와 JDBC를 Spring과 MyBatis로 마이그레이션했다. 멋쟁이사자처럼 Java 백엔드 과정에서 Spring 과제로 최우수 코드에 선정됐고, 팀 프로젝트에서 NCP 기반 Docker와 GitHub Actions CI/CD, 테스트와 코드 리뷰를 주도했다. 카카오테크 캠퍼스에서는 Spring 백엔드 코드 리뷰와 1on1 멘토링을 했다.
- 정직한 경계: Spring Boot 상용 서비스를 장기간 운영한 경험은 없다. 대신 같은 기간 NestJS로 트랜잭션, 이벤트, 성능 문제를 운영에서 다뤘다.
- 꼬리: 마이그레이션에서 가장 어려웠던 점, MyBatis와 JPA의 차이(SQL 통제와 객체 매핑의 트레이드오프).
- 회사 연결: C6 답변으로 이어간다.

## R10. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- 질문 의도: 스스로 문제를 정의해 만든 시스템의 설계 판단과, 검색 방식을 근거로 고르는 습관.
- 핵심 답변: 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템입니다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색 방식을 바꾸기 전에 평가 질문부터 고정했습니다. 양성 질문은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나와야 통과, 음성 질문은 빈 결과여야 통과로 쳤습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어 채택하지 않았습니다. 그 74개를 포함한 94개 질문으로 bge 리랭커도 비교했지만 통과가 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸려 채택하지 않았습니다. 이후 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- 판단 기준: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃거나 개선이 없는 방식, 지연만 늘리는 방식은 채택하지 않는다. 모두 기각한 판단이 이 답변의 강점이다.
- 골든 케이스 선정과 지표: 질문은 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본이 아니다. 지표는 응답 예산 안 필수 근거 그룹 통과 수, 후보 50개 안 필수 근거 수, 질문당 추가 지연이다. 결론은 병목이 후보 검색보다 절 선택이라는 것.
- 이력서 정정: 이력서의 골든 케이스 약 145건 문구는 부정확하다. 145건짜리 평가 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- 한계: 합성 표본이고 실제 답변 정확도나 사용자 만족도를 잰 것이 아니다. 자연어 무관 질문 거절은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- 회사 연결: 이 공고에는 AI나 검색 업무가 없다. AI 도구 활용 근거(FIT C8)로만 짧게 쓰고, 재현 가능한 색인과 고정한 평가 질문으로 검증하는 방식이 정산 대사의 재현성 감각과 닿는다고 닫는다.
- 주의: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 먼저 개인 프로젝트라고 밝힌다.
