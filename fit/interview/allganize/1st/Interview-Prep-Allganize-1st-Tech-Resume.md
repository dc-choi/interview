# 올거나이즈 1차, 이력서 기반 기술 질문 (R1~R10)

> 상위 문서: [[Interview-Prep-Allganize-1st|올거나이즈 1차 면접 준비]]. [[My-Tech-Cards]]의 카드 1~7을 R1~R7로 fork하고, 이력서 항목 R8, AI 협업 규약 R9와 개인 프로젝트 카드 하나(R10)를 더했다. 수치는 공개 이력서에 있는 것만 쓰고, 측정 조건을 설명할 수 없으면 정성 표현으로 낮춘다. FDE 면접이므로 각 카드 끝줄을 고객 현장 연결로 바꿨다.

## 공통 말하기 순서

결론, 당시 제약, 선택과 대안, 검증, 한계, 고객 현장 연결. 1차 비대면에서는 90초 안에 결론까지 말하고 깊이는 꼬리질문에 맞춘다.

## R1. 수천 대 IoT 하드웨어의 동시 요청 정합성 (경험형, 카드 1)

- **질문 의도**: 동시성 문제를 재현하고 선택지를 비교할 수 있는지, 과장 없이 한계를 아는지.
- **답변**: 같은 재고 상태를 동시에 바꾸는 요청에서 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한 재시도를 조합했습니다. 충돌이 잦은 쓰기라 낙관적 잠금으로 늦게 충돌을 발견하면 전체를 다시 해야 해서 비관적 잠금을 골랐습니다. 보호 대상이 단일 DB 트랜잭션 안에 있어 분산 락은 쓰지 않았습니다. 동시 요청을 재현해 최종 수량과 재시도 뒤 상태를 확인했습니다.
- **흔한 오답**: NOWAIT가 모든 대기를 없앤다고 말하기. NOWAIT는 해당 잠금 읽기의 행 잠금 대기만 없애고 메타데이터 잠금 등은 남는다.
- **꼬리**: 지금이라면 고정 간격 재시도 대신 지수 백오프와 지터를 검증한다. 급격한 유입은 잠금이 흡수하지 못하므로 업무 키별 순서 큐와 워커 동시성 제한을 함께 검토한다.
- **고객 현장 연결**: 고객 시스템과 연동할 때도 같은 원칙을 쓴다. 우리 쪽에서 잠글 수 없는 외부 원장은 잠금이 아니라 멱등성 키와 대사로 정합성을 확인한다.

## R2. Kafka 대신 EventBridge와 SQS로 발주 자동화 (경험형, 카드 2)

- **질문 의도**: 기술 선택을 조직 여건과 연결해 판단하는지. 공고의 독립적 결정 능력과 직접 연결된다.
- **답변**: 조직 내 Kafka 도입 여건을 고려해 관리형인 EventBridge와 SQS로 후속 처리를 분리했습니다. 워커는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 영구 오류는 격리, 일시 오류만 제한 재시도, 예산을 넘기면 DLQ와 수동 확인으로 보냈습니다.
- **한계를 먼저 말할 것**: Transactional Outbox는 적용하지 않았습니다. DB 커밋 뒤 발행 전에 프로세스가 죽으면 이벤트가 빠질 수 있어서, 다시 설계한다면 상태 변경과 outbox 레코드를 같은 트랜잭션에 저장하고 릴레이가 발행하게 하겠습니다.
- **꼬리**: 리플레이, 강한 순서 보장, 매우 높은 처리량이 핵심이면 Kafka를 다시 비교한다. SQS FIFO는 MessageGroupId 단위 순서를 보장하지만 처리량 한도는 공식 문서로 확인한다.
- **고객 현장 연결**: 고객사마다 쓸 수 있는 인프라가 다르다. 가장 좋은 도구보다 그 환경에서 운영 가능한 도구를 고르고, 한계와 보완 경로를 문서로 남기는 방식을 그대로 가져간다.

## R3. 복합 인덱스로 슬로우 쿼리 99.3% 개선 (경험형, 카드 3)

- **질문 의도**: 수치의 근거와 측정 조건을 설명할 수 있는지.
- **답변**: 최신 상태 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인하고, 업무 키 동등 조건과 최신 시각, 보조 키 정렬 순서에 맞춘 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스와 쿼리 구조를 함께 바꿨습니다. 이력서의 99.3%는 [측정 대상과 조건: 사용자 확인 필요, 예를 들어 같은 쿼리 1건의 전후 실행 시간인지]를 기준으로 말합니다.
- **흔한 오답**: 카디널리티 높은 컬럼을 무조건 앞에 둔다. 실제로는 동등 조건, 범위 조건, 정렬, 반환 컬럼을 쿼리에서 판단한다.
- **꼬리**: 인덱스는 쓰기와 저장 비용을 늘린다. 쿼리 1건 측정값과 배치 전체 시간을 같은 지표로 비교하지 않는다.
- **고객 현장 연결**: 고객 환경의 성능 불만도 재현 조건부터 맞춘다. 데이터 분포가 우리 테스트 환경과 다를 수 있으므로 고객 데이터 기준으로 다시 측정한다.

## R4. Prisma N개 쿼리를 단일 쿼리로 통합해 API 응답속도 90% 향상 (경험형, 카드 4)

- **질문 의도**: ORM 동작을 생성 SQL 수준에서 검증했는지.
- **답변**: 관계를 포함한 조회에서 예상보다 많은 SQL이 나가는 것을 로그로 확인했습니다. 당시 `relationJoins` Preview 기능이 꺼진 설정에서는 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했고, 기능을 켜고 `relationLoadStrategy: 'join'`을 적용해 MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했습니다. 이 사례로 하코 커뮤니티에서 발표했습니다.
- **흔한 오답**: 옵션 이름만 보고 SQL JOIN이 나간다고 단정하기. Prisma 버전과 DB에 따라 생성 형태가 다르다.
- **꼬리**: 조인 전략은 반환 데이터 중복과 DB 부하를 함께 본다. 대부분의 CRUD까지 ORM을 버릴 이유는 아니다.
- **출처**: [Prisma 관계 조회 공식 문서](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries)
- **고객 현장 연결**: 제품이 고객 데이터 규모에서 느려질 때, 추상화 아래에서 실제로 무슨 일이 일어나는지 확인하는 습관이 원인 파악 시간을 줄인다.

## R5. Grafana, Prometheus, Loki 관측과 경보 (경험형, 카드 5)

- **질문 의도**: 장애를 빨리 발견하고 좁히는 체계를 직접 만들었는지.
- **답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었습니다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼습니다. 메트릭은 추세와 사용자 영향, 로그는 개별 원인, 트레이스는 서비스 경계 흐름에 씁니다.
- **흔한 오답**: 사용자 ID나 요청 ID를 메트릭 라벨에 넣는 설계. 제가 실제로 겪은 실수이고, 그래서 라벨 설계 기준을 먼저 말한다.
- **꼬리**: API에는 RED, DB와 큐에는 USE 관점을 적용한다. 경보 기준은 사용자 영향 SLI에서 역산한다. 내부 임계값은 공개하지 않는다.
- **고객 현장 연결**: 온프레미스 고객사는 우리 관측 도구에 접근할 수 없는 경우가 있다. 이때 어떤 로그와 지표를 고객이 수집해 넘겨줄 수 있는지 사전에 합의하는 것이 장애 대응 시간을 좌우한다고 본다. (일반론이며 올거나이즈 방식은 역질문으로 확인)

## R6. Docker 이미지 909MB에서 513MB, 배포 3분 10초에서 2분 20초, Read Replica 도입 (경험형, 카드 6)

- **질문 의도**: 배포 경로와 인프라 전환을 실제로 설계했는지. 우대사항 Cloud, Database 운영에 대응.
- **답변**: 멀티스테이지 빌드로 빌드 도구와 실행 의존성을 분리해 이미지를 43.6% 줄이고 배포 시간을 26.3% 단축했습니다. 트래픽 증가에 맞춰 단일 NGINX 서버 구조를 CloudFront, ELB, ECS Fargate로 옮겼고, RDS Read Replica로 읽기 부하를 나눠 응답속도를 40% 개선했습니다. 쓰기와 쓰기 직후 읽기는 primary로 보냈습니다.
- **꼬리**: alpine은 musl과 네이티브 모듈 호환성, distroless는 디버깅 비용이 있다. Rolling과 Blue/Green은 자원 부담과 롤백 속도로 고른다. k8s는 멀티 워크로드, 복잡한 라우팅이 필요할 때 검토한다.
- **고객 현장 연결**: 폐쇄망 반입에서는 이미지 크기가 곧 반입 시간과 검수 부담이다. 작은 이미지와 재현 가능한 빌드는 온프레미스 배포에서 더 중요해진다고 본다.

## R7. 대형 고객사 PoC를 위한 모듈 중심 아키텍처 (경험형, 카드 7, FDE 핵심)

- **질문 의도**: 고객 요구가 바뀌는 상황에서 결과물을 안전하게 바꿀 수 있는 구조를 만들었는지. FDE 역할과 가장 가까운 질문이다.
- **답변 골격**: PMF 이후 대형 고객사 PoC를 앞두고 요구사항이 자주 바뀌었습니다. NestJS에서 도메인별 모듈과 UseCase를 나누고 의존 방향을 `interface -> application -> domain <- infrastructure`로 두어, 한 고객 요구가 바뀌어도 변경이 해당 모듈 안에 머물도록 했습니다. 계층을 늘리는 게 목표가 아니라 실제로 독립적으로 바뀌는 경계에만 추상화를 뒀습니다.
- **보강 필요**: PoC에서 고객과 직접 요구사항을 조율했는지, 성공 기준을 누가 정했는지는 [사용자 확정 필요]. 고객 대면 범위를 과장하지 않는다.
- **꼬리**: `forwardRef()`가 반복되면 모듈 책임을 다시 나눠야 한다는 신호다. 고객별 요구를 분기 코드로 받을지 설정과 확장점으로 받을지의 기준은 [[Interview-Prep-Allganize-1st-Service|서비스 맥락 문서]]의 S2와 같은 축이다.

## R8. 고객사 온프레미스 이전과 FIDO 명세 분석 (경험형, FDE 핵심)

- **질문 의도**: 고객 환경 제약과 외부 명세를 직접 다룬 경험.
- **답변 골격**: 시솔지주에서 고객사 온프레미스 환경 구축을 위해 AWS 기반 서비스를 옮겼습니다. 영양정보 데이터 정형화를 위해 MongoDB에서 MySQL로 데이터를 이전했습니다. FIDO 서버는 WebAuthn 명세를 직접 분석해 아키텍처를 설계하고 인증을 통과했으며, 사용하던 오픈소스가 명세와 다르게 동작하는 부분을 재현 결과와 함께 이슈로 제기했습니다.
- **보강 필요**: 온프레미스 이전에서 본인이 맡은 범위(환경 차이 분석, 설정 분리, 반입 절차, 검수 대응), 가장 어려웠던 제약, 고객 측 담당자와의 소통 방식을 [사용자 확정 필요]. 기억이 불확실한 세부는 말하지 않는다.
- **꼬리**: 클라우드 관리형 서비스(SQS, S3 등)에 의존한 코드를 온프레미스로 옮길 때는 대체 구성요소, 설정 주입, 기능 차이를 목록으로 만들고 검증 순서를 합의한다는 일반 원칙으로 답한다.

## R9. 팀 AI 협업 규약과 대규모 codebase 분석 (경험형, 우대사항 직접 대응)

- **질문 의도**: AI 코딩 도구를 생산성 도구가 아니라 검증 가능한 작업 흐름으로 쓰는지.
- **답변 ([[My-FIT-Answers]] 10번, 24번 fork)**: AI 협업 규약을 팀 레벨로 표준화해 AI가 건드릴 영역과 건드리면 안 되는 영역을 경로별 `CLAUDE.md`로 명문화하고, 작업 종료 시점에 AI가 스스로 품질을 점검하는 회귀 루프를 만들었습니다. 처음에는 구현보다 느려 보였지만 작은 영역부터 효과를 보여 다른 구성원도 같은 방식을 쓰게 됐습니다. 요구사항 해석, 설계 선택, 결과 채택은 제가 책임집니다.
- **낯선 codebase 분석 절차 (준비할 것)**: 진입점과 모듈 경계 파악, 요청 하나의 호출 흐름 추적, 테스트와 설정에서 실제 계약 확인, AI 요약을 원문과 대조. 이 순서를 실제 사례 하나로 [사용자 확정 필요].
- **꼬리**: AI 결과가 틀리면 테스트, 공식 문서, 실행 결과로 잡는다. 고객 코드와 데이터를 외부 AI 도구에 넣을 수 있는지는 고객 보안 정책이 먼저다.
- **고객 현장 연결**: FDE는 매번 낯선 고객 시스템을 짧은 시간에 이해해야 한다. AI로 탐색 속도를 올리되 원문 대조로 오해를 막는 절차가 그 속도를 안전하게 만든다.

## R10. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서, 우대사항 LLM과 AI 도구)

- **질문 의도**: LLM 기술에 대한 관심을 실제로 만들고 평가해 본 경험으로 보여 주는지. LLM 서비스 운영 경험이 없는 갭을 가장 직접 메우는 근거다.
- **답변**: 개인 프로젝트로, 개발 지식 Markdown을 근거 관계 그래프로 색인하고 그 검색을 MCP 도구와 CLI로 제공하는 시스템을 만들었습니다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했습니다. 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정하고, 응답 크기 예산 안에 그 근거가 모두 나와야 통과로 쳤습니다. 무관한 질문에는 빈 결과가 나와야 통과하는 음성 질문도 넣었습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, BM25와 E5 임베딩 결과를 RRF로 합친 방식을 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 늘지 않았고 기존 통과 사례 4개를 잃었습니다. 이 74개를 포함한 94개 질문으로 bge 리랭커도 붙여 봤지만 통과는 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸습니다. 그래서 BM25, 임베딩, 리랭커 모두 채택하지 않았고, 문제가 후보 검색보다 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다. 새 방식을 측정으로 기각한 것이 이 경험의 핵심이다.
- **골든 케이스 선정과 지표 (확정)**: 평가 질문은 대부분 원문을 보고 만든 합성 질문이다. 양성은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나오면 통과, 음성은 빈 결과여야 통과다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 쟀다.
- **한계를 먼저 말할 것**: 사람이 정답을 검수한 표본이 아니라 합성 표본이다. 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정 기준이다.
- **이력서 정정**: 제출한 이력서에는 골든 케이스 약 145건으로 비교했다고 적혀 있으나 145건짜리 평가 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **꼬리**: nDCG 같은 순위 지표는 왜 안 썼나 (목적이 응답 예산 안에 필요한 근거가 모두 들어가는지였고, 순위 가중 지표를 쓰지 않은 것은 한계로 인정한다).
- **이 회사 공고와의 연결**: 공고의 Agent RAG와 LLM 제품 맥락에서 [[Interview-Prep-Allganize-1st-Tech-JD|J3, J4]]의 검색 품질 진단, 평가 질문 세트와 회귀 비교, 리랭커 논의를 이 경험으로 받는다. 우대사항의 AI 도구 활용은 R9와 함께 답한다. 고객 프로젝트나 운영 서비스 경험이 아니라는 점은 유지한다.
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 면접에서 먼저 개인 프로젝트라고 밝힌다.
