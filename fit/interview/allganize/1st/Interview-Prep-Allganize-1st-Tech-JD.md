# 올거나이즈 1차, JD 기반 기술 질문 (J1~J10)

> 상위 문서: [[Interview-Prep-Allganize-1st|올거나이즈 1차 면접 준비]]. 설계형 질문의 골격은 일반 원리이며 올거나이즈의 실제 구현을 설명하지 않는다. 회사 구현을 아는 것처럼 말하지 않고, 필요하면 확인 질문으로 되돌린다.

## J1. Python 경험이 있나요? (사실형, 자격요건 갭)

- **질문 의도**: 자격요건 충족 여부와, 없다면 얼마나 빨리 전환할 사람인지.
- **답변**: Python 실무 경험은 없습니다. 실무 언어는 TypeScript와 Java였습니다. 대신 [합류 전에 Python으로 만든 결과물: 사용자 확정 필요]로 전환 속도를 보여드리고 싶습니다. 언어 자체보다 비동기 처리, 타입과 입력 검증, 테스트와 패키징처럼 운영에서 문제가 되는 지점을 먼저 맞추겠습니다.
- **개념 대응 (말할 수 있어야 할 것)**: asyncio는 Node처럼 단일 스레드 이벤트 루프에서 코루틴을 스케줄링한다. 이벤트 루프 안에서 동기 블로킹 호출을 하면 전체가 멈추는 점도 같다. 타입 힌트는 런타임에 강제되지 않으므로 외부 입력 검증에는 Pydantic 같은 런타임 검증을 쓴다(TypeScript 타입과 class-validator의 관계와 비슷). CPython 기본 빌드는 GIL 때문에 CPU 바운드 작업이 스레드로 병렬화되지 않아 멀티프로세스를 쓰고, I/O 바운드는 asyncio나 스레드로 처리한다.
- **흔한 오답**: Python 3.13부터 GIL이 사라졌다고 말하기. 3.13부터 GIL을 끈 free-threaded 빌드를 별도로 지원할 뿐 기본 빌드는 여전히 GIL을 쓴다. 준비되지 않은 확장 모듈은 free-threaded 빌드에서도 GIL을 다시 켤 수 있다. 버전별 지원 상태는 공식 문서로 확인한다(2026-09-29 확인).
- **꼬리**: 가상환경과 의존성 고정(venv, lock 파일), 폐쇄망에서 패키지 반입(wheel 사전 다운로드와 내부 미러).
- **출처**: [Python asyncio 문서](https://docs.python.org/3/library/asyncio.html), [Python free-threading 안내](https://docs.python.org/3/howto/free-threading-python.html)
- **조건 표기**: GIL 설명은 CPython 기본 빌드 기준이다.

## J2. Linux 서버에서 장애를 어떻게 좁히나요? (사실형, 자격요건)

- **질문 의도**: 고객사 서버에 혼자 접속했을 때 스스로 원인을 좁힐 수 있는지.
- **답변 순서**: 증상 확인(서비스 상태, 최근 로그) → 자원(CPU, 메모리, 디스크 용량과 inode, 파일 디스크립터) → 네트워크(리스닝 포트, 연결 상태, DNS, 방화벽) → 프로세스(좀비, OOM kill 흔적) → 최근 변경 이력.
- **도구 예**: `systemctl status`, `journalctl -u`, `top`/`htop`, `free -h`, `df -h`, `df -i`, `du`, `ss -tlnp`, `lsof`, `dmesg`(OOM), `curl -v`, `dig`, `docker logs`, `docker stats`.
- **근거 경험**: Amazon Linux 2, Ubuntu 서버와 Nginx, Docker 운영, 42서울 POSIX와 데비안 구축 과제, 리눅스마스터 2급.
- **흔한 오답**: 디스크 용량만 보고 inode 고갈이나 삭제됐지만 열려 있는 파일을 놓치는 것.
- **꼬리**: 고객사 서버에서 root 권한이 없다면 어떤 정보를 누구에게 요청할지 먼저 목록으로 만든다.

## J3. 고객사 사내 문서로 질의응답 RAG를 설계한다면? (설계형)

- **질문 의도**: FDE(SW)의 핵심 업무를 구조적으로 생각하는지.
- **먼저 물을 것**: 문서 종류(PDF, 스캔본, 표가 많은 문서), 규모와 갱신 주기, 사용자와 권한 구조, 답이 틀렸을 때의 비용, 배포 환경(클라우드 가능 여부, 폐쇄망), 성공 기준.
- **답변 골격**: 파싱(OCR과 레이아웃 복원) → 구조 기반 청킹과 `document_id`, `chunk_id`, 원문 위치, 버전 보존 → 임베딩과 BM25 하이브리드 검색, 필요하면 reranker → 문서 권한 필터를 검색 단계에서 적용 → 컨텍스트 구성(중복 제거, 인접 문맥 보강) → 근거 인용이 붙은 생성 → 근거가 없으면 모른다고 답하게 하기.
- **판단 기준**: 대표 질문 세트로 retrieval Recall@k와 답변 정확도, 근거 충실도를 따로 잰다. 주문번호, 규정 조항 번호처럼 정확 식별자 질문이 많으면 키워드 검색 비중을 높인다.
- **대안과 트레이드오프**: 청크를 작게 하면 정밀하지만 문맥이 끊기고, 크게 하면 토큰 비용과 노이즈가 늘어난다. 정답이 구조화 시스템에 있는 질문(재고, 잔액)은 검색이 아니라 API 조회로 라우팅한다.
- **꼬리**: 멀티테넌트 벡터 저장소에서 권한 누락은 교차 유출로 이어진다. 문서의 숨은 지시문을 통한 간접 프롬프트 인젝션을 고려한다.
- **학습 정본**: [[RAG-Retrieval-Engineering]], [[LLM-Application-Security]]

## J4. 고객이 RAG 답변이 엉망이라고 합니다. 어디부터 보나요? (설계형)

- **질문 의도**: 불만을 재현 가능한 문제로 바꾸는 능력. 백엔드 디버깅 순서가 그대로 드러나는 질문이다.
- **답변 골격**: 실패 사례를 먼저 모은다(질문, 기대 답, 실제 답). 각각을 검색 누락, 컨텍스트 구성 손실, 생성 오류, 근거 없는 주장으로 분류한다. 검색 누락이면 파싱과 청킹, 검색 방식, 권한 필터를 확인한다. 생성 오류면 같은 컨텍스트로 모델이나 프롬프트만 바꿔 비교한다.
- **판단 기준**: 고객의 엉망이다를 수치로 바꾼다. 대표 질문 세트를 고객과 함께 만들고 개선 전후를 같은 질문 세트로 비교한다.
- **트레이드오프**: 고객 한 곳의 문제를 고객별 커스텀으로 고칠지 제품 개선으로 올릴지는 재발 범위로 판단한다(S2와 연결).
- **꼬리**: LLM judge는 빠르지만 고위험 도메인(금융, 공공)에서는 사람 표본 검토를 같이 둔다.
- **내 경험 연결**: Prisma 조회 지연을 추측 대신 로그와 실행 계획으로 좁힌 방식과 같다. 층을 나눠 한 번에 한 변수만 바꾼다.

## J5. 폐쇄망 온프레미스에 AI 솔루션을 배포할 때 고려할 것은? (설계형)

- **질문 의도**: 온프레미스 제약을 상상할 수 있는지. FDE(Infra)와 협업할 때 필요한 공통 언어.
- **답변 골격**: 반입(컨테이너 이미지, 모델 가중치, Python 패키지를 사전 패키징하고 해시로 무결성 확인) → 자원(GPU 유무와 메모리, 모델 크기, 동시 사용자 수) → 의존성 대체(클라우드 관리형 서비스를 쓸 수 없으면 대체 구성요소) → 설정 분리(고객별 값을 이미지 밖으로) → 관측(고객이 수집해 줄 수 있는 로그와 지표 합의) → 업데이트와 롤백 경로 → 보안 심사 대응(데이터가 망 밖으로 나가지 않음을 증명).
- **트레이드오프**: 고객별 맞춤을 늘릴수록 업데이트 비용이 커진다. 표준 배포 단위와 고객별 설정의 경계를 먼저 정한다.
- **내 경험 연결**: 고객사 온프레미스 이전(R8), 멀티스테이지로 줄인 이미지(R6), 설정과 비밀을 이미지에서 분리한 원칙.
- **꼬리**: LLM 디코드는 연산보다 메모리 대역폭에 묶이므로 GPU 선택은 TOPS보다 메모리 용량과 대역폭을 먼저 본다. 양자화는 읽을 바이트를 줄여 속도와 메모리에 도움이 되지만 품질 영향을 같은 평가 세트로 확인한다.
- **학습 정본**: [[LLM-Inference-Bottlenecks]]

## J6. 에이전트로 고객 업무를 자동화할 때 무엇을 조심하나요? (설계형)

- **답변 골격**: 먼저 에이전트가 필요한지 판단한다. 절차가 확정되고 감사가 필요한 업무(정산, 보고)는 정해진 순서의 체인이 맞고, 탐색적인 업무에만 에이전트를 쓴다. 에이전트를 쓰면 도구 권한을 최소로, 되돌릴 수 없는 행동(메일 발송, 결제, 삭제) 직전에는 사람 승인을 둔다. 권한 검사는 프롬프트가 아니라 LLM 밖의 결정적 시스템에서 강제한다.
- **트레이드오프**: 에이전트는 시작이 가볍지만 같은 절차를 반복할 때마다 탐색 비용과 비결정성이 생긴다. 체인은 예측 가능하지만 요구가 바뀌면 재설계 비용이 든다.
- **꼬리**: 시스템 프롬프트는 비밀 저장소도 보안 경계도 아니다. 출력이 SQL이나 셸로 흘러가면 기존 인젝션이 재현되므로 출력도 불신한다.
- **학습 정본**: [[LLM-Workflow-Patterns]], [[LLM-Application-Security]]

## J7. AI 코딩 도구로 처음 보는 대규모 codebase를 어떻게 파악하나요? (경험형, 우대사항)

- **답변**: R9의 절차를 쓴다. 진입점과 모듈 경계 → 요청 하나의 흐름 추적 → 테스트와 설정으로 실제 계약 확인 → AI 요약은 원문 대조. 규칙 파일로 AI가 볼 범위와 금지 영역을 먼저 정한다.
- **꼬리**: 고객 코드를 외부 AI 서비스에 넣을 수 있는지는 고객 보안 정책이 먼저다. 불가하면 로컬 도구나 승인된 환경만 쓴다.

## J8. Kubernetes 경험이 있나요? (사실형, 우대사항 갭)

- **답변**: 운영 경험은 없고 ECS Fargate로 컨테이너를 운영했습니다. 개념 대응으로 설명드리면 ECS 서비스와 태스크 정의는 Deployment와 Pod 스펙, 헬스체크는 readiness와 liveness probe, 시크릿 주입은 Secret과 환경변수 또는 볼륨, 서비스 오토스케일링은 HPA에 대응합니다.
- **흔한 오답**: liveness와 readiness를 같은 것으로 말하기. readiness 실패는 트래픽에서 빼고, liveness 실패는 컨테이너를 재시작한다.
- **꼬리**: 폐쇄망 k8s에서는 내부 이미지 레지스트리와 이미지 pull 정책이 먼저 문제가 된다.
- **출처**: [Kubernetes probes 문서](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)
- **조건 표기**: ECS와 k8s의 대응은 개념 수준이며 기능이 1대1로 같지 않다.

## J9. LLM이 틀린 답을 하면 고객에게 어떻게 설명하나요? (설계형)

- **답변 골격**: 환각은 제거가 아니라 통제의 대상이라고 먼저 합의한다. 근거 인용, 근거가 부족하면 답하지 않기, 오류 비용이 큰 업무에는 사람 검토를 둔다. 정확도 약속은 고객과 함께 만든 평가 세트의 수치로만 한다.
- **트레이드오프**: 답하지 않기를 늘리면 정확도는 오르지만 사용자 만족이 떨어질 수 있다. 규정, 금전이 걸린 답변은 정확도 우선으로 분기한다.
- **학습 정본**: [[LLM-Eval-Strategy]]

## J10. 독립적으로 결정한 기술 판단과 그 결과 (경험형, 자격요건)

- **답변**: R2를 쓴다. 조직 여건에서 Kafka 대신 관리형 큐를 고른 근거, 포기한 것(리플레이, 강한 순서), 보완한 것(멱등 소비, DLQ), 남은 한계(Outbox 미적용)를 한 흐름으로 말한다.
- **꼬리 대비**: 틀렸다고 판단되면 어떻게 되돌리나. 되돌림 조건(처리량, 순서 요구가 바뀔 때)을 미리 적어 두는 방식으로 답한다.
