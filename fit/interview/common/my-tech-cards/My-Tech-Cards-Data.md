## 카드 1, IoT 입력 동시 갱신 정합성, DB Lock 전략

**결론**: IoT 입력이 동시에 같은 재고 상태를 바꾸던 경로에서 `SELECT ... FOR UPDATE NOWAIT`와 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했다. 당시에는 짧은 고정 간격을 사용했고, 현재 다시 설계한다면 동시 재시도 집중을 줄이기 위해 지수 백오프와 지터를 함께 검증한다.

**문제, 판단, 행동, 결과**:

- 충돌 빈도가 높은 갱신은 낙관적 잠금으로 늦게 충돌을 발견하면 작업 전체를 다시 해야 한다. 변경 전에 경합을 조정하는 비관적 잠금이 더 단순하다고 판단했다.
- 잠금 대상과 독립적인 입력 검증과 외부 호출만 트랜잭션 밖에서 끝냈다. 변경 가능한 상태에 의존하는 불변식은 잠금 읽기 뒤 다시 검증하고, 트랜잭션 안에는 이 검증, 상태 갱신과 기록만 넣었다. 여러 대상을 함께 갱신할 때는 업무 키 순서를 통일했다.
- 보호 대상이 단일 데이터베이스 트랜잭션 안에 있었으므로 별도 분산 잠금보다 데이터베이스 잠금을 우선했다. 여러 저장소나 외부 시스템을 한 임계 구역으로 묶어야 할 때만 분산 잠금을 다시 검토한다.
- 동시 요청을 재현해 최종 수량, 잠금 실패, 재시도 뒤 상태를 확인했고, 충돌을 조용히 덮지 않고 제한된 실패 경로로 드러내도록 했다.

**한계와 꼬리 질문**:

- `NOWAIT`는 해당 잠금 읽기의 대기를 없앨 뿐, 이후 쿼리의 잠금이나 메타데이터 대기까지 없애지는 않는다.
- 락 순서는 데드락 확률을 낮추지만 완전한 예방책은 아니다. 데드락 오류는 새 트랜잭션에서 제한 재시도하고, 반복되면 잠금이 필요한 갱신 자체를 줄일 방법을 찾는다.
- 실제 급격한 유입을 흡수해야 한다면 업무 키별 순서 보장 큐와 제한된 워커 동시성도 함께 검토한다. 잠금은 유입량을 흡수하지 못한다.
- 읽기 중심이거나 충돌이 드문 편집 작업은 버전 컬럼을 둔 조건부 갱신이 더 적합할 수 있다.

**추가 꼬리 질문**:

- 여러 읽기와 쓰기가 하나의 업무 불변식을 지켜야 할 때만 트랜잭션으로 묶고, 외부 호출과 오래 걸리는 계산은 잠금 범위 밖으로 뺀다.
- 외래 키는 같은 데이터베이스 안에서 참조 무결성이 업무 규칙이고 삭제, 갱신 정책을 명확히 정할 수 있을 때 둔다. 외부 시스템 식별자는 별도의 검증과 대사 경로를 둔다.
- 큰 스키마 변경은 호환 컬럼 추가, 배치 백필과 검증, 읽기 경로 전환, 구 컬럼 제거의 expand-and-contract 순서로 진행하고, 잠금과 복제 지연을 관측하며 중단과 롤백 경계를 둔다.

## 카드 2, EventBridge와 SQS 비동기 처리

**결론**: 실제 적용에서는 도메인 상태 변경 뒤의 후속 처리를 EventBridge와 SQS로 분리하고, 워커가 멱등하게 소비하도록 설계했다. 수동으로 이어지던 후속 업무를 자동화하되, 실패는 재시도와 수동 확인 경로로 분리했다. Transactional Outbox는 적용하지 않았고, DB 커밋과 이벤트 발행 사이의 유실 가능성을 줄이기 위한 개선안으로 남겼다.

**문제, 판단, 행동, 결과**:

- 상태 변경과 외부 연동을 한 요청에 모두 묶으면 느린 의존성 하나가 핵심 상태 변경까지 실패시킨다. 이벤트를 전달해 후속 처리를 비동기로 분리했다.
- 실제 구조는 핵심 상태 변경을 먼저 확정한 뒤 EventBridge와 SQS로 후속 작업을 전달했다. 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했다.
- 영구 오류는 즉시 격리하고, 네트워크나 일시 부하 같은 오류만 제한 재시도한다. 재시도 예산을 넘기면 DLQ와 수동 확인 경로로 보낸다.
- 운영 여력과 필요한 전달 보장을 비교해 관리형 큐를 골랐다. 리플레이, 강한 순서 보장, 매우 높은 처리량이 핵심이면 Kafka 같은 브로커를 다시 비교한다.

**한계와 꼬리 질문**:

- 실제 적용의 한계는 DB 커밋 뒤 프로세스 중단이나 발행 실패가 나면 이벤트가 누락될 수 있다는 점이다. 당시에는 발행 재시도와 운영 확인으로 다뤘지만 원자적으로 닫히지 않았다.
- 지금 다시 설계한다면 상태 변경과 Outbox 레코드를 같은 DB 트랜잭션에 저장하고 릴레이가 발행하도록 보강한다. Outbox 릴레이와 큐 소비는 모두 중복 가능성이 있으므로 정확히 한 번 처리라고 주장하지 않고, 업무 키 단위 중복 제거와 상태 전이 검증을 유지한다.
- 기존 도메인 로직을 재사용하고 데이터베이스 연결과 워커 동시성을 직접 제어해야 해 컨테이너 워커를 택한 경험이 있다. 짧고 독립적인 작업이면 서버리스 소비자도 적합하다.
- 순서가 핵심인 업무는 FIFO와 업무 키 그룹화를 검토하되, 순서 보장 범위와 처리량 제약을 먼저 확인한다.

## 카드 3, 실행 계획 기반의 슬로우 쿼리 개선

**결론**: 최신 상태를 찾는 조회가 느려졌을 때 실행 계획을 먼저 확인하고, 동등 조건과 정렬 순서를 맞춘 복합 인덱스와 쿼리 구조를 함께 조정했다.

**문제, 판단, 행동, 결과**:

- 최신 레코드를 찾는 경로에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했다.
- 업무 키로 동등 조건을 건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 설계했다.
- 카디널리티, 조건 순서, 정렬 방향을 함께 보고, 인덱스가 실제로 정렬과 상위 레코드 접근에 쓰이는지 실행 계획으로 재확인했다.
- 조회 지연을 의미 있게 줄였지만, 데이터 분포와 캐시 상태가 바뀌면 효과도 달라지므로 변경 뒤에도 다시 측정하는 것을 결과의 일부로 남겼다.

**측정 경계**:

- 전체 조회 안의 서브쿼리 관측값과 별도로 측정한 쿼리 1건의 전후 결과는 같은 지표로 비교하지 않는다.
- 배치 전체 시간은 애플리케이션 처리와 네트워크 왕복을 포함한 별도 end-to-end 지표로 구분한다.
- 실행 환경, cache 상태, 표본 수와 percentile이 기록되지 않은 수치는 다른 조건과 직접 비교하지 않는다.

**한계와 꼬리 질문**:

- 복합 인덱스는 읽기를 돕는 대신 쓰기와 저장 비용을 늘린다. 인접한 쓰기 경로와 다른 조회에 미치는 영향을 함께 본다.
- 컬럼 순서는 높은 카디널리티 하나로 결정하지 않는다. 동등 조건, 범위 조건, 정렬, 그룹화, 필요한 반환 컬럼을 실제 쿼리에서 판단한다.
- 필요한 컬럼이 모두 인덱스에 있으면 커버링 인덱스로 테이블 접근을 줄일 수 있지만, 인덱스를 무작정 넓히지는 않는다.

**추가 검증**: 같은 실행 환경과 cache 조건에서 Before/After P99, QPS를 비교하고, 인덱스로 인한 쓰기 비용을 모니터링한다.

## 카드 4, Prisma 관계 조회와 API 지연 분석

**결론**: Prisma 관계 조회의 성능은 ORM 이름이나 옵션 설명이 아니라 생성 SQL과 실행 계획으로 검증했다. 여러 관계가 별도 쿼리로 내려가던 경로에서 `relationLoadStrategy: 'join'`을 검토하고 실제 SQL을 확인해 필요한 경로만 조정했다.

**정확성 경계**: 당시 `relationJoins` Preview 기능이 비활성인 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했다. 이후 기능을 활성화하고 `relationLoadStrategy: 'join'`을 적용했으며, MySQL에서 correlated subquery와 JSON aggregation 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했다. 옵션 이름만으로 SQL `JOIN`을 가정하지 않는다. ([Prisma 관계 조회 공식 문서](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries))

**문제, 판단, 행동, 결과**:

- 관계를 포함한 조회에서 예상보다 많은 SQL이 발생하는 것을 로그와 요청 추적으로 확인했다. 전통적인 lazy loading과 같은 현상이라고 단정하지 않고 당시 설정과 생성 SQL을 분리해 봤다.
- 공식 문서와 실행 계획을 확인한 뒤 조인 전략을 적용했다. 데이터베이스에서는 조인 또는 상관 서브쿼리와 JSON 집계처럼 구현될 수 있으므로 옵션 이름만으로 형태를 단정하지 않았다.
- 성능이 중요한 조회 경로의 왕복과 지연을 줄였고, 나머지 경로는 타입 안정성과 변경 용이성을 유지했다.

**한계와 꼬리 질문**:

- 조인 전략은 호출 수를 줄일 수 있지만 반환 데이터 중복, 집계 비용, 데이터베이스 부하를 함께 확인해야 한다.
- Prisma 버전과 관계 로딩 설정에 따라 동작이 달라진다. 적용 전에는 공식 문서, SQL 로그, 실행 계획을 같은 환경에서 확인한다.
- 복잡한 윈도우 함수, 대량 연산, ORM 생성 SQL이 부적절한 경로만 명시적 쿼리로 낮춘다. 대부분의 CRUD까지 ORM을 버릴 이유는 아니다.
