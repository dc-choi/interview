# 내 이력서 기반 기술 답변 카드, 관측과 인프라

## 카드 5, 관측성 설계

**결론**: Grafana, Prometheus, Loki를 사용해 로그와 메트릭을 연결했고, 요청 식별자는 로그 본문으로 추적하되 메트릭 라벨에는 넣지 않았다. 트레이스를 추가할 때도 같은 카디널리티 원칙을 적용한다.

**문제, 판단, 행동, 결과**:

- 구조화한 JSON 로그에 `x-request-id`를 남기고, 메트릭 라벨은 HTTP method, 정규화한 route, status처럼 제한된 값으로 구성했다. 요청 지연은 histogram으로 보도록 했다.
- 메트릭은 추세와 사용자 영향을, 로그는 개별 원인과 맥락을, 트레이스는 서비스 경계를 넘는 흐름을 파악하는 데 쓴다. 서로 대체하는 도구가 아니라 탐색 순서를 줄이는 조합이다.
- 고유 식별자를 라벨로 넣으면 시계열 수가 급증해 대시보드와 경보가 불안정해질 수 있다. 식별자는 로그나 trace context에 남기고, 메트릭에는 exemplar 같은 연결 방식을 검토한다.
- SaaS, 클라우드 기본 도구, 자체 운영 스택을 비용 하나로 단정하지 않고 데이터 보존, 운영 부담, 관측 요구를 함께 비교했다. 당시에는 운영 가능한 범위의 오픈소스 조합을 선택했다.

**한계와 꼬리 질문**:

- 경보 기준은 과거 숫자를 복사하지 않는다. 사용자 영향 SLI와 정상 구간을 관찰한 뒤 팀이 합의한 기준으로 정한다.
- API에는 RED, 데이터베이스와 큐 같은 자원에는 USE 관점을 적용해 오류와 원인 지표를 구분한다.
- 장애가 나면 먼저 영향 범위와 현재 대응을 공유하고, 서비스 복구를 우선한 뒤 타임라인, 원인, 재발 방지 조치를 포스트모템으로 남긴다. 한 건의 중요한 실패가 비율 지표에 묻지 않는지도 별도 점검한다.
- 오류, 지연, 적체, 데이터베이스 포화 같은 실패를 재현해 알림에서 원인 확인과 복구 판단까지 이어지는지 검증한다.

## 카드 6, 컨테이너 이미지와 배포 경로

**결론**: Docker 멀티스테이지로 빌드 산출물만 실행 이미지에 넣고, 관리형 컨테이너 실행 환경으로 배포 경로를 점진적으로 옮겼다. 결과 수치보다 재현 가능한 배포, 롤백, 종료 절차를 우선했다.

**문제, 판단, 행동, 결과**:

- 빌드 도구와 실행 의존성을 분리해 이미지의 불필요한 내용을 줄이고, 실행 환경과 설정 주입을 배포 산출물에서 분리했다.
- 프로토콜과 고정 endpoint 같은 호환성 요구가 로드밸런서 선택을 좌우한다는 것을 경험했다. 웹 요청과 기기 통신을 같은 방식으로 단정하지 않고, 접근 경로의 요구부터 확인한다.
- Rolling 배포는 자원 부담을 낮추지만 즉시 전환과 빠른 롤백이 중요한 상황에서는 Blue/Green을 비교한다. 관리형 태스크 환경과 Kubernetes도 운영 인력, 배포 복잡도, 장애 복구 요구를 기준으로 골랐다.
- 쓰기와 쓰기 직후 읽기는 primary로 보내고, 일정한 지연을 허용할 수 있는 조회만 replica를 검토했다. 복제 지연을 숨기지 않는 것이 일관성 설계의 전제다.

**한계와 꼬리 질문**:

- 자동 확장은 CPU 같은 자원 수치만으로 정하지 않는다. 큐 작업은 실행 중인 워커 수를 고려한 backlog와 가장 오래된 메시지의 대기 시간을 함께 본다.
- 다중 가용 영역은 리전 장애를 해결하지 않는다. RTO와 RPO를 먼저 정하고, 백업 복원, 대기 환경, 전환과 복귀 훈련을 별도 계획으로 둔다.
- 컨테이너 종료 신호를 받으면 새 요청을 막고 진행 중 요청을 정리한다. 메시지 워커는 현재 작업의 완료 또는 재전달 경계를 명확히 한다.
- 런타임 비밀은 코드와 이미지에서 분리하고, 최소 권한, 회전, 감사가 가능한 비밀 저장소와 단기 자격 증명을 사용한다.
- 새 버전 배포, 중단, 롤백, 설정 주입, 로그 수집이 각각 독립적으로 재현되는지 확인한다.

## 카드 7, Clean Architecture와 NestJS 모듈 경계

**결론**: NestJS에서 Controller, UseCase, Domain, Repository port, 인프라 구현을 분리해 도메인 규칙이 프레임워크와 저장소 구현에 끌려가지 않도록 했다.

**문제, 판단, 행동, 결과**:

- 같은 도메인에서도 API 응답과 파일 내보내기처럼 사용자 의도가 다른 경로는 UseCase를 나눴다. 핵심 규칙은 공유하되 입출력 요구가 도메인에 스며들지 않도록 했다.
- 의존 방향은 `interface -> application -> domain <- infrastructure`로 두고, Repository는 Symbol token 또는 추상 타입으로 바인딩했다. 그러면 도메인 규칙을 프레임워크 없이 테스트하기 쉽다.
- 계층을 늘리는 것 자체가 목표는 아니다. 실제로 교체되거나 독립적으로 바뀌는 경계에만 추상화를 두고, 단순한 흐름에는 불필요한 인터페이스를 만들지 않는다.

**한계와 꼬리 질문**:

- `forwardRef()`는 순환 참조를 임시로 풀 수 있지만, 반복되면 모듈 책임이나 의존 방향을 다시 나눠야 한다는 신호다.
- NestJS에서 middleware는 요청 전처리, guard는 인증과 인가, interceptor는 요청과 응답 변환, pipe는 입력 변환과 검증, exception filter는 예외 변환을 맡는다. 호출 순서와 실패 경계를 이해하고 적용한다.
- provider는 대부분 singleton으로 두고, 요청별 맥락이나 매 주입마다 새 인스턴스가 필요한 경우에만 request 또는 transient scope를 선택한다.
- 도메인 규칙이 프레임워크 없이 테스트되고, 인프라 변경이 호출자 전체에 퍼지지 않는지로 경계의 효과를 검증한다.

## 카드 8, Cache-Aside와 스탬피드 방어

**결론**: 캐시는 원본 데이터의 대체물이 아니라 읽기 부하를 줄이는 보조 경로다. 외부 메타데이터를 매 요청마다 조회하던 경로에서 초기 적재와 저장소 캐시를 적용해 지연을 줄였고, 이후에는 Cache-Aside, 무효화, 만료 동시성을 구분해 설계한다.

**문제, 판단, 행동, 결과**:

- 요청 전에 적재하는 Cache Warming과, 미스가 나면 원본을 읽어 적재하는 Cache-Aside는 다른 패턴이다. 당시 경험은 초기 적재에 가까웠고, 모든 캐시 문제에 같은 답을 적용하지 않는다.
- Cache-Aside는 보통 읽기 미스 시 원본 조회와 적재, 쓰기 뒤 무효화를 조합한다. TTL은 안전망일 뿐 갱신 직후의 일관성 경계를 대신 정해주지 않는다.
- 인기 키가 함께 만료되면 원본 저장소가 몰릴 수 있다. TTL jitter, 요청 병합이나 mutex, 백그라운드 갱신, 오래된 값 허용 중 데이터 성격에 맞는 방법을 고른다.
- Redis 자료구조도 접근 패턴으로 고른다. 순위, 중복 제거, 플래그, 객체 조회는 각각 Sorted Set, Set, Bitmap, Hash 같은 선택지의 트레이드오프가 다르다.

**한계와 꼬리 질문**:

- 캐시가 실패하면 원본 저장소로 돌아가되, 동시에 몰리는 상황은 연결 풀 제한과 요청 제어로 보호한다. 캐시는 장애를 새 병목으로 옮기면 안 된다.
- Write-Through는 캐시와 원본을 함께 갱신하는 선택지이지만, 부분 실패와 순서 역전 복구가 필요하다. 저장소가 둘이라는 사실만으로 원자성이 생기지는 않는다.
- 외부에서 주기적으로 가져오는 데이터는 신선도와 정확성을 나눠 설계한다. 변경 빈도에 맞는 TTL, 스키마 검증, 부분 실패 격리, 마지막 성공 스냅샷, 실패 누적 알림을 함께 둔다.
- 캐시 누락, 동시 만료, 원본 장애, 무효화 지연을 재현하고 사용자 결과가 허용된 일관성 경계 안에 있는지 검증한다.
