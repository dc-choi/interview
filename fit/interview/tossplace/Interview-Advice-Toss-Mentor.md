# 토스 계열 면접 조언과 적용 회고

> 2026-03-11에 멘토 역할의 제3자에게 받은 조언을 요약하고, 2026-06-09 토스플레이스 1차 면접 경험과 대조한 기록이다. 제3자의 표현은 원문으로 옮기지 않는다.

## 받은 조언 요약

1. Node.js 역할의 채용 난도가 높을 수 있으므로 JD와 본인 경험의 연결을 깊게 준비한다.
2. 기술 선택만 설명하지 말고 데이터 정합성 문제가 사용자에게 어떻게 보이고 어떻게 복구되는지까지 연결한다.
3. 이력서와 포트폴리오에서 시작하는 꼬리 질문을 예상한다.
4. JD 요구 기술마다 실제 문제 해결 경험과 한계를 준비한다.
5. 정상 흐름뿐 아니라 내부 통신이나 외부 연동이 실패했을 때의 동작도 설명한다.

이 조언은 한 사람의 경험 범위에서 나온 준비 관점이며 토스 계열 전형 전체의 공식 기준이 아니다.

## 1차 면접 대조

| 조언 | 2026-06-09 토스플레이스 1차에서 경험한 내용 | 당시 판단 |
| --- | --- | --- |
| 포트폴리오 중심 질문 | 제출한 과제 코드와 설계 선택에서 꼬리 질문이 이어졌다. | 적중 |
| 데이터 정합성 | 동시 요청 충돌과 중복을 막는 불변식, 저장소에 따른 제어 방식이 주요 주제였다. 사용자 표시와 복구까지는 다루지 않았다. | 부분 적중 |
| 기술 내부 동작 | 단일 프로세스 알림과 분산 메시징의 가정을 구분하는 질문이 있었다. 통신 단절 시나리오는 다루지 않았다. | 부분 적중 |
| 트러블슈팅 경험 | 1차에서는 제출물의 설계 근거가 중심이어서 별도 경험 질문은 없었다. | 미확인 |
| 설계 깊이 | 정책이 늘어날 때의 구조와 도메인 모델, 저장 모델의 책임을 끝까지 설명해야 했다. | 적중 |

- 결과: 1차 탈락
- 본인 해석: 공식 사유를 받지 않았으므로 특정 질문 하나를 탈락 원인으로 단정하지 않는다. 라이브로 설계 경계를 더 명확히 설명하는 연습은 통제 가능한 보완점으로 남겼다.

## 다음 지원에 적용할 것

- 정합성이 깨졌을 때 탐지, 사용자 상태, 복구와 재대사를 한 흐름으로 설명한다.
- JD 요구 기술별 트러블슈팅 경험을 [[My-Tech-Cards]]에서 선별한다.
- 외부 연동 실패 시 타임아웃, 재시도, 서킷 브레이커와 멱등 재처리를 함께 설명한다.
- 제출한 코드의 정책 위치, 확장 비용, 도메인 모델과 저장 모델의 차이를 미리 점검한다.
- **지원 이력의 성장 곡선**: 2025-08 토스 Node.js 포지션 과제 탈락 → 2026-05 토스플레이스 과제 통과, 1차 면접 탈락. 과제 단계는 넘었고 다음 보완점은 설계 깊이를 라이브로 표현하는 일이다.
- 과거 지원 결과는 성장 경로로 보되 회사의 평가 기준이나 탈락 원인을 추정하지 않는다.
