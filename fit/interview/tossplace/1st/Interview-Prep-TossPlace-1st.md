# 토스플레이스 1차 직무 면접 준비 기록

> 일시: 2026-06-09 11:00, 화상 면접. 사전 과제 통과 뒤 진행한 1차 직무 면접의 본인 준비 기록이다. 과제 원문, 코드, 파일 경로, 비공개 요구사항과 제3자 발화는 제외하고, 당시의 설계 판단과 답변을 보존한다.

## 준비의 중심

| 주제 | 당시 설명한 접근 |
| --- | --- |
| 상태 전이 | 충돌한 요청은 대기로 남기고, 자원이 비면 확정 상태와 충돌하지 않는 항목만 승격한다. |
| 동시성 | 확정 상태 조회, 판단, 쓰기를 하나의 임계구역으로 보고 데이터베이스별 직렬화 수단을 구분한다. |
| 알림 | 알림 의미, 메시지 구성, 실제 전송을 분리한다. 이벤트와 리스너 분리는 구현했지만 영속 Outbox나 전달 보장은 구현하지 않았다. |
| 보안 | 비밀값의 평문 노출을 줄이고, 인증과 인가를 다른 책임으로 둔다. |
| 검증 | 순수 규칙은 단위 테스트, 저장소와 요청 경계는 통합 테스트로 검증한다. |

## 본인 답변 드릴

### 상태 전이와 대기 처리

충돌한 요청을 곧바로 거절하지 않고 대기 상태로 보관했다. 기존 확정 항목이 사라지면 대기를 생성 시각 순서로 검토하고, 동률은 결정적인 식별자로 정렬했다. 현재 확정 집합과 겹치지 않는 항목만 승격하고, 방금 승격한 항목도 즉시 확정 집합에 넣었다. 그래서 선두 항목이 막혀도 뒤의 실행 가능한 항목을 검토하면서, 한 번의 처리 안에서도 확정 항목끼리 겹치지 않는 불변식을 유지한다.

시간 구간은 끝 시각이 다음 항목의 시작 시각과 같을 때 충돌하지 않는 반열림 구간으로 설명했다. 이 규칙과 승격 정책을 별도 도메인 모델에 두어, 저장소 없이도 경계 사례를 검증할 수 있게 한 점을 강점으로 제시했다.

### 동시 요청과 트랜잭션

핵심 위험은 같은 자원의 확정 상태를 두 요청이 동시에 바꾸는 경우였다. 당시 과제의 SQLite 실행 환경에서는 쓰기 직렬화 특성을 전제로 했지만, 이것만으로 운영 환경의 동시성 문제가 해결된다고 일반화하지 않았다. 관계형 데이터베이스에서는 자원 또는 자원과 날짜 단위의 잠금, 충돌을 거부하는 데이터베이스 제약, 데드락 재시도 중 무엇을 선택할지 업무 불변식과 데이터베이스 기능에 맞춰 결정해야 한다고 답했다.

MySQL이라면 `SELECT FOR UPDATE` 같은 자원 잠금을, PostgreSQL이라면 겹치는 확정 구간을 거부하는 exclusion 제약도 후보로 들었다. 락 획득 순서를 통일하면 데드락 가능성을 줄일 수 있지만 제거할 수는 없으므로, 실패한 트랜잭션을 제한적으로 다시 실행하는 경로까지 있어야 한다고 현재 답변을 교정했다.

### 알림 확장과 전달 경계

새 채널을 넣을 때 핵심 상태 전이 코드를 고치지 않도록 전송 구현을 분리했다. 상태 변경 뒤의 후속 처리를 이벤트와 리스너로 분리해 한 수신자의 전송 실패가 핵심 상태 변경을 되돌리지 않게 했다. 다만 인프로세스 이벤트는 커밋과 외부 전송을 원자적으로 묶지 못한다. 당시 구현에 Transactional Outbox는 없었고, 재시도 가능한 영속 이벤트와 소비자 멱등성은 운영 확장 시의 개선안으로 구분했다.

당시 설명은 알림의 의미, 채널과 무관한 메시지 구성, 실제 전송 구현의 세 책임을 나누는 것이었다. 취소처럼 곧 사라질 상태의 알림도 만들 수 있도록 트랜잭션 안에서 필요한 값을 스냅샷으로 만들고, 실제 전송은 커밋 이후로 미루는 의도를 설명했다. 리마인더는 중복 방지 표식을 썼지만 발송 전에 표식이 기록되면 실패 시 유실될 수 있으므로, 중요한 알림에는 Outbox와 멱등 소비가 더 적합하다.

### 인증, 인가와 조회

사람이 만드는 비밀번호는 느린 비밀번호 해시가 필요하지만, 충분히 긴 무작위 비밀값은 해시 저장과 상수 시간 비교를 적용할 수 있다고 설명했다. 인증 실패는 인증 경계에서, 권한 부족은 업무 규칙 또는 데이터 접근 경계에서 구분했다. 목록 조회는 응답을 모두 만든 뒤 걸러내지 않고, 조회 조건 자체에 권한 범위를 넣어야 한다는 원칙을 사용했다.

무작위 비밀값의 원문은 발급 시 한 번만 보여 주고, 이후에는 표시용 접두부로 후보를 찾은 뒤 해시를 비교하는 흐름을 준비했다. 폐기는 삭제보다 상태를 남겨 감사 가능성을 유지하고, 비소유자에게 존재 여부를 드러내지 않으며, 인증 수단으로 새 인증 수단을 발급하는 권한 상승도 막아야 한다고 설명했다. 다만 권한 범위 구조를 만든 것과 실제 요청마다 인가를 적용한 것은 다르며, 당시 후자는 미완성이었다.

### 테스트와 성능 검증

대기 승격 같은 순수 규칙은 빠른 단위 테스트로, 요청과 저장소의 결합은 실제 SQLite 기반 통합 테스트로 확인했다. 시간과 전송은 제어 가능한 의존성으로 두어 재현성을 확보했다. 사용자 이름 접두 검색은 대소문자 구분 없는 인덱스와 실행 계획으로 검증했으며, 입력 길이, 결과 제한, 페이지 경계까지 함께 설계해야 한다는 보완점도 남겼다.

SQLite의 대소문자 구분 없는 `LIKE`가 일반 이진 콜레이션 인덱스를 사용하지 못할 수 있어, 검색 조건과 같은 콜레이션의 접두 인덱스를 두고 실행 계획 변화를 확인했다. 다른 데이터베이스로 옮기면 인덱스 규칙과 테스트 격리 비용이 달라지므로, 실행 SQL과 계획을 다시 확인해야 한다.

## 코드 검토에서 확인한 보완점

아래는 공식 면접 피드백이 아니라, 당시 과제 구현을 다시 읽어 확인한 본인 점검 결과다.

1. 대기 확정 알림의 수신 대상에 주최자가 빠질 수 있었다.
2. 존재하지 않는 참조를 입력했을 때 애플리케이션 검증과 데이터베이스 제약이 모두 부족한 경로가 있었다.
3. 날짜만 바꾸지 않은 일정 수정과 자정을 넘는 시간 구간은 충돌, 과거 시각 검증의 경계가 약했다.
4. 다중 인스턴스에서 스케줄러의 중복 실행과 발송 전 마킹에 따른 유실 가능성을 별도로 닫아야 했다.
5. 권한 범위를 위한 구조와 실제 인가 검증은 분리돼 있었고, 후자를 적용해야 했다.
6. 허용 알고리즘 제한과 인증 오류 메시지 일반화는 별도 보안 하드닝 항목이었다.
7. 검색 입력 최소 길이, 결과 제한, 경쟁 요청 테스트가 부족했다.

## 처리된 항목과 미처리 항목의 구분

- 쿠키의 `httpOnly`, 운영 환경의 `secure`, `SameSite` 설정과 만료는 적용했지만, `SameSite`만으로 상태 변경 요청의 모든 CSRF 위험이 사라진다고 말하지 않는다.
- 출력 DTO의 허용 필드와 그레고리력 날짜 검증은 처리된 강점이다. 반면 참조 존재 여부와 자정을 넘는 시간 범위는 별도 불변식과 데이터베이스 제약이 필요했다.
- 기본 보안 헤더, 입력 whitelist와 레이트 리밋은 있었지만, 프록시 환경의 실제 클라이언트 식별, 분산 저장소와 정상 종료는 운영 배포 전에 검증할 항목이었다.
- 순차 통합 테스트는 주요 시나리오를 검증했지만, 경쟁 요청에서 확정 결과가 하나만 남는지는 별도 동시성 테스트가 필요했다.

## Operations 직무로 연결한 판단

| 과제에서 설명한 일반 원리 | 공개 직무와의 연결 |
| --- | --- |
| 대기와 확정 상태 전이 | 단말과 물류 자산의 재고, 출고, 설치, 회수 같은 상태 전이 |
| 충돌 불변식과 트랜잭션 | 한 자산의 중복 할당과 재고 음수를 막는 정합성 |
| 멱등 표식과 재시도 | 배치 자동화의 중복 실행과 실패 복구 |
| 전송 구현 분리 | 외부 물류 시스템과 알림 채널을 어댑터로 추가하는 구조 |
| 상태 변경 이벤트 | 자산 변화에서 후속 업무 자동화를 시작하는 경계, 단 전달 보장은 별도 설계 |
| 조회 권한과 출력 제한 | 사내 운영 도구의 팀별 접근 통제와 정보 노출 제한 |

면접에서는 이 연결이 실제 회사 시스템의 구현이라고 단정하지 않고, 공개 역할을 이해하기 위한 비유라고 밝혔다. 역질문은 자산 상태 전이의 정본, 외부 물류 데이터의 재대사, 배치 실패의 재처리, 자동화 효과의 측정 기준에 맞췄다.
