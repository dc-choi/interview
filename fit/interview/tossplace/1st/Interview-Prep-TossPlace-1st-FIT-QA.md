# 토스플레이스 1차 직무 면접 FIT 준비 기록

> 2026-06 전형을 위해 정리한 본인 답변과 예상 질문이다. 당시의 경력과 판단은 보존하되, 과거 회사의 비공개 운영 정보, 제3자 정보, 보상, 정확한 운영 지표와 사전 과제 원문은 제외했다.

당시 공개 JD에서 이 역할은 결제 승인 백엔드가 아니라 Operations Team의 단말 생애주기, 물류 관리, 배치와 내부 업무 자동화를 다루는 Node.js 역할이었다. 그래서 답변의 중심을 결제가 아니라 재고, 자산 상태와 반복 업무의 시스템화에 뒀다.

## 자기소개, 당시 45~60초 답변

> 안녕하세요, 당시 4년 차 백엔드 개발자 [이름]입니다. 이썸에서 도메인 관점을 넓히고, 시솔에서 운영 품질의 중요성을 배웠으며, 트라이포드랩에서는 VMI 재고 관리 서비스의 백엔드 0→1과 운영 자동화를 주도했습니다. 상태가 바뀌는 운영 데이터를 데이터베이스 잠금으로 안전하게 갱신하고, 후속 업무를 비동기 흐름으로 분리했으며, 느린 조회는 실행 계획과 인덱스로 검증했습니다. 정확한 운영 수치와 내부 구조는 공개하지 않지만, 저는 빠르게 만드는 것보다 정합성, 복구 가능성, 검증 가능한 결과를 우선하는 엔지니어입니다.

> 토스플레이스 Operations가 물리 자산의 생애주기와 반복 업무를 데이터로 관리하고 자동화하는 문제라는 점에서, 재고 상태와 발주 후속 업무를 다룬 경험을 자연스럽게 연결할 수 있다고 보았습니다.

## 지원 동기와 이직 사유

### 지원 동기

1. 재고나 단말처럼 상태가 바뀌는 자산을 정합성 있게 다루는 문제에 흥미가 있다.
2. 반복 수작업을 시스템과 배치로 줄이고, 결과를 관찰 가능한 지표로 확인하는 일을 강점으로 삼는다.
3. 외부 연동, 비동기 처리, 데이터 검증 경험을 물류와 운영 자동화 문제에 적용하고 싶었다.

### 이직 사유

> 한 사람이 넓게 책임지는 환경에서 주도성과 기술 의사결정 경험을 쌓았습니다. 다음 단계에서는 더 깊은 기술 환경에서 동료와 설계를 검토하고, 장기 운영되는 시스템의 품질을 함께 높이고 싶었습니다. 기존 경험을 부정하기보다, 혼자 해낸 경험 위에 협업의 깊이를 더하려는 선택입니다.

### 이력 전환에 대한 꼬리 질문

> 각 자리에서 부족했던 한 축을 채웠습니다. 이썸에서는 도메인 시야, 시솔에서는 운영 품질, 트라이포드랩에서는 0→1과 자동화를 경험했습니다. 그래서 쉽게 이동하기보다 다음 자리에서 더 오래 기술적 깊이와 팀 협업을 쌓겠다는 기준을 세웠습니다.

## 핵심 FIT 답변

### 왜 백엔드인가

> 백엔드는 물리적 사건, 데이터, 시간을 연결하고 그 연결이 예외 상황에서도 유지되게 하는 일이라고 생각합니다. 재고 상태를 안전하게 바꾸고 후속 작업으로 이어지는 흐름을 만들면서, 그 연결이 실제 운영을 떠받친다는 책임을 배웠습니다.

### 강점과 보완점

| 구분 | 당시 답변 |
| --- | --- |
| 강점 | 문제를 관찰하고, 가설을 세우고, 실행 계획과 결과로 검증한 뒤 구조적으로 고친다. |
| 보완점 | 물류와 공급망의 용어와 운영 흐름은 새로 배워야 한다. 정합성, 이벤트, 배치의 원리는 전이하되 도메인 가정은 확인 질문으로 검증한다. |
| 협업 | 규칙과 우선순위를 문서, 테스트, 데이터로 고정해 역할 간 해석 차이를 줄인다. |
| 자동화 | 반복은 자동화하되 설계 판단과 결과 검증은 사람이 책임진다. |
| 비동기 처리 | 이전 업무에서 후속 처리를 이벤트 기반으로 분리했지만 Transactional Outbox는 적용하지 않았고, 커밋과 발행 사이의 유실 가능성을 줄일 개선안으로 남겼다. Kafka를 직접 운영한 경험도 없다고 구분하고, 전달 보장과 멱등성이라는 인접 원칙으로 설명한다. |

### 갈등과 소통

> 일정 압박과 정확성 위험이 충돌할 때, 사람의 주장보다 영향 범위와 복구 비용을 먼저 같은 화면에 올려 의사결정했습니다. 합의한 규칙은 테스트나 명세처럼 검증 가능한 형태로 남겨 재논의를 줄였습니다.

### 팀 협업

> 합류 초기에 핵심 기능의 규칙이 역할마다 다르게 해석되던 상황에서 제품 역할은 기준을 정리하고, 프론트엔드는 사용자 흐름을 확인했으며, 저는 백엔드 규칙을 테스트로 고정했습니다. 합의를 실행 가능한 검증으로 바꾸자 인식 차이를 줄일 수 있었습니다. 비공개 고객과 성과 수치는 말하지 않고 역할, 행동과 검증 방법만 설명했습니다.

### 자동화와 AI 도구

> 반복 작업은 저장소 영역별 지침, 공식 문서 조회, 목적별 검토와 편집 뒤 정적 검사로 연결했습니다. AI는 물류와 업무 자동화를 더 빨리 검증하기 위한 수단일 뿐, 문제 정의와 설계 판단을 대신하는 주제로 앞세우지 않았습니다.

### 장기 방향

> 당시 5년 뒤 목표는 권한보다 기술적 영향력을 넓히는 Staff Engineer 성격의 백엔드 리드였습니다. 관리자 역할 자체보다 직접 구현과 운영을 이해한 상태에서 팀의 기술 선택을 돕고, 장기적으로 기술과 사업의 연결을 책임지고 싶었습니다.

### 업무 강도와 지속 가능성

> 의미 있는 일에는 책임 있게 몰입할 수 있지만 무조건적인 장시간 근무를 약속하지는 않습니다. 높은 강도가 특정 마감 구간인지 상시인지, 반복 업무를 자동화하고 회복 가능한 속도를 유지하는 구조가 있는지를 역질문으로 확인하겠다고 준비했습니다.

## 사이드 프로젝트를 물으면

> 주일학교 출석 관리 플랫폼을 0→1로 만들며 사내 도구와 비슷한 운영 문제를 경험했습니다. 과거 자동화가 입력 지연과 실제 휴면을 구분하지 못한다는 한계를 발견해 되돌린 적도 있습니다. 자동화는 만들었다는 사실보다, 잘못된 가정을 어떻게 관찰하고 수정했는지를 함께 봐야 한다는 배움으로 설명했습니다.

## 예상 질문과 답변 포인트

| 질문 주제 | 준비한 답변 포인트 |
| --- | --- |
| 자산 생애주기를 어떻게 모델링할까 | 상태와 전이 규칙을 명시하고, 전이의 정합성은 트랜잭션과 데이터베이스 안전망으로 지킨다. |
| 외부 시스템 연동의 불일치는 어떻게 다룰까 | 멱등 재처리와 대사 작업을 두고, 실패를 격리하며 재시도 근거를 남긴다. |
| 배치가 실패하면 어떻게 할까 | 중복 실행과 유실을 다른 문제로 보고, 멱등 키, 재시도, 실패 격리를 조합한다. |
| 자동화 성과는 어떻게 확인할까 | 절감 시간, 오류율, 처리량처럼 관찰 가능한 지표와 기준 시점을 사전에 정한다. |
| 이벤트 기반 처리와 Outbox의 차이는 | 인프로세스 또는 브로커 이벤트 분리만으로 커밋과 발행의 원자성이 생기지 않는다. 필요한 전달 보장에는 Outbox와 멱등 소비를 추가로 설계한다. |
| 관리형 큐와 스트림 브로커는 언제 나눌까 | 리플레이, 파티션 단위 순서, 지속 처리량과 운영 부담을 비교한다. 직접 운영하지 않은 브로커 경험을 과장하지 않고 실제 요구를 먼저 확인한다. |
| 내부 도구의 우선순위는 어떻게 정할까 | 요구를 필수와 보조로 나누고, 영향과 비용의 근거를 함께 공유한다. |
| 장애가 나면 무엇부터 할까 | 영향 범위 확인, 전파 차단, 재현 조건 확보, 가설 검증, 복구, 회고 순으로 진행한다. |

## 역질문

- 입사 후 처음 몇 달 동안 가장 먼저 해결해야 할 운영 문제는 무엇인지
- 데이터 정합성과 상태 전이를 현재 어떤 계층에서 보장하는지
- 자동화의 효과를 팀이 어떤 관찰 지표로 판단하는지
- 여러 팀이 같은 시스템 경계를 다룰 때 책임과 의사결정을 어떻게 나누는지

## 점검 항목

- [x] 이직 사유를 외부 탓이 아니라 다음 성장 방향으로 설명한다.
- [x] 확인하지 않은 회사 정보는 사실처럼 말하지 않는다.
- [x] 자동화 경험은 구현보다 문제 정의, 검증, 되돌림 판단을 함께 말한다.
- [x] 도메인 가정은 단정하지 않고 질문으로 확인한다.
- [x] 결제 백엔드 경험처럼 말하지 않고 단말, 재고, 물류와 내부 업무 자동화에 맞춘다.
- [x] 사이드 프로젝트는 현업 경험을 대신하는 주제가 아니라 자동화의 실패와 되돌림을 묻는 경우에만 보조 근거로 쓴다.
- [x] AI 도구 이름보다 검증 흐름과 사람이 맡은 판단 책임을 먼저 설명한다.
