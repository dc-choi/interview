# 토스플레이스 1차 사전 과제 심화 리뷰 기록

> 사전 과제 직후 여러 차례 수행한 본인 설계 리뷰 기록이다. Pass 1~10은 당시 스냅샷과 테스트를 바탕으로 했고, Pass 11은 면접 전 실제 구현을 다시 읽어 사실과 추정을 구분한 단계다. 비공개 과제 원문, 코드와 파일 경로는 제외했다. 이 문서는 공식 피드백이 아니라 본인 점검 결과다.

## 검토 기준

- 상태 전이와 데이터 정합성
- 보안, 인증과 인가
- 조회 성능, 입력 검증과 데이터 무결성
- 테스트, 오류 처리와 운영 가정
- 확장성, 관찰 가능성과 유지보수성

## 반복 검토 흐름

| 검토 | 초점 | 확인한 결론 |
| --- | --- | --- |
| Pass 1 | 상태 변경과 시간 조건 | 일정 수정, 시간 경계, 후속 알림의 불변식을 다시 점검했다. |
| Pass 2 | 인증과 보안 | 비밀값 저장의 장점과 별도로 알고리즘 제한, 오류 일반화, 인가 적용을 확인했다. |
| Pass 3 | 조회와 데이터 무결성 | 권한을 조회 단계에 둔 점은 유지하고, 검색 제한과 참조 무결성을 보완 대상으로 남겼다. |
| Pass 4 | 테스트 품질 | 핵심 규칙 테스트는 강점이지만 경쟁 요청과 경계 조건의 검증은 부족했다. |
| Pass 5~7 | 입력, 모델, API 계약 | 존재 검증, 시간 범위, 중복 관계, 경로 입력과 페이지 경계를 분리해 점검했다. |
| Pass 8 | 비동기 전송 | 수신 대상, 채널별 표현, 실패 격리, 중복과 유실을 따로 봤다. |
| Pass 9~10 | 운영과 면접 설명 | 운영 가정과 실제 누락을 구분하고, 설명할 우선순위를 정리했다. |
| Pass 11 | 실제 구현 재검증 | 기억이 아니라 구현을 다시 읽어 확인된 결론과 미확정 항목을 나눴다. |

## 당시 구현을 다시 읽어 확인한 강점

1. 대기 승격은 결정적인 순서와 확정 집합의 충돌 검사를 사용해, 한 번의 처리에서도 확정 상태의 불변식을 유지하려 했다.
2. 조회 권한을 데이터 접근 조건에 넣어, 결과를 모두 가져온 뒤 메모리에서 거르는 방식보다 노출과 작업을 줄였다.
3. 비밀번호와 무작위 비밀값을 다른 위협 모델로 보고, 비밀값 해시와 상수 시간 비교를 사용했다.
4. 입력과 출력의 검증 경계를 나누고, 단위 테스트와 실제 SQLite 기반 통합 테스트의 목적을 구분했다.
5. 인덱스 선택은 접두 검색 패턴과 실행 계획으로 확인하려 했다.
6. 일정이 다른 자원이나 시간으로 이동할 때 기존 구간과 새 구간을 모두 재평가하려 했고, 여러 자원을 잠글 때의 순서도 설계 항목으로 인식했다.
7. 외부 응답은 허용 필드만 직렬화하고, 예상하지 못한 내부 오류는 일반화해 저장소 세부가 노출되지 않게 했다.
8. 비밀번호 해시에는 알고리즘과 파라미터를 함께 보존해 이후 비용을 높여도 기존 값을 검증할 수 있는 방향을 택했다.

## 확인한 실제 보완점

### 상태, 시간과 데이터 무결성

- 수정 요청에서 날짜를 바꾸지 않고 시간만 과거로 옮기는 경우, 과거 검증의 경계가 약했다.
- 기간 상한과 같은 날 종료 규칙이 없어 자정을 넘는 구간은 날짜 단위 충돌 검사에서 빠질 수 있었다.
- 존재하지 않는 자원이나 사용자 참조를 허용할 수 있는 경로가 있었고, 데이터베이스 외래 키 안전망도 꺼져 있었다.
- 같은 관계의 중복 생성과 중복 저장 값의 갱신 여부를 데이터베이스 제약과 테스트로 고정할 필요가 있었다.
- 일정 시작 시각을 관계 데이터에 중복 저장한 곳은 원본 일정이 이동해도 함께 갱신되지 않을 수 있었다. 사용하지 않는 중복 값은 제거하고, 필요하면 한 트랜잭션에서 동기화해야 했다.
- 요청 DTO의 형식 검증에만 기대지 않고 제목 길이, 양수 기간과 같은 핵심 불변식은 도메인 모델과 데이터베이스에서도 지켜야 했다.

### 인증, 인가와 조회

- 자격 증명 검증에는 허용 알고리즘 제한과 외부에 일반화한 오류 응답이 필요했다.
- 권한 범위용 구조가 있어도 실제 가드나 유스케이스에서 검증하지 않으면 모든 키가 전권이 되는 문제가 남는다.
- 접두 검색은 최소 입력 길이와 결과 제한이 없어 빈 입력에서 과도한 결과를 돌려줄 수 있었다.
- 권한 조건과 to-many 관계를 함께 조인한 페이지네이션의 정확성은 당시 실행 SQL로 끝까지 확정하지 못했다. 이 항목은 결함으로 단정하지 않고, 루트 식별자 기준의 분리 조회를 검증할 후보로 남겼다.
- 비밀값 후보가 없을 때 해시 비교 전에 바로 반환하는 흐름과 사용 시각을 매 인증마다 기록하는 쓰기는 각각 미세한 타이밍 차이와 쓰기 경합의 후보였다. 위협과 호출량을 측정해 더미 비교 또는 기록 주기 완화를 검토해야 했다.
- 쿠키의 `httpOnly`, 운영 환경의 `secure`, `SameSite`와 만료 설정은 확인했지만, `SameSite`는 CSRF 위험을 줄이는 한 층일 뿐 상태 변경 요청의 모든 방어를 대신하지 않는다.
- 목록 조회에 필요한 관계만 불러오는지, 개발용 전체 SQL 로그와 포매팅이 운영에서도 켜지는지는 성능 점검 항목으로 남겼다.

### 알림과 후속 처리

- 당시 수신자 구성에는 주최자가 빠질 수 있어, 대기 상태가 확정돼도 본인이 알림을 받지 못하는 경우가 있었다.
- 새로 추가된 수신자는 첫 알림과 변경 알림을 구분해야 했고, 단독 사용자의 리마인더 경로도 검증 대상이었다.
- 리마인더를 발송 전에 표시하는 방식은 중복을 줄이지만, 전송 실패나 실행 중단 때 유실되는 at-most-once 성격을 가진다.
- 이벤트와 리스너 분리는 있었지만 영속 Outbox, 메시지 재전송, 전달 보장은 구현하지 않았다. 이 셋은 향후 개선안이지 당시 적용 사실이 아니다.
- 같은 메시지를 모든 채널에 그대로 쓰면 길이와 표현이 맞지 않을 수 있어, 채널별 렌더링 책임을 메시지 빌더나 전송 어댑터 중 한곳에 명확히 둬야 했다.
- 주기적으로 리마인더 후보를 찾는 조회는 상태, 날짜와 미발송 조건에 맞는 복합 또는 부분 인덱스를 실제 데이터 분포로 검증해야 했다.
- 전송 로그에는 제3자 연락처를 남기지 않거나 마스킹해야 한다.

### 테스트와 운영

- 순차 시나리오 테스트만으로는 경쟁 요청의 안전을 증명할 수 없었다. 같은 자원을 동시에 요청했을 때 확정 상태가 하나만 되는지 확인하는 테스트가 필요했다.
- 다중 인스턴스에서 스케줄러 중복 실행을 막는 리더 선출, 분산 잠금 또는 전용 워커가 없었다.
- 구성 검증, 정상 종료, 관찰 가능성은 과제 기능과 별도로 운영 준비 항목으로 다뤄야 했다.
- 시간은 주입하고 외부 전송은 테스트 대역으로 바꿔 결과를 고정한 점은 유지한다. 다만 전송 이벤트의 수신자, 시간 경계와 실패 후 재시도까지 검증 범위를 넓혀야 했다.
- 테스트용 SQLite에서는 매 테스트 스키마 재생성이 단순했지만, 다른 RDBMS에서는 트랜잭션 롤백, 격리된 스키마나 컨테이너의 비용을 비교해야 했다.
- 운영 전에는 환경 변수 스키마 검증, 시작 실패 처리, 진행 중 요청의 정상 종료, 메트릭과 추적 문맥을 별도 체크리스트로 확인해야 했다.

## 면접에서 사용할 정리

| 구분 | 말할 내용 |
| --- | --- |
| 의도적으로 뒤로 미룬 범위 | 현재 전제와 운영 환경에서 필요한 보완 수단을 함께 말한다. |
| 실제 누락 | 영향, 수정 방향, 재발 방지 테스트를 짧게 연결한다. |
| 정책이 늘어나는 상태 처리 | 메서드 분리보다 정책 객체 추출을 먼저 고려해 상태 객체의 관심사 수를 고정한다. |
| 공유 모델의 위치 | 통합과 분리는 변경 이유, 모델 간 간극, 매핑 비용을 보고 결정한다. |
| 불확실한 부분 | 추측하지 않고 확인 방법과 다음 검증을 말한다. |
