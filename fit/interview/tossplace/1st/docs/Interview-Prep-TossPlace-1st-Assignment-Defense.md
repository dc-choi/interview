# 토스플레이스 1차 사전 과제 기반 설계 설명 기록

> 2026-06 1차 면접을 위해 만든 답변 드릴이다. 사전 과제의 원문, 코드, 파일 경로, 비공개 요구사항은 제외하고 당시 구현에서 확인한 설계 선택과 회고를 남긴다. 이 문서는 공식 평가 자료가 아니라 본인 설명 기록이다.

## 설명 전략

### 강점으로 제시한 카드

1. 대기와 확정의 상태 전이 규칙을 저장소와 분리해 설명 가능하고 테스트 가능한 모델로 둔 점
2. 동시 요청에서 읽기, 판단, 쓰기를 하나의 임계구역으로 본 점
3. 알림의 의미, 메시지, 전송을 분리하고 실패 경계를 인식한 점
4. 비밀값 보호, 조회 권한, 실행 계획 검증을 기능과 함께 다룬 점

### 먼저 구분한 한계

- 테스트용 단일 인스턴스의 가정과 다중 인스턴스 운영의 보완 수단은 다르다.
- 인증 구조를 만든 것과 실제 인가를 모든 요청 경계에 적용한 것은 다르다.
- 인프로세스 이벤트는 전달 보장이나 Outbox를 뜻하지 않는다.
- 시간, 참조 존재, 알림 수신 대상 같은 경계 조건은 별도 테스트로 확인해야 한다.

## 질문 드릴

### 1. 대기 상태를 어떻게 처리했는가

**답변 요약:** 충돌이 생긴 요청을 바로 버리지 않고 대기 상태로 보관했다. 자원이 비면 대기 항목을 생성 시각 순으로, 동률은 결정적인 식별자 순으로 검토했다. 이미 확정된 항목과 겹치지 않는 경우만 상태를 바꾸고, 새로 확정한 항목도 즉시 충돌 검사 대상에 넣어 한 번의 처리에서도 불변식을 유지했다.

**꼬리 질문 대비:** 앞 항목이 현재 조건에서 실행되지 못해도 뒤 항목의 가능성을 함께 보는 이유는, 순서를 존중하면서 자원을 불필요하게 비우지 않기 위해서다. 끝 시각과 다음 시작 시각이 같은 구간은 겹치지 않는 반열림 구간 규칙으로 처리했다.

**왜 한 번의 순회로 충분한가:** 승격은 확정 집합을 늘릴 뿐 다른 대기의 충돌을 해소하지 않는다. 새 확정 항목을 즉시 검사 집합에 넣으면 이후 후보까지 같은 불변식으로 판단할 수 있다. 이 규칙을 저장소 서비스가 아니라 별도 도메인 모델에 둔 이유도 배열만으로 경계 사례를 빠르게 검증하기 위해서였다.

### 2. 동시 요청 정합성은 어떻게 지켰는가

**답변 요약:** 확정 상태를 읽고, 새 상태를 결정하고, 저장하는 구간을 트랜잭션으로 묶었다. 당시 SQLite 테스트 환경의 쓰기 직렬화 특성은 전제로 사용했지만, 운영용 관계형 데이터베이스에서 같은 수준의 보호가 자동으로 생긴다고 말하지 않았다.

**꼬리 질문 대비:** 운영 환경에서는 자원 또는 자원과 날짜 단위의 잠금, 충돌을 거부하는 데이터베이스 제약, 제한된 재시도 중 무엇이 불변식과 데이터베이스에 맞는지 선택해야 한다. 락 순서를 통일해도 데드락이 사라지는 것은 아니므로 실패를 새 트랜잭션에서 다룰 경로가 필요하다.

**데이터베이스별 후보:** MySQL에서는 `SELECT FOR UPDATE` 같은 자원 잠금을, PostgreSQL에서는 겹치는 확정 구간을 거부하는 exclusion 제약을 검토할 수 있다. 애플리케이션 규칙과 데이터베이스 안전망을 함께 두되, 제약 실패와 데드락을 같은 오류로 취급하지 않는다.

### 3. 알림 기능을 어떻게 확장 가능하게 만들었는가

**답변 요약:** 알림 타입, 채널과 무관한 메시지 구성, 실제 전송 구현을 나눴다. 새 채널은 전송 구현과 조립 지점을 추가하는 방식으로 넣고, 상태를 바꾸는 흐름은 기존대로 둔다. 수신자 하나의 실패가 다른 수신자나 핵심 상태 변경을 막지 않도록 실패를 격리했다.

**꼬리 질문 대비:** 당시에는 도메인 이벤트와 리스너를 분리했을 뿐, 영속 Outbox나 큐 전달 보장을 구현하지 않았다. 다중 인스턴스에서는 중복 실행, 발송 전 마킹에 따른 유실, 소비자 멱등성을 별도로 설계해야 한다.

**트랜잭션 경계:** 취소처럼 상태가 사라진 뒤에도 알림을 만들 수 있도록 필요한 값은 트랜잭션 안에서 스냅샷으로 만들고 실제 전송은 커밋 뒤에 실행하려 했다. 한 수신자의 실패는 다른 수신자와 핵심 상태 변경에서 격리했다. 이 방식은 결합을 줄이지만 프로세스 중단 시 전달을 보장하지는 않는다.

### 4. 자격 증명은 어떻게 보호했는가

**답변 요약:** 사람이 기억하는 비밀번호와 무작위로 만든 고엔트로피 비밀값은 위협 모델이 다르므로 저장 방식을 나눴다. 비밀값은 평문 노출을 최소화하고 해시로 검증하며, 비교 시점의 정보 누출도 고려했다. 폐기는 삭제 대신 상태를 남기는 방식으로 추적 가능하게 했다.

**꼬리 질문 대비:** 인증이 성공했다고 모든 권한이 생기는 것은 아니다. 권한 범위는 실제 요청 경계에서 검사해야 하며, 허용 알고리즘 제한과 인증 오류 메시지 일반화도 별도 하드닝 항목이다.

**검증 흐름:** 무작위 비밀값의 원문은 발급 시 한 번만 노출하고, 이후에는 표시용 접두부로 후보를 찾은 뒤 해시를 상수 시간으로 비교한다. 활성 상태와 만료를 확인하고, 폐기는 삭제보다 상태를 남겨 감사 가능성을 유지한다. 비밀번호에는 느린 비밀번호 해시를 쓰는 이유와 위협 모델이 다르다고 설명했다.

### 5. 검색과 조회 권한은 어떻게 다뤘는가

**답변 요약:** 접두 검색 패턴에 맞는 대소문자 구분 없는 인덱스를 두고 실행 계획으로 확인했다. 조회 권한은 응답을 만든 뒤 메모리에서 필터링하지 않고, 데이터 접근 조건에 넣는 것을 원칙으로 삼았다.

**꼬리 질문 대비:** 검색에는 최소 입력 길이, 결과 제한, 페이지네이션을 함께 설계해야 사용자 열거와 응답 폭증을 막을 수 있다. 참조 식별자는 형식뿐 아니라 실제 존재 여부와 데이터베이스 제약으로도 보강해야 한다.

**실행 계획과 권한:** SQLite의 대소문자 구분 없는 접두 검색 조건과 같은 콜레이션의 인덱스를 두고, 풀 스캔이 인덱스 탐색으로 바뀌는지 확인했다. 인증 실패는 401, 인증된 사용자의 권한 부족은 403으로 나누고, 목록 권한은 응답 뒤 필터가 아니라 조회 조건에 넣었다. 날짜는 형식뿐 아니라 달력에 실제 존재하는지도 검사했다.

### 6. 테스트 전략은 무엇이었는가

**답변 요약:** 규칙 자체는 빠른 단위 테스트로, 요청과 저장소의 경계는 실제 SQLite 기반 통합 테스트로 검증했다. 시간과 외부 전송은 제어 가능한 의존성으로 만들어 결과가 흔들리지 않게 했다.

**꼬리 질문 대비:** 순차 시나리오만으로는 동시성 안전을 증명할 수 없다. 경쟁 요청에서 정확히 하나만 확정되는지, 시간 경계와 수신 대상이 맞는지를 별도로 검증해야 한다.

**격리와 아키텍처:** 요청 경계, 유스케이스 조율, 도메인 규칙을 변경 이유에 따라 나눴다. 단위 테스트는 저장소 없이 규칙을 검증하고, 통합 테스트는 실제 SQLite로 요청과 저장소의 결합을 확인했다. 시간과 전송은 제어 가능한 의존성으로 바꿨다. 다른 RDBMS로 옮기면 스키마를 매번 다시 만드는 방식보다 트랜잭션 롤백이나 격리된 데이터베이스를 비교해야 한다.

## 회고에서 확정한 개선 답변

| 상황 | 더 나은 답변 |
| --- | --- |
| 정책이 계속 늘어나는 상태 처리 | 메서드만 나누지 말고 정책을 Strategy 같은 별도 객체로 추출해 상태 객체의 관심사를 고정한다. |
| 여러 유스케이스가 공유하는 모델 | 통합과 분리는 자동 정답이 아니다. 퍼시스턴스 매핑과 도메인 행위의 변경 이유와 매핑 비용을 비교해 결정하고, 공유 개념은 특정 기능 폴더에 가두지 않는다. |
| 라이브 코딩 중 확장 요구 | 인터페이스, 구현체, 조립 지점 순서로 최소 골격을 먼저 만들고 세부를 채운다. |
| 실제 누락 발견 | 영향, 수정 방향, 재발 방지 테스트를 한 흐름으로 말한다. |

## 공개 직무와 연결한 답변

| 설계 원리 | Operations 역할로 일반화한 문제 |
| --- | --- |
| 상태 전이와 충돌 불변식 | 단말과 재고 자산의 중복 할당 방지 |
| 잠금과 데이터베이스 제약 | 동시 상태 변경과 재고 정합성 |
| 멱등 표식, 재시도와 실패 격리 | 배치 자동화와 외부 물류 연동의 복구 |
| 이벤트와 전송 어댑터 | 자산 변화에서 후속 업무를 시작하는 경계 |
| 조회 권한과 출력 제한 | 내부 운영 도구의 접근 통제 |

실제 회사 시스템이 이 구조라고 단정하지 않고, 공개 JD의 단말 생애주기, 물류 관리와 업무 자동화를 이해하기 위한 비유로만 사용했다. 역질문은 상태 전이의 정본, 외부 데이터 재대사, 배치 재처리와 자동화 성과 측정 방식에 맞췄다.
