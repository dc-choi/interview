# 토스플레이스 1차 본인 답변 스크립트

> 2026-06 전형을 위한 구어체 답변 기록이다. 사전 과제의 원문, 코드, 파일 경로는 재현하지 않고 당시의 설계 설명만 보존한다. 아래는 통암기용 정답이 아니라 본인 언어로 다시 말하기 위한 골격이다.

## 1. 상태 전이와 대기 처리

> 충돌하는 요청을 바로 버리기보다 대기 상태로 보관했습니다. 자원이 비면 대기 항목을 생성 시각 순으로 보고, 동률은 결정적인 식별자로 정렬했습니다. 각 후보는 이미 확정된 상태와 충돌하지 않을 때만 승격하고, 방금 확정한 항목도 즉시 검사 집합에 넣었습니다. 그래서 한 번의 처리 안에서도 확정 상태의 불변식이 유지됩니다. 선두가 막혔다고 실행 가능한 뒤 항목까지 멈추지는 않았습니다. 시간 구간은 끝과 다음 시작이 같으면 겹치지 않는 반열림 규칙으로 처리했습니다.

## 2. 동시 요청과 트랜잭션

> 확정 상태를 읽고, 판단하고, 저장하는 구간을 하나의 트랜잭션으로 묶었습니다. 과제의 SQLite 테스트 환경에서는 쓰기 직렬화 특성을 전제로 했지만, 이를 운영 해법으로 일반화하지는 않았습니다. 운영용 관계형 데이터베이스에서는 자원 단위 잠금이나 충돌 제약으로 불변식을 보강하고, 데드락이나 직렬화 실패는 제한된 재시도로 다뤄야 합니다. 데이터베이스가 바뀌어도 상태 전이 규칙은 같고, 그 규칙을 안전하게 실행하는 수단만 달라집니다.

## 3. 비밀값과 인증

> 사람이 만드는 비밀번호와 충분히 긴 무작위 비밀값은 공격 모델이 다르므로 저장 방식도 달라야 합니다. 비밀번호는 느린 비밀번호 해시가 필요하고, 무작위 비밀값은 평문을 한 번만 노출한 뒤 해시로 검증할 수 있습니다. 비교 시점의 정보 누출도 고려했습니다. 다만 인증에 성공했다고 곧바로 모든 권한이 생기는 것은 아니므로, 권한 범위는 실제 요청 경계에서 별도로 확인해야 합니다. 허용 알고리즘 제한과 외부 오류 메시지 일반화도 보안 하드닝으로 추가해야 합니다.

> 검증할 때는 표시용 접두부로 후보를 찾고 해시를 상수 시간으로 비교한 뒤 활성 상태와 만료를 확인합니다. 폐기는 삭제보다 상태를 남겨 감사 가능성을 유지하고, 비소유자에게 자격 증명의 존재를 노출하지 않으며, 한 인증 수단으로 새 인증 수단을 발급하는 권한 상승도 막아야 합니다.

## 4. 비동기 알림

> 알림의 의미, 메시지 구성, 실제 전송을 나눴습니다. 새 채널이 생겨도 핵심 상태 전이 규칙을 바꾸지 않게 하고, 한 수신자의 실패가 핵심 작업이나 다른 수신자를 막지 않도록 격리했습니다. 당시에는 이벤트와 리스너를 분리했을 뿐 영속 Outbox를 적용한 것은 아닙니다. 운영 환경에서는 커밋과 발행 사이의 유실, 중복 전송, 다중 인스턴스 스케줄 중복을 따로 보고 Outbox, 멱등 키, 재시도 또는 워커 구조를 결정해야 합니다.

> 취소처럼 상태가 사라진 뒤에도 알림 내용을 만들 수 있도록 필요한 값은 트랜잭션 안에서 스냅샷으로 만들고 실제 전송은 커밋 뒤로 미뤘습니다. 이 경계는 상태 변경과 전송 실패를 분리하지만, 프로세스가 멈춰도 전달된다는 보장은 아닙니다.

## 5. 검색과 조회 권한

> 검색은 실제 사용 패턴에 맞는 접두 인덱스를 선택하고 실행 계획으로 확인했습니다. 조회 권한은 응답을 만든 뒤 필터링하는 대신 데이터 접근 조건에 넣었습니다. 다만 인덱스만으로는 충분하지 않습니다. 최소 입력 길이, 결과 제한, 페이지네이션과 실제 참조 존재 검증을 함께 두어야 사용자 열거, 과도한 응답, 깨진 관계를 막을 수 있습니다.

> 당시 SQLite에서는 대소문자 구분 없는 접두 검색 조건과 인덱스의 콜레이션을 맞춘 뒤, 실행 계획이 풀 스캔에서 인덱스 탐색으로 바뀌는지 확인했습니다. 다른 데이터베이스에서는 같은 결론을 전제하지 않고 실제 SQL과 계획을 다시 봐야 합니다.

## 6. 검증과 오류 처리

> 인증 실패와 권한 부족은 다른 책임이므로 구분했습니다. 형식 검증만으로는 부족한 실제 존재 여부, 시간 범위, 관계 무결성은 도메인 경계와 데이터베이스 안전망을 함께 사용해야 합니다. 오류는 필요한 정보만 외부에 보이고, 내부 진단 정보는 별도로 남기는 방향이 맞습니다. 당시에는 일정 수정의 시간 경계와 자정을 넘는 구간, 알림 수신 대상처럼 별도 테스트가 필요한 누락도 있었습니다.

## 7. 아키텍처와 테스트

> 요청 처리는 경계 어댑터로, 업무 흐름은 유스케이스로, 핵심 규칙은 도메인 모델로 나눴습니다. 규칙 자체는 빠른 단위 테스트로, 저장소와 요청의 경계는 실제 SQLite 기반 통합 테스트로 검증했습니다. 시간과 외부 전송은 제어 가능한 의존성으로 만들어 재현 가능한 테스트를 유지했습니다. 다음에는 순차 시나리오뿐 아니라 경쟁 요청과 시간 경계를 검증하겠습니다.

> 테스트용 SQLite에서는 매 테스트 상태를 다시 만드는 방식이 단순했지만, 운영용 RDBMS로 옮기면 트랜잭션 롤백, 격리 스키마와 컨테이너 중 실제 비용에 맞는 방법을 선택해야 합니다. 테스트 대역은 무작위 외부 실패를 제거하는 경계에만 두고, 저장소 계약은 실제 데이터베이스로 확인하겠습니다.

## 8. 한계에 대한 답변

> 의도적으로 뒤로 미룬 범위는 현재 전제와 운영에서의 보완 방법을 함께 말하겠습니다. 실제 누락은 영향, 수정 방향, 재발 방지 테스트를 묶어 인정하겠습니다. 특히 정책이 늘어나는 경우에는 메서드만 나누지 않고 Strategy 같은 정책 객체로 책임을 추출해 상태 객체가 모든 규칙을 알지 않게 하겠습니다. 도메인 모델과 퍼시스턴스 모델도 변경 이유와 매핑 비용을 보고 통합 또는 분리를 결정하겠습니다.
