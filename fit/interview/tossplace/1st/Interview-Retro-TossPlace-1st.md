## 사전 과제 발표에서 설명한 설계와 당시 사고

- **계층 구조**: 컨트롤러는 요청과 응답, 유스케이스는 애플리케이션 흐름, 도메인 객체는 예약 규칙을 맡는다고 설명했다. MikroORM 엔티티에 행위를 둬 빈약한 도메인 모델을 피하려 했고, 예약의 시간 단위를 슬롯이라는 1급 객체로 분리했다.
- **예약과 승격**: 취소로 자리가 나면 대기 예약을 FIFO로 승격하는 흐름을 설명했다. 당시에는 슬롯이 승격 정책을 직접 알고 있었고, 이후 정책 종류가 늘어날 때의 책임 분리까지는 설계하지 못했다.
- **동시성**: 같은 회의실과 시간대의 동시 예약 충돌이 핵심이라고 봤다. 과제의 SQLite에서는 쓰기 직렬화와 트랜잭션 경계를 전제로 했고, MySQL이라면 조건 재검증과 잠금 전략을 비교하겠다고 답했다.
- **현재 교정**: SQLite가 단일 writer라는 사실만으로 애플리케이션 불변식이 자동 보호되는 것은 아니다. 트랜잭션 시작 방식, 충돌 오류 처리와 재시도, 최종 조건 재검증을 함께 설계해야 한다.
- **알림**: `NotificationSender` 경계 뒤에 이메일과 SMS 구현을 두고, 예약 이벤트를 프로세스 내부 리스너가 처리한다고 설명했다. 여러 인스턴스와 재처리가 필요하면 메시지 큐, 멱등성 키와 실패 복구가 추가돼야 한다고 구분했다.
- **API 키**: 고엔트로피 API 키의 원문 대신 SHA-256 digest를 저장하고 scope, tenant와 기본 권한을 함께 검증한다고 설명했다. 사용자 비밀번호처럼 엔트로피가 낮은 비밀은 느린 비밀번호 해시가 필요하다는 차이도 말했다.
- **테스트**: 규칙을 빠르게 검증하는 단위 테스트와 ORM, 데이터베이스 경계를 확인하는 통합 테스트의 역할을 나눠 설명했다.

### 핵심 꼬리 질문 기록

- **Q. 전송 설정은 보내는 코드가 직접 알아야 하는가?** 함수형 구현을 클래스로 바꾸고 설정 의존성을 주입하려 했지만, 객체 구성과 생성자 연결을 끝내지 못해 오류가 남았다.
- **Q. 기존 전송 계층을 분리한 의도는 무엇인가?** 기존 코드를 레거시로 보고 건드리지 않기 위해 어댑터를 붙였다고 답했다. 새 요구에 맞춰 추상화의 책임을 다시 설명하지는 못했다.
- **Q. 표현 계층과 유스케이스의 예외 책임은 어떻게 나뉘는가?** 표현 계층은 요청과 응답 및 예외 변환, 유스케이스는 조회와 실행이라고 답했다. 유스케이스에서도 도메인과 애플리케이션 오류를 만들어야 한다는 점을 놓쳤다고 인정했다.
- **Q. 여러 유스케이스가 공유하는 엔티티는 어디에 두는가?** 작은 과제에서는 함께 둔 선택을 설명했고, 변경 이유가 갈라지면 도메인 모델과 퍼시스턴스 엔티티를 분리하겠다고 답했다. 공유 도메인 경계를 바로 말하지 못해 되묻기를 반복했다.
- **Q. 예약의 일부인 슬롯을 왜 별도 객체로 뒀는가?** 수정과 삭제에서 예외가 늘어 리치 도메인 모델로 분리했다고 답했다. 파일 길이를 근거로 앞세워, 슬롯이 여러 정책을 모두 아는 책임 문제를 바로 짚지 못했다.

### 계층과 엔티티 위치 probe의 실제 흐름

1. 현업 엔지니어는 `common`, `infra`, `domain`의 책임을 어떻게 나눴는지 물었다.
2. 당시에는 `domain`을 예약, 사용자, 인증과 초대 같은 규칙, `common`을 설정, 가드, 필터, DTO와 유틸, `infra`를 이메일과 퍼시스턴스 같은 외부 연동으로 설명했다.
3. 이어 표현 계층에서 오류를 던진 코드를 근거로 유스케이스와의 경계를 물었다. 요청 변환과 응답 오류 변환은 표현 계층, 조회와 실행은 유스케이스라고 답했지만, 유스케이스가 도메인 오류를 만들고 표현 계층이 이를 변환하는 흐름을 바로 설명하지 못했다.
4. 여러 유스케이스가 같은 사용자 엔티티를 쓸 때 특정 기능 폴더 안에 두는 것이 맞는지 묻는 질문이 이어졌다. 인증과 사용자가 맞닿아 있다는 답을 반복하다가, 규모가 커지면 도메인 모델과 퍼시스턴스 엔티티를 분리하겠다고 답했다.
5. 현재 교정: 퍼시스턴스 모델은 스키마와 ORM 매핑 때문에, 도메인 모델은 비즈니스 규칙 때문에 변한다. 공유 개념은 특정 유스케이스 폴더에 종속시키지 않고 도메인 경계에 두며, 리포지터리에서 둘을 매핑한다. 작은 과제에서 하나로 둔 선택은 가능하지만 분리 기준을 변경 이유로 먼저 말했어야 한다.

### 슬롯과 정책 증가 probe의 실제 흐름

1. 현업 엔지니어는 예약의 일부로 볼 수 있는 슬롯을 왜 분리했는지 물었다. 당시에는 수정과 삭제 예외를 한곳에 모으고 리치 도메인 모델로 만들기 위해서라고 답했다.
2. 다음으로 특정 권한 사용자가 예약하면 기존 순서를 바꾸는 정책처럼 조건이 계속 늘어날 때 어떻게 할지 물었다. 처음에는 사용자 조건을 확인하는 메서드와 정렬 로직을 슬롯 안에 더하는 방향으로 답했다.
3. 정책이 계속 추가되면 슬롯이 비대해지는 문제를 구조적으로 어떻게 풀지 묻는 후속 질문에 메서드를 나누겠다고 답했다. 질문자는 메서드 분리만으로는 슬롯이 모든 정책을 안다는 책임이 줄지 않는다는 요지로 다시 짚었다.
4. 당시에는 도메인 객체를 더 만들겠다는 방향까지만 말하고, 구현을 보여 주려는 시점에 면접 시간이 끝났다.
5. 현재 교정: `PromotionPolicy` 같은 정책 경계를 두고 FIFO, 우선순위와 권한 정책을 별도 객체로 추출한다. 슬롯은 정책을 적용하고 결과 상태를 보호하는 책임만 가진다. 핵심은 파일 줄 수가 아니라 객체가 알아야 하는 관심사 수다.

## 잘 작동한 부분

1. 상태 전이, 동시성, 비동기 처리의 전제를 구분해 설명했다.
2. 구현의 빈틈을 발견했을 때 변명보다 영향과 수정 방향을 먼저 말했다.
3. 화면 공유 중 설계 선택을 코드 나열이 아니라 책임과 트레이드오프로 설명하려 했다.
4. 실제 구현이 아닌 설계 의도를 묻는 질문에서, 운영 환경의 보완 수단까지 연결했다.

## 다음에 보완할 부분

1. 정책이 늘어나는 문제에서는 메서드 분리보다 책임 추출을 먼저 제안한다.
2. 도메인 모델과 퍼시스턴스 모델의 분리 기준을 변경 이유로 짧게 말한다.
3. 라이브 코딩 전에는 전략, 어댑터, 의존성 주입 같은 구조를 화이트보드 수준으로 다시 구현해 본다.
4. 파일 길이나 형식보다 책임 수와 인지 부하를 설계 품질의 기준으로 둔다.

## 당시 판단과 다음 결정

- 면접 직후에는 `조졌다`는 감각이 컸지만, 결과 가능성은 반반 정도로 판단했다. 당시 감정 표현은 본인 회고이므로 그대로 보존한다.
- 정답 암기보다 설계 이유와 트레이드오프를 설명하는 면접 방식은 본인의 문제 해결 방식과 잘 맞는다고 느꼈다.
- 2025-08에는 사전 과제에서 탈락했지만, 2026-05에는 사전 과제를 통과해 1차 면접까지 진행했다. 결과와 별개로 이전 지원보다 한 단계를 더 통과한 기록이다.
- 다음 지원 전에는 준비한 설계를 즉석에서 구현하는 라이브 손코딩 드릴을 완료한다. 이 조건을 닫은 뒤 재지원을 검토한다.
