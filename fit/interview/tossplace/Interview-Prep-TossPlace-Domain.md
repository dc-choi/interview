# 토스플레이스 도메인 브리프 (전 차수 공통)

> 지원 직무의 공개 업무 범위와 면접 준비 원칙을 정리한 차수 공통 문서다.
> 내용은 2026-06 당시 공개 채용공고 스냅샷(job_id 7686375003)을 기준으로 한다. 이 직무는 결제 정합성 백엔드가 아니라 Operations Team의 사내 운영 플랫폼 직무였고, 이 점이 당시 FIT과 역질문의 축이었다.

## 지원 직무: Operations Team Node.js Developer

JD 원문 기준 정확한 정의:

- **소속**: 토스플레이스 Operations Team.
- **만드는 것**: 결제단말기 다변화와 물류 체인 고도화에 맞춘 **유연하고 확장 가능한 단말기 생애주기 관리 및 물류 관리 플랫폼**.
- **방향**: 구성원이 더 효과적으로 일하도록 **업무 자동화와 시스템**을 개발해 조직 전반에 영향과 인사이트를 제공.
- **범위**: 개발만이 아니라 **문제 정의부터 성과 측정까지** 전 과정 주도.

합류 후 업무(JD):

- 토스플레이스 여러 팀을 관찰하고, 반복적이거나 비효율적인 수작업을 기술로 자동화하고 시스템화한다.
- 다양한 외부 물류 시스템과 데이터를 연동하고, TypeScript, Node.js, Nest.js 기반의 **서버, 배치, Internal Product**를 개발한다.
- 반복되는 문제를 빠르게 패턴화하고, **재사용 가능한 모듈과 시스템**을 만들어 플랫폼을 점점 효율화한다.

핵심: 이 직무는 결제 승인 트래픽을 처리하는 대고객 백엔드가 아니라, **단말기와 물류라는 물리 자산의 생애주기를 데이터로 관리하고, 사내 반복 업무를 자동화하는 내부 플랫폼**이다.

## 토스플레이스는 무엇을 하는가

- 당시 공개 소개를 기준으로, 비바리퍼블리카(토스) 계열에서 오프라인 매장 운영과 대면결제를 다루는 사업이었다.
- 결제 단말을 가맹점에 공급하고 운영한다. 그래서 **물리 단말의 재고, 출고, 설치, 고장, 회수**라는 물류와 자산관리 문제가 사업의 중심에 있다.
- 이 직무(Operations)는 그 물류와 단말 운영을 떠받치는 내부 시스템과 자동화를 만든다.

## 토스 생태계 내 위치

- 토스(슈퍼앱), 토스뱅크, 토스증권, 토스페이먼츠(온라인 결제 PG), 토스플레이스(오프라인 결제와 단말).
- 당시 공고는 여러 계열사의 Node.js Developer 채용을 함께 다뤘지만 팀별 문제는 달랐다. 토스플레이스에서는 단말 생애주기와 물류 운영 플랫폼이라는 공개 역할 정의에 맞춰 준비했다.

## 사전 과제 설계와 직무의 연결

사전 과제의 원문이나 코드를 복제하지 않고, 당시 답변에서 사용한 일반화된 연결만 남긴다.

| 과제에서 설명한 설계 | 공개 역할과의 연결 | 당시 한 줄 답변 |
| --- | --- | --- |
| 대기와 확정 상태 전이 | 단말과 물류 자산의 상태 머신 | 상태와 전이 규칙을 바꾸면 자산 생애주기에도 적용할 수 있다. |
| 트랜잭션 경계와 충돌 불변식 | 재고 수량과 자산 상태 정합성 | 동시 상태 전이는 데이터베이스 안전망으로 보강해야 한다. |
| 멱등 표식과 재시도 | 배치 자동화와 실패 복구 | 중복 실행과 유실을 따로 보고 멱등 처리와 실패 격리를 설계한다. |
| 전송 구현 분리 | 외부 물류 시스템과 자동화 연결 | 새 연동 채널을 추가해도 핵심 상태 전이 규칙은 바꾸지 않는다. |
| 상태 변경 이벤트와 리스너 | 후속 업무 자동화의 시작점 | 인프로세스 분리는 결합을 줄이지만 전달 보장은 아니므로 Outbox와 멱등 소비를 별도로 검토한다. |
| 접두 검색, 조회 권한과 테스트 | 사내 운영 도구의 탐색성과 접근 통제 | 내부 도구도 권한, 성능, 검증 경계를 제품 품질로 다룬다. |

이 연결은 직무를 이해하기 위한 비유일 뿐, 실제 회사 시스템의 구현을 뜻하지 않는다.

## 왜 이 직무인가 (FIT 톤)

- JD가 "문제 정의부터 성과 측정까지 주도"를 명시한다. **명확한 기술 문제와 측정 가능한 성과**에서 강한 내 성향과 정확히 정렬된다.
- 반복 수작업을 시스템으로 제거할 때는 관찰, 패턴화, 자동화와 결과 검증을 한 흐름으로 다룬다.
- 물리 자산을 다루는 시스템은 상태 전이, 정합성, 재처리와 관측을 함께 설계해야 한다.

## 회사 맞춤 역질문 (직무 정렬)

- 단말기 생애주기를 상태 머신으로 모델링하나요, 이벤트 소싱에 가깝나요? 상태 전이의 정합성은 어디서 강제하나요?
- 외부 물류 시스템 연동에서 재고 카운트 어긋남 같은 정합성 문제는 어떻게 맞추나요(보상 트랜잭션, 재대사)?
- 업무 자동화의 성과를 어떤 지표로 측정하나요(절감 시간, 수작업 에러율, 처리량)?
- Internal Product라 사용자가 사내 구성원인데, 여러 팀의 요구 우선순위는 어떻게 정하나요?
- 배치와 실시간 처리의 경계는 어떻게 두나요? 배치 실패의 재처리와 멱등성은 어떻게 보장하나요?
