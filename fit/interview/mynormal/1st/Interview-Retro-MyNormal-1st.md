# 마이노멀컴퍼니 1차 면접 회고

자동 전사의 명백한 기술 용어 오기는 평가 근거에서 제외한다. 질문과 제3자 반응은 역할 기반으로 풀어 적고, 비공개 운영 수치, 회사 내부 구조와 업무 방식의 세부는 보존 대상에서 제외한다. 본인의 당시 답변과 현재 교정을 구분한다.

## 진행 흐름과 답변 교정

### 00:31~02:40 자기소개와 지원 동기
- 질문과 당시 답변: 정합성과 재고 관련 경력, 최근 검색 개선과 구조 단순화 경험을 소개했다. 식품 광고와 제품을 통해 회사를 알았고, 지원 제안을 사업 확장으로 이해해 경험과 맞는다고 설명했다. 제품에 대한 실제 관심과 구매 경험을 지원 이유로 연결했다.
- 현재 교정: 회사와 브랜드를 알게 된 계기와 현재 채용 역할에 지원한 이유를 분리한다. 사업 단계나 확장 방향은 확인한 정보만 말한다. 현재 앱의 기록과 알림 문제에 내 경험을 연결하고 커머스 확장은 개인 가설로 구분한다.

### 02:40~04:08 저장소와 서비스 분리
- 질문과 당시 답변: DB 쿼리를 서비스에서 별도 저장소로 뺀 이유를 물었다. 컨트롤러, 서비스, 저장소의 역할을 분리하고 싶었고, 리치 도메인은 과제 범위에 과하다고 판단해 트랜잭션 스크립트 방식으로 접근했다고 답했다.
- 현재 교정: 일반적인 계층 설명 뒤에 실제 변경 이유를 붙인다. 저장 방식 변경과 업무 정책 변경을 분리한 것, 트랜잭션과 사용자 범위를 어떻게 전달하는지 설명한다. 특정 계층이 예외 처리 전체를 맡는다고 일반화하지 않는다.

### 04:08~05:27 회차와 알림을 같은 서비스에 둔 이유
- 질문과 당시 답변: 파일이 늘면 관리 요소도 늘어나므로 현재 범위에서는 하나로 두는 편이 낫다고 답했다. AI로 생성한 뒤 코드를 검토했고, 요구사항이 구체적으로 달라지면 분리하겠다고 설명했다.
- 현재 교정: 파일 수만으로 판단하지 않고 같은 정책과 트랜잭션 흐름을 조정하는 책임, 별도 변경이 생길 때의 분리 기준을 말한다. AI 사용 사실에 더해 본인이 채택하거나 수정한 정책과 검증 사례를 설명한다.

### 05:27~07:51 API와 워커의 공통 처리
- 질문과 당시 답변: 두 경로가 같은 사용자 처리 메서드를 사용하는 이유를 물었다. 코드를 확인할 시간을 요청한 뒤 사용자 잠금, 예약 확인과 콜백의 공통 로직으로 정합성을 지키려 했다고 설명했다.
- 현재 교정: 코드 확인 요청 자체를 실패로 판단하지 않는다. 공통화한 대상이 시간 정책과 상태 전이이며, API와 워커 중 어느 쪽이 먼저 실행해도 같은 규칙을 적용하려는 선택이라고 구체화한다. 실제 코드 대조는 별도 확인 과제다.

### 07:51~09:34 발송 지연과 조회 응답
- 질문과 당시 답변: 조회 요청이 알림을 선점한 뒤 발송이 늦으면 발송 전에 응답할 수 있는지 물었다. 외부 발송인지 DB 기록인지 확인한 뒤, 잠금 때문에 순차 처리된다고 답했다.
- 현재 교정: 잠금 해제 시점과 요청 경로의 발송 완료 대기를 분리한다. 기존 과제 준비 문서 A4-1은 선점 커밋 뒤 잠금 밖에서 발송하고 다시 조회해 응답한다고 설명한다. 이 설계라면 발송 대기로 응답이 늦어질 수 있지만 사용자 행 잠금을 계속 잡기 때문은 아니다. 제출 코드의 실제 반환 경로는 재검증하지 않았다.

### 09:41~12:10 무중단 배포에서 기존 서버 종료
- 질문과 당시 답변: 사용 중인 서버를 내리기 전에 할 일을 물었다. 빅뱅, 롤링, 블루그린, 카나리와 롤백 비용을 설명하고 과거 롤링 배포 사용 경험을 말했다.
- 현재 교정: 새 요청 유입과 신규 작업 선점을 중단하고, 진행 중 요청과 작업을 유예 시간 안에 마무리하며, 미완료 작업의 복구 경계와 자원 정리를 먼저 답한다. 배포 전략 비교는 후속 설명이다. 선택한 전달 보장에 따라 재시도 가능 여부가 달라짐을 인정한다.

### 12:10~13:23 인덱스가 빠른 이유
- 질문과 당시 답변: MySQL의 B+Tree, 얕은 깊이와 루트에서 리프까지 찾아가는 구조를 설명했지만 구체적인 탐색 원리는 확신하지 못했다.
- 현재 교정: 정렬된 키와 높은 분기 수로 후보 범위를 좁혀 필요한 페이지 접근을 줄인다고 설명한다. 인덱스 구조를 실제 행 조회와 연결하고, 모든 조회가 같은 비용이나 상수 시간이라고 단정하지 않는다.

### 13:23~14:15 전체 스캔이 유리한 경우
- 질문과 당시 답변: 테이블이 작을 때 인덱스의 이점이 적다고 답했다. 인덱스를 클러스터드 인덱스와 테이블 복사 개념으로 설명했다.
- 현재 교정: 작은 테이블뿐 아니라 많은 행을 가져와야 해서 보조 인덱스 이후 행 접근이 반복되는 경우도 비교한다. InnoDB 클러스터드 인덱스는 행 데이터를 담고, 보조 인덱스는 검색 키와 기본키를 담는 구조로 구분한다. 커버링 여부와 실제 계획도 확인한다.

### 14:15~16:30 원자성과 격리 수준
- 질문과 당시 답변: 격리성을 먼저 설명하고 RU, RC, RR, SERIALIZABLE을 열거했다. MySQL과 Oracle의 기본 수준을 언급했지만 RC와 RR 차이는 답하지 못했다. 원자성은 한 번에 작업한다는 정도로 답했다.
- 현재 교정: 원자성은 트랜잭션 변경의 전부 반영 또는 전부 취소다. 격리성은 동시 실행의 상호 영향을 제어하는 성질이다. InnoDB 일반 비잠금 조회에서 RC는 조회마다 새 스냅샷, RR은 같은 트랜잭션의 첫 일관 읽기가 정한 스냅샷을 사용한다. 잠금 읽기는 별도로 설명한다. 지원하는 수준과 기본값을 구분한다.

### 16:30~17:35 트랜잭션 안에서도 동시성 문제가 남는 이유
- 질문과 당시 답변: 트랜잭션 실행 구간이 겹칠 수 있고, 두 요청이 재고를 차감할 때 결과가 어긋날 수 있다고 설명했다. 잘못된 차감 수량을 여러 방향으로 예시했으나 구체적인 실행 순서는 제시하지 않았다.
- 현재 교정: 두 요청이 같은 값을 읽고 각자 계산한 값을 덮어쓰는 lost update를 순서대로 보여 준다. 원자성만으로 읽기, 계산, 쓰기 사이의 충돌을 막지는 못하며 SQL 형태와 격리 수준, 잠금에 따라 결과가 달라진다. 다른 오류 결과는 별도 원인 없이 같은 예로 단정하지 않는다.

### 17:35~19:24 낙관적 락과 비관적 락의 선택
- 질문과 당시 답변: 비관적 락은 충돌을 전제하고, 낙관적 락은 충돌 시 처리하는 방식으로 설명했다. 실무에서는 동시 입력에 따른 충돌 빈도를 보고 SELECT FOR UPDATE를 선택했다고 답했다.
- 현재 교정: 충돌 빈도를 선택 기준으로 제시한 점은 유지한다. 낙관적 방식은 버전 등을 조건으로 갱신하고 영향받은 행 수로 충돌을 감지하며, 재시도 또는 충돌 응답을 설계한다. 비관적 방식도 대기와 데드락, 트랜잭션 길이의 비용이 있음을 설명한다.

### 19:24~20:32 데드락을 줄이는 방법
- 질문과 당시 답변: 자원을 서로 선점하려고 경쟁하는 상태로 설명하고 프로세스를 종료한 뒤 다시 처리해야 한다고 답했다.
- 현재 교정: 단순 경합과 순환 대기를 구분한다. 데드락 로그에서 쿼리와 잠금 순서를 확인하고 순서 통일, 짧은 트랜잭션, 인덱스로 잠금 범위를 줄인다. InnoDB가 감지해 롤백한 트랜잭션은 외부 부작용과 멱등성을 고려해 제한적으로 재시도한다. 프로세스 종료를 일반 예방책으로 제시하지 않는다.

### 20:32~21:57 캐시 도입 판단
- 질문과 당시 답변: DB 쿼리 수와 스파이크 부하를 줄여야 하며 무조건 스케일업할 수는 없다고 설명했다. DB CPU나 메모리가 절반 정도를 넘으면 캐시를 고려하는 기준을 제시했다.
- 현재 교정: 자원 사용률 하나를 공통 임계값으로 삼지 않는다. 반복 조회와 실제 병목, 지연 목표, 데이터 변경 빈도, 허용 가능한 오래된 값과 무효화 비용을 확인하고 효과를 검증한다. 쿼리 개선과 인덱스, 용량 확장도 같은 목표로 비교한다.

### 22:03~25:09 짧은 재직과 도메인 적합성
- 질문과 당시 답변: 현재 재직을 전제로 짧은 기간 뒤 이직을 검토하는 이유를 물었다. B2C를 경험하고 싶어 합류했지만 콘텐츠보다 식품, 물류와 현물이 오가는 문제에서 보람을 느끼며 커머스에 관심이 있다고 답했다. 앱 역할과 커머스의 차이를 묻는 후속 질문에는 웰니스 습관과 식품 구매가 이어질 수 있다는 가설을 설명했다.
- 현재 교정: 기존 마스터의 근무 종료 사실과 전사에서 현재 재직 전제를 명확히 정정하지 않은 점을 대조한다. 초반에 최근까지라는 표현은 있었으므로 의도적인 은폐로 단정하지 않는다. 도메인 선호로 확정된 종료 경위를 대신하지 않고, 다음 대화에서는 상태를 바로잡은 뒤 현재 앱 역할에 대한 동기를 설명한다.

### 25:09~28:42 최근 주요 작업, 제안과 본인 기여
- 질문과 당시 답변: 검색 이관과 구조 단순화에 시간을 썼다고 답했다. 기존 구조를 과하다고 평가했고, 본인의 검색 관심과 팀의 비용 절감 방향이 맞았다고 설명했다. API 전후 차이를 묻자 조회와 색인 변경을 구분해 설명했지만 내부 처리 배경이 길어졌다.
- 현재 교정: 팀의 기존 선택을 평가하는 표현을 줄이고 관측 조건, 팀의 결정과 내 담당 범위를 먼저 말한다. 조회 동작 유지와 변경한 처리 경로를 구분하며, 저장소 통합과 실행 서비스 통합을 같은 뜻으로 쓰지 않는다. 내부 구현 세부는 공개 기록에 옮기지 않는다.

### 28:42~31:14 알림 처리와 고정 대기 제거
- 질문과 당시 답변: 서로 다른 사례가 섞여 질문되자 알림 사례라고 정정했다. 고정 대기와 실행 시간 초과, 운영 요청의 불편과 큐 도입 배경을 설명했다. 대기를 제거해도 되는 근거를 다시 물었지만 원래 목적과 제거 후 검증은 설명하지 못했다.
- 현재 교정: 원래 대기의 목적, 실행 로그의 시간 비중, 호출 제한과 중복 처리, 같은 조건에서의 변경 전후 검증을 나눈다. 확인하지 않은 근거는 만들어 넣지 않는다. Lambda 함수에 설정한 제한과 서비스 일반 상한도 구분해 말한다.

### 31:14~33:31 데이터 수집 안정화
- 질문과 당시 답변: 로그인과 세션 변화에 의존하던 수집 문제를 조사하고 다른 데이터 접근 경로를 확인했다고 설명했다. 한 번의 처리량을 줄이고 진행 상태를 저장해 점진적으로 수집하는 방식으로 바꿨다고 답했다.
- 현재 교정: 문제, 관측, 변경과 남은 제약을 연결한 흐름은 유지한다. 이전의 가정과 직접 확인한 사실을 구분한다. 비공개 접근 경로와 수집 대상 내부 동작은 재사용 답변이나 공개 회고에 복제하지 않는다.

### 33:31~35:59 인덱스 개선의 원인과 검증

- 면접 직후 감정과 긴장 정도는 사용자에게 확인되지 않았다. 전사 오류나 말의 반복만으로 감정과 역량을 단정하지 않는다. 결과 확인 후 감정도 미확인이다.
