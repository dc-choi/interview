# 마이노멀컴퍼니 1차 FIT 답변, 컬처핏 질문, 역질문

> [[Interview-Prep-MyNormal-1st|메인 문서]]로 돌아가기. 답변은 common 마스터를 fork하고 공개 JD와의 연결 끝줄만 붙였다. [사용자 확정 필요]로 표시한 칸은 채우기 전까지 면접에서 쓰지 않는다.

## 1. 1분 자기소개 (자기소개 마스터 fork)

> 안녕하세요, 백엔드 개발자 [이름]입니다. Node.js와 TypeScript로 서비스를 설계부터 운영까지 맡아 왔습니다.
>
> 트라이포드랩에서 NestJS 기반 재고 관리 서비스의 백엔드를 설계하고 운영했습니다. IoT 입력으로 생기는 동시 재고 갱신은 DB 잠금과 짧은 트랜잭션으로 정합성을 지켰고, 수기 발주 흐름은 EventBridge와 SQS 기반 이벤트 처리로 자동화했습니다. 느린 조회는 실행 계획과 실제 호출 경로를 확인해 인덱스와 쿼리 구조를 함께 조정했고, Grafana, Prometheus, Loki로 운영 신호를 직접 확인할 수 있게 했습니다.
>
> 저는 개발 속도만큼 운영 안정성을 중시합니다. 실패와 재시도, 복구와 관측을 처음 설계에 포함하고, 변경이 미치는 범위를 확인합니다. 인아웃은 사용자의 기록이 안정적으로 쌓이고 알림이 제때 닿아야 신뢰가 생기는 서비스라서, 정합성과 예약 작업, 이벤트 처리를 운영해 온 경험으로 기록과 알림, AI 기능의 기반을 단단하게 만드는 데 기여하고 싶습니다.

**조건**: 현재 소속은 첫 문장에 넣지 않는다. 연차를 말한다면 이력서 연월로 계산한 값만 쓴다. 마이노멀에 낸 이력서에는 키노라이츠가 재직중으로 적혀 있으므로(사용자 확인) 자기소개 직후나 경력 질문에서 먼저 바로잡는다: 이력서에는 재직 중으로 되어 있는데, 키노라이츠는 9월 중순에 마쳤습니다. 이어서 C1 답변을 쓴다.

## 2. 지원 동기와 제안 수락 동기

**질문 예**: 제안을 받고 지원하셨는데, 수락한 이유가 무엇인가요? 왜 인아웃인가요?

**답변 골격**:

1. 공고를 읽고 역할의 문제 정의가 제 경험과 겹쳤다. 기록이 안정적으로 쌓이는 것, 알림이 제때 닿는 것, 로그와 지표로 원인을 찾아 재발을 막는 것.
2. 새로 도전할 축이 분명했다. LLM API와 서비스 데이터를 연결해 품질, 속도, 비용을 함께 개선하는 일은 제가 아직 운영해 보지 않은 영역이고, 기존의 정합성과 비동기 처리 경험이 그 기반이 된다고 봤다.
3. 공고가 AI 제안 코드의 검증을 명시한 점. AI 도구를 쓰되 채택 책임은 사람이 진다는 제 작업 방식과 같다.
4. 직전 역할에서 배운 기준(기대 결과와 완료 조건을 먼저 합의)을 처음부터 적용할 수 있는 역할을 찾았고, 이 공고는 기대하는 결과가 구체적으로 적혀 있었다.

> 제안을 받고 공고를 보니 기록, 알림, AI 기능을 안정적으로 운영하는 것이 역할의 중심이었습니다. 정합성과 예약 작업, 이벤트 처리를 직접 설계하고 운영해 온 경험을 바로 쓸 수 있고, LLM 기능의 품질과 비용을 다루는 일에서는 새로 배우며 기여할 수 있다고 봤습니다.

**꼬리**: 제품을 써 봤는가 → 직접 사용해 관찰한 사실 한두 개만 말한다. 사용 전이면 써 보지 못했다고 말하고 공고에서 이해한 사용자 흐름으로 답한다.

**피할 것**: 성장 가능성이 커서, 안정적인 회사라서 같은 어느 회사에나 붙는 말. 회원 규모나 손익분기점 같은 회사 주장을 근거로 칭찬하는 말.

## 3. 컬처핏 예상 질문 (9)

### C1. 직전 회사를 짧게 마친 이유, 이직 사유 (동기 마스터 현재 사이클 fork)

- **질문 의도**: 같은 이유로 곧 떠날 사람인지, 외부 탓을 하는지 본다.
- **답변 (30초 안에 끝낸다)**:

> 올해 6월 말 합류해 검색과 데이터 수집을 맡았는데, 팀이 기대하는 일하는 방식과 제 방식의 차이를 수습 기간 안에 좁히지 못해 본채용으로 이어지지 않았습니다. 돌이켜 보면 완료 조건을 먼저 맞추지 않고 제 판단으로 진행했고, 검증 결과를 공유하는 것도 늦었습니다. 그 뒤로는 합류 초기에 기대하는 결과와 완료 기준부터 합의하고, 진행 상황을 근거와 함께 먼저 공유하는 것을 기본으로 삼고 있습니다.

- **꼬리: 그 기준을 어디에 적용해 봤나** → [사용자 확정 필요: 퇴사 뒤 실제로 적용한 사례가 있으면 그것. 예를 들어 이번 과제에서 요구사항과 가정을 먼저 적고 시작했다면 그 사실]. 사례가 없으면 시제를 낮춰 다음 역할의 첫 주부터 이렇게 하겠다고 답한다.
- **이어서**: 해명을 덧붙이지 않고 트라이포드랩에서 설계부터 운영까지 책임진 경험으로 넘어간다. 인아웃에서는 수습 기간의 기대 결과를 역질문 1번으로 먼저 확인하겠다고 연결한다.
- **금지**: 회사, 동료, 평가 과정을 사유로 말하지 않는다. 직전 사이클(트라이포드랩에서 키노라이츠로 옮긴 이유) 답변을 섞지 않는다.

### C2. 짧은 재직 기간

- **질문 의도**: 적응 실패의 반복인지, 선택 기준이 있는지 본다.
- **답변 본문**: 키노라이츠는 C1 답변을 그대로 쓴다. 이썸테크는 아래 과거 사례를 쓴다.
- **답변 골격**: 기간은 반복하지 않고 사실만 짧게 인정한다. 역할 기대와 내 준비가 어디서 어긋났는지 자기 기준으로 말한다. 지금은 지원 전에 첫 90일의 범위와 완료 조건, 검토 구조를 확인한다는 행동으로 닫는다.
- **이미 쓸 수 있는 과거 사례**: 이썸테크의 짧은 첫 경력은 마스터 답변이 있다. 구현 경험은 쌓았지만 운영 책임이 있는 환경이 더 필요했고, 이후 지원 전에 운영 방식과 역할 범위를 확인하게 됐다.

### C3. 이력서에 없는 공백이나 현재 활동

- **질문 의도**: 이력서와 실제 상태가 일치하는지 본다.
- **답변**: 9월 중순 퇴사한 뒤 지난 경험을 회고하고 다음 역할을 준비하고 있습니다. 그때 정리한 기준이 앞서 말씀드린 기대 결과와 완료 조건을 먼저 합의하는 것입니다.
- **원칙**: 개인 사업 활동은 먼저 꺼내지 않는다. 겸업이나 사업 여부를 직접 묻는다면 사실대로 답한다.

### C4. AI 개발 도구를 어떻게 쓰고 검증하는가

- **질문 의도**: 자격요건 그대로다. 제안된 코드와 설계를 이해하고 검증할 수 있는가.
- **답변 (FIT 마스터 10번 fork)**:

> 코드 생성뿐 아니라 개발 흐름 자체를 설계하는 데 AI를 씁니다. 경로별 규칙 문서로 AI가 건드릴 영역과 건드리면 안 되는 영역을 나누고, 공식 문서를 조회하게 하며, 작업이 끝날 때 변경 파일 검사와 테스트가 자동으로 돌도록 팀 규약으로 만들었습니다. 반복 구현과 조사는 맡기지만, 요구사항 해석, 설계 선택, 결과 채택은 제가 결정하고 책임집니다. 인아웃에서도 제안 코드가 테스트와 실행 결과로 검증된 뒤에만 들어가도록 하겠습니다.

- **꼬리**: AI 제안을 기각한 사례 → [사용자 확정 필요: 공개 가능한 사례 하나]. 없으면 틀릴 수 있는 지점(버전 차이, 잠금 범위, 트랜잭션 경계)을 공식 문서와 테스트로 확인하는 절차로 답한다.

### C5. 요구사항이 모호할 때 어떻게 하는가

- **질문 의도**: 자격요건의 모호한 부분 확인과 동료 논의 역량.
- **답변 (FIT 마스터 2-A, 3번 fork)**:

> 기획 의도를 먼저 묻고 제가 이해한 내용을 다시 말해 맞춥니다. 정산과 연결된 환불 정책 변경 요청에서 새 정책이 기존 흐름과 충돌할 가능성이 보여, 고객 영향과 사후 정정 비용을 정리해 공유하고 범위를 나눠 검증하자고 제안했습니다. 일정은 조정됐지만 보호 조건을 먼저 마련해 안정적으로 출시했습니다. 백오피스처럼 요청자가 내부 동료인 기능에서도 같은 방식으로 필수와 보조를 나눠 합의하겠습니다.

- **꼬리**: 끝까지 의견이 다르면 → 위험과 대안을 문서로 남기고 결정 권한이 있는 역할에 판단을 요청한다.

### C6. 실패 경험

- **답변 (FIT 마스터 12번 fork)**: 시솔지주에서 외부 정보를 주기적으로 수집하는 배치의 오류가 늘었을 때, 수동 확인으로 버티다 지속 불가능하다고 판단해 영향과 원인 가설로 나누고 중요한 경로부터 자동 검증과 배포 전 검사를 넣었다. 이후 발견 뒤 대응보다 출시 전 실패를 줄이는 것을 기준으로 삼았다.
- **연결**: 공고의 같은 문제가 반복되지 않도록 개선한다는 업무와 맞춘다.
- **꼬리**: 지금 다시 만든다면 → 관측 지표, 재시도 정책, 테스트 게이트를 처음 설계에 포함한다.

### C7. 5년 후 목표

- **답변 (FIT 마스터 4번 fork)**: 직함보다 복잡한 문제를 끝까지 책임지고 팀의 기술 판단을 돕는 영향력을 목표로 한다. 백엔드 리드 또는 Staff 방향이다.
- **주의**: 개인 사업은 먼저 꺼내지 않는다. 장기 근속을 약속하는 말은 사용자가 정한 방향이 아니므로 하지 않는다.
- **꼬리**: 그 목표에 이 회사가 어떤 의미인가 → 기록, 알림, AI 기능을 한 사람이 전반적으로 맡는 역할이라 기술 판단의 범위를 넓힐 수 있다고 연결한다.

### C8. 동료와 일하는 방식, 피드백

- **답변 (FIT 보조 마스터 1, 10번 fork)**: 의견을 단정적으로 전달했던 경험 뒤로 결론을 먼저 말하되 의도를 묻고 대안을 함께 제시한다. 성급함을 보완하려고 중요한 결정 앞에서는 상대의 맥락과 대안을 확인하는 단계를 둔다.
- **연결**: 백엔드 전반을 관장하는 역할일수록 결정 근거를 문서로 남겨 동료가 검토할 수 있게 한다.
- **꼬리**: 동료와 기술 의견이 계속 다르면 → 판단 기준을 먼저 맞추고, 작은 범위로 실험해 결과로 정한다.

### C9. 업무 강도와 집요함에 대한 생각 (FIT 마스터 11번 fork)

- **질문 의도**: 공고의 집요하게, 가장 난이도 높은 스테이지 같은 문구에 맞는 사람인지 본다.
- **답변**:

> 의미 있는 문제라면 집중해서 끝까지 해결할 수 있습니다. 다만 지속 가능한 방식으로 일하고 싶어서, 팀이 우선순위를 어떻게 정하고 장애나 과부하를 어떻게 회고하며 회복하는지를 함께 확인하고 싶습니다.

- **주의**: 과도한 헌신을 약속하거나 강도를 부정적으로 단정하지 않는다.
- **꼬리**: 장애가 새벽에 나면 → 대응하되, 같은 장애가 반복되지 않도록 원인 제거와 알림 기준을 다음 날 정리한다고 답한다. 온콜 방식은 역질문 예비 후보로 확인한다.

## 3-1. 과제 방어 예상 질문 (6)

> 과제는 반복 일정에 맞춰 서버가 요청 없이 회차를 시작하고 종료하며 알림을 남기는 예약 실행 백엔드였다. 시간대와 서머타임 처리, 스키마 설계, 코드 구조가 평가 축이었다. 과제 원문, 코드, 과제 고유 수치와 비공개 저장소 정보는 이 공개 저장소에 옮기지 않고 설계 판단만 적는다(2026-09-29 과제 저장소 대조, 테스트 전체 통과 확인).

- **P1. 동시성은 어떻게 보장했나, 왜 사용자 단위 잠금인가**
  - 답: 모든 변경과 작업자 처리를 사용자 행 잠금 트랜잭션 안에서 하고, 잠금 직후 현재 시각을 한 번만 읽어 이전 설정의 적용 종료와 새 설정의 적용 시작을 같은 순간으로 고정했다. 겹침 검사가 한 사용자의 모든 일정과 진행 중 회차를 함께 봐야 하는 불변식이라 잠금 단위가 사용자여야 단순했다.
  - 대안: 일정 단위 잠금은 여러 일정을 함께 보는 검사를 보호하지 못한다. 사용자 행에 버전을 두는 낙관적 락도 가능하지만, 작업자와 API가 같은 상태를 바꾸고 알림이라는 부작용이 있어 충돌 뒤 재시도가 어렵다고 봤다.
  - 꼬리: 조회 요청도 같은 경로를 타는데 조회가 대부분인 트래픽에서 괜찮나 → 조회 때도 도래한 회차를 먼저 정리하도록 해 요청 시점 정확성을 택했다. 조회 비중이 높으면 읽기 전용 경로를 분리하고 정리는 작업자에게만 맡기는 쪽으로 바꾼다. 한 사용자의 동시 요청은 드물어 실제 경합은 작다고 판단했지만 측정하지 않았다고 말한다.
- **P2. 예정 회차를 미리 만들지 않은 이유, 스키마에서 무엇을 강제했나**
  - 답: 일정마다 다음 시작 시각 하나만 저장하고, 회차는 시작하는 순간에 당시 시간대, 현지 날짜, 지속 시간을 스냅샷으로 복사해 만든다. 설정을 바꿔도 미래 예약을 지우고 다시 만들 필요가 없고, 이미 시작한 회차는 이후 변경의 영향을 받지 않는다. 같은 일정의 같은 현지 날짜 회차는 유니크 제약으로 한 번만 생기고, 종료 시각과 상태의 일관성은 CHECK 제약으로 DB에서 막았다.
  - 꼬리: CHECK 제약은 MySQL 8.0.16 이상에서만 실제로 검사된다. 제약 위반은 애플리케이션 검증을 먼저 통과하므로 정상 경로에서는 나오지 않는다.
  - 꼬리: 작업자가 오래 멈췄다가 돌아오면 → 밀린 회차는 원래 예정 시각으로 기록하고, 기한이 지난 알림은 보내지 않고 생략 상태로 남긴다.
- **P3. 서머타임은 어떻게 처리했나**
  - 답: Temporal로 현지 시각을 시간대 기준 시각으로 바꿀 때 겹치는 시각은 앞쪽을 택하고, 바꾼 결과의 현지 시각이 입력과 다르면 존재하지 않는 시각으로 보고 그날을 건너뛴다. 종료는 현지 시각이 아니라 실제 경과 시간으로 계산한다. 45분 오프셋 지역, 30분 서머타임 지역, 서머타임 전환일을 테스트했고, 서버와 DB 세션의 시간대를 바꿔도 결과가 같은지도 확인했다.
  - 꼬리: 24시간짜리 매일 일정이 서머타임 전환일에 자기 자신과 겹치는 경우 → 일정 기간의 실제 구간을 모두 펼쳐 정렬한 뒤 인접 구간을 비교해 잡았다.
- **P4. 알림 중복은 어떻게 막았고 어디까지 보장하나**
  - 답: 회차 처리 트랜잭션을 커밋한 뒤 별도 트랜잭션에서 알림을 처리하고, 발송 직전에 시각을 다시 읽어 기한을 판정한다. 사용자 잠금 아래에서 대기 상태를 읽고 같은 트랜잭션에서 결과 상태를 커밋하는 직렬화가 중복을 막는다. 대기 상태 조건부 갱신은 이미 끝난 상태를 덮어쓰지 않게 하는 방어선이다.
  - 한계를 먼저 말할 것: 발송 호출과 결과 기록이 원자적이지 않아, 발송 뒤 프로세스가 죽거나 트랜잭션이 롤백되면 중복 발송이 생길 수 있다. README에 적었다. 또 발송을 사용자 잠금 안에서 호출하므로, 실제 외부 푸시라면 발송 지연이 같은 사용자의 요청을 막는다.
  - 꼬리: 실제 푸시를 붙인다면 → 발송 대상을 먼저 기록해 커밋하고 잠금 밖에서 보내는 아웃박스 방식으로 바꾸고, 제공자 멱등키를 쓰되 적어도 한 번 전달을 전제로 받아들인다.
- **P5. 테스트는 어디까지 했나**
  - 답: DB 없이 도는 일정 계산 단위 테스트(여러 시간대, 서머타임, 경계), 입력 검증 테스트, 수동 시계로 시간을 움직이는 DB 통합 테스트(재처리 멱등성, 설정 변경 경계, 충돌 시 전체 롤백, 알림 기한 경계, API와 작업자의 동시 처리), HTTP API 테스트, 실제 시계로 요청 없이 자동 시작되는지 보는 스크립트까지 두었다.
  - 꼬리: 테스트하지 않은 것 → 다중 작업자, 부하, 실제 외부 발송 실패. 과제 범위 밖이라 README에 한계로 적었다.
- **P6. 시간이 더 있었다면, 규모가 커지면 무엇을 바꾸나**
  - 답: 첫째, 발송을 잠금 밖으로 빼는 아웃박스. 둘째, 작업자를 늘릴 때 사용자 잠금이 직렬화는 해 주지만 같은 사용자 대기가 생기므로 SKIP LOCKED 기반 분할. 셋째, 한 사용자의 오류가 작업자 배치 전체를 멈추지 않도록 사용자별 예외 격리. 넷째, 쓰기마다 일정 구간을 펼치는 겹침 검사의 비용을 측정하고 줄이는 것. 규모 수치는 측정하지 않았다고 먼저 인정한다.
  - 꼬리: 제출 직전에 DB 계층을 Prisma와 Kysely로 바꾼 이유와 위험 → 두 도구가 같은 트랜잭션 연결을 쓰는지 검증하다가 확장 패키지가 겹친 트랜잭션에서 연결을 섞는 문제를 재현했고, 패치와 통합 테스트로 고정했다. 바꾼 동기는 유지보수다. 원시 SQL로는 이후 스키마가 바뀔 때마다 쿼리 문자열을 손으로 찾아 고쳐야 해 유지보수가 너무 어렵다고 판단했다. 그래서 일반 CRUD와 스키마, 마이그레이션은 Prisma로 관리하고, 행 잠금이나 컬럼 간 복사처럼 Prisma로 표현하기 어려운 쿼리만 타입이 있는 Kysely로 남겼다. 꼬리로 기한 안에 큰 교체를 한 판단을 물으면, 같은 트랜잭션 연결 검증과 전체 테스트 통과를 확인한 뒤에 바꿨다고 답한다. 서드파티 패치를 운영에 쓰는 위험은 인정하고 상위 수정 여부를 추적하겠다고 답한다.
  - 꼬리: AI는 어떻게 썼나 → 코드와 문서 작성 보조로 썼고, 설계 선택과 검증 결과는 제출 코드와 테스트로 확인할 수 있게 했다고 README와 같은 수준으로 답한다.

## 4. 역질문

역질문 마스터에서 네 개, 회사 특이 질문 두 개를 골랐다. 핵심 2~3개는 외워서 묻는다.

1. **B1 초기 과제와 성공 기준**: 합류 후 가장 먼저 책임질 과제와, 수습 기간에 잘하고 있다고 판단하는 기준은 무엇인가요?
2. **A4 팀 구성과 협업 경계**: 백엔드는 현재 어떤 역할로 구성돼 있고, 이 포지션은 누구와 어떤 결정을 함께 하나요?
3. **C3 관측성과 품질 기준**: 기록 누락이나 알림 지연 같은 문제를 어떤 신호로 감지하고, 해결 뒤에는 어떤 회고와 재발 방지를 거치나요?
4. **E2 코드 리뷰와 배포**: AI 도구로 작성한 코드는 리뷰와 배포에서 어떤 검증 기준을 거치나요?
5. **회사 특이, LLM 기능 평가**: 현재 AI 분석과 코칭 기능의 응답 품질은 무엇으로 평가하고, 품질, 속도, 비용 중 지금 가장 우선하는 축은 무엇인가요?
6. **회사 특이, 글로벌 전개**: 글로벌 사용자를 고려할 때 백엔드에서 먼저 바뀌어야 하는 부분은 시간대와 알림, 다국어 콘텐츠, 데이터 위치 중 어디라고 보고 계신가요?

**예비 후보**: 장애 대응과 온콜은 어떻게 나누고, 장애 뒤 회복 시간은 어떻게 확보하나요?
