# 마이노멀컴퍼니 1차 과제 방어 준비

> 상위 문서: [[Interview-Prep-MyNormal-1st|마이노멀컴퍼니 1차 준비]]. 파일과 줄 번호까지 적은 상세 코드 근거는 vault 밖의 비공개 로컬 메모에만 두고, 이 문서에는 설계 판단만 적는다.

과제는 반복 일정에 맞춰 서버가 요청 없이 회차를 시작하고 종료하며 알림을 남기는 예약 실행 백엔드였다. 1차 화상 인터뷰는 제출한 코드를 중심으로 리뷰한다고 안내됐다. 과제 원문, 코드, 과제 고유 수치는 옮기지 않는다(2026-09-30 제출 전 자체 검토 수정본 대조, 테스트 전체 통과 확인). 자체 검토 수정은 2026-09-30 커밋해 원격에 반영했다. 검토자에게 알릴 최종 커밋이 이 수정 뒤인지 확인하고 말한다.

## 1. 3분 코드 흐름 설명 스크립트

> 요청은 컨트롤러에서 헤더와 본문을 순수 함수로 검증합니다. 알 수 없는 필드나 자동 형변환은 여기서 막고 도메인 타입으로 바꿉니다. 그다음 모든 서비스 메서드는 사용자 처리 함수 하나를 거칩니다. 이 함수는 트랜잭션을 열어 사용자 행을 잠그고, 잠금을 얻은 뒤에 현재 시각을 딱 한 번 읽습니다. 그 시각까지 시작했어야 할 회차를 기존 설정대로 만들고, 끝난 회차를 종료 처리한 다음 요청한 작업을 합니다. 마지막으로 보낼 때가 된 알림을 대기에서 발송 중이나 건너뜀으로 조건부 갱신해 선점하고 커밋합니다.
>
> 커밋으로 잠금이 풀린 뒤에 선점한 알림을 하나씩 보냅니다. 보내기 직전에 시각을 다시 읽어 기한을 재판정하고, 결과는 알림마다 짧은 트랜잭션으로 완료나 건너뜀으로 남깁니다.
>
> 작업자는 같은 프로세스에서 주기적으로 돌면서, 트랜잭션 없이 처리할 일이 있는 사용자를 네 가지 조건으로 모읍니다. 다음 시작 도래, 종료 도래, 시작 알림 대기, 종료 알림 대기입니다. 그리고 사용자마다 API와 똑같은 처리 함수를 빈 작업으로 부릅니다. 그래서 API와 작업자가 시간 정책을 따로 갖지 않고, 누가 먼저 잠금을 잡든 결과가 같습니다.
>
> 데이터 쪽 불변식은 DB에도 걸었습니다. 같은 일정의 같은 현지 날짜 회차는 유니크로 한 번만 생기고, 회차와 일정 소유자가 어긋나지 않게 복합 외래 키를 두었고, 목표 종료 계산과 발송 완료일 때만 호출 시각이 있다는 규칙은 CHECK 제약으로 걸었습니다. 제출 전에 제약마다 위반 쓰기가 실제로 거부되는지 테스트로 확인했고, 그 과정에서 NULL이 빠져나가던 CHECK 두 개를 찾아 고쳤습니다.

**조건**: 세부 질문이 오면 트랜잭션 경계를 세 개로 나눠 말한다. 대상 조회는 트랜잭션 밖, 사용자 처리는 잠금 트랜잭션 하나, 발송 결과 기록은 알림마다 짧은 트랜잭션이다.

## 2. 먼저 인정할 약점 5개

1. **피크 처리량을 측정하지 않았다.** 사용자도 순차, 한 사용자 안의 알림도 순차로 보낸다. 같은 분에 몰리는 버스트에서 기한을 넘긴 알림은 조용히 건너뜀이 된다. 발송 호출마다 제한 시간을 둬서 멈추지는 않지만, 발송기가 느리면 선점한 알림마다 제한 시간이 그대로 쌓인다.
2. **겹침 검사가 사용자 잠금 안에서 CPU를 쓴다.** 활성 일정을 만들거나 바꿀 때마다 활성 일정 전체를 일정 기간만큼 펼치고, 이미 시작한 날짜를 이력 전체에서 일정마다 따로 읽는다. API와 작업자가 같은 이벤트 루프를 쓴다.
3. **조회 API도 잠금, 쓰기, 발송을 한다.** 발송이 끝날 때까지 기다렸다 응답하고, 작업자 잠금에 SKIP LOCKED가 없어 잠긴 사용자 하나가 뒤 사용자 전체를 밀 수 있다.
4. **최대 한 번 전달에 복구 경로가 없다.** 발송 중 상태가 영구히 남고 이를 세는 지표나 경보가 없다. 제한 시간을 넘긴 호출은 취소할 수단이 없어 나중에 실제로 나갈 수도 있다. 종료 신호를 받아도 처리 루프를 끝까지 기다려 종료 시간에 상한이 없고, 발송 실패와 결과 기록 실패가 같은 로그로 남는다.
5. **Kysely 쿼리는 소수인데 패치한 서드파티 확장을 들였고, 제출 직전에 DB 계층을 바꿨다.**

제출 전 자체 검토에서 찾아 고친 것은 약점이 아니라 검토 과정으로 말한다. NULL이 빠져나가던 CHECK 두 개, 제약 위반을 확인하는 테스트가 없던 점, 발송 호출을 끝없이 기다리던 점이다(A11, A18, A24).

## 3. 예상 질문

### 코드 흐름과 구조

**A1. 쓰기 요청 한 건이 응답까지 어떻게 흐르고, 각 단계는 어느 트랜잭션에서 도나요?**
- 답: 1절 스크립트 순서대로 답한다. 겹침 충돌로 거절되면 도래 회차 생성과 알림 선점까지 한꺼번에 롤백되고 발송도 일어나지 않는다. 같은 설정을 다시 저장하면 설정 변경은 아무것도 쓰지 않고 기존 값을 돌려줘 수정 시각과 예약이 그대로다. 다만 같은 트랜잭션의 정리 단계는 평소처럼 돈다.
- 판단 기준: 이전 설정이 끝나는 순간과 새 설정이 시작하는 순간을 같은 값으로 맞춰야 경계에서 빠지거나 겹치는 회차가 없다.
- 꼬리: 왜 잠금 뒤에 시각을 읽나 → 기다리는 동안 다른 처리자가 상태를 바꿀 수 있어서, 잠금 뒤에 읽어야 DB 상태와 적용 시각이 같은 순간을 가리킨다. 밀리초 단위 경계 테스트는 이미 시작한 것으로 보는 규칙을 확인한 것이고, 경합 중에 잠금 뒤에 읽는 순서 자체는 테스트하지 않았다. REPEATABLE READ인데 옛 스냅샷을 읽지 않나 → 드라이버가 일반 BEGIN만 보내고 첫 문장이 잠금 읽기라, 이후 일반 조회의 스냅샷은 잠금 뒤에 만들어진다. 유니크와 조건부 선점이 2차 방어선이다. 이 순서에 기대고 있다는 점은 인정한다.

**A2. API 요청이 없을 때 작업자는 무엇을 하고, 이전 실행이 안 끝났거나 한 사용자가 계속 실패하면요?**
- 답: 진행 중인 실행이 있으면 새로 시작하지 않고 그 결과를 공유해 한 프로세스 안에서 겹치지 않는다. 대상 조회는 네 조건별로 시각 순으로 잘라 합치고, 사용자마다 같은 처리 함수를 부른다. 한 사용자가 실패하면 로그를 남기고 그 실행 동안 제외하며, 제외 조건을 네 조건 각각의 안쪽에 넣어 실패 사용자가 배치를 채워 다른 사용자를 굶기지 않게 했다.
- 판단 기준: 도래 여부를 전부 DB 상태로 판단하면 재시작해도 놓치지 않는다. 밀린 회차는 원래 예정 시각으로 기록하고 기한 지난 알림은 건너뜀으로 남긴다.
- 꼬리: 무한 루프 위험 → 성공한 사용자는 다음 시작이 미래로 밀려 빠지고 실패한 사용자는 제외 목록에 들어간다. 비활성이나 삭제 조건이 조회에 없는 이유 → 활성이고 삭제되지 않은 일정만 다음 시작 시각을 갖도록 CHECK로 강제했다. 큐나 cron 라이브러리를 안 쓴 이유 → 인프라 추가 없이 처리 상태를 DB에 두는 쪽이 요구와 맞았다.

**A3. 작업자가 아직 처리하지 못한 회차가 있는데 그 뒤에 시작 시각을 바꾸는 요청이 오면요?**
- 답: 변경 요청이 잠금 직후 읽은 시각이 적용 시각이다. 요청 작업보다 먼저 정리 단계가 돌아 밀린 회차를 기존 설정과 원래 예정 시각으로 만들고, 새 설정의 다음 시작은 이미 시작한 현지 날짜를 건너뛰어 계산한다. 밀린 시작 알림도 기한 안이면 이 요청이 선점해 커밋 뒤 보낸다.
- 판단 기준: 예정 시작이 적용 시각 이하면 이미 시작한 것으로 본다는 규칙을 별도 분기 없이 처리 순서로 보장한다.
- 꼬리: 이 변경이 겹침으로 실패하면 → 회차 생성과 선점까지 롤백되고, 다음 주기에 작업자가 다시 만든다. 시간대를 바꾼 경우 이미 시작한 날짜 비교 → 현지 날짜 문자열로 비교하는 해석을 택했고, 다른 해석도 가능하다고 인정한다.

**A4. 모듈을 어떻게 나눴나요? 서비스 한 클래스가 너무 많은 일을 하지 않나요?**
- 답: 요청 흐름 순서로 나눴다. 컨트롤러는 HTTP 매핑, 입력 검증은 순수 함수, 반복 일정 계산은 DB와 프레임워크 없는 순수 모듈, 저장소는 생성자에서 트랜잭션과 사용자를 받아 모든 쿼리에 소유자 조건을 붙인다. 서비스는 트랜잭션 경계와 정책을 갖고 작업자는 주기와 종료만 맡는다. 서비스가 일정 유스케이스, 정리, 발송 세 역할을 가진 건 맞아서 기능이 하나 더 붙으면 정리와 발송을 떼고 기능 모듈도 나누겠다.
- 판단 기준: API와 작업자가 같은 경로를 타야 시간 정책이 두 벌이 되지 않는다. 시간대 규칙이 바뀌면 일정 모듈만, 저장 방식이 바뀌면 저장소만 바뀌게 한다.
- 꼬리: class-validator를 안 쓴 이유 → 필드가 적고 알 수 없는 필드 거부와 자동 변환 금지, 오류 코드 통일을 명시적으로 하려 했다. 대가는 스키마 문서 자동 생성이 없다는 점이다. 약점 → 대상 조회만 사용자 범위를 벗어나는 정적 메서드라 저장소 설명과 어긋나고, 종료 시각 계산과 다음 시작 계산이 여러 곳에 흩어져 있다. 한곳으로 모으겠다.

### 요구사항 변경 시 수정 범위

**A4-1. 회차 조회는 왜 처리 뒤에 한 번 더 읽나요?**
- 답: 과제가 API 요청 때도 회차와 알림을 자동 처리하라고 해서, 조회도 사용자 잠금 트랜잭션에서 밀린 처리와 소유 확인을 먼저 한다. 남의 회차면 404와 함께 그 요청의 처리까지 롤백한다. 알림은 잠금을 오래 잡지 않도록 커밋 뒤에 보내고 결과를 따로 기록하므로, 처음 읽은 값은 발송 전 상태다. 그래서 발송이 끝난 뒤 트랜잭션 없이 한 번 더 읽어 최종 상태를 응답한다.
- 꼬리: 요구가 없었다면 → API는 상태만 맞추고 발송은 작업자에게 전담시켜 API 지연을 발송기와 분리했을 것이다. 사본에서 시험 구현해 보니 발송 규칙은 그대로 지켜지고 테스트 두 개만 작업자를 돌리도록 고치면 됐다. 다시 읽는 사이에 바뀔 수 있지 않나 → 응답은 그 시점의 커밋된 상태면 충분하고, 순서가 중요한 쓰기는 모두 잠금 안에서 한다.

**A5. 알림 종류를 하나 더 추가하라면요?**
- 답: 알림 상태를 회차 행에 종류별 컬럼 쌍으로 두었기 때문에 스키마 변경이 먼저다. 상태와 호출 시각 컬럼, CHECK, 대상 조회 인덱스를 추가하고 대상 조회 조건, 선점 루프, 결과 기록 분기, 발송 타입이 바뀐다. 일정 계산, 입력 검증, 컨트롤러, 겹침 검사, 작업자는 그대로다. 종류가 더 늘면 회차와 종류를 유니크로 묶은 알림 테이블로 옮겨 종류 추가를 데이터 추가로 바꾸겠다.
- 판단 기준: 종류가 두 개로 고정일 때는 한 행 조건부 갱신과 CHECK로 상태를 한곳에 두는 편이 단순했다. 그 대가로 종류 추가가 여러 곳 수정으로 번진다.
- 꼬리: 배포 시 기존 회차 → 기본값이 대기면 과거 회차가 한꺼번에 대상이 되므로 끝난 회차는 건너뜀으로 채운다. 시작 전 예고 알림 → 회차가 시작 순간에 생기는 구조라 가장 비싸다. 알림 테이블과 다음 시작 시각 기준 탐지가 필요하다.

**A6. 알림 지연 허용 기한을 줄이거나 종류별로 다르게 하라면요?**
- 답: 기한 판단은 함수 하나에 있다. 잠금 안 선점과 발송 직전 재판정이 같은 함수를 불러 상수 하나와 경계 테스트, README만 바꾸면 된다. 종류별이면 함수가 이미 종류를 받으니 분기만 넣는다.
- 판단 기준: 이르게 보내지 않기, 기한 이내, 시작 알림은 회차 종료 전에만이라는 정책을 한곳에 모았다.
- 꼬리: 왜 두 번 판정하나 → 선점 뒤 앞 알림 발송이 늦으면 뒤 알림이 기한을 넘길 수 있어서다. 이를 재현한 테스트가 있다. 한계 → 예정 시각 뒤 일정 시간 안에 호출한다는 조건은 상수가 아니라 작업자 주기와 처리 속도의 결과다. 기한을 크게 줄이면 처리량이 먼저 문제인데 측정하지 않았다.

**A7. 한 일정에 하루 두 번 시작을 허용하라면요?**
- 답: 먼저 한 일정에 두 시각이 꼭 필요한지, 두 일정을 묶어 보여 주면 되는지 제품에 확인하겠다. 후자면 겹침 검사가 이미 사용자의 모든 일정을 함께 보니 묶음 표시 컬럼 하나면 된다. 전자면 같은 일정은 같은 현지 날짜에 한 번이라는 전제가 유니크, 일정 계산, 이미 시작한 날짜 집합, 입력 검증에 박혀 있어 범위가 크다. 반면 작업자, 대상 조회, 선점과 발송, 겹침 판정은 그대로다.
- 판단 기준: 시작 슬롯의 정체성(08시를 09시로 바꾼 게 같은 슬롯인가)을 정해야 이미 시작한 슬롯 제외 규칙을 적용할 수 있다. 이건 코드가 아니라 정책 결정이다.
- 꼬리: 개수 제한은 → 두 일정 방식이면 슬롯마다 한도를 차지하니 무엇으로 셀지부터 정한다.

**A8. 기간을 정한 일시정지나 특정 날짜 하나 건너뛰기를 넣으라면요?**
- 답: 수동 일시정지와 재개는 지금도 활성 토글로 된다. 기간 일시정지는 재개 시각을 두고 다음 시작 계산 기준을 재개 시각과 현재 중 늦은 쪽으로 바꾸고, 겹침 검사 시작점도 같이 옮긴다. 특정 날짜 건너뛰기는 더 작다. 일정 계산 함수가 이미 제외 날짜 집합을 받으니 건너뛸 날짜를 이미 시작한 날짜와 합쳐 넘기면 된다.
- 판단 기준: 다음 시작 계산 호출이 생성, 수정, 정리 세 곳에 흩어져 있어 헬퍼로 먼저 모은 뒤 기능을 넣는다.
- 꼬리: 조기 종료가 추가되면 → 완료 시 종료 시각이 목표 종료와 같아야 한다는 CHECK를 바꾸는 마이그레이션이 필요하다.

**A9. 일정의 시간대를 바꾸거나, 프로필 시간대를 따라 일정도 바뀌어야 한다면요?**
- 답: 일정은 현지 요일, 현지 시작 시각, 지속 시간, IANA 시간대를 저장하고 실제 순간은 다음 시작 하나만 캐시한다. 그래서 시간대 변경은 다른 필드와 같은 수정 경로에서 새 시간대로 다시 해석된다. 이미 시작한 회차는 당시 시간대와 현지 날짜, 지속 시간을 복사해 두어 영향이 없다. 프로필을 따라 움직여야 하면 사용자 잠금 하나 안에서 모든 일정을 바꾸고 겹침을 한 번에 검사하는 메서드를 두고, 일부가 겹치면 요청 전체를 거부한다.
- 판단 기준: 규칙이 원본이고 실제 순간은 파생값이다.
- 꼬리: 시간대 규칙 데이터가 바뀌면 → 런타임 내장 데이터를 쓰므로 버전을 올리면 저장된 다음 시작 하나가 옛 규칙 값으로 남는다. 배포 때 재계산 작업으로 보완하고, 지금은 README에 한계로만 적었다.

**A10. 삭제를 실제 행 삭제로 바꾸라면요?**
- 답: 지금은 소프트 삭제다. 기록 보존이 요구였고, 진행 중 회차는 삭제 뒤에도 정상 종료되며 겹침 검사에 계속 들어가야 했다. 회차가 복합 외래 키로 일정을 참조하고 연쇄 삭제가 없어 회차가 있는 일정은 삭제가 막힌다. 바꾼다면 진행 중 회차가 끝난 뒤 일정 행만 지우고 회차는 남긴다. 회차가 필요한 값을 스냅샷으로 들고 있어 조회는 그대로다.
- 판단 기준: 연쇄 삭제는 기록 보존 요구에서는 사고 경로다.
- 꼬리: 대가 → 외래 키를 풀면 참조 무결성을 DB가 보장하지 못한다. 회원 탈퇴 같은 개인정보 삭제는 사용자 잠금 안에서 회차와 일정을 한 트랜잭션으로 지우는 별도 경로로 다룬다.

### 스키마와 시간 처리

**A11. 테이블과 키, CHECK 제약은 무엇을 DB에서 강제하나요?**
- 답: 사용자, 반복 규칙인 일정, 실제로 시작한 회차 세 테이블이다. 일정에 ID와 사용자 ID를 묶은 유니크를 따로 둔 건 회차가 두 컬럼을 함께 참조하는 복합 외래 키의 대상이 필요해서다. 그러면 회차 사용자와 일정 소유자가 다른 행을 DB가 받지 않는다. CHECK로는 요일과 지속 시간 범위, 활성이고 삭제되지 않은 일정만 다음 시작을 갖는다는 규칙, 목표 종료 계산, 완료 시 종료 시각, 발송 완료일 때만 호출 시각을 걸었다.
- 판단 기준: 앱 검증이 먼저 막지만 수동 SQL이나 이후 코드 변경으로 불변식이 깨지는 걸 마지막에 막는다. 겹침 금지와 개수 제한처럼 여러 행에 걸친 규칙은 CHECK로 못 걸어 사용자 잠금 아래 앱에서 검사한다.
- 꼬리: 자체 검토에서 찾은 것 → MySQL CHECK는 식이 NULL이면 통과한다. 그래서 종료 시각 없는 완료 행과, 엄격 모드가 아닌 세션에서 날짜 덧셈이 범위를 넘어 NULL이 되는 목표 종료 행이 빠져나갔다. 앱은 그런 행을 만들지 않았지만 CHECK가 막는다고 말하려면 실제로 막아야 해서, 모든 CHECK를 NULL 입력으로 평가해 이 둘만 새는 걸 확인하고 NULL 안전 비교로 다시 만드는 마이그레이션을 제출 전에 넣었다. 검증은 두 가지다. 새던 쓰기가 엄격 모드와 비엄격 모드 모두에서 거부되는지 봤고, 제약 위반 테스트를 옛 정의에 돌려 새던 케이스만 실패하는지 확인했다. 운영 DB에 이미 위반 행이 있으면 마이그레이션이 실패하므로 적용 전 점검 조회와 실패 뒤 복구 순서도 문서에 남기고 재현해 봤다. 남은 것 → 복합 외래 키용 인덱스는 MySQL이 자동으로 만든 것이라 파일에 선언이 없다. CHECK는 MySQL 8.0.16부터 실제로 검사된다.

**A12. 인덱스는 각각 어떤 쿼리를 위한 건가요? 카디널리티 낮은 상태 컬럼을 왜 앞에 뒀나요?**
- 답: 작업자 대상 조회 네 갈래마다 인덱스를 하나씩 맞췄다. 상태는 등호, 시각은 범위와 정렬이라 상태를 앞에 두면 대기 구간만 시각 순으로 읽다 멈출 수 있고, 시각을 앞에 두면 끝난 행이 범위에 섞인다. 끝에 사용자 ID를 붙여 커버링 인덱스로 만들었다. 사용자 단위 조회는 사용자로 시작하는 인덱스가 맡는다.
- 판단 기준: 완료 이력이 쌓여도 대기 구간의 스캔 범위는 커지지 않게 한다.
- 꼬리: 실행 계획은 → 빈 DB로는 의미가 없어 운영 규모로 확인하지 못했다. 이력에 비례해 느려지는 쿼리 → 이미 시작한 날짜를 이력 전체에서 읽는 조회가 있다. 계산은 현재 현지 날짜부터라 며칠 전 이후로 하한을 두면 된다.

**A13. 예정 회차를 미리 만들지 않고 다음 시작 시각 하나만 저장한 이유는요?**
- 답: 일정의 원본은 규칙이고 다음 시작 시각은 작업자가 인덱스로 찾도록 둔 캐시다. 미리 만들면 일정 수 곱하기 기간만큼 행이 생기고, 설정 변경이나 비활성화, 시간대 변경마다 미래 행을 지우고 다시 만들어야 한다. 지금은 변경이 일정 한 행 갱신으로 끝나고, 회차는 시작 순간에 당시 값을 스냅샷해 만든다.
- 판단 기준: 쓰기 비용과 정합성 관리 비용을 줄이는 대신 겹침 검사와 일정 미리보기를 매번 메모리에서 계산하는 비용을 감수했다.
- 꼬리: 작업자가 오래 멈췄다 돌아오면 → 밀린 회차를 원래 예정 시각으로 모두 만들고, 끝난 회차는 같은 트랜잭션에서 완료, 기한 지난 알림은 건너뜀.

**A14. 알림 상태를 회차 테이블의 ENUM 컬럼으로 둔 이유는요?**
- 답: 회차 생성과 알림 대기가 한 행 삽입으로 함께 생기고 선점도 그 행의 조건부 갱신 한 번이라 원자성을 따로 맞출 필요가 없었다. 발송 중 상태는 발송을 잠금 밖으로 옮기면서, 선점했지만 결과를 모르는 상태를 표현하려고 추가했다.
- 판단 기준: 아직 판단하지 않은 대기와 보내지 않기로 확정한 건너뜀을 구분한다. 대상 조회는 대기만 본다.
- 꼬리: 먼저 인정할 것 → 발송 중 값을 ENUM 목록 중간에 넣어서 운영 대용량 테이블이었다면 테이블 복사가 일어났다. 끝에 추가했다면 ENUM 변경 자체는 메타데이터 변경으로 끝났을 것이다. 같은 문장에서 CHECK 두 개도 추가했는데 그 부분의 온라인 DDL 방식은 확인하지 못했다. 운영이었다면 별도 문장으로 나눠 확인하겠다. 건너뜀 사유와 선점 시각도 남기지 않았다.

**A15. 현지 반복 시각과 실제 순간을 어떻게 구분했고, 현재 시각은 어디서 읽나요?**
- 답: 일정에는 현지 규칙만, 실제 순간은 모두 UTC로 저장하고 DB 연결 시간대를 UTC로 고정했다. 현재 시각은 DB 함수가 아니라 주입한 앱 시계에서 잠금 직후 한 번 읽고, 발송 직전에 한 번 더 읽는다. 프로세스와 DB 세션의 시간대를 서로 다르게 바꿔도 결과가 같은지 테스트했다. 숫자 오프셋 시간대는 서머타임을 표현하지 못해 거부한다.
- 판단 기준: 서버와 DB 설정에 결과가 흔들리지 않게 한다.
- 꼬리: 시계가 뒤로 가면 → 회차는 상태를 되돌리는 경로가 없어 취소되거나 중복되지 않는다. 알림은 선점한 뒤 발송 직전 시각이 예정보다 앞으로 돌아가 있으면 일찍 보내지 않고 건너뜀으로 끝나 그 알림은 사라진다. 코드로 추론한 것이고 테스트하지 않았다. 인스턴스 간 시계 차이 → 앱 서버 시계를 신뢰하므로 시계가 빠른 인스턴스는 약간 일찍 보낼 수 있다. 시간대 입력 → IANA 이름을 받지만 대소문자나 옛 별칭을 정규화하지 않고 원문을 저장한다. 정식 ID를 저장하도록 고치겠다.

**A16. 서머타임 때문에 없는 시각과 두 번 나오는 시각은 어떻게 처리하나요?**
- 답: 현지 일시를 Temporal로 순간으로 바꿀 때 겹치는 시각은 앞쪽을 택하는 옵션을 준다. 없는 시각이면 변환 결과의 현지 일시가 입력과 달라지므로 그날은 건너뛴다. 회차는 현지 날짜마다 최대 하나라 두 번째 같은 시각은 후보가 되지 않고 DB 유니크가 한 번 더 막는다. 종료는 실제 경과 시간을 더해 계산한다.
- 판단 기준: 옵션 한 번과 비교 한 번으로 두 경우를 가른다.
- 꼬리: 테스트 범위 → 45분 오프셋, 30분 서머타임, 전환일, 하루 종일 단식이 봄 전환일에 자기 자신과 겹치는 경우. 겹침은 구간을 모두 펼쳐 정렬한 뒤 인접 구간을 비교해 잡는다. 사용자 입장 → 없는 시각이면 그날 단식이 통째로 빠진다는 점을 알고 말한다.

### 보장 범위 (작업자 증가, 발송 직후 종료)

**A17. 작업자를 여러 개 띄우면 무엇이 보장되고 무엇이 깨지나요?**
- 답: 중복 회차와 중복 알림은 DB가 막는다. 사용자 행 잠금이 프로세스와 무관하게 같은 사용자 처리를 직렬화하고, 회차는 유니크, 알림은 대기에서만 옮기는 조건부 갱신이라 나중에 잠금을 얻은 쪽에는 할 일이 남지 않는다. 깨지는 건 효율이다. 대상 조회가 잠금 없는 일반 조회라 작업자들이 거의 같은 목록을 받아 같은 잠금 앞에 줄을 선다. 늘린다면 작업자 경로의 잠금만 SKIP LOCKED로 바꾸거나 사용자 ID로 나눈다.
- 판단 기준: 정합성은 DB 제약과 조건부 갱신으로, 처리량은 작업 분배로 푼다.
- 꼬리: API도 SKIP LOCKED로? → API는 결과를 돌려줘야 하니 기다리는 잠금을 유지한다. 건너뛴 사용자는 잠금을 쥔 쪽이 같은 정리를 한다. 검증 범위 → 한 프로세스 안에서 작업자와 API를 동시에 돌린 테스트뿐이고 다중 프로세스는 돌려 보지 않았다. 앱 인스턴스가 둘이면 → 스케줄러 설정을 한 대에만 켜거나 작업자를 전용 프로세스로 뺀다.

**A18. 알림을 보낸 직후 프로세스가 죽으면 무엇이 남고 무엇이 보장되나요?**
- 답: 트랜잭션 경계로 나눠 답한다. 잠금 트랜잭션 도중이면 전부 롤백되고 다음 주기에 원래 예정 시각으로 중복 없이 다시 만든다. 선점 커밋 뒤 발송 전이면 발송 중으로 남고 다시 보내지 않아 유실된다. 발송 뒤 기록 전이면 실제로는 한 번 나갔지만 DB에는 발송 중으로 남아 앞의 경우와 구분할 수 없다. 어느 쪽이든 중복은 없고, 회차 기록은 알림과 따로 커밋돼 잃는 건 알림 호출뿐이다.
- 판단 기준: 최대 한 번 전달을 택했고, 유실 구간을 README에 적었다.
- 꼬리: 유실 범위 → 호출 중인 한 건이 아니라 같은 처리에서 선점하고 아직 차례가 안 온 알림 전체다. 발송기가 응답하지 않으면 → 자체 검토에서 발송 호출 하나가 돌아오지 않으면 작업자와 정상 종료가 함께 멈춘다는 걸 찾아, 제출 전에 호출마다 제한 시간을 걸고 시간 초과를 발송기 실패와 같은 경로로 처리했다. 발송 중으로 남고, 다시 보내지 않고, 다음 알림은 계속 보낸다. 기존 발송기 오류 테스트를 거부와 무응답 두 경우로 바꿨고, 제한 시간 코드를 빼면 무응답 경우가 끝나지 않는 것도 확인했다. 잘못된 설정값이 거의 0에 가까운 대기로 바뀌지 않도록 허용 범위 밖이면 기본값을 쓴다. 남은 것 → 호출을 취소할 수단이 없어 제한 시간을 넘긴 호출이 나중에 나갈 수 있고, 제한은 호출 한 번에만 걸려서 종료 신호를 받아도 처리할 일이 빌 때까지 루프를 도는 건 그대로다. 백로그가 크면 유예 시간을 넘길 수 있어, 중지 플래그로 현재 사용자까지만 끝내게 바꾸겠다.

**A19. 왜 최대 한 번을 골랐고, 적어도 한 번으로 바꾸려면 무엇이 필요한가요?**
- 답: 중복 요청을 막는 건 앱의 몫이었고 재시도와 장애 복구는 이번 범위에서 빠져 있어서 중복보다 유실을 택했다. 바꾸려면 발송 중 상태에 선점 시각과 시도 횟수를 두고, 임대가 만료된 발송 중 알림을 복구 작업이 조건부로 다시 선점하게 한다. 재시도도 기한 안에서만 하고, 제공자에게 회차와 알림 종류로 만든 멱등키를 넘기며, 결과 기록에 임대 토큰을 조건으로 넣어 늦게 온 이전 시도가 덮어쓰지 않게 한다.
- 판단 기준: 중복과 유실 중 사용자에게 무엇이 더 비싼지, 알림 유효 기한으로 알림 종류별로 고른다.
- 꼬리: 아웃박스와의 관계 → 선점을 커밋하는 게 같은 트랜잭션에 발송 의도를 남기는 구조라 비슷하다. 빠진 건 재시도와 멱등키다. 실패하면 바로 대기로 되돌리면 → 보내지 않은 게 확실할 때만. 타임아웃처럼 결과를 모르면 중복 위험이 있다. 지금 없는 것 → 오래된 발송 중 건수를 세는 지표와 경보. 먼저 걸겠다.

**A20. 한 사용자의 처리가 계속 실패하면 다른 사용자의 알림은요?**
- 답: 최근 변경에서 사용자별 실패 격리를 넣었다. 실패한 사용자는 로그를 남기고 그 실행에서만 제외한다. 실패 트랜잭션은 롤백되니 제외 자체가 선점만 된 알림을 남기지는 않는다. 다만 한 실행은 처리할 일이 남아 있는 동안 계속 돌아서, 실행이 길어지면 제외된 사용자의 알림이 기한을 넘겨 건너뜀이 될 수 있다. 커밋 응답 자체가 실패하면 선점이 반영됐는지 알 수 없어 발송 중으로 남을 수 있다는 것도 코드로 추론한 한계다. 실패 사용자의 데이터로 배치를 가득 채운 테스트로 다른 사용자가 처리되는지 확인했다.
- 판단 기준: 한 사용자의 오류가 전체 처리를 멈추지 않게 하되, 제외 자체가 선점만 된 알림을 남기지 않게 한다.
- 꼬리: 발송기 실패도 사용자 실패인가 → 아니다. 커밋 뒤라 알림 단위로 로그만 남고 다음 알림은 계속 보낸다. 제한 시간 초과도 같다. 약점 → 백오프가 없어 매 주기 오류 로그가 쌓이고, 격리 목록과 경보가 없어 결국 기한을 넘겨 건너뜀이 된다.

### 규모와 병목

**A21. 같은 분에 알림이 크게 몰리면 제시간에 다 보낼 수 있나요?**
- 답: 측정하지 않아서 보장한다고 말할 수 없고 구조상 위험하다. 사용자도, 한 사용자 안의 알림도 순차라 실제 푸시처럼 발송이 느리면 정상 실행 목표 시간부터 넘기고, 더 느려지면 뒤쪽 사용자는 기한을 넘겨 조용히 건너뜀이 된다. 발송 호출 하나가 돌아오지 않아 작업자 전체가 멈추는 문제는 제출 전에 호출마다 제한 시간을 걸어 막았지만, 이건 멈춤을 막는 장치지 처리량을 늘리는 장치가 아니다. 먼저 로그에 남는 예정 시각과 호출 시각의 차이로 지연 분포를 보고, 수동 시계로 같은 분에 몰리는 데이터를 넣어 한 번 실행에 걸리는 시간을 재겠다. 개선은 사용자 간 처리를 커넥션 풀보다 작은 동시성으로 병렬화한 뒤 발송을 별도 단계로 떼는 순서다.
- 판단 기준: 사용자 잠금이 사용자 내부를 직렬화하니 사용자 간 병렬화는 정합성을 해치지 않는다.
- 꼬리: 주기 폴링이 낭비 아닌가 → 한가할 때는 커버링 인덱스 범위 조회 한 번이다. 잠들었다 깨는 방식은 API가 일정을 바꿀 때 작업자를 깨워야 해 복잡하다. 지표 → 분당 건너뜀 수와 지연 p99를 경보로 둔다.

**A22. 활성 일정을 만들거나 바꿀 때마다 일정 기간을 펼쳐 겹침을 검사하는데 규모가 커지면요?**
- 답: 병목 후보로 README에 적은 부분이다. 비용은 날짜를 하루씩 돌며 요일이 맞는 날마다 시간대를 변환하는 데서 나오고, 이 계산이 사용자 잠금 안과 공유 이벤트 루프 위에서 돈다. 이미 시작한 날짜 조회도 이력 전체를 일정마다 따로 읽는다. 측정한 뒤 날짜 하한과 쿼리 묶기부터 하고, 서머타임 전환 시점만 구해 구간마다 오프셋을 한 번만 계산하는 축소는 기존 결과와 같은지 테스트로 확인한 뒤 넣겠다.
- 판단 기준: 검사 범위는 상수 한 곳이라 범위 변경은 쉽고, 비용 축소는 측정으로 필요를 확인한 뒤 한다.
- 꼬리: 잠금 밖에서 계산하면 → 잠금 전에 계산하고 잠금 뒤 변경 여부를 확인해 바뀌었으면 다시 계산하는 낙관적 방식이 가능하지만 복잡도가 는다. 예정 회차를 DB에 펼쳐 SQL로 검사하면 → 설정 변경마다 대량 재생성이 필요해 더 비싸다.

**A23. 요청 대부분이 조회인데 조회까지 행 잠금과 쓰기, 발송을 하는 건 괜찮나요?**
- 답: 조회 결과에 이미 시작했어야 할 회차가 빠지지 않도록 모든 API가 같은 정리 경로를 타게 했다. 자동 실행은 조회에 기대지 않고 작업자가 요청 없이 같은 코드를 돌린다. 비용은 인정한다. 조회마다 잠금 트랜잭션과 쓰기가 생기고, GET이 알림을 보낼 수 있다는 점도 안전한 메서드 의미와 맞지 않는다. 규모가 커지면 조회는 잠그지 않고 읽고 정리는 작업자에게만 맡기거나, 처리할 일이 있을 때만 잠그겠다.
- 판단 기준: 응답 시점 정확성과 읽기 비용의 교환이다. 작업자 주기 안의 지연은 허용 가능하다고 본다.
- 꼬리: 커넥션 풀과 이벤트 루프 공유 → API와 작업자가 한 프로세스라 CPU 작업이 몰리면 둘 다 늦어진다. 운영이면 설정으로 배포를 나누고 풀도 분리하며, 풀 크기는 초당 트랜잭션 수와 트랜잭션 시간으로 잡고 계측으로 정한다. 핫 유저 → 한 사용자의 요청이 몰리면 작업자가 그 잠금을 기다리며 뒤 사용자까지 밀린다. 작업자 경로의 SKIP LOCKED가 답이다.

### 테스트와 도구 선택

**A24. 테스트는 어떻게 나눴고 무엇을 증명하지 못하나요? README와 코드는 일치하나요?**
- 답: 시간 계산은 DB 없는 단위 테스트로 여러 시간대와 서머타임, 경계를 봤다. 잠금과 롤백은 모킹으로 증명할 수 없어 실제 MySQL에 앱을 띄우고 시계와 발송기만 바꾼 통합 테스트로 봤고, 작업자 테스트도 운영과 같은 실행 경로를 호출한다. 발송이 잠금 밖인지는 발송기 안에서 다른 연결로 같은 사용자 잠금을 대기 없이 얻는지로 확인했다. 예상하지 않은 오류 로그가 나오면 테스트가 실패하게 했다. 제출 전 자체 검토에서 유니크, 외래 키, CHECK를 선언만 하고 위반 행으로 거부를 확인한 테스트가 없다는 걸 찾아, 서비스를 거치지 않고 DB에 직접 잘못된 행을 쓰는 제약 위반 테스트를 추가했다. 제약마다 오류 코드와 제약 이름, 테이블이 그대로인지를 본다. 이 테스트를 쓰다가 CHECK 두 개의 NULL 누수를 찾아 고쳤고, 옛 정의로 되돌리면 그 케이스만 실패하는 것으로 테스트가 버그를 잡는다는 것도 확인했다. 발송기 무응답도 테스트로 넣었다. 아직 증명하지 못하는 건 다중 프로세스, 실제 강제 종료, 부하, 종료 중 드레인이다.
- 판단 기준: DB 동작에 기대는 보장은 실제 DB로, 순수 계산은 빠른 단위 테스트로.
- 꼬리: 동시성 테스트가 정말 겹치나 → 동시에 시작하지만 순서가 비결정적이라 매번 겹친다고 보장하지 못한다. README 불일치 → 저장소가 사용자 범위만 다룬다는 설명과 달리 대상 조회는 전 사용자를 본다, 조회 API도 잠근다는 점이 늦게 드러난다, 시간대 입력을 정규화하지 않는다. 이 세 군데를 알고 있다고 먼저 말한다. 서버 오류 본문 형식은 모순은 아니고 일관성을 높일 거리다.

**A25. Prisma에 Kysely까지, 그것도 패치한 확장을 들인 건 과하지 않나요?**
- 답: 타당한 지적이다. 동기는 유지보수였다. 원시 SQL로 두면 스키마가 바뀔 때마다 쿼리 문자열을 손으로 찾아 고쳐야 해서 유지보수가 너무 어렵다고 판단했다. 그래서 일반 CRUD와 스키마, 마이그레이션은 Prisma로 관리하고, Prisma로 표현하기 어려운 행 잠금과 컬럼 간 복사 같은 쿼리만 타입이 있는 Kysely로 남겼다. 두 도구가 같은 트랜잭션 연결을 쓰는지 검증하다가 확장이 겹친 트랜잭션에서 연결을 섞는 문제를 재현했고, 패치와 통합 테스트로 고정했다.
- 판단 기준: 스키마 변경을 타입 검사가 잡아 주는지가 유지보수 비용을 가른다.
- 꼬리: 위험 → 서드파티 배포본을 고친 코드를 운영에 싣는 것, 버전을 올릴 때마다 패치와 테스트를 확인해야 하는 것, 팀이 쿼리 API 두 개를 알아야 하는 것. 상위 수정 여부를 추적하겠다. 부품을 줄이자고 하면 → 해당 쿼리들을 파라미터 바인딩 원시 쿼리로 바꾸고 확장을 뺀다. 소스 쿼리와 DB 설정뿐 아니라 그 확장을 쓰는 테스트 도우미와 확장 회귀 테스트, 타입 생성기와 패치 설정까지 걷어 내야 하지만 범위는 분명하다. 제출 직전 교체 → 같은 연결 검증과 전체 테스트 통과 뒤에 바꿨지만 일정상 위험한 선택이었다고 인정한다.

**A26. AI를 썼는데 이 설계가 본인 것임을 어떻게 보여 주겠어요?**
- 답: AI는 코드와 문서 작성 보조로 썼고 README에 그 사실과 용도를 적었다. 커밋의 공동 작성자 표기는 마지막 커밋에만 있지만, 앞선 커밋도 구현 코드와 문서 작성에 AI 도움을 받았고 설계 결정과 검증은 직접 했다고 사실대로 말한다(2026-09-29 사용자 확정). 제 몫은 무엇을 만들고 어디까지 보장할지 정하고, 나온 결과를 테스트로 반증하는 것이었다. 사용자 단위 잠금과 잠금 직후 한 번 읽은 시각으로 변경 경계를 고정한 이유, 잠금 밖 발송으로 중복 대신 유실을 택한 이유, 확장 문제를 재현하고 패치한 과정은 코드를 보지 않고 설명할 수 있다. 코드에 남긴 단순화 표시 주석은 의도적으로 줄인 곳에 한계와 확장 경로를 적어 둔 것이다. 화면을 공유해 주시면 그 자리에서 고치거나 테스트를 추가해 보겠다.
- 판단 기준: 채택 책임은 사람이 지고 검증은 테스트와 실행 결과로 한다(FIT C4와 같은 원칙).
- 꼬리: AI 제안을 거절하거나 고친 사례(2026-09-29 사용자 확정) → DB 계층을 바꿀 때 AI는 확장을 붙이면 두 도구가 같은 트랜잭션을 쓴다고 설명했다. 잠금과 쓰기가 한 트랜잭션에 묶이는지가 정합성 전체의 전제라서 설명을 믿지 않고 직접 확인했다. 트랜잭션 안에서 두 도구가 조회한 연결 번호를 비교하고 트랜잭션 두 개를 겹쳐 실행해, 나중 트랜잭션이 앞 트랜잭션의 쿼리 빌더를 덮어써 연결이 섞이는 것을 재현했다. 트랜잭션마다 자기 빌더만 보이게 패치하고 재현을 통합 테스트로 남겼다. 상위 저장소 제보는 아직 하지 않았고, 재현 테스트와 함께 올리겠다고 답한다. 커밋이 짧은 시간에 몰려 있는 이유(2026-09-29 사용자 확정) → 로컬에서 기능을 끝까지 만든 뒤, 리뷰어가 따라 읽기 쉽게 스키마와 시간 계산, API와 겹침 검사, 스케줄러와 알림, 자동 실행 검증과 문서 순서의 층별로 나눠 올렸다. 이후의 검증 보강, DB 계층 교체, 발송 구조 변경은 작업 시점 그대로 올렸다. 중간 이력이 없는 이유를 물으면 시행착오가 섞인 로컬 이력을 정리해 올렸고, 판단 근거는 커밋 단위와 테스트로 확인할 수 있게 했다고 답한다. 가장 자신 없는 곳 → 처리량과 잠금 대기를 측정하지 않은 점.
