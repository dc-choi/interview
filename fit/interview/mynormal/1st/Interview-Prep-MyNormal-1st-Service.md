# 마이노멀컴퍼니 1차, 서비스 맥락 질문과 체크리스트

> 상위 문서: [[Interview-Prep-MyNormal-1st|마이노멀컴퍼니 1차 준비]]. 인아웃의 기능 설명은 공고와 원티드 회사 페이지의 공개 소개만 근거로 한다. 내부 구조는 추정하지 않고, 답 끝에 현재 방식을 되묻는다.

### S1. 사용자의 기록이 빠지거나 두 번 쌓이지 않게 하려면 (설계형)

- 의도: 직무 소개의 기록이 안정적으로 쌓이는 서비스
- 답변 골격: 모바일은 네트워크가 끊기고 재전송이 잦다. 클라이언트가 기록마다 고유 ID를 만들어 보내고, 서버는 `(user_id, client_record_id)` unique 제약으로 같은 기록의 재전송을 멱등하게 처리한다. 저장 응답을 받지 못한 기록은 앱이 보관했다가 다시 보낸다. 기록 저장은 가볍게 끝내고 집계, 배지, AI 분석은 이벤트로 넘겨 저장 실패가 후속 처리 때문에 생기지 않게 한다. 커밋 뒤 발행이 빠지는 틈은 Outbox 기록이나 주기적 대사로 메운다(R2에서 인정한 한계).
- 판단 기준: 사용자가 입력한 원본은 절대 잃지 않고, 파생 값은 늦어도 다시 계산할 수 있으면 된다.
- 트레이드오프: 오프라인 기록을 허용하면 기기 간 충돌 규칙(마지막 수정 우선인지, 병합인지)을 정해야 한다.
- 꼬리: 같은 기록을 두 기기에서 동시에 고치면 → 버전 컬럼 조건부 갱신으로 충돌을 드러내고 앱에서 선택하게 한다.
- 내 경험 연결: 워커의 멱등 소비와 상태 전이 검증(R2).
- 되물을 것: 지금 기록 누락이나 중복 문의가 있다면 어느 경로에서 주로 생기는지.

### S2. 원하는 시간에 알림이 제때 닿게 하려면 (설계형)

- 답변 골격:
  1. 예약: 사용자 시간대와 원하는 시각으로 다음 발송 시각을 UTC로 계산해 저장하고, 스케줄러가 도래한 대상을 묶어 큐에 넣는다.
  2. 중복 방지: `(user_id, 알림 종류, 발송 예정 시각)`을 발송 키로 삼아 우리 쪽 중복 발송을 막고, 스케줄러가 여러 대여도 같은 대상을 두 번 집지 않게 잠금이나 상태 전이로 선점한다. 푸시 제공자가 요청을 받은 뒤 응답 전에 끊기면 재시도로 중복이 생길 수 있어 완전히 한 번이라고 말하지 않는다.
  3. 실패: 푸시 제공자의 일시 오류는 제한 재시도, 무효 토큰은 즉시 정리한다.
  4. 폭주: 같은 시각(예: 아침 8시)에 몰리는 발송은 큐와 워커 동시성으로 흡수하고, 발송 지연을 지표로 본다.
- 트레이드오프: 정시 발송과 부하 분산은 충돌한다. 몇 분의 분산을 허용할 수 있는 알림과 없는 알림을 나눈다.
- 내 경험 연결: 주기 집계 리포트를 알림톡과 이메일로 자동 통보한 경험. 대량 모바일 푸시는 직접 운영해 보지 않았다고 말한다.
- 꼬리: 서머타임이 있는 지역 → 시간대 규칙을 라이브러리와 DB의 시간대 데이터로 계산하고 고정 오프셋을 저장하지 않는다.
- 되물을 것: 지금 알림 지연이나 중복 문의가 있다면 어느 시간대에 몰리는지.

### S3. 글로벌 사용자를 고려하면 백엔드에서 무엇이 바뀌나 (설계형)

- 답변 골격: 시간은 UTC로 저장하고 표시와 하루 경계만 사용자 시간대로 계산한다. 음식명, 영양 정보, 알림 문구 같은 콘텐츠는 언어별로 분리해 관리한다. 지역별 개인정보 규제와 데이터 저장 위치 요구를 먼저 확인하고, 지연이 문제가 되는 지역부터 CDN과 읽기 경로를 가깝게 둔다.
- 판단 기준과 트레이드오프: 데이터 위치 규제가 있으면 리전 분리가 필요하지만 운영 비용이 배로 는다. 규제가 없으면 단일 리전과 CDN으로 시작한다.
- 내 경험 연결: 국제 배송 서비스의 번역 기능과 환율 정보 배치(시솔지주).
- 꼬리: 다국어 콘텐츠의 번역 누락 → 기본 언어로 대체하고 누락 목록을 운영 화면에 드러낸다.
- 되물을 것: 현재 주력 해외 시장과 먼저 해결하고 싶은 문제.

### S4. 백오피스를 설계할 때 무엇을 먼저 정하나 (설계형)

- 답변 골격: 누가 무엇을 할 수 있는지 역할과 행위 단위 권한을 먼저 정하고, 사용자 데이터를 조회하거나 바꾼 행위는 감사 로그로 남긴다. 대량 수정과 일괄 발송은 미리보기, 대상 수 확인, 비동기 실행과 진행 상황 조회로 나눠 실수의 비용을 줄인다. 운영 요청을 반복하는 작업부터 화면으로 만든다.
- 트레이드오프: 백오피스를 빨리 만들수록 권한과 감사가 뒤로 밀린다. 민감 데이터 조회와 변경만큼은 처음부터 넣는다.
- 판단 기준: 운영자가 같은 요청을 반복하는가, 실수했을 때 되돌릴 수 있는가.
- 내 경험 연결: 내부 업무 효율화를 위한 자동화와 주기 리포트. 백오피스를 독립 제품으로 설계한 사례는 약하다고 인정한다.
- 꼬리: 운영자가 잘못 일괄 수정하면 → 변경 전 값을 감사 로그에 남겨 되돌리기 작업을 제공한다.
- 되물을 것: 지금 개발팀에 가장 자주 들어오는 운영 요청.

### S5. 건강 기록 데이터는 어떻게 다뤄야 하나 (설계형, 조건 있음)

- 답변 골격: 개인정보 보호법 제23조는 건강에 관한 정보를 민감정보로 분류하고 처리에 별도 동의 같은 요건을 둔다. 식단, 체중, 운동 기록이 법적으로 민감정보에 해당하는지는 서비스의 수집 목적과 해석에 따라 다르므로 단정하지 않고 회사 기준을 따른다. 기술적으로는 수집 최소화, 접근 권한과 조회 감사 로그, 저장 시 암호화, LLM 제공자에게 넘기는 데이터의 최소화와 보관 정책 확인을 기본으로 둔다.
- 흔한 오답: 암호화만 하면 된다는 답. 누가 조회할 수 있는지와 외부로 무엇이 나가는지가 더 자주 문제가 된다.
- 공개 기능: 같은 조 제3항은 서비스 과정에서 공개되는 정보에 민감정보가 포함돼 사생활 침해 위험이 있으면 제공 전에 공개 가능성과 비공개 선택 방법을 알리도록 한다. 커뮤니티와 배틀에서 체중 같은 기록이 드러난다면 기본 비공개와 공개 범위 선택을 둔다.
- 외부 LLM 전송: 외부 제공자로 기록을 보내면 처리위탁이나 국외 이전 요건 검토 대상이 될 수 있어 법무 확인을 먼저 요청한다.
- 꼬리: 사용자가 탈퇴하면 → 보관 의무가 있는 항목만 분리 보관하고 나머지는 삭제하며, 외부 제공자의 보관 정책도 확인한다.
- 되물을 것: 건강 기록을 LLM에 보낼 때 지금 어떤 비식별화나 동의 절차를 두고 있는지.
- 조건: 법 해석은 면접에서 단정하지 않는다. 조문은 [국가법령정보센터, 개인정보 보호법](https://www.law.go.kr/법령/개인정보보호법)으로 확인한다(2026-09-29 제23조 제1항과 제3항 대조).

### S6. 배틀과 랭킹 같은 게이미피케이션을 어떻게 구현하나 (설계형)

- 답변 골격: 실시간 순위는 Redis Sorted Set으로 점수를 갱신하고 조회하며, 최종 결과는 DB에 확정 기록한다. 이벤트가 재전달되면 증분 갱신은 점수를 이중 반영하므로, 원본 기록에서 점수를 다시 계산해 덮어쓰거나 처리한 이벤트 ID로 중복을 거른다. 동점은 먼저 달성한 시각 같은 규칙을 정해 둔다. 부정 기록을 막으려면 서버에서 비정상 값(짧은 시간의 급격한 체중 변화 등)을 검증한다.
- 정량 비교: Sorted Set은 점수 갱신과 순위 조회가 원소 수 N에 대해 로그 시간이라 참가자가 많아도 조회마다 전체를 정렬하는 DB 쿼리보다 가볍다.
- 트레이드오프: 캐시의 순위와 DB의 확정 결과가 어긋날 수 있어 배틀 종료 시점에 DB 기준으로 재계산한다.
- 꼬리: Redis가 날아가면 → DB 원본에서 다시 적재한다. 그래서 Redis를 정본으로 두지 않는다.
- 되물을 것: 배틀 참가 규모와 순위 갱신 주기.
- 출처: [Redis, Sorted sets](https://redis.io/docs/latest/develop/data-types/sorted-sets/)
- 내 경험 연결: 동시 갱신 정합성(R1)과 캐시 설계(J5).

## 면접 전 체크리스트

- [ ] 인아웃 앱을 설치해 기록, 알림, AI 기능, 배틀을 직접 써 보고 관찰한 사실 두 가지를 적는다
- [ ] FIT 문서 C1 답변을 30초 안에 말하고 트라이포드랩 경험으로 넘어가는 연습을 한다
- [ ] 이력서의 키노라이츠 재직중 표기와 요약 문단 현재 시제를 고쳤는지, 제출 판본이 재직중이었다면 바로잡는 문장을 연습했는지 확인한다
- [ ] 이력서 수치 네 개(99.3%, 90%, 43.6%와 26.3%, 40%)의 측정 조건을 한 문장씩 말해 본다
- [ ] J1~J3 LLM 설계 답을 경험 없음 인정, 설계 기준, 검증 방법 순서로 2분 안에 말한다
- [ ] S2 알림 설계를 그림 없이 말로 설명해 본다
- [ ] 제출한 과제의 요구사항, 선택한 설계, 트레이드오프, 다시 한다면 바꿀 점을 정리한다. 과제 원문과 코드는 저장하지 않는다
- [ ] 역질문 핵심 3개를 외운다(FIT 문서 4절)
- [ ] 화상 면접 환경(카메라, 마이크, 조용한 장소)을 점검한다
