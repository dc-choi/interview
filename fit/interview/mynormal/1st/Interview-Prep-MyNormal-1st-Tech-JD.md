# 마이노멀컴퍼니 1차, JD 기반 기술 질문

> 상위 문서: [[Interview-Prep-MyNormal-1st|마이노멀컴퍼니 1차 준비]]. 회사의 실제 구현, DB 제품, LLM 제공자는 공개되지 않았다. 모든 답은 일반 설계 원칙과 내 경험의 연결로 말하고, 회사 구조는 추정하지 않고 되묻는다.

### J1. 식단과 체중 기록을 LLM에 연결해 코칭 기능을 만든다면 (설계형)

- 의도: 주요 업무의 LLM API와 서비스 데이터 연결. 경험이 없어도 설계 기준이 서 있는가
- 먼저 인정: LLM 기능을 실서비스로 운영한 경험은 없다. 대신 개인 프로젝트에서 근거 그래프 기반 검색을 만들고 평가 세트로 검색 방식을 비교한 경험(R11)과 외부 API 연동, 비동기 처리 경험에서 옮겨 올 기준으로 답한다.
- 답변 골격:
  1. 입력: 필요한 기간과 필드만 요약해 넘긴다. 식별자와 불필요한 개인정보는 빼고, 원본 기록 대신 서버가 계산한 집계를 우선한다.
  2. 출력: 자유 텍스트를 그대로 믿지 않고 스키마(JSON)로 받아 서버에서 검증한다. 검증 실패는 제한 재시도 뒤 규칙 기반 기본 응답으로 폴백한다.
  3. 안전: 의료 진단처럼 들리는 표현을 막는 규칙과, 수치 계산은 LLM이 아니라 서버가 하도록 역할을 나눈다.
  4. 저장: 입력 요약, 모델과 프롬프트 버전, 출력, 검증 결과를 함께 남겨 나중에 품질을 재현한다.
- 판단 기준: 이 값이 틀리면 사용자가 해를 입는가. 그렇다면 서버가 계산하고 LLM은 설명만 맡는다.
- 대안과 트레이드오프: 규칙 기반 코칭은 예측 가능하고 싸지만 표현이 단조롭다. LLM은 맥락을 반영하지만 비용, 지연, 품질 편차가 있다. 입력을 많이 넣을수록 맥락은 좋아지지만 비용, 지연, 개인정보 노출이 함께 늘어난다.
- 꼬리: 환각을 어떻게 줄이나 → 사실 값은 서버가 넣고, LLM은 해석과 문장화만 맡긴다.

### J2. LLM 응답이 느리고 비쌀 때 무엇부터 보나 (설계형)

- 의도: 공고가 명시한 응답 품질, 처리 속도, 비용의 균형
- 답변 골격:
  - 먼저 계측한다: 요청별 입력과 출력 토큰, 지연, 실패율, 기능별 비용을 지표로 남긴다. 계측 없이 모델부터 바꾸지 않는다.
  - 속도: 즉시 필요 없는 분석은 큐로 보내 비동기 처리하고 완료 알림으로 돌려준다. 대화형은 스트리밍으로 첫 응답 시간을 줄인다. 타임아웃과 제한 재시도를 둔다.
  - 비용: 입력 요약으로 토큰을 줄이고, 난이도에 따라 작은 모델과 큰 모델을 나눠 쓴다. 제공자가 프롬프트 캐싱을 지원하면 앞부분이 같아야 재사용되므로 고정 지시문과 출력 스키마를 앞에, 사용자별 기록 요약을 뒤에 두고 적중 여부를 캐시 읽기 토큰 지표로 확인한다. 응답 결과 캐시는 개인 기록 기반이라 적중률이 낮고 건강 정보를 저장하게 되므로 사용자와 무관한 공통 콘텐츠에만 쓴다.
- 판단 기준: 사용자가 기다리는가, 결과가 매번 달라도 되는가, 실패 비용이 큰가.
- 꼬리: 외부 API 장애 → 서킷 브레이커와 폴백 응답으로 핵심 기록 기능과 격리한다.
- 조건: 캐싱, 배치, 스트리밍의 지원 범위와 가격 구조는 제공자와 모델마다 다르므로 공식 문서로 확인한 뒤 말한다.

### J3. LLM 기능의 품질은 어떻게 평가하나 (설계형)

- 의도: 감이 아니라 변경 전후를 비교하는 체계가 있는가
- 답변 골격: 대표 입력과 기대 기준을 모은 평가 세트를 만들고, 프롬프트나 모델을 바꿀 때마다 같은 세트로 회귀를 돌린다. 형식 준수처럼 자동으로 잴 수 있는 것은 자동화하고, 유용성과 안전성은 사람 검수 표본으로 본다. 출시 뒤에는 재생성 비율, 사용자 피드백, 이탈 같은 온라인 신호를 함께 본다.
- 흔한 오답: 몇 번 써 보니 괜찮았다는 판단. 변경 전후 비교가 되지 않는다.
- 판단 기준과 대안: 자동 채점은 싸고 빠르지만 유용성을 놓치고, 사람 검수는 정확하지만 표본이 작다. 자동은 매 변경마다, 사람 검수는 출시 전 표본으로 나눈다.
- 내 경험 연결: 개인 프로젝트에서 평가 질문을 먼저 고정하고 74개 질문으로 BM25, 임베딩, RRF를, 이를 포함한 94개 질문으로 리랭커를 비교해 모두 기각했다(R11). 평가 세트를 먼저 만들고 측정으로 채택 여부를 정한 경험으로 답한다.
- 꼬리: LLM으로 LLM을 채점해도 되나 → 기준이 명확한 항목에 한정하고 사람 판정과 일치율을 먼저 확인한다.

### J4. 사용자별 기록 테이블의 모델과 조회를 설계한다면 (설계형)

- 의도: 가장 많이 쌓이는 데이터의 인덱스와 페이지네이션 판단
- 답변 골격: 기록은 사용자별 최신순으로 조회되므로 `(user_id, recorded_at DESC, id DESC)` 복합 인덱스를 두고, 목록은 offset 대신 `(recorded_at, id)` 튜플을 커서로 쓰는 keyset 페이지네이션을 쓴다. 같은 시각의 기록이 있어도 고유 id가 순서를 확정해 경계에서 누락이나 중복이 없다. 기록 시각은 UTC로 저장하고, 기록 당시의 시간대나 로컬 날짜를 함께 저장해 일별 집계 키로 쓴다. 사용자가 시간대를 바꿔도 과거 일별 합계가 흔들리지 않는다.
- 정량 비교: 깊은 offset은 앞의 행을 모두 읽고 버리므로 페이지가 뒤로 갈수록 비용이 선형으로 늘지만, keyset은 인덱스에서 커서 위치부터 범위 탐색해 페이지 깊이와 무관하게 비슷하다.
- 판단 기준과 트레이드오프: keyset은 임의 페이지 이동이 어렵고, 사용자가 기록 시각을 고치면 이미 본 페이지 결과가 바뀔 수 있다. 무한 스크롤에는 keyset, 페이지 번호가 필요한 관리 화면에는 offset을 쓴다. 일별 집계 테이블은 읽기를 빠르게 하지만 원본과 어긋날 수 있어 재계산 경로가 필요하다.
- 꼬리: 테이블이 매우 커지면 → 시간 기준 파티셔닝이나 오래된 기록의 보관 분리를 실측 뒤 검토한다. 내 경험 연결은 R3의 `(business_key, created_at DESC, id DESC)` 인덱스와 같은 패턴이다.
- 출처: [Use The Index, Luke, Paging Through Results](https://use-the-index-luke.com/sql/partial-results/fetch-next-page)

### J5. 캐시는 어디에 쓰고 정합성은 어떻게 지키나 (카드 8 fork)

- 핵심 답변: 캐시는 원본의 대체가 아니라 읽기 부하를 줄이는 보조 경로다. 미스 시 원본을 읽어 적재하고 쓰기 뒤 무효화하는 Cache-Aside를 기본으로 두고, TTL은 안전망으로만 쓴다. 인기 키가 동시에 만료되면 TTL 지터, 요청 병합, 백그라운드 갱신 중 데이터 성격에 맞는 방법을 고른다.
- 흔한 오답: TTL만 짧게 하면 일관성이 해결된다는 답.
- 꼬리: 캐시 장애 → 원본으로 돌아가되 연결 풀 제한으로 원본이 몰리지 않게 막는다. 리더보드 → Redis Sorted Set(서비스 문서 S6).
- 판단 기준: 조회가 많고 약간 오래된 값을 허용할 수 있는 데이터만 캐시한다. 개인 기록처럼 쓰기 직후 바로 다시 읽는 데이터는 캐시 이득이 작고 불일치 비용이 크다.
- 출처: [AWS, Caching patterns](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/caching-patterns.html)

### J6. Node.js에서 무거운 작업이 API를 느리게 만들 때 (사실형)

- 의도: 런타임 모델을 이해하고 원인을 구분하는가
- 핵심 답변: Node.js는 JavaScript를 이벤트 루프 한 스레드에서 실행한다. I/O는 비동기로 넘기지만 CPU를 오래 쓰는 동기 작업(큰 JSON 처리, 암호화 계산, 대량 정렬)은 루프를 막아 모든 요청을 늦춘다. 무거운 작업은 큐와 별도 워커 프로세스로 빼거나 `worker_threads`로 옮기고, 이벤트 루프 지연을 지표로 본다.
- 흔한 오답: async만 붙이면 블로킹이 풀린다는 답. 동기 계산은 async 함수 안에서도 루프를 막는다.
- 꼬리: `Promise.all`로 외부 호출을 한꺼번에 보내면 → 동시성 제한 없이 보내면 상대 서비스와 연결 풀을 압박하므로 제한을 둔다.
- 출처: [Node.js, Don't Block the Event Loop](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)

### J7. 변경 영향을 테스트와 배포 자동화로 어떻게 확인하나 (설계형)

- 의도: 변경을 안전하게 내보내는 절차가 있는가
- 판단 기준: 실패하면 데이터가 틀어지는 경로(기록 저장, 결제, 알림 발송)부터 통합 테스트로 덮는다.
- 답변 골격: 도메인 규칙은 단위 테스트로, DB와 큐가 얽힌 경로는 실제 DB를 띄운 통합 테스트로, 외부 API는 계약과 실패 응답을 흉내 낸 테스트로 확인한다. CI에서 테스트와 마이그레이션 검사를 통과해야 배포되고, 배포는 롤링으로 하되 헬스 체크 실패 시 자동 중단과 이전 버전 롤백 경로를 둔다.
- 트레이드오프: 통합 테스트는 느리지만 ORM이 만드는 SQL과 잠금 동작을 실제로 확인한다. 전부 통합 테스트로 만들지 않고 위험한 경로에 집중한다.
- 꼬리: 스키마 변경 → 호환 컬럼 추가, 백필, 읽기 전환, 구 컬럼 제거 순서로 나눠 배포한다.

### J8. 로그와 지표로 원인을 찾고 재발을 막은 경험 (경험형, 카드 4와 5 연결)

- 의도: 공고의 로그와 지표로 원인을 찾고 재발을 막는 업무를 실제로 해 봤는가
- 답변 골격: 영향 범위 공유, 복구 우선, 지표로 범위를 좁히고 로그로 원인을 확인, 재발 방지 조치를 남긴다. 사례는 R4를 쓴다. 관계 포함 조회의 지연을 로그에서 과다 SQL로 확인하고, 공식 문서와 실행 계획으로 원인을 검증한 뒤 성능이 중요한 경로만 바꿨다. 관측 자체의 실수로는 R6(요청 식별자를 메트릭 라벨에 넣었다가 시계열 급증을 겪고 로그로 옮긴 경험)를 쓴다. 수집 배치 오류 사례는 실패 경험(C6)에만 쓴다.
- 판단 기준: 같은 문제가 두 번 나오면 사람의 주의가 아니라 검사, 알림, 게이트로 막는다.
- 꼬리: 알림이 너무 많으면 → 사용자 영향과 연결되지 않은 알림을 줄이고 조치 가능한 것만 남긴다.
