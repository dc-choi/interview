# 마이노멀컴퍼니 1차, 이력서 기반 기술 질문

> 상위 문서: [[Interview-Prep-MyNormal-1st|마이노멀컴퍼니 1차 준비]]. 답변은 기술 답변 마스터 카드 1~8을 fork했고, 수치는 공개 이력서에 적힌 값만 쓴다. 끝줄은 공고와의 연결이다. 모든 답은 결론, 선택 이유, 검증, 한계 순서로 말한다.

### R1. 수천 대 IoT 동시 요청의 Race Condition은 어떻게 해결했나 (카드 1)

- 의도: 정합성 문제를 재현하고 잠금 방식을 근거 있게 골랐는가
- 답변: 같은 재고 상태를 동시에 바꾸는 경로에 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한 재시도를 조합했습니다. 충돌이 잦은 갱신이라 늦게 충돌을 발견하는 낙관적 잠금보다 먼저 경합을 조정하는 비관적 잠금이 단순하다고 판단했습니다. 외부 호출과 입력 검증은 트랜잭션 밖으로 빼고, 잠금 읽기 뒤 불변식을 다시 검증했습니다. 동시 요청을 재현해 최종 수량과 재시도 뒤 상태를 확인했습니다.
- 흔한 오답: 분산 락을 먼저 꺼내는 답. 보호 대상이 한 DB 트랜잭션 안이면 DB 잠금이 더 단순하다.
- 꼬리: 왜 기다리지 않고 즉시 실패시켰나 → 충돌을 대기로 조용히 덮지 않고 제한된 실패 경로로 드러내려 했다(카드 1). 판단 기준은 잠금 대기가 커넥션을 붙잡아 다른 요청까지 막는 비용과, 실패 뒤 재시도 비용의 비교다. 즉시 반영이 꼭 필요한 업무라면 짧은 잠금 대기 제한을 택한다. [사용자 확정 필요: 당시 NOWAIT를 고른 구체 이유가 따로 있으면 그것으로 바꾼다] `NOWAIT`의 범위 → 해당 잠금 읽기의 대기만 없앤다. 데드락 → 업무 키 순서 통일은 확률을 낮출 뿐이고, 데드락 오류는 새 트랜잭션으로 제한 재시도한다.
- 꼬리: 여러 요청이 함께 재시도하면 몰리지 않나 → 단일 DB여도 같은 행을 두고 동시 재시도가 몰릴 수 있다. 당시는 짧은 고정 간격이었고, 지금은 지수 백오프, 지터, 재시도 상한을 둔다. 단일 DB라 괜찮다는 답은 하지 않는다.
- 조건: MySQL 8.0 이상 InnoDB의 잠금 읽기 기준이다. `NOWAIT`와 `SKIP LOCKED`는 8.0부터 지원된다.
- 연결: 인아웃의 기록과 배틀 점수처럼 같은 값을 동시에 바꾸는 경로에도 같은 판단 기준을 쓴다.

### R2. Kafka 대신 EventBridge와 SQS를 고른 이유와 한계 (카드 2)

- 의도: 기술 선택의 기준과 전달 보장에 대한 이해
- 답변: 조직의 운영 여력과 필요한 전달 보장을 비교해 관리형 큐를 골랐습니다. 핵심 상태 변경을 먼저 확정한 뒤 후속 발주 작업을 이벤트로 넘겼고, 워커는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했습니다. 영구 오류는 격리하고 일시 오류만 제한 재시도한 뒤 DLQ와 수동 확인 경로로 보냈습니다.
- 한계를 먼저 말할 것: DB 커밋 뒤 발행 전에 프로세스가 죽으면 이벤트가 빠질 수 있었습니다. Transactional Outbox는 적용하지 않았고 개선안으로 남겼습니다.
- 꼬리: 정확히 한 번 처리가 되나 → 주장하지 않는다. 적어도 한 번 전달을 전제로 소비자를 멱등하게 만든다. Kafka가 맞는 조건 → 리플레이, 강한 순서, 매우 높은 처리량이 핵심일 때.
- 꼬리: Outbox를 두면 결국 다시 큐로 보내는데 왜 필요한가 → 책임이 다르다. Outbox는 상태 변경과 발행 의도를 같은 트랜잭션에 남겨 유실을 막고, 릴레이는 그 기록을 발행하며, 큐는 소비자에게 전달하고 재시도를 맡는다. 릴레이도 중복 발행할 수 있어 소비자 멱등성은 그대로 필요하다.
- 연결: 알림 발송과 AI 분석 요청처럼 느린 의존성을 핵심 기록 저장에서 떼어 내는 데 그대로 쓴다.

### R3. 슬로우 쿼리 99.3% 개선은 무엇을 어떻게 쟀나 (카드 3)

- 의도: 수치의 측정 조건을 설명할 수 있는가
- 답변: 업무 키별 최신 레코드를 찾는 조회에서 후보 행 탐색과 정렬 비용이 큰 것을 `EXPLAIN ANALYZE`로 확인했습니다. 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 만들고, 인덱스가 정렬과 상위 레코드 접근에 실제로 쓰이는지 다시 확인했습니다.
- 측정 경계: 99.3%는 해당 쿼리의 변경 전후 비교다. 전체 API나 배치 시간과 같은 지표로 섞어 말하지 않는다. 실행 환경, 캐시 상태, 표본은 기록하지 못했다고 먼저 인정하고, 지금이라면 같은 환경과 캐시 조건에서 전후 P99를 반복 측정하겠다고 답한다.
- 꼬리: 인덱스를 늘리면 → 쓰기와 저장 비용이 늘어 인접 쓰기 경로를 함께 본다. 컬럼 순서 → 카디널리티 하나가 아니라 동등, 범위, 정렬 조건으로 정한다.
- 연결: 사용자별 기간 기록 조회가 이 패턴과 같다(JD 문서 J4).

### R4. Prisma N개 쿼리를 단일 쿼리로 바꿔 응답 90% 향상 (카드 4)

- 의도: ORM이 만드는 SQL을 직접 확인하는가
- 답변: 관계 포함 조회에서 예상보다 많은 SQL이 나가는 것을 로그로 확인했습니다. 당시 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했습니다. `relationJoins` 기능을 켜고 `relationLoadStrategy: 'join'`을 적용한 뒤, MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했습니다. 성능이 중요한 경로만 바꾸고 나머지는 타입 안정성을 유지했습니다.
- 흔한 오답: 옵션 이름만 보고 SQL JOIN이 나간다고 단정하는 답.
- 꼬리: 단일 쿼리가 항상 좋은가 → 상관 서브쿼리와 JSON 집계 비용이 DB로 옮겨 가고, 데이터 특성에 따라 여러 쿼리 방식이 더 빠를 수 있어 같은 환경에서 비교한다. 동작은 Prisma 버전과 설정에 따라 다르다.
- 꼬리: 느려질 때까지 왜 몰랐나 → 변명 없이 관측 공백을 인정한다. 지금이라면 경로별 쿼리 수와 지연 분포를 지표로 두고, 배포 전후를 비교하는 확인을 넣겠다고 답한다. 실제로 이후 무엇을 넣었는지는 [사용자 확정 필요]이며 확인 전에는 지금이라면으로만 말한다.
- 연결: 백오피스 목록처럼 관계가 많은 조회에서 먼저 생성 SQL을 확인한다.

### R5. 단일 NGINX에서 CloudFront, ELB, ECS Fargate로 전환한 이유 (카드 6)

- 의도: 인프라 전환의 판단 근거와 무중단 절차
- 답변: 트래픽이 늘면서 단일 서버가 장애 지점이자 확장 한계가 됐습니다. 앞단에 CloudFront와 ELB를 두고 애플리케이션을 ECS Fargate 태스크로 옮겨 수평 확장과 롤링 배포가 가능하게 했습니다. 기기 통신처럼 프로토콜과 고정 엔드포인트 요구가 있는 경로는 웹 요청과 같은 방식으로 단정하지 않고 접근 요구부터 확인했습니다. Read Replica로 읽기 부하를 나눴습니다.
- 측정 경계: 이력서의 40% 개선은 기준선, 기간, 측정 방법 기록이 없어 면접에서 수치로 강조하지 않는다. 물으면 기록이 남지 않았다고 인정하고 읽기 분산과 복제 지연 처리 원칙으로 답한다.
- 꼬리: 복제 지연 → 쓰기와 쓰기 직후 읽기는 primary로 보내고 지연을 허용하는 조회만 replica로 보낸다. Kubernetes를 안 쓴 이유 → 운영 인력과 배포 복잡도를 기준으로 관리형 태스크가 충분했다.
- 꼬리: 그 규모에 과잉 설계 아닌가 → 판단 기준은 단일 서버 장애의 영향과 전환 뒤 운영 부담의 비교다. 규모가 작다면 단일 인스턴스와 백업 복원 훈련이 먼저라는 기준도 함께 말한다. 당시 비교 내용은 [사용자 확정 필요]이며 부풀리지 않는다.
- 연결: 공고의 기존 동작을 유지하며 기술을 전환한 경험 우대와 맞는다.

### R6. Grafana, Prometheus, Loki 관측 체계를 어떻게 설계했나 (카드 5)

- 의도: 지표와 로그의 역할 구분, 카디널리티 이해
- 답변: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었습니다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼습니다. 지연은 histogram으로 봤습니다. 메트릭으로 추세와 사용자 영향을 보고, 로그로 개별 원인을 찾습니다. Grafana Alerting으로 실시간 알림을 받게 했습니다.
- 흔한 오답: 사용자 ID나 요청 ID를 메트릭 라벨에 넣는 설계. 제가 실제로 겪은 실수이고, 그래서 라벨 설계 기준을 먼저 말한다.
- 꼬리: 경보 기준 → 과거 숫자를 복사하지 않고 사용자 영향 SLI와 정상 구간을 본 뒤 합의한다. 장애 시 → 영향 공유, 복구 우선, 포스트모템.
- 연결: 기록 누락이나 알림 지연을 사용자보다 먼저 감지하는 신호 설계로 이어진다.

### R7. Docker 이미지 43.6% 감소, 배포 26.3% 단축 (카드 6)

- 의도: 빌드와 런타임 분리, 배포 재현성
- 답변: 멀티스테이지 빌드로 빌드 도구와 개발 의존성을 실행 이미지에서 빼서 909MB를 513MB로 줄였고, 배포 시간은 3분 10초에서 2분 20초가 됐습니다. 수치보다 중요하게 본 것은 같은 산출물이 환경만 바꿔 배포되고, 롤백과 종료 절차가 재현되는 것이었습니다.
- 꼬리: 종료 신호 처리 → SIGTERM을 받으면 새 요청을 막고 진행 중 요청과 워커 작업의 완료 또는 재전달 경계를 지킨다. 비밀 값 → 이미지에 넣지 않고 실행 시 주입한다.
- 연결: 공고의 배포와 반복 작업 자동화 업무.

### R8. 팀 AI 협업 규약과 검증 루프는 무엇이었나 (FIT 마스터 10번)

- 의도: 자격요건의 AI 제안 검증을 기술적으로 설명할 수 있는가
- 답변: AI가 건드려도 되는 영역과 안 되는 영역을 경로별 규칙 문서로 명문화하고, 작업이 끝나는 시점에 변경 파일 검사와 테스트가 자동으로 돌게 했습니다. 반복 구현과 조사는 맡기지만 요구사항 해석, 설계 선택, 결과 채택은 사람이 결정합니다.
- 꼬리: AI가 틀리기 쉬운 곳 → 버전 차이, 잠금과 트랜잭션 경계, 존재하지 않는 API. 공식 문서와 테스트로 확인한다. 기각한 사례 → [사용자 확정 필요: 공개 가능한 사례 하나]
- 연결: 공고가 AI 제안 코드를 이해하고 검증하는 능력을 자격요건으로 명시했다.

### R9. 영양정보를 MongoDB에서 MySQL로 옮긴 이유와 방법 (이력서 시솔지주)

- 의도: 식단 앱 회사가 가장 먼저 물을 수 있는 이력. 스키마 결정과 이관 검증을 설명할 수 있는가
- 답변 골격: 영양정보를 정형화할 필요가 있어 문서형 저장소에서 관계형으로 옮겼다. 식품, 영양 성분, 단위 같은 엔터티를 나누고 관계와 제약으로 품질을 지키는 구조를 택했다. [사용자 확정 필요: 스키마를 어떻게 나눴는지, 이관 뒤 건수와 값 검증 방식, 전환 방식(일괄 전환 또는 병행)]
- 판단 기준: 조회가 조건과 집계 중심이고 값의 형식이 일정해야 하면 관계형이 낫다. 항목 구조가 자주 바뀌고 문서 단위 조회가 대부분이면 문서형이 낫다.
- 꼬리: 이관 중 원본이 계속 바뀌면 → 일괄 복사 뒤 변경분 동기화, 건수와 샘플 대조, 읽기 경로 전환, 원본 쓰기 중단 순서로 나눈다.
- 연결: 인아웃의 식단 기록과 마이노멀 식품 정보를 다루는 데이터 모델 질문에 이 경험으로 답한다. 농식품정보서비스 대시보드(이썸테크)도 같은 결로 보탠다.

### R10. 키노라이츠에서는 무엇을 했나 (이력서 기재 후 예상)

- 의도: 짧은 경력도 실제로 무엇을 했는지 본다. C1 답변 직후 이어질 가능성이 높다
- 답변 골격: 검색 API의 서버 이관, 알림 워커의 비동기 처리 수정, 검색 색인 전환 검증 같은 업무를 맡았다고 역할과 문제 유형만 두세 문장으로 말한다. 내부 수치, 운영 정보, 동료 평가는 말하지 않는다. [사용자 확정 필요: 이력서에 넣는 문장과 같게 맞춘다]
- 배운 점 연결: 로컬 검증과 실제 실행 환경 검증은 다르고, 검증 결과를 환경별로 기록하고 먼저 공유해야 한다는 점.

### R11. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- 의도: 공고의 LLM 기능 품질 평가와 AI 도구 활용을 실제로 해 봤는지 본다. LLM 서비스 운영 경험이 없는 갭을 가장 직접 메우는 근거다
- 답변: 개인 프로젝트로, 개발 지식 Markdown을 근거 관계 그래프로 색인하고 그 검색을 MCP 도구와 CLI로 제공하는 시스템을 만들었습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했습니다. 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정하고, 응답 크기 예산 안에 그 근거가 모두 나와야 통과로 쳤습니다. 무관한 질문에는 빈 결과가 나와야 통과하는 음성 질문도 넣었습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, BM25와 E5 임베딩 결과를 RRF로 합친 방식을 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 늘지 않았고 기존 통과 사례 4개를 잃었습니다. 이 74개를 포함한 94개 질문으로 bge 리랭커도 붙여 봤지만 통과는 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸습니다. 그래서 BM25, 임베딩, 리랭커 모두 채택하지 않았고, 문제가 후보 검색보다 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- 판단 기준: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다.
- 한계를 먼저 말할 것: 평가 질문은 사람이 정답을 검수한 표본이 아니라 원문을 보고 만든 합성 질문이 대부분이다. 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 모든 방식에서 여전히 약했다.
- 이력서 정정: 제출한 이력서에는 골든 케이스 약 145건으로 BM25, 임베딩, 리랭커를 비교했다고 적혀 있다. 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- 꼬리: nDCG 같은 순위 지표는 왜 안 썼나 → 목적이 응답 예산 안에 필요한 근거가 모두 들어가는지였기 때문이다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 쟀다(사실상 그룹 단위 Recall@50). 순위 가중 지표를 쓰지 않은 것은 한계로 인정한다.
- 꼬리: 과적합은 어떻게 막았나 → 정답 절을 검색 로직에 넣지 않았고, 새 평가 질문은 구현을 보지 않은 상태에서 만들어 첫 관측 전에 해시로 고정했다. 다만 채택 판단은 주로 재사용 세트에서 나왔다는 한계가 있다.
- 꼬리: 재현성 → 원문 Git revision, 모델 revision, 코드와 벡터 checksum을 고정했다.
- 연결: J3 품질 평가의 평가 세트와 회귀 비교, 새 방식을 측정으로 기각한 판단을 이 경험으로 답한다.
