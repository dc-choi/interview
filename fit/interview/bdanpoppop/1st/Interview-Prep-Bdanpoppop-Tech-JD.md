# 비단팝팝 1차 — JD 기반 기술 질문

> 상위 TOC: [[Interview-Prep-Bdanpoppop|비단팝팝 1차 면접 준비]]

당시 JD 스냅숏에서 약하거나 중간 매칭으로 읽은 항목은 블록체인, 캐시, 메시징, 컨테이너 오케스트레이션과 트래픽 처리였다. 실제 제품의 기술 선택으로 단정하지 않고, 전이 가능한 설계 원칙을 우선 정리했다.

---

## 1. RESTful API 설계 — 자격요건 (강 매칭)

- REST 원칙: 자원 중심 URI, HTTP 메서드 의미 일관성, 무상태성, HATEOAS는 실무에서는 거의 안 씀
- 멱등성: GET, PUT, DELETE 멱등, POST 비멱등. 결제나 교환 같은 비멱등 작업은 **Idempotency-Key 헤더**로 멱등 보장
- 버전 관리: URI(`/v1/...`) vs 헤더(`Accept: application/vnd.api+json;version=1`). URI 방식이 단순하고 가시성 높음
- 에러 응답: HTTP 상태 코드 + RFC 9457 (Problem Details for HTTP APIs) 권장
- 꼬리: "REST vs GraphQL vs gRPC" — 외부 공개 API는 REST(접근성), 내부 마이크로서비스는 gRPC(성능, 타입), 프론트 BFF는 GraphQL(over-fetch 회피)

---

## 2. DB 설계(ERD) 및 쿼리 최적화 — 우대 (강 매칭)

- 정규화와 역정규화의 트레이드오프: 정규화는 무결성과 저장공간, 역정규화는 조회 성능에 유리하다. 읽기 부하가 큰 검색 도메인에서는 검색 전용 역정규화 모델을 검토한다.
- 외래키 제약: 무결성 보장하지만 lock 범위 확대, 삭제 cascade 성능 이슈. 대규모 트래픽에서는 애플리케이션 레벨 검증으로 빼기도 함
- 인덱스 설계 원칙: WHERE/JOIN/ORDER BY/GROUP BY 컬럼 후보. 카디널리티, 선택도 분석 필수
- 슬로우쿼리 디버깅: `EXPLAIN ANALYZE` (실제 실행 비용, rows 확인) → filesort/temporary table 발견 시 인덱스 추가
- 꼬리: "MySQL InnoDB vs PostgreSQL 차이" → InnoDB는 클러스터드 인덱스(PK 기준), PostgreSQL은 힙 + 별도 인덱스. PG는 JSONB, CTE, Window 함수가 더 강력. 트랜잭션 격리 기본값도 다름(InnoDB RR, PG RC)

## 3. Redis 캐시 — 우대 (중 매칭)

**디지털 교환 서비스 가정에서 캐시가 효과적인 데이터**
- 자주 조회되고 상대적으로 덜 바뀌는 목록과 시세성 데이터
- 사용자 세션, 인증 토큰
- 인기 항목과 정렬 결과
- API rate limit 카운터

**캐시 패턴**
- **Cache-Aside (Look-aside)**: 앱이 캐시 먼저 조회 → miss 시 DB → 캐시에 저장. 가장 흔하고 단순
- **Write-Through**: 쓰기 경로에서 DB와 캐시를 함께 갱신해 stale 가능성을 낮춤. 별도 저장소의 원자성을 자동 보장하지 않으므로 부분 실패, 재시도와 순서 역전 복구가 필요하고 쓰기 비용이 늘어남
- **Write-Behind (Write-Back)**: 캐시 우선 쓰고 DB 비동기. 성능 ↑, 데이터 유실 위험
- **TTL + LRU eviction**: 메모리 한정 → 사용 패턴 기반 만료

**문제 패턴**
- **Cache Stampede**: TTL 만료 직후 다수 요청이 동시에 DB로 → DB 폭주. 해결: 락(Mutex)으로 1개만 DB 조회, 나머지는 stale 반환. 또는 PER (Probabilistic Early Recomputation)
- **Cache Penetration**: 존재하지 않는 키 반복 조회 → DB 매번 hit. 해결: Bloom Filter + null 캐싱
- **Cache Avalanche**: 다수 키가 동시에 만료 → 일제히 DB로. 해결: TTL에 jitter

**꼬리 질문 대비**
- "캐시 무효화 전략?" → 데이터 변경 시 invalidate 또는 update. 분산 환경에서는 Pub/Sub으로 다른 노드 캐시 무효화 신호 전파
- Redis와 Memcached 비교: Redis는 다양한 자료구조와 영속성 선택지를 제공하고, Memcached는 단순 키-값 캐시에 집중한다. 정렬, 제한 카운터나 스트림이 필요한지로 선택한다.

## 4. 메시지 큐 (Kafka, RabbitMQ) — 우대 (중 매칭)

**큐와 스트림 개념을 Kafka/RabbitMQ에 어떻게 매핑하나**

| 기준 | SQS | Kafka | RabbitMQ |
|------|-----|-------|----------|
| 모델 | 큐(point-to-point) | 로그(파티션 기반) | Exchange + Queue (라우팅) |
| 순서 보장 | 그룹 단위 순서 보장을 지원하는 구성인지 확인 | 파티션 내 보장 | 기본 큐의 최초 적재와 전달 순서. 우선순위, 재전달과 다중 소비자가 있으면 처리 완료 순서는 달라질 수 있음 |
| 메시지 보관 | 제공자별 보존 정책 확인 | 기간 설정 가능 | 소비 시 삭제가 일반적 |
| 리플레이 | 오프셋 기반 임의 리플레이는 기본 큐 모델에 없고, DLQ redrive는 별도 지원 | 오프셋 리셋으로 가능 | 기본 Queue는 오프셋 기반 임의 리플레이가 없고, RabbitMQ Streams는 별도 모델 |
| 처리량 | 서비스 한도와 소비자 병렬성을 확인 | 파티션 수와 클러스터 구성에 좌우 | 라우팅과 큐 구성에 좌우 |
| 도입 비용 | 관리형 운영 부담이 낮음 | 클러스터 운영 비용이 큼 | 단순 구성은 쉬우나 클러스터링이 복잡할 수 있음 |

RabbitMQ에서 엄격한 처리 순서가 필요하면 단일 활성 소비자와 소비자 측 직렬 처리 등 추가 제약을 함께 둔다.

**스트림 기반 브로커가 필요해질 수 있는 시점**
- 이벤트를 분석과 리포팅에 재사용해야 할 때
- 순서와 재처리가 중요한 외부 원장 또는 거래 이벤트를 다룰 때
- 현재 큐의 보존, 리플레이와 처리량 한계가 실제 관측으로 드러날 때

**꼬리 질문 대비**
- "exactly-once delivery?" → SQS, Kafka 모두 기본은 at-least-once. Kafka EOS는 트랜잭션 프로듀서와 read_committed 컨슈머가 오프셋을 출력과 같은 트랜잭션에 커밋하는 Kafka 내부 read-process-write 경계에서만 성립하고, 단일 클러스터 한정이며 처리량 비용도 있음. 외부 DB나 API 호출 같은 부수효과는 그 경계 밖이라 컨슈머 멱등(처리 키 중복 제거)으로 effectively-once를 만든다. **현실적으로는 at-least-once + 멱등 소비자**가 표준
- RabbitMQ는 라우팅 규칙이 복잡하고 중간 처리량의 작업 큐가 필요할 때 비교한다. 실제 선택은 순서, 리플레이, 운영 부담과 기존 환경을 함께 본다.

## 5. 대용량 트래픽 처리와 튜닝 — 우대 (중 매칭)

**트래픽이 증가했을 때 백엔드 단계별 대응**
1. **수직 확장**: 인스턴스 사양 ↑ — 단순하지만 한계와 SPOF
2. **수평 확장**: 요청 로컬 상태를 외부 저장소로 분리하면 복제된 실행 단위와 로드밸런서로 단순하게 확장할 수 있다. 상태를 가진 워크로드는 파티셔닝, 복제와 합의 비용을 별도로 설계한다.
3. **DB 부하 분산**: Read Replica로 읽기 분리, 쓰기는 마스터 단일
4. **캐시 도입**: Redis로 hot data 메모리 hit
5. **CDN**: 정적 자산과 이미지는 엣지 캐싱을 검토한다.
6. **이벤트 기반 비동기화**: 결제나 외부 원장 기록처럼 오래 걸리는 작업은 작업 큐로 분리한다.
7. **DB 샤딩**: 트래픽이 한 DB의 한계를 넘으면. 샤드 키 설계와 재샤딩 비용이 큼

**디지털 교환 서비스에서 이벤트성 트래픽이 급증한다면**
- 사전 안내, 요청 제한과 대기 상태를 제공한다.
- CPU, 요청 수, 지연, 오류율과 큐 적체를 기준으로 실행 단위를 조정한다.
- 인기 항목은 캐시하고, 정렬과 대기열은 데이터 구조와 일관성 요구에 맞춰 설계한다.
- 외부 결제 또는 연동의 응답 지연은 동기 경로에서 격리한다.

**꼬리 질문 대비**
- "대용량 경험 한계는?" → 규모를 과장하지 않고, **트래픽 증가 시 단계별 옵션과 트레이드오프를 메트릭으로 검증해 결정한다**고 답한다.
- "단일 인스턴스 → 컨테이너 오케스트레이터 전환은?" → 무중단 배포, 자동 확장, 상태 없는 서비스 설계를 함께 검토하고, 현재 병목과 운영 요구를 근거로 전환 범위를 정한다.

## 6. Docker / Kubernetes (K8s) — 우대 (중 매칭)

**컨테이너 오케스트레이션 개념을 K8s로 매핑**

| ECS | K8s 대응 | 비고 |
|-----|---------|------|
| Task | Pod | 컨테이너 단위 실행 |
| Task Definition | 워크로드의 Pod template과 컨테이너 spec | 실행할 이미지, 자원과 환경 정의. 독립된 일대일 대응 객체는 아님 |
| Service | Deployment / StatefulSet | 원하는 실행 수와 롤아웃 관리. K8s Service는 별도의 네트워킹과 디스커버리 객체 |
| Cluster | Cluster | 노드 그룹 |
| Auto-scaling | HPA / VPA / Cluster Autoscaler | 수평, 수직, 노드 |
| ALB Target Group | Ingress + Service | 외부 노출 |

**K8s를 직접 안 다뤄봤을 때 설명 포인트**
- 컨테이너 오케스트레이션의 서비스 디스커버리, 롤링 업데이트, 헬스체크 개념을 먼저 설명한다.
- K8s 진입 비용은 manifest 작성과 운영 도구 학습에 있다. 원리는 컨테이너 배포와 운영의 기본 개념에 닿아 있다.
- "K8s는 학습 진행 중"이라고 솔직하게 말하고, 무중단 배포, 롤백, 로깅과 메트릭의 판단 기준을 연결한다.

**꼬리 질문 대비**
- "Helm 써봤나?" → 직접 운영 경험은 과장하지 않는다. 템플릿과 values 분리 개념을 알고 있으며, IaC에서도 선언형 배포 정의와 환경별 설정 분리라는 같은 목적을 설명한다.
- "Pod 간 통신은?" → ClusterIP Service로 내부 DNS, 외부 노출은 Ingress + LoadBalancer

## 7. 블록체인(Web3) 연동 — 학습 포인트

> 도메인 갭 보완용 — 면접 전 반드시 정리

**블록체인 연동이 포함된 서비스의 가정형 문제**
- 외부 원장에 거래 또는 소유권 상태를 기록하고 감사 추적을 제공할 수 있다.
- 토큰화된 자산을 다룬다면 실제 제도와 인가 범위를 최신 공식 출처로 확인해야 한다.
- 사용자 지갑이나 서명 검증이 필요하다면, 체인 규격과 보안 책임 경계를 먼저 확인한다.

**백엔드 엔지니어가 다루게 될 패턴**
- **RPC 호출**: 확인된 체인과 팀 표준에 맞는 클라이언트 라이브러리로 관리형 또는 자체 노드를 호출
- **이벤트 리스닝**: EVM이면 `eth_subscribe`와 폴링을 비교하고, 다른 체인이면 해당 체인의 구독 또는 Webhook 규격을 확인
- **트랜잭션 라이프사이클**: 제출, 대기, 블록 포함과 최종 확정 단계를 체인의 확정 모델에 맞춰 추적하고 재시도와 중복 발행을 통제
- **수수료 관리**: 사용하는 체인의 수수료 모델을 따르고, EVM에서 지원하는 경우 EIP-1559의 base fee와 priority fee를 고려
- **nonce 관리**: 계정 nonce를 쓰는 체인에서 같은 주소의 동시 발행 충돌을 직렬화하거나 전용 관리 계층으로 통제
- **멱등성**: 비즈니스 요청 키와 체인 트랜잭션 식별자를 함께 사용해 중복 처리를 방지
- **리오그(reorg) 대응**: 체인별 finality, confirmation 정책과 거래 위험에 따라 확정 전 데이터를 잠정 상태로 처리

**전이 가능한 백엔드 패턴**
- 외부 API 호출(체인 RPC)은 타임아웃, 재시도와 응답 검증이 필요한 외부 연동 패턴이다.
- 비동기 워커, 재시도와 DLQ는 부분 실패를 격리하고 복구하는 일반적인 처리 패턴이다.
- 멱등성 키와 상태 머신은 중복 요청과 상태 전이를 통제하는 기본 설계다.
- 도메인 지식을 보완하면 이 설계 원칙을 블록체인 연동에도 적용할 수 있다고 설명한다.

**꼬리 질문 대비**
- 어떤 체인을 쓰는가: 공개 자료의 용어만으로 호환성이나 연동 구조를 추론하지 않는다. 체인, 노드와 원장 연동 방식은 확인 질문으로 둔다.
- "트랜잭션이 확정되지 않으면?" → 사용하는 체인의 확정 모델, 수수료, nonce와 노드 장애 조건을 먼저 확인한 뒤 모니터링과 재시도 정책을 설명한다.
- "지갑 서명 검증?" → EVM과 EIP-712 사용이 확인된 경우에만 typed data와 주소 복원 검증을 설명하고, 다른 체인이면 해당 서명 규격을 따른다.

**학습 우선순위 (면접 전 1주)**
1. Ethers.js 기본 사용법 (Provider, Wallet, Contract)
2. EVM 트랜잭션 라이프사이클, gas, nonce
3. EIP-1559, EIP-712 (서명 표준)
4. STO와 ERC-1400 (Security Token Standard)
