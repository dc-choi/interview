# 비단팝팝 1차 — 이력서 기반 기술 질문

> 이 문서는 1차에서 설명할 본인 경험의 공개 가능한 요약이다. 이전 회사의 고객명, 운영 수치와 내부 구조는 일반화하고, 문제, 판단, 행동, 결과와 한계는 보존한다.

## 성과 카드의 공통 기준

| 순서 | 답변에서 확인할 내용 |
| --- | --- |
| 문제 | 어떤 사용자 또는 운영 위험이 있었는지 |
| 판단 | 왜 그 방법을 골랐고 어떤 대안을 보류했는지 |
| 행동 | 상태 변경, 데이터 접근, 실패 처리 중 무엇을 바꿨는지 |
| 검증 | 재현, 실행 계획, 테스트, 관측 중 무엇으로 확인했는지 |
| 성과와 한계 | 확인된 변화와 다시 점검해야 하는 조건이 무엇인지 |

이 구조는 특정 고객, 처리량, 비용 또는 내부 임계값 없이도 실제 판단과 검증을 설명하기 위한 카드다.

## 동시성 제어

- **문제**: 여러 장비 또는 요청이 동일한 재고성 상태를 동시에 갱신해, 먼저 읽은 값이 나중의 갱신으로 덮일 위험이 있었다.
- **판단과 행동**: 충돌 비용이 큰 쓰기 경로에 데이터베이스 비관적 잠금을 적용하고, 잠금 순서, 짧은 트랜잭션, 제한 재시도와 사용자 피드백을 함께 설계했다.
- **결과와 한계**: 정합성 기준과 실패 경로는 분명해졌지만, 잠금 경합과 데드락은 완전히 사라지는 문제가 아니므로 관측과 재시도 정책을 계속 조정해야 한다.
- 여러 요청이 같은 자원을 갱신할 때는 충돌 가능성, 재시도 비용, 사용자 영향으로 낙관적 잠금과 비관적 잠금을 선택한다.
- 비관적 잠금을 선택했다면 잠금 순서, 짧은 트랜잭션 범위, 재시도와 사용자 피드백을 함께 설명한다.
- 결제나 자산 이동처럼 복구 비용이 큰 흐름은 멱등성 키와 상태 전이를 추가한다.

**검증 드릴**

- 같은 키로 동시에 들어온 요청, 잠금 실패, 재시도 소진과 워커 재시작을 재현해 최종 상태가 하나인지 확인한다.
- 독립적인 입력 검증은 잠금 전에 하되, 변경 가능한 상태의 불변식은 잠금 뒤 다시 검사해 시간차 오류를 막는다.
- 특정 DB의 잠금 문법이나 격리 수준은 제품 버전과 공식 문서로 다시 확인한 뒤 말한다.

## 조회 성능

- **문제**: 최신 상태를 조회하는 경로가 데이터 증가와 함께 느려졌고, 응답 지연의 원인이 쿼리인지 애플리케이션인지 분리할 필요가 있었다.
- **판단과 행동**: 실행계획과 데이터 분포를 확인한 뒤, 실제 필터와 정렬 순서를 반영한 복합 인덱스를 검토했다. 전후 실행계획과 같은 조건의 지연을 비교했다.
- **결과와 한계**: 당시 같은 측정 조건에서 후보 행과 불필요한 정렬을 줄여 조회 지연을 개선했다. 인덱스는 쓰기 비용이 있어 쿼리와 데이터 분포가 바뀌면 재검증해야 한다.
- 느린 조회는 실제 실행계획, 필터와 정렬 조건, 데이터 분포를 먼저 확인한다.
- 복합 인덱스는 동등 조건, 범위 조건, 정렬, 선택도를 기준으로 설계하고 쓰기 비용도 검토한다.
- 개선 결과는 특정 숫자보다 측정 환경과 재측정 조건을 함께 설명한다.

**경험 수치의 측정 경계**

- 전체 조회에 포함된 서브쿼리 관측값과 별도로 측정한 쿼리 1건의 전후 결과는 같은 지표로 비교하지 않는다.
- 실행 환경, cache 상태, 표본 수와 percentile이 기록되지 않은 수치는 다른 조건과 직접 비교하지 않는다.

**검증 드릴**

- 같은 쿼리, 데이터 분포와 호출 조건에서 변경 전후 실행 계획을 비교한다.
- 후보 행, 정렬, 조인 방식, 인덱스 적용 여부와 인접 쓰기 경로의 비용을 함께 확인한다.
- ORM 옵션은 이름만 인용하지 않고 실제 생성 SQL과 실행 계획으로 검증한다.

## 비동기 이벤트 처리

- **문제**: 핵심 업무 상태 변경 뒤에 알림과 외부 연동을 동기 요청에 묶으면, 후속 실패가 사용자 흐름까지 전파될 수 있었다.
- **판단과 행동**: 핵심 상태는 먼저 확정하고, 후속 효과는 이벤트와 워커로 분리했다. 처리 키, 상태 전이, 제한 재시도와 최종 실패 확인 경로를 뒀다.
- **결과와 한계**: 재처리와 실패 격리의 경계는 분명해졌지만, 비동기화만으로 정합성이 보장되지는 않아 발행 누락, 중복과 운영 관측을 계속 검증해야 한다.
- 핵심 상태 변경은 트랜잭션에서 확정하고, 알림이나 외부 연동 같은 후속 효과는 비동기로 분리한다.
- 소비자는 멱등하게 만들고, 재시도 한계를 넘는 실패는 DLQ와 운영자 확인 경로로 보낸다.
- 메시지 브로커 선택은 순서 보장, 리플레이, 처리량, 운영 복잡성, 비용의 균형으로 설명한다.

**검증 드릴**

- 중복 전달, 소비자 재시작, 일시 오류, 영구 오류와 발행 누락을 구분해 재현한다.
- 메시지 처리 키, 상태 전이, 재시도 횟수와 DLQ의 재처리 책임을 같은 기록에서 추적한다.
- 핵심 상태를 확정하기 전에 외부 효과를 실행하지 않는지, 비동기화 뒤에도 누락과 중복을 관측하는지 확인한다.

## 외부 의존성 격리

- **문제**: 외부 API의 지연이나 오류가 핵심 사용자 흐름과 다른 의존성까지 전파될 수 있었다.
- **판단과 행동**: 의존성별 타임아웃, 제한된 재시도와 지수 백오프를 두고, 연결 또는 작업 풀을 분리했다. 제품 요구에 맞춰 마지막 정상 값, 보류 상태, 기능 축소와 수동 복구 중 폴백을 고른다.
- **검증과 한계**: 지연, 오류, 타임아웃과 복구를 주입해 격리 범위를 확인한다. 재시도는 장애를 키울 수 있으므로 호출량, 오류율과 대기 시간을 함께 관측한다.

## 이미지와 배포

- **문제**: 애플리케이션 이미지에 빌드 도구와 불필요한 파일이 함께 들어가 배포와 저장 부담이 커질 수 있었다.
- **판단과 행동**: 멀티스테이지 빌드와 제외 규칙으로 런타임에 필요한 산출물만 남겼고, 배포 전후의 빌드와 실행 경로를 확인했다.
- **결과와 한계**: 이미지와 배포 부담을 줄였지만, 경량 베이스 이미지는 네이티브 모듈 호환성과 현장 디버깅 가능성도 함께 검토해야 한다.
- 컨테이너 경량화는 멀티스테이지 빌드, 불필요 파일 제외, 런타임 의존성 최소화로 접근한다.
- 더 작은 이미지가 항상 정답은 아니므로 네이티브 모듈 호환성과 현장 디버깅 가능성도 확인한다.

**검증 드릴**

- 빌드 산출물, 런타임 의존성, 환경 변수 주입, 배포와 롤백 경로를 분리해 확인한다.
- 이미지 크기 변화만 보지 않고 실행 호환성, 취약점 점검과 복구 시간을 함께 확인한다.

## AI 자동화

- **문제**: 반복 검수 작업을 줄일 기회가 있었지만, 자동화 결과를 그대로 확정하면 오류 비용이 커질 수 있었다.
- **판단과 행동**: 오류 비용이 낮은 단계부터 시작하고, 검증 데이터와 사람 검토를 비교했다. 불확실한 결과와 예외는 사람에게 되돌리고, 로그와 롤백 경로를 뒀다.
- **결과와 한계**: 자동화의 대상과 책임 경계를 명확히 했다. 특정 모델의 성능이나 운영 효과는 재현 가능한 측정 없이 일반화하지 않는다.
- 자동화 대상은 오류 비용이 낮고, 사람이 검토할 경계를 명확히 정할 수 있는 작업부터 고른다.
- 정확도는 라벨된 데이터와 사람 검토를 비교해 검증하고, 예외와 불확실한 결과는 사람에게 되돌린다.
- 점진 도입, 로그, 이상치 알림, 롤백 경로를 함께 설계한다.

**공개 제품 맥락의 가정형 적용**

- 상품 이미지나 상품권 정보 검수는 모델이 이상 후보를 분류하고 사람이 최종 확정하는 보조 흐름부터 검토한다.
- 비정상 거래나 악용 패턴은 자동 차단보다 검토 우선순위를 정하는 신호로 시작한다.
- 고객 문의는 유형 분류와 답변 초안을 보조하되, 금전 또는 계정 상태를 바꾸는 결정은 검증된 규칙과 사람의 승인 경계를 둔다.
- 위 내용은 당시 공개 제품 맥락에서 만든 가설이며 실제 회사 기능이 아니다. 라벨된 검증 데이터, 불확실성 기준, 감사 기록과 롤백을 확인한 뒤 범위를 넓힌다.

**검증 드릴**

- 검증 데이터와 사람의 최종 판단을 비교하고, 오류 비용이 큰 결과는 자동 확정하지 않는다.
- 모델, 프롬프트, 입력 형식이 바뀌면 이전 결과와 비교할 수 있게 버전과 검증 범위를 남긴다.

## 관측성

- **문제**: 장애나 성능 저하가 발생했을 때, 사용자 영향과 기술 원인을 빠르게 연결할 공통 문맥이 부족했다.
- **당시 답변과 실제 경험**: 구조화 로그, 메트릭과 요청 식별자를 사용해 사용자 영향, 애플리케이션, 인프라와 외부 의존성을 나눠 확인했다. 분산 트레이싱 파이프라인을 직접 운영한 경험은 없었다.
- **현재 교정**: 여러 서비스와 비동기 작업을 함께 추적해야 한다면 trace context를 전파하고 로그와 메트릭을 같은 요청 문맥으로 연결한다. 이는 이후 설계 방향이지 당시 운영 성과로 말하지 않는다.
- **결과와 한계**: 로그와 메트릭으로 원인을 좁히는 판단 기준을 만들었다. 실제 경보의 효과는 기준선, 관측 기간과 대응 가능성을 두고 검증해야 한다.
- 비즈니스, 애플리케이션, 인프라, 외부 의존성의 네 계층으로 지표를 나눈다.
- 알림은 사용자 영향과 대응 가능성을 기준으로 만들고, 경보 피로를 피한다.
- 메트릭, 로그, 트레이스를 연결해 원인을 좁히고, 사건 뒤에는 재발 방지 기준을 남긴다.

**검증 드릴**

- 사용자 영향, 애플리케이션, 인프라, 외부 의존성의 네 계층에 정상 구간과 실패 신호를 둔다.
- 알림을 받았을 때 담당자가 어떤 로그, 지표, 배포 이력을 보고 어떤 복구를 할지 한 흐름으로 점검한다.
- 경보의 유용성은 발생 건수보다 실제 대응, 오탐과 복구 시간으로 다시 평가한다.
