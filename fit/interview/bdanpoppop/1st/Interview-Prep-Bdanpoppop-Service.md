# 비단팝팝 1차 — 서비스 맥락과 역질문

> 이 문서는 1차 준비에서 만든 가정형 서비스 질문과 본인 답변의 요약이다. 실제 제품 구조나 비공개 기술 선택을 주장하지 않는다.

당시 공고의 거래, 연동, 운영 맥락을 읽고 아래 질문을 준비했다. 2026-05-11 회사 사정으로 면접이 취소됐으므로 아래 내용은 실제 받은 질문이 아니라 준비 질문이다.

당시 공개 JD의 역할과 우대사항은 [[Interview-Prep-Bdanpoppop-JD|JD 분석과 FIT 답변]]에 역사 스냅숏으로 남겼다. 아래 설계는 그 공개 맥락에 대한 후보 답변일 뿐, 실제 제품의 데이터 모델, 결제 흐름, 외부 연동 또는 운영 기준을 뜻하지 않는다.

## 서비스 설계 질문

### 같은 자원에 동시 요청이 오면?

- 자원 식별자와 멱등성 키를 기준으로 중복 요청을 판단한다.
- 원자성이 필요한 상태 변경은 트랜잭션과 잠금으로 보호한다.
- 잠금 실패나 충돌에는 재시도 정책과 사용자에게 보일 상태를 설계한다.

**답변 검증**

- 동일 키의 동시 요청, 잠금 실패, 제한 재시도와 요청 중단을 재현해 최종 상태가 하나인지 확인한다.
- 여러 자원을 잠글 때는 일관된 순서를 쓰고, 외부 호출은 트랜잭션 밖으로 빼 잠금 시간을 짧게 유지한다.
- 낙관적 잠금과 비관적 잠금은 충돌 빈도, 재시도 비용과 사용자 영향으로 비교한다.

### 핵심 처리는 성공했지만 외부 연동이 실패하면?

- 핵심 상태 변경과 외부 기록, 알림, 정산을 분리한다.
- 외부 효과는 재시도 가능한 비동기 작업으로 만들고, 실패는 관측과 수동 복구 경로로 보낸다.
- 사용자에게는 확정된 상태와 보류 상태를 명확히 구분해 보여 준다.

**답변 검증**

- 소비자는 처리 키와 상태 전이로 중복 전달을 안전하게 처리한다.
- 일시 오류는 제한된 재시도로, 영구 오류는 DLQ와 확인 가능한 재처리 경로로 분리한다.
- 외부 기록의 실패가 핵심 상태를 임의로 되돌리지 않도록, 확정과 보류 상태의 책임을 분리한다.

### 트래픽이 급증하면?

- 먼저 캐시, 대기열, 요청 제한으로 데이터베이스와 외부 의존성을 보호한다.
- 동기 경로는 짧게 유지하고, 오래 걸리는 작업은 비동기화한다.
- 확장 정책은 추측이 아니라 요청량, 지연, 오류율, 큐 적재량의 관측값으로 조정한다.

**답변 검증**

- 부하가 커질 때 요청 제한, 캐시, 대기열과 비동기 전환이 데이터 저장소와 외부 의존성을 어느 지점에서 보호하는지 설명한다.
- 규모를 단정하지 않고 관측 기준을 먼저 정한 뒤, 수직 확장, 수평 확장과 데이터 분할의 선택 시점을 비교한다.

### 외부 API가 느리거나 실패하면?

- 타임아웃, 제한된 재시도, 지수 백오프와 격리로 장애 전파를 막는다.
- 마지막 정상 값 사용, 지연 응답, 기능 축소 같은 폴백을 제품 요구에 맞게 결정한다.
- 의존성별 오류율과 지연을 별도로 관측한다.

**답변 검증**

- 타임아웃, 오류, 느린 응답과 복구를 주입해 한 의존성의 장애가 다른 요청을 멈추게 하지 않는지 확인한다.
- 의존성별 연결 또는 작업 자원을 분리하고, 재시도가 전체 부하를 키우지 않게 호출량과 대기 시간을 함께 본다.
- 폴백은 최신성, 정합성, 사용자 안내와 수동 복구 가능성을 기준으로 선택한다.

## 관측성과 복구 드릴

| 계층 | 확인할 신호 | 복구 판단 |
| --- | --- | --- |
| 사용자 영향 | 성공과 실패 흐름, 지연, 보류 상태 | 사용자에게 보여 줄 상태와 우회 경로를 정한다. |
| 애플리케이션 | 오류, 지연, 상태 전이 실패 | 배포 변경, 코드 경로와 재시도를 함께 확인한다. |
| 데이터와 인프라 | 잠금 대기, 쿼리 지연, 큐 적재, 자원 포화 | 부하를 줄이고 병목을 재현한 뒤 안전하게 복구한다. |
| 외부 의존성 | API별 지연과 오류, 폴백 사용량 | 격리, 기능 축소, 수동 재처리 중 필요한 경로를 고른다. |

경보는 신호가 있다는 사실보다, 담당자가 실제로 확인하고 조치할 수 있는지로 평가한다.

## 첫 기간 실행계획

이 계획은 회사의 현재 상태에 관한 주장이 아니라, 공개 JD를 읽고 준비한 행동 가설이다.

1. 첫 30일에는 실제 데이터 흐름, 실패 경계, 배포와 관측의 기준을 문서와 코드로 확인한다.
2. 31일에서 60일에는 가장 위험한 한 흐름에 멱등성, 재시도, 실패 큐, 테스트와 관측을 보강한다.
3. 61일에서 90일에는 리뷰, 배포 또는 복구 절차 중 반복되는 기준을 팀이 재사용할 수 있는 작은 문서와 검사로 정리한다.

## 컬처핏 답변 원칙

- 장점은 관찰, 가설, 검증의 작업 방식으로 설명하고, Prisma 관계 다중 쿼리처럼 용어는 실제 생성 SQL에 맞춰 표현한다.
- 약점은 경험하지 않은 기술이나 도메인을 인정한 뒤, 학습 순서와 검증 계획으로 보완한다.
- 팀 기여는 개인 생산성보다 공통 기준, 리뷰, 운영 가시성을 만드는 행동으로 설명한다.
- 회사별 맞춤 답변은 공개 공고와 제품 자료에 근거하고, 개별 연락 내용은 사용하지 않는다.

## 역질문

1. 이 역할이 첫 기간에 해결해야 할 가장 중요한 문제는 무엇인가?
2. 팀의 기술 결정, 리뷰, 배포와 장애 대응은 어떤 경계로 나뉘는가?
3. 거래와 외부 연동에서 현재 가장 중요하게 보는 신뢰성 지표는 무엇인가?
4. 당시 공개 JD의 Web3 연동은 이 역할이 바로 책임질 범위인지, 인접 시스템과 협업할 범위인지?
5. 익숙하지 않은 도메인에 합류한 구성원에게 기대하는 학습 과정과 첫 성공 신호는 무엇인가?
6. 고용 조건과 평가 기준은 어느 시점에 서면으로 확인할 수 있는가?
