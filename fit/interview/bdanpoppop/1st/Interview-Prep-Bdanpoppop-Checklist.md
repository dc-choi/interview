# 비단팝팝 1차 준비 체크리스트

> 전형 기록: 1차 면접은 2026-05-14 16:00에 대면 단독 40~50분으로 예정됐으나, 2026-05-11 회사 사정으로 취소돼 진행되지 않았다.
> 면접관은 개발본부 부장 역할 1명으로 안내됐고, 기술, 직무와 문화 적합성을 함께 확인하는 자리로 준비했다.
> 당시 채용 측 안내는 자동화, 안정적 운영, AI 활용 경험을 추가로 확인한다는 취지로 요약한다. 원문, 발신자, 연락처와 장소는 기록하지 않는다.

## 1차 면접의 준비 초점

- 기술 구현 자체보다 선택 이유, 대안, 트레이드오프, 한계와 팀에 미친 영향을 짧게 설명한다.
- 자기소개는 30~45초로 압축하고, 동시성, 조회 성능, 비동기 처리, 관측성 중 한 사례를 꼬리 질문까지 설명할 수 있게 한다.
- 실제 회사의 팀 규모, 기술 스택, 운영 구조는 추측하지 않고 역질문으로 확인한다.

## 채용 측이 추가 확인할 가능성이 있었던 본인 경험

| 주제 | 본인 답변에서 보존할 핵심 |
| --- | --- |
| 반복 업무 자동화 | 핵심 상태 변경과 후속 효과를 분리하고, 멱등성, 재시도와 최종 실패의 확인 경로를 만들었다. |
| 안정적 운영 | 로그, 메트릭과 알림으로 사용자 영향과 병목을 관측하고, 변경과 복구의 기준을 남겼다. |
| AI 활용 | 자동화 결과를 사람의 최종 판단과 분리하고, 검증 데이터, 예외 처리와 롤백 경계를 뒀다. |

아래 체크리스트는 위 세 주제를 포함해 실제 사례를 문제, 판단, 행동, 결과와 한계 순으로 연습하기 위한 것이다.

## 실제 경험 카드의 답변 구조

각 카드는 이전 조직, 고객, 운영 수치와 내부 구현을 빼고도 설명 가능해야 한다.

| 카드 | 문제 | 판단과 행동 | 검증과 성과 |
| --- | --- | --- | --- |
| 동시 갱신 | 같은 재고성 상태를 여러 요청이 동시에 바꿀 수 있었다. | 충돌 비용이 큰 쓰기에는 행 잠금, 고정된 잠금 순서, 짧은 트랜잭션과 제한된 재시도를 적용했다. | 동시 요청, 잠금 실패와 재시작을 재현해 최종 상태와 사용자 피드백을 확인했다. |
| 조회 성능 | 최신 상태 조회가 느려졌고 원인을 분리할 필요가 있었다. | 실행 계획, 필터, 정렬과 데이터 분포를 보고 쿼리와 인덱스를 함께 조정했다. | 같은 조건의 전후 실행 계획과 지연 분포로 개선을 확인하고 쓰기 비용도 점검했다. |
| 후속 자동화 | 핵심 상태 변경 뒤의 알림과 외부 호출이 사용자 요청을 불안정하게 만들 수 있었다. | 핵심 상태는 먼저 확정하고, 후속 효과는 멱등 소비자와 상태 전이를 가진 비동기 작업으로 분리했다. | 중복 전달, 워커 재시작, 영구 실패를 재현하고 최종 실패는 DLQ와 확인 경로로 보냈다. |
| 관측성 | 장애와 성능 저하의 사용자 영향을 원인과 연결하기 어려웠다. | 당시에는 구조화 로그, 메트릭과 요청 식별자로 사용자 영향, 애플리케이션, 인프라, 외부 의존성을 나눴다. 분산 트레이싱 운영 경험은 없었다. | 정상 구간과 대응 가능성을 기준으로 경보를 조정하고 사건 뒤 재발 방지 기준을 남겼다. |

성과는 숫자만 말하지 않는다. 관찰한 증상, 선택하지 않은 대안, 검증 방법, 확인된 변화와 남은 한계를 한 묶음으로 말한다.

## 면접 전

- [ ] 공식 공고와 회사 홈페이지에서 역할, 제품, 최신 지원 조건을 다시 확인한다.
- [ ] 이동 계획과 면접 일정은 개인 기록으로 보존한다. 제3자 연락처와 정확한 장소는 공개 문서에 남기지 않는다.
- [ ] 당시 공개 채용 절차가 서류, 1차 직무와 문화 적합성 면접, 처우 협의, 최종 합격 순서였음을 확인한다. 취소된 전형의 이후 절차는 추정하지 않는다.
- [ ] 자기소개를 문제, 선택, 결과, 한계 흐름으로 짧게 연습한다.
- [ ] 동시성, 데이터 조회, 비동기 처리, 관측성 사례를 하나씩 준비한다.
- [ ] 모르는 도메인은 핵심 용어, 위험, 학습 계획을 정리한다.

## 기술 점검

| 영역 | 점검 질문 |
|---|---|
| DB와 동시성 | 잠금 선택, 데드락 회피, 멱등성과 복구를 설명할 수 있는가? |
| 조회 성능 | 실행계획과 데이터 분포를 바탕으로 인덱스를 설명할 수 있는가? |
| ORM 관계 조회 | 관계 로딩을 N+1로 단정하지 않고 당시 버전, 설정과 생성 SQL에서 다중 쿼리 여부를 확인할 수 있는가? |
| 메시지 처리 | 재시도, DLQ, 상태 전이, 중복 소비를 다룰 수 있는가? |
| 캐시와 확장 | 캐시 무효화, 요청 제한, 대기열, 점진 확장의 기준을 아는가? |
| AI 자동화 | 검증 데이터, 사람 검토 경계, 롤백을 설명할 수 있는가? |

### 당시 공개 JD 우대사항 보강

> 공개 공고에 적힌 Web3, Redis, 메시지 큐, Docker와 Kubernetes 우대사항을 기준으로 준비했다. 현재 공고 여부는 [[Interview-Prep-Bdanpoppop-JD|JD 분석과 FIT 답변]]의 출처와 한계를 따른다.

| 영역 | 체크리스트 |
| --- | --- |
| 블록체인, Web3 | 트랜잭션 상태, 재시도, 멱등성, 외부 API 실패를 설명하고 직접 경험이 없다는 범위를 분명히 말한다. |
| Redis | Cache-Aside, TTL, 무효화, 원본 데이터 보호와 캐시 장애 폴백을 설명한다. |
| 메시지 큐 | 순서, 재시도, DLQ, 중복 소비와 재처리 요구를 기준으로 Kafka와 큐를 비교한다. |
| Docker, Kubernetes | 컨테이너 배포의 기본 흐름을 설명하고, Kubernetes 직접 운영 경험과 개념 학습을 구분한다. |

## 재현과 검증 드릴

- [ ] 두 요청이 같은 상태를 바꾸는 예제로 잠금 대기, 잠금 실패, 제한 재시도와 고정된 잠금 순서를 설명한다.
- [ ] 실제 쿼리의 실행 계획을 읽고, 후보 행, 정렬, 조인, 복합 인덱스의 쓰기 비용을 함께 말한다.
- [ ] 소비자 중복, 워커 중단, 발행 누락과 영구 실패를 넣어 보고 멱등성 키, 상태 전이, 재시도와 DLQ의 책임을 구분한다.
- [ ] 외부 API 지연과 오류를 가정해 타임아웃, 지수 백오프, 격리, 폴백과 수동 복구 기준을 설명한다.
- [ ] 사용자 영향, 애플리케이션, 인프라, 외부 의존성의 네 계층에서 어떤 신호를 보고 어떤 경보가 실제 대응으로 이어지는지 설명한다.

## 첫 기간 실행계획

이 계획은 실제 회사 상태의 설명이 아니라, 공개 JD를 읽고 준비한 입사 후 행동 가설이다.

| 기간 | 행동 | 확인할 결과 |
| --- | --- | --- |
| 첫 30일 | 코드, 데이터 흐름, 배포와 장애 대응의 실제 경계를 문서와 관측으로 파악한다. | 역할의 성공 기준, 가장 큰 실패 경로와 측정 기준을 합의한다. |
| 31일에서 60일 | 가장 위험하거나 반복적인 한 흐름의 테스트, 상태 전이, 관측 기준을 보강한다. | 재현 가능한 검증과 복구 절차가 남는다. |
| 61일에서 90일 | 팀이 반복해서 쓰는 리뷰, 배포 또는 운영 기준을 작은 문서와 자동 검사로 정리한다. | 개인 의존성을 줄이고 다음 개선의 우선순위를 근거로 정한다. |

## 답변 연습

- [ ] 결론부터 말하고 근거, 사례, 한계 순으로 답한다.
- [ ] 기술 선택의 대안과 트레이드오프를 함께 말한다.
- [ ] 공개 정보와 확인되지 않은 가정을 구분한다.
- [ ] 역질문은 역할 범위, 성공 기준, 협업 구조, 공식 조건 확인에 집중한다.

## 연습 후

- [ ] 답변 중 보완할 점과 새로 배운 일반 원칙만 마스터에 반영한다.
- [ ] 회사, 전형과 발화 출처를 제거했는지 확인한다.

## 취소 전 예정했던 당일 운영과 후속 기록

> 2026-05-11 면접이 취소돼 아래 루틴은 실행되지 않았다. 준비 당시의 후속 행동 계획으로만 보존한다.

- [ ] 공식 안내에서 시간, 형식과 준비 자료를 다시 확인하고, 장소와 연락 수단은 공개 노트가 아닌 개인 일정에서 확인한다.
- [ ] 자기소개, 기술 선택 한 사례와 역질문을 짧게 소리 내어 점검한다.
- [ ] 면접 직후 받은 질문과 본인의 당시 답변, 막힌 지점과 새로 확인한 사실을 요약한다.
- [ ] 결과는 채용 트래커에 반영하되, 취소 또는 탈락 이유를 근거 없이 추정하지 않는다.
- [ ] 조건 협의가 이어질 경우 역할, 수습과 평가 기준, 시작 가능 시점과 주요 조건을 서면으로 확인하고 개인 처우 금액은 공개 문서에 남기지 않는다.
