# 한국모바일결제 1차, JD 기반 기술 질문 9개

> [[Interview-Prep-KoreaMobilePayment-1st|목차]]. 공고의 주요 업무와 자격 요건에서 뽑았다. 바로가 실제로 쓰는 PG사, 인프라, 단말 통신 방식은 확인되지 않았으므로 답변은 판단 기준으로 말하고 구현을 단정하지 않는다. PG마다 API 계약이 다르므로 구체 필드와 동작은 사용 중인 PG 공식 문서로 확인한다는 조건을 붙인다.

## J1. 결제와 취소 API에서 이중 결제, 이중 취소를 어떻게 막나 (사실형 + 설계형)

- **의도**: 결제 도메인의 기본 불변식을 아는지.
- **핵심 답변**: 쓰기 요청마다 업무 단위 멱등성 키(예: 주문 ID와 시도 번호)를 두고 DB 유일 제약으로 먼저 막는다. 같은 키가 다시 오면 새로 처리하지 않고 저장된 결과를 돌려준다. PG가 멱등성 키를 지원하면 같은 키를 전달한다. 결제 상태는 `READY → PAID → CANCELED` 같은 명시적 전이로만 바꾸고, 전이는 조건부 갱신(`WHERE status = 'PAID'`)이나 행 잠금 아래에서 한다. 금액은 서버가 다시 계산하고 원 단위 정수로 저장한다.
- **흔한 오답**: 버튼 중복 클릭 방지만 말한다. 클라이언트 금액을 믿는다. 금액을 float로 저장한다. POST가 자동으로 중복에 안전하다고 본다(POST는 HTTP 의미상 멱등이 아니다).
- **꼬리**: 부분 취소가 여러 번 들어오면 누적 취소액이 원결제액을 넘지 않는지 같은 트랜잭션에서 검증한다. 승인 취소와 매입 이후 환불은 카드사 처리와 고객 반영 시점이 다를 수 있어 PG 문서로 확인한다.
- **출처**: [RFC 9110 Idempotent Methods](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods), [IETF Idempotency-Key 헤더 초안](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)

## J2. PG 승인 요청이 timeout 났다. 결제된 건가 (설계형)

- **의도**: 결과 불명확 상태를 실패로 오판하지 않는지.
- **답변 골격**: timeout은 실패 확정이 아니다 → 내부 상태를 `UNKNOWN`(확인 필요)으로 두고 → 같은 멱등성 키로 재시도하거나 PG 조회 API로 주문 ID 기준 상태를 확인 → 확인 전에는 고객에게 성공도 실패도 단정하지 않는다 → 끝까지 불명확한 건은 대사 배치와 수동 검토로 닫는다.
- **대안과 트레이드오프**: 새 키로 즉시 재시도하면 빠르지만 이중 승인 위험이 있다. 조회 우선은 느리지만 안전하다. 키오스크 앞에서 고객이 기다리는 시간과 이중 결제 정정 비용을 함께 비교한다.
- **꼬리**: 웹훅이 동기 응답보다 먼저 오거나 늦게 오면? 상태 전이를 멱등하게 만들어 어느 쪽이 먼저 와도 같은 결과로 수렴하게 한다. 웹훅은 서명과 타임스탬프를 검증하고, 본문을 믿기 전에 PG 조회로 재확인하는 선택지도 있다.

## J3. 멤버십 자동결제(정기결제)를 설계하라 (설계형)

- **의도**: 스케줄러, 중복 청구, 실패 재시도, 해지를 함께 다루는지.
- **답변 골격**:
  1. 고객 동의와 인증으로 PG가 발급한 정기결제 수단 토큰(빌링키)을 받아 저장한다. 카드번호는 보관하지 않는다.
  2. 청구 대상 조회와 청구 실행을 분리한다. 청구 단위는 `(membership_id, billing_period)`에 유일 제약을 둔 청구 레코드다. 스케줄러가 두 번 돌아도 두 번째 삽입이 막힌다.
  3. 여러 인스턴스에서는 DB lease나 큐의 단일 작업으로 실행을 하나로 줄이고, 유일 제약은 최후 방어선으로 둔다.
  4. 실패는 사유별로 나눈다. 한도 초과 같은 재시도 가능 실패는 제한된 횟수와 간격으로 재시도하고 고객에게 알린다. 카드 만료 같은 영구 실패는 재시도하지 않고 결제 수단 갱신을 요청한다. 유예 기간이 지나면 혜택 정지 상태로 전이한다.
  5. 해지는 다음 갱신 중단과 즉시 환불을 구분한다. 어느 쪽이 정책인지는 회사가 정한다.
- **꼬리**: 청구 요청이 timeout이면 J2와 같이 확인 상태로 둔다. 금액이 바뀌는 요금제 변경은 다음 청구 주기부터 적용할지 일할 계산할지 정책 질문으로 돌린다.
- **바로 연결**: 공식 사이트가 월 멤버십과 첫 달 무료 체험을 안내하므로, 무료 체험 종료 시 첫 청구와 해지 가능 시점이 셀프 처리의 핵심 경로일 가능성이 크다. 실제 정책은 확인 질문으로 둔다.

## J4. 결제가 걸린 서비스의 배포와 롤백 (설계형)

- **답변 골격**: 롤백은 코드, 이미지, 설정만 되돌린다. 이미 나간 결제 승인, 웹훅 호출, 큐 메시지, 적용된 스키마는 되돌아가지 않는다 → 그래서 스키마는 확장, 이전, 축소 순서로 신구 버전이 함께 읽을 수 있게 바꾼다 → 결제 경로 변경은 기능 플래그 뒤에 두어 배포 없이 끌 수 있게 한다 → 배포 판정은 프로세스 기동이 아니라 결제 성공률, 오류율, 지연이 평소로 돌아왔는지로 한다 → 이미지 digest를 배포 이력에 남겨 정확히 되돌린다.
- **대안**: Rolling은 자원이 적게 들고 Blue/Green은 즉시 전환과 빠른 롤백이 쉽다. 트래픽이 적은 시간대 배포 원칙도 매장 영업시간을 기준으로 정한다.
- **꼬리**: 배포 뒤 문제가 결제 데이터를 이미 바꿨다면 코드 롤백으로 끝나지 않는다. 영향 건을 식별하고 보정 작업과 대사로 복구한 뒤 회고한다.

## J5. 결제 장애를 어떻게 감지하고 대응하나 (설계형)

- **감지 지표**: 결제 시도 대비 성공률, PG 응답 코드와 지연 분포, 확인 필요 상태 건 수와 가장 오래된 건의 나이, 웹훅 수신 지연, 대사 불일치 건 수, 큐 적체와 DLQ, 키오스크 heartbeat 누락.
- **대응 순서**: 영향 범위 공유 → 복구 우선(롤백, 플래그 끄기, PG 우회가 가능하다면 그 절차) → 영향 받은 결제 식별 → 고객 보상과 CS → 타임라인, 원인, 재발 방지 포스트모템.
- **핵심**: 비율 지표에 한 건의 중요한 실패가 묻히지 않도록 결과 불명확 건은 건수 기준 알림을 따로 둔다.
- **출처**: [Google SRE Book, Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)

## J6. AI가 만든 결제 코드를 어떻게 검수해 배포하나 (경험형 + 설계형)

- **의도**: 필수 요건. 위임 범위와 검수 기준이 구체적인지.
- **답변**: 먼저 명세를 쓴다. 입력, 상태 전이, 실패 경로, 금액 불변식을 문장으로 정하고 AI는 그 명세를 구현한다. 규칙 문서로 AI가 손대면 안 되는 영역(금액 계산, 결제 상태 전이, 비밀 정보, 마이그레이션)을 명시하고 작업 종료 시 테스트와 정적 검사가 돌게 한다. 사람은 diff에서 금액, 상태, 재시도, 트랜잭션 경계를 우선 본다. 샌드박스에서 결제, 취소, timeout 시나리오를 돌린 뒤 배포하고 배포 후 지표를 확인한다.
- **내 근거**: 팀 AI 협업 규약 표준화, 종료 시점 자가 검증 회귀 루프, 개인 출석부 프로젝트의 AI 협업 파이프라인(정성 결론만 말한다).
- **꼬리**: Codex 경험을 물으면 이력서에 없으므로 Claude Code 경험과 도구 비교 기준(코드베이스, 검토 경로, 보안 경계)으로 답한다.

## J7. 한 사람이 빠져도 서비스가 멈추지 않는 구조 (설계형)

- **답변 골격**: 운영 절차를 사람 머릿속에서 문서와 자동화로 옮긴다 → 배포, 롤백, 장애 대응 런북을 실제로 실행해 보고 소요 시간을 잰다 → 알림은 조치 가능한 것만, 알림마다 런북 링크 → 비밀 정보와 권한은 개인 계정이 아닌 역할 기반으로 → 결정 이력은 짧은 ADR로 남긴다 → 계열사 동료가 분기마다 한 번 실제 배포나 복구를 해 보는 연습.
- **내 근거**: 도메인별 규칙 문서로 인수인계를 쉽게 만든 경험(마스터 FIT 24).

## J8. 키오스크, 단말기 연동에서 통신이 불안정하다면 (설계형, 갭 포함)

- **갭 인정**: 결제 단말과 VAN 경로는 경험이 없다. IoT 하드웨어 상태 집계와 동시 요청 정합성 경험에서 전이되는 부분만 말한다.
- **답변 골격**: 기기 요청마다 기기 ID와 요청 ID를 두어 재전송을 멱등하게 처리 → 서버에서 기기로 가는 명령(세탁기 가동 등)은 응답 확인을 받고, 확인이 없으면 상태 조회로 결과를 확정 → heartbeat로 기기 상태를 관측하고 끊긴 매장을 알림 → 서버 장애 시 단말이 어떻게 동작해야 하는지(결제 차단, 제한 동작)는 사업 정책과 함께 정한다.
- **확인 질문**: 단말과 서버의 통신 방식, 오프라인 동작 정책, 펌웨어 배포 주체.

## J9. React Native, Next.js 경험이 없는데 점주앱과 어드민을 맡을 수 있나

- **답변**: 실무 경험은 없다고 먼저 말한다. 공고가 오류 수정을 중심으로 적고 있으므로, 첫 달에는 로컬 실행, 오류 재현, API 계약 확인, 빌드와 배포 경로를 익히는 순서로 접근하겠다. TypeScript와 API 계약 쪽은 이미 익숙하고, AI로 만든 변경은 같은 검수 기준으로 본다. 앱 스토어 배포 절차는 되돌리기 어려운 배포라 서버보다 보수적으로 다룬다.
- **확인 질문**: 프론트 작업 비중, 앱 배포 주기와 심사 대응 주체.
