# 한국모바일결제 1차, 서비스 맥락 질문 6개와 역질문

> [[Interview-Prep-KoreaMobilePayment-1st|목차]]. 공고와 공식 사이트에서 확인한 흐름(QR 결제, 키오스크 결제, 앱 결제, 멤버십 충전, 점주앱, 직영 매장 정산)만 전제로 삼는다. 실제 구현, 정책, 운영 수치는 모르므로 답변은 설계 골격과 확인 질문으로 끝낸다.

## S1. 서버가 느려지거나 멈추면 매장의 키오스크 결제는 어떻게 되어야 하나

- **공개 근거**: 공고는 전국 매장의 키오스크 결제가 멈추지 않게 하는 것을 이 자리의 첫 번째 일로 적는다.
- **답변 골격**: 먼저 서버 장애가 결제 전체를 막는 구조인지, 단말이 독립적으로 결제할 수 있는 구조인지 확인한다 → 서버 의존 경로라면 외부 PG 호출에 timeout과 서킷 브레이커를 두어 느린 의존성이 전체 스레드와 연결을 잡아먹지 않게 한다 → 결제와 무관한 기능(쿠폰, 통계, 알림)은 결제 경로에서 분리해 장애를 격리한다 → 단말은 결과 불명확 상태를 고객에게 명확히 표시하고 재시도 버튼이 이중 결제를 만들지 않게 같은 요청 ID를 쓴다.
- **트레이드오프**: 단말 쪽 오프라인 허용은 가용성을 높이지만 나중에 대사와 정정 비용이 생긴다.
- **내 경험 연결**: IoT 통신 지연 집계, 단일 서버에서 ECS 다중 태스크로 전환해 단일 장애점을 줄인 경험.

## S2. QR로 결제는 됐는데 세탁기가 돌지 않았다

- **답변 골격**:
  1. 결제와 기기 가동을 하나의 주문 상태 머신으로 묶는다. 예: `PAID → DEVICE_COMMANDED → DEVICE_STARTED`, 실패 분기 `DEVICE_FAILED`.
  2. 가동 명령에 확인 응답을 요구하고, 제한 시간 안에 확인이 없으면 기기 상태를 조회해 확정한다.
  3. 가동 실패가 확정되면 자동 취소 또는 멤버십 잔액 적립 같은 보상을 멱등하게 실행한다. 어느 보상을 할지는 사업 정책이다.
  4. 확정되지 않는 건은 CS 큐로 보내고 점주와 본사가 같은 화면에서 볼 수 있게 한다.
- **판단 기준**: 고객이 매장 앞에서 기다리는 시간, 이중 보상 위험, 점주 매출 정산에 미치는 영향.
- **꼬리**: 보상 실행이 두 번 되지 않으려면 보상에도 주문 단위 유일 키를 둔다.

## S3. 멤버십 해지와 환불을 셀프 처리로 바꾼다면

- **공개 근거**: 공고의 운영 자동화 업무. 공식 사이트는 월 멤버십과 첫 달 무료 체험, 충전 보너스를 안내한다.
- **답변 골격**: 정책을 코드 전에 문장으로 확정(해지 시점, 무료 체험 중 해지, 사용한 혜택이 있을 때 환불 범위, 충전 보너스 회수 여부) → 셀프 해지는 다음 청구 중단을 기본 경로로, 환불은 조건을 계산해 자동 승인 범위와 수동 검토 범위로 나눔 → 환불 요청은 멱등하게, PG 부분 취소 결과가 불명확하면 확인 상태로 → 모든 처리에 감사 로그 → 자동 처리된 건과 수동 건의 비율을 보고 규칙을 넓힌다.
- **대안**: 전부 자동은 CS 비용이 줄지만 악용과 과환불 위험이 있다. 금액 임계값과 반복 요청 제한을 둔다.
- **내 경험 연결**: 환불 정책 누락 위험을 먼저 정리해 보호 조건을 두고 출시한 사례(FIT 문서 C9), 수기 발주를 이벤트 기반으로 자동화한 경험.

## S4. 점주 매출과 정산 금액이 PG 정산 내역과 맞지 않는다

- **답변 골격**: 내부 결제 원장과 PG 거래 원장을 주기적으로 대사한다 → 차이는 즉시 수정 대상이 아니라 조사 후보다(반영 지연, 부분 취소, 시각 경계 차이) → 유예 기간 뒤 최신 상태를 다시 조회하고, 설명되지 않는 건만 기록해 조치 → 원장은 수정하지 않고 정정 항목을 추가해 이력을 남긴다 → 정산 마감 이후 변경은 다음 정산에 반영하는 규칙을 둔다.
- **흔한 오답**: 차집합이 나오자마자 자동 취소한다. 정산 금액을 UPDATE로 덮어쓴다.
- **꼬리**: 집계 조회가 느리면 일 단위 요약 테이블을 두되, 요약은 원장에서 다시 만들 수 있어야 한다.

## S5. 계좌이체 충전을 넣는다면

- **공개 근거**: 공고의 결제 안정성 업무에 계좌이체 충전이 있다. 실제 입금 확인 방식은 미확인이다.
- **답변 골격**: 충전 요청 생성(금액과 입금 식별자) → 입금 통지 수신은 서명 검증과 멱등 처리 → 입금 확인과 잔액 증가를 한 트랜잭션에서 → 금액 불일치, 중복 통지, 만료 뒤 입금은 별도 상태로 두고 수동 확인 → 대사로 누락 통지를 잡는다.
- **확인 질문**: 입금 확인을 어떤 경로로 받는지, 충전 잔액의 환불 정책.

## S6. 본사 직영 매장의 관리와 정산 기능을 새로 만든다

- **공개 근거**: 공고의 신규 운영 모델 업무, 무인매장 운영 전체로 넓힌다는 방향.
- **답변 골격**: 가맹 매장과 직영 매장의 차이를 먼저 정의(매출 귀속, 수수료, 비용 항목) → 매장 유형을 모델에 명시하고 정산 규칙을 유형별 전략으로 분리 → 기존 가맹 정산 경로를 건드리지 않고 새 경로를 플래그 뒤에서 병행 검증 → 첫 달은 수기 정산과 대조해 차이가 0인지 확인한 뒤 전환.
- **내 경험 연결**: PoC와 잦은 요구사항 변경을 도메인별 모듈 분리로 수용한 경험.

## 역질문

[[My-Reverse-Questions]]에서 고르고 회사 특이 질문을 더했다. 핵심 2~3개는 외워서 묻고 나머지는 흐름에 맞춰 고른다.

1. **B1 초기 과제와 성공 기준**: 합류 후 첫 90일에 가장 먼저 책임질 일과, 잘하고 있다고 판단할 기준은 무엇인가요?
2. **D1 온보딩, 인수인계**: 현재 바로의 서버와 결제 연동을 누가 어떤 상태로 운영하고 있고, 합류하면 코드와 운영 문서를 어떤 경로로 넘겨받게 되나요?
3. **A4 팀 구성과 협업 경계**: 공고에 계열사 AI 프로덕트 엔지니어와 서로 백업한다고 되어 있는데, 백업은 어떤 범위와 방식으로 이뤄지나요?
4. **E3 온콜과 장애 대응**: 매장 영업시간 기준으로 장애 대응을 어떻게 나누고, 사후 회복은 어떻게 운영하나요?
5. **C3 관측성과 품질 기준**: 결제 이상을 지금은 어떤 신호로 감지하고, 결과가 불명확한 결제는 어떤 기준으로 정리하나요?
6. **회사 특이, AI 검수 게이트**: AI로 만든 변경 중 결제 경로에 닿는 변경은 배포 전에 어떤 확인을 거치나요?
7. **회사 특이, 오프라인 동작**: 서버나 네트워크 장애 때 키오스크는 어떻게 동작하도록 설계되어 있나요?

**확인만 할 사항 (답을 추정하지 않는다)**: 고용 형태, 이후 전형 절차, 사용하는 PG와 인프라, 프론트 작업 비중. 처우는 역할 기준의 공개 가능한 밴드만 묻고 본인 금액은 먼저 말하지 않는다.
