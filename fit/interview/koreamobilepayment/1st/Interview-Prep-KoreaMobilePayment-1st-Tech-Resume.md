# 한국모바일결제 1차, 이력서 기반 기술 질문 9개

> [[Interview-Prep-KoreaMobilePayment-1st|목차]]. [[My-Tech-Cards]]를 fork했다. 수치는 공개 이력서에 있는 값만 쓰고, 측정 조건을 물으면 기억에 기대지 않고 확인 가능한 범위만 답한다. 전 직장 내부 지표와 비공개 구조는 말하지 않는다.

## R1. 수천 대 IoT 동시 요청의 경쟁 상태를 DB Lock으로 어떻게 풀었나 (경험형)

- **의도**: 동시성 문제를 재현하고 잠금 전략을 근거로 골랐는지. 결제 잔액, 충전과 직결된다.
- **핵심 답변**: 같은 재고 행을 동시에 바꾸는 경로에서 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한 재시도를 조합했다. 충돌이 잦아 늦게 충돌을 발견하는 낙관적 잠금보다 변경 전에 경합을 조정하는 비관적 잠금이 단순했다. 입력 검증과 외부 호출은 트랜잭션 밖으로 빼고, 잠금 읽기 뒤 불변식을 다시 검증했다. 여러 대상은 업무 키 순서를 통일했다. 동시 요청을 재현해 최종 수량과 실패 경로를 확인했다.
- **한계**: 당시 재시도는 짧은 고정 간격이었다. 지금이라면 지수 백오프와 지터를 검증한다. `NOWAIT`는 해당 잠금 읽기의 대기만 없애고 메타데이터 잠금 대기는 남는다. 잠금은 유입량을 흡수하지 못하므로 급격한 유입이면 업무 키별 순서 큐와 워커 동시성 제한을 검토한다.
- **꼬리**: NOWAIT와 SKIP LOCKED 차이(SKIP LOCKED는 잠긴 행을 건너뛰는 큐 패턴, 특정 행을 반드시 처리해야 하면 NOWAIT). 멀티 인스턴스에서도 같은 DB를 보는 한 DB 잠금으로 충분하고, 보호 대상이 여러 저장소를 넘을 때만 분산 잠금을 검토한다.
- **바로 연결**: 멤버십 충전 잔액 차감은 `UPDATE ... SET balance = balance - ? WHERE id = ? AND balance >= ?` 같은 조건부 갱신으로 먼저 풀 수 있는지 보고, 여러 행을 함께 바꿀 때 잠금을 쓴다.
- **출처**: [MySQL 8.0 Locking Reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)

## R2. EventBridge와 SQS로 발주 자동화를 설계한 이유와 한계 (설계형)

- **의도**: 조직 제약 안에서 메시징을 고른 판단, 전달 보장과 멱등성 이해.
- **답변 골격**: 상태 변경과 외부 연동을 한 요청에 묶으면 느린 의존성 하나가 핵심 변경까지 실패시킨다 → 상태를 먼저 확정하고 후속 작업을 이벤트로 분리 → 조직 내 Kafka 도입 한계와 운영 부담을 비교해 관리형 큐 선택 → 소비자는 멱등성 키와 상태 전이 검증으로 중복을 정상 경로로 처리 → 영구 오류는 격리, 일시 오류만 제한 재시도, 예산 초과는 DLQ와 수동 확인.
- **대안과 트레이드오프**: Kafka는 리플레이, 키 단위 순서, 높은 처리량이 핵심일 때 유리하지만 운영 부담이 크다. 관리형 큐는 운영이 가볍지만 장기 리플레이가 약하다.
- **한계 (먼저 꺼낸다)**: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 전에 프로세스가 죽으면 이벤트가 빠질 수 있었다. 지금이라면 상태 변경과 outbox 행을 같은 트랜잭션에 저장하고 릴레이가 발행하게 한다. 그래도 중복은 남으므로 정확히 한 번이라고 주장하지 않는다.
- **꼬리**: SQS visibility timeout은 처리 시간보다 길게 두고 긴 작업은 연장한다. FIFO는 MessageGroupId 단위로만 순서를 보장한다.
- **바로 연결**: 결제 성공 뒤 쿠폰 지급, 알림, CS 티켓 같은 부수 작업을 결제 트랜잭션에서 떼어 내는 구조와 같다.
- **출처**: [Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)

## R3. 복합 인덱스로 슬로우 쿼리 99.3% 개선 (경험형)

- **의도**: 수치의 근거와 측정 조건, 인덱스 설계 원리.
- **핵심 답변**: 최신 상태 레코드를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 실행 계획으로 확인했다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태로 설계하고, 인덱스가 정렬과 상위 레코드 접근에 실제로 쓰이는지 다시 확인했다.
- **측정 경계**: 99.3%는 이력서에 적은 쿼리 단위 개선이다. 서브쿼리 관측값, 단건 쿼리 전후, 배치 전체 시간은 서로 다른 지표라 섞지 않는다. 실행 환경, 캐시 상태, 표본을 물으면 기억나는 범위만 답하고 모르면 모른다고 한다.
- **흔한 오답**: 카디널리티가 높은 컬럼을 무조건 앞에 둔다. 실제로는 동등 조건, 범위 조건, 정렬, 반환 컬럼을 보고 정한다.
- **꼬리**: 인덱스의 쓰기 비용, 커버링 인덱스, OFFSET 대신 커서 페이지네이션.
- **바로 연결**: 점주앱 매출 조회는 매장 ID와 기간 조건이 반복되므로 같은 방식으로 실행 계획부터 본다.

## R4. Prisma 조인 성능 문제, N개 쿼리를 단일 쿼리로 (경험형)

- **의도**: ORM이 만드는 SQL을 직접 확인하는지.
- **핵심 답변**: 관계 포함 조회에서 SQL이 예상보다 많이 나가는 것을 로그와 요청 추적으로 확인했다. 당시 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했다. `relationJoins` 기능을 켜고 `relationLoadStrategy: 'join'`을 적용했으며, MySQL에서는 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는 것을 실행 계획으로 확인했다. 옵션 이름만 보고 SQL JOIN이라고 가정하지 않았다. 이력서의 API 응답 90% 향상은 이 경로의 결과다.
- **한계**: 조인 전략은 호출 수를 줄이지만 반환 데이터 중복과 DB 집계 비용을 늘릴 수 있다. 버전에 따라 동작이 다르므로 같은 환경에서 SQL 로그와 실행 계획을 본다.
- **꼬리**: 전통적 lazy loading N+1과 같은 현상인가(아니다, 당시 설정의 쿼리 분할 방식이었다). 대부분의 CRUD는 ORM을 유지하고 문제가 된 경로만 명시적 쿼리로 낮춘다.
- **출처**: [Prisma relation queries](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries). 하코 커뮤니티 발표 주제와 같다.

## R5. 단일 NGINX에서 CloudFront, ELB, ECS로 전환하고 Read Replica 도입 (설계형)

- **의도**: 인프라 전환 판단과 복제 지연 이해.
- **답변 골격**: 트래픽 증가로 단일 서버가 단일 장애점이 됨 → 정적 자원은 CloudFront, 앱은 ELB 뒤 ECS(Fargate) 태스크로 수평 확장 → 읽기 부하는 RDS Read Replica로 분산(이력서 기준 응답속도 40% 개선).
- **판단 기준**: 쓰기와 쓰기 직후 읽기는 primary, 지연을 허용하는 조회만 replica. 로드밸런서 선택은 프로토콜과 고정 endpoint 같은 호환성 요구가 좌우한다. 웹 요청과 기기 통신을 같은 방식으로 단정하지 않는다.
- **꼬리**: 결제 직후 잔액 조회를 replica에서 읽으면 복제 지연으로 이전 잔액이 보일 수 있다. 그래서 결제와 잔액은 primary로 고정한다. 다중 가용 영역은 리전 장애를 해결하지 않는다.
- **바로 연결**: 키오스크 통신이 어떤 프로토콜과 endpoint를 쓰는지 먼저 확인해야 같은 판단을 할 수 있다.

## R6. Grafana, Prometheus, Loki 관측 체계와 실시간 장애 알림 (경험형)

- **의도**: 로그, 메트릭, 알림의 역할 구분과 라벨 카디널리티 이해.
- **핵심 답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼다. 지연은 histogram으로 봤다. 메트릭은 추세와 사용자 영향, 로그는 개별 원인을 찾는 데 쓴다. Grafana Alerting으로 병목 구간을 조기 탐지했다.
- **흔한 오답**: 사용자 ID나 요청 ID를 메트릭 라벨에 넣는 설계. 본인이 실제로 겪은 실수라서 라벨 설계 기준을 먼저 말한다.
- **한계**: 경보 기준은 과거 숫자를 복사하지 않고 사용자 영향 SLI와 정상 구간을 관찰해 정한다. 당시 경보는 임계값 기반이었고 SLO burn-rate 경보는 아니었다.
- **바로 연결**: 결제 성공률, PG 응답 코드 분포, 결과 불명확 건 수, 키오스크 heartbeat 누락 수를 첫 대시보드로 제안한다.
- **출처**: [Prometheus naming and labels](https://prometheus.io/docs/practices/naming/)

## R7. Docker 멀티스테이지로 이미지 909MB에서 513MB, 배포 3분 10초에서 2분 20초 (경험형)

- **핵심 답변**: 빌드 도구와 실행 의존성을 분리해 빌드 산출물과 운영 의존성만 실행 이미지에 넣었다. 수치는 이력서 값이며 결과보다 재현 가능한 배포, 롤백, 종료 절차를 더 중요하게 봤다.
- **꼬리**: alpine은 native 모듈의 libc 호환성, distroless는 디버깅 어려움이 트레이드오프다. 컨테이너 종료 신호를 받으면 새 요청을 막고 진행 중 요청을 정리해야 결제 요청이 중간에 끊기지 않는다.
- **바로 연결**: 롤백은 이미지 digest로 직전 정상 버전을 다시 지정하는 일이어야 한다. 태그만 믿으면 다른 코드가 뜰 수 있다.

## R8. IoT 배터리 부족, 통신 지연 주기 집계와 알림톡, 이메일 자동 통보 (설계형)

- **의도**: 주기 작업의 중복 실행, 부분 실패, 알림 중복을 다뤘는지. 키오스크 상태 관측과 멤버십 정기 청구에 그대로 이어진다.
- **답변 골격**: 주기 집계(@nestjs/schedule)와 발송 작업(@nestjs/bullmq)을 분리 → 집계 결과를 저장한 뒤 채널별 발송은 큐로 → 발송 실패는 채널별 재시도와 격리.
- **판단 기준**: @nestjs/schedule의 cron은 프로세스마다 돈다. 인스턴스가 여럿이면 DB lease나 큐의 단일 작업 ID로 한 번만 실행되게 하고, 그래도 결과 단위 유일 키로 중복 효과를 막는다. 알림은 사건 ID와 채널을 함께 유일하게 두면 로컬 중복을 막지만, 외부 발송사가 수락한 뒤 응답 전에 끊긴 중복은 발송사 멱등 키나 조회로 닫는다.
- **한계**: [사용자 확인 필요] 당시 다중 인스턴스 중복 실행 방지를 실제로 어떻게 했는지. 모르면 지금의 설계 기준으로 답하고 당시 구현과 구분한다.
- **출처**: [NestJS Task Scheduling](https://docs.nestjs.com/techniques/task-scheduling), [NestJS Queues](https://docs.nestjs.com/techniques/queues)

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- **의도**: AI 도구를 실제로 만들어 검증해 봤는지, 검색 품질을 감이 아니라 평가 세트로 비교하는 사람인지 본다.
- **답변**: 개인 프로젝트로, 개발 지식 Markdown을 근거 관계 그래프로 색인하고 그 검색을 MCP 도구와 CLI로 제공하는 시스템이다. Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했다. 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정하고, 응답 크기 예산 안에 그 근거가 모두 나와야 통과로 쳤다. 무관한 질문에는 빈 결과가 나와야 통과하는 음성 질문도 넣었다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃었다. 74개를 포함한 94개 질문으로 bge 리랭커도 비교했지만 통과가 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸다. 그래서 모두 채택하지 않았고, 이후 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 비용과 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다. 새 방식을 측정으로 기각한 판단이 강점이다.
- **꼬리, 골든 케이스 선정**: 원문을 보고 만든 합성 질문이 대부분이고 사람이 정답을 검수한 표본은 아니다. 양성은 필수 근거 그룹이 응답 크기 예산 안에 모두 나오면 통과, 음성은 빈 결과여야 통과다.
- **꼬리, 지표**: 통과 개수와 후보 50개 안의 필수 근거 수를 봤다. 순위 가중 지표는 쓰지 않았다.
