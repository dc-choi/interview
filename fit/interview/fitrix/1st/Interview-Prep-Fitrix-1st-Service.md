# 피트릭스 1차, 서비스 맥락 질문 6

> [[Interview-Prep-Fitrix-1st|메인]]으로 돌아가기. 공개된 사실은 JD와 원티드 기업 소개, 2025-04 보도에 있는 범위뿐이다. 측정 기기와 서버의 연동 방식, 데이터 스키마, 저장 위치, 트래픽 규모, 현재 Azure 구성은 미확인이다. 아래 답변은 모두 가정을 밝힌 설계 골격이며, 면접에서는 가정부터 확인하고 시작한다.

## 공개 사실 요약

- OUTBODY는 비접촉 측정으로 자세와 신체 상태를 분석하고, 결과를 운동, 건강관리, 사후 코칭으로 잇는다. (JD)
- 제품은 검사와 해석 솔루션(FX), 데이터 통합 관리 웹과 앱(STUDIO), 개인 맞춤형 분석 앱(MOBILE)으로 소개된다. (원티드 기업 소개)
- 사용 현장은 피트니스 센터, 필라테스 스튜디오, 기업 건강관리, 검진센터, 병원이다. (JD, 원티드 기업 소개)
- 2025-04 보도는 자세, 유연성, 근력, 민첩성, 밸런스와 체성분 인자 등 100여 개 항목을 2분 만에 측정해 3D 데이터로 제공한다고 전했다. (한국경제)
- 해외에서도 서비스되며, 기업 소개는 국내와 일본 시장을 언급한다. (JD, 원티드 기업 소개)

## S1. OUTBODY의 신체 측정 데이터를 담을 DB 구조를 설계한다면 (설계형)

- 의도: JD 주요업무 3번. 데이터 구조 판단과 트레이드오프.
- 먼저 확인할 가정: 측정 항목이 버전마다 바뀌는지, 원시 측정값과 분석 결과 중 무엇을 서버가 계산하는지, 3D 데이터의 크기와 조회 빈도, 사업장과 회원 관계가 일대다인지 다대다인지.
- 답변 골격:
  1. 핵심 엔터티를 사업장, 회원, 측정 세션, 측정 결과로 나눈다. 측정 세션에는 기기 식별자, 측정 시각(UTC 저장, 표시 시간대 별도), 사업장, 분석 버전을 남긴다.
  2. 측정 결과는 수정하지 않는 이력으로 쌓는다. 재분석이나 정정은 새 버전으로 추가하고 어떤 버전이 유효한지 표시한다. 건강 관련 결과가 조용히 덮어써지면 코칭 근거를 설명할 수 없다.
  3. 원시값과 파생 지표를 구분한다. 분석 알고리즘이 바뀌면 파생값을 다시 계산할 수 있어야 하므로 계산에 쓴 버전을 함께 저장한다.
  4. 3D 데이터 같은 큰 산출물은 객체 저장소에 두고 DB에는 위치, 해시, 메타데이터만 둔다.
  5. 조회 패턴에 맞춰 인덱스를 둔다. 회원별 최신 결과와 기간 추이는 `(member_id, measured_at DESC)` 형태가 기본 후보다.
- 대안과 트레이드오프: 항목별 컬럼을 둔 넓은 테이블은 조회와 제약이 명확하지만 항목 추가마다 스키마 변경이 필요하다. 항목과 값을 행으로 두는 구조는 유연하지만 조회와 타입 검증이 어렵다. MySQL JSON 컬럼은 유연성과 검증 사이의 중간이며, 자주 거르는 항목은 생성 컬럼과 인덱스로 뺀다. 핵심 지표는 컬럼, 가변 항목은 JSON처럼 섞는 선택지를 실제 조회 패턴으로 결정한다.
- 경험 연결: 시솔지주에서 영양정보 데이터를 MongoDB에서 MySQL로 정형화했고, 트라이포드랩에서 업무 키별 최신 상태 조회를 복합 인덱스로 개선했다.
- 꼬리: 측정 항목이 국가별로 다르면(항목 정의 테이블과 버전), 수억 건 이력에서 추이 조회가 느려지면(요약 테이블, 기간 파티셔닝, 커서 페이지네이션).

## S2. 현장 기기에서 측정 결과 업로드가 실패하거나 중복되면 (설계형)

- 의도: 기기 입력 신뢰성. 트라이포드랩 IoT 경험과 가장 가까운 질문.
- 가정 확인: 기기가 직접 서버를 호출하는지, 로컬 앱을 거치는지, 오프라인에서 측정이 가능한지.
- 답변 골격: 측정 시점에 기기 쪽에서 고유한 측정 식별자를 만들고 서버는 그 값에 유일 제약을 둔다. 재시도는 같은 식별자로 보내므로 중복 저장 없이 이전 결과를 돌려준다. 네트워크가 끊기면 기기 쪽에 보관 뒤 지수 백오프와 지터로 재전송한다. 서버는 수신 확정과 무거운 후처리(리포트 생성, 알림)를 나눠 후처리는 큐로 비동기 처리하고, 실패는 DLQ와 재처리 경로를 둔다.
- 관측: 기기별 마지막 수신 시각, 업로드 실패율, 처리 지연을 본다. 트라이포드랩에서 IoT 하드웨어의 배터리 부족과 통신 지연을 주기적으로 집계해 알림톡과 이메일로 자동 통보하는 리포트를 만든 경험을 연결한다.
- 트레이드오프: 기기 쪽 보관은 유실을 줄이지만 기기 저장 공간과 시간 동기화 문제가 생긴다. 서버 시각과 기기 시각을 모두 남긴다.
- 꼬리: 같은 회원을 두 기기가 동시에 측정하면, 펌웨어 버전이 섞여 있으면(요청에 버전을 싣고 서버가 호환 범위를 검증).

## S3. 사업장, 트레이너, 회원 사이의 권한과 데이터 격리 (설계형)

- 의도: 여러 사업장이 한 플랫폼을 쓰는 구조에서 데이터가 섞이지 않게 하는 기준.
- 답변 골격: 모든 조회와 변경에 사업장 범위를 강제한다. 개별 쿼리마다 조건을 붙이는 방식은 누락 위험이 크므로 저장소 계층이나 미들웨어에서 공통으로 주입하고, 테스트로 다른 사업장 데이터가 보이지 않는지 검증한다. 회원이 여러 사업장을 오가거나 개인 앱으로 자기 데이터를 볼 수 있다면, 데이터의 소유자와 열람 권한을 분리하고 공유는 동의 기록을 근거로 한다.
- 대안: 사업장별 DB 분리는 격리가 강하지만 운영 비용이 크다. 공유 스키마에 사업장 키를 두는 방식은 효율적이지만 접근 제어를 코드와 테스트로 지켜야 한다. 대형 고객의 격리 요구가 있을 때만 분리를 검토한다.
- 경험 연결: 개인 출석 관리 서비스를 운영하며 여러 조직의 권한 경계, 이력 보존, 데이터 복구를 설계하고 검증했다. 수치는 말하지 않고 설계와 운영 결론만 말한다.
- 꼬리: 트레이너가 퇴사하면 그가 만든 코칭 기록은 누구 소유인가(사업장 소유, 작성자 이력은 보존).

## S4. 건강 관련 데이터를 다룰 때 보안과 데이터 관리 원칙 (설계형)

- 의도: JD 자격요건의 성능, 안정성, 보안, 데이터 관리 원칙.
- 법적 전제: 개인정보 보호법 제23조는 건강에 관한 정보를 민감정보로 규정하고, 별도 동의나 법령 근거가 있을 때만 처리하며 안전성 확보 조치를 요구한다. OUTBODY의 어떤 측정값이 여기에 해당하는지는 법적 판단이므로 단정하지 않고 회사의 기준을 확인한다.
- 답변 골격: 최소 수집, 전송과 저장 암호화, 역할 기반 접근 통제, 민감 데이터 열람과 변경의 감사 로그, 로그와 오류 메시지에 측정값과 식별자를 싣지 않기, 분석과 개발 환경에는 가명 처리된 데이터, 보존 기간과 파기 절차, 비밀값은 코드와 이미지 밖(Azure라면 Key Vault와 Managed Identity 후보).
- 경험 연결: FIDO 서버 개발에서 WebAuthn 명세를 분석해 인증을 설계했고, 규격을 지키지 않는 오픈소스 동작을 이슈로 제기했다. 보안은 라이브러리를 믿는 것이 아니라 명세와 재현으로 검증한다는 기준을 얻었다.
- 꼬리: 운영자가 장애 대응 중 회원 데이터를 봐야 하면(최소 권한, 기간 제한 권한, 열람 기록).

## S5. 해외 시장 확장에 백엔드는 무엇을 준비해야 하나 (설계형)

- 의도: JD의 해외 서비스와 확장 언급. 확장 단계의 설계 판단.
- 답변 골격: 시간은 UTC로 저장하고 표시만 현지화한다. 단위와 언어는 코드 값과 번역을 분리한다. 국가별로 다른 측정 항목이나 정책은 설정과 버전으로 관리한다. 데이터를 어느 리전에 둘지, 국가 간 이전이 허용되는지는 규제 확인이 먼저이며, 리전을 나누면 배포, 마이그레이션, 관측을 리전 단위로 반복할 수 있게 자동화한다.
- 한계: 일본을 포함한 국가별 개인정보 규제의 세부는 모른다고 말하고, 법무 기준을 받아 설계에 반영하겠다고 답한다.
- 꼬리: 한 리전 장애가 다른 국가 서비스에 번지지 않게 하려면(리전별 독립 배포와 데이터 경계, 공유 의존성 최소화).

## S6. 사업장 대시보드처럼 많은 측정 이력을 집계하는 화면이 느려지면 (설계형)

- 의도: OLTP 조회와 집계의 분리, 단계적 개선.
- 답변 골격: 실행 계획과 호출 경로로 병목부터 확인한다. 인덱스와 쿼리 구조, 페이지네이션을 먼저 고친다. 그래도 매 요청마다 대량 집계가 필요하면 측정 저장 시점이나 주기 작업으로 요약 테이블을 갱신하고, 지연을 허용하는 조회는 읽기 복제본으로 보낸다. 요약값에는 기준 시각을 함께 보여준다.
- 트레이드오프: 요약 테이블은 조회를 빠르게 하지만 갱신 누락과 재계산 경로가 필요하다. 읽기 복제본은 복제 지연을 전제로 한다.
- 경험 연결: 복합 인덱스 최적화, Prisma 단일 쿼리 통합, Read Replica 도입, 주기 집계 리포트.
- 꼬리: 요약값과 원본이 어긋나면(원본이 기준, 주기적 대사와 재계산 작업).
