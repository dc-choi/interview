# 피트릭스 1차, 이력서 기반 기술 질문 9

> [[Interview-Prep-Fitrix-1st|메인]]으로 돌아가기. [[My-Tech-Cards]] 8개 카드를 fork했다. 수치는 공개 이력서에 있는 값만 쓰고, 측정 조건을 설명할 수 없으면 정성 표현으로 낮춘다. 이전 직장의 내부 지표, 임계값, 고객 정보는 말하지 않는다. 답변은 결론, 선택 이유와 대안, 검증, 한계, 피트릭스 연결 순서다.

## R1. 수천 대 IoT 하드웨어 동시 요청의 Race Condition을 어떻게 해결했나 (경험형)

- 의도: 동시성 원인 분석과 잠금 전략 선택의 근거, 한계 인식.
- 핵심 답변: 같은 재고 상태를 여러 기기 입력이 동시에 바꾸던 경로에서 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한 재시도를 조합했다. 충돌이 잦은 갱신은 낙관적 잠금이면 늦게 충돌을 발견해 작업 전체를 다시 해야 하므로 비관적 잠금이 단순했다. 외부 호출과 독립 검증은 트랜잭션 밖으로 빼고, 잠금 읽기 뒤 불변식을 다시 검증했다. 여러 대상을 갱신할 때는 업무 키 순서를 통일했다. 동시 요청을 재현해 최종 수량, 잠금 실패, 재시도 뒤 상태를 확인했다.
- 대안과 트레이드오프: 충돌이 드문 편집은 버전 컬럼 조건부 갱신이 낫다. 보호 대상이 한 DB 트랜잭션 안에 있어 분산 잠금은 쓰지 않았다. 급격한 유입 자체를 흡수해야 하면 업무 키별 순서 큐와 워커 동시성 제한을 함께 본다. 잠금은 유입량을 흡수하지 못한다.
- 한계: 당시 재시도는 짧은 고정 간격이었다. 다시 한다면 지수 백오프와 지터를 검증한다. `NOWAIT`는 잠금 읽기의 행 잠금 대기만 없애고 메타데이터 잠금 대기는 남는다.
- 꼬리: NOWAIT와 SKIP LOCKED 차이(특정 행을 반드시 처리해야 하면 NOWAIT, 큐처럼 다음 행을 가져가도 되면 SKIP LOCKED), 데드락 분석(`SHOW ENGINE INNODB STATUS`의 최근 데드락 섹션), 락 순서가 데드락을 완전히 막지는 못하는 이유.
- 끝줄: 여러 측정 기기와 사업장이 같은 회원 데이터를 동시에 갱신할 수 있다면, 어떤 갱신이 경합하는지부터 확인하고 잠금이 필요한 경로를 최소화하겠습니다.

## R2. 발주 자동화를 EventBridge와 SQS로 설계한 이유 (경험형, 설계형)

- 의도: 기술 선택 기준, 전달 보장과 멱등성 이해, 적용하지 못한 개선안의 정직성.
- 핵심 답변: 상태 변경 뒤의 후속 처리를 이벤트로 분리해 느린 의존성이 핵심 상태 변경을 실패시키지 않게 했다. 소비자는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 영구 오류는 격리, 일시 오류만 제한 재시도, 예산을 넘으면 DLQ와 수동 확인으로 보냈다. Kafka는 조직의 운영 여력과 필요한 전달 보장을 비교해 도입하지 않고 관리형 큐를 골랐다.
- 한계: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 전에 프로세스가 죽으면 이벤트가 누락될 수 있었고, 발행 재시도와 운영 확인으로 다뤘다. 다시 설계하면 상태 변경과 outbox 행을 같은 트랜잭션에 저장하고 릴레이가 발행한다. 그래도 중복은 가능하므로 정확히 한 번이라고 말하지 않는다.
- 대안: replay, 장기 보존, 키 단위 순서, 독립 소비자 그룹이 필요하고 측정된 처리량에서 큐가 병목이면 Kafka를 다시 비교한다. 짧고 독립적인 작업은 서버리스 소비자도 적합하다.
- 꼬리: at-least-once에서 중복을 어디서 막나, 순서가 중요하면 FIFO와 그룹 키, DLQ 적체는 무엇으로 감지하나(가장 오래된 메시지 대기 시간).
- 끝줄: 측정 결과 저장 뒤 리포트 생성이나 알림 같은 후속 처리를 분리해야 한다면 같은 기준을 쓰고, Azure에서는 Service Bus의 DLQ와 세션 기능을 같은 판단 축으로 비교하겠습니다.

## R3. 복합 인덱스로 슬로우 쿼리 99.3% 개선 (경험형)

- 의도: 실행 계획을 읽고 인덱스를 설계하는 근거, 수치의 측정 조건.
- 핵심 답변: 업무 키별 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 큰 것을 `EXPLAIN ANALYZE`로 확인했다. 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 설계하고, 인덱스가 정렬과 상위 레코드 접근에 실제로 쓰이는지 실행 계획으로 재확인했다.
- 측정 경계: 99.3%는 이력서 수치다. 어떤 쿼리를 같은 환경과 캐시 조건에서 비교했는지 [사용자 확정 필요]. 설명할 수 없으면 조회 지연을 크게 줄였다는 정성 표현과 검증 방법만 말한다.
- 트레이드오프: 인덱스는 쓰기와 저장 비용을 늘린다. 컬럼 순서는 카디널리티 하나가 아니라 동등 조건, 범위 조건, 정렬, 반환 컬럼으로 정한다.
- 꼬리: EXPLAIN의 type, rows, filtered, Extra(Using filesort, Using index) 읽는 법, 커버링 인덱스, OFFSET 대신 커서 페이지네이션.
- 끝줄: 회원별 측정 이력의 최신값과 기간 조회가 핵심이라면 같은 패턴이 그대로 적용될 수 있어, 실제 쿼리부터 실행 계획으로 확인하겠습니다.

## R4. Prisma N개 쿼리를 단일 쿼리로 통합해 응답속도 90% 향상 (경험형)

- 의도: ORM이 만든 SQL을 직접 확인하는 습관, 옵션 이름으로 단정하지 않는지.
- 핵심 답변: 관계 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했다. 당시 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했다. `relationJoins` 기능을 켜고 `relationLoadStrategy: 'join'`을 적용해, MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했다. 성능이 중요한 경로만 바꾸고 나머지는 타입 안정성을 유지했다. 이 내용은 하코 커뮤니티에서 발표했다.
- 흔한 오답: 옵션 이름만 보고 SQL JOIN이 나간다고 단정하는 것. 전통적인 lazy loading N+1과 같은 현상이라고 단정하는 것.
- 트레이드오프: 호출 수는 줄지만 반환 데이터 중복, 집계 비용, DB 부하를 함께 본다. 동작은 Prisma 버전과 설정에 따라 다르다.
- 꼬리: ORM을 버리고 raw SQL로 가는 기준(윈도우 함수, 대량 연산, 부적절한 생성 SQL 경로만), Koa나 Express 환경에서 어떤 ORM을 쓰든 같은 검증을 하는가.
- 끝줄: 공고의 DB 최적화도 도구보다 실제 생성 SQL과 실행 계획으로 판단하겠습니다.

## R5. Grafana, Prometheus, Loki 기반 모니터링과 경보 구축 (경험형)

- 의도: 관측 설계 원칙, 카디널리티, 경보 피로 이해. JD 주요업무와 우대 직결.
- 핵심 답변: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었다. 식별자를 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼다. 지연은 histogram으로 봤다. 메트릭은 추세와 사용자 영향, 로그는 개별 원인, 트레이스는 서비스 경계를 넘는 흐름을 보는 조합으로 설계했다. Grafana Alerting으로 실시간 장애 알림을 만들고 경보 정책을 정했다.
- 판단: 직접 겪은 실수라서 라벨 설계 기준을 먼저 말한다. 요청 ID 같은 고유값은 라벨로 넣으면 시계열이 폭증하므로 로그와 trace context에 둔다. SaaS, 클라우드 기본 도구, 자체 운영 스택은 비용 하나가 아니라 보존, 운영 부담, 요구를 함께 비교했다.
- 한계: 경보 기준은 과거 숫자를 복사하지 않고 사용자 영향 지표와 정상 구간을 보고 합의한다. SLO burn-rate 경보는 적용했다고 말하지 않는다.
- 꼬리: RED와 USE, 알림 피로를 줄이는 방법, 장애 시 첫 10분에 하는 일(영향 범위 공유, 복구 우선, 이후 포스트모템).
- 끝줄: Azure 환경이라면 Azure Monitor와 Application Insights를 쓸지 기존 오픈소스 스택을 둘지부터 같은 기준으로 비교하겠습니다.

## R6. 단일 NGINX 서버에서 CloudFront, ELB, ECS(Fargate)로 전환하고 Read Replica 도입 (경험형, 설계형)

- 의도: 인프라 전환의 이유와 단계, 복제 지연 이해.
- 핵심 답변: 트래픽 증가에 따라 단일 서버 구조를 CDN, 로드밸런서, 관리형 컨테이너 실행 환경으로 옮겼다. 쓰기와 쓰기 직후 읽기는 primary로 보내고, 지연을 허용하는 조회만 Read Replica로 보내 읽기 부하를 나눴다(이력서 기준 응답속도 40% 개선, 측정 조건은 [사용자 확정 필요]).
- 판단: 관리형 태스크 환경과 Kubernetes는 운영 인력, 배포 복잡도, 복구 요구로 골랐다. Rolling은 자원 부담이 낮고 Blue/Green은 빠른 롤백에 유리하다.
- 꼬리: 복제 지연 때문에 방금 저장한 값이 안 보이면(read-after-write는 primary로 고정), 자동 확장 기준(큐 작업은 backlog와 가장 오래된 메시지 대기), 종료 신호 처리.
- 끝줄: 측정 직후 결과 화면처럼 쓰기 직후 읽기가 중요한 흐름은 primary 라우팅을 먼저 확인하겠습니다.

## R7. Docker 멀티스테이지 빌드와 Jenkins CI/CD로 배포 개선 (경험형)

- 의도: CI/CD 개선의 근거와 재현 가능성. JD 주요업무 8번과 우대 직결.
- 핵심 답변: 빌드 도구와 실행 의존성을 분리해 이미지 크기를 909MB에서 513MB로, 배포 시간을 3분 10초에서 2분 20초로 줄였다(이력서). 설정 주입은 이미지와 분리했다. 시솔지주에서는 Jenkins 기반 CI/CD 파이프라인을 구축해 배포 속도를 50% 단축했다(이력서, 비교 기준 [사용자 확정 필요]).
- 대안: alpine은 작지만 네이티브 모듈 호환성, distroless는 디버깅 어려움, 번들링은 외부화한 의존성 확인이 필요하다.
- 꼬리: 테스트를 파이프라인 어디에 두나, 배포 실패 시 롤백, 비밀값 관리(이미지와 코드에서 분리, 최소 권한 저장소).
- 끝줄: 피트릭스의 테스트, CI/CD 개선도 배포 시간과 실패 복구 시간을 먼저 재고 병목 단계부터 줄이겠습니다.

## R8. 잦은 요구사항 변경을 모듈 중심 아키텍처로 수용 (설계형)

- 의도: 클린 아키텍처 우대, 추상화의 적정선.
- 핵심 답변: NestJS에서 Controller, UseCase, Domain, Repository port, 인프라 구현을 나누고 의존 방향을 도메인 쪽으로 모았다. 사용자 의도가 다른 경로는 UseCase를 나눴다. 도메인 규칙은 프레임워크 없이 테스트할 수 있게 했다.
- 판단 기준: 실제로 교체되거나 독립적으로 바뀌는 경계에만 추상화를 둔다. 구현이 하나인데 인터페이스부터 만들지 않는다.
- 꼬리: 순환 참조가 반복되면 모듈 책임을 다시 나눈다. Koa나 Express처럼 DI 컨테이너가 없는 환경에서는 생성자 주입과 조립 지점을 명시적으로 둔다.
- 끝줄: 해외 확장으로 국가별 요구가 달라질 부분이 있다면 그 경계부터 모듈로 분리하겠습니다.

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- 의도: JD의 AI 개발 도구 활용과 생성 결과의 품질 판단을 실제로 해 봤는지 본다. 공고에 LLM 기능 개발 요건은 없으므로 AI 도구 활용 근거로 짧게 쓴다.
- 답변: 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템입니다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색은 MCP 도구와 CLI로 노출했습니다. 검색 방식을 바꾸기 전에 평가 질문부터 고정했고, 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정해 응답 크기 예산 안에 모두 나와야 통과로 쳤습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어 채택하지 않았습니다. 74개를 포함한 94개 질문으로 bge 리랭커도 비교했지만 통과가 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸려 채택하지 않았습니다. 이후 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- 판단 기준: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃거나 지연만 늘면 새 방식을 채택하지 않는다. 도입하지 않기로 한 판단도 측정으로 근거를 남긴다.
- 꼬리: 평가 질문은 어떻게 만들었나, 어떤 지표로 비교했나 → 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본은 아니다. 양성 질문은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나와야 통과, 음성 질문은 빈 결과여야 통과다. 지표는 통과 수와 후보 50개 안의 필수 근거 수, 질문당 추가 지연이다.
- 한계를 먼저 말할 것: 합성 표본이라 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- 이력서 정정: 이력서에는 골든 케이스 약 145건으로 비교했다고 적혀 있지만 145건짜리 평가 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- 이 회사 공고와의 연결: 주요업무 9번 AI 개발 도구 활용과 생성 코드 품질 판단의 근거다. 도구가 낸 결과를 평가 세트로 검증하는 습관으로 말하고, LLM 서비스 운영 경험처럼 말하지 않는다.
