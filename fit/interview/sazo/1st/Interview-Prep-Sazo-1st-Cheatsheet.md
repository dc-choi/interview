## 0. 면접장 들어가기 전 3원칙

1. **역질문은 마지막에 몰기** — 질문 기회가 올 때까지 답변에 집중한다.
2. **모든 답변 끝줄 = 사줘의 구매대행 파이프라인/성장 구간으로 연결.**
3. **갭은 인정 → 전이 → 흡수 3단, 우기지 말 것.** 답변은 핵심부터 짧게 말한다.

## 1. 오프닝 (이건 거의 그대로)

**자기소개 첫 문장**: "안녕하세요, 백엔드 개발자 [이름]입니다."
→ 동시 상태 갱신, 비동기 처리, 관측과 외부 연동을 다루는 역량 → **"빠르게보다 운영에서 안 깨지는 구조, 실패 전제 재시도와 복구 경로 설계를 중시합니다."**

**자기소개 끝줄(앵커)**: 사줘의 URL 파싱, 가격 확정, 구매와 국제배송 흐름은 외부 연동, 상태 정합성과 재처리 문제를 다루는 백엔드 역량이 직접 연결되는 영역이다.

## 2. FIT 답변 키워드 (입으로 나오는지 체크)

| 질문 | 트리거 키워드 (끝줄은 항상 사줘 연결) |
|---|---|
| **왜 사줘 (3축)** | ① 국제 배송, 환율, 통관과 추적 경험의 전이 ② 파서 안정화와 재고 경쟁처럼 측정 가능한 문제 ③ AI를 팀 워크플로우로 쓰는 방식 |
| **이직 사유** | 넓은 범위를 책임진 경험 다음에는 한 제품을 동료와 깊게 개선하고 싶다는 방향으로 설명한다. 외부 귀책은 피한다. |
| **잦은 이직 꼬리** | 각 자리에서 도메인 이해, 운영 품질, 자동화와 주도성을 차례로 쌓았고, 다음 역할에서는 장기적으로 깊이를 만들고 싶다고 설명한다. |
| **임팩트 있던 일** | 반복되는 후속 업무를 자동화할 때 실패 격리와 복구 경로를 함께 설계하는 판단을 정성적으로 설명한다. 구체적 비용이나 이전 조건은 공개 문서에 넣지 않는다. |
| **AI 보조 도구** | 반복 작업을 보조하지만, 설계와 의사결정의 근거는 직접 설명한다. |
| **협업/비개발 소통** | 의도 먼저 묻고 재확인, 상대 언어로. |
| **사이드 프로젝트** | 교육 도메인 멀티테넌트 서비스에서 고려한 격리, 권한과 운영 판단을 설명한다. 누적 사용량과 활성 사용량은 구분하되, 공개 노트에는 세부 사용량과 기준일을 남기지 않는다. |
| **워라밸/강도** | 의미 있으면 투자 OK + 지속가능성은 역질문으로 마이크 넘김. (부정단어 먼저 꺼내지 말 것) |
| **5년 후** | Staff 트랙, 권한 아닌 영향력. |

## 3. 기술 갭 3종 (1차에도 "Kafka 안 써봤는데?" 가능 — 인정→전이→흡수)

- **Kafka**: 클러스터 운영 경험은 과장하지 않는다. at-least-once 중복, 멱등 소비자, DLQ와 키 단위 순서처럼 큐와 스트림에 공통인 전달 보장 원칙을 설명한다. 사줘의 공개 성장 배수, 백프레셔와 다단계 소비는 Kafka 검토 신호일 뿐 정답의 근거는 아니다. 지속, 피크 이벤트 처리량과 현재 병목을 측정하고 replay, retention, 키 순서, 독립 consumer group, 운영 비용 요구가 확인될 때 선택한다.
- **Elasticsearch**: 운영 X. but **왜 RDB가 한계인지** 실무 체감(LIKE 선행 와일드카드 풀스캔 → 역색인). B-Tree 내부 아는 상태라 자료구조만 다름. 입사 후 mapping/analyzer + MySQL 동기화(CDC/배치)부터 파악. (kuromoji+nori 다국어 = 사줘 직격, 개념 언급 가치)
- **MSA**: 물리 분리 경험은 과장하지 않는다. 모놀리스에서도 **경계 긋기**(공유 테이블 최소화, 이벤트와 포트 통신, 계층 분리)를 먼저 적용하며, 물리 분리는 독립 배포와 운영 요구가 확인된 뒤 검토한다.
- **스크래핑**: 여러 제공자의 추적 정보를 API와 스크래핑으로 통합할 때는 어댑터 패턴과 변경 감지가 필요하다. 본질은 성공 응답처럼 보이지만 내용이 틀리는 실패를 잡는 것이므로, 모니터링과 스키마 검증을 함께 둔다.
- **PG/TypeORM**: 최적화 방법론 DB 중립(EXPLAIN, 카디널리티 복합인덱스, 커버링). PG 차이(BUFFERS, BRIN/GIN, VACUUM bloat) 정리됨. **Go/gRPC 미경험 — 솔직**, 개념만(HTTP/2, Protobuf, 내부통신).

## 4. 도메인 멘트 — 2개만 입에 붙이기

1. **(깨짐 감지)** "스크래핑은 만드는 것보다 깨짐을 빨리 아는 게 본질. 사줘 파서도 결국 **소스별 성공률 모니터링 싸움**이라 봅니다."
2. **(환율 시점)** "외부 환율 정보를 정기 수집하고 재시도한 경험이 있어, 표시와 결제에 쓰는 기준 시점이 다를 수 있다는 점을 압니다. 가격 엔진은 환율 스냅샷을 주문에 어떻게 고정하느냐가 핵심입니다."

> 여유가 있으면 재고 경쟁 상황, 과세 조건, 양방향 물류처럼 공개 문서에서 확인한 도메인 질문을 추가한다. 실제 규칙은 팀의 최신 설명으로 확인한다.

## 5. 수치 사용 원칙

- 개인 프로젝트와 과거 고용주의 운영 수치는 공개 노트에 적지 않는다.
- 수치가 필요한 면접에서는 원본 근거, 기간, 비교 조건을 직접 확인한 뒤에만 말한다.
- 지원 회사의 공개 사실도 공식 공고나 사이트의 최신 내용을 다시 확인하고, 추정한 팀 규모나 성장 수치를 사실처럼 말하지 않는다.

## 6. 역질문 (마지막에 몰기, 5개 중 시간 맞춰)

1. **다음 단계 형식** — "이후 전형은? 기술 면접 형식(과제/라이브코딩/이력서 딥다이브)을 알 수 있을까요?" (절차 미공지라 정보가치 최대)
2. **팀 구성** — "백엔드는 몇 분이고, 테크리드 두 분과 어떤 구조로 일하나요?"
3. **AI 우선순위** — "백엔드 개발 사이클에서 AI는 어디까지 적용돼 있나요?"
4. **스택 확인** — "우대에 Go/gRPC, PG/TypeORM이 있던데 NestJS와 Go 역할 분담은?" (JD 정독 시그널)
5. (시간 남으면) **병목** — "현재 백엔드에서 가장 먼저 해결해야 할 병목 하나는 무엇인가요?"
> 아껴둘 것(다음 단계): 6개월 핵심 과제, MSA 분리 수준, 앱 평점 로드맵(운영 안정화로 포장).

## 7. 지뢰밭 (절대 밟지 말 것)

- ⚠️ **입사 시점** — 개인 일정과 다른 전형의 상태는 기록으로 보존한다. 실제 대화에서는 사실을 짧게 설명하고, 처우 금액이나 제3자 연락처는 말하지 않는다.
- ⚠️ **일본어** — 못함, 솔직. "일본 사이트 파싱은 언어보다 **구조 문제** + AI 번역 활용." 영어 문서는 가능.
- ⚠️ **외부 귀책 금지** — 회사 사정/비전 없음 X. 회사 평가 톤(안정적이라서) X. 자기 귀책 + 학습 + 현재 적용.
- ⚠️ **부정 단어**(워라밸, 연봉) 본인이 먼저 꺼내지 않기.
- ⚠️ **Kafka/ES 우기지 말 것** — 다음 단계에서 들통.
- ⚠️ 따옴표 강조, 과한 대구 없이 사람처럼 말하기.
