# 트렉시 1차 예상 질문, 이력서 기반과 컬처핏

> [[Interview-Prep-Trexi-1st|메인]], [[Interview-Prep-Trexi-1st-Tech|JD와 서비스 맥락 기술 질문]]. 답변은 [[My-Tech-Cards]]와 [[My-FIT-Answers]]를 fork했고 끝줄에 트렉시 공고와의 연결을 붙였다. 이력서 수치는 공개 이력서에 있는 값만 쓰고, 기준 기간과 측정 조건을 설명할 수 없으면 말하지 않는다. 운영 임계값, 고객, 내부 지표는 말하지 않는다.

## 이력서 기반 질문

### R1. 수천 대 IoT 기기의 동시 요청 Race Condition을 DB Lock으로 어떻게 풀었나

- **의도**: 잠금 방식을 선택한 근거와 한계를 아는가.
- **답변**: 충돌이 잦은 재고 갱신이라 낙관적 잠금으로 늦게 충돌을 발견하면 작업 전체를 다시 해야 했습니다. 그래서 `SELECT ... FOR UPDATE NOWAIT`와 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했습니다. 외부 호출과 입력 검증은 트랜잭션 밖에서 끝내고, 여러 대상을 갱신할 때는 업무 키 순서를 통일했습니다. 동시 요청을 재현해 최종 수량과 재시도 뒤 상태를 확인했습니다.
- **한계**: `NOWAIT`는 해당 잠금 읽기의 대기만 없앤다. 락 순서는 데드락 확률을 낮출 뿐 완전 예방이 아니다. 당시 고정 간격 재시도였고, 지금은 지수 백오프와 지터를 검증하겠다.
- **꼬리**: 분산 락은 왜 안 썼나 → 보호 대상이 한 DB 트랜잭션 안에 있었다. 여러 저장소를 한 임계 구역으로 묶어야 할 때만 검토한다. 충돌이 드문 편집은 버전 컬럼 조건부 갱신이 낫다.
- **트렉시 연결**: 견적 확정과 거래 상태 전이도 같은 거래를 두 사람이 동시에 바꿀 수 있는 지점이라, 충돌 빈도에 맞춰 잠금 방식을 고르겠습니다.
- **출처**: [MySQL 8.4, Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

### R2. EventBridge와 SQS로 발주 자동화를 어떻게 설계했고, Kafka는 왜 아니었나

- **답변**: 핵심 상태 변경을 먼저 확정한 뒤 후속 발주 작업을 EventBridge와 SQS로 넘겼습니다. 소비자는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 일시 오류만 제한 재시도하고 초과분은 DLQ와 수동 확인으로 보냈습니다. 조직의 운영 여력과 필요한 전달 보장을 비교해 관리형 큐를 골랐습니다.
- **한계를 먼저 말한다**: DB 커밋 뒤 발행 전에 프로세스가 멈추면 이벤트가 빠질 수 있었고, 당시 원자적으로 닫지 못했다. 지금은 상태 변경과 Outbox 기록을 같은 트랜잭션에 넣고 릴레이가 발행하게 하겠다.
- **꼬리**: 정확히 한 번 처리가 되나 → 주장하지 않는다. 전달은 최소 한 번이고 업무 키 단위 중복 제거로 결과를 한 번으로 만든다. Kafka 운영 경험은 없다.
- **트렉시 연결**: 공고의 SQS와 Lambda 스택에서 견적 확정 뒤 메일 발송이나 정산 생성 같은 후속 작업을 같은 방식으로 분리할 수 있습니다.

### R3. 복합 인덱스로 슬로우 쿼리를 99.3% 개선했다는데 어떻게 측정했나

- **답변**: 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했습니다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 인덱스를 만들고, 실제로 정렬과 상위 레코드 접근에 쓰이는지 실행 계획으로 다시 봤습니다.
- **측정 경계**: 99.3%는 해당 쿼리 1건의 전후 비교다. 전체 API나 배치 시간과 같은 지표로 섞지 않는다. 환경, 캐시 상태, 표본 수를 함께 말할 수 있을 때만 수치를 꺼낸다.
- **꼬리**: 인덱스 비용 → 쓰기와 저장 비용이 늘어 인접 쓰기 경로를 함께 본다. 컬럼 순서는 카디널리티 하나가 아니라 동등, 범위, 정렬 조건으로 정한다.
- **트렉시 연결**: 거래 추적 화면은 거래처별 최신 상태 조회가 많을 것으로 보이는데, 실제 조회 패턴은 입사 후 실행 계획으로 확인하겠습니다.

### R4. Prisma에서 N개 쿼리를 단일 쿼리로 통합해 API를 90% 개선한 과정

- **답변**: 관계 포함 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했습니다. 당시 설정에서는 include 관계가 여러 쿼리로 나뉘어 애플리케이션에서 결합됐고, `relationJoins` 기능을 켜고 `relationLoadStrategy: 'join'`을 적용해 MySQL에서 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했습니다.
- **흔한 오답**: 옵션 이름이 join이니 SQL JOIN이 나간다. 생성 SQL은 DB와 버전에 따라 다르므로 로그로 확인해야 한다.
- **꼬리**: ORM을 버리지 않은 이유 → 성능이 중요한 경로만 조정하고 나머지는 타입 안정성과 변경 용이성을 유지했다. 하코 커뮤니티에서 이 사례를 발표했다.
- **출처**: [Prisma, Relation queries](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries)

### R5. 단일 NGINX에서 CloudFront, ELB, ECS(Fargate)로 전환하고 Read Replica로 응답을 40% 개선한 판단

- **답변**: 관리형 컨테이너 환경으로 옮겨 배포와 확장을 재현 가능하게 만들었고, 읽기 부하는 Read Replica로 분산했습니다. 쓰기와 쓰기 직후 읽기는 primary로 보내고, 지연을 허용할 수 있는 조회만 replica로 보냈습니다.
- **꼬리**: 복제 지연으로 방금 저장한 값이 안 보이면 → 해당 흐름은 primary로 읽는다. Kubernetes는 왜 아니었나 → 운영 인력과 워크로드 수에 비해 관리형 태스크 환경이 부담이 적었다.
- **비용 관점 보강**: 공고가 비용 최적화를 요구한다. 비용 절감 수치는 이력서에 없으므로 말하지 않고, 자원 선택을 운영 인력과 사용 패턴으로 판단한다는 기준만 말한다.

### R6. CI/CD를 어떻게 구성했나 (Jenkins 50% 단축, 멀티스테이지 빌드)

- **답변**: 시솔지주에서 Jenkins 파이프라인을 구축해 배포 속도를 50% 줄였고, 트라이포드랩에서는 Docker 멀티스테이지 빌드로 이미지를 909MB에서 513MB로, 배포 시간을 3분 10초에서 2분 20초로 줄였습니다. 빌드 도구와 실행 의존성을 분리하고 설정 주입을 산출물과 분리했습니다.
- **꼬리**: alpine은 → 네이티브 모듈의 libc 호환성을 확인해야 한다. 롤백은 → 이전 이미지 태그로 재배포가 독립적으로 되는지 검증한다.
- **트렉시 연결**: Turborepo 모노레포라면 변경된 패키지만 빌드하는 캐시 전략이 파이프라인 시간을 좌우할 것 같습니다. 모노레포 운영 경험은 없어 입사 후 기존 설정부터 익히겠습니다.

### R7. Grafana, Prometheus, Loki 관측 체계를 어떻게 설계했나

- **답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었습니다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 것만 남겼습니다. 메트릭으로 영향을, 로그로 원인을 찾고 Grafana Alerting으로 알림을 만들었습니다.
- **판단 기준**: 사용자 ID나 요청 ID를 라벨에 넣는 설계는 제가 실제로 겪은 실수이고, 그래서 라벨 설계 기준(값이 제한된 차원만)을 먼저 말한다.
- **꼬리**: 경보 기준 → 과거 숫자를 복사하지 않고 사용자 영향과 정상 구간을 관찰해 정한다. 내부 임계값은 말하지 않는다.
- **트렉시 연결**: AI 추출 파이프라인이라면 오류율뿐 아니라 공급처별 검증 실패율과 검수 대기 적체를 같이 봐야 한다고 봅니다.

### R8. 팀 AI 협업 규약은 무엇이고 Claude를 어떻게 쓰나

- **답변 (FIT 10 fork)**: 경로별 `CLAUDE.md`로 문맥을 나누고, AI가 건드릴 영역과 건드리면 안 되는 영역을 명문화했습니다. 공식 문서 조회, 역할별 검토, 변경 파일 검사, 작업 종료 시점 품질 점검이 이어지도록 구성했습니다. 반복 구현과 조사는 맡기지만 요구사항 해석, 설계 선택, 결과 채택은 제가 책임집니다.
- **꼬리**: AI가 틀리면 → 테스트, 공식 문서, 실행 결과로 검증한다. 이것은 개발 과정의 AI 활용이고, 제품 안의 LLM 파이프라인 운영과는 다른 경험이라고 구분한다.
- **트렉시 연결**: 공고가 Claude 활용과 AI 파이프라인 고도화를 함께 요구하는데, 개발 과정에서 만든 검증 루프 감각을 추출 파이프라인의 품질 게이트로 옮길 수 있다고 봅니다.

### R9. 시솔지주에서 외부 데이터(번역, 환율, 배송 정보)를 어떻게 다뤘나

- **답변**: Google API 연동 번역 기능을 개선해 성능을 70% 높였고, 환율 배치와 배송 정보 스크래핑을 담당했습니다. 배치 오류가 늘었을 때 수동 확인에서 벗어나 오류를 영향과 원인 가설로 나누고, 중요한 경로부터 자동 검증과 배포 전 검사를 넣었습니다(FIT 12 fork).
- **꼬리**: 70%의 기준 → 측정 조건을 기억으로 말할 수 없으면 개선 방식만 설명한다. 지금 다시 만든다면 → 관측 지표, 재시도 정책, 테스트 게이트를 처음 설계에 넣는다.
- **트렉시 연결**: 외부 시장 데이터 수집과 공급처 데이터도 상대가 형식을 보장하지 않는 입력이라, 실패를 조용히 넘기지 않는 구조가 먼저라고 봅니다.

### R10. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- **의도**: 공고의 AI 파이프라인 품질과 Claude 활용을 실제로 해 봤는지 본다. 운영 LLM 파이프라인 경험이 없는 갭을 가장 직접 메우는 근거다.
- **답변**: 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템입니다. Markdown 위키링크와 frontmatter의 근거 관계로 그래프를 구성하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색은 MCP 도구와 CLI로 노출했습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했습니다. 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정하고, 응답 크기 예산 안에 그 근거가 모두 나와야 통과로 쳤습니다. 무관한 질문에는 빈 결과가 나와야 통과하는 음성 질문도 넣었습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, BM25와 E5 임베딩 결과를 RRF로 합친 방식을 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 늘지 않았고 기존 통과 사례 4개를 잃었습니다. 이 74개를 포함한 94개 질문으로 bge 리랭커도 붙여 봤지만 통과는 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸습니다. 그래서 채택하지 않았고, 문제가 후보 검색보다 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다. 새 방식을 측정으로 모두 기각한 것이 이 경험의 핵심이다.
- **꼬리**: 골든 케이스는 어떻게 만들었나, 어떤 지표로 비교했나 → 원문을 보고 만든 합성 질문에 필수 근거 그룹(문서, 절, 본문 문구)을 정했고, 양성은 그 근거가 응답 크기 예산 안에 모두 나오면 통과, 음성은 빈 결과여야 통과로 봤다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 쟀다. 순위 가중 지표(nDCG 등)는 쓰지 않았고 한계로 인정한다.
- **한계를 먼저 말할 것**: 평가 질문은 사람이 정답을 검수한 표본이 아니라 원문을 보고 만든 합성 질문이 대부분이다. 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약했다. 수치는 2026-09-08 로컬 1회 측정 기준이다.
- **이력서 정정**: 제출한 이력서에는 골든 케이스 약 145건으로 BM25, 임베딩, 리랭커를 비교했다고 적혀 있다. 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **트렉시 연결**: 공고의 프롬프트, 모델, 추출 로직의 버전 관리와 모델별 결과 비교는 고정된 평가 세트로 회귀를 재는 일과 같은 구조입니다([[Interview-Prep-Trexi-1st-Tech|Tech]] J1, J2). 제품 안의 LLM 파이프라인을 운영한 경험은 아니라고 구분해서 말한다.
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 먼저 개인 프로젝트라고 밝힌다.

## 컬처핏과 민감 질문

### C1. 왜 이직하나, 왜 지금인가 (2026-09-29 확정, 동기 마스터 현재 사이클 fork)

- **답변 (30초 안에 끝낸다)**:

> 올해 6월 말 합류해 검색과 데이터 수집을 맡았는데, 팀이 기대하는 일하는 방식과 제 방식의 차이를 수습 기간 안에 좁히지 못해 본채용으로 이어지지 않았습니다. 돌이켜 보면 완료 조건을 먼저 맞추지 않고 제 판단으로 진행했고, 검증 결과를 공유하는 것도 늦었습니다. 그 뒤로는 합류 초기에 기대하는 결과와 완료 기준부터 합의하고, 진행 상황을 근거와 함께 먼저 공유하는 것을 기본으로 삼고 있습니다.

- **이어서**: 해명을 덧붙이지 않고 트라이포드랩의 설계부터 운영까지 책임진 경험으로 넘어간다. 트렉시에서는 수습 기간의 기대 결과를 역질문 B1로 먼저 확인하겠다고 연결한다.
- **금지**: 회사, 동료, 평가 과정을 사유로 말하지 않는다. 직전 사이클(트라이포드랩에서 키노라이츠로 옮긴 이유) 답변을 섞지 않는다.

### C2. 최근 재직 기간이 짧은데 (2026-09-29 확정)

- **답변 본문**: 키노라이츠는 메인 문서 이직 사유 절의 답변을 그대로 쓴다. 이력서의 키노라이츠 표기는 재직중이 아니라 2026.06~2026.09이므로, 경력 흐름을 말할 때 9월 중순에 마쳤다는 사실을 먼저 짧게 밝히고 C1로 잇는다. 이썸테크는 [[My-Motivation-Reasons]]의 첫 경력 답변을 쓴다.
- **골격**: 기간은 반복하지 않고 사실만 짧게 인정 → 역할 기대와 내 준비가 어디서 어긋났는지 자기 기준으로 → 지금은 지원 전에 첫 90일의 범위와 완료 조건, 검토 구조를 확인한다는 행동으로 닫는다. 외부 귀책과 조직 평가 금지.

### C3. 지금은 무엇을 하고 있나 (2026-09-29 확정)

- **답변**: 9월 중순 퇴사한 뒤 지난 경험을 회고하고 다음 역할을 준비하고 있습니다. 그때 정리한 기준이 앞서 말씀드린 기대 결과와 완료 조건을 먼저 합의하는 것입니다.
- **원칙**: 개인 사업 활동은 먼저 꺼내지 않는다. 겸업이나 사업 여부를 직접 묻는다면 사실대로 답한다.

### C4. 풀스택 역할인데 백엔드만 해 왔다 (Self-Analysis 새로움은 하나씩)

- **답변**: 백엔드가 가장 깊게 책임져 온 영역이라는 점은 그대로 말씀드립니다. 다만 사용자 화면까지 이어지는 흐름을 책임지는 경험이 필요하다고 봤고, 산업과 프론트엔드가 동시에 새로운 만큼 백엔드 문제에서 먼저 기여하면서 화면 작업의 범위를 넓히는 순서가 현실적이라고 생각합니다.
- **꼬리**: 프론트엔드가 절반이면 → 비중을 역질문으로 먼저 확인하고, 거짓 없이 학습 속도로 답한다.

### C5. 운영팀이나 공급처처럼 비개발 직군과 요구사항을 어떻게 맞추나 (FIT 3 fork)

- **답변**: 기획 의도를 먼저 확인하고 제가 이해한 내용을 다시 말해 맞춥니다. 그 뒤 선택지와 제약을 기술 용어 대신 사용자 영향, 비용, 다음 행동으로 설명합니다. 트렉시처럼 운영팀의 수기 업무를 자동화하는 일은 현재 업무 흐름을 그대로 관찰하는 것부터 시작해야 한다고 봅니다.

### C6. 일정과 리스크가 부딪친 경험 (FIT 2-A fork)

- **답변**: 정산과 연결된 환불 정책 변경 요청이 기존 흐름과 충돌할 가능성이 보였습니다. 고객 영향과 사후 정정 비용을 정리해 공유하고 범위를 나눠 검증하자고 제안했습니다. 일정은 조정됐지만 보호 조건을 먼저 두고 안정적으로 출시했습니다.
- **트렉시 연결**: 견적과 정산은 사후 정정 비용이 큰 영역이라 같은 방식으로 위험과 최소 검증 범위를 먼저 제시하겠습니다.

### C7. 실패 경험 (FIT 12 fork)

- R9의 배치 오류 사례를 쓴다. 원인 가설과 재발 방지를 분리하고, 발견 뒤 대응보다 출시 전 실패를 줄이는 기준을 얻었다는 배움으로 닫는다.

### C8. AI가 코드를 쓰는 시대에 개발자의 역할 (FIT 15 fork)

- **답변**: 구현이 빨라질수록 무엇을 왜 만들지 판단하고 결과를 검증하며 책임지는 역할이 더 중요해진다고 봅니다. AI 추출 결과가 견적 금액으로 이어지는 트렉시의 흐름에서는 검수 기준을 정하는 사람이 품질을 결정합니다.

### C9. 사이드 프로젝트 (FIT-Extended 5 fork, 정성만)

- **답변**: 주일학교 출석부를 전산화해 실제 사용자 문제를 풀었고, 여러 조직이 쓰는 구조라 권한 경계, 이력 보존, 실패 처리와 복구를 설계하고 검증했습니다. 1인 운영의 한계는 AI 협업 파이프라인으로 보완했습니다. 규모보다 실제 사용 흐름에서 책임 있게 운영하고 복구 가능성을 확인한 경험이 핵심입니다.
- **금지**: 사용자 수, 조직 수, 레코드 수 같은 정량 수치를 말하지 않는다. 공개 승인 전에는 지표 정의와 운영 결론만 말한다.

### C10. 5년 후, 업무 강도 (FIT 4, 11 fork)

- **5년 후**: 기술 깊이와 제품 맥락을 함께 갖추고 복잡한 문제를 끝까지 책임지는 백엔드 리드 방향. 직함보다 영향 범위.
- **업무 강도**: 의미 있는 문제라면 집중하되, 우선순위와 장애 뒤 회복 방식을 확인하고 싶다고 역질문으로 넘긴다. 과한 헌신 약속과 부정 평가 모두 피한다.
