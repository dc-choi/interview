# 트렉시 지원 전 기술 예상 질문, JD와 서비스 맥락

> [[Interview-Prep-Trexi-1st|메인]], [[Interview-Prep-Trexi-1st-Questions|이력서와 컬처핏 질문]]. 회사 내부 구현은 공개되지 않았다. 아래는 공고의 공개 문제에 대한 내 설계 골격이며, 트렉시의 현재 구조를 아는 것처럼 말하지 않는다. 갭 질문은 인정, 전이 근거, 학습 계획 순서로 답한다.

## JD 기반 질문

### J1. 공급처 메일과 엑셀을 LLM으로 상품 데이터로 구조화한다면 어떻게 설계하나 (설계형)

- **의도**: LLM 출력을 믿지 않고 검증과 실패 처리까지 설계하는가.
- **골격**: 원본 수신 → 원본을 S3에 불변 저장하고 메시지 식별자로 중복 수신 차단 → 큐로 추출 작업 분리 → 엑셀은 먼저 결정적 파서로 표를 읽고 LLM은 헤더 매핑과 비정형 문장 해석처럼 필요한 구간에만 사용 → 스키마 검증 → 값 범위 검증(음수 가격, 통화, 단위) → 집합 검증(행 수, 결측률) → 통과분만 상품으로 승격, 실패와 저신뢰 건은 검수 큐.
- **판단 기준**: LLM 출력은 사용자 입력처럼 불신한다. 모델이 JSON 형식을 지원해도 서버 검증을 생략하지 않는다. 가격, 수량처럼 틀리면 돈이 되는 필드는 사람 확인 경계를 둔다.
- **보안**: 공급처 메일은 비신뢰 콘텐츠라 간접 프롬프트 인젝션 경로가 된다. 추출 모델에는 도구와 상태 변경 권한을 주지 않고, 결과는 검증된 필드 값으로만 다운스트림에 넘긴다.
- **대안과 트레이드오프**: 규칙 파서만 쓰면 정확하고 싸지만 공급처별 양식 변화에 약하다. 전부 LLM이면 유연하지만 비용, 지연, 비결정성이 커진다. 혼합이 기본값이다.
- **꼬리**: 추출 결과가 형식은 맞는데 값이 틀리면? → 원본 대조가 가능한 필드는 역검증(원본 셀 위치 기록), 불가능하면 신뢰도와 과거 값 변동 폭으로 검수 대상 선별. 운영 LLM 파이프라인 경험은 없다고 먼저 밝힌다.
- **출처**: [OWASP, LLM01 Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

### J2. 프롬프트, 모델, 추출 로직을 어떻게 버전 관리하고 비교하나 (설계형)

- **의도**: AI 파이프라인을 코드처럼 변경 관리할 수 있는가.
- **골격**: 프롬프트, 모델 식별자, 파라미터, 후처리 로직을 묶은 파이프라인 버전을 저장소에서 관리 → 추출 결과마다 사용한 버전과 원본 참조를 기록 → 실제 실패 사례로 골든셋을 만들고 새 버전은 기준선 대비 필드별 정확도로 비교 → 통과 시 일부 공급처나 일부 트래픽에 먼저 적용 → 운영 실패를 다시 골든셋에 추가.
- **판단 기준**: 같은 입력에도 결과가 흔들리므로 한 번 실행한 점수 차이로 결정하지 않는다. 직전 버전과만 비교하면 조금씩 나빠지는 변화가 누적되므로 고정 기준선을 함께 둔다.
- **대안**: 운영 입력을 새 버전에도 그림자 실행하면 입력 분포를 반영할 수 있지만 추가 추론 비용과 데이터 취급 부담이 생긴다. 결과의 정답 여부는 별도 검수가 필요하다. 골든셋 게이트만 먼저 두고, 그림자 실행은 고위험 필드에 한정한다.
- **꼬리**: 모델 제공자가 모델을 바꾸면? → 제공자가 지원하면 모델 스냅숏을 고정하되 완전 재현성을 보장한다고 말하지 않는다. 교체는 새 버전으로 취급하고 고정 기준선, 반복 평가와 운영 표본으로 드리프트를 감지한다.
- **근거**: [[LLM-Eval-Strategy]], [[LLM-Application-Security]]. 검색 실험 경험과 제품 추출 모델 운영은 구분한다.

### J3. 견적 확정부터 정산까지 거래 상태를 어떻게 모델링하나 (설계형)

- **의도**: 돈과 상태가 얽힌 흐름에서 정합성과 재처리를 설계하는가.
- **골격**: 거래를 명시적 상태 머신으로 두고(예: 견적 작성, 제시, 확정, 발주, 입고, 출고, 정산 완료, 취소) 허용 전이만 코드로 정의 → 전이는 현재 상태 조건부 UPDATE나 버전 컬럼으로 경쟁을 막음 → 확정 시점의 가격, 환율, 수수료 조건을 스냅숏으로 저장해 나중에 원가가 바뀌어도 재계산하지 않음 → 전이마다 감사 이력 → 후속 작업(메일 발송, 정산 생성)은 이벤트로 분리하고 멱등성 키로 중복 처리 방지.
- **전이 경험**: 재고 동시 갱신의 DB Lock, 발주 자동화의 멱등 소비와 DLQ. DB 커밋과 이벤트 발행 사이 유실은 당시 해결하지 못했고 지금이라면 Transactional Outbox를 쓴다고 구분해 말한다.
- **트레이드오프**: 상태를 세분하면 추적은 쉬워지지만 전이 규칙과 예외 경로가 늘어난다. 운영팀이 실제로 구분해 행동하는 상태만 둔다.
- **꼬리**: 정산 후 취소가 오면? → 원 레코드를 고치지 않고 반대 기록으로 정정하고, 외부 정산 결과와 주기적으로 대사한다.

### J4. 마진과 견적 금액을 Node.js에서 어떻게 다루나 (사실형)

- **의도**: 부동소수점 금액 오류를 아는가.
- **핵심**: JavaScript `number`는 IEEE 754 배정밀도라 `0.1 + 0.2`가 정확히 `0.3`이 아니다. DB는 `DECIMAL(p, s)`로 저장하고, 애플리케이션은 최소 통화 단위 정수나 decimal 라이브러리로 계산하며, 반올림 방식과 시점(행 단위인지 합계 단위인지)을 업무 규칙으로 정한다.
- **정량 예시 (가정)**: 0.335인 두 행을 소수 둘째 자리에서 사사오입하면 행별 합계는 0.68, 합산 후 반올림은 0.67이다. 같은 decimal 연산이라도 반올림 시점이 다르면 견적이 달라진다. 정수 방식도 `Number.MAX_SAFE_INTEGER`를 넘는지 확인하고, API 경계에서는 decimal 문자열과 통화 정보를 보존한다.
- **흔한 오답**: DB만 DECIMAL이면 된다. mysql2는 기본 설정에서 DECIMAL을 문자열로 돌려주고, `decimalNumbers: true`로 숫자 변환하면 다시 부동소수점 오차가 생긴다.
- **꼬리**: 환율이 섞이면? → 적용 환율과 기준 시각을 견적 스냅숏에 저장한다. 통화별 소수 자릿수가 다르다는 점도 스키마에 반영한다.
- **출처**: [MDN, Number.EPSILON](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/EPSILON), [MySQL 8.4, DECIMAL Data Type Characteristics](https://dev.mysql.com/doc/refman/8.4/en/precision-math-decimal-characteristics.html), [node-mysql2, ConnectionOptions 타입 정의](https://github.com/sidorares/node-mysql2/blob/master/typings/mysql/lib/Connection.d.ts)

### J5. 외부 시장 데이터를 안정적으로 수집하는 파이프라인 (설계형)

- **의도**: 계약 없는 소스의 조용한 실패를 다룰 줄 아는가.
- **골격**: 파싱 직후를 신뢰 경계로 두고 구조, 값 범위, 집합 수준 3층 검증 → 항목 단위로 실패를 격리하고 원본 응답을 보관 → 실패를 일시, 차단, 구조 변경으로 나눠 대응(재시도, 속도 하향, 파서 수정) → 건수가 급감하면 반영을 보류하고 직전 스냅숏 유지 → 신선도는 성공률이 아니라 데이터 나이로 보고, 마지막 성공 시각으로 스케줄러 정지를 감지.
- **내 경험**: 국제 배송 서비스의 배송 정보 수집과 환율 배치. 대규모 크롤러 운영을 입증할 근거로 확대하지 않는다.
- **트레이드오프**: 검증 실패 때 이전 스냅숏을 유지하면 오염은 막지만 신선도가 떨어진다. 실패 건은 삭제 대상에서 제외하고 보류 해제와 재수집 경로를 둔다.
- **꼬리**: 약관과 robots.txt는? → robots.txt 규칙을 따른다. 서버나 네트워크 오류로 도달 불가하면 기본적으로 전체 금지로 다루며 RFC의 캐시 예외도 확인한다. 파일 부재를 뜻하는 4xx와 구분한다. 이용약관과 저작권은 기술 규격과 별개로 소스별 확인이 필요하다.
- **출처**: [RFC 9309, Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html)

### J6. SQS 소비자를 Lambda로 둘지 ECS 워커로 둘지 (설계형)

- **의도**: 비용뿐 아니라 DB 연결 예산과 실패 복구 방식으로 실행 환경을 고르는가.
- **골격**: 도메인 로직 재사용, DB 연결과 동시성 제어, 작업 길이, 부하 패턴 4축으로 고른다. 짧고 독립적이며 불규칙한 작업은 Lambda, 기존 NestJS 로직을 쓰고 DB 연결 수를 직접 제한해야 하면 ECS 워커.
- **사실 포인트**: Lambda 이벤트 소스 매핑에서는 visibility timeout은 함수 timeout의 6배에 설정한 배치 대기 시간을 더하도록 권장한다. `ReportBatchItemFailures`를 켜고 실패 항목을 반환하면 해당 항목을 재전달한다. FIFO는 첫 실패 뒤 중단하고 미처리 항목도 반환한다. DLQ 이동은 오류 분류가 아니라 수신 횟수 정책에 따른다.
- **정량 예시 (가정)**: 초당 20건, 건당 평균 0.5초면 평균 동시 작업은 10개다. 이는 목표 워커 수가 아니라 출발점이다. 버스트, 재시도, 배치와 DB/API 상한을 반영하고 큐 대기 시간을 측정해 여유를 정한다.
- **흔한 오답**: SQS면 한 번만 처리된다. 표준 큐는 최소 한 번 전달이라 소비자가 멱등해야 한다.
- **꼬리**: Lambda 동시 실행이 늘어 MySQL 연결이 부족하면? → 기본 모드에서는 이벤트 소스 최대 동시성을 제한하고 연결 예산을 계산한다. provisioned 모드는 poller 상한으로 제어하며 maximum concurrency와 병용하지 않는다. 필요 시 RDS Proxy를 검토하되 DB 처리량 제한이 사라지는 것은 아니다.
- **출처**: [AWS, Configuring an SQS event source](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-configure.html), [AWS, Handling errors for an SQS event source](https://docs.aws.amazon.com/lambda/latest/dg/services-sqs-errorhandling.html), [AWS, SQS dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)

### J7. 내부 시스템을 공급업체와 바이어까지 쓰는 플랫폼으로 확장할 때 권한 설계 (설계형)

- **의도**: 다자 거래에서 데이터 노출 경계를 먼저 보는가.
- **골격**: 사용자는 조직(공급업체, 바이어, 내부)에 속하고, 권한은 역할과 자원 소유의 조합으로 판단 → 저장소 계층에서 조직 범위를 기본 조건으로 강제해 누락을 막음 → 응답 DTO를 사용자 유형별로 분리해 마진, 매입가, 다른 거래처 정보가 외부로 나가지 않게 함 → ID만 바꿔 남의 거래를 조회하는 IDOR을 테스트로 고정 → 권한 변경과 민감 조회는 감사 기록. 캐시 키, 파일 다운로드, 내보내기와 백그라운드 작업에도 같은 조직 범위를 전달해 재검증한다.
- **트레이드오프**: 한 테이블에 조직 키로 논리 격리하면 단순하지만 실수 한 번이 유출이 된다. 격리 강도는 계약과 민감도에 맞춘다.
- **꼬리**: 한 회사가 공급업체이면서 바이어라면? → 역할을 조직 단위가 아니라 거래 단위 관계로 부여한다.

### J8. React와 Next.js 경험을 보여 달라면 (근거 미확인 갭)

- **의도**: 필수 프론트엔드 요건을 실제 산출물과 맡은 범위로 설명하는가.
- **답변 골격**: ① 현재 자료에는 직접 수행 근거가 없다. 실제 사용했다면 맡은 화면과 검증한 동작을 추가하고, 경험이 없다면 없다고 말한다. ② 전이 근거는 API 계약을 OpenAPI로 요청, 응답, 실패 조건까지 명확히 맞춰 온 경험과, 화면이 쓰는 데이터 모양을 백엔드에서 설계해 온 경험이다. ③ 첫 기간에는 기존 화면의 작은 변경부터 맡아 사내 UI 라이브러리와 데이터 조회 패턴을 익히겠다고 구체화한다.
- **금지와 꼬리**: 문서만 읽은 개념을 써 본 것처럼 말하지 않는다. 당장 화면 작업을 맡을 수 있는가? → 검증 가능한 경험 범위로 답하고, 풀스택 비중과 초기 검토 구조를 확인한다.
- **출처**: [Next.js Docs](https://nextjs.org/docs)

### J9. Turborepo 모노레포와 사내 라이브러리 배포 (설계형, 직접 경험 근거 없음)

- **의도**: 공용화의 이득과 변경 영향 범위를 함께 판단하는가.
- **골격**: 모노레포는 저장소 단위이지 배포 단위가 아니다. 패키지 간 의존 방향을 정하고 공개 API만 가져다 쓰게 하며, 변경된 패키지와 그 의존자만 빌드, 테스트하도록 작업 그래프와 캐시를 쓴다. 공용 라이브러리는 버전과 변경 이력을 두고 호환성을 깨는 변경을 분리한다.
- **함정**: 모든 것을 공용 패키지에 넣으면 작은 변경이 전체 재빌드와 배포를 부른다. 두 곳 이상에서 실제로 반복될 때 공용화한다.
- **꼬리와 트레이드오프**: 캐시가 잘못 재사용되면? → 환경 변수와 생성 파일 등 빌드 입력을 확인하고 캐시 없는 결과와 비교한다. 공유로 중복은 줄지만 결합과 호환성 관리 비용은 늘어난다.
- **출처**: [Turborepo Docs](https://turborepo.com/docs)

## 서비스 맥락 질문

### S1. 공급처 메일 한 통이 상품 데이터가 되기까지를 그려 보라

- **의도와 답변**: 전체 흐름의 신뢰 경계를 본다. 수신 → 원본과 첨부 보관 → 중복 차단 → 작업 큐 → 추출과 검증 → 검수 → 상품 반영으로 나누고 각 단계의 실패 상태를 남긴다. SES 수신인지 기존 메일함 연동인지는 공개되지 않았다.
- **대안과 실패**: 동기 처리보다 큐는 재시도와 부하 제어가 쉽지만 완료 상태를 보여 줄 화면이 필요하다. 첨부 크기, 압축 해제 한도와 악성 파일을 검사하고, 원본 접근 권한과 보존 기간을 정한다.
- **꼬리**: 저장 뒤 큐 발행에 실패하면? → DB 작업 기록과 발행 대기 상태를 원자적으로 남기고 재발행한다. 재전달에도 같은 작업 결과가 중복 반영되지 않게 한다.
- **출처**: [AWS, Email receiving with Amazon SES](https://docs.aws.amazon.com/ses/latest/dg/receiving-email.html), [[External-Collection-Pipeline-Reliability]].

### S2. 같은 상품이 공급처마다 다른 이름과 양식으로 오면

- **의도와 답변**: 오병합의 비용을 아는가. 바코드와 모델 번호를 검증한 뒤 후보 키로 쓰고, 없으면 이름과 규격을 정규화해 후보를 찾는다. 상품과 공급처별 오퍼를 분리해 가격, 최소 주문량, 납기를 보존한다.
- **트레이드오프**: 자동 병합은 검수량을 줄이지만 잘못 합친 주문의 복구 비용이 크다. 낮은 확신은 사람에게 보내고 병합 근거와 되돌릴 이력을 남긴다.
- **꼬리**: 같은 바코드인데 포장 단위가 다르면? → 단위와 구성 수량을 확인하기 전에는 같은 판매 단위로 합치지 않는다. 확신 임계값은 검수 표본의 오병합률로 정한다.

### S3. AI 추출이 틀려 잘못된 견적이 나갔다면

- **의도와 답변**: 이미 발생한 고객 영향을 먼저 줄이는가. 후속 확정과 자동 발송을 멈추고 영향 범위를 찾는다. 업무 담당자와 정정 절차를 진행한 뒤 입력과 파이프라인 버전으로 같은 오류 후보를 찾는다.
- **트레이드오프와 검증**: 전체 중단은 정상 업무도 막으므로 공급처, 버전과 필드로 범위를 좁힌다. 실패 사례를 평가 세트에 추가하고 원본 대조, 금액 검수와 재발 방지 게이트를 검증한다.
- **꼬리**: 모델을 롤백하면 끝인가? → 이미 생성되거나 전송된 견적은 복구되지 않는다. 해당 거래를 따로 대사하고 수정 이력을 남긴다. [[LLM-Eval-Strategy]]

### S4. 자동화할 수기 업무를 어떻게 고르나

- **의도와 답변**: 개발량보다 업무 결과를 기준으로 판단하는가. 빈도, 처리 시간, 오류 비용, 규칙의 명확성과 예외 비율을 먼저 확인한다. 반복되는 정상 경로부터 자동화하고 예외는 검수에 남긴다.
- **정량 비교 (가정)**: 하루 30건의 5분 작업을 1분 검수로 줄이면 잠재 절감은 하루 120분이다. 여기서 예외 처리와 시스템 운영 시간을 빼야 실제 이득이다. 실제 회사 규모나 내 성과 수치가 아니다.
- **꼬리와 한계**: 예외가 절반이면? → 전체 자동화 대신 입력 검증이나 초안 생성만 지원한다. 발주 자동화 경험은 전이 근거이며 이 가정의 성과 증거가 아니다.

### S5. 배송, 통관 같은 외부 상태를 주기적으로 동기화할 때

- **의도와 답변**: 중복, 순서 역전과 정정을 구분하는가. 웹훅을 제공하면 받고 폴링으로 누락을 보정한다. 사건 식별자와 버전을 검증하고 오래된 이벤트는 막되 취소와 정정은 별도 허용 전이로 기록한다. 마지막 동기화 성공과 데이터 나이를 함께 본다.
- **한계와 대안**: 사건/채널 유일 키만으로 이메일이 정확히 한 번 나간다고 보장하지 않는다. 제공자 수락 뒤 응답 유실이 가능하므로 발송 상태와 제공자 식별자를 기록하고, 지원되는 멱등 키나 조회로 대사한다. 수락 여부가 불명확하면 무조건 재발송하지 않는다.
- **꼬리**: 반송이나 수신 거부는? → 알림을 받아 대상 정책에 반영한다. SES sandbox에서는 검증된 수신 주소 등 발송 제한도 확인한다.
- **출처**: [AWS, SES sandbox](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html), [AWS, SES notifications](https://docs.aws.amazon.com/ses/latest/dg/monitor-sending-activity-using-notifications.html).

### S6. LLM 비용과 지연이 커지면

- **의도와 답변**: 품질을 지키며 낭비를 줄이는가. 입력 유형별 결정적 파서 적용을 늘리고, 작은 모델과 큰 모델을 고정 평가 세트로 비교한다. 입력 크기, 재시도와 총 비용에 상한을 두고 큐 대기와 추론 지연을 분리해 본다.
- **트레이드오프**: 작은 모델의 호출 비용이 싸도 검수와 재시도가 늘면 업무 비용은 커진다. 문서당 최종 검수 완료 비용과 지연을 기준으로 고른다. 캐시는 데이터 권한, 재사용 가능 구간과 무효화 조건을 확인하고 적용한다.
- **꼬리**: 품질이 떨어지면? → 고위험 필드를 큰 모델이나 검수로 전환하고 이전 검증 버전으로 되돌린다. 가격과 제공자 한도는 적용 시점의 공식 문서로 확인한다. [[LLM-Eval-Strategy]]
