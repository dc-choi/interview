# 브랜뉴닷컴 1차 이력서 기반 기술 질문

> [[Interview-Prep-BrandNewCom-1st|목차]]로 돌아가기. My-Tech-Cards 마스터를 fork했다. 수치는 공개 이력서에 적힌 값만 쓰고, 측정 조건을 설명할 수 없으면 수치 대신 문제, 판단, 검증 방법으로 말한다. 각 카드의 끝줄은 브랜뉴닷컴 업무와의 연결이다.

## R1. 동시 요청 정합성, DB Lock 전략 (경험형)

- **의도**: 동시성 문제를 재현하고 잠금 범위를 설계했는지, 대안을 비교했는지 본다.

> 수천 대 IoT 기기의 입력이 같은 재고 상태를 동시에 바꾸던 경로에서 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위와 제한된 재시도를 조합했습니다. 충돌이 잦은 갱신이라 늦게 충돌을 발견하는 낙관적 잠금보다 변경 전에 경합을 조정하는 비관적 잠금이 단순하다고 판단했습니다. 외부 호출과 독립적인 검증은 트랜잭션 밖에서 끝내고, 동시 요청을 재현해 최종 수량과 재시도 뒤 상태를 확인했습니다.

- **한계**: 당시 재시도는 짧은 고정 간격이었다. 지금이라면 지수 백오프와 지터를 함께 검증한다. `NOWAIT`는 그 잠금 읽기의 대기만 없애고 이후 쿼리나 메타데이터 잠금 대기까지 없애지는 않는다.
- **꼬리, NOWAIT와 SKIP LOCKED 차이**: SKIP LOCKED는 잠긴 행을 건너뛰어 작업 큐에 맞고, 특정 행을 반드시 처리해야 하는 재고에는 NOWAIT가 맞다.
- **꼬리, 서버가 여러 대여도 충분한가**: 같은 DB를 보는 한 충분하다. 보호 대상이 여러 저장소나 외부 시스템을 넘을 때만 분산 락을 검토한다.
- **꼬리, 데드락은**: 여러 행을 갱신할 때 업무 키 순서를 통일해 확률을 낮추고, 데드락 오류는 새 트랜잭션에서 제한 재시도한다.
- **연결**: 여러 마켓에서 같은 상품 재고나 같은 주문 상태를 동시에 바꾸는 경로에 같은 판단이 필요하다.

## R2. EventBridge와 SQS 기반 발주 자동화 (경험형)

- **의도**: 비동기 분리의 이유, 중복과 실패 처리, 선택하지 않은 대안을 설명하는지 본다.

> 상태 변경과 후속 업무를 한 요청에 묶으면 느린 의존성 하나가 핵심 상태 변경까지 실패시킵니다. 그래서 핵심 상태를 먼저 확정하고 후속 처리를 EventBridge와 SQS로 전달했습니다. 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 일시 오류만 제한 재시도한 뒤 DLQ와 수동 확인 경로로 보냈습니다. 조직의 Kafka 운영 여력을 고려해 관리형 큐를 골랐습니다.

- **한계**: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 전에 프로세스가 멈추면 이벤트가 누락될 수 있었고, 당시에는 발행 재시도와 운영 확인으로 다뤘다. 지금이라면 상태 변경과 outbox 레코드를 같은 트랜잭션에 쓰고 릴레이가 발행하게 한다.
- **꼬리, 정확히 한 번 처리되나**: 아니다. SQS 표준 큐는 적어도 한 번 전달이므로 업무 키 단위 중복 제거와 상태 전이 검증으로 결과를 한 번으로 만든다.
- **꼬리, Lambda가 아니라 컨테이너 워커를 쓴 이유**: 기존 도메인 로직 재사용과 DB 연결, 워커 동시성의 직접 제어가 필요했다. 짧고 독립적인 작업이면 서버리스 소비자도 적합하다.
- **연결**: 공고의 주문, 정산, 알림 자동화는 같은 구조다. 주문 확정 뒤 정산 기록과 알림을 분리하고 실패는 재처리 가능한 상태로 남긴다.

## R3. 슬로우 쿼리 99.3% 개선 (경험형, 수치 방어)

- **의도**: 실행 계획을 읽고 인덱스를 설계했는지, 수치의 기준을 설명할 수 있는지 본다.

> 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했습니다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 설계하고, 인덱스가 실제로 정렬과 상위 레코드 접근에 쓰이는지 실행 계획으로 다시 확인했습니다.

- **수치 방어**: 99.3%는 이력서에 공개된 쿼리 단위 개선이다. 배치 전체 시간이나 API 응답 같은 다른 지표와 섞어 말하지 않는다. 측정 환경과 캐시 상태를 물으면 기억나는 범위만 말하고 모르는 조건은 모른다고 한다.
- **꼬리, 컬럼 순서 기준**: 카디널리티 하나가 아니라 동등 조건, 범위 조건, 정렬, 필요한 반환 컬럼을 실제 쿼리에서 판단한다.
- **꼬리, 인덱스의 대가**: 쓰기와 저장 비용이 는다. 인접 쓰기 경로의 영향을 함께 본다.
- **연결**: 주문과 정산 이력은 시간이 갈수록 쌓이므로 셀러별 최근 주문 조회에 같은 설계가 필요하다.

## R4. Prisma N개 쿼리를 단일 쿼리로, 응답 90% 향상 (경험형)

> 관계를 포함한 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했습니다. 당시 `relationJoins` 기능이 꺼진 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합하고 있었습니다. 기능을 켜고 `relationLoadStrategy: 'join'`을 적용한 뒤, MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했습니다. 이 사례는 하코 커뮤니티에서 발표했습니다.

- **흔한 오답**: 옵션 이름만 보고 SQL JOIN이 나간다고 단정하는 것. 실제 생성 SQL은 DB와 버전에 따라 다르다.
- **꼬리, 조인 전략의 대가**: 호출 수는 줄지만 반환 데이터 중복, 집계 비용, DB 부하를 확인해야 한다. 성능이 중요한 경로만 바꾸고 나머지는 ORM의 타입 안정성을 유지했다.
- **연결**: 관리자 화면처럼 주문, 상품, 셀러를 함께 보여주는 조회에서 같은 문제가 자주 생긴다.

## R5. 국제 배송 서비스의 배송 정보 스크래핑과 환율 배치 (경험형)

- **의도**: 계약이 없는 외부 소스를 다룰 때 실패를 어떻게 정의하고 감지했는지 본다.

> 시솔지주에서 국제 배송 서비스의 배송 정보 스크래핑과 환율 정보 배치를 맡았습니다. 외부 소스는 예고 없이 형식이 바뀌고, 정상 응답 안에 잘못된 데이터가 담겨 올 수 있습니다. 오류가 늘었을 때 영향과 원인 가설로 나누고, 중요한 경로부터 자동 검증과 배포 전 검사를 추가했습니다.

- **한계와 현재 설계**: 당시에는 정상 응답 안의 조용한 실패를 소스별 성공률로 탐지하는 수준까지 닫지 못했다. 지금이라면 파싱 직후 스키마 검증을 신뢰 경계로 두고, 수집 건수가 직전보다 급감하면 반영을 보류하고 직전 값을 유지하며, 마지막 성공 수집 시각을 감시한다.
- **꼬리, 실패를 어떻게 나누나**: 일시(타임아웃, 5xx)는 백오프 재시도, 차단(429, 403, 챌린지 페이지)은 속도를 낮추고 Retry-After를 따르며, 구조 변경(200인데 검증 실패가 집단 발생)은 재시도하지 않고 파서 수정으로 넘긴다.
- **꼬리, 환율은 언제 값을 쓰나**: 계산 시점의 환율 스냅숏을 기록해 나중에 금액을 재현할 수 있어야 한다. `[사용자 확인 필요: 당시 환율 배치의 실제 갱신 방식]`
- **연결**: 해외 구매처 상품 정보와 배송 상태 수집에 그대로 쓰이는 경험이다.

## R6. Google API 번역 연동, 70% 성능 향상 (경험형, 수치 방어)

- **답변 골격**: 무엇이 느렸는지, 어떤 기준으로 측정했는지, 무엇을 바꿨는지, 실패 시 어떻게 대체했는지 순서로 답한다.
- `[사용자 확인 필요]`: 70%가 응답 시간인지 처리량인지, 무엇을 바꿨는지(호출 묶기, 캐시, 병렬화 등). 확인 전에는 방법을 지어내지 않는다.
- **꼬리, 외부 API 할당량을 넘으면**: 동시 호출 수를 제한하고 429에는 Retry-After와 백오프로 대응한다. 같은 원문은 캐시로 재호출을 줄인다.
- **연결**: 마켓 API도 호출 한도가 있으므로 동시성 제한과 재시도 예산이 같은 문제다.

## R7. Docker 멀티스테이지와 Jenkins CI/CD (경험형)

> 빌드 도구와 실행 의존성을 분리한 멀티스테이지 빌드로 이미지를 909MB에서 513MB로, 배포 시간을 3분 10초에서 2분 20초로 줄였습니다. 시솔지주에서는 Jenkins 기반 CI/CD 파이프라인을 구축해 배포 속도를 50% 단축했습니다. 수치보다 재현 가능한 배포, 롤백, 종료 절차를 우선했습니다.

- **꼬리, 이미지를 더 줄이려면**: alpine은 작지만 musl 때문에 네이티브 모듈 호환성을 확인해야 하고, distroless는 셸이 없어 보안에 유리하지만 디버깅이 어렵다.
- **꼬리, 컨테이너 종료 시**: 종료 신호를 받으면 새 요청을 막고 진행 중 작업을 정리한다. 메시지 워커는 현재 작업의 완료 또는 재전달 경계를 명확히 한다.
- **연결**: 우대 사항의 Docker와 Jenkins 경험에 직접 해당한다.

## R8. 관측성 구축과 주기 리포트 자동화 (경험형)

> Grafana, Prometheus, Loki로 로그와 메트릭 수집, 경보 정책을 정립했습니다. 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었습니다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼습니다. 또 IoT 기기의 배터리 부족과 통신 지연을 주기적으로 집계해 알림톡과 이메일로 자동 통보하는 리포트를 만들었습니다.

- **꼬리, 사용자 ID를 라벨로 넣으면**: 제가 실제로 겪은 실수다. 요청마다 새 시계열이 생겨 시계열 수가 급증했다. 그래서 라벨 설계 기준을 먼저 말하고, 식별자는 로그에 남긴다.
- **꼬리, 알림이 중복 발송되면**: 알림 사건의 안정적인 식별자와 채널을 함께 유일하게 만들어 로컬 중복을 막는다. 외부 발송사가 수락한 뒤 응답 전에 멈춘 경우까지는 막지 못하므로 발송사가 지원하면 같은 멱등 키를 전달한다.
- **연결**: 공고의 알림 자동화와 연동 실패 감지에 바로 쓰인다.

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP (개인 프로젝트, 이력서)

- **의도**: AI 도구를 검토와 검증 대상으로 다뤄 봤는지, 검색 방식을 정량 비교로 골랐는지 본다.

> 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템입니다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색은 MCP 도구와 CLI로 노출했습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했고, 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했습니다. BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어 채택하지 않았습니다. 그 74개를 포함한 94개 질문으로 bge 리랭커도 비교했는데 통과가 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸려 채택하지 않았습니다. 대신 문제가 후보 검색보다 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.

- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 비용과 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다. 모두 기각한 판단 자체가 강점이다.
- **꼬리, 평가 질문은 어떻게 만들었나**: 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본은 아니다. 양성 질문은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나와야 통과, 음성 질문은 빈 결과여야 통과로 쳤다.
- **꼬리, 어떤 지표로 비교했나**: 위 통과 개수와 후보 50개 안의 필수 근거 개수다. 순위 가중 지표(nDCG 등)는 쓰지 않았고 한계로 인정한다.
- **이력서 정정**: 이력서에는 골든 케이스 약 145건으로 비교했다고 적혀 있으나 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **한계를 먼저 말할 것**: 합성 표본이고 실제 답변 정확도나 사용자 만족도를 잰 것이 아니다. 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- **연결**: 공고에 LLM 기능이나 검색 품질 요소는 없다. AI 개발 도구 활용과 생성 코드 검토 우대 항목의 근거로만 짧게 쓴다. 같은 평가 질문으로 변경을 비교하는 방식은 연동 코드 회귀 검증과도 통한다.
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 먼저 개인 프로젝트라고 밝힌다.
