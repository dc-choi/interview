# 브랜뉴닷컴 1차 서비스 맥락 질문, 역질문, 체크리스트

> [[Interview-Prep-BrandNewCom-1st|목차]]로 돌아가기. 공개된 사실은 공고 업무 문장과 셀록홈즈 공식 홈페이지 소개까지다. 아래 설계는 그 사실 위에 세운 가정이며, 실제 구조를 아는 것처럼 말하지 않는다. 답변 첫 문장에 가정을 밝힌다.

## 1. 서비스 맥락 질문

### S1. 여러 셀러의 마켓 주문을 모아 처리한다면 무엇이 어렵나

- **공개 근거**: 국내 마켓 연동과 주문 자동화가 업무로 명시됨. 어떤 마켓인지는 미확인.
- **답변 골격**: 셀러별 데이터와 권한 경계를 먼저 나눈다. 모든 조회와 쓰기에 셀러 식별자를 강제하고, 마켓 인증 정보는 셀러별로 암호화 저장하며 만료와 갱신 실패를 따로 감지한다. 마켓 API 호출 한도는 셀러와 마켓 단위로 나눠, 한 셀러의 대량 수집이 다른 셀러를 막지 않게 한다.
- **트레이드오프**: 셀러별 큐 분리는 공정성이 좋지만 운영할 큐가 늘어난다. 처음에는 하나의 큐에 셀러별 동시성 상한을 두고, 편중이 측정되면 분리한다.
- **유사 경험**: 트라이포드랩의 기기 단위 동시 요청 처리, 출석 관리 사이드 프로젝트의 멀티테넌트 권한 경계 설계(정성적 경험만 말한다).

### S2. 해외 구매처 상품의 가격과 마진을 계산할 때 주의할 점

- **공개 근거**: 셀록홈즈가 타오바오와 1688 상품 검색, 공급가와 마진 확인용 가격 비교를 내세움. 실제 계산 방식은 미확인.
- **답변 골격**: 원가, 환율, 배송비, 수수료의 출처와 조회 시각을 함께 저장해 나중에 같은 금액을 재현할 수 있게 한다. 금액은 통화별 최소 단위 정수로 계산하고 반올림 시점을 정한다. 환율은 주기 배치로 갱신하되 갱신 실패 시 마지막 성공 값과 그 시각을 화면에 드러낸다.
- **유사 경험**: 시솔지주 환율 정보 배치와 국제 배송 서비스.
- **꼬리, 환율이 급변하면**: 표시용 참고 가격과 실제 주문 확정 가격을 구분하고, 확정 시점의 값을 주문에 고정한다.

### S3. 여러 택배사의 배송 상태를 하나로 보여주려면

- **공개 근거**: 배송 연동과 알림 자동화가 업무로 명시됨.
- **답변 골격**: 택배사별 어댑터가 각자의 상태 값을 내부 공통 상태로 바꾸고, 공통 상태는 허용된 전이만 받는다. 운송장 번호와 이벤트 시각을 유일 키로 저장해 재수집해도 중복이 생기지 않게 하고, 오래된 이벤트가 최신 상태를 덮지 않게 한다. 택배사 하나가 느려지면 그 소스만 격리하고 마지막으로 성공한 상태를 보여준다.
- **유사 경험**: 시솔지주 배송 정보 스크래핑.

### S4. 정산을 자동화할 때 가장 조심할 점

- **공개 근거**: 정산 업무 자동화가 명시됨. 정산 주체와 주기는 미확인.
- **답변 골격**: 정산은 틀리면 사후 정정 비용이 크므로 속도보다 재현 가능성과 대사를 우선한다. 정산 대상 구간과 입력 원장을 고정해 같은 입력이면 같은 결과가 나오게 하고, 정산 실행마다 식별자를 둬 재실행이 이중 정산을 만들지 않게 한다. 외부 원장(마켓, 결제사)과 내부 원장을 비교해 차이를 기록하고, 자동 보정은 조건이 명확한 경우로 제한한다.
- **유사 경험**: FIT C9 환불 정책 조율 사례(소속은 `[사용자 확인 필요]`), R2 이벤트 기반 자동화.

### S5. 주문, 배송 알림을 보낼 때 중복과 누락을 어떻게 막나

- **답변 골격**: 알림 사건마다 안정적인 식별자를 만들고 채널과 함께 유일하게 저장해 로컬 중복을 막는다. 알림 요청은 업무 데이터와 같은 트랜잭션에 기록한 뒤 별도 발송기가 보내게 해 누락을 줄인다. 발송사가 수락했는지 불명확한 건은 같은 키로 재시도하거나 발송 결과 조회로 닫는다. 발송 실패율과 대기 건수를 경보로 본다.
- **유사 경험**: 트라이포드랩 알림톡과 이메일 자동 리포트.

### S6. 처음 보는 기존 연동 코드를 고쳐야 한다면

- **공개 근거**: 기존 시스템을 점진적으로 개선하고 문서화하는 업무가 명시됨.
- **답변 골격**: 먼저 데이터 흐름을 따라가 입력, 상태 전이, 외부 호출, 재시도 위치를 그림으로 남긴다. 바꾸기 전에 현재 동작을 고정하는 테스트를 추가하고, 작은 변경을 배포해 지표로 확인한 뒤 넓힌다. 알게 된 실패 유형과 재처리 절차는 운영 문서로 남긴다.
- **유사 경험**: FIT C7 문서화 경험, 고객사 온프레미스 이전과 MongoDB에서 MySQL로의 데이터 이전.

## 2. 역질문

> 1차가 실무진 면접이고 공고상 다음 단계는 최종합격이다. 기술 질문을 아껴 두지 말고 이번에 역할의 실제 모습을 확인한다. 핵심 3개는 외워서 말하고 나머지는 시간에 맞춰 고른다.

1. **초기 과제와 성공 기준 (B1)**: 합류 후 가장 먼저 책임질 과제와, 계약 기간 동안 잘하고 있다고 판단하는 기준은 무엇인가요? 정규직 전환을 판단할 때 어떤 결과를 보시는지도 함께 듣고 싶습니다.
2. **기술 경계 (C1)**: 이 역할이 직접 맡는 서비스와 연동 범위는 어디까지이고, 신규 개발과 기존 시스템 개선의 비중은 어느 정도인가요?
3. **연동 실패의 현재 처리 방식 (C2, C3 변형, 회사 특이)**: 마켓이나 결제 연동이 실패하거나 중복될 때 지금은 어떤 신호로 알게 되고, 재처리는 자동과 수동 중 어느 쪽으로 하고 있나요?
4. **팀 구성과 협업 (A4)**: 현재 개발은 어떤 역할로 구성돼 있고, 코드 리뷰와 배포는 어떤 방식으로 하나요?
5. **화면 개발 비중 (회사 특이)**: 관리자와 고객용 화면 개발은 백엔드 업무 가운데 어느 정도 비중인가요? React 쪽은 입사 전에 어디까지 준비해 두면 좋을까요?
6. (시간이 남으면) **서비스 범위**: 빅타오와 리뷰브릿지는 셀록홈즈와 데이터나 연동을 공유하는 구조인가요?

**피할 것**: 급여와 복지 먼저 묻기, 재무와 투자 캐묻기, 공고 학력 표기 차이는 면접이 아니라 채용 담당 채널로 확인한다.

## 3. 면접 준비 체크리스트

### 면접 시작 전

- [ ] 면접 일시와 형식(대면 또는 화상), 참여 역할을 확인했다. 실명과 연락처는 적지 않는다.
- [ ] 퇴사와 이직 사유, 짧은 재직 기간, 공백 답변(FIT C1~C3)을 30초 안에 소리 내어 말해 봤다. 남은 `[사용자 확정 필요]` 슬롯은 계약직 수용 여부다.
- [ ] 이력서 경력 표기(트라이포드랩 2024.02~2026.05, 키노라이츠 2026.06~2026.09로 수정)와 면접에서 말할 내용이 서로 어긋나지 않는다.
- [ ] 셀록홈즈 홈페이지를 다시 보고, 가능하면 무료 체험으로 흐름을 한 번 확인했다.
- [ ] 역질문 핵심 3개(1, 2, 3번)를 외웠다.

### 보강할 기술 영역

| 영역 | 보강할 핵심 | 복습 |
| --- | --- | --- |
| 연동 신뢰성 | 조회형과 거래형 구분, timeout 종류, 재시도 조건, 3단계 분리 (J1, J3) | [ ] |
| 중복과 정합성 | 유일 제약, 조건부 상태 전이, check-then-act 레이스 (J2) | [ ] |
| 결제와 정산 | 결제 시도 선기록, 같은 키 재시도, 대사 배치와 유예 시간 (J4, S4) | [ ] |
| 배치 | 반개구간과 워터마크, 멀티 인스턴스 중복 실행 (J5) | [ ] |
| 프론트엔드 | React props, state, key 기본과 갭 답변 (J7) | [ ] |
| 리눅스 운영 | 장애 분석 순서와 명령어 (J8) | [ ] |

### 강하게 어필할 포인트

- 공고 업무 문장과 경험이 겹치는 지점: 시솔지주 국제 배송의 스크래핑과 환율 배치, 트라이포드랩의 동시성, 이벤트 기반 자동화, 알림 리포트.
- 수치는 이력서에 공개된 값만 쓰고, 각각의 측정 대상을 한 문장으로 붙인다.

### 공개 전 점검

- [x] 회사 사실은 공고와 셀록홈즈 공식 홈페이지로 확인했고 나머지는 미확인으로 표시했다.
- [x] 제3자 실명, 연락처, 발화 원문이 없다.
- [x] 처우 금액이 없다.
- [x] 전, 현 직장 비공개 정보와 사이드 프로젝트의 정량 수치가 없다.
