# 브랜뉴닷컴 1차 JD 기반 기술 질문

> [[Interview-Prep-BrandNewCom-1st|목차]]로 돌아가기. 공고의 업무 문장(연동 실패, 중복 처리, 재시도, 주문, 정산, 알림 자동화)과 자격, 우대 요건에서 뽑았다. 브랜뉴닷컴의 실제 연동 대상과 구조는 미확인이므로 설계형 질문은 가정을 먼저 말하고 답한다.

## J1. 외부 마켓 API 연동에서 실패를 어떻게 다루나 (설계형)

- **의도**: 타임아웃, 오류 분류, 재시도 조건을 구분하는지, 외부 장애가 내부로 번지지 않게 하는지 본다.
- **답변 골격**:
  1. 연동을 조회형(상품, 가격, 배송 상태)과 거래형(주문 확정, 결제, 취소)으로 나눈다. 조회형은 내결함성과 대체값, 거래형은 일관성과 멱등성이 우선이다.
  2. 호출마다 전체 deadline과 연결, 읽기 timeout을 명시하고, 마켓별로 커넥션과 동시 요청 수를 분리해 한 마켓의 지연이 다른 마켓 처리를 막지 않게 한다.
  3. 오류를 일시(타임아웃, 5xx), 한도(429), 영구(검증 실패, 권한 오류)로 나눠 일시와 한도만 재시도한다.
  4. 외부 호출은 DB 트랜잭션 밖에서 한다. 짧은 트랜잭션으로 중간 상태를 기록하고, 트랜잭션 밖에서 호출한 뒤, 조건부 UPDATE로 완료를 반영한다.
  5. 지속 실패하는 마켓은 호출을 잠시 멈추고 알림을 보낸다.
- **트레이드오프**: 서킷 브레이커는 빠른 실패를 주지만 회복 뒤 정상 복귀를 늦출 수 있다. 재시도 부하만 문제면 토큰 버킷 재시도 예산이 더 단순하다.
- **꼬리, timeout이 나면 실패인가**: 아니다. 응답 없는 timeout은 상대가 처리하지 않았다는 증거가 아니므로 비멱등 요청은 상태 조회로 먼저 확인한다.
- **내 경험**: 시솔지주 외부 API와 스크래핑, 트라이포드랩 알림 발송.

## J2. 같은 주문이 두 번 수집되거나 웹훅이 중복으로 오면 (설계형)

- **의도**: 중복을 정상 경로로 보는지, 확인 후 처리의 레이스를 아는지 본다.
- **답변 골격**:
  1. 자연 키에 유일 제약: `UNIQUE(market, market_order_id)` 같은 외부 식별자 기준 제약을 DB에 둔다. 코드의 조회 후 삽입만으로는 동시 수집에서 뚫린다.
  2. 원자적 처리: `INSERT ... ON DUPLICATE KEY UPDATE`나 삽입 실패를 중복 신호로 받는다. 단, 갱신 쪽이 카운터 증가나 부수효과를 만들면 멱등이 아니다.
  3. 상태 전이 가드: `UPDATE orders SET status = 'PAID' WHERE id = ? AND status = 'PENDING'`처럼 유효한 전이만 허용하고, 영향 행 수 0이면 이미 처리된 것으로 끝낸다.
  4. 부수효과(알림, 정산 기록)는 주문 식별자와 이벤트 종류로 만든 멱등 키로 한 번만 실행한다.
- **흔한 오답**: Redis `SET NX`를 처리 완료 표시로 먼저 써 버리는 것. 처리 전에 죽으면 작업이 유실된다. SET NX는 짧은 선점일 뿐이다.
- **꼬리, 순서가 뒤바뀌어 오면**: 외부 이벤트의 시각이나 버전을 저장하고 더 오래된 이벤트가 최신 상태를 덮지 않게 한다.
- **내 경험**: R1 잠금, R2 소비자 멱등성과 상태 전이 검증.

## J3. 재시도는 어떻게 설계하나 (사실형과 설계형)

- **핵심 답변**: 재시도는 멱등하거나 멱등 키로 중복 효과를 막은 요청에만, 한 계층에서만, 횟수와 전체 시간 상한을 두고, 지수 백오프에 지터를 섞어 한다. 상한을 넘으면 DLQ나 실패 상태로 보내 사람이 볼 수 있게 한다.
- **공식**: full jitter는 `sleep = random(0, min(cap, base * 2 ** attempt))`. 지터가 없으면 같은 순간 실패한 클라이언트들이 같은 순간 다시 몰린다.
- **흔한 오답**: 모든 4xx를 재시도하거나 모든 계층에서 재시도하는 것. 계층마다 3회씩 5계층이면 최하단 부하가 243배가 된다.
- **예외**: 429와 408은 재시도 대상일 수 있고 `Retry-After`가 있으면 우선한다.
- **꼬리, 주기 배치도 지터가 필요한가**: 여러 서버의 cron이 같은 초에 몰리면 외부 API 한도를 한꺼번에 쓴다. 서버마다 일관된 지연을 둔다.
- **출처**: [Exponential Backoff and Jitter — AWS Architecture Blog](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/), [RFC 6585, 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)
- **내 경험**: R1 당시 고정 간격 재시도의 한계와 개선안.

## J4. 결제는 됐는데 내부 주문 반영이 실패하면 (설계형)

- **의도**: 결제 상태의 정본이 어디인지, 불일치를 어떻게 수렴시키는지 본다.
- **답변 골격**:
  1. 결제 요청 전 내부에 결제 시도 레코드와 멱등 키를 먼저 저장한다.
  2. 동기 응답, 웹훅, 대사 배치가 모두 같은 완료 로직을 호출하게 해 경로마다 결과가 달라지지 않게 한다.
  3. 응답을 못 받았으면 새 키로 다시 결제하지 않고 같은 키로 재시도하거나 결제사 조회 API로 상태를 확인한다.
  4. 대사 배치가 결제사 거래 목록과 내부 원장을 주기적으로 비교한다. 차이는 즉시 취소하지 않고 반영 지연을 고려한 유예 시간 뒤 다시 조회하고, 설명되지 않는 건만 정책에 따라 처리하거나 수동 검토로 보낸다.
  5. 금액은 부동소수점이 아니라 최소 단위 정수로 다룬다.
- **트레이드오프**: 자동 보정은 운영 부담을 줄이지만 잘못된 취소의 비용이 크다. 처음에는 보수적으로 수동 검토 비중을 높인다.
- **정직 포인트**: PG 직접 연동 경험 범위는 `[사용자 확인 필요]`. 확인 전에는 원칙과 설계로만 답한다.
- **출처**: [Stripe, Idempotent requests](https://docs.stripe.com/api/idempotent_requests), [PortOne REST API V2](https://developers.portone.io/api/rest-v2?v=v2)

## J5. 주문 수집이나 정산 배치를 어떻게 만드나 (설계형)

- **답변 골격**:
  1. 수집 구간은 `from <= t < to` 반개구간으로 잡고 경계를 조금 겹쳐 다시 읽은 뒤 외부 식별자로 중복을 제거한다.
  2. 페이지를 저장한 뒤에만 커서나 워터마크를 전진시켜, 중간에 죽어도 이어서 재실행할 수 있게 한다.
  3. 한 건 실패로 배치 전체를 롤백하지 않고 실패 건만 원본과 함께 따로 보관한다.
  4. 큰 쓰기는 작은 트랜잭션으로 나눠 잠금 보유 시간을 줄인다.
- **NestJS 주의**: `@nestjs/schedule`은 프로세스 안에서 돌기 때문에 서버가 N대면 같은 cron이 N번 실행된다. 분산 락이나 전용 워커로 한 곳에서만 실행한다. 긴 작업은 `waitForCompletion`으로 같은 프로세스 안의 겹침을 막는다.
- **정지 감지**: 스케줄러가 조용히 죽으면 오류 로그가 0건이다. 마지막 성공 시각을 기록하고 임계를 넘으면 알린다.
- **출처**: [NestJS, Task scheduling](https://docs.nestjs.com/techniques/task-scheduling)
- **내 경험**: 환율 배치, IoT 리포트 배치, @nestjs/schedule과 @nestjs/bullmq.

## J6. 웹 스크래핑과 브라우저 자동화의 신뢰성 (설계형)

- **의도**: 200 응답을 성공으로 믿지 않는지, 차단과 구조 변경을 구분하는지 본다.
- **답변 골격**: 파싱 직후 구조, 값 범위, 집합 수준(건수 급감) 세 층으로 검증하고, 검증 실패는 데이터가 아니라 오류로 다룬다. 실패는 소스 단위로 집계해 일시, 차단, 구조 변경으로 분류하고 각각 다르게 대응한다. 실시간 수집과 재수집(백필)은 워커뿐 아니라 소스별 요청 예산도 나눈다.
- **규범**: robots.txt(RFC 9309)와 429 Retry-After를 따르고, 이용약관과 법적 허용 범위는 기술 규격과 별개로 소스별로 확인한다.
- **정직 포인트**: Puppeteer, Playwright 실무 경험은 없다. 헤드리스 브라우저는 페이지를 finally에서 닫고, 동시 페이지 수를 제한하며, 이미지와 폰트 요청을 막고, 주기적으로 브라우저를 재시작하는 자원 관리가 추가된다는 점만 원리로 말한다.
- **출처**: [RFC 9309, Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309.html)
- **내 경험**: R5 배송 정보 스크래핑.

## J7. React 화면을 만들거나 고쳐 본 적이 있나 (갭 질문과 사실형)

- **답변**:

> React로 화면을 만든 실무 경험은 없습니다. 지금까지 프론트엔드와는 OpenAPI 기반으로 요청, 응답, 실패 조건을 합의하며 협업했습니다. 관리자 화면 수정이 필요하면 기존 컴포넌트가 어떤 props와 state로 그려지는지부터 읽고, 작은 수정부터 리뷰를 받아 넓히겠습니다. 입사 전까지 목록, 검색, 상세 수정 정도의 관리자 화면을 직접 만들어 보겠습니다.

- **사실형 대비**: JSX는 HTML이 아니라 JavaScript로 변환되는 문법이다. props는 부모가 넘기는 읽기 전용 입력, state는 React가 보존하는 스냅숏이며 setter는 다음 렌더를 요청할 뿐 현재 변수를 바꾸지 않는다. 목록의 key는 형제 사이에서 안정적이고 고유해야 하며, 순서가 바뀌는 목록에 index를 key로 쓰면 상태가 다른 행에 붙을 수 있다.
- **흔한 오답**: `count && <Badge />`는 count가 0이면 0을 그린다.
- **출처**: [React, Describing the UI](https://react.dev/learn/describing-the-ui), [React, State as a Snapshot](https://react.dev/learn/state-as-a-snapshot)
- `[사용자 확인 필요]`: 사이드 프로젝트에서 직접 작성한 프론트엔드 코드가 있다면 그 범위만 사실대로 추가한다.

## J8. 리눅스 서버에서 장애가 나면 무엇부터 보나 (절차형)

- **답변 골격**: 영향 범위와 시작 시각을 먼저 확인하고, 직전 배포나 설정 변경을 본다. 그다음 자원을 본다. CPU와 부하(`top`, `uptime`), 메모리와 OOM 흔적(`free`, `dmesg`), 디스크 용량과 inode(`df -h`, `df -i`), 연결 상태(`ss`), 서비스 로그(`journalctl`, 애플리케이션 로그) 순서다. 원인보다 복구를 먼저 하고, 타임라인과 재발 방지 조치를 남긴다.
- **흔한 오답**: 로그부터 무작정 뒤지는 것. 영향 범위와 최근 변경을 먼저 좁혀야 탐색 범위가 준다.
- **꼬리, 디스크가 꽉 찼는데 지운 파일 용량이 안 돌아오면**: 프로세스가 아직 연 파일은 삭제해도 공간이 반환되지 않는다. `lsof`로 삭제된 열린 파일을 찾고 로그 로테이션 설정을 확인한다.
- **내 경험**: Amazon Linux 2, Ubuntu 운영, Grafana 경보, 리눅스마스터 2급.
