> 이력서, 포트폴리오, [[Common-Interview-Questions|FIT]], [[Self-Analysis|나찾기]]와 같은 회사의 이전 회고를 바탕으로 회사 맞춤 답변을 구성한다.
> 회사 사실은 공개 출처로 확인하고, 제3자는 역할로만 적는다. 연락처, 개인 처우 금액, 비공개 회사 정보와 제3자 발화 원문은 기록하지 않는다.

## 2. 회사 맞춤 FIT 답변

> `common/` 마스터의 공개 가능한 경험을 fork하고, 필요한 핵심을 이 문서에 자기완결적으로 적는다.

### 공개 가능한 성과 표기

- 수치는 공개 가능한 범위이고, 기준 기간, 전후 비교 기준, 측정 방법과 본인 기여 범위를 모두 설명할 수 있을 때만 쓴다.
- 고객, 계약, 조직 규모와 운영 지표를 추론하게 하는 수치는 쓰지 않는다. 공개하기 어렵다면 수치 대신 문제, 판단, 검증 방법과 배움을 말한다.

### 1분 자기소개

- 구조: 역할, 도메인 경험, 핵심 성과, 문제 해결 원칙, 회사와 역할 연결, 마무리
- 회사 연결은 공개된 문제와 역할 책임에만 근거한다.

### 지원 동기

- 구조: 회사가 공개적으로 설명한 문제, 내 관련 경험, 연결점, 기여하고 싶은 결과
- 확인되지 않은 문화, 성장 환경과 기술 과제를 사실처럼 말하지 않는다.

### 이직 사유

- 구조: 이전 역할에서 배운 점, 자기 기준으로 본 다음 과제, 지원 역할과의 연결
- 먼저 [[My-Motivation-Reasons#0. 직전 이직 사이클 변수 (다음 이직 전에 교체)|이직 사이클 변수]]와 [[Sensitive-Question-Answers|현재 회사 퇴사 이유 작성 규칙]]을 확인한다.
- 다음 사이클 변수가 비었거나 사용자가 현재 이직 사유를 확정하지 않았다면 과거 사이클 답변을 재사용하지 않는다.
- 외부 귀책으로 끝내지 않고 본인의 판단, 학습과 현재 적용을 함께 말한다.

## 3. 예상 질문과 답변

> 예상 질문은 공개 JD, 일반 질문 풀과 이전 회고에서 고른다. 이전 회고의 질문은 요약하고 제3자 표현을 원문으로 복제하지 않는다.

### 질문 카드 작성 형식

#### 사실형

- 질문 의도
- 한 문장 핵심 답변과 적용 조건
- 흔한 오답 또는 혼동하기 쉬운 경계
- 공식 출처 또는 학습 정본
- 꼬리 질문

#### 설계형

- 질문 의도
- 문제, 제약과 판단 기준
- 답변 골격
- 대안과 트레이드오프
- 검증 방법, 실패 시 대응과 한계
- 꼬리 질문

### 이력서 기반 기술 질문

#### 질문 제목

- 질문 유형: 사실형/설계형/경험형
- 질문 의도
- 핵심 답변 또는 답변 골격
- 문제, 제약, 선택, 검증과 한계
- 사실형일 때: 흔한 오답, 학습 정본이나 공식 출처
- 설계형일 때: 판단 기준, 대안과 트레이드오프
- 꼬리 질문 대비

### JD 기반 기술 질문

#### 질문 제목

- 질문 의도
- 핵심 답변 또는 답변 골격
- 공개된 역할 요건과 내 경험 연결
- 대안, 트레이드오프와 검증 방법
- 꼬리 질문 대비

### 서비스 맥락 질문

#### 질문 제목

- 공개 자료에서 확인한 문제
- 답변 골격과 판단 기준
- 대안과 트레이드오프
- 유사 경험과 한계
- 꼬리 질문 대비

### 컬처핏과 협업 질문

[[Common-Interview-Questions]]에서 역할과 관련된 항목을 고른다. 회사별 문서에는 선택한 마스터 답변을 fork하고 공개된 역할과의 연결을 끝줄에 붙인다.

#### 질문 제목

- 질문 의도
- 준비 포인트
- `common/` 마스터 fork 답변
- 회사와 역할 연결
- 꼬리 질문 대비

## 4. 역질문

### 역할과 기대치

- 이 역할이 먼저 해결할 문제와 성공 기준
- 공개 JD의 책임 가운데 실제 우선순위

### 기술과 협업

- 의사결정과 문서화 방식
- 역할이 협업하는 직무와 책임 경계

### 성장과 온보딩

- 초기 기대치와 피드백 방식
- 공개 자료로 확인되지 않은 부분은 질문으로만 두고 답을 추정하지 않는다.

## 5. 면접 준비 체크리스트

### 면접 시작 전

- [ ] 회사, 포지션, 일시, 차수와 형식을 확인했다.
- [ ] 참석자는 실명이나 연락처 대신 역할로만 적었다.
- [ ] 공개된 채용 절차와 현재 차수를 구분했다.
- [ ] 핵심 역질문 2~3개와 보충 질문 1~2개를 골랐다.

### 보강이 필요한 기술 영역

| 영역 | 보강할 핵심 개념과 판단 기준 | 복습 완료 |
| --- | --- | --- |
| DB와 성능 | | [ ] |
| 아키텍처와 설계 | | [ ] |
| 프레임워크와 런타임 | | [ ] |
| 인프라와 운영 | | [ ] |
| 테스트와 품질 | | [ ] |

### 강하게 어필할 포인트

- 매칭도가 강한 항목 중 역할의 사용자 문제와 직접 연결되는 경험을 고른다.
- 성과를 말할 때는 공개 가능한 수치의 기준 기간, 비교 조건, 측정 방법과 본인 역할을 함께 준비한다.

### 공개 전 점검

- [ ] 회사 관련 사실에 공개 근거가 있거나 `미확인`으로 표시했다.
- [ ] 제3자 실명, 연락처와 발화 원문이 없다.
- [ ] 본인 처우 금액과 비공개 계약 조항이 없다. 고용 형태, 역할, 시작일과 전형 상태 같은 비금액 조건은 보존했다.
- [ ] 고객, 계약, 조직 계획, 운영 수치와 내부 구현 같은 비공개 회사 정보가 없다.
- [ ] 성과 수치에는 기준 기간, 비교 조건, 측정 방법, 본인 기여 범위와 공개 가능 여부가 있다.
- [ ] 같은 회사의 이전 질문과 본인 답변은 회고에서 요약해 가져왔다.
- [ ] 링크한 마스터, 회고와 기술 정본이 실제로 존재한다.
