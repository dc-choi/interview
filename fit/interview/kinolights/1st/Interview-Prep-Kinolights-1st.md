### 강점 카드

- **0→1과 운영 책임**: 이전 회사에서 백엔드와 운영 경계를 함께 설계하며 기능 구현 뒤의 장애, 배포와 복구까지 책임졌다.
- **기술 의사결정**: 메시지 처리, 실행 환경, 데이터 조회 경로를 기능 목록이 아니라 전달 보장, 운영 부담, 비용과 롤백 가능성으로 비교했다.
- **정합성과 성능**: 동시 갱신은 DB 트랜잭션으로, 조회 병목은 실행계획과 복합 인덱스로, 후속 작업은 멱등성과 재처리 경계로 다뤘다.
- **협업**: 제품 규칙이 흔들릴 때 기획 의도와 화면 계약을 확인하고, 합의를 테스트로 고정해 재해석과 회귀를 줄였다.

### 갭과 대응

| 영역 | 답변 원칙 |
|---|---|
| 연차 | 당시 공고의 5년 이상 기준에 비해 약 1년이 부족했다. 숫자를 부정하지 않고, 해결한 문제의 깊이와 검증 방식을 근거로 설명한다. |
| TypeORM | Prisma 경험을 단순 도구 숙련으로 포장하지 않는다. ORM이 만든 SQL과 실행계획을 확인한 경험을 근거로, 데이터 매퍼와 쿼리 빌더의 사용 경계를 빠르게 익히겠다고 답한다. |
| GraphQL Federation | 실무 경험은 없다고 먼저 말한다. 서브그래프 경계, N+1, DataLoader, 스키마 변경 호환성은 학습했고 실제 경계와 운영 규칙은 팀에 확인하겠다고 한다. |
| OpenSearch와 검색 | 직접 운영 경험은 없음을 인정한다. 색인, 분석기, 동의어, 랭킹과 가용성 최신성이 사용자 검색 품질에 영향을 준다는 점을 이해하고, 공식 문서와 작은 재현부터 학습하겠다고 한다. |
| DynamoDB, Serverless Framework, release-please와 Monorepo | 액세스 패턴 우선 모델링, 서버리스 실행 경계와 배포 자동화의 원리는 이해하지만 해당 도구의 실무 사용은 구분해 말한다. 실제 사용 범위와 운영 기준은 질문으로 확인한다. |

## 3. 핵심 전략

1. **메인 서사**: 작은 조직에서 백엔드, 운영과 기술 의사결정을 함께 맡아 0→1부터 안정화까지 완주한 경험을 발표 전체에 일관되게 연결한다.
2. **결정과 트레이드오프**: 어떤 도구를 썼는지보다 무엇이 실패할 수 있었고, 어떤 대안을 포기했으며, 무엇으로 검증했는지를 먼저 말한다.
3. **재지원의 변화**: 첫 지원 때는 경험의 넓이를 설명하는 데 그쳤다면, 이번에는 운영 안정성과 기술 판단의 축으로 자신의 강점을 정확히 설명한다.
4. **팀 협업의 다음 단계**: 단독 주도성을 증명한 뒤에는 동료와 설계를 다듬고 피드백 루프를 만들며 깊이를 더하고 싶다는 판단을 말한다.
5. **모르는 영역의 태도**: 모른다고 말한 뒤 인접 원리, 학습 순서, 실제 적용 전 확인할 조건을 짧게 붙인다.

## 4. 사전 확인과 리허설

- [ ] 발표 자료와 사전질문지의 지원 동기가 같은 기준으로 이어지는지 확인
- [ ] 발표는 28분 안팎으로 연습하고 질의응답을 위한 여유를 남김
- [ ] 회사 공개 사실, 내 경험 사실, 면접에서 확인할 가설을 구분
- [ ] 외부 귀책 없이 이직과 실패를 내 판단, 학습, 다음 적용 순서로 설명
- [ ] GraphQL, 검색, ORM 갭 질문은 한계, 인접 지식, 학습 계획 순서로 답변
