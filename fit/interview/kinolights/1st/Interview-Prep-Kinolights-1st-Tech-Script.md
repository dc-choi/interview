# 키노라이츠 1차, 30분 기술 발표 대본

> 2026-06-08 1차 실무 인터뷰 발표용. 누적 목표는 28분이며 질의응답을 위한 여유를 남긴다.
> 발표는 실제 경험의 요약이다. 이전 회사의 고객명, 운영 수치, 비공개 시스템 구성과 대상 회사의 내부 정보는 말하지 않는다.

## 0. 오프닝 [0:00~0:30]

안녕하세요, 4년차 백엔드 개발자 [이름]입니다. 제 경험을 한 문장으로 줄이면, 작은 팀이 운영할 수 있는 데이터 서비스가 되도록 기술 결정을 제품 단계와 함께 내려온 시간입니다. 오늘은 트라이포드랩에서 백엔드를 설계하고 운영하며 겪은 문제를 시간 순서대로 말씀드리겠습니다.

## 1. 약력과 발표의 관점 [0:30~2:00]

초기에는 이썸테크에서 Java와 Spring으로 기본기를 쌓았습니다. 이후 시솔지주에서는 배치 안정화, 테스트와 인증 기능을 다루며 운영 품질을 책임지는 법을 배웠습니다. 트라이포드랩에서는 현장 장비 데이터가 서비스 결과로 이어지는 백엔드를 0→1부터 운영까지 맡았습니다.

오늘의 관점은 기술 나열이 아니라 **문제, 선택, 검증, 남은 한계**입니다. 제품을 정상화하고, 관측을 만들고, 실행 환경과 정합성을 다듬은 뒤, 복잡한 후속 처리를 이벤트로 분리한 흐름으로 설명하겠습니다.

## 2. 출발점과 목표 [2:00~4:00]

처음에는 기능은 있었지만 핵심 규칙의 실패를 빠르게 찾기 어렵고, 운영 신호와 배포 경계도 충분하지 않았습니다. 데이터 입력, 처리와 사용자 결과가 한 경로에 얽혀 있었기 때문에 하나의 문제가 다른 부분으로 전파될 위험이 있었습니다.

목표는 화려한 구조가 아니라 다음 네 가지였습니다.

1. 제품 규칙을 재현 가능한 테스트로 고정한다.
2. 운영 이상을 사용자 영향 전에 발견한다.
3. 확장과 배포가 정합성을 깨지 않게 한다.
4. 독립적인 후속 작업은 실패를 격리하고 재처리할 수 있게 한다.

## 3. 제품 규칙을 테스트로 정상화 [4:00~6:30]

합류 초기에 핵심 기능의 동작이 불안정해 제품을 안정화하는 일이 우선이었습니다. 기획과 프론트엔드가 규칙과 화면 계약을 맞추는 동안, 저는 백엔드의 규칙을 테스트 코드로 고정했습니다. 단위 테스트만으로는 데이터베이스와 실제 변환 경계의 오류를 찾기 어려워 실제 DB에 붙는 통합 테스트를 추가했습니다.

이 선택의 핵심은 테스트 수가 아니라 합의의 재사용입니다. 규칙이 바뀌면 영향 범위를 테스트가 먼저 보여 주고, 의도한 변경은 테스트와 함께 고칠 수 있습니다. 지금이라면 더 이른 시점부터 핵심 사용자 경로의 자동 검증을 배포 게이트에 두겠습니다.

## 4. 보이지 않던 운영을 관측 가능하게 [6:30~10:00]

오류가 반복되는데 원인을 좁히는 시간이 길었습니다. 그래서 메트릭, 구조화 로그와 요청 문맥을 연결하는 관측 기반을 만들었습니다. 도구는 오픈소스 스택을 직접 운영했지만, 중요한 것은 특정 제품명이 아니라 탐색, 보존, 경보와 운영 부담을 비교한 판단입니다.

- 메트릭은 수집 지연, 오류와 포화 구간을 보여 준다.
- 로그는 요청 문맥과 실패 원인을 추적한다.
- 고유 식별자는 로그와 트레이스 연결에 두고, 메트릭 라벨에는 넣지 않아 카디널리티 폭발을 막는다.
- 초기 경보는 운영 기준선에 맞춘 정적 임계였다. 이후에는 사용자 영향 SLI와 목표 기간을 정해 SLO 기반 경보로 발전시킬 수 있다.

관측을 만든 뒤에야 다음 선택을 감이 아니라 실제 포화와 지연 신호에 근거해 할 수 있었습니다.

## 5. 실행 환경과 정합성을 함께 설계 [10:00~15:00]

트래픽과 배포 위험이 하나의 실행 환경에 함께 몰리면서, 요청 성격과 배포 경계를 분리할 필요가 생겼습니다. 컨테이너 기반 실행 환경을 선택할 때는 기존 운영 역량, 워크로드 종류, 롤백과 운영 인력을 비교했습니다. 더 복잡한 오케스트레이션은 향후 다수 워크로드와 운영 요구가 생길 때 재검토할 선택지로 남겼습니다.

스케일아웃은 동시 갱신 문제와 분리할 수 없었습니다. 여러 인스턴스가 같은 상태를 갱신하면 인메모리 제어만으로는 충분하지 않습니다. 그래서 보호할 대상이 DB 행인 경우 트랜잭션 안에서 락과 갱신을 같이 처리했습니다.

- 충돌 빈도가 높은 경로에서는 비관적 락과 제한된 재시도를 검토한다.
- 여러 행을 잠글 때는 일관된 순서를 사용해 데드락 확률을 낮춘다.
- DB 밖 자원을 함께 조정할 필요가 있을 때만 분산 조정을 검토한다.
- 금액이나 수량처럼 정확도가 중요한 값은 부동소수점 대신 정밀한 표현과 반올림 규칙을 사용한다.

## 6. 성능은 실행계획으로 검증 [15:00~19:30]

성능 문제는 세 가지 원칙으로 다뤘습니다.

첫째, 최신 상태 조회가 느릴 때는 실제 실행계획에서 정렬과 후보 행 스캔을 확인하고, equality 조건과 정렬 순서를 맞춘 복합 인덱스로 범위를 줄였습니다. 전체 조회 안에서 관측한 서브쿼리 지연과 별도로 측정한 쿼리 1건의 전후 결과는 같은 지표로 비교하지 않았습니다. 실행 환경, cache 상태, 표본 수와 percentile이 남지 않은 수치는 다른 조건과 직접 비교하지 않습니다. 인덱스는 읽기를 빠르게 하지만 쓰기 비용도 늘리므로, 데이터 분포가 바뀌면 다시 측정해야 합니다.

둘째, 당시 `relationJoins` Preview 기능이 비활성인 Prisma 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했습니다. 기능을 활성화하고 `relationLoadStrategy: 'join'`을 적용한 뒤, MySQL에서 correlated subquery와 JSON aggregation 형태의 단일 쿼리가 생성되는지 실행계획으로 확인했습니다. 옵션 이름만으로 SQL `JOIN`을 가정하지 않습니다. 단순 CRUD는 ORM의 생산성을 유지하고, 복잡한 조회는 쿼리 빌더나 명시적 SQL로 내려가 같은 조건에서 비교하는 경계를 만들었습니다.

셋째, 최적화가 회귀하지 않도록 주요 경로에 부하 테스트를 두었습니다. 동시성은 예상 처리량과 응답시간으로 가설을 세우고, 운영 환경과의 차이는 절대 수치가 아닌 상대 회귀 감시로 보정했습니다.

## 7. 후속 처리의 이벤트 분리 [19:30~24:00]

마지막으로 복잡한 도메인 처리에서 핵심 상태 변경과 독립적인 후속 작업을 분리했습니다. 동기 호출로 모두 묶으면 한 단계의 실패가 전체 흐름을 막고, 재처리와 확장이 어려워집니다. 도메인 이벤트를 기준으로 관리형 이벤트 버스와 큐를 사용해 워커가 독립 처리하도록 만들었습니다.

- 선택 기준은 리플레이, 순서 보장, 처리량, 비용과 운영 부담이었다.
- 적어도 한 번 전달을 전제로 멱등성 키, 상태 전이와 DLQ를 설계했다.
- 영구 오류와 일시 오류를 구분해 재시도 예산과 수동 복구 경계를 분리했다.
- 돌아보면 DB 저장 성공 뒤 발행 실패를 더 강하게 막기 위해 Transactional Outbox를 처음부터 적용했을 것이다.

이 사례는 도구 선택보다 기술 결정을 제품 단계와 복구 가능성에 맞춰야 한다는 학습을 남겼습니다.

## 8. AI 도구와 검증 책임 [24:00~25:30]

혼자 맡는 영역이 넓을수록 속도와 품질을 동시에 관리해야 했습니다. AI는 반복 작업의 보조로 쓰되, 저장소 규칙, 공식 문서, 테스트와 코드 리뷰를 연결해 결과를 검증했습니다. 설계와 최종 의사결정의 책임은 직접 가지는 것이 원칙입니다.

## 9. 마무리, 키노라이츠 연결 [25:30~28:00]

저는 제품 규칙을 테스트로 안정화하고, 관측으로 운영을 보이게 하며, 정합성과 성능을 지킨 뒤, 독립 작업을 이벤트로 분리해 왔습니다. 키노라이츠의 공개 제품 표면에서 보이는 콘텐츠 탐색과 시청 가능 정보의 신뢰 문제는, 여러 입력의 최신성과 정합성을 사용자 결과로 연결하는 문제로 이해했습니다. 검색과 추천은 새로 깊게 배울 영역이지만, 운영 안정성과 데이터 품질을 다루는 제 경험을 그 도메인에서 더 깊게 쓰고 싶습니다. 감사합니다.
