# 키노라이츠 1차, 섹션별 꼬리질문 드릴

> 2026-06-08 기술 발표 중 끊고 들어오는 질문을 대비한다. 각 질문은 1차 답변, 꼬리 1개, 더 깊은 꼬리 1개 순서로 소리 내어 답한다.
> 이전 회사의 고객, 운영 수치와 비공개 구성은 일반화한다. 대상 회사의 실제 기술 구조는 아는 척하지 않고 역질문으로 확인한다.

## 1. 약력과 이직 판단

**Q. 프로젝트 중심 개발에서 제품 개발로 옮긴 이유는?**

- 1차: 기능을 만드는 것보다 실제 사용, 운영, 장애와 개선이 이어지는 사이클을 책임지고 싶었다.
- D2: 언어가 아니라 운영 책임이 이어지는 환경을 선택했다.
- D3: 다음에도 쉽게 떠나는 것 아니냐면, 이전 선택은 부족한 축을 채운 과정이었고 이제는 2~3년 동안 한 도메인과 팀에 깊게 기여할 기준이 분명하다고 답한다.

**Q. 단독으로 맡은 경험이 있는데 왜 팀 환경을 원하는가?**

- 1차: 주도성은 검증했고, 다음에는 설계와 운영 결정을 동료와 검토하며 더 깊게 만들고 싶다.
- D2: 의사결정의 근거를 문서, 테스트와 리뷰로 남겨 피드백 루프를 만든다.
- D3: 팀이 있어도 책임을 넘기지 않고, 내 영역의 문제 정의와 복구까지 끝까지 맡겠다고 답한다.

**Q. 학습 과정에서 얻은 방식이 실무에 어떻게 이어졌는가?**

- 1차: 시스템 프로그래밍과 협업 과제에서 모르는 것을 자료와 실험으로 확인하고, 동료가 납득할 수 있게 설명하는 방식을 익혔다.
- D2: 실무에서는 공식 문서, 작은 재현, 테스트와 실행 결과를 같은 순서로 써서 추측을 줄였다.
- D3: 혼자 결론을 고집하지 않고 문서와 리뷰로 반례를 받아들이는 경로를 만든다고 답한다.

## 2. 제품 정상화와 테스트

**Q. 불안정한 제품을 어떻게 정상화했는가?**

- 1차: 기획 의도와 화면 계약을 다시 확인하고, 백엔드 규칙을 테스트로 고정했다.
- D2: 단위 테스트로 충분하지 않은 DB, 변환과 정합성 경계는 실제 DB 통합 테스트로 검증했다.
- D3: 규칙 변경 때 테스트가 깨지는 것은 족쇄가 아니라 영향 범위를 보여 주는 장치라고 설명한다.

**Q. 협업에서 본인의 역할은 무엇이었나?**

- 1차: 규칙 해석을 합의하고, 백엔드에서는 그 합의를 검증 가능한 테스트로 만들었다.
- D2: 사람의 주장보다 사용자 영향과 계약을 같은 화면에 올려 판단했다.
- D3: 합의가 바뀌면 테스트, 문서와 배포 순서를 함께 갱신해 재해석을 막는다.

## 3. 관측과 운영

**Q. 왜 관측 기반을 직접 만들었나?**

- 1차: 오류가 반복될 때 추측이 아니라 수집 지연, 오류, 포화와 요청 문맥으로 원인을 좁히고 싶었다.
- D2: 메트릭은 추세와 포화를, 로그는 개별 실패 문맥을, 트레이스는 경계 간 흐름을 보여 준다고 구분한다.
- D3: 도구 선택은 탐색, 보존, 경보, 총운영비와 팀 역량을 함께 비교한 단계 의존적 판단이었다고 답한다.

**Q. 메트릭 카디널리티는 어떻게 관리했나?**

- 1차: 사용자나 요청처럼 고유한 값은 메트릭 라벨이 아니라 로그와 트레이스 문맥에 둔다.
- D2: 경로는 정규화하고, 필요한 집계는 recording rule로 미리 만든다.
- D3: SLO 경보를 도입한다면 먼저 사용자 영향 SLI와 목표 기간을 합의하고, 정적 임계와 구분한다.

## 4. 실행 환경과 배포

**Q. 컨테이너 실행 환경을 선택한 기준은?**

- 1차: 기존 운영 역량, 워크로드 수, 트래픽, 롤백과 운영 부담을 비교해 현재 단계에 맞는 선택을 했다.
- D2: 더 복잡한 오케스트레이션은 여러 워크로드, 세밀한 제어와 운영 인력이 필요한 시점에 재검토한다.
- D3: 선택이 영구 정답이 아니므로 포화 지표, 배포 위험과 복구 비용이 바뀌면 다시 판단한다.

**Q. 무중단 배포와 롤백은 어떻게 다루나?**

- 1차: 헬스체크와 점진 전환으로 새 버전을 확인하고, 문제면 이전 버전으로 되돌릴 경로를 남긴다.
- D2: 스키마는 확장 후 수축하는 방식으로 두 버전의 호환성을 보장한다.
- D3: API와 워커는 진행 중 요청, 메시지 가시성 시간과 재전달을 고려해 종료 순서를 설계한다.

## 5. 동시성 및 정밀도

**Q. 왜 비관적 락을 선택했는가?**

- 1차: 같은 상태의 충돌 빈도가 높고, 보호 대상이 DB 행이어서 락과 갱신을 하나의 트랜잭션으로 처리하는 것이 단순하고 안전했다.
- D2: 충돌이 드문 읽기 중심 경로라면 버전 기반 낙관적 락을 검토한다.
- D3: 데드락은 완전히 없애기보다 락 획득 순서 통일, 트랜잭션 축소와 재시도로 회복한다.

**Q. 분산 락은 왜 쓰지 않았나?**

- 1차: DB 행만 보호하면 DB 트랜잭션이 이미 원자성을 제공한다.
- D2: 별도 락은 TTL, 크래시와 DB 상태의 불일치, 운영 복잡성을 추가한다.
- D3: 여러 저장소나 외부 자원을 하나로 조정해야 하는 상황이면 분산 조정을 다시 검토한다.

## 6. 성능과 ORM

**Q. 복합 인덱스는 어떤 근거로 설계했나?**

- 1차: 실제 실행계획에서 후보 행 스캔과 정렬 병목을 확인한 뒤 equality 조건과 정렬 순서를 맞췄다.
- D2: 인덱스는 읽기를 빠르게 하지만 쓰기 비용을 늘리므로, 쿼리 패턴과 데이터 분포가 바뀌면 다시 측정한다.
- D3: 커버링 인덱스, 파티셔닝과 캐시는 실행계획만으로 결정하지 않고 사용 패턴과 갱신 비용을 함께 본다.

**Q. ORM의 한계를 어떻게 다뤘나?**

- 1차: 관계 조회에서 실제 SQL과 실행계획을 보고 원인을 좁힌 뒤 로딩 전략을 검증했다.
- D2: 단순 CRUD는 ORM의 타입과 마이그레이션 이점을 유지하고, 복잡한 조회만 쿼리 빌더나 명시적 SQL로 분리했다.
- D3: TypeORM이든 다른 ORM이든 추상화 비용을 실행계획까지 확인하는 원칙은 같다고 답한다.

## 7. 이벤트 기반 후속 처리

**Q. 왜 동기 호출 대신 이벤트와 큐를 썼나?**

- 1차: 핵심 상태 변경 뒤의 독립 작업을 분리하면 실패가 전체 흐름을 막지 않고 재처리와 확장이 쉬워진다.
- D2: 전달 보장, 순서, 리플레이, 처리량과 운영 부담을 비교해 관리형 큐와 스트림 플랫폼을 구분한다.
- D3: 실제 요구가 순서 보장이나 대규모 리플레이라면 해당 도메인만 스트림 플랫폼으로 분리할 수 있다.

**Q. 중복 처리와 발행 실패는 어떻게 막나?**

- 1차: 실제 구현에서는 소비자의 멱등성 키, 상태 전이와 유니크 제약으로 중복을 흡수하고, 실패는 DLQ와 수동 복구로 격리했다. Transactional Outbox는 적용하지 않은 개선안이다.
- D2: DB 저장 성공 뒤 발행 실패는 듀얼 라이트 문제이며, 다시 설계한다면 Transactional Outbox로 완화한다.
- D3: 규모와 운영 복잡도에 따라 폴링 릴레이와 CDC 중 단순한 쪽부터 선택한다고 답한다.

## 8. 검색, API와 갭 질문

**Q. 검색 엔진 경험이 부족한데 어떻게 기여하나?**

- 1차: 직접 운영 경험은 없다고 먼저 말한다.
- D2: 색인, 분석기, 동의어, 랭킹과 가용성 최신성이 검색 품질을 만든다는 점을 학습했고, 작은 재현과 공식 문서로 기본기를 쌓겠다고 답한다.
- D3: 실제 데이터 계약, 갱신 주기와 품질 지표는 입사 후 팀의 맥락을 먼저 확인한다고 답한다.

**Q. GraphQL Federation은 어떻게 학습할 것인가?**

- 1차: 서브그래프 경계와 단일 스키마의 목적은 이해하지만 실무 운영 경험은 없다고 말한다.
- D2: N+1, DataLoader, 스키마 호환성과 변경 거버넌스를 핵심 위험으로 본다.
- D3: 팀이 이미 정한 경계와 운영 규칙을 먼저 읽고 작은 변경으로 검증하겠다고 답한다.

## 9. AI 도구와 품질

**Q. AI가 만든 코드의 품질은 어떻게 통제하나?**

- 1차: AI는 반복 구현을 돕지만, 사람이 요구사항, 설계와 최종 채택을 책임진다.
- D2: 저장소 규칙, 공식 문서, 테스트, 실행 결과와 코드 리뷰를 함께 통과시킨다.
- D3: AI가 제시한 결론은 가설로 두고, 성능과 정합성처럼 영향이 큰 결정은 직접 재현과 검증을 한다.
