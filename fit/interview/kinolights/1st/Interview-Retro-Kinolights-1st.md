## 실제 질문 흐름과 당시 답변

### 1. 발표, 설계 선택과 운영 경험

- 발표에서는 불안정했던 제품 흐름을 정상화하고, 단일 서비스 운영에서 정합성, 확장, 비동기 처리, 실패 복구와 관측을 함께 고민한 경험을 설명했다. 기획 의도와 화면 계약을 다시 확인하고 실제 데이터베이스 통합 테스트로 규칙을 고정한 과정도 포함했다. 정확한 운영 규모, 성능 수치와 내부 토폴로지는 일반화해 남긴다.
- **질문 요지:** Kubernetes 계열 오케스트레이션과 더 단순한 관리형 컨테이너 서비스를 왜 비교했는가?
  - **당시 답변:** 기존 컨테이너와 배포 자동화 흐름을 크게 바꾸지 않으면서 확장성을 얻고, 현재 팀이 감당할 운영 복잡도를 넘기지 않기 위해 더 단순한 관리형 서비스를 골랐다고 답했다.
- **질문 요지:** 이벤트 스트리밍 플랫폼까지 왜 고려했는가?
  - **당시 답변:** 여러 후속 작업을 느슨하게 연결하고 실패를 격리하기 위해 이벤트 기반 설계를 검토했고, 다른 사람이 정한 선택이 아니라 직접 고민한 판단이라고 답했다.
- **질문 요지:** 실제 부하가 크지 않은데 미리 복잡하게 설계한 것은 아닌가?
  - **당시 답변:** 관측 지표로 병목과 수요를 확인하며 필요한 시점에 판단한다고 답했다.

### 2. 관측과 가시성

- **질문 요지:** 기존 모니터링의 한계가 애플리케이션 오류였는지 트래픽 볼륨이었는지 물었다.
  - **당시 답변:** 단순한 수집 문제가 아니라 개발 외 역할도 상태를 이해할 수 있는 시각화와 가시성의 문제였다고 답했다.
- 관리형 모니터링에서 오픈소스 관측 도구로 보완한 과정, 장기 데이터 보관 방식, 요청 식별자를 메트릭 라벨에 넣어 카디널리티가 폭증한 뒤 로그 본문으로 옮긴 경험을 설명했다.
- **현재 교정:** 제품명과 배치 구조보다 메트릭 라벨은 값의 종류가 제한된 차원에만 쓰고, 요청 단위 식별자는 로그나 트레이스에 둔다는 원칙을 먼저 말한다.

### 3. 동시성, 잠금과 금액 정합성

- **질문 요지:** 같은 품목을 여러 장비가 동시에 변경할 때 레이스 컨디션을 어떻게 막았는가?
  - **당시 답변:** 같은 데이터베이스 행을 직렬화하는 비관적 잠금을 사용했고, 별도 분산 잠금은 운영 복잡도와 단일 장애 지점을 늘릴 수 있어 보류했다고 답했다.
- **질문 요지:** 잠금 실패 뒤 여러 요청이 함께 재시도하면 thundering herd가 생기지 않는가?
  - **당시 답변:** 단일 데이터베이스이므로 발생하지 않는다고 답해 핵심을 피했다.
  - **현재 교정:** 단일 데이터베이스여도 같은 행에 경쟁하면 대기와 동시 재시도가 몰릴 수 있다. 업무 의미에 맞게 즉시 실패 또는 제한된 대기를 택하고, 재시도에는 지수 백오프, 지터와 상한을 둔다.
- **질문 요지:** 분산 잠금은 언제 적절한가?
  - **당시 답변:** 데이터베이스 트랜잭션만으로 묶을 수 없는 외부 API 작업까지 조정해야 할 때 검토한다고 답했다.
- **질문 요지:** 금액 정합성은 어떻게 지켰는가?
  - **당시 답변:** 이진 부동소수점 대신 십진 표현을 사용하고 통화별 반올림 규칙을 명시했다고 답했다.

### 4. 성능과 데이터 접근

- 인덱스와 조회 전략을 바꿔 느린 경로를 큰 폭으로 개선하고, ORM의 관계 로딩과 데이터베이스 내부 변환이 병목이 된 구간에는 타입 안전한 쿼리 빌더를 제한적으로 사용한 경험을 설명했다.
- **질문 요지:** 초 단위로 느려질 때까지 왜 문제를 더 일찍 알지 못했는가?
  - **당시 답변:** 단독 운영이라 모든 구조를 완벽하게 만들 수 없었다고 먼저 답해 변명처럼 들렸다.
  - **현재 교정:** 당시 해당 조회 경로가 슬로우 쿼리 알림 범위에 들어오지 않았던 관측 공백을 먼저 인정하고, 탐지 범위를 어떻게 보완했는지 말한다.
- **질문 요지:** 원시 쿼리나 서브쿼리를 직접 다듬는 대신 쿼리 빌더를 택한 이유는 무엇인가?
  - **당시 답변:** 타입 안정성과 유지보수성을 우선했고, 성능이 중요한 경로에만 제한적으로 사용해 추상화와 직접 제어 사이의 균형을 잡았다고 답했다.

### 5. 이벤트 처리와 기술 선택

- **질문 요지:** 트랜잭셔널 아웃박스가 어떤 문제를 푸는지 설명해 달라는 질문이었다.
  - **당시 답변:** 업무 데이터 저장은 성공했지만 네트워크를 통한 메시지 발행이 실패하는 듀얼 라이트 문제를 줄이기 위해, 같은 데이터베이스 트랜잭션에 발행할 이벤트를 함께 기록한다고 설명했다. 실제 운영에는 적용하지 않은 개선안이라는 점도 밝혔다.
- **질문 요지:** 아웃박스를 폴링한 뒤 다시 외부 메시징으로 전달하는 구조는 폴링과 이벤트 방식을 섞은 것 아닌가? 소비자가 곧바로 처리하면 안 되는가?
  - **당시 답변:** 각 단계의 책임을 한 문장으로 나누지 못하고 빙빙 돌았다.
  - **현재 교정:** 아웃박스는 업무 데이터와 발행 대상 기록의 원자성을, 릴레이는 기록 전달을, 외부 브로커는 인스턴스 간 전달, 버퍼링과 소비자 분산을 담당한다. 릴레이가 폴링인지 CDC인지는 전달 방식의 선택이며, 인메모리 이벤트만으로는 여러 인스턴스에 내구성 있게 전파할 수 없다.
- **질문 요지:** 서버리스 실행 환경은 왜 고려하지 않았는가?
  - **당시 답변:** 혼자 운영해 별도 코드와 배포 단위를 관리하는 비용이 크다고 봤다고 답했고, 더 검토했어야 했다는 점은 인정했다.
  - **현재 교정:** 실행 시간, 빈도, 콜드 스타트 허용도, 재시도 의미와 운영 단위 수를 비교해야 한다. 혼자라서라는 이유만으로 결론내리지 않는다.
- **질문 요지:** 넓은 기술 후보를 검토할 때 비용 균형을 어떻게 잡았는가?
  - **당시 답변:** 초기에는 선택지를 넓게 보느라 운영 비용 판단이 부족했고, 고정비가 큰 스트리밍 서비스와 아웃박스 개선안은 실제 적용하지 않았다고 솔직히 답했다.
  - **현재 교정:** 당시 말한 정확한 가격은 구성, 저장량, 시간과 전송량 가정이 없어 재현할 수 없으므로 다시 인용하지 않는다. 고정비와 사용량 과금, 운영 인력 비용을 같은 조건에서 비교한다.
- **질문 요지:** 특정 기술 스택을 꼭 쓰고 싶은 열망이 있는가?
  - **당시 답변:** 기술 자체에 대한 열망은 없고, 회사의 필요를 도메인 이해와 기존 시스템의 역사로 판단해 선택한다고 답했다.
  - **당시 판단:** 이번 면접에서 가장 잘 작동한 시니어 관점의 답변이었다.

### 6. 기초 단답, 당시 답변과 현재 교정

- **Promise**
  - **당시 답변:** 콜백 중첩을 줄이고 resolve와 reject로 결과를 다룬다고 설명했지만 세 상태를 바로 떠올리지 못했다.
  - **현재 교정:** Promise는 비동기 작업의 최종 완료 또는 실패를 나타내며 pending에서 fulfilled 또는 rejected로 한 번만 전이된다. 생성자 실행 함수는 즉시 실행되고, then과 catch의 반응은 마이크로태스크로 처리된다.
- **protected**
  - **당시 답변:** 상속받은 자식 클래스에서 접근할 수 있다고 답했다.
  - **현재 교정:** TypeScript의 protected는 선언 클래스와 하위 클래스에서 접근할 수 있게 하는 컴파일 시점 제약이다. JavaScript 런타임 보안 경계가 아니며 타입과 함께 소거된다.
- **대칭키와 비대칭키 체계**
  - **당시 답변:** 대칭키와 비대칭키의 차이를 PKI, FIDO 인증 사례에 연결해 설명했다.
  - **현재 교정:** 대칭키는 같은 비밀키를 공유해 암복호화하고 대량 데이터 처리에 유리하다. 비대칭키는 공개키와 개인키 쌍을 사용해 암호화, 서명, 검증과 키 교환 문제를 푼다. PKI는 인증서로 공개키와 신원을 연결하고, FIDO는 서비스별 공개키 자격 증명으로 인증한다.
- **TypeScript 타입 가드**
  - **당시 답변:** 인터프리터가 실행 중 타입을 결정하는 것이라고 잘못 답했다. 면접에서 타입 가드와 Node.js 런타임은 다른 층이라는 지적을 받았다.
  - **현재 교정:** TypeScript 타입은 컴파일 뒤 소거된다. 타입 가드는 typeof, instanceof, in, 판별 필드나 value is Type 형태의 사용자 정의 술어처럼 실제 JavaScript 검사의 결과를 컴파일러가 제어 흐름에서 좁히는 장치다.
- **NestJS 요청 라이프사이클**
  - **당시 답변:** 미들웨어 다음에 인터셉터, 가드, 파이프 순이라고 답해 가드와 인터셉터의 순서를 틀렸다.
  - **현재 교정:** 일반 요청의 진입은 미들웨어, 가드, 인터셉터의 전처리, 파이프, 컨트롤러와 서비스 순이다. 정상 응답은 인터셉터를 역순으로 통과하고, 처리되지 않은 예외가 생기면 예외 필터가 다룬다.
- **NestJS DI 스코프**
  - **당시 답변:** DEFAULT와 REQUEST만 답하고 TRANSIENT를 빠뜨렸다.
  - **현재 교정:** DEFAULT는 애플리케이션에서 공유되는 기본 싱글턴, REQUEST는 요청별 인스턴스, TRANSIENT는 주입받는 소비자별 독립 인스턴스다. 상태와 생성 비용을 근거로 선택한다.
- **소프트 삭제와 MySQL 유니크 제약**
  - **당시 답변:** 모른다고 답했다.
  - **현재 교정:** 행이 남기 때문에 단일 UNIQUE 컬럼은 삭제된 값의 재사용을 막는다. 반대로 UNIQUE(value, deleted_at)는 MySQL이 여러 NULL을 허용해 활성 행 중복을 막지 못할 수 있다. 활성 값만 유니크하게 만드는 생성 컬럼이나 명시적 활성 표식 등 데이터베이스 특성에 맞는 설계가 필요하다.
- **merge, rebase와 fast-forward**
  - **당시 답변:** rebase 설명은 부정확했고 fast-forward는 말이 떠오르지 않아 답하지 못했다.
  - **현재 교정:** merge는 두 이력을 합치며 필요하면 merge commit을 만든다. rebase는 커밋을 새 기준 위에 다시 적용해 커밋 ID를 바꾸므로 공유된 이력에는 주의한다. fast-forward는 현재 끝이 대상 끝의 조상일 때 새 커밋 없이 브랜치 참조만 앞으로 옮기는 병합이다.
- **RxJS**
  - **당시 답변:** NestJS 인터셉터에서 사용하지만 깊게 알지 못한다고 답했다.
  - **현재 교정:** Observable은 시간에 따라 0개 이상의 값을 내보낼 수 있고 연산자 조합과 구독 해제를 지원하며, Promise는 한 번 완료되거나 실패한다. NestJS 인터셉터에서는 CallHandler가 반환한 Observable 파이프라인에 전처리, 후처리, 오류 처리와 종료 동작을 조합한다.
- **시크릿 관리**
  - **당시 답변:** CI의 시크릿 저장소에 둔 환경변수 파일을 배포 시 복사하는 당시 방식을 설명하고 키 관리 서비스 도입을 검토한다고 답했다.
  - **현재 교정:** 관리형 시크릿 또는 파라미터 저장소, 최소 권한과 워크로드 자격 증명으로 장기 키와 파일 복사를 줄이는 방안을 함께 비교한다.
- **서버 오류 인지**
  - **당시 답변:** 백분율 기반 SLO로 인지한다고 답했고, 통계 지표가 단 한 건의 치명 오류를 가릴 수 있다는 피드백을 받았다.
  - **현재 교정:** 전체 오류율과 SLO 소진은 추세 판단에 쓰고, 결제나 정합성처럼 치명적인 오류 유형은 중복 억제와 우선순위를 둔 건별 이벤트 알림으로 별도 감시한다.

### 7. AI 시대의 개발자와 지원 동기

- **질문 요지:** AI가 구현을 많이 하면 왜 여러 개발자가 필요하며 CTO라는 목표가 여전히 유효한지 물었다.
  - **당시 답변:** AI가 사람의 의사결정과 조직 맥락을 모두 대신하지 못하고 결과 책임도 지지 않으며, 팀의 집단지성과 내적 동기가 필요하다고 답했다. 핵심을 늦게 말해 방어적이고 반복적으로 들렸다.
  - **현재 교정:** 구현 비용이 낮아질수록 무엇을 왜 만들지 판단하고 결과를 검증하며 책임지는 사람의 가치가 커진다는 한 문장으로 먼저 답한다.
- **질문 요지:** 풀고 싶은 문제와 지원 이유를 물었다.
  - **당시 답변:** B2B보다 빠른 B2C 피드백 속에서 검색과 추천 문제를 풀고 싶고, 데이터 정합성과 운영 안정성 경험을 연결하고 싶다고 답했다.
- 역질문으로 일하는 방식과 기술 결정 권한을 물었다. 회사가 설명한 내부 운영 정보는 이 공개 회고에 남기지 않는다.

## 잘 작동한 점

1. 기술 선택을 선호가 아니라 도메인 문제와 기존 맥락으로 판단한다고 답한 점.
2. 카디널리티 실패까지 포함해 관측 경험을 설명한 점.
3. 실제로 적용하지 않은 대안과 판단의 한계를 솔직히 구분한 점.
4. 검색, 추천과 빠른 사용자 피드백에 대한 지원 동기가 일관된 점.
