# 윤회 1차 기술, 당시 공고 역할 매핑과 API 협업

> 상위: [[Interview-Prep-Yunhoe-1st-Tech|윤회 1차 예상 기술 질문]]

당시 공개 공고에서 DPP 관련 데이터, 식별, 외부 연동, 운영 책임을 읽었다. 아래는 그 역할을 준비하기 위한 매핑이며 실제 구현이나 조직의 현재 방식은 아니다.

| 당시 역할 키워드 | 예상 질문 | 내 답변의 근거 |
|---|---|---|
| 물리와 디지털 식별 | 전역 ID, QR 검증, 키 회전, 권한 검사를 어떻게 설계할까? | UUID 또는 ULID의 조건, 서명, 데이터베이스 유일성, 인증과 인가 분리 |
| 데이터 생애주기 | 상태 전이, 감사 이력, 중복과 순서 문제를 어떻게 다룰까? | 현재 상태와 전이 로그, 잠금 또는 버전 검사, 멱등성, 재처리 |
| 다중 사용자 데이터 | 데이터 격리와 권한을 어느 경계에서 강제할까? | 명시적 테넌트 범위, RLS 검토, 통합 테스트, 복구 단위 비교 |
| 외부 표준과 연동 | 변경된 입력 모델과 API 실패를 어떻게 흡수할까? | 어댑터 경계, 버전 관리, timeout, 제한된 재시도, 실패 큐 |
| 운영과 리드 | 성능, 장애, 변경 위험의 우선순위를 어떻게 정할까? | 실행 계획, 관측성, 단계적 마이그레이션, 롤백, 결정 기록 |

## API 협업 질문

- 계약과 스키마 변경은 어떻게 검토하고 이전 버전과 호환되게 배포하는가?
- 입력 검증, 권한, 오류 표현은 어느 계층에서 책임지는가?
- 클라이언트와 서버가 병렬 개발할 때 명세와 샘플, 버전 호환성을 어떻게 유지하는가?
- 신뢰성이나 성능 개선의 우선순위는 어떤 사용자 영향과 관측 지표로 정하는가?

프론트엔드 구성원 개인의 프로필이나 비공개 구현을 근거로 협업 방식을 추정하지 않는다. 실제 API 계약과 변경 흐름은 면접에서 확인한다.
