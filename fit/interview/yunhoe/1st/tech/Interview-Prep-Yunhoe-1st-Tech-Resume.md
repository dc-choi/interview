# 윤회 1차 기술, 이력서 기반 기술 질문, Q1~Q4

> 상위: [[Interview-Prep-Yunhoe-1st-Tech|윤회 1차 예상 기술 질문]]

## Q1. 동시 갱신을 어떻게 정합하게 처리했는가?

여러 장치와 요청이 같은 상태를 갱신하는 흐름에서 충돌이 반복됐다. 충돌이 치명적인 행은 비관적 잠금으로 보호하고, 여러 행의 잠금 순서를 고정했다. 트랜잭션을 짧게 유지하고 데드락에는 제한된 재시도, 같은 입력의 중복에는 멱등 키를 적용했다. 서로 다른 변경의 충돌은 잠금으로, 동일 이벤트의 중복은 멱등성으로 다룬다는 구분이 핵심이다. 잠금 대기와 교착 상태를 관측해야 한다는 한계도 함께 답한다.

**대안 판단**

- 충돌이 드물고 버전 충돌 뒤 전체 작업을 안전하게 다시 실행할 수 있다면 낙관적 잠금을 비교한다.
- 특정 행을 반드시 갱신해야 하는 흐름에는 잠긴 행을 건너뛰는 방식보다 즉시 실패와 제한 재시도가 명확하다.
- 같은 데이터베이스의 행을 보호하는 문제에 분산 락을 먼저 추가하지 않는다. 여러 저장소나 외부 시스템을 함께 조정해야 할 때는 TTL, fencing과 복구까지 포함해 검토한다.

## Q2. 비동기 자동화를 어떻게 설계했는가?

핵심 상태 변경은 먼저 트랜잭션에서 확정하고, 알림과 외부 연동은 EventBridge와 SQS의 후속 이벤트로 분리했다. 소비자는 중복 실행을 전제로 멱등하게 만들고, 영구 오류와 일시 오류를 구분해 제한 재시도, 실패 큐와 운영자 확인 경로를 뒀다. 당시 Transactional Outbox는 적용하지 않아 DB 커밋과 이벤트 발행 사이의 누락 가능성이 남았다. 지금이라면 상태 변경과 Outbox 기록을 같은 트랜잭션에 넣고 릴레이가 재시도 가능하게 발행하도록 보강한다.

**꼬리 질문**

- 정확히 한 번 처리를 보장한다고 말하지 않는다. 적어도 한 번 전달을 전제로 소비자의 멱등성과 중복 관측을 설계한다.
- 순서가 중요한 범위는 전체 큐가 아니라 업무 키 단위로 좁히고, 처리량과 지연의 대가를 함께 설명한다.
- 장기 재생과 여러 소비자의 스트림 처리가 핵심이면 로그 기반 브로커를 비교하지만, 당시에는 운영 복잡도와 실제 요구를 기준으로 관리형 이벤트와 큐를 선택했다.
- Event Sourcing과 여러 서비스의 Saga는 당시 운영 경험으로 과장하지 않는다.

## Q3. 느린 조회를 어떻게 개선했는가?

APM과 느린 쿼리 로그로 문제 경로를 재현하고, 실행 계획과 데이터 분포로 가설을 검증했다. 필터와 정렬 조건에 맞춰 복합 인덱스를 조정하고, 필요한 경우 ORM 조회 형태와 응답 조립 방식을 바꿨다. 개선 뒤에는 읽기 지연뿐 아니라 인덱스가 쓰기에 주는 비용과 다른 경로의 영향을 관측했다. 구체 수치나 내부 데이터 구조는 공개 가능한 근거가 없으면 말하지 않는다.

**검증 기준**

- 실행 계획의 예상 행과 실제 행, 스캔 방식, 정렬과 임시 결과를 확인한다.
- 동등 조건, 범위와 정렬 순서에 맞춰 인덱스 후보를 만들고, 읽기 개선과 쓰기 비용을 같은 조건에서 비교한다.
- ORM 옵션 이름만 보고 생성 SQL을 추정하지 않고 로그와 실행 계획으로 확인한다.

## Q4. 저장 구조 마이그레이션을 어떻게 했는가?

스키마 변화와 관계 조회의 요구가 커지면서 문서형 데이터를 관계형 구조로 옮긴 경험이 있다. 한 번에 전환하지 않고 이중 쓰기, 백필, 읽기 점진 전환, 검증, 쓰기 전환 순서로 나눴다. 단계마다 차이 검증과 되돌림 경로를 준비했다. 이 경험은 표준이나 외부 입력이 바뀌는 도메인에서도 데이터 모델을 안전하게 바꾸는 판단 기준으로 연결할 수 있다. 대상 회사의 저장소 구성이나 실제 모델은 추정하지 않는다.

**실패 대비**

- 이중 쓰기 경계가 다르면 부분 실패와 순서 뒤바뀜이 생길 수 있으므로 차이 리포트와 재처리 경로를 둔다.
- 읽기 전환은 한 번에 바꾸지 않고 비교 가능한 단위로 나누며, 불일치가 확인되면 이전 경로로 되돌린다.
- 하위 소비자가 있다면 호환 기간과 버전 규칙을 두고, 제거 조건을 측정 가능한 검증으로 정한다.
