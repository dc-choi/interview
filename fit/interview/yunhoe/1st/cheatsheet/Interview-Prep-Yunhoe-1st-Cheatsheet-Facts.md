## 당시 공개 공고에서 읽은 범위

공고는 과거 시점의 자료다. 백엔드 리드 역할, DPP 관련 데이터 문제, 외부 연동과 운영 책임을 준비의 출발점으로 읽었고, 현재 회사 사실이나 실제 구현으로 단정하지 않는다.

| 정보 종류 | 이 문서에서의 처리 |
|---|---|
| 공개 공고와 공식 사이트 | URL, 확인 시점, 역할 수준의 사실만 짧게 남긴다. |
| 법령과 표준 | 공식 원문과 적용 시점을 다시 확인한 뒤에만 말한다. 불명확하면 가설로 표시한다. |
| 면접에서 들은 내용 | 비공개 조직, 계약, 기술과 계획은 기록하지 않고 공개 자료로 확인할 질문으로 바꾼다. |
| 개인 경험 | 문제, 판단, 행동, 결과와 한계는 남기되 이전 회사의 고객명, 운영 수치, 내부 구조는 일반화한다. |
| 처우와 연락처 | 개인 처우 금액과 제3자 연락처는 기록하지 않는다. 고용 조건의 서면 확인 시점은 질문할 수 있다. |

## 확인할 질문

1. 이 역할이 처음 해결해야 할 문제와 성공 기준은 무엇인가?
2. 실제 데이터 생애주기와 식별, 검증 흐름에서 가장 위험한 지점은 어디인가?
3. 외부 표준이나 파트너 요구가 바뀔 때 어떤 검증, 계약, 마이그레이션 절차를 거치는가?
4. 기술 결정, 리뷰, 배포, 장애 대응의 책임 경계는 어떻게 나뉘는가?
5. 고용 조건과 평가 기준은 어느 공식 단계에서 서면으로 확인할 수 있는가?

## 직전 점검

- 공개 사실, 내 경험, 아직 검증하지 못한 가설을 구분했는가?
- 회사 내부 계획을 이미 확정된 사실처럼 말하지 않는가?
- 면접에서 들은 설명은 역할 기반 요약과 확인 질문으로만 남겼는가?
- 제3자 실명, 연락처, 처우 금액이 없는가?
