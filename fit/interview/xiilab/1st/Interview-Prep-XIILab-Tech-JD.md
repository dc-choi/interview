# 씨이랩(XIILab) 1차 면접 준비, JD 기반 기술 질문

> 당시 공개 JD에 나타난 Full Stack, 제품 책임, AI 제품 맥락과 AI Tool 지원을 기준으로 정리한다. AI 도구는 공개 자격 요건이 아니라 지원 항목이므로 필수 역량처럼 단정하지 않는다. 제품별 설계 질문은 준비용 답변이며, 실제 제품 구현이나 실제 면접 문답으로 단정하지 않는다. 개인 프로젝트의 사용량, 설정값, 자동화 도구 묶음, 이전 조직의 환경은 넣지 않는다.

## 공개 제품 기반 맞춤 설계 질문

### X-AIVA의 분석 이벤트를 웹 화면에 실시간으로 보여준다면?

**답변 골격**: 영상 자체의 전송과 분석 이벤트 전달을 분리한다. 분석 서비스가 만든 이벤트에는 카메라 또는 장치 식별자, 이벤트 시간, 유형, 모델 버전과 중복 방지 키를 포함한다. 백엔드는 이벤트를 검증하고 저장한 뒤 WebSocket이나 SSE로 필요한 변경만 전달한다.

**판단 기준**:

- 늦게 도착하거나 중복된 이벤트의 정렬과 멱등 처리
- 이벤트 폭증 시 버퍼, 집계, backpressure와 화면 갱신 주기
- 연결이 끊긴 클라이언트의 재동기화와 마지막 확인 위치
- 모델 결과의 불확실성과 사람이 확인해야 할 상태 표시
- 장치, 이벤트 수신, 저장, API와 화면 전달 각 구간의 지연 및 오류 관측

공개 JD는 X-AIVA의 객체 인식, 이벤트 감지와 실시간 알림을 소개할 뿐 실제 전송 프로토콜이나 저장 구조는 공개하지 않는다. 위 내용은 예상 설계 답변이다.

### AstraGo 같은 GPU 작업 운영 제품의 API를 설계한다면?

**답변 골격**: 긴 GPU 작업을 동기 HTTP 요청으로 붙잡지 않고 작업 접수, 대기, 실행, 완료, 실패와 취소 상태를 가진 비동기 Job으로 모델링한다. 접수 API는 클라이언트가 보낸 멱등 키로 중복 접수를 판별해 job ID를 반환하고, 같은 키의 재시도에는 같은 ID를 돌려준다. 워커나 스케줄러가 실행한다.

**판단 기준**:

- GPU 종류, 메모리, 우선순위와 테넌트 quota를 반영한 배치
- 재시도 가능한 실패와 즉시 종료해야 할 실패 구분
- 취소, timeout, 고아 작업과 중복 실행 방지
- GPU 사용률, 메모리, 대기 시간, 작업 성공률과 비용 관측
- 작업 로그와 산출물 접근 권한, 보존 및 삭제 정책

### Xniper 같은 제조 QA/QC 결과를 추적한다면?

**답변 골격**: 검사 대상, 생산 lot, 촬영 시점, 모델과 임계값 버전, 판정 결과와 사람의 재검토를 하나의 추적 가능한 기록으로 연결한다. 원본 판정을 덮어쓰지 않고 정정과 재검사 이력을 남긴다.

**판단 기준**:

- false positive와 false negative의 비용을 반영한 임계값과 승인 흐름
- 모델 또는 규칙 변경 전후 결과 비교와 재현 가능성
- 설비 시간과 서버 시간 차이, 중복 및 누락 이벤트 처리
- lot 단위 집계와 개별 검사 추적의 데이터 모델 분리
- 모델 성능 저하, 입력 분포 변화와 수동 판정 비율 관측

## React와 Full Stack 경험

**답변 골격**: 프론트엔드와 백엔드를 기능 단위로 함께 설계한 경험이 있다. 서버 상태와 화면 상태를 구분하고, API 계약과 오류 경계를 먼저 정한 뒤 UI를 구현한다.

**설계 기준**:

- 서버 상태는 명시적인 캐시 정책과 무효화 경로를 둔다.
- 인증 갱신은 동시 요청에서 중복 실행되지 않도록 하나의 갱신 작업을 공유한다.
- 모노레포의 타입 공유는 변경 감지에 유리하지만, 외부 클라이언트가 필요하면 REST나 GraphQL 경계를 별도로 둔다.
- 접근성, 오류 처리, URL 상태, 사용자 권한을 컴포넌트 구조와 함께 설계한다.

**당시 준비 판단**: 백엔드가 주된 강점이더라도 Full Stack 역할에서는 UI 구현만 나열하지 않고, 사용자 상태, API 오류, 인증과 권한, 데이터 변경의 복구 경계를 하나의 기능 흐름으로 설명해야 한다.

## 데이터 모델과 테스트

**답변 골격**: 도메인 모델을 먼저 정규화하고, 실제 조회 패턴이 확인되면 비정규화나 인덱스를 검토한다. 마이그레이션은 백업, 검증, 롤백 경로를 함께 설계한다.

**테스트 기준**: 핵심 규칙은 단위 테스트로, 경계 통합은 통합 테스트로, 주요 사용자 흐름은 종단 간 검증으로 확인한다. 특정 데이터 양, 커버리지, 내부 기준은 공개하지 않는다.

### 데이터 변경과 마이그레이션은 어떻게 검증하는가?

**답변 골격**: 문서형 데이터를 관계형 구조로 옮긴 경험에서, 새 모델을 먼저 검증하고 백필, 읽기 전환, 검증과 되돌림을 작은 단계로 나눴다. 마이그레이션은 스키마 변경만이 아니라 기존 데이터, 애플리케이션 호환성, 운영 복구를 함께 다루는 작업이라고 설명한다.

**판단 기준**:

- 새 쓰기와 기존 읽기가 함께 존재하는 호환 기간
- 데이터 수, 누락, 중복과 참조 무결성의 검증 방법
- 긴 작업의 재시작, 체크포인트와 실패한 배치의 격리
- 읽기 전환 전후의 비교, 되돌림 조건과 책임자 확인
- 대량 변경을 한 번에 잠그지 않기 위한 배치, 인덱스와 배포 순서

**테스트 피라미드**: 도메인 규칙은 단위 테스트로 빠르게 확인하고, 저장소와 외부 경계는 통합 테스트로, 중요한 사용자 흐름은 종단 간 검증으로 확인한다. 테스트 수나 커버리지 비율이 아니라 위험한 규칙이 실제 실패를 잡는지로 품질을 설명한다.

## 클라우드와 장애 대응

**답변 골격**: 정적 자산, 웹 트래픽, 비동기 작업, 데이터 저장소의 경계를 분리하고, 실패한 경로가 원인을 추적하고 복구할 수 있게 만든다.

**운영 기준**: 로그, 메트릭, 배포 이력을 같은 문제 맥락에서 본다. 경보 기준은 사용자 영향과 정상 구간을 관측해 정하고, 이전 환경의 임계값을 복사하지 않는다.

## 공개 가능한 경험 증거

### FIDO와 WebAuthn

표준 기반 인증 서버를 다루며 WebAuthn과 FIDO 요건을 직접 확인했고, 오픈소스 구현의 규격 준수 여부를 재현과 명세 대조로 검증해 공개 이슈로 기여했다. 이 사례는 보안 요구를 라이브러리 이름이나 관습으로 처리하지 않고, 명세, 재현과 서버 검증 기준으로 판단한다는 증거다.

### 데이터, 테스트와 관측

데이터 모델 변경은 검증과 되돌림까지 포함해 준비하고, 품질 검증은 단위, 통합, 종단 간 테스트로 위험을 나눠 다뤘다. 운영 문제는 로그, 지표와 배포 이력으로 원인을 좁히고, 복구 뒤에는 같은 문제가 다시 발견될 수 있게 테스트나 경보 기준을 보강했다.

### 공개 발표와 멘토링

ORM 조회 성능 문제를 재현하고 실행 계획과 공식 문서로 검증한 과정을 공개 발표로 설명했다. 백엔드 멘토링에서는 답을 전달하는 데 그치지 않고, 상대가 판단 근거를 재현할 수 있는지 질문과 피드백으로 점검했다. 이 두 경험은 Product Engineer 역할에서도 해결 과정을 팀의 공통 기준으로 남기는 방식으로 연결한다.

## AI 도구 활용

**답변 골격**: 공개 JD의 복지 항목에는 AI Tool 지원이 있다. 도구는 조사, 반복 구현과 리뷰 보조에 활용하되 요구사항 해석, 설계 선택, 결과 검증과 책임은 직접 가진다. 저장소 규칙, 공식 문서, 테스트와 코드 리뷰를 같은 검증 흐름으로 연결한다.

**당시 사용 맥락**: 면접 준비 당시 팀에서 사용한 도구는 Claude Code였고, 저장소와 하위 경로의 맥락은 계층형 `CLAUDE.md`로 나눴다. 책임별 보조 작업, 편집 범위 품질 검사와 작업 종료 시 자체 리뷰를 연결했다. 이는 지원 회사가 특정 도구를 요구했다는 뜻이 아니다.

## 컬처핏 연결

> 공개된 제품 책임과 협업 방식을 확인한 뒤, 문제 정의부터 검증까지 책임진 경험을 연결한다. 확인되지 않은 팀 규모, 면접 진행, 내부 문화는 추정하지 않는다.

- 장단점, 협업 갈등과 긴급 이슈 우선순위는 [[My-FIT-Answers|FIT 답변 마스터]]의 검증된 사례로 준비한다.
- 새로운 기술을 학습할 때는 공식 문서, 작은 재현, 테스트와 피드백을 연결해 설명한다.
- AI 도구를 활용한 경험은 코드 생성 자체가 아니라 요구 해석, 리뷰와 검증 책임을 직접 지는 방식으로 설명한다.
