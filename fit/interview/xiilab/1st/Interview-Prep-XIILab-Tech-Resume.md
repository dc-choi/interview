# 씨이랩(XIILab) 1차 면접 준비, 이력서 기반 기술 질문

> 이 문서는 공개된 포지션 요구와 본인이 직접 수행한 일을 일반화한 답변만 담는다. 이전 회사의 고객, 장비, 비용, 처리량, 배포와 경보 수치는 넣지 않는다. 실제 적용과 현재 개선안은 구분한다.

## DB Lock으로 동시 갱신을 어떻게 처리했는가?

**답변 골격**: 같은 상태를 동시에 갱신하는 경로에서는 트랜잭션 안에서 필요한 행을 잠그고, 읽기와 갱신을 원자적으로 처리했다. 충돌이 잦은 구간에는 비관적 잠금을, 충돌이 드문 구간에는 버전 기반 조건부 갱신을 비교했다.

**트레이드오프**: `NOWAIT`는 대기 시간을 줄이지만 호출자가 제한된 재시도와 실패 처리를 가져야 한다. 여러 자원은 일관된 순서로 잠근다. 잠금 대상과 독립적인 입력 검증과 외부 호출만 미리 수행하고, 변경 가능한 상태의 불변식은 잠금 뒤 다시 검증해 TOCTOU를 막는다.

**검증**: 동시 요청, 잠금 실패, 재시도, 데드락을 재현해 최종 상태와 오류 경로를 확인한다.

**당시 구현과 현재 개선안**: 당시 `NOWAIT` 실패에는 짧은 고정 간격으로 최대 세 번 재시도했다. 현재 다시 설계한다면 재시도 집중을 줄이는 지수 백오프와 지터를 별도로 검증한다. 이는 당시 구현이 아니라 개선안이다.

## 실행 계획으로 최신 상태 조회를 개선한 방법은?

**답변 골격**: 실행 계획과 실제 호출 경로에서 후보 행, 정렬, 조인 방식을 확인한 뒤 복합 인덱스와 쿼리 구조를 함께 조정했다.

**트레이드오프**: 조회 인덱스는 쓰기 비용과 저장 공간을 늘리므로, 선택도와 쓰기 영향을 비교해야 한다. ORM 옵션은 생성 SQL과 실행 계획으로 확인한 뒤 적용한다.

**검증**: 변경 전후 실행 계획, 지연 분포, 호출량과 인접 경로를 같은 조건에서 비교한다. 내부 데이터 규모와 성능 수치는 공개하지 않는다.

**당시 학습 기록**: 업무 키로 동등 조건을 건 뒤 최신 시각과 보조 키로 정렬하는 조회에서 `EXPLAIN ANALYZE`와 실제 호출 경로를 확인했다. 복합 인덱스는 동등 조건, 정렬과 반환 컬럼을 함께 보고 설계하며, 데이터 분포와 캐시 상태가 바뀌면 같은 조건에서 다시 측정한다.

**측정 해석**: 당시 기록에는 조회에 포함된 서브쿼리, 단일 쿼리와 배치 전체처럼 서로 다른 측정 범위가 함께 있었다. 이를 같은 지표로 직접 비교하지 않는다. 실행 환경, 캐시 상태, 표본 수와 percentile이 남아 있지 않아 정량 개선율은 재현 가능한 결과로 인용하지 않는다.

## Prisma 관계 조회를 어떻게 검증하고 조정했는가?

**답변 골격**: 관계 조회가 여러 쿼리로 분리되는 원인을 로그와 실행 계획으로 확인하고, 관계 로딩 전략을 조정했다.

**트레이드오프**: 조인 전략은 호출 수를 줄일 수 있지만 데이터베이스 부하와 결과 형태가 달라질 수 있다. 성능이 중요한 경로만 명시적 쿼리로 전환하고, 나머지는 타입 안전성과 변경 용이성을 유지한다.

**당시 학습 기록**: 전통적인 lazy-loading N+1로 단정하지 않고, 당시 설정에서 `relationJoins` Preview 기능이 꺼져 관계 조회가 여러 쿼리로 분리되는 모습을 로그에서 확인했다. 기능을 켠 뒤 `relationLoadStrategy: 'join'`을 검토했으며, MySQL에서는 이름과 달리 correlated subquery와 JSON 집계 형태가 생성될 수 있으므로 옵션 이름만으로 SQL `JOIN` 여부를 단정하지 않았다. 공식 문서, 생성 SQL과 실행 계획으로 다시 확인한 뒤 필요한 경로에만 적용했다. ([Prisma 관계 조회 공식 문서](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries))

## EventBridge와 SQS로 후속 처리를 분리한 이유는?

**답변 골격**: 실제 적용에서는 핵심 상태를 확정한 뒤 EventBridge와 SQS로 후속 작업을 분리하고, 메시지 소비자를 멱등하게 처리했다. 영구 오류와 일시 오류를 나눠 재시도, DLQ와 수동 확인 경로를 설계했다. Transactional Outbox는 적용하지 않았으며, DB 커밋과 이벤트 발행 사이의 누락 가능성을 줄이기 위한 개선안으로 설명한다.

**트레이드오프**: 관리형 큐는 운영 부담을 줄이지만, 리플레이, 강한 순서 보장, 장기 보관이 핵심이면 다른 브로커를 비교해야 한다.

**검증**: 중복 전달, 소비자 재시작, 영구 실패와 지연을 재현해 상태 전이와 복구 경로를 확인한다. 개선안에서는 같은 트랜잭션의 Outbox 기록, 릴레이 재시작과 중복 발행도 별도로 검증한다.

**적용과 한계**: 실제 적용은 핵심 상태를 확정한 뒤 EventBridge와 SQS로 후속 작업을 전달하고 멱등 소비자로 중복을 처리한 방식이다. Transactional Outbox는 적용하지 않았으며, DB 커밋과 발행 사이의 누락 가능성을 줄이기 위한 후속 개선안이다.

## 컨테이너와 관측성을 어떻게 운영했는가?

**답변 골격**: 멀티스테이지 이미지와 분리된 실행 환경으로 배포 경로를 단순화하고, 로그와 메트릭을 요청 문맥으로 연결했다.

**트레이드오프**: Rolling과 Blue/Green은 롤백 속도, 자원 사용, 운영 절차를 기준으로 비교한다. 고유 식별자는 메트릭 라벨이 아니라 로그와 트레이스 연결에 사용한다.

**검증**: 배포, 롤백, 설정 주입, 장애 알림과 원인 확인이 각각 재현되는지 점검한다. 내부 임계값과 전후 수치는 공개하지 않는다.

**당시 학습 기록**: 멀티스테이지 이미지와 `.dockerignore`로 실행 이미지에 빌드 산출물과 런타임 의존성만 남기고, 관리형 컨테이너 환경으로 배포 경로를 옮겼다. 당시에는 정적 임계값 경보를 운영했고, SLO burn-rate 경보는 나중에 검토할 개선안으로 구분한다.
