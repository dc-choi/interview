## 제출 답변 요약

- 지원 동기: AI를 단순 코드 생성기가 아니라 명세, 구현, 리뷰와 검증을 잇는 개발 흐름으로 사용한 경험을 브랜드 운영 자동화 문제에 확장하고 싶다고 설명했다.
- 주요 결과: 사람이 반복하던 업무를 이벤트 기반 흐름으로 바꾸고, 재시도, 실패 격리, 알림과 수동 복구 경로까지 설계한 경험을 제시했다.
- 답변 경계: 당시 제출 원문과 이전 회사의 내부 수치, 고객과 시스템 구조는 복제하지 않고 문제, 판단, 행동과 배움만 보존한다.

## 공개 역할 및 조직 맥락

| 항목 | 공식 공개 정보 | 준비에 쓰는 방법 |
|---|---|---|
| 회사와 도메인 | 에고이즘은 브랜드의 정체성과 고객 경험을 중심에 둔 브랜드 빌더를 지향한다고 공개적으로 설명한다. 공고의 우대사항은 D2C와 이커머스의 주문, 정산, 재고와 채널 관리 데이터 구조를 명시한다. | 제품과 고객 경험의 연결을 묻는 질문에 기술 선택의 사용자 가치와 검증 방법을 함께 설명한다. |
| 조직 | 공개 공고는 Growth팀을 주요 브랜드와 운영의 성장을 가로막는 병목을 정의하고 해결하는 조직으로 소개하며, 미뇽맨션과 바쏠을 예시로 든다. | 단일 기능 구현보다 문제 정의, 실행, 학습의 닫힌 루프를 보여준다. |
| 역할 | AX Engineer는 AI가 활용할 데이터와 인프라 기반을 설계하고 구축하는 역할로 소개된다. | 데이터 품질, 권한, 운영 안정성을 AI 기능의 선행 조건으로 설명한다. |
| 업무 | 공고에는 ETL, 지식 베이스 관리, 데이터 정의 기준, 클라우드 운영, LLM API 연동과 지속 개선이 포함된다. | 입력 데이터부터 배포 후 관측까지의 책임 경계를 분명히 설명한다. |
| 요구 역량 | 여러 데이터 소스의 정규화, 클라우드 운영, SQL과 데이터 모델링, End-to-End 실행, 비개발 직군과의 협업, 코딩 에이전트 활용이 명시되어 있다. | 직접 경험과 학습이 필요한 영역을 구분하고, 검증 가능한 사례만 연결한다. |

공고의 역할과 조직 설명은 확인 시점의 공개 포지셔닝이다. 실제 우선순위, 팀 구성, 내부 데이터와 운영 방식은 면접에서 확인할 사실로 남긴다.

### 회사별 강점과 갭

- **강점**: 반복 업무를 이벤트, 상태, 예외 처리와 복구 경로로 나눠 자동화한 경험은 ETL, 자동화 환경과 지속 안정화의 역할 설명에 직접 연결된다.
- **강점**: 클라우드 운영, 데이터 정합성, SQL 기반 문제 분석과 비개발 직군의 요구를 기술 구조로 번역한 경험을 End-to-End 실행 역량으로 제시한다.
- **갭**: RAG, 벡터 DB, 데이터 웨어하우스와 Cafe24는 직접 운영 경험이 아니다. 인접 경험을 과장하지 않고, 데이터 계약, 품질 지표와 운영 경계를 먼저 학습하겠다고 답한다.

## 역할 이해

- 공고에 나온 업무를 입력, 판단, 실행, 검증, 예외 처리로 분해한다.
- AI 도구는 구현 속도를 높일 수 있지만, 문제 정의와 결과 검증의 책임은 사람이 진다.
- 자동화 대상은 단순히 시간이 오래 걸리는 일이 아니라 오류 비용과 재작업이 큰 흐름부터 선택한다.

## 전화 스크리닝 당시 준비 전략

- 30분 전화에서는 기술 구현을 길게 설명하기보다 지원 동기, 역할 이해, 경력의 연결과 협업 방식을 먼저 짧게 답한다.
- 이미 제출한 지원 동기와 성과 답변을 기준점으로 삼고, 통화에서 갑자기 다른 성과나 과장된 수치를 추가하지 않는다.
- 직접 경험하지 않은 RAG, 데이터 플랫폼과 이커머스 도구는 경험이 없다고 밝힌 뒤 가장 가까운 전이 경험과 학습 순서를 설명한다.
- 자동화는 모델 이름보다 사람이 하던 일, 오류 비용, 사람의 승인 경계, 실패 시 복구와 검증 방법으로 설명한다.

## 예상 질문과 당시 준비 답변

| 예상 질문 | 당시 준비 답변의 핵심 |
|---|---|
| 왜 이 역할에 지원했는가 | AI를 코드 생성에만 쓰지 않고 명세, 구현, 리뷰와 검증을 잇는 흐름으로 사용한 경험을 실제 운영 자동화로 확장하고 싶었다. |
| 가장 임팩트 있던 결과는 무엇인가 | 반복 업무를 이벤트와 상태 전이로 나누고, 재시도, 실패 격리, 알림과 수동 복구 경로까지 포함해 자동화한 경험을 설명한다. |
| AI 도구를 실제 업무에서 어떻게 쓰는가 | 반복 작업은 보조받되 문제 정의, 설계 선택과 결과 검증은 직접 책임진다고 답한다. |
| 비개발 직군과 어떻게 협업하는가 | 요구 문장을 그대로 구현하지 않고 의도를 재확인한 뒤, 위험과 대안을 상대의 언어로 설명한다. |
| 익숙하지 않은 도메인 경험을 어떻게 메우는가 | 직접 경험과 인접 경험을 분리하고, 데이터 흐름과 오류 비용부터 작은 검증으로 학습한다고 답한다. |
| 왜 이직하려는가 | 넓은 운영 책임에서 쌓은 자동화 역량을 더 빠른 제품 피드백과 사용자 가치에 연결하고 싶다고 설명한다. |

### 실제 통화 뒤 답변 교정

- **당시 답변**: AI 도구와 반복 업무 자동화 경험을 주로 구현 흐름과 운영 안정성 관점에서 설명했다.
- **현재 교정**: 이 역할에서는 요청받은 일을 구현한 경험뿐 아니라, 반복 업무를 먼저 관찰하고 요청 전에 개선 후보를 제안해 자동화한 사례를 분명히 보여 줘야 한다. 다만 사용자 또는 업무 소유자의 동의 없이 실행했다는 뜻은 아니며, 문제 관찰, 영향 확인, 작은 범위 합의, 검증과 되돌리기 순서로 설명한다.

## 경험 설명 틀

1. 사람이 하던 반복 업무와 실패 비용을 설명한다.
2. 이벤트, 상태, 예외 경로를 어떤 기준으로 나눴는지 말한다.
3. 관측과 수동 복구 경로를 어떻게 만들었는지 덧붙인다.
4. 측정 근거가 없으면 수치를 주장하지 않고, 검증 방법을 제시한다.

## 갭 질문 대응

- 직접 경험하지 않은 도메인은 모른다고 먼저 말한다.
- 인접 경험의 구조가 어디까지 전이되는지와 학습 계획을 짧게 설명한다.
- 제품, 고객, 조직의 비공개 정보를 추측해 답변 근거로 쓰지 않는다.

## 역질문

- 공개 공고의 ETL, 지식 베이스, 데이터 정의 기준 중 입사 초기에 가장 먼저 책임질 범위는 무엇인가?
- 자동화 결과의 정확도와 데이터 품질을 어떤 신호로 검증하고, 오류가 생기면 어떻게 되돌리는가?
- 비개발 직군의 요구를 데이터와 기술 구조로 번역할 때, 역할 간 결정과 검토는 어떻게 나뉘는가?

## 기록 경계

1. 회사와 역할 정보는 공식 공개 페이지에서 확인한 사실만 기록한다.
2. 회사, 차수, 일정, 결과, 받은 질문과 본인 답변은 요약해 보존한다.
3. 제3자 실명과 연락처, 처우 금액, 제출 원문, 제3자 발화 원문과 비공개 온보딩 정보는 남기지 않는다.
4. 조직 규모, 고객 데이터, 내부 시스템, 실제 우선순위는 공식 공개 정보가 아니면 질문으로만 남긴다.
