# 블리츠다이나믹스 1차, 이력서 기반 기술 질문

> [[Interview-Prep-BlitzDynamics-1st|1차 메인]]의 하위 문서다. 이력서의 공개 서술과 common 기술 카드만 근거로 쓴다. 전, 현 직장의 비공개 지표와 구조는 쓰지 않는다. 각 카드 끝줄에 공고의 역할을 연결한다.
> AX 포지션이므로 면접관은 기술 깊이보다 이 경험이 사내 자동화와 에이전트 인프라로 어떻게 옮겨지는지를 물을 가능성이 높다. 결론, 판단 기준, 확인 방법, 한계 순서로 짧게 답하고 꼬리에서 깊이를 조절한다.

## R1. 팀 AI 협업 규약은 무엇을 어떻게 만들었나 (경험형)

- **질문 의도**: 이력서에서 이 역할과 가장 가까운 항목이다. 규칙을 만든 것인지, 실제로 동료가 쓰게 만든 것인지를 본다.
- **핵심 답변**: AI가 수정해도 되는 영역과 안 되는 영역을 경로별 규칙 문서로 명시하고, 작업이 끝나는 시점에 변경 파일 검사와 테스트 같은 검증을 AI가 스스로 돌리게 했다. 맥락이 사람 머릿속에만 있으면 사람도 도구도 같은 실수를 반복한다는 문제에서 출발했다. 작은 영역부터 적용해 검토와 인수인계가 쉬워지는 것을 보인 뒤 팀 규약으로 넓혔다.
- **판단 기준**: 자연어 규칙은 무시될 수 있으므로 되돌리기 어려운 동작은 코드 수준의 훅이나 검사로 막고, 규칙 문서는 맥락 제공에 쓴다.
- **꼬리**: 규약 효과를 어떻게 알았나 → 리뷰에서 반복되던 지적과 재작업이 줄었는지를 관찰했다고 말하되, 측정 수치는 내부 정보라 말하지 않는다. 비개발자에게도 같은 방식이 통하나 → 규칙 문서를 쓰게 하는 대신 템플릿과 기본 가드레일을 인프라가 제공해야 한다.
- **회사 연결**: 사내 바이브코딩 도구도 누구나 쓰게 하려면 사용자가 규칙을 외우는 대신 도구가 안전한 기본값을 주는 구조가 필요하다.

## R2. 수기 발주를 EventBridge와 SQS로 자동화한 이유와 실패 처리 (경험형, 설계형)

- **질문 의도**: 업무 흐름을 자동화할 때 어디까지 자동으로 넘기고 어디를 사람이 확인하게 했는지 본다.
- **핵심 답변**: 상태 변경과 외부 연동을 한 요청에 묶으면 느린 의존성 하나가 핵심 처리까지 실패시킨다. 핵심 상태를 먼저 확정하고 후속 작업을 이벤트로 넘겼으며, 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했다. 영구 오류는 즉시 격리하고 일시 오류만 제한 재시도했으며, 재시도 예산을 넘기면 DLQ와 수동 확인 경로로 보냈다.
- **대안과 트레이드오프**: 조직 내 Kafka 도입 한계를 고려해 관리형 큐를 골랐다. 리플레이, 강한 순서, 매우 높은 처리량이 핵심이면 다시 비교한다.
- **한계**: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 실패 시 누락 가능성이 남아 있었고 지금이라면 같은 트랜잭션에 outbox를 저장하고 릴레이가 발행하게 보강한다.
- **꼬리**: 자동화 결과가 틀렸을 때 사람이 어떻게 알았나 → 실패는 조용히 덮지 않고 수동 확인 경로와 알림으로 드러냈다.
- **회사 연결**: 에이전트 전환에서도 자동 경로와 사람의 확인 경로를 처음부터 함께 설계해야 팀이 믿고 맡길 수 있다.

## R3. IoT 배터리와 통신 지연 리포트 자동 통보 (경험형)

- **질문 의도**: 이력서의 내부 업무 효율화 항목이다. 반복 업무를 찾고 자동화한 방식을 본다.
- **핵심 답변**: 사람이 주기적으로 확인하던 기기 상태를 스케줄 작업으로 집계해 알림톡과 이메일로 자동 통보했다. 확인 누락을 줄이고 담당자가 판단이 필요한 기기에만 집중하게 하는 것이 목적이었다.
- **설계 포인트**: 같은 사건이 여러 번 발송되지 않도록 사건 식별자와 채널을 묶어 중복을 막고, 외부 발송 결과가 불명확하면 재조회나 수동 대사로 닫는다. 알림이 많아지면 무시되므로 조치가 필요한 것만 보내는 기준을 둔다.
- **꼬리**: 일이 실제로 줄었나 → 확인 방식이 사람 조회에서 자동 통보로 바뀐 것은 사실로 말하되, 절감 시간 수치는 말하지 않는다. 지금이라면 도입 전 기준선을 먼저 기록하겠다고 보완한다.
- **회사 연결**: 공고의 에이전트 인프라가 팀의 일을 실제로 줄였는지 확인하는 업무와 같은 질문이다.

## R4. Grafana, Prometheus, Loki 관측 설계 (사실형과 경험형)

- **질문 의도**: 사용 현황 집계 체계를 만들 역량을 관측 경험에서 확인한다.
- **핵심 답변**: 트라이포드랩에서 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증했다. 식별자를 구조화 JSON 로그 본문으로 옮기고, 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼다. 고유 식별자를 라벨로 넣으면 시계열이 폭증해 대시보드와 경보가 불안정해진다.
- **흔한 오답**: 사용자 ID나 요청 ID를 메트릭 라벨로 두는 설계. 내가 실제로 겪은 실수이므로 라벨 설계 기준을 먼저 말한다. 메트릭, 로그, 트레이스를 서로 대체하는 도구로 설명하는 것도 오답이다.
- **꼬리**: 팀별 사용 현황은 어떻게 모으겠나 → 팀과 도구 같은 제한된 값만 집계 차원으로 두고 개별 실행 기록은 로그 계열 저장소에 남긴다. 사용량은 활동 신호이지 생산성 지표가 아니므로 결과 지표와 분리한다.
- **회사 연결**: 팀별 사용 현황 집계의 첫 설계 결정은 무엇을 차원으로 둘지와 개인 단위 감시로 읽히지 않게 할 경계다.

## R5. 수천 대 IoT 동시 요청의 Race Condition을 DB Lock으로 해결 (사실형)

- **질문 의도**: 정합성 기본기. 공용 에이전트 인프라에서도 여러 작업이 같은 자원을 동시에 바꾸는 상황이 생긴다.
- **핵심 답변**: 충돌 빈도가 높은 재고 갱신이라 낙관적 잠금보다 `SELECT ... FOR UPDATE NOWAIT`와 짧은 트랜잭션, 제한된 재시도를 조합했다. 외부 호출과 독립 검증은 트랜잭션 밖으로 빼고 여러 대상을 갱신할 때는 키 순서를 통일했다.
- **흔한 오답**: NOWAIT가 모든 대기를 없앤다고 말한다. 해당 잠금 읽기의 행 잠금 대기만 없앤다. 락 순서 통일이 데드락을 완전히 막는다고 말한다.
- **꼬리**: 에이전트 작업 여러 개가 같은 시트나 레코드를 바꾸면 → 작업 단위 멱등성 키, 조건부 갱신, 사람 승인이 필요한 쓰기는 대기 상태로 두는 구조를 말한다.

## R6. 슬로우 쿼리 99.3% 개선과 Prisma 응답 90% 향상, 수치 방어 (경험형)

- **질문 의도**: 이력서 수치가 어떤 조건에서 측정됐는지와 성과를 판단하는 습관을 본다.
- **핵심 답변**: 최신 상태 조회가 느려진 경로를 실행 계획으로 확인하고 동등 조건과 정렬 순서에 맞춘 복합 인덱스와 쿼리 구조를 조정했다. Prisma 관계 조회는 생성 SQL을 확인해 N개 쿼리를 단일 쿼리로 통합했고 하코 커뮤니티 발표로 공유했다.
- **측정 경계**: 전체 조회 안의 서브쿼리 관측값과 단건 쿼리의 전후 결과는 같은 지표로 비교하지 않는다. 환경, 캐시 상태, 표본 수가 다르면 직접 비교하지 않는다.
- **꼬리**: 이 습관이 AX에서 어떻게 쓰이나 → 자동화 성과도 도입 전 기준선, 같은 조건의 비교, 인접 영향(재작업, 오류)을 함께 봐야 한다.

## R7. 모듈 중심 아키텍처로 잦은 요구사항 변경 수용 (설계형)

- **질문 의도**: 공통 인프라를 여러 팀이 쓰게 만들 때의 확장 경계 감각을 본다.
- **답변 골격**: NestJS에서 Controller, UseCase, Domain, Repository port를 나눠 도메인 규칙이 프레임워크와 저장소에 끌려가지 않게 했다. 실제로 독립적으로 바뀌는 경계에만 추상화를 두고 단순한 흐름에는 인터페이스를 미리 만들지 않았다.
- **대안과 트레이드오프**: 계층을 늘리면 테스트와 교체가 쉬워지지만 초기 속도가 느려진다. 공용 인프라라면 팀마다 달라지는 부분(데이터 소스, 알림 채널, 승인 방식)을 확장 지점으로 두고 나머지는 고정한다.
- **꼬리**: 팀별 요구가 계속 늘면 → 공통 함수에 옵션이 쌓이는 신호가 보이면 책임을 나누고 팀별 어댑터로 분리한다.

## R8. 출석부 사이드 프로젝트의 1인 운영과 AI 협업 파이프라인 (경험형)

- **질문 의도**: 실사용자가 있는 서비스를 직접 운영하며 피드백을 받아 개선했는지, 혼자서 운영 한계를 어떻게 넘었는지 본다.
- **핵심 답변**: 출석부를 전산화해 실제 사용자 문제를 해결했고, 멀티테넌트 권한 경계, 이력 보존, 실패 처리와 데이터 복구를 설계했다. 사용자 인터뷰와 운영 지표 점검을 했고, 혼자 운영하는 한계를 AI 협업 파이프라인으로 보완했다. 가장 큰 배움은 기능 완료보다 실제 사용 흐름에서 책임 있게 운영하고 복구할 수 있어야 한다는 점이다.
- **수치 규칙**: 사용 조직 수, 사용자 수 같은 정량값은 말하지 않는다. 물으면 활성 지표와 누적 지표를 구분해 관리했다는 정의까지만 답한다.
- **꼬리**: 본업과 어떻게 분리했나 → 본업 시간과 개인 작업 시간을 분리했다.
- **회사 연결**: 비개발 사용자가 매일 쓰는 도구를 만들고 피드백을 반영해 온 경험이 사내 바이브코딩 도구의 채택 문제와 가장 가깝다.

## R9. CloudFront, ELB, ECS 전환과 Docker 경량화 (경험형)

- **질문 의도**: 사내 도구와 에이전트 워커를 안정적으로 배포하고 운영할 수 있는지 본다.
- **핵심 답변**: 트래픽 증가에 맞춰 단일 NGINX 구조를 CloudFront, ELB, ECS(Fargate)로 옮겼고, RDS Read Replica로 읽기 부하를 나눠 응답속도를 40% 개선했다. Docker 멀티스테이지 빌드로 이미지를 909MB에서 513MB로 줄이고 배포 시간을 3분 10초에서 2분 20초로 단축했다.
- **꼬리**: 사내 에이전트 워커는 어디에 올리겠나 → 짧고 독립적인 작업은 서버리스, 긴 작업이나 도메인 로직 재사용과 연결 수 제어가 필요하면 컨테이너 워커를 고른다. 비밀은 이미지와 코드에서 분리한다.
- **수치 규칙**: 수치를 말할 때는 비교 대상과 측정 조건을 함께 설명할 수 있을 때만 말한다.

## R10. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 경험형)

- **질문 의도**: 이력서의 AI 활용 항목을 실제로 만들고 평가해 봤는지 본다. 공고의 에이전트 평가와 AI 도구 활용에 직접 닿는 근거다.
- **핵심 답변**: 개인 프로젝트로, 개발 지식 Markdown을 근거 관계 그래프로 색인하고 그 검색을 MCP 도구와 CLI로 제공하는 시스템이다. Markdown 위키링크와 frontmatter의 근거 관계로 그래프를 구성하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했다. 검색 방식을 바꾸기 전에 평가 질문부터 고정했다. 질문마다 돌려받아야 하는 문서, 절, 본문 문구를 필수 근거 그룹으로 정하고, 응답 크기 예산 안에 모두 나와야 통과로 쳤다. 무관한 질문은 빈 결과여야 통과하는 음성 질문이다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45에서 51로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어 채택하지 않았다. 그 74개를 포함한 94개 질문으로 bge 리랭커도 비교했지만 통과가 41에서 40으로 개선이 없었고 질문당 약 4.7초가 더 걸려 채택하지 않았다. 이후 절 선택 방식을 개선해 기존 94개 중 통과를 41에서 43으로 올렸다. 새 방식을 측정해 보고 기각한 판단이 핵심이다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 이득이 있어도 바로 바꾸지 않고, 비용과 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다.
- **꼬리**: 골든 케이스는 어떻게 만들었나, 어떤 지표로 비교했나 → 평가 질문은 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본이 아니다. 지표는 양성 질문의 필수 근거 그룹 전체가 응답 예산 안에 나오는지(통과), 음성 질문의 빈 결과 여부다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 봤다.
- **이력서 정정**: 이력서의 골든 케이스 약 145건 문구는 부정확하다. 145건짜리 평가 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **한계**: 합성 표본이고 실제 답변 정확도나 사용자 만족도를 잰 것이 아니다. 자연어로 된 무관한 질문의 거절은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- **회사 연결**: 공고의 에이전트 평가(골든셋, 배포 게이트)와 에이전트가 참조할 맥락을 근거 있게 제공하는 설계에 이 경험으로 답한다. 실서비스 LLM 에이전트 운영 경험은 아니므로 그렇게 말하지 않는다.
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 면접에서 먼저 개인 프로젝트라고 밝힌다.
