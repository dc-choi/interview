# 블리츠다이나믹스 1차, JD 기반 질문

> [[Interview-Prep-BlitzDynamics-1st|1차 메인]]의 하위 문서다. 공고의 5개 주요 업무와 자격 요건에서 나올 질문이다. 대부분 설계형이므로 단일 정답 대신 답변 골격, 판단 기준, 대안과 트레이드오프, 꼬리를 둔다.
> **경험 경계**: 비개발자용 LLM 에이전트를 제품으로 배포한 경험은 없다. 아래 설계 내용 중 이력서에 없는 것은 학습한 지식과 설계 판단으로 말하고, 해본 것처럼 말하지 않는다. 실제 사내 도구의 형태와 스택은 확인 질문이다.

## J1. 업무 흐름에서 어디를 에이전트에 넘기고 어디를 사람에게 남기나 (설계형)

- **질문 의도**: 자격 요건 1번. 업무를 분해하는 기준을 갖고 있는지 본다.
- **답변 골격**: 담당자의 하루 업무를 단계로 적는다 → 단계마다 입력 형태, 판단 성격, 틀렸을 때 비용, 되돌리기 가능성, 빈도를 표시한다 → 입력이 구조화돼 있고 규칙이 명확하면 결정론 자동화, 입력이 비정형이지만 틀려도 되돌릴 수 있으면 에이전트 초안과 사람 확인, 돈이나 고객 약속처럼 되돌리기 어려우면 사람 결정으로 남긴다.
- **판단 기준**: 틀렸을 때 누가 언제 알아차리는가. 알아차릴 장치가 없으면 자동화 범위를 줄인다.
- **대안과 트레이드오프**: 모두 에이전트로 보내면 초기 속도는 빠르지만 비결정성이 쌓여 신뢰를 잃는다. 규칙 기반 자동화는 안정적이지만 비정형 입력(리뷰, 문의)에 약하다. 둘을 섞고 경계에 사람 확인을 두는 것이 기본값이다.
- **내 경험 연결**: 발주 자동화에서 정상 경로는 자동으로, 실패는 수동 확인 경로로 분리했다.
- **꼬리**: 사람 확인이 병목이 되면 → 확인 결과를 기록해 오류가 없던 유형부터 자동 승인으로 단계적 자율성을 높인다.

## J2. 에이전트 전환 대상을 어떻게 고르고 순서를 매기나 (설계형)

- **질문 의도**: 주요 업무 3번. 자동화 난이도와 회사 임팩트를 어떻게 수치화하는지 본다.
- **답변 골격**: 후보를 모은다(PO 인터뷰, 반복 요청 로그) → 임팩트 축(주당 소요 시간 x 담당자 수, 매출이나 품질에 닿는 정도, 지연 시 비용) → 난이도 축(데이터 접근 가능성, 입력 정형성, 예외 비율, 필요한 권한, 실패 비용) → 2x2로 나눠 임팩트 높고 난이도 낮은 것부터, 임팩트 높고 난이도 높은 것은 작게 쪼개 첫 단계만 → 각 후보에 성공 기준과 관측 기간을 붙인다.
- **판단 기준**: 추정 임팩트는 가정이다. 도입 전 기준선을 짧게라도 측정해 가정을 확인한다.
- **흔한 실수**: 요청한 목소리가 큰 팀 순서로 만든다. 기술적으로 재밌는 것부터 만든다.
- **회사 연결**: 브랜드 기획, 출시, 매출 확인, 수정 사이클에서 반복되는 확인 업무가 후보가 될 수 있다. 실제 업무는 확인 전이므로 예시로만 말한다.
- **꼬리**: 두 팀의 요청이 충돌하면 → 같은 기준표로 비교하고, 기준이 동률이면 결정권자에게 선택지와 포기하는 것을 함께 올린다.

## J3. 사내 바이브코딩 도구를 누구나 쓰게 하려면 (설계형)

- **질문 의도**: 주요 업무 1번. 비개발자가 만든 도구가 늘어날 때의 위험과 지원 구조를 아는지 본다.
- **답변 골격**: 시작 장벽 낮추기(자주 쓰는 업무 유형별 템플릿, 사내 데이터 연결을 미리 붙인 커넥터, 한 번에 배포되는 실행 환경) → 안전한 기본값(격리된 실행 환경, 읽기 전용 기본 권한, 쓰기와 외부 발송은 승인 단계, 비밀은 플랫폼이 주입) → 운영 책임(만든 사람, 소유 팀, 장애 시 연락 경로를 등록해야 배포) → 확산(잘 쓰는 사례를 템플릿으로 승격).
- **대안과 트레이드오프**: 자유를 크게 주면 확산은 빠르지만 데이터 유출과 방치된 도구가 쌓인다. 통제를 강하게 하면 안전하지만 아무도 안 쓴다. 기본값은 안전하게, 예외는 요청으로 여는 방식이 절충이다.
- **근거 사례**: 비개발 담당자가 AI와 사내 도구를 만든 공개 사례에서도 사내망 도구의 외부 노출을 피하려 아웃바운드 연결 방식을 쓰고, 대표 계정 하나로 모든 작업을 하던 구조를 사용자별 최소 권한 위임으로 바꾸는 판단이 필요했다. 비개발자가 만들어도 보안 판단은 생략되지 않는다.
- **꼬리**: 누가 만든 도구가 고장 나면 → 소유자 등록과 사용 중단 절차, 플랫폼 수준의 실행 로그로 원인을 좁힌다.

## J4. 팀별 사용 현황 집계 체계를 어떻게 만드나 (설계형)

- **질문 의도**: 주요 업무 2번. 무엇을 셀지와 그 숫자의 한계를 아는지 본다.
- **답변 골격**: 질문부터 정한다(어느 팀이 무엇을 만들어 쓰는가, 계속 쓰는가, 막히는 곳은 어디인가) → 이벤트 스키마(팀, 도구, 실행 결과, 소요 시간, 실패 유형) → 도구 생성 수보다 반복 사용과 유지 비율, 실패와 중단 지점을 본다 → 사용이 낮은 팀은 숫자로 판단을 끝내지 않고 찾아가 이유를 듣는다.
- **판단 기준**: 사용량과 토큰 수는 활동 신호이지 생산성이나 품질이 아니다. 목표 숫자로 삼으면 숫자 맞추기가 생긴다(Goodhart). 비용, 완료 시간, 재작업은 별도 축으로 본다.
- **데이터 경계**: 개인별 순위나 감시로 읽히지 않게 팀 단위로 집계한다. 프롬프트 원문처럼 민감할 수 있는 내용은 수집 범위와 보존 기간을 먼저 정한다.
- **내 경험 연결**: 처음에 요청 식별자를 메트릭 라벨에 넣었다가 시계열 급증을 겪고 로그로 옮긴 뒤 제한된 차원만 라벨로 쓴 관측 원칙을 그대로 적용한다. 재전송이 이중 집계되지 않게 집계 키 기준으로 교체하는 멱등 동기화를 쓴다.
- **꼬리**: 사용량이 늘었는데 일이 줄지 않았다면 → J6의 결과 지표로 가서 병목이 도구 밖(승인, 핸드오프)에 있는지 본다.

## J5. 공용 에이전트 인프라를 어떤 구조로 만드나 (설계형)

- **질문 의도**: 주요 업무 4번. 각 팀이 직접 자동화하게 하는 공통 구조를 설계할 수 있는지 본다.
- **답변 골격**: 채널 수신(메신저, 웹, 스케줄) → 요청 분류와 세션 관리 → 의도 정리와 부족한 정보 재확인 → 도메인별 워커(조회, 분석, 보고서, 발송) → 도구와 데이터 커넥터 레지스트리 → 실행 로그와 비용 집계.
- **안전 계층**: 역할(워커별 허용 도구), 진입 게이트(맥락 부족 시 재확인), 자연어 규칙(읽기 전용, 스캔 한도), 실행 직전 코드 훅(쓰기, PII 컬럼, 비용 초과 차단). 자연어 규칙은 무시될 수 있으므로 마지막 방어선은 코드로 둔다.
- **루프 가드레일**: 도구 호출 라운드 상한, 같은 인자 반복 호출 차단, 도구별 재시도 제한, 결과 크기 제한과 잘림 표시, 사용량은 응답 뒤 실제 토큰으로 사후 반영.
- **대안과 트레이드오프**: 범용 에이전트 프레임워크는 PoC가 빠르지만 핵심 루프의 제어와 디버깅이 어렵다. 초기에는 프레임워크로 검증하고 핵심 경로가 굳으면 직접 제어할 수 있는 구조로 옮기는 방식을 검토한다.
- **내 경험 연결**: 큐와 DLQ, 멱등 소비, 관측과 알림은 에이전트 워커에도 그대로 필요하다.
- **꼬리**: 팀마다 규칙이 다르면 → 상위 에이전트는 규칙 본문이 아니라 위치만 알고, 워커가 자기 규칙만 불러오게 해 권한과 유지보수를 분리한다.

## J6. 일이 실제로 줄었는지, 도입 성과를 어떻게 판단하나 (설계형)

- **질문 의도**: 공고가 한 사이클의 끝으로 정의한 확인 단계다. 가장 중요한 질문일 수 있다.
- **답변 골격**: 도입 전에 기준선(해당 업무의 주당 소요 시간, 처리 건수, 오류와 재작업, 대기 시간)을 기록한다 → 목표와 관측 기간, 관측 뒤 결정(확대, 수정, 중단)을 미리 정한다 → 도입 뒤 같은 지표를 비교하고 담당자 인터뷰로 보완한다.
- **판단 기준**: 체감과 실측은 다를 수 있다. 숙련 개발자를 대상으로 한 2025년 무작위 대조 연구에서 AI 도구 사용 시 실제로는 19% 느려졌지만 본인들은 20% 빨라졌다고 느꼈다는 결과가 있다. 특정 시점과 조건의 결과라 일반화하지 않지만, 체감 설문만으로 성과를 판단하지 않는 근거로 쓴다.
- **흔한 실수**: 도구 생성 수나 호출 수를 성과로 보고한다. 절감 시간을 인원 감축 목표로 바로 연결한다.
- **출처**: [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity — METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/). 대상은 익숙한 오픈소스 저장소에서 작업한 숙련 개발자 16명, 246개 태스크다.
- **꼬리**: 기준선을 못 쟀다면 → 일부 팀이나 기간을 나눠 비교하거나, 최소한 도입 직후부터라도 같은 지표를 기록하고 한계를 밝힌다.

## J7. 에이전트 결과 품질은 어떻게 검증하나 (설계형)

- **질문 의도**: 만든 에이전트를 믿고 쓰게 하는 장치를 아는지 본다.
- **답변 골격**: 실제 요청에서 대표 사례를 모아 기대 결과가 있는 골든셋을 만든다 → 정답이 하나가 아니면 루브릭으로 채점한다 → 프롬프트나 모델, 도구를 바꿀 때마다 같은 세트로 회귀 평가하고 기준 미달이면 배포하지 않는다 → 운영에서 실패한 사례를 골든셋에 다시 넣는다.
- **추가 장치**: 근거가 부족하면 모른다고 답하거나 사람에게 넘기게 한다. 틀린 답을 확신 있게 내는 것보다 기권이 낫다.
- **내 경험 연결**: 테스트와 CI 게이트, AI 작업 종료 시 자동 검증 루프를 운영했다. 에이전트 평가는 결과가 비결정적이라 테스트보다 표본과 기준이 중요하다는 차이를 말한다.
- **꼬리**: 평가 세트 자체가 낡으면 → 운영 실패 사례의 유입 경로와 주기적 검토 책임자를 정한다.

## J8. 사내 데이터에 닿는 에이전트의 보안과 거버넌스 (설계형)

- **질문 의도**: 팀이 직접 자동화할수록 커지는 권한 위험을 다룰 수 있는지 본다.
- **답변 골격**: 최소 권한(워커와 도구 단위, 기본 읽기 전용) → 사용자별 위임(공용 관리자 계정 대신 요청자 권한으로 실행) → 비밀은 코드와 도구 정의에서 분리하고 회전 가능하게 → 개인정보 컬럼 차단과 마스킹 → 모든 도구 호출의 감사 로그 → 외부 발송, 결제, 삭제 같은 되돌리기 어려운 동작은 사람 승인.
- **대안과 트레이드오프**: 공용 계정 하나는 빠르지만 사고 범위가 전사로 커지고 책임 추적이 어렵다. 사용자별 위임은 설정 비용이 있지만 사고 범위와 퇴사 시 권한 정리가 명확하다.
- **내 경험 연결**: 컨테이너 런타임 비밀 주입, 최소 권한과 회전, FIDO 인증 서버 개발 경험.
- **꼬리**: 외부 입력(리뷰, 문의)에 숨은 지시가 있으면 → 외부 텍스트는 데이터로만 취급하고, 그 결과로 권한 있는 동작을 바로 실행하지 않도록 쓰기 전에 규칙 검사와 승인을 둔다.

## J9. 목표 전달과 우선순위 배분을 에이전트가 맡는 구조 (설계형)

- **질문 의도**: 주요 업무 5번. 가장 새로운 요구다. 정보 원천, 정의, 사람의 역할을 나눌 수 있는지 본다.
- **답변 골격**: 정보 원천을 먼저 정한다(OKR, 마일스톤, 프로젝트 상태를 한 곳에서 구조화) → 목표와 지표의 정의를 한 곳에 명시해 같은 질문에 같은 답이 나오게 한다 → 구성원 질문(이번 분기 할 일, 우선순위)과 대표 질문(진행 상황, 위험)을 같은 원천에서 답한다 → 우선순위 충돌, 평가, 사람의 상태에 관한 판단은 에이전트가 결정하지 않고 담당 리더에게 넘긴다.
- **판단 기준**: 에이전트는 원천 데이터보다 정확해질 수 없다. 원천이 최신이 아니면 에이전트가 틀린 확신을 퍼뜨린다. 갱신 책임과 최신성 표시가 먼저다.
- **회사 연결**: 회사 소개문이 OKR 훈련과 마일스톤 관리를 조직 습관으로 소개한다. 이미 구조화된 원천이 있는지 확인하는 것이 첫 질문이다.
- **꼬리**: 구성원이 에이전트 답을 불신하면 → 답마다 근거 원천과 갱신 시각을 붙이고, 틀린 답을 신고하는 경로를 둔다.

## J10. MCP가 무엇이고 왜 쓰나 (사실형)

- **질문 의도**: 에이전트와 사내 도구를 연결하는 표준을 아는지 본다.
- **핵심 답변**: MCP(Model Context Protocol)는 AI 애플리케이션을 파일, 데이터베이스 같은 데이터 소스와 도구, 워크플로에 연결하는 오픈소스 표준이다. 호스트 애플리케이션 안의 클라이언트가 MCP 서버에 연결하고, 서버는 도구, 리소스, 프롬프트를 노출한다. 모델마다 도구마다 연동을 따로 만드는 N×M 문제를 공통 인터페이스로 줄인다.
- **흔한 오답**: MCP가 권한과 보안을 자동으로 해결한다고 말한다. 서버가 노출하는 도구의 권한 범위와 인증, 감사는 여전히 설계해야 한다.
- **꼬리**: 사내 시트나 매출 데이터를 MCP로 붙일 때 주의점은 → 읽기와 쓰기 도구를 분리하고, 사용자 권한으로 호출하며, 반환 크기와 민감 필드를 제한한다.
- **학습 정본과 출처**: [MCP 공식 문서, Introduction](https://modelcontextprotocol.io/introduction), [MCP 공식 문서, Architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture) (2026-09-29 Introduction 원문 대조)
