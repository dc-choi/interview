# 블리츠다이나믹스 1차, 서비스 맥락 질문, 역질문, 체크리스트

> [[Interview-Prep-BlitzDynamics-1st|1차 메인]]의 하위 문서다. 회사의 실제 업무, 조직, 사내 도구와 에이전트 구현은 공개되지 않았다. 아래 서비스 예시는 공개 소개문에서 출발한 가설이며 면접에서 사실처럼 말하지 않는다.

## 서비스 맥락 질문

### S1. 우리 사업을 어떻게 이해했나

- **공개 자료에서 확인한 문제**: 배달 F&B 브랜드를 기획해 배달앱에 올리고 매출을 보고 고치는 사이클을 반복하며, 직영 매장에서 여러 브랜드를 운영한다고 소개했다. 회사 소개문은 인사와 교육, 생산과 품질, 마케팅과 고객 응대를 에이전트가 맡는 방향을 제시한다.
- **답변 골격**: 사업을 한 문장으로 요약 → 이 사이클에서 반복되는 확인과 조율 업무가 많을 것이라는 가설 → 그래서 AX 담당자가 개별 자동화보다 팀이 직접 자동화하는 인프라를 만드는 것이 사업 속도와 연결된다는 이해.
- **주의**: 매출 수치와 매장 계획은 인용하지 않는다. 제3자 페이지에서 본 운영 대행 모델, 브랜드명, 인원 수도 말하지 않는다.
- **꼬리 대비**: 배달앱으로 우리 브랜드를 주문해 봤나 → [사용자 확인 필요] 면접 전 확인한 사실만 말한다. 운영 브랜드 목록은 공개 자료로 확인하지 못했으므로 모르면 모른다고 답한다.

### S2. 배달 브랜드 운영에서 첫 에이전트 전환 후보를 하나 고른다면

- **답변 골격**: 후보를 바로 단정하지 않고 J2의 기준(주당 소요 시간, 담당자 수, 입력 정형성, 실패 비용)으로 고르겠다고 먼저 말한다 → 예시로만 두 가지를 비교한다. 브랜드별 매출과 리뷰를 모아 주간 리포트 초안을 만드는 일은 입력이 정형에 가깝고 틀려도 되돌리기 쉬워 초기 후보가 되기 좋다. 고객 환불 응대처럼 돈과 고객 약속이 걸린 일은 초안과 사람 승인으로 시작한다.
- **판단 기준**: 이미 에이전트가 맡고 있는 영역일 수 있으므로 현재 상태를 먼저 묻는다.
- **유사 경험**: IoT 상태 집계와 자동 통보 리포트.
- **한계**: 배달앱 판매자 데이터 접근 방식과 약관 제약은 모른다. 데이터를 어떻게 가져오는지가 난이도를 크게 바꾼다는 점을 말한다.

### S3. 이미 에이전트가 운영을 맡는다고 했는데, 무엇을 더할 수 있나

- **답변 골격**: 현재 에이전트를 만드는 주체와 방식을 먼저 확인하겠다 → 공고가 말한 병목(AX 담당자가 대신 만들면 그 속도가 사업 속도를 제한)을 공통 인프라로 푸는 데 기여 → 구체적으로는 실행 기록과 실패 관측, 권한과 비밀 관리, 재사용 템플릿, 성과 측정처럼 개별 에이전트마다 반복되는 부분을 플랫폼으로 올리는 일.
- **내 경험 연결**: 큐, 재시도, DLQ, 관측과 알림을 운영한 백엔드 경험, 팀 AI 협업 규약.

### S4. 매장 현장 직원처럼 PC 앞에 있지 않은 구성원도 쓰게 하려면

- **답변 골격**: 새 도구를 설치하게 하기보다 이미 쓰는 메신저나 알림 채널로 질문하고 답을 받게 한다 → 입력은 짧게, 답은 한 가지 행동으로 → 틀린 답을 신고하는 버튼 하나를 둔다 → 교대 근무라면 요청과 알림 시간대를 맞춘다.
- **판단 기준**: 현장 사용자는 도구를 배우는 시간이 곧 업무 시간이다. 학습 비용이 가장 낮은 채널이 우선이다.
- **한계**: 현장 업무 흐름을 직접 보지 않고는 설계하지 않는다. 첫 주에 현장 업무를 따라가 보겠다고 말한다.

### S5. 활용이 저조한 팀을 찾아갔더니 도구가 아니라 업무 절차가 문제였다면

- **답변 골격**: 반대 이유를 방향(목적이 안 맞음), 부담(쓰면 일이 늘어남), 정보(효과를 못 믿음)로 나눈다 → 절차 문제라면 도구를 억지로 맞추지 않고 해당 PO와 절차 변경을 먼저 합의한다 → 도구가 풀 수 있는 부분만 좁혀 다시 시도하고, 결과를 같은 기준으로 확인한다.
- **대안과 트레이드오프**: 도구를 계속 고치면 개발 비용만 늘고, 절차를 바꾸자고 하면 조직 저항이 생긴다. 어느 쪽이 병목인지 기준선 데이터로 보여 주는 것이 설득의 출발점이다.
- **유사 경험**: 팀 AI 협업 규약을 작은 영역부터 적용해 효과를 보인 방식.

### S6. 합류하면 첫 90일에 무엇을 하겠나

- **답변 골격**: 첫 30일은 현재 바이브코딩 도구와 사용 현황, 기존 에이전트를 파악하고 팀별 PO를 만나 반복 업무 후보를 모은다 → 60일까지 사용 현황 집계를 먼저 만들고 우선순위 기준표로 후보 한두 개를 골라 기준선을 잰다 → 90일까지 한 팀과 공통 인프라 위에서 첫 전환을 끝내고 일이 줄었는지 확인한 결과를 공유한다.
- **판단 기준**: 첫 성과는 큰 플랫폼이 아니라 한 팀에서 확인된 결과다. 플랫폼은 두 번째 팀부터 반복되는 부분을 올리며 키운다.
- **주의**: 실제 기대치는 역질문 B1로 확인하고 답을 맞춘다.

## 역질문

[[My-Reverse-Questions]]에서 5개를 고르고 회사 특이 질문 2개를 더한다. 핵심 2~3개는 외워 자연스럽게 던지고, 나머지는 시간에 맞춰 고른다.

1. **B1, 초기 과제와 성공 기준**: 합류 후 가장 먼저 책임질 과제와, 잘하고 있다고 판단할 기준은 무엇인가요?
2. **A1, 가장 먼저 풀 문제**: 지금 사내 자동화에서 가장 먼저 해결해야 할 팀이나 업무는 어디이고, 그 우선순위가 높은 이유도 듣고 싶습니다.
3. **A4, 협업 경계**: 이 역할은 누구에게 보고하고, 각 팀 PO와는 어떤 방식으로 우선순위를 결정하나요? 개발 조직과는 어떻게 역할을 나누나요?
4. **B2, 도입 결정 방식**: 새 AI 도구나 외부 서비스 도입, 사내 데이터 접근 권한은 어떤 근거와 절차로 결정하나요?
5. **F1, 이후 전형**: 이후 단계의 목적과 형식, 참여 역할을 미리 알 수 있을까요? 과제나 설계 면접이 있다면 준비 깊이를 맞추고 싶습니다.
6. **회사 특이, 현재 도구 상태**: 공고에 사내 바이브코딩 도구가 지금은 기본 기능만 있다고 적혀 있었는데, 현재 어떤 형태이고 어느 팀이 가장 많이 쓰고 있나요?
7. **회사 특이, 성과 판단**: 인프라를 만든 뒤 팀의 일이 실제로 줄었는지를 지금은 어떤 방식으로 확인하고 계신가요? 이 역할의 성과도 같은 기준으로 보시는지 궁금합니다.

**아껴둘 질문**: 조직 운영 에이전트 설계의 현재 진행 상황, 에이전트 실패 사례와 대응, 공고 문안의 R&D 문단이 이 역할과 관련이 있는지(필요할 때만 가볍게).

**하지 않을 질문**: 매출과 투자 세부, 처우 금액, 강도에 대한 부정적 프레임.

## 면접 준비 체크리스트

### 면접 시작 전

- [ ] FIT 문서 C3 이직 사유 답변을 소리 내어 30초 안에 말하는 연습을 한다 (답변 확정, 2026-09-29)
- [ ] 면접 일시, 차수, 형식, 참여 역할을 확인한다. 참석자는 역할로만 적는다
- [ ] 공고 5개 주요 업무를 각각 한 문장으로 말할 수 있다
- [ ] 회사가 운영하는 배달 브랜드를 공개 경로로 확인하고, 확인한 사실만 한 문장으로 준비한다
- [ ] 핵심 역질문 2~3개(B1, 회사 특이 7번, A4)를 외운다

### 보강이 필요한 영역

| 영역 | 보강할 핵심 개념과 판단 기준 | 복습 완료 |
| --- | --- | --- |
| 업무 분해와 우선순위 | 되돌리기 가능성, 실패 비용, 빈도, 입력 정형성 기준표 (J1, J2) | [ ] |
| 성과 측정 | 기준선, 결과 지표와 활동 지표의 구분, 체감과 실측 차이 (J4, J6) | [ ] |
| 에이전트 인프라 | 워커 분리, 4겹 안전 계층, 루프 가드레일, 비용 사후 반영 (J5) | [ ] |
| 평가와 품질 | 골든셋, 루브릭, 회귀 게이트, 기권 (J7) | [ ] |
| 보안과 권한 | 최소 권한, 사용자별 위임, 감사 로그, 외부 입력의 숨은 지시 (J8) | [ ] |
| 설계형 진행 방식 | 명확화, 제약과 가정, 대안 비교, 구현, 개선 순서로 말하기 | [ ] |

### 강하게 어필할 포인트

- 팀 AI 협업 규약: 규칙, 코드 수준 검증, 작은 영역부터 확산
- 반복 업무 자동화: 발주 이벤트 자동화와 상태 리포트 자동 통보, 실패를 사람 확인 경로로 드러낸 설계
- 실사용자 운영: 출석부의 사용자 인터뷰와 운영 지표 점검 (수치 없이)
- 측정 습관: 수치마다 측정 조건을 설명할 수 있는 태도

### 답변 점검

- [ ] 외부 귀책과 전 직장 평가 표현이 없다
- [ ] 부정적 단어(워라밸, 연봉)를 먼저 꺼내지 않는다
- [ ] 모든 답변 끝줄이 공고의 역할(팀이 직접 자동화, 일이 줄었는지 확인)에 연결된다
- [ ] LLM 에이전트 제품 배포 경험이 없다는 사실을 먼저 밝히고 설계 판단으로 답한다
- [ ] 출석부와 전, 현 직장 수치 중 이력서에 없는 것은 말하지 않는다
