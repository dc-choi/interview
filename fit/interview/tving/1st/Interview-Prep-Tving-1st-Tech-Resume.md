# 티빙 1차, 이력서 기반 기술 질문

> [[Interview-Prep-Tving-1st|메인]]으로 돌아가기. [[My-Tech-Cards]]의 카드를 fork했다. 수치는 공개 이력서에 있는 값만 쓰고, 측정 조건을 설명할 수 있을 때만 말한다. 각 카드 끝줄은 공고의 공개 문장에만 연결한다.

## R1. 수천 대 IoT 하드웨어 동시 요청의 Race Condition을 어떻게 풀었나 (카드 1)

- 유형: 경험형. 의도: 동시성 문제를 재현하고 잠금 전략의 대가까지 아는지.
- 핵심 답변: 같은 재고 상태를 동시에 바꾸는 경로에서 `SELECT ... FOR UPDATE NOWAIT`와 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한된 재시도를 조합했다. 충돌이 잦은 쓰기라 늦게 충돌을 발견하는 낙관적 잠금보다 비관적 잠금이 단순했다. 입력 검증과 외부 호출은 트랜잭션 밖에서 끝내고, 여러 대상을 갱신할 때는 업무 키 순서를 통일했다. 보호 대상이 한 DB 트랜잭션 안에 있어 분산 락보다 DB 락을 우선했다.
- 검증: 동시 요청을 재현해 최종 수량, 잠금 실패, 재시도 뒤 상태를 확인했다.
- 한계: 당시 재시도는 고정 간격이었다. 다시 한다면 지수 백오프와 지터를 검증한다. 잠금은 유입량을 흡수하지 못하므로 급증을 흡수하려면 업무 키별 순서 보장 큐와 제한된 워커 동시성을 함께 본다.
- 꼬리: `NOWAIT`와 `SKIP LOCKED`의 차이(특정 행을 반드시 처리해야 하면 NOWAIT, 큐처럼 다른 행을 가져가도 되면 SKIP LOCKED). 락 순서가 데드락을 완전히 막는가(아니다, 확률을 낮출 뿐이고 데드락 오류는 새 트랜잭션에서 제한 재시도).
- 티빙 연결: 순간적인 트래픽 급증에서 정합성을 지키는 문제는 같다. 다만 재생 요청처럼 읽기 중심 경로에는 잠금보다 캐시와 전달 구조가 먼저라는 점도 함께 말한다.

## R2. 왜 Kafka가 아니라 EventBridge와 SQS를 골랐나 (카드 2)

- 유형: 경험형과 설계형. 의도: 브로커를 용도로 비교했는지. 공고의 Kafka 우대와 직접 연결된다.
- 핵심 답변: 상태 변경 뒤 후속 발주 처리를 비동기로 분리해야 했고, 필요한 것은 재시도와 DLQ가 있는 작업 큐였다. 당시 조직에서 Kafka를 운영할 여력과 필요한 리플레이, 강한 순서 보장, 매우 높은 처리량 요구를 비교해 관리형 큐를 골랐다. 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했다.
- 한계: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행이 실패하면 이벤트가 누락될 수 있었고, 당시에는 발행 재시도와 운영 확인으로 다뤘다. 다시 한다면 상태 변경과 Outbox 레코드를 같은 트랜잭션에 쓴다.
- 꼬리: 어떤 조건이면 Kafka를 고르나. 여러 소비 팀이 같은 이벤트를 각자 속도로 읽어야 하고, 과거 이벤트를 다시 읽어 재계산해야 하며, 키 단위 순서가 중요할 때다.
- 티빙 연결: 시청 로그는 추천, 지표, 정산이 각자 소비하고 재처리할 수 있어야 하므로, 공고가 Kafka 기반 비동기 처리를 명시한 이유가 이 조건과 맞는다고 본다. 이는 공고 문장에서 읽은 해석이며 실제 구성은 확인한다.

## R3. 복합 인덱스로 슬로우 쿼리를 99.3% 개선한 과정 (카드 3)

- 유형: 경험형. 의도: 실행 계획을 근거로 판단했는지, 수치의 측정 조건을 아는지.
- 핵심 답변: 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 `EXPLAIN ANALYZE`로 확인했다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 설계하고, 실행 계획에서 정렬과 상위 레코드 접근에 쓰이는지 재확인했다.
- 측정 경계: [사용자 확정 필요: 99.3%가 쿼리 1건의 전후인지, 어떤 환경과 cache 조건인지]. 서브쿼리 관측값과 배치 전체 시간을 같은 지표로 비교하지 않는다.
- 한계: 인덱스는 쓰기와 저장 비용을 늘린다. 인접 쓰기 경로에 미치는 영향을 함께 본다.
- 꼬리: 컬럼 순서는 카디널리티 하나로 정하지 않는다. 동등 조건, 범위 조건, 정렬, 반환 컬럼으로 판단한다.
- 티빙 연결: 공고의 RDB 모델링과 성능 최적화 요건에 직접 대응한다.

## R4. Prisma N개 쿼리를 단일 쿼리로 합쳐 응답속도 90% 향상 (카드 4)

- 유형: 경험형. 의도: ORM이 만든 SQL을 직접 확인하는지. Spring Data JPA의 N+1로 꼬리가 이어질 수 있다.
- 핵심 답변: 관계를 포함한 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했다. 당시 설정에서는 include 관계를 여러 쿼리로 읽어 애플리케이션에서 결합했다. `relationJoins` 기능을 켜고 `relationLoadStrategy: 'join'`을 적용해, MySQL에서 correlated subquery와 JSON aggregation 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했다. 하코 커뮤니티에서 이 사례를 발표했다.
- 한계: 호출 수는 줄지만 반환 데이터 중복과 DB 집계 비용이 늘 수 있다. Prisma 버전과 설정에 따라 동작이 다르다.
- 꼬리, JPA라면: 연관 관계 지연 로딩에서 컬렉션을 순회하면 N+1이 생긴다. fetch join, `@EntityGraph`, batch size 설정을 비교하고, 컬렉션 fetch join과 페이지네이션을 함께 쓰면 메모리에서 페이징할 수 있다는 점을 조건으로 말한다. 적용 전에는 실제 SQL 로그로 확인한다.
- 티빙 연결: 언어가 바뀌어도 ORM이 만든 SQL을 확인하는 습관은 그대로 가져간다.

## R5. 단일 NGINX에서 CloudFront, ELB, ECS로 전환하고 Read Replica를 도입한 이유 (카드 6)

- 유형: 경험형과 설계형. 의도: 전달 계층과 읽기 분산의 판단 근거.
- 핵심 답변: 트래픽 증가로 단일 서버의 병목과 장애 영향 범위가 커져, 정적 자원은 CloudFront로, 애플리케이션은 ELB 뒤 ECS Fargate로 옮겼다. RDS Read Replica로 읽기 부하를 분산해 응답속도를 40% 개선했다. 쓰기와 쓰기 직후 읽기는 primary로 보내고, 지연을 허용할 수 있는 조회만 replica로 보냈다.
- 한계: 복제 지연을 숨기면 안 된다. 다중 가용 영역은 리전 장애를 해결하지 않으며, RTO와 RPO를 먼저 정해야 한다.
- 꼬리: Kubernetes는 왜 안 썼나. 당시 운영 인력과 워크로드에서 관리형 태스크 환경이 운영 부담을 낮췄다. 멀티 워크로드와 복잡한 트래픽 라우팅이 필요하면 다시 비교한다.
- 티빙 연결: CDN 도입 경험은 있지만 멀티 CDN과 경로 전환은 경험이 없다고 경계를 분명히 한다.

## R6. Docker 멀티스테이지 빌드로 이미지와 배포 시간을 줄인 방법 (카드 6)

- 유형: 경험형. 의도: 배포 효율 개선의 원리와 트레이드오프.
- 핵심 답변: 빌드 도구와 실행 의존성을 분리하고 빌드 산출물만 실행 이미지에 복사해 이미지 크기를 909MB에서 513MB로 43.6% 줄였고, 배포 시간을 3분 10초에서 2분 20초로 26.3% 단축했다.
- 꼬리: alpine은 musl과 glibc 차이로 네이티브 모듈 호환성 문제가 있고, distroless는 셸이 없어 디버깅이 어렵다. JVM 이미지라면 JRE 기반 실행 이미지와 레이어 분리를 검토하고, 컨테이너 메모리 한도와 힙 설정을 함께 본다.
- 티빙 연결: 공고의 CI/CD와 테스트 자동화 문화에 연결한다.

## R7. Grafana, Prometheus, Loki 관측 체계와 경보를 어떻게 설계했나 (카드 5)

- 유형: 경험형과 설계형. 의도: 시청 데이터 품질 모니터링과 장애 조기 탐지로 확장할 수 있는지.
- 핵심 답변: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었다. 식별자는 구조화 JSON 로그 본문으로 옮기고, 메트릭 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼다. 개별 요청은 로그에서 추적한다. Grafana Alerting으로 실시간 장애 알림을 만들고, 배터리 부족과 통신 지연을 주기 집계해 알림톡과 이메일로 자동 통보하는 리포트를 구축했다.
- 한계: 경보 기준은 과거 숫자를 복사하지 않고 사용자 영향 SLI에서 역산한다. 당시 경보가 SLO burn-rate 경보였다고 말하지 않는다.
- 꼬리: API에는 RED, 큐와 DB 같은 자원에는 USE 관점을 적용한다.
- 티빙 연결: 시청 데이터 품질 모니터링도 같은 원칙이다. 이벤트 ID와 세션 ID 같은 고유값은 라벨이 아니라 이벤트 본문에 두는 것을 직접 겪은 실수로 말한다. 이벤트 수, 누락률, 지연 도착 비율 같은 품질 지표를 정의하고 사용자 영향과 연결해 경보한다. 상세는 [[Interview-Prep-Tving-1st-Service|서비스 맥락]] S5.

## R8. 팀 AI 협업 규약과 회귀 루프는 구체적으로 무엇인가

- 유형: 경험형. 의도: 공고의 AI 도구 활용, 채용 사이트의 AI One team. 실제 적용 범위와 검증 책임.
- 핵심 답변: 경로별 `CLAUDE.md`와 `AGENTS.md`로 도메인 규칙과 검증 절차를 나눠 문맥을 자동 로드하게 하고, AI가 건드릴 영역과 건드리면 안 되는 영역을 규약으로 명문화했다. 작업 종료 시점에 변경 파일 검사와 테스트를 돌려 품질을 스스로 검증하는 회귀 루프를 붙였다. 최종 채택과 책임은 사람이 진다.
- 한계: 팀 전체 효과를 수치로 말하지 않는다. 공개 이력서에 없는 내부 지표는 쓰지 않는다.
- 꼬리: AI가 만든 테스트를 어떻게 믿나. 테스트가 실패해야 할 조건에서 실제로 실패하는지, 스펙과 대조해 확인한다.

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- 유형: 경험형. 의도: 공고의 AI 도구 활용을 실제로 해 봤는지, 검색 방식을 정량 비교로 고르는지.
- 주의: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 먼저 개인 프로젝트라고 밝힌다.
- 핵심 답변: 개인 프로젝트로, 설계 문서와 의사결정을 근거 관계가 있는 그래프로 색인해 사람과 AI가 이전 판단을 재사용하게 만든 지식 시스템이다. Markdown 위키링크와 frontmatter의 근거 관계를 그래프로 추출하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했다. 검색은 MCP 도구와 CLI로 노출했다. 검색 방식을 바꾸기 전에 평가 질문부터 고정했고, 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정해 응답 크기 예산 안에 모두 나와야 통과로 쳤다. 무관한 질문은 빈 결과여야 통과하는 음성 질문으로 넣었다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, RRF를 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 그대로였고 기존 통과 4건을 잃어 채택하지 않았다. 그 74개를 포함한 94개 질문으로 bge 리랭커를 비교했더니 통과가 41개에서 40개로 개선이 없고 질문당 약 4.7초가 더 걸려 이것도 채택하지 않았다. 문제가 후보 검색보다 예산 안의 절 선택에 있다고 보고 절 선택 방식을 고쳐 기존 94개 중 통과를 41개에서 43개로 올렸다. 모두 기각한 판단을 측정으로 내렸다는 점이 강점이다.
- 판단 기준: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 이득이 있어도 바로 바꾸지 않고, 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다.
- 꼬리: 골든 케이스 선정과 지표는 → 별도로 사람이 검수한 골든 세트는 아니다. 평가 질문은 대부분 원문을 보고 만든 합성 질문이고, 지표는 양성은 필수 근거 그룹이 예산 안에 모두 나오면 통과, 음성은 빈 결과면 통과, 후보 단계는 필수 근거가 후보 50개 안에 드는지다.
- 이력서 정정: 제출한 이력서의 골든 케이스 약 145건 문구는 부정확하다. 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- 한계를 먼저 말할 것: 합성 표본이라 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문의 거절은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- 판단 기준 연결: 근거 없는 수치를 만들지 않고, 측정한 범위 안에서만 결론을 말한다.
- 티빙 연결: 공고의 AI One team과 AI 도구 활용 개발 요건에 대한 근거다. 서비스에 LLM 기능을 운영한 경험은 아니므로 AI 도구를 설계하고 검증한 경험으로만 말한다.
