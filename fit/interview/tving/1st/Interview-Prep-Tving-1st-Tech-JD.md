# 티빙 1차, JD 기반 기술 질문

> [[Interview-Prep-Tving-1st|메인]]으로 돌아가기. 공고의 필수요건과 우대사항에서 나올 질문이다. 사실형은 의도, 핵심, 흔한 오답, 꼬리, 출처를, 설계형은 판단 기준과 대안을 둔다. 직접 운영해 보지 않은 기술은 답변 첫 문장에서 경험 범위를 밝힌다. 버전에 따라 달라지는 동작은 조건을 붙였다.

## J1. Node.js 이벤트 루프와 Spring MVC 스레드 모델은 어떻게 다른가 (사실형)

- 의도: 주력 런타임에서 JVM으로 넘어올 때 동시성 모델을 이해하는지.
- 핵심: Node.js는 단일 이벤트 루프가 JavaScript를 실행하고 I/O를 비동기로 위임하므로, CPU를 오래 쓰는 코드가 루프 전체를 막는다. Spring MVC는 기본적으로 요청당 스레드 모델이라 블로킹 I/O를 써도 코드가 단순하지만, 동시 요청 수가 스레드 풀과 DB 커넥션 풀 크기에 묶인다. Java 21 이상에서는 가상 스레드로 블로킹 코드 스타일을 유지하면서 대기 중인 스레드 비용을 줄일 수 있고, Spring Boot 3.2 이상은 설정으로 이를 켤 수 있다. Kotlin 코루틴은 suspend 함수로 비동기 흐름을 순차 코드처럼 쓰게 해 주는 언어 수준의 방식이다.
- 흔한 오답: 가상 스레드를 켜면 처리량이 무조건 오른다고 말한다. 하위 자원인 DB 커넥션 풀, 외부 API 한도는 그대로이고, 가상 스레드는 CPU 작업을 빠르게 하지 않는다.
- 꼬리: 스레드 풀 크기를 늘리면 좋아지나(하위 자원과 컨텍스트 전환 비용 때문에 정점 뒤 떨어진다). WebFlux는 언제 쓰나(대부분 대기인 I/O를 많이 다중화해야 하고 팀이 리액티브 디버깅 비용을 감당할 때).
- 내 연결: Node.js에서 이벤트 루프 블로킹을 피하던 판단은 JVM에서 블로킹 호출이 어느 풀을 점유하는지로 옮겨 온다.

## J2. `@Transactional`은 어떻게 동작하고 언제 적용되지 않나 (사실형)

- 의도: Spring 실무 공백을 원리로 메울 수 있는지. RDB 정합성 요건과 연결.
- 핵심: 선언적 트랜잭션은 AOP 프록시가 메서드 호출을 가로채 트랜잭션을 열고 닫는다. 그래서 같은 클래스 안에서 자기 메서드를 호출하면 프록시를 거치지 않아 적용되지 않는다. 기본 롤백 대상은 unchecked 예외와 Error이며, checked 예외는 `rollbackFor`로 지정해야 롤백된다. 전파 속성은 기본이 기존 트랜잭션 참여(REQUIRED)이고, REQUIRES_NEW는 기존 트랜잭션을 보류하고 새로 연다.
- 흔한 오답: 모든 예외에서 롤백된다고 말한다. private 메서드에도 붙이면 된다고 말한다.
- 꼬리: 트랜잭션 안에서 외부 API를 호출하면 무엇이 문제인가(커넥션과 락 보유 시간이 늘고, 외부 호출은 롤백되지 않는다. 카드 1처럼 외부 호출을 트랜잭션 밖으로 뺀다). 읽기 전용 트랜잭션은 무엇을 바꾸나(구현과 드라이버에 따라 플러시 생략과 최적화 힌트가 달라지므로 조건을 확인한다).
- 내 연결: NestJS에서 트랜잭션 경계를 UseCase 단위로 잡던 판단을 서비스 계층의 트랜잭션 경계로 옮긴다.

## J3. Kafka는 순서와 전달을 어떻게 보장하나 (사실형)

- 의도: 우대사항 Kafka. 운영 경험이 없어도 모델을 정확히 아는지.
- 경험 범위: Kafka 운영 경험은 없고, 이력서의 브로커 선택 비교까지 했다고 먼저 말한다.
- 핵심: 토픽은 파티션으로 나뉘고 순서는 파티션 안에서만 보장된다. 같은 키를 같은 파티션으로 보내 키 단위 순서를 얻는다. 컨슈머 그룹 안에서 한 파티션은 한 컨슈머에게만 할당되므로 병렬도의 상한은 파티션 수다. 컨슈머는 오프셋을 커밋해 어디까지 읽었는지 남기며, 처리 후 커밋하면 실패 시 다시 읽어 적어도 한 번 처리가 되고, 처리 전 커밋하면 유실될 수 있다.
- 흔한 오답: 토픽 전체 순서가 보장된다고 말한다. 파티션을 늘려도 키 순서가 유지된다고 말한다(파티션 수가 바뀌면 키와 파티션의 매핑이 바뀔 수 있다).
- 꼬리: 리밸런싱 중 중복 처리는 왜 생기나(커밋 전에 파티션이 다른 컨슈머로 넘어가면 같은 레코드를 다시 읽는다). Kafka 트랜잭션이 외부 DB 쓰기까지 정확히 한 번을 보장하나(아니다, Kafka 내부의 읽기, 처리, 쓰기 범위다. 외부 부작용은 멱등성으로 막는다).

## J4. 소비 실패와 재처리는 어떻게 설계하나 (설계형)

- 의도: Kafka와 MQ 기반 비동기 처리의 운영 판단. 시청 로그 소비 팀과의 계약으로 이어진다.
- 판단 기준: 일시 오류인지 영구 오류인지, 순서를 지켜야 하는지, 재처리가 멱등한지.
- 답변 골격:
  1. 영구 오류(스키마 위반, 필수 필드 누락)는 재시도하지 않고 격리 토픽으로 보낸다.
  2. 일시 오류는 제한 재시도한다. 제자리 재시도는 순서를 지키지만 파티션을 막고, 재시도 토픽으로 돌리면 흐름은 막히지 않지만 해당 키의 순서가 깨질 수 있다.
  3. 재시도 예산을 넘기면 DLT로 보내고, 원인과 원본 오프셋을 남겨 재처리 도구로 되돌릴 수 있게 한다.
  4. 소비 로직은 이벤트 ID 기준으로 중복을 제거해 재전달을 정상 경로로 만든다.
- 대안과 트레이드오프: Spring Kafka는 블로킹 재시도용 에러 핸들러와 재시도 토픽을 쓰는 논블로킹 재시도를 모두 제공한다. 순서가 중요한 키는 블로킹, 처리량이 중요한 분석 이벤트는 논블로킹이 후보다.
- 꼬리: DLT가 쌓이면 누가 무엇을 보나(소비 지연과 DLT 유입률 경보, 재처리 담당과 절차).
- 내 연결: SQS에서 영구 오류 격리, 제한 재시도, DLQ와 수동 확인 경로로 설계한 경험(카드 2)을 그대로 옮긴다.

## J5. 순간 트래픽 급증에 대응하는 캐시와 전달 구조 (설계형)

- 의도: 공고의 캐시와 전달 구조, 라이브 시작처럼 요청이 한꺼번에 몰리는 상황.
- 판단 기준: 응답이 사용자 공통인지, 권리와 지역처럼 사용자나 조건별인지. 얼마나 오래된 값을 허용하는지.
- 답변 골격:
  1. 공통 응답(편성, 공개 메타)은 CDN과 공유 캐시에 두고 짧은 TTL과 stale 허용 윈도를 준다.
  2. 조건별 판단(권리, 디바이스)은 판단에 필요한 입력만 캐시하고, 개인별 응답이 공유 캐시 키에 섞이지 않게 한다.
  3. 인기 키 동시 만료는 TTL 지터, 요청 병합, 백그라운드 갱신으로 막는다.
  4. 애플리케이션 로컬 캐시와 Redis 두 단계를 쓰면 원격 호출은 줄지만 무효화가 어려워지므로, 로컬은 아주 짧은 TTL로만 둔다.
  5. 캐시가 실패하면 원본으로 돌아가되 동시 요청 수를 제한해 원본을 보호한다.
- 흔한 실수: 캐시가 장애를 새 병목으로 옮긴다. 이벤트 직전에 캐시를 비워 원본으로 몰린다.
- 꼬리: 이벤트 시작 전에 무엇을 미리 데우나(편성과 재생 경로 결정 입력, 인기 콘텐츠 메타).
- 내 연결: 외부 메타데이터를 초기 적재한 경험(카드 8)과 CloudFront 도입. Cache Warming과 Cache-Aside를 구분해 말한다.

## J6. HLS와 DASH는 어떻게 동작하나 (사실형)

- 의도: 우대사항 HLS와 DASH. 재생 경로 결정이 무엇을 반환하는지 아는지.
- 경험 범위: 스트리밍 전달을 운영한 경험은 없고 개념을 학습했다고 먼저 말한다.
- 핵심: 둘 다 HTTP 기반 적응형 스트리밍이다. 영상을 짧은 segment로 나누고, 재생 목록(HLS는 m3u8 playlist, DASH는 MPD)이 여러 화질 표현과 segment 위치를 알려 준다. HLS는 표현 목록을 담은 multivariant playlist와 표현별 media playlist로 나뉜다. 어떤 화질을 받을지는 플레이어가 측정한 처리량과 버퍼로 segment마다 고르며(ABR), 서버는 segment를 중계하지 않고 CDN이 전달한다. 라이브에서는 재생 목록이 계속 갱신되므로 재생 목록은 짧게, segment는 길게 캐시하는 식으로 성격이 다르다.
- 흔한 오답: 서버가 사용자별로 화질을 정해 스트림을 밀어 준다고 말한다. 라이브 재생 목록을 VOD처럼 길게 캐시해도 된다고 말한다.
- 꼬리: 라이브 지연을 줄이려면(segment 길이를 줄이면 요청 수와 부하가 늘어난다. HLS는 부분 segment를 쓰는 저지연 확장이 별도 초안으로 정리돼 있다). 재생 시작 API가 반환하는 것(권리 확인 결과, 서명된 접근 정보, 재생 목록 위치).

## J7. 테스트 코드는 어떻게 작성하나, Spring에서는 (사실형)

- 의도: 필수요건 코드 리뷰와 테스트. JVM 도구를 아는지.
- 핵심: 도메인 규칙은 프레임워크 없이 단위 테스트하고, 저장소와 메시징 경계는 실제 의존성에 가까운 통합 테스트로 검증한다. Spring에서는 전체 컨텍스트를 띄우는 `@SpringBootTest`와, 웹 계층이나 JPA 계층만 띄우는 테스트 슬라이스(`@WebMvcTest`, `@DataJpaTest`)를 구분한다. DB와 Kafka는 Testcontainers로 실제 컨테이너를 띄워 H2 같은 대체 DB의 방언 차이를 피한다.
- 흔한 오답: 모든 테스트를 `@SpringBootTest`로 작성해 느리고 경계가 흐려진다.
- 꼬리: 테스트 이름과 대상(공개 동작과 결과로 검증하고, private 메서드는 공개 동작을 통해 검증한다).
- 내 연결: 멋사에서 통합과 단위 테스트 작성을 주도했고, NestJS에서는 Jest와 SuperTest로 같은 구분을 했다.

## J8. 고가용성과 Low Latency를 위한 구조 개선 (설계형)

- 의도: 라이브는 장애가 나면 되돌릴 시간이 없다는 공고 문장.
- 판단 기준: 사용자 영향 SLI(재생 시작 성공률, 시작 지연, 버퍼링), 의존성별 실패 방식, 복구 목표.
- 답변 골격:
  1. 재생 시작 경로의 의존성을 나열하고 각 의존성의 timeout, 재시도 예산, 실패 시 대체 동작을 정한다.
  2. 느린 의존성이 전체 스레드를 잡지 않도록 격리(bulkhead)하고, 반복 실패는 circuit breaker로 빠르게 끊는다.
  3. 핵심 경로에서 동기 호출 수를 줄이고, 로그 적재처럼 늦어도 되는 일은 비동기로 뺀다.
  4. p99 지연과 오류율을 경로별로 보고, 평균에 가려진 지역, 디바이스, 앱 버전 slice를 따로 본다.
  5. 멀티 리전은 active-active와 active-standby의 데이터 일관성, 비용, 전환 시간을 비교해 고른다.
- 트레이드오프: 재시도는 가용성을 높이지만 장애 시 부하를 증폭한다. 지터와 예산이 없으면 복구를 늦춘다.
- 꼬리: 권리 확인 서비스가 죽으면 재생을 허용하나(새 재생은 fail closed가 원칙이고, 이미 발급된 접근 정보의 만료 정책을 따른다. 실제 정책은 사업과 권리 계약이 정하므로 확인한다).
