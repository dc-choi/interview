# 티빙 1차, 서비스 맥락 질문

> [[Interview-Prep-Tving-1st|메인]]으로 돌아가기. 공고가 공개한 팀의 문제에서 뽑은 설계형 질문이다. 티빙의 실제 트래픽 규모, CDN 구성, 권리 계약과 로그 구조는 공개되지 않았으므로 답변에서는 가정을 먼저 말하고 확인 질문으로 닫는다. 화이트보드 설계는 요구 확인, 가정, 대안, 선택과 대가, 실패 대응, 검증 순서로 말한다.

## S1. 재생 요청의 CDN과 스트림 경로를 고르는 서비스를 설계해 보라

- 공개 근거: 재생 요청의 CDN, 스트림 경로 선택과 지역, 디바이스, 권리 조건에 따른 경로 분기, 멀티 리전 라우팅이 주요 업무다.
- 먼저 확인할 것: 라이브, VOD, 쇼츠, 뉴스별 응답 요구, 권리 조건의 종류, 품질 신호가 들어오는 주기, 결정의 단위(요청마다인지 세션마다인지).
- 답변 골격:
  1. 재생 시작 요청이 들어오면 권리, 지역, 디바이스 조건으로 허용 경로 후보를 먼저 거른다. 이 단계는 틀리면 안 되는 정합성 판단이므로 규칙과 버전을 명시적으로 관리한다.
  2. 남은 후보 중 품질 신호(오류율, 시작 지연, 가용성)와 비용, 가중치 정책으로 하나를 고른다. 이 단계는 최적화이므로 신호가 없거나 오래되면 기본 정책으로 떨어지게 한다.
  3. 결과로 재생 목록 위치와 서명된 접근 정보, 선택 이유를 담은 결정 ID를 돌려준다. 결정 ID는 시청 로그에 남겨 나중에 경로별 품질을 비교할 수 있게 한다.
  4. 경로 정책과 품질 신호는 요청마다 원격 조회하지 않고 메모리에 두고 주기적으로 갱신해 재생 시작 지연을 줄인다.
- 대안과 트레이드오프: 서버가 하나만 고르면 통제와 감사가 쉽지만, 재생 중 전환은 플레이어가 해야 한다. 후보 여러 개를 우선순위와 함께 내려주면 플레이어가 빠르게 전환할 수 있지만 클라이언트 동작을 버전별로 관리해야 한다. DNS나 CDN 앞단의 전환은 빠르지만 권리 같은 애플리케이션 조건을 반영하기 어렵다.
- 유사 경험과 한계: 여러 입력 조건을 확인한 뒤 상태를 판정하는 흐름과 정책 버전 관리 원칙은 가져올 수 있다. 미디어 라우팅 자체는 경험이 없다.
- 꼬리: 권리 조건 판정 결과는 캐시해도 되나(콘텐츠와 지역 단위의 공통 조건은 짧게 캐시하고, 권리 만료 시각을 TTL보다 우선한다).

## S2. CDN 장애나 품질 저하 때 경로를 어떻게 전환하나

- 공개 근거: CDN 장애나 품질 저하 시 경로를 전환하는 구조 설계가 주요 업무다.
- 답변 골격:
  1. 신호를 정한다. 합성 점검(주기적 요청), 플레이어가 보내는 실제 재생 오류와 버퍼링, CDN 제공 지표를 조합하고, 지역과 디바이스로 나눠 본다.
  2. 전환 기준에 히스테리시스를 둔다. 나빠졌다고 판단하는 기준과 회복했다고 판단하는 기준을 다르게 하고 최소 유지 시간을 둬 경로가 흔들리지 않게 한다.
  3. 전환은 단계적으로 한다. 신규 재생부터 비중을 옮기고, 이미 재생 중인 세션은 플레이어의 재시도와 대체 경로에 맡긴다.
  4. 대체 경로의 수용량을 미리 확인한다. 한 CDN의 트래픽을 한꺼번에 옮기면 대체 경로와 원본이 무너질 수 있다.
  5. 자동 전환과 수동 차단 스위치를 함께 두고, 모든 전환을 이벤트로 기록해 사후 분석한다.
- 트레이드오프: 민감하게 전환하면 오탐으로 멀쩡한 경로를 버리고, 둔하게 전환하면 사용자가 먼저 버퍼링을 겪는다.
- 유사 경험: Grafana Alerting으로 경보 기준을 정할 때 정상 구간을 관찰하고 사용자 영향에서 기준을 역산한 원칙.
- 꼬리: 플레이어 지표가 늦게 들어오면(합성 점검을 빠른 신호로, 실제 재생 지표를 확인 신호로 두 단계로 쓴다).

## S3. 라이브 시작 직전 요청이 한꺼번에 몰리면 무엇이 먼저 무너지고 어떻게 막나

- 공개 근거: 실시간성이 중요한 라이브 백엔드의 안정성과 확장성, 순간 트래픽 급증 대응.
- 답변 골격:
  1. 먼저 무너지는 곳을 가정하고 측정으로 확인한다. 재생 시작 API의 인증과 권리 확인, 공유 캐시 미스로 인한 원본 쏠림, DB 커넥션 풀, 외부 의존성 호출 한도가 후보다.
  2. 사전 준비: 편성으로 시작 시각을 알 수 있으므로 경로 정책, 콘텐츠 메타, 권리 판단 입력을 미리 적재하고, 오토스케일링은 반응형만 믿지 말고 예정된 증설을 둔다.
  3. 요청 경로: 공통 응답은 CDN과 공유 캐시로 흡수하고, 동일 키 요청은 병합하며, 원본 보호를 위해 동시 요청 수를 제한한다.
  4. 과부하 시: 핵심 경로(재생 시작)를 지키고 부가 기능(추천 영역, 비필수 로그 동기 전송)을 먼저 끄는 우선순위를 정해 둔다.
- 대안과 트레이드오프: 대기열로 도착을 평탄화하면 원본은 보호되지만 라이브 시작 경험이 늦어진다. 과증설은 안전하지만 비용이 든다.
- 유사 경험과 한계: 수천 대 IoT 하드웨어의 동시 요청 정합성, 트래픽 증가에 따른 인프라 전환. 소비자 라이브 규모의 급증은 경험이 없다고 말한다.
- 꼬리: 사전 부하 테스트는 무엇을 재현하나(시작 직전 몇 분의 도착 곡선, 캐시가 빈 상태, 의존성 하나가 느린 상태).

## S4. 시청 로그 이벤트를 어떤 기준으로 정의하나

- 공개 근거: 미디어 시청 로그 스키마와 이벤트 정의, 도메인 모델 설계. 무엇을 어떤 기준으로 남길지 정의하는 일.
- 답변 골격:
  1. 소비 목적부터 나눈다. 정산은 정확성과 감사 가능성, 지표는 일관된 정의, 추천은 빠른 반영이 중요하다. 목적이 다르면 같은 이벤트라도 필요한 보장이 다르다.
  2. 사실 이벤트를 남긴다. 재생 시작, 진행 heartbeat, 일시정지, 종료, 오류처럼 관측한 사실을 남기고, 시청 완료나 유효 시청 같은 해석은 하류에서 버전이 있는 규칙으로 계산한다. 해석을 원천 이벤트에 굳히면 기준이 바뀔 때 과거와 비교할 수 없다.
  3. 공통 필드를 고정한다. 이벤트 ID(중복 제거 키), 재생 세션 ID, 콘텐츠와 미디어 유형, 발생 시각과 수신 시각, 클라이언트와 앱 버전, 스키마 버전, S1의 경로 결정 ID.
  4. 라이브와 VOD의 차이를 모델에 반영한다. VOD는 콘텐츠 내 재생 위치가, 라이브는 방송 시각이 의미 있는 축이다.
- 대안과 트레이드오프: heartbeat 주기를 짧게 하면 시청 시간 정밀도는 오르지만 이벤트 양과 비용이 커진다.
- 유사 경험: 요청 식별자를 메트릭 라벨에 넣었다가 시계열 급증을 겪고, 식별자는 구조화 JSON 로그로 옮기고 집계 라벨과 분리한 설계.
- 꼬리: 클라이언트 시각은 믿을 수 있나(시계가 틀릴 수 있으므로 수신 시각을 함께 남기고, 순서 판단은 세션 안의 시퀀스 번호로 보강한다).

## S5. 시청 데이터의 정합성은 어떻게 검증하고 모니터링하나

- 공개 근거: 시청 데이터 정합성 검증과 품질 모니터링 체계 구축.
- 답변 골격:
  1. 수집 시점 검증: 스키마 위반, 필수 필드 누락, 허용 범위 밖 값은 격리 토픽으로 보내고 원본을 보존한다.
  2. 중복과 지연: 이벤트 ID로 중복을 제거하고, 늦게 도착한 이벤트를 받아 줄 기간과 이후의 정정 절차를 정한다.
  3. 대사: 서로 다른 경로의 수치를 맞춰 본다. 재생 시작 API 호출 수와 재생 시작 이벤트 수, 세션 시작과 종료 짝, 경로별 이벤트 비율을 비교한다.
  4. 품질 지표와 경보: 수신량, 누락 추정률, 스키마 위반률, 지연 도착 비율, 소비 지연을 지역, 디바이스, 앱 버전 slice로 보고, 급변을 경보한다. 앱 배포 뒤 특정 버전만 이벤트가 끊기는 문제는 평균에서 보이지 않는다.
- 트레이드오프: 수집 시점에 엄격하게 거르면 하류가 깨끗하지만 원천 이벤트를 잃을 수 있어, 거르되 버리지 않고 격리한다.
- 유사 경험: IoT 하드웨어의 배터리 부족과 통신 지연을 주기 집계해 자동 통보한 리포트, Grafana Alerting.
- 꼬리: 정산에 쓰는 수치가 틀린 것을 나중에 알면(원천 이벤트 보존과 규칙 버전 덕분에 재계산할 수 있어야 하고, 정정 이력을 남긴다).

## S6. 추천, 지표, 정산 팀과 데이터 계약을 어떻게 맺고 바꾸나

- 공개 근거: 시청 로그를 소비하는 팀과의 데이터 계약 설계, 우대사항의 스키마 버저닝.
- 답변 골격:
  1. 계약에 담을 것: 필드의 의미와 단위, 필수 여부, 허용 값, 중복과 지연 도착의 처리, 전달 보장 수준, 변경 절차와 담당자.
  2. 호환성 규칙: 선택 필드 추가처럼 기존 소비자를 깨지 않는 변경은 같은 버전에서 허용하고, 필드 의미 변경이나 삭제는 새 버전 이벤트나 새 토픽으로 병행 발행한 뒤 소비자 전환을 확인하고 구 버전을 내린다.
  3. 강제 수단: 스키마 레지스트리나 계약 테스트로 발행 전에 호환성을 검사한다.
  4. 의미 변경은 스키마 검사로 잡히지 않는다. 같은 필드명으로 계산 기준이 바뀌는 변경은 버전과 공지로 다룬다.
- 대안과 트레이드오프: 중앙에서 스키마를 강하게 통제하면 안정적이지만 변경이 느리고, 느슨하면 빠르지만 하류가 조용히 깨진다.
- 유사 경험과 한계: 프론트엔드와 OpenAPI로 요청, 응답, 실패 조건과 변경 이력을 합의한 경험. 이벤트 스키마 레지스트리 운영은 경험이 없다.
- 꼬리: 호환되지 않는 변경이 이미 배포됐다면(발행 쪽 롤백 또는 구 형식 병행 발행, 영향받은 기간의 재처리 범위를 소비 팀과 합의).

## S7. 라이브, 쇼츠, 뉴스 API는 VOD와 무엇이 다른가

- 공개 근거: 같은 재생이라도 요구되는 응답 특성과 트래픽 모양이 다르다는 공고 설명.
- 답변 골격:
  1. 라이브: 시작 시각에 요청이 몰리고, 재생 목록이 계속 바뀌며, 편성과 권리가 시간에 따라 바뀐다. 재생 시작 경로의 가용성과 사전 준비가 핵심이다.
  2. 쇼츠: 짧은 콘텐츠가 연속으로 이어져 재생 시작 횟수가 많다. 다음 콘텐츠의 재생 정보를 미리 받아 두는 구조와 시작 지연이 중요하다. 시청 이벤트 수도 많아진다.
  3. 뉴스: 편성과 시의성이 중요해 콘텐츠 공개와 교체가 빠르다. 캐시 무효화와 최신성의 균형이 핵심이다.
  4. 공통 모델과 분리: 권리 확인, 경로 결정, 로그 기록은 공통 흐름으로 두고, 미디어 유형별 차이는 정책과 응답 필드로 분기한다. 유형마다 API를 따로 만들면 초기엔 빠르지만 권리와 로그 기준이 갈라진다.
- 꼬리: 새 미디어 유형이 추가되면 무엇부터 정하나(권리 조건, 로그 이벤트의 의미, 트래픽 모양을 먼저 정의하고 공통 흐름에 붙일 수 있는지 판단한다).
- 한계: 쇼츠와 뉴스의 실제 요구는 공개되지 않았으므로 역질문으로 확인한다.
