# 티빙 1차, FIT 답변과 컬처핏 질문

> [[Interview-Prep-Tving-1st|메인]]으로 돌아가기. 마스터 답변을 fork하고 끝줄에 공고와 채용 사이트의 공개 맥락만 연결했다. 1차는 직무 면접이므로 각 답변은 60초 안쪽으로 줄여 두고, 꼬리 질문에서 근거를 보탠다.
>
> **현재 이직 사이클 확정**: [[My-Motivation-Reasons]]의 "현재 이직 사이클 (2026-09-29 사용자 확정)" 절을 fork했다. 퇴사 사유는 정본 문장을 그대로 쓰고 끝에 공고 연결 한 줄만 붙인다. 회사, 동료, 평가 과정은 사유로 쓰지 않는다. 직전 사이클(트라이포드랩에서 키노라이츠) 답변은 현재 사유로 옮기지 않는다.

## F1. 1분 자기소개 ([[My-Self-Intro]] fork)

- 질문 의도: 어떤 문제를 어떤 기준으로 푸는 사람인지, 이 팀과 왜 맞는지.
- 주의: 현재 소속은 첫 문장에 넣지 않는다. 연차를 말한다면 이력서 연월로 계산한 값만 쓴다. 키노라이츠는 이력서에 있고(2026.06~2026.09로 고칠 것), 물으면 F3 답변을 쓴다. 경력 흐름을 말할 때는 9월 중순에 마쳤다는 사실을 먼저 짧게 밝히고 F3 퇴사 답변으로 잇는다. 이미 제출한 이력서가 재직중으로 되어 있을 수 있기 때문이다.

> 안녕하세요, 백엔드 개발자 [이름]입니다. Node.js와 TypeScript로 서비스를 설계부터 운영까지 맡아 왔습니다.
>
> 트라이포드랩에서 NestJS 기반 재고 관리 서비스의 백엔드를 설계하고 운영했습니다. 수천 대 IoT 하드웨어가 동시에 보내는 요청은 DB 잠금과 짧은 트랜잭션으로 정합성을 지켰고, 수기 발주 흐름은 EventBridge와 SQS 기반 이벤트 처리로 자동화했습니다. 트래픽이 늘면서 단일 서버 구조를 CloudFront, ELB, ECS로 옮겼고, Grafana, Prometheus, Loki로 운영 신호와 경보를 직접 확인할 수 있게 했습니다. 첫 경력은 Java와 Spring 기반 공공 프로젝트였습니다.
>
> 저는 빠르게 만드는 것보다 실패해도 복구 가능한 구조를 중시합니다. 실패와 재시도, 관측을 처음 설계에 넣고, 기준이 없으면 계약과 검증 경로부터 세웁니다. Media API Platform은 재생 요청을 어디로 보낼지와 시청을 어떤 기준으로 남길지를 함께 책임지는 새 팀이라, 순간적인 요청 속에서 정합성을 지키고 이벤트 기준을 세워 본 경험으로 기여할 수 있다고 봤습니다.

## F2. 왜 티빙, 왜 Media API Platform인가

- 질문 의도: 공고를 읽고 자기 경험과 연결했는지. 중복 지원이 불가한 공고에서 이 팀을 고른 이유.
- 답변 축: 팀의 문제, 내 경험의 연결, 새 팀이라는 역할의 성격. 확인되지 않은 규모나 사업 상황은 말하지 않는다.

> 네 개 포지션 중 이 팀을 고른 이유는 제가 가장 깊게 다뤄 온 두 문제가 공고의 두 축과 같기 때문입니다. 하나는 순간적으로 몰리는 요청에서 상태를 정확히 판단하고 장애 시 안전하게 전환하는 문제이고, 다른 하나는 이벤트를 어떤 기준으로 남겨야 다음 처리와 지표가 흔들리지 않는지 정하는 문제입니다. 시청 로그 기준이 흔들리면 추천, 지표, 정산이 함께 흔들린다는 설명을 보고, 이 팀의 일이 제가 중시해 온 정합성과 복구 가능성의 문제라고 느꼈습니다. 또 새로 만들어지는 팀이라 기준을 처음 세우는 일에 참여할 수 있다는 점이 끌렸습니다.

**꼬리, 미디어 경험이 없는데**: 인정한다. 스트리밍 전달 구조는 개념과 판단 기준까지 준비했고, 입사 후에는 현재 재생 경로와 로그 흐름을 먼저 읽고 작은 변경으로 검증하겠다고 답한다.

**꼬리, 티빙을 써 봤나**: 면접 전에 직접 써 보고 관찰한 사실 한 문장만 말한다. [사용자 확정 필요: 실제 사용 경험]

## F3. 현재 회사 퇴사 사유, 직전 회사를 짧게 마친 이유

- 질문 의도: 같은 이유로 또 나갈 사람인지, 외부 귀책 성향인지, 이 자리와 이유가 연결되는지.
- 정본: [[My-Motivation-Reasons]] 현재 이직 사이클. 30초 안에 끝낸다.

> 올해 6월 말 합류해 검색과 데이터 수집을 맡았는데, 팀이 기대하는 일하는 방식과 제 방식의 차이를 수습 기간 안에 좁히지 못해 본채용으로 이어지지 않았습니다. 돌이켜 보면 완료 조건을 먼저 맞추지 않고 제 판단으로 진행했고, 검증 결과를 공유하는 것도 늦었습니다. 그 뒤로는 합류 초기에 기대하는 결과와 완료 기준부터 합의하고, 진행 상황을 근거와 함께 먼저 공유하는 것을 기본으로 삼고 있습니다.
>
> Media API Platform은 새로 만들어지는 팀이라, 합류 후 첫 기간에 기대하는 결과와 완료 조건이 무엇인지를 역질문으로 먼저 확인하고 시작하겠습니다.

**골격 규칙**: 답한 뒤 해명을 덧붙이지 않고 트라이포드랩에서 설계부터 운영까지 책임진 경험으로 넘어간다. 회사, 동료, 평가 과정의 문제를 사유로 말하지 않는다. 회사 내부 사정과 평가 세부는 답변과 이 저장소에 옮기지 않는다.

## F4. 짧은 재직과 잦은 이직

- 질문 의도: 장기 기여 가능성, 선택 기준이 성숙했는지.
- 키노라이츠는 F3 답변을 그대로 쓴다. 이썸테크는 [[My-Motivation-Reasons]] 1번 과거 사례를 쓴다.

> 이썸테크에서는 구현 경험은 쌓았지만 실제 트래픽과 장애 대응까지 맡아 보는 경험이 더 필요했고, 그래서 다음 선택부터는 언어보다 운영 책임이 있는 환경인지 확인했습니다. 이번에는 기대 결과와 완료 조건을 처음에 맞추지 못한 것이 원인이었고, 지금은 지원 전에 첫 90일의 범위와 완료 조건, 검토 구조를 확인합니다. 이 공고는 재생 경로와 시청 로그 기준이라는 두 문제가 구체적으로 적혀 있어 확인할 수 있었습니다.

**골격 규칙**: 기간을 반복해 변명하지 않고 사실만 짧게 인정한다. 얼마나 머물지 약속하는 말은 하지 않는다. 키노라이츠는 이력서에 기재돼 있으므로 기간을 묻는 질문에 이력서와 같은 연월(2026.06~2026.09)로 답한다.

## F5. 지금은 무엇을 하고 있나, 병행하는 활동이 있나

- 질문 의도: 현재 상태의 투명성, 겸업이 본업에 영향을 주는지.

> 9월 중순 퇴사한 뒤 지난 경험을 회고하고 다음 역할을 준비하고 있습니다. 그때 정리한 기준이 앞서 말씀드린 기대 결과와 완료 조건을 먼저 합의하는 것입니다.

**골격 규칙**: 개인 사업, 1인 대표, 창업 계획은 먼저 꺼내지 않는다. 겸업이나 사업 여부를 직접 묻는다면 사실대로 답한다. 계약, 매출, 고객 정보는 말하지 않는다.

## F6. 정해진 것이 없는 새 팀에서 어떻게 일하나

- 질문 의도: 공고의 빈 곳을 재미있어하는 사람인지. 기준을 세우고 합의하는 방식.
- fork: [[My-FIT-Answers]] 24번, 이력서의 모듈 중심 아키텍처와 팀 AI 협업 규약.

> 빈 곳에서는 먼저 무엇을 지금 정해야 하고 무엇을 나중에 정해도 되는지 나눕니다. 트라이포드랩에서는 요구사항이 자주 바뀌는 상황에서 도메인별 모듈 경계를 먼저 정해 변경을 흡수했고, 팀에서 맥락이 사람 머릿속에만 있던 문제는 도메인별 규칙과 검증 절차를 문서로 만들자고 제안했습니다. 처음에는 느려 보였지만 작은 영역에 먼저 적용해 검토와 인수인계가 쉬워지는 것을 보여 줬고, 다른 구성원도 같은 방식을 쓰게 됐습니다. 새 팀에서도 재생 경로의 입력과 시청 이벤트의 정의처럼 되돌리기 어려운 기준부터 문서로 합의하겠습니다.

**꼬리, 합의가 안 되면**: 반대가 방향, 부담, 정보 중 무엇인지 나누고, 리스크와 대안을 문서로 남긴 뒤 결정 권한이 있는 역할에 판단을 요청한다.

## F7. Kotlin과 Spring으로 전환할 수 있나, 새 기술을 어떻게 배우나

- 질문 의도: 필수요건 갭에 대한 태도, 학습 루틴의 구체성.
- fork: [[My-FIT-Answers-Extended]] 4번, [[My-Motivation-Reasons]] 1번의 이썸테크 사실.

> 최근 실무는 TypeScript와 NestJS라는 점을 먼저 말씀드립니다. 첫 경력에서 Java와 Spring으로 JSP와 JDBC 코드를 Spring MVC와 MyBatis로 옮겼고, 이후 Java 백엔드 과정과 Spring 코드 리뷰 멘토링을 하며 계속 다뤘습니다. NestJS의 DI, 모듈, 인터셉터 구조는 Spring의 Bean, 설정, AOP와 대응되는 부분이 많아 설계 판단은 그대로 옮길 수 있다고 봅니다. 새 기술은 공식 문서, 작은 예제, 기존 코드의 패턴 순서로 익히고, 제가 이해한 내용을 코드 리뷰에서 확인받습니다. Kotlin은 null 안전성과 코루틴처럼 Java와 다르게 동작하는 부분부터 작은 변경으로 검증하며 익히겠습니다.

**꼬리, 언제 제 몫을 하나**: 기간을 약속하지 않는다. 첫 과제의 범위와 리뷰 경로를 확인한 뒤, 기존 패턴을 따르는 작은 변경부터 배포하겠다고 답한다.

## F8. AI 도구는 어떻게 쓰나 ([[My-FIT-Answers]] 10번 fork)

- 질문 의도: 채용 사이트의 AI One team, 공고의 AI 도구 활용과 맞는지. 위임 범위와 검증 책임.

> 코드 생성뿐 아니라 개발 흐름을 재설계하는 데 AI를 씁니다. 트라이포드랩에서는 AI가 건드릴 영역과 건드리면 안 되는 영역을 규약으로 명문화하고, 작업 종료 시점에 AI가 스스로 품질을 검증하는 회귀 루프를 팀 레벨로 만들었습니다. 요구사항 해석, 설계 선택, 결과 채택은 제가 결정하고 책임집니다. 사람과 AI Agent가 함께 코드 리뷰를 한다는 티빙의 방식에서도 검증 기준을 먼저 세우는 역할을 하고 싶습니다.

**꼬리, AI가 틀리면**: 테스트, 공식 문서, 실행 결과로 검증한다. 익숙하지 않은 Kotlin 코드일수록 생성 결과를 그대로 채택하지 않는다.

## F9. 데이터를 소비하는 다른 팀과 어떻게 협업하나

- 질문 의도: 추천, 지표, 정산 팀과의 데이터 계약. 비개발 직군과의 소통.
- fork: [[My-FIT-Answers]] 3번, 2-A.

> 상대가 데이터로 무엇을 판단하는지부터 확인하고, 제가 이해한 내용을 다시 말해 맞춥니다. 그 다음 필드의 의미, 누락과 중복이 생길 때의 처리, 변경 절차를 계약으로 남깁니다. 프론트엔드와는 OpenAPI로 요청, 응답, 실패 조건을 명확히 했고, 일정과 위험이 충돌할 때는 사용자 영향과 사후 정정 비용을 정리해 범위를 나눠 검증하자고 제안한 경험이 있습니다. 시청 로그도 소비 팀이 같은 의미로 읽을 수 있어야 정산과 지표가 흔들리지 않는다고 봅니다.

## F10. 라이브 장애와 업무 강도 ([[My-FIT-Answers]] 11번, Extended 6번 fork)

- 질문 의도: 라이브는 되돌릴 시간이 없다는 공고 문장. 압박 속 우선순위 판단과 지속 가능성.

> 장애가 나면 사용자 직접 영향, 복구 가능성, 확산 가능성을 먼저 비교하고, 영향이 크면 즉시 필요한 역할에 알리며 현재 판단과 다음 확인 항목을 공유합니다. 의미 있는 문제라면 집중해서 해결할 수 있습니다. 다만 지속 가능하게 일하고 싶어서, 큰 이벤트 전 준비와 장애 후 회고, 회복을 팀이 어떻게 운영하는지 여쭤보고 싶습니다.

**핵심**: 과도한 헌신을 약속하지 않고, 강도를 부정적으로 단정하지 않는다. 역질문 7번으로 넘긴다.

## 마지막 한마디 ([[My-FIT-Answers]] 16번 fork)

> 오늘 재생 경로와 시청 로그라는 두 문제를 팀이 어떻게 보고 있는지 더 이해하게 됐습니다. 언어는 새로 익혀야 하지만, 정합성과 복구 가능성을 먼저 설계하는 방식으로 새 팀의 기준을 함께 세우는 동료가 되겠습니다.
