# 티빙 1차, JD와 회사 분석

> [[Interview-Prep-Tving-1st|메인]]으로 돌아가기. 회사 사실은 2026-09-29에 확인한 티빙 채용 사이트와 공고 원문, 잡코리아 공고에 적힌 내용만 쓴다. 공개 근거가 없는 사업 단계, 재무, 조직 규모, 고객, 트래픽과 내부 구현은 `미확인`으로 두고 확인 질문으로 남긴다.

## 1. 공개된 회사 개요

| 항목 | 확인한 내용 | 출처 |
| --- | --- | --- |
| 서비스와 도메인 | 채용 사이트는 티빙을 NO.1 K-CULTURE PLATFORM으로 소개한다. Technology 조직은 영상 스트리밍 기술을 바탕으로 여러 디바이스의 재생 기술, 대규모 스트리밍 플랫폼 성능 개선, 글로벌 확장 가능한 아키텍처를 만든다고 적는다. | 채용 사이트 |
| 미디어 범위 | 공고는 티빙에서 소비되는 미디어가 VOD만이 아니라 라이브, 쇼츠, 뉴스로 확장됐다고 설명한다. | 공고 |
| 개발 문화 | AI One team(AI Agent를 팀원으로 협업), 사람과 AI Agent 간 코드 리뷰, CI/CD와 테스트 자동화, 데이터 기반 의사결정(버그 현황, 테스트 커버리지, 사용자 로그), 유지보수성과 확장성을 고려한 리팩토링, AI 기반 테스트 생성 도구 활용을 소개한다. | 채용 사이트 |
| 근무 방식 | 플랫폼 개발 중심의 선릉 오피스와 콘텐츠 사업 중심의 상암 오피스가 온라인 중심으로 협업하고, 주 2회 재택 집중 근무를 권장한다고 적혀 있다. 근무지는 서울 강남구 선릉로 428이다. | 채용 사이트, 공고 |
| 업종과 규모 표기 | 잡코리아 기업 정보에는 영화, 비디오물 및 방송프로그램 배급업, 51~300명 규모로 표기돼 있다. 제3자 집계 표기이므로 면접에서 사실처럼 인용하지 않는다. | 잡코리아 |
| 사업 단계, 재무, 모회사 관계, 합병 등 사업 변화 | 미확인. 이번 확인 범위의 공식 출처에 없으므로 추정하지 않는다. | 없음 |
| 트래픽 규모, 사용 CDN, 클라우드 구성 | 미확인. 우대사항의 AWS, Kubernetes, CDN은 후보자 경험 요구이며 현재 운영 구성의 증거가 아니다. | 없음 |

## 2. 포지션 정보

| 항목 | 확인한 내용 |
| --- | --- |
| 팀 | Media API Platform. 사용자가 콘텐츠를 실제로 소비하는 구간을 담당하는 새 조직이며 첫 동료를 찾는다고 적혀 있다. |
| 팀이 맡는 두 문제 | 재생 요청을 어디로 보낼지 정하는 일, 그 소비를 어떤 기준으로 남기고 해석할지 정하는 일. 재생 경로를 잘못 고르면 사용자가 버퍼링으로 먼저 알아채고, 시청 로그의 기준이 흔들리면 추천, 지표, 정산이 함께 흔들린다고 설명한다. |
| 채용 절차 | 서류전형, 1차 면접, CJ Culture Fit Test 및 2차 면접, 최종합격. 서류 결과는 Working Day 기준 24시간 내 안내 예정. 합격 후 필요에 따라 동의를 받고 평판조회, 이후 처우협의, 채용검진, 입사일 협의. |
| 지원 조건 | 상세 경력기술서 필수, 협업 프로젝트는 본인 역할을 명확히 작성. 티빙 공고 간 중복 지원 불가. 접수는 채용 시 마감. 정규직. |
| 연차 기준 | 공식 FAQ는 절대적인 연차보다 역량을 우선 검증한다고 적는다. |

### 주요 업무 (공고 원문 요약)

1. Kotlin/Java와 Spring Boot 기반 백엔드 시스템 설계, 개발, 운영
2. 라이브, 쇼츠, 뉴스 등 미디어 도메인 API 설계, 개발, 운영
3. 재생 요청의 CDN과 스트림 경로 선택 로직 설계와 운영
4. 지역, 디바이스, 권리 조건에 따른 경로 분기와 멀티 리전 라우팅
5. CDN 장애나 품질 저하 시 경로를 전환하는 구조 설계
6. 실시간성이 중요한 라이브 백엔드 구조 개선과 확장성 확보
7. 미디어 시청 로그 스키마와 이벤트 정의, 도메인 모델 설계
8. 시청 데이터 정합성 검증과 품질 모니터링 체계 구축
9. 시청 로그를 소비하는 팀(추천, 지표, 정산 등)과의 데이터 계약 설계
10. 순간적인 트래픽 급증에 대응하는 캐시와 전달 구조 설계
11. Kafka와 MQ 기반 비동기 이벤트 처리 시스템 설계
12. 고가용성과 Low Latency를 고려한 구조 개선
13. AI 도구를 활용한 개발 생산성 향상

## 3. 핵심 키워드

- 재생 경로 라우팅, CDN 전환, 멀티 리전, 권리 조건
- 라이브의 실시간성, 순간 트래픽 급증, 캐시와 전달 구조
- 시청 로그 스키마, 이벤트 정의, 데이터 계약, 정합성 검증, 품질 모니터링
- Kafka 비동기 처리, 고가용성, Low Latency
- 새 팀, 정할 것이 많은 환경, AI One team

## 6. 기술 스택 비교

| 공고 스택 | 내 경험 | 판단 |
| --- | --- | --- |
| Kotlin | 없음 | 보강 필요 |
| Java | 이썸테크 실무, 교육 과정 | 유사, 최근 공백 |
| Spring Boot | Spring MVC 실무, Spring Boot는 교육과 멘토링 범위 | 유사 |
| Node.js, NestJS (내 주력) | 트라이포드랩 설계와 운영 | 구조 개념은 전이. DI, 모듈, 인터셉터와 Spring의 Bean, AOP 대응 |
| RDB | MySQL, MariaDB 설계와 튜닝 | 동일 |
| Kafka, MQ | SQS, EventBridge, SNS | 유사. 파티션과 오프셋 모델은 보강 |
| 캐시 | Redis, CloudFront | 유사 |
| CDN, HLS, DASH | CloudFront만 | 보강 필요 |
| AWS | 다수 서비스 운영 | 동일 |
| Kubernetes | 없음, ECS Fargate | 유사 개념, 보강 필요 |

> 우대 기술 목록은 티빙의 현재 운영 스택을 증명하지 않는다. Kotlin과 Java의 비중, Kafka 외 MQ, 클라우드와 Kubernetes 사용 범위는 면접에서 확인한다.
