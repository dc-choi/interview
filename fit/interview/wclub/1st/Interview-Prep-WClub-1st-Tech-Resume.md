# 더블유클럽 1차, 이력서 기반 기술 질문

> 상위 문서: [[Interview-Prep-WClub-1st|더블유클럽 1차 준비]]. [[My-Tech-Cards]]를 fork했다. 수치는 이력서에 공개된 값만 쓰고, 말할 때는 측정 기준(전후 비교 대상, 환경)을 함께 설명할 수 있을 때만 꺼낸다. 내부 운영 수치와 경보 임계값은 말하지 않는다.

### R1. 동시 요청의 재고 정합성을 어떻게 지켰나 (경험형)

- 의도: 동시성 문제를 재현하고 잠금 전략의 비용을 아는가
- 핵심 답변: 같은 재고 행을 동시에 바꾸는 경로에서 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한 재시도를 조합했다. 충돌이 잦아 낙관적 잠금은 뒤늦은 전체 재실행 비용이 컸다. 외부 호출과 독립 검증은 트랜잭션 밖으로 빼고, 잠금 읽기 뒤 불변식을 다시 검증했다. 여러 대상을 갱신할 때는 업무 키 순서를 통일했다.
- 검증: 동시 요청을 재현해 최종 수량, 잠금 실패, 재시도 뒤 상태를 확인했다.
- 한계: NOWAIT는 해당 잠금 읽기의 대기만 없앤다. 잠금 순서는 데드락 확률을 낮출 뿐 완전 예방이 아니다. 당시 고정 간격 재시도였고 지금이라면 지수 백오프와 지터를 검증한다.
- 꼬리: 멀티 인스턴스에서도 DB 잠금이면 충분한가 → 같은 DB 트랜잭션 안의 자원이면 충분하다. 여러 저장소를 한 임계 구역으로 묶어야 할 때만 분산 잠금을 검토한다.
- 회사 연결: 만남권 차감이나 매칭 수락처럼 같은 자원을 두 요청이 동시에 바꿀 수 있는 경로에 같은 판단을 적용한다.

### R2. EventBridge와 SQS로 발주를 자동화한 구조 (경험형)

- 의도: 비동기 분리의 실패 경로를 설계했는가
- 핵심 답변: 핵심 상태 변경을 먼저 확정하고 후속 처리를 이벤트로 넘겼다. 조직 상황상 Kafka 도입보다 관리형 큐가 운영 부담에 맞았다. 소비자는 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 영구 오류는 격리, 일시 오류만 제한 재시도, 초과분은 DLQ와 수동 확인으로 보냈다.
- 한계: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 실패 시 누락 가능성이 남았고, 지금이라면 상태 변경과 outbox 행을 같은 트랜잭션에 저장한다.
- 꼬리: 정확히 한 번 처리가 가능한가 → 전달은 적어도 한 번이고, 업무 키 중복 제거와 상태 전이 가드로 결과를 한 번으로 만든다.
- 회사 연결: 결제 완료 뒤 알림, 매칭 제안 같은 후속 작업을 결제 성공 경로와 분리할 때 같은 원칙을 쓴다.

### R3. 슬로우 쿼리 99.3% 개선 (경험형, 이력서 수치)

- 의도: 수치의 기준과 인덱스 판단 근거를 설명하는가
- 핵심 답변: 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용을 `EXPLAIN ANALYZE`로 확인했다. 동등 조건 업무 키, 최신 시각 내림차순, 보조 키 순서의 복합 인덱스를 설계하고 실행 계획으로 재확인했다.
- 수치 경계: 99.3%는 어떤 쿼리의 전후 비교인지, 같은 환경과 캐시 조건이었는지를 먼저 말한다. 조건을 설명할 수 없으면 수치 대신 원인과 검증 방법을 말한다.
- 트레이드오프: 복합 인덱스는 쓰기와 저장 비용을 늘린다. 인접 쓰기 경로를 함께 본다.
- 꼬리: 컬럼 순서 기준 → 카디널리티 하나가 아니라 동등 조건, 범위 조건, 정렬, 필요한 반환 컬럼으로 정한다.

### R4. Prisma 조회를 단일 쿼리로 바꿔 응답 90% 향상 (경험형, 이력서 수치)

- 의도: ORM이 만드는 SQL을 직접 확인하는가
- 핵심 답변: 관계 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 확인했다. `relationJoins` 기능과 `relationLoadStrategy: 'join'`을 적용하고, MySQL에서 상관 서브쿼리와 JSON 집계 형태의 단일 쿼리가 생성되는지 실행 계획으로 확인했다.
- 흔한 오답: 옵션 이름만 보고 SQL JOIN이 나간다고 단정하는 것. 생성 SQL은 DB와 버전에 따라 다르다.
- 한계: 호출 수는 줄지만 결과 중복과 집계 비용이 DB로 옮겨 간다. 성능 민감 경로만 바꿨다.
- 꼬리: AI가 만든 ORM 코드를 리뷰할 때도 생성 SQL과 쿼리 수를 확인한다.
- 출처: [Prisma 관계 조회 공식 문서](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries)

### R5. Grafana, Prometheus, Loki 관측 체계와 경보 (경험형)

- 의도: 장애를 어떻게 먼저 발견하고 좁히는가
- 핵심 답변: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증하는 문제를 겪었다. 식별자를 구조화 JSON 로그 본문으로 옮기고, 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼다. 메트릭으로 추세와 영향을, 로그로 개별 원인을 본다.
- 흔한 오답: 사용자 ID나 요청 ID를 메트릭 라벨에 넣는 설계. 직접 겪은 실수라서 라벨 설계 기준을 먼저 말한다.
- 경보 원칙: 과거 숫자를 복사하지 않고 사용자 영향 SLI와 정상 구간을 관찰해 정한다. API는 RED, DB와 큐는 USE 관점으로 본다.
- 꼬리: 장애가 나면 → 영향 범위와 현재 대응 공유, 복구 우선, 이후 타임라인, 원인, 재발 방지를 포스트모템으로 남긴다.
- 회사 연결: AI 결과물을 자주 배포하는 환경일수록 배포 이벤트와 오류율, 지연을 함께 보는 판정 신호가 필요하다.

### R6. 단일 NGINX에서 CloudFront, ELB, ECS로 전환하고 이미지 43.6% 축소 (경험형, 이력서 수치)

- 의도: 배포 구조와 롤백 경로를 이해하는가
- 핵심 답변: Docker 멀티스테이지로 빌드 산출물만 실행 이미지에 넣어 이미지 909MB에서 513MB, 배포 시간 3분 10초에서 2분 20초로 줄였다(이력서 공개 수치). 트래픽 증가에 맞춰 관리형 컨테이너로 옮기고 Read Replica로 읽기를 분산했다.
- 판단: 쓰기와 쓰기 직후 읽기는 primary로, 지연을 허용하는 조회만 replica로 보낸다. Rolling은 자원 부담이 낮고, 즉시 전환과 빠른 롤백이 중요하면 Blue/Green을 비교한다.
- 꼬리: 종료 신호를 받으면 새 요청을 막고 진행 중 요청을 정리한다. 워커는 현재 메시지의 완료 또는 재전달 경계를 명확히 한다.

### R7. WebAuthn 명세를 분석해 FIDO 서버를 설계한 과정 (사실형과 경험형)

- 의도: 인증 프로토콜을 명세 수준으로 이해하는가
- 핵심 답변: 등록 시 서버가 challenge를 발급하고, 인증기가 키 쌍을 만들어 공개키와 attestation을 돌려주면 서버가 origin, challenge, 서명을 검증해 공개키를 저장한다. 인증 시에는 새 challenge에 대한 서명을 저장된 공개키로 검증하고 서명 카운터로 복제 의심을 본다. 비밀번호 대신 origin에 묶인 키를 써서 피싱 저항성이 생긴다.
- 경험: 사용한 오픈소스 동작이 명세와 다를 수 있다는 의견이 나왔을 때 명세와 재현 결과를 대조해 공개 이슈로 제기하고 팀과 안전한 방식을 골랐다.
- 흔한 오답: 생체 정보가 서버로 전송된다고 말하는 것. 생체 인증은 기기 안에서 끝나고 서버는 서명만 검증한다.
- 꼬리: challenge 재사용을 막는 방법 → 1회용, 짧은 만료, 세션 바인딩.
- 출처: [W3C, Web Authentication Level 2](https://www.w3.org/TR/webauthn-2/)

### R8. 팀 AI 협업 규약과 자기 검증 회귀 루프 (경험형)

- 의도: JD 첫 자격 요건의 실제 깊이
- 핵심 답변: AI가 건드릴 영역과 건드리면 안 되는 영역을 규칙 파일로 명문화하고, 작업 종료 시점에 AI가 테스트와 점검을 스스로 돌려 품질을 확인하는 루프를 만들었다(이력서). 규칙은 잊힐 수 있는 요청 층과, 어겨도 걸리는 강제 층(훅, 권한, CI)으로 나눈다.
- 구체 사례: 어떤 결함을 이 루프가 잡았는지, 어떤 규칙을 강제 층으로 내렸는지 [사용자 확정 필요]. 비공개 저장소의 세부는 말하지 않고 원리와 결과만 말한다.
- 꼬리: 만드는 쪽과 검사하는 쪽을 왜 분리하나 → 같은 문맥의 자기 검토는 자기 확인으로 끝나기 쉽다.

### R9. MongoDB에서 MySQL로 데이터를 옮긴 마이그레이션 (경험형)

- 의도: 스키마 전환과 데이터 검증 경험
- 핵심 답변: 영양정보 데이터의 정형화가 필요해 문서 모델에서 관계형 스키마로 옮겼다(이력서). 스키마 설계, 변환, 건수와 샘플 대조 검증 순서로 진행한다.
- 세부: 당시 변환 방식, 중단 시간 여부, 검증 기준은 [사용자 확정 필요]. 기억이 불확실하면 지금이라면 어떻게 하는지로 답한다.
- 지금이라면: 이중 쓰기보다 변경 추적과 백필, 읽기 경로 전환, 대조 검증, 구 저장소 제거 순서로 되돌릴 지점을 둔다.
- 회사 연결: 7년 운영된 스키마에 AI가 만든 마이그레이션을 올릴 때 같은 되돌림 경계가 필요하다.

### R10. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- 의도: AI 도구를 단순 사용을 넘어 직접 만들고 품질을 수치로 비교해 본 경험이 있는가
- 핵심 답변: 개인 프로젝트로, 개발 지식 Markdown을 근거 관계 그래프로 색인하고 그 검색을 MCP 도구와 CLI로 제공하는 시스템을 만들었습니다. Markdown 위키링크와 frontmatter의 근거 관계로 그래프를 구성하고, Git blob 스냅샷과 SHA-256 해시 게이트로 같은 입력이면 같은 색인이 나오게 했습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했습니다. 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정하고, 응답 크기 예산 안에 그 근거가 모두 나와야 통과로 쳤습니다. 무관한 질문에는 빈 결과가 나와야 통과하는 음성 질문도 넣었습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, BM25와 E5 임베딩 결과를 RRF로 합친 방식을 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 늘지 않았고 기존 통과 사례 4개를 잃었습니다. 이 74개를 포함한 94개 질문으로 bge 리랭커도 붙여 봤지만 통과는 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸습니다. 그래서 BM25, 임베딩, 리랭커 모두 채택하지 않았고, 문제가 후보 검색보다 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- 판단 기준: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 비용과 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다.
- 케이스 선정과 지표: 평가 질문은 대부분 원문을 보고 만든 합성 질문이다. 양성은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나와야 통과, 음성은 빈 결과여야 통과다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 쟀다.
- 한계를 먼저 말할 것: 평가 질문은 사람이 정답을 검수한 표본이 아니라 합성 질문이 대부분이다. 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정이다.
- 이력서 정정: 제출한 이력서에는 골든 케이스 약 145건으로 비교했다고 적혀 있다. 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- 꼬리: 골든 케이스는 어떻게 만들었나 → 위 케이스 선정과 지표 줄대로 답한다. 골든이라 부를 만큼 사람이 검수한 세트는 아니라고 먼저 인정한다.
