# 더블유클럽 1차, JD 기반 기술 질문

> 상위 문서: [[Interview-Prep-WClub-1st|더블유클럽 1차 준비]]. 회사의 실제 구현은 미확인이므로 모든 답변은 일반 설계 원칙과 내 경험의 연결로만 말한다.

### J1. AI가 만든 PR을 리뷰할 때 무엇부터 보나 (설계형)

- 의도: 공고의 핵심 자격 요건. 결함을 찾는 순서와 기준이 있는가
- 답변 골격: 변경의 의도와 요구사항을 먼저 확인하고, 실패 비용이 큰 순서로 본다.
  1. 인가: 요청의 식별자로 자원을 찾을 때 요청자가 소유자나 권한자인지 서버가 확인하는가. 인증 통과만 보고 끝나는 코드가 가장 흔한 결함이다.
  2. 데이터 경계: 트랜잭션 범위, 동시 갱신, 멱등성, 파괴적 마이그레이션 여부
  3. 입력과 출력: 서버에서 금액과 수량을 재계산하는가, 응답에 필요 이상의 개인정보가 실리는가
  4. 비밀과 설정: 키 하드코딩, 로그에 민감 정보 출력, 환경별 설정 혼입
  5. 테스트의 진위: 테스트가 구현을 그대로 따라 써서 결함까지 통과시키는지, 실패 경로 테스트가 있는지
  6. 존재하지 않는 API나 버전과 맞지 않는 라이브러리 사용, 불필요한 추상화
- 트레이드오프: 모든 PR을 같은 깊이로 보면 속도가 죽는다. 민감 경로(결제, 인증, 서류, 권한)만 강제 검수 대상으로 두고 나머지는 자동 게이트에 맡긴다.
- 꼬리: 리뷰로 놓친 결함은 어떻게 줄이나 → 같은 실수가 두 번 나오면 문장 규칙에서 린트, 훅, CI 게이트로 내린다.

### J2. Claude Code와 Codex 작업 규칙과 리뷰 기준을 어떻게 운영하나 (설계형)

- 의도: 규칙을 문서가 아니라 운영 체계로 만드는가
- 답변 골격: 두 도구가 같은 정본 규칙을 읽게 한다(루트와 경로별 규칙 파일, 한쪽이 다른 쪽을 import). 상시 규칙에는 빌드와 테스트 명령, 완료 정의, 건드리면 안 되는 경로만 두고, 긴 지식은 필요할 때 로드한다. 어기면 곤란한 규칙은 권한 deny, 차단 훅, CI 게이트로 강제한다.
- 판단 기준: 어기면 아쉬운가 곤란한가. 아쉬우면 요청 층, 곤란하면 강제 층.
- 대안: 게이트를 많이 걸수록 오탐과 승인 피로가 늘어 승인이 형식화된다. 위험한 것만 사람에게 올리고 허용 구역은 명시적으로 넓힌다.
- 꼬리: 만드는 에이전트와 검사하는 에이전트를 분리하는 이유 → 자기 코드의 자기 검토는 확인 편향이 크다.

### J3. 결제 연동을 설계한다면 (설계형)

- 의도: 돈이 걸린 경로의 정합성과 보안
- 답변 골격:
  - 금액과 상품은 서버에서 재계산하고 클라이언트 값을 믿지 않는다. 금액은 원 단위 정수로 저장한다.
  - 주문 생성 시 업무 키로 결제 시도를 만들고 unique 제약과 멱등성 키로 중복 결제를 막는다.
  - 상태 머신: 대기, 승인, 실패, 취소, 환불 요청, 환불 완료. 전이는 명시적 API로만 허용하고 행 잠금이나 조건부 갱신으로 동시 전이를 막는다.
  - PG 웹훅은 서명과 시각을 검증하고 같은 이벤트의 반복 수신을 멱등하게 처리한다.
  - 동기 응답과 웹훅이 놓친 건은 주기적 대사로 수렴시킨다. 차이는 즉시 취소하지 않고 유예 뒤 재조회한다.
- 트레이드오프: 결제 확정을 동기로 기다리면 사용자 경험은 단순하지만 타임아웃 시 결과가 불명확하다. 타임아웃은 실패 확정이 아니므로 새 키로 재시도하지 않고 같은 키 재시도나 상태 조회로 확인한다.
- 내 경험 연결: 환불 정책 변경에서 실패와 환불 경로를 출시 전에 먼저 닫자고 설득한 사례. PG 연동을 직접 구현한 깊이는 [사용자 확정 필요]이며 부풀리지 않는다.
- 꼬리: 외부 결제 API가 멱등성 키를 지원하지 않으면 → 요청 전 내부에 시도 기록을 커밋하고, 불명확한 결과는 거래 조회와 대사로 닫는다.

### J4. 인증과 인가를 어떻게 나누고 구현하나 (사실형과 설계형)

- 의도: 인증과 자원 단위 인가를 구분하는가
- 핵심 답변: 인증은 누구인지, 인가는 이 자원에 이 행위를 해도 되는지다. NestJS에서는 Guard가 인증과 역할 검사를 맡고, 자원 소유권은 서비스 계층에서 토큰의 사용자 ID로 조회 조건을 걸어 확인한다.
- 설계 선택: 모바일 앱은 짧은 액세스 토큰과 회전하는 리프레시 토큰, 관리자 웹은 세션이나 짧은 토큰과 추가 인증을 검토한다. 리프레시 토큰 재사용이 감지되면 해당 계열을 모두 폐기한다.
- 흔한 오답: UUID로 바꾸면 IDOR가 해결된다는 답. 추측을 어렵게 할 뿐 서버 인가가 근본 방어다.
- 꼬리: 관리자 권한 → 역할과 행위 단위로 쪼개고 민감 데이터 조회 자체를 감사 로그로 남긴다.
- 출처: [OWASP API Security Top 10, API1 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)

### J5. 신분증과 소득 서류 같은 인증 자료를 어떻게 다루나 (설계형)

- 의도: 회복 불가능한 개인정보의 수명 주기를 설계하는가
- 답변 골격:
  1. 수집 최소화: 검증에 필요한 항목만 받는다. 가장 강한 통제는 애초에 보관하지 않는 것이다.
  2. 업로드: 비공개 버킷에 짧은 만료의 서명 URL로 직접 올리고, 서버는 파일 형식과 크기를 검증한다.
  3. 저장: 서버 측 암호화, 원본과 검증 결과의 분리. 검증 뒤에는 결과(승인 여부, 검증 시각, 검수자)만 남기고 원본은 정해진 기간 뒤 자동 삭제한다.
  4. 접근: 검수 역할만 조회 가능, 조회 URL은 짧은 만료, 모든 열람을 감사 로그로 기록한다. 감사 로그는 애플리케이션 계정이 수정하거나 지우지 못하게 권한을 분리한다.
  5. 로그와 분석: 운영 로그와 학습이나 분석 경로로 원본이 흘러가지 않게 마스킹과 경계를 둔다.
- 트레이드오프: 원본을 오래 두면 분쟁 대응이 쉽지만 유출 시 피해가 영구적이다. 보관 기간은 법적 의무와 분쟁 대응 필요에서 역산한다.
- 한계: 이 영역의 실무 경험은 없다. 원칙과 설계로 답하고 현재 방식은 역질문으로 확인한다.
- 꼬리: 외부 인증 벤더를 쓴다면 → 데이터가 거치는 하위 처리자, 보관과 삭제 조건을 계약과 점검으로 확인한다.

### J6. 운영 중인 테이블의 스키마를 바꾸는 순서 (설계형)

- 의도: 무중단 변경과 되돌림 경계
- 답변 골격: 호환 컬럼 추가, 새 코드가 양쪽을 읽고 쓰기, 배치 백필과 대조 검증, 읽기 경로 전환, 구 컬럼 제거의 expand-contract 순서다. MySQL이라면 변경 종류별로 INSTANT, INPLACE 가능 여부를 대상 버전 문서로 확인하고 알고리즘을 명시해 무거운 방식으로 조용히 넘어가지 않게 한다. 장기 트랜잭션이 메타데이터 잠금을 쥐면 뒤 쿼리가 막히므로 실행 전에 확인한다.
- 회사 맥락: 모바일 앱은 구버전이 오래 남으므로 서버 스키마와 API는 구버전 클라이언트를 한동안 함께 지원해야 한다.
- 꼬리: 마이그레이션과 앱 배포를 한 번에 묶으면 → 코드 롤백으로 스키마가 돌아가지 않아 롤백 불가능한 배포가 된다.

### J7. 배포, 롤백, 장애 대응을 어떻게 설계하나 (설계형)

- 의도: 되돌릴 수 있는 것과 없는 것을 구분하는가
- 답변 골격: 코드, 이미지, 설정은 되돌아가지만 적용된 스키마, 발송된 메시지, 결제 승인 같은 외부 부수효과는 되돌아가지 않는다. 그래서 되돌림은 설계 시점에 정한다. 비용 순서는 기능 플래그 끄기, 트래픽 전환, 이전 이미지 재배포, 데이터 복구다. 롤백 대상은 변경될 수 있는 태그보다 이미지 digest로 고정한다.
- 판단 기준: 원인이 불명확하고 피해가 진행 중이면 롤백이 기본값이다. 스키마나 외부 부수효과가 이미 앞으로 갔다면 롤포워드가 유일한 경로일 수 있다.
- 완료 조건: 이전 버전이 떴다는 것이 아니라 오류율과 지연이 평시로 돌아온 것.
- 모바일 앱: 스토어에 배포된 앱은 즉시 되돌릴 수 없다. 서버 하위 호환, 원격 기능 플래그, 최소 지원 버전과 강제 업데이트로 대응한다.

### J8. React Native와 Next.js 경험이 없는데 괜찮은가 (경험형, 갭)

- 답변 골격: 실무 경험이 없다는 사실을 먼저 인정한다. 이 역할에서 두 영역이 백엔드와 맞닿는 지점(API 계약, 인증 토큰 저장과 갱신, 앱 구버전 호환, 관리자 화면의 권한)은 백엔드 관점에서 이미 다뤄 온 문제라고 연결한다. 입사 후에는 기존 앱의 릴리스 절차와 스토어 심사 흐름부터 따라가 보고, AI가 만든 프론트 코드는 API 호출과 인가 경계부터 검수하겠다고 말한다.
- 금지: 써 본 것처럼 말하지 않는다.

### J9. NestJS 요청 파이프라인에서 각 구성 요소의 책임 (사실형)

- 핵심 답변: middleware는 요청 전처리, guard는 인증과 인가 판단, interceptor는 요청과 응답 전후 처리와 변환, pipe는 입력 변환과 검증, exception filter는 예외를 응답으로 변환한다. 실행 순서는 middleware, guard, interceptor(전), pipe, 핸들러, interceptor(후), 그리고 예외 시 filter다.
- 흔한 오답: 인가를 interceptor에 두는 것. 거부는 핸들러 진입 전 guard에서 끝내는 것이 맞다.
- 꼬리: provider 스코프 → 대부분 singleton, 요청별 맥락이 꼭 필요할 때만 request 스코프를 쓰며 성능 비용이 있다.
- 출처: [NestJS 공식 문서, Request lifecycle](https://docs.nestjs.com/faq/request-lifecycle)
