# 문토 1차 JD 기반 기술 질문 (8문항)

> [[Interview-Prep-Munto-1st|목차로]]. 공고의 주요 업무와 기술 스택에서 뽑았다. 문토의 실제 구현은 공개 자료로 확인되지 않았으므로 답변은 일반 설계 판단과 내 경험으로 말하고, 현재 구조는 역질문으로 확인한다.

## J1. 신사업 첫 제품의 기술과 서비스 구조를 어떻게 정하겠나

- **유형과 의도**: 설계형. 출시 속도, 운영 비용, 유지보수를 함께 판단하는지 본다.
- **판단 기준**: 검증할 가설과 실패해도 되는 범위, 팀 인원과 운영 여력, 되돌리기 쉬운 결정인지, 기존 문토 플랫폼과 공유해야 하는 자산(계정, 결제, 데이터).
- **답변 골격**: 팀이 가장 빨리 움직이는 기존 스택(TypeScript, NestJS, Prisma, PostgreSQL)으로 하나의 서비스에 도메인별 모듈 경계를 둔 모놀리스로 시작한다. 인프라는 관리형 서비스를 우선해 운영 부담을 줄이고, 결제와 개인정보처럼 되돌리기 어려운 경계만 처음부터 단단하게 만든다. 나머지는 기능 플래그와 작은 배포로 빠르게 바꾼다. 가설이 검증되고 병목이 측정되면 그때 분리하거나 확장한다.
- **대안과 트레이드오프**: 서버리스 함수는 유휴 비용이 낮고 운영이 가볍지만 도메인 로직 재사용, DB 연결 수 관리, 로컬 재현이 어렵다. 컨테이너는 기존 코드와 배포 경로를 재사용하지만 상시 실행 비용이 있다. 처음부터 서비스를 쪼개면 검증 속도보다 분산 시스템 비용이 먼저 온다.
- **내 경험**: 트라이포드랩에서 요구사항이 자주 바뀌는 PoC 단계에 도메인별 모듈을 분리해 변경을 흡수했고, 트래픽이 늘자 단일 서버에서 관리형 컨테이너 구조로 단계적으로 옮겼다.
- **꼬리**: 무엇을 만들지 않겠나. 가설 검증에 필요 없는 관리자 화면이나 자동화는 수동 운영으로 대체하고, 반복이 확인되면 만든다.

## J2. PostgreSQL을 쓰는데 MySQL과 무엇이 다른가

- **유형과 의도**: 사실형. 주력 DB와의 차이를 운영 관점으로 아는지 본다.
- **핵심 답변**: 기본 격리 수준이 InnoDB는 REPEATABLE READ, PostgreSQL은 READ COMMITTED다. MVCC 구현이 다르다. InnoDB는 이전 버전을 undo log에 두고, PostgreSQL은 갱신마다 새 튜플을 만들고 옛 튜플을 dead tuple로 남겨 VACUUM이 회수한다. PostgreSQL은 연결마다 프로세스를 띄워 연결 비용이 커서 커넥션 풀러를 함께 검토한다. 부분 인덱스, JSONB와 GIN 인덱스, `CREATE INDEX CONCURRENTLY`, `ON CONFLICT` 같은 기능이 있다.
- **흔한 오답**: PostgreSQL이 항상 빠르다는 답. 단순 OLTP는 비슷하거나 MySQL이 빠를 수 있다. autovacuum이 있으니 신경 쓸 필요 없다는 답. 갱신이 많은 테이블은 bloat를 관찰해야 한다.
- **꼬리**: 격리 수준 차이로 같은 코드가 다르게 동작할 수 있는 지점은 무엇인가. 읽고 판단한 뒤 쓰는 로직은 격리 수준에 기대지 말고 `FOR UPDATE`나 조건부 갱신, 유니크 제약으로 명시한다.
- **학습 정본**: [[MySQL-vs-PostgreSQL]], [[PostgreSQL-Production-Operations]]

## J3. 고객 결제의 보안과 안정성을 어떻게 관리하겠나

- **유형과 의도**: 설계형. 돈이 걸린 경로의 정합성과 공격 대비를 본다.
- **답변 골격**: 금액, 상품, 수량은 클라이언트 값을 믿지 않고 서버에서 다시 계산한다. 결제 요청에는 안정적인 멱등성 키를 두고 DB 유니크 제약으로 중복을 막는다. 결제 상태는 대기, 승인, 취소, 환불 같은 상태 머신으로 두고 전이는 잠금이나 조건부 갱신으로 보호한다. 결제 대행사 콜백은 서명과 타임스탬프를 검증하고, 대행사 스펙은 그대로 따른다. 승인 결과가 불명확한 건은 조회 API와 주기적 대사로 닫는다. 금액은 정수로 저장한다.
- **대안과 트레이드오프**: 결제를 직접 구현하기보다 검증된 통합 결제 서비스로 시작해 범위를 줄이는 것이 초기 팀에 안전하다. 동기 승인은 결과가 즉시 명확하지만 외부 지연이 사용자 흐름을 막고, 비동기 확정은 상태 추적과 대사 비용이 든다.
- **내 경험과 한계**: 동시 갱신 정합성, 멱등 소비자, DLQ와 수동 확인 경로는 직접 설계했다. 환불 정책 변경에서 보호 조건을 먼저 두고 구독 결제를 출시한 사례가 있다. [결제 연동 직접 구현 범위: 사용자 확인 필요]
- **꼬리**: 결제는 승인됐는데 참가 확정 저장이 실패하면. 결제를 정본으로 두고 확정을 재시도하거나, 정해진 시간 안에 확정되지 않으면 자동 취소하는 보상 흐름을 둔다.
- **학습 정본**: [[Payment-System-Principles]], [[Idempotency-Key]]

## J4. 배포와 오류 모니터링 환경을 처음부터 만든다면

- **유형과 의도**: 설계형. 작은 팀에 맞는 최소 운영 체계를 고르는지 본다.
- **답변 골격**: GitHub Actions에서 테스트와 이미지 빌드, 컨테이너 레지스트리 푸시, ECS 배포까지 한 흐름으로 만들고 이전 버전으로 되돌리는 절차를 먼저 검증한다. 애플리케이션은 요청 식별자를 담은 구조화 로그와 오류 추적 도구로 예외를 모으고, 사용자 영향과 연결되는 몇 개 지표(오류율, 지연, 결제 실패)부터 알림을 건다. 되돌리기 어려운 기능은 기능 플래그로 배포와 노출을 분리한다.
- **대안과 트레이드오프**: 오픈소스 관측 스택을 직접 운영한 경험이 있지만, 인원이 적은 초기에는 운영 부담 때문에 관리형 도구나 클라우드 기본 도구가 더 맞을 수 있다. 비용, 보존 기간, 쿼리 요구가 커지면 다시 비교한다.
- **꼬리**: 경보 기준은 어떻게 정하나. 과거 숫자를 복사하지 않고 정상 구간과 사용자 영향을 관찰해 정한다. 경보가 많으면 무시되므로 행동이 필요한 것만 알린다.
- **학습 정본**: [[Feature-Flag]], [[GitHub-Actions]]

## J5. 고객 행동과 결제 데이터를 수집해 PO와 분석하려면

- **유형과 의도**: 설계형. 제품 실험을 데이터로 판단할 수 있게 만드는지 본다.
- **답변 골격**: 먼저 PO와 가설별 성공 지표를 정하고, 그 지표를 계산하는 데 필요한 이벤트만 정의한다. 이벤트 이름, 속성, 사용자 식별 방식을 문서로 고정한다. 결제와 참가 확정처럼 정확해야 하는 사실은 클라이언트 이벤트가 아니라 서버 DB 기록을 정본으로 쓴다. 분석 쿼리가 운영 DB를 누르지 않도록 읽기 복제본이나 별도 분석 저장소로 분리한다. 개인정보는 목적에 필요한 만큼만 모은다.
- **대안과 트레이드오프**: 분석 SaaS는 빠르게 붙지만 데이터 소유와 비용을 확인해야 하고, 직접 적재는 유연하지만 초기 부담이 크다. 처음에는 운영 DB 기반 간단한 대시보드로 시작하고 질문이 늘면 옮긴다.
- **꼬리**: 클라이언트 이벤트와 서버 기록 수치가 다르면. 유실과 중복 경로를 구분하고, 금액과 확정 건수는 서버 기록을 기준으로 삼는다.
- **내 경험**: IoT 기기의 배터리 부족과 통신 지연을 주기적으로 집계해 알림톡과 이메일로 알리는 리포트를 자동화했다.

## J6. 화면 개발 경험이 없는데 화면부터 인프라까지 가능한가

- **유형과 의도**: 갭 확인. 과장 없이 인정하고 빠르게 흡수할 근거가 있는지 본다.
- **답변 골격** (인정, 전이, 학습 3단):
  > React, Next.js, Flutter로 제품을 만들어 운영한 경험은 없습니다. 제가 강한 곳은 서버, 데이터, 인프라이고, 화면과 맞닿는 API 계약과 오류 조건은 OpenAPI 기반으로 프론트엔드와 맞춰 왔습니다. 화면은 공식 문서와 작은 기능 구현으로 익히고, AI 도구로 속도를 내되 동작과 품질은 제가 직접 확인하겠습니다. [입사 전 직접 만들어 볼 기능: 사용자 결정 필요]
- **알아 둘 개념**: Next.js는 라우팅, 서버 렌더링, 데이터 패칭을 제공하는 React 프레임워크다. Flutter는 Dart로 하나의 코드베이스에서 iOS와 Android 앱을 만드는 UI 툴킷이다. Fastlane은 앱 빌드, 서명, 스토어 배포를 자동화하는 도구다.
- **꼬리**: 첫 90일 안에 화면 작업을 혼자 맡으면. 서버와 인프라에서 먼저 기여하면서 화면은 작은 범위부터 맡고, 검토받을 수 있는 경로를 역질문으로 확인한다.
- **주의**: 출석부에서 화면을 만든 경험이 확인되면 이 답의 첫 문장을 바꾼다. 확인 전에는 경험이 있다고 말하지 않는다.

## J7. Redis와 MongoDB는 각각 언제 쓰나

- **유형과 의도**: 설계형. 저장소를 접근 패턴으로 고르는지 본다.
- **답변 골격**: 정본 데이터와 트랜잭션이 필요한 관계형 데이터는 PostgreSQL에 둔다. Redis는 캐시, 세션, 요청 제한, 짧은 수명의 카운터처럼 빠른 조회와 만료가 중요한 곳에 쓰고 정본으로 쓰지 않는다. MongoDB는 함께 읽고 함께 바뀌는 문서형 데이터, 스키마가 자주 바뀌는 로그나 콘텐츠에 맞는다. 여러 문서에 걸친 불변식은 트랜잭션이나 보상 설계가 필요하다.
- **내 경험**: 영양정보 데이터를 정형화하기 위해 MongoDB에서 MySQL로 옮긴 적이 있다. 관계와 제약이 핵심인 데이터였기 때문이다.
- **꼬리 캐시 스탬피드**: 인기 키가 한꺼번에 만료되면 원본이 몰린다. TTL 지터, 요청 병합, 백그라운드 갱신 중 데이터 성격에 맞게 고른다.
- **학습 정본**: [[MongoDB-Schema-Design]], [[Cache-Stampede]]

## J8. 외부 서비스 연동이 실패하거나 느리면

- **유형과 의도**: 설계형. 외부 의존성 장애가 핵심 흐름으로 번지지 않게 하는지 본다.
- **답변 골격**: 타임아웃을 명시하고, 일시 오류만 백오프와 지터로 제한 재시도하며, 영구 오류는 바로 실패 처리한다. 사용자 응답에 필요 없는 호출은 비동기로 분리한다. 외부 호출은 DB 트랜잭션과 잠금 밖에서 한다. 실패 누적은 알림과 수동 확인 경로로 보낸다.
- **대안과 트레이드오프**: 재시도는 성공률을 높이지만 외부 서비스에 부하를 더하고 중복 부작용을 만들 수 있으므로 멱등성 키와 함께 쓴다. 회로 차단은 연쇄 장애를 막지만 일부 기능을 포기한다.
- **내 경험**: 시솔지주에서 번역 기능을 Google API 연동으로 개선해 성능을 70% 높였고, 환율 배치와 배송 정보 수집의 실패 경로를 다뤘다.
