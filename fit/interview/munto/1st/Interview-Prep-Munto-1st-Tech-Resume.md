# 문토 1차 이력서 기반 기술 질문 (9문항)

> [[Interview-Prep-Munto-1st|목차로]]. [[My-Tech-Cards]] 8개 카드를 fork했고, R9는 카드 밖 개인 프로젝트다. 수치는 공개 이력서에 있는 값만 쓰고, 측정 대상과 비교 조건을 함께 말할 수 없으면 정성 표현으로 낮춘다. 각 카드 끝의 문토 연결은 공개 JD 요구만 근거로 한다.

## R1. 동시 요청의 재고 정합성을 어떻게 지켰나 (카드 1)

- **유형과 의도**: 경험형. 동시성 문제를 재현하고 잠금 범위를 설계했는지 본다.
- **핵심 답변**: 여러 기기 요청이 같은 재고 행을 동시에 바꾸던 경로에 `SELECT ... FOR UPDATE NOWAIT`, 짧은 트랜잭션, 인덱스 키로 좁힌 잠금 범위, 제한 재시도를 조합했다. 충돌이 잦은 쓰기라 낙관적 잠금으로 늦게 충돌을 발견하면 작업 전체를 다시 해야 해서 비관적 잠금을 골랐다. 외부 호출과 독립 검증은 트랜잭션 밖으로 빼고, 여러 행을 갱신할 때는 업무 키 순서를 통일했다. 동시 요청을 재현해 최종 수량과 실패 경로를 확인했다.
- **한계**: `NOWAIT`는 행 잠금 대기만 없앤다. 잠금 순서 통일은 데드락 확률을 낮출 뿐 없애지 못하므로 데드락 오류는 새 트랜잭션으로 제한 재시도한다. 재시도는 지금이라면 지수 백오프와 지터를 넣는다. 잠금은 급격한 유입을 흡수하지 못하므로 그 경우 키 단위 순서 큐와 워커 동시성 제한을 검토한다.
- **꼬리 PostgreSQL에서도 같은가**: PostgreSQL도 `FOR UPDATE`의 `NOWAIT`, `SKIP LOCKED`를 지원한다. 기본 격리 수준이 InnoDB의 REPEATABLE READ와 달리 READ COMMITTED이고 gap lock이 없으므로, 범위 조건의 중복 방지는 유니크 제약이나 조건부 갱신으로 지킨다.
- **문토 연결**: 모임 정원, 선착순 신청, 결제처럼 같은 자원을 여러 고객이 동시에 다투는 경로에 같은 판단 기준을 쓴다(S2).

## R2. EventBridge와 SQS로 발주를 자동화한 이유, Kafka는 왜 안 썼나 (카드 2)

- **유형과 의도**: 설계 경험형. 도구 선택 근거와 전달 보장 이해를 본다.
- **핵심 답변**: 상태 변경과 외부 연동을 한 요청에 묶으면 느린 의존성이 핵심 상태 변경까지 실패시킨다. 핵심 상태를 먼저 확정하고 후속 작업을 EventBridge와 SQS로 넘겼다. 소비 쪽은 멱등성 키와 상태 전이 검증으로 중복 전달을 정상 경로로 처리했고, 영구 오류는 즉시 격리, 일시 오류만 제한 재시도, 예산을 넘기면 DLQ와 수동 확인으로 보냈다. 조직의 운영 여력과 필요한 전달 보장을 비교해 관리형 큐를 골랐다.
- **한계와 개선안**: Transactional Outbox는 적용하지 않았다. DB 커밋 뒤 발행 전에 프로세스가 죽으면 이벤트가 빠질 수 있어 발행 재시도와 운영 확인으로 다뤘다. 다시 한다면 상태 변경과 outbox 행을 같은 트랜잭션에 쓰고 릴레이가 발행하게 한다. 그래도 정확히 한 번이라고 주장하지 않고 소비자 멱등성을 유지한다.
- **꼬리 언제 Kafka를 고르나**: replay와 긴 보존, 키 단위 순서, 독립 consumer group이 필요하고 측정된 처리량에서 현재 큐가 병목일 때 비교한다. Kafka 운영 경험은 없다고 먼저 밝힌다.
- **문토 연결**: 신사업 초기에는 관리형 서비스로 운영 부담을 줄이고, 알림이나 결제 후속 처리처럼 실패해도 재처리할 수 있는 작업을 비동기로 분리한다.

## R3. 슬로우 쿼리를 99.3% 개선했다는데 어떻게 했나 (카드 3)

- **유형과 의도**: 경험형. 수치의 측정 조건과 인덱스 설계 판단을 본다.
- **핵심 답변**: 최신 상태를 찾는 조회에서 후보 행 탐색과 정렬 비용이 커지는 것을 실행 계획으로 확인했다. 업무 키 동등 조건 뒤 최신 시각과 보조 키로 정렬하는 패턴에 맞춰 `(business_key, created_at DESC, id DESC)` 형태의 복합 인덱스를 만들고, 인덱스가 실제로 정렬과 상위 레코드 접근에 쓰이는지 다시 확인했다.
- **수치 말하는 법**: 99.3%는 특정 쿼리 1건의 전후 비교다. 배치 전체 시간이나 API 전체 지연과 같은 지표로 섞지 않는다. 측정 환경과 캐시 상태를 설명하지 못하면 크게 줄였다고만 말한다.
- **한계**: 복합 인덱스는 쓰기와 저장 비용을 늘린다. 데이터 분포가 바뀌면 효과가 달라지므로 변경 뒤에도 다시 측정한다.
- **꼬리 PostgreSQL이라면**: `EXPLAIN (ANALYZE, BUFFERS)`로 실제 실행과 버퍼 적중을 보고, 누적 통계는 `pg_stat_statements`로 찾는다. 활성 상태 행만 자주 조회하면 부분 인덱스가 인덱스 크기를 줄이는 선택지가 된다.
- **문토 연결**: JD의 느린 기능 개선과 성장에 따른 성능 개선 업무에 그대로 쓰는 방법론이다.

## R4. Prisma 관계 조회를 단일 쿼리로 바꿔 API 응답을 90% 개선한 과정 (카드 4)

- **유형과 의도**: 경험형. ORM을 추상화 뒤에 두지 않고 생성 SQL까지 확인하는지 본다. 문토 백엔드가 Prisma를 쓰므로 가장 직접적인 카드다.
- **핵심 답변**: 관계를 포함한 조회에서 예상보다 많은 SQL이 나가는 것을 로그와 요청 추적으로 발견했다. 당시 설정에서는 관계를 여러 쿼리로 읽어 애플리케이션에서 결합하고 있었다. 공식 문서와 실행 계획을 확인한 뒤 관계 조인 전략을 켜 MySQL에서 서브쿼리 기반 단일 쿼리로 합쳤고, 성능이 중요한 경로만 바꾸고 나머지는 타입 안정성과 변경 용이성을 유지했다. 이 사례는 하코 커뮤니티에서 발표했다.
- **흔한 오답**: 옵션 이름만 보고 SQL `JOIN`이 나간다고 단정하는 것. 실제 SQL 형태는 DB와 Prisma 버전에 따라 다르므로 SQL 로그와 실행 계획으로 확인한다.
- **한계**: 단일 쿼리는 왕복을 줄이지만 반환 데이터 중복, 집계 비용, DB 부하를 늘릴 수 있다. ORM이 부적절한 복잡한 집계만 명시적 쿼리로 낮춘다.
- **꼬리 PostgreSQL에서도 같은 결과일까**: 같은 코드라도 생성 SQL과 실행 계획이 달라질 수 있다. 사용하는 Prisma 버전 문서와 PostgreSQL 실행 계획으로 다시 검증한다고 답한다.
- **문토 연결**: Prisma와 PostgreSQL 조합에서 성능 문제가 생기면 같은 순서로 원인을 좁힌다.

## R5. 단일 NGINX 서버를 CloudFront, ELB, ECS로 옮긴 이유와 Read Replica (카드 6)

- **유형과 의도**: 설계 경험형. 트래픽 증가에 맞춘 단계적 인프라 전환 판단을 본다.
- **핵심 답변**: 트래픽이 늘며 단일 서버가 가용성과 배포의 병목이 됐다. 정적 자원과 캐시는 CloudFront, 트래픽 분산은 ELB, 애플리케이션은 ECS Fargate로 옮겨 서버 관리 부담을 줄였다. 읽기 부하는 RDS Read Replica로 나눠 응답 속도를 40% 개선했다. 쓰기와 쓰기 직후 읽기는 primary로 고정하고, 지연을 허용하는 조회만 replica로 보냈다.
- **대안과 트레이드오프**: Kubernetes는 다중 워크로드와 복잡한 라우팅이 필요할 때 검토하고, 작은 팀에는 관리형 태스크 환경이 운영 부담이 낮다. Rolling 배포는 자원 부담이 낮고, 즉시 전환과 빠른 롤백이 중요하면 Blue/Green을 비교한다.
- **꼬리**: 복제 지연을 숨기지 않는 것이 일관성 설계의 전제다. 자동 확장은 CPU만 보지 않고 큐 적체와 가장 오래된 메시지 대기 시간도 본다.
- **문토 연결**: JD의 출시 속도, 운영 비용, 유지보수를 고려한 구조 선택과 같은 축이다. 첫 제품은 단순하게 시작하고 병목이 측정될 때 한 단계씩 올린다.

## R6. Docker 멀티스테이지로 이미지와 배포 시간을 줄인 방법 (카드 6)

- **유형과 의도**: 사실과 경험 혼합. 빌드와 실행 의존성 분리를 이해하는지 본다.
- **핵심 답변**: 빌드 도구와 실행 의존성을 단계로 나눠 산출물만 실행 이미지에 넣었다. 이미지 909MB를 513MB로 43.6% 줄였고 배포 시간은 3분 10초에서 2분 20초로 26.3% 줄었다. 설정과 비밀은 이미지에서 분리해 주입했다.
- **흔한 오답**: alpine이면 무조건 좋다는 답. musl 기반이라 네이티브 모듈 호환성을 확인해야 한다. distroless는 셸이 없어 보안에 유리하지만 디버깅이 어렵다.
- **꼬리**: 컨테이너 종료 신호를 받으면 새 요청을 막고 진행 중 요청을 정리한다. 워커는 현재 메시지의 완료 또는 재전달 경계를 명확히 한다.
- **문토 연결**: 공고의 GitHub Actions, Docker 배포 경로를 처음부터 구성할 때 재현 가능한 빌드, 롤백, 종료 절차를 먼저 둔다.

## R7. Grafana, Prometheus, Loki로 무엇을 관측했나 (카드 5)

- **유형과 의도**: 설계 경험형. 로그, 메트릭, 경보의 역할 구분과 카디널리티 이해를 본다.
- **핵심 답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 요청마다 새 시계열이 생겨 시계열 수가 급증했다. 식별자를 구조화 JSON 로그 본문으로 옮기고, 라벨은 method, 정규화한 route, status처럼 값이 제한된 차원만 남겼다. 지연은 histogram으로 봤다. 메트릭은 추세와 사용자 영향, 로그는 개별 원인, 트레이스는 서비스 경계를 넘는 흐름을 본다. Grafana Alerting으로 실시간 장애 알림을 만들었다.
- **내가 겪은 실수**: 사용자 ID나 요청 ID를 메트릭 라벨에 넣는 것. 직접 겪었듯 시계열 수가 급증해 저장소와 경보가 불안정해진다. 식별자는 로그 본문에, 라벨은 값이 제한된 차원에만 둔다.
- **대안과 트레이드오프**: 당시에는 운영 가능한 범위의 오픈소스 조합을 골랐다. 인원이 적은 신사업 초기라면 자체 운영 부담이 큰 스택보다 관리형 모니터링과 오류 추적 도구를 먼저 비교한다(J4).
- **문토 연결**: JD의 배포와 오류 모니터링 환경 구성 업무에 해당한다.

## R8. 팀 AI 협업 규약은 무엇이고 효과는 어떻게 확인했나 (FIT 10, 24번)

- **유형과 의도**: 경험형. AI를 쓰는 수준이 아니라 검증 가능한 흐름으로 만들었는지 본다.
- **핵심 답변**: 팀 맥락이 사람 머릿속에만 있으면 새 구성원과 AI 도구 모두 같은 실수를 반복한다. 도메인별 지침 파일에 규칙, AI가 건드릴 영역과 금지 영역, 변경 시 확인 조건을 적고, 작업 종료 시점에 테스트와 검사로 AI가 스스로 품질을 확인하는 회귀 루프를 만들었다. 작은 영역부터 적용해 검토와 인수인계가 쉬워지는 것을 보여 주고 다른 구성원도 같은 방식을 쓰게 됐다.
- **꼬리 저항은 없었나**: 처음에는 구현보다 느려 보인다는 반응이 있었다. 취향이 아니라 반복 실수와 인수인계 비용 문제로 정리하고 작은 단위로 효과를 보였다.
- **꼬리 AI가 만든 코드의 품질을 어떻게 믿나**: 믿지 않고 검증한다. 테스트, 타입 검사, 실행 결과, 공식 문서 대조로 확인하고 채택은 사람이 결정한다.
- **문토 연결**: JD의 AI로 반복 개발, 테스트, 배포 작업을 줄이는 업무와 생성 코드 검증 요건에 직접 연결된다.

## R9. 개발 지식 온톨로지와 컨텍스트 검색 MCP는 무엇인가 (개인 프로젝트, 이력서)

- **유형과 의도**: 경험형. AI 도구를 쓰는 데서 그치지 않고 검색 품질을 평가 세트로 검증해 봤는지 본다.
- **핵심 답변**: 개인 프로젝트로, 개발 지식 Markdown을 근거 관계 그래프로 색인하고 그 검색을 MCP 도구와 CLI로 제공하는 시스템을 만들었습니다. 검색 방식을 바꿔 보기 전에 평가 질문부터 고정했습니다. 질문마다 반드시 돌려받아야 하는 문서, 절, 본문 문구를 근거 그룹으로 정하고, 응답 크기 예산 안에 그 근거가 모두 나와야 통과로 쳤습니다. 무관한 질문에는 빈 결과가 나와야 통과하는 음성 질문도 넣었습니다. 74개 질문으로 기존 어휘 검색, 형태소 기반 BM25, 다국어 E5 임베딩, BM25와 E5 임베딩 결과를 RRF로 합친 방식을 비교했는데, BM25는 후보 50개 안의 필수 근거를 45개에서 51개로 늘렸지만 최종 반환 근거는 늘지 않았고 기존 통과 사례 4개를 잃었습니다. 이 74개를 포함한 94개 질문으로 bge 리랭커도 붙여 봤지만 통과는 41개에서 40개로 개선이 없었고 질문당 약 4.7초가 더 걸렸습니다. 그래서 BM25, 임베딩, 리랭커 모두 채택하지 않았고, 문제가 후보 검색보다 예산 안에서 어떤 절을 고르느냐에 있다고 보고 절 선택 방식을 개선해 기존 94개 중 통과를 41개에서 43개로 올렸습니다.
- **판단 기준**: 검색 방식을 감으로 고르지 않고 고정한 평가 질문으로 비교한다. 기존 통과 사례를 잃으면 새 방식의 이득이 있어도 바로 바꾸지 않는다. 지연이 큰 방식은 품질 이득이 측정될 때만 쓴다. 새 방식을 측정으로 기각한 판단이 강점이다.
- **꼬리 평가 질문은 어떻게 만들었나, 어떤 지표로 비교했나**: 대부분 원문을 보고 만든 합성 질문이고 사람이 정답을 검수한 표본은 아니다. 양성 질문은 필수 근거 그룹(문서, 절, 본문 문구)이 응답 크기 예산 안에 모두 나오면 통과, 음성 질문은 빈 결과여야 통과다. 후보 단계는 필수 근거가 후보 50개 안에 드는지를 따로 쟀다. 비교 결론은 BM25와 리랭커 모두 미채택, 절 선택 개선만 채택이다.
- **이력서 정정**: 제출한 이력서에는 골든 케이스 약 145건으로 BM25, 임베딩, 리랭커를 비교했다고 적혀 있다. 145건짜리 세트는 없다. 물으면 먼저 바로잡는다: 이력서 숫자가 정확하지 않았습니다. 실제로는 74개 질문으로 검색 방식을 비교했고, 리랭커는 그 74개를 포함한 94개 질문으로 따로 비교했습니다.
- **한계를 먼저 말할 것**: 합성 표본이라 실제 답변 정확도나 사용자 만족도를 잰 것이 아니고, 자연어로 된 무관한 질문을 거절하는 성능은 여전히 약하다. 수치는 2026-09-08 로컬 1회 측정 기준이다.
- **문토 연결**: JD에 검색이나 LLM 기능 요소는 없다. AI 도구를 쓰고 결과 품질을 직접 검증하는 역량의 근거로 짧게 연결한다(R8과 함께).
- **주의**: 이력서에는 키노라이츠 경력 아래에 적혀 있지만 개인 프로젝트다. 회사 업무로 오해받지 않게 면접에서 먼저 개인 프로젝트라고 밝힌다.
