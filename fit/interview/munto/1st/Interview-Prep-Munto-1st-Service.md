# 문토 1차 서비스 맥락 질문, 역질문, 체크리스트

> [[Interview-Prep-Munto-1st|목차로]]. 공개 사실은 취미, 취향 모임 플랫폼이라는 점, 소셜링과 클럽 형태(2022 보도 기준), 공고의 실적 기재뿐이다. 신청, 결제, 알림의 실제 구현은 미확인이므로 아래 설계는 가정을 먼저 말하고 답한다.

## 1. 서비스 맥락 예상 질문 (6문항)

### S1. 문토를 써 봤나, 어떻게 이해했나

- **준비**: 면접 전에 앱을 설치해 모임 탐색, 상세, 신청 또는 결제 직전까지의 흐름을 직접 본다. [직접 사용한 뒤 관찰 한 문장: 사용자 작성]
- **답변 골격**: 사용자로서 본 흐름 한 가지 → 백엔드 관점에서 중요해 보이는 지점 한 가지(정원 마감, 결제와 참가 확정, 모임 전 알림) → 그 지점에서 내가 쓸 판단 기준.
- **주의**: 써 보지 않았다면 써 봤다고 말하지 않는다. 내부 구현을 아는 것처럼 말하지 않는다.

### S2. 정원이 있는 모임에 신청과 결제가 몰리면 어떻게 설계하겠나

- **유형**: 설계형. 가정: 모임마다 정원이 있고 결제 후 참가가 확정된다.
- **판단 기준**: 정원 초과 금지, 한 사람의 중복 신청 금지, 결제 실패나 이탈 시 자리 반환, 외부 결제 지연이 자리 잠금을 오래 잡지 않을 것.
- **답변 골격**: 신청 시 하나의 트랜잭션에서 `(모임, 사용자)` 유니크 제약으로 중복을 막고, `남은 자리 > 0` 조건부 갱신으로 자리를 먼저 선점한다. 선점에는 만료 시각을 두고, 결제 승인 콜백이 오면 확정, 만료되면 자리를 돌려준다. 결제 호출은 트랜잭션 밖에서 하고, 승인 결과가 불명확한 건은 조회와 대사로 닫는다.
- **대안과 트레이드오프**: 비관적 잠금은 단순하지만 인기 모임 한 행에 경합이 몰린다. 조건부 원자 갱신은 잠금 시간을 줄인다. 대기열은 도착을 평탄화할 뿐 정합성 수단이 아니므로 측정된 병목이 있을 때만 붙인다.
- **내 경험**: 동시 재고 갱신을 DB 잠금과 짧은 트랜잭션으로 정합성 있게 처리했다(R1).
- **꼬리**: 선점 만료와 결제 승인이 동시에 오면. 상태 전이를 조건부 갱신으로 하나만 성공하게 하고, 늦게 온 승인은 자동 취소나 환불 흐름으로 보낸다.

### S3. 신사업 아이템을 검증할 첫 제품의 범위를 어떻게 정하나

- **유형**: 설계형이자 협업형.
- **답변 골격**: PO와 검증할 가설 하나와 성공, 중단 지표를 먼저 정한다. 그 지표를 측정하는 데 꼭 필요한 흐름만 만들고, 관리자 기능이나 정산 자동화처럼 빈도가 낮은 일은 처음에는 수동으로 한다. 결제와 개인정보처럼 실수의 비용이 큰 부분은 줄이지 않는다. 출시 뒤 데이터와 고객 반응을 보고 다음 실험을 정한다.
- **트레이드오프**: 범위를 줄일수록 빨리 배우지만 수동 운영 비용과 기술 부채가 쌓인다. 부채는 기록하고 가설이 검증되면 갚을 시점을 PO와 합의한다.
- **내 경험**: 출석부를 직접 만들고 운영하며 사용자 인터뷰와 운영 지표 점검까지 한 사이클을 돌렸다(정성만).

### S4. 모임 알림(신청 확정, 모임 전 안내, 채팅)을 어떻게 보내겠나

- **유형**: 설계형. 가정: 푸시, 알림톡 같은 여러 채널이 있다.
- **답변 골격**: 알림은 핵심 트랜잭션과 분리해 큐로 비동기 발송한다. 사건마다 안정적인 이벤트 ID를 두고 `(이벤트 ID, 채널)` 유일성으로 로컬 중복을 막는다. 일시 실패만 재시도하고, 최종 실패는 DLQ와 확인 경로로 보낸다. 예약 알림은 시각 기반 스케줄러로 발송하고 모임 취소나 변경 시 함께 취소한다. 사용자별 수신 설정과 야간 발송 제한을 둔다.
- **트레이드오프**: 외부 발송 대행사가 수락 후 응답 전에 끊기면 중복을 완전히 막지 못한다. 대행사가 멱등성 키를 지원하면 전달하고, 아니면 발송 이력 조회로 확인한다.
- **내 경험**: IoT 상태를 집계해 알림톡과 이메일로 자동 통보하는 리포트를 만들었다.

### S5. 기존 문토 서비스와 신사업의 시스템 경계를 어떻게 나누겠나

- **유형**: 설계형. 가정: 신사업이 기존 회원과 결제를 쓸 수도, 안 쓸 수도 있다.
- **답변 골격**: 공유가 필요한 것(계정, 결제, 고객 데이터)과 실험 속도가 중요한 것(신사업 도메인)을 나눈다. 공유 자산은 기존 시스템의 공개 인터페이스로 쓰고 테이블을 직접 공유하지 않는다. 신사업 실패 시 걷어내기 쉽게 경계를 둔다.
- **트레이드오프**: 기존 자산을 쓰면 고객 유입과 결제 신뢰를 얻지만 기존 시스템 변경 일정에 묶인다. 분리하면 빠르지만 중복 구현과 데이터 연결 비용이 생긴다.
- **확인 질문으로 전환**: 이 경계는 사실을 모르므로 역질문 Q5로 확인한다.

### S6. 출시 후 고객 불편이나 오류를 어떻게 찾아 고치나

- **유형**: 경험형.
- **답변 골격** ([[My-FIT-Answers]] 14번 fork): 재현 → 원인 가설 → 분리, 검증 → 해결 → 영향 범위 점검 → 재발 방지. 오류 추적 도구와 로그로 빈도와 영향을 보고, 느린 기능은 실행 계획과 요청 추적으로 원인을 좁힌다. 고객 문의는 PO와 함께 분류해 빈도와 영향이 큰 것부터 고친다.
- **내 경험**: Prisma 조회 지연을 요청 추적과 실행 계획으로 좁혀 단일 쿼리로 바꿨다. 배포 뒤에는 인접 경로와 오류 신호를 함께 확인했다.

## 2. 역질문

[[My-Reverse-Questions]]에서 5개, 회사 특이 질문 2개를 골랐다. 핵심 3개(Q1, Q2, Q6)는 외워서 묻고 나머지는 흐름에 따라 고른다.

1. **Q1 (A1 변형)**: 신사업 팀이 지금 검증하려는 고객 문제는 무엇이고, 이 역할이 가장 먼저 풀어야 할 부분은 어디인가요?
2. **Q2 (B1)**: 합류 후 첫 90일 동안 책임질 과제와, 잘하고 있다고 판단할 기준은 무엇인가요?
3. **Q3 (A4 변형)**: 신사업 팀은 지금 어떤 역할로 구성돼 있고, 제 설계나 코드를 검토할 엔지니어는 누구인가요?
4. **Q4 (C2 변형)**: 결제와 고객 데이터처럼 정합성이 중요한 경계는 현재 어떤 방식으로 검증하고 있나요?
5. **Q5 (C1 변형)**: 신사업이 기존 문토의 회원, 결제, 인프라와 공유하는 부분과 새로 만드는 부분의 경계는 어떻게 되나요?
6. **Q6 (회사 특이)**: 아이템을 계속 키울지 멈출지는 어떤 지표와 시점으로 판단하나요? 개발자는 그 판단에 어떻게 참여하나요?
7. **Q7 (회사 특이, 갭 확인)**: 화면, 서버, 인프라 중 이 역할에 기대하는 비중은 어떻게 되고, Flutter와 Next.js 경험이 적은 사람은 어떻게 적응하는 편인가요?

면접 전 확인(F1): 1차 형식과 참여 역할, 과제나 라이브 코딩 여부를 공식 채널로 묻는다.

## 3. 면접 준비 체크리스트

### 면접 전

- [ ] [[Interview-Prep-Munto-1st-FIT#3. 이직 사유와 현재 상황|이직 사유 답변]], C3, C4, C5, C6의 답을 확정했다.
- [ ] 이력서 기간 표기(트라이포드랩 2024.02~2026.05, 키노라이츠 2026.06~2026.09 종료 표기)와 말할 내용을 맞췄다.
- [ ] 지원 공고(시니어 또는 일반)를 확정했다.
- [ ] 면접 일시, 형식, 참여 역할을 확인했다. 참석자는 역할로만 적는다.
- [ ] 문토 앱으로 모임 탐색에서 신청 직전까지 직접 확인하고 S1 관찰 문장을 적었다.
- [ ] 핵심 역질문 3개를 외웠다.

### 보강이 필요한 기술 영역

| 영역 | 보강할 핵심 개념과 판단 기준 | 복습 완료 |
| --- | --- | --- |
| DB와 성능 | PostgreSQL 격리 수준 기본값, MVCC와 VACUUM, 부분 인덱스, `EXPLAIN (ANALYZE, BUFFERS)` | [ ] |
| 결제 | 서버 재계산, 멱등성 키, 상태 머신, 콜백 서명 검증, 대사 | [ ] |
| 아키텍처와 설계 | 0에서 1 구조 선택(J1), 정원과 결제 동시성(S2), 알림(S4) | [ ] |
| 프레임워크와 화면 | Next.js 라우팅과 렌더링 방식, Flutter 위젯 구조, Fastlane 역할 | [ ] |
| 인프라와 운영 | GitHub Actions에서 ECS 배포, 롤백, 오류 추적과 최소 경보 | [ ] |
| 테스트와 품질 | AI 생성 코드 검증 루프, 결제와 동시성 경로의 테스트 방법 | [ ] |

### 강하게 어필할 포인트

- 서비스를 설계부터 운영, 인프라 전환까지 혼자 끝까지 책임진 경험.
- 동시성과 결제 성격의 정합성 경로를 재현하고 검증한 방식.
- Prisma 성능 문제를 생성 SQL까지 파고든 사례와 발표.
- AI를 팀 흐름으로 만들고 결과를 검증하는 기준.

### 답변 점검

- [ ] 외부 귀책 표현(회사 사정, 비전, 동료)이 없다.
- [ ] 부정적 단어(워라밸, 연봉)를 내가 먼저 꺼내지 않는다.
- [ ] 모든 답변 끝줄이 신사업 팀의 가설 검증, 출시, 운영 책임과 연결된다.
- [ ] 화면 개발과 Kafka처럼 해 보지 않은 것은 해 봤다고 말하지 않는다.
- [ ] 출석부의 정확한 수치, 전, 현 직장의 비공개 정보를 말하지 않는다.

### 공개 전 점검

- [ ] 회사 관련 사실에 출처가 있거나 미확인으로 표시했다.
- [ ] 제3자 실명, 연락처와 발화 원문이 없다.
- [ ] 본인 처우 금액과 비공개 계약 조항이 없다.
- [ ] 성과 수치는 공개 이력서에 있는 값만 썼다.
