# 시옷 경험과 컬처핏 질문

> 지원 전 예상 질문이다. 실제 면접에서 받은 질문이 아니다. 경험은 PDF, 경력 상세와 마스터에서 확인된 범위만 말한다. 실제 적용, 지금의 개선안, 설계 가정을 구분한다.

## 이력서 기반 경험 8문항

### R1. IoT 동시 갱신에 왜 DB 잠금을 골랐나요?

- **유형과 의도**: 경험형. 보호할 불변식, 잠금 범위와 대안을 실제로 판단했는지 확인.
- **답변**: 같은 재고 상태를 동시에 바꾸는 입력에서 DB 잠금과 짧은 트랜잭션으로 갱신을 조정했습니다. 변경 가능한 상태는 잠금 뒤 다시 읽어 검증하고, 외부 호출은 트랜잭션 밖으로 분리했습니다. 충돌이 잦고 보호 대상이 같은 DB에 있어 별도 분산 잠금보다 단순했습니다. 동시 입력을 재현해 최종 상태와 재시도 결과를 확인했습니다.
- **대안과 대가**: 한 SQL로 표현 가능하면 조건부 UPDATE를 먼저 비교. 충돌이 드물면 version 조건부 갱신이 선택지. 행 잠금은 대기와 데드락 위험이 있다.
- **흔한 오답과 조건**: 트랜잭션만 열면 lost update를 막는다고 말하지 않는다. MySQL 8.4 `NOWAIT`는 행 잠금 대기 정책이며 모든 대기를 없애지 않는다. [MySQL 잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).
- **꼬리**: 기준값을 잠금 전에 읽으면? 데드락을 재시도할 때 같은 트랜잭션을 재사용하면? 단일 hot key 유입 자체는 어떻게 제한하나?
- **시옷 연결**: 대용량 트랜잭션에서도 보호할 데이터와 실제 잠금 범위를 먼저 찾겠습니다.

### R2. EventBridge와 SQS 자동화에서 중복과 유실은 어떻게 다뤘나요?

- **유형과 의도**: 경험형. 적용한 보장과 미해결 경계를 구분하는지 확인.
- **답변**: 핵심 상태 변경 뒤 후속 발주를 EventBridge와 SQS로 분리했습니다. 소비자는 업무 키와 상태 전이로 중복 효과를 막고, 일시 실패만 제한 재시도하며 최종 실패는 격리해 확인했습니다. 운영 부담과 필요한 전달 보장을 비교해 관리형 큐를 골랐습니다.
- **한계와 대안**: DB 커밋과 발행은 원자적이지 않았습니다. Outbox는 당시 적용하지 않은 개선안입니다. 지금은 같은 트랜잭션에 이벤트를 기록하고 발행 재시도를 두되, 소비자 멱등성도 유지하겠습니다.
- **오답과 출처**: 큐가 업무를 정확히 한 번 실행한다고 말하지 않는다. SQS Standard는 중복 전달이 가능하다. [AWS 전달 보장](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html).
- **검증과 꼬리**: 발행 직전 중단, 성공 후 삭제 전 중단을 재현한다. 외부 시스템이 중복 키를 지원하지 않으면 결과 조회와 대사는 어떻게 하나?
- **시옷 연결**: 서비스 연동의 실패를 핵심 API와 분리하면서 완료 여부를 추적하겠습니다.

### R3. 복합 인덱스 최적화에서 무엇을 먼저 봤나요?

- **유형과 의도**: 경험형. 증상에서 SQL 병목을 좁히고 효과를 검증하는지 확인.
- **답변**: 최신 상태를 찾는 조회의 실행 계획을 먼저 봤습니다. 동등 조건과 정렬 순서에 맞춰 복합 인덱스와 쿼리를 조정하고, 읽는 행과 정렬 비용이 실제로 줄었는지 재확인했습니다. 인덱스는 쓰기 비용도 늘려 인접 쓰기 경로와 함께 확인했습니다.
- **대안과 한계**: 필요한 열만 조회, 쿼리 형태 변경, cursor 페이지네이션도 비교한다. 데이터 분포와 캐시가 바뀌면 같은 계획도 결과가 달라진다.
- **오답과 정량 예제**: 높은 카디널리티 컬럼부터 기계적으로 배치하지 않는다. 가정으로 `actual rows=5, loops=200`이면 총 반환은 1,000행이며, 부모/자식 시간은 중복 합산하지 않는다. [MySQL 8.4 EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html).
- **꼬리**: estimated rows와 실제가 다르면? filesort가 보여도 스캔이 더 큰 비용이면? read replica에서 측정한 값을 primary와 직접 비교할 수 있나?
- **시옷 연결**: SQL 튜닝을 인덱스 추가가 아니라 같은 조건의 검증 결과로 설명하겠습니다.

### R4. Prisma 관계 조회를 한 쿼리로 바꾸면 항상 빠른가요?

- **유형과 의도**: 경험형. ORM 옵션과 생성 SQL, 측정 경계를 이해하는지 확인.
- **답변**: 관계 조회에서 여러 SQL이 나가는 것을 확인한 뒤 공식 문서와 실행 계획을 대조해 필요한 경로를 조정했습니다. 옵션 이름보다 실제 SQL과 요청 지연을 기준으로 선택했습니다. 단일 쿼리는 왕복을 줄일 수 있지만 DB 집계 부담을 늘릴 수 있어 데이터 형태를 함께 봤습니다.
- **대안과 검증**: `join`과 `query`, 명시적 쿼리를 대표 데이터에서 비교. 쿼리 수, DB 시간, 연결 대기와 API p95/p99를 분리한다.
- **오답과 조건**: `include`를 모두 N+1로 부르거나 `join`이 SQL JOIN 한 종류라고 단정하지 않는다. 당시 MySQL은 correlated subquery와 JSON 집계가 가능한 전략이며 현재 지원과 설정은 설치 버전에서 재확인한다. [Prisma 관계와 조인](https://www.prisma.io/docs/orm/fundamentals/relations-and-joins).
- **꼬리**: 반환 데이터가 늘면 전략은? 여러 쿼리 읽기의 일관성은? explicit SQL로 낮출 기준은?
- **시옷 연결**: 라이브러리를 바꾸기 전에 SQL과 호출 경로의 원인을 먼저 확인하겠습니다.

### R5. 관측성을 구축하며 잘못 판단한 경험이 있나요?

- **유형과 의도**: 경험형. 실수를 인정하고 운영 신호의 위치를 교정하는지 확인.
- **답변**: 처음에는 요청 식별자를 메트릭 라벨에 넣었다가 시계열이 급증했습니다. 이후 식별자는 구조화 로그로 옮기고, 메트릭은 method, 정규화한 route, status 같은 제한된 차원으로 바꿨습니다. 로그로 개별 원인을, 메트릭으로 추세와 사용자 영향을 찾는 역할을 나눴습니다.
- **대가와 검증**: 상세 검색은 로그 탐색 비용을 감수하고 시계열 수, 쿼리 지연과 경보 경로를 확인한다. 전체 payload나 토큰을 그대로 기록하지 않는다. [Prometheus 라벨 기준](https://prometheus.io/docs/practices/naming/).
- **정량 예제**: 가정으로 4 method × 20 route × 5 status는 최대 400조합이다. 요청 ID가 추가되면 실제 관측 조합이 계속 늘어난다. 모든 조합이 반드시 생긴다는 뜻은 아니다.
- **꼬리**: 필요한 사용자 상세를 버리지 않으려면? 로그와 메트릭의 접근 권한은? 보안 사고 1건이 비율 경보에 묻히면?
- **시옷 연결**: 보안 데이터의 최소 기록과 접근 통제를 관측 편의와 함께 검토하겠습니다.

### R6. Docker와 ECS 전환은 어떤 기준으로 진행했나요?

- **유형과 의도**: 경험형. 결과 수치보다 배포, 복구와 호환성 판단을 확인.
- **답변**: 빌드 도구와 실행 파일을 Docker 멀티스테이지로 분리해 이미지와 배포 대기를 줄였습니다. 관리형 컨테이너 환경으로 전환할 때는 프로토콜과 접근 경로, 운영 부담을 비교했습니다. 읽기 분산은 stale read를 허용하는 경로와 쓰기 직후 조회를 나눴습니다.
- **대안과 한계**: Rolling은 구 버전 공존과 종료 처리가 필요하고 Blue/Green은 추가 자원이 든다. Kubernetes는 직접 운영 경험이 없으며 운영 요구를 확인해 비교한다.
- **검증과 꼬리**: 실행 이미지의 주요 API, 종료 중 요청, 새 버전 장애와 롤백, 복제 지연을 확인한다. 이미지가 작아졌는데 배포가 느리면 어떤 구간을 재나? [Docker 멀티스테이지](https://docs.docker.com/build/building/multi-stage/).
- **시옷 연결**: CI/CD 개선도 실행 가능성과 롤백 검증까지 완료 조건으로 삼겠습니다.

### R7. NestJS에서 경계를 나누는 이유는 무엇인가요?

- **유형과 의도**: 경험형. 구조가 실제 변경과 테스트를 돕는지 확인.
- **답변**: Controller는 입력과 응답, UseCase는 흐름과 트랜잭션, Domain은 불변식을 맡도록 분리했습니다. 저장소는 필요한 경계에서 주입해 도메인 규칙을 DB 없이 검증할 수 있게 했습니다. 단순한 흐름까지 계층과 인터페이스를 늘리는 것이 목표는 아닙니다.
- **대안과 대가**: 작은 CRUD는 Nest module/service로 충분할 수 있다. 바뀌는 경계와 독립 테스트 필요가 있을 때 port를 추가하며 파일과 변환 비용도 비교한다.
- **검증과 꼬리**: 도메인 규칙을 프레임워크 없이 확인하고 변경이 호출부에 퍼지는 범위를 본다. `forwardRef`가 반복되면? 한 트랜잭션에 여러 repository가 참여하면?
- **시옷 연결**: 레거시는 실제 변경 위험이 큰 경계부터 작은 단위로 정리하겠습니다.

### R8. FIDO 서버에서 표준과 라이브러리를 어떻게 검증했나요?

- **유형과 의도**: 경험형. 보안 도메인에서 추측을 재현과 명세로 확인하는지 검증.
- **답변**: WebAuthn 규격을 분석하며 서버를 개발했고, 라이브러리 동작이 명세와 다를 수 있는 지점을 재현해 비교했습니다. 공개 이슈로 문제를 제기하고 수정 여부를 검증했습니다. 라이브러리가 널리 쓰인다는 이유만으로 신뢰 경계의 검증을 생략하지 않는 기준을 얻었습니다.
- **한계와 대안**: 당시 특정 구현 경험이며 최신 WebAuthn 전체나 OAuth2/RBAC 실운영 숙련을 뜻하지 않는다. 업그레이드 시 명세와 버전별 동작을 다시 검증한다. [W3C WebAuthn](https://www.w3.org/TR/webauthn-3/).
- **꼬리**: 기대값과 재현 입력은 어떻게 정했나? 자체 수정과 upstream 반영은 어떻게 비교하나? 표준 준수가 제품 인가 정책까지 해결하나?
- **시옷 연결**: 보안솔루션에서도 표준, 코드와 재현 결과를 함께 보고 팀에 판단 근거를 공유하겠습니다.

## 컬처핏 5문항

### C1. 짧은 재직 뒤 다음 팀에서는 무엇이 달라지나요?

- **의도와 준비**: 책임 수용과 행동 변화. 현재 이직 사유는 메인 문서의 확정 답변을 먼저 30초 안에 말한다.
- **답변, My-Motivation-Reasons fork**: 합류 초기에 기대 결과와 완료 조건을 먼저 합의하고, 진행 상황을 근거와 함께 먼저 공유하겠습니다. 모르는 도메인 판단은 검토받고 작은 변경의 결과를 확인한 뒤 책임 범위를 넓히겠습니다.
- **꼬리**: 구체적으로 무엇을 공유하나? → 변경 이유, 검증 결과, 남은 위험과 다음 결정. 현재 상태는 경험을 회고하고 다음 역할을 준비한다고 답하며 직접 질문받은 사실은 숨기지 않는다.
- **시옷 연결**: 첫 90일에 API 운영과 보안 검토에서 무엇을 완료로 보는지 먼저 확인하겠습니다.

### C2. 기획과 프론트엔드의 일정이 품질 기준과 충돌하면?

- **의도와 준비**: 함께 결정하는 소통. My-FIT-Answers의 일정 조율과 비IT 소통을 fork.
- **답변**: 기획 의도를 확인하고 제가 이해한 내용을 다시 말해 맞춥니다. 오류 비용과 되돌리기 가능성을 기준으로 필수 범위를 나누고, 단계적 출시와 검증 경로를 제안합니다. 프론트엔드와는 요청, 응답, 실패 조건과 변경 이력을 명세로 합의합니다.
- **꼬리**: 합의가 안 되면? → 위험과 대안을 기록해 결정권자에게 판단을 요청하고 결정 뒤 남은 위험을 관리한다. PR은 문제, 선택, 검증과 영향 범위를 먼저 설명한다.
- **시옷 연결**: 보안 제약은 지키면서도 신규 API와 레거시 개선을 작은 배포 단위로 조율하겠습니다.

### C3. Kafka나 Kubernetes 경험이 부족한데 어떻게 배울 건가요?

- **의도와 준비**: 정직한 경험 경계와 전이 가능한 학습. My-FIT-Answers 장단점, Extended 학습 방식 fork.
- **답변**: 해당 제품을 직접 운영한 경험은 부족합니다. SQS와 관리형 컨테이너에서 다룬 전달 보장, 멱등성, 동시성 제한과 복구 개념을 먼저 연결하겠습니다. 팀의 실제 구성을 확인하고 공식 문서와 작은 실패 실험으로 차이를 검증한 뒤 리뷰를 받겠습니다.
- **꼬리**: 무엇부터 재현하나? → 소비자 중단과 중복 처리, 배포 실패와 복구. 실험을 끝냈다는 말과 실제 운영 경험은 구분한다.
- **시옷 연결**: 우대 기술을 전부 새로 도입하기보다 현재 팀의 과제를 해결하는 데 필요한 깊이부터 채우겠습니다.

### C4. AI 도구를 보안 개발에 활용할 때 무엇을 지키나요?

- **의도와 준비**: 개발 속도와 책임 경계. My-FIT-Answers 10번 fork, 회사가 AI 코딩을 의무화했다는 뜻은 아니다.
- **답변**: 코드 생성뿐 아니라 문맥 분리, 공식 문서 조사, 보안과 성능 검토에도 AI를 씁니다. 다만 요구사항 해석, 설계 선택과 결과 채택의 책임은 제가 맡습니다. 팀이 허용한 정보 범위와 도구부터 확인하고, 결과는 명세, 테스트와 실행 근거로 검증합니다.
- **꼬리**: 운영 LLM 제품 경험인가? → 개발 협업 적용 경험이며 제품 추론 파이프라인과 구분. 민감 정보와 자격증명은 승인된 경계를 따르고 도구에 임의 입력하지 않는다.
- **시옷 연결**: 보안 제품의 신뢰 경계를 개발 자동화에도 같은 기준으로 적용하겠습니다.

### C5. 위험이 여러 개 보이거나 긴급 이슈가 겹치면?

- **의도와 준비**: 주도성과 우선순위, 지속 가능성. My-FIT-Answers-Extended 긴급 이슈와 My-FIT-Answers 11번 fork.
- **답변**: 사용자 영향, 오류 비용, 복구 가능성과 확산 가능성을 먼저 비교합니다. 영향이 크거나 혼자 닫기 어렵다면 필요한 역할에 즉시 알리고, 현재 판단과 다음 확인 항목을 공유합니다. 의미 있는 문제에는 집중하되 장애 뒤 회고와 회복을 포함해 지속 가능한 대응을 만들고 싶습니다.
- **꼬리**: 발견한 위험을 모두 고치나? → 우선순위를 합의하고 최소 안전장치, 완료 조건과 재검토 시점을 정한다. 온콜 여부와 실제 역할 분담은 확인되지 않았다.
- **시옷 연결**: 위험 발견을 제안에서 끝내지 않고 우선순위, 적용과 관측까지 닫겠습니다.
