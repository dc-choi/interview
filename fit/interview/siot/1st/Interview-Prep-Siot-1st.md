## 1. 지원 전략과 확인된 회사 정보

시옷은 공고에서 정보보호 기술과 AI 경량 설계를 기반으로 보안솔루션과 AI 플랫폼을 개발하는 AI 보안 전문 기업으로 소개한다. 이 포지션은 API 신규 개발뿐 아니라 데이터 모델링, SQL 튜닝, 대용량 트랜잭션 대응, 레거시 개선과 테스트, CI/CD 운영을 함께 맡는다. 구체적 제품의 기능, 고객 유형, 조직 구성, 투자 단계, 재무와 현재 트래픽은 이번 공개 자료로 확인하지 못했다. 우대 기술 목록은 실제 운영 중인 스택의 증거로 보지 않는다.

**핵심 메시지**: 같은 데이터에 몰리는 요청, 느린 조회, 후속 작업 실패를 재현하고 안전하게 개선한 경험을 API 운영에 연결한다. 보안 제품 경험을 모두 갖췄다고 넓히지 않고, FIDO 표준 검증 경험과 입력 검증, 권한 경계, 실패 시 거부 원칙을 근거로 도메인 적응력을 설명한다.

**WHY와 답변 시그널**: 익숙한 Node.js와 데이터 정합성 문제를 발판으로 새로운 보안 도메인을 배우고 기여한다. 문제, 본인 역할, 선택 근거, 검증, 한계를 순서대로 말하고 위험 발견을 팀 우선순위와 완료 기준으로 닫는 행동을 보여준다. 구조를 많이 만드는 사람이 아니라 안전한 작은 변경을 검증하고 공유하는 동료라는 인상을 남긴다.

## 2. 바로 말할 FIT 답변

### 1분 자기소개, My-Self-Intro fork

> 안녕하세요, 백엔드 개발자 [이름]입니다. Node.js와 TypeScript로 서비스를 설계부터 운영까지 맡아 왔습니다.
>
> 트라이포드랩에서 NestJS 기반 재고 관리 서비스의 백엔드를 설계하고 운영했습니다. IoT 입력으로 같은 재고가 동시에 바뀌는 경로는 DB 잠금과 짧은 트랜잭션으로 정합성을 지켰고, 사람이 챙기던 발주 흐름은 EventBridge와 SQS로 자동화했습니다. 느린 조회는 생성 SQL과 실행 계획을 확인해 인덱스와 쿼리 구조를 조정했고, 로그와 메트릭을 연결해 운영 문제를 확인할 수 있게 했습니다. 그 전에는 FIDO 서버를 개발하며 WebAuthn 명세와 라이브러리 동작을 대조한 경험도 있습니다.
>
> 저는 실패와 재시도, 복구와 검증을 함께 생각하는 편입니다. 시옷 공고의 API 운영, SQL 튜닝과 레거시 품질 개선에 이 경험을 연결하고, 보안 도메인의 기준은 팀과 먼저 맞추며 기여하고 싶습니다.

### 지원 동기

> 공고에 API를 새로 만드는 일과 기존 운영 품질을 높이는 일이 함께 적혀 있다는 점에 관심을 가졌습니다. 저는 동시 갱신의 정합성, 조회 병목과 후속 작업의 실패를 직접 다뤄 왔습니다. 익숙한 Node.js와 RDBMS 기반에서 이 경험을 활용할 수 있고, 보안솔루션과 AI 플랫폼이라는 새 도메인에서는 데이터와 권한의 신뢰 경계를 더 깊게 배울 수 있다고 봤습니다. 합류한다면 담당 제품의 사용자와 먼저 풀 문제를 이해하고, 팀이 확인할 수 있는 작은 개선부터 만들고 싶습니다.

제품을 직접 써 본 경험이나 AI 모델, 보안 제품 내부 구성을 확인한 것처럼 답하지 않는다. 꼬리로 보안 깊이를 물으면 FIDO 명세 검증 경험과 새로 배워야 할 OAuth2/RBAC 운영 경계를 나눠 말한다.

### 짧은 재직과 이직 사유, 2026-09-29 확정

> 올해 6월 말 합류해 검색과 데이터 수집을 맡았는데, 팀이 기대하는 일하는 방식과 제 방식의 차이를 수습 기간 안에 좁히지 못해 본채용으로 이어지지 않았습니다. 돌이켜 보면 완료 조건을 먼저 맞추지 않고 제 판단으로 진행했고, 검증 결과를 공유하는 것도 늦었습니다. 그 뒤로는 합류 초기에 기대하는 결과와 완료 기준부터 합의하고, 진행 상황을 근거와 함께 먼저 공유하는 것을 기본으로 삼고 있습니다.

시옷에서도 첫 과제의 범위, 보안 검토와 완료 조건을 먼저 확인한다. 답변은 30초 안에 끝내고 이전 조직이나 평가 과정을 해명하지 않는다. 현재 활동을 물으면 지난 경험을 회고하고 다음 역할을 준비한다고 짧게 답하며, 겸업이나 사업을 직접 묻는 경우에는 사실대로 답한다.

## 3. 강점, 갭과 지원 전 순서

1. **먼저 바로잡을 이력서**: 키노라이츠는 2026-09-15 근무 종료다. PDF의 재직중과 현재 시제를 과거로 수정할 필요가 있다. 온톨로지는 개인 프로젝트이며 평가 약 145건 문구는 오류로 기존 기록에서 확인돼 이 준비에는 사용하지 않는다. 원본 수정은 별도 작업이다.
2. **가장 강한 근거**: 동시성 R1, 실행 계획 R3와 ORM R4를 각각 문제, 본인 판단, 검증, 한계로 설명한다. 개선률과 직장 내부 트래픽은 복제하지 않았다.
3. **보안 도메인 보강**: JWT 검증과 객체 수준 인가 S1/S2, 권한 변경 후 폐기, 로그의 민감 정보 경계를 우선 복습한다. FIDO 경험을 OAuth2 실운영으로 바꾸지 않는다.
4. **실운영 갭 확인**: Redis, K8s, Kafka/RabbitMQ/BullMQ의 실제 사용 경험과 첫 과제 요구 수준을 구분한다. MongoDB는 이관 경험과 지속 운영의 깊이를 구분한다. J3/J6/J7의 개념 설명은 경험 증명이 아니다.
5. **연습 순서**: 자기소개 1분, 이직 답변 30초, R1/R3 각 2분, S1/S2/S4 설계 각 5분. 라이브 코딩 여부는 미확인이라 형식이 확정되면 범위를 맞춘다.

## 4. 역질문 6개

1. **B1 초기 성공 기준**: 합류 후 먼저 책임질 과제와 첫 90일에 기대하는 결과는 무엇인가요?
2. **C1 소유 범위**: API 신규 개발, 레거시 개선과 성능 대응 중 우선순위는 무엇이며, 이 역할이 소유하는 제품 경계는 어디인가요?
3. **E2 리뷰와 배포**: 코드 리뷰와 긴급 배포에 적용하는 검증 기준은 무엇이고, 보안 검토는 어느 단계에서 함께 진행하나요?
4. **D1 온보딩**: 새 구성원이 보안 도메인과 기존 시스템을 이해하고 첫 변경을 배포하기까지 어떤 검토와 피드백을 받을 수 있나요?
5. **회사 특이, 데이터 경계**: 보안솔루션과 AI 플랫폼에서 이 포지션이 직접 책임지는 데이터와 권한 경계는 무엇인가요? 실제 고객이나 민감 정보의 상세 없이 역할 수준에서 알고 싶습니다.
6. **회사 특이, 운영 성능**: 공고의 대용량 트랜잭션과 급증 트래픽 대응은 현재 어떤 사용자 흐름에서 가장 중요하며, 개선 완료는 어떤 지표로 판단하나요?
