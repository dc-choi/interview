# 시옷 JD와 서비스 기술 질문

> 2026-10-01 공식 문서와 대조한 예상 질문이다. 서비스 문제는 공고의 보안솔루션과 AI 플랫폼이라는 범위에서 만든 연습 가정이며, 시옷의 실제 시스템 구성이나 현재 장애를 뜻하지 않는다. 사실형은 동작과 오답, 설계형은 요구 확인과 대안을 말한다.

## JD 기반 7문항

### J1. Node.js API는 CPU가 여유로운데 왜 느릴 수 있나요?

- **유형과 의도**: 사실형. 이벤트 루프, 비동기 I/O와 하위 자원 병목 구분.
- **핵심 답변**: 이벤트 루프 지연, 연결 풀 대기, SQL, 외부 API, 네트워크를 나눠 봅니다. I/O를 비동기로 호출해도 그 앞뒤 JS 계산은 메인 스레드에서 실행될 수 있습니다. 큰 JSON 파싱이나 동기 연산은 입력 크기를 제한하고 프로파일링한 뒤 분할하거나 별도 worker로 옮깁니다.
- **대안과 대가**: worker는 CPU 작업의 격리에 유리하지만 전달과 메모리 비용이 든다. I/O 대기는 worker를 늘리기보다 제한된 동시성과 연결 예산을 검토한다.
- **오답과 검증**: `async`면 모든 연산이 별도 스레드로 간다는 답은 틀리다. 요청 지연, 이벤트 루프 지연, CPU, DB 대기를 같은 부하에서 비교한다. [Node.js 이벤트 루프 차단](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop).
- **꼬리**: `Promise.all`로 제한 없이 요청하면? 평균 CPU는 낮은데 한 코어가 바쁘면? 공격적 입력이 정규식과 JSON 파싱을 오래 붙잡으면?
- **경험 연결**: 비동기 후속 처리 경험을 쓰되 Node 런타임 튜닝 실적을 새로 주장하지 않는다.

### J2. 대용량 트랜잭션은 어떻게 나누나요?

- **유형과 의도**: 설계형. 원자성 요구와 처리량을 함께 판단하는지 확인.
- **골격**: 전체 작업이 하나의 불변식인지, 행별 독립 작업인지 확인합니다. 외부 호출은 잠금 구간에서 빼고, 독립 작업은 키 순서가 안정적인 청크와 체크포인트로 나눕니다. 부분 성공을 허용하지 않는 업무는 임의 분할하지 않고 상태 모델과 확정 시점을 먼저 정합니다.
- **대안과 대가**: 큰 단일 트랜잭션은 원자성이 분명하지만 잠금, 로그와 롤백 비용이 크다. 청크는 복구가 쉽지만 부분 완료 상태와 멱등 재시작을 관리해야 한다.
- **검증**: 처리량, lock wait, 연결 대기, 복제 지연을 측정하고 중간 실패 뒤 중복/누락을 검증한다. [MySQL 잠금 읽기](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).
- **꼬리**: 한 업무 키에 작업이 몰리면? chunk 경계에 신규 행이 들어오면? 원자성 요구를 팀과 어디서 합의하나?
- **경험 연결**: R1의 짧은 트랜잭션과 재시도 판단을 큰 작업의 경계에 연결한다.

### J3. Redis 캐시가 장애 나거나 인기 키가 동시에 만료되면?

- **유형과 의도**: 설계형. 캐시의 정합성과 원본 보호 경계.
- **골격**: 먼저 허용 신선도와 읽기 대상 권한을 정합니다. Cache-Aside에서 읽기 미스는 원본을 조회해 적재하고 쓰기 뒤 무효화합니다. TTL은 안전망이며 같은 키의 동시 미스는 요청 병합으로 줄이고 원본 접근은 동시성과 연결 예산으로 제한합니다.
- **대안과 대가**: 여러 키 만료는 TTL jitter, 한 hot key는 single-flight나 갱신 조정이 선택지다. 단일 프로세스 병합은 다른 인스턴스를 묶지 못한다. 오래된 값은 허용된 데이터에만 반환한다.
- **오답과 검증**: jitter만으로 단일 hot key 폭주를 없앤다고 말하지 않는다. 권한 변경 결과에 임의 stale fallback을 적용하지 않는다. 미스율, 원본 QPS와 장애 시 최악 지연을 확인한다.
- **꼬리**: 갱신과 삭제 순서가 역전되면? 캐시 키에 tenant가 빠지면? Redis 장애에서 fallback이 DB를 쓰러뜨리면?
- **경험 연결**: 실제 경험은 캐시 초기 적재이며, 여기의 Cache-Aside와 stampede 대응은 설계 판단이다.

### J4. REST API 명세에서 오류와 중복 요청을 어떻게 정의하나요?

- **유형과 의도**: 사실형. HTTP 의미론과 호출자 계약의 구분.
- **핵심 답변**: 리소스와 행위, 입력 검증, 인증/인가, 실패 조건과 재시도 가능성을 정의합니다. GET은 안전한 조회, PUT은 같은 요청의 의도된 효과가 멱등하며 POST는 자동으로 멱등하지 않습니다. 중요한 변경에는 업무 키, 요청 fingerprint와 기존 결과를 보관하는 중복 처리 정책을 별도로 정합니다.
- **대안과 대가**: 즉시 완료가 필요하면 동기 응답, 오래 걸리면 접수와 상태 조회 계약을 나눈다. 단순 URI 규칙만으로 REST를 설명하지 않는다.
- **오답과 검증**: DELETE를 두 번 호출해 HTTP 응답이 달라도 의도된 효과의 멱등성과는 별개다. 응답 schema, 오류, 권한과 재요청을 계약 검사로 고정한다. [RFC 9110 HTTP 의미론](https://www.rfc-editor.org/rfc/rfc9110.html).
- **꼬리**: 같은 중복 키로 다른 body가 오면? 기존 클라이언트를 깨지 않는 변경은? PUT/PATCH를 어떻게 나누나?
- **경험 연결**: API 이관의 계약 유지 경험을 명세와 변경 검증으로 연결한다.

### J5. 레거시를 바꾸기 전에 어떤 테스트를 붙이나요?

- **유형과 의도**: 설계형. 테스트 수보다 실제 실패를 잡는 검증 경계.
- **골격**: 먼저 바뀌면 안 되는 공개 동작을 확인합니다. 도메인 규칙은 단위 검사, SQL과 커밋/롤백은 실제 DB 통합 검사, 인증과 응답 계약은 HTTP 경로 검사로 나눕니다. 변경하는 hot path부터 실패 사례를 고정하고 기능 변화와 구조 정리를 작은 단위로 나눕니다.
- **대안과 대가**: mock은 빠르지만 DB 잠금과 SQL 동작을 증명하지 못한다. 통합 검사는 비용이 들지만 실제 저장 결과를 확인한다. SQLite가 운영 MySQL의 격리 동작을 대신한다고 가정하지 않는다.
- **검증**: 첫 저장 뒤 두 번째 작업에 실패를 주입하고 트랜잭션 밖에서 결과를 읽어 롤백을 확인한다. 테스트 자체의 외부 트랜잭션이 커밋을 가리지 않게 한다. [NestJS Testing](https://docs.nestjs.com/fundamentals/testing).
- **꼬리**: 인증 Guard를 모두 우회한 테스트는 무엇을 놓치나? TDD 경험이 없으면? → 테스트 경험과 개발 순서는 구분해 사실대로 답한다.
- **경험 연결**: 배치 자동 검증과 배포 검사 경험을 출발점으로 쓴다.

### J6. Kafka, RabbitMQ, BullMQ 중 무엇을 선택하나요?

- **유형과 의도**: 설계형. 제품 이름보다 전달과 운영 요구를 비교하는지 확인.
- **골격**: 작업 큐인지 이벤트 배포인지, 보존과 재생, 순서의 범위, 지연과 운영 책임부터 확인합니다. 현재 팀 표준이 목표를 만족하면 재사용합니다. 제품별 정확한 보장과 제한은 실제 버전의 공식 문서로 확인하고 작은 장애 실험으로 검증합니다.
- **제품 비교**: 여러 소비자가 보존된 사건을 각자 재생해야 하면 Kafka의 파티션 로그와 보존 정책을, 라우팅 규칙으로 작업을 큐에 분배해야 하면 RabbitMQ의 exchange/binding을, Node.js에서 지연 작업과 재시도를 관리하고 Redis 운영을 감당할 수 있으면 BullMQ를 우선 비교한다. 기능이 배타적이라는 뜻은 아니며 RabbitMQ에도 Streams가 있다.
- **대안과 대가**: Kafka는 파티션과 보존 용량, RabbitMQ는 라우팅과 확인 응답, BullMQ는 Redis 내구성과 메모리 정책을 운영해야 한다. 기존 팀 표준으로 충분하면 새 제품을 추가하지 않는다. 어떤 큐도 DB 커밋과 발행을 자동으로 원자화하지 않는다.
- **비교 근거**: [Kafka 개요](https://kafka.apache.org/intro/), [RabbitMQ Exchanges](https://www.rabbitmq.com/docs/exchanges), [BullMQ 개요](https://docs.bullmq.io/).
- **검증과 오답**: 소비 중단, 발행 중단과 중복 처리를 재현한다. 정확히 한 번 전달이라는 문구를 외부 업무 부작용까지 확장하지 않는다. [AWS Outbox와 중복 소비](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).
- **꼬리**: 재생이 필요한 기간은? 한 키의 순서를 지키면 처리량은? Redis와 작업 큐를 함께 잃으면 복구 원본은?
- **경험 연결**: 직접 운영 경험은 EventBridge/SQS다. 세 제품을 운영했다고 답하지 않는다.

### J7. RDBMS와 MongoDB는 어떤 데이터에 맞나요?

- **유형과 의도**: 사실형. 데이터 모델, 관계와 불변식 기준의 선택.
- **핵심 답변**: 함께 읽고 같은 생명주기를 가진 제한된 데이터는 문서 내장을 검토할 수 있습니다. 관계와 여러 데이터의 정합성, 복잡한 SQL이 핵심이면 RDBMS가 명확할 수 있습니다. MongoDB도 스키마 검증과 인덱스가 필요하며 여러 문서에 걸친 갱신 경계는 별도로 설계합니다.
- **대안과 대가**: embed는 함께 읽기 쉽지만 독립 갱신과 배열 성장에 불리하다. reference는 중복을 줄일 수 있으나 추가 조회와 관계 관리 비용이 든다.
- **오답과 조건**: NoSQL은 SQL 튜닝을 모두 소진한 뒤의 마지막 단계가 아니다. 무제한 배열을 한 문서에 계속 넣지 않는다. MongoDB의 단일 문서 원자성은 다중 문서 업무의 원자성과 다르다. [MongoDB 내장 모델](https://www.mongodb.com/docs/manual/data-modeling/embedding/).
- **꼬리**: audit event를 사용자 문서에 누적하면? 문서→RDB 이관은 어떻게 검증하나? → 구간별 건수, 키 매핑과 실제 값의 대조, 재실행 경계를 설명한다.
- **경험 연결**: 경력 상세의 MongoDB→MySQL 이관은 모델 복원과 구간 검증 경험으로 말하고, MongoDB 대규모 운영 숙련으로 넓히지 않는다.

## 서비스 맥락 5문항

### S1. 보안 플랫폼의 관리자 API에 JWT와 RBAC를 어떻게 적용하나요?

- **유형과 의도**: 설계형. 인증, 역할 권한과 객체 수준 인가의 경계.
- **가정과 골격**: 여러 조직의 관리자가 있다는 연습 가정입니다. JWT의 서명, 허용 알고리즘, 발급자, 대상과 시간 조건을 검증한 뒤 서버가 신뢰하는 조직과 역할을 확인합니다. 실제 대상 객체의 조직과 요청 행위 권한까지 서버에서 검사하고 기본은 거부로 둡니다.
- **대안과 대가**: 역할 표는 단순하지만 소유자/조직 같은 속성 조건을 모두 표현하기 어렵다. 중요한 권한 변경은 세션 조회, token version 또는 denylist 비용과 즉시 폐기 요구를 비교한다.
- **오답과 검증**: 유효 JWT가 모든 객체에 대한 접근을 허용하지 않는다. 다른 tenant ID, 객체 ID 바꾸기, 역할 변경 후 기존 토큰과 deny 상태를 검사한다. [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html).
- **꼬리**: Guard만으로 충분한가? 토큰은 정상인데 객체가 다른 조직이면? 인증 저장소가 장애 나면 허용하나?

### S2. OAuth2, OIDC와 JWT는 같은 개념인가요?

- **유형과 의도**: 사실형. 인가 프로토콜, 로그인과 토큰 형식의 구분.
- **핵심 답변**: OAuth2는 위임된 접근 권한을 다루고, OIDC는 OAuth2 위에서 사용자 인증 정보를 정의하며, JWT는 claim을 표현하는 형식입니다. OAuth access token이 반드시 JWT일 필요는 없고 ID token을 임의 API access token으로 받으면 안 됩니다.
- **보안 경계**: 서명은 기밀성을 뜻하지 않고 Bearer token은 통째로 탈취되면 재사용될 수 있다. redirect 검증, PKCE, 토큰 수명과 refresh 재사용 방어는 클라이언트 유형과 위협 모델에 맞춰 정한다.
- **오답과 출처**: JWT면 stateless이므로 즉시 폐기가 자동이라는 답은 틀리다. [RFC 8725 JWT 검증](https://www.rfc-editor.org/rfc/rfc8725.html), [RFC 9700 OAuth2 보안](https://www.rfc-editor.org/rfc/rfc9700.html), [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html).
- **꼬리**: redirect wildcard가 위험한 이유는? access/ID token 검증 규칙을 어떻게 나누나? cookie 저장은 CSRF까지 해결하나?
- **한계**: 여기의 설명은 복습용 지식이며 해당 흐름을 실제 운영한 경력 주장과 구분한다.

### S3. AI 연산이 느린 플랫폼에서 API 응답을 어떻게 설계하나요?

- **유형과 의도**: 설계형. 연산 지연과 요청 계약, 자원 예산.
- **가정과 골격**: 느린 AI 작업을 API가 요청한다는 연습 가정입니다. 즉시 완료가 필요한지 접수 후 조회가 가능한지 먼저 묻습니다. 입력 크기, 실행시간, 동시성과 tenant별 예산을 제한하고 오래 걸리면 작업 ID, 상태 조회와 취소 경계를 둡니다.
- **대안과 대가**: 동기는 단순하지만 timeout과 자원 점유가 크다. 비동기는 사용자 지연을 설명해야 하고 중복 접수, 실패와 결과 보존을 관리해야 한다. 외부 연산을 await한다는 이유만으로 무한 동시 호출을 허용하지 않는다.
- **정량 가정과 검증**: 가정으로 평균 유입 100건/초, 평균 처리 0.5초이면 안정 상태의 평균 진행 작업은 약 50건이다. peak와 tail은 별도로 측정해 동시성 상한을 정한다. 큐 적체와 오래된 작업, 실패율과 사용자 완료 지연을 확인한다.
- **꼬리**: 취소 요청이 늦으면? 이미 연산은 끝났는데 결과 저장이 실패하면? 예산을 넘은 요청은 어떤 상태를 반환하나?

### S4. 정책 저장은 성공했지만 외부 적용이 실패하면 어떻게 하나요?

- **유형과 의도**: 설계형. 분산 연동의 상태와 불명확한 결과 처리.
- **가정과 골격**: 정책을 저장하고 외부 서비스에 적용한다는 연습 가정입니다. 요청됨, 적용 중, 적용 완료와 실패를 나누고 사용자에게 저장과 적용 완료를 구분해 보여줍니다. 같은 DB의 정책과 적용 이벤트는 같은 트랜잭션에 기록하고 소비는 멱등하게 설계합니다.
- **대안과 대가**: 동기 적용은 즉시 결과를 줄 수 있지만 외부 장애가 전파된다. 비동기는 장애 격리 대신 버전, 적용 지연과 재시도 상태가 필요하다. Outbox는 외부 부작용의 원자적 롤백을 보장하지 않는다.
- **검증과 출처**: commit 후 발행 중단, 적용 후 응답 유실, 구 버전의 늦은 도착을 재현한다. 외부가 같은 키/버전 검증을 지원하면 활용하고 불명확한 결과는 조회와 대사로 닫는다. [AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).
- **꼬리**: 보상할 수 없는 보안 변경이면? 재시도 전에 최신 정책이 바뀌면? 오래된 owner가 완료 기록을 남기면?

### S5. 보안 로그를 남기면서 민감 정보와 조회 성능을 어떻게 다루나요?

- **유형과 의도**: 설계형. 감사에 필요한 근거와 데이터 최소화.
- **가정과 골격**: 관리 행위의 감사 기록이 필요하다는 연습 가정입니다. 행위자 식별, 대상, 행위, 결과와 시각처럼 필요한 항목을 먼저 정하고 토큰과 비밀 원문은 제외합니다. 접근권한, 보존과 변조 방지 요구를 확인하며 수집 실패를 정상 행위와 어떻게 묶을지도 정책으로 합의합니다.
- **대안과 대가**: 주요 업무와 같은 DB에 기록하면 일관성 경계가 분명하나 쓰기 부하가 있다. 별도 저장은 조회를 분리할 수 있지만 유실과 적재 지연의 검증이 필요하다.
- **검증**: 권한별 조회, 정보 마스킹, 원문 secret 미포함, 적재 실패와 보존 종료를 확인한다. 메트릭에는 사용자/요청별 고유 식별자를 무제한 라벨로 넣지 않는다. [Prometheus 라벨 기준](https://prometheus.io/docs/practices/naming/).
- **꼬리**: 감사 기록 저장이 실패하면 요청을 거부하나? 법적 보존 기간은 어떻게 정하나? → 회사의 적용 요구를 확인하며 임의 기간을 제시하지 않는다.
