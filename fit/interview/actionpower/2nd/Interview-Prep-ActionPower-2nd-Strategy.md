# 액션파워 2차 — 전략과 본인 경험 답변

> 상위 TOC: [[Interview-Prep-ActionPower-2nd|액션파워 2차 면접 준비]]

이 문서는 액션파워 2차 면접 준비 스냅숏이다. 회사의 실제 문화나 개별 면접 참여자의 기대를 단정하지 않고, 공개 가치와 본인의 일하는 방식을 연결한다.

## 면접 운영 전략

> 아래 내용은 당시의 준비 가설이다. 회사의 비공개 평가표나 실제 참여자의 의도를 설명하는 사실이 아니다.

- 2차는 일방적으로 선택받는 자리가 아니라, 장기적으로 함께 문제를 풀 수 있는지 서로 확인하는 자리로 준비했다.
- 답변은 결론부터 짧게 말하고, 추가 질문에 맞춰 문제, 판단, 행동과 검증 근거를 확장한다.
- 경험은 직접 설계한 것, 직접 구현한 것, 팀이 함께 결정한 것과 관찰만 한 것을 구분한다.
- 성과 수치는 출처, 기간과 비교 조건을 설명할 수 있을 때만 쓰고, 그렇지 않으면 변화와 한계를 정성적으로 말한다.

### 개인 점검 가설

1. 문제를 스스로 정의하고 해결 범위를 정할 수 있는가
2. 현재 기술을 실제 운영 판단으로 연결할 수 있는가
3. 모르는 영역을 숨기지 않고 학습과 검증 순서로 바꿀 수 있는가
4. 한 번의 성과보다 일관된 태도와 후속 행동을 보여 주는가
5. 동료와의 협업에서 본인의 기여와 타인의 기여를 정확히 구분하는가

### 예상하지 못한 질문을 받았을 때

1. 질문이 확인하려는 문제를 짧게 되묻는다.
2. 현재 알고 있는 사실과 모르는 사실을 나눈다.
3. 제약, 가능한 대안과 선택 기준을 설명한다.
4. 실제 업무라면 무엇을 측정하거나 재현해 판단할지 덧붙인다.

### 당시 가정과 현재 교정

- **당시 가정**: 대표와 채용 역할이 참여할 것으로 예상해 문화와 장기 방향 질문을 중심으로 준비했다.
- **현재 교정**: 실제 참여 역할은 CEO와 CTO였다. 참여자를 고정해 추측하기보다 역할별로 제품 방향, 기술 의사결정과 협업 방식을 확인하는 질문을 준비했어야 한다.
- 절박함을 강조하기보다 지원 이유와 선택 기준을 설명하고, 마지막 질문 기회에는 본인 답변에서 불명확했던 부분을 먼저 확인한다.

## 공개 출처로 확인한 가치

액션파워의 공개 채용 페이지는 존중, 질문, 실행을 핵심가치로 제시한다. 이것이 이 면접의 실제 평가 기준이나 개별 참여자의 기대를 뜻하지는 않으므로, 아래 사례는 그 가치와 연결해 스스로 점검하는 용도로만 쓴다.

## 답변을 점검할 축

> 아래 축은 회사의 내부 평가표가 아니라, 공개 가치가 행동으로 드러나는지 확인하는 개인 점검표다.

1. 문제를 정의하고 끝까지 책임지는가
2. 모르는 것을 검증 가능한 질문으로 바꾸는가
3. 동료와의 의견 차이를 근거로 다루는가
4. 실패 이후 행동을 바꾸고 확인하는가
5. 역할의 사용자 가치와 자신의 경험을 연결하는가

## 답변 구조

| 질문 | 답변 순서 |
|---|---|
| 갈등 | 공통 목표, 위험, 근거, 합의, 결과 |
| 실패 | 사실, 원인 가설, 조치, 재발 방지 |
| 이직 | 선택 기준, 배운 점, 다음 검증 |
| 장기 목표 | 직함보다 책임질 문제와 기여 방식 |

## 가치와 내 행동 사례

### 존중, FIDO 규격 검증

- 상황: 동료가 인증 라이브러리의 FIDO 관련 규격 준수에 의문을 제기했다.
- 행동: 일정 압박보다 검증을 우선해 공개 규격과 구현을 대조하고, 실패 경로를 재현해 가정을 수정했다.
- 배움: 이견은 누가 맞는지를 가리는 재료가 아니라, 결정의 검증 범위를 넓히는 입력이다.

### 질문, Prisma 조회 진단

- 상황: 조회 지연이 있어 ORM 추상화만 믿지 않고 실제 호출 경로를 확인했다. 당시 `relationJoins`가 비활성인 구성에서 관계를 여러 쿼리로 읽고 애플리케이션에서 결합하는 흐름을 로그로 확인했다.
- 행동: Prisma 관계 조회 문서와 대조해 `relationJoins`를 활성화하고 `relationLoadStrategy: 'join'`을 적용한 뒤, MySQL의 단일 correlated subquery와 실행계획을 확인했다.
- 결과: 같은 조건에서 변경 전후 지연을 비교해 개선을 확인하고 과정과 학습을 기술 커뮤니티 발표로 공유했다. 내부 수치와 커뮤니티 규모는 공개하지 않는다.
- 배움: 성능 개선은 직감이 아니라 재현 가능한 관측과 비교 조건으로 설명해야 한다.

### 실행, 단계적 전환과 테스트 품질 개선

- 큰 구조 변경은 한 번에 전환하지 않고 작은 단계로 나눠 각 단계의 관측, 검증과 되돌릴 경로를 확인했다.
- 테스트가 부족한 코드베이스에서는 핵심 경로부터 PR 검증을 도입하고, 팀이 수용할 수 있는 속도로 기준을 높였다.
- 배움: 실행은 빠르게 바꾸는 것만이 아니라, 다음 변경을 안전하게 할 수 있는 피드백 경로를 남기는 일이다.

## 핵심 답변 카드

### 자기소개와 지원 동기

동시 상태 갱신, 느린 조회, 비동기 후속 처리처럼 사용자 결과에 직접 영향을 주는 문제를 다뤘다. 정합성은 트랜잭션과 잠금 범위로, 후속 작업은 재처리 가능한 경계로, 성능 문제는 실행계획과 관측으로 검증했다. 빠른 기능 실험도 운영에서 복구 가능한 구조 위에서 이뤄져야 한다는 경험을 지원 역할에서의 기여 방식으로 설명하고 싶었다.

### 의견 충돌

- 상황: 일정이 촉박한 요구사항에서 제품 요구와 안정성 위험이 충돌했다.
- 판단: 사람이나 직무를 탓하기보다 영향 범위, 실패 비용, 되돌릴 수 있는 선택지를 분리했다.
- 행동: 요구 의도를 다시 확인하고, 반드시 지켜야 할 안전 경계와 나중에 개선할 범위를 제안했다.
- 결과와 한계: 합의 가능한 작은 변경으로 진행했고, 이후 검증 항목을 남겼다. 초기 설명이 부족하면 같은 갈등이 재발할 수 있어 문서와 리뷰를 보완했다.

### 질문을 통해 결정을 바꾼 경험

- 상황: 동료가 인증 또는 API 계약의 안전성에 의문을 제기했다.
- 행동: 공식 명세, 재현 환경과 실패 경로를 확인해 기존 가정을 검증했다.
- 결과: 직감 대신 검증 가능한 근거로 결정을 수정했고, 이후에는 의문 제기를 환영하는 리뷰 기준을 만들었다.

### 짧은 이직 경험과 성장

이전의 짧은 역할에서는 한 제품을 장기 운영하며 피드백을 반영하는 경험이 부족했다. 이후에는 더 긴 운영 맥락에서 정합성, 자동화, 관측과 제품 단계까지 함께 보려는 습관을 만들었다. 이 경험은 이전 조직을 평가하기 위한 것이 아니라, 내가 바꾼 판단 방식과 다음 역할에서 확인할 기준을 설명하기 위한 것이다.

### 회고와 팀 기여

- 회고는 감상이 아니라 다음 행동을 정하는 과정으로 본다.
- 반복된 문제는 원인, 검증 방법, 소유자와 기한이 있는 후속 행동으로 남긴다.
- 기술 발표, 멘토링, 리뷰를 통해 개인의 해결을 팀이 재사용할 수 있는 기준으로 바꾼다.
- 공식 리더가 아니어도 병합 기준과 피드백 방식을 팀 합의로 만들며 기여할 수 있다.

## 주의

- 특정 조직의 인재상이나 내부 발언을 일반화하지 않는다.
- 다른 후보의 상태나 전형 결과의 원인을 추측하지 않는다. 이 전형의 사실로 확인된 일정과 결과는 기록하고, 개인 처우 금액은 제외한다.
- 확실하지 않은 사실은 면접에서 확인할 질문으로 남긴다.
