## 2. 인성/소프트스킬 예상 질문

### 자기소개

> 구조: 이름과 역할, 핵심 경험, 일하는 방식, 지원 동기

안녕하세요, 백엔드 개발자 [이름]입니다.

동시 상태 갱신, 비동기 처리와 느린 조회처럼 사용자 결과에 직접 영향을 주는 문제를 다뤘습니다. 정합성에는 트랜잭션과 잠금 범위를 두고, 후속 작업은 재처리 가능한 경계로 분리했으며, 조회와 장애 징후는 실행계획과 관측으로 검증했습니다.

저는 문제를 발견하면 관성으로 넘기지 않고 원인을 확인하는 편입니다. 동시에 혼자 해결하는 것보다 팀과 함께 해결해 나가는 것을 중요하게 생각합니다. 작은 단위로 바꾸고 검증하는 방식이 제 일하는 방식과 맞는지 면접에서 상호 확인하고 싶었습니다.

### 왜 액션파워인가? (2차 버전)

- 당시 공개 공고의 제품 문제와 역할 설명을 중심으로 지원 동기를 설명한다.
- AI 기능을 제품 흐름에 연결할 때 기능 실험뿐 아니라 안정성, 복구와 운영 기준이 중요하다는 점에 공감했다.
- 변경을 작은 단위로 검증하고 기록하는 방식이 역할에 기여할 수 있다고 판단했다.
- 기술 발표, 멘토링과 문제 해결 기록을 통해 지식 공유에 기여해 온 경험을 설명한다.

### 이직 사유 (2차 버전 — 방어적이지 않게)

- 새 기능 도입, 검증, 안정화와 관측의 판단 기준을 쌓으며 충분히 성장
- 다음 성장 단계에서는 제품 피드백을 더 가까이 보고 개선 역량을 키우고 싶었다.
- 이전의 정합성, 운영 안정성과 협업 경험은 도메인이 달라져도 계속 활용할 수 있다.
- 꼬리 질문에는 이직 기준이 속도만이 아니라 책임질 문제, 성장 기회와 장기 기여 가능성이라고 답한다.

### 이전 회사 퇴사 사유

**초기 이직 경험**: 프로젝트 단위 개발이라 한 서비스를 장기적으로 개선하는 경험을 쌓기 어려워 제품 중심 조직으로 이직을 결심했다.
- 꼬리: "너무 빠른 결정 아닌가?" → 충분히 배우고 검토했지만 방향이 맞지 않는다는 판단이었고, 이후에는 장기 운영 경험을 통해 판단 방식을 보완했다.

**조직 변화 경험**: 인증과 외부 연동을 맡았지만, 당시에는 기술 결정과 제품의 장기 운영, 사업 검증을 함께 보는 관점이 부족했다. 조직 변화가 생긴 뒤 그 한계를 인식했고, 이후에는 운영 자동화, 관측, 데이터 정합성과 사업 단계까지 함께 판단하는 습관을 쌓았다.
- 꼬리: "개인 역량 부족?" → 권고사직이라는 사실은 그대로 설명하되 평가를 방어하지 않는다. 당시 내가 충분히 보지 못한 점, 배운 점, 이후 실제로 바꾼 행동 순서로 답한다.

### 장단점

- **장점: 실행력**. 문제를 발견하면 공식 문서, 재현과 검증으로 원인을 좁히고, 필요한 품질 경계와 관측을 빠르게 제안한다.
- **단점: 실행 판단이 빠른 만큼 성급할 때가 있음**. 충분히 검토하기 전에 움직이는 경향
- 개선: 중요한 결정 전 "이게 정말 최선인가?" 한 번 더 생각. 급할수록 우선순위 먼저 정리. 실행 전 검증 단계를 의식적으로 추가

### 동료 갈등 경험 / 같이 일하기 힘든 동료

- 기술만 잘하는데 협업 안 되는 사람, 커뮤니케이션은 좋은데 실력이 따라오지 않는 사람, 책임을 회피하는 사람 — **기술, 커뮤니케이션, 책임감의 균형**이 중요
- 개별 대화의 발언이나 분위기는 공개 문서에 기록하지 않는다.
- 꼬리:
  - "그런 동료와 일하게 되면?" → 직접 대화로 해결 시도. 구체적 사실 기반으로 피드백 ("이 부분이 이렇게 되면 팀에 이런 영향이 있다"). 개인 성향 비난 아님
  - "그래도 안 바뀌면?" → 팀의 그라운드 룰로 해결한다. 일하는 방식의 기준이 있으면 개인 감정이 아니라 팀 합의로 문제를 풀 수 있다.

### 소통 방식

- **기획자**: 기획 의도를 먼저 물어보고 이해 확인. 기술 용어는 풀어서 설명. "이런 게 가능하다"를 알려줌
- **프론트엔드**: API 문서를 자세하게 작성 (Request/Response 예시, 에러 케이스). "문서가 곧 소통". 에러 처리 방식 통일
- **백엔드 동료**: 의견 충돌은 감정이 아닌 논리로. 근거 기반 검증 후 함께 해결
- 비개발자에게 기술 설명: 개념 먼저 → 예시 → 비유 순서. 상대의 역할과 맥락에 맞춰 핵심 판단을 설명한다.

### 성장 목표

**장기 목표**: 개발 리드. 코드를 잘 짜는 것을 넘어 팀의 기술 방향을 제시하고 주니어 성장을 돕는 역할
- Staff Engineer 지향 — 코드 직접 짜면서 팀 기술 방향 제시 + 멘토링

**최종 목표**: 기술 조직을 이끄는 리더. 기술적 깊이, 팀 리드, 더 큰 조직에의 기여를 순서대로 쌓는다.
- 꼬리: "회사 이용만 하고 나가겠네?" → CTO가 될 만한 사람으로 성장하고 싶은 것. 함께 성장 가능하면 오래 함께할 것
- **"권한"이 아니라 "영향력"과 "기여의 크기"로 표현**

### 함께 성장하는 개발 문화를 어떻게 만드는가

- "먼저 공유하는 사람"이 되기: 기술 발표, 멘토링, 트러블슈팅 노트로 판단 기준을 공유한다.
- 코드 리뷰: "이게 틀렸다"가 아니라 "왜 이렇게 했는지" 먼저 물어보고 "이런 방법도 있다" 제안
- 지식 공유가 실제로 어떻게 이뤄지는지는 면접에서 확인하고, 내 경험은 기술 발표, 멘토링과 문제 해결 기록으로 설명한다.
- 회고는 주기보다 판단과 학습을 기록하는 방식이 중요하며, **기록으로 남기는 습관**을 통해 같은 실수의 반복을 방지

### 어떻게 회고하고 어떻게 성장하는가

> [[Retrospective-Methods|회고 기법]] — 개인과 팀의 학습 방식을 설명하는 핵심 질문

- **회고 없는 깨달음은 자기만족** — "오늘 당장 뭘 할 건가"로 구체화되지 않으면 같은 실수가 반복됨
- 상황별로 다른 프레임을 사용:
  - **주간 단위**: KPT (Keep / Problem / Try) — 문제 정의 단계가 명시되어 있어 원인 분석에 강함
  - **스프린트/릴리즈 직후**: CSS (Continue / Stop / Start) — 액션 아이템 즉시 도출
  - **프로젝트 중간 점검**: 4L (Liked / Learned / Lacked / Longed For) — 감정, 니즈까지 포함
  - **분기/연간 커리어 재설정**: WIW (What I want — 한 일/배운 것/해야 할 것)
  - **매일 학습 기록**: TIL (Event / Emotion / Learning / Action)
- 실제 적용 사례:
  - 회고에서 반복되는 ORM 문제를 원인과 검증 방법으로 정리해 재발을 줄였다.
  - 분기 회고에서 제품 피드백을 더 가까이 보고 싶다는 인식을 다음 역할의 선택 기준으로 바꿨다.
- **회고의 5가지 공통 원칙**: 구체적 행동으로 끝낼 것 / 정직할 것 / 기록으로 남길 것 / 타인 피드백 포함 / 행동→피드백→조정 루프
- 팀의 회고 리듬과 그라운드룰은 실제 운영 방식을 확인한 뒤 맞춘다.

- 꼬리:
  - "회고가 형식적으로 끝나는 경우는 없었나?" → 있었다. 그래서 회고 끝에 반드시 **"이번 주에 누가 무엇을 한다"**까지 적게 함. 액션 아이템에 담당자와 데드라인이 없으면 회고는 의미가 없음
  - "혼자 회고할 때는 어떻게?" → 주간 KPT를 노트에 기록. 분기말에는 WIW로 커리어 방향 점검. 면접 직전에도 WIW로 자기 객관화

### 리더십 발휘 경험

> 공식 리더가 아니어도 가능 — 의사결정 과정 + 팀원 설득 + 결과 책임의 3박자

- **리더십 사례의 답변 원칙**:
  - 일정 압박 속에서도 팀원의 규격과 안전성에 대한 의문을 먼저 검증하고, 근거에 따라 결정을 책임진다.
  - 사후에는 어떤 질문이 판단을 바꿨는지 공유해 다음 의문 제기도 환영받는 분위기를 만든다.
- 공식 리더 여부와 관계없이 코드 리뷰와 병합 조건을 팀 합의로 정리해, 개인 감정이 아니라 팀 기준으로 충돌을 푼다.
- 리더십 철학: **서번트 리더십** — 팀원의 장애물을 제거하고 방향을 제시하는 역할. 권한이 아니라 영향력으로 표현
- 꼬리:
  - "공식 리더가 아닌데 어떻게 팀원을 설득했나?" → 권한이 없을 때일수록 **데이터와 근거**가 중요하다. 반복되는 실패의 유형과 검증 공백을 함께 확인해 기준을 제안한다.
  - "갈등이 있을 때 리더로서 어떻게 결정했나?" → 결정권자가 결정하되, 결정 전까지는 모든 의견이 동등하게 들리는 자리를 만드는 것이 리더의 역할

### 소규모 팀 리드를 가정한다면, 팀 성장을 어떻게 도모하시겠습니까?

> 시니어로 가는 길에 대한 고민을 보는 질문

1. **기술 성장**: 코드 리뷰 문화, 정기 스터디(예: Node.js Design Patterns), RFC 문화로 큰 결정의 맥락을 문서화, 기술 부채 우선순위화
2. **업무 성장**: 1on1으로 개인 목표와 팀 목표 정렬, 회고를 정기 리듬으로 (주간 KPT + 분기 WIW), 성과를 정량으로 측정
3. **심리적 안전감**: 실패를 비난 없이 기록, 공유(blameless postmortem), 질문을 환영하는 분위기, "모르겠다"를 말할 수 있는 문화
4. **자율성과 책임**: 작은 의사결정은 팀원에게 위임, 작은 성공 경험을 누적, **자기 조직화** 지향
5. **리더의 역할**: 외부 노이즈 차단(unblock), 방향 제시, 팀의 시간을 지켜주는 것
- 공식 리더 여부와 관계없이 코드 리뷰 기준과 병합 조건을 팀 합의로 정리하는 방식을 설명한다.
- 꼬리:
  - "소규모 팀이면 1on1이 부담스럽지 않나?" → 정기적인 짧은 대화면 충분하다. 길이보다 **꾸준함**이 중요
  - "성과가 안 나오는 팀원은?" → 비난이 아니라 **시스템 점검**이 먼저. 작업 분배가 잘못됐는지, 컨텍스트 공유가 부족했는지, 학습 여건이 부족한지 — 회고와 1on1으로 원인부터 분리
