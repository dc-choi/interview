### 관측성 설계 — 무엇을 모니터링하고 알림 기준은 어떻게 정하나?
> 관련: [[Incident-Detection-Logging|장애탐지, 로깅]], [[Structured-Logging|구조화로깅]], [[Log-Pipeline|로그파이프라인]]

**본인 경험 요약**
- 문제: 장애나 느린 요청이 발생했을 때 사용자 영향, 애플리케이션 원인과 외부 의존성 문제를 빠르게 연결할 기준이 필요했다.
- 판단과 행동: 구조화 로그와 제한된 메트릭 라벨을 `x-request-id`로 연결하고, 경보는 사용자 영향과 대응 가능성을 기준으로 설계했다. 분산 추적 파이프라인은 당시 적용 사실이 아니다.
- 결과와 한계: 원인을 좁히는 공통 언어를 만들었지만, 경보의 효과는 기준선, 관측 기간과 실제 대응 기록으로 계속 검증해야 한다.

**설계 원칙**
- 당시에는 `x-request-id`로 로그를 요청 단위로 연결했다. 분산 추적을 추가한다면 로그, 메트릭과 트레이스를 같은 요청 문맥으로 연결하되, 고유 식별자는 메트릭 라벨이 아니라 로그 본문과 트레이스 연결에 사용한다.
- 도구 선택은 사용자 영향, 질의와 경보 요구, 운영 인력, 보존과 복구 요구를 비교해 결정한다.
- 관리형과 자체 운영 방식의 총소유비용은 사용량뿐 아니라 유지보수와 장애 대응 부담까지 포함해 평가한다.

**관측 구성의 책임 분리**
- 애플리케이션은 구조화 로그, 사용자 영향에 연결되는 메트릭과 상관관계 ID를 남긴다.
- 수집 계층은 전송 실패가 요청 처리에 영향을 주지 않게 격리한다.
- 저장소와 조회 계층은 탐색, 집계, 보존과 복원 요구에 맞춰 선택한다.
- 경보 계층은 현재 상태와 장기 추세를 함께 보고, 사용자 영향 SLI를 기준으로 알림을 만든다.

**경보 설계 원칙**
- 에러율과 지연은 사용자 영향 SLI와 정상 구간의 관측값을 바탕으로 정한다.
- SQL 지연, event loop, DB 포화와 복제 지연은 별도 지표로 관측한다.
- 내부 임계값과 지속 시간은 공개하지 않는다.

**보존 전략**
- 로그와 메트릭의 보존 정책은 비용, 복구 요구와 사용량을 기준으로 설계한다.
- 로그 폭증 시에는 수집 단위, 샘플링과 불필요 필드 제거를 조정하고, 선택한 수집기의 지원 설정을 확인한다.

**비용 관리**
- 메트릭 카디널리티 관리가 핵심이다. route/path 라벨을 정규화하고 **userId/traceId를 라벨에 포함하지 않는다**.
- 로그는 구조화된 형식으로 남기고 불필요 필드를 줄여 저장과 전송 부담을 관리한다.
- 저장소 사용량, 활성 시계열과 수집량을 정기적으로 관측한다.

**리스크 및 대응**

| 리스크 | 대응 |
| --- | --- |
| 카디널리티 폭발 | 라벨 가이드 수립, route 정규화, 고유 식별자 라벨 금지 |
| 로그 과다 유입 | 수집 단위, 샘플링과 필드 정리 |
| 구성 복잡성 증가 | 팀이 유지할 수 있는 도구 수와 배포 경계를 먼저 제한 |

**꼬리 질문 대비**
- "관리형 대신 자체 운영을 택하는 기준은?" → 질의와 경보 기능, 이식성, 운영 인력과 총소유비용을 비교한다. 현재 팀이 운영할 수 있는 범위를 넘기지 않는 것이 전제다.
- "로그 저장소 선택 기준은?" → 검색, 집계, 인덱싱, 보존과 복원 요구를 먼저 정하고 그에 맞는 저장소를 고른다.
- "pull 방식의 한계는?" → 짧은 수명 작업은 수집 전에 사라질 수 있다. 작업 성격에 따라 push 경로나 별도 수집 방식을 제한적으로 검토한다.
- "로그 양이 폭증하면?" → 수집 단위와 샘플링을 조정하고 불필요 필드를 제거한다. 저장 경계와 보존 정책은 실제 구성에서 확인한다.
- "고유 ID를 라벨에 넣으면 왜 안 되나?" → 고유값을 라벨에 넣으면 카디널리티가 요청 수만큼 늘어 메모리를 고갈시킬 수 있다. 로그 본문과 트레이스 연결에 사용한다.
- "프런트엔드 관측은?" → 브라우저 오류와 사용자 체감 지연을 수집하고, 전체 요청 흐름이 필요하면 trace context 전파와 양쪽 계측을 함께 설계한다.
