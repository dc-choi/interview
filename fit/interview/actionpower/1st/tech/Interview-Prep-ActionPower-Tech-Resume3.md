### 서비스 확장과 비동기 분리 — 왜? 어떤 문제가 있었나?
> 관련: [[Load-Balancer|로드밸런서]], [[Docker|Docker]], [[Messaging-Patterns|메시징패턴]]

**본인 경험 요약**
- 문제: 한 실행 환경에 요청 경로와 후속 작업이 집중돼 변경 위험과 장애 영향이 커질 수 있었다.
- 판단과 행동: 컨테이너화와 요청 경계 분리, 핵심 상태와 후속 작업의 비동기 분리, 단계별 검증과 롤백 경로를 함께 준비했다.
- 결과와 한계: 변경 단위와 장애 격리의 기준은 명확해졌지만, 실제 확장 효과는 트래픽, 큐 적체와 운영 기간을 함께 보며 검증해야 한다.

**문제 인식**
- 하나의 실행 환경에 서로 다른 요청 경로가 몰리면 포화와 장애가 함께 전파될 수 있다.
- 배포와 복구가 단일 실행 환경에 묶이면 변경 위험과 중단 범위가 커진다.
- 상태 변경 뒤의 외부 호출을 동기 요청에 묶으면 지연과 실패가 사용자 흐름까지 전파된다.

**왜 이벤트 기반 아키텍처가 답인가**
- 상태 변경은 핵심 트랜잭션에서 확정하고, 독립적인 후속 작업은 이벤트로 분리한다.
- 소비자는 멱등성 키와 상태 전이를 사용해 중복 전달을 정상 경로로 다루고, 영구 오류와 일시 오류에는 다른 복구 경로를 둔다.
- 이 구조는 실패 격리, 독립 확장, 새 후속 작업 추가와 재처리 경로를 분명하게 만든다.

**적용 역량**
- 컨테이너화, 트래픽 분리와 안전한 배포 방식을 사용해 실행 환경의 변경 위험을 낮춘다.
- 비동기 워커에는 동시성 예산, 재시도, DLQ와 관측을 함께 설계한다.
- 읽기와 쓰기 특성이 다를 때는 일관성 요구와 복제 지연을 확인한 뒤 읽기 경로 분리를 검토한다.

**꼬리 질문 대비**
- "한 번에 전환하나?" → 변경 단위를 나누고 각 단계에서 기능, 실패 경로와 롤백을 확인한 뒤 다음 단계로 간다.
- "로드밸런서 선택 기준은?" → 애플리케이션 계층 라우팅이 필요한지, 전송 계층 특성이 필요한지, 연결 방식과 장애 복구 요구를 기준으로 비교한다.
- "Rolling Update vs Blue/Green?" → Rolling은 자원을 절약하지만 구버전과 신버전이 공존한다. Blue/Green은 빠른 전환과 롤백이 가능하지만 별도 환경 비용이 든다.
- "오토스케일링 기준은?" → API와 워커의 포화 지표, 큐 적체, 허용 지연과 처리 시간을 함께 보며 정한다.
- "동기에서 비동기로 바꿀 때 핵심은?" → 하나의 트랜잭션으로 묶이던 부수 효과를 분리하더라도 상태 정합성이 깨지지 않게 멱등성, 재시도와 최종 실패 처리를 함께 설계한다.
- "이벤트 유실은 어떻게 막나?" → 실제 적용에서는 EventBridge와 SQS로 후속 처리를 분리하고, 소비자 멱등성, 제한 재시도, DLQ와 수동 확인으로 실패를 다뤘다. Transactional Outbox는 당시 적용하지 않아 DB 커밋과 이벤트 발행 사이의 누락 가능성이 남았다. 지금 보강한다면 상태 변경과 outbox 기록을 같은 트랜잭션으로 묶고 relay가 재발행하게 한다. CDC는 지연과 운영 복잡성을 비교해 별도로 검토한다.
- "복제 지연은?" → 쓰기 직후 일관성이 필요한 조회는 정본에서 처리하고, 지연을 허용하는 조회만 분리된 읽기 경로를 사용한다.
- "Graceful Shutdown은?" → 종료 신호 뒤 새 작업 수신을 멈추고 진행 중 작업을 안전하게 마무리한다. 완료하지 못한 메시지는 가시성 만료 뒤 재처리되도록 설계한다.
