### 관리형 이벤트와 큐를 선택한 이유, 스트림과의 차이
> 관련: [[MQ-Kafka|MQ, Kafka]], [[Messaging-Patterns|메시징패턴]], [[Delivery-Semantics|전달보장]]

**이벤트 기반이 필요한 이유는 아키텍처 전환 섹션 참고** — 핵심은 상태 변경과 후속 처리(부수 효과)를 분리하여 실패 격리, 독립 확장과 복구 가능한 구조를 만드는 것이다.

**본인 경험 요약**
- 문제: 핵심 업무 상태 변경 뒤의 알림과 외부 연동을 한 요청에 묶으면 지연과 실패가 사용자 흐름까지 전파될 수 있었다.
- 판단과 행동: 핵심 상태를 먼저 확정하고, 관리형 이벤트와 큐를 통해 후속 작업을 분리했다. 소비자에는 처리 키, 상태 전이, 제한 재시도와 최종 실패 확인 경로를 뒀다.
- 결과와 한계: 실패 격리와 재처리 가능성을 높였지만, 비동기 경계는 발행 누락과 중복을 숨길 수 있어 관측과 복구 훈련이 필요하다.

**도구를 고른 판단 기준**
- 관리형 큐와 브로커 기반 구성을 전달 보장, 순서, 리플레이 요구와 운영 부담으로 비교한다.
- 실시간 처리가 필수가 아니고 최종 일관성이 허용되는 후속 작업에는 관리형 큐가 적합할 수 있다.
- 이벤트는 독립 워커가 처리하도록 분리해 실패 격리와 개별 재시도를 가능하게 한다.
- 영구 오류와 일시 오류를 구분해 DLQ, 알림과 수동 확인 경로를 설계한다.
- 이벤트 리플레이, 강한 순서 보장이나 지속적인 고처리량이 핵심이면 브로커 기반 대안을 비교한다.
- 꼬리:
  - 큐 메시지 유실 가능성: 일반적으로 at-least-once 전달을 전제로 소비자가 중복을 정상 경로로 다뤄야 한다. 멱등성 키와 상태 전이를 두고, 처리 성공 뒤에만 완료 처리한다.
  - 서버리스 소비자와 상시 워커: 전자는 불규칙한 작업에, 후자는 연결 수 제어나 기존 실행 환경과의 결합이 필요한 작업에 유리할 수 있다. 동시성, 연결 예산, 배포 경계와 장애 복구를 비교한다.
  - 가시성 시간 제한: 소비자가 가져간 메시지를 일정 시간 안에 완료하지 않으면 다시 처리할 수 있게 하는 경계다. 실제 처리 시간보다 넉넉하게 잡고 중복을 고려한다.
  - 순서 보장: 순서가 정말 필요한지 먼저 판단하고, 필요하다면 그룹 단위 큐나 파티션 기반 스트림을 검토한다. 한도는 공식 문서에서 확인한다.
  - 팬아웃과 작업 큐: 여러 소비자가 같은 이벤트를 각자 받아야 하면 토픽 기반 팬아웃, 한 작업을 한 소비자가 처리하면 큐 기반 분배를 검토한다.

### Docker 이미지 경량화 방법?
> 관련: [[Multi-Stage-Build|멀티스테이지빌드]]

- 본인 경험에서는 빌드 결과물에 불필요한 의존성이 포함돼 이미지와 배포 부담이 커질 수 있음을 확인했다.
- .dockerignore로 불필요 파일 제외 + 멀티스테이지 빌드(build stage → production stage에 필요 파일만 복사)
- 멀티스테이지 빌드와 불필요한 파일 제외로 이미지와 배포 부담을 줄인다.
- 레지스트리 저장 사용량도 배포 비용 검토에 포함한다.
- 결과는 배포와 저장 부담을 줄이는 방향이었지만, 경량화보다 런타임 호환성과 문제 재현 가능성을 우선 확인했다.
- 꼬리:
  - "alpine 이미지로 더 줄일 수 있지 않나?" → 가능하지만 native 모듈(bcrypt, sharp 등) 호환성 문제 발생 가능. musl libc vs glibc 차이. 안정성과 경량화의 트레이드오프
  - "distroless 이미지는?" → Google이 제공하는 최소 런타임 이미지. 셸이 없어 보안 강화되지만 디버깅이 어려움. 프로덕션에 적합
  - "더 최적화할 수 있는 방법?" → node_modules 대신 번들러(esbuild) 사용, 불필요한 devDependencies 제거 확인, Docker layer 캐싱 최적화(자주 변경되는 레이어를 뒤에 배치)
