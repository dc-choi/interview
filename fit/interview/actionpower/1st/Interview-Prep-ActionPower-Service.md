## 3-3. 서비스 맥락 예상 질문

아래는 당시 공고에서 읽은 AI 기능과 백엔드 역할을 바탕으로 만든 가정형 질문이다. 실제 제품 구조나 내부 기술 선택을 주장하지 않는다.

### 대량의 음성 또는 문서 처리 요청이 동시에 오면 어떻게 설계할까?

- 음성 인식이나 문서 변환은 처리 시간이 길 수 있으므로 동기 요청으로 끝내지 않는다.
- 요청 접수, 작업 식별자 반환, 큐 발행, 워커 처리, 완료 알림으로 경계를 나눈다.
- 큐 적체, 워커 동시성 및 허용 대기 시간을 함께 관측해 처리량을 제어하고 워커 과부하를 막는다.
- 유사한 처리 원칙: 상태 변경 뒤의 작업을 큐로 분리하고, 워커가 중단돼도 메시지가 재처리되도록 멱등성과 실패 경로를 둔다.

**대용량 파일 업로드와 스트리밍 처리**
- 파일 전체를 메모리에 올리면 프로세스가 포화될 수 있으므로, 스트림 단위로 수신하고 저장한다.
- Node.js Stream으로 chunk 단위 처리:
  - 클라이언트 → API 서버: `multipart/form-data`를 busboy처럼 `Readable`을 노출하는 파서로 스트리밍 수신
  - API 서버 → 오브젝트 스토리지: 수신하면서 동시에 `stream.pipeline()`으로 업로드하고 오류를 호출자에게 전파
  - 메모리 사용량: 파일 전체를 적재하지 않고 각 스트림 버퍼와 처리 중인 청크만 유지. 전체 사용량은 스트림 단계 수, `highWaterMark`와 라이브러리 버퍼에 따라 달라짐
- **백프레셔(Backpressure)**: 소비자의 `write()`가 `false`를 반환하면 읽기를 멈추고 `drain` 뒤 재개합니다. `pipeline()`과 `pipe()`가 이 흐름 제어를 연결하지만, 오류 전파와 정리는 `pipeline()`이 더 안전합니다.
- Presigned URL 패턴: 대용량 파일은 API 서버를 경유하지 않고, 서버가 제한된 업로드 권한을 발급한 뒤 클라이언트가 저장소에 직접 업로드한다. 완료 이벤트가 후속 처리를 시작한다.

**답변 연결**: 비동기 워커의 재처리, 스트리밍 수신의 메모리 경계, 멱등성과 실패 복구라는 원칙으로 설명한다.

**꼬리:**
- 큐가 밀리면: 워커 동시성, 큐 적체와 허용 대기 시간을 관측해 확장하고, 사용자에게 처리 상태를 알린다.
- 결과 저장: 대용량 원본은 객체 저장소, 구조화된 결과와 상태는 데이터 저장소에 두는 방식을 검토한다.
- 동시 요청 제한: 게이트웨이 또는 애플리케이션 경계에서 사용자별 제한과 재시도 안내를 설계한다.
- 업로드 권한의 보안: 짧은 만료, 제한된 객체 경로와 크기, 완료 뒤 실제 포맷 검증을 둔다.
- 연결 중단: 재개 가능한 업로드와 미완료 업로드 정리 정책을 확인한다.

### 외부 AI API 호출의 타임아웃, 재시도와 비용은 어떻게 다룰까?

- 외부 API는 불안정함이 전제
- 타임아웃: 연결과 응답 시간 제한을 나누고, 제공자의 처리 특성, 사용자 대기 시간과 취소 가능성을 반영한다.
- 재시도: 지수 백오프와 지터로 동시 재시도를 분산하고, 횟수는 오류 종류와 허용 지연을 기준으로 제한한다.
- Circuit Breaker: 연속 실패 N회 시 일정 시간 요청 차단 → half-open에서 단건 테스트 → 복구 확인
- 실패 격리: DLQ에 실패 메시지 보관, 수동 재처리 or 알림
- 영구 오류는 재시도하지 않고 확인 대상으로 분류하며, 일시 오류만 제한적으로 재시도한다. 최종 실패는 DLQ, 알림과 수동 확인 경로로 처리한다.
- 비용: 요청 단위 사용량을 관측하고, 제한, 예산 경보와 대체 경로를 제품 정책에 맞게 둔다.
- 꼬리:
  - 회로 차단 상태는 단일 프로세스인지 분산 환경인지에 따라 보관 위치와 공유 방식을 정한다.
  - 폴백은 대체 제공자, 마지막 정상 결과, 지연 안내 중 제품 안전성에 맞는 것을 선택한다.
  - 지터는 같은 시점의 재시도 폭주를 분산한다.

### 오래 걸리는 작업의 상태는 어떻게 관리할까?

- Job 테이블 설계: id, type, status(pending→processing→done/failed), progress(%), created_at, updated_at, error_message
- 상태 알림:
  - 폴링 — 간단하지만 불필요한 요청 많음
  - SSE — 서버에서 클라이언트로 상태를 알릴 때 HTTP 기반으로 단순
  - WebSocket — 양방향 상호작용이 필요할 때 유리하지만 커넥션 관리 필요
  - 허용 지연이 크면 폴링으로 시작할 수 있고, 실시간성, 연결 수와 양방향 요구를 기준으로 SSE 또는 WebSocket을 고른다. 트래픽 증가만으로 전환을 결정하지 않는다.
- 멱등성 키로 동일 작업 중복 생성 방지(사용자 실수로 여러 번 클릭)
- 정기 작업도 재시도, 상태 관리와 멱등성으로 중복 실행을 방지한다.
- 꼬리:
- "processing 중 서버가 죽으면?" → 작업 시도마다 lease 또는 heartbeat와 소유자 토큰을 두고, 만료한 소유자만 원자적으로 회수한다. 아직 실행 중인 작업을 단순히 failed로 바꾸면 중복 실행될 수 있으므로 완료 갱신 때도 같은 소유자 토큰을 확인한다.
  - "폴링 vs WebSocket vs SSE?" → 폴링(구현 간단, 불필요 요청), WebSocket(양방향, 커넥션 관리 복잡), SSE(서버→클라이언트 단방향, HTTP 기반으로 간단). 진행률 알림은 서버→클라이언트 단방향이니 SSE도 좋은 선택
- "멱등성 키 구현은?" → 클라이언트가 UUID를 요청 헤더에 포함하고, 서버는 사용자와 요청 경로, 키, 요청 본문 해시 및 결과 상태를 함께 저장한다. 같은 키와 같은 요청은 기존 결과를 반환하고, 본문이 다르면 충돌로 처리한다. TTL은 업무 보존 기간과 재시도 창을 확인한 뒤 정한다.

### 여러 고객 조직의 데이터를 다뤄야 한다면?

- 3가지 접근:
  1. 논리적 격리(tenant_id 컬럼) — 구현 간단, 비용 낮음, 쿼리마다 WHERE 조건 필수
  2. 스키마 분리(테넌트별 스키마) — 격리 강화, 마이그레이션 복잡
  3. 물리적 분리(테넌트별 DB) — 더 강한 격리와 더 큰 운영 비용
- 초기에는 논리적 격리를 검토하되, 실제 보안과 성능 요구에 따라 격리 수준을 정한다.
  - 저장소 경계에서 고객 식별 조건을 일관되게 구성한다.
  - 데이터베이스가 지원한다면 행 수준 보안처럼 조건 누락을 줄이는 방어층도 검토한다.
- 테넌트별 요구는 모듈 경계에서 분리하고, 핵심 도메인 규칙은 공유한다.
- 꼬리:
  - "논리적 격리의 단점?" → 한 테넌트의 대량 쿼리가 다른 테넌트에 영향(noisy neighbor)을 줄 수 있다. 테넌트 범위로 자주 조회하는 경로는 `tenant_id`를 인덱스와 함께 검토한다.
  - "noisy neighbor 어떻게 대응?" → 테넌트별 rate limiting, 쿼리 리소스 제한(커넥션 풀 분리)과 임계치 알림을 검토한다. 궁극적으로는 특정 고객은 스키마나 DB 분리를 검토한다.
  - "논리적 → 물리적 격리로 전환 시점?" → 보안/컴플라이언스 요구(고객 데이터 완전 분리 필요), 성능 격리 필요(한 테넌트의 부하가 다른 테넌트에 영향), 운영 요구가 물리적 격리를 필요로 할 때

### 서비스 장애 시 어떻게 대응?

1. 경보는 사용자 영향 SLI와 정상 구간의 관측값을 바탕으로 설정한다.
2. 대시보드와 상관관계 ID로 영향 범위를 좁히고, route와 status를 집계한 메트릭에서 영향을 받는 API를 확인한다.
3. 데이터 정합성 위험이 크면 롤백을 우선하고, 범위가 제한된 로직 오류는 핫픽스를 비교한다.
4. 로그, 메트릭과 실행계획을 교차 확인해 근본 원인을 좁힌다.
5. 경보, 테스트와 배포 게이트를 보강하고 포스트모템으로 재발 방지 항목을 남긴다.
- 꼬리:
  - "장애 등급을 어떻게 나누나?" → 예를 들어 P1(서비스 전체 중단), P2(주요 기능 장애), P3(일부 사용자 영향), P4(성능 저하)처럼 사용자 영향과 복구 긴급도로 나누고, 실제 등급과 대응 목표는 조직의 운영 정책에 맞춘다.
  - "포스트모템에 뭘 쓰나?" → 타임라인(발생→감지→대응→복구), 근본 원인, 영향 범위, 재발 방지 액션 아이템. 비난 없는 문화(blameless postmortem)가 핵심
  - "장애를 미리 방지하는 방법?" → 당시에는 정적 임계 경보로 조기 감지했다. 사용자 영향 SLI와 목표 기간을 합의하면 multi-window, multi-burn-rate SLO 경보는 후속 개선안으로 검토한다. 카나리 배포, 로드 테스트와 코드 리뷰, 테스트 게이트도 함께 사용한다.

- [ ] **추가**: "빠르게 변화하는 AI 기술을 어떻게 따라가나?"
  - **원칙**: 기술 자체를 쫓는 게 아니라, **"이 단계의 서비스에 필요한가?"**로 판단
  - **정보 수집**: AI 관련 기술 블로그(OpenAI, Google AI, Anthropic), Hacker News, 커뮤니티 디스커션을 주기적으로 확인. 새 모델/API가 나오면 **비용, 레이턴시, 정확도** 3가지 축으로 빠르게 평가
  - **검증 프로세스**: 관심 기술은 작은 프로토타입으로 검증하고 기존 시스템 대비 관측 결과를 바탕으로 도입 여부를 판단한다. 과거 비용 산정값과 처리량은 공개하지 않는다.
  - **커뮤니티 활동**: 기술 주제를 발표하고 멘토링하며, 질문과 피드백으로 관점을 넓혔다. 참여 규모는 공개하지 않는다.
  - **백엔드 엔지니어로서의 포지셔닝**: AI 모델 자체를 개발하는 게 아니라, AI를 **안정적으로 서빙하는 인프라**가 역할. 새 AI 기술이 나와도 큐+워커, 타임아웃/재시도, 비용 관리 같은 서빙 패턴은 공통 → 이 패턴을 탄탄히 갖추면 어떤 AI 기술이든 빠르게 통합 가능
  - 꼬리:
    - "최근 관심 있는 기술은?" → AI 도구가 외부 시스템과 연결될 때 권한 경계, 입력 검증, 감사 로그를 설계하는 방법에 관심이 있다.
    - "기술 도입 실패 경험은?" → 모든 기술 도입이 성공하진 않음. 중요한 건 **빠르게 실패하고 빠르게 되돌리는 것**. 프로토타입 단계에서 걸러내면 프로덕션 리스크 최소화

## 역질문

### 기술과 아키텍처
1. 이 역할의 현재 실행 환경과 운영 제약은 무엇인가?
2. 오래 걸리는 작업은 동기와 비동기 중 어떤 경계로 나뉘는가?
3. 데이터 저장, 조회, 캐시와 ORM의 주요 선택지는 무엇인가?
4. 현재 가장 크게 투자하고 있는 신뢰성 또는 성능 문제는 무엇인가?

### 팀/조직
5. 팀의 역할 분담과 백엔드 책임 경계는 어떻게 되는가?
6. 코드 리뷰, 배포와 장애 대응은 어떻게 운영되는가?
7. 현재 팀에서 우선순위가 높은 기술 부채 또는 운영 문제는 무엇인가?

### 성장/기대치
8. 새 구성원이 맡을 초기 문제와 학습 지원 방식은 무엇인가?
9. 제품과 고객 요구 변화가 백엔드 팀의 우선순위에 어떤 영향을 주는가?
10. 역할의 평가 기준과 지원 체계는 무엇인가?
