# 올세일, 경험과 FIT 12문항

지원 전 예상 1차 대비다. 실제 차수/형식/일정은 미정이며 아래 질문은 예상 질문이다. 경험 7개, FIT 5개로 구성했다. 결론을 먼저 말하고 본인 역할, 대안, 검증과 한계를 붙인다. 회사 연결은 공개 JD의 외부 데이터 연동, SaaS, 반복 업무 개선에만 둔다.

## 이력서 기반 7문항

### E1. 동시 재고 갱신에 왜 DB 잠금을 선택했나요?

- **의도**: 실제 경쟁 조건, 불변식과 선택 이유를 확인한다.
- **핵심 답변**: 같은 재고 상태를 동시에 갱신하는 경로에서 충돌을 늦게 발견하고 작업을 다시 하는 비용보다 짧은 직렬화가 단순하다고 판단했습니다. `FOR UPDATE NOWAIT`로 잠금 실패를 드러내고 제한 재시도를 뒀습니다. 불변식에 쓰는 가변 값은 잠금 뒤 다시 확인하고 상태 변경과 기록을 짧은 트랜잭션에 넣었습니다. 동시 요청을 재현해 최종 상태와 실패 뒤 재시도 결과를 확인했습니다. 올세일에서도 동시 작업이 같은 고객 데이터를 바꾸는 경계를 먼저 찾겠습니다.
- **대안/오답**: 단일 조건부 UPDATE로 표현되는 불변식은 먼저 비교한다. 충돌이 드문 편집은 version 방식도 가능하다. 잠금을 썼다는 이유로 모든 경쟁 조건이 사라졌다고 말하지 않는다. 당시 고정 재시도와 현재 백오프/지터 개선안을 구분한다.
- **꼬리**: 잠금 전 읽은 값이 바뀌면? 외부 API를 트랜잭션 안에서 호출하면? → 가변 기준값을 재검증하고 외부 호출은 잠금 밖으로 분리한다. `NOWAIT`가 모든 대기를 없애지는 않는다.
- **출처**: 제공 PDF의 VMI 경험, [[My-Tech-Cards-Data#카드 1, IoT 입력 동시 갱신 정합성, DB Lock 전략]], [[Lock]].

### E2. EventBridge/SQS를 선택했고 남은 한계는 무엇인가요?

- **의도**: 메시지 도구보다 발행/소비의 실패 경계를 이해하는지 본다.
- **핵심 답변**: 핵심 상태 변경과 느린 후속 업무를 분리해 발주 흐름을 자동화했습니다. 운영 여력과 전달 보장을 비교해 관리형 EventBridge/SQS를 선택했고 소비는 업무 키와 상태 전이로 중복을 다뤘습니다. 일시 오류만 제한 재시도하고 최종 실패는 DLQ와 확인 경로로 분리했습니다. 올세일에서는 외부 플랫폼 지연이 핵심 요청까지 묶지 않도록 작업 경계를 먼저 맞추겠습니다.
- **대안/오답**: 실제 적용은 DB 커밋 뒤 이벤트 발행의 틈이 남았습니다. Outbox는 당시 미적용 개선안입니다. 상태와 Outbox를 같은 트랜잭션에 넣어도 릴레이/소비 중복은 남습니다. Kafka 직접 운영이나 exactly-once 종단간 보장을 주장하지 않습니다.
- **꼬리**: 처리 성공 후 삭제 전에 죽으면? 순서가 필요하면? → 멱등한 재처리와 업무 키별 순서 계약을 둔다. FIFO도 외부 효과 중복을 자동 해결하지 않는다.
- **출처**: PDF, [[My-Tech-Cards-Data#카드 2, EventBridge와 SQS 비동기 처리]], [[Delivery-Semantics]], [AWS, Transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

### E3. 슬로우 쿼리 개선은 어떤 근거로 했나요?

- **의도**: 성과 귀속과 실행 계획에 따른 판단을 확인한다.
- **핵심 답변**: 최신 상태를 찾는 조회에서 후보 탐색과 정렬 비용을 확인했습니다. 업무 키 동등 조건과 시각/보조 키 정렬을 맞춘 복합 인덱스를 검토하고 쿼리 구조도 함께 조정했습니다. 개선 뒤 실제 계획과 조회 지연을 다시 확인했습니다. 인덱스가 쓰기에 더하는 비용도 결과의 일부로 봤습니다. 올세일의 데이터 조회에서도 대표 고객별 조건과 분포를 먼저 보겠습니다.
- **대안/오답**: 높은 카디널리티 컬럼을 앞에 놓는 단일 규칙으로 정하지 않는다. 캐시/복제본은 신선도와 읽기 부하 요구가 맞을 때 검토한다. 서브쿼리 시간, 쿼리 한 건과 배치 전체 시간을 같은 성과로 비교하지 않는다.
- **꼬리**: 작은 고객은 빠르고 큰 고객만 느리면? → skew가 있는 대표 파라미터별 계획/행 수/정렬을 비교한다. 계획 추정과 실제 결과 차이도 본다.
- **출처**: PDF, [[My-Tech-Cards-Data#카드 3, 실행 계획 기반의 슬로우 쿼리 개선]], [[Execution-Plan-PostgreSQL]].

### E4. Prisma 관계 조회를 어떻게 개선했나요?

- **의도**: ORM 동작을 실제 SQL과 검증으로 설명하는지 본다.
- **핵심 답변**: 관계 조회에서 SQL이 여러 번 나가는 것을 요청 추적과 쿼리 로그로 확인했습니다. 당시 MySQL 설정에서 관계 로딩 전략을 검토하고 `relationLoadStrategy: 'join'` 적용 후 생성 SQL과 계획을 확인해 필요한 경로의 왕복과 지연을 줄였습니다. 올세일의 PostgreSQL 환경에서는 같은 옵션도 SQL 형태와 비용을 다시 확인하겠습니다.
- **대안/오답**: 옵션 이름이 전통적인 SQL JOIN을 보장하지 않는다. Prisma v7 문서 기준 PostgreSQL은 LATERAL JOIN/JSON 집계, MySQL은 상관 서브쿼리다. 이는 버전 조건이며 회사 버전은 미확인이다. 단일 쿼리가 모든 데이터 분포에서 빠르다고 주장하지 않는다.
- **꼬리**: fan-out이 커지면? → 필요한 필드와 관계 범위를 줄이고 `query` 전략의 앱 병합 비용과 DB 집계 비용을 대표 데이터에서 비교한다.
- **출처**: PDF, [[My-Tech-Cards-Data#카드 4, Prisma 관계 조회와 API 지연 분석]], [[Prisma-Query-Performance]], [Prisma v7, Relation queries](https://docs.prisma.io/docs/orm/v7/prisma-client/queries/relation-queries), 2026-10-01 확인.

### E5. 관측 시스템에서 시행착오는 무엇이었나요?

- **의도**: 도구 설치 이후 운영 가능한 계측을 만들었는지 본다.
- **핵심 답변**: Grafana, Prometheus, Loki를 연결했는데 처음 요청 식별자를 메트릭 라벨에 넣어 시계열이 늘어난 경험이 있습니다. 식별자는 구조화 로그 본문으로 옮기고 메트릭은 정규화한 경로, 메서드와 상태처럼 제한된 차원으로 구성했습니다. 오류/지연의 추세에서 개별 로그로 내려가는 흐름을 만들었습니다. 올세일에서도 작업 적체와 데이터 신선도에서 원인 로그로 이어지게 하겠습니다.
- **대안/오답**: 요청/고객 ID를 라벨로 무제한 넣지 않는다. 상세 맥락을 지우는 대신 접근을 통제한 로그/추적에 둔다. 경보 임계값은 과거 숫자를 복사하지 않고 사용자 영향과 정상 구간에서 정한다.
- **꼬리**: 전체 성공률은 좋은데 한 고객은 실패하면? → 소스/업무 단위 분해가 필요하지만 라벨 조합 예산과 민감정보 경계를 함께 정한다.
- **출처**: PDF, [[My-Tech-Cards-Ops#카드 5, 관측성 설계]]의 2026-09-29 확인 경험, [[Cardinality]].

### E6. Docker/ECS 개선에서 무엇을 책임졌나요?

- **의도**: 배포 산출물과 운영 경계의 실제 기여를 확인한다.
- **핵심 답변**: 빌드와 실행 단계를 나누고 실행 이미지에는 산출물과 런타임 의존성만 남기도록 정리했습니다. 서비스 성장에 맞춰 관리형 컨테이너 배포 경로를 구성하는 경험도 했습니다. 목표는 이미지 크기뿐 아니라 재현 가능한 실행, 설정 주입, 롤백과 종료였습니다. 올세일에서도 기존 ECS/Docker 경로와 호환되는 작은 변경으로 배포 결과를 확인하겠습니다.
- **대안/오답**: Alpine이나 distroless는 네이티브 모듈과 진단 비용을 같이 검토한다. Node 서버의 런타임 의존성을 전부 없애면 안 된다. PDF와 포트폴리오의 배포시간 차이가 있어 시간 성과는 말하지 않는다.
- **꼬리**: 배포 중 워커가 종료되면? → 새 작업 수신을 중단하고 현재 작업의 완료/재전달 경계를 둔다. DB 변경은 이전/새 버전이 함께 동작할 호환성을 확인한다.
- **출처**: PDF, [[My-Tech-Cards-Ops#카드 6, 컨테이너 이미지와 배포 경로]], [[Multi-Stage-Build]], [Docker, Multi-stage builds](https://docs.docker.com/build/building/multi-stage/).

### E7. 외부 데이터 수집기를 왜 DB 큐로 바꿨나요?

- **의도**: 수집의 시간 예산과 실패를 실제로 다룬 경험을 확인한다.
- **핵심 답변**: 외부 데이터 수집에서 한 번의 실행이 길어지거나 일부 실패가 이어질 때 진행을 추적하기 어렵다는 문제를 다뤘습니다. DB 큐 기반 순환 수집으로 바꾸고 실행시간 예산, 세션 재시도와 연속 오류 중단 정책을 넣었습니다. 정상 완료만이 아니라 다음 실행으로 이어질 수 있는 흐름을 만들었습니다. 올세일에서도 연동 실패가 나도 진행과 마지막 성공을 확인할 수 있게 하겠습니다.
- **대안/오답**: DB 큐 경험을 BullMQ 운영 경험으로 바꾸지 않는다. 스키마/집합 검증과 데이터 신선도 SLO는 여기서 제안할 보강이며 전부 적용했다고 말하지 않는다. 수집 성공률과 데이터의 정확성은 다르다.
- **꼬리**: 200 응답인데 빈 결과면? → 응답 구조/값/집합을 검증하고 불완전한 목록의 부재를 삭제로 해석하지 않는다. 마지막 스냅샷 보존과 재확인 정책을 둔다.
- **출처**: PDF의 수집 재설계, [[External-Collection-Pipeline-Reliability]], [[External-API-Integration-Patterns]].

## FIT 5문항

### F1. AI로 반복 문제를 어떻게 개선했나요?

- **의도**: JD의 AI 활용을 실제 개선과 책임 경계로 설명하는지 본다.
- **핵심 답변**: 코드 생성만이 아니라 개발 흐름에 AI를 넣었습니다. 경로별 문맥 문서, 공식 자료 조회, 역할별 보안/성능 검토와 변경 파일 검사를 연결했습니다. 반복 조사와 구현은 도구에 맡겨도 요구사항, 설계 선택과 결과 채택은 제가 책임졌습니다. 올세일에서도 반복되는 운영/개발 업무를 먼저 관찰하고 검증 가능한 작은 자동화부터 적용하겠습니다.
- **오답/대가**: 코딩 도구 활용을 LLM 고객 제품의 모델 운영 경험으로 말하지 않는다. 자동 리뷰도 실행/테스트를 대신하지 않는다. 온톨로지의 미검증 평가 건수를 성과로 쓰지 않는다.
- **꼬리**: AI가 그럴듯한 오답을 주면? → 실제 호출부, 공식 문서와 실패 재현으로 확인하고 근거가 없는 부분은 채택하지 않는다.
- **출처**: PDF의 AI 협업 규약, [[My-FIT-Answers#10. AI 도구 활용 깊이 ★ (자주 받음)]].

### F2. 실패 뒤 무엇을 바꿨나요?

- **의도**: 실패 인정과 재발 방지 행동, 다음 팀의 신뢰를 본다.
- **핵심 답변**: 외부 정보를 수집하는 배치에서 오류가 늘었을 때 수동 확인에 의존하던 대응이 지속 가능하지 않다고 판단했습니다. 영향과 원인 가설을 나눠 중요한 경로부터 자동 검증과 배포 전 검사를 추가했습니다. 이후에는 관측과 실패 조건을 처음부터 설계합니다. 또 최근 역할에서 완료 조건과 공유가 늦었던 점을 돌아보고 기대 결과와 완료 기준을 먼저 맞추는 행동을 기본으로 삼고 있습니다. 올세일에서도 변경 결과를 팀과 먼저 맞추겠습니다.
- **오답/대가**: 서로 다른 사건을 하나의 프로젝트인 것처럼 합치지 않는다. 팀/동료를 실패 원인으로 평가하지 않는다. 짧은 재직 질문은 메인 문서의 30초 답변으로 끝낸다.
- **꼬리**: 다음 팀에서 무엇이 달라지나요? → 첫 과제의 완료 기준, 검토자와 공유 시점을 합의하고 위험을 결과가 나기 전에 알린다.
- **출처**: [[My-FIT-Answers#12. 프로젝트 실패 / 품질 사고 (운영 사례)]], [[My-Motivation-Reasons]]의 현재 사이클.

### F3. 고객 요청과 기술적 위험이 충돌하면 어떻게 하나요?

- **의도**: 고객 문제 집념과 일정/품질의 실제 조율을 본다.
- **핵심 답변**: 요청의 목적을 먼저 확인하고 제가 이해한 내용을 다시 말해 맞춥니다. 일정이 중요해도 실패 비용이 큰 부분은 사용자 영향과 되돌릴 수 있는지를 설명하고 필수/보조 범위를 나눕니다. 프론트엔드와는 요청, 응답, 오류 조건과 변경 이력을 포함한 API 계약을 맞춥니다. 올세일에서는 화면 기능과 함께 데이터 지연/부분 실패가 고객에게 어떻게 보일지를 합의하겠습니다.
- **오답/대가**: 품질을 이유로 출시를 전부 미루거나 고객 요구를 무조건 수용하지 않는다. 범위를 줄이는 대신 남은 위험과 후속 책임을 밝힌다.
- **꼬리**: 상대가 다른 선택을 하면? → 선택지/위험을 기록하고 결정 권한이 있는 역할과 합의한다. 결정 뒤에는 관측 결과로 다시 검토한다.
- **출처**: [[My-FIT-Answers#2. 갈등, 소통 (일정, 우선순위 조율 패턴)]], [[My-FIT-Answers#3. 기획자, 비IT 소통]], [[Experience-Value-Framing]].

### F4. 낯선 PostgreSQL/BullMQ를 어떻게 배우겠나요?

- **의도**: 직접 경험의 한계와 전이 가능한 학습 방식을 본다.
- **핵심 답변**: MySQL/SQS의 정합성, 재처리와 관측 경험은 있지만 PostgreSQL/Supabase와 BullMQ 운영은 분리해 인정합니다. 회사의 버전과 실제 작업 한 개를 먼저 확인하고 공식 문서를 읽은 뒤 중복, 재시작, 권한 거부 같은 실패를 작은 범위에서 재현하겠습니다. 검토를 받아 첫 변경의 결과를 확인한 뒤 책임 범위를 넓히겠습니다. 올세일에서 필요한 학습도 첫 과제와 연결하겠습니다.
- **오답/대가**: 문서를 보유하거나 도구를 실행한 것을 운영 숙련으로 말하지 않는다. 새로운 산업/기술/단독 운영 책임을 동시에 이미 감당할 수 있다고 약속하지 않는다.
- **꼬리**: 언제 업무에 기여하나요? → 익숙한 NestJS 흐름과 관측 개선으로 시작하되 실제 우선 과제/검토 경로를 팀과 정한다. 확정되지 않은 기간을 약속하지 않는다.
- **출처**: [[My-FIT-Answers-Extended#4 빠르게 변하는 기술과 학습 방식]], [[Self-Analysis]]의 다음 역할 선택 기준.

### F5. 강점과 보완점을 한 흐름으로 설명해 주세요.

- **의도**: 객관적 자기 인식과 지속적인 책임감을 본다.
- **핵심 답변**: 문제가 생기면 재현과 실행 계획, 로그를 통해 원인을 좁히고 구조를 바꾸는 것이 강점입니다. Prisma 관계 조회와 동시 재고 갱신에서도 이 방식을 썼습니다. 더 큰 시스템이나 낯선 도구의 직접 운영 경험은 보완해야 하므로 기존 결론을 그대로 가져오지 않고 팀의 표준을 배우고 측정합니다. 올세일에서도 고객 문제를 끝까지 보되 기대 범위와 검증 경로를 먼저 맞추겠습니다.
- **오답/대가**: 완벽주의처럼 장점을 약점으로 포장하지 않는다. 규모를 부풀리지 않고 선택의 한계와 도움받을 지점을 말한다.
- **꼬리**: 과부하나 긴급 이슈가 동시에 오면? → 사용자 영향, 오류 비용, 복구/확산 가능성으로 우선순위를 정하고 도움을 요청한다. 집중 이후 회고와 회복 방식도 팀과 맞춘다.
- **출처**: [[My-FIT-Answers#1. 장단점 (한 흐름으로 묶기)]], [[My-FIT-Answers-Extended#6 긴급 이슈 동시 발생]], [[Developer-Interview-Signals]].
