# AI 시대 1인 소프트웨어 사업의 유형과 순서

AI 코딩 도구가 서버, 데이터베이스, 인증과 외부 연동까지 만들어 주면서 한 사람이 제품을 만드는 비용은 크게 내려갔다. 만드는 비용이 내려가면 병목은 다른 곳으로 옮겨 간다. 누구에게 어떻게 도달할지, 어떤 모델로 돈을 받을지, 출시 뒤 데이터를 잃지 않고 운영할 수 있는지가 사업의 성패를 가른다. 이 문서는 1인 소프트웨어 사업의 유형과, 여러 사례에서 반복되는 진행 순서를 정리한다.

## Mental model

- **만들 수 있는가보다 쓰이는가와 팔리는가를 묻는다.** 제작 속도는 모두에게 같이 빨라졌으므로 차별점이 되지 않는다.
- **유통이 제품보다 먼저다.** 올릴 곳과 첫 사용자를 만날 경로가 정해지지 않은 제품은 출시해도 발견되지 않는다([[Distribution-As-Moat|도달력이 새 해자]]).
- **서버가 있는 서비스는 구현이 일부다.** 결제를 받는 순간부터 업데이트 중에도 데이터를 잃지 않고 멈추지 않는 운영이 제품의 대부분이 된다.

## 사업 유형

| 유형 | 형태 | 첫 고객을 만나는 곳 | 주의점 |
|---|---|---|---|
| 소비자 앱 | 반복되는 불편 하나를 푸는 앱(음식 사진으로 칼로리 추정 등) | 앱스토어 검색, 숏폼, 커뮤니티 | 획득 비용과 수익 모델이 맞아야 한다([[App-Monetization-Models|앱 수익 모델]]) |
| 직업별 AI SaaS | 특정 직업의 반복 업무를 줄이는 도구(교사 채점 보조 등) | 직업 커뮤니티, 협회, 현직자 소개 | 도메인 이해 없이는 워크플로를 잘못 짚는다 |
| 기존 프로그램 애드온 | 이미 쓰는 도구에 기능 하나를 붙이는 확장, 연동 앱 | 해당 도구의 마켓플레이스 | 호스트 플랫폼 정책 변경에 취약하다 |
| 고객 한 곳 맞춤 B2B | 한 조직의 구체 업무에 맞춰 만들고 반복 요구를 공통 기능으로 제품화 | 기존 인맥, 외주 고객 | 맞춤 개발에 머물면 외주와 같아진다 |
| 특정 문서 AI 도구 | 회의록 추출, 상품 자료 정리, 사내 자료 검색처럼 한 종류의 문서만 처리 | 해당 문서를 매일 다루는 실무자 | 고객 정보와 외부 문서의 권한, 개인정보 요건 |
| 한 업무 흐름 에이전트 | 문의 응대에서 예약, 배정까지 한 흐름을 처리 | 전화와 문의가 몰리는 소규모 사업장 | 오류가 곧 고객 응대 실패라 검증과 사람 개입 경로가 필요하다 |
| 개발자 도구 | AI로 만드는 사람을 위한 코드 리뷰, 배포, 테스트 도구 | 개발자 커뮤니티, 오픈소스 | 대형 도구와 기능이 겹치기 쉽다 |

유형마다 사례로 소개되는 기업(칼로리 추정 앱, 교사 채점 도구, 홈서비스와 식당 전화 응대 에이전트, AI 코드 리뷰 도구)이 있지만, 투자 규모와 매출 수치는 확인하지 않았으므로 판단 근거로 쓰지 않는다.

## 공통 진행 순서

여러 1인 사업 사례를 모으면 다음 순서가 반복된다.

1. **팔 곳부터 정한다.** 제품보다 먼저 올릴 채널과 첫 사용자를 만날 경로를 정한다. 무료 자료로 연락처를 모으는 방식, 소규모 창작자 협업처럼 비용이 작은 유통 실험을 먼저 해 본다.
2. **창피한 첫 제품을 짧은 기간에 낸다.** 2주 안에 낼 수 있는 크기로 자르고, 완성도보다 반응을 확인하는 속도를 우선한다.
3. **자기 문제를 제품화한다.** 매주 반복하는 귀찮은 작업이 첫 제품 후보다. 자신이 첫 사용자라 요구 확인 비용이 낮다.
4. **남의 플랫폼에만 짓지 않는다.** 한 플랫폼의 정책 변경으로 제품이 한순간에 사라진 사례가 있다. 고객 연락처, 결제, 데이터를 자기 쪽에 두는 구조로 설계한다.
5. **인원이 아니라 자동화로 확장한다.** 반복 작업은 먼저 자동화하고, 필요하면 프리랜서를 쓰고, 채용은 가장 늦게 한다([[Scaling-and-Hiring|1인 제품 확장과 첫 채용]]).

### 1인 조직도로 일을 나눈다

혼자 하는 사업도 회사의 역할은 그대로 있다. PM, 개발, 디자인, 마케팅, 고객 응대(CS), 재무와 세무를 한 장의 조직도로 그리고, 지금 하는 일을 역할별로 적는다.

- 역할마다 AI나 도구에 맡길 일과 사람이 판단할 일을 나눈다. 초안 작성, 코드 생성, 반복 응대처럼 결과를 검토할 수 있는 일은 맡기고, 우선순위, 가격, 고객과의 약속, 법률과 세무 판단은 사람이 남긴다.
- 역할별로 쓰는 도구를 붙여 두면 빈 칸(아무 도구도 사람도 없는 역할)과 겹치는 도구가 드러난다. 도구를 바꾸거나 더할 때 이 표를 기준으로 삼는다.
- 업무 대부분이 디지털이라도 모든 역할을 AI로 대체할 수 있다는 뜻은 아니다. 맡긴 일의 결과를 확인하는 시간도 조직도에 적는다.

사례의 공통점 중 하나는 성공 이전의 실패 경험이다. 여러 번의 실패 뒤에 성공한 사례가 공유되지만, 이는 생존자만 보이는 선택 편향이 섞인 관찰이다.

## 사례

- **2인 팀의 버티컬 틈새:** 빠른 제품 개발자와 타깃 언어를 아는 숏폼 마케터 두 사람이 사용자 인터뷰에서 나온 불만 하나(예: 영상 생성의 카메라 구도 제어)를 먼저 해결하고, 30일 안에 첫 결제를 받아 투자보다 첫날부터의 현금흐름으로 버티는 구조다. 빅테크와 범용 기능으로 경쟁하지 않고 월 수천 달러를 낼 수 있는 특정 업종 B2B 고객을 노린다. 이런 사례에 함께 인용되는 단기간 연 반복 매출 수치는 확인하지 않았다.
- **앱 대량 출시 실험:** AI로 앱을 빠르게 많이 만들어도 순위가 매출로 이어지지 않고, 디자인, 마케팅, 유통, 가격과 수익 모델이 병목으로 남는다. 구체적인 실험 수치와 광고 회수 계산은 [[App-Monetization-Models|앱 수익 모델]]에서 다룬다. 만들기가 쉬워진 만큼 아는 도메인과의 결합이 차별화 수단으로 거론된다.

## 서버가 있는 구독형 서비스의 운영

월 구독 서비스로 월 500만 원을 벌려면 월 2만 원 구독자 250명이 필요하다. 250명이 매달 돈을 내는 서비스에서는 다음 사고가 곧 사업 위험이다.

- **데이터 전체 소실:** 백업과 복원 절차가 없으면 AI 도구도 되살릴 수 없다([[Backup-Restore|백업과 복원]]).
- **업데이트 중 컬럼 소실:** 스키마 변경은 되돌리기 어려운 작업이다. 배포 전 백업과 호환 가능한 변경 순서가 필요하다([[DB-Migration|배포 파이프라인의 DB Migration 전략]]).
- **서버 접속 불가:** 로그를 볼 줄 알면 원인을 좁힐 수 있다. 로그 보관 설정이 없으면 디스크가 차서 멈추기도 한다.
- **외부 장애:** 클라우드 리전 장애, 외부 API 장애를 자기 버그와 구분하는 방법이 필요하다.
- **개인정보:** 사용자 데이터가 쌓일수록 유출 위험과 법적 책임이 커진다. 개인정보처리방침, 이용약관, 수집 항목과 보관 기간을 출시 전에 정한다.

권고 순서는 다음과 같다.

- AI 코딩으로 제품 검증까지 간다.
- 결제 발생, 사용자 급증처럼 수익 신호가 보이면 백엔드 운영을 제대로 배우거나 고용, 파트타임, 외주로 협업한다. 언어보다 계층(애플리케이션, 데이터, 인프라)의 역할을 이해하는 것이 우선이다.
- 서버 운영 경험이 없다면 서버 없는 앱(광고 SDK, 구독 결제 대행 서비스)으로 시작하고, 서버 기능을 붙여 가며 배운다.

### 운영 도구 범주

위 사고를 알아차리고 대응하려면 범주별로 도구 하나씩은 붙여 둔다. 아래 무료 조건은 2026-09-30 각 공식 가격 페이지 기준이며 자주 바뀌므로 도입 전에 다시 확인한다.

| 범주 | 예시 | 무료 조건(2026-09-30) |
|---|---|---|
| 트래픽 분석 | Google Analytics(GA4) | 표준 버전 무료, 대기업용 Analytics 360은 유료 |
| 세션 녹화, 히트맵 | Microsoft Clarity | 무료, 트래픽 한도 없음 |
| 고객 채팅 | Crisp | Free 플랜 좌석 2개, AI와 지식베이스 제외 |
| 에러 추적 | Sentry | Developer 플랜 사용자 1명, 월 에러 5,000건 |
| 가동 감시, 로그 | Better Stack | 모니터 10개, 로그 3GB를 3일 보관 |
| 웹 호스팅 | Vercel | Hobby 플랜은 개인, 비상업 용도 한정 |
| 서버 호스팅 | Render, Railway | Render 무료 웹 서비스는 15분 무요청 시 정지, 무료 Postgres는 생성 30일 뒤 만료. Railway Free 플랜은 월 1달러 사용 크레딧 |
| DB | Supabase | Free 플랜 활성 프로젝트 2개, DB 500MB, 1주 비활성 시 일시 정지 |

- 무료 플랜은 검증 단계용이다. 결제를 받기 시작하면 상업 이용 조건(Vercel Hobby는 비상업 한정), 슬립과 일시 정지, 로그 보관 기간이 곧 서비스 품질 문제가 되므로 유료 플랜 비용을 가격에 반영한다.
- 세션 녹화와 채팅 도구는 사용자 행동과 대화 내용을 외부 서비스로 보낸다. 개인정보처리방침의 처리 위탁과 국외 이전 항목에 반영한다.

## 트레이드오프와 한계

- 유형 표는 출발점을 고르는 지도이지 성공 확률 순위가 아니다. 본인의 도메인 경험과 접근 가능한 고객이 유형 선택을 좌우한다.
- 빠른 출시는 반응 확인에 유리하지만, 결제와 개인정보를 다루는 기능까지 급하게 내면 회복 비용이 크다. 속도를 낼 범위와 신중할 범위를 나눈다.
- 플랫폼 독립은 비용이 든다. 초기에는 플랫폼의 유통력을 빌리되 고객 연락처와 결제 관계를 옮길 수 있는지 점검하는 정도로 시작할 수 있다.
- 사례 수치는 공개 인터뷰와 게시글의 주장이며 확인하지 않았다. 성공 사례만 공유되는 구조를 감안한다.
- 계정 생성과 앱 배포의 연령, 지역 조건은 서비스마다 다르므로 해당 서비스의 공식 약관을 확인한다.

## 적용 점검

- 제품을 만들기 전에 올릴 채널과 첫 사용자 10명을 만날 경로를 적었는가
- 첫 버전이 2주 안에 낼 수 있는 크기인가
- 그 문제를 나 또는 내가 아는 고객이 매주 겪는가
- 한 플랫폼이 사라져도 고객 연락처와 결제 관계가 남는가
- 결제가 시작되기 전에 백업, 복원, 스키마 변경 절차와 개인정보 문서를 갖췄는가
- 인원을 늘리기 전에 자동화와 외부 지원으로 풀 수 있는지 확인했는가
- 역할별 조직도에 AI에 맡길 일, 직접 판단할 일과 쓰는 도구를 적었는가
