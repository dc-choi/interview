# 서비스 설계 원칙 (GOV.UK)

영국 정부 디지털 서비스 조직(GDS)이 정립한 설계 원칙. 부처별로 난립하던 정부 웹사이트를 단일 서비스(gov.uk)로 통합하며 검증됐고, 공공 서비스를 넘어 어드민, B2B 도구, 일반 프로덕트 설계에 그대로 적용된다. 2012년 10원칙으로 출발해 2025년 4월 환경 영향 최소화가 추가되어 현재는 11원칙이다.

## 11원칙

| 원칙 | 핵심 |
|---|---|
| 1. 사용자 니즈 우선 | 추측 금지 — 데이터, 조사, 사용자와의 대화로 설계 |
| 2. 적게 하라 | 핵심만 직접 만들고, 나머지는 재사용 플랫폼과 API로 제공 |
| 3. 데이터 기반 설계 | 프로토타입 테스트와 분석이 의사결정에 선행 |
| 4. 단순성 추구 | 항상 그래왔다는 이유를 거부, 복잡성은 시스템 뒤로 숨김 |
| 5. 반복과 개선 | MVP → 알파 → 베타 단계 반복, 작은 실패 권장 |
| 6. 포용적 설계 | 접근성이 최우선, 미적 요소는 후순위 |
| 7. 맥락 이해 | 사용자의 환경과 능력까지 고려 |
| 8. 디지털 서비스 | 웹사이트가 아니라 끝까지 완결되는 서비스를 만든다 |
| 9. 일관성 | 디자인 시스템으로 컴포넌트와 톤을 통일 |
| 10. 투명성 | 코드, 아이디어, 실패까지 공개 공유 |
| 11. 환경 영향 최소화 (2025.4 추가) | 디지털 서비스의 에너지와 자원 소비를 줄이는 것도 설계 결정 |

## 주요 원칙의 실무 해석

### 검색엔진이 우리의 홈이다

사용자는 서비스 사이트를 직접 방문하지 않고 검색으로 진입한다. 따라서 첫 화면 디자인보다 **SEO에 전력**하는 것이 진짜 입구 설계다 ([[Content-Marketing|콘텐츠 마케팅]]의 SEO). 검색 결과 상단에 공식 페이지가 노출되는가가 서비스 도달률을 결정한다.

### 포용적 설계는 대체 수단 제공

휴대폰을 잃어버렸거나 청각 장애가 있을 수 있다는 전제로 설계한다 — 문자 인증만 제공하지 않고 음성 인증을 병행하는 식. 접근성은 마지막에 덧붙이는 체크리스트가 아니라 기능 명세의 일부다.

### 명사보다 동사

도메인 용어를 사용자 언어로 번역한다. 수수료 감면(제도 명칭)보다 수수료 비용을 지원하다(사용자가 얻는 것)가 이해도 낮은 사용자도 움직이게 한다. [[Product-Roadmap|프로덕트 로드맵]]의 Theme 작성 원칙(기능이 아니라 고객 가치 문장)과 같은 축.

### 디자인 시스템

서비스가 커지면 담당자와 페이지가 늘며 일관성이 무너진다. 컴포넌트와 톤을 묶은 디자인 시스템이 해법이고, GOV.UK 디자인 시스템은 공개돼 있어 어드민, 백오피스 기획의 참고 자료로 바로 쓸 수 있다 — 검증된 공공 표준이라 개발자 설득도 쉽다.

국내 공공 레퍼런스로는 행정안전부의 범정부 UI/UX 디자인시스템 KRDS(krds.go.kr)가 있다. 2025년 1월 정식 개시됐고 디자인 원칙, 스타일, 컴포넌트, 기본 패턴과 서비스 패턴을 디자인 토큰 기반으로 정리한다. 2026-09 확인 기준으로 디지털 정부서비스 UI/UX 가이드라인(2025년 8월판), Figma 라이브러리 v1.0.0, HTML Component Kit v1.1.0(2026-01 갱신)과 React, Vue Storybook을 제공한다. 한국어 공공 서비스의 컴포넌트와 서비스 패턴을 학습하는 교재와 어드민, 백오피스 기획의 참고 자료로 쓸 수 있다. 다만 공공 서비스 기준이라 브랜드 표현과 상업 서비스의 전환 설계는 따로 판단하고, 자체 점검표는 HWP로 배포된다.

#### 반복되는 판단을 공동 기준으로 남긴다

디자인 시스템은 컴포넌트 파일뿐 아니라 사용 조건, 선택 이유와 예외를 함께 관리하는 체계다. 같은 문제를 매번 다시 논의하는 비용을 줄이되, 고객과 사업 조건이 바뀌면 기존 결정을 재검토할 수 있어야 한다.

- **도입 신호:** 여러 화면과 담당자가 같은 문제를 반복해서 해결하며 결과나 설명이 달라진다. 먼저 화면, 코드와 업무 흐름을 비교하고 실제 중복을 찾는다.
- **최소 구성:** 재사용할 컴포넌트나 패턴, 해결하는 사용자 문제, 사용하지 말아야 할 조건, 접근성 점검과 담당자를 함께 남긴다.
- **검증 범위:** GOV.UK는 여러 서비스에서의 유용성, 기존 패턴과의 차이, 대표 사용자와 장애인 사용자를 포함한 사용성, 일관성과 다양한 맥락의 적용 가능성을 기여 기준으로 둔다. 다른 조직의 검증이 우리 고객에게도 그대로 유효한지는 별도로 확인한다.
- **운영 제안:** 공통 패턴은 기본 선택으로 삼고 예외에는 이유와 검증 결과를 남긴다. 반복되는 예외는 기준을 고칠 신호다. 사용자 과업 완료, 오류와 구현 시간을 함께 보며 효과를 평가한다.
- **작은 팀의 시작점:** 반복이 확인된 패턴 몇 개부터 문서와 코드로 맞춘다. 아직 자주 바뀌는 가설까지 표준으로 고정하면 유지 비용과 실험 제약이 더 커질 수 있다.

### 적게 하라

모든 것을 직접 만들지 않는다. 공통 기능은 재사용 가능한 플랫폼과 API로 제공하고 각 팀은 고유 문제에 집중한다 — 플랫폼 팀, 공통 컴포넌트 사고의 원형.

기능 단위에서도 같은 원칙이 적용된다 — 혹시 모르니까 만들어 둔 기능은 주머니 열 개 달린 건빵바지처럼 실제로는 기본 주머니 두 개만 쓰인다. 기능의 기본값은 추가가 아니라 **필요성 증명**이고, 비즈니스 목표와 고객 UX 양쪽에서 효과를 검증하지 못한 기능은 제거도 설계 결정이다. 미사용 기능도 공짜가 아니다 — 화면 복잡도, 유지보수, 테스트, 마이그레이션 비용을 계속 낸다.

## 정보 서비스의 확인 범위와 갱신 책임

정보를 찾아주는 서비스는 무엇을 확인해 주는지부터 정한다. 시설의 연락처를 확인했다고 특정 날짜의 예약 가능 여부까지 확인한 것은 아니며, 지원사업 후보를 추천했다고 개별 신청자의 자격이 확정되는 것도 아니다.

다음은 정보 탐색 서비스의 기획 자료에서 추출한 설계 질문이다. 운영 성과가 검증된 공식 기준으로 보지는 않는다.

| 질문 | 설계에 남길 내용 |
|---|---|
| 무엇을 확인했는가 | 출처, 확인 시점, 적용 대상과 확인한 조건 |
| 무엇이 아직 불명확한가 | 미확인 조건, 추가 문의 경로, 최종 판단 주체 |
| 출처가 충돌하면 어떻게 하는가 | 일반 안내와 개별 공고의 대상, 적용 시점, 예외 조건 대조 |
| 누가 최신 상태를 유지하는가 | 갱신 담당자, 변경 빈도와 오정보 피해에 맞춘 재확인 주기 |
| 잘못된 정보는 어떻게 고치는가 | 오류 신고, 정정, 만료 또는 비공개 처리 경로 |

한 페이지를 오늘 열어봤다는 이유로 모든 항목에 오늘 기준으로 유효하다고 표시하지 않는다. 오래된 정보의 노출 여부는 정보의 용도와 피해 가능성에 따라 정하고, 확정할 수 없는 조건은 사용자에게 확인 경로를 제공한다. 기술적인 관측 시각과 가용성 표현은 [[Content-Availability-Data-Contract|콘텐츠 가용성 데이터 계약]]으로 연결한다.

## 면접 체크포인트

- 어드민, 백오피스 설계 질문에 GOV.UK 디자인 시스템 같은 공개 표준을 참고했다는 답은 근거 있는 설계 결정의 좋은 예가 된다.
- 접근성 질문에 포용적 설계 원칙으로 — 대체 수단(인증 채널 다중화)은 장애 대응 설계와도 연결된다.
- 적게 하라 원칙은 공통 플랫폼화, API 우선 설계와 연결해 말할 수 있다.
- 단순성 원칙의 한 줄 — 사용자에게 단순해 보이려면 복잡성을 없애는 게 아니라 시스템 뒤로 옮겨야 한다. 백엔드가 무게를 지는 이유.
