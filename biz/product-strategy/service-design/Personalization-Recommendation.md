# 개인화와 추천

## 개인화 vs 커스터마이징

| 구분 | 개인화 (Personalization) | 커스터마이징 (Customizing) |
|---|---|---|
| 주체 | 시스템 — 고객이 요청하지 않아도 자동으로 맞춤 | 고객 — 직접 UI나 서비스를 설정 |
| 입력 | 행동 데이터 분석 | 명시적 설정값 |

상반된 개념이 아니라 같은 화면에서 동시에 쓰일 수 있다 (추천 피드 + 관심 카테고리 직접 설정).

## 추천의 3요소

- **추천 대상** — 상품, 기획전, 카테고리. 무엇을 추천하는가
- **추천 범위** — 전체 풀 vs 수동 등록된 후보군
- **추천 로직** — 고정 추천(사람이 지정) vs 자동 선별(알고리즘)

## 데이터 신호와 처리 방식의 5가지 예

아래 표는 한 커머스 사례를 설명하는 휴리스틱이며 보편적인 성숙도 모델이나 필수 도입 순서가 아니다. 여러 유형을 동시에 사용할 수 있고, 우선순위는 제품 목표, 동의와 데이터 품질, 증분 효과와 운영 비용으로 결정한다.

| 유형 | 데이터 | 활용 | 한계 |
|---|---|---|---|
| 저장 신호 | 고객이 저장한 데이터 (위시리스트, 장바구니) | 명시적 관심사 기반 노출 | 주문내역 재노출은 박탈감 유발 — 이미 산 상품은 제외 |
| 프로필 | 동의받은 인구통계와 프로필 | 기본 타겟팅 | 목적 제한, 대표성, 개인정보보호 검토 필요 |
| 최근 행동 | 쿠키 기반 행동 (최근 본 상품) | 세션 맥락 추천 | 멀티 디바이스에서 휘발 — 서버 저장으로 보완 |
| 연관 행동 | 함께 구매하거나 본 기록 | 협업 필터링형 추천 | 입력 데이터 오염, 관심사 변화 미반영 |
| 실시간 이벤트 | EBM (Event Based Marketing) | 행동에 즉각 대응 | 효과적인 시나리오 설계가 어려움 |

### 커머스 확장 방향: 구매 여정의 축약

커머스에서는 구매 여정의 일부를 줄이는 것을 확장 방향 중 하나로 볼 수 있다. IoT가 소모품 교체 시점을 감지하고, 대화형 인터페이스가 탐색을 돕고, 간편 인증과 결제가 마찰을 줄이는 식이다. 추천이 구매 대행으로 확장될수록 사용자 통제, 설명, 취소와 오류 복구가 더 중요해지며 수익 개선이 자동으로 보장되지는 않는다.

## 대화 기억, 추천과 광고의 경계를 나눈다

대화형 개인화는 프로필과 클릭 이력 외에 사용자가 직접 말한 선호와 대화 문맥을 입력으로 쓸 수 있다. 다만 그 입력을 답변에 사용하는 것과 다른 서비스의 콘텐츠나 광고 추천에 사용하는 것은 서로 다른 제품 정책이다.

2026-10-22 대조한 Meta의 공개 발표는 이 구분을 보여준다.

- **2025년 1월 발표:** Meta AI는 1:1 대화에서 일부 정보를 기억하고 사용자가 기억을 삭제할 수 있다고 안내했다. 당시 미국과 캐나다의 제공 범위를 명시했으므로 모든 지역과 계정에 같은 기능이 있다는 근거로 쓰지 않는다. 프로필, 콘텐츠 이용과 기억을 조합한 추천도 사례로 제시했다.
- **2025년 10월 발표:** 생성 AI와의 텍스트/음성 상호작용을 콘텐츠와 광고 추천 신호로 활용하는 변경을 2025-12-16부터 대부분 지역에 적용한다고 안내했다. 같은 Accounts Center에 추가한 계정 간 정보 이용과 민감 주제의 광고 활용 제외를 구분했다. 실제 계정의 적용 여부와 현재 정책은 별도로 확인한다.

따라서 개인화된 추천이라는 이유만으로 광고 이해관계가 없다고 판단하지 않는다. 무료 제공, 개인화와 광고 수익화는 각각 확인해야 할 축이다.

다음은 사업 판단에 적용할 검토 기준이다. 기억이 쌓일수록 서비스의 효용과 다른 서비스에서 다시 설정할 비용이 커질 수 있지만, 지속적인 경쟁 우위가 생겼는지는 별도 가설이다. 반복 사용, 추천 만족도와 전환율을 측정하고 기억의 수정, 삭제와 이전 가능성도 확인한다. 개인의 좋은 사용 경험이나 기능 발표만으로 시장 독점, 특정 종목의 수익률 또는 기존 검색 서비스의 소멸을 결론 내리지 않는다.

## 운영 함정

- **데이터 오염** — 오픈 전 테스트 주문 데이터가 연관 분석에 섞이면 무관한 상품이 함께 구매한 상품으로 고정 노출된다. 입력 데이터 검증과 재학습 주기가 운영 요건이다.
- **유사 상품 도배** — 한 번 보거나 산 상품과 유사한 것만 반복 노출하면 추천 효용이 떨어진다. 정확도와 탐색 다양성의 트레이드오프.
- **이미 구매한 상품의 재추천** — 명시적 제외 규칙이 필요하다 (소모품 재구매는 예외).
- 알고리즘이 자동화돼도 무시할 데이터와 집중할 고객층을 가르는 판단은 사람의 몫으로 남는다.

## 개인화의 증분 효과를 검증한다

개인화 기능을 배포한 사실과 구매나 이용 성과가 개선된 사실은 구분한다. 추천 모델을 비교할 때는 측정 가능한 업무 목표와 가설을 먼저 정하고, 기존 추천을 유지하는 대조군과 변경된 추천을 받는 실험군을 비교한다.

- 클릭률, 시청 시간이나 구매 금액처럼 가설에 맞는 지표를 고른다. 클릭 증가만으로 매출 개선을 결론 내리지 않는다.
- 시작 전에 사용자 분할 방식과 실험 기간을 정하고, 실행 중 분할 비율을 임의로 바꾸지 않는다.
- 가설과 무관한 화면, 지연 시간, 필터와 정렬 변경은 비교를 흐릴 수 있다. 행사와 마케팅 캠페인의 영향도 함께 점검한다.
- 표본 규모와 통계적 불확실성을 확인한 뒤 판단한다. 짧은 기간의 수치 상승만으로 개인화의 효과를 확정하지 않는다.
- 추천 영역의 지표만 보지 않는다. 추천 경로의 담기가 늘어도 검색이나 카테고리 같은 다른 경로의 담기가 줄었다면 기존 행동이 자리만 옮긴 것일 수 있으므로, 서비스 전체의 담기 수와 구매로 순증을 확인한다.
- 가설의 연결 고리를 단계별로 확인한다. 전환율 상승이 장바구니 금액을 키워 사용자당 매출을 올린다는 가설이라면 장바구니 금액과 구매 빈도를 따로 보고, 효과가 예상과 다른 경로로 나타났는지 확인한다.

이 절차는 Amazon Personalize의 A/B 테스트 지침을 제품 판단에 적용한 것이다. 운영 적용에서는 효과 측정과 별도로 데이터 수집, 추천 제공과 검수에 드는 비용을 계산해 확대 여부를 정한다.

### 사례: 신선식품 커머스의 추천 A/B (발표 기준, 2021)

컬리는 규칙 기반으로 운영하던 추천 영역에 Amazon Personalize를 A/B 테스트로 붙이고 핵심 지표를 장바구니 전환율로 정했다. 실험군은 당시의 HRNN-Metadata 레시피를 썼는데, 2026-10-14 확인한 공식 문서 기준으로 이 레시피는 더 이상 제공되지 않는 legacy 레시피이며 AWS는 User-Personalization 레시피를 권장한다.

- 추천 영역의 장바구니 전환율은 실험군 20.8%, 기존 규칙 기반 5.8%로 약 3.6배였다.
- 서비스 전체로 보면 추천 경로의 담기는 38% 늘고 검색과 카테고리 경로의 담기는 2~7% 줄어, 전체 담기 이벤트는 약 2% 늘었다.
- 결제한 장바구니 금액은 통계적으로 유의한 차이가 없었다. 대신 결제 횟수가 약 2% 늘어 매출이 약 1.3% 증가했다. 장바구니가 커질 것이라는 가설은 맞지 않았고 구매 빈도가 늘었다.
- Personalize의 실시간 추천 campaign은 최소 프로비저닝 TPS를 기준으로, 요청이 그보다 많으면 실제 TPS를 기준으로 과금된다. 클릭이 없을 때는 캐시한 추천을 재사용해 호출을 줄이고, 추천 API 지연 지표(CloudWatch의 `GetRecommendationsLatency`)가 나빠지지 않는 선까지 최소 TPS를 단계적으로 낮춰 비용을 초기의 절반 이하로 줄였다.

## 추천 AI의 윤리: FAT

딥러닝 기반 추천은 인간이 과정을 평가하기 어려운 알고리즘을 단시간에 만들어낸다 — 블랙박스 문제. 그래서 공정성(Fairness), 책임감(Accountability), 투명성(Transparency)의 FAT 원칙이 추천 시스템의 운영 요건으로 들어온다.

| 원칙 | 추천에서의 문제 | 대응 |
|---|---|---|
| 공정성 | 광고비 많은 상품, 마진 높은 상품으로 편향된 추천 | 고객 유용성 기준의 중립 평가, 컴플라이언스 절차 |
| 책임감 | 민감 콘텐츠가 알고리즘을 타고 노출 | 카테고리별 포커스 그룹, 노출 조정 |
| 투명성 | 추천 근거 불명 (왜 이게 나에게?) | 추천 이유를 사용자에게 명시 — 상호 신뢰 장치 |

실무 장치로는 항의 버튼(이상 결과를 사용자가 신고 — 피드백 루프), 핵심 가치를 정의하는 포커스 그룹, 윤리 시나리오 학습이 제안된다. 주의할 역설 하나 — **추천이 정확할수록 위험할 수 있다.** 본인이 밝히지 않은 사실(임신 등)을 추천 결과가 주변에 노출하는 사례처럼, 정밀한 프로파일링은 그 자체가 프라이버시 침해가 된다.

## 백엔드 관점

- 최근 본 상품을 쿠키(디바이스 종속)에 둘지 서버(계정 종속)에 둘지는 멀티 디바이스 일관성의 저장 위치 결정 문제다.
- 연관 추천의 배치 집계와 event trigger의 실시간 처리는 신호의 우열보다 반영 시점과 파이프라인 비용이 다른 선택지다.
- 추천 모델의 출력과 실제 노출 사이에는 서빙 시점 필터(품절, 이미 구매, 연령 제한)라는 비즈니스 규칙 계층이 있다.
- 투명성 요건은 API 설계로 내려온다 — 추천 응답에 추천 이유 메타데이터를 함께 내리는 구조, 신고(항의 버튼) 이벤트를 모델 개선으로 되돌리는 피드백 파이프라인.

## 면접 체크포인트

- 추천 기능은 단계표보다 제품 목표와 현재 신호부터 본다. 지금 가능한 baseline과 다음 개선에 필요한 수집을 구분해야 현실적인 답이 된다.
- 알고리즘 고도화 이전에 제외 규칙(이미 구매, 품절, 테스트 데이터)이 추천 품질의 체감을 좌우한다.
