# 결제 세무 증빙

결제 승인, 세무 증빙 발급, 매출 신고는 서로 다른 업무다. 카드나 PG를 통해 거래 자료가 전달되어도 사업자의 세무 신고가 모두 끝나는 것은 아니다.

## 증빙의 종류를 구분한다

| 증빙 | 구분할 내용 |
|---|---|
| 카드 매출전표 | 카드 거래 사실, 승인과 취소 자료 |
| 현금영수증 | 현금성 거래, 소득공제용/지출증빙용, 발급과 취소 |
| 세금계산서 | 부가가치세 과세 거래의 공급가액과 세액 |
| 계산서 | 부가가치세 면세 거래의 공급 내용 |

세금계산서와 계산서는 과세/면세 구분이 다르다. 영수증 대신 계산서를 발급할 수 있는 조건과 동일 거래의 증빙 처리도 업종과 거래 조건에 따라 확인한다. 현금영수증을 B2C 전용으로 설명하면 사업자의 지출증빙용 발급을 놓친다.

## 현금영수증의 의무와 자진 발급

현금영수증 가맹점 가입 의무와 개별 거래의 발급 의무를 구분한다. 가입 대상은 사업자 형태, 업종과 수입 기준 등으로 판단한다.

국세청 안내 기준으로, 현금영수증 의무발행 업종의 건당 10만원 이상 현금 거래는 부가가치세를 포함한 거래 금액으로 판단하며 고객의 요청이 없어도 발급 대상이다. 일반적인 고객 요청에 따른 발급과 이 의무발행 규칙은 서로 다른 조건이다. 업종은 실제 영업 내용과 해당 시점의 목록으로 확인한다.

거래 상대방의 인적 사항을 모르는 경우의 무기명 자진 발급에는 현금을 받은 날부터 5일 이내라는 안내가 있다. 착오나 누락 이후 자진 신고/발급에 따른 가산세 감면 기한과 혼동하지 않는다. 식별 정보를 받지 못했다는 이유로 발급 대상 거래를 누락시키지 않는다.

PG를 이용한 계좌이체나 가상계좌 거래는 계약 설정에 따라 자동 발급될 수 있다. 자동 발급 요청과 국세청 처리 결과는 같은 상태가 아니므로 승인 번호, 발급 일시와 처리 상태를 조회할 수 있어야 한다. 휴대폰 결제와 상품권도 실제 발급 주체를 확인한다.

## 전자 증빙 의무는 업종 이름만으로 판단하지 않는다

2026-10-01 국세청 안내 확인 기준, 전자세금계산서는 법인사업자와 직전 연도 사업장별 과세/면세 공급가액 합계가 기준 이상인 개인사업자에게 발급 의무가 적용된다. 개인사업자의 기준은 2024년 7월부터 8천만원이며 적용 기간과 통지, 수정 신고 조건도 확인해야 한다.

면세 거래의 전자계산서는 별도 제도이며 법인 여부와 사업장별 총수입금액 등의 기준을 확인한다. 의료업/약사업이라는 이유만으로 매출액과 관계없이 전자세금계산서 의무가 생긴다고 일반화하지 않는다. 현금영수증 가입 의무, 과세 여부와 전자 발급 의무를 섞으면 잘못된 판단을 하게 된다.

세금계산서는 공급 시기 발급이 원칙이다. 월 합계 발급 등 허용된 특례에서는 다음 달 10일 기한이 적용될 수 있지만 모든 거래의 공통 발급일은 아니다. 전자 증빙의 발급일과 국세청 전송일도 구분한다. 지연 발급과 미전송의 제재는 유형별로 다르므로 하나의 가산세율로 저장하지 않는다.

## 공급자 금액 필드와 증빙의 시간차

2026-10-02 토스페이먼츠 복합 과세 계약의 계산 예시는 `totalAmount = taxFreeAmount + suppliedAmount + vat`이며 vat는 과세 금액을 11로 나눈 후 반올림한다. 부분 취소 요청에는 취소분의 면세 금액을 따로 지정한다. 세금 처리 가이드는 `Payment.taxFreeAmount`가 최초 면세 금액을 유지하고 잔여 면세 금액은 `balanceAmount - suppliedAmount - vat`로 계산한다고 설명한다. 그러나 같은 날 API reference는 부분 취소 때 taxFreeAmount도 변한다고 서술해 공식 문서 사이에 차이가 있다. 실제 MID/API 버전의 부분 취소 응답으로 확인하기 전에는 어느 설명도 모든 응답의 공통 불변조건으로 확정하지 않는다.

이 의미는 POS 프론트 SDK의 `supplyValue`와 다르다. 이름이나 예제의 세율만 보고 필드를 공통 모델에 직접 매핑하지 않고 포함 금액과 반올림/절사 계약을 대조한다. 영세율과 면세의 세법상 분류도 공급자의 편의 필드만으로 같게 취급하지 않는다.

토스페이먼츠 결제에 연결해 발급한 현금영수증은 결제 취소에 따라 정정되는 반면, 별도 현금영수증 API로 발급한 거래는 상점이 취소 API를 호출해야 한다. NICEPAY 별도 현금영수증 API도 발급/취소 요청과 국세청 완료를 구분하며 영업일 D+2 조회 조건을 안내한다. 부분 취소는 취소분의 공급가액, 부가세, 면세와 봉사료를 함께 전달하는 별도 계약이다. 신청 직후의 요청 상태와 국세청 처리 상태를 나누어 본다. 현재 API reference는 처리 결과 확인까지 1~2일이 걸릴 수 있다고 안내하므로 다음 날 완료를 보장하지 않는다. 시험 환경에서 실제 매출전표/현금영수증 데이터를 받았다고 주장하지 않는다.

지갑 복합결제의 매출전표는 카드 사용분만 포함할 수 있다. 머니, 포인트와 쿠폰의 증빙/소득공제 주체도 지갑별로 다르므로 전체 주문액을 카드 전표 하나로 대사하지 않는다. 원결제 구성과 증빙별 금액을 연결해 중복 발급과 누락을 확인한다.

## 환불과 정정의 데이터 계약

결제 취소가 증빙 취소까지 자동으로 처리하는지 제공자와 수단별로 확인한다. 직접 발급한 현금영수증과 PG가 발급한 영수증은 취소 경로가 다를 수 있다. 세금계산서는 사유에 맞는 수정 발급 절차가 필요하다.

증빙은 다음처럼 결제와 별도의 레코드로 관리할 수 있다. 아래는 설계 예시이며 법정 전송 스키마가 아니다.

| 데이터 | 용도 |
|---|---|
| 주문/결제/증빙 식별자 | 원거래와 발급 건 연결 |
| 유형, 공급가액, 세액, 면세금액 | 과세 구분과 금액 대사 |
| 발급 요청/승인/취소 상태 | 외부 결과와 내부 처리 진행 분리 |
| 원발급 참조, 정정 사유와 일시 | 중복 발급 방지와 변경 이력 |

부분 환불은 원거래 금액과 과세 구분을 보존해 계산한다. 환불 완료, 증빙 정정 완료와 고객에게 알림 완료를 별도 사건으로 남기면 한 단계 실패를 복구할 수 있다. 민감한 고객 식별 정보는 필요한 범위만 보관하고 로그에서 제외한다.
